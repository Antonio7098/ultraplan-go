# Dimension 18.06: Leak and Quiescence Verification

## Purpose

Study how runtimes prove that completed runs release owned tasks, observers, timers, processes, connections, and retained references.

## Steps

1. Define quiescence for each execution path.
2. Inventory runtime-owned resources and their lifetime signals.
3. Inspect leak detectors, counters, profiles, and teardown assertions.
4. Test success, failure, cancellation, timeout, panic, and observer abandonment.
5. Determine how CI detects and reproduces leaks.

## Evidence to Capture

- Task, goroutine, thread, and process ownership
- Timer, subscription, connection, and reference cleanup
- Leak tests and profiling hooks
- Shutdown and quiescence barriers
- CI repetition and diagnostic artifacts

## Questions

1. What must be absent or stable when a run becomes quiescent?
2. Can terminal completion precede resource release?
3. Which resources may intentionally outlive a run?
4. How are slow leaks distinguished from expected caching?
5. Can a failed leak test identify the owning run and resource?
