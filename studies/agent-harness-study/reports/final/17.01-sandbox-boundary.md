Note on comparability: only agent-framework both executes model-generated code and owns isolation machinery. opa is a policy engine whose "agents" are human-authored Rego policies evaluated in-process. openhands is a frontend that never executes tool code at all — it addresses external runtimes. Each rating measures the dimension applied to the system's own trust domain, not agent safety per se; the comparison below accounts for this explicitly.

## Executive Summary

None of the three sources implements *a* sandbox. The central finding is that every mature system studied here treats the sandbox boundary as a **spectrum of tiers** — language interpreter, wasm/micro-VM guest, container, remote service, or nothing-plus-procedure — and the real architectural work lies in three places: centralizing "what code may touch" into one auditable control plane, choosing which tier is the *default*, and being explicit about which tiers are not actually walls.

agent-framework (8/10) ships the fullest spectrum: five execution environments with per-environment threat models, tested boundary logic, and enforced honesty about non-boundaries. opa (7/10) draws a coherent language-level capability boundary around in-process policy evaluation with an opt-in Wasm escape hatch — undermined by permissive defaults and uneven enforcement across ingestion paths. openhands (7/10) consumes boundaries owned elsewhere, and shows that a tier that executes no tool code still owns real boundary work: credential lifecycle, proxy-mediated addressing, lifecycle state machines, and CI-enforced traffic discipline — while shipping one mode (local `uvx`) with no technical boundary at all.

The clearest cross-cutting weakness mirrors the 08.01 finding from the other direction: **the strongest available substrate is frequently not wired by default**, and where defaults are open (opa egress, environment exposure; openhands local mode), the burden of restriction silently shifts to operators and integrators who rarely know the knobs exist.

## Core Thesis

Sandbox maturity is not measured by whether a system has a strong isolation tier — all three sources have access to one (wazero VM, Hyperlight micro-VM, cloud sandboxes, Docker). It is measured by whether the *weak* tiers are labeled, whether enforcement is consistent across every path code can enter, and whether the boundary's configuration surface makes the safe choice the default choice. The gap between agent-framework's 8 and opa/openhands' 7s is almost entirely composed of defaults and consistency, not mechanism: agent-framework denies OS calls by default in Monty, drops all container capabilities by default, and throws unless the developer types `acknowledgeUnsafe`; opa allows any host by default and compiles bundle-delivered policies with a weaker compiler than ad-hoc queries; openhands runs the agent with full user privileges locally and mitigates with documentation. A second-order finding: boundaries enforced at *static* time (compilation, AST validation, CI scans) age better than runtime checks because they fail fast, leave audit trails, and cannot be bypassed by inputs that arrive after the check was written.

## Approach Models

The three systems occupy different positions in the same design space, and each spans multiple isolation tiers. Grouping by *where the wall lives*:

### Tier 1 — Structural memory isolation (micro-VM / Wasm guest)

agent-framework's Hyperlight packages run model-generated Python/JS inside a hypervisor/WASM guest where the only host contact is staged `/input` copies, captured `/output` files, registered FFI tools, and allow-listed HTTP domains (`python/packages/hyperlight/agent_framework_hyperlight/_execute_code_tool.py:1025-1066`; .NET wiring in `dotnet/src/Microsoft.Agents.AI.Hyperlight/Internal/SandboxExecutor.cs:174-228`). opa's `-t wasm` target achieves the same shape differently: policy compiles to a module whose only imports come from an `env` glue module, with real side effects behind a wazero host-module dispatcher (`internal/wasm/sdk/internal/wasm/vm.go:71-79`; `glue.go:15-23`). Convergent properties despite different stacks: imports-as-capabilities, ABI version gating (`vm.go:106-114`), and reduced feature coverage as the price of safety (`http.send` unsupported natively in opa Wasm, `docs/docs/wasm.md:22-27`).

### Tier 2 — Kernel/container isolation

agent-framework's `DockerShellExecutor` constructs runs with restrictive-by-default flags — `--cap-drop ALL`, `--security-opt no-new-privileges`, no network, 512 MiB / 256 pids, tmpfs, optional read-only root — and asserts them in unit tests (`dotnet/src/Microsoft.Agents.AI.Tools.Shell/DockerShellExecutor.cs:62-83,360-418`; tests `DockerShellExecutorTests.cs:17-45`). openhands packages the upstream agent-server image as non-root with tini, pins `runAsNonRoot: 10001` and default-off RBAC in Helm, and adds an entrypoint that refuses to start automation without a generated session key (`docker/Dockerfile:73,151-168,170`; `helm/agent-canvas/values.yaml:170-180`; `docker/entrypoint.sh:175-218`). Both configure a boundary whose actual enforcement lives in the kernel — appropriate layering, but it means neither can guarantee what the daemon does.

### Tier 3 — Language-level containment in-process

Two implementations, one idea: deny I/O primitives at the language surface and mediate everything else. opa's Rego has no exec/file primitives; everything a policy can do must be a declared builtin admitted through the compiler's capabilities map (`v1/ast/compile.go:2038-2050`), with ambient authority funneled through one narrow `BuiltinContext` (`v1/topdown/builtins.go:36-60`, assembled at `v1/topdown/eval.go:1058-1085`). agent-framework's Monty intercepts OS functions in its Rust bridge and resumes them as `PermissionError`s, with mounts (`read-only/read-write/overlay`) and resource limits strictly opt-in (`python/packages/monty/agent_framework_monty/_monty_bridge.py:262-267,238-243`). Both share fate with the host process; both rely on the executed language lacking reach rather than the OS withholding it.

### Tier 4 — No technical boundary, procedural compensation

Three explicit instances: agent-framework's `LocalShellExecutor` declares human approval the real boundary and refuses to construct without `requireApproval` or `acknowledgeUnsafe: true` (`LocalShellExecutor.cs:43-50,339-347`); `LocalCodeAct` documents itself as *not a sandbox* in XML docs and the assembly description (`LocalCodeActProvider.cs:19-30`; csproj:25). openhands local mode spawns the agent-server via `uvx` with full user privileges and says so plainly, offering firewalls and key hygiene as compensations (`electron/main.mjs:593-616`; `docs/SELF_HOSTING.md:8-10,50-58`). opa's *default posture* belongs here too even though mechanism exists: unset `AllowNet` permits any host and `opa.runtime().env` dumps the whole environment (`v1/ast/capabilities.go:94-96`; `v1/runtime/info/info.go:47-58`).

### Tier 5 — Delegated execution (boundary owned elsewhere)

openhands cloud conversations provision per-conversation sandboxes whose lifecycle the frontend observes as a five-state union (`src/api/cloud/sandbox-service.types.ts:1-21`) and reaches only through a server-side proxy envelope with ephemeral session keys (`src/api/cloud/proxy.ts:18-39`). agent-framework's hosted `code_interpreter` similarly serializes a descriptor — `{"type": "auto"}` container — and cedes execution entirely to the service (`python/packages/foundry/agent_framework_foundry/_tools.py:45-48`). Neither source can verify the guarantees it depends on; both compensate with contract-shaped payloads and client-side discipline.

## Pattern Catalog

### P1. Centralized capability control plane

- **Problem:** Scattered permission decisions drift, become unauditable, and get bypassed by paths added later.
- **Demonstrated by:** All three, most explicitly opa: one JSON-described `Capabilities` structure governs available builtins, language features, Wasm ABI versions, and the network allowlist; the older `WithUnsafeBuiltins` option was deprecated in its favor (`v1/ast/capabilities.go:84-101`; `v1/ast/compile.go:596-602`), and 100+ generated per-release snapshots make the power set diffable and pinnable (`capabilities/vX.Y.Z.json`; workflow at `cmd/build.go:220-256`). agent-framework shapes the same idea per-backend: tools, mounts, domains, and limits are constructor options feeding a config fingerprint. openhands gates the tool surface through payload fields (`browser_tool_set`, `task_tool_set`) driven by settings and server-advertised `usable_tools` (`src/api/agent-server-adapter.ts:114-118,627-640`).
- **Why it works:** "What can this code touch?" becomes answerable by reading one artifact; consolidation eliminates divergent enforcement paths by construction.
- **Copy when:** Always — this is the load-bearing wall of every source.
- **Risky:** When the plane exists but not every ingestion path reads it (see opa's bundle seam below).

### P2. Static-first enforcement

- **Problem:** Runtime checks are bypassable, expensive, and discovered late.
- **Demonstrated by:** opa rejects unknown/banned builtins, recursion, and disabled `print()` at compile time — `print()` calls are literally erased from the module unless enabled (`v1/ast/compile.go:1959,7558-7570,1290-1316,2685-2692`), and the server's ad-hoc query ban on `http.send` is a compile-time unsafe-builtin map with regression tests (`v1/server/server.go:104,996`; `v1/server/server_test.go:1264`). agent-framework validates model-generated code with an AST validator subprocess before execution (`CodeValidator.cs:16,55-67`). openhands enforces cross-boundary traffic discipline as a CI test that fails on raw axios/fetch outside three allow-listed files (`src/api/no-direct-agent-server-calls.test.ts:30-60`).
- **Why it works:** Violations fail fast with precise locations; there is no input sequence that arrives "after" the check.
- **Copy when:** The forbidden behavior is expressible statically — imports, function names, call-graph cycles, traffic routes.
- **Risky:** Compile-time posture must match *every* ingestion path, or it manufactures false confidence (opa's bundles skip exactly this check, `v1/plugins/bundle/plugin.go:627`).

### P3. Host-mediated I/O through a single chokepoint

- **Problem:** If guests/policies/agents can touch the host through multiple channels, each becomes an attack surface to audit forever.
- **Demonstrated by:** opa funnels all ambient authority through `BuiltinContext` (context, seed, clock, caches — no fds, no process handles) and, in Wasm, through one registered host module + dispatcher (`v1/topdown/builtins.go:36-60`; `internal/wasm/sdk/internal/wasm/bindings.go:33`). agent-framework stages inputs via link-rejecting copies and returns outputs as validated attachments — guests never see host paths (`_execute_code_tool.py:674-682,817-848`). openhands forces all sandbox traffic through typed clients behind the cloud-proxy envelope, architecturally enforced by P2's CI scan (`src/api/cloud/proxy.ts:18-39`; `bash-service.api.ts:82-118`).
- **Why it works:** One place to log, rate-limit, test, and evolve.
- **Copy when:** Always.
- **Risky:** Chokepoints invite silent widening — opa's global `RegisterBuiltinFunc` registry lets any linked Go package inject new host reach with no central review point (`v1/topdown/builtins.go:88-91`).

### P4. Re-verify authority at every trust transition

- **Problem:** Authority checked once can be invalidated when the underlying target changes between check and use.
- **Demonstrated by:** opa re-applies the `AllowNet` host check inside the HTTP client's redirect hook, closing the cross-host redirect bypass most allowlists miss (`v1/topdown/http.go:402-423,647-648`; tests `http_test.go:793,3696`). agent-framework defends output reads against TOCTOU swaps with `O_NOFOLLOW` plus fstat inode-identity verification (`_execute_code_tool.py:685-715`), and rejects symlinks/junctions at input staging separately (`_copy_path`, `_execute_code_tool.py:639-671`). openhands intersects the server-reported editor capability with the origin's own route table so the UI never renders a workspace it has no route to (`src/utils/vscode-origin.ts:1-22`).
- **Why it works:** Time-of-check/time-of-use and redirect-class attacks exploit exactly the gap between two observations of the world.
- **Copy when:** Any allowlist governs a resource that can change identity mid-operation: URLs that redirect, files that get swapped, origins that embed other origins.
- **Risky:** Overkill for immutable resources; adds syscall/code complexity per read.

### P5. Restrictive-baseline container defaults, tested at construction

- **Problem:** Secure container configs are easy to omit flag-by-flag and impossible to verify by reading prose docs.
- **Demonstrated by:** agent-framework defaults every flag defensively and locks the baseline in unit tests asserting cap-drop, no-new-privileges, read-only, memory, and pids (`DockerShellExecutor.cs:25-37,376-401`; `DockerShellExecutorTests.cs:17-45`), while documenting honestly that the boundary is "best-effort" and recommending gVisor/Kata for high stakes (`DockerShellExecutor.cs:20-36`). openhands reaches the same destination from packaging: non-root user, tini, pinned security contexts in Helm values (`docker/Dockerfile:73,170`; `helm/agent-canvas/values.yaml:170-180`).
- **Why it works:** Tests on argument construction catch regressions without needing a daemon; defaults mean the insecure path requires typing extra.
- **Copy when:** Shelling out to a container runtime.
- **Risky:** Escape hatches (`ExtraRunArgs`) can undo the baseline — agent-framework warns explicitly that overrides weaken the boundary (`DockerShellExecutor.cs:27-30`); and argv tests prove intent, not runtime effect (no daemon-present CI coverage exists).

### P6. Secure-by-default credential lifecycle with refuse-to-start

- **Problem:** Default or absent credentials turn every deployment into an open boundary.
- **Demonstrated by:** openhands generates 64-hex secrets from `/dev/urandom`, persists them `chmod 600`, reuses across restarts, and *refuses to start automation without a session key* rather than degrading to open access (`docker/entrypoint.sh:175-218`). Public-mode static serving requires explicit key entry and never bakes keys into HTML; mutually exclusive auth flags error at startup (`scripts/static-server.mjs:149,181-190`).
- **Why it works:** Fail-safe boot converts misconfiguration from silent exposure into visible failure.
- **Copy when:** Any component fronts an execution runtime.
- **Risky:** Key *reuse across subsystems* undermines the hygiene — openhands' editor token derives from the session key (upstream #4317), forcing route-omission workarounds instead of a fix (`docker/entrypoint.sh:419-433`).

### P7. Remote sandbox lifecycle as a typed state machine with preflight gating

- **Problem:** Sandboxes that pause, resume, and vanish produce stale-host requests, doomed WebSocket connections, and confusing errors.
- **Demonstrated by:** openhands models `STARTING|RUNNING|PAUSED|ERROR|MISSING` as a discriminated union flowing through polling cadence, WS suppression while paused, archive detection, and a preflight classifier mapping statuses (and 404/5xx fallbacks) onto a `SandboxIssue` taxonomy before requests fire (`sandbox-service.types.ts:1-21`; `websocket-provider-wrapper.tsx:25-31`; `use-bash-command-logs.ts:39-57,110-157`), with regression tests (`__tests__/api/cloud/conversation-pause.test.ts:66-84`).
- **Why it works:** Transient infrastructure states become first-class UX instead of raw failures; the client stops talking to dead hosts by construction.
- **Copy when:** Execution lives behind a service with its own lifecycle you don't control.
- **Risky:** Classification conflation — openhands maps genuine upstream crashes to "unreachable," masking real bugs as sandbox issues (`use-bash-command-logs.ts:74-78`).

### P8. Declared non-boundaries, enforced where possible

- **Problem:** Integrators overtrust mechanisms that look like isolation but aren't.
- **Demonstrated by:** agent-framework states "not a sandbox" in type-adjacent docs and the assembly description for LocalCodeAct (`ProcessExecutionLimits.cs:9-11`; csproj:25) and *throws* unless dangerous local shells receive `acknowledgeUnsafe: true` (`LocalShellExecutor.cs:341-347`). openhands' architecture doc disclaims the isolation layer outright and recommends Docker mode (`docs/architecture.md:17,82`). The counter-example is instructive: opa's `allow_net` doc comment claims it only governs JSON-Schema fetches while it actually gates `http.send` too — documented drift that invites operators to under-trust the knob (`v1/ast/capabilities.go:97-99` vs `v1/topdown/http.go:403`).
- **Why it works:** Written deviations prevent assumption drift; enforceable declarations show up in review.
- **Copy when:** Any mitigation is advisory, partial, or environment-dependent.
- **Risky:** Declarations rot like any doc — pair with tests that pin the claimed behavior.

### P9. Per-run configurability via fingerprints, snapshots, and scoped mutation

- **Problem:** Customizable sandboxes drift toward global mutable state where one run's mounts leak into another's.
- **Demonstrated by:** agent-framework caches sandboxes keyed by a config fingerprint (backend/tools/mounts/domains) and rebuilds on change (`_execute_code_tool.py:76-87,990-997`; `SandboxExecutor.cs:157-172`; fingerprint tests `SandboxExecutorTests.cs:12-103`), hands each run an immutable snapshot via `create_run_tool()` (`_execute_code_tool.py:1256-1271`), and resets guests to warm snapshots between invocations (`SandboxExecutor.cs:132-135,219-227`). opa offers extensive but coarser-grained configurability — `--capabilities` accepting version names or custom JSON across six commands (`cmd/flags.go:138-139,199-230`), fixed at process start or compile call. openhands scopes per-conversation options (working dir, worktree, confirmation policy, tool sets) into the start payload, though the cloud `sandbox_spec_id` remains read-only (`agent-server-config.ts:196-205`; `agent-server-adapter.ts:593-613,1125`; `sandbox-service.types.ts:16`).
- **Why it works:** Fingerprints make per-run customization cheap *and* correct — reuse when identical, rebuild when not.
- **Copy when:** Sandbox setup costs more than a few milliseconds or carries state.
- **Risky:** Snapshot/restore assumes the substrate supports it; without it, expect persistent-session state bleed across users (the failure mode agent-framework's own docs mandate per-session ownership against, `DockerShellExecutor.cs:46-57`).

### P10. Teach the agent its own boundary

- **Problem:** Agents probe their edges blindly because nothing tells them where the edges are.
- **Demonstrated by:** openhands injects a `<RUNTIME_SERVICES>` block into every conversation start payload explaining which ports are the agent itself versus other services, reducing boundary-blind probing; E2E tests confirm it reaches the LLM (`src/api/agent-server-adapter.ts:215-297`; `tests/e2e/mock-llm/automations/mock-llm-automation.spec.ts`). Relatedly, its child-launch tool returns corrective guidance teaching the delegation boundary rules instead of throwing opaque errors (`child-conversation-launch.ts:143-158`).
- **Why it works:** An accurately informed model stops wasting turns (and risk surface) on self-discovery.
- **Copy when:** The runtime topology differs from what a model would assume (localhost conventions, proxied hosts, isolated worktrees).
- **Risky:** Topology text must stay synchronized with reality or it becomes a lie the model trusts.

## Key Differences

- **Who authored the executed code drives the default posture.** opa evaluates policies written by trusted-ish humans/operators, so a language-level boundary with open defaults feels proportionate (`AllowNet` nil ⇒ any host, `v1/ast/capabilities.go:96`). agent-framework executes model-generated code — adversarial by construction — so its strongest tier (Hyperlight) defaults to isolation-instead-of-approval while its weakest tier demands explicit `acknowledgeUnsafe` (`_execute_code_tool.py:1101-1110` vs `LocalShellExecutor.cs:339-347`). openhands executes nothing; its posture work concentrates on credentials and addressing. Same dimension, three different threat assumptions.
- **Enforcement locus: engine-internal vs externally-configured vs delegated.** opa enforces in its own compiler and interpreter — self-contained and testable end-to-end (`server_test.go:1264`). agent-framework delegates enforcement to Hyperlight, the Docker daemon, and the Monty interpreter while testing its own *configuration* code — appropriate layering, but guarantees stop at the process edge (`DockerShellExecutorTests.cs:355-357` admits argv-only coverage). openhands delegates wholesale upstream and can only enforce client discipline; it cannot verify the isolation it advertises (`docs/architecture.md:17`).
- **Consistency across ingestion paths.** opa's single real inconsistency — ad-hoc queries ban `http.send` while bundle-loaded policies are compiled without the ban (`v1/server/server.go:104` vs `v1/plugins/bundle/plugin.go:627`) — creates a false sense of uniform egress policy. agent-framework's analogous risk is opt-in: mixing packages can pair a never-require-approval sandboxed tool with an always-require local shell, easy to misconfigure precisely because each package's default is locally coherent. openhands has one ingestion path per concern by construction (typed clients), which is why its weakest enforcement (CI lint) still holds.
- **Granularity of per-run configurability.** agent-framework supports dynamic mutation plus rebuild-on-fingerprint plus per-run immutable snapshots; opa fixes configuration at process start or compile call with no per-request toggle; openhands offers per-conversation payloads but cannot select the sandbox spec itself. Configurability scales with ownership of the sandbox lifecycle.
- **Where the user learns about weak tiers.** agent-framework labels weaknesses in code-adjacent docs and assembly metadata; openhands puts them in ops-facing docs (`SELF_HOSTING.md`) and inline config comments ("routes but does not isolate", `config/defaults.json:34-38`); opa's weaknesses live in rating rationales rather than in-repo warnings — its SECURITY docs contain no sandbox threat-model statement at all.

## Tradeoffs

**In-process speed vs shared fate** (opa native topdown; Monty; agent-framework LocalCodeAct)
- Benefit: no IPC overhead, trivial embedding, works everywhere with zero platform requirements.
- Cost: a panicking builtin or runaway loop takes down the host; opa has no memory/CPU ceiling for native evaluation — cancellation is cooperative only (`v1/topdown/builtins.go:41`), unlike the Wasm target's hard interruption (`vm.go:58-59`).
- Best fit: trusted authors, short evaluations, embedding simplicity prized.
- Failure mode: resource exhaustion with no supervisor boundary; opa's own report flags this as the price of its architecture.
- Alternative seen elsewhere: Monty accepts the same shared process but adds opt-in `ResourceLimits` (duration/memory/recursion/allocations, `python/packages/monty/README.md:146-149`) — proof that in-process and bounded are compatible.

**Structural isolation vs operational weight and feature parity** (Hyperlight vs opa Wasm target)
- Benefit: hypervisor/WASM memory isolation; host contact reduced to an auditable import surface.
- Cost: platform availability requirements and graceful-degradation complexity for Hyperlight (`IsAvailableAsync` probes, `DockerShellExecutor.cs:312-353` analogue at `_execute_code_tool.py:307-316,1250`); opa's Wasm target cannot run `http.send` natively, forcing hosts to reimplement network builtins outside the audited dispatcher (`docs/docs/wasm.md:24-27`).
- Best fit: high-stakes model-generated code, or policy deployment where network builtins aren't needed.
- Failure mode: silent fallback to weaker tiers, or hosts hand-rolling the missing builtuns badly.
- Alternative: agent-framework resolves this with a *portfolio* — the developer picks per use case rather than the platform picking per build.

**Container convenience vs kernel-shared boundary** (both Docker users)
- Benefit: universal tooling, meaningful namespace/cgroup separation, cheap to reason about.
- Cost: shared kernel means escape classes survive; agent-framework's docs admit flags are best-effort and depend on image/runtime/`ExtraRunArgs` (`DockerShellExecutor.cs:20-37`); openhands inherits whatever the upstream image does, unverifiable from its tree (`docker/Dockerfile:73`).
- Best fit: medium stakes, multi-tenant-ish workloads, existing Docker operations.
- Failure mode: `--network host` publishing an admin surface past the ingress path — openhands' openvscode-server binds `0.0.0.0` inside the container (`entrypoint.sh:20-25`).
- Alternative: micro-VM tiers above, or gVisor/Kata beneath the same interface (agent-framework's stated recommendation).

**Open-by-default operability vs shifted burden** (opa vs Monty/default-deny)
- Benefit: simple deployments work immediately; policies keep full expressive power including `http.send`.
- Cost: restriction becomes an undocumented configuration act — operators often don't know `allow_net` exists, and `opa.runtime().env` hands every evaluatable policy the entire environment including injected secrets (`v1/runtime/info/info.go:47-58`).
- Best fit: single-operator CLI usage with trusted policy authors.
- Failure mode: SSRF-style probing from bundle-delivered policies at the OPA process's network position (the exact combination of `AllowNet == nil` plus the bundle compiler gap).
- Alternative: deny-by-default with opt-in grants (Monty's `PermissionError` bridge; opa's own `print()` opt-in pattern shows the house style already exists — it just isn't applied to `opa.runtime`).

**Approval-only flexibility vs honest labeling** (LocalShellExecutor/LocalCodeAct vs openhands local mode)
- Benefit: maximum speed and compatibility for interactive development; approval integrates with the human's judgment about specific commands (deny-first regex policy, exclusive allow lists, callback last, `ShellPolicy.cs:187-214`).
- Cost: approval fatigue, name-collision bypass risk in auto-approval rules (`DockerShellExecutor.cs:262-268`), and zero defense when the human rubber-stamps.
- Best fit: single-user local workflows where the operator watches every action.
- Failure mode: openhands' variant — no technical boundary and only documentation standing guard (`docs/SELF_HOSTING.md:8-10`) — is the same tradeoff with the compensating control made weaker and more deniable.
- Alternative: agent-framework's approach — permit it, but force the developer to type the acknowledgment in code.

**Proxy hop / addressing indirection vs directness** (openhands cloud topology)
- Benefit: solves CORS, centralizes auth on ephemeral per-conversation keys, keeps sandbox URLs out of browser reach entirely (`proxy.ts:18-39`; `runtime-service.ts:17-23`).
- Cost: extra hop, hard dependency on the local server being up, cookie-based embedding excluded on the cloud path (`use-workspace-session.ts:21-34`).
- Best fit: any browser UI fronting remotely-provisioned execution.
- Failure mode: automation backend falling back to cloud auth when env vars are unset — a misconfiguration that masquerades as auth failure (`entrypoint.sh:261-267`).
- Alternative: direct connectivity trades the hop for exposed sandbox URLs and browser-held credentials.

## Decision Guide

- **Executing human-authored declarative policy where latency matters?** Follow opa: in-process interpreter, language stripped of I/O primitives, builtins allowlisted from one versioned `Capabilities` artifact, restrictions decided at compile time. Budget effort for keeping *every* ingestion path on the same compiler posture — the bundle seam is the lesson.
- **Executing model-generated code where compromise is expensive?** Follow agent-framework's Hyperlight shape: structural guest isolation, link-free staged input mounts, validated output extraction, domain allowlists, snapshot-reset between invocations. Add symlink/TOCTOU defenses on the host side of every mount — the guest boundary doesn't cover the staging code.
- **Need something stronger than in-process but lighter than a VM requirement?** Use the Docker tier with agent-framework's discipline: secure flags default-on, argv construction unit-tested, override hatches named and warned, gVisor/Kata recommended in docs above your actual risk threshold.
- **Interactive local development?** Approval-in-the-loop is legitimate, but adopt agent-framework's rule: refusal without explicit `acknowledgeUnsafe`, deny-first command policies, and documentation that names the mechanism as *not* isolation.
- **Building a frontend or orchestrator that doesn't execute tools?** Follow openhands: own addressing, credentials, lifecycle modeling, and traffic discipline; do not attempt isolation. Model remote sandboxes as typed state machines with preflight gating, tunnel through a proxy hop, generate secrets at startup with refuse-to-start semantics, and teach the agent its topology in the prompt.
- **Choosing a default posture?** Decide which side fails safe and make the other side require typing: deny-by-default with opt-in grants (Monty) for hostile input; if you must ship open-by-default (opa's operability bet), then mirror the `print()` pattern — gate the dangerous primitive (`opa.runtime().env`) behind explicit enablement rather than leaving it ambient.
- **Need per-run sandbox variation?** Design fingerprint-keyed caching and run-scoped snapshots before adding configurability, or you will accumulate global mutable state that bleeds between runs.

## Practical Tips

Patterns to copy now:

- Consolidate boundary configuration into one data artifact and deprecate parallel knobs (opa's `Capabilities` consolidation).
- Enforce statically wherever the violation is expressible: compile-time builtin bans, AST validation, CI route-discipline scans.
- Route all host interaction through one chokepoint per boundary and audit that chokepoint's ambient-authority struct.
- Re-verify allowlists at trust transitions: redirects, file swaps, origin intersections.
- Test boundary construction (container argv, fingerprint divergence, rejection paths) even when runtime enforcement lives elsewhere.
- Generate credentials at startup, persist restrictively, refuse to start without them.
- Declare non-boundaries next to the code they describe, and pin the declarations with tests.

Patterns to delay until needed:

- A multi-tier execution portfolio — ship one good tier plus honest labeling first; agent-framework earns its portfolio through breadth of consumers that don't exist in smaller projects.
- Snapshot/restore lifecycle and fingerprint caching — only pay once sandbox setup is measurably expensive or stateful.
- Wasm compilation targets — a large investment justified mainly when policies/modules must run in foreign hosts.
- MicroVM-grade tiers — adopt when executing genuinely untrusted generated code at scale, not before.

Decision rule of thumb: **match the tier to the authorship of the code, then spend remaining effort on defaults and consistency, not on upgrading the tier.**

## Anti-Patterns / Caution Signs

Signs the boundary design is going brittle or dishonest:

- **Enforcement that varies by ingestion path.** opa compiles bundle policies with a bare `NewCompiler()` while ad-hoc queries get the unsafe-builtin ban (`v1/plugins/bundle/plugin.go:627` vs `v1/server/server.go:104`). If you can't answer "which compiler does this code go through?", the boundary is already uneven.
- **Documentation drift on security-critical knobs.** opa's `allow_net` comment contradicts its actual scope (`capabilities.go:97-99` vs `http.go:403`). Security semantics documented wrong are worse than undocumented.
- **Credentials shared across subsystems.** openhands' editor token deriving from the session key forces permanent workaround scaffolding (`entrypoint.sh:419-433`). One credential per trust role, or the roles collapse.
- **Routing mistaken for isolation.** "A path prefix routes but does not isolate" — shared origin means shared localStorage (`config/defaults.json:34-38`). Treat any same-origin adjacency between privileged editor and app as a boundary question.
- **Ambient environment exposure.** Full `os.environ` reachable from evaluated code by default (`info.go:47-58`) is a standing secrets-leak vector that no amount of egress policy repairs after the fact.
- **Global registries that widen the boundary silently.** opa's `RegisterBuiltinFunc` mutates process-global state; any linked package can add policy-reachable host access without central review (`builtins.go:88-91`).
- **Cooperative-only resource limits.** Cancellation that requires the running code to poll (`Cancel` in `builtins.go:41`) does not bound adversarial or buggy loops.
- **Silent isolation downgrades for availability.** openhands' worktree→shared downgrade with only an `isolation_note` trades isolation for uptime implicitly (`child-conversation-launch.ts:300-310`); acceptable only if surfaced loudly.
- **Name-based auto-approval rules.** Tool-name collisions can approve commands nobody intended (`DockerShellExecutor.cs:262-268`) — bind approvals to full identity, not display strings.
