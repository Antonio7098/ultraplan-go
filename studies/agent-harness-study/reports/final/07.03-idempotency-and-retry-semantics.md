## Executive Summary

Six harnesses answer one question — *can a payment/email/delete tool be retried safely?* — with six different architectures, but they converge on a single verdict: **no framework makes external side effects automatically exactly-once.** Every source either delegates effect-deduplication to users or builds structural primitives (keys, ledgers, deterministic identities, durable timers) that make *user-implemented* idempotency possible.

The spread runs from temporal (9/10), which owns persistence and turns every activity retry into a durably scheduled timer task guarded by request-ID dedup and stamp fencing, down to crewai (5/10), whose core ReAct loop blindly re-invokes any exception-raising tool with identical arguments up to three times — precisely the behavior that double-charges a card whose response was lost after commit. Between them sit three distinct philosophies:

- **Retry-as-conversation** (pydantic-ai 8/10): a tool retry is a message to the model (`RetryPromptPart`), never a silent re-invocation; safety comes from explicit taxonomies (`ModelRetry` vs `ToolFailed` vs deferrals) and per-tool budgets.
- **Structural identity without effect protection** (langgraph 7/10): node-granularity retries plus deterministic task IDs make *task completion* idempotent across crashes, while external effects remain explicitly unprotected.
- **Per-tool declared idempotency** (openhands 6/10, agent-framework 8/10): idempotency is a property each tool declares (`idempotentHint`) and the executor enforces locally — via a pre-network claim ledger in the browser, or an authority state machine with an `INDETERMINATE` sink in the approval lifecycle.

The single sharpest axis of divergence is the **default classification posture**: langgraph, crewai, and openhands treat unknown failures as retryable (liveness-first); agent-framework and pydantic-ai treat unknown failures as fatal (safety-first). For a side-effecting tool that fails after committing, these two postures produce opposite outcomes from identical code.

## Core Thesis

Idempotency and retry safety in agent harnesses is not achieved by a retry wrapper — every source that relies primarily on one (crewai's ReAct loop, openhands' blanket `withRetry`) scores lowest. It is achieved by **making the unsafe default explicit and requiring proof before repetition**: a request that may have started work must be acknowledged before it can be re-sent (agent-framework's submit-vs-track rule), an interrupted execution must prove non-start (`SAFE_TO_RETRY`) or present a matching key (`recover_execution`) before authority is re-granted, an ambiguous resume must fail closed rather than guess (pydantic-ai, temporal), and a completed task must be recognizable by deterministic identity so replays become no-ops (langgraph, temporal). The mature sources spend their complexity budget on *identity and state machines*; the fragile sources spend it on *backoff curves*. Where you put that budget determines whether a lost response costs one retry or two payments.

## Approach Models

**agent-framework — side-effect-aware regimes with an authority state machine.** Three coexisting regimes: model-inference retries delegated entirely to user middleware/SDK (sample-level tenacity, `python/samples/02-agents/auto_retry.py:87-95`); MCP transport retries restricted to explicitly classified connection-loss errors with exactly one reconnect-retry (`python/packages/core/agent_framework/_mcp.py:2108-2160`); and approval-gated side effects governed by a full lifecycle state machine (`PENDING→CLAIMED→EXECUTING→SETTLED/…/INDETERMINATE`) where re-execution requires either provable non-start or a matching caller-declared `idempotency_key` (`python/packages/ag-ui/agent_framework_ag_ui/_approval_lifecycle.py:780-847`). Ordinary tools get no automatic retry at all — errors become data for the model, bounded by a consecutive-error budget (`python/packages/core/agent_framework/_tools.py:96`).

**crewai — four independent retry scopes, blind at the core.** Tool-call retries recurse into `self.use(...)` on *any* exception up to a shared attempt budget (`lib/crewai/src/crewai/tools/tool_usage.py:451-479`); task retries re-enter `execute_task` except for litellm-module exceptions (`lib/crewai/src/crewai/agent/core.py:721-747`); guardrail failures re-run the entire task including all its tools (`lib/crewai/src/crewai/task.py:1376-1408`); transport wrappers classify locally per integration. The declarative `ToolFailure(retryable=...)` flag exists but no executor consumes it yet (`lib/crewai/src/crewai/tools/tool_failure.py:95-98`).

**langgraph — task-granularity policy plus deterministic completion identity.** `RetryPolicy` re-executes whole nodes with backoff/jitter and first-match-wins policy matching (`libs/langgraph/langgraph/pregel/_retry.py:573-683`); graph-state consistency is preserved by clearing pending writes between attempts (`_retry.py:615,738`). Separately, deterministic task IDs hashed from checkpoint coordinates (`libs/langgraph/langgraph/pregel/_algo.py:614-624`) plus `ON CONFLICT` write upserts make completed tasks skippable on crash-resume — idempotent *execution records*, not idempotent *effects*.

**openhands — declared hints enforced beside each handler.** Client tool specs carry MCP-style annotations (`idempotentHint: false` on the billable launch tool, `src/api/launch-child-conversation-client-tool.ts:103-111`), and enforcement lives next to the handler: a localStorage claim ledger records handled `tool_call_id`s before any network work (`src/services/child-conversation-launch.ts:205-227`). WebSocket reconnect replays are gated at the event level by an id set checked before non-idempotent side effects (`src/contexts/conversation-websocket-context.tsx:556-568`). Mutations are never auto-retried; only reads and idempotent-by-construction writes use the unclassified `withRetry` helper.

**pydantic-ai — five layers, five budgets, retry-as-message.** Transport (tenacity), model fallback, tool, output, and hook retries have independent budgets (`docs/retries.md:3-15`). A tool retry produces a `RetryPromptPart` keyed by `tool_call_id` that *replaces* the result — there is never both a return and a retry for one ID (`pydantic_ai_slim/pydantic_ai/messages.py:1636-1739`). The exception taxonomy encodes retryability explicitly: `ModelRetry` charges the budget, `ToolFailed` is terminal and uncharged, deferrals are control flow, unknown exceptions abort (`pydantic_ai_slim/pydantic_ai/exceptions.py:57-147`). Effect idempotency is pushed to durable engines — notably Prefect's value-addressed cache that replays recorded tool results instead of re-running non-idempotent tools (`pydantic_ai_slim/pydantic_ai/durable_exec/prefect/_cache_policies.py:171-196`).

**temporal — retry as durable server-side state.** Activity retries are classified against a user-supplied `RetryPolicy` (`common/retrypolicy/retry_policy.go:24-64`) and materialized as persisted `ActivityRetryTimerTask`s in the timer queue (`service/history/tasks/activity_retry_timer.go:14`) — crash-proof and cluster-wide. Every layer has dedup: start-request IDs (`service/history/api/startworkflow/api.go:340-358`), per-attempt stamps rejecting duplicate dispatch (`service/history/api/recordactivitytaskstarted/api.go:150-184`), conditional persistence writes with typed conflicts. User side effects remain at-least-once; the server supplies attempt numbers and heartbeat details as idempotency raw material.

## Pattern Catalog

### P1. Submit-vs-track split for may-have-started operations

- **Problem:** Re-issuing a request that might already have been accepted can start the operation twice.
- **Demonstrated by:** agent-framework — the augmented long-running `tools/call` is never re-sent before a `task_id` exists ("task state unknown"); only acknowledged track phases (poll/fetch against the same id) are retryable (`python/packages/core/agent_framework/_mcp.py:2243-2256`; pinned by `test_mcp.py:7148-7177` asserting `send_calls == 1`).
- **Why it works:** It splits the world into "unacknowledged create = unrepeatable" and "acknowledged track = read-only retry," which mirrors authorize-then-poll payment practice without requiring servers to implement idempotency keys.
- **Copy when:** Driving long-running remote operations over flaky transports where you cannot know whether a disconnect beat the response.
- **Risky/overkill when:** Applied to pure reads or genuinely idempotent calls, where it just adds state machinery.
- **Evidence:** agent-framework report, Architectural Decision 2.

### P2. Authority state machine with an INDETERMINATE sink

- **Problem:** "Did my execution actually start?" is often unknowable after a crash; collapsing uncertainty into "failed" invites blind retry, collapsing it into "done" invites omission.
- **Demonstrated by:** agent-framework — `INDETERMINATE` is a first-class status recorded when execution may have started, blocking automatic retry ("automatic retry is unsafe", `_approval_lifecycle.py:500-503`, `:808-826`), carrying its own longer retention window (7 days vs 15 min for terminal states, `_approval_lifecycle.py:239-265`).
- **Why it works:** Uncertainty gets dedicated handling and time to be resolved by operators or key-proofed recovery, instead of being laundered into a retryable-looking failure.
- **Copy when:** You gate dangerous actions behind approvals and need exactly-once confidence more than availability.
- **Risky/overkill when:** Your tools are read-mostly; stranding work in indeterminate states will frustrate users for no benefit.
- **Evidence:** agent-framework report, Architectural Decisions 3–4; contrast with temporal, which resolves equivalent uncertainty via attempt counts rather than a distinct state.

### P3. Claim-before-execute ledger

- **Problem:** Replay vectors (socket reconnects, redelivered messages, retried RPCs) arrive both after completion and *mid-flight*; post-hoc dedup misses the second class.
- **Demonstrated by:** openhands — `claimToolCall` writes the `tool_call_id` to persistent storage on line 1 of the handler, before validation/network work, so mid-flight replays are also dropped (`src/services/child-conversation-launch.ts:505-510`, ledger at `:205-227`); temporal — per-attempt stamps reject a second worker claiming the same attempt (`api.go:178-184`); crewai — atomic `_claim_usage` check-and-increment under lock returns a structured refusal (`base_tool.py:302-324`).
- **Why it works:** Recording *intent to handle* before any await point converts duplicate delivery into a cheap local lookup covering both completed and concurrent replays.
- **Copy when:** Any handler triggers billable/unrepeatable external work and can receive duplicates through any channel.
- **Risky/overkill when:** The store is weaker than the guarantee needed — openhands' localStorage ledger is non-atomic across tabs and proceeds unprotected when quota is exhausted (`:222-225`), a documented residual risk.
- **Evidence:** openhands report Q4/Q5; temporal report Architectural Decision 5; crewai report Notable Patterns.

### P4. Deterministic identity as the dedup substrate

- **Problem:** Crash-resume needs to recognize "this work already happened" without a shared live process.
- **Demonstrated by:** langgraph — task IDs are hashes of `(checkpoint_id, checkpoint_ns, step, name, kind, triggers)` (`_algo.py:614-624`), so resumed runs regenerate identical keys; persisted writes upsert with `ON CONFLICT DO NOTHING/UPDATE` (postgres `base.py:146-159`) and completed tasks are skipped on resume (`main.py:2968`); pydantic-ai — Prefect cache keys are value-addressed so flow retries *replay* tool results rather than re-run them, while keeping the dispatching `tool_call_id` verbatim so two same-argument parallel calls still each execute (`_cache_policies.py:80-106`).
- **Why it works:** Identity derived from stable coordinates means dedup needs no coordination protocol — the key *is* the proof.
- **Copy when:** Your execution model already has stable step/checkpoint coordinates; this gives crash-safe completion dedup nearly for free.
- **Risky/overkill when:** Inputs feed the hash — unstable serialization poisons keys (langgraph's pickle-based cache keys have this documented hazard, `_internal/_cache.py:26-31`).
- **Evidence:** langgraph report Architectural Decision 2; pydantic-ai report Pattern "Prefect replay-vs-rerun".

### P5. Retry-as-conversation (errors as data)

- **Problem:** Silent automatic retries hide attempts from both the model and the audit trail; silent suppression hides failures from the model entirely.
- **Demonstrated by:** pydantic-ai — retries are `RetryPromptPart` messages rendered "Fix the errors and try again.", reused verbatim by OTel spans (`messages.py:1676-1697`, `capabilities/instrumentation.py:332-363`); agent-framework — tool exceptions become `"Error: Function failed."` function results with a 3-error consecutive budget (`_tools.py:1412-1434`, `:96`); langgraph — handled tool errors become `ToolMessage(status="error")` with fix-it templates (`tool_node.py:1005-1012`); openhands — client-tool failures become corrective guidance posted into the conversation ("retry only if the cause looks transient", `child-conversation-launch.ts:525`); crewai — duplicate-usage refusals are prompt-engineered i18n strings returned as results (`translations/en.json:49`).
- **Why it works:** Five of six sources independently converged on this: it makes retries observable in history, bounds them by budget rather than loop counter, and lets the model adapt (fix arguments, choose another tool) rather than repeat.
- **Copy when:** Almost always, for tool-level failures. This is the closest thing to a consensus pattern in the study.
- **Risky/overkill when:** Transient transport faults — paying a full model round trip to learn about a 503 is waste (pydantic-ai docs say exactly this, `docs/retries.md:15`); handle those below the agent layer.
- **Evidence:** all six source reports; strongest single articulation in pydantic-ai's Architectural Decision 1.

### P6. Per-attempt write buffering and clearing

- **Problem:** A partially-failed attempt must not leak half its outputs into durable state before retrying.
- **Demonstrated by:** langgraph — `task.writes.clear()` before every attempt, timeout watchdogs also clear stale/late writes from cancelled background tasks, and guarded-config scopes physically block post-timeout sends (`_retry.py:615, :486-502, :225-235`; regression tests at `tests/test_retry.py:1091-1156`).
- **Why it works:** Buffering writes until commit-time plus clearing between attempts yields all-or-nothing state semantics per attempt even though the node body ran twice.
- **Copy when:** Your retry unit accumulates outputs incrementally into shared state.
- **Risky/overkill when:** External systems — this protects *your* state only; the email already left (the study's central limitation, acknowledged by langgraph Q5).
- **Evidence:** langgraph report Architectural Decision 4.

### P7. Durable retry scheduling instead of in-process sleep loops

- **Problem:** An in-memory backoff loop dies with the process, losing both the attempt count and the pending retry.
- **Demonstrated by:** temporal — each retry becomes a persisted `ActivityRetryTimerTask{Attempt, Stamp}` executed by the timer queue (`task_generator.go:572-583`), surviving restarts; attempt counters and full policy fields live in `ActivityInfo` mutable state (`mutable_state_impl.go:6911-6928`). Contrast: langgraph keeps attempt counters in local variables (crash mid-backoff loses history, `_retry.py:584-600`), and agent-framework's lifecycle dicts are explicitly process-local (`_snapshots.py:121-126`).
- **Why it works:** Persisting the retry itself makes recovery deterministic after any failure — the timer fires or it doesn't, and the state says which.
- **Copy when:** Retries must survive process death or span workers/machines.
- **Risky/overkill when:** Sub-second infra retries inside one process, where a persistence round trip per retry is pure overhead (temporal reserves its cheap `ThrottleRetry` loop for exactly this internal case, `common/backoff/retry.go:46-102`).
- **Evidence:** temporal report Architectural Decision 1; tradeoff noted in temporal Tradeoffs.

### P8. Fencing stale attempts (stamps, generations, guards)

- **Problem:** Slow/zombie executions from earlier attempts can commit effects after newer attempts superseded them.
- **Demonstrated by:** temporal — monotonically increasing `Stamp` fields cause obsolete tasks to be rejected (`ObsooleteMatchingTask`, `api.go:178-184`) and timers skip superseded attempts (`timerSequenceID.Attempt < ai.Attempt`, `timer_queue_active_task_executor.go:297-307`); langgraph — `_TimedAttemptScope.wrap_config` blocks writes after the timeout boundary (`_retry.py:169-193`); agent-framework — argument-drift detection rejects resumed decisions whose arguments differ from the registered occurrence (`_approval_lifecycle.py:524-530`).
- **Why it works:** Monotonic tokens turn "is this execution still current?" into a comparison, closing races that would otherwise need distributed locks.
- **Copy when:** Attempts can overlap (timeouts firing late, cancellations racing completions, resumes racing originals).
- **Risky/overkill when:** Strictly serial single-threaded execution.
- **Evidence:** temporal Notable Patterns; langgraph Notable Patterns; agent-framework Failure Modes.

## Key Differences

**Default classification posture — the sharpest divergence.** LangGraph's `default_retry_on` retries any exception not on an explicit fatal list — including application-specific custom exceptions (`_internal/_retry.py:29`, test at `test_retry.py:175-246`); crewai's ReAct loop retries *any* escaping exception identically (`tool_usage.py:451-479`); openhands' `withRetry` retries every caught error with zero classification (`with-retry.ts:12-21`). Agent-framework takes the opposite pole: only enumerated connection-loss shapes retry; everything else raises immediately (`_mcp.py:2125-2134`); pydantic-ai aborts the run on unknown exceptions unless a hook converts them (`docs/retries.md:131`). Temporal sits deliberately in between for user code: application failures retry unless marked non-retryable, because the workflow author owns the policy (`retry_policy.go:53-56`). Identical post-commit failure code therefore double-executes under three harnesses and halts safely under two.

**Where idempotency state lives.** Temporal: server persistence blobs and timer queues. Openhands: browser localStorage keyed per conversation. Agent-framework: process-local lifecycle dicts plus session-backed approval bindings (`_tools.py:2109-2138`). Langgraph: checkpointed write rows in Postgres/SQLite. Pydantic-ai: nowhere in-core; in durable-engine cache policies when present. Crewai: an opt-in in-memory dict (`cache_handler.py:20`) disabled by default (`crew.py:229-238`). This tracks product shape directly — the platform owns durable state; libraries refuse to; the frontend uses what the browser offers.

**Who pays for a retry.** In pydantic-ai every tool retry costs a model round trip by design (`docs/retries.md:15`) — expensive but fully auditable. Crewai, langgraph, and temporal retry within the process/engine at compute cost only — cheaper, but crewai's internal MCP wrapper masks up to 3 transparent attempts from downstream observers entirely (`mcp_tool_wrapper.py:113-115`). Openhands splits the difference: background service retries are silent; agent-facing failures always surface as guidance.

**Retry visibility.** Temporal writes a `RetryState` enum into terminal history events and tags metrics with attempt numbers (`event_factory.go:300-379`) — observability as contract. Agent-framework emits structured audit events including a `"duplicate"` marker for deduped decisions (`_approval_lifecycle.py:762-778`). Pydantic-ai guarantees telemetry text matches what the model saw via a shared rendering contract (`messages.py:1684-1687`). Langgraph offers logs plus a deliberately private server observer contract (`_retry.py:87-127`). Openhands shows retry buttons to users but logs nothing for successful background retries. Crewai exposes aggregate telemetry only. The gradient correlates strongly with score: mature sources treat retry visibility as an interface, fragile ones as an afterthought.

**Granularity of the retry unit.** Whole-node re-execution (langgraph) trades wasted computation and repeated effects for simplicity; whole-task re-runs (crewai guardrails) amplify this further — a blocked-but-successful run's side effects recur wholesale, with only failure-*records* deduplicated afterward (`task.py:1337-1437`). Single-call conversational retries (pydantic-ai) and single-transport-attempt retries (agent-framework MCP) minimize blast radius. Temporal decouples the question entirely: the *dispatch* is retried, and the unit of user work defines its own scope.

## Tradeoffs

**Liveness-default vs safety-default classification.**
Benefit (liveness): unknown transient provider faults recover without intervention — langgraph's stated posture, maximizing recovery (`_internal/_retry.py:11-29`). Cost: exactly wrong for side-effecting tools whose failures surface as custom exceptions. Best-fit: read-heavy nodes, parse/validation loops. Failure mode: post-commit double execution. Alternative seen: agent-framework's enumerate-or-refuse posture, which converts some recoverable blips into hard failures but structurally cannot double-fire an unclassified mutation. CrewAI demonstrates the middle path emerging: a declarative `ToolFailure` schema exists to encode per-tool intent — but nothing consumes it yet, so the intent is documentation, not protection.

**Durable vs in-memory retry state.**
Benefit (durable, temporal): crash-proof, cluster-consistent, auditable. Cost: a persistence write plus timer round trip per retry; backward-compat fallback reads for old record formats (`startworkflow/api.go:329-337`). Benefit (in-memory, crewai/openhands-withRetry): trivially fast and simple. Failure mode: restart loses all dedup context — crewai loses usage counters and call fingerprints; agent-framework compensates by failing closed (`APPROVAL_RESUME_NOT_FOUND`) at the cost of losing replayable outcomes across restarts (`_agent_run.py:1279-1304`). Best-fit follows ownership: persist what outlives the process; fence what doesn't.

**Model-driven vs programmatic retries.**
Benefit (model-driven): explainable, adaptive, self-auditing in history; bounded by budgets. Cost: token latency and expense per retry, nondeterminism — agent-framework notes ordinary-tool retry counts depend on model behavior, capped only by the consecutive-error budget (`_tools.py:2718-2733`). Benefit (programmatic): deterministic, fast. Failure mode: blind programmatic loops duplicate effects (crewai) or burn backoff cycles against dead auth (openhands' `withRetry` hitting 401s three times before invalidation). Pydantic-ai resolves the tension by layering: deterministic flakiness belongs in tenacity transports; semantic failures belong in conversation.

**Exactly-once bias vs availability (INDETERMINATE).**
Agent-framework's interrupted approvals strand work until operator action or key-proofed recovery (`_approval_lifecycle.py:846-847`) — maximum confidence, real convenience cost. Temporal's alternative: keep dispatching (at-least-once) and hand users attempt numbers/heartbeat details to build their own guards — maximum availability, transferred burden. Both are honest answers; the failure mode of the first is stranded work, of the second, duplicate payments by surprised users.

**Centralized vs scattered classification.**
Temporal's single `IsRetryableFailure` keeps SDK-visible semantics uniform but forces exotic predicates into string-encoded `NonRetryableErrorTypes`. Crewai's per-integration wrappers (MCP, uploads, Brave, A2A) each invent retryable sets and backoff constants — flexible, non-uniform, and silently broken by wording changes in provider messages (`mcp_tool_wrapper.py:139-153` substring matching). Openhands shows the drift endgame: two copy-pasted `withRetry` implementations evolving independently (`settings-service.api.ts:134-156`).

## Decision Guide

Choose your primary mechanism by answering three questions:

**1. Must retry state survive process death?**
- Yes, and you own infrastructure → durable retry scheduling with persisted attempts and typed-conflict persistence (temporal model). This is the only pattern proven at scale for cross-restart correctness.
- Yes, but you're a library → deterministic identity + durable write dedup (langgraph model): derive task keys from stable coordinates, upsert results, skip completed work on resume. Conformance-test the saver contract so every backend honors it.
- No → in-memory budgets are fine, but fail closed on ambiguity at resume boundaries (pydantic-ai raises `UserError` on unmatched deferred results; agent-framework refuses unknown interrupts rather than re-registering them).

**2. What is your default when failure type is unknown?**
- Tools can move money/delete data → safety-default: enumerate retryable classes explicitly; everything else propagates (agent-framework MCP, pydantic-ai unknown-exception-abort).
- Mostly reads/pure computation → liveness-default with budgets (langgraph, crewai) is acceptable, *provided* mutating paths are separately fenced by approval gates, usage caps, or caches.
- Mixed, user-extensible → require per-tool declaration (openhands annotations, crewai `ToolFailure.retryable`) and make the executor actually honor the declaration — crewai's inert flag is the cautionary version.

**3. Who decides to try again?**
- The model, when adaptation matters → retry-as-conversation with per-tool budgets and reset-on-success accounting (pydantic-ai); accept the round-trip cost.
- The framework, when speed matters → bounded attempt loops with explicit classification at the seam that knows the failure domain (agent-framework's transport-layer enumeration; temporal's engine-level policy), never a blanket catch-all.
- The human, when effects are irreversible → approval/interrupt gating *before* execution (langgraph `interrupt()`, agent-framework `always_require`, pydantic-ai `requires_approval`), remembering langgraph's documented caveat that code before the interrupt re-runs on resume (`types.py:864`) — sequence effects after the gate.

If you can only afford one mechanism: a claim-before-execute ledger on your known-dangerous tools (P3) plus errors-as-data for everything else (P5) captures most of the safety at minimal complexity — it is essentially openhands' architecture with its generic-retry weaknesses patched.

## Practical Tips

- **Sequence claims before awaits.** Record intent-to-handle before the first network call, not after success — openhands places `claimToolCall` on line 1 specifically so mid-flight replays are caught (`child-conversation-launch.ts:505-510`).
- **Never cache or retain failures as if they were successes.** CrewAI's rule — "a cached failure would make a transient error permanent" (`cache_handler.py:38-41`, tested at `test_tool_failure.py:915-953`) — generalizes: any memoization layer must distinguish outcomes from errors.
- **Give each budget a distinct owner.** Pydantic-ai's five independent budgets prevent one noisy layer from exhausting another's allowance (`docs/retries.md:3-15`); agent-framework separates the model-facing consecutive-error cap from transport attempt counts. Conversely, crewai's shared `_run_attempts` pool lets three unrelated one-off failures exhaust the budget like one persistent bug (`tool_usage.py:109`).
- **Honor server hints.** Respect `Retry-After` headers over local backoff (crewai Brave Search, `brave_search_tool/base.py:67-79`; pydantic-ai `wait_retry_after` parsing seconds/HTTP-date, `retries.py:514-590`), and let workers override the next retry delay when they know their own side effect's cadence (temporal `NextRetryDelay`, `workflow/retry.go:47-52`).
- **Make retried operations converge by construction.** Upserts, 404-tolerant deletes, and diff-merge patches make retries harmless without any key infrastructure (openhands `secrets-service.ts:60-76`, `settings-service.api.ts:607-694`). Redesigning the operation beats wrapping it.
- **When a retry changes semantics, disclose it.** OpenHands' worktree→shared fallback returns an `isolation_note` explaining the downgrade (`child-conversation-launch.ts:308-323`); silent semantic-changing retries poison trust in results.
- **Pin unsafe behavior with negative tests.** The highest-signal tests in this study assert what must *not* happen: `send_calls == 1` after pre-acknowledgment loss (agent-framework), replay launches nothing twice (openhands), duplicate `(task_id, idx)` writes don't duplicate rows (langgraph conformance suite). Write the "does not re-execute" test, not just "retries eventually succeed."
- **Prefer anti-retry fallbacks where looping is meaningless.** Returning an empty page when filters are unsupported "so the UI doesn't retry indefinitely" (openhands `event-service.api.ts:149-163`) beats bounding a doomed loop.
- **Block instead of retrying for predictable waits.** CrewAI's rate controller sleeps until the minute window rather than failing into a retry loop (`rpm_controller.py:47-58`) — reserve retry machinery for genuine failures.

## Anti-Patterns / Caution Signs

- **Blind exception-driven re-invocation of arbitrary tools.** CrewAI's ReAct loop recurses on any exception with identical arguments (`tool_usage.py:476-479`) — the canonical double-payment vector, flagged as its highest-severity gap. Caution sign: a retry loop whose condition is `except Exception`.
- **Unknown-is-retryable defaults on extensible surfaces.** Langgraph's classifier retries custom exceptions by default (`_retry.py:29`); openhands' `withRetry` retries 4xx deterministics. Caution sign: new tool authors inherit duplication risk without writing any retry code themselves.
- **Whole-scope retries as repair strategy.** Guardrail failures re-running entire tasks repeat every contained side effect; only the bookkeeping is later deduplicated (`task.py:1403-1408`). Caution sign: retry radius larger than the failing operation's blast radius.
- **Declarative flags nobody reads.** CrewAI's `retryable` field has no consumer branch; openhands ships `classification.retryable` from the server but treats it as display metadata. Caution sign: schema fields documenting intent that the executor ignores — worse than absent, because they suggest safety that isn't enforced.
- **Unclassified shared helpers drifting apart.** Two independent `withRetry` copies, neither with tests (`openhands gap`: zero test hits for `withRetry|with-retry`). Caution sign: retry logic reachable by copy-paste rather than import.
- **Silent success-path retries.** Neither openhands nor crewai records that a save needed N attempts; only final failure surfaces. Caution sign: incident diagnosis requires asking "how many times did this actually run?" with no way to answer — crewai's MCP wrapper hides up to three internal attempts behind one result string.
- **Opt-in safety on the dangerous path.** CrewAI's strongest dedup (result cache) defaults off, pushing the mutation hazard onto users via a warning string (`crew.py:232-236`). Caution sign: the README explains how to be safe rather than the code being safe.
- **Storage weaker than the guarantee.** localStorage ledgers that proceed on quota exhaustion, corrupt-ledger resets forgetting prior claims, non-atomic multi-tab read-modify-writes (openhands `child-conversation-launch.ts:209-225`). Caution sign: the idempotency store shares a failure domain with the effects it guards.
- **Reset-on-success counters without run-level caps.** Pydantic-ai documents unbounded fail/succeed alternation within request limits (`docs/retries.md:35`) and fresh budgets per hallucinated tool name (`:37`). Caution sign: any per-operation budget with no aggregate ceiling.
- **Substring-based classification.** Retrying when lowercased error text contains `"connection"` breaks silently when providers reword (`mcp_tool_wrapper.py:139-153`). Caution sign: `error_message.lower().find(` anywhere in a retry predicate.

## Notable Absences

Consistent absences across all six sources — evidence of a field-wide design frontier rather than individual neglect:

- **No HTTP-level idempotency keys anywhere.** Agent-framework searched its whole tree: hits only in the ag-ui lifecycle; openhands searched `Idempotency-Key`/`X-Request-ID`: zero hits; crewai: none; langgraph repo-wide: only SDK stream bookkeeping and conformance tests; temporal explicitly delegates key injection to users. Nobody auto-generates or plumbs request keys for arbitrary tool calls.
- **No cross-process durable idempotency store outside the platform.** Only temporal persists dedup state as a first-class concern. Agent-framework's lifecycle, crewai's cache, and openhands' ledger are all explicitly non-durable or single-host; langgraph persists *outcomes* but not attempt counters.
- **No generic idempotency-key parameter on tool APIs.** Pydantic-ai states it outright: no `idempotency_key` exists anywhere in the tool API; the closest analogues are durable-engine cache policies. Agent-framework lists generalizing its approval-flow key to ordinary `@tool` functions as future work.
- **No transactional outbox / side-effect journal in any library-tier source.** Effects that landed before a crash are detected (langgraph skips completed tasks) but never reconciled against the external system.
- **No public stream/callback surface for in-flight retry attempts** in langgraph (private observer only) and no per-attempt events in crewai (aggregates only) — retry visibility lags retry mechanics almost everywhere except temporal and pydantic-ai.
- **No cross-language parity.** Agent-framework's .NET implementation has no counterpart to the approval-lifecycle machinery (Azure pipeline retries only, `FoundryChatClient.cs:624-632`).

## Per-Source Notes

- **agent-framework (8/10).** The study's deepest treatment of the unsafe-retry boundary. Its submit-vs-track rule, `ClaimRecoveryPolicy.SAFE_TO_RETRY` proof requirement (releasable only from CLAIMED, never EXECUTING), and rejection-cannot-be-upgraded conflict semantics form a coherent authority model backed by negative tests. Weakest points: in-memory lifecycle, retry sophistication confined to the ag-ui package, and one documented at-least-once window (sync sibling tools completing during batch cancel with discarded results, `docs/specs/004-python-function-calling-loop.md:337`). Institutionalizes the hazard: its function-calling-loop spec mandates exactly-once review for changes in this area, citing issue #6851.
- **crewai (5/10).** Four retry layers with no unifying budget or philosophy; the core loop is the hazard. Genuine strengths worth keeping: failures-never-cached with rationale-pinned tests, atomic usage-limit claims, ContextVar-scoped failure collection surviving nested guardrail retries, and well-classified integration wrappers (status-code tables, `Retry-After` honoring). Path-dependence is the sleeper issue: identical code auto-retries on the ReAct path and never retries on the native function-calling path (`agent_utils.py:1767-1786`).
- **langgraph (7/10).** Proves crash-resume dedup can be a framework guarantee when identity is deterministic — conformance tests enforce saver idempotency for every backend. Equally instructive in what it declines to do: external effects are architecturally delegated to `interrupt()`/caching/user middleware, and the interrupt mechanism itself documents that pre-gate code re-executes on resume (`types.py:864`). Zombie-attempt hygiene (guarded-config write fencing, cancelled-error disambiguation LSD-1507) is exemplary defensive engineering.
- **openhands (6/10).** Best small-scale demonstration that frontend harnesses face the same problem: its one billable tool gets annotation, prompt guidance, pre-network claim, and replay regression tests. The generic layer undermines the specific layer — an unclassified `withRetry`, duplicated helper, ~40 divergent per-hook query policies, and zero observability of background attempts. Its graceful-degradation-with-disclosure pattern (semantic fallbacks reported via `isolation_note`) is transferable anywhere retries change meaning.
- **pydantic-ai (8/10).** The cleanest conceptual model: retries as messages, budgets as interfaces, ambiguity as errors. Distinctive mechanisms: `ToolFailed` reporting terminal failure *without* consuming budget; the free first availability-refusal separating run-state mistakes from argument mistakes; deterministic, idempotent transcript repair synthesizing marked `'interrupted'` returns for dangling calls (protected by pipeline determinism tests); Prefect's exhaustive-projection cache keys with a test that fails when a new field is uncategorized. Documented quirks (reset-on-success alternation, hallucinated-name budget farming, dual-budget issue #5238) show unusual honesty about edge cases.
- **temporal (9/10).** The reference implementation of durable retry semantics: persisted timer tasks, centralized classification, optimistic concurrency with typed conflicts, stamp fencing, request-ID dedup at start/activity/update/cancel/pause layers, and `RetryState` written into history events as an observability contract. Crucially candid about the boundary: dispatch is at-least-once and user effects stay user-owned — the codebase even documents closing specific replay windows (pause re-application, cancellation-after-terminal) as features matured. Deducted points are for rough edges (`RETRY_STATE_PAUSED` unsupported, hard-coded throttle policy, infinite default attempts relying on deadlines as circuit breakers).

## Open Questions

- **Can standing auto-approval rules bypass occurrence registration?** Agent-framework could not exhaustively prove no bypass path between `ToolApprovalMiddleware` standing rules and the AG-UI lifecycle's idempotency keys within its study boundary (`_agent_run.py:2734-2739` registers at emit time; full tracing incomplete).
- **Does anything persist crewai's dedup context?** The "never persisted" claim rests on cited in-memory implementations; a full audit of every storage backend was out of scope, and hierarchical-process delegation retries were not traced end-to-end.
- **Do langgraph retry budgets interact with step/recursion bounds under async durability?** Retries occur inside one superstep and don't consume steps, but whether long backoff sequences can stall progress under `durability="async"` is undocumented.
- **What does the server do beneath openhands' `client_tools` acknowledgement?** The frontend asserts acknowledgement precedes browser execution but cannot verify agent-server-side retry/idempotency semantics from its repository; likewise the exact semantics of `ErrorClassification.retryable` live in an external package.
- **Do pydantic-ai error hooks see timeouts before or after `ModelRetry` conversion?** Code reading suggests hooks see the already-wrapped retry (conversion happens inside `FunctionToolset.call_tool`), but no dedicated test pins it; wire-shape cassettes for `RetryPromptPart` across all three major providers were not inspected.
- **How do temporal's Nexus operations classify retries?** Parallel dedup machinery exists (`chasm/lib/nexusoperation/handler.go:55-56`) but was not fully traced; SDK-side retry ergonomics live in a separate module outside the studied repository.
- **Field-wide:** will any harness generalize caller-declared idempotency keys from special flows (approvals, durable engines) into ordinary tool APIs — the single most-requested capability implied by every source's future-work list?
