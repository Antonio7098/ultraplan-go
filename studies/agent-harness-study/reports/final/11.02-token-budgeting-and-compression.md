## Executive Summary

Seven harnesses answer the dimension's core question — *"Can the system handle context overflow without losing critical information?"* — with seven different postures along a single axis: **how much of the context problem does the framework own versus delegate?** At one extreme, agent-framework (8/10) ships a full client-side compaction engine that measures, projects, and enforces a token budget before every model call (agent-framework, `python/packages/core/agent_framework/_compaction.py:1651-1702`). Letta (7/10) owns the loop end-to-end with layered compaction modes, model-specific trigger thresholds, and rich observability (letta, `letta/services/summarizer/thresholds.py:27-41`). pydantic-ai (7/10) and openai-agents-sdk (7/10) delegate compression to provider-native compaction APIs but invest heavily in owning the *boundary semantics* around them (pydantic-ai, `pydantic_ai_slim/pydantic_ai/messages.py:2774-2814`). CrewAI (6/10) treats overflow as an exception-handling problem, recovering via whole-transcript summarization triggered by string-matched provider errors (crewai, `lib/crewai/src/crewai/utilities/exceptions/context_window_exceeding_exception.py:4-13`). OpenHands' frontend (6/10) is an observer plus manual relief valve by architectural necessity (openhands, `src/hooks/use-await-context-compaction.ts:62-164`). LangGraph (3/10) abstains deliberately: no token counting exists anywhere in the repo — the only `max_tokens` occurrence is a commented example line (`libs/cli/examples/graphs/storm.py:27`) — replaced by precisely contracted escape hatches.

Despite these differences, the sources converge on four things: recency is sacred, tool-call/result pairs must never be split, tool outputs are capped at ingestion time, and summarization faithfulness is prompt-engineered but never programmatically verified. They also converge on three shared weaknesses: nobody reconciles local estimates against actual provider-reported usage, nobody verifies that summaries preserved what matters, and context-window sizes are hand-maintained tables or hardcoded values nearly everywhere.

## Core Thesis

Token budgeting maturity tracks **ownership of the agent loop**, not codebase size or language. The two systems that own the loop and treat compaction as a first-class subsystem (agent-framework, letta) are the only ones that measure context before it reaches the wire — and even they only estimate. Systems built on top of provider APIs that expose server-side compaction (pydantic-ai, openai-agents-sdk) show that delegation can be safe when the framework rigorously owns what delegation cannot do: defining where the compacted boundary is, replaying derived state from post-compaction windows, and making history replacement transactional. Systems that neither own nor delegate cleanly (crewai's error-triggered recovery; openhands' cosmetic meters) leave overflow protection to luck or user vigilance. LangGraph demonstrates that deliberate absence can be well-engineered — its `pre_model_hook`, `llm_input_messages`, and `INVALID_CHAT_HISTORY` guard make user-implemented trimming *safe* (langgraph, `libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py:243-271`) — but against this dimension's question the honest answer is still no: nothing measures tokens, so nothing can react to overflow at all.

The deepest finding is what everyone lacks. No source closes the calibration loop between estimated and actual tokens (agent-framework explicitly searched for usage feeding compaction decisions and found zero matches, `python/packages/core/tests/core/test_observability.py:200`; letta's estimate is simply the previous response's reported usage, `letta/agents/letta_agent_v3.py:1306-1307`). No source validates summary content programmatically. And every system encodes context-window knowledge as hand-curated constants — crewai across six files (`llm.py:168-229` plus five provider modules), openai-agents-sdk as compiled literals (`src/agents/sandbox/capabilities/compaction.py:25-115`), pydantic-ai not at all ("thresholds are blind guesses relative to the actual window"). These three gaps define the current frontier of the discipline.

## Approach Models

The seven approaches cluster into four families:

**Family A — Owned local compaction engines** (measure and shape context inside the framework):
- **agent-framework**: conversation grouped into atomic units (system/user/assistant_text/tool_call/summary), tokens annotated per message (real tokenizer if supplied, else chars÷4), strategies exclude whole groups until budget satisfied. A two-phase `ContextWindowCompactionStrategy` evicts tool results into bounded summaries at 50% of input budget and truncates oldest-first at 80%; LLM summarization is separate opt-in with provenance links (agent-framework, `_compaction.py:1651-1702`, `1197-1397`). Budgets configurable per client, agent, and run.
- **letta**: a per-agent context estimate from the last provider usage report is compared against a per-model threshold (90% proactive for GPT-5-family, 100% otherwise), triggering one of four compaction modes with cascading fallbacks and post-compaction verification (letta, `letta/services/summarizer/thresholds.py:27-41`; `letta/services/summarizer/compact.py:189-346, 359-412`). Counters abstracted behind a `TokenCounter` factory: native count APIs for Anthropic/Gemini (Redis-cached), tiktoken for OpenAI-compatible, bytes÷4×1.3 default (`letta/services/context_window_calculator/token_counter.py:268-316`).

**Family B — Boundary owners delegating compression to providers**:
- **pydantic-ai**: `UsageLimits` checked before each request, after each response, mid-stream, and mid-continuation, raising `UsageLimitExceeded` fail-fast (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:1600-1621, 1786-1795`; `pydantic_ai_slim/pydantic_ai/result.py:1047-1062`). Compression wraps OpenAI/Anthropic server-side compaction behind a neutral `CompactionPart`; the framework owns wire-trim semantics and recomputes all derived state from `post_compaction_window` (`pydantic_ai_slim/pydantic_ai/models/__init__.py:2072-2131`). Model-agnostic strategies are a user extension point (`ProcessHistory`).
- **openai-agents-sdk**: four independent mechanisms — post-hoc `Usage` accounting, server compaction via `context_management.compact_threshold` or a session wrapper with transactional replacement (`src/agents/memory/openai_responses_compaction_session.py:271-336`), opt-in `ToolOutputTrimmer` input filter, beta handoff-transcript summarization (`src/agents/run_config.py:374-381`). Overflow surfaces as explicit `ModelBehaviorError` on empty length-truncated completions (`src/agents/models/openai_chatcompletions.py:328-343`).

**Family C — Reactive recoverers**:
- **crewai**: overflow detected post-hoc by matching vendor error phrases; executor then either replaces every non-system message with a chunked, structured LLM summary or aborts via `SystemExit` depending on `respect_context_window` (crewai, `lib/crewai/src/crewai/utilities/agent_utils.py:795-832, 1048-1131`). Budget sizing from a per-model window table × 0.85 ratio, used only inside recovery.

**Family D — Observers and abstainers**:
- **openhands**: frontend renders server-reported fill with 70%/90% thresholds and offers a manual condense endpoint whose completion is event-sourced — a `Condensation` event plus a measured token drop, with honest `no_change`/`timeout` outcomes (openhands, `src/hooks/use-await-context-compaction.ts:96-110, 150-154`).
- **langgraph**: provides append/upsert/tombstone reducer semantics, a non-destructive `llm_input_messages` view for hooks, step budgets (`recursion_limit`, `RemainingSteps` graceful degradation), and checkpoint-storage compression — none of which touch prompt size (langgraph, `libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py:396-424, 684-692`; `libs/langgraph/langgraph/channels/delta.py:25-64`).

## Pattern Catalog

### 1. Atomic tool-call groups with referential-integrity guards
- **Problem**: trimming history naively orphans tool results from their calls, producing provider API errors mid-conversation.
- **Demonstrated by**: agent-framework links declarations and results into indivisible groups via union-find over `call_id`s (`_compaction.py:105-198, 253-297`); langgraph raises `INVALID_CHAT_HISTORY` before any model call if a trimmed history has an unpaired tool call (`chat_agent_executor.py:243-271`); letta constrains eviction cutoffs to assistant/approval messages so tool groups stay intact (`summarizer_sliding_window.py:156-161`); openai-agents-sdk strips orphaned assistant IDs after reasoning-item drops and defers compaction past turns with fresh tool outputs (`openai_responses_compaction_session.py:458-484`; `run_internal/session_persistence.py:656-696`); pydantic-ai documents the same hazard for user-authored slicing (`docs/message-history.md:780-781`).
- **Why it works**: it converts a class of remote, hard-to-debug provider errors into local, typed, pre-flight failures.
- **Copy when**: any truncation, sliding-window, or summarization feature touches conversation history. **Risky when**: ignored — five independent sources identified this as the primary corruption vector.
- **Evidence**: agent-framework tests atomicity directly (`tests/core/test_compaction.py:209-344`).

### 2. Graduated degradation ladders instead of a single cliff
- **Problem**: one-shot compression either under-shoots or destroys too much.
- **Demonstrated by**: agent-framework composes eviction→truncation→deterministic fallback with re-measurement between steps and early stop at budget (`_compaction.py:1400-1472`); letta cascades `self_compact_all → self_compact_sliding_window → all` then verifies against the trigger threshold with further fallback (`summarizer/compact.py:189-346, 359-381`); openai-agents-sdk's trimmer picks the largest informative header that fits and downgrades compaction modes automatically (`tool_output_trimmer.py:308-332`; `openai_responses_compaction_session.py:589-604`); crewai splits oversized messages into `[Part i/n]` chunks within its summarizer (`agent_utils.py:855-885`).
- **Why it works**: cheaper, lossier steps handle common cases; expensive or destructive steps fire only on verified failure.
- **Copy when**: compression failure is worse than partial success. **Overkill when**: context shape is simple and bounded (e.g., fixed tool schemas only).
- **Evidence**: letta records which mode actually ran in `compaction_stats`, keeping the ladder debuggable (`summarizer/compact.py:189, 431`).

### 3. Non-destructive projection over deletion
- **Problem**: compressed history should not destroy the authoritative record.
- **Demonstrated by**: agent-framework flags messages `_excluded` with machine-readable reasons while originals persist (`_compaction.py:33-34, 718-724`); langgraph's `llm_input_messages` changes what the model sees without mutating persisted state (`chat_agent_executor.py:400-409, 636-658`); letta keeps evicted messages queryable in recall storage; openai-agents-sdk treats clear→rewrite as one transaction with restore-on-cancel (`openai_responses_compaction_session.py:271-336`).
- **Why it works**: auditability, resumability, and the ability to re-read original content in later turns survive aggressive context reduction.
- **Copy when**: durability matters (long-lived agents, compliance). **Cost**: unbounded storage growth — accepted explicitly by both agent-framework and letta.

### 4. Ingestion-time capping of tool outputs
- **Problem**: a single giant tool result can blow the budget before any conversation-level mechanism engages.
- **Demonstrated by**: letta dynamically caps tool returns at ~20% of the context window plus per-tool char limits (`letta_agent_v3.py:143-153, 1714-1746`); openai-agents-sdk truncates sandbox output head+tail under a bytes÷4 policy and offers per-tool `max_output_tokens` (`sandbox/util/token_truncation.py:73-113`); pydantic-ai cuts fetched web content at 50k chars with an explicit marker (`common_tools/web_fetch.py:135-136`); agent-framework caps deterministic tool-result summaries at 4096 chars (`_compaction.py:983-986`).
- **Why it works**: bounding inputs makes downstream budgets tractable; compaction rarely has to fight individual giant messages.
- **Copy always.** **Risk**: caps disconnected from real budgets (pydantic-ai notes its ~4-chars/token heuristic, `web_fetch.py:175-176`).

### 5. Recency anchoring and protected message classes
- **Problem**: eviction must not discard the state the agent is actively using.
- **Demonstrated by**: agent-framework keeps the newest N tool-call groups verbatim and never excludes the last non-system group (`_compaction.py:1665, 778-786`; .NET floor `SummarizationCompactionStrategy.cs:64-67`); openai-agents-sdk's trimmer protects everything after the last recent-turn user message and excludes user messages from compaction candidates (`tool_output_trimmer.py:204-220`; `openai_responses_compaction_session.py:42-55`); letta protects pending approvals and their preceding assistant turn (`self_summarizer.py:265-289`); crewai preserves system messages verbatim and re-attaches files to summaries (`agent_utils.py:1069-1131`); pydantic-ai replants the standing prompt unless provably retained (`models/__init__.py:2099-2106`).
- **Why it works**: positional recency is a cheap, robust proxy for relevance that requires no scoring model.
- **Copy universally.**

### 6. Outcome-honest compaction observability
- **Problem**: silent compression hides both failures and information loss.
- **Demonstrated by**: openhands distinguishes `compacted`/`no_change`/`timeout` rather than reporting false success (`use-await-context-compaction.ts:150-154`); letta packs trigger, token counts, and mode used into stream events (`system.py:207-239`); agent-framework stamps every exclusion with a reason string enabling negative assertions in tests (`test_compaction.py:1835-1839`); openai-agents-sdk logs trimmed char counts and folds compaction cost into run usage (`tool_output_trimmer.py:195-200`; `openai_responses_compaction_session.py:240-242`).
- **Why it works**: compaction is where information silently dies; observability is the only mitigation available without semantic verification.
- **Copy always.**

### 7. Tiered token-counter abstraction
- **Problem**: exact counting needs provider calls or tokenizer dependencies; estimation drifts.
- **Demonstrated by**: letta's `create_token_counter` factory selects native count APIs (Anthropic/Gemini, Redis-cached 1h TTL) vs tiktoken vs bytes÷4 with a documented 1.3× safety margin (`token_counter.py:268-316`; `summarizer_sliding_window.py:21-42`); agent-framework accepts any `TokenizerProtocol` with a chars÷4 default (`_compaction.py:51-80`); pydantic-ai defines abstract `Model.count_tokens` implemented on exactly four adapters, raising `NotImplementedError` elsewhere (`models/__init__.py:518-526`).
- **Why it works**: accuracy where it pays (tight thresholds, cached counts), speed everywhere else.
- **Copy when**: multi-provider. **Risk**: the approximate tier becomes permanent — none of the three wires a real tokenizer by default.

### 8. Cache-prefix awareness as a budget constraint
- **Problem**: naive per-request context shaping invalidates prompt caches, turning token savings into cost increases.
- **Demonstrated by**: pydantic-ai keeps the `search_tools` slot stable across turns specifically to preserve the cacheable prefix and treats moving injection anchors as review-blocking regressions (`toolsets/_tool_search.py:362-377`; `models/AGENTS.md` rule 478); letta's self-compaction deliberately matches parallel-tool-call flags and tool schemas "for cache compatibility" (`self_summarizer.py:100-118`).
- **Why it works**: cached-prefix tokens are dramatically cheaper; a budget strategy blind to cache boundaries optimizes the wrong number.
- **Copy when**: prompts exceed cache breakpoints. **Overkill when**: conversations are short.

## Key Differences

**What converges despite different implementations:** All six sources that touch conversation content protect structural integrity (Pattern 1) and recency (Pattern 5). All cap tool outputs at ingestion (Pattern 4). All rely on provider-reported usage for *accounting*; none uses it to calibrate *budgets*. None gates the first call of a turn by default: agent-framework measures heuristically every call but never reconciles; letta uses the prior response's number (`letta_agent_v3.py:1306-1307`); pydantic-ai's pre-request counting is opt-in and costs an extra round trip (`usage.py:459-472`); crewai, langgraph, and openhands do nothing before sending.

**Why they diverge:**
- **Product shape.** Letta and openhands are products; the loop owner can and must own compaction (letta builds four modes; openhands' frontend cannot enforce anything and honestly doesn't try). LangGraph is a runtime library that treats message history as durable graph state — destructive trimming conflicts with its checkpoint/time-travel value proposition, hence non-destructive views instead (`chat_agent_executor.py:400-409`).
- **Provider coupling.** Single-vendor SDKs (openai-agents-sdk, pydantic-ai's OpenAI/Anthropic paths) can lean on server-side compaction endpoints that don't exist elsewhere. Multi-provider frameworks (crewai, letta, agent-framework) need portable mechanisms: phrase-list error matching (`context_window_exceeding_exception.py:4-13`), mapped exception types (`ContextWindowExceededError`), or local projection engines.
- **Durability requirements.** Where transcripts are the product (langgraph checkpoints, letta recall storage, agent-framework audit exclusions), nothing is ever deleted. Where sessions are mutable infrastructure, openai-agents-sdk engineers replacement-with-rollback instead.
- **Maturity and legacy.** Letta carries three generations of agent loops including a dead legacy path with broken imports (`letta/agent.py:35` imports names that don't exist); crewai has a default mismatch between agent (`respect_context_window=True`) and executor (`False`) layers (`agent/core.py:251-254` vs `agents/crew_agent_executor.py:126`); openai-agents-sdk beta-gates handoff summarization. These are maturity artifacts, not quality verdicts on the current architecture.
- **Frontend/backend split.** OpenHands proves that a clean observer role can be excellent engineering (race-safe baselines captured before POST dispatch, `use-compact-context-action.ts:83-88`) while still failing the dimension's question, because observation without autonomy cannot prevent overflow.

## Tradeoffs

- **Estimate-before-every-call vs trust-the-provider.** Agent-framework measures per call but with chars÷4 accuracy and zero reconciliation against returned usage; letta and crewai accept one failed round trip as the price of provider ground truth; pydantic-ai offers exact pre-request counting but bills an extra API call and covers 4 of ~30 adapters. Source A (agent-framework) gains determinism; Sources B/C gain accuracy at latency's expense.
- **Wholesale summarization vs selective graduated eviction.** CrewAI replaces the entire dialogue with one structured summary — preserving global task coherence but destroying verbatim detail (tool outputs become `"[Called tools: <names>]"`, `agent_utils.py:918-940`) and costing O(full history) per recovery. Agent-framework's group-level exclusion preserves detail at the cost of configuration surface and overshoot risk when one group alone exceeds budget (documented at `_compaction.py:805-807`).
- **Fail-fast vs compress-and-continue vs hard exit.** Pydantic-ai aborts the run on limit violation — spend-safe, availability-hostile. Letta compresses and continues, degrading to a logged-critical-but-proceeding state when compaction can't get under threshold (`compact.py:409-410`). CrewAI's `respect_context_window=False` path is a cliff: `SystemExit` (`agent_utils.py:830-832`) rather than truncate-and-continue.
- **Opaque delegated summaries vs auditable local ones.** OpenAI compaction returns an encrypted blob with `content=None` — unfalsifiable and uninspectable (pydantic-ai, `messages.py:1996-2005`); agent-framework summaries carry bidirectional ID links to originals (`_compaction.py:35-37, 1374-1392`); letta embeds stats and lookup hints. Control and auditability trade directly against fidelity of provider-native summarization.
- **Never-delete vs replace-with-rollback.** Agent-framework/langgraph/letta keep everything and grow storage; openai-agents-sdk replaces session history but must engineer restoration for cancellation mid-replacement (`openai_responses_compaction_session.py:271-336`) — and acknowledges that if both replacement and restore fail, history is lost with only a warning (`docs/sessions/index.md:289`).
- **Absolute vs relative budgets.** Pydantic-ai's thresholds are absolute token counts that become guesses because profiles carry no context-window metadata; letta and agent-framework express triggers as fractions of a configured window (90%, 50%/80%), which survives new models but requires the window itself to be known.

## Decision Guide

Choose your approach by answering four questions:

1. **Do you own the model call site?**
   - Yes, multi-provider → build an owned engine like agent-framework's: grouping + annotation + composed strategies + deterministic fallback (`_compaction.py:1400-1472`).
   - Yes, single-provider with compaction APIs → wrap the provider like pydantic-ai/openai-agents-sdk, but own the boundary semantics: define the compacted-window rule and recompute derived state from it (`messages.py:2774-2814`).
   - No (thin client) → be an excellent observer: honest outcomes, race-safe completion detection, schema-forwarded config (openhands pattern).
2. **Is the transcript a durable artifact?** If yes, project, never delete (flags/views/recall storage). If sessions are disposable infrastructure, transactional replacement with rollback is acceptable — but test cancellation paths (openai-agents-sdk dedicates ~350 test lines to restore-on-cancel, `tests/memory/test_openai_responses_compaction_session.py:1080-1190`).
3. **Can you tolerate a failed call?** If no, you need pre-flight measurement — which today means accepting heuristic accuracy (agent-framework) or extra provider count calls (pydantic-ai). If yes, reactive triggers with a bounded retry loop are simpler and exact (letta, `letta_agent_v3.py:1218-1251`).
4. **Is provider breadth required?** Cross-provider portability forces local mechanisms (estimation, phrase-matching); provider lock-in buys server-side fidelity.

Universal rules regardless of choice: express thresholds relative to a configured window; cap tool output at ingestion; protect recency and tool-pair structure; instrument outcomes; centralize window-size metadata in one place (nobody in this study fully does).

## Practical Tips

**Patterns to copy now:**
- Cap tool returns at ingestion time with explicit markers — cheapest defense, demonstrated in four sources (letta's dynamic 20%-of-window cap is the most sophisticated, `letta_agent_v3.py:143-153`).
- Stamp every exclusion/compression with a machine-readable reason and emit compaction events; it enables both debugging and negative test assertions (agent-framework `_exclude_reason`, letta `LettaCompactionEvent`).
- Make compaction completion event-sourced and outcome-typed rather than assuming the HTTP response means done (openhands, `use-await-context-compaction.ts:57-61`).
- Add a safety margin to any estimator and document its measured error — letta states bytes÷4 "underestimates by ~25-35%" and applies 1.3× (`summarizer_sliding_window.py:21-24`).
- Validate history integrity after any user/hook-driven mutation, before the provider sees it (langgraph's `INVALID_CHAT_HISTORY` guard is the cleanest implementation).
- Route summarization to a cheap, fast model distinct from the agent's (letta defaults Haiku/GPT-5-mini/Gemini Flash, `summarizer_config.py:11-32`).

**Delay until needed:**
- LLM-backed summarization strategies — deterministic eviction/truncation handles most growth; treat summarization as opt-in with security documentation of the prompt-injection risk (agent-framework, `_compaction.py:1207-1217`).
- Multi-mode fallback ladders — start with one mode plus verification; add cascades when failure data justifies them.
- Semantic faithfulness verification — no source has it; structured prompts + provenance links + retrieval escape hatches are the current best practice (letta's "lookup hints", `prompts/summarizer_prompt.py:22-45`).
- Auto-compaction triggers in UI clients — the plumbing is reusable, but decide the policy after observing fill distributions (openhands has everything except the trigger).

## Anti-Patterns / Caution Signs

- **Error-string matching as the only overflow detector** (crewai): portable but fragile across vendor wording changes; acceptable as a fallback layer, dangerous as the sole mechanism (`context_window_exceeding_exception.py:4-13`).
- **Default mismatches between layers**: crewai's `Agent.respect_context_window=True` vs `CrewAgentExecutor.respect_context_window=False` means any path that skips constructor wiring silently switches to abort-on-overflow (`agent/core.py:1160` vs `crew_agent_executor.py:126`).
- **Dead configuration surface**: letta's `desired_memory_token_pressure`, `keep_last_n_messages`, and `evict_all_messages` have zero consumers — configuring them does nothing (`settings.py:91-111`). Caution sign: settings files growing faster than their wiring.
- **Legacy generations coexisting with broken imports**: importing `letta.agent` raises ImportError due to missing definitions (`letta/agent.py:35`), yet the module is still imported by a live router — dead budget code that can detonate.
- **Summarize-the-summary loops without shrinking targets**: crewai re-summarizes the previous summary on repeated overflow with no "already compacted" guard or decreasing budget (`crew_agent_executor.py:444-460`).
- **Merge heuristics that hide spikes**: openhands takes `Math.max` for `per_turn_token` across usage components, so a sub-agent holding more context than the main agent masks the true total (`conversation-websocket-context.tsx:244-260`).
- **Thresholds above the actual window, unvalidatable**: pydantic-ai cannot check a compaction threshold against the model's real window because profiles lack the metadata — a misconfiguration silently never triggers.
- **Static percentage thresholds late-firing on small windows**: openhands' 70/90% constants assume large contexts; on a small-window model one turn can jump tens of percent (`context-meter.tsx:7-21`).
- **Single oversized items passing through**: agent-framework documents that one group exceeding the whole budget still reaches the wire (`_compaction.py:805-807`); crewai handles this better by splitting oversized messages (`agent_utils.py:855-885`).
- **Unbudgeted adjacent injection paths**: crewai concatenates upstream task outputs verbatim into the next task's prompt with no cap (`formatter.py:13-45`) — context pressure entering where per-turn machinery never looks.

## Notable Absences

Across all seven sources, no evidence was found of:
- **Estimate↔actual reconciliation**: no source feeds provider-reported usage back to correct its estimator (agent-framework searched explicitly, zero matches; letta substitutes prior-response usage for estimation entirely).
- **Programmatic faithfulness verification of summaries**: verification is always structural (provenance links, replay normalization, tag extraction) or numeric (token deltas), never semantic. OpenAI-path compaction summaries are literally unreadable client-side (encrypted blobs, pydantic-ai `messages.py:1996-2005`).
- **Relevance-scored selection of general conversation sections**: ranking exists only outside the transcript path — crewai's memory-recall composite score (`memory/types.py:345-380`) and pydantic-ai's tool-search ordering (`toolsets/_tool_search.py:465-483`). Within history, priority is always positional (recency) or class-based (protected types).
- **A unified budget object coordinating all mechanisms**: openai-agents-sdk names the gap itself — `max_tokens`, `compact_threshold`, trimmer limits, and session limits are never tied together; its own future-work list proposes a `ContextBudget`.
- **Automatic context-window resolution from model identity**: crewai maintains six hand-curated tables; openai-agents-sdk compiles literals and raises on unknown models (`compaction.py:128-133`); agent-framework requires callers to hardcode; only letta ships both a required per-agent field and a broad catalog (`schemas/llm_config.py:65`; `constants.py:249-284`), and only openhands receives it from the server at runtime.
- **Pre-send draft awareness in user-facing input paths**: openhands' composer does not warn about oversized submissions; no source measures what the human is about to cause.

## Per-Source Notes

- **agent-framework (8/10)**: The reference implementation for owned compaction. Grouping engine with union-find linking, incremental suffix-only retokenization, exclusion reasons as an audit vocabulary, deterministic last-resort fallback guaranteeing a non-empty projection, and full dual-language parity (.NET adds turn-count triggers and session-persisted indexes Python lacks). Weaknesses are estimator crudeness and missing usage feedback.
- **crewai (6/10)**: Recovery-over-prevention philosophy taken to its conclusion: litellm path deliberately re-raises so the executor chooses summarize-vs-abort (`llm.py:1909-1913`). Well-tested chunking/preservation mechanics; undermined by no gating, all-or-nothing granularity, the SystemExit cliff, and stale docstrings/constants (75% documented, 85% enforced).
- **langgraph (3/10)**: Absence by design, engineered responsibly. `pre_model_hook` + `llm_input_messages` + tombstone-validating reducers + `INVALID_CHAT_HISTORY` give users safe DIY tools; step budgets (`recursion_limit=10007` default, `RemainingSteps` graceful exit) bound loops, not context. Storage-side `DeltaChannel` shows where compression effort went — checkpoints, not prompts.
- **letta (7/10)**: Broadest feature set: counter factory with caching, model-specific proactive thresholds, four compaction modes with verified fallbacks, protected approval messages, per-section token observability API, byte-aware middle truncation, cheap-summarizer routing. Dragged down by reactive-first measurement, approximate OpenAI counting, inert config knobs, and the dead v1 loop.
- **openai-agents-sdk (7/10)**: Deepest engineering on delegation safety: transactional session replacement with shielded restore, deferred compaction for turn consistency, orphan-ID stripping for replay validity, marker-delimited re-parseable handoff summaries that survive re-summarization. Fragmentation is the weakness: four mechanisms, three unit systems, no coordinator.
- **openhands (6/10)**: Best-in-class honest UX for an enforcer-less position: exported/tested thresholds, unknown-window guards, outcome taxonomy, pre-dispatch race baselines, disabled-during-run safeguards. Its limits are constitutional: no client counting, cosmetic danger signals, faithfulness checks reduced to a token delta.
- **pydantic-ai (7/10)**: Cleanest separation of concerns: limits are enforcement, providers are compression, the framework owns boundaries and derived-state recomputation (`post_compaction_window` feeding tool discovery and capability loading). Cache-prefix rules elevated to reviewed engineering standards. Costs: post-hoc default, four-adapter counting coverage, absolute-token thresholds without window metadata.

## Open Questions

- **Where did LangGraph's official trimming go?** The deprecated `create_react_agent` points to `create_agent` in the external `langchain` package (`chat_agent_executor.py:53-56`); no successor exists in-tree. Does anything in the closed-source LangGraph Server bound request size?
- **What does OpenHands' `condenser_max_size: 240` mean?** Units are indeterminate from frontend code (backend schema says "tokens kept after summarization", but the magnitude suggests another unit — `mocks/settings-handlers.ts:333`); whether the server auto-condenses mid-task, and how it picks eviction candidates, is invisible from this repo.
- **Does Letta's streaming fallback counter feed compaction?** The tiktoken-based counters in `openai_streaming_interface.py:130-141` appear diagnostic-only; the compaction estimate provably comes from adapter usage, but end-to-end tracing was inconclusive.
- **Which provider error strings map to overflow, exhaustively?** Letta spot-checked four clients; CrewAI's phrase list covers known vendors but nothing enumerates coverage or tests against future wording changes.
- **Does agent-framework's five-sentence summary constraint preserve task-critical detail over long horizons?** Tests assert structural properties only; summary quality is untested (`tests/core/test_compaction.py` asserts links/bounds/failure handling).
- **What do pydantic-ai's external harness strategies actually do?** Tiered escalation, `WarnNearLimits`, and `ToolOutputLimits` live in the out-of-tree `pydantic-ai-harness` package (`README.md:41-72`) and could not be verified.
- **Are CrewAI summaries auditable?** No evidence of persistence, events, or logging of compactions; and nothing bounds how many times compaction may recur within one task beyond generic iteration limits.
