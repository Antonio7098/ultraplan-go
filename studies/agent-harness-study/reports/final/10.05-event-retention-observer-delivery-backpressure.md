They are patterns for *running* this kind of study, not for building event systems.

### P1. Fail-fast preflight for degenerate sources

- **Problem:** an orchestration pipeline that selects sources for analysis can silently ingest an empty or mis-staged snapshot, producing a full-length report with zero information gain — discovered only after spending an entire analysis run.
- **Sources:** reports (this corpus). The per-source report's Future Considerations recommend exactly this guard: "fail fast (or emit a warning status) when a selected source contains 0 files" (`…/reports.md:106`).
- **Why it works:** it moves detection from post-analysis (expensive, ambiguous) to pre-analysis (cheap, unambiguous). A zero-file check cannot produce false positives on a materialized tree.
- **Copy when:** any multi-stage pipeline where upstream staging populates inputs consumed by downstream analysis stages.
- **Overkill/risky when:** sources are legitimately allowed to be partial — then use a warning status plus an explicit marker (P3 below) rather than hard failure.

### P2. Staging-name/dimension correspondence checks

- **Problem:** a snapshot staged for one dimension can be reused (or left behind) for another, and nothing in a bare directory listing reveals the mistake until analysis time.
- **Sources:** reports (this corpus). The lone staged subdirectory is named `07.04-timeouts-and-cancellation` while the task targeted 10.05; the report flags this as a probable staging mismatch and recommends cross-checking names against the dimension id (`…/reports.md:88,99,107`).
- **Why it works:** naming conventions are cheap machine-checkable metadata; verifying them catches the failure mode where "presence of a path" masks "absence of relevant data."
- **Copy when:** snapshots are staged per-dimension by automated tooling.
- **Limit:** a matching name proves intent, not content — pair it with the zero-file preflight (P1), which this report's own recommendations do by listing both (`…/reports.md:105-107`).

### P3. Explicit "insufficient data" markers in aggregates

- **Problem:** rubric scores are defined over implemented behavior; feeding them a non-implemented source yields numbers that look commensurate but are not.
- **Sources:** reports (this corpus): "Any aggregate scoring across sources should treat this as 'not measurable' rather than 'measured poorly'" (`…/reports.md:98`), operationalized as a distinct marker in comparative outputs (`…/reports.md:108`).
- **Why it works:** it preserves the semantic meaning of low scores (implemented but weak) versus absent measurements (nothing staged), keeping averages and rankings honest.
- **Copy when:** any scoring rubric can encounter unanalyzable inputs.
- **Cost:** slightly more complex aggregation logic; negligible compared with the cost of a corrupted comparison.

The one tradeoff the corpus does document — and which study operators will actually face — is **run-anyway vs fail-fast on a degenerate input:**

- **Run anyway with an honest gap report.**
  - *Benefit:* the absence itself becomes durable, auditable evidence (search boundaries recorded per question, anomaly flagged); downstream stages are never blocked waiting for restaging (`…/reports.md:23,35,96-99`).
  - *Cost:* an analysis run is spent producing no dimension knowledge; the emitted numeric score risks misreading by aggregators unless annotated (`…/reports.md:98`).
  - *Best fit:* exploratory runs, or when restaging turnaround is slow and you want the gap formally on record.
  - *Failure mode:* silent ingestion into means/rankings — precisely why the report demands the insufficient-data marker (`…/reports.md:108`).
- **Fail fast at preflight.**
  - *Benefit:* no wasted analysis runs; forces the upstream fix (re-stage, `…/reports.md:105`) before any downstream work.
  - *Cost:* blocks the pipeline; requires the preflight step to exist (`…/reports.md:106`).
  - *Best fit:* production study pipelines where analysis compute matters and staging is expected to be reliable.
  - *Alternative seen:* this corpus effectively exercised the first option and recommended adding the second (`…/reports.md:101-108`) — the two are complementary, with the gap report serving as the fallback artifact when preflight warnings are overridden.
