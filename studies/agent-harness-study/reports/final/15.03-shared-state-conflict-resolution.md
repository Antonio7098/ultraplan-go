## Executive Summary

Six harnesses were studied for what agents share (memory, tools, artifacts, plans, workspaces) and how conflicts over those shared resources are detected and resolved. The central finding is a strong convergence on **prevention over resolution**: every source avoids concurrent writes to one resource — through execution barriers, write serialization, namespace partitioning, or isolation defaults — rather than merging conflicting writes at runtime. Where independent writers genuinely cannot be prevented from racing (durable storage shared across processes), all sources that handle it well converge on the same recipe: optimistic concurrency detection plus bounded retry-with-backoff inside the storage adapter.

Three results stand out. First, **execution-engine ownership predicts conflict-handling quality**: langgraph and agent-framework control scheduling and therefore can stage writes and commit them atomically at superstep boundaries (langgraph: `libs/langgraph/langgraph/pregel/_algo.py:232-345`; agent-framework: `python/packages/core/agent_framework/_workflows/_runner.py:160-168`), turning conflict semantics into declarative, tested contracts. Second, **shared-by-reference user state is the universal weak spot** — openai-agents-sdk's run context (`docs/context.md:28-30`), crewai's live Flow state (`lib/crewai/src/crewai/flow/runtime/__init__.py:3157-3165`), and pydantic-ai's cross-thread `RunUsage` all have zero coordination machinery; correctness is outsourced to application code. Third, **conflict observability is immature everywhere**: not one of the six sources ships a dedicated, queryable conflict log; visibility ranges from typed lifecycle events (crewai) to OTel spans (pydantic-ai) to Debug-level logs or silence (the rest).

Ratings span 6–8. langgraph leads (8) because its channel/reducer model makes conflicts fail fast with error codes and its behavior is directly unit-tested. agent-framework, crewai, and openai-agents-sdk score 7 with different strengths (barrier commit discipline + ETag checkpoint concurrency; distributed lock service + LLM semantic arbitration; per-backend OCC adapters with three-tier tests). openhands (6) and pydantic-ai (6) both disclose their gaps honestly but lack mechanical protection where it matters most — file writes between agents and cross-thread/cross-process budget sharing respectively.

## Core Thesis

Conflict handling maturity tracks how much of the concurrency surface the framework owns.

Frameworks that own an execution engine (langgraph's Pregel loop, agent-framework's superstep runner, pydantic_graph's iterator) can *eliminate* mid-step interleaving by construction: writes buffer per task and commit at a barrier, so "conflict" becomes a question answered deterministically by declared merge policy or rejected loudly. Libraries that merely coordinate object references (openai-agents-sdk handoffs sharing one context, pydantic-ai passing `usage=ctx.usage`) cannot enforce anything at await points they don't control, so they document sharing and push safety to users. Applications built above an out-of-boundary runtime (openhands frontend, whose agent loop lives in a sibling server) fall back to avoidance (git worktrees), dedup, idempotency ledgers, and disclosure.

Across process boundaries every source converges on the same answer — push arbitration into the storage backend: ETag preconditions (agent-framework Foundry store, openai-agents-sdk Dapr), Redis `WATCH/MULTI` (openai-agents-sdk), generation counters (openai-agents-sdk MongoDB), commit-conflict retries (crewai LanceDB), or plain last-write-wins upserts where no versioning exists (langgraph Store, agent-framework file stores). And on observability, all six fail identically: detected-and-resolved conflicts leave little or no durable trace, which means contention is invisible until something raises.

## Approach Models

- **langgraph — declarative merge policy as schema metadata.** Every state key maps to a channel whose class owns the conflict contract: `LastValue` rejects ≥2 values per step, `BinaryOperatorAggregate` folds them, `Topic` accumulates, `NamedBarrierValue` rendezvous-synchronizes (`libs/langgraph/langgraph/channels/last_value.py:56-64`, `channels/binop.py:123-144`, `channels/named_barrier_value.py:69-75`). Conflict detection is centralized per channel class, tagged `INVALID_CONCURRENT_GRAPH_UPDATE` (`libs/langgraph/langgraph/errors.py:36`). Cross-thread memory via `BaseStore` is deliberately minimal and pushes concurrency control to backends (`libs/checkpoint/langgraph/store/base/__init__.py:708-754`).
- **agent-framework — layered sharing with prevention-first policy.** Workflow KV state stages writes in pending buffers committed at superstep boundaries (Python `State`, `.NET StateManager`: `python/packages/core/agent_framework/_workflows/_state.py:6-127`, `dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StateManager.cs:13-16`); orchestrations share a mutex-protected conversation with bookmarks (`dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/MultiPartyConversation.cs:11-69`); concurrency itself is gated by an opt-in `declareCrossRunShareable` contract enforced at runner construction (`dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs:47-51`). Merge semantics are fixed last-write-wins by documented design (`_state.py:36-42`).
- **crewai — partitioned blackboard plus externalized locking.** One physical vector `Memory` namespaced per crew and per agent role (`lib/crewai/src/crewai/crew.py:652-688`), writes serialized through a single-worker pool with a drain-before-read barrier (`lib/crewai/src/crewai/memory/unified_memory.py:165-171,350-363`), cross-process writers arbitrated by a pluggable Redis/file lock factory (`lib/crewai-core/src/crewai_core/lock_store.py:33-54`), and *semantic* content conflicts resolved by an LLM emitting a typed keep/update/delete plan (`lib/crewai/src/crewai/memory/analyze.py:103-141,321-375`).
- **openai-agents-sdk — reference-shared context, adapter-owned durability.** One user context object plus SDK runtime metadata is shared by reference across handoffs and nested runs with no synchronization (`src/agents/run_context.py:72-115`); all real conflict machinery lives in `Session` persistence adapters encoding each backend's native mechanism — Dapr etags, Redis transactions, Mongo generations, SQLite locks (`src/agents/extensions/memory/dapr_session.py:250-287`, `redis_session.py:506-517`, `mongodb_session.py:273-286`, `sqlite_session.py:118-142`).
- **openhands — client-tier avoidance and disclosure.** No locks exist in the frontend; conflicts are avoided by defaulting child conversations to git-worktree isolation (`src/services/child-conversation-launch.ts:276-298`), absorbed by event-id dedup and atomic store transitions (`src/stores/use-event-store.ts:99-107`), prevented for billable side effects by a localStorage claim-before-work ledger (`child-conversation-launch.ts:196-227`), and delegated to HTTP 409s for named resources. The one unguarded resource — a `shared` workspace — gets a written warning instead of a mechanism.
- **pydantic-ai — explicit aliasing plus serialized reduction.** Nothing is shared implicitly; parents share budgets/deps/history by passing mutable references (`docs/multi-agent-applications.md:20,99-104,211-215`). Parallel graph branches converge through a single iterator task that applies user-chosen reducers serially (`pydantic_graph/pydantic_graph/graph_builder.py:687-726`), resource contention is coordinated by shareable `ConcurrencyLimiter` wrappers with atomic queue bookkeeping (`pydantic_ai_slim/pydantic_ai/concurrency.py:207-219`), and namespace collisions fail eagerly with remediation hints (`pydantic_ai_slim/pydantic_ai/toolsets/combined.py:70-77`).

## Pattern Catalog

### 1. Barrier-commit state staging (superstep buffering)

- **Problem:** concurrent agents writing one state object corrupt each other mid-flight.
- **Demonstrated by:** langgraph (`apply_writes` applies all per-task buffered writes once per superstep, `libs/langgraph/langgraph/pregel/_algo.py:232-345`) and agent-framework (pending buffer + `commit()` at superstep end, Python `_runner.py:160-168`; .NET queued updates published after `Task.WhenAll`, `StateManager.cs:201-233`, `InProcessRunner.cs:347,360`). pydantic_graph is a lighter variant: branch results funnel through one iterator that reduces sequentially (`graph_builder.py:687-726`).
- **Why it works:** there is no interleaving window to reason about; each step sees exactly the previous committed state, which also makes checkpoints trivially consistent (agent-framework additionally refuses to export checkpoints while updates are pending, `StateManager.cs:243-259`).
- **Copy when:** you own the scheduler and steps have a natural boundary.
- **Overkill/risky when:** agents need to observe each other's partial progress within a step, or latency demands immediate visibility.
- **Evidence:** failure-isolation tests confirm rollback semantics in both engines (langgraph `tests/test_pregel.py:5334-5369`; agent-framework `python/packages/core/tests/workflow/test_state.py:210-267`).

### 2. Declared merge policy attached to state keys

- **Problem:** "who wins?" must be answerable before a collision happens, and visible statically.
- **Demonstrated by:** langgraph's `Annotated[type, reducer]` wiring validated at graph compile time (`libs/langgraph/langgraph/graph/state.py:1904-1922`) and pydantic-ai's Join reducers (append/extend/dict-update/sum/first-wins, `pydantic_graph/pydantic_graph/join.py:101-147`).
- **Why it works:** merge semantics become data, reviewable per key; naive fan-out onto a single-value key fails loudly instead of silently dropping writes.
- **Copy when:** multiple producers legitimately write the same key with commutative or order-tolerant merges.
- **Overkill/risky when:** keys have single natural owners — the ceremony adds friction without value.
- **Evidence:** parallel-overwrite rejection is directly tested in langgraph (`tests/test_pregel.py:9333-9368`).

### 3. Optimistic concurrency with bounded retry at the durable boundary

- **Problem:** independent processes/hosts commit to shared durable storage; coarse locks don't scale across hosts.
- **Demonstrated by:** agent-framework Foundry checkpoint index (ETag `ifMatch`, 412/409 → lost-race classification, 8 retries with reread, `dotnet/src/Microsoft.Agents.AI.Foundry.Hosting/FoundryJsonCheckpointStore.cs:218-261`); openai-agents-sdk Dapr etag RMW with 5 retries + jittered backoff (`src/agents/extensions/memory/dapr_session.py:250-287`), Redis `WATCH/MULTI` re-run loops (`redis_session.py:587-617`), Mongo generation counters (`mongodb_session.py:273-286`); crewai LanceDB "Commit conflict" retries with table reopen (`lib/crewai/src/crewai/memory/storage/lancedb_storage.py:128-153`).
- **Why it works:** detection rides the backend's native versioning, so correctness holds wherever the backend does; bounded retries converge without thundering-herd amplification.
- **Copy when:** any shared persistent store accepts writes from more than one process.
- **Overkill/risky when:** single-writer deployments pay complexity for races that can't occur.
- **Evidence:** contended integration test with two Dapr sessions firing 20 parallel appends (`tests/extensions/memory/test_dapr_redis_integration.py:523-570`).

### 4. Avoidance by partitioning and isolation defaults

- **Problem:** the cheapest conflict to resolve is the one that structurally cannot happen.
- **Demonstrated by:** crewai's `/crew/{name}/agent/{role}` memory scopes with read-only slice views (`base_agent_executor.py:31-65`, `memory_scope.py:227-324`); langgraph thread-scoped checkpoints and store namespaces (`checkpoint/base/__init__.py:227-318`); openhands worktree-first child isolation with disclosed fallback (`src/services/child-conversation-launch.ts:252-323`); openai-agents-sdk scope-ID isolation of restored tool states (`src/agents/agent_tool_state.py:87-91`); agent-framework's concurrent orchestrator giving each agent an isolated conversation merged deterministically (`python/packages/orchestrations/.../_concurrent.py:83-136`).
- **Why it works:** removes the shared resource rather than arbitrating it.
- **Copy when:** consumers' views naturally decompose by owner, tenant, thread, or task.
- **Overkill/risky when:** genuine cross-agent collaboration requires reading others' work-in-progress — partitioning then just moves the merge problem to the boundaries.
- **Evidence:** openhands tests pin worktree fallback behavior (`__tests__/services/child-conversation-launch.test.ts:299,324`).

### 5. Fail-fast rejection with actionable errors

- **Problem:** silent winner-picking hides modeling mistakes until they corrupt data.
- **Demonstrated by:** langgraph's `InvalidUpdateError` prescribing the fix ("Use an Annotated key...", `last_value.py:59-64`) with stable error code (`errors.py:36`); pydantic-ai's `UserError` on duplicate tool names pointing at `PrefixedToolset` (`toolsets/combined.py:70-77`); agent-framework's constructor throw listing non-shareable executors (`InProcessRunner.cs:47-51`); crewai's kickoff validators rejecting illegal async/context graphs before launch (`crew.py:840-880`); openai-agents-sdk's refuse-to-guess verdicts returning literal `"conflict"`/`None` for unreconcilable identities (`run_internal/tool_execution.py:1321-1360`, `agent_tool_state.py:224-225`).
- **Why it works:** converts latent corruption into immediate, diagnosable developer feedback.
- **Copy when:** a conflict indicates a modeling error rather than legitimate contention.
- **Overkill/risky when:** availability matters more than strictness — langgraph notes one bad node poisons the whole superstep (`_runner.py:616-634`).
- **Evidence:** each rejection path carries a test in its source report (e.g., `tests/test_channels.py:33-49`).

### 6. Copy-at-the-boundary to stop aliasing

- **Problem:** shared objects leak mutations across logical boundaries (sessions, checkpoints, resumes).
- **Demonstrated by:** agent-framework copy-on-read session snapshots (`_sessions.py:1826-1855`); openai-agents-sdk deep-copying usage/approvals/tool-invocation state at checkpoint boundaries with the exact bug class documented in comments (`src/agents/run_context.py:117-130`); crewai's `__deepcopy__` recreating executors/locks (`unified_memory.py:174-204`); pydantic-ai clone-before-mutate on shared output toolsets (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:1462-1474`) and deepcopy-projected batch-limit checks (`_tool_execution.py:444-452`).
- **Why it works:** identity is severed exactly where logical isolation begins, keeping steady-state sharing cheap.
- **Copy when:** snapshots, resumes, or parallel continuations read the same underlying object.
- **Overkill/risky when:** copies are large and frequent — cost lands on hot paths (pydantic-ai flags heavy aggregation on the iterator's critical path).
- **Evidence:** the openai-agents-sdk comment records the precise failure (shared `Usage` landing tokens on sibling checkpoints) the copy eliminates (`run_context.py:120-124`).

### 7. Idempotency ledgers and first-wins dedup

- **Problem:** replays, redeliveries, and duplicate triggers turn one intended effect into many.
- **Demonstrated by:** openhands claim-before-work localStorage ledger guarding billable launches (`child-conversation-launch.ts:196-227`) plus O(1) event-id Set dedup in the store (`use-event-store.ts:99-107`); crewai collecting one action per record ("first wins") to prevent interleaved delete/update conflicts (`encoding_flow.py:371-412`); openai-agents-sdk treating ambiguous EXEC outcomes as failures rather than blind retries (`tests/extensions/memory/test_redis_session.py:1551`).
- **Why it works:** converts exactly-once worries into checkable claims recorded before side effects.
- **Copy when:** effects are non-idempotent or expensive (billing, launches, cache invalidation).
- **Overkill/risky when:** the ledger itself becomes unsynchronized shared state — openhands documents a multi-tab read-modify-write race in its own ledger (`child-conversation-launch.ts:205-227`).
- **Evidence:** replay-drop pinned by test (`__tests__/services/child-conversation-launch.test.ts:490`).

### 8. Semantic conflict resolution via arbiter with safe fallback (single-source)

- **Problem:** text/memory records can *contradict* without colliding mechanically.
- **Demonstrated by:** crewai alone — cosine-similarity detection above 0.85 (`types.py:185-213`), LLM-produced typed `ConsolidationPlan` (keep/update/delete per record, `analyze.py:103-141`), first-wins action dedup within batches, and fallback-to-insert on LLM failure so user data is never lost (`analyze.py:369-375`).
- **Why it works:** mechanical detectors cannot judge contradiction; a constrained-schema LLM plan keeps decisions auditable while the fallback bounds worst-case damage to duplicates rather than loss.
- **Copy when:** shared knowledge stores accumulate near-duplicate facts from many writers.
- **Overkill/risky when:** records are structured/keyed — ordinary CAS suffices, and LLM arbitration adds nondeterminism and latency (crewai acknowledges both).
- **Evidence:** consolidation thresholds and plans cited at `encoding_flow.py:121-140`, `analyze.py:321-375`.

## Key Differences

**Rejection vs. silent overwrite.** langgraph treats two writers to a single-value key as a programming error and aborts the superstep (`last_value.py:56-64`), while agent-framework resolves the identical situation silently via documented last-write-wins (`_state.py:36-42`) and pydantic-ai's `reduce_dict_update` is last-arrival-wins per key by design (`join.py:118-121`). Same problem shape, opposite philosophies: langgraph bets loud failures teach better schemas; the others bet convention (partition your keys) preserves ergonomics.

**Where conflict logic lives.** langgraph and agent-framework embed it in the engine core (channel classes, `StateManager`); openai-agents-sdk pushes it entirely into per-backend session adapters behind a conflict-agnostic protocol (`session.py:15-56`); crewai externalizes it to a dedicated infrastructure service (`lock_store.py`) plus an LLM; openhands has almost none in-boundary because the runtime lives elsewhere. The locus follows product shape: engines own scheduling so they own conflicts; SDKs own persistence seams so conflicts live there.

**What is shared at all.** The studied resources differ radically: workflow KV state and conversation history (agent-framework, langgraph), long-term vector memory (crewai), a user-supplied context object (openai-agents-sdk, pydantic-ai), UI event streams and browser registries (openhands), and the filesystem itself (openhands children). Sources sharing *values* (KV entries) could afford barriers; sources sharing *live object references* could not, which explains why the latter group's guarantees collapse to "single event loop saves you."

**Enforcement vs. disclosure.** agent-framework enforces concurrency contracts mechanically (constructor throws, `Workflow.cs:89-92`); openhands discloses the equivalent risk in prose ("the two agents may conflict over the same files", `child-conversation-launch.ts:269-270`). This is not purely a quality gap: openhands is a frontend whose enforcement point (workspace server) is outside the repo, so disclosure is the honest option available — but the practical protection difference for users is large.

**Cross-process posture.** crewai ships an actual distributed-lock seam (Redis-backed when configured); agent-framework and openai-agents-sdk implement optimistic concurrency inside specific stores; langgraph and pydantic-ai delegate wholly to whatever backend the user attaches (Postgres upserts; a sketched-but-unshipped Redis limiter subclass). None ships general-purpose multi-host coordination as a first-class framework feature.

## Tradeoffs

- **Barrier staging vs. immediate visibility.** Benefit: deterministic, restartable, checkpoint-consistent transitions (both engines prove this with tests). Cost: intra-step writes invisible to peers until commit, and a bad writer can poison a whole step (langgraph cancels siblings on failure, `_runner.py:616-634`). Best fit: workflow engines with discrete steps. Alternative seen: openai-agents-sdk's cooperative single-loop model, which gives instant visibility but no engine-enforced consistency at all.
- **Fail-fast rejection vs. silent LWW.** Benefit (langgraph): modeling errors surface immediately with prescribed fixes. Cost: strictness taxes simple use cases — every unannotated key defaults to reject-on-fanout (`graph/state.py:1871-1873`). Best fit: library audiences expected to learn the model. Failure mode of the alternative: agent-framework users lose same-key writes invisibly (`_state.py:36-42`); nothing warns.
- **Optimistic-retry adapters vs. aggregate rewrite windows.** Benefit: backend-portable correctness. Cost: openai-agents-sdk's Dapr adapter rewrites the whole history blob per append (`dapr_session.py:370-388`), making conflict windows grow with history length, versus Redis transactional appends that shrink them. Best fit: short histories or delta-friendly stores. Failure mode: exhausted retries raise with no conflict-specific exception type.
- **Shared-reference ergonomics vs. safety.** Benefit: handoff/nested-run composition stays cheap and type-simple (openai-agents-sdk, pydantic-ai). Cost: zero mechanical protection — openai-agents-sdk documents sharing as user responsibility (`docs/context.md:28-30`); pydantic-ai's `RunUsage` is unguarded across threads. Best fit: asyncio single-loop apps. Failure mode: parallel tool calls mutating context interleave freely; only `max_function_tool_concurrency` throttles the blast radius (`run_config.py:139-156`).
- **Centralized lock service vs. backend-delegated arbitration.** Benefit (crewai): one injectable seam covers every store, test-swappable, scales to Redis. Cost: file-lock fallback is host-local, so "distributed" silently degrades unless operators configure it (`lock_store.py:1-10`); lock swap during operation is unsupported. Best fit: products running their own multi-process deployments. Alternative seen: langgraph's approach — say nothing in the API, let Postgres transactions do the work.
- **Isolation-by-default vs. shared-context value.** Benefit (openhands): worktrees make sibling collisions structurally impossible. Cost: `shared` mode trades all protection for letting a child see work-in-progress — accepted corruption risk (`launch-child-conversation-client-tool.ts:50-52`). Best fit: delegated subtasks with disjoint file scopes. Failure mode: prompt-level instructions to keep scopes disjoint are unverifiable compliance (`launch-child-conversation-client-tool.ts:36-38`).

## Decision Guide

1. **Do you own the execution loop?** If yes, adopt barrier-commit staging and declare per-key merge policy (langgraph/agent-framework pattern). If no, never hand users raw shared mutables without a documented contract — prefer copy-on-share or snapshot APIs.
2. **Choosing between reject-on-conflict and LWW:** reject when concurrent writes to one key indicate a modeling error (most fan-out bugs); choose LWW only when the key space is partitioned by convention *and* the overwrite rule is documented at the API where users will see it (agent-framework puts it in the `State` docstring).
3. **Multiple processes writing one store?** Put optimistic concurrency in the storage adapter with bounded retries, fresh reads per attempt, and jittered backoff. Match the mechanism to the backend (etags, WATCH, generation columns) rather than inventing a generic one.
4. **Multi-host writers beyond one database?** You need a real coordination service (Redis-class) behind an injectable interface — crewai's `lock_store` is the study's only shipped example. File locks alone never cross hosts (explicitly documented in agent-framework `_sessions.py:1894-1898` and crewai alike).
5. **Content that can semantically contradict?** Add similarity-triggered arbitration with a constrained decision schema and a never-lose-data fallback; log the decisions durably if you can (crewai's `ConsolidationAction.reason` exists but isn't persisted — a missed opportunity noted in its report).
6. **Delegating agents onto a shared filesystem?** Isolate by default (worktrees/sandboxes); if a shared mode must exist, gate it behind explicit confirmation plus machine-readable consequence notes, not prose warnings.
7. **Non-idempotent side effects (spawning, billing)?** Record a claim before doing the work; treat ambiguous outcomes as failures rather than blind retries (openai-agents-sdk's EXEC rule).
8. **Need observability?** Budget for it explicitly: emit structured events or metrics on every detected conflict, retry, and dropped write — none of the studied systems did this adequately, so copying any of them wholesale leaves you blind.

## Practical Tips

- Partition shared state by owner before adding any synchronization: crewai namespaces, langgraph threads, agent-framework scoped `StateManager` keys, and openhands worktrees all bought safety with structure, not locks.
- Put the conflict rule where the schema is declared. `Annotated[type, reducer]` (langgraph) and Join reducers (pydantic-ai) make "what happens when two write" reviewable per field; buried engine defaults are not.
- Deep-copy at exactly the boundaries where logical isolation begins (checkpoints, restores, per-run toolset customization) and nowhere else — openai-agents-sdk's checkpoint copy with its explanatory comment is the model to imitate.
- Classify conflicts precisely: openai-agents-sdk distinguishes retryable watch conflicts from ambiguous outcomes and refuses to retry the latter; blanket retry loops cause double-appends.
- Gate whole-system concurrency modes behind explicit opt-ins validated up front (agent-framework's `declareCrossRunShareable` constructor throw) rather than discovering non-thread-safe components at runtime.
- Emit contention telemetry even if you resolve everything internally: pydantic-ai's OTel spans on limiter waiting (`concurrency.py:224-240`) and crewai's typed checkpoint/save events (`runtime.py:245-263`) are the best available baselines — extend them to cover resolved conflicts too.
- When degradation is unavoidable, attach machine-readable notes to the artifact produced (openhands `isolation_note` fed back into the parent conversation) so downstream logic and humans both learn the safety property changed.
- Test conflict paths at three levels like openai-agents-sdk: fake-client unit tests for detector logic, container/integration tests for real contended writers, and edge tests for ambiguity — single-level coverage left crewai's cross-process claims formally unverified (skipped suite, `test_concurrent_storage.py:11-13`).

## Anti-Patterns / Caution Signs

- **Silent same-key overwrite with no warning or trace** — the signature weakness of otherwise-strong systems (agent-framework `_state.py:37-41`; pydantic-ai `reduce_dict_update`; langgraph `BaseStore.put` blind upserts, `store/base/__init__.py:856-935`). Caution sign: users can't answer "what happens if two write?"
- **Shared mutable objects with no stated contract** — openai-agents-sdk user context, crewai live Flow state under `asyncio.gather` listeners, pydantic-ai cross-thread `RunUsage`. Caution sign: correctness arguments begin "since asyncio is single-threaded..."
- **Prompt-level coordination** — instructing an LLM to avoid file collisions (openhands) shifts enforcement onto model behavior with zero verification. Caution sign: a safety property whose only guard is a string.
- **Degradation that silently drops a safety property** — openhands falling back to `shared` isolation, crewai consolidation degrading to insert-on-failure (duplicate accumulation), project-ID minting proceeding best-effort when the lock backend fails (`project.py:311-313`).
- **Disabled or missing concurrency stress tests while claiming cross-process safety** — crewai's skipped N-process suite; agent-framework lacking a dedicated two-run shared-state stress test despite the feature.
- **Contention logged at Debug level or below** — agent-framework lost races (`FoundryJsonCheckpointStore.cs:245-254`), langgraph unknown-channel writes demoted to warnings and dropped (`_algo.py:310-313`). Operators learn of contention only at terminal failure.
- **Module-global caches relying on GIL-era assumptions** — openai-agents-sdk `agent_tool_state.py:33-48`, flagged as a latent free-threading hazard.
- **Success-after-retry leaving no trace** — openai-agents-sdk notes retried-and-committed operations are invisible, so chronic contention is undetectable until retries exhaust.

## Notable Absences

Across all six sources, several capabilities are consistently absent — these are ecosystem-wide gaps, not individual shortcomings:

- **No queryable, durable conflict log anywhere.** Every report independently states this: agent-framework (Debug logs and exceptions only), langgraph (warnings + ERROR writes, no audit trail), openai-agents-sdk (silent successes), pydantic-ai (OTel spans only), openhands (chat messages as sole trace), crewai (typed events come closest but consolidation decisions aren't persisted).
- **No distributed consensus, leases, or fencing primitives in-core** — explicitly searched and absent in agent-framework, langgraph, and pydantic-ai; crewai's Redis lock is the closest shipped facility.
- **No compare-and-swap/version parameters on generic item stores** — langgraph `BaseStore.put`, crewai `StorageBackend.update`, and agent-framework's `FileSessionStore`/`FileCheckpointStorage` all lack them (each report proposes adding them).
- **No general merge/CRDT layer for shared state** beyond langgraph's `BinaryOperatorAggregate` fold and pydantic-ai's join reducers — both limited to programmer-supplied associative functions.
- **No runtime file-content conflict detection between agents** — openhands finds no diff/check/precondition before shared-mode children write alongside parents; pydantic-ai similarly defers artifact/file toolsets to third parties.
- **No merge-back story for durable-execution boundaries** — pydantic-ai's Temporal activities receive copied contexts so delegate usage vanishes (pinned by `tests/test_temporal.py:11507-11528`); agent-framework's AG-UI whole-snapshot round-trips likewise clobber concurrent frontends with no delta events observed.

## Per-Source Notes

- **agent-framework (7):** Three-layer sharing (workflow KV state, orchestration conversations, sessions/checkpoints) under a symmetric dual-language BSP contract; strongest evidence base with mirrored Python/.NET citations. Standouts: bookmark-based incremental conversation consumption, read-modify-write closures, quiescent-export guards, retention preserving concurrent runs' sibling branches (`FoundryJsonCheckpointStore.cs:38-43`). Weakness: fixed silent LWW; no merge hooks despite pending-buffer information existing pre-commit. Gap: Go SDK out of tree, uninspected.
- **crewai (7):** Richest conflict *typology* — mechanical (locks/retries/OCC), structural (validators, recursion caps), and semantic (LLM consolidation) in one codebase. Standouts: serialize-then-barrier memory writes, injectable lock factory, checkpoint fork/branch lineage instead of merging. Weakness: Flow listeners mutate `self._state` concurrently with no protection; the one multiprocess stress test is skipped.
- **langgraph (8):** The study's clearest conflict model — cardinality checks centralized in channel classes, stable error codes, version vectors powering both stale-read triggering and ambiguity detection, task-keyed durable writes making storage collisions structurally impossible (`checkpoint/postgres/base.py:146-158`). Weakness: cross-thread Store is bare LWW and `InMemoryStore` is unsynchronized; unknown-channel writes vanish with a warning.
- **openai-agents-sdk (7):** Best test discipline for conflict paths (unit + container-integration + ambiguity edges) and honest documentation of residual races (etag-less creation LWW, compaction-vs-mutation). Standouts: refusal-to-guess identity reconciliation, refcounted per-file SQLite lock registry, two-layer instance-lock/backend-CAS scheme. Weakness: the primary shared resource (user context) has no contract at all.
- **openhands (6):** Studied boundary is the frontend only — the agent runtime lives in a sibling repo, so several questions (server-side file behavior) are unanswerable from evidence here. Standouts: sender-scoped streaming reconciliation born from issue #1656, claim-before-work ledgers, watchdog liveness timers, disclosed degradation notes. Weakness: highest-stakes shared resource (workspace files) protected by default-plus-warning only; no locks exist in-repo by design.
- **pydantic-ai (6):** Most deliberate about *documented* sharing invariants (comments explaining why capability sets must be mutated in place, `_agent_graph.py:413-421`) and the only source with race-regression tests for its limiter plus OTel contention attributes. Standouts: projected-usage batch simulation, first-wins-with-cancellation reducer, clone-before-mutate. Weakness: thread-unsafe `RunUsage`, Temporal usage loss, no shipped distributed primitive behind the `AbstractConcurrencyLimiter` seam.
