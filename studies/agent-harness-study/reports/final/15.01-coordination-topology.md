## Executive Summary

Across six sources the study found four coordination archetypes rather than one: (1) **engine substrates** that provide a general coordination kernel on which users compose topologies — langgraph's Pregel/BSP channel engine and agent-framework's `Workflow` graph engine with five named orchestration builders; (2) **named-topology frameworks** that ship opinionated processes — crewai's sequential/hierarchical enum plus Flows and A2A federation; (3) **primitive libraries** where topology is user-composed from function calls — pydantic-ai's delegation-as-tool-call and typed DAG; and (4) an **application-brokered star** — openhands' server-mediated conversations with fire-and-forget child delegation.

Despite these different product shapes, five properties converge across all six sources: the possible wiring is **declared statically at construction time while actual traffic is routed dynamically**, usually by an LLM emitting ordinary tool calls that a coordinator intercepts; **discovery is never autonomous** — peers are surfaced as text in prompts (role lists, handoff descriptions, AgentCards); every source accepts a **centralized coordinator as a deliberate single point of failure**, mitigating with durability (checkpoints, resume) rather than redundancy; **conversation loops are always bounded** by explicit limits; and no source implements coordinator failover, runtime membership changes, or marketplace-style discovery.

Ratings span 7–9: langgraph scores highest for rigorous, conflict-detecting channel semantics backed by extensive tests; the two 7-rated sources (crewai, pydantic-ai) lose points for fragile or convention-based coordination contracts; openhands scores well operationally but hardcodes topology assumptions.

## Core Thesis

Modern agent harnesses converge on a design that this report summarizes as **"static graph, dynamic traffic."** The set of participants and the edges between them are fixed at build/construction time — a compiled node registry (langgraph `StateGraph.compile()`), an edge list emitted by builders (agent-framework), constructor-declared `handoffs`/`tools` lists (openai-agents-sdk), frozen membership fields (crewai), registered delegation tools (pydantic-ai), or a singleton planning sub-conversation plus bounded child fan-out (openhands). What is dynamic is *activation*: which edge carries traffic next is decided per step by conditional predicates, selection functions, or — dominantly — the LLM itself choosing among tools.

The second half of the thesis: **coordination rides on the function-calling channel.** Five of six sources implement agent-directed routing as tool calls intercepted by a coordinator — synthetic `handoff_to_<target>` tools caught by middleware (agent-framework `_handoff.py:132-154`), `DelegateWorkTool`/`AskQuestionTool` (crewai `base_agent_tools.py:37-120`), `transfer_to_<name>` tools handled by the runner loop (openai-agents-sdk `turn_resolution.py:584-586`), a client-executed `launch_child_conversation` tool (openhands `launch-child-conversation-client-tool.ts:61-112`), and plain delegation tools awaiting child runs (pydantic-ai `docs/multi-agent-applications.md:43-49`). Only langgraph routes purely through its channel substrate without borrowing the tool-calling surface. The consequence is systemic: routing quality everywhere depends on prompt/tool-description quality, so discovery, addressing, and failure reporting all inherit the strengths and fragilities of natural-language interfaces.

Where sources genuinely diverge is not topology vocabulary (pipeline, supervisor, mesh, star appear in most of them) but **who owns the coordinator and how strictly delivery semantics are enforced**: an engine loop with typed channels and crash-on-conflict rules (langgraph), builder-wired orchestrator executors (agent-framework), an LLM manager agent addressed by role strings (crewai), a single sequential runner loop (openai-agents-sdk), user application code (pydantic-ai), or a networked server broker (openhands).

## Approach Models

- **agent-framework — "topology kit on a shared engine" (hub-and-spoke, mesh, star, pipeline, fan-out/fan-in).** Five orchestration builders each lower into the same `WorkflowBuilder` edge primitives (`_sequential.py:260-272`, `_concurrent.py:429-432`, `_group_chat.py:1029-1038`, `_handoff.py:989-1010`, `_magentic.py:1796-1805`). Communication is typed messages along declared edges plus optional superstep-staged shared state (`_state.py:6-23`). Topology choice is a build-time decision made immutable by a `graph_signature_hash` checked on checkpoint resume (`_workflow.py:332-336`). Dynamic behavior comes from routing predicates, speaker-selection functions, and LLM-driven handoff/speaker decisions.
- **crewai — "enum-selected processes with LLM-tool delegation."** `Process.sequential|hierarchical` dispatch in `kickoff` (`process.py:4-11`, `crew.py:1051-1058`); hierarchical mode auto-creates a manager agent whose only capabilities are two delegation tools resolving coworkers by sanitized role-string match (`base_agent_tools.py:37-120`). Flows add a method-level `@start/@listen/@router` event graph with `or_`/`and_` joins (`flow/dsl/_conditions.py:22-27`); A2A wraps agents at class construction for cross-process federation (`a2a/wrapper.py:115-237`).
- **langgraph — "coordination substrate, not topologies."** Actors are `PregelNode`s communicating exclusively through typed channels — `LastValue` (single-value, conflict-detecting), `Topic` (PubSub), `BinaryOperatorAggregate` (reducer fold), `NamedBarrierValue` (join barrier), `EphemeralValue` (routing) (`pregel/main.py:454-502`). One central loop plans tasks (`prepare_next_tasks`, `_algo.py:392-513`) and commits writes atomically per superstep (`apply_writes`, `_algo.py:232-345`). Dynamic activation via `Send` and `Command(goto=...)` travels over a reserved `__pregel_tasks` topic so it checkpoints like data (`main.py:804-809`, `_write.py:178-179`).
- **openai-agents-sdk — "centralized control-transfer over a static agent graph."** Exactly two LLM-facing primitives: handoffs (`transfer_to_<name>` tools that swap the run's active agent, `run_loop.py:1390-1412`) and agents-as-tools (`as_tool()` bounded nested sub-runs where the caller keeps control, `agent.py:583-634`), explicitly contrasted in code (`agent.py:608-612`). Deterministic pipelines/fan-out are delegated to user code via `asyncio.gather` under a shared trace (`examples/agent_patterns/parallelization.py:29-57`).
- **openhands — "server-brokered star of independent conversations."** All events traverse the agent-server over per-conversation WebSockets; the browser executes UI-owned client tools. Coordination shapes: a singleton linked planning sub-conversation (`conversation-websocket-context.tsx:402-421`), dynamically launched child conversations that are deliberately disconnected ("you do not see its output... cannot see this conversation's history", `launch-child-conversation-client-tool.ts:14-38`) returning exactly one `[child-conversation]` result message, and gated in-loop subagents via `task_tool_set` (`agent-server-adapter.ts:636-641`).
- **pydantic-ai — "composition primitives with explicit state channels."** No coordination engine: delegation is a tool whose body awaits a child `run()` and returns its output (`multi-agent-applications.md:13-49`); programmatic hand-off passes `message_history` between successive runs (`message-history.md:503-533`); `pydantic_graph` provides typed Fork/Join DAG nodes (`node.py:61-80`, `join.py:151-175`). Cross-agent concerns travel as explicit parameters: shared mutable `RunUsage` (`abstract.py:511`), thread-safe tree-wide `CancellationToken` (`_cancel.py:42-90`).

## Pattern Catalog

### P1. Coordination-as-tool-calls

- **Problem:** how does an LLM-driven agent redirect control flow to a peer without a bespoke inter-agent protocol?
- **Sources:** agent-framework (synthetic `handoff_to_X` tools short-circuited by function middleware, `_handoff.py:306-350`), crewai (`DelegateWorkTool`, `delegate_work_tool.py:8-20`), openai-agents-sdk (`transfer_to_<name>`, `handoffs/__init__.py:207-218`), openhands (`launch_child_conversation` client tool, `launch-child-conversation-client-tool.ts:61-112`), pydantic-ai (delegation tools awaiting child runs, `multi-agent-applications.md:43-49`).
- **Why it works:** it reuses the existing tool-call pipeline — schemas, validation, tracing, approval machinery apply uniformly — and makes routing decisions inspectable in the transcript. openai-agents-sdk additionally emits a machine-readable switch record `{"assistant": "<name>"}` instead of prose (`handoffs/__init__.py:203-204`).
- **Copy when:** your agents are LLM-driven and you want routing decisions visible, testable, and permission-gated through existing tool infrastructure.
- **Avoid when:** you need guaranteed delivery or deterministic routing — tool-call routing inherits model misfires; openai-agents-sdk mitigates only with recommended prompts (`docs/handoffs.md:141-145`).
- **Evidence:** the interception mechanics differ (middleware vs runner loop vs browser handler vs plain Python call) but all five convert a model decision into a coordinator-executed routing act.

### P2. Static wiring, dynamic activation

- **Problem:** how do you keep topologies auditable and checkpointable while still allowing adaptive behavior?
- **Sources:** all six. langgraph freezes nodes/channels at compile then resolves `Send`/conditional edges per superstep (`_algo.py:468-512`); agent-framework rejects checkpoint resume against changed graphs (`_runner.py:312-317`); openai-agents-sdk evaluates `is_enabled` gates each turn but never mutates edges (`turn_preparation.py:105-115`); crewai freezes membership at kickoff while the manager picks targets per step (`crew.py:1853-1863`); pydantic-ai fixes the possible call tree via registered tools while traversal varies (`multi-agent-applications.md:18`); openhands fixes one planning sub-conversation while child launches are dynamic.
- **Why it works:** static structure enables validation (missing-handoff parse errors at `tests/test_run_step_processing.py:303`), rendering, and replay; dynamic activation delivers adaptivity without invalidating any of that.
- **Copy when:** essentially always — this is the closest thing to a consensus architecture in the corpus.
- **Watch out:** dynamic addressing must be bounded by the static registry. langgraph drops unknown `Send` targets with only a warning (`_algo.py:977-979`) — adaptive routing that fails softly can silently shrink your worker pool.

### P3. Prompt-side capability advertisement (discovery-as-text)

- **Problem:** how do agents learn who their peers are without a service-discovery layer?
- **Sources:** all six. Magentic seeds the manager context with `participant_descriptions` (`_magentic.py:936-940`); crewai bakes coworker role lists into tool descriptions and renders fetched A2A AgentCards as `<AVAILABLE_A2A_AGENTS>` (`agent_tools.py:24-34`, `templates.py:7-14`); openai-agents-sdk derives tool name/description from the target agent's `name`/`handoff_description` (`agent.py:189-192`); openhands persists `sub_conversation_ids` server-side and relays child ids via result text (`child-conversation-launch.ts:213-234` test); pydantic-ai uses direct module-level references with names only labeling spans (`agent/__init__.py:1303-1304`); langgraph addresses by compile-time node name.
- **Why it works:** the LLM is already the router, so the model's context *is* the discovery registry. It unifies local peers, remote peers, and structural metadata into one representation.
- **Copy when:** participant sets are small, stable, and human-curated.
- **Avoid when:** fleets grow — there is no capability matching beyond what the model reads, and stale or duplicated descriptions directly cause misrouting (crewai's silent duplicate-role first-match resolution, `base_agent_tools.py:80-84`).

### P4. Bounded conversation loops as universal safeguard

- **Problem:** multi-agent conversations can cycle forever.
- **Sources:** agent-framework (`max_rounds` forcing completion, `_base_group_chat_orchestrator.py:499-518`; convergence cap raising `WorkflowConvergenceException` after 100 supersteps, `_runner.py:176-177`), langgraph (`recursion_limit` → `GraphRecursionError`, `main.py:3001-3011`), openai-agents-sdk (`DEFAULT_MAX_TURNS=10` → `MaxTurnsExceeded`, `run_config.py:45`), crewai (A2A turn budgets surfaced to the LLM, `templates.py:7-29`), openhands (bounded provisioning polls, 3 s × 180 s, `child-conversation-launch.ts:365-384`), pydantic-ai (`UsageLimits` enforced mid-turn against provisional totals, `_agent_graph.py:875-886`).
- **Why it works:** a coarse global bound is cheap, universally applicable, and converts hangs into catchable errors.
- **Copy when:** always, but treat it as a backstop, not a policy — agent-framework's group chat explicitly warns it "will continue indefinitely" if neither `max_rounds` nor `termination_condition` is set (`_group_chat.py:142-143`), so defaults matter more than availability.

### P5. Barrier-synchronized supersteps with staged commit (the Pregel twins)

- **Problem:** how do you get deterministic, checkpointable multi-agent execution?
- **Sources:** langgraph (plan → execute → update with invisible intra-step writes, `main.py:464-477`) and agent-framework (superstep delivery with commit-at-boundary shared state, `_runner.py:106-177`, `_state.py:14-23`). These are the only two engine-level substrates in the corpus and both independently landed on BSP semantics.
- **Why it works:** committing writes only at superstep boundaries eliminates interleaving nondeterminism and creates clean checkpoint points; both engines checkpoint per superstep.
- **Copy when:** you need replay, auditability, or durability guarantees.
- **Cost:** every hop pays a full barrier — tight ping-pong loops cost minimum two hops (langgraph `Send`s land in superstep n+1, `_algo.py:962`), noted as latency overhead for agent-framework's Magentic inner cycle too.

### P6. Fan-out/fan-in join semantics

- **Problem:** how do parallel branches re-synchronize?
- **Sources:** langgraph compiles multi-parent edges into `NamedBarrierValue` channels that gate until all named producers write (`named_barrier_value.py:56-81`); agent-framework wires explicit `FanInEdgeGroup`s and a deterministic aggregator (`_concurrent.py:429-432`); crewai drains `async_execution` futures before the next synchronous task (`crew.py:1597-1625`); pydantic-ai offers typed `Fork`/`Join` with reducers (`join.py:151-175`) plus barrier-segmented parallel tool segments (`_tool_execution.py:254-297`).
- **Why it works:** joins make partial-progress ambiguity impossible — downstream work starts only when the join condition is met.
- **Failure mode:** barrier starvation. A langgraph producer that exits without writing leaves subscribers permanently unfired, with termination guaranteed only by the recursion limit (no deadlock diagnostics found in `pregel/`).
- **Copy when:** you have genuinely independent branches; prefer reducer-typed joins (pydantic-ai/langgraph channels) over ad-hoc result collection.

### P7. Idempotency and replay protection for side-effectful coordination acts

- **Problem:** reconnects and retries can double-execute expensive coordination actions (e.g., launching billable cloud sandboxes).
- **Sources:** openhands claims tool-call ids into a localStorage ledger before any network side effect so WS replays cannot double-launch children (`child-conversation-launch.ts:196-227`, tested at `__tests__/services/child-conversation-launch.test.ts:490-508`); agent-framework enforces a single-active-run lock (`_workflow.py:768-771`); langgraph versions channels and checkpoints dynamic Sends so replays stay consistent (`main.py:804-809`).
- **Why it works:** coordination acts are state transitions; treating them like financial transactions (claim-before-act) closes the most expensive race in the corpus's only networked source.
- **Copy when:** any coordination action with external side effects or cost.

### P8. Ledger-driven supervision with stall detection (unique to agent-framework)

- **Problem:** centralized chat orchestration degenerates when the team stops making progress.
- **Source:** Magentic maintains plan/progress ledgers, counts non-progress rounds, triggers reset-and-replan past `max_stall_count`, and degrades gracefully to a final answer when the ledger names an invalid speaker (`_magentic.py:1057-1154`, `1117-1138`), with optional human plan sign-off (`_magentic.py:893-908`).
- **Why it works:** supervision policy is externalized behind `MagenticManagerBase.plan/create_progress_ledger` (`_magentic.py:469-512`), separating *what to watch* from *how to route*.
- **Copy when:** long-running orchestrated teams where silent stalling is the dominant risk. **Overkill when:** simple triage routing (openai-agents-sdk handles that with turn caps alone).

## Key Differences

- **Engine-mediated channels vs tool-call delegation.** LangGraph forbids direct agent-to-agent messaging entirely — every interaction folds through channel reducers after the superstep (`_algo.py:232-345`) — while openai-agents-sdk has *no* message primitive at all, only control transfer and nested runs. LangGraph pays a barrier per hop for determinism; openai-agents-sdk gets linear-chain simplicity and trivially consistent accounting (`run_loop.py:1184`) but cannot express negotiation or debate inside a run.
- **Strict conflict detection vs soft conventions.** Two concurrent writes to a langgraph `LastValue` key crash with `INVALID_CONCURRENT_GRAPH_UPDATE` (`last_value.py:56-64`), forcing conscious reducer choice; pydantic-ai's analogous contract — propagating `usage=ctx.usage` to delegates — is opt-in documentation advice that silently under-counts spend when forgotten (`multi-agent-applications.md:20`); crewai resolves duplicate role names to `agent[0]` silently (`base_agent_tools.py:80-84`). Same underlying problem (uncoordinated writers), three enforcement levels: crash, convention, silence.
- **Built-in topologies vs composable primitives.** Agent-framework ships five named, tested topologies; crewai ships two processes plus Flows; langgraph deliberately ships zero executable multi-agent patterns — supervisor recipes survive only as comments (`tool_node.py:981`) and out-of-repo packages, pushing topology correctness onto users; pydantic-ai documents a five-level complexity ladder but implements only the mechanisms.
- **In-process vs networked coordination.** Four sources confine coordination to one process (with durability outsourced to checkpoints or external durable extensions); crewai and agent-framework embrace cross-process federation through A2A AgentCard discovery and HTTP delegation (`a2a/utils/delegation.py:135-199`); pydantic-ai deliberately moved A2A upstream to `fasta2a` (`migration.md:24`); openhands is natively distributed because it is an application — its broker is a server, its clients are browsers, and its children run in separate sandboxes or worktrees.
- **Centralized vs decentralized routing.** Group chat and Magentic place all routing authority in one orchestrator (guaranteed ordering authority, throughput bottleneck, SPOF); agent-framework's handoff pattern removes the bottleneck by letting every agent route itself via tools — but coverage can't be guaranteed, and an agent with no configured handoffs merely logs "your workflow may get stuck" (`_handoff.py:1096-1099`) instead of failing fast. CrewAI's hierarchical mode is the extreme of centralization: the manager executes *every* task (`crew.py:1714-1717`), so workers are reached only through it.
- **Structured errors vs corrective-guidance strings.** LangGraph raises typed errors with registered codes (`errors.py:36`); openai-agents-sdk raises `ModelBehaviorError` on unknown handoffs (`tests/test_run_step_processing.py:303`); crewai returns formatted error strings to keep the ReAct loop alive for self-correction (`base_agent_tools.py:121-124`); openhands converts malformed launches into actionable guidance text because the server already ACK'd the call (`child-conversation-launch.ts:85-89`). The string approach preserves agent autonomy but destroys machine-checkable failure semantics.

## Tradeoffs

- **Central hub vs decentralized mesh.**
  - *Benefit (hub):* single ordering authority, easy broadcast-minus-speaker echo avoidance (`_group_chat.py:224-231`), one place to enforce round limits.
  - *Cost:* orchestrator is bottleneck and SPOF; recovery relies on checkpoints, never redundancy (no source implements coordinator failover).
  - *Best fit:* moderated discussions, plan-driven teams.
  - *Failure mode:* manager LLM failure halts everything — crewai has no fallback coordinator or quorum.
  - *Alternative seen:* handoff meshes and fire-and-forget stars remove the bottleneck but sacrifice coverage guarantees and mutual visibility (openhands children "cannot see this conversation's history").
- **Deterministic barriers vs immediate interaction.**
  - *Benefit:* checkpointable, replayable steps (both Pregel engines).
  - *Cost:* latency floor per hop; no streaming of partial results between peers mid-step.
  - *Best fit:* durable, audited, long-running workflows.
  - *Failure mode:* ping-pong-heavy designs pay 2× hops (langgraph Send timing, `_algo.py:962`).
  - *Alternative seen:* openai-agents-sdk/pydantic-ai immediate sequential turns with no barriers — faster, but resume depends on serializing the whole loop state instead.
- **Crash-on-conflict vs convention-based sharing.**
  - *Benefit (crash):* lost-update races become impossible; developers must pick reducers consciously.
  - *Cost:* verbose setup; loosely coordinated topologies must redesign data flow.
  - *Best fit:* shared blackboard-style state with many writers.
  - *Failure mode (convention):* silent under-accounting (pydantic-ai usage) and silent wrong-target routing (crewai role collisions) surface only as mysterious downstream behavior.
  - *Middle ground seen:* agent-framework's last-write-wins per superstep (`_state.py:30-43`) — predictable but lossy.
- **Independence vs observability in delegation.**
  - *Benefit:* openhands' isolated children "do not fight over the same files" (`launch-child-conversation-client-tool.ts:36-37`); pydantic-ai's sub-agent self-cancellation becomes a failed tool return the parent survives (`_tool_execution.py:41-62`).
  - *Cost:* parents cannot watch, cancel, or join children post-launch (openhands searched and found no such path); deep chains lose lineage (cloud children carry no parent link, `child-conversation-launch.ts:416-419`).
  - *Best fit:* parallelizable, self-contained subtasks.
  - *Alternative seen:* openai-agents-sdk's `as_tool()` keeps a live caller-callee relationship with extracted outputs — less isolated, fully observable.
- **History forwarding vs context hygiene.**
  - *Benefit:* verbatim forwarding (openai-agents-sdk default) loses nothing.
  - *Cost:* context bloat and leakage across specialist boundaries; filters/nesting are opt-in and partially unsupported with server-managed conversations (`turn_resolution.py:495-524`).
  - *Alternatives seen:* nested `<CONVERSATION HISTORY>` summaries (openai-agents-sdk `history.py:376-398`), aggregated prior-output context strings (crewai `formatter.py:16-26`), explicit `message_history` interchange (pydantic-ai `message-history.md:511-533`).

## Decision Guide

1. **Need guaranteed delivery semantics, replay, or durability first?** Choose an engine substrate. LangGraph if you need pluggable dataflow semantics (PubSub, aggregates, join barriers) and accept crash-on-conflict discipline; agent-framework if you want named, pre-tested topologies with builder ergonomics and don't need custom channel semantics. Both are Pregel-style, so expect barrier latency.
2. **Building a triage/routing product (support, voice, realtime)?** The openai-agents-sdk model — static handoff graph + `as_tool()` for bounded subtasks — is the most precisely specified and traced version of it, at the price of strictly sequential execution.
3. **Want ready-made team workflows with minimal plumbing?** CrewAI's processes give you a manager-with-tools hierarchy or pipeline out of the box, but budget for its weak spots: enforce unique role names yourself, wrap the manager with retries, and avoid deep sync delegation stacks (no timeout exists).
4. **Embedding an agent library inside a larger application where you own orchestration?** Pydantic-ai's primitive set (delegation tools, explicit usage/cancellation/history channels, optional typed DAG) maximizes control; be prepared to lint your own conventions since nothing enforces them.
5. **Coordination crossing process/org boundaries?** Only two viable models in the corpus: A2A federation with prompt-injected AgentCards (crewai, agent-framework demonstrate it end-to-end) or a server-brokered conversation star (openhands). Both push correctness onto prompt content and idempotency ledgers respectively.
6. **Default rule of thumb:** if you can draw your intended topology as a fixed diagram, use a framework that compiles and validates that diagram (langgraph, agent-framework, openai-agents-sdk visualization); if your topology is inherently dynamic in membership, no source in this corpus supports runtime rewiring — design around it with static registries plus dynamic activation, or federate via protocol.

## Practical Tips

- **Make the topology renderable.** Every source that can draw itself got that way cheaply: DOT/Mermaid export including sub-workflow clusters (agent-framework `_viz.py:29-62,301-344`), graph drawing with destinations metadata (`state.py:704-714`), Graphviz generation walking handoff/tool/MCP edges (openai-agents-sdk `visualization.py:146-168`), flow-graph visualization (crewai `builder.py:111-146`). Renderability doubles as an audit artifact — the dimension's driving question ("can you draw the communication topology of a multi-agent run?") is answerable programmatically in four of six sources, and the other two are simple enough shapes to state in one sentence.
- **Reserve and validate routing names.** openai-agents-sdk reserves handoff tool names against MCP collisions (`agent.py:216-235`); crewai does neither for roles and pays with silent first-match wins. Validate uniqueness of participant identifiers at construction, not at first delegation.
- **Fail fast on empty routing options.** If an agent has no outbound edges (handoffs/delegation tools), raise at build time — agent-framework's runtime-only "may get stuck" log (`_handoff.py:1096-1099`) is the anti-example.
- **Tag senders in merged streams.** OpenHands' `isFromPlanningAgent` flag and per-stream delta batchers exist because bug #1656 taught them the cost of un-tagged merges (`handle-event-for-ui.ts:31-37`). Any time multiple coordinators write one log/event stream, sender identity must ride on every event.
- **Propagate accounting and cancellation explicitly down the tree.** Pydantic-ai shows the shape: one shared `RunUsage` instance incremented in place gives tree-wide budgets (`usage.py:383`), one shared `CancellationToken` cancels the whole tree (`_cancel.py:42-90`). Adopt this even if your framework doesn't require it.
- **Convert sub-agent failures into parent-visible tool results, not crashes.** Both pydantic-ai (`cancelled_sub_agent_return`, `_tool_execution.py:44-55`) and crewai (error strings returned as observations) keep the delegating agent alive; choose structured payloads over prose if you need machine-checkable outcomes.
- **Pair every dynamic-routing feature with a soft-failure detector.** Unknown targets, dangling Sends, and unreachable barriers all fail quietly today (langgraph warns-and-drops, `_algo.py:977-979`; barrier starvation relies on the recursion limit). Add build-time checks or metrics for them.

## Anti-Patterns / Caution Signs

- **Free-string addressing for coordination targets.** Coworker resolution by casefolded role-string match with silent duplicate resolution (crewai `base_agent_tools.py:72-84`) — the signature smell is addressing that depends on display text.
- **Silent soft-failures in routing paths.** Dropped unknown Sends (`_algo.py:977-979`), logged-not-raised missing handoff configs (`_handoff.py:1096-1099`), prompt notices asking the LLM not to delegate to unavailable peers (crewai `templates.py:22-29`). Caution sign: correctness resting on a model obeying instructions.
- **Conventions where contracts belong.** Opt-in usage propagation, "generally compatible" deps advice (pydantic-ai `multi-agent-applications.md:20,101`) — coordination invariants that only tests or lints can catch after the fact.
- **Hardcoded topology assumptions.** Planning pinned to `subConversations[0]` in three separate code sites (openhands `conversation-websocket-context.tsx:408,858-861,908-909`) — generalizing later requires touching every assumption site.
- **Unguarded defaults on unbounded conversations.** Infinite group chat unless limits are set (`_group_chat.py:142-143`); safe defaults beat available safeguards.
- **Guardrail scope coupled to topology position.** Input guardrails fire "only if the agent is the first agent in the chain," leaving post-handoff specialists uncovered by input checks (openai-agents-sdk `agent.py:350-353`, `docs/guardrails.md:65`).
- **Client-side execution of consequential coordination without server truth.** Server ACK-before-work forces natural-language error envelopes (openhands `child-conversation-launch.ts:99-109`) and origin-scoped localStorage ledgers that degrade silently when full (`:214-226`).
- **Sync delegation on shared threads.** Deep hierarchies stack frames with no timeout (crewai shares the delegator's cache/RPM controller, `crew.py:1543-1548`), and a sync A2A wrapper "blocks the entire thread by creating and running a new event loop" (`a2a/utils/delegation.py:163-165`) — deadlock risk inside async contexts.

## Notable Absences

Across all six sources, the corpus collectively lacks:

- **Coordinator failover or replication.** Every centralized orchestrator (Magentic manager, crewai manager agent, openai-agents-sdk runner loop, langgraph Pregel loop, openhands agent-server) is a single point of failure; recovery is uniformly checkpoint/resume, never redundancy.
- **Runtime membership changes.** No source allows adding/removing participants mid-run; agent-framework actively rejects it via graph-signature mismatch (`_runner.py:312-317`); langgraph bounds dynamic addressing by the static registry.
- **Marketplace/brokered discovery.** The closest is A2A AgentCard fetching from pre-configured endpoints (crewai `wrapper.py:240-279`, agent-framework `_a2a_executor.py:43-92`) — pull-based cards, not queryable registries.
- **Deadlock/starvation detection.** Mesh deadlocks (empty handoff sets) and barrier starvation (missing producers) rely on generic loop bounds; agent-framework lists a build-time deadlock detector as future work, langgraph found no barrier-timeout handling in-source.
- **In-runner concurrency for the sequential SDKs.** openai-agents-sdk runs exactly one active agent per turn; parallelism exists only when user code gathers independent runs (`parallelization.py:29-43`). Its hosted beta's `max_concurrent_subagents` signals demand but is experimental and mutually exclusive with local handoffs (`model.py:396-400`).
- **Executable multi-agent references in the substrate repo.** LangGraph's example notebooks were moved to docs stubs, leaving no end-to-end in-repo demonstration of supervisor/network topologies.

## Per-Source Notes

- **agent-framework (8/10):** Most complete topology vocabulary in the corpus — five named patterns all compiling to one edge-graph substrate, with the strongest safeguard set (round limits, convergence caps, stall detection with replanning, unknown-participant validation) and first-class topology export. Weaknesses are concentration (central orchestrators, single asyncio process) and leaky tool-call-as-signal plumbing (parallel tool calls must be disabled for handoff, `_handoff.py:287-289`).
- **crewai (7/10):** Broadest topology menu including the corpus's only in-crew LLM-manager hierarchy and full A2A federation; flows add cyclic event graphs with careful once-only OR-listener locking (`runtime/__init__.py:1023-1078`). Held back by string-keyed delegation addressing, string-error failure semantics, and a completely unmitigated manager SPOF.
- **langgraph (9/10):** Highest score: the only source enforcing communication semantics at the type level (five channel classes with distinct conflict policies) and detecting concurrent-write conflicts as registered errors. Dynamic control rides the same channel/versioning machinery as data, so it survives checkpointing. Loses points only for silent unknown-target handling and absent in-repo multi-agent guidance.
- **openai-agents-sdk (8/10):** The cleanest small API: two primitives with precisely documented ownership semantics, first-of-multiple handoff arbitration with span errors, serialize/resume validated on restore, and the same model reused across text/voice/realtime surfaces (`voice/workflow.py:77-101`). Strict sequentiality is the defining constraint.
- **openhands (7/10):** The only application-shaped source and the only networked broker; brings production-grade safeguards unusual for a browser coordinator (idempotency ledger, isolation fallback ladder worktree→shared→reported-failure, version-gated features). Hardcoded singleton planning and absent child lifecycle management cap the score.
- **pydantic-ai (7/10):** The minimalist counterpoint: no engine, no registry, no messaging — just explicit state channels passed down a dynamic call tree, with unusually careful cancellation semantics (first-party vs external attribution, `_cancel.py:92-257`) and sub-agent failure isolation. Enforcement gaps (usage/deps conventions) and zero discovery are the trade.

## Open Questions

- **Multi-host coordination remains unspecified for four of six sources.** LangGraph defers to an out-of-repo server behind `RemoteGraph` (`remote.py:118`); agent-framework delegates durable/distributed execution to an external extension (per `python/AGENTS.md`); pydantic-ai externalizes to Temporal/`fasta2a`; crewai's Enterprise Celery reference has no transport in-tree. How the BSP/engine loop is owned across replicas could not be assessed from these sources.
- **Is dynamic handoff dispatch a supported contract?** openai-agents-sdk's `Handoff.on_invoke_handoff` type permits returning arbitrary agents, the helper discourages it, docs permit it "for your own handoff code," and serialization/resume of such targets is untested (`handoffs/__init__.py:148-153`, `docs/handoffs.md:44`).
- **OpenHands subagent concurrency is out of boundary.** The in-loop `TaskAction`/`TaskObservation` machinery lives in a sibling repo; whether those subagents run concurrently could not be determined from this source.
- **No source quantifies routing quality.** Misroute rates, token costs of prompt-advertised peer catalogs, and summary-compaction fidelity under real models were out of scope for static analysis (noted explicitly by openai-agents-sdk and implied by crewai's sanitization-only mitigations).
- **Whether Go/.NET surfaces expose identical topologies** was verified only by spot-check for agent-framework's .NET builder parity (`GroupChatWorkflowBuilder.cs:77-78`); the Go implementation was not analyzed for this dimension.
