## Executive Summary

None of the four agent systems studied here has a single policy engine; each injects governance rules through four to six distinct points — runtime code, tool metadata annotations, deployment/config files, prompt text, human approval responses, and (in two cases) an external policy service. Only OPA has a unified model, and that is because a policy engine *is* its product: policies arrive as Rego bundles via REST push, HTTP/OCI/file polling, discovery-driven reconfiguration, startup files with opt-in hot reload, or an embedded SDK, and all five paths converge on one transactional store-write → compile → trigger pipeline (opa report; `v1/plugins/bundle/plugin.go:607-694`).

The dimension's headline question — *can a governance rule be added without modifying agent code?* — splits cleanly along an instance/logic line. OPA answers "yes, first-class": bundle polling with rollback-to-last-good-revision is the primary operating model (`v1/plugins/bundle/plugin.go:513-520`, retention verified at `v1/plugins/bundle/plugin_test.go:3994`). The other sources answer "partially, by design": runtime-editable *instances* exist everywhere (standing approval rules in agent-framework session state `_harness/_tool_approval.py:218-245`; role assignments and protected labels in langfuse DB tables `runLifecycle.ts:333-343`; callable policies consulting external state in openai-agents-sdk `tool.py:486-493`; schema-driven settings values in openhands `use-save-settings.ts:21-45`), while policy *logic* — scope catalogs, tool approval classifications, guardrail lists, analyzer mappings — is deliberately bound to construction or deploy. Langfuse makes this split explicit and defends it with a test that refuses to let a new MCP tool ship unclassified (`in-app-agent-mcp-policy.servertest.ts:13-27`).

Auditing is the weakest thread across all five sources. No source mechanically guarantees audit coverage of policy changes; the strongest implementation (langfuse's structured actor+before/after audit log, invoked across 72 files) is convention-enforced rather than intercepted (`auditLog.ts:7-155`). OPA propagates bundle revisions into every decision log, status payload, Prometheus gauge, and provenance response (`v1/plugins/logs/plugin.go:49-81`) but keeps no internal change history and captures no mutating actor on its REST path (`v1/server/server.go:2217-2329`).

## Core Thesis

Policy injection architecture follows product shape. OPA, whose product *is* policy evaluation, invests everything in runtime distribution safety: pull-based bundles, signature verification at every remote injection point, rejection-based conflict handling, atomic activation with last-good-state retention (`v1/bundle/store.go:1139-1252`, `v1/plugins/bundle/plugin.go:607-694`). Multi-tenant SaaS (langfuse) needs both review-gated logic and operator-editable instances, so it compiles policy vocabularies into shared packages while pushing instances into databases. Libraries and SDKs (agent-framework, openai-agents-sdk) bind policy to constructed object graphs because their users are developers, then compensate with callables that can proxy any external decision source. A thin frontend (openhands) injects parameters and leaves enforcement to another repo, paying for that split with convention-based parity. The transferable insight: **the question is not whether policies live in code or config, but which layer owns *logic* versus *instances*, and whether conflicts are resolved by declared precedence, structural rejection, or accidental pipeline ordering.** Four of five sources lack a cross-mechanism precedence arbiter; only OPA resolves conflicts deterministically, and it does so by refusing them outright rather than arbitrating.

## Approach Models

**agent-framework — composable layered enforcement without a registry.** Governance enters at six points ranked by strength: per-tool `approval_mode` checked in the calling loop (`_tools.py:1763-1790`), FIDES information-flow middleware enforcing integrity/confidentiality labels (`security.py:1643-1704`), tool metadata in `additional_properties` (`source_integrity`, `max_allowed_confidentiality`, `accepts_untrusted`), remote MCP annotations mapped to local labels (`security.py:3018-3096`), declarative YAML approval modes (`MicrosoftLearnAgent.yaml:18-21`), and external Purview DLP terminating runs on violation (`purview/_middleware.py:24-147`). There is no unified policy object; mechanisms compose implicitly through pipeline position, and within-mechanism precedence is documented but cross-mechanism precedence is not (agent-framework report, Answers §1/§3).

**langfuse — split ownership: compiled vocabulary, database instances.** The RBAC scope grammar (`Resource:Action`), role→scope maps, the ~90-tool approval classification, and the entitlement matrix are compile-time constants in `@langfuse/shared` consumed identically by web, worker, and browser (`projectAccessRights.ts:5-272`, `mcpPolicy.ts:27-360`). Instances — memberships, protected labels, rate-limit overrides, per-conversation grants — are runtime-editable data. Enforcement funnels through tRPC middleware composition (`trpc.ts:297-401`) with three independent gates between the agent and side effects: RBAC filters the tool list before the model sees it, approval-class tools interrupt for a human, and the transport layer independently restricts capability-typed API keys (langfuse report, Architectural Decisions §3).

**opa — policy distribution as first-class subsystem.** Five injection points converge on one destination. Bundles declare disjoint manifest roots; overlapping activation fails atomically while the previous revision keeps serving (`v1/bundle/store.go:1139-1252`). JWT signature verification attaches at download time for every remote source (`v1/bundle/verify.go:70-210`). Discovery goes further: a downloaded Rego bundle evaluates to produce OPA's own configuration, making governance topology remotely steerable, with the discovery endpoint itself pinned against remote change (`v1/plugins/discovery/discovery.go:508`). Even OPA's static config is validated by an embedded Rego policy (`v1/config/validate.rego`) — governance machinery applied reflexively to governance inputs.

**openai-agents-sdk — typed callables at construction, additive enforcement.** Guardrails are dataclasses wrapping Python functions attached to four host objects (Agent lists, RunConfig lists, FunctionTool attributes, MCPServer `require_approval`), normalized once at init (`mcp/server.py:548-576`). Precedence is additive: agent- and run-level guardrails concatenate and all execute; the first tripwire cancels siblings (`run_internal/guardrails.py:144-168`). Structural conflicts are rejected up front — MCP always/never overlap raises `UserError` (`server.py:783-788`), output guardrails incompatible with server-managed conversations abort before the loop starts (`agent_runner_helpers.py:263-275`). Runtime flexibility comes from callables evaluated per event, which may consult external state without SDK modification.

**openhands — parameter injection with delegated enforcement.** A typed settings model (`confirmation_mode`, `security_analyzer`, `settings.ts:128-129`) is translated client-side into wire-level policy objects (`NeverConfirm`/`ConfirmRisky{threshold}`/`AlwaysConfirm`; analyzer kinds) stamped onto every conversation-start payload (`agent-server-adapter.ts:593-618,1120-1121`). Enforcement lives in the external agent-server. The repo's own hard boundary is manifest admission: extension-authored automation manifests are untrusted data, version-checked fail-closed before anything renders, with host validation explicitly refusing to defer to schemas shipped alongside the manifests being validated (`manifest-validation.ts:1-17,587-592`).

## Pattern Catalog

### 1. Fail-closed defaults on ambiguity

- **Problem:** Policies must behave safely when inputs are unknown, unevaluable, or malformed.
- **Demonstrated by:** agent-framework (unlabeled content defaults UNTRUSTED/PUBLIC-sink `security.py:303-306,3057-3062`; unknown YAML approval mode → AlwaysRequire `McpServerToolApprovalModeExtensions.cs:20-27`); openai-agents-sdk (MCP callable policy without agent context → `needs_approval=True` `mcp/server.py:815-846`); openhands (manifest version mismatch → refuse outright `manifest-validation.ts:37-38,587-592`).
- **Why it works:** Unknown states cannot silently widen permissions; every unmappable case collapses toward restriction.
- **Copy when:** Building any gate that consumes labels, enums, or remote hints.
- **Overkill/risky when:** Applied without escape valves for availability-critical paths — note langfuse deliberately made masking fail-open-by-default with an explicit `failClosed` env knob because dropping ingestion events has business cost (`applyIngestionMasking.ts:200-215`).
- **Evidence:** Per-source reports, Failure Modes sections.

### 2. Rejection-based conflict resolution over runtime arbitration

- **Problem:** Multiple policy sources can contradict.
- **Demonstrated by:** opa (cross-bundle root overlap is fatal to activation, old state keeps serving `v1/bundle/store.go:1200-1251`); openai-agents-sdk (MCP always/never overlap → `UserError` at construction naming tools `mcp/server.py:783-788`); langfuse (unclassified tool breaks the exhaustiveness test, blocking merge `in-app-agent-mcp-policy.servertest.ts:13-27`); openhands (host validation wins over shipped schemas, whole-manifest rejection `manifest-validation.ts:6-8`).
- **Why it works:** Conflicts become build/deploy-time errors instead of runtime surprises; no arbitration semantics need documenting or trusting.
- **Copy when:** Policy authors are developers whose changes pass review anyway.
- **Overkill/risky when:** Legitimate overlap exists — OPA pays for disjointness with mandatory root planning and no override escape hatch (opa report, Tradeoffs).

### 3. Human approval as durable, replay-safe state — not an inline callback

- **Problem:** Approvals must survive restarts, resist replay against changed risks, and expire.
- **Demonstrated by:** agent-framework (`_PendingPolicyApproval` binds consent to function-signature+label+session+exact disclosed violation tuple, consumes on use, forces re-approval if violations change `security.py:1624-1639,1853-1862`); openai-agents-sdk (approve/reject serialized into resumable schema-versioned `RunState` with sticky scopes `run_state.py:1300-1324`, `CURRENT_SCHEMA_VERSION = "1.17"` at `:182`); langfuse (exactly-once CAS transition; double-approve yields conflict error; TTL expiry fails the parked run with `APPROVAL_EXPIRED`; decisions record `decidedByUserId` in append-only events `runLifecycle.ts:263-297`, `approvalEvents.ts:10-18`).
- **Why it works:** Binding consent to the exact disclosed risk closes the approve-blindly hole; persistence closes the crash window; CAS closes races.
- **Copy when:** Any approval flow that parks a run awaiting a human.
- **Weaker variant:** openhands' confirmation UI deduplicates submissions in client memory only — refresh clears the guard (`conversation-confirmation-buttons.tsx:17-22,96-97`).

### 4. Metadata annotations as decentralized policy input

- **Problem:** Tool owners and remote servers need to participate in policy formation without touching harness code.
- **Demonstrated by:** agent-framework (MCP `readOnlyHint`/`openWorldHint` mapped to FIDES labels; operator overrides replace derived labels but force `accepts_untrusted=False` so overrides can't widen integrity tolerance `security.py:3186-3194`); langfuse (agent API keys require `readOnlyHint === true` or explicit allowlist `registry.ts:170-189`); openai-agents-sdk (`needs_approval`, `is_enabled`, tool-scoped guardrails as FunctionTool fields `tool.py:472-493`).
- **Why it works:** Policy rides alongside capability declarations, staying fresh as tools evolve.
- **Risks observed:** Annotations parsed but never enforced (agent-framework skill-frontmatter `allowed-tools` stored at `_skills.py:3477-3478`, no consumer found); mapped-but-unreachable choices (openhands translates `pattern`/`policy_rail` analyzers no settings surface exposes `settings-handlers.ts:433-436`).

### 5. Test/type-enforced policy completeness

- **Problem:** Adding a capability without classifying it creates silent policy holes.
- **Demonstrated by:** langfuse (`satisfies Record<string, InAppAgentMcpToolPolicy>` derives the tool-name type from map keys, so a new tool fails compilation until classified `mcpPolicy.ts:360-363`, backed by the equality test); openai-agents-sdk (setting `needs_approval` on a hosted shell tool raises at construction since it could never be honored `tool.py:1405-1409`).
- **Why it works:** Policy drift becomes a type error or failing test — cheaper than audit.
- **Copy when:** A policy map must cover a growing, enumerable surface.

### 6. Prompt rules as advisory layer, structurally separated from enforcement

- **Problem:** Behavioral guidance wants natural language; guarantees want code.
- **Demonstrated by all four agent sources:** agent-framework documents harness instructions as advisory with nothing verifying compliance (`_harness/_agent.py:54-79`); openai-agents-sdk derives sandbox prompt text deterministically from the trusted manifest while enforcing mount authority in code (`sandbox/remote_mount_policy.py:30-46`, `_mount_security.py:155-160`); openhands injects `<RUNTIME_SERVICES>` with self-ranking directives (`agent-server-adapter.ts:281-297`); langfuse uniquely serves its governing prompt from prompt management and records resolved name+version with every run (`runtime/agent.ts:1488-1499`) — the one case where prompt policy is itself versioned, rollable, and provenance-linked.
- **Why it works:** Separation prevents false assurance; langfuse's addition makes even advisory text auditable.
- **Evidence:** Per-source reports, Where-do-rules-live answers.

### 7. Revision propagation to decision surfaces

- **Problem:** Operators must answer "which policy produced this decision?"
- **Demonstrated by:** opa best-in-class — decision logs carry per-bundle revisions read per request (`logs/plugin.go:49-81`, `getRevisions` `server.go:1058-1084`), status exposes `active_revision` + Prometheus gauges (`bundle/status.go:25-97`, `status/plugin.go:576-591`), query responses return provenance (`server.go:2766-2786`). Partial analogs: langfuse stores prompt name+version per agent run (`runtime/agent.ts:1477-1481`); openai-agents-sdk schema-versions persisted state with documented summaries (`run_state.py:176-225`).
- **Why it works:** Provenance turns debugging and compliance from archaeology into a lookup.

### 8. External policy delegation with explicit failure semantics

- **Problem:** Centralized policy services introduce a new failure domain.
- **Demonstrated by:** langfuse (masking callback POSTs events to an operator-supplied service before storage; default fail-open, `LANGFUSE_INGESTION_MASKING_CALLBACK_FAIL_CLOSED=true` drops instead; both modes instrumented `applyIngestionMasking.ts:190-216`); agent-framework (Purview terminates runs via `MiddlewareTermination`, but `ignore_exceptions` converts evaluation failures into pass-through and post-checks skip streaming responses entirely `purview/_middleware.py:100-107,139-147`).
- **Why it works / when to copy:** Delegation scales governance org-wide, but only if fail-open vs fail-closed is a deliberate, observable knob — not a hidden tolerance flag.

## Key Differences

**Update mechanism is the sharpest divide.** OPA treats runtime updates as the primary operating model — etag long-polling, delta bundles, discovery-driven reconfiguration of the entire plugin set, with rollback safety (`v1/download/download.go:290-309`, `plugin.go:513-520`) — because fleet-wide consumers need fresh policy without deploys. Langfuse deliberately gates policy *logic* behind deploys ("review-gated policy changes instead of live edits") while keeping instances hot, because its threat model includes its own operators. openai-agents-sdk offers no reload at all — guardrail lists are captured at Agent construction and input guards bind at turn 0, so mid-run mutation wouldn't reliably take effect anyway (`run_loop.py:1192-1196`) — but callables give an application-level escape hatch. openhands applies changed values at next conversation start only, leaving running conversations stale by construction (`buildStartConversationRequest`, `agent-server-adapter.ts:1050-1132`). These are constraint responses, not quality differences.

**Conflict resolution spans three philosophies.** OPA rejects overlaps before they exist (root disjointness). Langfuse uses intersection: human approval can only promote tools already RBAC-available — `available.has(toolName)` guard, re-validated server-side — so "approval relaxes workflow friction, not permissions" (`mcpPolicy.ts:501-507`, README.md:231). agent-framework uses most-restrictive-wins *within* FIDES (`combine_labels`: any UNTRUSTED taints, highest confidentiality wins `security.py:240-254`) but has no arbiter *across* mechanisms — a Purview block and a FIDES allow coexist, decided by pipeline position, not declared precedence (agent-framework report, Answers §3). openai-agents-sdk runs everything additively with strictest-outcome-wins via first tripwire. openhands resolves by exclusion (deprecated field copies hidden from UI, `verification-settings.tsx:9-12`).

**Audit maturity ranks roughly by product surface.** Langfuse, where audit logs are a paid product feature, records actor identity, roles-at-decision-time, and serialized before/after state, and gates reading the trail behind its own entitlement+scope (`auditLog.ts:7-155`, `auditLogs.ts:88-99`) — but coverage depends on 72 files remembering to call it. OPA propagates revisions everywhere decisions are observable yet never records who pushed a policy (`storage.Store` is current-state-only, `interface.go:19-44`). openai-agents-sdk audits execution (guardrail spans) and outcomes (serialized approvals) but not actors or change history. agent-framework's FIDES audit log is an in-memory list with clear-and-read APIs and no persistence (`security.py:2163-2184`). openhands has nothing durable; manifest rejections go to `console.warn` (`manifest-registry.ts:32`).

## Tradeoffs

- **Composability vs global visibility** — agent-framework reuses the middleware pipeline for all policy, gaining zero new abstractions and per-agent configurability (ADR-0024) but yielding no single place answering "what is this agent allowed to do?" and ordering-sensitive cross-mechanism outcomes; OPA takes the opposite bet, funneling every transport through one transactional pipeline so atomicity is uniform regardless of how policy arrives (`plugin.go:607-694`).
- **Hot updates vs review gates** — OPA's live bundles mean a compromised or buggy bundle service pushes everywhere instantly (mitigated by signatures and the pinned discovery stanza); langfuse's deploy-gated catalogs make unauthorized change impossible but a misclassification fix waits on a release cycle (langfuse report, Tradeoffs §1).
- **Expressivity vs operability** — openai-agents-sdk's Python-callable policies are maximally flexible but need a code deploy and offer no YAML/env surface for non-developers; its own report notes callables proxying external services as the mitigation, effectively rebuilding what OPA sells natively.
- **Disjointness vs flexibility** — OPA's root-rejection prevents silent clobbering but forces up-front root coordination with no layering override; empty/unset roots claim everything, rejecting all other writes (`server.go:2538-2550`) — safe default, sharp footgun.
- **Fail-open availability vs strictness** — langfuse rate limiting returns undefined when Redis is down, letting requests proceed (`RateLimitService.ts:117-123`); agent-framework executes the tool with only a warning when the label tracker didn't run (`security.py:1969-1976`) — a fail-open seam inside an otherwise fail-closed design. Both trade correctness for uptime, but only langfuse's masking path makes the choice configurable.
- **Client-side translation vs duplication** — openhands keeps the server generic by compiling policy client-side, but every semantic change needs synchronized releases across three repos, bridged only by a test name asserting parity (`agent-server-adapter.test.ts:349`).

## Decision Guide

- **Many consumers need policy refreshed without deploys?** Adopt OPA's model: pull-based signed bundles, transactional activation, last-good-state retention, revision propagation to every decision surface. This is the reference implementation for policy-as-data distribution.
- **Building a multi-tenant platform where operators and users both change policy?** Copy langfuse's split: compile the *vocabulary* (scopes, classifications) into reviewed code with exhaustiveness tests; store *instances* (assignments, grants, overrides) in the database; rebuild derived policy per request/run so revocations take effect immediately (`executeInAppAgentRun.ts:330-344`).
- **Building a library/SDK where users are developers?** Follow openai-agents-sdk: typed policy objects at construction, structural conflict rejection with named errors, fail-closed callable evaluation, durable schema-versioned approval state. Accept that ops-facing hot-reload is out of scope; expose callables so applications can proxy their own decision services.
- **Frontend/client slice of a larger system?** Inject-don't-enforce like openhands, but invest the saved enforcement complexity in admission rigor (fail-closed version checks, closed-vocabulary allowlists) and get a machine-checked contract with the enforcing backend — not a parity test named after a convention.
- **Choosing between conflict-resolution styles:** use structural rejection (OPA/SDK style) when policy changes flow through CI; use intersection guards (langfuse style) when human or runtime actions might try to widen permissions; most-restrictive-wins (agent-framework FIDES) works well for data-label combination but does not scale to cross-mechanism arbitration — define declared precedence there (external engine > enforcement middleware > approval > advisory prompt) rather than inheriting pipeline order.
- **Adding an external policy engine?** Make fail-open/fail-closed an explicit, instrumented knob (langfuse pattern), never a silent exception-tolerance toggle (agent-framework `ignore_exceptions`).

## Practical Tips

1. **Bind consent to the disclosed risk.** Copy agent-framework's replay-bound approvals: approval tied to function signature, security label, session, and exact violation tuple, consumed on use, invalidated when the violation set changes (`security.py:1840-1870`).
2. **Make policy drift a build error.** Derive types from the policy map (langfuse `satisfies` pattern) and pin completeness with an equality test; reject impossible combinations at construction (SDK `UserError` pattern).
3. **Recompute derived policy at the moment of use.** Langfuse rebuilds agent tool policy every run, closing the stale-grant window after role revocation; openhands conversely builds conversation payloads once, freezing policy for the conversation's lifetime.
4. **Propagate versions to decisions.** Attach the policy artifact identity (bundle revision, prompt name+version, schema version) to whatever record a decision produces — OPA's decision-log revisions are the template; openai-agents-sdk's `SCHEMA_VERSION_SUMMARIES` shows the cheap version for persisted state.
5. **Give overrides non-widening semantics.** agent-framework's `annotation_overrides` replace labels but force `accepts_untrusted=False`; langfuse's always-allowed grants can only promote RBAC-available tools. Overrides should relax friction, never permissions.
6. **Separate advisory prompt text from enforced behavior, then version the prompt anyway.** Langfuse serving governed prompts through prompt management with recorded versions gets audit-grade provenance out of what other sources treat as throwaway strings.
7. **Persist approval decisions atomically with the transition.** Langfuse commits the grant and the `decidedByUserId` event in the same transaction as the exactly-once CAS — decision, effect, and audit cannot diverge.

## Anti-Patterns / Caution Signs

- **Parsed-but-unenforced declarations:** agent-framework stores skill-frontmatter `allowed-tools` that nothing consults (`_skills.py:3477-3478`) — an operator reading the file reasonably believes it constrains execution. If you parse a policy declaration, enforce it or remove the parser.
- **Dead mappings and mock-only surfaces:** openhands translates `pattern`/`policy_rail` analyzers exposed by no real settings surface, and its options endpoint exists only in mocks (`settings-handlers.ts:804`) — mapped-but-unreachable policy kinds rot silently.
- **Fail-open seams inside fail-closed systems:** agent-framework executes unchecked when the label-tracking middleware didn't run (`security.py:1969-1976`); Purview skips streaming post-checks entirely. Audit your composition order for paths that bypass enforcement.
- **Silent exception tolerance on external engines:** `ignore_exceptions` converting Purview evaluation failures into pass-through weakens the strongest policy layer precisely during incidents.
- **Name-based identity for auto-approvals:** standing rules matching by tool-name can approve unrelated same-named tools — agent-framework documents the bypass rather than structurally preventing it (`_tool_approval.py:365-376`); SDK guardrail names break trace continuity when renamed.
- **Unexplained strictness escalations:** openhands collapsing to `AlwaysConfirm` whenever the analyzer isn't exactly `"llm"` means a user picking a lighter analyzer gets a stricter experience with no explanation (`agent-server-adapter.ts:600-604`).
- **Audit-as-convention:** 72 files calling `auditLog()` with no interception guarantee means new routes stay silent until review catches the omission; likewise OPA's REST PUT logs no principal, so "who changed this" needs sink correlation.
- **Client-memory guards on server protocols:** openhands' duplicate-submission protection evaporates on refresh; anything guarding a protocol step belongs server-side.
- **Empty catch-all ownership:** OPA bundles shipping without explicit roots claim every path and block all other writes — warn at publish time.

## Notable Absences

- **No unified cross-mechanism precedence anywhere except by rejection.** All four agent sources resolve conflicts per-subsystem; none documents a global ordering (e.g., external engine > middleware > approval > prompt). agent-framework names this gap explicitly in its Future Considerations.
- **No engine-level actor capture on policy mutation.** OPA's PUT handler doesn't log the authenticated principal; openai-agents-sdk's approval ledger stores outcomes, not approver identity; openhands records nothing. Only langfuse attributes actors — at the application layer, via opt-in calls.
- **No per-rule semantic versioning with deprecation.** OPA's revision is a single free-form string per bundle; agent-framework found no versioning scheme at all in searched surfaces; langfuse's scope catalog has history only via git.
- **No mechanical audit-coverage guarantee** in any source — no lint rule, middleware interception, or base-class requirement tying mutations to audit emission.
- **Not tested, therefore unknown:** whether OPA's Purview-style decision caching serves stale policy after admin tightening (no invalidation policy verified); whether the agent-server honors `ConfirmRisky.threshold` as the frontend assumes (enforcement lives outside openhands' repo boundary); realtime/voice guardrail parity in openai-agents-sdk was not traced.

## Per-Source Notes

- **agent-framework (6/10):** Richest injection-point inventory (six mechanisms) with genuinely novel pieces — FIDES information-flow labels with three-tier propagation precedence, replay-bound pending approvals, session-backed standing rules, .NET parity. Held back by the missing-label fail-open path, in-memory-only audit, constructor-bound allowlists with no file loader, and zero policy versioning. Best-in-study documentation of precedence *within* mechanisms (docstring contracts at `security.py:692-710`).
- **langfuse (7/10):** Clearest instance/logic ownership split, backed by the study's only test-enforced policy completeness and its only actor-attributed change auditing. Three-gate defense-in-depth for the agent (RBAC filter → human approval → capability-typed keys) is a strong template. Gaps: opt-in audit coverage, absent precedence document, fail-open Redis dependency, undocumented session-staleness window for embedded roles.
- **opa (9/10):** The maturity benchmark. Transactional activation with verified last-good-retention, etag rollback retry-safety, root-disjointness conflict rejection, signature verification at every remote boundary, reflexive config-as-policy validation, and revision provenance on every observable surface. Missing the last mile: internal change journal, actor attribution, concurrency guard on same-ID PUTs, typed revisions.
- **openai-agents-sdk (7/10):** Most disciplined construction-time hygiene — conflict rejection, hosted-tool mismatch detection, fail-closed unevaluable policies — plus durable schema-versioned approval state enabling crash-resilient human-in-the-loop. Constrained by code-bound lifecycle, implicit additive precedence, and no policy content identity beyond name strings.
- **openhands (6/10):** As a frontend slice, correctly refuses to enforce and instead excels at admission: fail-closed version-gated manifest validation with prose specifications tied line-for-line to checks. Its weaknesses are the costs of the split repo: parity by test name, unaudited settings, stale policy on live conversations, and unanswerable questions about server-side enforcement semantics.

## Open Questions

- Should agent frameworks adopt a declared cross-mechanism precedence order, or is pipeline-position composition acceptable if fail-open seams (like agent-framework's missing-label path, `security.py:1969-1976`) are eliminated? No studied source demonstrates the former; agent-framework demonstrates the risks of the latter.
- Can OPA's rejection-based root-disjointness model work at agent-harness scale, where tool/policy owners vastly outnumber bundle publishers and up-front root coordination may be impractical?
- What is the right staleness bound for session/JWT-embedded roles used in authorization decisions? Langfuse knows roles ride the session (`trpc.ts:313-317`) but could not locate the refresh trigger in reviewed files.
- Is there a middle ground between langfuse's deploy-gated classification maps and fully hot operator configuration that preserves the exhaustiveness guarantee (its report suggests promoting the map to configurable data using the existing test as migration validation)?
- Does openai-agents-sdk preserve full guardrail-result fidelity across `RunState` resume cycles, and do realtime/voice pipelines match core-loop policy injection points? Both were explicitly out of traced scope.
