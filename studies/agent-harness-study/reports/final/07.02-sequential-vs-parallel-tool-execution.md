## Executive Summary

Seven sources split into three camps on the core question of whether tools in one model turn run one-at-a-time or concurrently. Four harnesses are **parallel-by-default** inside a turn: agent-framework's Python stack gathers one task per call (`python/packages/core/agent_framework/_tools.py:1848-1864`), pydantic-ai launches every non-barrier call as a task with a per-tool `sequential=True` opt-out (`pydantic_ai_slim/pydantic_ai/_tool_execution.py:807-827`, `232-251`), openai-agents-sdk runs function tools concurrently but deliberately serializes its side-effecting built-ins (shell, apply-patch, computer) per category (`src/agents/run_internal/tool_execution.py:1655-1665`, `2334-2459`), and langgraph fans out both inside `ToolNode` and across Pregel tasks via `Send` (`libs/prebuilt/langgraph/prebuilt/tool_node.py:855-858`; `chat_agent_executor.py:849-859`). Three are **sequential-by-default**: agent-framework's .NET stack gates concurrency behind `AllowConcurrentInvocation = false` (`dotnet/src/Microsoft.Agents.AI/ChatClient/ChatClientAgentOptions.cs:64-75`), openhands exposes `tool_concurrency_limit` documented as "1 = sequential (default)" (`src/mocks/settings-handlers.ts:92-105`), and crewai's older paths execute strictly one tool per turn, with only its newer native tool-calling executors running batches in a hardcoded `ThreadPoolExecutor(max_workers=min(8, n))` (`lib/crewai/src/crewai/agents/crew_agent_executor.py:742-767`).

Despite these opposing defaults, the corpus converges on almost everything else: all seven produce **deterministic result ordering regardless of completion order**, all seven convert ordinary per-call failures into data while reserving exception-based aborts for deliberate control flow, and six of seven have **no read/write side-effect metadata** on user-defined tools — conflict management lives in owner-component locks, state-schema rules, or developer discipline rather than in the scheduler. Temporal is the lone first-class exception with its `PureTask` vs `SideEffectTask` declaration taxonomy (`chasm/registrable_task.go:46-130`).

The maturity spread is wide: openai-agents-sdk, pydantic-ai, and temporal score 9 with explicit models, configurable limits, and failure-proven tests; langgraph scores 8 with structural conflict detection; agent-framework 7 (strong Python contract, divergent .NET default, no batch-width cap); crewai and openhands score 6 (path-dependent or boundary-limited models with real but narrow safeguards).

## Core Thesis

Sequential-vs-parallel is decided twice, at two different layers, and the sources disagree far more about the second decision than the first. The **first decision** — do calls in a turn overlap? — is a product-shape choice: libraries that mirror provider behavior pick parallel defaults (pydantic-ai documents this motivation at `docs/tools-advanced.md:736-740`), while platforms serving non-expert operators pick safe serial defaults (openhands' dial, .NET's flag). The **second decision** — what prevents concurrent calls from corrupting each other — is where designs genuinely differentiate, and none of them solve it inside the tool scheduler itself. Instead, conflict management migrates outward: to the state layer (temporal's size-1 workflow semaphore plus RangeID-fenced persistence, `service/history/workflow/context.go:116` and `common/persistence/data_interfaces.go:113-148`; langgraph's immutable-snapshot supersteps with reducer-gated merges, `libs/langgraph/langgraph/pregel/main.py:2959-2972`), to fixed categories for framework-owned tools (openai-agents-sdk's serial write executors), to per-tool developer declarations (pydantic-ai's barriers), or to component owners who discover races themselves (the MCP header snapshot lock in agent-framework, `python/packages/core/agent_framework/_mcp.py:3123-3130`). The transferable insight: **make parallelism safe by construction where you already own shared state, declare effectfulness where you can't, and never leave it to arrival-time luck.**

## Approach Models

**Cluster A — Parallel-by-default, developer-declared serialization (Python asyncio libraries).**
pydantic-ai is the purest expression: `'parallel'` is the ContextVar default (`pydantic_ai_slim/pydantic_ai/tool_manager.py:40-46`), and opting out happens at two scopes — a per-tool `ToolDefinition.sequential` barrier (`tools.py:583-591`) or a run-scoped `parallel_execution_mode('sequential')` (`tool_manager.py:170-185`). agent-framework's Python stack shares the default but has no per-tool opt-out; its only serialization gates are approval requirements pausing the whole batch (`python/packages/core/agent_framework/_tools.py:1775-1832`) and provider-owned locks. langgraph applies the same default at two layers simultaneously (node-level `gather`, graph-level `Send` fan-out). openai-agents-sdk belongs here for its function-tool tier, with a validated `max_function_tool_concurrency` cap (`src/agents/run_config.py:136-158`).

**Cluster B — Sequential-by-default, opt-in concurrency (platforms and conservative stacks).**
.NET agent-framework flips the switch (`AllowConcurrentInvocation` default false, pinned by tests at `dotnet/tests/Microsoft.Agents.AI.UnitTests/ChatClient/ChatClientAgentOptionsTests.cs:27`); openhands defaults its user-facing dial to 1; crewai's ReAct path, StepExecutor, and LLM fallback are all sequential — the fallback path actually drops every call after the first (`lib/crewai/src/crewai/llm.py:1755`). These sources treat concurrency as a capability users earn, not a behavior they disable.

**Cluster C — Category/kind-based policy (framework knows the tool's nature).**
openai-agents-sdk splits each response into six category executors launched together; function tools parallelize, while shell/local-shell/apply-patch/custom/computer executors loop serially ("Run … serially", `src/agents/run_internal/tool_execution.py:2370-2424`). temporal achieves the same effect with richer machinery: CHASM forces authors to register tasks as `PureTask` (atomic with the state transition) or `SideEffectTask` (validated, outbound-queued, destination-grouped, circuit-broken) (`chasm/registrable_task.go:46-130`). This cluster sidesteps per-tool metadata entirely by classifying at the type/registration level.

**Cluster D — State-layer conflict management (correctness below the scheduler).**
langgraph's BSP runtime makes parallel tasks read an immutable channel snapshot and merge writes only at step boundaries; a reducer-less channel receiving two values per step fails loudly with `InvalidUpdateError` (`libs/langgraph/langgraph/channels/last_value.py:56-64`), and reducer-backed merges apply in task-path order (`_algo.py:253-256`). temporal funnels all mutation of one workflow through a size-1 priority semaphore backed by optimistic-concurrency fencing and monotonically assigned event IDs (`mutable_state_impl.go:2483-2485`). In both, the tool scheduler can be aggressively parallel precisely because the state layer refuses corruption.

**Cluster E — Boundary-limited observation.**
openhands owns the protocol, settings surface, and two client-executed tools, but the executor honoring `tool_concurrency_limit` lives in a sibling repo; agent-framework's .NET concurrent executor likewise lives in external Microsoft.Extensions.AI, leaving only the flag surface inspectable (`dotnet/src/Microsoft.Agents.AI/ChatClient/ChatClientExtensions.cs:93-109`). Both rate honestly around what they can prove.

## Pattern Catalog

**1. Order-preserving fan-in (indexed reorder buffer).** *Problem:* parallel completion scrambles transcripts. *Mechanism per source:* `asyncio.gather` input-order preservation plus per-call result groups (agent-framework, `python/packages/core/agent_framework/_tools.py:1878-1879`); preallocated `ordered_results[idx]` filled from `as_completed` (crewai, `experimental/agent_executor.py:1764-1794`); `_combine_tool_outputs` flattening in input order plus `apply_writes` sorted by task path (langgraph, `tool_node.py:862-887`; `_algo.py:253-256`); results keyed by plan order and rebuilt by iterating the original sequence (openai-agents-sdk, `tool_execution.py:337-356`, `2239-2241`); per-index dicts drained in `sorted(...)` order even on exception (pydantic-ai, `_tool_execution.py:838-852`); event IDs drawn from a single cursor (temporal, `mutable_state_impl.go:2483-2485`); ULID-keyed log with re-sort and `action_id` back-links (openhands, `use-event-store.ts:41-53,131-151`). *Why it works:* correlation is positional or identity-based, never arrival-based. *Copy when:* any concurrent output feeds an ordered history, transcript, or replayable log — i.e., essentially always in this domain. *Overkill when:* consumers are order-insensitive telemetry sinks. *Evidence:* ordering is asserted by tests in at least four sources (`tests/agents/test_agent_executor.py:1274-1277`; `libs/prebuilt/tests/test_tool_node.py:237-250`; `tests/test_run_step_execution.py:287-323`; `common/tasks/execution_queue_scheduler_test.go:145-149`).

**2. Errors-as-data, control-flow-as-exceptions.** *Problem:* one bad tool shouldn't kill a batch, but genuine control flow must not be swallowed. *Demonstrated:* agent-framework converts ordinary exceptions to error `function_result` contents while deliberately re-raising `MiddlewareTermination`/`MiddlewareFailure` (`_tools.py:1569-1574,1696-1722`); crewai turns generic exceptions into per-call error messages but lets `ToolExecutionFailedError` abort (`experimental/agent_executor.py:1780-1791`); langgraph routes handled errors to `ToolMessage(status="error")` while exempting `GraphBubbleUp` interrupts from sibling cancellation (`tool_node.py:1002-1012`; `_runner.py:616-634`); openai-agents-sdk pipes exceptions through `failure_error_function` into model-visible strings (`tool.py:1863-1870`); pydantic-ai isolates `ModelRetry`/`ToolFailed` as parts but cancels siblings on unexpected exceptions (`_tool_execution.py:697-702,828-837`); temporal nacks per task with backoff/DLQ, never aggregating (`executable.go:706-750`). *Why it works:* it cleanly separates "the model gave bad arguments" (recoverable, feed back to the model) from "infrastructure broke" (abort deterministically). *Copy universally.*

**3. Barrier segmentation (structural happens-before without locks).** *Problem:* certain calls must not overlap neighbors. *Clear demonstration:* pydantic-ai's `_segment_by_barriers` partitions the emission sequence so each `sequential=True` tool becomes a single-element segment executed inline between parallel segments (`_tool_execution.py:232-251`), asserted by an active-counter test showing zero in-flight siblings (`tests/test_agent.py:7017-7065`). Analogues: langgraph's superstep boundary makes sibling writes invisible until merge; temporal's workflow lock gives happens-before per execution. *Why it works:* ordering constraints become structure, not lock bookkeeping, and one barrier no longer serializes the entire batch (v1 behavior consciously dropped, pinned by `tests/test_toolsets.py:1314-1334`). *Copy when:* user-supplied tools need opt-out granularity. *Risky when:* developers forget to declare writers — nothing enforces the annotation.

**4. Concurrency caps at the spawning tier.** *Problem:* a model emitting N calls spawns N executions; resources exhaust. *Demonstrated:* langgraph wraps submitted coroutines in `gated(semaphore, coro)` when `max_concurrency` is set, proven by capping 100 Sends at 10 (`libs/langgraph/langgraph/pregel/_executor.py:214-217`; `test_pregel_async.py:3492-3541`); openai-agents-sdk refills slots as tasks settle rather than using a semaphore object (`tool_execution.py:1643-1653`); temporal exposes worker counts, queue concurrency, and group limiters as dynamic config (`common/dynamicconfig/constants.go:2134-2256`). *Contrast:* agent-framework searched clean for any semaphore in the invocation path; pydantic-ai's limiter wraps whole runs, not tool batches (`agent/__init__.py:694`); crewai's `min(8, n)` is hardcoded (`experimental/agent_executor.py:1754`). *Lesson:* a cap at one tier does not bound another tier — langgraph's own report notes node-level `gather` escapes the task-level cap (`tool_node.py:855-858`).

**5. Failure arbitration with deterministic precedence.** *Problem:* simultaneous multi-failure outcomes must be reproducible. *Clear demonstration:* openai-agents-sdk's `_FunctionToolFailure(error, order, source)` ranks `CancelledError(0) < Exception(1) < BaseException(2)`, breaks ties by lowest call order, and merges late teardown failures without masking the root cause (`tool_execution.py:180-186,258-304`). Related: pydantic-ai's retry-wins invariant suppresses an otherwise-valid output when a retry exists (`_tool_execution.py:881-908`); langgraph re-raises the first error after cancelling siblings (`_runner.py:650-697`). *Copy when:* batches are large or failure semantics feed durable logs.

**6. Contention as a routing signal, not an error.** *Problem:* hot contended units degrade everyone or thrash. *Demonstrated:* temporal converts lock-acquisition timeouts into `ErrResourceExhaustedBusyWorkflow` and reroutes the affected workflow onto a dedicated sequential queue with TTL'd lifecycle and capped count (`service/history/workflow/cache/cache.go:327-357`; `common/tasks/execution_queue_scheduler.go:121-151`). *Counter-examples:* crewai's provider-support fallback silently switches the concurrency model mid-run (native parallel → ReAct sequential, `crew_agent_executor.py:577`); langgraph's `InvalidUpdateError` at least forces a declarative fix (add a reducer) rather than last-write-wins silence.

**7. Idempotency claims and fencing at execution edges.** *Problem:* replays, retries, and duplicate completions double-execute mutating or billable work. *Demonstrated:* openhands claims `tool_call_id` in a localStorage ledger *before* network work (`child-conversation-launch.ts:196-227`); temporal fences duplicate completions by `(schedID, attempt, version)` identity and stamps conditional writes with shard RangeID (`context.go:61-66`; `cassandra/shard_store.go:126-151`); crewai's RWLock cache excludes failures so a transient error is never cached permanently (`cache_handler.py:38-41`). *Copy at every trust boundary where ACK precedes work.*

**8. Concurrency behavior pinned by timing and barrier tests.** *Problem:* async bugs don't reproduce naturally. *Demonstrated:* crewai asserts elapsed `< 0.5s` for parallel versus `>= 0.2s` for sequential and reproduces races with `threading.Barrier` (`tests/agents/test_agent_executor.py:1273,1316`; `tests/tools/test_tool_failure.py:1384-1391`); langgraph proves two sleeping nodes finish in less than the sum of sleeps (`test_pregel.py:5258-5288`); openai-agents-sdk asserts max observed concurrency equals exactly 3 by default and that a queued call never starts after an earlier failure under a cap (`test_run_step_execution.py:251-283,327-363`); pydantic-ai counts active siblings at a barrier (`test_agent.py:7017-7065`); agent-framework maps spec scenarios to named tests including cancellation twins (`docs/specs/004-python-function-calling-loop.md:439,528,532`). *Copy:* if a concurrency guarantee isn't pinned by a timing/counting test, it isn't a guarantee.

## Key Differences

**Default posture tracks product shape, not quality.** pydantic-ai states the reasoning plainly: models emit parallel calls, so the harness mirrors them (`docs/tools-advanced.md:736-740`). openhands and .NET agent-framework serve operators who didn't write the tools, so they ship serial and require an explicit raise. crewai shows the cost of evolving between the two without unifying: the same prompt can execute with different concurrency depending on which of its four stacks handles it (`llm.py:1755` vs `crew_agent_executor.py:742-767`).

**Where write-serialization lives differs fundamentally.** openai-agents-sdk serializes writes it owns (built-in categories) and leaves user functions to convention; pydantic-ai inverts this — user tools self-declare via barriers, and there is no built-in category concept; langgraph and temporal refuse the question at the tool layer entirely, arbitrating at the state layer instead; agent-framework delegates to whoever owns mutable state (MCP headers, session stores, todo stores each carry their own lock, `python/packages/core/agent_framework/_mcp.py:3126-3130`, `_sessions.py:2438-2443`).

**Configurability spans the full spectrum.** temporal tunes everything at runtime via dynamic config with documented defaults (`constants.go:2134-2157`); openai-agents-sdk and langgraph expose public, validated knobs (`max_function_tool_concurrency`, `max_concurrency`); crewai hardcodes 8 workers with no override; agent-framework and pydantic-ai offer no intra-batch width control at all.

**Ordering guarantees split by consumer where durability matters.** pydantic-ai maintains emission order for message history but ships a separate `parallel_ordered_events` mode explicitly motivated by DBOS durable replay (`_tool_execution.py:1153-1156`; `tests/test_agent.py:7387-7390`); langgraph keeps final channel state deterministic while streaming events follow completion order (`_algo.py:253-256` vs `_runner.py:574-613`); openai-agents-sdk similarly commits streaming outputs as they finish while keeping the canonical item list ordered. Simpler harnesses (agent-framework, crewai) maintain one ordered transcript and don't distinguish channels.

**Cancellation honesty varies.** All thread-using sources admit in-flight threads cannot be interrupted — agent-framework documents and tests that sync-tool side effects survive an abort (`docs/specs/004-python-function-calling-loop.md:336-338`), crewai notes the window in code comments (`experimental/agent_executor.py:1775-1777`), and openai-agents-sdk bounds the drain (0.25 s / 64 steps, `tool_execution.py:167-169`). The difference is operational transparency, not capability.

## Tradeoffs

- **Latency vs corruption safety.** pydantic-ai and agent-framework maximize throughput and bet entirely on developer discipline — pydantic-ai's docs present `sequential=True` as the remedy without enforcing it (`docs/tools-advanced.md:736-740`). openai-agents-sdk buys structural safety only for its own write-categories, still leaving two parallel function tools free to race shared state. temporal eliminates the bet by making the correctness boundary the state machine plus fencing, paying with per-transition latency and author-side Validate/Execute/Discard complexity (`chasm/registrable_task.go:46-130`). Best fit: library ↔ platform respectively.
- **Post-hoc vs pre-flight budget enforcement.** agent-framework checks `max_function_calls` after each batch completes, accepting overshoot up to batch size — tested explicitly at limit 5 with six executions (`test_function_invocation_logic.py:1939-1943`). pydantic-ai projects post-batch usage *before* fanning out so an exceeding batch executes nothing (`_tool_execution.py:444-448`). Pre-flight is stricter; post-hoc avoids orphaned call/result pairs.
- **Fail-fast vs partial progress.** On failure, langgraph cancels siblings and their committed writes survive only if checkpointed (`_runner.py:616-697`); openai-agents-sdk converts cancelled siblings into model-visible errors and relies on model recovery next turn (`test_run_step_execution.py:1183-1189`); pydantic-ai preserves completed returns as an `interrupted` history request (`_agent_graph.py:2158-2172`); agent-framework stores approval-blocked safe siblings session-side for later resume (`_tools.py:1796-1832`). The more durable your results, the more partial-progress preservation pays.
- **Bounded-drain constants vs tunability.** openai-agents-sdk hardcodes its 0.25 s/64-step/0.1 s windows, trading operator control for simplicity (`tool_execution.py:167-169`); temporal makes equivalent lifecycle values dynamic config (`constants.go:2134-2157`). Slow cleanup paths turn into fire-and-forget tasks in the former.
- **Expressive declarations vs determinism debt.** temporal's Pure/SideEffect split enables aggressive in-transition batching but pushes correctness burden onto authors implementing validation/discard correctly; langgraph's reducers demand schema foresight — forgetting one converts a latent race into a loud `InvalidUpdateError` abort at runtime (`channels/last_value.py:59-64`). Both trade silent-corruption risk for declared-up-front effort, a good trade in this domain.
- **Global dial vs per-tool granularity.** openhands' single integer (`tool_concurrency_limit`) is trivially operable but cannot express "safe to run concurrently with X"; its `SecurityRisk` enum gates confirmation, not scheduling (`common.ts:59-64`). pydantic-ai's per-tool flag costs registration-time thought but yields minimal-overhead precision.

## Decision Guide

1. **Pick the default by audience, not preference.** Tool authors are developers reading provider docs → parallel-by-default with a per-tool opt-out (Cluster A). Operators configure agents they didn't write → sequential-by-default behind a validated setting (Cluster B). crewai is the cautionary tale for drifting between camps without unifying the model.
2. **Choose the serialization locus by ownership.** You control a fixed set of write-tools → category serialization (openai-agents-sdk style): zero metadata, guaranteed correct. Tools are user-supplied → declaration-based barriers (pydantic-ai style). You own a shared-state abstraction → arbitrate at that layer with declared merge policy or exclusive writes (langgraph/temporal style). You can see none of the tools → ship the blunt global dial plus confirmation gating (openhands style).
3. **Escalate infrastructure only when durability demands it.** If runs are replayed or resumed (durable executors), you need emission-ordered event streams and deterministic merge — pydantic-ai's `parallel_ordered_events` and langgraph's path-sorted writes exist precisely for this. For ephemeral in-process runs, completion-ordered streaming is cheaper and fine.
4. **Add a concurrency cap as soon as tool bodies consume threads or connection pools, at the same tier that spawns tasks.** Don't repeat langgraph's gap (task-tier cap, unbounded node-tier gather) or crewai's hardcoded ceiling.
5. **If contention concentrates on specific entities, route rather than block** — temporal's busy-workflow → dedicated sequential queue beats global slowdown, but only pair it with honest signals (events/metrics) so downstream telemetry can tell which concurrency model ran.
6. **Before adopting parallel batching for user tools, decide what one failed call means.** Continue-and-collect (errors-as-data) for model-facing recoverability; fail-fast-with-arbitration when siblings are expensive or side-effectful. openai-agents-sdk's arbitration design is the reference implementation.

## Practical Tips

- Correlate parallel results by identity or position, never by arrival time; make it contractual (spec line, docstring) and test it (agent-framework's spec-to-test mapping, `docs/specs/004-python-function-calling-loop.md:340`).
- Keep the two failure tiers visibly separate in code: conversion helpers for ordinary errors, a small closed set of deliberate exception types for aborts — and test the cancellation path including what happens to already-running siblings.
- Propagate tracing context into spawned work with `contextvars.copy_context().run(...)` — agent-framework and crewai converged on this independently (`python/packages/core/agent_framework/_tools.py:1846-1862`; `crew_agent_executor.py:748-757`), and agent-framework has a telemetry test asserting nested spans survive parallelism (`test_observability.py:5992-6068`).
- Separate "how many calls the model may emit" from "how many the host runs concurrently": .NET's `AllowMultipleToolCalls` vs `AllowConcurrentInvocation` and OpenAI's `parallel_tool_calls` vs `max_function_tool_concurrency` are orthogonal knobs; conflating them produces surprising serial batches.
- Match budget-check units to their purpose: agent-framework's circuit breaker counting *batches* means five simultaneous failures advance the streak by one (`_tools.py:2718-2733,2856-2860`) — decide whether your breaker guards rounds or calls.
- Give client-side/fire-and-forget tools an idempotency claim before side effects (openhands' `claimToolCall`) and a total failure contract that converts errors into agent-visible guidance (`child-conversation-launch.ts:499-536`).
- Group parallel calls in your event model with a shared response ID even if the UI ignores it today — openhands shows the rendering pass is one step away once IDs exist (`action-event.ts:51-56`).
- When threads can't be interrupted, say so in docs and pin it with a test (agent-framework's cooperative-cancellation twins, `test_middleware_with_agent.py:2596-2659`) instead of implying a stronger guarantee than exists.

## Anti-Patterns / Caution Signs

- **Flags-as-gates.** crewai reuses `result_as_answer` and `max_usage_count` to mean "don't parallelize," coupling three unrelated concerns (turn-ending, scarcity, concurrency safety) to two booleans whose descriptions never mention batching (`experimental/agent_executor.py:1903-1909`; `base_tool.py:180-187`). Sign your design is drifting: a flag's docstring no longer predicts its scheduling effect.
- **Duplicated concurrency logic across executors.** crewai implements `_should_parallelize_native_tool_calls` twice (production and experimental executors) — drift is inevitable. Extract one shared policy function the moment a second caller appears.
- **Silent concurrency-model changes.** crewai's fallback ladder (native → first-call-only → ReAct) changes latency and reflection granularity mid-run with no emitted event, and the fallback silently drops all calls after the first (`llm.py:1755`). Any change to effective concurrency should be observable.
- **Unbounded fan-out at the tier you forgot.** langgraph's node-level `gather` bypasses `max_concurrency` (`tool_node.py:855-858`); agent-framework and pydantic-ai have no intra-batch cap at all. Audit every `gather`/`TaskGroup`/pool submission for who bounds N.
- **Shared mutable counters touched from workers without tests.** agent-framework's `FunctionTool.invocation_count +=` runs inside worker threads for sync tools with no coverage (`_tools.py:530-553,562`) — classic latent race. Caution sign: instance state on tool objects assumed single-threaded while the scheduler is not.
- **Breaker/budget unit mismatches.** Per-batch error counting and post-batch budget checks are defensible only when documented and tested; otherwise operators discover overshoot in production.
- **Safety optimizations shipped off-by-default forever.** temporal's ExecutionQueueScheduler sits disabled with no soak path (`constants.go:2134-2139`), so most clusters absorb repeated busy-workflow churn — shadow features decay.
- **Coarse enums substituting for effect metadata.** openhands' four-level `SecurityRisk` drives confirmation but cannot express co-run safety; a harness offering only a global integer plus a risk level will eventually need real read/write declarations.

## Notable Absences

- **No general resource-keyed lock registry for user tools exists anywhere in the corpus.** The closest mechanisms are temporal's destination grouping for its *own* side-effect tasks (`outbound_queue_factory.go:108-177`) and transport-specific locks (agent-framework MCP header lock, openai-agents-sdk MCP `_request_lock`, `src/agents/mcp/server.py:932-961`). openai-agents-sdk names an advisory lock registry as future work; every other source reports negative findings for resource-conflict detection searches.
- **No side-effect/read-write metadata on user-defined tools in six of seven sources** (all but temporal's CHASM, which covers server components, not user function tools). Multiple reports independently propose identical remedies — a `parallel_safe`/read-write-set annotation feeding the scheduler.
- **Batch-unit timeouts/backpressure:** agent-framework explicitly found no evidence of a batch-level timeout; pydantic-ai offers per-tool timeouts converted to `ModelRetry` (`toolsets/function.py:684-691`) but no per-step bound; langgraph has step timeouts at the superstep level wired via `step_timeout` (`main.py:2969`).
- **End-to-end verification was impossible for two sources within their study boundaries:** openhands' executor (separate backend repo) and agent-framework's .NET concurrent executor (external Microsoft.Extensions.AI dependency) — only flag surfaces, protocols, and defaults were provable.
- **Retry/idempotency tied to parallel batches is largely delegated:** agent-framework found no retry-once/idempotency handling in its invocation layer; retries live with callers/providers across most sources (dimension 07.03 territory).

## Per-Source Notes

- **agent-framework (7).** Python executes every actionable call in one response as gathered tasks with span-preserving spawn, ordered groups, per-call error isolation, a consecutive-error circuit breaker (default 3), and post-batch budgets; approval-required tools pause the whole batch with safe siblings stashed for resume. .NET exposes `AllowConcurrentInvocation` (default false) onto an external executor, with tests pinning wiring but not observed concurrency. Conflict handling is owner-localized (MCP header lock, store locks). Weakest points: no batch-width cap, no side-effect model, cross-stack default divergence.
- **crewai (6).** Four execution stacks disagree: ReAct sequential, first-call-only fallback (`llm.py:1755`), provider-serial loops, and native thread-pool batches (`min(8, n)` with copied contexts). Batching is gated by `result_as_answer`/`max_usage_count`; results replay in call order; per-call errors isolated, deliberate aborts cancel futures. Real strengths: race-regression tests with barriers and timing assertions, RWLock cache excluding failures, thread-safe usage claiming. Weakest: flag conflation, hardcoded cap, silent fallback truncation, undocumented batching behavior.
- **langgraph (8).** Two parallel layers over a BSP runtime: node-level `executor.map`/`gather` and graph-level `Send` fan-out to independent Pregel tasks. Conflict detection is channel-based (reducer-less channels reject multi-writes; reducers merge in task-path order). `max_concurrency` throttles async task submission via semaphore; failure stops/cancels siblings except interrupts, which aggregate. Errors degrade to `status="error"` ToolMessages. Weakest: no tool side-effect metadata, node-tier gather uncapped, sync limiting outsourced to langchain-core.
- **openai-agents-sdk (9).** Six category executors run concurrently; function tools start all-at-once (validated optional cap with slot-refill), write-categories loop serially. Failure handling is engineered: priority arbitration with order tie-breaks, bounded drains (0.25 s/64 steps/0.1 s), cross-category failure event, background-task exception reporting, deterministic plan-position ordering. Provider-side `parallel_tool_calls` kept separate from local execution. Weakest: function-tool safety by convention, cross-category write conflicts undetected, drain windows hardcoded.
- **openhands (6).** Frontend-only source owning protocol and UX: `llm_response_id` groups parallel calls, `tool_call_id`/`action_id` link results, `tool_concurrency_limit` (default 1) is a schema-driven validated setting, `SecurityRisk` drives confirmation policies, and client-executed tools use an idempotency ledger with never-reject guidance contracts. Event store provides dedup, re-sort, in-place reconciliation. Weakest: enforcement unverifiable in-boundary, coarse risk enum, localStorage claims defeatable by multi-tab.
- **pydantic-ai (9).** Parallel default with two-scope opt-outs (per-tool barrier flag, run-scoped mode ContextVar); `_segment_by_barriers` gives happens-before structure; three end-strategy processors govern output/function interleaving; history is always emission-ordered while events are completion-ordered (or emission-ordered under `parallel_ordered_events` for durable replay); failures split into isolated model-visible retries vs cancel-and-drain on unexpected exceptions with completed returns preserved as interrupted history; usage projected before fan-out. Weakest: unbounded per-step tasks, undeclared writers unprotected, raw asyncio inside an anyio codebase.
- **temporal (9).** Composable `Scheduler[T]` algebra over FIFO pools, weighted round-robin channels, and per-workflow sequential queues reached via busy-workflow routing. Correctness rests on a size-1 priority semaphore per workflow context, RangeID-fenced conditional persistence, and cursor-assigned event IDs — schedulers stay aggressive because the state layer refuses corruption. CHASM declares `PureTask` vs `SideEffectTask` with validate/group/circuit-break pipelines. Failures are per-task (nack/backoff/DLQ), never aggregated. Weakest: sequential queues off by default, `QueueConcurrency=2` nuance, best-effort dispatch ordering.
