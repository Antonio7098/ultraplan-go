## Executive Summary

Nine sources, all with full evidence. Three score **9** (langfuse, openai-agents-sdk, pydantic-ai), one scores **8** (agent-framework), four score **7** (crewai, langgraph, letta, temporal), and one scores **5** (openhands). Every source produces a coherent, followable run tree *within* a single process — this is now table stakes across the cohort. What separates the scores is how each handles the four genuinely hard problems: streaming/async boundary stitching, durable execution across interrupts and checkpoints, cross-process propagation, and semantic completeness of the step inventory.

The cohort splits into distinct approach models rather than quality tiers. Two frameworks emit native OpenTelemetry GenAI semantic-convention spans (agent-framework, pydantic-ai); one builds a first-party typed span subsystem with its own wire format (openai-agents-sdk); one delegates the entire tree to host-ecosystem callbacks (langgraph); one stamps hierarchy onto domain events at emit time (crewai); one derives lineage from a flat event log at render time (openhands); one stores flat rows and reassembles the tree in the backend (langfuse, with letta as an OTel-plus-relational-bridge hybrid); and one instruments at infrastructure granularity with attribute-based correlation across async boundaries (temporal).

Cross-cutting findings: ambient-context parenting (contextvars or threaded config) is near-universal and works, but every mature implementation adds *explicit* stitching at async/streaming seams because ambient context alone leaks. Trace identity persistence across resume/checkpoint is the second-most-shared mechanism among high scorers. Cross-process propagation is the weakest link nearly everywhere — only temporal proves it end-to-end in tests, langfuse preserves foreign IDs verbatim, agent-framework covers MCP and workflow messages but not HTTP surfaces, and pydantic-ai covers Temporal and realtime integrations specifically. Guardrail spans exist in only four of nine sources; eval spans in three; retrieval spans in effectively one (as a backend type, not emitted by any framework here). The answer to the dimension question — *"can you see the full path from user request to tool result in one trace?"* — is **yes in-process for all nine, and across process boundaries for only about half, under specific conditions each**.

## Core Thesis

A coherent in-process run tree is a solved problem whose solution has converged: **ambient-context parenting (contextvars or a threaded config object) plus explicit stitching at async boundaries**. The cohort's real design divergence lies in three decisions that no two top sources answer the same way:

1. **Where hierarchy is enforced.** Write-time structural enforcement (langgraph's manager chain at three call sites, crewai's scope-stack pairing, pydantic-ai's `'outermost'` capability ordering, openai-agents-sdk's contextvar provider) versus eventual consistency with read-time repair (langfuse's iterative tree builder hardened after production OOM crashes, openhands' client-side action↔observation pairing). Write-time enforcement yields provable trees but breaks silently when emitters miss a pair or drop a config argument; read-time repair tolerates messy producers but must defend against orphaned parents, duplicate IDs, and cycles.

2. **How trace identity survives durability boundaries.** High scorers serialize trace identity into the durable state itself: openai-agents-sdk persists a `TraceState` into resumable `RunState` and reattaches without duplicate start events; agent-framework carries W3C headers inside workflow messages through checkpoints; letta writes the OTEL `trace_id` onto each relational `Step` row to bridge runs→spans; crewai rebuilds its scope stack from recorded events on resume. Temporal demonstrates the failure mode of skipping this: history tasks execute from `context.Background()`, so one workflow lifetime fragments into hundreds of disjoint traces stitched only by `temporalWorkflowID` attributes and TraceQL queries.

3. **Whether the trace format is a standard.** Sources that adopted OTel GenAI semconv or preserved W3C identity verbatim (agent-framework, pydantic-ai, langfuse, temporal) interoperate with ecosystems by construction; sources with bespoke formats (openai-agents-sdk's `trace_…` IDs and ingest endpoint, crewai's AMP batches, openhands' event union) get cohesive end-to-end experiences inside their own products but require bridges everywhere else. Notably, the two 9-scoring frameworks reached that score through opposite bets — one standard-first (pydantic-ai), one platform-first (openai-agents-sdk) — because both compensated with exceptional operational safeguarding and tested tree-shape guarantees.

## Approach Models

### Model A — Native OTel GenAI semantic-convention instrumentation (agent-framework, pydantic-ai)

**Where implemented.** agent-framework: `python/packages/core/agent_framework/observability.py` (spans) and `_workflows/*` (workflow spans); .NET mirrors via `System.Diagnostics.Activity` (`dotnet/src/Microsoft.Agents.AI/OpenTelemetryAgent.cs`). pydantic-ai: the `Instrumentation` capability (`capabilities/instrumentation.py`), shared `open_model_request_span` (`_instrumentation.py`), and realtime variants (`realtime/_instrumentation.py`).

**Main mechanism.** Framework classes emit spans named per OTel GenAI semconv — `invoke_agent {name}`, `chat {model}`, `execute_tool {name}` — on a tracer resolved from the global/provider `TracerProvider`; parentage follows OTel context propagation. Both pin the tree shape by construction: agent-framework composes telemetry layers as mixins so function-loop iterations become sibling `chat` spans under one `invoke_agent` (`_chat_client.py:3430-3436`); pydantic-ai declares the run span `'outermost'` and disables graph-engine auto-instrumentation to guarantee a single root (`capabilities/instrumentation.py:116-117`, `_agent_graph.py:2587`).

**Supporting mechanisms.** Centralized attribute registries (`OtelAttr`, `InstrumentationNames`); sensitive-data gating separate from enablement; usage roll-up from inner chat spans onto the agent span; fan-in causality expressed as span *links* (agent-framework) and versioned wire formats v2–v6 (pydantic-ai).

**Fits best.** Libraries and frameworks consumed by third parties who bring their own backends; polyglot stacks needing one vocabulary.

### Model B — First-party bespoke span subsystem (openai-agents-sdk)

**Where implemented.** `src/agents/tracing/` — `TraceImpl`/`SpanImpl`, `DefaultTraceProvider`, `BatchTraceProcessor`, 13 typed `SpanData` classes (`span_data.py:28-451`).

**Main mechanism.** A `Trace` context manager wraps each `Runner` invocation (`run.py:736-745`); every step emits a typed span (`task_span`, `turn_span`, `agent_span`, `response_span`, `function_span`, `guardrail_span`, `handoff_span`, `mcp_tools_span`); parents resolve from contextvars at creation (`provider.py:433-481`). Export is flat payloads carrying `(trace_id, parent_id)`; the hosted dashboard reconstructs the tree.

**Supporting mechanisms.** Processor plug-in architecture (OpenAI backend is just the default consumer); `NoOpTrace`/`NoOpSpan` preserving semantics when disabled; resume-as-reattach via serialized `TraceState`; task/turn spans opt-out for flatter trees.

**Fits best.** Products that own both SDK and dashboard and want schema-driven rendering and deep lifecycle invariants without depending on external standards maturity.

### Model C — Delegated host-ecosystem tracing (langgraph)

**Where implemented.** `libs/langgraph/langgraph/pregel/main.py` (root run), `_algo.py` (task runs), `_internal/_runnable.py` (node runs); viewers are external (`langgraph dev` → Studio, LangSmith).

**Main mechanism.** LangGraph emits only generic LangChain callback events; the run tree is built by threading `RunnableConfig["callbacks"]` through loop → task prep → node runnable → user code, deriving child managers via `get_child()` at exactly three sites (`main.py:2792-2797`, `_algo.py:716-720`, `_runnable.py:421-445`). Subgraphs inherit config, so their roots nest automatically; LangSmith's tracing context is installed alongside so `@traceable` calls join the tree (`_runnable.py:96-101`).

**Supporting mechanisms.** `checkpoint_ns` as the durable spine reassociating resumed executions; `TAG_HIDDEN` suppressing framework internals; `TracePolicy` redaction at the span boundary; stream handlers correlating fragments via `run_id` + injected metadata instead of tracer internals.

**Fits best.** Frameworks embedded in a larger ecosystem that already owns the tracer; teams trading standards breadth for zero-cost ecosystem integration.

### Model D — Event-bus run tree with emit-time hierarchy stamping (crewai)

**Where implemented.** `lib/crewai/src/crewai/events/event_bus.py` (stamping), `events/event_context.py` (scope-stack rules), `events/listeners/tracing/` (batch collection), `crewai_core/plus_api.py` (AMP export).

**Main mechanism.** Every execution step emits a typed `BaseEvent` onto an in-process bus; the bus stamps `event_id`, `parent_event_id` (from a contextvar scope stack of ~26 start/end event-type pairs), `previous_event_id`, and a monotonic `emission_sequence` at emit time (`event_bus.py:537-570`). A listener buffers events per session into batches shipped to the vendor AMP backend, which renders the tree. Parentage is deterministic and validated (mismatch → WARN/RAISE configurable), not inferred from timestamps.

**Supporting mechanisms.** Batch ownership rules preventing nested flows/crews from stealing or finalizing a parent's batch; checkpoint restore rebuilding the scope stack and sequence counter; signal-handler flushes; consent-first enablement. Crucially, CrewAI's *separate* OTel pipeline emits deliberately flat root spans for product telemetry — the run tree never touches OTel.

**Fits best.** Products with a hosted observability surface where the same domain events can feed UI, checkpoints, and console formatting.

### Model E — Event-sourced log with derived lineage (openhands)

**Where implemented.** Frontend ("Agent Canvas") consuming the agent-server: `src/types/agent-server/core/openhands-event.ts` (event union), `src/utils/handle-event-for-ui.ts` (pairing), `src/stores/use-event-store.ts` (dedup/sort).

**Main mechanism.** There is no tracing system — no OTel, no span/trace IDs. One persisted, timestamp-ordered event log holds every step (messages, actions, observations, hooks, rejections, condensation, errors); hierarchy is *derived* by consumers from reference fields: observations point to actions via `action_id`/`tool_call_id`, sibling tool calls share `llm_response_id`, hook events carry `action_id`/`message_id` (`observation-event.ts:18-39`, `action-event.ts:52-56`). The UI pairs started/terminal events by id replacement at render time.

**Supporting mechanisms.** ULID ids + timestamp re-sorting + id dedup for delivery continuity; transcript/trajectory exports as alternative projections; conversation-per-subexecution isolation for delegation.

**Fits best.** Chat-first products where the log doubles as the UI feed, replay anchor, and export format — and where cross-conversation tracing is consciously sacrificed for workspace isolation.

### Model F — Store-flat, reassemble-on-read backends (langfuse; letta's viewer half)

**Where implemented.** langfuse: ClickHouse `observations` table + `treeBuilding.ts` + OTLP/native dual ingestion (`OtelIngestionProcessor.ts`, `ObservationTypeMapper.ts`). letta: collector→ClickHouse `otel_traces` + `GET /v1/runs/{run_id}/trace` joining `Step.trace_id` rows (`step_manager.py:157`, `runs.py:267-307`).

**Main mechanism.** Observations persist as independent rows keyed by `(project, type, date, id)` with nullable parent pointers; observation IDs *are* OTel span IDs and parents are `parentSpanId` passed through verbatim, so any W3C-propagating client nests correctly without server work (`OtelIngestionProcessor.ts:902-905, 1168-1171`). The tree is rebuilt deterministically at read time with defense-in-depth: id-collision dedup, orphan-parent nulling, cycle-safe BFS, iterative (non-recursive) traversal hardened after real OOM incidents (`treeBuilding.ts:88-122, 405-528`). A priority-ordered mapper registry translates foreign vocabularies (OpenInference, OTel GenAI, Genkit, Vercel AI, LiveKit…) onto one typed taxonomy.

**Supporting mechanisms.** Shallow-trace backfill for children arriving before roots; Redis seen-set TTL dedup; fail-open operational posture (Redis outage → empty set, processing continues); edge validation rejecting malformed OTLP with remediation hints.

**Fits best.** Platforms ingesting from many heterogeneous frameworks, where write throughput matters more than write-time integrity and the vendor controls the read path.

### Model G — Infrastructure-grade distributed tracing with attribute correlation (temporal)

**Where implemented.** `common/telemetry/*` (fx modules, gRPC stats handlers, generated persistence decorators), `service/history/queues/executable.go` (task spans), Nexus HTTP instrumentation.

**Main mechanism.** Four span layers — otelgrpc internode spans, gowrap-generated persistence decorators over every store method, per-task consumer spans, otelhttp spans for Nexus/callbacks — wired through per-service `TracerProvider`s (no global provider). Synchronous hops nest and propagate correctly (proven by e2e tests asserting identical TraceIDs and parent/child relations, `tests/nexus_otel_test.go:209-258`). Asynchronous continuation is deliberately *not* nested: durable tasks execute from a fresh context, and correlation falls to `temporalWorkflowID`/`temporalRunID` span attributes joined by TraceQL in Tempo (`docs/development/tracing.md:20-23`), with span links prescribed (but not yet used in production) for batch workers.

**Fits best.** Multi-service systems where durability, not LLM semantics, dominates; where "the trace" is per-request and the business identifier is the durable join key.

## Pattern Catalog

### P1. Ambient-context parenting with explicit async-boundary stitching

**Problem.** Zero-touch nesting of deeply nested work (agents → tools → model calls → subagents) without threading span/context parameters through every signature — while surviving asyncio task boundaries, streaming pulls, and thread pools.

**Sources.** All seven Python/TS framework sources demonstrate the ambient half (agent-framework `observability.py:2380-2400`; crewai `event_bus.py:537-570` + contextvars copied into thread pools at `event_bus.py:513-516`; langgraph `get_child()` chaining and contextvar snapshotting `_runnable.py:143-153`; openai-agents-sdk `scope.py:11-49`; pydantic-ai `capture_current_context()` `_instrumentation.py:547-577`; letta ambient inheritance into `safe_create_task` `utils.py:1200`). The explicit-stitching half appears precisely where streaming is taken seriously: agent-framework attaches the chat span per iterator pull and closes unconsumed streams via `weakref.finalize` (`observability.py:2103-2117, 1780`); pydantic-ai captures OTel context so continuation segments in a *consumer task* update the right `chat` span, carrying TTFT between tasks via a ContextVar (`_instrumentation.py:561-575`, `78-87`); openai-agents-sdk tolerates `GeneratorExit` from foreign tasks when finalizing spans (`spans.py:31-56`).

**Why it works.** Contextvars ride asyncio task creation for free; the explicit captures cover the two cases where that fails — streams consumed in a different context than created, and coroutines awaited in another task's context.

**Copy when.** Building any async agent runtime. The pairing (ambient default + seam-local explicit capture) is the cohort's consensus answer.

**Risky when.** Work crosses processes or thread pools that don't copy context — then spans silently become no-op or rootless (openai-agents-sdk logs debug guidance at `provider.py:436-441`; langgraph documents silent subtree detachment when user code drops the config argument).

### P2. Typed step taxonomy spanning the full execution inventory

**Problem.** Ad-hoc span names make traces unqueryable and viewers dumb; consumers need to distinguish a model call from a tool call from a guardrail evaluation structurally.

**Sources.** openai-agents-sdk: 13 `SpanData` classes with stable type discriminators (`span_data.py:28-451`) — the only source with dedicated guardrail *and* handoff span types. langfuse: `ObservationType` enum explicitly covering GENERATION/EMBEDDING/TOOL/GUARDRAIL/RETRIEVER/EVALUATOR/AGENT/CHAIN (`domain/observations.ts:5-16`). crewai: enumerated start/end event pairs including `llm_guardrail_started/completed` and memory/knowledge/reasoning/skills/A2A types (`event_context.py:240-320`). agent-framework & pydantic-ai: GenAI semconv operation names serve the same role for agent/model/tool steps. letta: span-name conventions (`agent_step`, `%._execute_tool`) act as the de facto query contract (`clickhouse_otel_traces.py:60-78`).

**Why it works.** Schema-driven rendering (openai-agents-sdk), type-specific analytics and bottom-up cost aggregation (langfuse), and deterministic parenting validation (crewai) all fall out of a closed type set.

**Copy when.** You control the emitter vocabulary. **Risky when.** The taxonomy ossifies: langfuse pays for unknown frameworks with a generic-`SPAN` fallback (`ObservationTypeMapper.ts:507`), and letta's hard-coded name filters require SQL edits to evolve (see Caution Signs).

### P3. Flat storage/wire format with deterministic tree reconstruction

**Problem.** Hierarchical storage couples write throughput to tree shape and complicates out-of-order arrival.

**Sources.** langfuse (ClickHouse flat rows, read-time BFS builder, `treeBuilding.ts:405-528`); openai-agents-sdk (flat exported spans carrying `(trace_id, parent_id)`, with a test proving correct nesting even under tied timestamps, `test_span_ordering.py:30-74`); openhands (append-only log, client-side pairing `handle-event-for-ui.ts:404-441`); letta (ClickHouse `otel_traces` filtered by name conventions for the viewer).

**Why it works.** Producers stay append-only and lossless; each viewer picks its projection; late/out-of-order data merges naturally (ReplacingMergeTree upserts, update-last batch ordering).

**Copy when.** You operate the backend/viewer. **Risky when.** Nobody owns the reconstruction: openhands pushes pairing to every consumer, and its search API omits fork `parent_id`, forcing N+1 fetches (`agent-server-conversation-service.api.ts:830-841`). langfuse shows the required investment — its builder was rewritten iterative/no-recursion after production OOM crashes from multi-parent DAGs.

### P4. Persisted trace identity across interrupts, resumes, and checkpoints

**Problem.** Ambient context dies at any durability boundary; resumed work must rejoin the original trace or fragment it.

**Sources.** openai-agents-sdk serializes `TraceState` (trace id, workflow name, hashed key) into `RunState` and reattaches on resume *without* re-emitting start, guarded by an LRU of started trace ids (`traces.py:305-404`, `context.py:63-79`). agent-framework serializes W3C carriers inside workflow messages through checkpoints (`_runner_context.py:46-93`, tested `test_workflow_observability.py:438-471`). crewai rebuilds scope stack + emission counter from the recorded event graph on resume (`crew.py:573-601`). langgraph treats `checkpoint_ns` as the durable spine reattaching interrupt/resume events (`callbacks.py:55-76`). letta persists `get_trace_id()` on every `Step` row, making the public trace-viewer join possible (`step_manager.py:156-158`). pydantic-ai retains the W3C traceparent on the finished `AgentRunResult` so post-hoc feedback/eval spans attach to the same trace (`run.py:604-613`, `tests/test_logfire.py:1289-1401`).

**Why it works.** It converts "resume" from a new root into a reattachment — the difference between one investigation artifact and many.

**Copy when.** Any pause/resume/HITL/durable-workflow feature exists or is plausible. This is the strongest single predictor of high scores in this cohort.

### P5. Causality without nesting: links, causal fields, and correlation ids

**Problem.** Many-to-one joins (fan-in, batch processing, delegation returns) don't fit single-parent trees; forcing nesting loses information or duplicates spans.

**Sources.** agent-framework builds remote-SpanContext **links** from traceparents carried on converging workflow messages, documented "linked (not nested)… for causality tracking" (`observability.py:3223-3280`). crewai maintains a separate `triggered_by_event_id` causal chain beside `parent_event_id` (`base_events.py:82-87`). temporal prescribes OTEL span links for batch workers in its dev guide though production code doesn't yet use them (`docs/development/tracing.md:220-226`). openai-agents-sdk's `group_id` correlates otherwise-separate Realtime trees (weakest form — correlation only, `.agents/references/realtime-tracing.md:16`).

**Why it works.** Preserves true causality graphs where execution genuinely branches; keeps the common chain case a clean tree.

**Copy when.** Fan-in, scatter-gather, or batch consumption exists. **Risky when.** Used as an excuse to skip real propagation — `group_id`-only correlation cannot answer "what did the child do."

### P6. Telemetry must never break the run (defense-in-depth fail-open)

**Problem.** Tracing sits on the hot path of every operation; any telemetry exception is a production incident multiplier.

**Sources.** openai-agents-sdk catches per-processor exceptions in fan-out (`provider.py:117-175`), prevents exporter failures from killing the batch worker (`processors.py:696-710`), and uses deadline-aware shutdown (`processors.py:623-645`). pydantic-ai degrades serialization to `str()`, redaction failures to placeholders, pricing failures to `None`, and computes metrics even when spans are unsampled (`_instrumentation.py:220-230, 160-167, 520-525`). agent-framework swallows malformed traceparents during link building and warns-and-skips on serialization failures (`observability.py:3251, 2511-2518`). crewai wraps its exporter (`SafeOTLPSpanExporter`), retries batch init then degrades, and flushes on signals (`crewai_core/telemetry.py:66-74`; `trace_batch_manager.py:175-232`). letta budgets span attribute sizes (2MB/value, 4MB total) with truncation markers (`tracing.py:250-277`). temporal accepts dropping queued traces on shutdown past a 1s deadline (`temporal/fx.go:1093-1102`).

**Copy when.** Always. This is the least glamorous and most differentiating pattern between a 7 and a 9 in this study.

### P7. Sensitive-data gating decoupled from enablement

**Problem.** Full-fidelity traces (prompts, args, results) conflict with privacy/compliance; a single on/off switch forces choosing between no observability and over-exposure.

**Sources.** agent-framework: metadata always available when instrumented; content requires explicit `enable_sensitive_data` + semconv opt-in (`observability.py:762-774, 927-934`). pydantic-ai: `include_content` / `include_binary_content` flags with container-walking redaction (`_instrumentation.py:141-217`). openai-agents-sdk: `ModelTracing.ENABLED_WITHOUT_DATA` plus URL sanitizers stripping auth/query params (`model_tracing.py:6-14`, `models/_trace.py:9-31`). langgraph: per-node `TracePolicy` transforming recorded payloads (fail-open caveat noted below). temporal: `TEMPORAL_OTEL_DEBUG` env gate around full payload/header capture. letta: parameter skip-lists and size budgets.

**Copy when.** Always, from day one — retrofitting gating after spans carry raw prompts is a migration project.

### P8. Deterministic test oracles for tree shape

**Problem.** "The trace looked right" is not a regression test; parenting bugs surface only in backends days later.

**Sources.** langgraph's `FakeTracer` records full `Run` trees and enables golden assertions of `child_runs`/`parent_run_id` (`fake_tracer.py:46-85`, `test_pregel_async.py:2288-2331`); pydantic-ai's `LogfireSummary` reconstructs parent-child structure from exported spans for snapshot tests (`test_logfire.py:50-92`); openai-agents-sdk asserts parent-before-child ordering under tied timestamps (`test_span_ordering.py:44-74`); agent-framework asserts workflow.run→executor.process→message.send parentage and fan-in links end-to-end (`test_workflow_observability.py:261-399`); temporal ships deterministic-ID helpers plus e2e suites asserting exact span lists across services (`testtelemetry/spans.go:63-87`, `nexus_otel_test.go:394-473`); langfuse integration-tests the full trace→span→generation→event chain (`IngestionService.integration.test.ts:1182-1309`).

**Why it works.** Tree shape becomes a reviewed artifact; every parenting refactor is caught at PR time.

**Copy when.** Always. Note the inverse lesson: langgraph's flagship cross-system test is *skipped* in CI (`test_tracing_interops.py:60`) and letta has **no** parent-child structure test at all (`tests/test_otel_tracing.py` covers sizing only) — both correlate with their lower scores.

### P9. Single canonical root via duplicate-suppression policy

**Problem.** Layered engines (graph engine under agent framework, realtime over classic, auto-instrumentation under manual) mint competing roots, splitting or duplicating trees.

**Sources.** pydantic-ai disables graph auto-instrumentation for agent graphs and skips a second run span in realtime mode (`_agent_graph.py:2587`; `capabilities/instrumentation.py:158-162`); openai-agents-sdk's `create_trace_for_run` returns `None` when a trace is already current and warns that a nested explicit trace is "probably a mistake" (`context.py:58-88`, `create.py:63-67`); agent-framework dedups `gen_ai.response.id`/usage between layers so the agent span doesn't double-report chat data (`observability.py:2056-2064`); letta's .NET analog checks for an existing `OpenTelemetryChatClient` before auto-wiring (`OpenTelemetryAgent.cs:263-269`).

**Copy when.** Any layering exists. **Risky when.** Suppression is implicit — openai-agents-sdk still *creates* the sibling tree on user error (warning only), fragmenting rather than failing.

### P10. Identity passthrough of foreign trace context

**Problem.** A backend cannot stitch what it rewrites; inventing its own IDs orphans cross-service clients.

**Sources.** langfuse keeps sender-supplied W3C trace/span IDs verbatim — observation IDs *are* OTel span IDs (`OtelIngestionProcessor.ts:902-905, 3428-3432`); temporal honors externally injected `traceparent` headers, asserted by e2e test (`nexus_otel_test.go:359-389`); pydantic-ai propagates run identity via OTel baggage keys (`gen_ai.agent.name`, `gen_ai.agent.call.id`, `gen_ai.conversation.id`) stamped onto every downstream span (`_instrumentation.py:123-135`).

**Copy when.** You ingest from or serve arbitrary clients. This is why langfuse achieves cross-process nesting "for free" while framework peers must build it per-integration.

## Key Differences

**Standards posture vs. product cohesion.** agent-framework and pydantic-ai adopt OTel GenAI semconv outright — pydantic-ai even mandates via repo rule that `_otel_*.py` modules implement only spec-defined features, quarantining conveniences like `gen_ai.aggregated_usage.*` under a custom namespace (`models/instrumented.py:136-141`). openai-agents-sdk deliberately ships `trace_<uuid>` IDs, a private ingest endpoint, and a hosted dashboard, achieving tighter end-to-end polish but requiring custom processors for OTel (`docs/tracing.md:155-158`). Neither 9-scorer's choice dominated the other's score; operational depth did.

**Write-time structure vs. read-time repair.** langgraph can point to three literal call sites that determine the whole tree (`main.py`, `_algo.py`, `_runnable.py`); crewai validates start/end pairing with configurable WARN/RAISE (`event_context.py:171-223`). langfuse instead accepts orphaned parents, duplicate IDs, and out-of-order arrival and repairs at read time with incident-hardened algorithms (`treeBuilding.ts:88-122`). The first camp fails silently when emitters misbehave (a missed end event flattens a crewai subtree; a dropped langgraph config detaches a subtree); the second camp shows users a temporarily fragmented tree.

**Semantic vs. infrastructure span granularity.** Frameworks speak domain vocabulary (`invoke_agent`, `handoff_span`, `guardrail_span`); temporal speaks transport vocabulary (`persistence.<Store>/<Method>`, gRPC stats) and explicitly lacks domain spans like "ScheduleActivity" (`docs/development/tracing.md:139-167` roadmap). Same coherence, radically different investigative ergonomics: a temporal user infers workflow intent from method names and workflow-ID attributes, while an openai-agents-sdk user reads intent off the span type.

**Cross-process propagation, four ways.** (1) Verified standard propagation: temporal injects and honors `traceparent` across gRPC/Nexus/HTTP with e2e proof. (2) Partial, framework-mediated: agent-framework injects into workflow message carriers (checkpoint-survivable) and MCP request `_meta`, but not hosted-MCP or A2A/hosting HTTP surfaces (`_mcp.py:294-308`; samples README:170 limitation note). (3) Integration-specific: pydantic-ai rides Temporal's interceptor, realtime WebSocket headers, and result-artifact traceparents — no uniform story (`durable_exec/temporal/_logfire.py:57-60`, `realtime/google.py:609-618`). (4) Absent or one-directional: letta injects outbound via `RequestsInstrumentor` but never extracts inbound; crewai, langgraph, openai-agents-sdk, and openhands have no W3C propagation in-source (negative searches documented in each report).

**Delegation modeling.** openai-agents-sdk makes handoffs first-class (`handoff_span` wrapping execution, receiving agents getting fresh `agent_span`s under the same trace, `Agent.as_tool()` reusing ambient trace, `turn_resolution.py:578-597`, `agent.py:961-969`). agent-framework compiles orchestrations to workflows so handoffs appear as `executor.process` → `invoke_agent` nesting (`_handoff.py:46-52`). pydantic-ai's delegation nesting is *emergent* from asyncio/OTel mechanics with docs recommending names for distinguishability but nothing enforcing containment (`docs/multi-agent-applications.md:380-412`). At the other pole, openhands' child conversations structurally leave the parent log (cloud children send `parent_conversation_id: null`, `child-conversation-launch.ts:416-419`), and letta's database run-tree diverges from its trace-tree — each participant agent gets its own `Run` row while sharing one trace (`sleeptime_multi_agent_v3.py:167-187`).

**Enablement defaults.** agent-framework instruments by default (`ENABLE_INSTRUMENTATION` default true, sticky disable); openai-agents-sdk traces unless disabled; pydantic-ai and crewai are opt-in (capability flag / consent flow, with pydantic-ai asserting zero spans when un-instrumented, `test_logfire.py:163-165`); temporal and letta are deployment-configured; openhands has nothing to enable. Opt-in buys zero overhead and privacy-by-default at the cost of "no tree when you needed one."

## Tradeoffs

**Native semconv (agent-framework, pydantic-ai) vs. bespoke format (openai-agents-sdk, crewai).**
Benefit (native): instant interoperability — any OTel backend, no bridge code, future spec alignment for free. Cost: coupled to evolving spec versions (pydantic-ai manages wire-format versions 2–6 with deprecation warnings; agent-framework openly documents divergences from v1.41 guidance, samples README:220). Best-fit: libraries with unknown consumers. Failure mode: self-admitted shortcuts erode trust — agent-framework's manual traceparent splitting is labeled "simplified" in-code (`observability.py:3253-3256`) and breaks for foreign propagators. Alternative seen: openai-agents-sdk's bespoke route buys schema-driven rendering and platform features (hashed-key resume guards, `traces.py:187-192`) unavailable through generic formats.

**Ambient implicit parenting vs. explicit plumbing.**
Benefit: zero-touch nesting across arbitrary call depth (every framework's position). Cost: silent detachment when context doesn't travel — thread pools without copies, configs dropped by user code (langgraph's documented leak), foreign-task span finalization (openai-agents-sdk tolerates but logs). Best-fit: dynamic agent loops with deep tool chains. Failure mode: a *rootless* subtree looks like missing data, not broken code. Alternative: openai-agents-sdk offers explicit `parent=` overrides (`create.py:95`) for the cases ambient context can't express; agent-framework verifies parentage before attribution (`observability.py:2809-2841`) to catch leakage defensively.

**Write-time integrity vs. eventual consistency.**
Benefit (integrity): provable trees, testable invariants, no repair logic. Benefit (consistency): ingest throughput, out-of-order tolerance, producer freedom. Best-fit: integrity for in-process frameworks controlling their own emitters; consistency for platforms ingesting from the internet. Failure modes: crewai's missed-end-event flattening (WARN default) vs. langfuse's fragmented-tree visibility window until cleanup (`treeBuilding.ts:142-148`). Neither camp escapes validation entirely — langfuse just moved it to the read path.

**Attribute correlation vs. SpanContext persistence across durable boundaries.**
Temporal chose attributes: benefit is a clean hot path with no schema/serialization burden on task records; cost is "one trace per workflow" being impossible today, acknowledged and remediation-prescribed but unresolved (`executable.go:276-280`; `docs/development/tracing.md:194-226`). The cohort's counter-evidence: every framework that persists trace identity into durable state (P4) keeps continuous trees through resume. Failure mode of the attribute approach: hundreds of disjoint traces per long-running workflow, distinguishable only by query.

**Vendor-hosted viewer vs. open export.**
Benefit (vendor): polished zero-config UX — crewai prints an AMP URL per finalized batch (`trace_batch_manager.py:420-455`). Cost: data lockout and loss-on-send-failure with no local spool (`trace_batch_manager.py:308-319`). Contrast: langfuse exposes the full node list via public API (`GET /api/public/traces/{id}`), letta serves filtered spans from its own REST endpoint, and openhands exports transcripts/trajectories as files. Best-fit depends on who operates the backend; the failure mode of vendor-only is losing the tree exactly when the vendor path fails (auth fallback to ephemeral traces mitigates, `trace_batch_manager.py:207-218`).

**Payload fidelity vs. size/cost.**
pydantic-ai defaults `include_content=True` putting full prompts, completions, schemas, and args on spans — maximal debuggability, real exposure and bloat risk, mitigated by opt-out flags rather than opt-in capture. letta hit the wall and split stores: full payloads bypass OTel into a denormalized `llm_traces` table for analytics, "bypass[ing] OTEL for large payloads" (`settings.py:389-394`) — at the price of a null correlation column between the two stores (`provider_trace_backends/clickhouse.py:124`). temporal gates payload capture behind debug env entirely. The pattern: fidelity decisions migrate toward configuration, never disappear.

**Nesting vs. flattening for step detail.**
openai-agents-sdk's task+agent+turn+generation stack is deep enough that users asked for an opt-out flag flattening it (`config.py:12-18`). letta flattened permanently: `agent_step`/TTFT spans were created but never activated, making per-step children siblings under the request root — robust against forgotten closes, but waterfall views overlap and attribution leans on timestamps and `step_id` events (`letta_agent.py:293` vs. `tracing.py:394`). Depth aids navigation; flatness aids resilience; pick based on whether viewers or humans consume the shape.

## Decision Guide

**Building an agent framework/library?** Emit native OTel GenAI semconv spans behind an API-only dependency so any globally configured SDK picks them up (agent-framework's architecture, samples README:164,176). If you have a capability/hook system, make instrumentation a composable capability with declared ordering (`'outermost'`) rather than core plumbing (pydantic-ai). Pin the tree shape by construction — suppress secondary roots, dedup usage between layers (P9).

**Own both SDK and dashboard?** A first-party typed-span subsystem (Model B) is defensible and scored 9 — *if* you replicate the safeguards: non-fatal processors, worker-surviving exporters, deadline-aware shutdown, ordering tests, no-op objects, and resume-reattachment. Budget for a W3C bridge eventually; every bespoke source in this cohort lists it as future work.

**Execution is durable/pausable/resumable?** Persist trace identity into the durable artifact (state blob, checkpoint, step row) and reattach on resume without re-emitting starts (P4). Treat temporal's attribute-correlation stance as a documented debt, not a destination — its own guide prescribes SpanContext persistence/span links as remediation.

**Multi-process or multi-service topology?** Adopt W3C `traceparent` injection/extraction at every boundary you own, honor inbound context (temporal proves this testable end-to-end), and pass identity through whatever message envelope exists — agent-framework's checkpoint-surviving message carriers show envelopes work. If you're the ingestion backend, pass sender IDs through verbatim and map vocabularies via a prioritized registry (langfuse P10).

**Need guardrails/evals/retrieval in traces?** Define the span/event types *when the primitives ship*, not after — the four sources with guardrail representation (openai-agents-sdk, crewai, langfuse, openhands) grew the types alongside the feature; the frameworks lacking the primitive lack the span, and retrofitting is on every roadmap but in nobody's release.

**Frontend/conversation product?** An event-sourced log with reference-field lineage (openhands) is legitimate — but persist origin/parent linkage server-side, keep model calls attributable to specific actions (not aggregate metrics keyed by usage ids), and never rely on client-memory-only tags for attribution (see Caution Signs).

**Choosing between nesting and links?** Nest chains; link fan-ins, batch consumers, and delegations that return. Correlation-id-only (`group_id`) is acceptable solely for surfaces you cannot instrument.

## Practical Tips

- **Stitch streams explicitly.** Attach the active span per iterator pull (agent-framework `with_pull_context_manager`, `observability.py:2103-2117`) and snapshot captured OTel context into consumer tasks (pydantic-ai `capture_current_context`, rationale cites issue #6569). Ambient context alone *will* orphan streamed children.
- **Make the tree a snapshot test.** Reconstruct parent-child from exported spans and assert golden shapes (pydantic-ai `LogfireSummary`; langgraph `FakeTracer`). Assert error status and zero-span behavior when disabled too (agent-framework `test_observability.py:3221-3263, 3685-3715`).
- **Roll usage up the tree once.** Accumulate token usage from inner chat spans in contextvars and apply totals on the agent span with response-id dedup (agent-framework `INNER_ACCUMULATED_USAGE`, `observability.py:3078-3103`; openai-agents-sdk usage deltas on turn/task spans; pydantic-ai `gen_ai.aggregated_usage.*` computed even when unsampled).
- **Keep a kill switch that sticks.** agent-framework's `disable_instrumentation()` is sticky against accidental re-enablement and consulted before side-effect setup (`observability.py:823-871`); letta short-circuits setup under pytest (`tracing.py:150-151`). Both prevent observability from becoming the outage.
- **Return the trace ID to callers.** letta embeds `trace_id` in error responses (`app.py:487`); pydantic-ai retains traceparent on run results for post-hoc feedback spans. Support/users get a grep handle without backend access.
- **Suppress duplicate roots deliberately.** Check for existing current-trace/chat-client before opening another root (P9 sources). Warn loudly — don't silently branch — when users nest explicit traces anyway.
- **Backfill partial trees at ingestion.** If you run a trace backend, emit shallow traces for children arriving before roots and dedupe via TTL'd seen-sets (langfuse `OtelIngestionProcessor.ts:705-803`); reject malformed batches at the edge with reason counts instead of burning worker retries (`otel/v1/traces/index.ts:115-236`).
- **Delay until needed:** sampler knobs (crewai, temporal, and most frameworks live without them initially), pluggable exporter registries, and per-execution batch isolation — all appear in source roadmaps, none blocked shipping. **Avoid:** shipping a second parallel telemetry system for the same execution (crewai's flat-OTel + event-tree split) — derive counters from the canonical event stream instead.

## Anti-Patterns / Caution Signs

- **Two tracing systems, one story.** CrewAI's flat product-telemetry OTel spans and its event-tree coexist with different backends, flags, and semantics (`telemetry/telemetry.py:296` vs. `event_bus.py:537-570`); anyone wanting both trees in one stack needs custom glue. Caution sign: answering "where do traces go?" requires a paragraph.
- **Spans created but never activated.** letta's `agent_step`/TTFT spans aren't made current context, so the rendered hierarchy contradicts the trace-viewer's own filter expectations — attribution survives only via `step_id` attributes and events (`letta_agent.py:293`; `clickhouse_otel_traces.py:60-78`). Caution sign: waterfall views where step internals visibly overlap.
- **Attribution state living only in client memory.** openhands tags planning-agent events with `isFromPlanningAgent` — a non-persisted boolean set by whichever socket delivered the event (`use-event-store.ts:10-12`), with cross-agent delta bleed fixed twice already (#1656). Related: goal-loop re-prompts distinguished from real user input by brittle prompt-text prefixes, self-described "brittle by design" (`should-render-event.ts:15-26`).
- **Convention contracts with no tests.** letta's viewer SQL hard-codes span-name filters; renaming a span silently empties the viewer, and no test covers the filter. Its analytics bridge writes `trace_id=None` while neighboring code warns "trace correlation across backends will fail" for the analogous case (`provider_trace_backends/clickhouse.py:111,124`).
- **Skipped keystone tests.** langgraph's end-to-end LangSmith nesting test — the only proof of `dotted_order` continuity across sync/async boundaries — is disabled for CI timeouts (`test_tracing_interops.py:60`). An unenforced invariant is an uninforced invariant.
- **Wired but dead instrumentation.** temporal's update registry receives a TracerProvider and never starts a span (`service/history/workflow/update/util.go:16-29`) — dead config that suggests coverage that doesn't exist.
- **Lossy backpressure.** openai-agents-sdk drops spans on queue overflow with a warning only (`processors.py:618-621`); crewai abandons events if the send fails, with no local spool (`trace_batch_manager.py:308-319`). Under load — precisely when you need traces — these systems quietly go blind. Counter-example: bounded budgets with truncation markers (letta) or synthetic dropped-span counters (openai-agents-sdk's own roadmap item).
- **Fragmented identity at delegation boundaries.** openhands' cloud children send `parent_conversation_id: null`, leaving "links that mean nothing" across systems (`child-conversation-launch.ts:416-419`); letta mints fresh root traces per HTTP request so multi-turn runs produce disjoint traces stitched only by scanning recent steps for the first populated `trace_id` — an assumption the code itself flags as unverified (`runs.py:299-304`).
- **Fail-open redaction without disclosure.** langgraph's `TracePolicy` records raw payloads if the processor raises (`_runnable.py:80-85`) — availability over confidentiality is a defensible default only when surfaced; temporal's debug mode records full headers/payloads verbatim with intentionally unbounded buffering (`http.go:176-182, 282-283`).

## Notable Absences

- **Guardrail spans in frameworks that lack guardrail primitives.** agent-framework's approval flow contains zero tracing references (`_harness/_tool_approval.py` searched); langgraph has no guardrail concept at all (searched across `libs/langgraph`); letta has no guardrail abstraction (tool-rule enforcement is untraced); pydantic-ai represents validation failures only as retry prompts inside message attributes, with output validators explicitly "not span-worthy" (`capabilities/instrumentation.py:537-545`). Represented well: openai-agents-sdk (`guardrail_span` + tripwire `SpanError` attached to parents), crewai (`LLMGuardrailStarted/Completed` pairs), langfuse (`GUARDRAIL` type — though no dedicated outcome field for blocked/passed), openhands (hook events with `blocked`/`reason` plus per-action `security_risk`).
- **Eval spans.** Only langfuse (`EVALUATOR` type, scores attachable to the exact observed node) and pydantic-ai (evaluator-facing `SpanTree`/`SpanQuery` over collected spans, `span_tree.py:26-120`; online evals extracting span references) represent evals structurally. agent-framework's `_evaluation.py` consumes traces but emits nothing; openai-agents-sdk, langgraph, letta, openhands delegate evals to external products.
- **Retrieval spans.** Effectively absent as *emitted* constructs: agent-framework's registry defines no retrieval span (visible only if RAG is tool-implemented); pydantic-ai likewise (tools/httpx spans only). langfuse's `RETRIEVER` type exists for ingestion but no studied framework emits it natively.
- **Incoming trace-context extraction.** letta (outbound-only), crewai, langgraph, openai-agents-sdk, and openhands extract nothing inbound — external callers cannot join their traces. Combined with the guardrail/eval gaps, "follow one request across every boundary it crosses" is currently achievable in this cohort only under Model A/F/G conditions.
- **Sampling controls.** crewai's enablement is binary (no sampler found across `lib/`); temporal has no sampler knob (searched config; only all-or-nothing); most frameworks defer to the underlying provider. Only pydantic-ai demonstrates sampling-*aware* behavior (metrics survive unsampled spans) and langfuse demonstrates sampling-safe parent forwarding (`PassthroughTracer`, `observability.config.ts:33-46`).
- **Handoff edge semantics beyond typing.** Even langfuse found no dedicated delegated-to/causal edge metadata distinct from parent-child spans — such modeling rides scores/metadata conventions. openai-agents-sdk's typed `handoff_span` is the richest in-cohort representation.

## Per-Source Notes

- **agent-framework (8)** — Native OTel GenAI spans across Python/.NET; workflow layer adds `workflow.build/run` → `executor.process` → `message.send` with fan-in links; checkpoint-surviving W3C carriers and MCP `_meta` injection. Held from 9 by missing guardrail/eval/orchestration spans, partial boundary propagation, and self-admitted simplified traceparent parsing.
- **crewai (7)** — Run tree lives in an event bus: scope-stack pairing stamps parents deterministically, extensively tested, broad step coverage including guardrails and A2A (client side). Vendor-hosted AMP-only viewing, zero cross-process propagation, concurrent in-process executions merge into one batch, and a parallel flat-OTel telemetry system clouds the story.
- **langfuse (9)** — The platform case: flat ClickHouse observations reassembled at read time, foreign OTel IDs preserved verbatim, ten-mapper vocabulary registry, incident-hardened tree builder, shallow-trace backfill. Integrity is eventual and propagation trust is placed in clients — appropriate for its product shape, unverifiable server-side.
- **langgraph (7)** — Pure delegation: three manager-chain call sites define the tree; subgraphs and functional-API tasks nest via config inheritance; `checkpoint_ns` survives resumes. No native OTel/W3C (compat-only via monkey-patch test), keystone interop test skipped, guardrails unrepresented.
- **letta (7)** — OTel middleware + `@trace_method` ubiquity + the pivotal `Step.trace_id` relational bridge powering a public trace-viewer endpoint. Flat step hierarchy (unactivated spans), no inbound extraction, optional-ClickHouse degradation to 501, and a null analytics-correlation column.
- **openai-agents-sdk (9)** — First-party subsystem with a span type for every step class including guardrails and handoffs; resume-as-reattach via persisted `TraceState`; processor/exporter isolation and deadline-aware shutdown; ordering-under-tied-timestamps tested. Bespoke format, drop-on-overflow, and `group_id`-only Realtime correlation are the gaps.
- **openhands (5)** — No tracing system; a typed, persisted event log with id-reference lineage (`action_id`, `tool_call_id`, `llm_response_id`) that is excellent per-conversation and structurally broken across delegation: child conversations unlink, planning-agent merge tags are volatile, model calls appear only as aggregates. Rated against the dimension, not the product's goals.
- **pydantic-ai (9)** — Semconv-maximalist: versioned formats, `'outermost'` capability ordering, snapshot-proven trees including third-party spans, TTFT/task stitching, traceparent-as-artifact, eval `SpanTree`. Gaps: no guardrail/validator spans, integration-specific propagation, sequential-request assumption in bookkeeping (`capabilities/instrumentation.py:88-92`).
- **temporal (7)** — Infrastructure exemplar: per-service providers, generated persistence decorators, e2e-proven synchronous cross-process nesting, deterministic span-test harness. The durable-task context reset fragments workflow lifetimes into attribute-linked trace shards — documented, prescribed remediation, unresolved.

- Is langgraph's JS runtime run-tree behavior equivalent? No LangGraph.js runtime sources existed in the snapshot (client libs only).
- Does openai-agents-sdk's ingestion backend ever stitch cross-service traces, and will Realtime server traces ever merge beyond `group_id`? Both live outside the repository.
- Does the OpenHands agent-server (separate `software-agent-sdk` repo) emit spans internally, and does guardrail policy evaluate before or after the LLM call? Unverifiable from the frontend contract alone.
- Would a pydantic-ai evaluation run produce one unified trace spanning evaluator + agent spans end-to-end? Implied by `context_subtree()` but unasserted by any test; Prefect/DBOS durable paths lack tracing integration entirely.
- How do temporal traces behave under cross-cluster failover task processing, and does the worker SDK join server traces? No XDC-specific handling found; SDK is another repo.
