## Executive Summary

Six sources, six ratings from 4 to 8, and one shared blind spot. Langfuse (8/10) is the only source where dollar cost is computed end-to-end as ordinary product data — priced deterministically at ingestion and inherited by every eval surface (`worker/src/services/IngestionService/index.ts:1265-1383`). Pydantic-ai (7/10) is the only SDK whose eval reports carry actual USD cost inside per-case metrics, harvested from OpenTelemetry span attributes (`pydantic_evals/pydantic_evals/_task_run.py:59-74`; pricing at `pydantic_ai_slim/pydantic_ai/_cost.py:62-95`). Agent-framework (5/10) has the most mature success-rate machinery — typed pass/fail/error counts with CI-gate assertions (`python/packages/core/agent_framework/_evaluation.py:440-468`, `470-543`) — but records tokens only as unpriced counts and omits latency from every eval type. CrewAI (5/10) measures execution time in its eval table yet leaves a `token_usage` parameter wired-but-dead in its report printer (`lib/crewai/src/crewai/utilities/evaluators/crew_evaluator_handler.py:95-96`). OpenAI Agents SDK (4/10) ships excellent cost *primitives* (per-request usage entries built for tiered pricing, `src/agents/usage.py:218-229`) but no evaluation that uses them. OpenHands (4/10), an application frontend with no eval harness at all, renders server-computed costs and automation success rates while transporting latency fields that no code reads (`sources/openhands/src/api/conversation-service/agent-server-conversation-service.types.ts:284-288`).

The dimension's headline question — "Can you compare two model choices on cost vs quality?" — is answered **no out of the box by all six sources**. Each provides a partial manual recipe: pydantic-ai's baseline diff over metadata-tagged runs, langfuse's dataset-experiment run comparison, agent-framework's sample-level model stamping plus Foundry portal views, crewAI's two CLI invocations eyeballed side by side, openai-agents-sdk's raw ingredients awaiting glue code, and openhands' per-model cost attribution with no quality join.

## Core Thesis

The industry default captured by this study is: **instrument tokens and time exhaustively at runtime; stop short of composing them into economic evaluation.** The binding constraint across all six sources is not measurement but *joining* — model identity, token/cost data, duration, and outcome exist somewhere in every system, yet rarely land in the same record where they could be compared.

The rating spread tracks exactly one design choice: whether economics flow through the same pipeline as everything else or ride in a separate lane. Langfuse prices at write time inside its universal ingestion path so evals inherit dollars for free (`worker/src/services/IngestionService/index.ts:1361-1365`); pydantic-ai's evals read standard GenAI OTel span attributes emitted by the same instrumentation used at runtime (`pydantic_evals/pydantic_evals/_task_run.py:50-74`). Both make cost *data*. The lower-scoring sources keep cost in a separate lane: agent-framework puts token counts on eval items but no price table anywhere (searches for `cost|price` return zero functional hits), crewAI routes rich runtime `UsageMetrics` everywhere except the eval report (the dead parameter at `crew_evaluator_handler.py:95-96`), openai-agents-sdk explicitly declines to evaluate ("instrument, don't evaluate", `src/agents/usage.py:195-229` + absence of any harness), and openhands displays server economics it never aggregates (`sources/openhands/src/utils/conversation-metrics.ts:12-79` combines within one conversation only). The gap between 8/10 and 4/10 is roughly "cost is queryable data" versus "cost is a display."

A second convergence matters just as much: comparison itself is consistently delegated upward — to the Microsoft Foundry portal (`docs/decisions/0023-foundry-evals-integration.md:41`), the hosted CrewAI AMP platform (`docs/edge/en/learn/llm-selection-guide.mdx:604-616`), Logfire dashboards (unverifiable from the pydantic-ai source), or generic observability backends. OSS libraries deliberately stop at primitives and let hosted platforms monetize the join.

## Approach Models

Three archetypes emerged, plus two hybrids:

**1. Observability-substrate reuse (langfuse, pydantic-ai).** Cost/latency/quality are not eval features; they are properties of a shared telemetry pipeline that evals consume. Langfuse computes cost once at ingestion via model-match → pricing-tier-match → usage×price (`worker/src/services/IngestionService/index.ts:1265-1383`, `1617-1689`) and declares latency/TTFT/tokens-per-second as SQL measure objects consumed by dashboards, monitors, and eval endpoints alike (`packages/shared/src/features/query/dataModel.ts:551-604`). Pydantic-ai harvests standard GenAI semantic-convention attributes (`operation.cost`, `gen_ai.usage.*`) from an in-memory span subtree per eval case (`pydantic_evals/pydantic_evals/_task_run.py:59-74`, `pydantic_evals/pydantic_evals/otel/_context_subtree.py`), delegating pricing to the third-party `genai-prices` snapshot with a never-fail contract (`pydantic_ai_slim/pydantic_ai/_cost.py:62-95`).

**2. Purpose-built eval framework with partial economics (agent-framework).** A minimal `Evaluator` protocol (`name` + `evaluate(items) -> EvalResults`, `python/packages/core/agent_framework/_evaluation.py:683-724`) with typed results carrying per-item `token_usage: dict[str, int]` (`_evaluation.py:353`) — but whether latency or dollars exist depends entirely on each provider implementation, because orchestration adds no telemetry of its own. Quality/success accounting is mature; the economic axis stops at raw counts.

**3. Runtime instrumentation without eval composition (openai-agents-sdk, openhands).** OpenAI Agents SDK captures usage at the lowest possible layer — synthesizing per-request entries inside `Usage.add()` precisely so tiered pricing stays recoverable (`src/agents/usage.py:295-312`) — and exposes it via `RunContextWrapper.usage` (`src/agents/run_context.py:83`), while its only shipped "evals" are single-artifact assertion scripts (`examples/sandbox/tutorials/dataroom_metric_extract/evals.py:240-302`). OpenHands goes further operationally (typed cost schemas, budget bars, provider balances, `sources/openhands/src/components/features/conversation-panel/budget-display.tsx:12-34`) but computes nothing analytical: aggregation exists only within one conversation, mirroring the Python SDK's combiner (`sources/openhands/src/utils/conversation-metrics.ts:8-11`).

**Hybrid: split-tier rollout (crewai).** A stable minimal scorer — LLM-judged quality scores plus an "Execution Time (s)" row (`crew_evaluator_handler.py:164-171`) — ships in core, while a richer framework (datasets, baselines, regression assertions, rendered Success Rate %) sits quarantined under `experimental/evaluation/` with baseline-as-file persistence and pytest-style guards (`experiment/result.py:48-143`; `testing.py:13-53`). An intentional rollout boundary, at the cost of adoption fragility.

## Pattern Catalog

### P1. Price-at-write, aggregate-at-read
Langfuse computes cost deterministically during ingestion and stores it; read-side queries only sum stored values (`packages/shared/src/features/query/dataModel.ts:588-595`). Every downstream consumer — dashboards, per-evaluator totals, activation estimates — gets consistent numbers cheaply.
- **Why it works**: one computation point, explicit precedence for user-provided costs (`worker/src/services/IngestionService/index.ts:1634-1656`), cached model/pricing resolution with negative-result caching (`packages/shared/src/server/ingestion/modelMatch.ts:308-325`).
- **Copy when** you have a central ingestion point and many consumers. **Risky when** price lists change retroactively (history isn't rewritten) or models lack pricing tiers — rows stay permanently unpriced until new traffic arrives.
- **Evidence**: `activationCostService.servertest.ts:70,140-156`; contrast with all five other sources computing nothing.

### P2. Telemetry-first metric harvesting (GenAI OTel conventions)
Pydantic-ai's evals derive cost/tokens/requests from span attributes rather than threading usage objects through user task boundaries (`_task_run.py:50-74`); hand-written synthetic spans feed identical metrics (`tests/evals/test_dataset.py:914-941`). Agent-framework has the same telemetry stream available but doesn't connect it — its OTel histograms (`gen_ai.client.operation.duration`, `gen_ai.client.token.usage`) live beside evals, not inside them (`python/packages/core/agent_framework/observability.py:274-275`). CrewAI achieves a similar decoupling via its event bus, letting telemetry, tracing, and eval listeners subscribe independently (`telemetry.py:696-725`).
- **Copy when** you want provider-agnostic metrics that survive refactoring of task APIs. **Risky when** tracer configuration is optional: pydantic-ai silently produces empty `metrics` when no capturing provider exists (`_task_run.py:55-56`) — the pattern's main failure mode, acknowledged in its own tradeoffs.

### P3. Per-request usage fidelity for tiered pricing
Aggregated token totals destroy pricing information. Three sources independently protect per-call granularity: openai-agents-sdk preserves `request_usage_entries` explicitly "for accurate per-request cost calculation," with a named regression test simulating a 200K tiered-pricing threshold (`src/agents/usage.py:218-229`; `tests/test_usage.py:427-488`); pydantic-ai documents that `RequestUsage.__add__` "CANNOT be used to sum multiple requests without breaking some pricing calculations" (`usage.py:292-301`); crewAI folds Anthropic cache tokens back into billed prompt tokens "so prompt_tokens and total_tokens don't undercount billed usage" (`types/usage_metrics.py:111-140`).
- **Copy whenever** any downstream consumer might apply non-linear pricing. Cheap to maintain at capture time, impossible to reconstruct later.

### P4. Unknown-cost-is-not-zero
Pydantic-ai keeps `UsageBase.cost: Decimal | None = None` with the documented invariant that `None` distinguishes unknown from zero (`usage.py:130-135`) and warns `CostNotFoundWarning` when a limit is set but unpriceable (`usage.py:528-535`). Langfuse renders explicit "Unavailable" copy instead of fabricating estimates (`EvaluatorSavedCostSummary.tsx:110-115`). The counterexamples are instructive: agent-framework only records token usage when `total_tokens` is truthy (`_foundry_evals.py:616`), making legitimate zeros indistinguishable from missing data; openai-agents-sdk counts requests whose providers omitted usage payloads as zero tokens (`usage.py:318-324`); crewAI's dead `token_usage` parameter silently ignores whatever callers pass (`crew_evaluator_handler.py:95-96`).
- **This is the single highest-leverage pattern in the study**: honest absence-marking is what separates the 7–8 band from the 4–6 band on the cost axis.

### P5. Errors separated from quality failures in success math
Agent-framework types status as `{pass, fail, error}` with `error_code` so infrastructure flakiness cannot pollute quality metrics (`_evaluation.py:330-369`). Pydantic-ai tracks hard task crashes separately as `ReportCaseFailure` with stacktraces (`reporting/__init__.py:123-148`). Langfuse groups job executions by status (`COMPLETED/PENDING/ERROR/CANCELLED`, `job-executions.ts:24-39`). OpenHands excludes cancelled/skipped runs from success-rate math as uninformative (`sources/openhands/src/manifests/automation-insights.ts:57-99`). CrewAI's counterexample proves the point negatively: an exception mid-experiment returns `ExperimentResult(score=0.0, passed=False)` (`runner.py:104-112`), indistinguishable from genuine zero-quality output.

### P6. Assertion-style gates and persisted baselines
Agent-framework exposes `raise_for_status()`, `assert_score_at_least()`, `assert_no_failed_items()` raising `EvalNotPassedError` as documented CI gates (`_evaluation.py:470-543`). CrewAI's experimental stack persists JSON baselines (auto-created on first run, `result.py:70-78`) and offers `assert_experiment_successfully` / `assert_experiment_no_regression` (`testing.py:13-53`). Pydantic-ai makes baseline diffing a renderer feature spanning scores, labels, metrics (including cost), assertions, and durations (`reporting/__init__.py:1160-1242`). Langfuse generalizes alerting over any declared measure with warning/alert thresholds and no-data modes (`monitors/types.ts:248-290`).
- These four are variations of one idea: **evaluation results must be build signals, not dashboard decoration.**

### P7. Economy-aware evaluation machinery (evals watching their own spend)
The most distinctive cluster. CrewAI's efficiency heuristics use cheap statistical signals (n-gram Jaccard > 0.7 for loop detection, timing consistency) to decide whether an expensive LLM-judge call is worth making (`reasoning_metrics.py:244-258`, `351-383`). Langfuse turns sampling into a first-class cost knob multiplied directly into the activation estimate (`EvaluatorSavedCostSummary.tsx:31-37`; `activationCostService.ts:148-151`). OpenHands encodes test economy as policy: mock-LLM E2E fabricates fixed usage chunks so full-stack tests cost $0, and live E2E pins a Haiku-class model under a written "stay cheap" rule (`tests/e2e/mock-llm/scripts/mock-llm-server.py:300-310`; `AGENTS.md:211-212`). Agent-framework warns that unpinned judge evaluators degrade replay stability (`_foundry_evals.py:73-102`) — implicitly acknowledging that eval economics must be reproducible to be meaningful.

### P8. Stamp-the-model-label (universal, never joined)
Every source records model identity somewhere — agent-framework stamps `agent_response_model` per persisted record (`self_reflection.py:319`), crewAI sets `model_name` on events and telemetry spans (`crew_evaluator_handler.py:211`; `telemetry.py:722`), langfuse breaks p95 latency and cost dashboards down *by model* (`langfuse-dashboards.json:180`, `197`, `316`), openai-agents-sdk pairs model with usage on generation spans (`span_data.py:169-209`), openhands attributes cost per profile-switched usage id (`conversation-state-event.ts:44-47`), pydantic-ai filters spans by `gen_ai.request.model` then discards the value (`_task_run.py:62`). All six record; none joins label × cost × outcome into a comparison artifact. This is the clearest evidence that the missing piece is composition, not capture.

## Key Differences

The divergences track product shape, not quality:

- **Vendor observability vs SDK vs application.** Langfuse *is* the billing-visible observability product, so cost is core data (`IngestionService/index.ts:1265-1383`). SDKs (openai-agents-sdk, agent-framework, pydantic-ai, crewai) treat evals as developer tooling and push comparative analysis outward — Foundry portal (`docs/decisions/0023-foundry-evals-integration.md:41`), CrewAI AMP (`docs/edge/en/learn/llm-selection-guide.mdx:604-616`), or generic backends. OpenHands is a frontend: server-owned economics, client-rendered (`AGENTS.md:60-70`; `use-live-conversation-metrics.ts:22-84`).
- **Where latency lands.** In eval surfaces for crewAI ("Execution Time (s)" row asserted by tests, `test_crew_evaluator_handler.py:81-125`) and pydantic-ai (three granularities including TTFT histograms, `models/instrumented.py:189-203`); beside evals for agent-framework and openai-agents-sdk (OTel histograms and span timestamps respectively, `observability.py:274-275`, `tracing/spans.py:343-357`); nowhere consumable for openhands (`response_latencies[]` with zero readers, `__tests__/hooks/query/use-conversation-metrics.test.tsx:25`).
- **Rollout posture.** CrewAI quarantines ambition under `experimental/` (four runner tests, absent from testing docs, `docs/edge/en/concepts/testing.mdx` mentions neither baselines nor experiments); agent-framework ships a minimal protocol with smart defaults and an ADR recording what was consciously left out (lowest concept count, `docs/decisions/0023-foundry-evals-integration.md:39`).
- **Success-rate semantics are irreconcilable as shipped.** Typed counts with error separation (agent-framework), averaged boolean assertions exported as a span attribute (`assertion_pass_rate`, `dataset.py:1056-1060`), status-count groupBy requiring user assembly (langfuse, `router.ts:1300-1353`), COMPLETED/(COMPLETED+FAILED) over automations (openhands), mean judge scores with no pass/fail notion (crewAI stable path), and bare assertion errors (openai-agents-sdk).
- **Pricing responsibility.** Externalized to a versioned third-party snapshot (pydantic-ai via genai-prices), internalized as a managed pricing-tier database (langfuse), or left entirely to consumers (openai-agents-sdk's `preserve_raw_usage`, agent-framework's absent price tables, crewAI's LiteLLM feed powering only the model-picker catalog, `model_catalog.py:12-15`).

## Tradeoffs

Each major design choice appears on both sides of the ledger across sources:

- **Write-time pricing (langfuse) vs consumer-side computation (everyone else).** Write-time buys consistent reads and trivial aggregation (`dataModel.ts:588-595`) at the cost of no retroactive repricing and permanent gaps for unmatched tiers. Consumer-side avoids infrastructure coupling but reliably fails to materialize — five of six sources compute no dollars at all.
- **OTel-span coupling (pydantic-ai) vs typed result fields (agent-framework).** Span harvesting decouples evals from framework internals and accepts hand-authored spans (`tests/evals/test_dataset.py:917-926`), but silently loses all resource metrics without a tracer (`_task_run.py:55-56`). Typed fields like `EvalItemResult.token_usage` (`_evaluation.py:353`) are explicit and testable, but each new metric requires schema changes in two languages (.NET parity at `dotnet/src/Microsoft.Agents.AI/Evaluation/EvalItemResult.cs:50-51`).
- **Platform delegation (agent-framework, crewai) vs local reproducibility.** Returning a `report_url` (`_evaluation.py:383`) or deferring "teams serious about optimizing their LLM selection" to hosted AMP (`llm-selection-guide.mdx:604-616`) avoids building reporting UI, but makes offline/CI cost-vs-quality regression tracking impossible without custom export code.
- **Experimental quarantine (crewai) vs shipping thin-but-documented (others).** CrewAI's `experimental/` fence protects users from instability yet strands genuinely useful capabilities (baseline regression detection, success rates) behind undocumented APIs with four runner tests. Agent-framework's shipped-but-minimal protocol gets adopted and leaves cost/latency permanently unbuilt.
- **Predicted quality proxies vs measured outcomes (openhands).** The critic's predicted-success probability gives instant per-conversation signal (`critic.ts:43-46`), verified by dedicated live E2E (`real-agent-server-conversation.spec.ts:142-192`), but hardcoded color thresholds (0.6/0.4, `critic-result-display.tsx:35-39`) have no evidenced calibration against labeled outcomes, and one-off interactive work has no measured ground truth at all.
- **Cheap-CI discipline vs coverage realism (openhands).** Pinning live E2E to Haiku with fabricated-token mock tiers controls spend exactly (`mock-llm-server.py:300-310`), but the flagship live test validates behavior only on a small model — regressions specific to stronger models' behavior go unseen (`AGENTS.md:211-212`).
- **Minimal protocol vs built-in telemetry (agent-framework).** The ADR's "lowest concept count" driver (`docs/decisions/0023-foundry-evals-integration.md:39`) yields low-friction evals where cost/latency instrumentation depends entirely on each provider — teams get simplicity but must assemble their own cost story.

## Decision Guide

Rules for choosing between the observed approaches:

1. **Building an observability product or platform with central ingestion?** Copy langfuse's price-at-write model: deterministic computation at ingestion (`IngestionService/index.ts:1361-1365`), stored costs, declarative measures shared by dashboards/monitors/evals (`dataModel.ts:551-604`), and estimate-before-commit flows grounded in real billable calls rather than static lists (`activationCostService.ts:116-139`).
2. **Building an SDK eval framework?** Copy pydantic-ai: harvest standard GenAI OTel attributes so runtime and eval share one instrumentation story (`_task_run.py:59-74`), route all pricing through a best-effort adapter that never fails a run (`_cost.py:62-95`), keep unknown distinct from zero (`usage.py:130-135`), and make baseline diff the single comparison substrate (`reporting/__init__.py:1160-1242`). Then fix its gap: persist model identity per case.
3. **Need CI gating this quarter?** Copy agent-framework's assertion surface (`raise_for_status`, `assert_score_at_least`, `_evaluation.py:470-543`) plus its error/failure separation (`330-369`); borrow crewAI's auto-baselining first-run behavior (`result.py:70-78`) if you want zero-config regression tracking.
4. **Shipping a library without eval ambitions?** OpenAI Agents SDK shows the floor done well: per-request usage fidelity (`usage.py:218-229`), retry-aware honest accounting (`usage.py:315-343`; `run_internal/model_retry.py:338`), raw-payload preservation (`model_settings.py:205`). But note its ceiling: without a recording layer, your users cannot answer economic questions without writing everything themselves.
5. **Rendering economics in an app?** OpenHands is a solid template for display-layer hygiene (null-tolerant combination, honest estimate labeling, division-by-zero guards, `sources/openhands/src/manifests/automation-insights.ts:87-99`) — but pair it with server-side history persistence, which it lacks, or cross-conversation analysis stays impossible.
6. **Any context:** adopt P4 (unknown ≠ zero) and P5 (error/failure separation) regardless of architecture. They were present in every high scorer and absent in every low scorer.

## Practical Tips

- **Make the eval record self-describing.** Persist `(model, usage, wall_clock_duration, pass/fail)` together per case — openai-agents-sdk's own future-work list names exactly this tuple, noting every primitive already exists (`usage.py:195-229`, `span_data.py:169-209`, `tracing/spans.py:343-357`). Pydantic-ai's discarded `gen_ai.request.model` filter value (`_task_run.py:62`) shows how close even good designs get.
- **Join data you already have before instrumenting new things.** CrewAI could add a tokens row beside "Execution Time (s)" today: `Crew.test` already calls `calculate_usage_metrics()` (`crew.py:2201-2225`) and merely fails to pass it into `print_crew_evaluation_result` (`crew.py:2259`). OpenHands' critic scores and accumulated cost coexist on the same event stream (`conversation-state-event.ts:25-75`).
- **Reuse existing pricing feeds.** CrewAI's CLI already caches LiteLLM's `model_prices_and_context_window.json` for its model catalog (`model_catalog.py:12-21`); joining it with `UsageMetrics` would enable cost-per-run reporting with no new data source.
- **Count failed attempts in budgets.** Pydantic-ai's `MaxToolCalls` counts failed tool calls by default because "they still consume budget... time and tokens" (`agentic.py:22-30,511-542`) — resource accounting must include waste or it understates spend.
- **Gate expensive judges behind cheap statistics.** CrewAI's n-gram-similarity loop detector and timing-consistency checks decide when an LLM-judge call earns its cost (`reasoning_metrics.py:244-258`, `373-381`).
- **Expose sampling as an explicit cost knob.** Langfuse's slider multiplies directly into both the estimate and the persisted rule (`EvaluatorSavedCostSummary.tsx:31-37`), making coverage-vs-cost a configuration-time decision instead of an invoice surprise.
- **Report the harness's own consumption separately.** CrewAI's judge-in-loop design spawns extra LLM calls per evaluated task × iteration (`crew_evaluator_handler.py:194-199`) that are invisible in reported output; attribute eval-machinery spend distinctly from system-under-test spend.
- **Add distributional latency, not just averages.** CrewAI already captures per-call timestamps in traces (`evaluation_listener.py:320-326`) but reports means only; pydantic-ai's span-tree `min_duration/max_duration` queries (`span_tree.py:57-58`) show how cheap percentile-capable structure is.

## Anti-Patterns / Caution Signs

- **Dead parameters as fossilized intentions.** `print_crew_evaluation_result(token_usage=None)` accepted and ignored (`crew_evaluator_handler.py:95-96`) — callers passing data today see it silently dropped. A dead seam signals an abandoned integration; either wire it or remove it.
- **Transported-but-unread schemas.** OpenHands' `response_latencies[]` exists in two wire contracts with zero readers; all fixtures hardcode `[]` (`__tests__/hooks/query/use-conversation-metrics.test.tsx:25`). Carrying unused fields costs maintenance surface and misleads API consumers about what's real.
- **Silent swallowing of economic evidence.** Agent-framework's `_fetch_output_items` catches `AttributeError/KeyError/TypeError` and logs a warning, returning partial parses (`_foundry_evals.py:654-655`); its timed-out runs return bare results with no counts or elapsed time (`_foundry_evals.py:423-424`). Operators learn nothing about spend before failure.
- **Truthy guards conflating zero with missing.** Token usage recorded only when `usage.total_tokens` is truthy (`_foundry_evals.py:616`); providers omitting usage payloads produce silent zero-cost readings in openai-agents-sdk unless users set `include_usage=True` (`docs/usage.md:37-42`; `model_settings.py:156`).
- **Fake-zero crash scores.** CrewAI maps mid-run exceptions to `score=0.0, passed=False` (`runner.py:104-112`) — indistinguishable from genuine worst-quality output in aggregates.
- **First-wins resolution of conflicting limits.** Multiple concurrent usage ids with different budget caps resolve arbitrarily to whichever iterates first, in both WS reducer and REST combiner (`sources/openhands/src/contexts/conversation-websocket-context.tsx:234-239`; `conversation-metrics.ts:32-35`).
- **Unguarded aggregate math.** `crew_average` divides task averages without a total>0 check while the display path guards correctly (`crew_evaluator_handler.py:122` vs `result_display.py:26`) — inconsistent defensive posture within one module.
- **Caution signs a design area is going brittle:** cost/latency metrics living only in samples (`self_reflection.py`), docs discussing tradeoffs qualitatively with no measurement loop behind them (`llm-selection-guide.mdx:90-142`), repetition knobs multiplying spend invisibly (`num_repetitions` N× API spend with no feedback in results, `_evaluation.py:1791`), and comparison features that exist exclusively behind hosted-platform walls.

## Notable Absences

Absences evidenced by explicit searches in the source reports:

- **No joint cost-vs-quality comparator anywhere.** None of the six repos contains an artifact running two models over one dataset and tabulating cost against quality. Closest: pydantic-ai's manual metadata-tag + baseline-diff recipe (`dataset.py:281-316`; `reporting/__init__.py:1160-1242`); langfuse's dataset-run metrics joining avg cost, avg latency, and score aggregates per run (`dataset-run-items.ts:95-107`) with no scatter/ratio view.
- **Monetary cost computed in only 2 of 6 sources** (langfuse, pydantic-ai). Agent-framework: grep for `cost|price` across eval packages yields zero functional hits.
