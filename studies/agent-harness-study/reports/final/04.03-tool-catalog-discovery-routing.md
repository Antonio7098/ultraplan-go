## Executive Summary

Across the seven sources, the tool-catalog problem decomposes into four jobs: (1) decide which tools exist, (2) decide which tools a particular agent can see, (3) decide which tools are sent to the model on a given turn, and (4) record enough to explain (3) afterwards. Mature implementations (pydantic-ai, agent-framework, openai-agents-sdk, letta) treat all four as first-class; intermediate ones (crewai, langgraph) treat (3) as a one-shot construction-time binding; openhands collapses (1)–(3) into a binary preset choice.

The convergent shape is a per-agent catalog composed from multiple sources, routed by name through a dict lookup, with a per-server MCP filter (static allow/block or dynamic callable) and a per-tool approval gate. The divergent axis is **how the model-facing list is chosen at run time**: pydantic-ai rebuilds and filters per turn via a four-rule `Model._resolve_native_tool_swap`, openai-agents-sdk exposes `is_enabled` and `defer_loading`, letta intersects attached tools with a rules solver, agent-framework unions agent/run/provider/MCP and lets middleware mutate, and langgraph/openhands freeze the list at construction.

The clearest gap is **explainability of the resolution decision**: every source records *what* the model saw on a span, but no source records *why* a tool was hidden, dropped, or never offered. That gap is largest in openhands (no catalog trace at all) and smallest in pydantic-ai (where `RunContext.available_tool_names` and `ToolManager._resolve_tool` include the available list in error messages).

## Core Thesis

The single lesson that survives the cross-source comparison is **separate the catalog from the per-request filter**. A toolset is a thing with a lifecycle (connection, schema, label, ownership); a per-request filter is a small, testable function that turns a toolset into a wire payload. Sources that conflate the two (one-shot construction-time binding, no per-turn re-derivation) end up with large static catalogs, no retrieval, and no way to answer "why did the model see what it saw?" Sources that separate the two (pydantic-ai's `Model._resolve_native_tool_swap`, openai-agents-sdk's `get_all_tools` + `convert_tools`, agent-framework's union + middleware) earn the right to use either a small curated catalog or a large searchable one without losing safety.

A second lesson: **provider-managed tool search is a real discovery primitive, not a toy**. Both pydantic-ai and openai-agents-sdk integrate a native `tool_search` capability (Anthropic bm25/regex, OpenAI `tool_search`) into the wire payload and validate that capability is present when deferred tools exist. Sources that ignore it (`defer_loading` without a search surface — openai-agents-sdk's `prune_orphaned_tool_search_tools` is a documented no-op) ship a feature that cannot be safely used.

A third lesson: **the per-MCP-server filter is the de facto capability filter**. Five of the seven sources put a `tool_filter` (static allow/block or a callable receiving `(context, tool)`) on `MCPServer`. This is the closest the ecosystems come to a general "agent of role X may not call tool of class Y" policy, and it works because MCP is the dominant extension surface. Sources that only filter at the agent list (langgraph, openhands) have no analogous layer.

## Approach Models

The seven sources cluster into four approach models when viewed through the lens of "how is the model-facing tool list chosen":

**Capability-driven toolset composition (pydantic-ai).** The catalog is a tree of `AbstractToolset` instances. Cross-cutting behavior is added via wrapper toolsets (`Filtered`, `Prefixed`, `Renamed`, `Prepared`, `ApprovalRequired`, `CapabilityOwned`, `ToolSearch`, `DeferredCapabilityLoader`) that compose like middleware. Each model request re-derives the visible list via `Model._resolve_native_tool_swap` using a four-rule filter on `defer_loading` / `with_native` / `unless_native`. Read-side observers (`RunContext.available_tool_names`, `available_capability_ids`) give tools a stable view of the current per-step map. Discovered tools and loaded capabilities are persisted in message history so rehydration across runs is free.

**Layered per-agent union with explicit filters (agent-framework, openai-agents-sdk, letta).** Each agent owns a list (`tools` + `mcp_servers` / `Agent.tools` + `MCPServer`s / persisted `tools` + `tool_rules`). The model-facing list is the result of explicit filters: `is_enabled` per tool, `tool_filter` per MCP server, allow-list or block-list by name, dynamic callable filter, or a rules solver. The model sees the post-filter list, and that list is attached to a tracing span (`AgentSpanData.tools`, OTel agent span, `gen_ai.tool.definitions`). Approval is a separate layer.

**Ad-hoc multi-source union (crewai).** Six sources feed a per-task list: `agent.tools`, `task.tools`, `apps`, `mcps`, delegation pair, memory pair. Augmentation happens in `Crew._prepare_tools` via a long conditional; dynamic filtering exists only for MCP. Dispatch is name-based via a unified `sanitize_tool_name` contract, with two parallel routing implementations (legacy `ToolUsage._select_tool` with fuzzy match, modern `AgentExecutor._execute_single_native_tool_call` with exact match). The catalog is the union, not a registry.

**Static catalog + middleware (langgraph, openhands).** LangGraph puts everything in one per-node `ToolNode._tools_by_name` dict built once at `__init__`; the only dynamic extension is `wrap_tool_call`, which can override `request.tool` for a name the model already knows. OpenHands picks one of two preset catalogs at conversation start (`get_default_tools` vs `get_planning_tools`) and layers user MCP servers on top; the catalog cannot be re-derived mid-conversation.

## Pattern Catalog

### Pattern 1 — Name-based dispatch via a dict lookup

**Problem.** When the model emits a tool call by name, the framework must bind the name to an executable instance.

**Where it appears.** Every source. `ToolNode.tools_by_name.get(call["name"])` in langgraph (`libs/prebuilt/langgraph/prebuilt/tool_node.py:1032`), `sanitize_tool_name(tool.name)` lookup in crewai (`lib/crewai/src/crewai/experimental/agent_executor.py:1889-1898`), `build_function_tool_lookup_map` in openai-agents-sdk (`src/agents/_tool_identity.py:352-359`), `ToolManager._resolve_tool` in pydantic-ai (`pydantic_ai_slim/pydantic_ai/tool_manager.py:356`), `agent_manager._resolve_tool_names` in letta (`studies/agent-harness-study/sources/letta/letta/services/agent_manager.py:389-427`), and the MCP discovery path in agent-framework (`studies/agent-harness-study/sources/agent-framework/python/packages/core/agent_framework/_mcp.py:1404-1529`).

**Why it works.** A single `dict[str, Tool]` is the cheapest possible dispatch and the most testable. It is the only routing primitive every source shares.

**When to copy it.** Always for the first version. Do not invent a different dispatch unless you need capability-based or semantic matching on the name itself.

**When it is overkill or risky.** When tool names can collide across sources (MCP + agent + handoff), a single dict silently overwrites. The fix is *not* a different data structure but a *validation* step before the dict is built (openai-agents-sdk's `validate_function_tool_lookup_configuration` at `src/agents/_tool_identity.py:310-349`, agent-framework's duplicate-name error at `python/packages/core/agent_framework/_tools.py:918-929`, pydantic-ai's `CombinedToolset` name-conflict guard at `pydantic_ai_slim/pydantic_ai/toolsets/combined.py:73-77`).

**Evidence.** `libs/prebuilt/langgraph/prebuilt/tool_node.py:773-786`, `lib/crewai/src/crewai/experimental/agent_executor.py:1860-2024`, `src/agents/_tool_identity.py:352-359`, `pydantic_ai_slim/pydantic_ai/tool_manager.py:78-369`, `studies/agent-harness-study/sources/agent-framework/python/packages/core/agent_framework/_tools.py:901-929`.

### Pattern 2 — Per-MCP-server filter (static + dynamic callable)

**Problem.** A remote MCP server exposes more tools than an agent should see; the user wants to narrow by name or by a runtime predicate.

**Where it appears.** agent-framework (`_apply_*` over `tools/list` output, `studies/agent-harness-study/sources/agent-framework/python/packages/core/agent_framework/_mcp.py:745-762`), crewai (`StaticToolFilter` + `create_dynamic_tool_filter` + `ToolFilterContext`, `lib/crewai/src/crewai/mcp/filters.py:17-163`), openai-agents-sdk (`_apply_static_tool_filter` / `_apply_dynamic_tool_filter`, `src/agents/mcp/server.py:641-699`), letta (organization-scoped listing + tool approval metadata, `studies/agent-harness-study/sources/letta/letta/services/tool_manager.py:699-727`).

**Why it works.** The filter sits at the discovery boundary, so the model never sees the unfiltered list. The dynamic callable pattern (`(context, tool) -> bool`) is generic enough to encode role, run, and approval signals without committing to a permission model.

**When to copy it.** The moment you allow any MCP server. Static allow/block lists handle the 80% case; a callable covers the rest.

**When it is risky.** If the filter is applied after the full list is loaded into memory (agent-framework's internal `_functions` is larger than the exposed view, `python/packages/core/agent_framework/_mcp.py:1424-1521`), the discovery cost is paid before the filter. Move the filter upstream where the protocol permits.

**Evidence.** `src/agents/mcp/server.py:641-699`, `lib/crewai/src/crewai/mcp/filters.py:17-163`, `studies/agent-harness-study/sources/agent-framework/python/packages/core/agent_framework/_mcp.py:745-762`.

### Pattern 3 — Progressive disclosure: advertise → load → call

**Problem.** A skill or tool has too much content to send to the model up front, but the model needs to know it exists.

**Where it appears.** agent-framework's `load_skill` / `read_skill_resource` / `run_skill_script` (`python/packages/core/agent_framework/_skills.py:2058-2179`), pydantic-ai's `ToolDefinition.defer_loading` + `ToolSearchToolset` (`pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:284-345`), openai-agents-sdk's `defer_loading=True` + `ToolSearchTool` (`src/agents/tool.py:449-450`, `src/agents/tool.py:1338-1352`), letta's `SkillFrontmatter.allowed_tools` (parsed but unused, `studies/agent-harness-study/sources/letta/letta/skills/models.py:78-93`), crewai's `discover_skills` / `activate_skill` / injected skill block (`lib/crewai/src/crewai/skills/loader.py:36-143`, `lib/crewai/src/crewai/utilities/prompts.py:117-133`).

**Why it works.** Prompts always have a token budget; advertising a thin index (name + one-line description) and loading the body or script on demand keeps the catalog compact while preserving discoverability.

**When to copy it.** Any tool whose initial schema (or whose containing skill's instructions) is large, or any tool set with more than ~20 entries.

**When it is risky.** When the discovery surface is not actually wired to a search tool. openai-agents-sdk's `prune_orphaned_tool_search_tools` is a documented no-op (`src/agents/tool.py:1492-1499`), so a `ToolSearchTool` without a searchable surface only fails at conversion time. crewai's `SkillFrontmatter.allowed_tools` is parsed but never enforced (`lib/crewai/src/crewai/skills/models.py:78-93`). Half-features are worse than no feature.

**Evidence.** `pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:84-345`, `src/agents/tool.py:1338-1489`, `studies/agent-harness-study/sources/agent-framework/python/packages/core/agent_framework/_skills.py:1719-2179`.

### Pattern 4 — Per-turn error response that lists the available tools

**Problem.** When the model hallucinates a tool name, the next prompt must help it recover.

**Where it appears.** langgraph's `INVALID_TOOL_NAME_ERROR_TEMPLATE` enumerates the registered names (`libs/prebuilt/langgraph/prebuilt/tool_node.py:108-110`), pydantic-ai's `ModelRetry` raises with the full available list (`pydantic_ai_slim/pydantic_ai/tool_manager.py:362-369`), letta's `ToolConstraintError` includes the valid names and possible rule hints (`studies/agent-harness-study/sources/letta/letta/agents/letta_agent.py:1793-1800`), agent-framework's `ToolMode` validation rejects malformed `allowed_tools` (`python/packages/core/agent_framework/_types.py:3569-3606`).

**Why it works.** It converts an opaque failure into a one-token correction. The model learns the catalog from the error string.

**When to copy it.** Always. The cost is one template string; the benefit is non-zero across all models.

**When it is risky.** Never. If the available list is large, consider truncating with a hint to "ask for the full list" rather than removing the listing.

**Evidence.** `libs/prebuilt/langgraph/prebuilt/tool_node.py:108-110`, `pydantic_ai_slim/pydantic_ai/tool_manager.py:362-369`, `studies/agent-harness-study/sources/letta/letta/agents/letta_agent.py:1793-1800`.

### Pattern 5 — Span-recorded post-filter tool list

**Problem.** Operators need to answer "what tools did this agent see on this turn?" in production.

**Where it appears.** openai-agents-sdk's `AgentSpanData.tools` and `AgentSpanData.handoffs` (`src/agents/run.py:1051-1055`, `src/agents/tracing/span_data.py:28-61`), agent-framework's `gen_ai.tool.definitions` on agent spans (`python/packages/core/agent_framework/observability.py:1725-1777`), pydantic-ai's `RunContext.available_tool_names` and `available_capability_ids` (`pydantic_ai_slim/pydantic_ai/_run_context.py:181-225`), letta's `tool_execution` span with tool name/duration/type/ID (`studies/agent-harness-study/sources/letta/letta/otel/tracing.py:228-327`).

**Why it works.** The post-filter list is the only thing the model could have called. Recording it on the agent span ties it to a turn, an agent, and (optionally) a request body.

**When to copy it.** Any framework that emits agent-level spans. The attribute is cheap (a list of strings) and high-value for debugging and audit.

**When it is risky.** When sensitive payload capture is enabled by default. agent-framework and openai-agents-sdk both gate arguments/results behind a sensitive-telemetry flag (`studies/agent-harness-study/sources/agent-framework/python/packages/core/agent_framework/_tools.py:733-775`, `src/agents/tool.py:101-118`). The tool *names* do not need that gate.

**Evidence.** `src/agents/run.py:1051-1055`, `studies/agent-harness-study/sources/agent-framework/python/packages/core/agent_framework/observability.py:2228-2238`, `pydantic_ai_slim/pydantic_ai/_run_context.py:181-225`.

### Pattern 6 — Capability attribution + lookup-key tuple

**Problem.** A tool's name alone is insufficient to route it: the same name may exist at multiple namespaces (MCP servers, deferred surfaces, agent-as-tool), and some names are reserved by hosted systems.

**Where it appears.** openai-agents-sdk's `BareFunctionToolLookupKey` / `NamespacedFunctionToolLookupKey` / `DeferredTopLevelFunctionToolLookupKey` (`src/agents/_tool_identity.py:10-17`), and `ToolOrigin(type=FUNCTION|MCP|AGENT_AS_TOOL, mcp_server_name, agent_name, agent_tool_name)` (`src/agents/tool.py:270-322`). pydantic-ai's `capability_id` on `CapabilityOwnedToolset` (`pydantic_ai_slim/pydantic_ai/toolsets/_capability_owned.py:36-42`). crewai's `ToolUsageEvent.source_fingerprint` / `source_type` (`lib/crewai/src/crewai/events/types/tool_usage_events.py:46-53`).

**Why it works.** It moves the disambiguation off the name string and onto a structured key. The same name "search" can resolve to different tools depending on the call's namespace prefix. The lookup map is built once per turn and validated against collisions before any model call.

**When to copy it.** When you have at least one of: multiple MCP servers, deferred surfaces, or agent-as-tool that share a name with a function tool.

**When it is risky.** When the validation is silent. openai-agents-sdk's `validate_function_tool_lookup_configuration` raises `UserError` (`src/agents/_tool_identity.py:310-349`); langgraph's `bind_tools` / `ToolNode` consistency check raises `ValueError` (`libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py:194-215`). crewai's two routing paths silently last-wins on duplicate names (`lib/crewai/src/crewai/experimental/agent_executor.py:1889-1898`). Always raise on the ambiguity; never silently overwrite.

**Evidence.** `src/agents/_tool_identity.py:10-349`, `pydantic_ai_slim/pydantic_ai/toolsets/_capability_owned.py:19-50`, `lib/crewai/src/crewai/events/types/tool_usage_events.py:46-53`.

## Key Differences

**Why pydantic-ai is a 9 and langgraph is a 6.** pydantic-ai treats the toolset as a tree with lifecycle and composes cross-cutting behavior via wrappers; the per-request filter (`Model._resolve_native_tool_swap`) is a single, testable function that reads the deferred/loaded state from `RunContext`. langgraph treats the catalog as a flat dict built once at `__init__`; the only per-request decision is `wrap_tool_call`, which overrides execution on a name the model already knows. The shape of the catalog is the same data structure (a dict of name → tool); the difference is whether anything outside the dict can change the model's view of it.

**Why agent-framework is an 8 and crewai is a 7.** Both have rich multi-source catalogs. agent-framework has a single typed layer (`tools` field with `FunctionTool`, MCP-allowed tools, provider tools, additional_tools) where every participant has an explicit `name`, `description`, and approval/policy hooks; duplicate names raise. crewai's catalog is assembled across six sources through a long conditional in `Crew._prepare_tools`, with no central catalog object and a tool type registry that resolves `tool_type` strings after the fact. The frameworks agree on the shape (a list of typed tools) but disagree on whether the list is a deterministic object or a function of execution order.

**Why openai-agents-sdk and letta are both 7 with different shapes.** openai-agents-sdk's catalog is per-agent, in-process, with a strong filter surface (`is_enabled`, deferred loading, MCP filter) and a strict lookup-key model. letta's catalog is per-organization, persisted in SQL, with rules that form a state machine (initial, parent, child, conditional, terminal, approval). Same score because each has a clear model and tests, but the gap is different: openai-agents-sdk's is the harness-level (no retrieval, no `is_enabled` for non-`FunctionTool`); letta's is the runtime-vs-search gap (optional Turbopuffer retrieval is not invoked by the runtime loop).

**Why openhands is a 4.** OpenHands applies a two-preset binary catalog at conversation start (`get_default_tools` or `get_planning_tools`) and layers user MCP servers on top. There is no per-task filtering, no per-tool ACL, no catalog trace, and no endpoint exposing the resolved tool set. The catalog logic lives in two functions (`_configure_llm_and_mcp`, the `tools = ...` branch of `_build_start_conversation_request_for_user`) and there is no observability surface. The model is *present* in the sense that tools are selected, but it is not *adressable* — there is no API to ask "what tools does this conversation see?" and no log to answer the question after the fact.

**Why langgraph is rated lower than pydantic-ai despite being from the same vendor.** langgraph's prebuilt `create_react_agent` and `ValidationNode` are deprecated; the deprecation messages redirect to `langchain.agents` (`libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py:274-277`, `libs/prebuilt/langgraph/prebuilt/tool_validator.py:43-46`). The durable catalog story is therefore partly out of scope for this source. Even within langgraph, the catalog is static and the only dynamic surface is `wrap_tool_call`.

## Tradeoffs

**Static catalog vs. per-turn re-derivation.** langgraph and openhands freeze the catalog at construction time. The benefit is determinism and a single `bind_tools` snapshot. The cost is that the smallest useful tool set cannot shrink mid-run without a `wrap_tool_call` override (langgraph) or a new conversation (openhands). pydantic-ai and openai-agents-sdk re-derive per turn. The benefit is the ability to honor `defer_loading`, `is_enabled`, and rules. The cost is per-step list construction; pydantic-ai mitigates this with `_cached_tool_defs` on MCP toolsets (`pydantic_ai_slim/pydantic_ai/mcp.py:1119`).

**Allow-list vs. block-list.** Three of seven sources prefer allow-list or "allow-then-block" semantics (agent-framework's MCP allow-list, openai-agents-sdk's `_apply_static_tool_filter` applies allow first then block, langgraph's threat-model-anchored allowlist). The remainder use block-list or mixed. Allow-list is safer for unknown future tools; block-list is easier to retrofit on a registry. The MCP filter convention is allow-first-then-block, which is the right default.

**Centralized toolset (pydantic-ai) vs. union across sources (agent-framework, crewai).** A single `AbstractToolset` tree is easy to walk, compose, and replace. A union is easy to extend by adding another source. The cost of a tree is that every cross-cutting concern (filter, prefix, approval, capability ownership) must be a wrapper — you cannot add it to the base class. agent-framework absorbs this cost by using middleware over the union; crewai accepts the cost of a long conditional and two parallel routing paths.

**Visibility hidden vs. approval gated.** Most sources keep approval-required tools visible and gate at invocation (letta's `RequiresApprovalToolRule` keeps availability, agent-framework's `always_require` pauses rather than hides, openai-agents-sdk's `needs_approval` is invoked but not hidden). pydantic-ai's `ApprovalRequiredToolset` keeps the tool in the catalog but raises `ApprovalRequired` on `call_tool` (`pydantic_ai_slim/pydantic_ai/toolsets/approval_required.py:16-31`). The visibility policy is the same: model sees the tool, knows the gate, can ask. Hiding it instead (which is possible for `is_enabled=False` or `defer_loading=True`) is a stronger guarantee but requires the model to know the tool exists by another path.

**Native tool search vs. local search.** pydantic-ai supports both: Anthropic native (bm25/regex/custom), OpenAI Responses native (`tool_search`), and a local keyword function (`pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:84-118`). openai-agents-sdk supports only the hosted Responses `tool_search` (`src/agents/tool.py:1338-1352`). The native path is faster and reduces prompt size; the local path is portable. The pattern to copy is to auto-inject the local fallback when the provider lacks native support, then swap to native when `supported_native_tools` declares it.

**Catalog durability across runs.** letta persists the catalog in SQL with org/project scoping (`studies/agent-harness-study/sources/letta/letta/orm/tool.py:17-59`). pydantic-ai persists discovery and capability-load state in message history (`pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:185-216`). openhands forgets the resolved set at the end of `_build_start_conversation_request_for_user` (`app_conversation_models.py:112-156` has no `tools` field). The pattern to copy is: persist enough state to replay the catalog.

**Catalog vs. model catalog drift.** langgraph's `_should_bind_tools` asserts that the model-bound tool list matches the `ToolNode` tool list (`libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py:194-217`). agent-framework merges agent-default + run + provider + MCP into a single `final_tools` and rejects duplicate names across the merge (`python/packages/core/agent_framework/_tools.py:901-929`). crewai's two routing paths do not have a single authoritative merge step; they agree on a `sanitize_tool_name` contract and rely on the executor's `_tool_name_mapping` to be index-compatible. The lesson is to validate the merge, not the per-tool registration.

## Decision Guide

The dimension the framework must answer is "what is the smallest useful tool set the model sees?" The decision tree:

**1. Do you allow external MCP servers?**
- Yes → an MCP filter is required. Use the static + dynamic callable pattern (Pattern 2). Wire it at the discovery boundary so the model never sees the unfiltered list.
- No → skip the filter layer; a per-agent `tools` list is enough.

**2. Do you have more than ~20 tools in the steady-state catalog?**
- Yes → adopt a discovery surface. Either native tool search (Anthropic/OpenAI) or local keyword search. Validate that the capability is present when deferred tools exist (pydantic-ai's `validate_responses_tool_search_configuration` is the model).
- No → send the full list per turn. The cost is bounded.

**3. Do you need per-task or per-context filtering?**
- Yes → re-derive the model-facing list per turn. The minimum: `is_enabled` (per-tool callable) + `tool_filter` (per-MCP-server callable). The richer: a `Model.prepare_request` filter that reads runtime state.
- No → a construction-time binding is fine. Document the contract.

**4. Do you need a permission model?**
- Yes, user/role-level → build a wrapper toolset (pydantic-ai's `FilteredToolset` is the seed) that consults a policy table. Apply it inside the composition, not at the agent constructor.
- Yes, action-level → use approval gating. agent-framework's `always_require` and the `.NET` `ToolApprovalAgent` are the model.
- No → leave it for the deployment layer.

**5. Do you need to explain tool availability after the fact?**
- Yes → attach the post-filter list to a per-turn span (openai-agents-sdk's `AgentSpanData.tools`). Expose `available_tool_names` on the run context (pydantic-ai's `RunContext.available_tool_names`). Include the available list in the model-visible error when a name is unknown (Pattern 4).
- No → at least emit a structured event on the catalog transition (crewai's `LiteAgentExecutionStartedEvent` carries the `tools` list).

**6. Do you need a persisted catalog?**
- Yes → use an ORM-level catalog with org/project scoping (letta's pattern). Index it for retrieval if the catalog is large.
- No → keep the catalog in-process; this is fine for libraries and SDKs.

**7. Do you need to extend the model-facing catalog at runtime?**
- Yes → either (a) require the model to call a known name (langgraph's `wrap_tool_call` pattern), or (b) expose a discovery surface that the model can search (pydantic-ai's `ToolSearchToolset`). The first is simpler; the second scales.
- No → a static catalog is fine.

## Practical Tips

**Patterns to copy.**
- A single `dict[str, Tool]` for the dispatch table, with a validation step before construction that raises on duplicate names. (pydantic-ai, agent-framework, openai-agents-sdk.)
- A per-MCP-server `tool_filter` accepting both `allowed_tool_names` / `blocked_tool_names` and a callable. (pydantic-ai, openai-agents-sdk, crewai, agent-framework.)
- A post-filter list attached to the agent span. (openai-agents-sdk, agent-framework, pydantic-ai.)
- An error response that enumerates the available tools when the model hallucinates a name. (langgraph, pydantic-ai, letta.)
- Per-tool `is_enabled` as a callable receiving `(run_context, agent)`. (openai-agents-sdk, agent-framework.)
- Tool-search corpus keyed on the real tool name, with `defer_loading` flipped per turn. (pydantic-ai.)
- A capability-attached toolset that tags `capability_id` and hidden state on every tool. (pydantic-ai's `CapabilityOwnedToolset`.)
- A rules solver that intersects child/parent/conditional rules against the attached tools. (letta.)

**Patterns to avoid or delay until needed.**
- A binary preset catalog (openhands). The moment you have a third use case, the preset is wrong.
- A two-path routing (crewai's `ToolUsage._select_tool` + `AgentExecutor._execute_single_native_tool_call`). One is enough.
- A per-source `_filter` flag without a `tool_filter` callable. Callables cover the 80% cases the flags do not.
- Fuzzy matching on the dispatch name (crewai's `SequenceMatcher` with 0.85). Typo-recovery is a recovery-loop concern, not a routing concern.
- Sharing a module-level schema cache across agents without an invalidation hook (crewai's `_mcp_schema_cache`, `lib/crewai/src/crewai/mcp/tool_resolver.py:41-42`).
- Documenting a field that is not enforced at runtime (crewai's `SkillFrontmatter.allowed_tools`).
- A no-op stub like openai-agents-sdk's `prune_orphaned_tool_search_tools` (`src/agents/tool.py:1492-1499`). Either implement it or delete the symbol.
- Letting a runtime filter mutate the agent's `tools` list (called out as a question in openai-agents-sdk's gap analysis, `src/agents/agent.py:250-263`).

**Decision rules.**
- If your catalog is the union of more than two sources, lift it into a first-class object with explicit `add(category, tools, filter=...)` and `resolve(agent, run_context)`. The lack of one is crewai's biggest gap.
- If you have both deferred and visible tools, validate that the search surface is present at conversion time, not at construction. pydantic-ai's `validate_responses_tool_search_configuration` is the model.
- If you have a host-managed tool search (Anthropic bm25, OpenAI `tool_search`), also implement a local callable fallback. The corpus is dropped on providers without it (`pydantic_ai_slim/pydantic_ai/models/__init__.py:505-506`).
- If you have agent-as-tool, use a capability-attached toolset so the child cannot see the parent's approval state directly (openai-agents-sdk's `as_tool()` + `agent_tool_state_scope`).

**Caution signs that the catalog is becoming brittle.**
- The same tool name gets resolved by different code paths in different scenarios (crewai's two routing paths).
- A `ToolSearchTool` exists but no deferred tools exist (or vice versa). The validation should produce a `UserError` at conversion time.
- A `tool_filter` is applied to the exposed view but the internal list is loaded first (agent-framework's MCP internal `_functions` vs exposed `functions`).
- A span records the tool list but not the filter decision that produced it. Attach the allowed/blocked/deferred names to the span.
- A tool name conflict is silently overwritten (crewai's `_tool_name_mapping` last-wins, langgraph's `bind_tools` concatenation).
- A persisted tool catalog forgets the resolved per-conversation set (openhands' `AppConversationInfo` has no `tools` field).
- A "permission" feature is implemented as a `security_config` fingerprint (crewai's `security_config`) without a filter implementation. Names without enforcement are not permissions.
- A deferred tool is silently dropped by the wire filter because no search surface is configured.

## Anti-Patterns / Caution Signs

- **Binary preset per agent type (openhands).** Switching between `get_default_tools` and `get_planning_tools` based on `AgentType` is fine for a product with two modes, but it cannot express "browser but not bash" without a fork. The moment a third use case appears, the preset is the wrong abstraction.
- **Two parallel routing implementations (crewai).** `ToolUsage._select_tool` (legacy, fuzzy match) and `AgentExecutor._execute_single_native_tool_call` (modern, exact match) share a name contract but diverge on dispatch. The duplication is consistent but is a maintenance hazard.
- **Module-level schema cache without invalidation (crewai's `_mcp_schema_cache`).** A 300-second TTL on a cache shared across all agents in the process. A change to an MCP server is invisible until the TTL expires.
- **Documented features without enforcement (crewai's `SkillFrontmatter.allowed_tools`).** The field is parsed and serialized; no code consumes it. Half-features are worse than no feature.
- **Silent shadowing of system MCP servers (openhands).** `_merge_custom_mcp_config` iterates user servers without collision detection, so a user server named `default` silently replaces the system one.
- **Hard-coded tool preset import (openhands).** `from openhands.tools.preset.default import (...)` runs at module load; if the wheel is missing, the entire service fails to import with no fallback preset.
- **No-op stubs that pretend to be validation (openai-agents-sdk's `prune_orphaned_tool_search_tools`).** The function returns its input and is annotated "preserves misconfiguration until request conversion validates it." Either implement or remove.
- **Filter visible but not enforced (agent-framework's `tool_choice.allowed_tools`).** The framework validates the field but provider-specific enforcement is left to the provider. The validation is not the guarantee.
- **Hidden security-analyzer strings (openhands).** `_create_security_analyzer_from_string` silently coerces unknown values to `None` and logs a warning. The user typed `"LLM"` and gets no analyzer.
- **Catalog never persisted on the conversation row (openhands).** No replay tool can answer "what tools did conversation X see?" without re-running the start logic.
- **Catalog vs. model catalog drift (langgraph).** `_should_bind_tools` catches the mismatch at construction time, but a `bind_tools` call made after construction is the caller's responsibility.
- **Non-`FunctionTool` tools cannot be `is_enabled`-filtered (openai-agents-sdk).** `_check_tool_enabled` short-circuits to `True` for anything that isn't a `FunctionTool` (`src/agents/agent.py:251-253`). The filter is silently ignored.
- **Tool-search corpus dropped with no fallback (pydantic-ai).** On providers without `ToolSearchTool` support and no deferred tool owned by a capability, `_resolve_native_tool_swap` drops the corpus. The local `search_tools` fallback exists but is path-dependent.
- **Routing by name without a lookup-key model (crewai).** Two tools with the same sanitized name trigger a last-wins overwrite; the model sees only the first.
- **Empty restrictive allowlist falls back to all attached (letta).** A solver that returns no valid tools is converted by `... or list(set(t.name for t in tools))` into "all tools". Strict conditional rules become no-ops.
- **No retry / observability surface for skipped-or-denied capability loads (pydantic-ai).** A `load_capability` on an already-available capability raises `ModelRetry` once (using a retry-budget entry) rather than mutating the catalog; the trade-off is documented but the reasoning is not surfaced.

## Notable Absences

- **No source records *why* a tool was hidden, dropped, or excluded.** Every source records *what* the model saw; none records the decision lineage. The closest is openai-agents-sdk's `AgentSpanData.tools` (what), pydantic-ai's `RunContext.available_tool_names` (what), and letta's `ToolConstraintError` (why this name was rejected). None produce a structured "excluded because X" record.
- **No source provides a "this conversation has tools T1, T2, T3" endpoint.** openhands explicitly notes the absence of a `/tools` or `/catalog` endpoint. crewai's `LiteAgentExecutionStartedEvent` carries the list but only at kickoff. langgraph has no public API to inspect the resolved `tools_by_name` beyond the property accessor.
- **No source implements a general capability/permission engine.** Search exists (letta's Turbopuffer, pydantic-ai's `tool_search`), but it is either optional or not invoked by the runtime loop. The only "permission" primitives are approval (gate at execution) and per-MCP filter (gate at discovery).
- **No source implements retrieval over the tool catalog at request time.** pydantic-ai and openai-agents-sdk have provider-native tool search; letta has Turbopuffer but does not call it from the agent loop. The "model retrieves the right tool from a 1000-tool registry" pattern is not yet first-class.
- **No source implements cross-conversation tool audit.** letta persists the catalog; openhands does not persist the resolved set. There is no "history of what tools were used in conversation X" beyond the agent-server's span stream.
- **No source has a documented policy engine for "agent of role X may not call tool that touches Y".** The pattern is recoverable (pydantic-ai's `FilteredToolset` + `ToolFilterContext` would suffice, crewai's `tool_filter` callable is the seed), but no source ships it as a feature.
- **No source exposes a "smallest useful tool set" assertion API.** openai-agents-sdk's `validate_responses_tool_search_configuration` covers one corner; the rest is "send and see".

## Per-Source Notes

**agent-framework (8/10).** Layered tool model. Three composition sources are unioned into `final_tools` per run (`python/packages/core/agent_framework/_agents.py:1253-1316`); the .NET layer follows the same shape (`dotnet/src/Microsoft.Agents.AI/ChatClient/ChatClientAgent.cs:625-649`). Duplicate names raise. MCP allow-lists filter the exposed view. Progressive tool mutation is supported via a run-local mutable list (`python/packages/core/agent_framework/_tools.py:2544-2550`). Hidden execution tools (`additional_tools`) are documented and tested. Approval gating is at execution time. Security middleware enforces trust and confidentiality labels. Skills advertise/load/read/run. Text search either injects context or exposes a single on-demand `Search` tool. OpenTelemetry covers agent, chat, function, and MCP operations. The rating is held below 9 because the catalog is additive by default, authorization is post-model, and traces do not explain why a tool was included.

**crewai (7/10).** Ad-hoc multi-source union. Six sources feed the per-task list (`agent.tools`, `task.tools`, `apps`, `mcps`, delegation, memory). `Crew._prepare_tools` is a long conditional. MCP is the only source with a dynamic filter (`StaticToolFilter` / `create_dynamic_tool_filter`). Routing is name-based via `sanitize_tool_name`; two parallel implementations (legacy fuzzy, modern exact). Skills are prompt-injected, not tools. `SkillFrontmatter.allowed_tools` is parsed but not enforced. The closest to per-task filtering is `TodoItem.tool_to_use` + `_validate_expected_tool_usage`, which is advisory. Memory `_read_only` removes the write tool. The biggest gap is the absence of a central catalog object.

**langgraph (6/10).** Narrow static catalog. `ToolNode._tools_by_name` is built once at `__init__` (`libs/prebuilt/langgraph/prebuilt/tool_node.py:773-786`). Routing is a dict lookup plus `_validate_tool_call` (`libs/prebuilt/langgraph/prebuilt/tool_node.py:1032-1268`). The only dynamic surface is `wrap_tool_call`, which can override `request.tool` for a name the model already knows. `_should_bind_tools` asserts the model and runtime catalogs agree. `tools_condition` decides whether to invoke `tools`, not which subset. The threat model anchors the allowlist-over-blocklist stance. Public APIs (`create_react_agent`, `ValidationNode`, `AgentState*`, `HumanInterrupt*`) are deprecated with redirects to `langchain.agents`. The durable catalog story is partly out of scope for this source.

**letta (7/10).** Persisted catalog with per-agent attachment. `tools_agents` is the many-to-many table (`studies/agent-harness-study/sources/letta/letta/orm/tools_agents.py:7-18`). `ToolRulesSolver` is the rules engine (`studies/agent-harness-study/sources/letta/letta/helpers/tool_rule_solver.py:24-60`). Rules form a state machine: initial, parent, child, conditional, terminal, approval. The model-facing list is the intersection of rules and attached tools. Client-side tools override same-named server tools. Optional Turbopuffer retrieval is implemented but not called by the runtime loop. The biggest gap is the empty-allowlist fallback (`... or list(set(t.name for t in tools))`).

**openai-agents-sdk (7/10).** Per-agent explicit catalog. `Agent.tools` + `Agent.mcp_servers` are the canonical sources (`src/agents/agent.py:185-188`). `get_all_tools` is the per-run pipeline: MCP tools → `is_enabled` filter → merge → orphan-prune → name-collision check (`src/agents/agent.py:246-266`). MCP filter is `_apply_static_tool_filter` + `_apply_dynamic_tool_filter` (`src/agents/mcp/server.py:641-699`). Routing is a 3-key lookup (`BareFunctionToolLookupKey`, `NamespacedFunctionToolLookupKey`, `DeferredTopLevelFunctionToolLookupKey`) with last-wins precedence and explicit validation (`src/agents/_tool_identity.py:10-349`). Hosted tool search is opt-in and validated. `AgentSpanData.tools` records the post-filter list per turn. The biggest gaps are `is_enabled` only applied to `FunctionTool`, `prune_orphaned_tool_search_tools` being a no-op, and no retrieval.

**openhands (4/10).** Binary preset. `get_default_tools` vs `get_planning_tools` is the only branching (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:1611-1625`). User MCP servers are layered on top via `_merge_custom_mcp_config`. Skills are proxy-loaded from the agent-server. Confirmation policy is post-tool, not catalog. The catalog is not persisted on the conversation row. No endpoint exposes the resolved tool set. The biggest gap is the absence of any catalog-side observability.

**pydantic-ai (9/10).** Capability-driven toolset composition. `AbstractToolset` is the unit of catalog (`pydantic_ai_slim/pydantic_ai/toolsets/abstract.py:74`). Wrapper toolsets compose (`Filtered`, `Prefixed`, `Renamed`, `Prepared`, `ApprovalRequired`, `CapabilityOwned`, `ToolSearch`, `DeferredCapabilityLoader`). The four-rule `Model._resolve_native_tool_swap` filters per request (`pydantic_ai_slim/pydantic_ai/models/__init__.py:437-521`). `RunContext.available_tool_names` / `available_capability_ids` are read-side observers. Discovery is four-way: native (provider-managed), client-executed native, custom callable, local keyword. Discoveries and capability loads are persisted in message history. `ToolManager._resolve_tool` raises `ModelRetry` with the available list. The gaps are the dual-meaning `defer_loading` and the convention-only `with_native`/`unless_native` flags.

## Open Questions

- **How does `langchain.agents` complete the picture?** langgraph's `create_react_agent`, `ValidationNode`, `AgentState*`, and `HumanInterrupt*` are deprecated with redirects to `langchain.agents`. The modern catalog, discovery, and routing primitives live there. Studying that source is required to characterize the durable shape.
- **Where is the canonical list of tools in openhands' preset?** The implementations live in the external `openhands-tools` package (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:132-138`). This source has no observable inventory of what the model actually sees.
- **How is the canonical "what the model saw" list reconstructed on a resumed run state in openai-agents-sdk?** `run_state.py:1731-1735` re-calls `current_agent.get_all_tools(context)`, which depends on the *current* state of the agent's `tools` and the *current* MCP server filters, not on a snapshot taken at the first turn. There is no public helper that returns the exact wire payload used in a past turn.
- **What is the durable API for runtime tool addition in the OpenAI Agents SDK?** The run loop recomputes the tool list per turn (`src/agents/run.py:1030-1033`), but the user-facing surface for mutating the catalog mid-run is undocumented. Tests suggest the surface exists.
- **Does pydantic-ai's `ToolSearch` corpus shrink when no deferred tools exist?** `_agent_graph.py:519-525` drops the auto-injected `ToolSearchTool` when the corpus is empty. The local `search_tools` function tool is also suppressed (`_tool_search.py:295-296`). What happens when a capability's tools are deferred but no standalone tools are deferred?
- **What is the expected behavior of two `RealtimeAgent`s with overlapping function tool names in the OpenAI Agents SDK?** The realtime path builds `function_map` keyed by `tool.name` (`src/agents/realtime/session.py:820`), so duplicate names overwrite each other silently.
- **Does agent-framework's MCP loader remove tools when the server later omits them?** The loader tracks existing names and skips duplicates (`python/packages/core/agent_framework/_mcp.py:1424-1493`); no regression test was found for server-side removal.
- **Is the `is_enabled` callable allowed to mutate `agent.tools` or `RunContextWrapper` in openai-agents-sdk?** Nothing in the code prevents it (`src/agents/agent.py:250-263`), but no documentation warns against it.
- **What is the contract for `SkillFrontmatter.allowed_tools` in crewai?** The field is parsed and serialized; no runtime code consumes it. Either the runtime must honor it or the field should be removed.
- **How do pydantic-ai's `LoadCapabilityCallPart` and `ToolSearchReturnPart` survive message history truncation?** A history processor that drops them forces re-discovery (`pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:185-216`, `pydantic_ai_slim/pydantic_ai/_deferred_capabilities.py:141`). What is the recommended replacement pattern?
- **Does openhands' `AppConversationInfo` ever grow a `tools` field for audit?** Currently no (`openhands/app_server/app_conversation/app_conversation_models.py:112-156`).
- **No source exposes a public, structured "tool policy" / "agent tool manifest"** that downstream systems (UI, observability) can read to know which tool is exposed to which capability under which state. The closest is the implicit per-run `ModelRequestParameters` in pydantic-ai.
