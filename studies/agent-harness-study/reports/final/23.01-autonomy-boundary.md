## Executive Summary

Seven agent harnesses were studied for how they decide what an agent may do autonomously versus what requires human review. The single most striking convergence: **all seven default to fully autonomous execution**. Gating is opt-in everywhere — Microsoft Agent Framework's tools run unless marked `always_require` (`python/packages/core/agent_framework/_tools.py:408`), the OpenAI Agents SDK's `needs_approval` defaults to `False` (`src/agents/tool.py:486-493`), LangGraph gates nothing unless a developer installs interrupts, letta's test fixtures must manually opt even "scary bash operations" into approval (`tests/managers/conftest.py:224-250`), and OpenHands ships `confirmation_mode: false` (`src/services/settings.ts:13`). Safety is always layered on top of an autonomous core, never built into it.

Maturity splits into three bands. A first tier (agent-framework 8/10, openai-agents-sdk 8/10, pydantic-ai 8/10) implements a typed suspend/resume approval protocol with fail-closed evaluation, identity-bound consume-once authority, heavy adversarial testing, and unusually honest documentation. A second tier (langgraph 7/10, letta 7/10) provides mechanically enforced but narrower mechanisms — checkpoint-backed interrupt primitives in one case, per-tool approval rules duplicated across three loop generations in the other. A third tier (crewai 6/10, openhands 6/10) has real building blocks but fragile boundaries: advisory-only blocking with no escalation path (crewai), and headless automations that escape gating entirely (openhands).

The strongest systems share four traits: a typed pause/resume protocol rather than synchronous blocking; fail-closed behavior whenever anything is ambiguous (unparseable arguments, crashed policy callables, forged approvals); decisions bound to specific call identities that execute exactly once; and enforcement concentrated at a single choke point. That last trait is usually earned the hard way — pydantic-ai's centralization exists because a realtime bypass bug proved that distributed enforcement drifts (`pydantic_ai_slim/pydantic_ai/tool_manager.py:1099-1121`, `pydantic_ai_slim/pydantic_ai/realtime/AGENTS.md:20-23`).

The recurring weakness across every source is boundary coverage at the edges: secondary execution engines (crewai's LiteAgent), newer loop versions (letta v1/v2/v3 duplication), cross-language ports (agent-framework's external Go repo), headless modes (openhands automations), MCP tools (letta, ungated), and background agents all have documented holes.

## Core Thesis

Agent harness autonomy boundaries are converging on one recognizable shape — **declare the gate on the tool, pause durably instead of blocking, bind the human's decision to a specific call identity, feed denials back to the model as feedback, and fail closed under ambiguity** — yet no implementation closes its own boundary completely. Every source leaves at least one execution surface outside the gate, none offers graded autonomy levels or approver accountability, and the difference between an 8 and a 6 is mostly where enforcement lives (one auditable choke point vs. scattered developer-written hooks) and whether abnormal conditions escalate to humans or silently degrade. Autonomy-by-default is universal because ergonomics drive adoption; the compensating mechanisms are what separate mature from fragile designs.

## Approach Models

Five distinct models emerged. They cluster by *where the boundary decision lives*:

1. **Typed approval protocol on tool declarations** (agent-framework, openai-agents-sdk, pydantic-ai). The unit of autonomy is the tool call; each tool carries a declarative gate (`approval_mode`, `needs_approval`, `requires_approval`) optionally refined by a callable predicate. When gated, the run suspends with structured request content and resumes with a typed decision: `function_approval_request/response` contents (`python/packages/core/agent_framework/_tools.py:1775-1832`), `ToolApprovalItem` interruptions with `RunState.approve()/reject()` (`src/agents/run_state.py:1255-1298`), or `DeferredToolRequests`/`DeferredToolResults` (`pydantic_ai_slim/pydantic_ai/_deferred.py:26-42, 99-118`). These are libraries: they serialize state and hand correlation responsibility back to the host application.

2. **First-class approval state machine inside a product backend** (letta). Approvals are persisted conversation messages with dedicated roles; a pending approval blocks other inputs with HTTP 409 (`PendingApprovalError`), runs stop with a filterable `requires_approval` reason while remaining "completed" to support an approval-inbox UX (`studies/agent-harness-study/sources/letta/letta/schemas/letta_stop_reason.py:21,26-32`; `services/agent_manager.py:1067-1133`). Unlike the libraries, the product owns persistence, idempotency, and observability end-to-end.

3. **Control-flow interrupt primitives in a graph engine** (langgraph). The core knows nothing about approvals — it knows about interrupts. Static `interrupt_before` node lists (`libs/langgraph/langgraph/graph/state.py:1183-1184`) and dynamic in-node `interrupt()` calls (`libs/langgraph/langgraph/types.py:851-974`) raise `GraphInterrupt` at superstep boundaries, riding on checkpoints so pauses survive restarts. UI semantics (`accept|ignore|response|edit`) live in prebuilt schemas the engine deliberately ignores (`libs/prebuilt/langgraph/prebuilt/interrupt.py`).

4. **Developer-authored interception hooks over an autonomous loop** (crewai). There is no policy engine; four independent opt-in mechanisms exist (task-level `human_input` flag reviewing only the final answer, `before_tool_call` hooks that can block or prompt, flow-level `@human_feedback` decorators, capability flags like `allow_delegation`), each hand-wired by the developer (`lib/crewai/src/crewai/task.py:233-236`; `hooks/tool_hooks.py:142-150`). Absent them, everything executes unattended.

5. **Policy-as-data compiled to a remote enforcer** (openhands). This frontend source transmits a declarative `confirmation_policy` discriminated union (`NeverConfirm` / `ConfirmRisky{threshold:"HIGH", confirm_unknown:true}` / `AlwaysConfirm`) at conversation start and treats the backend as sole enforcer (`src/api/agent-server-adapter.ts:593-605,1120-1121`). Risk metadata (`UNKNOWN|LOW|MEDIUM|HIGH`) travels on every action event, letting the UI explain *what* it is asking about (`src/types/agent-server/core/events/action-event.ts:58-61`).

## Pattern Catalog

### P1. Typed pause/resume approval protocol (control-plane, not transcript)

- **Problem**: A human decision can take minutes or days; the agent loop cannot hold a call stack that long, and approval chatter must not pollute model context.
- **Sources**: agent-framework (`_types.py:1273-1362`; control contents filtered from replay `_sessions.py:878-932`), openai-agents-sdk (`run_steps.py:171-175`, serialized `RunState` `docs/human_in_the_loop.md:187-199`), pydantic-ai (`_deferred.py:26-197`), letta (approval message roles, derivable pending state from history alone `orm/agent.py:317-337`), langgraph (`Command(resume=...)` `types.py:798-848`).
- **Why it works**: Suspension becomes durable state, enabling multi-process workflows, restart survival, and clean audit separation. Agent Framework's ADR explicitly rejected callbacks because hosted scenarios require suspend/resume without a live stack (`docs/decisions/0006-userapproval.md:50-57, 381-383`).
- **Copy when**: Any human review may exceed one process lifetime, or approvals must survive restarts.
- **Overkill when**: Purely interactive CLI sessions where a blocking prompt suffices — though note crewai's terminal `input()` path is exactly what makes its OSS flow unusable headless (`core/providers/human_input.py:364`).

### P2. Fail-closed evaluation under ambiguity

- **Problem**: The gate evaluator itself can fail — malformed arguments, crashing policy functions, missing context — and a naive implementation fails open.
- **Sources**: openai-agents-sdk (unparseable args force approval `src/agents/run_internal/tool_execution.py:1306-1310`; policy-callable exceptions map to "requires approval" `run_internal/turn_resolution.py:1269-1270`; MCP callable without agent returns `True` `mcp/server.py:820-831`); agent-framework (only strict boolean `True` consents; non-boolean = rejection, `docs/specs/004-python-function-calling-loop.md:374`); pydantic-ai (deferral without expressible output type raises hard `UserError` `_tool_execution.py:1043-1049`; unknown result IDs raise `ValueError` `_deferred.py:70-84`); openhands (`confirm_unknown: true` — UNKNOWN-risk actions still gated `agent-server-adapter.ts:601`); letta (malformed approval payloads abort with `invalid_tool_call` rather than executing nothing silently, `agents/letta_agent_v3.py:1007-1017`).
- **Why it works**: Ambiguity escalates toward human review instead of away from it. The OpenAI SDK's docs state the fail-closed rule for malformed arguments matches implementation exactly.
- **Copy when**: Always, for any gate evaluation. This is the cheapest high-value pattern in the study.
- **Risky when**: Fail-closed paths become so frequent they train users to approve reflexively — openhands' keyboard-first ⌘↩ accept combined with frequent UNKNOWN gating invites rubber-stamping.

### P3. Identity-bound, consume-once authority

- **Problem**: An approval for one action must not silently authorize another (replayed, reordered, or renamed) invocation.
- **Sources**: agent-framework (occurrence-aware binding to ordered call occurrences, arguments, security labels, and hosted `server_label`; approved executes exactly once, rejections zero times — spec `:377-379`, tests `test_harness_tool_approval.py:1224-1284`); openai-agents-sdk (canonical tool-invocation fingerprints; ambiguous duplicate IDs raise `UserError` instead of guessing `run_state.py:1241-1252`); letta (symmetric-diff validation between requested and answered tool-call IDs `agents/helpers.py:121-144`); pydantic-ai (duplicate `tool_call_id`s rejected up front `_tool_execution.py:966-973`); langgraph (stable interrupt IDs hashed from checkpoint namespace enable targeted resume `types.py:607-618`).
- **Why it works**: Adversarial tests confirm real attacks fail: forged standing approvals dropped (af `test_harness_tool_approval.py:708`), wrong-ID rejections (letta integration tests `integration_test_human_in_the_loop.py:222-245`).
- **Copy when**: More than one gated action can be in flight, or resume payloads traverse untrusted channels.
- **Overkill when**: Single sequential tool calls in a trusted local session — but the cost is low relative to the class of bugs eliminated.

### P4. Denial-as-feedback-to-model (with a hard-stop caveat)

- **Problem**: After rejection, the agent needs to know why so it can adapt rather than flail — but feedback must not become a soft bypass.
- **Sources**: letta (denied calls become error `ToolReturn`s carrying the user's reason `server/rest_api/utils.py:230-264`); pydantic-ai (`ToolDenied` produces `ToolReturnPart(outcome='denied')` with customizable message `_deferred.py:110-114`); openai-agents-sdk (rejection-as-tool-output with configurable text `run_internal/approvals.py:24-43`); agent-framework (synthetic "rejected by user" result, executed zero times `_tools.py:2599-2606`); langgraph (`ignore` response type).
- **Why it works**: Preserves conversational coherence; the model reroutes productively.
- **The caveat**: crewai demonstrates the failure mode when denial is *only* feedback — blocked tools yield the string `"Tool execution blocked by hook..."` with no hard stop, notification, or audit, so the agent can simply plan around the block (`agents/crew_agent_executor.py:962-969`). The mature sources pair feedback with structural enforcement (the call does not execute, full stop) and per-step re-checks (letta re-evaluates the rule each attempt).
- **Copy when**: Rejection should inform retry strategy. **Pair with**: guaranteed non-execution and repeated gating checks on each new attempt.

### P5. Single enforcement choke point

- **Problem**: If every execution path must remember to check the gate, some path will eventually forget.
- **Sources**: pydantic-ai is the clearest case study: declaratively deferred tools once ran silently when callers skipped graph-side kind classification; the fix centralized conversion of the declarative kind into a raised deferral inside `ToolManager.handle_call`, with a comment documenting the bug and a standing policy note that reimplementing the policy layer "is a security bug, not a style problem" (`tool_manager.py:1099-1121`; `realtime/AGENTS.md:20-23`). Agent-framework classifies whole batches before any execution in the invocation loop (`_tools.py:1775-1832`); langgraph fires gates inside engine ticks application code cannot skip (`pregel/_loop.py:666-671,719-724`).
- **Contrast**: letta duplicates the check across three loop implementations (`letta_agent.py:1780-1794`, `letta_agent_v2.py:1138-1153`, `letta_agent_v3.py:1682-1709`) — working today, but the report itself flags silent-regression risk for future loops. crewai distributes enforcement into user-written hooks, where a buggy hook's exceptions are swallowed into allow-all (`hooks/tool_hooks.py:164-190`, `dispatch.py:21`).
- **Why it works**: New callers inherit the gate "for free"; audits have one place to look.
- **Copy when**: You have more than one execution entry point (streaming, nested agents, realtime, sandboxes) — which is essentially always at maturity.

### P6. Scoped standing grants ("don't ask again") with explicit governance limits

- **Problem**: Repeated identical approvals create friction; blanket grants create blast radius.
- **Sources**: agent-framework (standing rules scoped to tool name + optional exact arguments, where `{}` means exactly-no-argument calls and never becomes a wildcard; hosted grants respect `server_label` boundaries — `_harness/_tool_approval.py:86-117,553-572`; tests `:1284,:1368,:1224`); openai-agents-sdk (`always_approve`/`always_reject` sticky records keyed by tool identity, scoped to one resumable run `run_context.py:56-68`, `docs/human_in_the_loop.md:53`).
- **Why it works**: Scoping bounds what a standing grant covers; both document residual risk inline (af warns of name-collision auto-approval bypass `_harness/_tool_approval.py:365-377`).
- **Risky when**: Grants lack expiry, quotas, or revocation — neither source ships TTL/max-use/revoke, and oai's sticky decisions don't persist across fresh runs by default. Copy the scoping; add governance the sources lack.

### P7. Structural gating for inherently-remote or inherently-risky surfaces

- **Problem**: Some actions can't sensibly ask permission at execution time (the executor isn't you), and some tool families are risky enough that opt-in-per-tool is too weak.
- **Sources**: letta marks client-side tools structurally always-gated because only the client can execute them (`schemas/letta_request.py:12-18`); openai-agents-sdk forbids self-gating on hosted shell entirely — misconfiguration raises `UserError` and forces the flag off (`tool.py:1403-1410`); agent-framework denies MCP server-initiated sampling by default absent an explicit callback, rate-limited and token-capped (`_mcp.py:1434-1462`), and ships file-access/skills providers pre-gated to `always_require` with opt-outs (`_harness/_file_access.py:1444-1447`).
- **Why it works**: Removes entire action classes from the discretion question instead of relying on per-call judgment.
- **Copy when**: You ship batteries-included tool families or bridge to environments you don't control.

### P8. Autonomy escape hatch in automation loops, plus resource bounds as the autonomy ceiling

- **Problem**: Autonomous loops that hit a human gate must stop cleanly rather than spin or deadlock; runaway autonomy needs a backstop independent of HITL.
- **Sources**: agent-framework's looping middleware checks for pending approvals before continuing, so approvals reach a human (`_harness/_loop.py:442-459`), and budgets count auto-approved iterations so loops can't bypass caps via auto-approval (`test_harness_tool_approval.py:987-1088`); letta synthesizes denials for all pending calls on cancellation so the conversation stays consistent (`services/run_manager.py:649-759`) and caps looping at `DEFAULT_MAX_STEPS = 50` (`constants.py:75`); langgraph offers cooperative drain at superstep boundaries plus `GraphRecursionError` (`runtime.py:79-104`, `errors.py:67-87`); crewai's `max_iter=25` bounds automated retries.
- **Why it works**: "The system stops when out of its depth" is the dimension's key question; these mechanisms make stopping a designed outcome, not a crash.
- **Copy when**: Any autonomous loop longer than a handful of steps, regardless of whether HITL exists.

### P9. Post-mortem-encoded boundary policy

- **Problem**: Boundary regressions recur when the lesson lives only in a fix commit.
- **Sources**: pydantic-ai converted its realtime bypass into contributor law (`realtime/AGENTS.md:18-23`); agent-framework declares the approval area extra-validation-gated with scenario-to-test mapping (`python/AGENTS.md:62-66`; spec `004-python-function-calling-loop.md:359-412`); openai-agents-sdk freezes field ordering around `needs_approval` to preserve constructor compatibility and schema-gates legacy approval-state reconstruction (`tool.py:477-478`; `turn_resolution.py:1279-1293`). Contrast: openhands retains dead i18n keys describing an older, richer per-severity confirmation UI whose documentation vanished with the feature (`src/i18n/translation.json:8944-8985`).
- **Why it works**: Turns individual fixes into structural constraints future contributors cannot casually violate.
- **Copy when**: A boundary bug of any severity has occurred — that moment is the cheapest time to write the rule down.

## Key Differences

- **Default posture is uniform; compensation differs.** All seven ship autonomous-by-default. Agent-framework compensates by pre-gating its own shipped risky provider families while keeping the framework-wide default ergonomic (`_tools.py:408` vs `_file_access.py:1444-1447`); openai-agents-sdk compensates with fail-closed evaluation edges; openhands relies almost entirely on the user finding a setting hidden behind progressive disclosure (`__tests__/routes/verification-settings.test.tsx:98-101`); crewai compensates not at all beyond `max_iter`.

- **Enforcement locus is the deepest split.** Engine-level enforcement (langgraph ticks, agent-framework batch classifier, pydantic-ai choke point) means application code physically cannot skip the gate. Application-level enforcement (crewai hooks, openai-agents-sdk per-tool declarations evaluated by the runner) depends on developer diligence and evaluator correctness. Remote enforcement (openhands) moves guarantees outside the studied code entirely — its report states enforcement fidelity is unverifiable in-source.

- **Risk-awareness is rare.** Only openhands classifies action risk at runtime (LLM/pattern analyzers producing a four-level vocabulary feeding a threshold policy, `agent-server-adapter.ts:593-618`); agent-framework approximates it statically by pre-gating risky families; everyone else leaves conditional gating ("approve only refunds", "interrupt only for market DE") to hand-written predicates (`docs/human_in_the_loop.md:27-33`; `tests/test_large_cases.py:4147-4176`).

- **Library vs product determines who owns durability.** The libraries (openai-agents-sdk, pydantic-ai, agent-framework) serialize pause state and explicitly delegate correlation/authentication to hosts — pydantic-ai documents "Approval is not an authorization boundary" in three places (`docs/deferred-tools.md:101-102`, `docs/ui/overview.md:138-141`, `docs/message-history.md:406-417`). The products (letta, openhands) own persistence and UX: letta derives pending state from message history alone; openhands persists settings server-side and drives the UI from backend-provided schemas.

- **Granularity varies independently of maturity.** Per-tool-call predicates (oai, pydantic-ai wrapper toolsets), per-node lists (langgraph), whole-run tri-modal policies (openhands), per-artifact toggles (crewai), per-agent tool rules (letta). CrewAI's granularity problem is semantic, not size: its four mechanisms answer different questions (answer review vs action gating vs step review vs capability) with no guidance on composition or choice.

- **Escalation quality diverges sharply.** Mature sources escalate by design: pending approvals halt automation loops (af), cancellation degrades to denial not deadlock (letta), unresolved realtime deferrals return honest `failed` outcomes rather than fake success (pydantic-ai `realtime/_session.py:378-403`), operators get cooperative drain (langgraph). crewai has literally no escalation concept — searching `escalat` finds zero matches — so repeated guardrail failures just exhaust retries and error out (`lib/crewai/src` search noted in its report).

## Tradeoffs

- **Autonomous-by-default vs safe-by-default.**
  Benefit: zero-config adoption, minimal friction (every source chose this).
  Cost: undeclared dangerous actions run unattended; safety burden shifts to tool authors/users.
  Best fit: developer libraries seeking adoption; local interactive use.
  Failure mode: openhands' most autonomous surface (headless automations) has no gate anywhere in its contract (`src/types/automation.ts:24-46`).
  Alternative seen: agent-framework's hybrid — ergonomic core default, deny-by-default for shipped risky families and untrusted initiators.

- **Centralized choke point vs distributed interception.**
  Benefit (choke point): new callers inherit gates; one audit location; drift-proof (pydantic-ai's post-fix posture).
  Cost: choke-point logic concentrates complexity and maintenance burden — agent-framework mandates extra validation for changes there (`python/AGENTS.md:62-66`).
  Best fit: frameworks with multiple execution surfaces.
  Failure mode (distributed): swallowed hook exceptions degrade to allow-all (crewai `dispatch.py:21`); three-generation duplication invites regression (letta).
  Alternative seen: langgraph splits the difference — minimal engine enforcement, policy-free core, semantics pushed to clients (at the cost of unvalidated resume responses).

- **Pause-the-world vs inline resolution.**
  Benefit (pause): unlimited human deliberation latency; survives restarts; simple mental model.
  Cost: liveness — pydantic-ai's realtime sessions cannot pause at all, so the same gated tool becomes a refusal there, a behavioral difference developers must know (`realtime/_session.py:390-397`).
  Best fit: text/batch workflows; approval-inbox products (letta).
  Failure mode: non-idempotent side effects before the pause repeat on resume — langgraph documents that resuming re-executes the node from its start (`types.py:862-864`).
  Alternative seen: pydantic-ai composes both — an inline handler resolves a subset while the rest bubbles up (`_tool_execution.py:1030-1041`).

- **Sticky standing grants vs repeated prompting.**
  Benefit: friction removal for high-frequency safe calls (both af and oai ship this).
  Cost: unrevocable-for-the-run authorization with no TTL, quota, or argument-fingerprint binding (oai `run_context.py:56-68`); name-string matching admits collision-based widening (af `_harness/_tool_approval.py:365-377`).
  Best fit: tightly scoped grants (exact arguments, server labels) within single runs.
  Failure mode: a colliding tool name auto-approved by someone else's rule.
  Alternative seen: one-shot decisions as default in both, stickiness strictly opt-in per decision.

- **Policy-free core vs opinionated harness.**
  Benefit: flexibility; clients/UIs compete on review UX (langgraph's deliberate stance).
  Cost: two clients enforce different policies against the same interrupt; predictability across UIs is not guaranteed (`libs/prebuilt/langgraph/prebuilt/interrupt.py` advisory flags).
  Best fit: platforms with diverse frontend ecosystems.
  Failure mode: response-side enforcement becomes pure convention — core delivers any resume payload verbatim (`types.py:950-965`).
  Alternative seen: openhands compiles policy into a wire contract so enforcement semantics travel with the request, not the client.

- **Rich feedback to the model vs hard termination.**
  Benefit: adaptive retry with reasons preserves usefulness after denial.
  Cost: if the block is advisory, the agent routes around it (crewai's soft string).
  Best fit: pair them — feed the reason back *and* guarantee non-execution with re-checks per attempt, as letta/pydantic-ai/oai do.
  Failure mode: denial-as-error-feedback without fresh gating per retry would let variants slip through; letta's per-step rule re-check is load-bearing.

## Decision Guide

Choose your approach model by product shape and trust boundary:

- **Building a library/framework with multiple execution surfaces?** Adopt the typed approval protocol + single choke point (pydantic-ai / openai-agents-sdk shape). Encode the gate in the tool definition so it survives serialization and streaming (pydantic-ai's `ToolDefinition.kind` approach, `tools.py:506`), normalize all surfaces through one evaluator, and make evaluation fail closed. Budget for the resume-correlation complexity early — it is where both 8-scoring libraries concentrate their code.

- **Building a hosted product where users configure oversight?** Compile declarative policy into an explicit wire contract (openhands' `confirmation_policy` union) so enforcement is server-side and auditable, and expose risk metadata per action so humans know what they're approving. Do not repeat openhands' gap: give your most autonomous surface (automations/headless) a gating story from day one.

- **Building a long-running agent service with an inbox-style UX?** Letta's shape fits: approvals as persisted first-class messages, pending-state guards (409), ID-symmetric validation, cancel-degrades-to-denial, and stop reasons that keep runs queryable. Centralize the gate check now, before loop-version proliferation forces refactoring.

- **Building a graph/workflow engine?** Langgraph's primitive-first design scales well: interrupts as engine-raised control flow on checkpoints, stable interrupt identities, resume primitives. But validate resume payloads against declared affordances server-side — the one thing langgraph leaves to convention is where its report locates the residual risk.

- **Prototyping quickly?** CrewAI's hook seam gets you interactive gating fast, but treat it as scaffolding: replace soft blocks with hard ones, add escalation, and do not assume any boundary transfers to lighter execution engines (its LiteAgent has none).

If forced to one heuristic: **prefer the design where removing the human causes an exception, not a behavior change.** In crewai, removing the hook changes nothing observable; in pydantic-ai, removing resolution capability makes deferral raise `UserError` (`_tool_execution.py:1043-1049`).

## Practical Tips

1. **Make the gate part of the tool's identity**, not a runtime side-channel — a declaration on registration (`requires_approval=True`, `approval_mode`, `needs_approval`) survives streaming, serialization, and replay without re-running user code (pydantic-ai `tools.py:506`; af decorator `_tools.py:1252-1259`).
2. **Fail closed in the evaluator**: unparseable args, crashed predicates, missing context ⇒ require approval. Three of four top-rated sources implement exactly this; it costs a few branches and eliminates the worst bypass class.
3. **Bind decisions to canonical call identities and consume them once.** Symmetric ID validation plus exactly-once execution is table stakes once approvals can queue (letta `helpers.py:121-144`; af spec `:377-379`).
4. **Filter approval traffic out of model replay.** Approval requests/responses are control-plane; resolved wrappers should vanish from context while unresolved ones stay resumable (af `_sessions.py:878-932`).
5. **Give automation loops a gate-aware exit**: check for pending approvals before continuing loops; count budget against auto-approved iterations; cap steps (af `_loop.py:442-459`; letta `constants.py:75`).
6. **Scope standing grants narrowly** (exact arguments, server/namespace labels) and document their collision risks at the API surface, as agent-framework does inline (`_harness/_tool_approval.py:365-377`).
7. **Show validated arguments to humans.** Enforce validation-before-deferral so approvers see what will actually run (pydantic-ai invariant, `tool_manager.py:306-428`); consider allowing arg override with revalidation on approve (`ToolApproved.override_args`).
8. **Write the trust-model warning down**: approval guards against the model acting unilaterally, not against malicious clients — say so where developers will read it (pydantic-ai's triple documentation is the benchmark).
9. **Test adversarially**: forged approvals, wrong IDs, replayed history, removed tools mid-flight, malformed consent values, cancel-during-pending. The 8-scored sources' test suites read like attack inventories (af `test_harness_tool_approval.py:45-1368`; oai's 83-function call-ID-reuse suite).
10. **When a boundary bug happens, encode the lesson as policy** (contributor rules, specs, parity-test requirements) the same sprint, while the pain is specific.

## Anti-Patterns / Caution Signs

- **Advisory blocks.** If a "denial" reaches the agent as ordinary text and execution continues elsewhere, you don't have a boundary — you have a suggestion (crewai `crew_agent_executor.py:962-969`).
- **Enforcement logic duplicated across engines/versions.** Each additional copy is a future silent bypass (letta v1/v2/v3; af's Go port living outside the repo). Caution sign: reviewers approving a gate change must remember N places.
- **Gate code whose failures are swallowed.** Exceptions from approval hooks caught-and-warned convert bugs into allow-all (crewai `tool_hooks.py:164-190`). Gates need fail-closed exception handling.
- **Boundaries lost on serialization round-trips.** Callable guardrails silently dropped during checkpointing mean restored runs skip validation (crewai `guardrail.py:12-31`). If state doesn't capture the boundary, restoration deletes it.
- **Heuristic identification of the gated action.** Inferring "the thing being confirmed" as "last agent event" mislabels targets after reconnects/replays (openhands `conversation-confirmation-buttons.tsx:30-36`); positional matching of multiple interrupts per node silently reshuffles which answer lands where on reorder (langgraph `types.py:866-868`).
- **The most-autonomous surface having the weakest boundary.** Headless automations with no gating field (openhands), voice agents stripping approval logic (letta `voice_agent.py:412-465`), background memory edits ungated by design (letta `sleeptime_v2.py:4-10`), lightweight engines without HITL (crewai LiteAgent), hidden tasks exempt from wildcard interrupts (langgraph `_algo.py:176-179`).
- **One-keystroke approval + frequent prompts.** Ergonomic accept shortcuts over high-frequency UNKNOWN-risk gating trains rubber-stamping (openhands ⌘↩ + `confirm_unknown:true`).
- **Unvalidated resume payloads.** Clients answering interrupts with arbitrary values, or affordance flags (`allow_edit`) enforced only by UI convention, mean the boundary is whoever's-client-is-running-deep (langgraph `types.py:950-965`).
- **Documentation decay.** Normative behavior surviving only in i18n strings and mock data, or moved off-repo entirely (openhands, langgraph `docs/llms.txt:1-5`), signals nobody owns the model anymore.

## Notable Absences

Things no source does — consistent gaps across the cohort:

- **Graded autonomy levels.** Every source explicitly reports the absence of a global dial (supervised/auto tiers, `require_approval="all"` run modes). Configuration is compositional per tool/node/artifact everywhere (af Q&A §2; letta searched settings for `approv|autonom` — no matches; pydantic-ai searched package-wide — no knob; langgraph "no named levels").
- **Approver identity, RBAC, or dedicated audit trails.** Who approved what is invisible to every framework core; pydantic-ai delegates to app deps, openai-agents-sdk offers only trace spans, letta records reasons in conversation but no approver concept.
- **Standing-grant governance.** No TTL, max-use, or revocation API on any sticky/always-approve record (af, oai).
- **Pending-approval hygiene.** No timeout/expiry for stale pending approvals beyond manual cancellation (letta Future Considerations); no quota on re-requesting denied tools within step budgets.
- **Automatic risk classification** beyond openhands' LLM analyzer; argument-destructiveness detection is left entirely to user predicates (oai Future Considerations).
- **Cross-run approval memory.** Sticky decisions don't persist to fresh runs by default (oai); no source applies past approvals automatically across sessions.
- **Evidence gaps to flag honestly**: openhands' actual enforcement fidelity is unverifiable within its frontend-only source; agent-framework's .NET parity was spot-checked, not line-audited, and its Go port is external; letta's cross-conversation contention around a pending approval was not traced end-to-end; pydantic-ai's claimed CLI approval prompts were not found in-tree.
