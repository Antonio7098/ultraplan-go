## Executive Summary

Governance that a human can operate without reading code exists nowhere as a complete product across these sources except in **Langfuse (8/10)**. Four of five sources prove that a mature *approval kernel* is insufficient for operator usability: agent-framework (6/10) and openai-agents-sdk (5/10) ship excellent server-authoritative pause/resume primitives, typed states, and durability but only a reference DevUI or CLI `window.confirm` demo; opa (4/10) is intentionally not a workflow engine and answers governance through observable decision logs and health gates; openhands (3/10) is a single-conversation inline gate with no queue.

The central finding: **approval mechanism maturity does not predict operator workflow maturity**. All sources except OPA converge on server-authoritative, replay-safe decisions (client sends only IDs + boolean, server resolves from persisted request). Only Langfuse closes the loop with review queues, RBAC double-enforcement, audit snapshots, lease-based work claiming, keyboard-first triage, and observable async bulk jobs. Everywhere else an operator can approve one action but cannot *find* what needs review, act *in bulk*, or *prove* what was decided without building host tooling.

Evidence packs — the dimension's explicit artifact of a packaged decision + rationale + outcome — are absent in all five; the nearest analogs are checkpoint inspectors (agent-framework), audit-log before/after JSON (Langfuse), decision-log `EventV1` + explain traces keyed by `decision_id` (OPA), and transcript/zip exports (OpenHands).

## Core Thesis

Sources diverge not because some teams ignored governance UX, but because they occupy different product shapes with different human-operator contracts:

* **Langfuse** is a multi-tenant observability/review application where operators are first-class users — so it invests in queues, locking, bulk jobs, and audit.
* **agent-framework and openai-agents-sdk** are embeddable libraries/frameworks — they intentionally delegate dashboards to hosts and maximize protocol correctness (atomic batches, exactly-once, occurrence-aware identity, versioned durability) at the cost of shipped usability.
* **OPA** is a policy decision point (PDP) — it externalizes approvals to the control plane and maximizes evidence *generation* (decision logs, status, health, traces) while refusing in-process human pauses.
* **OpenHands** is a solo-developer agent canvas — it minimizes governance to an opt-in per-conversation gate and optimizes for zero-friction demo use.

What **converges** despite those constraints is a de facto standard for usable governance *if* you build the UI: approvals as first-class typed content/events persisted server-side, decisions as state-machine transitions (PENDING → CLAIMED/SETTLED/REJECTED/EXPIRED/INDETERMINATE), server-owned resolution that ignores client-supplied `function_call` payloads, fail-closed ambiguity handling (reject ambiguous matches, force manual review on uninspectable args), and correlation IDs (`decision_id`, `call_id`, `thread_id+occurrence_id+interrupt_id`) threading operator action to system outcome. What remains absent everywhere is the synthesis of those primitives into an aggregated, cross-project, evidence-bearing review surface that works under pressure with bulk, attribution, and revocation.

> A human can approve or block an action without reading code in every source except OPA — but only Langfuse and (narrowly) agent-framework's DevUI let that human *find* and *triage* the work efficiently.

## Approach Models

Four archetypes emerged; two are variants of the same hosting pattern.

### 1. Productized Review Workflow — Langfuse

Governance is a product surface humans live in. Two subsystems share patterns but not UI: **annotation queues** for human judgment on traces/observations/sessions, and **in-app-agent approvals** for destructive MCP tool calls. Review is queue-based with server-side leasing (`fetchAndLockNext` stamping `lockedAt/lockedByUserId` with 5-min staleness at `web/src/features/annotation-queues/server/annotationQueuesRouter.ts:466-516`), per-queue pending/completed aggregates (`annotationQueuesRouter.ts:64-96`), RBAC double-enforcement (client `useHasProjectAccess` + server `throwIfNoProjectAccess` at `annotationQueueItemsRouter.ts:79-83`), and audit log entries with actor/before/after (`auditLog.ts:7-52`). Agent approvals are exactly-once CAS transitions over an append-only event stream (`packages/shared/src/in-app-agent/server/runLifecycle.ts:235-297`), anti-tamper (client sends IDs+boolean, server re-derives tool name at `backgroundRunService.ts:396-400`), TTL-bounded and reconciled (`APPROVAL_EXPIRED`, `APPROVAL_SUPERSEDED`). Destructive bulk work is reified as durable `BatchActionJob`s with progress/failed counts surfaced in a dashboard (`BatchActionsTable.tsx:71-107`).

Best fit: teams where operators *are* the user and throughput under pressure matters.

### 2a. Host-Delegated Kernel + Reference UI — agent-framework

Governance primitives are protocol-owned; the shipped UI is explicitly "a development-only sample app, not a production hosting surface" (`python/packages/devui/AGENTS.md`). Core is `ApprovalLifecycle` — sole owner of registration with `ApprovalStatus` enum including `INDETERMINATE` for crash-surviving executions (`python/packages/ag-ui/agent_framework_ag_ui/_approval_lifecycle.py:93-119`), atomic batch ops `claim_batch/resolve_batch/cancel_batch/expire_batch` with per-batch locking (`_approval_lifecycle.py:34-62,478-681`), occurrence-aware identity `(thread_id, occurrence_id, interrupt_id, call_id)` at `:_approval_lifecycle.py:137-144`, capacity `max_entries=10_000` with retention windows. DevUI renders per-conversation banners (`agent-view.tsx:2091-2155`) and schema-driven HIL forms (`hil-timeline-item.tsx:27-153`) but stores `pendingApprovals` in Zustand wiped on conversation switch (`devuiStore.ts:505-538`), hides resolved approvals from history (`agent-view.tsx:1097-1102`), and offers no bulk UI. Foundry hosting persists approvals via `FunctionApprovalStore` (`foundry_hosting/_state_store.py:204-253`), checkpoints provide forensic read-only views (`checkpoint-info-modal.tsx:110-223`).

### 2b. Headless Pause/Resume Kernel — openai-agents-sdk

No shipped UI at all beyond `window.confirm` demo (`examples/realtime/app/static/app.js:566`) and CLI prompt loops (`examples/agent_patterns/human_in_the_loop.py:114-133`). Run loop terminates into `NextStepInterruption` carrying `ToolApprovalItem`s (`src/agents/result.py:515-516`, `src/agents/run_state.py:985-1017`), host resolves via `RunState.approve/reject` (`src/agents/run_state.py:1255-1298`) writing `_ApprovalRecord` (bool-or-call-ID-lists plus sticky messages at `src/agents/run_context.py:56-68`). Decisions survive serialization via `RunState.to_json/from_string` versioned to `1.17` (`run_state.py:179-222`). Supports nested collapsing (one outer surface), identity-scoped stickiness (`always_approve` bound to namespace/server, `run_context.py:903-907`), fail-closed on malformed args (`util/_approvals.py:18-29`), and layered rejection messaging (`run_config.py:83-105`). Like 2a, correctness is excellent; discoverability is pull-only with no notification hook in the non-realtime path.

2a vs 2b tradeoff: agent-framework ships more lifecycle states and reference UI chrome; openai-agents-sdk ships deeper validation (3.8k lines of `test_hitl_error_scenarios.py`) and versioned durability but thinner UI.

### 3. Observable Decision Point — OPA

No human pause concept. Human governance lives upstream (author, test, sign) and in the surrounding control plane. OPA maximizes operator *visibility* without requiring Rego reads at triage time for health, but requires it for diagnosis: `EventV1` decision logs with decision_id/bundles/input/result/erased/masked (`v1/plugins/logs/plugin.go:49-76`) via pluggable `Logger` (`logs/plugin.go:38-43`), aggregated `UpdateRequestV1` status snapshots (`status/plugin.go:41-49`) pushed to console/Prometheus/service, `/health` gates including policy-driven `?policy=` probes (`v1/server/server.go:1299-1416`), `/v1/policies` inventory with compile errors (`server.go:2179-2275`), `explain=full|notes` traces (`server.go:1813-1814`) correlated by `decision_id` (`server/types/types.go:267`). Change is blocked via bundle JWT verification (`bundle.go:916`) and atomic compile-or-reject activation (`plugins/bundle/plugin.go:607-681`). Bulk is batch evaluation `opa exec` (`cmd/exec.go:36-56`).

### 4. Solo-Developer Inline Gate — OpenHands

Governance is a per-conversation, opt-in flag (`confirmation_mode=false` default at `src/services/settings.ts:13`). Policy at `agent-server-adapter.ts:593-605` maps to `NeverConfirm / ConfirmRisky(HIGH) / AlwaysConfirm`; when `waiting_for_confirmation` (`common.ts:71`) the frontend reverses the event log to find the last `source==="agent"` event and renders two buttons (`conversation-confirmation-buttons.tsx:30-136`) posting to single-id `POST /api/conversations/{id}/events/respond_to_confirmation` (`event-service.api.ts:40-69`) with `useRespondToConfirmation` dedup via `submittedEventIds` (`use-respond-to-confirmation.ts:12-32`). No queue, no bulk, no audit; status dot collapses `WAITING_FOR_CONFIRMATION` to ordinary green `active` (`conversation-status-dot.tsx:32-34`).

## Pattern Catalog

### P1. Server-Authoritative Approval Resolution (anti-tamper)

*Problem:* Client-compromised or stale UIs must not forge or widen approval scope.
*Sources:* agent-framework, langfuse, openai-agents-sdk. Demonstrated clearly in Langfuse (client sends only IDs+boolean, server re-parses persisted interrupt at `packages/shared/src/in-app-agent/server/backgroundRunService.ts:379-400` with doc comment at `web/src/features/in-app-agent/server/router.ts:260-268`), agent-framework (executor tracks issued requests and replaces client `function_call` data at `python/packages/devui/agent_framework_devui/_executor.py:126-131` + `AG-UI/_agent_run.py:1243-1287` canonicalization), openai-agents-sdk (canonical call-ID validation at `src/agents/run_context.py:888-1041`).
*Why it works:* Persistence is the ground truth; UI is a narrow decision bit.
*When to copy:* Always if approvals authorize side effects.
*When overkill:* Read-only annotation that carries no privilege.
*Evidence:* `EventService.respondToConfirmation` branching to `callCloudProxy` still validates server-side (`openhands/src/api/event-service/event-service.api.ts:40-69`); CWE-863 tests (`agent-framework/python/packages/devui/tests/devui/test_approval_validation.py:109-199`).

### P2. Approvals as First-Class Typed Content / Events

*Problem:* Governance must flow through the same transports, persistence, and observability as other messages.
*Sources:* agent-framework (`function_approval.requested/responded` SSE at `python/packages/devui/agent_framework_devui/_mapper.py:188-189`), openai-agents-sdk (`ToolApprovalItem` union at `src/agents/items.py:556-676`, `Result.interruptions` at `src/agents/result.py:515-516`), Langfuse (append-only decision events `InAppAgentApprovalDecisionSchema` at `packages/shared/src/in-app-agent/approvalEvents.ts:10-18`), OPA ( `EventV1` at `v1/plugins/logs/plugin.go:49-76` ).
*Why:* No side-channel API to maintain; history providers, traces, and exports automatically include governance.
*When to copy:* When you need audit or replay for free.
*Risk:* If you filter these contents from the user-visible transcript (agent-framework `agent-view.tsx:1097-1102` does), you erase the audit trail you just created.
*Evidence:* History-provider audit retention note at `docs/specs/004-python-function-calling-loop.md:391-409` (agent-framework).

### P3. Atomic Batch / Bulk as Durable Jobs vs Inline Mutations

*Problem:* Acting on many approvals/triaging many items must be observable, safe, and resumable.
*Sources:* Strongest in Langfuse (select-all-matching banner at `web/src/components/table/data-table-multi-select-actions/data-table-select-all-banner.tsx:17-58`, `createBatchActionJob` with audit + queue at `features/table/server/createBatchActionJob.ts:147-196`, dashboard with processed/failed/log at `features/batch-actions/components/BatchActionsTable.tsx:71-107`); protocol-level in agent-framework (`claim_batch/resolve_batch` atomically validated at `python/packages/ag-ui/agent_framework_ag_ui/_approval_lifecycle.py:478-607` with lock decorator `:_approval_lifecycle.py:34-62`), workflow HIL batch submit (`workflow-view.tsx:951-1000`).
*Why:* Inline loops fail on partial errors and leave no trace.
*When to copy:* For any destructive or high-volume triage (delete, add-to-queue, dataset, evaluation).
*Overkill:* Single-conversation developer gate (OpenHands) where volume is one.
*Failure mode:* All-or-nothing validation (`workflow-view.tsx:968-972`) couples unrelated decisions and blocks valid ones.

### P4. Work Claiming via Short-Lived Leases (not locks)

*Problem:* Distribute review work without distributed-lock infrastructure, while avoiding duplicate effort.
*Sources:* Langfuse `fetchAndLockNext` stamps `lockedAt/lockedByUserId` and ignores locks >5 min (`web/src/features/annotation-queues/server/annotationQueuesRouter.ts:485-516`), surfaces staleness via `isItemLocked` (`annotationQueueItemsRouter.ts:32-38`) and red banner `AnnotationDrawerSection.tsx:53-60`. Absent elsewhere — agent-framework enforces ownership via `ApprovalLifecycle` batch locks instead.
*Why:* Simple, recovers from crashed clients, surfaces rather than blocks conflicts.
*When to copy:* Human review queues with multiple annotators.
*Risk:* Abandoned lease can be re-claimed and processed twice; resolution is social (warning banner), not blocking.
*Evidence:* Tests for concurrent-editor handling are UI-centric, not transactional.

### P5. Exactly-Once via CAS on Persisted State (the queue's counterpart for agent approvals)

*Problem:* Two deserialized copies of the same state must not both decide the same interrupt.
*Sources:* Langfuse `decideToolApproval` uses `updateMany` where `status=AWAITING_APPROVAL` (`packages/shared/src/in-app-agent/server/runLifecycle.ts:235-297`, conflict message "already decided, reload" at `:293-297`); agent-framework `ApprovalLifecycle` serializes per `thread+interrupt` set and rejects duplicate interrupts (`_approval_lifecycle.py:34-62`); openai-agents-sdk raises `UserError` on duplicate identities (`src/agents/run_state.py:1087-1092`).
*Why:* Durable, database-native, avoids external locks.
*When to copy:* Whenever approvals outlive a process (serialized RunState, persisted interrupts).
*Tradeoff:* Last-writer semantics under race; operator sees reload guidance rather than optimistic merge.
*Evidence:* Server tests `traces-batch-delete-trpc.servertest.ts:148-199` (Langfuse), `test_approval_lifecycle.py:719-772` (agent-framework).

### P6. Schema-Driven HITL Forms & Tiered Rejection Messaging

*Problem:* Operators need structured context and the model needs controlled feedback on rejection.
*Sources:* agent-framework renders `request_schema` into `SchemaFormRenderer` with validation-gated submit (`python/packages/devui/frontend/src/components/features/workflow/hil-timeline-item.tsx:42-153`, `models/_openai_custom.py:144-170`); openai-agents-sdk offers two-layer rejection text: run-wide `tool_error_formatter` (`src/agents/run_config.py:83-105`) plus per-call `rejection_message` (`src/agents/run_context.py:1051-1059`); OpenHands shows `RiskAlert` only for HIGH (`src/components/shared/risk-alert.tsx:12-36`) plus `getRiskText` for MEDIUM/HIGH (`get-action-content.ts:30-97`).
*Why:* Decouples server policy (what to ask) from frontend rendering; gives operator/model distinct channels.
*When to copy:* Workflows with structured inputs (forms) or where model retry behavior depends on rejection phrasing.
*Risk:* Generic risk strings (`HIGH_RISK_WARNING` in OpenHands) explain nothing about *why* it is risky.

### P7. Keyboard-First Triage + Progress & Disabled-With-Reason

*Problem:* Operators under pressure need flow without mouse, and need to know *why* an action is unavailable before submitting.
*Sources:* Langfuse `AnnotationQueueItemPage.tsx:239-358` (⌘/Ctrl+Enter complete+advance, arrows, numeric keys, `?` cheatsheet, typing-target guards, invalid-input veto at `:270-277`, progress `n/total` at `:103-138`, pulses at `:212-234`) and `TableAction.disabledReason` pre-submit (`web/src/components/table/use-cases/traces.tsx:631-650`); OpenHands `Cmd+Enter/Shift+Cmd+Backspace` at `conversation-confirmation-buttons.tsx:60-90`.
*Why:* Reduces click fatigue, preserves flow, prevents wasted submissions.
*When to copy:* Any queue where throughput matters; disabled-with-reason is universally cheap.
*Overkill:* Single-item gates where keyboard adds no throughput.
*Evidence:* Storybook coverage of approval card states (`InAppAgentToolCallCard.stories.tsx:157-243`).

### P8. Before/After Audit Snapshots + Correlation IDs

*Problem:* Post-incident forensics needs "what changed, by whom, linking decision to outcome."
*Sources:* Langfuse `auditLog()` serializes `before/after` JSON with actor/roles (`web/src/features/audit-logs/auditLog.ts:86-155`) displayed side-by-side (`AuditLogsTable.tsx:121-140`) and exportable (`BatchExportTableButton` at `:152-158`); OPA threads `decision_id` through response (`server/types/types.go:267`), log event (`plugins/logs/plugin.go:52`), and bulk reports (`cmd/internal/exec/json_reporter.go:11`), plus `erased/masked` residue (`logs/plugin.go:64-65`); agent-framework correlates via `decision_id` and occurrence-aware identities (`_approval_lifecycle.py:137-144`).
*Why:* Join-free investigation; redaction is auditable.
*When to copy:* Always for state-changing governance.
*Risk:* Entitlement-gating (Langfuse `audit-logs` entitlement at `AuditLogsSettingsPage.tsx:12`) creates a visibility cliff between tiers.

## Key Differences

* **What "needs review" means and where it lives.** Langfuse counts pending vs completed per queue via SQL aggregates (`annotationQueuesRouter.ts:64-96`) and surfaces `unseenPendingItemCountByQueueId` (`annotationQueueItemsRouter.ts:253-279`); agent-framework shows per-conversation banners (`agent-view.tsx:2091-2112`) but wipes `pendingApprovals` on conversation/mode switch (`devuiStore.ts:505-538`) with no cross-conversation aggregation; openai-agents-sdk exposes `result.interruptions`/`get_interruptions()` pull-only (`result.py:515-516`, `run_state.py:985-1017`); OPA has no pending concept — health/status answer "what's broken" (`plugins/bundle/status.go:25-39`); OpenHands shows one inline prompt per active chat (`conversation-confirmation-buttons.tsx:30-36`) and maps `WAITING_FOR_CONFIRMATION` to the same green dot as idle (`conversation-status-dot.tsx:32-34`), making triage invisible at scale.

* **Bulk efficiency ladder.** Langfuse ships end-to-end bulk (select-all-matching, async jobs, conflict guards at `createBatchActionJob.ts:110-145`, operations dashboard). agent-framework has protocol-level atomic batches but zero UI bulk (`approveAll` grep = 0). openai-agents-sdk has none — "write your own `for` loop" (`docs/human_in_the_loop.md:154-163`). OPA's bulk is evaluation (`opa exec` with `--fail*` exit codes at `cmd/exec.go:84-86`), not approval. OpenHands has strictly single-id RPC (`event-service.api.ts:40-69`).

* **Exception surfacing philosophy.** Langfuse and agent-framework surface structured typed errors to the operator *and* the model: Langfuse renders `ObjectNotFoundCard` (`AnnotationQueueItemPage.tsx:379-401`) and maps Prisma P2025 to NOT_FOUND (`annotationQueueItemsRouter.ts:461-471`), agent-framework carries `WorkflowErrorDetails` with traceback (`_workflows/_events.py:70-99`) and typed resume codes `APPROVAL_RESUME_*` (`ag_ui/_agent_run.py:1278-1316`), openai-agents-sdk appends synthetic `ToolCallOutputItem` (`run_internal/approvals.py:24-43`). OPA surfaces degradation as telemetry (bundle `Code/Message/Errors`, `status.go:25-39`; health `exclude_plugin` at `server.go:1304-1308`) not triage. OpenHands reuses generic `ErrorMessageBanner` (`error-message-banner.tsx:95-210`) and collapses `STUCK→ERROR` (`use-agent-state.ts:30-31`).

* **Durability & identity.** Langfuse: append-only event stream + relational CAS + TTL + supersede (`runLifecycle.ts:210-216,263-281`). agent-framework: `INDETERMINATE` with 7-day retention vs 900s terminal (`_approval_lifecycle.py:243-245`), capacity `10_000`, server-owned registration, occurrence-aware IDs. openai-agents-sdk: versioned `RunState` (`1.17`) with schema minima (`run_state.py:179-222`). OPA: status is snapshot-on-demand (`status/plugin.go:330`) not persisted queue. OpenHands: in-memory `submittedEventIds` dedup, relies on re-derived `curAgentState` from websocket.

* **RBAC & attribution.** Langfuse double-enforces every mutation (`throwIfNoProjectAccess` per procedure, `useHasProjectAccess` in UI) over a shared scope matrix (`projectAccessRights.ts:5-86,91-272`) and records `decidedByUserId` (`approvalEvents.ts:10-18`); agent-framework warns standing rules can bypass via name collisions (`_tool_approval.py:365-377`) and dev UI is unauthenticated localhost (`AGENTS.md`); openai-agents-sdk has no RBAC — possession of serialized state is the only boundary; OPA trusts signatures not humans (`bundle.go:916`); OpenHands has no attribution (no who/when on decisions).

* **Evidence-pack readiness.** None generate a first-class reviewer-ready bundle. Each has a fragment: agent-framework read-only checkpoints (`checkpoint-info-modal.tsx:110-223`, `workflows/_checkpoint.py:129-249`), Langfuse before/after audit + batch export (EE-gated), OPA per-decision `EventV1` + explain trace keyed by `decision_id`, OpenHands transcript/zip exports (`transcript-export/index.ts:514-677`, `use-download-conversation.ts:9-27`), openai-agents-sdk underscored `_approvals` dict visible only by parsing serialized state.

## Tradeoffs

* **Productized UX vs embed-ability (Langfuse vs kernels).** *Benefit:* Productized queues give throughput (keyboard, leases, progress, bulk) and observability (audit, batch dashboard). *Cost:* Two parallel governance surfaces (annotation queues vs agent approvals vs batch dashboards) with no unified inbox; entitlement gating creates incidents where OSS operators lack audit under pressure (`ee/features/audit-log-viewer/AuditLogsSettingsPage.tsx:12`). *Best-fit:* End-user-facing review products. *Alternative:* Host-delegated kernels keep SDKs portable to any host but push all operator tooling onto adopters.

* **Server-authoritative correctness vs stale-UI operability.** *Benefit:* Anti-tamper and consumption-on-use block forgery/replay (CWE-863 tests `test_approval_validation.py:109-199`). *Cost:* Stale browser tab submissions fail silently with typed errors (`APPROVAL_RESUME_NOT_FOUND`, `runLifecycle.ts:293-297`) requiring rediscovery. *Best-fit:* High-risk approvals. *Mitigation elsewhere:* Langfuse's CAS gives explicit "reload" guidance; agent-framework could show retention countdowns.

* **Pause-and-resume vs inline blocking.** *Benefit:* Pause/resume (agent-framework, openai-agents-sdk) survives process restarts and enables async human latency (hours). *Cost:* No push notification — latency to first touch is unbounded; host must build polling/inbox (openai-agents-sdk has no webhook in non-realtime path). OpenHands inline gate is immediate but only works while the conversation is open.

* **Lease-based work sharing vs strict locks.** *Benefit:* 5-min TTL leases avoid lock service and recover from crashes (Langfuse `fetchAndLockNext`). *Cost:* Double-processing possible; conflict resolution is social (red banner). Strict alternatives (Langfuse thread+interrupt batch serialization via `_serialized_by_batch` at `_approval_lifecycle.py:34-62`, OPA snapshot folding) avoid duplication but add infrastructure. *Best-fit:* Low-contention human queues; avoid for exactly-once financial approvals — use CAS instead.

* **Rich telemetry vs learning curve (OPA / explain traces vs dashboards).** *Benefit:* Decision logs, Prometheus gauges, explain traces, and dual console/service sinks work without a UI dependency (`logs/plugin.go:312,790-794`, `status/metrics.go:36-43`). *Cost:* Operator must be fluent in Rego traces/API ergonomics; under pressure diagnosis is slow vs a purpose-built review UI. *Failure:* Mask/drop misconfig can silently drop evidence (`logs/plugin.go:785-788` fail-closed) with only log lines, no dead-letter queue — safety over completeness.

* **Sticky `always_approve` efficiency vs blast radius.** *Benefit:* Reduces fatigue (agent-framework `create_always_approve_tool_response` at `_tool_approval.py:218-245`, openai-agents-sdk `always_approve=True` at `run_state.py:1255-1268`). *Cost:* Run-long authority with no TTL, no revocation UI, and collision risk via same-named tools (`_tool_approval.py:365-377`). *Alternative seen:* Langfuse scopes grants by `(server_label, tool_name)` (`mcpPolicy.ts:477-510`, `runLifecycle.ts:319-355`) and persists in the same transaction as the decision, but also lacks revocation surface.

* **All-or-nothing batch validation vs independent decisions.** *Benefit:* Atomic batches keep resume semantics simple. *Cost:* One malformed HIL response blocks submitting all valid ones (`workflow-view.tsx:968-972`; Langfuse disabled-with-reason is the mitigated variant at `traces.tsx:631-650`). Independent resolution (openai-agents-sdk partially resolving and re-interrupting per `docs/human_in_the_loop.md:57`) trades atomicity for progress.

## Decision Guide

Choose the archetype that matches your operator contract, then borrow patterns from the others.

1.  **Are you building an operator-facing product where humans triage many items?**
    → Copy Langfuse's model. Implement a persisted queue with pending/completed counts, `fetchAndLockNext`-style leases, keyboard-first processor with progress, RBAC double-enforcement, and async `BatchActionJob`s for bulk. Gate audit behind availability, not entitlement if possible.

2.  **Are you a library/SDK that hosts will embed in unknown stacks?**
    → Copy agent-framework / openai-agents-sdk. Ship a pause/resume kernel with server-authoritative IDs, typed statuses including crash states (`INDETERMINATE`), versioned durability (schema minima), occurrence-aware identities, and fail-closed/loud validation. Provide one reference UI (DevUI) explicitly labeled dev-only, plus clear host integration docs — not a dashboard you will need to operate.

3.  **Are you a policy/decision point with no human-in-the-loop at runtime?**
    → Copy OPA. Invest in evidence generation over workflow: decision logs with correlation IDs, status snapshots with dual sinks, health gates (including policy-driven `?policy=` probes), signature-verified change gates, and explain traces. Document the expected control-plane that builds queues on top.

4.  **Are you a solo-dev / single-conversation canvas?**
    → OpenHands inline gate suffices, but immediately add: a distinct visual for `WAITING_FOR_CONFIRMATION` (not green `active`), a global pending count, and persistence of pending IDs beyond in-memory dedup.

**Bulk decision rule:** If destructive or high-volume actions exist → reify as durable jobs with `processedCount/failedCount/log` and single-flight guards (Langfuse `createBatchActionJob.ts:110-145`). If volume is per-conversation and low → protocol-level atomic batches are enough. Never use inline loops for destructive multi-select.

**RBAC rule:** If any approval authorizes side effects → double-enforce (UI disable + server `throwIfNoProjectAccess` per procedure) and record `decidedByUserId`; anti-tamper re-derive tool identity server-side. If possession of state is the boundary (SDK case), document it loudly.

**Evidence-pack rule:** If compliance or incident response matters → bundle `decision_id` + inputs + result + explain trace + bundle revision + policy hash + approval decision + actor/timestamp into one export (OPA's pieces plus Langfuse's before/after are the blueprint); do not rely on stitching logs manually.

## Practical Tips

**Patterns to copy immediately (low cost, high leverage):**
- *Disabled-with-reason for bulk actions* (`web/src/components/table/use-cases/traces.tsx:631-650`): show why bulk is unavailable before submission (e.g., comment filters) rather than failing post-submit.
- *Keyboard shortcuts with cheatsheet and pulses* (`AnnotationQueueItemPage.tsx:212-234,558-617`): ⌘Enter to complete+advance, arrows, `?` discoverability — cheap for any queue.
- *Server-rederived tool targets* (`backgroundRunService.ts:396-400`): accept only IDs+boolean from client; resolve name/scope from persisted interrupt.
- *Correlation-ID threading* (`server/types/types.go:267`, `logs/plugin.go:52`, `json_reporter.go:11`): propagate `decision_id`/`call_id` through API, logs, and reports so investigations are join-free.
- *Synthetic output items for failures* (`src/agents/run_internal/approvals.py:24-43`): surface approval-application errors in the normal item stream so consumers need not handle a second channel.
- *Checkpoint / snapshot forensics* (`workflows/_checkpoint.py:129-249`, `checkpoint-info-modal.tsx:110-223`): read-only inspection without mutation risk; deletion is a separate explicit action.

**Patterns to avoid or delay until needed:**
- *Entitlement-gating governance visibility* (`ee/features/audit-log-viewer/AuditLogsSettingsPage.tsx:12`): delay monetization gates on audit/evidence exports until you have a free-tier alternative — incidents happen on OSS/self-host.
- *Sticky always-approve without TTL/revocation* (`src/agents/run_state.py:1255-1268`, `_tool_approval.py:218-245`): avoid until you can scope by `(server_label, tool_name)` and add revocation UI/TTL; otherwise same-named tool collisions silently inherit trust.
- *All-or-nothing HIL batching without validation preview* (`workflow-view.tsx:968-972`): delay batch atomicity until you can validate per-item and surface `disabledReason`; otherwise one invalid blocks all valid.
- *In-memory dedup or Zustand wiped state* (`devuiStore.ts:505-538`, OpenHands `submittedEventIds`): do not rely on ephemeral stores for pending-approval truth; persist in server state.
- *Fail-closed mask/drop without dead-letter metric* (`v1/plugins/logs/plugin.go:785-788`): if you must drop, count and expose the drops as a status field rather than log lines alone.

**Decision rules in practice:**
- If your UI hides resolved approvals from the transcript (agent-framework `agent-view.tsx:1097-1102`) → either render them or guarantee host retention for audit; otherwise "who approved what" is unanswerable.
- If you support cross-process approvals → version your serialized state (`run_state.py:179-222` schema minima) and enforce `updateMany where status=AWAITING_APPROVAL` CAS.
- If you support multiple annotators → prefer leases + warning banners over strict locks for review, CAS for privileged tool approvals — they solve different contentions.

## Anti-Patterns / Caution Signs

- **Per-conversation state collapse:** `pendingApprovals` wiped on conversation/mode switch (`devuiStore.ts:505-538`) or dedup in ephemeral Zustand (`conversation-confirmation-buttons.tsx:17-22`) — signal that governance does not survive navigation or refresh; operator loses work.
- **Status indistinguishability:** Mapping `WAITING_FOR_CONFIRMATION` to the same visual as idle (`conversation-status-dot.tsx:32-34` green `active`, title emoji ✅ for waiting) — pending work has no priority signal; under pressure it is invisible.
- **Invisible history:** Filtering `function_approval_response` from display (`agent-view.tsx:1097-1102`) or only persisting `_approvals` privately (`run_context.py:89` underscore) — audit depends on undocumented host retention ("may retain for audit" at `docs/specs/004-python-function-calling-loop.md:409`).
- **Capacity without alerting:** `max_entries=10_000` with `ApprovalCapacityError` (`_approval_lifecycle.py:239-259`) or buffered decision logs that warn on `Stop` with "decisions possibly still in buffer" (`logs/plugin.go:704-712`) — no UI surfaces exhaustion/loss; fleet scale will hit this silently.
- **Generic error UX for governance:** Reusing `ErrorMessageBanner` for all failures (`error-message-banner.tsx:95-210`) and collapsing `STUCK→ERROR` (`use-agent-state.ts:30-31`) — governance-specific triage (timeout, analyzer failure, override) is unrecoverable.
- **Entitlement cliff on evidence:** Audit exports, protected labels, or status details gated behind paid flags (`audit-logs` entitlement) — the moment you need evidence under pressure is when the gate hurts most.
- **Pull-only approval discovery:** No inbox, no webhook, no notification wiring (`annotationQueueAssignmentsRouter` persistence-only, `get_interruptions()` pull-only) — approvals sit unnoticed with unbounded latency.
- **Fail-closed without visibility:** Mask evaluation errors that drop events (`logs/plugin.go:785-788`) or unparsable args that silently require manual review (`_approvals.py:18-29`) with only server-side logs — auditors see gaps, not explanations.

## Notable Absences

Across all five, **first-class evidence packs are absent**. Every source can emit the pieces (checkpoints, decision logs, explain traces, before/after audit, transcript zips) but none assembles a reviewer-ready bundle of decision + inputs + policy rationale + outcome + actor/timestamp + bundle revision at approval time (searched `evidence pack` in agent-framework = 0 hits; Langfuse batch exports are closest at `AuditLogsTable.tsx:149-161` but EE-gated; OPA `EventV1` at `logs/plugin.go:49-76` + explain at `server.go:2576` remain separate fetches).

Other systemic absences:
- **Unified cross-project / cross-conversation review inbox** — Langfuse has per-queue counts but no global "your pending work everywhere" (`countPendingItems` is per-queue); agent-framework and OpenHands are strictly per-conversation; openai-agents-sdk is per-run (`result.interruptions`).
- **Bulk approve/reject in shipped UI** — only Langfuse's table bulk (which is not agent-approval bulk) and agent-framework's protocol-level batches exist; openai-agents-sdk and OpenHands require N single calls.
- **Rejection / needs-rework disposition** — Langfuse Prisma enum is `PENDING/COMPLETED` only (`schema.prisma:526-529`), skip is client-side `seenItemIds`; other sources similarly lack structured disposition reasons.
- **RBAC + attribution as default** — only Langfuse enforces scope matrix universally; agent-framework and openai-agents-sdk document that possession equals authority.
- **Proactive operator notification** — Slack/monitor integrations exist adjacent to governance (Langfuse `web/src/features/slack`, `web/src/features/monitors`) but no source wires assignment or approval expiry to push alerts; sound/title emoji (`use-agent-notification.ts:6-48`, `use-app-title.test.tsx:73`) are the richest signals shipped.
- **Revocation/TTL for sticky grants** — "always allow" has no management UI or expiry in any source (Langfuse `alwaysAllowedTools` per conversation is the most durable but invisible).

## Per-Source Notes

**agent-framework (6/10) — Best kernel with a dev-only face.** Can a human approve without reading code? Yes in DevUI: "Approval Required" banner shows function name + JSON args with Approve/Reject per item (`agent-view.tsx:2091-2155`) and HIL forms are schema-generated (`hil-timeline-item.tsx:42-153`). But DevUI is dev-only, single-conversation, non-durable, no bulk UI, and resolved approvals vanish from transcript (`agent-view.tsx:1097-1102`). Underneath, the lifecycle is production-grade: typed states, atomic batches, indeterminate protection, Foundry durability (`_state_store.py:204-253`), checkpoint forensics, and policy→approval middleware (`security.py:1642-1679`). Adopt if you need a host-built operator console; do not ship DevUI as is.

**langfuse (8/10) — Only source where governance is usable under pressure.** Operators see pending/completed per queue (`AnnotationQueuesTable.tsx:82-95`), who completed what (`AnnotationQueueItemsTable.tsx:306-357`), unseen counts (`annotationQueueItemsRouter.ts:253-279`), and per-batch processed/failed/log (`BatchActionsTable.tsx:71-107`). They act efficiently via keyboard (`AnnotationQueueItemPage.tsx:239-358`), Approve/Always/Decline cards (`InAppAgentToolCallCard.tsx:64-144`), and select-all-matching → async jobs. Exceptions are first-class (concurrent-edit banner, `ObjectNotFoundCard`, CONFLICT on concurrent deletes, `APPROVAL_EXPIRED`). The audit trail is complete but entitlement-gated.

**opa (4/10) — Governance by evidence generation, not workflow.** Intentionally absent by design (`dashboard|approval` search hits only `v1/ast/index_test.go:1314`, no HTML assets). Operators block via health/signature/compile gates but never approve a pending action. Under pressure they curl `/health` (`server.go:1299`), watch console status (`status/plugin.go:554-568`), diff `/v1/policies` (`server.go:2179`), replay with `explain=full` (`server.go:1813`). Powerful for a PDP, but requires building the review plane elsewhere — documented as ecosystem responsibility (`docs/docs/management-status.md:309`).

**openai-agents-sdk (5/10) — Strongest kernel tests, weakest shipped workflow.** Pending is `result.interruptions` (`result.py:515-516`) with full `tool_name/arguments/call_id/agent` per item (`items.py:556-676`), pausing via `NextStepInterruption` and resuming via `RunState.approve/reject` with identity-checked routing (`run_state.py:1255-1298`, `_apply_approval_decision` at `run_context.py:888-1041`). Fail-closed on bad args (`util/_approvals.py:18-29`), configurable rejection layers, durable versioned state (`run_state.py:179-222`). No queue, no bulk, no audit, no RBAC — every workflow is "write your own loop" (`docs/human_in_the_loop.md:154-163`), demo UI is `window.confirm` (`app.js:566`).

**openhands (3/10) — Minimal gate for a solo dev.** One pending action at a time, inline Confirm (`⌘↩`)/Reject (`⇧⌘⌫`) with `RiskAlert` for HIGH (`risk-alert.tsx:12-36`), chat blocked while awaiting (`interactive-chat-box.tsx:62-65`), dual-plane RPC (`event-service.api.ts:40-69`). No dashboard, no queue, no bulk, no audit, and fleet-scale failure modes (tab-hunting, status dot indistinguishability, ephemeral dedup, `STUCK→ERROR` collapse). Suitable as a safety brake, not an operator workflow.

## Open Questions

- Cross-project/ cross-conversation inbox: does any deployment overlay aggregate pending agent approvals + queue assignments? Langfuse has the per-queue building blocks (`countPendingItems`, `isCurrentUserAssigned` at `annotationQueuesRouter.ts:114-134`, `pendingToolApprovals` at `backgroundRunService.ts:424-444`); is a unified cockpit on the roadmap or left to custom queries?
- Notification: is workspace wiring of Slack/email to queue assignment or batch-action failure planned? Langfuse has `web/src/features/slack` and `web/src/features/monitors` adjacent but disconnected; OpenHands sound (`use-agent-notification.ts:6-48`) is the only push-like signal found.
- Evidence-pack standard: should a `decision_id`-keyed bundle (decision event + explain trace + active bundle revision + policy hash + approval decision + actor/timestamp) become a productized export? All sources have fragments but no bundler; OPA's future considerations explicitly flag this at `v1/plugins/logs/plugin.go:49-76` context.
- Sticky-grant governance: where is `alwaysAllowedTools` managed/revoked? Langfuse persists grants transactionally (`runLifecycle.ts:319-355`) with no visible UI; agent-framework and openai-agents-sdk similarly lack TTL/revocation. Is revocation a missing API?
- Approval expiry recovery UX: Langfuse fails runs with `APPROVAL_EXPIRED` (`runLifecycle.ts:263-281`); agent-framework expires pendings after `pending_retention_seconds` (`_approval_lifecycle.py:176-212`, default 24h). How does the UI prompt re-dispatch after expiry? End-to-end recovery was not traced in any source.
- Audit retention guarantees: is "may retain for audit" (`docs/specs/004-python-function-calling-loop.md:409`) actually durable in shipped history providers? Base provider filters resolved wrappers from model replay; backing-store behavior was unverified.
- OpenHands analyzer transparency: current `confirmation_policy` (`NeverConfirm / ConfirmRisky / AlwaysConfirm` at `agent-server-adapter.ts:593-605`) is not surfaced beyond a lock icon (`confirmation-mode-enabled.tsx:7-27`); how does an operator confirm which threshold is active without inspecting settings payloads?
