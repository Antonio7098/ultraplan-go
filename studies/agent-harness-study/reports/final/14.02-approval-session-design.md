## Executive Summary

Across the five sources, approval is universally implemented as a **pause-and-resume control flow**: every framework suspends its execution loop, surfaces a typed request to a human, and later resumes with the decision. The sources divide into three durability archetypes: (1) **approval-as-persisted-engine-state** (langgraph folds interrupts/resumes into checkpoint writes; openai-agents-sdk serializes decisions into portable versioned `RunState` JSON; agent-framework snapshots surfaced requests into session state and workflow checkpoints; crewai persists Flow pause contexts to SQLite), (2) **server-authoritative status projection** (openhands' frontend stores nothing and re-derives pending approvals from server `execution_status`, making refresh-survival free), and (3) **ephemeral blocking prompts** (crewai's hook/console/task HITL, which die with the process).

The dimension's driving question — *can an approval session survive a browser refresh?* — is answered **yes** by four of five sources, each via a different mechanism: langgraph by construction (interrupt and resume are both rows in `checkpoint_writes`), openai-agents-sdk by portable JSON snapshot, agent-framework by session/checkpoint persistence plus a proven cross-restart rehydrate test, crewai for Flows only via SQLite rows, and openhands by refusing to hold client-side truth at all.

Two findings converge across all five sources as industry-wide gaps: **pending approvals almost never time out** (only agent-framework's AG-UI transport implements explicit expiry — a 24 h pending-retention window), and **none ships a real audit trail** (no durable, queryable record of who approved what, when, and with which scope; auditing is at best structural, reconstructable from checkpoint or history data). A third convergence is more encouraging: the mature sources harden against forged, replayed, aliased, and widened approvals using immutable request snapshots, consume-once binding, and identity fingerprints that refuse to silently expand authority.

## Core Thesis

Approval session design is not one mechanism but the composition of four separable concerns — **request surfacing**, **durability substrate**, **decision scope model**, and **lifecycle policy** — and the sources show that frameworks which fold all four into one object tend to fragment (crewai's three parallel HITL APIs), while those that keep them composable scale across hosting surfaces (agent-framework's protocol reused across session state, workflow checkpoints, Foundry stores, and the AG-UI lifecycle engine). The single most consequential design choice observed is **where the approval state lives relative to the engine's own persistence**: langgraph and openai-agents-sdk make approvals ordinary persisted engine data (checkpoint writes, serialized run state) and get durability, replayability, and time-travel "for free" — but then have nowhere natural to put expiry, identity, or audit, because generic persistence rows carry no approval-specific fields. The lesson: durability comes cheap when approvals ride existing state machinery; lifecycle policy (expiry, audit, revocation) is exactly what doesn't come free and must be designed in deliberately — as agent-framework's AG-UI lifecycle engine demonstrates with statuses, claims, retention windows, and idempotency keys.

## Approach Models

**agent-framework — layered approval protocol.** Approval requests are first-class message content (`function_approval_request` / `function_approval_response`, `python/packages/core/agent_framework/_types.py:373-374`) rather than side-channel state. Tools opt in per-tool (`approval_mode="always_require"`, `_tools.py:106,408`); a mixed batch containing any gated tool pauses entirely before execution (`_tools.py:1775-1795`). Surfaced requests are snapshotted into `AgentSession.state` under the shared `tool_approval` key (`_tools.py:2075-2095`); inbound responses must bind to a snapshot and are consumed once (`_tools.py:2182-2246`). Harness middleware adds standing rules ("always approve tool", "always approve tool with exact arguments") persisted in the same session state (`_harness/_tool_approval.py:218-245`). Workflows serialize pending HITL events into chained checkpoints (`_workflows/_checkpoint.py:59-61,91`). Durability tier is host-selected: in-memory/file session stores, a server-side durable `FunctionApprovalStore` in Foundry hosting (`foundry_hosting/_state_store.py:204-261`), and an AG-UI transport lifecycle engine with full status machine (`ag-ui/_approval_lifecycle.py:93-119`).

**crewai — three parallel HITL generations.** (a) Task/crew `human_input`: blocking console prompt→re-invoke loop (`core/providers/human_input.py:237-264`). (b) Hook gates: `before_tool_call` hooks call `context.request_human_input()` (blocking stdin, `hooks/tool_hooks.py:86-128`) or raise `HookAborted` to deny (`hooks/dispatch.py:64`); denial becomes a synthetic tool result fed back to the model (`agents/crew_agent_executor.py:962-966`). (c) Flow `@human_feedback`: the only durable path — providers raise `HumanFeedbackPending`, kickoff auto-persists `{state_json, context_json}` into SQLite table `pending_feedback` (`flow/persistence/sqlite.py:96-112`; auto-persist at `flow/runtime/__init__.py:2355-2406`), and a fresh process restores via `Flow.from_pending(flow_id)` + `resume(feedback)` (`flow/runtime/__init__.py:1199-1266,1285-1336`).

**langgraph — approvals as checkpointer data.** No approval-session object exists. A node calls `interrupt(value)` (`types.py:851-974`), raising `GraphInterrupt` with a payload whose id is deterministically derived (xxh3_128 of the checkpoint namespace, `types.py:616-618`). The runner commits it as a pending write under reserved channel `__interrupt__` (`pregel/_runner.py:585-591`); the human decision arrives later as `Command(resume=...)`, itself persisted as a `__resume__` write (`pregel/_io.py:74-75`) before the node re-executes from its start and consumes resume values positionally (`types.py:950-965`). A checkpointer is mandatory (`pregel/_loop.py:905-908`). The prebuilt package layers an advisory UI contract (`HumanInterruptConfig` / `ActionRequest` / `HumanResponse`, `prebuilt/interrupt.py:11-105`).

**openai-agents-sdk — decision records in portable run state.** Tools declare `needs_approval` rules (`tool.py:486-493`); unresolved calls become `ToolApprovalItem`s that end the turn via `NextStepInterruption` (`run_internal/run_steps.py:171-181`) surfaced as `RunResult.interruptions` (`result.py:515-516`). Decisions live in `RunContextWrapper._approvals` keyed by provider call id or sticky scope (`run_context.py:56-68,998-1037`). `RunState.to_json()/from_json()` is the explicit durability boundary ("the durable pause/resume boundary for human-in-the-loop flows", `run_state.py:748-762`), persisting decisions, rejection messages, sticky scopes, and a canonical tool-invocation ledger under schema version 1.17 (`run_state.py:182-217,1326-1339`).

**openhands — client-derived, server-owned.** The frontend declares a confirmation policy at conversation creation (`NeverConfirm` / `AlwaysConfirm` / `ConfirmRisky`, `src/api/agent-server-adapter.ts:593-605`); the server suspends the agent with `execution_status = "waiting_for_confirmation"` (`src/types/agent-server/core/base/common.ts:67-75`); the UI projects that status plus the latest agent action event into approve/reject controls (`src/components/shared/buttons/conversation-confirmation-buttons.tsx:30-36`) and posts `{ accept }` to `/api/conversations/{id}/events/respond_to_confirmation` (`src/api/event-service/event-service.api.ts:40-69`). Enforcement lives out-of-boundary in a sibling SDK.

## Pattern Catalog

### P1. Immutable-snapshot binding with consume-once semantics

- **Problem:** Forged, stale, duplicated, or tampered responses executing actions nobody approved.
- **Demonstrated by:** agent-framework (surfaced requests snapshotted; unknown ids dropped with warning; duplicate ids raise; `_tools.py:2141-2246`, DevUI rejects unknown ids at `devui/_executor.py:755-759`), langgraph (null-task resume values consumed once via `get_null_resume(consume=True)`, `_algo.py:1320-1331`), openai-agents-sdk (restored per-call decisions without a matching invocation-ledger entry are demoted to re-approval, `run_context.py:1308-1316`), crewai partially (pending row cleared during resume).
- **Why it works:** The approved artifact is frozen at request time; the response can only attach to a recorded snapshot, so caller mutation, id recycling, and replay cannot redirect authority.
- **When to copy:** Any system where the approving human is remote from the executor. This is the baseline safety floor.
- **When overkill:** Single-process CLI tools where requester and approver are the same person.
- **Evidence:** agent-framework tests forgery rejection and mixed-batch replay (`tests/core/test_harness_tool_approval.py:649-1368`); openai-agents-sdk tests call-id reuse (`tests/test_tool_approval_call_id_reuse.py`).

### P2. Identity-fingerprinted sticky approvals with anti-widening semantics

- **Problem:** "Always approve" answers accidentally authorizing different tools, other servers' identically-named tools, or argument sets broader than what was shown.
- **Demonstrated by:** agent-framework (rule matching on canonicalized args + `server_label`; `arguments=None` = tool-wide while `{}` matches exactly no-argument calls and "can never widen", `_harness/_tool_approval.py:50-58,301-321`), openai-agents-sdk (sticky decisions bind to an approval-scope fingerprint from invocation type + lookup key or hosted-MCP `(server_label, tool_name)` identity; incomplete hosted identity raises `UserError` rather than creating permanent authority, `_tool_invocation.py:236-279`, `run_context.py:902-907`).
- **Why it works:** Scope expansion requires an explicit, distinct representation (`None` vs `{}`, complete vs incomplete tuple), making silent widening structurally impossible.
- **When to copy:** Whenever offering any "don't ask again" affordance, especially across hosted/remote tool servers.
- **When risky anyway:** Both sources note residual hazards — agent-framework documents name-collision bypass for heuristic `auto_approval_rules` callbacks (`_tool_approval.py:365-376`); openai-agents-sdk has no revocation API for sticky decisions once granted.
- **Evidence:** Cross-server isolation tested in `tests/test_run_context_approvals.py:30,360-379` and `tests/core/test_harness_tool_approval.py:1224`.

### P3. Deterministic, content-derived request IDs stable across processes

- **Problem:** Correlating a resume answer to its request after process death, restarts, or providers that recycle call ids.
- **Demonstrated by:** langgraph (`Interrupt.from_ns` hashes the checkpoint namespace, `types.py:616-618`, enabling id-keyed resume maps for concurrent interrupts, `_loop.py:910-920`), agent-framework (occurrence-aware correlation matches reused `call_id` values by ordered occurrence, documented in `python/packages/core/AGENTS.md`, exercised at `tests/ag_ui/test_approval_lifecycle.py:1122`), openai-agents-sdk (invocation fingerprints hash semantic payload, `_tool_invocation.py:155-219`), crewai (`execution_uuid` preserved in the pending context keeps traces continuous across resume, `async_feedback/types.py:40-43`; `flow/runtime/__init__.py:1359`).
- **Why it works:** IDs derived from stable content survive serialization boundaries and enable addressable multi-request protocols.
- **When to copy:** Any durable approval queue; prerequisite for answering multiple simultaneous requests independently.
- **Caveat:** langgraph's positional matching *within* a single node is compact but brittle to reordering (`types.py:866-868`) — cross-task cases correctly avoid it via explicit ids.

### P4. Versioned serialization with compatibility guarantees

- **Problem:** Persisted approval states becoming unreadable after upgrades, or old approvals silently gaining new meaning.
- **Demonstrated by:** openai-agents-sdk most thoroughly: `$schemaVersion` stamped on every write, older readers reject newer versions intentionally, per-version change summaries document approval-relevant bumps (1.6 rejection messages, 1.14 hosted-MCP scoping by server label, 1.16 exact-call overriding sticky), and a fixture corpus proves every released version still resumes (`run_state.py:175-218`; `tests/test_run_state_compatibility_corpus.py:165-250`). Notably, current-schema restores *refuse* to reconstruct missing sticky bindings from interruption items alone — a deliberate tightening over legacy behavior (`tests/test_run_state.py:3053-3204`).
- **When to copy:** Whenever approval state outlives deploy cycles.
- **When overkill:** Ephemeral in-memory approvals.

### P5. Full lifecycle state machine for high-churn transports

- **Problem:** In hosted/multi-client settings, approvals need claims, concurrent-access arbitration, retry deduplication, and bounded storage — not just pending/settled.
- **Demonstrated by:** agent-framework's AG-UI engine exclusively: statuses PENDING→CLAIMED→EXECUTING→SETTLED/REJECTED/CANCELLED/**EXPIRED**/**INDETERMINATE**, occurrence registry with aliases, capacity-bounded store raising `ApprovalCapacityError` instead of evicting live approvals, terminal outcomes retained 900 s for duplicate-execution protection, indeterminate executions retained 7 days with idempotency keys as the only retry path after execution began (`_approval_lifecycle.py:93-119,186,195-222,781-789`; `_approval_state.py:106-110`).
- **Why it works:** Explicit statuses turn ambiguous crash moments (mid-execution interruption) into named states with defined recovery paths.
- **When to copy:** Server-side approval services, multi-replica deployments, anything with retries.
- **When overkill:** Single-user embedded runs — the rest of the sources operate fine with implicit pending/settled.

### P6. Fail-closed evaluation everywhere ambiguity arises

- **Problem:** Malformed input or uncertain state defaulting to "approved".
- **Demonstrated by:** agent-framework (non-bool `approved` coerced to `False` and checked with `is True`, `_types.py:1304-1313`, `_tools.py:1975-1978`; deny-by-default MCP sampling gate with rate limit, `_mcp.py:135-138,456-464`), openai-agents-sdk (callable `needs_approval` rules skipped → approval required — when arguments can't be parsed safely, `util/_approvals.py:18-29`, `run_internal/tool_execution.py:1306-1310`), langgraph (ambiguous singular resume with >1 pending interrupts raises `RuntimeError` loudly rather than misdirecting, `_loop.py:916-920`).
- **Contrast:** crewai fails **open** in places: empty feedback means approve/skip via `default_outcome` fallback (`flow/runtime/__init__.py:3618-3622`) — an accidental Enter counts as consent — and a crashing approval-gate hook lets the tool proceed unless it raises `HookAborted` (`hooks/tool_hooks.py:164-190`).
- **When to copy:** Always, for anything security-relevant.

### P7. Denial as synthetic observation fed back to the model

- **Problem:** Rejections ending runs abruptly or leaving the agent confused about why its tool didn't execute.
- **Demonstrated by:** crewai (blocked calls become the string "Tool execution blocked by hook…" returned to the LLM, `agents/crew_agent_executor.py:962-966`), openai-agents-sdk (rejection messages persisted since schema 1.6, replayed to the model with run-wide formatter fallback, `run_context.py:692-702`; `run_internal/approvals.py:24-43`), agent-framework (strict boolean semantics with rejected calls simply not executing; recorded-tool-disappeared case leaves the approved call unexecuted, `tests/core/test_harness_tool_approval.py:842`).
- **When to copy:** Agent-loop systems where the model should adapt after denial.

### P8. Refresh-survival via server-authoritative status derivation (UI pattern)

- **Problem:** Web clients losing approval state on reload.
- **Demonstrated by:** openhands: the frontend never stores "an approval is pending"; it projects polled/WebSocket `execution_status` plus REST-seeded event history into UI (`use-agent-state.ts:45-59`; `conversation-websocket-context.tsx:638-645`; `use-conversation-history.ts:53-54`), so refresh survival is free.
- **Complementary pattern from the engines:** auto-checkpoint before waiting — crewai snapshots state under `_ask_checkpoint` before any `ask()` (`flow/runtime/__init__.py:3343-3366`); agent-framework checkpoints capture pending request-info events (`_checkpoint.py:59-61`).

## Key Differences

**Where approval state lives.** langgraph makes approvals ordinary checkpoint writes (`__interrupt__`/`__resume__` reserved channels, `_constants.py:7-12`) — maximum reuse of existing machinery, but approval-specific concerns "have nowhere natural to live" (its own analysis). openai-agents-sdk keeps decisions in run-scoped context copied into every checkpoint, made portable through explicit JSON serialization. agent-framework uses a dedicated, cooperatively-shared session-state key. crewai gives Flows their own SQLite table. openhands alone holds nothing client-side. The divergence tracks product shape: engine-first projects (langgraph) generalize existing persistence; application frameworks (crewai) add purpose-built stores; thin clients (openhands) delegate entirely.

**Resume semantics: re-execute vs restore.** langgraph re-executes the whole node from its start on resume, replaying prior `interrupt()` answers positionally — side effects before the interrupt must be idempotent, a documented but user-enforced constraint (`types.py:862-868`). openai-agents-sdk, agent-framework, and crewai restore snapshotted state instead, avoiding re-execution but requiring far richer serialization (resume contexts, invocation ledgers, hidden batch siblings). This is the deepest architectural fork in the study: replay-resume keeps the engine tiny and the checkpointer simple; snapshot-resume protects side effects at the cost of elaborate restore logic and versioned formats.

**Scope granularity.** openai-agents-sdk and agent-framework offer the richest model: per-call decisions plus sticky decisions bound to fingerprinted identities, with explicit anti-widening rules. langgraph scopes per-interrupt-id and per-task but offers no standing approvals at all — every interrupt re-prompts. openhands fixes scope whole-conversation at creation time with no mid-conversation change. crewai scopes hooks statically by tool-name/agent-role filter lists. Notably, none offers role-based approver constraints or wildcard session-wide grants except agent-framework/openai-agents-sdk's sticky-per-tool — there is no "approve all tools" anywhere, which several reports characterize as conservative by design.

**Timeout philosophy.** agent-framework is internally split: core/session approvals wait indefinitely, while its AG-UI transport expires pendings after a configurable 24 h window and forwards client-facing `expiresAt` hints (`_approval_lifecycle.py:669-741`; `_run_common.py:347-349`). crewai times out only interactive `Flow.ask()` — best-effort, leaking the provider thread on expiry (`flow/runtime/__init__.py:3452-3470`). langgraph, openai-agents-sdk, and openhands have no approval timeout at all (each report documents exhaustive searches confirming absence). The divergence reflects deployment target: long-lived durable HITL workflows treat indefinite validity as a feature; hosted transports with bounded memory treat it as a capacity leak.

**Audit posture.** Three gradations emerge. Structural-durable: langgraph's every request/answer lands in `checkpoint_writes` rows and checkpoints carry timestamps/step/run metadata, making reconstruction possible though not forensic (no actor identity, no per-write timestamp). Log/history-based: agent-framework retains unresolved controls in history and emits structured AG-UI transition logs without payloads. Event-bus-only: crewai emits typed lifecycle events (`HumanFeedbackRequestedEvent` etc.) with optional platform `request_id` never populated in OSS, plus in-memory histories that vanish at exit. None-default: openai-agents-sdk (tracing has zero approval spans) and openhands frontend.

## Tradeoffs

**Durability-by-construction vs. ergonomics.** langgraph mandates a checkpointer for any interrupt (`RuntimeError` otherwise, `pregel/_loop.py:905-908`) — heavier setup for trivial flows, guaranteed refresh-survival. openai-agents-sdk inverts this: zero built-in storage, hosts persist `RunState` themselves, keeping the SDK storage-agnostic but delegating retention, expiry, and multi-process coordination to every integrator (`run_state.py:1704-1846`).

**Opt-in durability's silent failure.** agent-framework's convenient defaults (in-memory sessions, in-memory checkpoint storage, process-local AG-UI store at `ag-ui/_approval_state.py:38-76`) trade durability for zero setup, failing silently — state is simply gone after restart. crewai has the mirror-image hazard: its `FlowPersistence.save_pending_feedback` default just calls `save_state`, dropping the resume context, so a custom backend that forgets the overrides yields flows that pause forever (`persistence/base.py:87-88`; `from_pending` raises `ValueError`).

**Sticky approvals: UX vs oversight.** openai-agents-sdk's `always_approve` silences all future prompts for that tool identity with no revocation API short of abandoning the run context; combined with no audit log, misuse would be invisible to the SDK. agent-framework mitigates with hosted-boundary matching and warnings on name-based auto-approval, but shares the pattern.

**LLM-mediated consent.** crewai maps arbitrary free-text feedback onto declared outcomes via a configured LLM (`flow/runtime/__init__.py:3606-3650`) — conversationally flexible but introduces misrouting risk precisely where intent fidelity matters most. Every other source uses structured binary or enum decisions.

**Generality vs. enforcement.** langgraph's `interrupt(Any)` keeps the core schema-free, pushing the accept/edit/respond vocabulary into an advisory prebuilt package — even with it, response-type allow-listing is not validated server-side in OSS. openai-agents-sdk pays the opposite cost: much of `run_context.py` exists solely to decide which record governs a given call across bare/namespaced/deferred/hosted aliases (`run_context.py:1108-1235`), a maintenance price paid for isolation guarantees.

**Protocol duplication within one codebase.** agent-framework's five surfaces (core content protocol, workflow `request_info`, AG-UI lifecycle, DevUI tracking dicts, Foundry stores) each re-implement parts of correlation — centralized within packages, but raising cross-surface consistency cost, mitigated by heavy cross-surface tests. .NET mirrors Python semantics nearly 1:1 (`ToolApprovalState.cs:13-64`), trading duplication for cross-ecosystem consistency.

**Coarse policy vs friction.** openhands' `AlwaysConfirm` maximizes safety but forces a round-trip per action; `NeverConfirm` (the default, `services/settings.ts:13`) removes all friction and all protection, with no per-tool middle ground in the surface studied.

## Decision Guide

Choose your durability substrate by where your approvals must survive:

- **Must survive process restarts and arbitrary disconnects, minimal new infrastructure:** langgraph's model — if you already run a checkpointer, approvals inherit durability, deterministic addressing, and time-travel handling without any approval-specific store.
- **Must be portable across hosts/queues/databases you don't control:** openai-agents-sdk's approach — serialize the entire paused run as versioned JSON and let the application own storage. Accept the operational burden consciously.
- **Multi-surface product (CLI + workflow + hosted transport):** agent-framework's layering — define one wire protocol (typed request/response content), keep a single session-state source of truth, and add transport-specific lifecycle engines only where the transport demands them.
- **Web product with a capable backend:** openhands' split — server owns state, client derives UI. Do not replicate its memory-only dedup; pair it with server-side idempotency.
- **Desktop/interactive tooling:** ephemeral blocking prompts (crewai tasks/hooks style) remain acceptable — but hide them behind a provider interface (as crewai's `HumanFeedbackProvider` does) so embedding contexts can substitute durable transports.

For scoping: start per-call only (langgraph's implicit model); add sticky "always approve" only with (a) identity fingerprints including server/boundary labels (P2), (b) anti-widening representation rules (`None` vs `{}` distinction), and (c) a revocation API — the last missing in both sources that implement stickiness.

For timeouts: if approvals gate irreversible actions in hosted/multi-user settings, adopt explicit retention windows like AG-UI's (default 24 h pending, short post-terminal dedup retention, extended indeterminate window) rather than the indefinite-wait default shared by four of five sources.

For audit: plan a dedicated decision sink from day one. No source demonstrates one; retrofitting identity/timestamps onto generic checkpoint rows (langgraph's noted gap) or run-scoped records (openai-agents-sdk's noted gap) is exactly the work these frameworks deferred.

## Practical Tips

- **Freeze the request at surface time.** Snapshot exactly what the human saw (tool, arguments, server origin) before asking; validate inbound decisions against the snapshot; consume once. All three top-rated sources do this.
- **Make ambiguity loud.** Reject forged/stale responses with warnings (agent-framework), raise on ambiguous multi-interrupt resumes (langgraph), demand unique identities for duplicate pending approvals (openai-agents-sdk `UserError`).
- **Derive IDs from content, not counters,** when approvals cross process boundaries — xxh3-of-namespace (langgraph) or semantic fingerprints (openai-agents-sdk) stay valid across restarts.
- **Version your serialized approval state** and pin historical fixtures (openai-agents-sdk's corpus covers versions back through 1.x). Use schema bumps to tighten safety over time, as openai-agents-sdk did when current-schema restores stopped reconstructing sticky bindings from interruption items.
- **Handle the interrupted-mid-execution case explicitly.** Name it (AG-UI's `INDETERMINATE`), retain it longer than normal terminals, and require idempotency keys to retry after execution began.
- **Persist enough to rebuild the world, not just the question.** crewai's `PendingFeedbackContext` carries flow state, method output, emit outcomes, default outcome, LLM config (minus API keys), and the outer execution UUID for trace continuity — the reason `from_pending` works in a fresh process.
- **In web UIs, project server status; never own approval truth client-side** — but add a persistent submission guard and rely on documented server idempotency (openhands shows the gap: its in-memory submitted-id set resets on reload).
- **Feed denials back to the model** as synthetic observations with persisted messages, so agents adapt instead of thrashing.
- **Test the hostile paths directly:** forged responses, recycled call ids, schema downgrades, malformed serialized payloads, concurrent pauses, and expired-authority claims. The two 8/10 sources distinguish themselves largely by this test depth (`tests/ag_ui/test_approval_lifecycle.py`, `tests/test_run_state_compatibility_corpus.py`, `tests/core/test_harness_tool_approval.py`).

## Anti-Patterns / Caution Signs

- **Empty-input-means-consent.** crewai normalizes whitespace-only feedback to approve/skip via `default_outcome` fallback — an accidental Enter counts as consent (`flow/runtime/__init__.py:3618-3622`). Never map silence to approval.
- **Fail-open approval hooks.** crewai's dispatch swallows handler exceptions by verbosity; a crashing gate lets the tool proceed (`tool_hooks.py:164-190`). Gates must fail closed.
- **One-pending-slot overwrite.** crewai's `pending_feedback.flow_uuid` UNIQUE + `INSERT OR REPLACE` silently replaces an earlier pause with a newer one — no outstanding-approvals queue (`sqlite.py:100,229-244`).
- **Concurrency-unguarded resume.** Nothing prevents two processes calling `crewai Flow.from_pending` concurrently and double-executing the resumed leg; docs merely advise idempotent handlers. openai-agents-sdk similarly notes branches resumed from one snapshot make independent decisions.
- **Advisory-only authorization.** langgraph's `allow_accept/edit/respond/ignore` flags describe UI affordances but nothing validates the returned `HumanResponse.type` server-side in OSS.
- **Memory-only dedup guards.** openhands' submitted-event set resets on refresh, reopening double-submission exactly around reloads — the moment users retry.
- **Zombie-approval indicators.** openhands classifies waiting as "active" with a green ✅ dot, making abandoned approvals indistinguishable from success in lists; no staleness marker exists. Combined with universal no-TTL defaults, stale approvals can be honored arbitrarily late everywhere except AG-UI.
- **Silent persistence degradation.** Default implementations that quietly drop resume context (crewai) or process-local stores documented as non-durable (AG-UI's own docstring) turn misconfiguration into unrecoverable pauses discovered only in production.
- **Foregone signal.** openhands defines a rejection `reason` field but never populates it from the UI — wasted audit/steering signal at zero protocol cost to fix.
- **Fragmented HITL APIs.** crewai's three coexisting mechanisms (console/hooks/flows) with divergent durability and audit properties confuse integrators about which guarantee applies. Consolidate on the durable plumbing early.
- **Caution signs your approval design is brittle:** approval state living only in UI/component memory; "approve all" without identity fingerprints; resume paths lacking idempotency contracts; no named state for crash-interrupted executions; auditability depending on host-side logging nobody mandated.

## Notable Absences

Consistent across sources — treat as open industry gaps, not source-specific flaws:

- **No pending-approval TTL/expiry** in langgraph (exhaustive search found only node/cache/store TTLs, none applying to checkpoint writes), openai-agents-sdk, openhands, or agent-framework core; only AG-UI's transport-layer retention windows exist. crewai's persisted rows carry `created_at` but no reaper.
- **No approver identity, timestamp, or reason captured with the decision** anywhere: langgraph's resume writes carry no principal; openai-agents-sdk's `_ApprovalRecord` has no actor fields; crewai's metadata is free-form; openhands defers wholly to the server.
- **No durable, queryable decision ledger** in any source — auditing is at best reconstruction from checkpoints/history/events.
- **No revocation API for sticky/standing approvals** in either implementing source.
- **No "approve all"/policy-based batching primitives** beyond agent-framework's queued prompts with retroactive standing rules; langgraph's future-work list explicitly notes teams hand-roll batching today.
- **No server-side validation of declared response affordances** (langgraph OSS; whether closed-source LangGraph Server enforces is unverifiable).
- **Unverifiable server halves:** openhands' server persistence/idempotency and Foundry's server-side retention sit outside the analyzed trees — the reports say so explicitly rather than guessing.
