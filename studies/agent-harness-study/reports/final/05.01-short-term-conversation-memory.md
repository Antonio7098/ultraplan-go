## Executive Summary

Across seven harnesses, short-term conversation memory has converged on a common skeleton: an append-mostly transcript store, a per-call selection step that projects a "view" of that store for the model, and tool-call call/result pairing treated as a correctness invariant rather than an optimization. What the model sees is, by default in six of seven sources, *everything* stored for the conversation — windowing, summarization, and retrieval are opt-in everywhere they exist at all.

The sources diverge on three axes: **who owns storage** (framework-managed pluggable stores in agent-framework/langgraph/openai-agents-sdk; a durable server product in letta and openhands' backend; the caller in pydantic-ai; nobody across invocations in crewai), **when overflow is handled** (proactive token thresholds in letta and .NET agent-framework vs reactive provider-error recovery in crewai vs "mechanics only, no policy" in langgraph/pydantic-ai/openai-agents-sdk defaults), and **whether compaction destroys or preserves history** (destructive summary replacement in crewai and openai-agents-sdk's decorator vs non-destructive projection via annotations/tombstones/pointers in agent-framework, langgraph, and letta).

Maturity tracks failure engineering more than feature count: the highest-rated sources (langgraph 9, openai-agents-sdk 9, pydantic-ai 9) are distinguished by rollback discipline, corruption tolerance, conformance tests, and cache-aware repair — not by shipping the fanciest summarizer. The weakest-rated source (openhands 6) is not poorly built but structurally unable to answer this dimension's core question because model-visible selection lives outside its repo boundary.

## Core Thesis

Short-term memory design is converging on a **storage/view split**: history accumulates durably and mostly append-only, while what the model sees per call is a separately controlled projection (pointer, tombstone-filtered state, annotation-based inclusion set, callback-shaped input, or server condenser View). Given that split, the decisive quality signals are:

1. **Tool-call atomicity under reduction** — every source that implements trimming protects assistant-call/tool-result grouping; those that don't guarantee it expose runtime failures far from the edit site (langgraph's `INVALID_CHAT_HISTORY`, `libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py:243-271`).
2. **Non-destructive exclusion beats destructive replacement** — keeping originals and projecting inclusion (agent-framework annotations, letta pointer rewrites, langgraph tombstones) makes eviction reversible-by-query, whereas whole-history replacement (crewai's `summarize_messages`) permanently destroys pairing and detail.
3. **Cache-prefix stability is becoming a first-class constraint** — repair passes are made deterministic and idempotent so they never churn provider prompt caches (pydantic-ai `_agent_graph.py:2844-2846`; letta skips system refreshes around compaction, `letta_agent_v3.py:966-967`; crewai stamps cache breakpoints on stable prefixes).
4. **Overflow policy is the unfinished work** — no source ships safe-by-default token budgeting; every source requires opting into protection, which means naive users get unbounded prompt growth until a provider rejects the request.

## Approach Models

Clustering the seven sources by how they answer the dimension's questions yields four approach models:

### Model A — Framework-managed pluggable store with lifecycle hooks
**Sources:** agent-framework, langgraph, openai-agents-sdk.

The framework owns a keyed store behind an explicit contract — Python `HistoryProvider.get_messages/save_messages` (`_sessions.py:967-1000`), .NET `ChatHistoryProvider` (`ChatHistoryProvider.cs:51-77`), LangGraph's `BaseCheckpointSaver` over channel state (`base/__init__.py:227-415`), or the `Session` protocol's four operations (`src/agents/memory/session.py:15-56`). Loading happens before the run and persistence after it; backends range from in-memory to SQLite/Postgres/Redis/Mongo. Selection policy defaults to full replay; shaping hooks exist at defined seams (compaction strategies, `pre_model_hook`, session input callbacks). This model maximizes operational durability and testability; its cost is that memory policy must still be configured by users, and the framework carries the maintenance burden of many backends.

### Model B — Durable server-side store with pointer/window management
**Sources:** letta; openhands' server (consumed via contract by the studied frontend).

Memory is a database-backed product surface: all messages persist immutably (letta `messages` table with `sequence_id` ordering, `letta/orm/message.py:23-96`), and the in-context window is a separate mutable pointer — ordered message IDs (`letta/schemas/agent.py:78`) or `conversation_messages` rows with position/in-context flags (`conversation_manager.py:613-650`). Eviction rewrites the pointer and never deletes rows. Compaction is a managed subsystem with layered triggers (proactive 90% threshold at `letta/constants.py:82-83`, reactive retry on `ContextWindowExceededError`, manual API) and machine-readable outcomes (`compaction_stats`). Openhands mirrors the same shape from the client side: the server owns a `CondensationEvent` contract (`forgotten_event_ids`, `summary`, `summary_offset`) and the client triggers and verifies but never computes condensation (`use-await-context-compaction.ts:57-163`). This model buys observability, auditability, and ops APIs at the cost of running a real storage service.

### Model C — Caller-owned transcript, stateless core
**Source:** pydantic-ai (with crewai as an ephemeral variant).

The library holds no session store: history is an explicit typed list (`ModelMessage = ModelRequest | ModelResponse`, `messages.py:2764`) handed in via `message_history` and returned to the caller for persistence (`docs/message-history.md:406`). Reduction happens through user-supplied `ProcessHistory` processors that replace run-state history, provider-native compaction surfaced as typed `CompactionPart` visibility boundaries, and a wire-validity cleanup pass that drops orphaned results and synthesizes returns for dangling calls (`_agent_graph.py:2960-2986`). CrewAI applies the same philosophy within a narrower scope: one task execution owns an in-process list cleared at each invocation (`experimental/agent_executor.py:2831-2854`), with continuity between tasks achieved by injecting prior outputs into the next task's prompt text (`formatter.py:16-45`). This model buys transparency and composability; the cost is that durability, scoping, and budgeting are entirely the application's problem.

### Model D — Execution-scoped scratchpad with reactive recovery (variant of C)
**Source:** crewai (distinct enough to call out).

CrewAI deliberately defines "a conversation" as one agent-task tool loop. Nothing survives the execution except sanitized snapshots exposed for debugging (`agent/utils.py:247-283`) and textual composition into subsequent tasks. Overflow handling is purely reactive: when the provider raises a context-length error and `respect_context_window=True`, the entire non-system history is chunk-summarized and replaced (`agent_utils.py:1048-1131`). This is the simplest model in the study and the only one where cross-task continuity is prompt-textual rather than message-list-based.

## Pattern Catalog

### P1. Full-replay default with opt-in reduction

- **Problem:** How much history does each model call need?
- **Who demonstrates it:** All seven. agent-framework sends `session_context.get_messages(include_input=True)` in full (`_agents.py:1516-1517`); crewai passes `list(self.state.messages)` whole each iteration (`experimental/agent_executor.py:1429-1439`); langgraph prepends the prompt to the entire `state["messages"]` (`chat_agent_executor.py:137-170`); letta hydrates exactly the pointer contents (`helpers.py:206-220`); openai-agents-sdk fetches unbounded history unless `SessionSettings.limit` resolves a cap (`session_persistence.py:350-383`); pydantic-ai sends everything in `message_history` (`_agent_graph.py:1466-1499`); openhands' architecture implies full log plus condenser view.
- **Why it works:** Maximum fidelity, trivially correct tool pairing, and stable prefixes that provider prompt caches reward. Reduction introduces information loss and pairing hazards, so making it opt-in avoids harming the common case.
- **When to copy:** Almost always as the default; it is the industry consensus point.
- **When risky:** Long-running sessions and fat tool outputs grow prompts until hard provider rejection. Every source flags this; none solves it by default (e.g., langgraph withholds a rubric point precisely for this, `chat_agent_executor.py` rationale; agent-framework lists it first among why-not-10 reasons).
- **Evidence:** Ratings rationales in all seven source reports.

### P2. Storage/view separation ("kept" ≠ "shown")

- **Problem:** Trimming must not destroy auditability or make eviction irreversible.
- **Who demonstrates it:** langgraph's dual-view — `pre_model_hook` may return `llm_input_messages` shown to the model while canonical `messages` stay intact (`chat_agent_executor.py:395-425`); letta's pointer rewrite over an immutable table; agent-framework's annotation-based projection where exclusions live in message metadata and originals survive in storage (`_compaction.py:27-37,736-737`); openai-agents-sdk's two view-shaping hooks (`session_input_callback`, `call_model_input_filter`) over an append-only store (`run_config.py:431-446`); pydantic-ai's processors replacing run-state while callers retain their own copy; openhands' raw `events` vs render-ready `uiEvents` arrays (`use-event-store.ts:55-129`).
- **Why it works:** Exclusion becomes a per-run decision re-evaluated each time, summaries can be superseded, and debugging can always recover what was dropped.
- **When to copy:** Anywhere history outlives a single run or must be auditable.
- **When risky/overkill:** For ephemeral single-execution scratchpads (crewai's choice), a second view layer is unnecessary machinery.
- **Evidence:** As cited above; also letta's `list_messages` exposes evicted-but-persisted history filtered only by soft-delete (`message_manager.py:895-955`).

### P3. Tool-call atomicity as a reduction invariant

- **Problem:** Naive trimming splits assistant tool-call declarations from their results; providers reject the result, and semantics break silently otherwise.
- **Who demonstrates it:** agent-framework merges reasoning prefixes, function calls, and following tool messages into atomic spans, linking non-contiguous pairs by `call_id` union-find (`_compaction.py:200-325,105-198`); letta snaps compaction cutoffs backward to assistant/approval-with-tool-calls boundaries and grows eviction in 10% steps until valid (`summarizer_sliding_window.py:144-198`); langgraph raises `INVALID_CHAT_HISTORY` on orphaned calls and requires tools returning `Command` to include matching `ToolMessage`s (`chat_agent_executor.py:243-271`; `tool_node.py:1545-1578`); pydantic-ai drops orphaned results and synthesizes `'interrupted'` returns for dangling calls (`_agent_graph.py:2771-2898`); openai-agents-sdk drops orphan calls before replay, strips dangling reasoning items, and defers compaction while local tool outputs remain unpersisted (`items.py:171-304`; `session_persistence.py:656-673`); crewai preserves pairing throughout the loop and knowingly destroys it only when whole-history summarization collapses everything into one summary message (`agent_utils.py:1123-1131`); openhands retains `tool_calls`/`tool_call_id` in its wire contract but cannot verify survival through server condensation.
- **Why it works:** Pairing integrity is a provider-level requirement; enforcing it at the memory layer prevents an entire class of hard-to-debug request rejections.
- **When to copy:** Universally — this is the strongest convergence in the study.
- **Failure mode if ignored:** crewai's post-summary transcripts would be rejected by providers strictly validating consecutive tool chains (noted in its report); langgraph turns violations into loud runtime errors instead.

### P4. Non-destructive exclusion over destructive replacement

- **Problem:** Summarize-and-replace loses detail permanently and can brick follow-up turns.
- **Who demonstrates it:** letta (pointer rewriting; "nothing is deleted"), agent-framework (annotations + `project_included_messages`), langgraph (`RemoveMessage` tombstones flow through the same merge path as messages, so deletions are checkpointed and replayable, `message.py:221-234`).
- **Contrast:** crewai replaces all non-system history with merged prose (`agent_utils.py:1074-1131`); openai-agents-sdk's compaction decorator clears and re-adds underlying storage, mitigated by transactional restore-on-failure (`openai_responses_compaction_session.py:271-337`); letta's older partial-evict mode likewise inserts recursive summaries but keeps them as persisted `summary`-role messages.
- **Why non-destruction wins:** Evicted content remains queryable (letta), summaries carry bidirectional trace links (`_summary_of_message_ids`/`_summarized_by_summary_id`, `_compaction.py:35-37`), and fork/time-travel features depend on intact timelines (langgraph forks branch from checkpoints).
- **When destructive replacement is acceptable:** Single-execution loops that restart from a clean turn anyway (crewai's stance), or when a vendor endpoint owns the compacted representation (openai-agents-sdk delegating to `responses.compact`).

### P5. Layered trigger policies: proactive + reactive + manual

- **Problem:** When should compaction fire?
- **Who demonstrates it:** letta most completely — proactive post-step check against 90% of the context window using provider-reported usage (`letta_agent_v3.py:1438-1505,1306-1307`), reactive compact-and-retry bounded by `max_summarizer_retries` on `ContextWindowExceededError` (`1218-1294`), and manual API endpoints (`conversations.py:1029-1058`). agent-framework's .NET `ContextWindowCompactionStrategy` derives budgets as `maxContextWindowTokens − maxOutputTokens` with staged thresholds (tool eviction at 50%, truncation at 80%) — the study's only quantitative budget formula (`ContextWindowCompactionStrategy.cs:13-44`). openai-agents-sdk triggers decorator compaction after ≥10 candidate items accumulate (`openai_responses_compaction_session.py:28-60`). crewai has only the reactive leg (`agent_utils.py:781-832`); openhands adds a manual UI action with verification.
- **Why it works:** Each leg covers the others' blind spots: proactive checks avoid wasted requests; reactive legs catch estimate drift; manual controls give operators an escape hatch.
- **When to copy:** Any service-grade harness. Reactive-only (crewai) costs one failed provider round-trip per overflow event and depends on string-matching error signatures (`context_window_exceeding_exception.py:6-9`).

### P6. Fingerprint/idempotence discipline for persistence

- **Problem:** Streaming saves, retries, replays, and reconnects must not duplicate or lose items.
- **Who demonstrates it:** openai-agents-sdk pops only an exact fingerprint-matched tail suffix on retry rewind and restores popped items on any mismatch (`session_persistence.py:978-1065`), counts persisted items so streaming saves are exactly-once (`563-583`), and dedupes inputs preferring latest by `call_id`/item-id (`items.py:681-800`). pydantic-ai makes repair passes deterministic and idempotent specifically to avoid churning prompt-cache prefixes and guards `run_id` reuse with `UserError` (`_agent_graph.py:2644-295,2844-2846`). agent-framework's `filter_new_messages` aligns replays via message-id then role+content hash without superlinear growth (`_sessions.py:191-244`). openhands dedupes all ingest channels on an event-id `Set` (`use-event-store.ts:55-129`).
- **Why it works:** Memory integrity under partial failure is what separates mature harnesses from fragile ones; fingerprints turn "what belongs to this attempt" into a decidable question.
- **When to copy:** Everywhere multi-attempt execution exists (retries, streaming, resume, reconnects).

### P7. Cache-aware memory shaping

- **Problem:** Compaction and role conversion can invalidate provider prompt caches mid-conversation.
- **Who demonstrates it:** pydantic-ai hoists standing system prompts only from leading positions of the first request and documents the cache rationale (`models/__init__.py:2052-2069`); regression-tested by `tests/test_cache_prefix_stability.py`. crewai stamps cache breakpoints on stable system/user prefixes and content-matches them after adapter rewrites (`llms/cache.py:24-32`; anthropic adapter `758-797`). openai-agents-sdk derives `prompt_cache_key` partly from the session id so repeated prefixes group (`run_grouping.py:12-52`). letta preserves prefixes by skipping system-message refreshes except around compaction and offers `self_compact_*` modes so the agent's own model produces cache-friendly summaries (`letta_agent_v3.py:966-967,1461`).
- **Why it works:** Prompt caches price repeated prefixes dramatically lower; memory operations that preserve prefix stability convert directly into cost savings.
- **When to copy:** Anywhere per-turn cost matters and the provider supports caching.
- **Caution:** Cache incentives can conflict with aggressive trimming; letta's "sharp context discontinuity at the eviction cliff" tradeoff is the visible cost.

### P8. Verify-after-mutation for compaction

- **Problem:** Compaction can fail partially, silently, or racily; trusting the trigger acknowledgment hides damage.
- **Who demonstrates it:** openhands refuses to trust the HTTP ack — completion requires a fresh `Condensation` event plus a measured `per_turn_token` drop, else reports timeout as failure, with baseline ids captured pre-request to win races (`use-await-context-compaction.ts:39-163`; `use-compact-context-action.ts:83-99`). letta re-counts tokens including tools after compaction, falls back down a mode chain, and escalates to a typed error if the system prompt alone cannot fit (`compact.py:350-412`). agent-framework escalates summarizer failures after three consecutive misses and returns "no change" rather than crashing (`_compaction.py:1273-1284`). openai-agents-sdk restores prior history transactionally if replacement fails or is cancelled.
- **Why it works:** Compaction is the rare memory operation that both rewrites state and can fail nondeterministically (LLM summarizers); verification converts silent corruption into observable failure.
- **When to copy:** Whenever summarization or wholesale replacement occurs.

## Key Differences

**Ownership determines everything downstream.** agent-framework, langgraph, and openai-agents-sdk manage pluggable stores inside the process, which pushes them toward generic protocols and backend ecosystems (langgraph even ships a conformance suite classifying mandatory vs optional saver capabilities, `capabilities.py:15-63`). letta, as a service, invests instead in pointer machinery, permission-scoped actor checks on every manager call (`message_manager.py:351-376`), and REST-level compaction/fork APIs. pydantic-ai refuses ownership entirely and compensates by treating caller-supplied history as an attack surface (`sanitize_messages`, `messages.py:2953-3026`). crewai's execution scope means it needs neither.

**Proactivity of overflow handling spans the full spectrum.** letta fires compaction before the next turn at 90% usage; agent-framework (.NET) budgets quantitatively with staged thresholds; crewai waits for the provider to reject the request; langgraph, pydantic-ai, and openai-agents-sdk ship mechanics (tombstones/hooks/processors/callbacks/decorators) but no default policy. Notably, the two most mature ratings (langgraph 9, pydantic-ai 9) were awarded despite — not because of — overflow policy, showing raters weighted correctness engineering above feature completeness.

**Token accounting quality varies wildly.** letta trusts provider-reported `total_tokens` from the previous request as its pressure signal and reserves local counting for validation (`letta_agent_v3.py:1306-1307`; `compact.py:350-356`). agent-framework's Python ships a 4-chars/token heuristic with pluggable real-tokenizer interfaces (`_compaction.py:76-80`); its .NET derives budgets from declared context/output windows. crewai uses `len(text)//4` (`agent_utils.py:835-844`), acknowledged to underestimate CJK/code-heavy content. langgraph and openai-agents-sdk count nothing (the latter windows by item count, which "can still be arbitrarily large"). openhands exposes live token meters but leaves policy to the server.

**Mutability stances split cleanly.** letta removed message editing outright — the REST endpoint returns 405 — precisely because forked conversations share message objects (`agents.py:1627-1644`). openhands similarly offers fork/rebranch but no edit-in-place. langgraph embraces mutability through attributed edits (`update_state(as_node=...)`) while making time-travel replay fork-on-write so history stays an immutable audit trail (`_loop.py:952-971`). openai-agents-sdk allows tail editing via `pop_item` and full rewrite via clear+add. crewai and pydantic-ai treat the list as plain mutable data.

**Cross-task continuity models differ fundamentally.** Only crewai composes continuity textually (prior task outputs joined with dividers into the next prompt, `formatter.py:13-45`); everyone else carries actual message lists across turns within a scoped conversation. This is a direct consequence of crewai's crew-of-tasks product shape, not a quality deficit — though it forfeits verbatim recall between tasks.

**Scope keys are universal but shallow.** Every source scopes by some conversation/session/thread key (session UUIDs, `thread_id` + `checkpoint_ns`, caller-chosen `session_id`, agent → conversation layers, `conversationId`). None provides built-in user-level hierarchy: langgraph explicitly delegates tenant partitioning to app design (`README.md:31-43`), openai-agents-sdk suggests naming conventions like `"user_123"` (`docs/sessions/index.md:515-524`), letta layers org/actor checks but not automatic end-user partitioning, and agent-framework shows the intended pattern only in a .NET vector-store scope object (`ChatHistoryMemoryProviderScope.cs:35-52`).

## Tradeoffs

**Full-replay fidelity vs cost/overflow.** Benefit: perfect continuity, guaranteed pairing, cache-friendly stable prefixes. Cost: linear-to-quadratic growth in tokens sent; eventual provider rejection. Best-fit: interactive assistants with moderate session lengths. Failure mode: long autonomous runs hit the wall mid-task — precisely when recovery is hardest. Alternative: proactive budgeting (letta, agent-framework .NET) trades implementation complexity for bounded prompts; crewai accepts a wasted failed call per overflow as the price of zero up-front accounting.

**Non-destructive projection vs payload/storage overhead.** agent-framework persists group/token/exclusion annotations alongside messages, making compaction incremental and durable but inflating payloads and coupling storage format to framework internals (`_compaction.py:614`). letta pays a two-table consistency surface (messages + pointer). langgraph amortizes per-step snapshots with blob+manifest splitting (`memory/__init__.py:125-140`) but still pays write amplification every superstep. The alternative — crewai's in-place replacement — is cheap and simple but irreversible.

**Reactive vs proactive compaction.** Reactive (crewai) is provider-agnostic and requires no token estimation, but burns a failed request per overflow and hinges on brittle error-signature matching. Proactive (letta's 90% rule) prevents waste but suffers a first-turn blind spot when `context_token_estimate` starts as `None` (`letta_agent_v3.py:935-936`) and encodes model-specific knowledge that needs maintenance (`thresholds.py:33-40`).

**Immutable shared history vs debuggability.** letta's immutability protects fork integrity but removes in-place redaction of bad content; operators fall back to deletion managers or compaction. langgraph's editable-but-forking-on-replay middle path preserves both, at the cost of ambiguity rules (concurrent updates require `as_node` attribution, `main.py:1921-1929`).

**Provider-native storage format vs portability.** openai-agents-sdk persists Responses-format dicts verbatim, eliminating a translation layer and enabling server-side Conversations sessions — but binding stored history to one provider's item vocabulary. pydantic-ai's neutral typed parts keep histories portable across providers (cross-agent reuse documented at `docs/message-history.md:505-551`) at the cost of maintaining conversion in adapters (`models/__init__.py:690-783`).

**Rich view-shaping hooks vs intricate reconciliation.** openai-agents-sdk's `session_input_callback` lets users reorder/filter the model view freely, but the SDK must then reconstruct "which items are actually new" via deep copies, identity, and frequency maps (`session_persistence.py:394-451`) — powerful, documented as subtle. pydantic-ai's replace-semantics processors have the same profile, compensated by layered resumed-request detection with documented residual gaps (`_agent_graph.py:2651-2670`).

**Dual implementations vs velocity.** agent-framework maintains near-symmetric Python/.NET memory subsystems (~1.7k-line `_compaction.py` vs ~15-file .NET `Compaction/`), explicitly flagging drift risk as its reason for not scoring higher. crewai carries deprecated and experimental executors with duplicated message-lifecycle logic. Consolidation versus parallel-team velocity is a standing cost of both.

## Decision Guide

Choose based on product shape, matching each source's constraints to yours:

- **Building an agent platform/service where conversations are durable products** (multi-tenant, auditable, operator-managed): follow **letta**'s model — immutable message store, separate in-context pointer, layered triggers (proactive threshold + reactive retry + manual API), boundary-safe eviction, post-compaction verification, and fork-via-sharing instead of copying.
- **Building an orchestration engine whose users compose their own graphs/workflows**: follow **langgraph** — memory as reducible state, storage behind a conformance-tested protocol, editing/forking as first-class primitives, context-window policy deliberately pushed upward with clean extension points (`pre_model_hook` dual-view).
- **Building a library for sophisticated developers who want transparency**: follow **pydantic-ai** — explicit typed transcripts, caller-owned persistence, capability-hook reduction, wire-validity repair, and trust boundaries for externally supplied history.
- **Building a vendor SDK tied to specific provider APIs**: follow **openai-agents-sdk** — store provider-native items, delegate compaction to provider endpoints behind a decorator, invest heavily in fingerprint/idempotence/rollback discipline, and enforce single-ownership between local and server-managed history.
- **Building an enterprise framework, possibly polyglot**: follow **agent-framework** — small explicit provider contracts, symmetric stacks, conflict detection between local and service-owned history, governance gates (persistence deferral pending egress verdicts).
- **Building workflow crews where a "conversation" is legitimately one task**: crewai's scratchpad model is defensible — but adopt its documented future-work items (proactive budgeting, persistent chat threads) rather than its current limitations.
- **Building a frontend over someone else's agent server**: adopt openhands' client disciplines — anchor-and-dedupe sync, verify compaction outcomes by observed effect, fork-based correction — without expecting to control selection policy.

If forced to choose between proactive token-budgeted trimming and mechanical-but-unpolicyed primitives: the evidence favors shipping primitives with strong defaults documentation (langgraph/pydantic-ai posture) *only* for libraries; services should ship the budget (letta posture).

## Practical Tips

- **Separate the store from the view from day one.** Whether via pointers (letta), annotations (agent-framework), tombstones (langgraph), callbacks (openai-agents-sdk), or processors (pydantic-ai), every durable design in the study keeps "what happened" distinct from "what the model sees." Retrofitting this is painful; starting with it makes compaction, debugging, and forking tractable.
- **Make tool-call pairing a tested invariant, not a convention.** Copy agent-framework's union-find linking and occurrence-based pairing (reused `call_id`s across approval rounds), langgraph's pre-call validation, and letta's cutoff-snapping. Add a test that trims aggressively and asserts no orphaned results survive (agent-framework pins this: `test_compaction.py:346-380`).
- **Prefer exclusion-with-provenance to summarize-and-replace.** If you must summarize, keep trace links (agent-framework's `_summary_of_message_ids`), persist the summary as a queryable message (letta's `summary` role with `compaction_stats`), and expose what was forgotten (openhands' `forgotten_event_ids`).
- **Use provider-reported usage as your context-pressure signal**, with local counting reserved for post-compaction validation (letta's split). Avoid character heuristics in production paths; if unavoidable, document their skew (crewai's `len//4` underestimates CJK).
- **Design persistence for exactly-once under retries and streams.** Adopt openai-agents-sdk's trio: persisted-item counting, fingerprint-matched suffix rollback with restore-on-mismatch, and cancellation-draining mutations.
- **Protect prompt-cache prefixes in every memory operation.** Make repairs deterministic and idempotent (pydantic-ai), stamp cache breakpoints on stable prefixes (crewai), and avoid refreshing system text mid-conversation (letta).
- **Verify compaction by observed effect, not acknowledgment.** Wait for the artifact plus a measurable token drop (openhands), or re-count and fall back down a strategy chain (letta).
- **Treat client-supplied or externally supplied history as untrusted.** Sanitize roles, strip foreign system prompts and file URLs, and validate pairing before mixing with trusted history (pydantic-ai `sanitize_messages`).
- **Give operators a manual compaction lever** even when automation exists — every service-grade source ships one, and it doubles as the recovery tool when automated compaction misbehaves.

## Anti-Patterns / Caution Signs

- **Two generations of the same mechanism coexisting.** Letta's legacy count-based `Summarizer` beside the newer token-based `compact_messages` (its stated reason for missing 9-10); crewai's duplicated legacy/experimental executors. Sign of drift: divergent behavior between paths for the same operation.
- **Defaults inconsistency across layers.** crewai's `Agent.respect_context_window=True` default vs executor field default `False` changes failure semantics depending on construction path (`agent/core.py:251-254` vs `experimental/agent_executor.py:206`).
- **Item-count windows masquerading as token budgets.** openai-agents-sdk's `limit=N` bounds items, not size; a "windowed" session can still overflow arbitrarily.
- **Silent degradation of history.** Corrupt rows skipped without user-facing warning (openai-agents-sdk SQLite reads); cloud pagination falling back to empty pages with console-only warnings (openhands). History quietly shrinking is worse than failing loudly.
- **Brittle string matching against provider errors** as the only overflow trigger (crewai's keyword list) — provider error-copy changes break compaction invisibly.
- **Text-prefix matching for filtering machine-generated content** — openhands marks its own goal-loop filter "Brittle by design" and prescribes a persisted flag as the fix.
- **Destructive replacement without restore.** Whole-history summarization that strands providers requiring strict tool chains (crewai post-summary state); compaction replacements without transactional restore (contrast openai-agents-sdk, which restores).
- **Estimate-driven control with cold-start blind spots.** letta skipping the proactive check on the first turn because the estimate starts `None`.
- **Unbounded in-session growth in mirrors.** openhands' client event store appends for the session lifetime; even UI-layer memory needs caps for long autonomous runs.
- **Bounded idempotency scans.** Duplicate detection that only inspects the last N messages (letta scans 10) can miss older matches — history-as-ledger patterns must define their scan horizon honestly.

## Notable Absences

- **No built-in per-user hierarchy anywhere.** User → session/thread mapping is delegated to applications in all seven sources; only letta (org/actor checks) and agent-framework (.NET vector-store scope fields) show partial patterns.
- **No default-safe overflow protection.** Every source requires opting into windowing/summarization/budgeting; several raters explicitly withheld points for this (langgraph, openai-agents-sdk, agent-framework).
- **Summarization is absent from two of the three top-rated cores.** LangGraph contains no summarization node/util (verified by search in its report); pydantic-ai ships summarization only as doc prose and provider-native compaction. Both push it to external packages or provider endpoints.
- **No first-class introspection hook for "what did the model see"** in most sources. agent-framework lists adding one as future work; openhands is the counter-example (`MessageEvent.llm_message` is "the exact LLM message") and langgraph's `get_state_history` approximates it for state, not per-call views.
- **No background/scheduled compaction independent of the step loop** found in any source (letta explicitly searched and absent).
- **No TTL/retention/quota in core short-term memory** (openai-agents-sdk searched; TTL exists only in optional wrappers/extensions).
- **Semantic retrieval over short-term history is universally out of scope** — confirmed absent in openai-agents-sdk by directory inspection and positioned as long-term-memory territory elsewhere.
- **Cross-session recall is absent everywhere**; agent-framework's `origin_session_ids` attribution exists but its retrieval integrations live in separate packages.
