## Executive Summary

Ten systems — six LLM agent libraries, two platforms/servers, one policy engine, and one frontend — were studied for how they make failures visible to four stakeholders: the model (or its analog, the programmatic consumer), the user, the developer, and the operator. The headline finding is convergence: **every source independently implements failure visibility as a per-stakeholder fan-out rather than a single error channel**, and every agent harness converges on converting tool failures into model-visible data while reserving exceptions for callers. The differences are in rigor and placement, not in kind.

The maturity spread is narrow but meaningful. pydantic-ai (9/10) is the only source that proves the exact bytes the model receives with wire-format tests (`tests/test_tool_failed_wire.py:291-316`) and mandates that telemetry render failures identically to the conversation (`pydantic_ai_slim/pydantic_ai/messages.py:1676-1697`). temporal (8/10) is the strongest operator story — masked errors joined to server logs by an 8-hex hash (`common/rpc/interceptor/mask_internal_error.go:80-111`), escalation ladders, and doc-synced runbook log lines (`service/history/queues/executable.go:603-618`, `docs/admin/dlq.md:28-60`). openhands (7/10) shows what visibility looks like when your only channel is UX: sticky-vs-transient error lifetimes and recovery affordances replace logs entirely.

Three systemic weaknesses recur across nearly all sources. First, **the operator tier is emission-rich but dashboard-poor**: temporal ships an empty Grafana provisioning directory (`develop/docker-compose/grafana/provisioning/dashboards/dashboard.yml:1-13`), letta defines ~20 failure-shaped metrics with no boards (`letta/otel/metric_registry.py:94-494`), and no source ships alert rules. Second, **masking policies leak at seams**: letta masks REST 500s but ships raw `str(exc)` over SSE (`letta/server/rest_api/app.py:469` vs `streaming_response.py:369`); langfuse masks via tRPC but returns raw `error.message` from REST fallbacks (`web/src/server/api/trpc.ts:194-212` vs `web/src/features/public-api/server/withMiddlewares.ts:196-202`). Third, **streaming paths are the least reliable failure surfaces** across sources: langgraph's message mode drops LLM errors silently (`libs/langgraph/langgraph/pregel/_messages.py:181-189`), agent-framework's DevUI stream has a literal "Could yield error event here" comment instead of an event (`python/packages/devui/agent_framework_devui/_executor.py:255-256`), and openai-agents-sdk has no error variant in its stream-event union (`src/agents/stream_events.py:51-61`).

## Core Thesis

Failure visibility matures not by adding more logging, but by making three structural commitments that the highest-scoring sources share:

1. **Failures cross trust boundaries as data, exceptions stay within them.** pydantic-ai encodes everything the model should react to as serializable message parts (`RetryPromptPart`, failed `ToolReturnPart` — `messages.py:1637-1674`); temporal makes `failurepb.Failure` the canonical currency that simultaneously drives retries, persists as history, and answers queries (`common/failure/failure.go:14-91`); langgraph checkpoints `(ERROR, exception)` writes so any past failure is replayable from state history (`libs/langgraph/langgraph/pregel/_runner.py:574-603`, tested at `tests/test_pregel.py:5372-5432`). Systems that instead rely on ad-hoc strings at boundaries lose structure exactly where consumers change.
2. **One rendering, many audiences — enforced at one choke point per boundary.** Whether it is pydantic-ai's canonical `RetryPromptPart.from_error()`, langfuse's single `BaseError` hierarchy rendered by three auditable middlewares (`web/src/server/api/trpc.ts:141-149`), or opa's one envelope conversion per surface (`v1/server/writer/writer.go:27-55`), the durable designs make detail-level policy *auditable in a handful of places*. Every source with an inconsistent masking story got that way by letting a second path improvise.
3. **Detail exposure is an explicit, configurable decision per audience — never an accident of code path.** crewai resolves an ignore/warn/raise policy through a strict precedence chain (`lib/crewai/src/crewai/tools/tool_failure.py:177-208`); langgraph accepts bool/string/callable/type-tuple strategies for `handle_tool_errors` (`libs/prebuilt/langgraph/prebuilt/tool_node.py:383-391`); temporal scopes masking to namespaces via dynamic config (`common/dynamicconfig/constants.go:874-878`). Where this knob is missing or broken — letta's dead `LogSettings.log_level` (`letta/settings.py:527`), openhands' hard-coded verbosity constants — it is flagged in the source reports as a trust-eroding defect.

The corollary: **redaction and visibility are not opposites; they are two renderings of one event plus a correlation token.** temporal joins masked responses to full server-side forensics via a shared hash; letta embeds `trace_id` in error bodies; langfuse hands users a Sentry Error ID. The best systems do not choose between secrecy and debuggability — they make the two joinable.

## Approach Models

Each source's model for this dimension, in its own vocabulary:

- **pydantic-ai — failures-as-messages.** Anything the model must react to becomes a message-history part (`RetryPromptPart`, `ToolReturnPart(outcome='failed')`) that survives serialization, replay, UI transmission, and provider round-trips; `ModelRetry` vs `ToolFailed` makes retryable-versus-terminal an explicit author choice with separate budget semantics (`pydantic_ai_slim/pydantic_ai/exceptions.py:57-147`). Telemetry is required to reproduce the canonical conversation text (`messages.py:1684-1687`).
- **temporal — failures-as-protocol-data with layered sanitization.** The `failurepb.Failure` graph drives retry computation (`common/retrypolicy/retry_policy.go:27-62`), persists as durable history (`workflow_task_state_machine.go:889-970`), and is truncated in priority order under size pressure (`common/failure/failure.go:48-91`). Users get masked messages + hash; developers get classified logs; operators get a two-tier metric taxonomy separating unexpected errors from all errors (`common/metrics/metric_defs.go:657-665`).
- **langgraph — multi-surface fan-out with durable failure records.** One task exception fans to: error `ToolMessage`s for the model, laundered tracebacks for callers, checkpointed `__error__` writes for post-mortems, and lifecycle/observer events for the server (`_retry.py:87-125`). Control-flow interrupts ride a separate exception lineage exempt from every error surface (`errors.py:50-133`).
- **letta — four separated channels with a single dispatch registry.** Bounded dual-field tool results to the model (`func_return` capped at 1000 chars, `stderr` keeps the traceback — `tool_execution_manager.py:131-155`); ~30-entry typed exception→HTTP map in one file (`app.py:534-611`); JSON logs with Datadog/OTEL correlation; a readiness state machine with reference-counted degradation (`readiness_state.py:39-84`).
- **crewai — declarative failures with policy-resolved severity.** Only an explicit `ToolFailure` return marks a soft failure (string-sniffing rejected after a Slack false-negative incident, `tools/tool_failure.py:1-11`); an ignore/warn/raise policy resolves tool→task→agent→crew, and the central event bus isolates handler crashes so observability cannot break execution (`events/event_bus.py:401-456`).
- **agent-framework — sanitize-by-default with opt-in depth, mirrored across languages.** Model sees `"Error: Function failed."` unless `include_detailed_errors=True` (`_tools.py:1412-1434`); workflows emit structured `WorkflowErrorDetails` events before re-raising in a guaranteed order (`_workflows/_workflow.py:601-623`); .NET reproduces the same policy (`AgentSkillsProviderOptions.cs:23-33`).
- **openai-agents-sdk — redaction-aware rendering per surface.** One failure renders as full caller text, message-only log lines behind secure-by-default flags (`_debug.py:12-28`), or fixed placeholders in traces (`util/_error_tracing.py:46-53`) — with traceback detachment and exception-graph scrubbing ensuring redacted errors cannot leak through `__context__` or frame locals (`src/agents/exceptions.py:140-215`).
- **opa — machine-readable envelopes end-to-end.** Typed engine errors carry source locations (`v1/topdown/errors.go:29-34`); each boundary converts once (HTTP `ErrorV1`, CLI `OutputError`, SDK `sdk.Error`); failed decisions enter the decision log with `error` as a first-class field (`plugins/logs/plugin.go:781-783`); operators get labeled failure counters and health probes that explain themselves (`server.go:1300-1428`).
- **openhands — guard-driven presentation with managed lifetimes.** Type guards partition the event stream into inline chat cards vs banner errors (`types/agent-server/type-guards.ts:80-89`); connection errors auto-clear on healthy signals while conversation errors stick until dismissed (`stores/error-message-store.ts:4-9`); telemetry carries classifications and IDs but never raw messages (`utils/error-handler.ts:42-44`).
- **langfuse — right-sized disclosure with remediation pushed outward.** Per-event 207 multi-status for batch clients (`pages/api/public/ingestion.ts:176-182`); 4xx verbatim, 5xx replaced by deployment-aware copy (`trpc.ts:194-212`); internal engine stacks stripped but docs URLs and advice attached (`withMiddlewares.ts:116-203`).

## Pattern Catalog

### P1. Dual-channel failure rendering (sanitized audience text + forensic sideband)

- **Problem:** the model/user needs bounded, safe text; developers need the full exception — without running anything twice.
- **Demonstrated by:** agent-framework attaches the raw exception string out-of-band on the same content object while the visible text stays sanitized (`_tools.py:1429-1434`); letta splits `func_return` (model-safe) from `stderr` (traceback) inside one result schema (`schemas/tool_execution_result.py:8-13`); temporal pairs the masked response with a same-hash server log line (`mask_internal_error.go:82-111`); openai-agents-sdk renders caller text, message-only logs, and redacted trace placeholders from one event (`logger.py:31-51`, `_error_tracing.py:46-53`).
- **Why it works:** fidelity becomes a downstream choice, not a fork in execution; sanitization cannot be forgotten because the safe default is the only default.
- **Copy when:** any failure crosses an audience or trust boundary (model↔framework, service↔client).
- **Overkill/risky when:** the sideband itself can leak (see letta's SSE seam below) or when both channels drift apart because there is no single emission point — which is why openai-agents-sdk routes all three renderings through centralized helpers.

### P2. Correlation-token handoff (join user-visible failure to server forensics)

- **Problem:** masking protects internals but strands users who cannot self-diagnose.
- **Demonstrated by:** temporal's 8-hex `ErrorHash` appears in both the masked response and the server log (`common/util.go:409-414`, `mask_internal_error.go:89-111`); letta stamps `trace_id` into validation and traced error bodies (`app.py:487`, `otel/tracing.py:142`); langfuse surfaces the Sentry Error ID in its crash modal for support tickets (`CrashModal.tsx:37-50`); opa returns `decision_id` in every response, threadable to decision logs and spans (`types/types.go:267`, documented at `docs/docs/monitoring.md:10-13`); langgraph's SDK captures `x-request-id` on API errors (`sdk-py/langgraph_sdk/errors.py:82-93`).
- **Why it works:** support conversations become join operations; masking cost drops from "operator-mediated investigation" to "grep for this token."
- **Evidence note:** temporal's report explicitly frames the hash as mitigating — not eliminating — the self-diagnosis gap.

### P3. Event-before-abort ordering

- **Problem:** if the abort happens first, subscribers of record/event streams miss the cause of terminal failures.
- **Demonstrated by:** crewai emits `ToolFailureDetectedEvent` before raising under RAISE policy, with a test pinning the order (`tools/tool_failure.py:359-382`; `tests/tools/test_tool_failure.py:376`); agent-framework drains pending events → yields structured `failed` → sets FAILED status → records telemetry → then re-raises (`_workflows/_workflow.py:601-623`); langgraph invokes `on_chain_error` callbacks before re-raising and deduplicates handled exceptions by id so fatal and recovery paths don't double-report (`pregel/main.py:3018-3021`, `_runner.py:166-169,224-248`).
- **Why it works:** observers see identical information whether they consume streams or catch exceptions.
- **Copy when:** you have both push (events/callbacks) and pull (raise) consumers of the same failure.

### P4. Failures as durable, queryable records

- **Problem:** log lines rotate; post-mortems need failure state addressable after the process is gone.
- **Demonstrated by:** langgraph persists `(ERROR, exc)` pending writes to the checkpointer, recoverable via `get_state_history` — proven by a crash/resume test asserting the original `RuntimeError('Simulated failure')` reappears (`_runner.py:574-603`; `test_pregel.py:5372-5432`); temporal appends `WorkflowTaskFailedEvent` to immutable history (`workflow_task_state_machine.go:889-970`); letta persists run metadata `{"error": ...}` and step-level `error_type`/`error_data`, filterable through the runs API by `stop_reason` (`agents/letta_agent_v2.py:648-651`, `routers/v1/runs.py:57`); crewai attaches structured `ToolFailureRecord`s (tool name, args, agent role, task id) to `TaskOutput.tool_failures` (`tasks/task_output.py:50-61`); opa's decision log carries `error` through the same event shape as successes (`plugin.go:66,781-783`).
- **Why it works:** failure becomes part of run identity, enabling resume-after-fix semantics and aggregate queries.
- **Risky when:** durability has latency costs — langgraph gates error-writes on durability settings (`_loop.py:466`), trading record timeliness against throughput.

### P5. Fail-open observability / panic-hardened telemetry

- **Problem:** monitoring must never become the outage.
- **Demonstrated by:** crewai's `SafeOTLPSpanExporter` catches export failures and init is wrapped so telemetry degrades to no-op (`telemetry/telemetry.py:71-91,128-158`); langfuse skips failure-marking when Redis is absent and fails open when its rate limiter errors (`ingestionFailureTracking.ts:73-76`; `ingestion.ts:127-131`); openai-agents-sdk contains exporter exceptions so the worker survives, with deadline-bounded flushes (`processors.py:696-717`); letta's watchdog swallows its own telemetry exceptions ("Observability must never interfere with watchdog safety", `event_loop_watchdog.py:97-100`); temporal's zap encoder recovers from marshal panics and throttled logging never drops Fatal/Panic (`zap_logger.go:50-77`, `throttle_logger.go:60-80`); opa logs registry gather failures instead of panicking (`prometheus.go:109-118`); langgraph swallows observer-handler exceptions so they can't mask the primary error (`_retry.py:407-414`).
- **Why it works:** it converts "observability caused the incident" into "observability logged a warning during the incident."
- **Cost:** silent-ish telemetry loss under pressure — openai-agents-sdk queue-full drops leave only warnings (`processors.py:604,621`).

### P6. Policy-configurable severity/detail with resolution rules

- **Problem:** one hardcoded failure behavior fits nobody.
- **Demonstrated by:** crewai's `ToolFailurePolicy` (ignore/warn/raise) with precedence tool→task→agent→crew and a warn-and-fallback on malformed values (`tool_failure.py:177-208`, precedence matrix tested at `tests/tools/test_tool_failure.py:175-322`); langgraph's `handle_tool_errors` accepting bool/str/callable/type/tuple, with type-signature inspection routing custom handlers (`tool_node.py:383-391,444-479`); pydantic-ai's per-tool/toolset/run/output retry budgets deciding when a failure escalates from model-visible to run-aborting (`tools.py:378,410-423`; escalation message tested at `tests/test_agent.py:13660`); temporal's namespace-scoped dynamic config for masking, log-all-errors, and message caps (`dynamicconfig/constants.go:874-878,3631-3641`); opa's per-request `explain`/`strict-builtin-errors` params (`server/types/types.go:564-580`).
- **Why it works:** the knob lives next to the entity that understands context (a flaky tool, a noisy namespace).
- **Caution:** knobs need tests pinning both sides (only some sources do — see Notable Absences) and must actually be read (letta's dead knob, `settings.py:527`).

### P7. Control-flow separated from failure lineage

- **Problem:** approvals, interrupts, and cancellations are not errors, but naive plumbing reports them as such.
- **Demonstrated by:** langgraph subclasses `GraphBubbleUp`/`GraphInterrupt` into a lineage exempt from ToolMessage conversion, retry handling, and sibling cancellation (`tool_node.py:973-983`; `_retry.py:632-634`); agent-framework constructs `UserInputRequiredException` specifically so HITL approval requests propagate as content rather than generic tool errors, with `log_level=None` (`exceptions.py:184-211`); pydantic-ai records deferrals with span status left UNSET ("deferrals are control flow, not errors", instrumentation v5+ — `capabilities/instrumentation.py:452-471`) and synthesizes `outcome='interrupted'` returns to keep resumed histories valid (`_agent_graph.py:2866-2898`); langgraph additionally disambiguates user-cancel from framework teardown via `asyncio.Task.cancelling()` after a referenced misreporting bug (`_retry.py:315-334`); openhands applies the same idea at the UI layer with transient-connection vs sticky-conversation lifetimes (`error-message-store.ts:4-9`).
- **Why it works:** dashboards stop counting approvals as incidents; users stop seeing "error" for things that need their input.

### P8. Traceback hygiene (launder, annotate, truncate — deliberately)

- **Problem:** raw tracebacks expose framework internals, payloads, or secrets, and overwhelm their readers.
- **Demonstrated by:** langgraph recursively strips framework frames so the top of the stack points at user code, then annotates with task name/id notes preserving exception identity for retry matching (`_runner.py:58-68,240-248`; `_retry.py:641-643`); temporal truncates oversized failures in priority order — NonRetryable flag first, then Source/Message/StackTrace, then cause chain at depth 20 — so retry semantics survive even when root cause cannot (`common/failure/failure.go:52-91`); openai-agents-sdk detaches tracebacks and scrubs exception graphs on redacted errors so suppressed data provably cannot leak (`src/agents/exceptions.py:140-215,315-405`).
- **Copy when:** your stack crosses framework/user boundaries or size limits force triage.

### P9. Expected-vs-unexpected taxonomy as noise firewall

- **Problem:** at scale, most "errors" are client mistakes or routine contention; alerting on all of them trains operators to ignore alerts.
- **Demonstrated by:** temporal splits `service_errors` (unexpected only) from `service_error_with_type` (all), suppressing deadlines and ResourceExhausted from default logs unless a namespace opts into `system.logAllReqErrors` (`request_error_handler.go:64-116`; `metric_defs.go:657-665`); letta downgrades expected sandbox errors to DEBUG explicitly "to avoid triggering Sentry alerts" (`tool_execution_sandbox.py:230-232`); langfuse governs Sentry with individually-tested denylist rules where near-miss signatures are asserted to survive filtering (`sentryFilters.clienttest.ts:204,801-871`); crewai avoids polluting telemetry dimensions by reporting empty tool names for parse failures instead of raw model output (`tool_usage.py:925-931`).
- **Risky when:** suppression hides real incidents — temporal admits latency storms manifest precisely as suppressed deadline-exceeded errors until the flag flips (`request_error_handler.go:84-91`).

### P10. Canonical single-source rendering

- **Problem:** when multiple surfaces describe the same failure, prose drifts and consumers parse inconsistently.
- **Demonstrated by:** pydantic-ai documents `RetryPromptPart.from_error()` as "the exact message the model receives" and requires instrumentation to build identical text (`messages.py:1676-1697`, honored at `capabilities/instrumentation.py:362-363`); langfuse throws `BaseError` subclasses everywhere and lets exactly three boundary middlewares decide presentation (`trpc.ts:141-149`, `withMiddlewares.ts:165-174`, ingestion aggregation); opa converts engine errors once per boundary, retaining code+location (`writer.go:46-55`).
- **Why it works:** detail-level policy becomes auditable in N choke points rather than M×N call sites.

## Key Differences

**Convert-always vs re-raise-by-default toward the model.** agent-framework, letta, openai-agents-sdk, pydantic-ai, and crewai convert tool failures into model-visible content unconditionally (opt-out exists in most). langgraph's `ToolNode` default converts only argument-validation errors and *re-raises* execution errors, and `create_react_agent` does not override it — so one flaky tool crashes the whole run unless the developer knows the flag (`chat_agent_executor.py:554-561`, flagged as novice-hostile in the source report). This is a genuine philosophical split: predictability-for-experts versus resilience-by-default. Both camps mitigate the risk differently — the converters with circuit breakers and budgets (agent-framework's consecutive-error limiter, `_tools.py:2718-2731`; pydantic-ai's retry exhaustion raising with docs links, `tool_manager.py:256-265`), the re-raiser with configurability.

**How much detail escapes to less-trusted audiences.** OPA exposes full nested engine errors including `file:row:col` locations in 500 bodies, asserted verbatim in tests (`server_test.go:1575-1596`) — appropriate because its clients are engineers operating infrastructure. temporal masks Internal/Unknown behind neutral copy + hash by default, per namespace (`mask_internal_error.go:67-87`). Between these poles sit the inconsistent ones: letta masks REST 500s but leaks `str(exc)` on SSE (`app.py:469` vs `streaming_response.py:369`); langfuse masks tRPC 5xx with deployment-aware copy but returns raw `error.message` from REST fallbacks (`trpc.ts:198-211` vs `withMiddlewares.ts:196-202`). Neither inconsistency is documented as intentional — the reports found commented-out alternatives suggesting unresolved intent in both repos.

**Where failure records live.** Durable-execution and server systems put failures in queryable stores (temporal history, langgraph checkpoints, letta runs/steps, opa decision logs). Libraries keep them on exceptions and in-process structures (openai-agents-sdk's `RunErrorDetails` snapshot attached to raised exceptions, `run.py:2132-2144`; pydantic-ai's `capture_run_messages()` post-mortem API, `_agent_graph.py:2522-2563`; crewai's output-attached records straddle the two). This follows product shape: libraries assume the caller owns persistence.

**Configurability granularity.** Per-tool/per-run knobs in libraries (pydantic-ai budgets, openai-agents-sdk `failure_error_function=None`, langgraph handler callables); per-namespace/global knobs in servers (temporal dynamic config, letta env vars); fixed constants in openhands (220-char collapse, constant truncation — `error-message-banner.tsx:22`), which its report flags as a limitation. The pattern matches who is expected to tune: application developers vs operators vs end users.

**Privacy posture asymmetries.** openai-agents-sdk defaults logs to hide payloads (`DONT_LOG_*` = True) while traces include sensitive data by default (`run_config.py:53-56`) — an asymmetry its own report warns teams must consciously reconcile. agent-framework gates all payload-bearing telemetry behind one global opt-in (`observability.py:920-934`). pydantic-ai offers structural telemetry without values (`include_content=False` keeps shapes, drops prompts/args/results, `instrumented.py:76-164`). openhands never transmits raw messages at all, extending redaction to test artifacts like screenshots and Playwright traces (`tests/e2e/live/utils/agent-server-conversation.ts:88-102`, `playwright.live.config.ts:47`).

**Scope honesty.** Two sources could not fully answer the dimension within their boundaries and said so: openhands (frontend-only; model-facing formatting lives in a sibling repo — its report explicitly refuses to invent evidence) and temporal (CLI/Web UI rendering lives elsewhere; only wire format is guaranteed). This is itself a quality signal worth noting against sources whose gaps are silent.

## Tradeoffs

Comparative, per major design choice:

- **Sanitize-by-default (agent-framework, openai-agents-sdk) vs rich-detail-to-model (pydantic-ai validation details, OPA location-carrying errors).** Benefit of sanitizing: prompt-injection-via-stack-trace is structurally prevented and token spend is bounded. Cost: models may retry blindly without the actual exception — agent-framework mitigates with the out-of-band `exception=` field whose usefulness depends on the provider protocol honoring it (`_tools.py:1429-1434`). pydantic-ai chooses repairability and accepts that model-bound validation echoes user data through provider traffic, with mitigation existing only on the telemetry side (`messages.py:1716`, noted in its tradeoffs). Best-fit: sanitize when tools execute untrusted-influenced code; expose detail when failures are mostly benign argument mistakes the model can fix.
- **Masking with correlation tokens (temporal, letta, langfuse) vs full-disclosure envelopes (OPA).** Masking protects topology and PII but converts every internal error into an operator-mediated flow; temporal's hash reduces but does not eliminate this (`mask_internal_error.go:67-87`). OPA's full nested detail makes clients self-sufficient but assumes engineer audiences and trusted networks. Alternative seen: langfuse differentiates by deployment — cloud users get "we have been notified," self-hosters get "check your logs" (`trpc.ts:200-202`), respecting who can actually read the logs.
- **Durable failure records (langgraph, temporal, letta) vs ephemeral events (agent-framework workflow streams).** Durability enables post-mortems and resume-after-fix (proven by langgraph's recovery test) but adds write latency gated by configuration (`_loop.py:466`) and retention obligations. Ephemeral streams are simpler but vanish with the process — agent-framework's facade consumers additionally lose structured failure events entirely due to deliberate forwarding filters (`_events.py:133-143`).
- **Expected-error suppression (temporal) vs log-everything (crewai's problem in reverse).** Suppression keeps signal high at scale but hides incident classes that manifest as suppressed errors (deadline storms). CrewAI shows the opposite failure: coupling error logs to `verbose` means production runs emit nothing at all (`utilities/logger.py:25-33`). Both reports converge on the same fix shape: severity-independent sinks plus opt-in full-fidelity modes.
- **Redaction-as-guarantee (openai-agents-sdk) vs redaction-as-policy (most others).** openai-agents-sdk spends ~900 lines of blocked-output machinery and exception-graph scrubbing to make "invisible" *provably* invisible, with tests asserting redacted paths never invoke hostile `__str__` (`exceptions.py:292-312`; `tests/test_error_logging_redaction.py:93-150`). Others achieve practical redaction with far less machinery but no leak-proofing guarantees — sufficient where threat models are lower. Cost of the guarantee: audit complexity.
- **Policy flexibility vs predictability (crewai's four-scope resolution vs langgraph's per-node flag).** CrewAI's chain is powerful but requires reading precedence rules; its mitigation is an extensive test matrix. LangGraph's single-node knob is predictable but coarse. Temporal lands in between with flat, named, discoverable config keys ("config-as-taxonomy", all in `constants.go`).

## Decision Guide

Rules of thumb for choosing between the approaches found here, keyed to what you are building:

1. **Building an LLM library/harness?** Start from pydantic-ai: encode model-directed failures as serializable message parts, pick retryable-vs-terminal semantics explicitly, prove provider wire formats with parametrized tests, and mandate one canonical renderer used by both the conversation and telemetry. Borrow openai-agents-sdk's redacted-exception scrubbing if your surfaces can carry payloads into shared environments.
2. **Building a server/product API?** Adopt the letta/langfuse shape: one typed exception hierarchy, one dispatch point mapping exceptions to presentation (letta's ~30-entry registry; langfuse's three middlewares), correlation tokens embedded in error bodies, and deployment-aware copy. Then audit *every* transport seam (REST, SSE/WebSocket, batch) against the same masking policy — this is precisely where both sources leaked.
3. **Building durable/replayable systems?** Follow temporal: failures as typed protocol data driving behavior (not just reporting), priority-order truncation under size pressure, escalation ladders with doc-synced marker log lines, and an expected/unexpected metric split to protect alert sanity.
4. **Building a policy/engine consumed programmatically?** Follow opa: location-carrying typed errors, one canonical envelope per boundary, correlation ids threaded through response/logs/traces, and explain-modes returning traces to callers.
5. **Building a UI over an agent backend?** Follow openhands: classify at the event layer with reusable guards, give errors lifetimes (transient auto-clears on healthy signal; real problems stick until resolved), route to recovery affordances (retry/reauth/modals) instead of dead ends, and keep telemetry free of raw messages.
6. **Choosing convert-vs-raise defaults for tool errors:** convert-always if your users are novices or tools are flaky-prone (and add budget breakers like agent-framework/pydantic-ai); re-raise-by-default if correctness matters more than liveness and your audience reads exceptions (langgraph) — but document the default loudly either way.
7. **Choosing what to gate behind flags:** gate *payload content*, never *structural facts*. Agent-framework's rule — `error.type`/status always emitted, payloads opt-in — gives operators monitoring without PII ingestion (`observability.py:920-934`). Contrast letta's readiness gates defaulting OFF, which leaves default deployments unprotected until an operator discovers them (`settings.py:600-628`).

## Practical Tips

Patterns to copy, concretely:

- **Put the correlation token in the response body.** A hash or trace-id in the error payload (temporal's hash, letta's `trace_id`, langfuse's Error ID) turns support escalations into lookups. Costs almost nothing; adopt before launch.
- **Emit failure events before raising, and test the order.** CrewAI and agent-framework both pin this with tests; it is cheap insurance that stream consumers and exception catchers agree.
- **Give every abnormal termination a stable enum value.** Letta's `StopReasonType` persists onto steps and filters through the list API (`letta_stop_reason.py:9-49`); temporal's non-retryable flags drive server behavior from the same value. Strings like `"Error: ..." ` rot; enums survive refactors.
- **Split model-facing and human-facing channels inside one result object** (letta's `func_return`/`stderr`; agent-framework's sanitized text + `exception=` field) rather than formatting twice at call sites.
- **Make observability code unable to throw into the hot path** — wrap exporters, recover in log encoders, bypass rate limits for Fatal/Panic (six sources demonstrate variants; see Pattern P5).
- **Write the runbook quoting exact log lines, next to the code emitting them.** Temporal keeps DLQ docs and code comments synchronized (`executable.go:603,615`; `docs/admin/dlq.md:44`); langfuse ships Datadog query recipes beside its metric names (`.agents/skills/datadog-query-recipes/references/queue-consumers.md:199-215`).
- **Prove the bytes.** If your model-facing error format matters (it does), add a wire-format test suite like pydantic-ai's `test_tool_failed_wire.py` asserting native error channels per provider and no double-framing of legitimate `{"error": ...}` outputs (`tests/test_tool_failed_wire.py:269-333`).

Patterns to avoid or delay until needed:

- **Exception-graph scrubbing, payload-free replacement errors, blocked-output rebuilders** (openai-agents-sdk): valuable only if your redaction must be adversarially leak-proof. Start with placeholder rendering and add guarantees when threat models demand them.
- **Four-scope policy resolution chains** (crewai): begin with one scope + sensible default; add precedence only when real multi-tenant embedding needs it.
- **Deep opt-in health probes** (langfuse): useful once you operate restart orchestration; premature for simple deployments.

Decision rules distilled from divergence:

- If failures must influence control flow (retries, resume), represent them as data (temporal, pydantic-ai), not logs.
- If a failure crosses a trust boundary, render twice (safe text + forensic sideband) and join with a token.
- If two surfaces would describe the same failure, force both through one renderer (P10) — otherwise you will accumulate the letta/langfuse-style seams.
- If a knob exists, test both sides of it and verify something actually reads it.

Caution signs that the failure-visibility design is going brittle — see the next section; the short version is: dead knobs, seam inconsistencies, verbose-coupled logging, stringly-typed boundaries, silent streams, and safety features defaulted off.

## Anti-Patterns / Caution Signs

Recurring anti-patterns observed, with sources demonstrating each:

- **Dead configuration knobs.** letta declares `LogSettings.log_level` but no code reads it — effective level derives solely from `settings.debug` (`settings.py:527` vs `log.py:13,258-261`). opa defines `CodeEvaluation = "evaluation_error"` but `writer.ErrorAuto` routes eval failures to `internal_error` anyway (`types/types.go:120` vs `writer.go:33-34`). openhands' `RuntimeStatus` union has i18n keys but no component renders those codes today (`runtime-status.ts:10-19`). Caution sign: advertised tunability that silently does nothing erodes trust in the whole config surface.
- **Masking policy that varies by transport seam.** letta REST vs SSE (above); langfuse tRPC vs REST middleware (above); agent-framework DevUI streaming path that logs but yields no error event (`_executor.py:255-256`). Caution sign: when asked "what does a 500 look like?", the answer starts with "depends on the endpoint."
- **Verbose-coupled or sink-less logging.** CrewAI's logger returns early unless `verbose`, dropping even error-level lines, with stdout as the only sink (`utilities/logger.py:25-33`). LangGraph's core/prebuilt emit almost nothing conventionally — `prebuilt` has zero logger calls (`_log.py:1-3`), so developers without a tracer/checkpointer get exceptions only. Pydantic-ai has no stdlib logging channel at all (spans only, per its gaps section). Caution sign: headless deployments with no error visibility.
- **Stringly-typed failure payloads at boundaries.** langgraph's lifecycle/task-result error fields are `str(err)` (`transformers.py:588,604`; `debug.py:118`); crewai events carry `error=str(e)`, discarding stack traces (`task.py:800`). Caution sign: remote clients forced to regex prose to branch on failure kinds.
- **Streams that fail silently.** langgraph message-mode drops LLM errors with no in-band marker (`_messages.py:181-189,248-256`); openai-agents-sdk's `StreamEvent` union lacks an error variant, so UIs learn of failure only via raised exceptions after drain (`stream_events.py:51-61`); crewai mid-stream exceptions return accumulated partial output with only a logged warning (`llm.py:1098-1115`). Caution sign: UIs rendering confident partial answers from failed generations.
- **Suppression mechanisms without aggregate accounting.** opa drops decision-log events (an audit channel!) with only `logger.Error` lines — no counter (`sizeBuffer.go:117-125`); temporal throttled logging silently drops duplicate diagnostics under bursts (`throttle_logger.go:60-80`); openai-agents-sdk queue-full trace drops leave warnings only (`processors.py:604,621`). Caution sign: telemetry loss you can only discover by reading individual log lines.
- **Safety features defaulted off.** letta's readiness gates all default OFF ("non-breaking"), so default deployments always report healthy (`health.py:29-30`, `settings.py:600-628`); temporal's `logAllReqErrors` off means deadline-storm debugging needs a config flip. Caution sign: protection that requires discovering the flag during the incident.
- **Brittle classification heuristics.** openhands filters goal-loop re-prompts by matching English prompt prefixes, acknowledged in-code as "Brittle by design" (`should-render-event.ts:15-26`); temporal's expected-error switch is hand-maintained and admits partial coverage in its own comments, so new errors inflate the unexpected metric until updated (`request_error_handler.go:148-154`). crewai's fuzzy tool matching above 0.85 similarity can execute an unintended tool instead of erroring (`tool_usage.py:810-825`). Caution sign: classifiers maintained by editing string lists.
- **Boundary filters that eat failure richness.** agent-framework's `as_agent()` forwards only output/request events, deliberately excluding failure diagnostics — facade users lose structured failure visibility (`_events.py:133-143`). Caution sign: abstraction layers where error information strictly decreases.

## Notable Absences

Evidence genuinely missing across sources — stated as absence, not inferred:

- **No source ships monitoring dashboards or alert definitions.** Temporal's Grafana provisioning points at an empty directory (`develop/docker-compose/grafana/provisioning/dashboards/dashboard.yml:1-13`); letta's metric registry names ~20 failure series with no boards; langfuse externalizes alerts with only query recipes in-repo; langgraph delegates to LangGraph Platform via a server-consumed observer contract; openhands and crewai delegate entirely to SaaS tenants. OPA comes closest with a documented span/metric table (`docs/docs/monitoring.md`), but still ships no dashboards.
- **No runtime-hot-reloadable verbosity control anywhere.** openai-agents-sdk caches debug flags at import time (`_debug.py:20-27`); letta's level knob is dead (above); others require restarts or config pushes.
- **Only pydantic-ai verifies model-facing bytes with tests.** Other harnesses assert types/fields but not exact rendered content across providers (langgraph pins template text for its own templates, but not per-provider wire formats).
- **Traceback preservation in user-facing failure events is rare.** crewai and langgraph stringify at boundaries; only letta (step `error_data` includes traceback), temporal (failure stack traces within truncation budget), and openai-agents-sdk (caller-side snapshots) retain them past the raise site.
- **Cross-language parity was unverifiable in two sources:** langgraph's JS SDK is a submodule stub (`libs/sdk-js/` README only) and agent-framework did not trace .NET hosting-layer error mapping or confirm .NET test parity in-pass.
- **No unified client-side mutation-error reporting seam in web frontends:** langfuse toasts vary per feature team (its own tradeoff note), and openhands handles toasts separately from its banner store.
- **Model-facing redaction:** pydantic-ai's report notes there is no redaction story for model-bound payloads (only telemetry is redactable); no other source addresses model-bound PII either — the gap is industry-wide among the studied set.
