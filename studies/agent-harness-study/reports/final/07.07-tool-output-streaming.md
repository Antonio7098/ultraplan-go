## Executive Summary

Seven harnesses share one invariant and diverge on everything else: **in none of the sources does the model see partial tool output** — every framework delivers exactly one settled result per tool call into model context (agent-framework: `_tools.py:3424` awaits `get_final_response()` before executing; openai-agents-sdk builds a single `function_call_output` post-guardrails at `items.py:845-923`; pydantic-ai normalizes only settled returns via `build_tool_return_part`, `_tool_execution.py:65-116`; langgraph's deltas "never injected into messages channel", tested in `test_tool_node.py:1600-1618`; crewai appends only the final formatted string, `crew_agent_executor.py:1059-1065`; temporal's orchestrating workflow gets only completion or failure-with-partials). The one caveat is openhands, whose frontend-only scope means the model-side question could not be directly confirmed — though its display-only client is consistent with the rule.

What varies dramatically is what everyone *else* sees. Scores span 3–10-wide territory (3 to 8): crewai offers lifecycle events but no progress path at all; agent-framework, openai-agents-sdk, and pydantic-ai stream richly around tools while keeping tools themselves single-shot; langgraph ships a first-class per-tool-call delta protocol; temporal makes partial output a durable, retry-surviving snapshot; and openhands shows the consumer's side of the bargain — including deliberately *removing* mid-stream tool-output frames because flashing half-formed UI cards was worse than no live output (`should-render-event.ts:124-137`).

The practical answer to the dimension question — *"Can a long-running tool keep the user informed without confusing the model?"* — is yes, and the best implementations do it by splitting audiences: ephemeral, clearly-marked streams for humans/UIs; atomic results for the model; explicit poll/decompose patterns when the model needs agency over long work.

## Core Thesis

Across all seven sources, transcript atomicity is treated as load-bearing: tool execution happens strictly between finalized model turns, and every `function_result` enters history as an atomic unit. Because that boundary is fixed, each project spends its engineering budget elsewhere — and *where* it spends reveals its product shape:

- **Interactive libraries** (langgraph, openai-agents-sdk, pydantic-ai, agent-framework, crewai) invest in observer-facing event infrastructure — typed channels, lifecycle brackets, cancellation hygiene — while leaving the tool contract single-shot.
- **Durable-execution infrastructure** (temporal) invests in making partial output survive crashes, retries, failover, and cross-cluster replication — because its core promise is resilience, not liveness.
- **Production frontends** (openhands) invest in rendering discipline — coalescing, reconciliation, idempotent replay — and have learned that more streaming granularity can be a UX hazard rather than a feature.

The consequence: intra-tool progress is not a capability ladder where mature projects score high and immature ones low. It is a deliberate product decision, and several sources document why they chose *not* to build it.

## Approach Models

Using this dimension's vocabulary (streaming tool APIs, progress events, partial-output durability, cancellation during streaming, model visibility of partials, UI integration):

- **agent-framework — "streaming lives at the response layer."** Tools are single-shot in both stacks (`invoke(...) -> list[Content] | Any`, `python/packages/core/agent_framework/_tools.py:587-595`; `ValueTask<object?> InvokeAsync` shape throughout .NET). Provider-executed hosted tools stream genuinely (code-interpreter deltas at `agent_framework_openai/_chat_client.py:2977-3023`, partial images at `:3203-3230`), while local long-running work is decomposed into poll loops: MCP SEP-2663 tasks (`TaskAwareMcpClientAIFunction.cs:132-212`) and background-agent task ids polled via status tools (`BackgroundTaskStatus.cs:12-33`). Durability is invested where streams break (continuation tokens), not where tools compute.
- **crewai — "observability-only streaming around a batch contract."** `BaseTool._run` returns one value (`lib/crewai/src/crewai/tools/base_tool.py:387-403`); all tool visibility flows through bus emissions at two fixed points (started/finished, `tool_usage.py:291,487-495`) projected onto an ordered `StreamFrame` timeline's `"tools"` channel (`utilities/streaming.py:143-190`). Frames carry start/finish/error facts, never incremental output.
- **langgraph — "first-class multi-channel tool streaming."** Three composable modes (`tools`, `custom`, `messages`) plus a beta projection architecture (StreamMux → transformers → typed channels). Tool bodies push deltas via `ToolRuntime.emit_output_delta()` (`libs/prebuilt/langgraph/prebuilt/tool_node.py:1732-1750`); a handler brackets each call with `tool-started`/`tool-output-delta`/`tool-finished`/`tool-error` keyed by `tool_call_id` (`libs/langgraph/langgraph/pregel/_tools.py:35-53`).
- **openai-agents-sdk — "run-level streaming, opt-in callback intra-tool streaming."** Three typed event tiers (`raw_response_event` / `run_item_stream_event` / `agent_updated_stream_event`, `src/agents/stream_events.py:10-61`). Intra-tool progress exists only as opt-in callbacks: `Agent.as_tool(on_stream=...)` forwards nested-run events (`src/agents/agent.py:592,887-958`) and the experimental Codex tool aggregates a streamed thread behind a single-shot interface (`codex_tool.py:374-401`).
- **openhands — "discrete typed event stream consumed with render-side discipline."** One ordered WebSocket event substrate; LLM deltas are animation-frame batched and merged in place, then atomically superseded by canonical final events (`handle-event-for-ui.ts:225-250`). ACP tool calls get a two-event persisted lifecycle; native tools get nothing until completion, compensated by a model-driven polling contract (empty command fetches logs when exit code is `-1`, `src/types/agent-server/core/base/action.ts:27-44`).
- **pydantic-ai — "deferral instead of streaming."** `call_tool(...)` is settle-only (`pydantic_ai_slim/pydantic_ai/toolsets/abstract.py:170-173`). Long-running work suspends the graph via `'external'`/`'unapproved'` tool kinds resolved later through `DeferredToolResults` (`pydantic_ai_slim/pydantic_ai/tools.py:593-602`). Events flow around execution (`FunctionToolCallEvent`/`FunctionToolResultEvent` as parallel tasks settle), and UI protocol adapters translate them into AG-UI/Vercel lifecycles.
- **temporal — "progress as durable snapshot, delivered in-band."** A running activity periodically uploads `Details` payloads via `RecordActivityTaskHeartbeat` (`service/frontend/workflow_handler.go:1445-1511`); the server persists the latest snapshot in mutable state (`mutable_state_impl.go:2105-2135`), redelivers it to retry attempts (`recordactivitytaskstarted/api.go:288`), promotes it into immutable history on timeout/failure (`timer_queue_active_task_executor.go:346`), and uses the same RPC's response to carry cancel/pause/reset control flags back (`recordactivitytaskheartbeat/api.go:97-101`).

## Pattern Catalog

### 1. Lifecycle bracketing with correlation keys

Every source wraps each tool call in started → finished|error markers carrying a stable correlation id.

- **Problem solved:** coarse liveness and attributable progress without any intra-tool protocol.
- **Demonstrated by:** all seven. agent-framework (`pre_tool_call`/`post_tool_call` hooks, `_agent_hooks.py:1420-1481`; AG-UI `TOOL_CALL_START/ARGS/END/RESULT` mapping, `_event_converters.py:82-204`); crewai (`ToolUsageStartedEvent`/`ToolUsageFinishedEvent`, `tool_usage_events.py:57-75`); langgraph (`_tools.py:142-201`, keyed by `tool_call_id`, parallel calls isolated by test); openai-agents-sdk (`on_tool_start`/`on_tool_end` hooks plus `tool_called`/`tool_output` item events, `lifecycle.py:70-105`); openhands (two persisted ACP events per `tool_call_id`, `acp-tool-call-event.ts:52-66`); pydantic-ai (`FunctionToolCallEvent`/`FunctionToolResultEvent`, `messages.py:3946-4048`); temporal (`PendingActivityInfo` with attempt/state/timestamps, `activity.go:100-176`).
- **Why it works:** cheap, orderable, persistable, and sufficient for most UIs; correlation ids let flat streams be reconstructed into per-call trees by consumers.
- **Copy when:** always — this is the floor.
- **Overkill/risky when:** never, but it must not be mistaken for progress (a spinner naming the running action is all openhands shows during multi-minute bash commands, `typing-indicator.tsx:70-124`).
- **Evidence:** the bracket shape is asserted directly in langgraph tests (`test_tool_stream_handler.py:102-126`).

### 2. Provisional-then-canonical reconciliation

Streamed previews render immediately and are later atomically superseded by the authoritative final record.

- **Problem solved:** liveness without double-rendering or transcript pollution.
- **Demonstrated by:** openhands most explicitly — `finalizeStreamingDeltasInPlace` replaces streamed text with the canonical MessageEvent/ActionEvent, including stripping model-repeated thought text (`handle-event-for-ui.ts:225-301`); agent-framework merges argument deltas into one logical call via `__add__` (`_types.py:1984-1988,1479`); pydantic-ai passes raw JSON arg fragments verbatim because concatenation is what makes them valid (`ui/ag_ui/_event_stream.py:350-358`).
- **Why it works:** persistence stays clean (previews never stored), rendering stays duplicate-free.
- **Copy when:** anything streams toward a UI that also has a durable final artifact.
- **Risky when:** reconciliation matching is heuristic — openhands needed whitespace-tolerant matching and regression fixes (#1534, #1656) for cross-sender bleed and duplicated thoughts.

### 3. Dual-write durability escape hatch

When streamed data must survive, write it twice: once to the ephemeral stream, once to durable state.

- **Problem solved:** keeping the hot path cheap while offering a sanctioned durability route.
- **Demonstrated by:** langgraph's `push_ui_message` sends the event both to the stream writer and to a checkpointed `ui` state key, replayable through `ui_message_reducer` (`graph/ui.py:99-130,165-227`). Temporal is the inverted variant: heartbeats overwrite one mutable-state field by default and are promoted to immutable history only on terminal outcomes (`timer_queue_active_task_executor.go:346`; `respondactivitytaskfailed/api.go:87-91`) — bounding storage while preserving forensic value.
- **Copy when:** users would lose meaningful context on reload/crash otherwise.
- **Avoid when:** every event matters equally — then you want temporal's model or an event log, not selective dual-writes.

### 4. Bidirectional rendezvous point for progress and control

One periodic call uploads partial output and downloads control flags.

- **Problem solved:** interruption during streaming without a second channel; natural checkpoints for cooperative cancellation.
- **Demonstrated by:** temporal's heartbeat response carries `CancelRequested`/`ActivityPaused`/`ActivityReset` (`recordactivitytaskheartbeat/api.go:97-101`), and the code comment explicitly recommends heartbeating just to discover cancellation (`mutable_state_impl.go:4871-4873`). Weaker analogues: agent-framework's MCP polling responses carry task states with best-effort remote cancel (`TaskAwareMcpClientAIFunction.cs:215-233`); pydantic-ai's deferred-request/result events frame paused calls (`messages.py:4059-4109`).
- **Why it works:** gives every long invocation a natural rendezvous without persistent connections.
- **Copy when:** workers are cooperative and polling-shaped anyway.
- **Failure mode:** a non-heartbeating worker is reaped only by timeouts (`timer_sequence.go:399-444`); late heartbeats after timeout race into `EntityNotExistsError` (exercised in `tests/activity_test.go:807-898`).

### 5. Silent-degradation writers (and their evil twin)

Tool-side emission APIs default to harmless no-ops when streaming is unconfigured.

- **Problem solved:** tool code stays stream-mode agnostic; unobserved runs pay nothing.
- **Demonstrated by:** langgraph's `_no_op_stream_writer` default and `emit_output_delta` no-op outside `tools` mode, explicitly documented and tested (`config.py:13-14`; `tool_node.py:1737-1750`; `test_tool_stream_handler.py:149-173`).
- **Evil twin:** crewai's formatting fall-through stringifies a generator-returning tool into `<generator object ...>` sent to the model — silent degradation applied to *data* instead of *emission* (`structured_tool.py:59-93`; the Tavily tool actually triggers it, `tavily_research_tool.py:145-169`).
- **Lesson:** no-op defaults belong in the emission path, never in result handling; result-shape surprises should fail loud.

### 6. Failure-as-data and closeout honesty

Interruption produces explicit, marked terminal states rather than crashes or stuck spinners.

- **Problem solved:** transcripts stay valid and UIs stay truthful after cancellation.
- **Demonstrated by:** openai-agents-sdk converts a cancelled tool's `CancelledError` into a model-visible error string via `failure_error_function` (`tool_execution.py:2069-2095`) and records `"Tool execution cancelled"` span errors; pydantic-ai deterministically synthesizes `outcome='interrupted'` returns for dangling calls, shared verbatim across graph repair, realtime sessions, and UI closeout (`_agent_graph.py:2844-2898`; `messages.py:1290-1341`; `ui/_event_stream.py:330-358`); langgraph records `(ERROR, CancelledError)` writes flushed to the checkpointer even mid-cancellation (`_runner.py:579-591`); openhands distinguishes running cards by absence-of-result styling and exports streamed reasoning with `{ streaming: true }` markers.
- **Copy when:** always — this is what separates ratings ≥6 from ≤4 in practice.

### 7. Terminal-state sweeps

On run exit, error, or consumer abandonment, every still-open stream handle is deterministically closed or failed.

- **Problem solved:** consumers cannot hang on half-open channels.
- **Demonstrated by:** langgraph's transformer `finalize`/`fail` hooks close/fail all in-flight projections (`_tool_call_transformer.py:152-165`; `_mux.py:298-345`); pydantic-ai's `UIEventStream` synthesizes terminal results for pending calls "so the UI doesn't show them as still running" (`ui/_event_stream.py:318-358`, pinned by tests).
- **Contrast:** agent-framework's remote MCP cancel swallows exceptions silently (`TaskAwareMcpClientAIFunction.cs:277-280`), so a failed remote cancel leaves server-side work running with no client-visible indication — sweep logic that stops at the client boundary.
- **Copy when:** any multiplexed/handle-based stream API; make sweeps run even if individual hook invocations raise (langgraph's mux does, `_mux.py:424-449`).

### 8. Decomposition into model-visible state machines

When streaming cannot (or should not) reach the model, latency is converted into explicit poll loops.

- **Problem solved:** gives the model agency over long work without violating atomic results.
- **Demonstrated by:** MCP SEP-2663 task polling (agent-framework `_mcp.py:2209-2311`; pydantic-ai blocks on `tool_task.result()` instead, `mcp.py:1341-1364` — same protocol, opposite choice); background-agent task ids polled via status/result tools (agent-framework `BackgroundAgentsProvider.cs:590-635`); openhands' empty-command log-polling and `C-c` interrupt contract (`base/action.ts:27-44`); pydantic-ai's external/deferred tools suspending the graph entirely (`tools.py:593-602`); temporal's queries and update long-polls as the orchestrator's opt-in feedback loop (`queryworkflow/api.go:168-307`; `pollupdate/api.go:19-82`).
- **Why it works:** the model polls deliberately, keeps its context clean, and each poll is itself an atomic turn.
- **Cost:** extra turns, token overhead, and the burden falls on tool authors to design good status vocabularies.

## Key Differences

Three clusters emerge:

**Cluster A — settled-contract libraries (agent-framework, crewai, openai-agents-sdk, pydantic-ai).** Tools return one value; streaming surrounds the tool. They differ in what surrounds it: response-update content chunks plus provider-side deltas (agent-framework), a fire-and-forget event bus (crewai), a typed three-tier run event taxonomy (openai-agents-sdk), or deferral semantics replacing streaming altogether (pydantic-ai). None offers an intra-tool emission API.

**Cluster B — first-class progress channels (langgraph, temporal).** Both give tool bodies an explicit push API, but for opposite audiences: langgraph's deltas are ephemeral, consumer/UI-facing, and schema-free ("no retention beyond what's currently queued", `stream_channel.py:24-27`); temporal's heartbeat details are durable, operator/orchestrator-facing snapshots that survive retry and replication (`executions.proto:629`; `raw_task_converter.go:182`). Neither lets the model see partials.

**Cluster C — the consumer's verdict (openhands).** Given streaming machinery, a production frontend deliberately rolled back granularity: per-progress cumulative frames for ACP tools were removed because they "flashed half-formed cards mid-stream" (`should-render-event.ts:124-137`). Stability beat richness.

Why they diverge — these are constraint responses, not quality differences:

- **Product shape:** temporal sells survival under failure, so progress is a durability feature; agent libraries sell interactivity, so progress is a UX feature. Comparing temporal's snapshot model to crewai's absence misses that only one of them has a database row per activity.
- **Run-loop ownership:** langgraph installs ContextVar-bound writers inside tool execution because it owns the loop (`_tools.py:25-32`); openai-agents-sdk exposes callbacks instead of protocols partly to keep the tool contract simple and stable.
- **Maturity evidence:** openhands' removal of progress frames is production learning encoded in code; crewai's generator-stringify gap is the opposite — a streaming-capable tool existing outside framework assumptions.
- **Library-vs-platform:** a library can make partials ephemeral by default (crash = lost deltas is acceptable); a platform storing executions durably cannot afford per-heartbeat history volume, hence last-writer-wins snapshots promoted to history only on terminal outcomes.

## Tradeoffs

- **Atomicity vs liveness (universal).** Benefit: consistent, replay-safe transcripts; small changes to the function-loop contract risk duplicating side effects or orphaning call/result pairs (agent-framework treats this as load-bearing per its function-loop spec, `docs/specs/004-python-function-calling-loop.md`). Cost: zero intra-tool feedback — users stare at silence during long calls across five of seven sources. Best-fit: almost always keep atomicity; buy liveness on the observer side.
- **Push vs pull.** Temporal pulls (poll-only observation; works everywhere gRPC unary works; freshness bounded by poll interval), langgraph pushes (caller-driven pump with backpressure, `run_stream.py:320-333`). Alternative seen: openai-agents-sdk's hybrid — push to a queue with consumer acknowledgment gating between turns (`result.py:866-880`).
- **Snapshot vs timeline.** Temporal's last-writer-wins bounds storage but makes "how did progress evolve" unanswerable from the server alone (`mutable_state_impl.go:2113` is an assignment, not an append); langgraph's delta channels preserve the timeline but discard it on consumption. Neither source offers both.
- **Callback vs protocol for intra-tool streaming.** openai-agents-sdk's `on_stream` callback requires no new tool contract and composes with existing single-shot tools (`agent.py:592`), but only nested-agent/Codex tools can use it; langgraph's `emit_output_delta` protocol works for *any* tool body but required handler/mode wiring and ContextVar plumbing. Failure mode of callbacks: slow handlers stall consumption unless dispatched off-loop (openai-agents-sdk handles this explicitly, `agent.py:905-938`).
- **Early-completion vs deterministic ordering.** pydantic-ai makes this an explicit knob: `'parallel'` yields result events as tasks complete; `'parallel_ordered_events'` buffers and re-emits in emission order (`tool_manager.py:171-189`). Consumers choose between fastest signal and reproducible order — a pattern any parallel executor should steal.
- **Stability vs richness (openhands).** Removing live ACP output frames eliminated flashing cards *and* eliminated live tool output for external agents entirely (`should-render-event.ts:132-134`). The alternative — richer frames with better rendering discipline — was evidently judged not worth the risk.
- **Strict payload guards vs rich partials.** Temporal fails an activity outright whose heartbeat details exceed the size limit, returning `CancelRequested: true` to stop the worker (`workflow_handler.go:1471-1496`). Protects persistence; converts a payload-policy mistake into a hard tool failure. Alternative: soft truncation with markers (agent-framework's `HeadTailBuffer` `[... truncated N bytes ...]`, `HeadTailBuffer.cs:9-29`).

## Decision Guide

Choosing between the main approaches found in the sources:

1. **Are your tools short (< a few seconds)?** Lifecycle brackets + a busy indicator suffice. Openhands runs an entire coding-agent UI this way for native bash commands; crewai's console panels cover the same need. Do not build a delta protocol yet.
2. **Do users need live output from arbitrary tool bodies?** Adopt a langgraph-style dedicated channel: mode-gated handler, per-call correlation ids, bracketed events, no-op writer defaults. This is the highest-scoring interactive design in the study (8/10) and its tests show exactly which edge cases matter (parallel isolation, subgraph namespaces, error events, no-op outside the mode).
3. **Must runs survive crash/retry with their progress intact?** Adopt a temporal-style durable snapshot: overwrite-one-field persistence, redelivery to the next attempt, promotion to history on terminal outcomes, size limits enforced before writes. Accept the loss of the progress timeline.
4. **Does the model need to act on intermediate information?** Do not stream to it. Decompose: background task ids + status-poll tools (agent-framework), external/deferred tools that suspend the graph (pydantic-ai), or an explicit re-poll contract in the tool schema (openhands). Each poll is an atomic turn the model reasons over cleanly.
5. **Are your long-running tools mostly nested agents?** Forward the inner run's event stream via an opt-in callback and resolve to a single value (openai-agents-sdk's `as_tool(on_stream=...)`). Cheaper than inventing a protocol; dispatch handlers off-loop so they cannot stall consumption.
6. **Rendering streamed output?** Budget for reconciliation from day one: provisional previews superseded by canonical finals, flush-before-non-delta ordering invariants, id-scoped dedup, sender scoping (all proven necessary by openhands' regression list #1534/#1656).

## Practical Tips

- **Bracket every call, key everything by call id.** The single most portable pattern: `tool-started … tool-finished|tool-error` with `tool_call_id` (langgraph) maps directly onto AG-UI events (agent-framework's converters), ACP two-event lifecycles (openhands), and pending-activity info (temporal).
- **Make emission no-op by default, make result-shape surprises fail loud.** Langgraph's silent writers keep tools stream-mode agnostic; crewai's stringify-a-generator shows the mirror-image bug to avoid.
- **Convert cancelled work into marked data, not exceptions.** Synthesize `interrupted` outcomes (pydantic-ai), model-visible error strings (openai-agents-sdk), and persisted `(ERROR)` task writes (langgraph) so both the model's next turn and a reloading UI see a coherent story.
- **Sweep terminal states on every exit path** — success, error, consumer abandonment, cancellation — closing or failing all open handles, even if individual cleanup hooks raise.
- **Persist partials only where your product promises survival**, and say which tier each artifact belongs to: transient deltas (openhands "never persisted/resent"), dual-written state keys (langgraph `ui`), snapshot-in-mutable-state (temporal). Mixing tiers silently is how consumers end up assuming durability that isn't there.
- **Enforce ordering invariants at the batching boundary**: openhands requires `flush()` before any non-delta event so a durable message cannot render ahead of its own streamed text (`streaming-delta-batcher.ts:33-34`) — enforce it in one place, test it byte-exactly.
- **Use monotonic sequence numbers, not timestamps, for ordering** — langgraph documents that `ProtocolEvent.timestamp` is wall-clock and can go backwards under NTP (`stream/_types.py:15-20`).
- **If you adopt parallel tool execution, expose an ordering knob** like pydantic-ai's `'parallel'` vs `'parallel_ordered_events'` rather than picking for everyone.
- **Give operators metrics on progress traffic itself**: temporal tags heartbeat counters with `has_details` and tracks payload bytes (`mutable_state_impl.go:2124-2134`), telling you how much streaming actually carries output versus bare liveness pings.

## Anti-Patterns / Caution Signs

- **Generator-as-result hazard.** Any pipeline that stringifies arbitrary return values will eventually send `<generator object ...>` to the model (crewai: `structured_tool.py:59-93` with a real triggering tool). Caution sign: result formatting with a broad fallback branch.
- **Observation-cancel ≠ work-cancel.** CrewAI's `close()` detaches the stream but `thread.join()`s the worker; cancelling observation leaves the runaway tool running with no signal into its body (`utilities/streaming.py:276-287`). Caution sign: cancellation paths that touch only consumers.
- **Silent stalls.** With no intra-tool progress and no timeout, a hung tool is indistinguishable from a slow one until something external intervenes — noted in agent-framework, crewai (non-MCP tools get no timeout while MCP tools get 60s, an inconsistency within one repo), and implicit in every settled-contract design.
- **Half-formed-card flash.** Cumulative progress frames rendered eagerly produce flickering, misleading UI (openhands removed the feature). Caution sign: rendering pipelines that commit every frame without provisional/canonical separation.
- **Uninterruptible execution lanes.** Sync tools in worker threads cannot be interrupted mid-body in agent-framework; results are discarded while side effects continue (`_tools.py:1868-1876`). Know which lanes are cooperative before promising cancellation.
- **Best-effort remote cancellation that fails silently.** Swallowed `tasks/cancel` exceptions leave remote work running with no indication (agent-framework: `TaskAwareMcpClientAIFunction.cs:277-280`).
- **Divergent marking schemes for the same concept.** agent-framework marks executed calls via .NET in-place `InformationalOnly` mutation, Python metadata-only echoes, `status` strings, and `is_partial_image` flags — consumers must learn four conventions (`MessageInjectingChatClient.cs:333-361`; `_tools.py:2843-2846`). Caution sign: each surface inventing its own partiality marker.
- **Timestamp-based ordering.** Wall-clock timestamps that go backwards corrupt cross-source merging (langgraph documents the trap); buffered-query saturation turning observer pressure into hard errors is acceptable, silent drops are not (temporal fails loudly with `ErrConsistentQueryBufferExceeded`).
- **Payload policy enforced as execution death.** Oversized partials killing the activity (temporal) protects the store but surprises authors; pair hard limits with early validation and clear failure reasons (`FailureReasonHeartbeatExceedsLimit` does this right, but the design is inherently punitive).

## Notable Absences

Evidence-disciplined absences confirmed by multiple source reports:

- **No source feeds partial tool output to the model automatically.** Directly verified in six sources; openhands could not confirm from the frontend boundary alone (the agent loop lives in a sibling repo). Langgraph's report explicitly searched for delta-accumulation into `ToolMessage` and found only consumer-side projections.
- **No unified partial-output marking contract anywhere.** Each stack (and within agent-framework, each language stack) uses different markers: `status` fields, `InformationalOnly`, `is_partial_image`, `outcome='interrupted'`, `{ streaming: true }`, `HeartbeatDetails`. ## Per-Source Notes

- **agent-framework (4/10):** Deliberately asymmetric — hosted/provider tools stream richly, local tools cannot. Compensating strengths in durability (continuation tokens serializing accumulated `ResponseUpdates`, resume-tested) and cancellation (end-to-end CT propagation including remote MCP). The background-task poll pattern is its most transferable idea.
- **crewai (3/10):** Excellent adjacent plumbing (ordered frame channels, contextvars-scoped sinks, tested cancellation of sessions) around a total absence of tool progress. The Tavily generator case demonstrates the framework's assumptions breaking on a streaming-capable tool.
- **langgraph (8/10):** The reference design for interactive tool streaming: dedicated `tools` mode, bracketed per-call protocol, custom-event side channel, projection mux, abort that propagates into nodes while cancelled tasks still flush checkpoint writes. Deductions: ephemeral-by-default deltas, beta v3, typing gaps.
- **openai-agents-sdk (7/10):** Most polished run-level streaming: three-tier typed events, documented eleven-name event table, back-pressure between turns, two-mode cancellation with extensive tests. Function tools themselves remain opaque black boxes during execution.
- **openhands (6/10):** The consumer-side view and the study's only negative evidence about streaming granularity — progress frames removed on UX grounds. Strongest rendering engineering: byte-exact coalescing, reconciliation, replay idempotency. Native tools degrade to a spinner chip.
- **pydantic-ai (6/10):** Clearest articulation of the settled-only philosophy plus a genuinely different answer to long work (deferral/suspension). Best-of-study cancellation attribution machinery (`Task.uncancel()` accounting) and closeout honesty; weakest integration of an available progress source (MCP notifications).
- **temporal (8/10):** The reference design for durable progress: heartbeat details survive retry, timeout, failure, failover, and cross-cluster replication; the same call carries control flags back. Deductions: snapshot-only, pull-only, orchestrator-blind by default, Web UI unverifiable from this source.
