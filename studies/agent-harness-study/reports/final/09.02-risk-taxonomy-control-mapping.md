## Executive Summary

No source in this study ships a mature, unified risk taxonomy with a queryable risk→control map. Scores span 4–7 (mean ~5.6), and the single point that separates them is not control strength — every source has working gates — but whether risks are *named at all*. openai-agents-sdk (7/10) leads because it pairs the study's densest control coverage with one genuinely explicit two-tier taxonomy (mount credential exposure) and fail-closed enforcement; openhands (6/10) is the only source with an end-to-end severity enum on every action, but maps it through a single hardcoded threshold; agent-framework (6/10) has four parallel vocabularies (approval bit, FIDES labels, Purview DLP verbs, file/skill categories) that are each locally sound but never composed; opa (5/10) and langfuse (4/10) both answer the dimension by proxy — capability inventories and RBAC scopes standing in for risk — leaving the operator to reconstruct "which controls apply here?" from code.

The headline finding: **controls exist without taxonomies, and taxonomies exist without controls, but no source binds the two into one registry an operator can query at runtime.** Every source can enforce a gate per tool or per action; none can answer `assessRisk(action) → { risks, controls }` from a single authority. Where risks *are* named, bypass resistance is engineered (agent-framework's bundled-disclosure binding `python/packages/core/agent_framework/security.py:1889-1924`, SDK's provenance-closed tables `src/agents/sandbox/_mount_security.py:1348-1392`, langfuse's CAS grant revalidation `packages/shared/src/in-app-agent/server/tools.test.ts:17-23`); where they are implicit, bypasses are documented conventions (name-collision auto-approvals, `allow_net` string matches, client-authored `NeverConfirm`).

## Core Thesis

Risk-taxonomy architecture follows what the product *sells*:

* **A policy engine (opa)** externalizes risk judgment to policy authors. Its engine provides generic, composable enforcement points (compiler gates, authorizer middleware, log masking at `v1/server/authorizer/authorizer.go:107-165`, `v1/plugins/logs/mask.go:18-76`) and a machine-readable capability inventory (`capabilities.json`, `v1/ast/builtins.go:3632-3650`) rather than a built-in risk model. This is deliberately inverted: controls are named and machine-readable, risks are left unnamed.

* **A multi-tenant observability platform (langfuse)** models risk as RBAC capabilities (86 `ProjectScope` strings at `packages/shared/src/features/rbac/projectAccessRights.ts:5-86`). One source of truth serves both UI entitlements and agent tool authorization via the exhaustive `IN_APP_AGENT_LANGFUSE_MCP_TOOL_POLICIES` map (`packages/shared/src/in-app-agent/server/mcpPolicy.ts:27-360`). Operators already understand roles, but lose any risk vocabulary.

* **Application frameworks/SDKs (agent-framework, openai-agents-sdk)** express risk as tool metadata (`ApprovalMode = "always_require" | "never_require"` at `python/packages/core/agent_framework/_tools.py:106`; `needs_approval: bool | Callable` at `src/agents/tool.py:486-493`). Each tool carries its own gate, so no global view exists. The SDK that went furthest built a true taxonomy only where platform trust demanded it — mount credential exposure (`_MountCredentialExposurePolicy` at `src/agents/sandbox/manifest.py:75-78`) — and left everything else fragmented.

* **A thin frontend canvas (openhands)** is the outlier that *does* name a severity taxonomy (`SecurityRisk { UNKNOWN, LOW, MEDIUM, HIGH }` at `src/types/agent-server/core/base/common.ts:58-64`) assessed per action by an LLM analyzer (`src/types/agent-server/core/events/action-event.ts:46-61`). It compiles a boolean + analyzer choice into a single server policy (`getConversationConfirmationPolicy` at `src/api/agent-server-adapter.ts:593-605`). The taxonomy exists but is shallow: one threshold (HIGH), no sub-categories.

**What converges** despite those shapes is telling: every source gates at least per-tool and per-action, every approval gate converges on a binary approve/warn/block dispatch, and every source fails closed on unparseable inputs where it bothers to handle them (`src/agents/util/_approvals.py:18-29`, `python/packages/core/agent_framework/security.py:2061-2095`). **What diverges** is durability and naming: only the two SDKs persist risk metadata to runtime-replayable state, only openhands performs per-action *risk* assessment (vs. per-action *policy* evaluation), and only opa exposes a versioned count of how many "tools" (builtins) it governs.

> Can an operator explain what controls apply to a given action? In openhands, partially — `HIGH → pause` is explicit and tested (`__tests__/api/agent-server-adapter.test.ts:349-376`), everything below is display-only. In agent-framework, only by reading five subsystems. In langfuse, opa, and openai-agents-sdk, only by translating capability/scope metadata back into risk in their head.

## Approach Models

Three archetypes emerged; two sources each occupy the first two:

### Model A — Fragmented Metadata Controls (agent-framework, openai-agents-sdk)

Risk is an attribute of a tool declaration, not a first-class domain object. Each surface invents its own naming: `ApprovalMode`, `IntegrityLabel`/`ConfidentialityLabel`, `SandboxPathGrant.read_only`, `PendingSafetyCheck`, `require_approval` per MCP server. There is no central registry; an operator queries the tool instance. Granularity is fine — per-tool static plus per-call dynamic (`needs_approval` callable receives `(ctx, params, call_id)` at `src/agents/tool.py:486-493`; FIDES per-action label check at `python/packages/core/agent_framework/security.py:1733-1748`) — but coverage is uneven because each control must be opted into at construction. Where a trust boundary demanded it, the SDK did build a real taxonomy: the mount-credential two-tier table mapping `(mount_type, strategy, pattern)` → `{mount_scoped_fields, broad_fields}` at `src/agents/sandbox/_mount_security.py:301-409` is the study's most data-driven risk→allowed-exposure map, gated by `PrivateAttr` and rejected on deserialized input (`src/agents/sandbox/manifest.py:261-271`).

Best fit: embeddable libraries where hosts own identity and policy, and flexibility beats auditability.

### Model B — Capability-Inventory Proxy (langfuse, opa)

No `Risk` type exists (langfuse glob `**/*risk*` = 0; opa grep `risk|Risk` = incidental comments only). Risk is proxied by enumerating capabilities: Langfuse's 86 `ProjectScope` strings and ~90-entry approval table; OPA's 206 builtins with `Deprecated`/`Nondeterministic` flags (`v1/ast/builtins.go:3632-3650`, serialized to `capabilities.json`). Every capability maps to a control (scope→role, builtin→`allow_net`/compile stage), but the mapping is tool→gate, not risk→gate, so "PII exfiltration risk" has no address. Enforcement is dual-layer and consistent; revalidation-on-use is the distinctive strength (langfuse per-run `createInAppAgentToolPolicy` recheck; OPA per-request authorizer `v1/server/authorizer/authorizer.go:128`).

Best fit: platforms where operators already reason in permissions and tool surfaces change fast.

### Model C — Per-Action Severity Gate (openhands, alone)

One four-value severity enum (`UNKNOWN|LOW|MEDIUM|HIGH`) typed through events, UI, and i18n (`src/types/agent-server/core/base/common.ts:58-64`; `src/i18n/translation.json:563-626`). Risk is assessed at runtime per action by the analyzer and travels on `ActionEvent.security_risk` (`src/types/agent-server/core/events/action-event.ts:58-61`). Controls are compiled from two settings fields (`confirmation_mode`, `security_analyzer` at `src/types/settings.ts:128-129`) into a discriminated-union policy `NeverConfirm | ConfirmRisky{threshold:HIGH, confirm_unknown:true} | AlwaysConfirm` (`src/api/agent-server-adapter.ts:593-605`). Hierarchy is implicit in the threshold; there are no risk categories.

Best fit: single-tenant canvases where one threshold keeps the model explainable and enforcement can be delegated.

## Pattern Catalog

### P1. Binary approval bit as minimal taxonomy

*Problem:* Every tool needs a default posture without building a full risk model.
*Demonstrated by:* agent-framework `ApprovalMode = "always_require" | "never_require"` (`python/packages/core/agent_framework/_tools.py:106`) enforced pre-execution (`_tools.py:1775-1832`); langfuse `InAppAgentMcpToolApproval = "auto" | "approval"` (`packages/shared/src/in-app-agent/server/mcpPolicy.ts:7`); openai-agents-sdk `needs_approval: bool | Callable` (`src/agents/tool.py:486-493`); opa `allow_net` as binary egress gate (`v1/ast/capabilities.go:82-101`).
*Why it works:* One bit is cheap to maintain, fail-closed by default where applied, and trivially testable.
*When to copy:* Always as the baseline; any richer taxonomy should be additive.
*When overkill/risky:* When one bit collapses distinct consequences (langfuse: delete vs. create vs. read-PII all = `"approval"`; agent-framework FIDES nuance hidden behind experimental flag). Evidence: langfuse Breadth-vs-fidelity tradeoff; agent-framework binary loses nuance (`_tools.py:106` comment).

### P2. Tiered exposure taxonomy with capability table

*Problem:* Some risks need field-level precision (which credential fields may go where).
*Demonstrated by:* openai-agents-sdk `_MountCredentialExposurePolicy {mount_scoped, broad}` (`src/agents/sandbox/manifest.py:75-78`) + `_AUTHORITY_FIELDS_BY_MOUNT_TYPE` (`src/agents/sandbox/_mount_security.py:60-78`) + `_IN_CONTAINER_MOUNT_CREDENTIAL_CAPABILITIES` (`_mount_security.py:301-409`).
*Why it works:* Data-driven, testable (132 tests), trust-gated (private attr, provenance-checked classes win, custom subclasses rejected at `src/agents/sandbox/_mount_security.py:193-196`).
*When to copy:* Any surface where authority varies by destination scope (mounts, network, auth tokens).
*When overkill:* CRUD tools with no credential transport.

### P3. Capability inventory as proto-risk metadata

*Problem:* Governing what a runtime *can* do without naming risks.
*Demonstrated by:* opa `Builtin{Deprecated, Nondeterministic}` (`v1/ast/builtins.go:3632-3650`) with `IsNondeterministic()` driving real control (PE save at `v1/topdown/save.go:535`); langfuse `projectScopes` capability list (`packages/shared/src/features/rbac/projectAccessRights.ts:5-86`).
*Why it works:* Machine-readable, versioned (`capabilities/v0.17.0.json`), generable, auditable as a bill of materials via `buildRequiredCapabilities` (`v1/ast/compile.go:1198-1240`).
*When to copy:* Policy-as-data engines and platforms where capability drift is the risk.
*Risk:* Properties without flags have no control; opa `Categories` field is still aspirational (`v1/ast/builtins.go:3638-3640`).

### P4. Unified risk→control dispatch ladder (block / approve / warn)

*Problem:* Different severities need different operator friction.
*Demonstrated by:* agent-framework `approve-consume → request-approval → block → warn` in `PolicyEnforcementFunctionMiddleware.process` (`python/packages/core/agent_framework/security.py:2065-2095`); openai-agents-sdk tri-state `allow | reject_content | raise_exception` (`src/agents/tool_guardrails.py:40-77`) vs binary `tripwire_triggered` (`src/agents/guardrail.py:19-32`); openhands implicit `HIGH→pause, MEDIUM/LOW→badge` (`src/components/shared/risk-alert.tsx:19-35`).
*Why it works:* One dispatch point gives an operator a single place to reason about friction.
*When to copy:* Whenever you have more than one consequence class.

### P5. Exhaustiveness-by-test — policy drift as build error

*Problem:* A new tool shipping without a classification silently inherits the default.
*Demonstrated by:* langfuse test asserting `IN_APP_AGENT_LANGFUSE_MCP_TOOL_POLICIES` covers every `toolRegistry` entry (`web/src/features/in-app-agent/README.md:233` pattern); opa named compile stages (`v1/ast/compile.go:455-477`) as audit-able pipeline.
*Why it works:* Turns review-time hope into a compile/test failure.
*When to copy:* Any growing tool/API surface mapped to a gate table.
*Evidence:* langfuse report Notable Patterns; opa Architectural Decisions.

### P6. Fail-closed on unknown/unparseable

*Problem:* Ambiguity must not widen authority.
*Demonstrated by:* openai-agents-sdk `parse_function_tool_arguments → None` forces manual approval (`src/agents/util/_approvals.py:18-29`, documented `docs/human_in_the_loop.md:15`); agent-framework `combine_labels` most-restrictive-wins (`python/packages/core/agent_framework/security.py:212-264`); opa masking failure drops event rather than pushing unmasked (`v1/plugins/logs/plugin.go:785-788`); openhands `confirm_unknown: true` (`src/api/agent-server-adapter.ts:601`).
*When to copy:* Universally — cheapest safety pattern in the study.

### P7. Trust-gated risk acceptance

*Problem:* Risk acknowledgment must come from trusted code, not untrusted data.
*Demonstrated by:* openai-agents-sdk `Manifest._reject_mount_credential_exposure_policy_input` (`src/agents/sandbox/manifest.py:261-271`) + `with_in_container_mount_credential_exposure_acknowledged` on trusted instances only (`manifest.py:297-351`); agent-framework provenance-closed mount boundaries (`src/agents/sandbox/_mount_security.py:1348-1370`).
*When to copy:* Any acknowledgement/override path.

## Key Differences

**Do risks have names at all?** Openhands yes — one severity enum end-to-end. Agent-framework partially — experimental `IntegrityLabel`/`ConfidentialityLabel` plus two violation strings (`"untrusted_context"` `python/packages/core/agent_framework/security.py:2008-2024` and `"max_allowed_confidentiality"` `security.py:2142-2157`). Openai-agents-sdk partially — two-tier credential taxonomy plus decentralized behavioral hints. Opa and langfuse no — only capability names.

**What granularity is risk assessed at?** Tool vs action vs agent matters. Per-tool static: agent-framework `approval_mode` (`_tools.py:1763`); langfuse `mcpPolicy.ts:452-470`; opa `allow_net` per builtin-type. Per-action dynamic: openhands `ActionEvent.security_risk` per tool call (LLM-predicted); agent-framework FIDES per-call label+violation set bound including session (`security.py:1624-1639`); SDK `needs_approval` callable with `(ctx, params, call_id)`. Per-agent: nowhere — all five reports searched for per-agent risk scores, budgets, posture and found nothing (`risk|severity|posture` → doc comments only).

**Is the mapping queryable at runtime?** No source provides `controlsFor(action)` as one call. Agent-framework has no control map (answer assembled ad hoc across `_tools.py`, `security.py`, provider factories, `purview/_middleware.py`). Langfuse can answer "auto vs approval" from the map but not "what risk does `createScore` carry?" (`packages/shared/src/in-app-agent/server/mcpPolicy.ts:284-287` shows scope, not consequence). Opa exposes capabilities CLI-only (`cmd/capabilities.go:36-43`), not via HTTP (`v1/server/server.go:904-927` has no endpoint). Openai-agents-sdk exposes per-call `get_approval_status` (`src/agents/run_context.py:1065-1077`) and tracing `GuardrailSpanData` (`src/agents/tracing/span_data.py:292-313`), but no aggregate. Openhands exposes `security_risk` on events and a red alert for HIGH only (`conversation-confirmation-buttons.tsx:102-118`), with `RiskAlert` null for lower severities (`risk-alert.tsx:35`).

**Who decides what is risky?** Statically classified (langfuse approval table, agent-framework `approval_mode`, opa builtin flags) vs LLM-judged per call (openhands) vs capability-evaluated per request (opa authorizer). Openhands trades determinism for context sensitivity; the cost is that the same model performing the action judges its risk.

**Can standing grants be contained?** Langfuse grants (`InAppAgentConversation.alwaysAllowedTools` at `packages/shared/prisma/schema.prisma:248-249`) are revalidated against current role every run (`packages/shared/src/in-app-agent/server/tools.test.ts:6-24`) — demotion revokes. Agent-framework auto-approval rules match by bare name and document the collision as a warning instead of an invariant (`python/packages/core/agent_framework/_harness/_file_access.py:1411-1420`). Openai-agents-sdk sticky grants are fingerprinted by invocation ledger (`src/agents/_tool_invocation.py:236-289`) with cross-server collision tests, but have no TTL. Opa tokens and signatures have no expiry (`v1/bundle/verify.go:118-208`).

## Tradeoffs

* **Generality vs operator legibility.** Opa's externalized-risk design (`docs/blog/2017-12-14-opas-full-stack-policy-language-caeaadb1e077.md:165` "Rego is domain-agnostic") maximizes generality but forces the operator to reconstruct the implicit mapping across five subsystems; doc table in opa report §2 lists 8 risks → 8 controls that are nowhere co-located in code. Langfuse pays the same cost with RBAC-as-proxy: broad coverage, zero risk vocabulary.

* **Fragmentation vs flexibility.** SDKs attach controls to declarations (`FunctionTool`, `Agent`, `Manifest`) for locality (`src/agents/tool.py:472-493`). This keeps each surface evolvable but guarantees no global view; the report notes "no single registry, nothing composes them" (agent-framework) and "invent new naming per surface" (SDK Tradeoffs). Unifying into a central risk service would buy auditability at the cost of host coupling.

* **Latency vs safety on parallel verdicts.** Openai-agents-sdk notes `run_in_parallel=True` default lets the agent consume tokens before a tripwire fires (`docs/guardrails.md:34-38`, knob at `src/agents/guardrail.py:100-103`); blocking mode is safe but slow. Langfuse's dual enforcement (worker filter + server `canCallTool` at `web/src/features/mcp/server/registry.ts:170-189`) pays latency for defense-in-depth.

* **Hot classification vs curated accuracy.** Langfuse's static table must be curated per tool (~90 entries) — cheap fidelity but manual. Openhands' LLM judgment is hot and context-aware but non-deterministic; `confirm_unknown: true` is the safety compensator. Agent-framework's `combine_labels` deterministic join (`security.py:212-264`) is predictable but blind to semantics.

* **Safety defaults vs autonomy.** Temporal-adjacent pattern visible here: opa authz off by default (`docs/docs/security.md:117-119`), SDK `needs_approval=False` default, openhands `confirmation_mode=false` (`src/services/settings.ts:13-14`) — all favor adoption. Agent-framework flips dangerous file/skill surfaces to `always_require` and escalates `execute_code` if any tool requires approval (`python/packages/hyperlight/agent_framework_hyperlight/_execute_code_tool.py:335-346`) — safer default, more friction.

* **Fail-closed strictness vs observability.** Opa dropping mask-failed events (`v1/plugins/logs/plugin.go:785-788`) protects data but creates silent audit gaps; SDK fail-closed on unparseable args produces safe but surprising approval storms.

## Decision Guide

**Choose by operator contract first, then copy the compensating patterns:**

* **Building an agent SDK/library where users are developers?** Follow openai-agents-sdk: typed per-tool `needs_approval` bool-or-callable, three-valued verdicts at the tool layer, durable binding records, fail-closed parsing, plus one deep, table-driven taxonomy where secrets cross a boundary. Use provenance-closed allowlists so subclasses cannot self-promote (`src/agents/sandbox/_mount_security.py:193-196`). Accept no unified risk dashboard; expose `get_approval_status`-style query per call.

* **Building a multi-tenant platform where operators and users both configure policy?** Copy langfuse: compile the tool→approval vocabulary into a shared package with exhaustiveness-by-test, enforce twice (builder + server `canCallTool`), store standing grants durably, and *revalidate grants on every use* against current role (`mcpPolicy.ts:477-510`). Do not conflate `readOnlyHint` with safety; give sandbox tools (`bash`/`write` at `mcpPolicy.ts:410-421`) their own risk tier instead of blanket auto-approval.

* **Building a policy decision point?** Copy opa: machine-readable capability inventory (`capabilities.json` 206 builtins) with named compile stages (`v1/ast/compile.go:455-477`), per-request input schema `{path, method, params, headers, body, identity}` (`v1/server/authorizer/authorizer.go:192-224`), fail-closed undefined handling, plus `allow_net` as the minimal viable risk flag. Publish capabilities at runtime (opa's gap is CLI-only) and emit "controls applied" into decision logs.

* **Building a thin frontend/canvas over someone else's enforcement?** Copy openhands: server-evaluated severity enum (not client-evaluated), pure mapping functions (`getConversationConfirmationPolicy` `src/api/agent-server-adapter.ts:593-605`), UNKNOWN fail-safe, and per-action risk surfacing (badges + alerts). Eliminate the client-authored downgrade to `NeverConfirm` (`tests/e2e/live/utils/agent-server-conversation.ts:243-245` is the live bypass); make `confirm_unknown` visible in UI (currently only at `agent-server-adapter.ts:601`).

**Decision rules within a design:**

* Need risk names? Only if you need categorization beyond "needs human." If you have one irreversible consequence, a binary bit suffices (P1); add tiers when consequences differ (P2).
* Need per-action assessment? Only if context changes the risk (paths, arguments, data labels). Static per-tool suffices for capability-gating; dynamic per-call is required for exfiltration/taint.
* Grant lifetime: prefer occurrence-scoped over sticky. If sticky, revalidate on use (langfuse) or fingerprint by invocation identity (SDK) and add a TTL — every source missing this lists it as a gap.

## Practical Tips

**Patterns to copy immediately (low cost, high leverage):**

* Make policy drift a build error. Derive the tool-name type from the policy map keys (`satisfies Record<...>` at `packages/shared/src/in-app-agent/server/mcpPolicy.ts:360-363`) and pin completeness with an equality test. Langfuse is the only source that does this; it prevents "dangerous tool with default auto" accidents.
* Bundle violations into one disclosure. Agent-framework surfaces all detected `violations[]` in one approval request so approval cannot wave undisclosed risks (`python/packages/core/agent_framework/security.py:1889-1924`). Copy this bundling invariant wherever multiple risk detectors run.
* Bind approvals to the exact disclosed tuple. `_PendingPolicyApproval {body_signature, label_key, session_key, disclosed_violations}` (`security.py:1624-1639`) and SDK's SHA-256 invocation fingerprint (`src/agents/_tool_invocation.py:236-289`) both invalidate approval when the call or violation set changes. Generic "approve tool" is the bypass.
* Mirror authoritative semantics through MCP. Openhands' `ToolDefinition.annotations` (`web/src/features/mcp/core/define-tool.ts:52-61`) and agent-framework's MCP `always_require_approval`/`never_require_approval` lists (`python/packages/core/agent_framework/_mcp.py:77-88`) both normalize protocol hints into local policy — do this rather than asking models to infer risk.
* Make fail-closed visible. Emit audit/span on trip (`src/agents/tracing/span_data.py:292-313`), denial rate caps, and warning logs on sampling deny (`python/packages/core/agent_framework/_mcp.py:1435-1461`). Opa's masked-drop (`logs/plugin.go:785-788`) warns — ensure those warns are observable.

**Patterns to avoid or delay until needed:**

* Attaching structured risk metadata only after the fact. No dashboard surfaces "pending risky approvals by risk class" in any source (langfuse gap); instrument before you need incident response.
* Capability-tier tables before you have secrets. The two-tier mount table is excellent for its problem; applying it to generic CRUD tools adds ceremony with no field-level payoff.
* LLM-judged risk as the sole gate. Openhands gates on the model's own claim about its action (`action-event.ts:43-49`); reserve LLM signals for advisory triage and keep a deterministic threshold as the hard gate.

## Anti-Patterns / Caution Signs

* **Parsed-but-unenforced risk signals.** Agent-framework skill-frontmatter `allowed-tools` stored but never consulted (`python/packages/core/agent_framework/_skills.py:3477-3478` pattern); langfuse `InAppAgentPendingToolApproval` table retained but "background execution never reads or writes this table" (`packages/shared/prisma/schema.prisma:315-331`); `readOnlyHint`/`destructiveHint` used as de-facto safety signals without enforcement beyond admission (`web/src/features/mcp/server/registry.ts:176`). If you parse it, enforce it or remove the parser.
* **Name-based auto-approval.** Standing rules matching by bare tool name silently approve caller-named collisions (agent-framework `ToolApprovalMiddleware` warning `python/packages/core/agent_framework/_harness/_tool_approval.py:365-376`; file-access warning `python/packages/core/agent_framework/_harness/_file_access.py:1411-1420`). Switch to identity fingerprinting or server_label scoping.
* **Fail-open composition seams.** Policy enforcement that warns-and-continues when its prerequisite didn't run (`python/packages/core/agent_framework/security.py:1969-1976`: label tracker missing → pass). Assert prerequisite presence; don't degrade to allow.
* **Client-authored safety downgrade.** Openhands `buildStartConversationRequest` serializes whatever `confirmation_mode` the client holds into `confirmation_policy` (`src/api/agent-server-adapter.ts:1120-1121`), so any API caller can send `NeverConfirm` (`tests/e2e/live/utils/agent-server-conversation.ts:243-245`). Server must validate downgrades against permissions.
* **Binary risk collapse.** 90 tools → 1 bit (`auto`/`approval`) and read-only ↔ safe conflation (langfuse `registry.ts:176`). An operator cannot distinguish "expensive" from "destructive" from "PII-sensitive."
* **String-match egress control.** `verifyHost` literal compare (`v1/topdown/http.go:402-406`) bypassed by IP-literal vs hostname or IP-vs-IP literal mismatch; docs acknowledge (`docs/docs/policy-language.md:3728`) but behavior remains. Normalize/canonicalize.
* **Opt-in wiring as "control."** Capabilities, `allow_net`, strict builtin errors dormant unless configured (`v1/ast/compile.go:1014-1020`); SDK `needs_approval=False` default; sandbox `bash`/`write` outside approval entirely (`packages/shared/src/in-app-agent/server/mcpPolicy.ts:410-421`). Default-deny must be the shipped posture, not the documented one.
* **Silent auxiliary failures.** Opa's mask error that drops the event with only a local log line (`v1/plugins/logs/plugin.go:785-788`) and approval expiry with no notification (`web/src/features/in-app-agent/server/router.ts:124-131` "attention gap") both hide risk decisions exactly when audit needs them.

## Open Questions

* Is FIDES intended to unify `ApprovalMode` into a single descriptor ("untrusted-source tool writing PRIVATE data requires approval") or remain an optional experimental layer? Agent-framework gap frames promotion as future work; no ADR answers it.
* Can opa's aspirational `Categories` field (`v1/ast/builtins.go:3638-3640`) become an enforced classification (network/fs/crypto/dangerous) that `capabilities.json` and `allow_net` jointly enforce, and should it be exposed via `/v1/capabilities` at runtime rather than CLI-only?
* Why does langfuse's `readOnlyHint === true` remain the de-facto low-risk signal for ephemeral agent keys when a read-only bulk-PII tool (`listDatasets`) is as sensitive as many writes? No per-source rationale beyond MCP spec advisory.
* Should agent frameworks adopt a fixed risk taxonomy string (e.g., `data:exfiltration`, `cost:llm`) or leave risk as capability metadata plus an override header? Langfuse's `x-langfuse-in-app-agent-tool-override` (`mcpPolicy.ts:386-404`) shows the midpoint.
* Where is `alwaysAllowedTools` managed/revoked in langfuse, and should `admin=true` bypass emit an `adminOverride` audit flag distinct from policy grants (`packages/shared/src/features/rbac/projectAccessRights.ts:287`, `web/src/server/api/trpc.ts:320-360`)?
* Does openhands' server validate `confirmation_policy` downgrades, and what do `PatternSecurityAnalyzer`/`PolicyRailSecurityAnalyzer` (`agent-server-adapter.ts:611-614`) actually do — no implementation or E2E coverage exists in the studied frontend tree.
* For SDKs: should `needs_approval` be default-deny with a risk-category declaration (`risk_categories=["filesystem_write"]`) mapping to default controls, rather than opt-in per tool with no global inventory?
