## Executive Summary

Across all seven sources, the answer to the driving question — *can repeated identical requests avoid paying full cost each time?* — is **"only through provider-side prompt caching; never through local response memoization."** No source implements a client-side model-response cache. Instead, the sources split their effort along a clear line: model-call cost is treated as the provider's problem (steered via cache keys, breakpoints, and markers), while everything *around* the model call is treated as their own problem and solved aggressively — tool results, skill/tool-list discovery, task writes, storage inserts, telemetry export, embedding transport, and even UI rendering are cached or batched under strict safety disciplines.

Quality varies widely with product shape. pydantic-ai (8/10) and langfuse (8/10) demonstrate the two poles of maturity: pydantic-ai mechanically enforces prompt-cache prefix stability across its entire test corpus (`tests/cassette_utils.py:54-76`), while langfuse pairs two-tier caches with epoch-token invalidation and buffered storage writes backed by dedicated test suites. openai-agents-sdk (7/10) automates prompt-cache-key generation with a documented grouping hierarchy that survives resume; langgraph (7/10) ships a clean pluggable task-result cache with three backends but zero hit-rate observability. crewai (6/10) has guarded, tested mechanisms but uneven coverage and unbounded caches. agent-framework (5/10) shows exemplary internal cache engineering (skills discovery) but leaves the dimension's core surfaces as thin vendor pass-throughs. openhands (4/10) scores low only because it is a frontend that delegates inference entirely to an out-of-tree backend — judged purely as a client data layer it would score ~7.

Three findings are universal: failures are never cached; batching applies to everything except chat-model calls (embeddings, storage, telemetry, rendering — but never inference); and caching is opt-in or narrowly scoped by default because staleness is a correctness risk, not just a cost.

## Core Thesis

The studied harnesses converge on a division of labor: **delegate response-cost reduction to provider prompt caches, but own the steering, the observability, and every non-model repeated cost.** Concretely, they invest in three places — (1) making provider prefix caches *hit* (stable routing keys in openai-agents-sdk, explicit breakpoints in pydantic-ai, layout discipline in crewai); (2) making cache effectiveness *observable* (six of seven normalize cache-read/write tokens into usage contracts); and (3) eliminating their own repeated costs (single-flight fetches, result decorators, batch-shaped store APIs). Response memoization, embedding reuse, and LLM request batching are absent everywhere — mostly by deliberate, reasoned design (staleness danger, workload non-determinism) rather than neglect. The practical lesson: mature harnesses do not cache model outputs; they engineer the conditions under which providers discount them.

## Approach Models

- **agent-framework — delegate-to-provider + composable internal decorators.** Typed pass-through of provider knobs (`prompt_cache_key`, `prompt_cache_retention`, `prompt_cache_options`, Anthropic `cache_control` blocks) with no framework-level shaping; own caching confined to a well-engineered skills-discovery layer built as delegating decorators (`CachingSkillsSource` / `CachingAgentSkillsSource`) with single-flight fetches, monotonic-clock TTLs, isolation keys, and fail-open semantics (`python/packages/core/agent_framework/_skills.py:3810-3984`; `dotnet/src/Microsoft.Agents.AI/Skills/Decorators/CachingAgentSkillsSource.cs:32-148`). Cache economics normalized into core usage types plus a seven-vendor OTel alias table (`python/packages/core/agent_framework/_types.py:416-426`; `observability.py:384-400`).

- **crewai — opt-in tool-result cache + neutral breakpoint markers + batch-native memory.** A thread-safe `CacheHandler` keyed `"{tool}-{input}"` behind a reader-writer lock, wired through every tool-execution path, opt-in via `Crew(cache=True)`, refusing declared failures, vetoable per tool via `cache_function` (`lib/crewai/src/crewai/agents/cache/cache_handler.py:20-44`; `tools/base_tool.py:176-177`). Provider-agnostic `mark_cache_breakpoint` stamped by executors, translated to Anthropic `cache_control` by the adapter, stripped elsewhere (`lib/crewai/src/crewai/llms/cache.py:24-37`; `llms/providers/anthropic/completion.py:758-953`). Memory pipeline embeds whole batches in ONE call with intra-batch cosine dedup (`memory/encoding_flow.py:112-152`).

- **langfuse — layered platform-data caching + buffered storage batching.** Two-tier caches for hot ingestion lookups (model/pricing match: L1 LRU → L2 Redis → Postgres; API-key auth with sliding TTL; prompt resolution with epoch-token rotation instead of key scans), all env-gated, metric-instrumented, negative-caching, and fail-open (`packages/shared/src/server/ingestion/modelMatch.ts:26-42`; `web/src/features/public-api/server/apiAuth.ts:320-413`; `PromptService/index.ts:179-192`). A singleton `ClickhouseWriter` coalesces up to 1,000 rows or 1 s of writes per table, with retry → split → truncate → drop ladder (`worker/src/services/ClickhouseWriter/index.ts:46-65, 406-573`). LLM calls made by the platform itself are never cached or batched.

- **langgraph — pluggable task-result cache + storage-boundary batching.** A `BaseCache` ABC (in-memory, SQLite, Redis backends) caching node/task channel *writes* — state transitions, not raw completions — driven by per-node/per-task `CachePolicy(key_func, ttl)` with xxh3-128 hashed namespaced keys, bulk-fetched once per superstep and populated write-behind (`libs/checkpoint/langgraph/cache/base/__init__.py:15-48`; `libs/langgraph/langgraph/pregel/_loop.py:1549-1625`). An `AsyncBatchedBaseStore` coalesces queued store ops per event-loop tick with duplicate collapsing, and Postgres-store embeddings are issued one `embed_documents` call per op batch (`libs/checkpoint/langgraph/store/base/batch.py:58-101`; `libs/checkpoint-postgres/langgraph/store/postgres/base.py:1070-1088`).

- **openai-agents-sdk — auto-generated cache routing keys + immutable-by-contract metadata caches.** A per-run `PromptCacheKeyResolver` generates one stable `prompt_cache_key` scoped by grouping hierarchy (conversation → session → group → fresh run UUID), hashes session/group IDs, persists the key across resume in serialized state, and gates generation on official OpenAI endpoints only (`src/agents/run_internal/prompt_cache_key.py:17-130`; `run_grouping.py:12-34`). The MCP tool-list cache is dirty-flag based with deep-copy snapshot reads and manual invalidation (`src/agents/mcp/server.py:947-949, 1486-1489`). Cached-token aggregation feeds usage and spans (`src/agents/usage.py:71-108`).

- **openhands — client data-cache layer + render-boundary batching.** No direct LLM calls exist (CI-guarded ban on direct agent-server access, `src/api/no-direct-agent-server-calls.test.ts:1`); provider prompt caching is observed end-to-end (typed `cache_read_tokens`/`cache_write_tokens` fields → accumulation → UI panel) rather than constructed (`src/types/agent-server/core/events/conversation-state-event.ts:14-15`; `src/components/features/conversation/metrics-modal/usage-section.tsx:24-37`). Own costs are attacked at the presentation boundary: a `StreamingDeltaBatcher` commits at most one store update per animation frame (`src/utils/streaming-delta-batcher.ts:36-75`), REST reads use batch endpoints, module caches pair TTLs with explicit invalidation, and a version cache adds single-flight coalescing plus negative entries (`src/hooks/query/use-automation-sdk-version.ts:43-69`).

- **pydantic-ai — prompt caching as an engineered, CI-guarded feature.** A portable `CachePoint` message part carries explicit boundaries inside serialized history (`pydantic_ai_slim/pydantic_ai/messages.py:761-788`); provider-namespaced settings expose Anthropic automatic/per-block caching, OpenAI keys/options, Google `cached_content`, Mistral keys (`models/anthropic.py:409-461`; `models/openai.py:585-698`). Static-before-dynamic instruction ordering positions boundaries after stable prefixes (`models/__init__.py:222-230`); Anthropic's four-breakpoint budget is enforced by newest-first trimming with `UserError` on unfixable overflow (`models/anthropic.py:2262-2333`). Uniquely, a suite-wide invariant fails any recorded cassette whose consecutive requests move the wire prefix without a written waiver (`tests/cassette_utils.py:54-76`). The Prefect durable-execution integration is the study's only cross-run response-reuse mechanism, keyed by hand-authored input projections (`durable_exec/prefect/_cache_policies.py:199-224`).

## Pattern Catalog

### P1. Steer, don't store: provider-managed prompt caching via keys, breakpoints, and markers
- **Problem:** Repeated prompt prefixes pay full input-token cost on every turn.
- **Demonstrated by:** All seven sources observe provider caching; five actively steer it — pydantic-ai (`messages.py:761-788`, `models/openai.py:585-609`), openai-agents-sdk (`prompt_cache_key.py:17-66`), crewai (`llms/cache.py:24-37`), agent-framework (`python/packages/openai/.../_chat_client.py:227-239`), and openhands renders the backend's retention knob schema-driven (`src/utils/sdk-settings-field-metadata.ts:25-31`). LangGraph only passes content through unchanged (`libs/langgraph/langgraph/graph/message.py:143-160`).
- **Why it works:** Providers discount identical prefixes; the client needs only a stable routing identity plus explicit boundaries. openai-agents-sdk's hierarchy prevents unrelated traffic from sharing cache groups (`run_grouping.py:12-34`).
- **When to copy:** Multi-turn agents, shared system prompts, high-volume similar traffic.
- **When risky/overkill:** Providers without support or below minimums (OpenAI's 1024-token minimum, `docs/models/openai.md:146` per pydantic-ai report); single-shot tiny prompts. Savings are unverifiable client-side — openai-agents-sdk notes the contract "ends at placing the field" (`prompt_cache_key.py:105-107`).
- **Evidence:** See per-source refs above; all confirmed by tests (e.g., `tests/test_prompt_cache_key.py:39-269`, `lib/crewai/tests/llms/test_prompt_cache.py:14-191`).

### P2. Failures, cancellations, and control records never enter the cache
- **Problem:** A cached transient error converts a blip into a permanent outage for the cache's lifetime; cached interrupt/error records would break resumption semantics.
- **Demonstrated by:** Four independent implementations — crewai refuses `ToolFailure` (`cache_handler.py:38-41`, tested `tests/tools/test_tool_failure.py:915-930`); agent-framework never caches failed/cancelled fetches on both stacks (`_skills.py:3981-3984`; `CachingAgentSkillsSource.cs:77-82` with a cancellation test matrix); langgraph excludes INTERRUPT/ERROR writes on the async path (`_loop.py:1872-1874`); langfuse fails open, falling through to the source of truth on any cache error (`PromptService/index.ts:159-163`).
- **Why it works:** Preserves the invariant that cache hits imply successful past executions.
- **When to copy:** Always — this is near-universal consensus across heterogeneous codebases.
- **Risks:** The asymmetry means successes can rot while failures can't be frozen (documented in crewai report, `cache_handler.py:26-29`).
- **Evidence:** Refs above; each backed by dedicated regression tests per source reports.

### P3. Single-flight / in-flight request coalescing
- **Problem:** Concurrent identical expensive lookups stampede the backend.
- **Demonstrated by:** agent-framework's double-checked locking with per-key asyncio locks / `SemaphoreSlim(1,1)` gates (`_skills.py:3941-3984`; `CachingAgentSkillsSource.cs:60-88`); openhands' shared-promise map (`sdkVersionRequests`, `use-automation-sdk-version.ts:47-68`); langgraph's store-op deduper mapping duplicates to the first occurrence's index and its per-tick input cache (`store/base/batch.py:283-323`; `_algo.py:1357-1392`).
- **Why it works:** Collapses N identical costs into one remote call while queuing callers transparently.
- **When to copy:** Any cache miss that triggers remote I/O.
- **When overkill:** Cheap local computations; already-coalesced layers (TanStack Query handles this for openhands queries).
- **Evidence:** Refs above; agent-framework additionally tests first-caller-cancel/all-cancel/no-poisoning matrices (`CachingAgentSkillsSourceTests.cs:198-325`).

### P4. Negative caching for common misses
- **Problem:** Hot misses hammer the source of truth (auth checks against deleted keys, unmatched models, config-less projects).
- **Demonstrated by:** langfuse systematically (`NOT_FOUND_TOKEN` for models, `API_KEY_NON_EXISTENT`, no-eval-configs markers — `modelMatch.ts:308-325`; `packages/shared/src/server/auth/types.ts:38`; `evalJobConfigCache.ts:21-99`); openhands caches `null` SDK-version probes for the TTL (`use-automation-sdk-version.ts:60-63`).
- **Why it works:** Protects backing stores from miss storms on read-heavy paths.
- **When to copy:** Lookup paths where absence is a frequent, legitimate answer.
- **When risky:** Setup friction — newly created entities stay invisible until TTL expiry or explicit clearing (langfuse accepts this knowingly with clear functions; see tradeoffs below).
- **Evidence:** Refs above, including langfuse's project-scope clearing tests covering not-found tokens (`worker/src/__tests__/modelMatch.test.ts:61-360`).

### P5. Immutability-on-read (snapshot discipline)
- **Problem:** Callers mutating cached structured objects poison subsequent readers.
- **Demonstrated by:** openai-agents-sdk deep-copies every returned MCP tool so schema tampering cannot bypass validation (`mcp/server.py:131-133, 1486-1489`, tested `tests/mcp/test_caching.py:242-272, 280-329`); pydantic-ai deepcopies memoized validated stream outputs on every yield (`result.py:76-77, 231-242`); crewai strips cache markers in copies only so executor buffers survive iterations (`base_llm.py:825-850`, pinned by `test_prompt_cache.py:30-50`).
- **Why it works:** Sharing mutable cached structures across trust boundaries is a latent corruption bug; snapshots make corruption structurally impossible.
- **When to copy:** Any cache handing structured values to third-party code.
- **Cost:** CPU for large catalogs (acknowledged by openai-agents-sdk report).
- **Evidence:** Refs above.

### P6. Prefix-stability engineering (layout rules + mechanical enforcement)
- **Problem:** Dynamic content early in the prompt silently busts provider caches — a regression that surfaces no error (pydantic-ai's own AGENTS.md wording).
- **Demonstrated by:** pydantic-ai most thoroughly: static-before-dynamic instruction ordering (`models/__init__.py:222-230`; `models/anthropic.py:2230-2254`), deferred-tool relocation, tool retention for stability (`toolsets/_tool_search.py:366-371`), and the corpus-wide cassette invariant with waiver markers (`tests/cassette_utils.py:54-76`). crewai renders volatile date at the prompt tail and uses content-matching (not positional indexing) to stamp breakpoints after formatter rewrites (`prompts.py:143-163`; `completion.py:758-796`). openai-agents-sdk contributes stable key grouping so prefixes group predictably (`run_grouping.py:12-34`).
- **Why it works:** Cache hits require byte-stable prefixes; mechanical gates catch regressions that review misses, converting correctness into a CI property.
- **When to copy:** Whenever prompts are assembled programmatically at scale — the invariant especially.
- **When overkill/risky:** Maintenance overhead when dynamism is legitimate (waivers required); advisory tables cannot catch runtime busts (client-side tool filtering silently breaks prefixes with no signal except `cache_read_tokens == 0`, per pydantic-ai residual risks).
- **Evidence:** Refs above.

### P7. Batch-shaped APIs and boundary batching — for everything except model calls
- **Problem:** Per-item round trips dominate latency and cost.
- **Demonstrated by:** Batch-shaped contracts pushing batching into the API itself: langgraph's bulk `cache.get(tuple(keys))` per superstep and `abatch(dedupped)` stores (`_loop.py:1553-1558`; `batch.py:58-101`); langfuse's ClickhouseWriter size/time triggers with producer-side S3 event grouping sorted updates-last (`index.ts:46-65`; `processEventBatch.ts:201-294, 441-460`); trace exporters batching spans (openai-agents-sdk `processors.py:541-582`; agent-framework OTel processors `observability.py:1021-1063`; crewai `TraceBatch`); embedding batching everywhere it exists (crewai one-call `embed_texts` `types.py:312-339`; pydantic-ai Bedrock single-request batch vs semaphore fan-out `embeddings/bedrock.py:580-643`; langgraph Postgres store one `embed_documents` per op batch); and render batching in openhands (≤1 commit/frame, byte-exact over 5000 sub-frame deltas, `streaming-delta-batcher.test.ts:145-172`).
- **Why it works:** Amortizes transport/locks/render work; write-behind variants keep critical paths responsive (langgraph submits cache sets off-path, `_loop.py:1617-1625`).
- **When to copy:** Universally, for storage/telemetry/embedding/render boundaries.
- **Note:** Chat-model calls are batched by **zero** of seven sources — concurrency substitutes (see Key Differences).
- **Evidence:** Refs above; langfuse's writer ladder is unit-tested down to drop-after-max-attempts (`ClickhouseWriter.unit.test.ts:66-530`).

### P8. Identity-keyed serialization micro-caches
- **Problem:** Re-serializing unchanged structures per request/event dominates instrumentation cost.
- **Demonstrated independently by two sources:** agent-framework caches serialized OTel tool JSON in a `WeakKeyDictionary` keyed by object identity with a sentinel distinguishing cached-None from never-computed (`observability.py:2485-2551`); pydantic-ai's `MessageJsonCache` pins the message object itself so an `id()` collision after GC cannot serve stale fragments, evicts per request, and detects in-place mutation by re-serialization compare (`_instrumentation.py:91-120, 256-274`).
- **Why it works:** Makes span attributes O(new messages) instead of O(history) while entries die with their objects.
- **When to copy:** Per-request derived artifacts keyed to object lifetimes.
- **Risk:** Identity ≠ equality; both sources implement exactly the guards (weak refs / pinned identity + staleness detection) needed to avoid serving garbage.
- **Evidence:** Refs above.

### P9. Epoch-token rotation for scoped invalidation
- **Problem:** Invalidating many cached keys safely requires scans and races.
- **Demonstrated clearly by langfuse alone:** `invalidateCache` writes a fresh project-scoped random epoch token (48-bit, SET NX with winner re-read); old keys expire naturally — O(1) writes, zero scans, cluster-safe initialization (`PromptService/index.ts:179-192, 216-240`).
- **Why it works:** Turns bulk invalidation into a pointer flip when keys encode the epoch.
- **When to copy:** Keys sharing a scope where TTL-bounded staleness is acceptable and writers are known.
- **When not:** Precise per-entity freshness (langfuse uses exact deletes for API keys instead, `invalidateApiKeys.ts:24-50`).
- **Evidence:** Refs above, covered by `web/src/__tests__/server/promptCache.servertest.ts:62-280`.

## Key Differences

Clustering before comparing, three approach families emerge:

**Cluster 1 — Provider-steering frameworks** (pydantic-ai, openai-agents-sdk, crewai, agent-framework): none caches responses; all steer provider prompt caches. They diverge on depth. pydantic-ai engineers boundaries as portable message content plus a CI invariant; openai-agents-sdk automates key generation with lifecycle persistence and conservative endpoint gating; crewai defines a neutral marker protocol translated per adapter; agent-framework ships thin typed pass-throughs with no shaping guidance ("nothing stabilizes system-prompt ordering," per its report). Depth correlates with how central multi-turn chat is to the product.

**Cluster 2 — Internal-result caches** (langgraph, agent-framework skills, crewai tools, openai-agents-sdk MCP lists): all four cache expensive non-model operations, but the unit differs meaningfully. langgraph caches state *transitions* (channel writes replayed on hit, keeping reducer semantics intact — `test_pregel.py:2807-2874` asserts identical end state with/without cache); the others cache metadata or tool *outputs*. That difference drives safety policy: agent-framework auto-wraps only context-independent built-in leaf sources and refuses caller-supplied ones because shared-bucket caching would leak one context's skills into another (`_skills.py:2143-2147`), while crewai makes tool caching opt-in entirely because replaying stale output was "silently wrong for live-data tools" (`tests/test_tool_cache_default.py:1-15`).

**Cluster 3 — Platform/application data layers** (langfuse, openhands): caching targets their own hot paths (auth, prompt resolution, settings, SDK versions), never models. This is a valid response to product shape, not lower quality — langfuse explicitly reasons that stale cached eval scores would be *wrong*, not free, and openhands structurally cannot make LLM calls (its score reflects scope coverage, not mechanism quality).

Other principled divergences:

- **Backend-outage semantics:** langfuse fails open with metrics (degradation visible, requests succeed); langgraph's Redis backend swallows errors silently (uptime maximized, but "a degraded Redis silently disables caching — cost regression invisible to operators"); SQLite/memory backends error loudly. Same goal, different consistency/visibility tradeoffs.
- **Invalidation strategy follows mutability:** epoch rotation for prompts (langfuse), precise deletes for mutable auth keys (langfuse), manual dirty-flag invalidation for append-mostly tool catalogs (openai-agents-sdk, openhands), explicit `clear_cache` APIs for computed task results (langgraph), and TTL-only for low-harm pricing drift (langfuse model-match L1).
- **Concurrency vs batching for models:** every source runs concurrent-not-batched (langgraph `BackgroundExecutor`, agent-framework `asyncio.gather` tool batches, crewai `ThreadPoolExecutor(max_workers=10)` memory consolidation, pydantic-ai concurrency limiters). langgraph's report names the cost directly: streaming/interrupt semantics are preserved but "provider batch pricing and cross-request prefix reuse" are forfeited — deliberately pushed onto model wrappers outside the orchestrator.

These differences are constraint-driven, not quality-ranked: an orchestrator (langgraph) cannot assume determinism; an observability platform (langfuse) sees user-driven evaluations; a frontend (openhands) owns neither inference nor retrieval; a dual-language framework (agent-framework) pays a parity tax implementing every semantic twice.

## Tradeoffs

- **Freshness vs repeat cost on responses.** All seven sources guarantee freshness at full price; none memoizes production traffic. The alternative appears exactly once, scoped where determinism dominates: pydantic-ai's Prefect integration replays persisted model-response tasks on flow retry (`_cache_policies.py:199-224`) — evidence that response caching is viable precisely when the workload tolerates staleness.
- **Prompt-steering depth vs maintenance burden.** agent-framework's thin pass-through minimizes maintenance and version coupling but offers no hit-rate help (users must even know `prompt_cache_options` requires `openai>=2.45.0` — runtime guard at `_chat_client.py:1404-1407`); pydantic-ai's deep engineering raises hit rates but adds waiver-marking overhead on every legitimate prefix change and version-adaptive fallback complexity elsewhere (compare openai-agents-sdk's gating approach as the middle path).
- **Auto-caching vs opt-in for side-effectful results.** agent-framework auto-wraps vetted static sources (fast, but requires leak-proof isolation-key design and still grows unbounded without TTL); crewai opts users in explicitly (safe for live-data tools, but users who skip the flag pay full duplicate-execution cost — accepted explicitly in `crew.py:232-237`).
- **Simplicity vs boundedness.** Plain dict caches (crewai `CacheHandler`, agent-framework skill buckets) have no eviction and grow monotonically; langfuse's sized LRUs bound memory but ship the L1 disabled-by-default, signaling the team didn't consider it proven enough to default-on.
- **Availability vs visibility during backend degradation.** langfuse's fail-open-with-metrics surfaces degradation immediately; langgraph's silent-swallow Redis trades operator awareness for uptime. Both are tested behaviors (`promptCache.servertest.ts:237-280`; `test_redis_cache.py:223-266`).
- **Throughput vs durability in batch buffers.** langfuse's ClickhouseWriter buys massive insert efficiency but loses the in-memory buffer on hard crash and drops rows after three failed attempts with only metrics/logs (DLQ noted as TODO, `index.ts:544-548`); openai-agents-sdk's trace processor likewise drops telemetry on queue-full rather than blocking runs. Contrast: agent-framework's fail-open *fetch* semantics degrade to latency, never to stale-or-lost data.
- **Hygiene vs debuggability in key design.** openai-agents-sdk hashes session/group IDs before they leave the process (`prompt_cache_key.py:119-121`) preventing leakage but complicating cross-referencing sent keys back to sessions.
- **Embedding freshness vs spend.** langgraph re-embeds on every put/search — correct under churn but doubles cost on churn-heavy workloads; crewai's indirect reuse (ChromaDB persistence keeps stored chunks embedded, updated records carry old vectors forward when re-embedding fails, `encoding_flow.py:468-470`) saves money at the cost of eventual staleness. Neither builds an actual memoization layer.

## Decision Guide

Choosing between the main approaches found across sources:

1. **Interactive/multi-turn workloads with stable prefixes → provider-steered prompt caching.** Prefer explicit boundaries as message content (pydantic-ai's `CachePoint` survives serialization/persistence) when you control history assembly; prefer generated routing keys (openai-agents-sdk style) when you want zero per-user effort; add layout discipline (static-before-dynamic ordering, volatile data at tail) before adding either.
2. **Expensive operation with static/context-independent inputs (catalog discovery, skill enumeration) → internal decorator/result cache** with the full discipline stack: single-flight + TTL + isolation keys + failure-refusal (agent-framework pattern). If inputs are context-dependent or side-effectful, flip to opt-in with per-item veto (crewai pattern) instead of auto-wrapping.
3. **Repeated identical model requests must be cheap (evals, replay, durable execution) → scoped response memoization**, not a general response cache. Key by projected semantic inputs, strip per-run fields, and require exhaustive field categorization so new fields can't silently collide (pydantic-ai Prefect policy). Do not ship this on production traffic paths — no source does.
4. **Read-heavy lookup path where absence is common → negative caching** with explicit clear-on-create hooks (langfuse pattern).
5. **Many concurrent identical fetches possible → single-flight wrapper** regardless of whether a cache exists (all three demonstrating sources treat it as an independent concern).
6. **Invalidation strategy rule:** known writers + precise freshness → event-driven delete; scoped bulk expiry acceptable → epoch rotation; append-only/static → manual invalidation with dirty flags; derived-from-input → TTL only. Pair every TTL with explicit invalidation invoked from mutation paths (openhands discipline) — or accept the staleness window knowingly (langfuse).
7. **Never cache:** failures, cancellations, interrupt/control records (four-source consensus), and anything whose staleness is a correctness hazard rather than a cost.

## Practical Tips

- **Put cache tokens in your usage contract from day one.** Every mature source normalizes `cache_read`/`cache_write` into core types with alias tables reconciling vendor naming (agent-framework `_types.py:416-426` + `observability.py:384-400`; pydantic-ai `usage.py:96-119`; openai-agents-sdk `usage.py:71-108`). Retrofitting observability is far harder than reserving the fields.
- **Enforce prefix stability mechanically, not by review.** pydantic-ai's cassette invariant (`check_cache_prefix_stability`, `tests/cassette_utils.py:54-76`) converts a silent cost regression into a red build — the highest-leverage testing idea in this dimension.
- **Render volatile content at the prompt tail** so everything ahead stays a stable anchor (crewai `prompts.py:143-163`).
- **Anchor per-request injections to positions that don't move with history length**; moving anchors shift the cacheable prefix every turn and surface no error (pydantic-ai AGENTS.md token-counting rule).
- **Make cached values immutable-on-read** via deep-copy snapshots when third-party code receives them (P5), or pin identity with staleness detection (P8).
- **Wrap remote-fetching caches in single-flight** and test cancellation matrices (first-caller-cancel, all-cancel, no-poisoning) as agent-framework does.
- **Batch embeddings and telemetry even though you'll never batch chat calls** — every source does exactly this split.
- **Emit hit/miss metrics from generic cache primitives**, not ad-hoc maps (langfuse `LocalCache<V>` with namespace-tagged counters, `localCache.ts:18-141`); it makes degradation diagnosable and enables the hit-ratio analytics all sources list as future work.
- **Give items a replay-safety veto** (crewai's `cache_function`) and document which operations are unsafe to replay — only the tool author knows.
- **Manage breakpoint budgets explicitly** for Anthropic's four-slot limit: trim newest-first, raise a typed error when system+tools alone exceed budget (pydantic-ai `anthropic.py:2277-2333`).
- **Surface cache hits into domain events** (`from_cache` on tool events, crewai) so dedup behavior is auditable at the product level, not just in metrics.

## Anti-Patterns / Caution Signs

- **Order-sensitive string cache keys.** crewai keys are `f"{tool}-{input}"` with raw `json.dumps` — semantically identical arguments with different key insertion order produce false misses, with no normalization or TTL (`tools_handler.py:43-44`). Canonicalize keys (sorted keys/hashing) before shipping.
- **None-as-miss ambiguity.** crewai's `read(): Any | None` means tools legitimately returning `None` re-execute forever (`tool_usage.py:309-312`). Distinguish "cached empty" from "never computed" (agent-framework's `_CACHE_MISS` sentinel exists precisely for this).
- **Unbounded process-local caches.** Both crewai's handler and agent-framework's skills buckets grow monotonically with acknowledged-but-unenforced limits — a long-running host leaks until restart unless configured otherwise.
- **Silent backend degradation without metrics.** langgraph's swallowing Redis hides cost regressions from operators; if you must swallow errors, emit counters (langfuse pattern) so degradation is visible.
- **Module singletons relying on hand-placed invalidation.** openhands' settings cache has no backend-scoped keys; correctness depends entirely on every mutation hook remembering `invalidateCache()` — "a fragile-by-convention invariant." Scope keys by tenant/backend instead (as its own version cache does).
- **Moving cache anchors.** Injections positioned relative to history length shift the cacheable prefix every turn (pydantic-ai codified this as an anti-pattern rule).
- **Coverage gaps in stamping/wiring.** crewai's LiteAgent path lacks breakpoint stamping entirely, silently relegating those runs to implicit caching; partial coverage reads as full coverage to users.
- **Docs/code drift on defaults.** crewai docs claim caching "Defaults to True" while code defaults False — users assume dedup behavior that isn't active. Keep default documentation generated from code.
- **Invisible prefix busts from client-side filtering.** Restricting tools client-side can invalidate provider prefixes with no runtime signal — only post-hoc `cache_read_tokens == 0` hints at it (pydantic-ai residual risk). Watch for this ratio dropping after logic changes.
- **Concurrency mistaken for batching.** Parallel fan-out preserves streaming semantics but forfeits batch pricing and cross-request prefix sharing (langgraph analysis); know which lever your workload actually needs.

## Notable Absences

- **No client-side model-response cache anywhere (7/7 sources).** The universal decision of this dimension; the only response-reuse mechanism in the entire study is pydantic-ai's Prefect-scoped durable-task cache.
- **No embedding memoization/reuse in any source that computes embeddings (4/4: agent-framework, crewai, langgraph, pydantic-ai).** Embeddings are batched everywhere they exist but re-computed for identical strings every time; pydantic-ai's grep found zero cache references across all 13 embedding modules.
- **No LLM request batching anywhere (7/7).** Batching is applied to embeddings, storage writes, telemetry export, and rendering — never to inference requests.
- **Minimal prompt-shaping automation.** Beyond pydantic-ai/crewai layout efforts, nothing stabilizes serialization order or places breakpoints automatically (agent-framework names this gap explicitly).
- **Incomplete hit-rate observability.** Raw counters exist broadly (6/7 — langgraph has none at all), but first-class ratios are rare (pydantic-ai's `cache_hit_ratio()`, `usage.py:204-216`, is the exception; openhands shows raw rows without a computed ratio; multiple sources list surfacing ratios as future work).
- **No retrieval-result caching wherever retrieval exists.** crewai's targeted search of `rag/` returned zero matches; agent-framework found none across its search/history providers; langgraph offers only node-level opt-in memoization.
- **No dead-letter handling for dropped batch records** (langfuse TODO), and **no benchmark/load-test evidence** of cache effectiveness under scale in any repo — quality judgments rest on unit tests, not production telemetry.

## Per-Source Notes

- **agent-framework (5):** Best-in-study internal cache engineering (dual-stack single-flight skills decorators with cancellation matrices) attached to the thinnest core-dimension surface; provider knobs passed through unshaped; Go implementation out of scope. Distinctive: cross-language port discipline and the deliberate refusal to auto-cache caller-supplied context-aware sources.
- **crewai (6):** The only tool-*result* cache in the study, with the strongest safety story (opt-in default flipped by a documented incident, per-tool vetoes, failure refusal, observable `from_cache`) undermined by unbounded order-sensitive keys, missing LiteAgent stamping, and a docs/default contradiction. Distinctive: batch-native memory pipeline with intra-batch cosine dedup.
- **langfuse (8):** The reference implementation for platform-data caching discipline — two tiers, negative caching, three distinct invalidation strategies matched to data mutability, self-healing zod validation, sliding TTLs, cluster-aware plumbing — applied entirely outside the model boundary; its writer's drop-after-retry row loss is the study's most significant durability gap.
- **langgraph (7):** Cleanest cache abstraction (six-method ABC, three backends, batch-shaped contract) caching the most interesting unit (state transitions preserving reducer semantics), limited by zero observability, silent Redis failure, pickle-based default keys, and a flagged medium-severity deserialization consideration in the cache layer.
- **openai-agents-sdk (7):** Most automated prompt-cache steering (generated keys with grouping hierarchy, resume persistence, endpoint gating, user-intent precedence) plus corruption-proof metadata caching; hampered by no TTLs anywhere and fundamentally unverifiable server-side savings.
- **openhands (4):** Scope-limited by architecture (no LLM calls in-tree); what exists is a disciplined frontend data layer — frame-bounded delta batching with byte-exactness tests, single-flight, negative caching, TTL+invalidation pairing — with prompt caching observed but not controllable, and one convention-fragile settings singleton worth redesigning.
- **pydantic-ai (8):** Deepest prompt-cache engineering in the study: portable in-content boundaries, budget-aware trimming, unified retention resolution, measured-behavior encoding, and a CI-enforced prefix-stability net; main weakness is friction-heavy explicitness plus the Prefect-only response-reuse story.
