## Executive Summary

Nine sources were analyzed for how they define the smallest meaningful unit of execution. Eight are real implementations spanning libraries (pydantic-ai, openai-agents-sdk, langgraph, agent-framework, crewai), servers (letta, openhands), and a distributed workflow engine (temporal). One (`reports`) is an empty output scaffold with no code at all (1/10); it contributes no implementation evidence but accidentally demonstrates the exact hazard this dimension probes — a created-but-unpopulated directory slot that persists as a torn state with nothing to distinguish "not yet run" from "ran and produced nothing" from "crashed mid-write" (reports analysis, scan record R1–R3 at `reports/source/01.03-step-turn-task-atomicity/reports.md:97-99`).

Three findings dominate the real implementations. First, **no system unifies the atomic unit across persistence, retry, tracing, and UI** — all eight answer the alignment question with an explicit "No," and the mature ones treat the divergence as a designed, documented tiering rather than an accident (langgraph: `libs/langgraph/langgraph/types.py:626-640`; letta: `letta/schemas/step.py:16-65`; openai-agents-sdk: `src/agents/run_internal/run_steps.py:178`; temporal: `docs/architecture/chasm.md:216-238`). Second, **the retried unit is almost always finer than the persisted unit**: the model call retries inside letta's Step (`letta/agents/letta_agent_v3.py:1093`), inside openai-agents-sdk's turn (`src/agents/run_internal/model_retry.py:511`), and inside crewai's Task loop (`agents/crew_agent_executor.py:460`); langgraph retries task attempts between superstep checkpoints (`libs/langgraph/langgraph/pregel/_retry.py:615`). Third, **tool calls are first-class atomic units in only two of eight systems** (agent-framework's `_auto_invoke_function` pipeline at `_tools.py:1424-1645`; pydantic-ai's per-tool budgets plus Temporal `call_tool_activity` at `durable_exec/temporal/_function_toolset.py:43-105`), while langgraph, openai-agents-sdk, letta, and openhands deliberately absorb them into a larger unit.

Scores land in two bands among the real sources: 7/10 for clear-but-ununified or partially-enforced models (agent-framework, crewai, letta) and 8/10 for models with explicit transactional, schema-versioned, or engine-delegated safety nets (langgraph, openai-agents-sdk, pydantic-ai, temporal); openhands sits at 6/10 because its event ledger cannot actually answer "what completed and what did not" across a partial batch save (`openhands/app_server/event_callback/webhook_router.py:519-522`). What separates the bands is not vocabulary richness — every source has plenty — but whether crash-mid-step recovery is enforced by a transactional boundary, a schema-gated snapshot, or an engine contract, versus merely claimed by convention.

## Core Thesis

**Atomic-unit design is dictated by product shape, and maturity is determined by how honestly the system answers one question: can it say exactly what completed and what did not?**

Every source converges on tiering the atomic unit differently for persistence, retry, tracing, and UI — the divergence itself is universal and correct. What varies is the strategy for keeping those tiers consistent under failure:

1. **Barrier strategies** (langgraph supersteps, agent-framework workflow commits, temporal DB transactions) persist coarse boundaries and recover by replaying forward from the last durable boundary, discarding partial in-boundary work. langgraph makes durability a configurable axis precisely because the right coarseness is deployment-dependent (`libs/langgraph/langgraph/types.py:87-93`).
2. **Named-record strategies** (letta's Step rows, pydantic-ai's node snapshots, openai-agents-sdk's RunState) persist a typed record per unit with an explicit status lifecycle, so an interrupted unit is visible even if not resumable. letta writes the Step row as `PENDING` before the LLM call fires specifically for early observability (`letta/agents/letta_agent_v2.py:946-962`).
3. **Ledger strategies** (crewai's event DAG, openhands' opaque event files) record fine-grained events and infer completion from started/finished pairs. This gives the best forensic story and the weakest recovery story — crewai pairs it with opt-in checkpointing (`state/checkpoint_config.py:171-175`), while openhands returns HTTP `Success` even after a partial batch save, making gaps permanent (`openhands/app_server/event_callback/webhook_router.py:520-522`).
4. **Engine-delegation strategies** (pydantic-ai's Temporal/Prefect wrappers, temporal natively) push atomicity down into engine-native units — activities, tasks, transactions — inheriting proven retry and durability semantics rather than reimplementing them (`pydantic_ai_slim/pydantic_ai/durable_exec/temporal/_model.py:84-129`, `service/history/workflow/mutable_state_impl.go:7484-7528`).

A system's rating tracks how many of these layers it composes *and* how honestly it surfaces partial states. openai-agents-sdk scores high not because tool calls are atomic (they are not) but because its persist-counter and fingerprint rewind make the non-atomic window explicitly reconstructable (`src/agents/run_state.py:263-264`, `src/agents/run_internal/session_persistence.py:416-468`). openhands scores low not because events lack structure but because a mid-batch failure is reported as success, collapsing three distinct states into one indistinguishable on-disk appearance.

## Approach Models

Clustering by dominant strategy, using the dimension's vocabulary (persisted / retried / traced / shown unit):

### Model A — Barrier checkpointing (langgraph, agent-framework workflows, temporal)

The smallest **persisted** unit is a boundary commit: langgraph's superstep triggers the loop's only regular `_put_checkpoint({"source": "loop"})` (`libs/langgraph/langgraph/pregel/_loop.py:706`); agent-framework's runner calls `State.commit()` then `_create_checkpoint_if_enabled` after each superstep (`_workflows/_runner.py:141-144`); temporal flushes MutableState + history events + queued tasks in one DB write via `CloseTransactionAsMutation|Snapshot` (`service/history/workflow/mutable_state_impl.go:7484-7573`). The smallest **retried** unit is finer: langgraph's `PregelExecutableTask` attempt with its own `retry_policy` and pre-attempt `task.writes.clear()` (`libs/langgraph/langgraph/pregel/_retry.py:615-617`); temporal's Executable with Nack/reschedule (`service/history/queues/executable.go:680-715`). The **traced** unit is the task attempt (langgraph's `langgraph_step` metadata under a `graph:step:{n}` span, `libs/langgraph/langgraph/pregel/_algo.py:654-717`; temporal's OTEL span wrapping `Executable.Execute()`, `service/history/queues/executable.go:259-300`). The **shown** unit is mode-dependent in langgraph (seven stream modes expose step, task, or checkpoint, `libs/langgraph/langgraph/types.py:120-134`) and is the Workflow Task turn in temporal (`service/history/workflow/workflow_task_state_machine.go:39-60`). agent-framework adds a distinctive twist: the checkpoint also captures `pending_request_info_events`, so a paused-for-human run resumes with its outstanding question intact (`_workflows/_checkpoint.py:60`, restore at `_workflows/_runner_context.py:414-426`).

### Model B — Named-record lifecycle (letta, pydantic-ai nodes, openai-agents-sdk turns)

The persisted unit is a typed record whose lifecycle is explicit. letta persists a `Step` row (`PENDING → SUCCESS/FAILED/CANCELLED`, `letta/schemas/enums.py:268-274`) owned by a `Run`, with messages batch-written only at step success (`letta/agents/letta_agent_v3.py:1404-1410`). pydantic-ai snapshots graph nodes with `SnapshotStatus ∈ {created, pending, running, success, error}` and drives them through a `record_run` context manager that records duration and terminal status (`pydantic_graph/pydantic_graph/persistence/__init__.py:32-103`, `in_mem.py:55-74`). openai-agents-sdk persists turn items into a session plus a schema-versioned `RunState` JSON payload (`CURRENT_SCHEMA_VERSION = "1.11"` with fail-fast version gating, `src/agents/run_state.py:124-149`). In all three, the **retried** unit drops below the persisted one: letta retries the inner LLM request with fallback-model swap and compaction (`letta/agents/letta_agent_v3.py:1093,1183-1299`); openai-agents-sdk retries the model request and rewinds session/server tails (`src/agents/run_internal/model_retry.py:511-608`); pydantic-ai splits budgets between global output retries and per-tool `max_retries` counters (`tool_manager.py:177-181`, `_agent_graph.py:162-179`). Tracing aligns with the named record — letta's `agent_step` OTel span correlated via `step.trace_id`/`request_id` columns (`letta/services/step_manager.py:157-158`); openai-agents-sdk's strict `Trace → TaskSpan → AgentSpan → TurnSpan → Generation/Function span` hierarchy (`src/agents/tracing/span_data.py:64-451`). The shown unit is the same record: SSE chunks per Step in letta, `RunItemStreamEvent`s per item in openai-agents-sdk.

### Model C — Event ledger (crewai, openhands)

The atomic markers are event pairs. crewai brackets every action with started/finished/error events recorded into an `EventRecord` directed graph wired by parent/trigger/previous edges (`events/base_events.py:82-87`, `state/event_record.py:99-225`); persistence is separately tiered through `CheckpointConfig` (default `["task_completed"]`, optional `["*"]` per-event snapshots onto pluggable JSON/SQLite providers, `state/checkpoint_config.py:171-182`). openhands persists one opaque SDK `Event` per UUID-named file or blob with no batching or transaction (`openhands/app_server/event/filesystem_event_service.py:33-36`); its only state machine is the coarse 8-state `AppConversationStartTaskStatus` setup workflow yielded and persisted per transition (`openhands/app_server/app_conversation/app_conversation_models.py:262-271`). In this model the **shown** unit is rich (crewai's console formatter consumes the whole event stream) while the **retried** unit is thin — openhands has essentially no per-event retry, only callback polling and export locks (`openhands/app_server/event_callback/set_title_callback_processor.py:32-34`).

### Model D — Engine delegation overlay (pydantic-ai durable_exec, temporal native)

Rather than inventing durability, map framework units onto an engine's native ones. pydantic-ai wraps the model request in `TemporalModel.request_activity`, each tool call in `TemporalFunctionToolset.call_tool_activity`, and MCP I/O likewise, with Prefect and DBOS equivalents sharing one `AbstractToolset` interface (`durable_exec/temporal/_model.py:84-205`, `_function_toolset.py:43-105`). Temporal itself defines the target semantics: the CHASM Transition is the officially named "atomic unit of state change," committing field writes and task schedules together or rolling back entirely (`docs/architecture/chasm.md:216-238`). Notably, crewai's report flags `crewai.experimental.durable_exec` as an emerging direction — this model is spreading (crewai analysis, Future Considerations).

## Pattern Catalog

**P1. Tiered atomic units per concern.** Problem: persistence, retry, tracing, and UI have conflicting granularity needs. Demonstrated by all eight implementation sources (e.g., letta's concern-by-concern table at `letta/agents/letta_agent_v3.py:1093` vs `letta/schemas/enums.py:268-274`; langgraph's write/task/superstep layering at `libs/langgraph/langgraph/pregel/_loop.py:294,706`). Why it works: each axis optimizes independently instead of compromise. Copy when: building anything with more than one observer of progress. Risky when: the tiers' relationship is undocumented — agent-framework's four counters (`attempt_idx`, middleware `iteration`, checkpoint `iteration_count`, executor events) are exactly this pattern without a stated mapping (`_tools.py:2567`, `_harness/_loop.py:456`, `_workflows/_checkpoint.py:78`).

**P2. Explicit status machine on the persisted record.** Problem: a crashed process must leave an inspectable, classifiable residue. Demonstrated by pydantic-ai's five-state `SnapshotStatus` (`persistence/__init__.py:32-41`), letta's four-state `StepStatus` with separate update methods and transition tests (`letta/services/step_manager.py:368-555`, `tests/test_managers.py:9593-9691`), temporal's five-state Executable FSM (`common/tasks/state.go:6-17`), and openai-agents-sdk's four-way tagged `next_step` union used with `isinstance` dispatch instead of exception control flow (`src/agents/run_internal/run_steps.py:154-174`). Why it works: terminal states are enumerable, so monitoring and sweeps become possible. Copy always; it is the cheapest high-value pattern in the study.

**P3. Guaranteed-progress and cleanup markers via `finally`.** Problem: exceptions must still advance observable state. Demonstrated by crewai advancing `iterations += 1` in `finally` so the counter never lies about attempts (`agents/crew_agent_executor.py:459-460`), letta recording step metrics from the `finally` block (`letta/agents/letta_agent_v3.py:1582-1590`), openai-agents-sdk sealing `turn_span` in `try/finally` (`src/agents/run.py:1273-1278`), and temporal converting panics into errors at the Executable boundary so Ack/Nack still runs (`service/history/queues/executable.go:302-315`). Copy universally.

**P4. Deterministic, idempotent resume keys.** Problem: re-delivery and replay must converge instead of duplicating. Demonstrated by langgraph hashing `(checkpoint_id, ns, step, name, type, triggers)` into stable task IDs that enable time-travel (`libs/langgraph/langgraph/pregel/_algo.py:616-623`), openhands keying event files by UUID hex so re-saves are file-level idempotent (`openhands/app_server/conversation_paths.py:11-35`), openai-agents-sdk tracking `_current_turn_persisted_item_count` to skip already-committed items on resume (`src/agents/run_state.py:263-264`), crewai restoring the monotonic emission counter from the event record (`base_agent.py:488-490`), and temporal's `VersionedTransition` giving total ordering across data centers (`docs/architecture/chasm.md:277-296`). Copy whenever any consumer might redeliver.

**P5. Durable pending-work buffers.** Problem: work begun but not committed must survive or be explicitly discarded. Demonstrated by langgraph's `put_writes` rows plus `checkpoint_pending_writes` re-applied on resume via `_reapply_writes_to_succeeded_nodes` (`libs/langgraph/langgraph/pregel/_loop.py:245,724-737`), agent-framework persisting `pending_request_info_events` in checkpoints (`_workflows/_checkpoint.py:60`), letta writing the Step row as `PENDING` before the LLM call (`letta/agents/letta_agent_v2.py:946-962`), and openai-agents-sdk persisting interruption turns with both the approval item and the processed response (`src/agents/run_internal/session_persistence.py:264-352`). Why it works: it converts "unknown mid-state" into "known pending state." Copy for any long-running or pausable work.

**P6. Structured-error-as-result envelopes for tools.** Problem: a failed tool should inform the model, not kill the run. Demonstrated by agent-framework catching exceptions and returning `Content.from_function_result(..., exception=...)` so `function_call`/`function_result` stay paired (`_tools.py:1632-1645`), letta surfacing tool failures as normal `role=tool` messages with `status="error"` results (`letta/agents/letta_agent_v3.py:1822-1824`), and crewai returning synthetic blocked-by-hook results while still emitting the Finished event (`agents/crew_agent_executor.py:967-979`). Trade-off: preserves loop liveness but hides operational failure from status fields — letta's Step stays `SUCCESS` even on tool-rule violations (`letta/agents/letta_agent_v3.py:1546-1553`).

**P7. Rewind-and-retry for model calls.** Problem: retrying a model call must not double-append conversation history. Best demonstrated by openai-agents-sdk: `get_response_with_retry` pops a fingerprint-matched session tail via `rewind_session_items` and rewinds server-managed conversation deltas through the same callable, verifying cleanup afterward (`src/agents/run_internal/session_persistence.py:416-468,518-557`, `run_loop.py:1876-1880`). Related: letta's compaction-then-retry on `ContextWindowExceededError` inside the same Step (`letta/agents/letta_agent_v3.py:1218-1299`). Copy whenever a provider retry can follow a partial side effect; skip for stateless single-shot calls.

**P8. Sibling cancel-and-drain on parallel failure.** Problem: one failing parallel task must not leak asyncio tasks or leave silent stragglers. pydantic-ai's `CancelAndDrain` cancels the in-flight task plus readiness waiter, drains cleanup, then re-raises (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:686-693,1947-1956`); openai-agents-sdk partitions pending tool tasks and cancels pre-invoke siblings on first failure (`src/agents/run_internal/tool_execution.py:1480-1499`); langgraph's runner panics and cancels siblings except for handlers (`libs/langgraph/langgraph/pregel/_runner.py:616-634`). Contrast: crewai's parallel native-tool path lets a `BaseException` in one tool leave siblings running (crewai analysis explicitly notes Pydantic-AI's `CancelAndDrain` as the missing mechanism, `crew_agent_executor.py:742-776`), and agent-framework's `asyncio.gather` intentionally runs every sibling to completion (`_tools.py:1821-1823`). Choose drain-vs-complete deliberately; both are defensible, silence is not.

**P9. Atomic write discipline at the storage boundary.** Problem: torn files must not masquerade as data. agent-framework writes checkpoints via tmp-plus-`os.replace` (`_workflows/_checkpoint.py:317-323`); openhands uses bare `path.write_text` with corrupt reads silently returning `None` (`openhands/app_server/event/filesystem_event_service.py:23-36`) — the study's clearest negative example, echoed structurally by the empty `reports` scaffold whose unpopulated slot survives indefinitely (reports analysis, R2–R3 at `reports/source/01.03-step-turn-task-atomicity/reports.md:98-99`). Copy: temp-file-then-rename plus a completion marker for any machine-written artifact.

**P10. Human-in-the-loop as a persisted pause outcome.** Problem: waiting for a human must be a durable, resumable state, not a dropped thread. Demonstrated by openai-agents-sdk making `NextStepInterruption` a first-class turn outcome carrying approval items (`src/agents/run_internal/run_steps.py:169-174`), agent-framework's checkpoint-resident `pending_request_info_events` with `request_id`-correlated responses (`_workflows/_runner_context.py:457-486`), and letta reusing the original `step_id` across an approval pause so the record stays continuous (`letta/agents/letta_agent_v3.py:1019-1027`). Copy whenever approvals or interrupts exist.

**P11. Commit-together / transactional outbox.** Problem: state and the tasks spawned from it must not diverge across a crash. Temporal states it outright: MutableState, history events, and queued tasks commit in one DB transaction, with transfer tasks implementing the outbox pattern (`docs/architecture/history-service.md:294-322`); CHASM transitions "commit together as a single database write, or roll back entirely" (`docs/architecture/chasm.md:216-238`). agent-framework approximates at library scale by exporting only `_committed` state and committing at superstep barriers (`_workflows/_state.py:106-111`). Copy when side effects must be provable; overkill for ephemeral UI state.

**P12. Speculative zero-write fast paths with fallback.** Problem: latency-critical turns shouldn't pay durability cost when they usually succeed. Temporal's Speculative Workflow Task never touches the DB and converts to a normal task after a timeout (`docs/architecture/speculative-workflow-task.md:33-48`); langgraph's `durability="exit"` similarly defers everything to `__exit__` (`libs/langgraph/langgraph/pregel/_loop.py:1201-1311`). Both accept that a crash before conversion loses the turn — acceptable only where the caller can cheaply re-drive.

## Key Differences

- **Persistence granularity.** langgraph and agent-framework checkpoint per superstep/tick; letta persists a row per Step but its messages only at step success; openai-agents-sdk persists per-turn items continuously during streaming; crewai defaults to per-Task checkpoints; openhands persists per individual event; temporal per DB transaction. Source A (langgraph) uses coarse ticks because channel state is reconstructable from deltas (`libs/checkpoint/langgraph/checkpoint/base/__init__.py:582-649`), while Source B (openhands) uses maximal fineness because it stores an immutable audit trail it never replays (`openhands/app_server/event/event_service_base.py:145-156`).
- **Where retry lives.** Inside the unit (letta inner LLM loop with fallback swap; openai-agents-sdk model-call retry with rewind; crewai guardrail budget on the Task) versus around it (langgraph task attempts between checkpoints; temporal Nack/reschedule with deliberate `IsRetryableError = false` so the goroutine is never held, `service/history/queues/executable.go:623-628`). Around-the-unit scales better operationally (backoff lives in infrastructure); inside-the-unit gives tighter conversational context for the retry.
- **Crash answer.** Three distinct postures: re-run the whole unit (letta's crashed Step regenerates a new `step_id`; crewai without `CheckpointConfig` restarts with empty `messages`, `crew_agent_executor.py:217-223`); resume from the prior boundary (langgraph, agent-framework, temporal — losing only the failing superstep, `_workflows/_executor.py:280-285` vs `_runner.py:240-300`); or reconstruct the interrupted unit precisely (openai-agents-sdk via `_last_processed_response` + persist counter, `src/agents/run_internal/run_loop.py:730-748`; pydantic-ai via message-history reconstruction with `run_id`/`conversation_id` stamped on every message, `_agent_graph.py:912,969`).
- **Tool-call atomicity.** First-class in agent-framework (per-tool lifetime budgets `max_invocations`/`max_invocation_exceptions`, own middleware pipeline, `_tools.py:308-345,1424-1645`) and pydantic-ai (per-tool `ctx.retries[name]` propagating across steps via `for_run_step`, `tool_manager.py:120-145`); absorbed elsewhere — langgraph inherits the node task's `RetryPolicy.max_attempts` (`types.py:428`), openai-agents-sdk aggregates into the turn, letta has no per-tool row at all (`letta/agents/letta_agent_v3.py:1840-1862`), and openhands sees only unpaired Action/Observation events (`webhook_router.py:57`). Consequence: only the first group can answer "which tool failed, how many times, at what cost" without parsing messages.
- **Failure honesty.** Most systems surface failure as status (letta `FAILED`, pydantic-ai `error` snapshots, agent-framework `executor_failed` then re-raise). openhands is the outlier: the webhook handler catches batch-save exceptions and returns `Success` anyway, so the sandbox never retries and gaps become permanent (`webhook_router.py:519-522`). crewai has a subtler variant — trace batches that fail to send within the 30s flush are simply lost (`events/listeners/tracing/trace_batch_manager.py:301-318`).
- **Vocabulary discipline.** openai-agents-sdk collapses nearly everything to "turn" with one tagged union; temporal names six nested units but documents their mapping ("one Executable ≈ one Task ≈ one DB transaction's emitted task; multiple Executables → one Workflow Task turn"); agent-framework and crewai carry multiple live vocabularies simultaneously — crewai ships two executors with different atomicity contracts, the legacy one `DeprecationWarning`'d yet still primary on some paths (`crew_agent_executor.py:145-151`).

## Tradeoffs

**Coarse barrier checkpoints vs fine-grained unit records.**
Benefit of barriers: cheap writes, simple mental model, trivially correct rollback (discard the failing tick). Cost: a crash wastes all in-boundary work, and fine-grained questions ("did tool X finish?") need auxiliary streams — langgraph consumers wanting exactly-once visibility must inspect `pending_writes` directly (langgraph analysis, Questions/Gaps). Fine-grained records invert this: letta's `PENDING` row gives instant observability but no automatic resume and requires manual triage via `GET /v1/steps` (`letta/services/step_manager.py:45-88`). Best fit: barriers for graph-shaped compute with cheap re-execution; records for audited, expensive, or externally-visible steps.

**Retry inside vs around the unit.**
Inside (openai-agents-sdk, letta): benefit is context-preserving retries (rewound sessions, swapped fallback models, compacted context). Cost is complexity — openai-agents-sdk must keep two storage layers in lockstep through one rewind path (`run_loop.py:1876-1880`), and its rewind silently aborts if the tail fingerprint mismatches (`session_persistence.py:454-462`). Around (temporal, langgraph): benefit is uniform infrastructure-managed backoff; cost is that every retry replays the whole task, which is why langgraph cannot offer per-tool retry without splitting nodes into tasks (langgraph analysis, Tradeoffs).

**Structured-error-as-result vs raise-and-stop.**
Envelopes (P6) keep loops alive and models informed but blur status: letta marks a tool-rule-violating or max-steps-exhausted Step `SUCCESS` with a stop reason rather than `FAILED` (`letta/agents/letta_agent_v3.py:394-395,1546-1553`). Raise-and-stop (temporal Executables, agent-framework executors, letta's unconditional `should_continue = False` on step exceptions at `letta_agent_v3.py:1511-1540`) keeps semantics crisp but forfeits partial progress — agent-framework's `executor_failed` re-raise means callers that don't catch it lose all in-superstep pending state (`_workflows/_state.py:106-111`).

**Deferred durability vs synchronous durability.**
Deferral buys latency: temporal's speculative tasks skip DB writes entirely; langgraph's `exit` mode flushes once. Cost is a loss window — a process death before exit or conversion discards everything, and langgraph must synthesize stub parent checkpoints to keep delta-channel ordering intact (`_loop.py:1230-1258`). Sync durability (waiting on the put future between ticks, `main.py:3002-3003`) costs a round-trip per tick but bounds loss to one tick. langgraph making this a user-facing axis (`types.py:87-93`) is the right call; hardcoding either end is not.

**Opaque event ledger vs interpreted typed units.**
openhands' opacity decouples it from SDK evolution (new event kinds auto-widen the callback filter via derived Literals, `event_callback_models.py:28-30`) but blinds it: no step counts, no Action/Observation pairing, `turn_count` permanently `None` at this layer (`webhook_router.py:162,180`). crewai shows the middle path — an interpreted event DAG plus separately-tiered checkpoints — at the cost of maintaining both systems and migrating between executors.

## Decision Guide

Choose your atomicity strategy by answering four product questions:

1. **Must work survive process death?** No → in-memory counters plus `finally`-guaranteed progress markers suffice (crewai's legacy path, P3). Yes → pick a durable substrate: engine-delegate (Model D) if you can adopt an engine; barrier checkpoints (Model A) for graph compute; named records (Model B) for server-audited steps.
2. **Is the work a graph or a conversation?** Graph/channel compute fits superstep barriers with deterministic IDs (langgraph's hash-addressable tasks enable free time-travel, `_algo.py:616-623`). Conversation-shaped work fits turn/step records with tagged outcomes (openai-agents-sdk's `next_step` union) because the natural resume point is "next model call."
3. **Are tool side effects expensive or irreversible?** Then make tool calls first-class atomic units with their own budgets (agent-framework, pydantic-ai) and add idempotency tokens — every source lacks them, and openai-agents-sdk explicitly lists user-supplied de-dup keys as a future need for irreversible tool families (oai-sdk analysis, Future Considerations). Cheap, pure tools can ride along inside larger units safely.
4. **Who observes progress?** Humans debugging production incidents want named records with statuses and trace correlation (letta's `trace_id`/`request_id` columns). Programmatic UIs want discriminated event unions (pydantic-ai's `HandleResponseEvent`, openai-agents-sdk's `RunItemStreamEvent`). Auditors want append-only ledgers (crewai, openhands). Pick the primary observer and tier the rest around it.

Rule of thumb extracted from the ratings: **an 8 comes from composing at least two strategies** — langgraph couples barriers with per-task retry and durability modes; openai-agents-sdk couples turn records with rewind-based retry and schema gating; pydantic-ai couples node snapshots with engine delegation; temporal couples transactions with outbox and FSM discipline. Single-strategy designs plateau at 7 (or 6 when recovery claims outrun enforcement).

## Practical Tips

Copy these:

- **Write the unit record before doing the work** (letta's `PENDING`-first insert, `letta/agents/letta_agent_v2.py:946-962`) and update it from `finally` (P3). This pair alone makes crashes inspectable.
- **Make durability a configuration axis, not a constant** (langgraph's `sync`/`async`/`exit`, `types.py:87-93`).
- **Version your resume payloads and fail fast on downgrade** (openai-agents-sdk's schema gate rejecting unknown versions, `run_state.py:128-130`).
- **Persist what you're waiting on** — approval requests, pending sends, unanswered questions (P10; agent-framework's `pending_request_info_events`).
- **Pair every start marker with a guaranteed terminal marker**, including synthetic terminals for hook-blocked or cache-hit paths (crewai emits `Finished` even for blocked calls, `crew_agent_executor.py:977-979`) — but note crewai's cache-hit gap where no `Started` ever fired (its analysis, Failure Modes).
- **Split validation from execution for side-effecting calls** (pydantic-ai's `ValidatedToolCall.args_valid`, `tool_manager.py:46-75`) so retry accounting can distinguish "attempted" from "executed."

Delay until needed:

- Per-tool-call persistence rows (letta's listed future item) — start with structured tool-result messages plus OTel spans; add rows when operators actually need per-tool latency queries.
- Full event-sourcing with replay (crewai's `RuntimeState` + `EventRecord`) — powerful but heavy; a plain checkpoint stream covers most recovery needs.
- Speculative zero-write paths (P12) — only worth it with measured tail-latency pressure and a safe conversion fallback.
- Branch/fork lineage on checkpoints (crewai's `_branch`/`fork()`, `state/runtime.py:352-389`) — wait for an actual time-travel requirement.

## Anti-Patterns / Caution Signs

- **Multiple live vocabularies for the same concept.** crewai's two executors, agent-framework's four counters, letta's overlapping `RunStatus`/`JobStatus` enums (`letta/schemas/enums.py:133-161,227-231`). When contributors must ask "which iteration do you mean?", drift has already begun.
- **Success signals that outrun durability.** openhands returning `Success` on partial batch failure (`webhook_router.py:520-522`) and callbacks firing after the HTTP 200 (`webhook_router.py:513-517`) mean callers cannot distinguish delivered from dropped. Any "ack before durable" path deserves a red test.
- **Best-effort caps.** agent-framework's `max_function_calls` is checked only after each parallel batch, so it overshoots by design (`_tools.py:2636-2644`); crewai's output-parser retry is a soft limit that can loop indefinitely (`crew_agent_executor.py:434-442`). If a limit exists for cost or safety, enforce it pre-batch or say plainly that it isn't a limit.
- **Orphan states with no sweeper.** letta's forever-`PENDING` Steps (`letta/services/step_manager.py:45-88` triage only), openhands' stuck `WAITING_FOR_SANDBOX` start tasks, and the empty `reports` scaffold slot all show the same shape: a created marker that nothing ever reconciles. Absence of a reconciliation sweep is a leading indicator of brittleness.
- **Rollback claimed by convention.** letta's comment "rollback to previous state" holds only if no side effects occurred, and no test simulates a mid-step crash (`letta/agents/letta_agent_v3.py:1511-1540`; letta analysis, Questions/Gaps). Untested recovery claims are the most common gap between 7 and 8 in this study.
- **Silent drops at observability boundaries.** crewai losing trace batches past the 30s flush (`trace_batch_manager.py:301-318`), temporal dropping terminal failures when DLQ is not configured (`executable.go:175-181`), openhands swallowing corrupt event files with a log line (`filesystem_event_service.py:28-31`). Every async delivery hop needs a loss policy, not just a logger.
- **Shared mutable buffers across an atomic boundary.** crewai's legacy `messages` list can hold an assistant message without its tool result mid-crash, and its parallel batch can strand the assistant message with partial results (`crew_agent_executor.py:432,769-776`). If a buffer crosses a persistence boundary without a transactional wrapper, enumerate its torn states explicitly or serialize appends.

## Notable Absences

- **No canonical cross-axis event.** langgraph, letta, and pydantic-ai each explicitly ask "what is the single atomic event joining persistence, tracing, and UI?" and each report finds no unified record (`libs/langgraph/langgraph/types.py:120-134` mode-dependence; letta analysis, Questions/Gaps; pydantic-ai analysis, Questions/Gaps).
- **No tool-side-effect idempotency tokens anywhere.** openai-agents-sdk handles duplicate `tool_call_item`s by skipping on resume rather than by idempotency key (`src/agents/run.py:1298-1333`); crewai's tool cache is non-transactional with execution (`crew_agent_executor.py:925-1006`); pydantic-ai notes its Temporal activity re-derives tools by mutation-prone lookup (`durable_exec/temporal/_function_toolset.py:43-105`). Non-idempotent tools are unsafe to retry in all eight systems.
- **No per-tool-call persistence in servers.** letta's `tool_execution_ns` is a max across tools, not a breakdown (`letta/agents/letta_agent_v3.py:1866`); openhands cannot pair actions with observations at all.
- **No second-level failure chaining.** langgraph finds no evidence for handling a crash inside an error-handler node (`libs/langgraph/langgraph/graph/state.py:1327-1331`); agent-framework delegates executor retry entirely to users or external engines.
- **No crash-mid-step tests in most suites.** Explicitly missing in letta, openai-agents-sdk (process-death-between-tool-execution-and-save), and langgraph (ordering invariant under concurrent crashes); temporal is the partial exception with panic-recovery and ambiguity handling (`transaction_impl.go:78-82`).
- **Nothing at all in `reports`** — included here because its empty-slot state is a live specimen of the torn-write condition the dimension warns about, and because its own report recommends the fix this study endorses: atomic rename plus completion markers plus a manifest distinguishing expected from completed slots (reports analysis, Future Considerations).

- **langgraph (8)** — Cleanest formal model: write/task/superstep tiering with BSP semantics, deterministic task IDs, reserved control-write keys with negative indices, and a user-facing durability axis; weaknesses are absorbed tool calls, future-ordering-instead-of-transactions between `apply_writes` and `put`, and seven overlapping stream modes.
- **letta (7)** — Strongest database-backed observability: typed Step/Run/Message FK hierarchy, four-state status machine with tests, dual trace/request correlation columns, metrics decoupled into their own fire-and-forget row; core weakness is asymmetry — LLM requests retry inside a Step while tool failures abort it, and crashed Steps linger `PENDING`.
- **openai-agents-sdk (8)** — Tightest contract surface: one turn, one tagged union, one schema-gated snapshot format, one rewind path serving two storage layers; interruptions are turn outcomes rather than side channels; deductions for aggregated tool calls and best-effort streaming persistence.
- **openhands (6)** — Deliberately minimal: opaque UUID-keyed event files, coarse persisted start-workflow states, live-fetched execution status; honest about its limits but the limits are severe — no turn/step vocabulary, permanent partial-save gaps reported as success, fire-and-forget pending messages.
- **pydantic-ai (8)** — Best layered-budget design (global output retries vs per-tool retries vs usage limits), cleanest snapshot ABC with five-state lifecycle, and unique engine-delegation breadth across Temporal/Prefect/DBOS; main gaps are the agent loop not snapshotting by default and hand-maintained coupling among node/step/usage counters.
- **temporal (8)** — Deepest durability engineering: transactional outbox, single-writer semaphore, VersionedTransition total ordering, panic-safe Executables with DLQ routing, speculative tasks; deducted for six un-unified unit vocabularies and the HSM→CHASM transitional overlap.

## Open Questions

- Is there a practical design for one canonical event record that joins persistence, tracing, and UI without collapsing their granularity differences? All three axes want different shapes (langgraph, letta, and pydantic-ai analyses all leave this open).
- Can tool-side-effect idempotency be standardized at the framework level (a per-call de-dup key on RunState/checkpoint), or must it remain a user obligation? openai-agents-sdk frames it as future work; no source has it.
- Should stale in-flight units be swept by infrastructure (cron/startup re-classifying letta's `PENDING` steps, openhands' stuck start tasks) or exposed as-is? Neither approach appears implemented anywhere.
- What is the correct loss policy at async observability boundaries — bounded queues with backpressure (temporal's notifier at 1000, `service/history/events/notifier.go:25`), timeouts with drop (crewai's 30s flush), or blocking acks? None of the choices is tested against crash timing.
- How should mixed parallel batches behave — complete-all (agent-framework), cancel-siblings (pydantic-ai/openai-agents-sdk), or run-uncoordinated (crewai)? The sources diverge with no shared rationale, suggesting an unsettled design space.
- For the `reports` source: does the producing harness create directories transactionally with file writes, and would a completion-marker manifest close the torn-state window its empty slot demonstrates? Unanswerable inside that source boundary.
