## Executive Summary

Eight sources reveal four distinct postures toward dataset and golden-task management. **langfuse** (8/10) treats datasets as a product surface: persistent entities with temporal item versioning, schema-enforced golden answers, and immutable run-time snapshots. **pydantic-ai** (7/10) ships a typed, file-backed `Dataset` artifact in a dedicated sub-package with round-trip-tested serialization and pluggable golden-answer enforcement. A middle band of frameworks — **agent-framework** (5/10), **crewai**, **langgraph**, **letta**, **openai-agents-sdk** (all 4/10) — each manage real benchmark or golden-output machinery but fragment it across experimental packages, CI scripts, example trees, or in-memory APIs without durable versioning. **openhands** (3/10) has no benchmark surface at all because the analyzed repo is a frontend; its well-engineered E2E fixture layer is a test analog, not an eval corpus.

Two findings dominate. First, **golden answers are nearly universal even where datasets are absent**: seven of eight sources define explicit per-task expectations (`expected_output`, golden tables, sentinel tokens, score thresholds), and most engineer them well. Second, **versioning is the systemic failure point**: only langfuse versions anything (dataset items, via temporal rows), agent-framework pins external dataset revisions to commit hashes, and everyone else delegates implicitly to git. On the dimension's guiding question — *can a benchmark result be reproduced six months later?* — no source fully answers yes. langfuse comes closest at the data layer (point-in-time re-materialization plus recorded model/prompt config); letta preserves readable reports but not runnable conditions; langgraph reproduces the procedure but not the numbers; crewai and openai-agents-sdk persist nothing comparable at all.

## Core Thesis

Dataset-management maturity tracks how central evaluation is to the *product*, not engineering skill. Every source demonstrates competent golden-output engineering somewhere in the codebase — tested scorers, typed expectation schemas, deterministic replay harnesses — but only sources whose business depends on eval data invest in versioning, provenance, and migration tooling (langfuse's bitemporal items with backfill tests and dual-implementation migration strategy are the clear example). Frameworks deliberately keep the dataset layer thin and push custody onto users: agent-framework rejected "full eval infrastructure" by design decision (ADR `docs/decisions/0023-foundry-evals-integration.md:47-53`), openai-agents-sdk keeps only determinism *mechanisms* in the library (`src/agents/testing/model.py:249-254`) and delegates evaluation to examples, and crewai quarantines experiments under `crewai.experimental`. The recurring consequence is that golden answers — the cheap half of the problem — are solved everywhere, while dataset identity and result provenance — the expensive half — are solved almost nowhere.

## Approach Models

Sources cluster into four models, defined by where dataset custody lives:

- **Model A — Dataset as platform product (langfuse).** Datasets, items, and runs are first-class persisted entities (`packages/shared/prisma/schema.prisma:561-644`) exposed through public REST, tRPC, MCP, and CSV surfaces. Items carry optional `expectedOutput` plus optional dataset-level JSON Schemas enforced on every write path (`packages/shared/src/server/services/DatasetService/DatasetSchemaValidator.ts:23-91`). Item edits create bitemporal row versions (`validFrom`/`validTo` composite PK, `schema.prisma:606-613`) queryable at any timestamp (`packages/shared/src/server/repositories/dataset-items.ts:1260-1336`). Run results embed denormalized snapshots of item content and version into ClickHouse at ingestion time (`packages/shared/clickhouse/migrations/unclustered/0022_dataset_run_items.up.sql:1-36`). Scoring is deliberately out of scope — delegated to the separate evals/scores subsystem.

- **Model B — Dataset as typed library artifact (pydantic-ai).** A generic `Dataset[InputsT, OutputT, MetadataT]` of `Case` rows serializes deterministically to YAML/JSON with an auto-generated JSON-schema sidecar wired into editors (`pydantic_evals/pydantic_evals/dataset.py:747-794`). Golden answers sit on each case as `expected_output` (`dataset.py:141-142`); enforcement is policy separated from data via evaluators (`EqualsExpected`, `Equals`, `Contains`, `IsInstance`, plus LLM judges; `evaluators/common.py:46-174`). Nondeterminism is measured rather than suppressed via `repeat` with per-run aggregation (`dataset.py:269-279`; `reporting/__init__.py:343-392`). Versioning is a filename convention demonstrated by committed examples (`time_range_v1.yaml` vs `time_range_v2.yaml`).

- **Model C — Golden answers as API/code constructs, no dataset layer (agent-framework, crewai, openai-agents-sdk).** agent-framework defines golden-answer fields on evaluation items in both languages (`python/packages/core/agent_framework/_evaluation.py:206-214`; `dotnet/src/Microsoft.Agents.AI/Evaluation/EvalItem.cs:113-124`) while actual benchmark datasets are fetched externally at runtime (GAIA from Hugging Face pinned to revision `gaia.py:426`; τ² cloned manually from upstream, `tau2/README.md:40-44`). openai-agents-sdk embeds hardcoded golden tables in grader scripts validated against produced artifacts (`dataroom_metric_extract/evals.py:47-210,240-302`). crewai takes caller-supplied `list[dict]` with `expected_score >=` threshold semantics judged by LLMs (`experiment/runner.py:27,65-70,130-165`). In all three, expected outputs are first-class; datasets as named, versioned artifacts do not exist.

- **Model D — Benchmarks/goldens as CI and test infrastructure (letta, langgraph, openhands).** letta's model sweep lives under `.github/scripts/`, treating ~45 per-model config files (`tests/configs/llm_model_configs/*.json`) crossed with behavioral assertion helpers as its implicit dataset (`.github/scripts/model-sweep/model_sweep.py:33-38,109-146`), publishing dated MDX reports via automated PR. langgraph runs pyperf micro-benchmarks from a registry of scenario tuples (`libs/langgraph/bench/__main__.py:99-464`) against cache-resident baselines, while correctness goldens live in syrupy snapshots and a pip-installable conformance suite (`libs/checkpoint-conformance/README.md:14-16`). openhands expresses goldens as exact sentinel tokens asserted through UI and events APIs against a scripted trajectory server (`tests/e2e/mock-llm/scripts/mock-llm-server.py:47-72`; `tests/e2e/live/utils/agent-server-conversation.ts:12-14`). None of these maintain a citable dataset artifact.

## Pattern Catalog

### P1. Golden answer as a first-class field on the task/item record

- **Problem:** Expectations must be reviewable alongside tasks and machine-checkable without custom plumbing.
- **Demonstrated by:** agent-framework (`_evaluation.py:206-214`, `EvalItem.cs:113-124`, mismatched counts raise: `_evaluation.py:1757-1759`, `EvaluationTests.cs:1431`), pydantic-ai (`dataset.py:141-142`), langfuse (`schema.prisma:593-620`), openai-agents-sdk (`models.py:16-31`), crewai (`task.py:153`, `runner.py:66`).
- **Why it works:** Co-locating expectation with input makes drift visible in diffs and enables defensive validation — agent-framework raises when expected-output count mismatches queries, in both languages.
- **Copy it:** Always. This is the cheapest high-value pattern in the study.
- **Risk:** Dead expectations. openai-agents-sdk's healthcare scenarios type rich `ScenarioExpectation.gold` metadata that *no grader ever reads* (`models.py:19-21,30` are the sole grep hits) — documentation-grade gold rots silently.
- **Evidence:** Source reports for all five sources above.

### P2. Snapshot provenance into results (immutable result envelopes)

- **Problem:** Results must stay interpretable after the dataset changes.
- **Demonstrated by:** langfuse denormalizes item content *and* resolved version into ClickHouse run items at ingestion (`worker/src/services/IngestionService/index.ts:510-602`; `0032_add_dataset_version_to_dataset_run_items_rmt.up.sql:1`); agent-framework exports timestamp, task metadata, full message transcripts, and prediction metadata to per-run JSONL (`gaia.py:613-649`) and τ² embeds the entire task dump in each result row (`run_benchmark.py:42`); pydantic-ai echoes `expected_output` into report cases and stamps OTel trace/span IDs (`dataset.py:1170-1174`, `377-382`).
- **Why it works:** Decoupling historical results from mutable sources converts "reproduce" from a data problem into merely a config problem.
- **Copy it:** Whenever results outlive the dataset — which is essentially always.
- **Overkill when:** Results are ephemeral CI diagnostics consumed within one PR window (langgraph's case).

### P3. Pin external data to immutable identifiers — separately from code

- **Problem:** Upstream datasets drift independently of your code.
- **Demonstrated by:** agent-framework pins GAIA to an HF snapshot revision (`gaia.py:426`); openai-agents-sdk pins the reviewed repo to a full commit SHA (`repo_code_review/main.py:33-34`). The cautionary pair: τ² pins the *package* to commit `5ba9e3e...` but instructs a bare `git clone` of default branch for the *data* (`tau2/README.md:35` vs `40-44`); letta's version-named legacy dirs (`tests/data/memgpt-0.2.11/`) show conventions without enforcement decaying into archaeology.
- **Copy it:** For any third-party data feeding published numbers. Pin data and code independently — pinning only one is worse than documenting neither, because it manufactures false confidence.

### P4. Schema contracts at the dataset boundary

- **Problem:** Hand-edited or multi-writer datasets accumulate malformed entries.
- **Demonstrated by:** pydantic-ai emits a per-type JSON-schema sidecar plus a `yaml-language-server` header on every save, making editor-time validation the primary defense (`dataset.py:769-794`), with `extra='forbid'` rejecting unknown fields (`dataset.py:89-107`) and duplicate case names rejected at construction (`dataset.py:254-260`). langfuse enforces optional dataset-level `inputSchema`/`expectedOutputSchema` through compile-once Ajv validators funneled into a single repository layer used by *all* writers — REST, tRPC, MCP, CSV (`DatasetSchemaValidator.ts:23-91`; `repositories/dataset-items.ts:337-358`), with index-preserving bulk errors mapping failures back to CSV rows (`dataset-items.ts:957-967`).
- **Why it works:** Validation at the single choke point every write crosses cannot be bypassed; compile-once validators make it affordable (langfuse documents a measured ~3800x speedup from validator reuse, `DatasetItemValidator.ts:38-39`).
- **Copy it:** When datasets are hand-edited files (sidecar pattern) or written through multiple surfaces (single-repository choke point).
- **Residual risk:** Stale sidecars go undetected (pydantic-ai rewrites the schema only on save, `dataset.py:863-864`).

### P5. Scripted subjects / deterministic replay instead of live models

- **Problem:** Correctness testing needs repeatability that live LLMs cannot provide.
- **Demonstrated by:** openhands' mock-llm server serving registered trajectories with admin reset and request capture (`mock-llm-server.py:79-112,165-168`); langgraph's `FakeFunctionChatModel` replaying scripted messages in benchmarks (`react_agent.py:18-35`); crewai's VCR cassettes with CI locked to `record_mode=none` (`conftest.py:424-425`); openai-agents-sdk's `ScriptedModel` (`testing/model.py:249-254`); agent-framework's SHA-256-hashed sample-validation playbooks replayed without LLM involvement (`playbook.py:96-162`).
- **Why it works:** Fixes the subject, isolates the system under test, costs nothing per run.
- **Limitation:** Measures plumbing, not quality. crewai's cassette fixates a judge score of 5.0 whose origin is undocumented (`test_agent_evaluator.py:99`) — recorded goldens answer "does the wiring work," not "is the output good."
- **Copy it:** For framework self-tests and E2E suites. Never mistake cassette-replay reproducibility for benchmark reproducibility.

### P6. Structural shape assertions ("golden shapes") as tolerant oracles

- **Problem:** Non-deterministic generators need assertions robust to cosmetic variance yet sensitive to structural regressions.
- **Demonstrated by:** letta asserting exact message-type sequences and OTID suffix conventions instead of free text (`model_sweep.py:109-146`); openhands' sentinel tokens asserted identically for mocked and live runs (`real-agent-server-conversation.spec.ts:113-121,127`); agent-framework's ag-ui golden scenario suites asserting ordered event-sequence bookends in memory (`event_stream.py:84-175`); langgraph counting streamed events (`__main__.py:20-33`).
- **Why it works:** Shape survives verbosity drift; identical oracles work across mock and live modes.
- **Failure mode:** Under-assertion. langgraph's event counts pass any graph streaming the wrong events; openhands' critic check verifies only that `critic_result.score` is a finite number, not whether it was good (`agent-server-conversation.ts:602-614`).

### P7. Make nondeterminism measurable rather than suppressed

- **Problem:** Single-shot scores on stochastic subjects hide variance.
- **Demonstrated by:** pydantic-ai's `repeat` parameter producing run-indexed cases aggregated via `case_groups()`/`averages()` (`dataset.py:269-279`; `reporting/__init__.py:343-392`), with tenacity-backed retries for transient failures (`dataset.py:989-995`); agent-framework's validated `num_repetitions` loop designed into an accepted ADR (`_evaluation.py:1641,1791`; `docs/decisions/0023-foundry-evals-integration.md:117-130`); crewai's `n_iterations` (though it persists nothing comparable afterward, `crew.py:2227-2272`).
- **Copy it:** Any time scores inform decisions. Contrast: agent-framework's own GAIA runner *creates* hidden nondeterminism via unseeded `random.shuffle` before `max_n` truncation (`gaia.py:357-360`).

### P8. Report-as-committed-artifact with provenance front-matter

- **Problem:** Benchmark outputs must outlive CI caches and local disks.
- **Demonstrated by:** letta's pipeline converting pytest JSON → weighted-score Markdown → git-committed MDX via bot PR with generation-timestamp front matter (`.github/workflows/model-sweep.yaml:113-135`; `supported-models.mdx:1-8`). The negative space is equally instructive: langgraph stores baselines only in a rolling Actions cache keyed to latest main SHA (`.github/workflows/baseline.yml:32-37`, `fail-on-cache-miss` at `bench.yml:38`), and openai-agents-sdk persists nothing — graders print pass/fail lines only.
- **Incomplete without raw detail:** letta's MDX aggregates away per-test rows; raw JSON survives only as expiring artifacts.

### P9. Conformance corpora as executable behavior specs

- **Problem:** Plugin/storage interfaces need a runnable definition of correct behavior for third parties.
- **Demonstrated by:** langgraph's checkpoint-conformance package: capability enum with auto-detection from method overrides (`capabilities.py:15-63,90-96`), per-capability spec modules with named assertions (`spec/test_put.py:22-51`), structured `CapabilityReport` output (`report.py:17-24`), and an implementation registry with opt-in skips (`initializer.py:23-30`). agent-framework's ag-ui golden scenario suites serve the same function internally.
- **Copy it:** For any extension-point contract. Risk: undeclared `skip_capabilities` mask partial compliance without justification fields.

## Key Differences

**Versioning mechanism.** langfuse versions dataset *items* temporally — updates close `validTo` and insert new versions, reads accept a `version` timestamp predicate, and auxiliary APIs expose history, drift-since-version counts, and run→version resolution (`schema.prisma:606-613`; `dataset-items.ts:430-487,1893-1956`). pydantic-ai uses filename suffixes on immutable committed examples (`time_range_v1.yaml` → `time_range_v2.yaml` extends v1 without mutating it). agent-framework pins one external revision (GAIA) while leaving others to float (τ² data). Everyone else relies on bare git history — which openai-agents-sdk notes is unusable for citation because its checkout is squashed to one commit. Notably, even langfuse does not version the dataset *container* (schemas, name, metadata mutate in place with only `updatedAt`, `schema.prisma:581-582`).

**Golden semantics.** Four tiers coexist: exact equality (pydantic-ai `EqualsExpected`; openai-agents-sdk bidirectional keyed-row checks asserting duplicates absent, count exact, all keys matched, none unexpected, `evals.py:242-300`); structural containment (agent-framework .NET `ContainsExpected`/`ToolCallArgsMatch` subset matching, `EvalChecks.cs:224-244,138-198`); judged thresholds (crewai `actual >= expected_score` on 0–10 LLM-judge scores, `runner.py:130-165`); and shape/sequence matching (letta, openhands, langgraph per P6). The choice correlates with subject determinism: pinned-data benchmarks can afford exactness; live-model sweeps fall back to shape or judgment.

**Where datasets live.** Product database (langfuse), repo files (pydantic-ai datasets, letta configs, openai-agents-sdk scenario JSON, agent-framework vendored RL JSONL), external services fetched at runtime (GAIA via HF hub, LangSmith notebooks in langgraph's examples, τ² upstream clone), and pure code constants (crewai dicts, openai-agents-sdk grader tables, openhands inline trajectories). Only the first two support citation; the last two have no existence independent of the runner source.

**Reproduction path.** langfuse: re-materialize the item set at the recorded version and replay with recorded model/prompt config (`router.ts:255-280` records prompt id, provider, model params, `dataset_version`). letta: re-*read* committed reports, but re-running requires self-hosted runners and an internal secrets binary (`model-sweep.yaml:11,51-60`). langgraph/openai-agents-sdk: reproduce the procedure, not the numbers. crewai: compare only if the user preserved a baseline file. openhands: moot — no benchmarks in scope.

**Divergence causes.** These differences track constraints, not quality. langfuse can afford bitemporal storage, dual-implementation migration flags, and backfill-migration tests because datasets are a paid product feature; a framework shipping the same machinery would be over-engineering. letta accepts irreproducibility because sweeping live provider models *is the point* — coverage of whatever the deployment serves beats pinning (`conftest.py:273-278`). langgraph tolerates unseeded benchmark inputs because perf numbers measure throughput, not correctness — but the same tolerance would be disqualifying for an accuracy benchmark. openai-agents-sdk keeps evaluation out of the shipped package by explicit posture ("prefer `ScriptedModel`", AGENTS.md), accepting fragility in examples to keep the library opinion-free. openhands simply lacks the surface: its repo map assigns evaluation to sibling repos.

## Tradeoffs

- **Platform-managed vs repo-local datasets.** langfuse gains real versioning, UI history panels, diff views, and multi-writer validation at the cost of snapshot-storage inflation and a transitional `STATEFUL`/`VERSIONED` dual implementation where behavior silently differs by deployment flag (`executeWithDatasetServiceStrategy.ts:18-41`; degenerate STATEFUL returns at `dataset-items.ts:1971-1974`). pydantic-ai gains zero-infrastructure portability and VCS-native review at the cost of no machine-readable version binding a report to a dataset revision.
- **Inline golden fields vs file-backed corpora.** agent-framework and openai-agents-sdk make evaluation trivially accessible with inline arrays/constants, but nothing records which dataset produced a result, and adding tasks means editing code. pydantic-ai's file-backed model adds serialization, schema sidecars, and round-trip tests in exchange for format maintenance.
- **Exact-match goldens vs judged rubrics.** Exact match (pydantic-ai, openai-agents-sdk, agent-framework GAIA scorer with numeric/list/string normalization rules tested at `test_gaia.py:11-35`) yields strict regression semantics but brittle formatting sensitivity ("USD millions" typos fail runs). Judged thresholds (crewai) tolerate variance but place pass/fail on a nondeterministic signal with no tolerance controls — 8.0 passes an expected 8 while 7.9 fails — and crewai's scores come from LLM calls on both sides of the comparison.
- **Live-model sweeps vs scripted subjects.** letta maximizes coverage of actually-served models but forfeits pinning, requires internal infrastructure, and produces task sets that vary day-to-day. CrewAI-style cassettes invert everything: fully reproducible, but they measure wiring, not model quality.
- **Rolling CI baselines vs committed artifacts.** langgraph keeps the repo clean and comparisons automatic, but `fail-on-cache-miss: true` means baseline expiry breaks PR benchmarking outright and historical comparison dies with the cache window. letta's committed MDX is durable and human-diffable but aggregates away the raw rows needed for longitudinal analysis.
- **Dynamic discovery vs static manifests.** letta parametrizing against `client.models.list()` covers whatever the server exposes but lets the effective dataset drift silently (one config already commented out with a TODO, `model_sweep.py:94`). Static registries (langgraph's tuple list) are stable but rot differently — vestigial targets appear, like prebuilt's declared-but-unimplemented `benchmark` Make target.

## Decision Guide

- **Must results survive dataset edits?** Adopt snapshot-at-ingestion (P2): copy item content and resolved version into each result row (langfuse), or at minimum export full task metadata and transcripts per result (agent-framework). If you skip this, six-month interpretability depends on reconstructing history by hand.
- **Are datasets hand-edited files in a repo?** Use a typed format with schema sidecar, duplicate-ID rejection, and round-trip tests (pydantic-ai model). Add machine-readable `version` or content-hash fields — the one gap pydantic-ai leaves open.
- **Wrapping external benchmarks?** Pin the *data* revision separately from any code/package pin, and verify the pin covers exactly what the loader reads (the τ² lesson). Cache downloaded data keyed by revision, not mere existence (GAIA's existence-check cache silently evaluates stale downloads, `gaia.py:408-409`).
- **Subject is nondeterministic?** Choose the oracle by purpose: structural shapes for compatibility sweeps (P6), exact goldens for regression gates, judged thresholds only with repeats and aggregation (P7). Persist the selected subset (task IDs, seeds) alongside results so sampled runs are reconstructible.
- **Benchmark runs in CI?** Store baselines as durable artifacts attached to releases or commits, never solely in caches (P8). Record commit SHA, workflow URL, environment pins, and resolved subject list in every published report.
- **Minimum viable provenance manifest** (no source implements this fully): `{dataset_id, dataset_revision_or_checksum, split, task_ids_if_sampled, model/prompt/judge config, seed, timestamp}` written into every result record. Assembling it from existing pieces: langfuse's run metadata (`router.ts:255-280`) + pydantic-ai's experiment metadata + agent-framework's JSONL envelope covers nearly every field already.

## Practical Tips

- Put `expected_output` (or equivalent) directly on the task/item record and validate cardinality defensively — raise when expectation counts mismatch inputs, as agent-framework does symmetrically in Python and .NET.
- Separate golden *data* from scoring *policy*: store answers on cases, enforce via swappable evaluators (pydantic-ai's `EqualsExpected`/`Contains`/judge split). This lets one dataset serve strict gates and fuzzy scoring without schema changes.
- When a golden answer is absent, fail loudly or warn — pydantic-ai's `EqualsExpected` quietly returning `{}` converts an assertion-bearing case into a metrics-only case on a typo (`evaluators/common.py:52-55`).
- Version evaluators/judges even if you don't version datasets: pydantic-ai stamps `get_evaluator_version()` into results and OTel attributes (`evaluator.py:185-193`), enabling dashboards to filter retired judge versions — cheap attribution when scores shift.
- Keep golden fixtures reviewable in the same PR as the code they constrain: letta co-locates `{name}.py` ↔ `{name}.json` ↔ `{name}_so.json` schema triples (`test_tool_schema_parsing.py:63,70,83`).
- Exclude infrastructure errors from quality scores before aggregating — letta drops `_error` tests from support-status computation (`generate_model_sweep_markdown.py:33-41`); contrast crewai, where a kickoff exception zeroes the score and becomes indistinguishable from a regression in baseline diffs (`runner.py:104-112`).
- Document a concrete "reproduce this experiment" recipe as an API sequence, not prose intent — langfuse's future-work list sketches exactly this: resolve `datasetVersion` from run metadata → fetch items at version → replay with recorded model params.
- For shared cross-language goldens, generate constants from one source rather than duplicating with comments — openhands maintains documented TS/Python token duplication that drifts only when the comment is ignored.

## Anti-Patterns / Caution Signs

- **Dead golden metadata.** Schemas implying rigor that nothing enforces: openai-agents-sdk's `required_tool_calls`/`gold.expected_next_step` read by no grader; crewai's declared-but-unimplemented `WEIGHTED_BY_COMPLEXITY` aggregation (`base_evaluator.py:82` vs always-simple-average at `evaluation_display.py:250-304`); langgraph's `prebuilt` benchmark Make target with no implementation behind it.
- **Self-mutating reference baselines.** crewai silently creates a baseline from the current run when missing and appends every run back into it unless opted out (`result.py:70-78,88-95`) — corrupting "reference" with "history," and leniently overwriting unreadable baselines, so a truncated file destroys regression protection.
- **Hidden nondeterminism in sampling paths.** Unseeded shuffles before subset truncation (agent-framework `gaia.py:357-360`), `uuid4()` fixture identities (langgraph `react_agent.py:37-61`), runtime-discovered task sets (letta `conftest.py:273-278`). Two identical commands produce different evaluations with no warning.
- **Existence-keyed caches guarding correctness-critical data.** GAIA short-circuits on any pre-existing `metadata.jsonl` in the temp dir, so stale or foreign data silently changes the evaluated set (`gaia.py:408-409`).
- **Environment pins by mutable tag.** `sandbox-tutorials:latest` (openai-agents-sdk `misc.py:56`) undermines reproduction even with identical prompts.
- **Transcription-duplicated goldens.** openai-agents-sdk hand-copies "$1,284 million" between generator and golden table with no cross-validation — editing one silently breaks the other.
- **Two parallel evaluation stacks drifting.** crewai's stable stack (1–10 scale) and experimental stack (0–10 scale) share neither models nor storage (`crew_evaluator_handler.py:25` vs `base_evaluator.py:35`); langfuse's `STATEFUL`/`VERSIONED` split is the disciplined version of the same move — deliberate, flagged, and scheduled for retirement.
- **Orphaned versioned artifacts.** letta's `memgpt-0.2.11/` trees: version-named data loaded by nothing signals a convention that died without cleanup.

- **Brittleness warning sign generally:** when changing serialization or SDK internals breaks goldens (byte-exact preview==step payload checks, padding-turn workarounds absorbing internal condenser calls), the oracle is coupled to implementation detail rather than behavior.

## Notable Absences

Consistent gaps across sources — none of these exist in any analyzed repository except where noted:

- **No central benchmark-results store, dashboard, or historical tracking** in-repo. Results are per-run JSONL files (agent-framework), stdout tables (crewai), expiring artifacts (letta raw JSON), or untracked `out/` directories (langgraph). langfuse is the exception precisely because result tracking *is* the product.
- **No difficulty/category taxonomy beyond one flat level.** GAIA's integer `level` 1–3 emitted as span attributes (`gaia.py:512-524`); letta's three-category JSON; openai-agents-sdk's README-prose difficulty ladder; pydantic-ai's user-supplied generic `TaskMetadata(difficulty=..., category=...)` demo; langfuse explicitly has none (zero hits searching `difficulty`; free-form JSON only, `schema.prisma:566,599,632`). crewai's complexity weighting remains vaporware.
- **No named/frozen dataset versions with human-friendly labels anywhere.** langfuse offers raw ISO timestamps with monotonicity floors but no "v3"-style tags; its own report flags this as a gap.
- **No end-to-end regeneration path for any published table.** τ²'s results table is a manual artifact; letta's sweep needs internal secrets; langgraph's baselines expire; openai-agents-sdk computes no aggregates at all.
- **No stored reference-transcript corpora for comparing answer distributions over time** (letta confirms absence despite being the likeliest candidate).
- **No server-side golden-answer comparator in langfuse** — the strongest dataset platform still outsources scoring to a separate subsystem, leaving "benchmark score" itself unreproducible as a platform artifact.

## Per-Source Notes

- **agent-framework (5):** Strongest golden-answer plumbing in the study — tested official GAIA scorer with normalization rules, symmetric Python/.NET `expected_output`/`expected_tool_calls` fields with mismatch validation, rich JSONL result envelopes, observability-instrumented runs. Fragmentation across lab/core/playbook layers plus the unseeded shuffle and unpinned τ² data cap the score. Best future-work list in the study (seed shuffles, manifest headers, promoted file-backed dataset loader).
- **crewai (4):** The experimental evaluation layer is a coherent skeleton (threshold logic, baseline classification, six-metric taxonomy) with zero internal adoption and no persistence discipline. Its genuinely excellent asset — VCR cassette replay with CI-forced playback-only mode — belongs to test infrastructure, not benchmark management. Pickle training artifacts add an unsafe, unversioned container to the inventory.
- **langfuse (8):** The reference implementation for this dimension: bitemporal item versions with point-in-time queries, integration-tested version semantics, snapshot-at-ingestion, compile-once schema validators, deterministic distributed ids, seeded perf scenarios, and backfill-migration tests. Remaining gaps are deliberate scope choices (no scorer, no container versioning, no taxonomy).
- **langgraph (4):** Exemplary correctness goldens (snapshot testing, capability conformance suite publishable to third parties) alongside exemplary benchmark fragility (cache-only baselines, unseeded inputs, output-blind assertions). The checkpoint/no-checkpoint pairing design for performance attribution is worth copying broadly.
- **letta (4):** The most automated benchmark pipeline studied (dispatch → pytest → weighted leaderboard MDX → bot PR), undermined by an unpinnable subject (live models), internal-infrastructure gating, and absent versioning/provenance. Behavioral sequence-shape assertions and error-tolerant categorization are transferable patterns.
- **openai-agents-sdk (4):** Two tutorials implement complete, deterministic, runnable golden-grading protocols; the healthcare demo types a richer golden schema than anyone else and then never executes it. The released-API-contract fixture (`baseline` + `baseline_commit`, enforced by test) proves the team knows versioned-golden discipline — it just was never applied to task data.
- **openhands (3):** Score reflects dimension scope, not craft. The scripted-trajectory server with admin lifecycle, request capture, deterministic timestamps, and dual-layer token contracts is excellent E2E engineering; there is simply no dataset, versioning, or metadata surface — and the repo's own governance acknowledges upstream benchmarks it cannot measure locally.
- **pydantic-ai (7):** The best library-grade dataset model studied: generics for user-defined metadata schemas (difficulty/category demonstrated in its own tests), evaluator registry with grouped load-time errors, `$schema` sidecars, guarded removal of dangerous features, nondeterminism made measurable via repeat/aggregation, and honest docs about metadata-vs-reality drift causing unreproducible results.
