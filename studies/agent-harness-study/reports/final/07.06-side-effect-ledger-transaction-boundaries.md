## Executive Summary

The three systems answer "what did the agent change?" from three fundamentally different positions of **ownership**, and their designs track that position rather than a shared quality ladder. **temporal** owns both execution and persistence, so it makes the ledger the system itself: an append-only, transactionally-chained history where every state change — including scheduled side effects and SDK-recorded markers — becomes a typed `HistoryEvent` written atomically-enough with the corresponding state mutation (`service/history/workflow/mutable_state_impl.go:7592-7636`). It scores 9/10 because even its failure semantics are codified rather than ad-hoc (`common/persistence/error_type.go:5-22`). **agent-framework** owns tool invocation inside someone else's application, so it builds a *control-plane* ledger around authority to act: immutable approval-request snapshots stored in session state keyed by provider `call_id` (`packages/core/agent_framework/_tools.py:2141-2157`), an eight-status occurrence state machine with idempotency keys and retention windows (`packages/ag-ui/agent_framework_ag_ui/_approval_lifecycle.py:93-144`, `242-247`), and an exactly-once contract enforced by spec-mandated regression tests (`docs/specs/004-python-function-calling-loop.md:377-379`). It scores 7/10 — mature for gated calls, absent for ungated ones. **openhands** is a frontend that owns neither execution nor durability, so it builds the read/observe half of the ledger with unusual rigor: pair-linked `ActionEvent`/`ObservationEvent` records carrying before/after file content (`src/types/agent-server/core/base/observation.ts:111-146`), git-derived change summaries at three granularities, and exports that throw rather than ship partial history (`src/utils/transcript-export/load-complete-events.ts:106-110, 153-160`). It scores 6/10 — strong ledger display, weak compensability.

Two convergences stand out despite completely different stacks. First, every system links intent → execution → outcome through stable identifiers (`call_id`, `action_id`/`tool_call_id`, `TxnID`/event ID chains). Second, every system refuses to fabricate certainty about ambiguous writes: temporal classifies errors into "definitely not committed" vs "possibly committed" (`error_type.go:5-22`), agent-framework marks unsettled executions `INDETERMINATE` and retains them for 7 days (`_approval_lifecycle.py:242-244`), and openhands maps `exit_code === -1` to a distinct `timeout` status instead of mislabeling in-flight work as failed (`get-observation-result.ts:30-34`). Equally notable is what none of them do: undo arbitrary external changes. Compensation is either platform-owned artifact cleanup (temporal trims orphaned history, `execution_manager.go:263-274`), raw data without wiring (openhands persists `old_content` snapshots but ships no undo UX), or explicitly out of scope delegated to workflow authors (temporal retry/saga boundary, `retry.go:43-53`; agent-framework's documented sync-tool cancellation gap, `_tools.py:1866-1876`).

## Core Thesis

A side-effect ledger has four distinct jobs — **record intent**, **gate execution**, **record outcomes durably**, and **compensate or honestly classify failures** — and no source implements all four at one layer. Maturity comes from making the division of labor explicit:

- **temporal** makes recording and classification first-class at the storage layer (the ledger *is* the database; conflict detection uses the ledger's own watermark `next_event_id` as the compare-and-swap condition, `mutable_state_impl.go:7626`, `sql/execution_util.go:645-662`). Gating is admission control (fencing, task validation), not human judgment. Compensation exists only for platform-owned artifacts.
- **agent-framework** makes gating first-class (confirmation before execution rather than journaling after; write-ish built-in tools default to `always_require`, `_file_access.py:1444-1445`) and records outcomes only for gated calls. Its most distinctive commitment is *truthful ambiguity*: `ApprovalStatus.INDETERMINATE` exists precisely so "may have executed but no retained terminal outcome" is representable (`_approval_lifecycle.py:77-78`).
- **openhands** makes recording-and-displaying first-class on the client while delegating durability to the server and compensation to git. Its confirmation gate is the only transaction boundary, and it is the weakest one in the study — the pending-action binding scans for "any last agent event" rather than the specific gated action (`conversation-confirmation-buttons.tsx:30-36`).

The practical consequence: "can the system answer 'what did the agent change?'" is answered **by construction** in temporal (replay the history), **by gating** in agent-framework (but only for approved calls — ungated tools leave no registry beyond OTel spans, `_tools.py:733-801`), and **by projection** in openhands (chat stream + git endpoints, with no inventory outside git-tracked paths). When choosing a design, decide which of these three answers your product needs, then note that the cheapest gaps to close are always in the job you assumed someone else owned.

## Approach Models

The sources cluster into three approach models defined by what the ledger is *for*.

**Ledger-as-the-platform (temporal).** Event sourcing means mutable state is derivable entirely from history, so every transaction packages a state diff, new events, generated tasks, and an optimistic condition into one mutation (`CloseTransactionAsMutation`, `mutable_state_impl.go:7592-7636`). Transaction boundaries are explicit at three layers: shard write lock + monotonic `RangeID` fencing (`shard/context_impl.go:597-657`), conditional DB updates guarded by row lock plus `next_event_id`/`db_record_version` conditions (`sql/execution_util.go:629-695`), and in-memory provisional states finalized strictly by post-persist commit/rollback effects (`workflow/update/update.go:258-368`). Write order is deliberately append-history-first, condition-second, trading a transient orphaned-data window for concurrency (`sql/execution.go:334-358`), with trimming as the compensation (`execution_manager.go:263-274`). External-call integrity comes from durable request-ID ledgers mapping client IDs to `(EventType, EventId)` with age/count-bounded sweeping (`mutable_state_impl.go:2591-2700`) and validate-then-execute-then-record CHASM task handlers (`chasm/lib/nexusoperation/operation_tasks.go:61-69, 147-213`). Pro: strongest possible auditability and provable behavior under ambiguous failure. Con: enormous infrastructure cost; business-level compensation explicitly pushed to workflow authors (`retry.go:31-97`).

**Authority-first control-plane ledger (agent-framework).** The ledger's primary job is preventing unauthorized effects, not accounting for them afterwards. Surfaced approval requests are stored as immutable snapshots bound to the provider `call_id`; responses are honored only against the server-held snapshot, with executable data sourced from the request rather than the response and consumed exactly once (`_tools.py:2182-2213`). The AG-UI transport adds an occurrence state machine (`PENDING → CLAIMED → EXECUTING → SETTLED/REJECTED/CANCELLED/EXPIRED/INDETERMINATE`) with optional idempotency keys — a claimed occurrence may only be retried safely with a matching pre-declared key, otherwise recovery degrades to indeterminate (`_approval_lifecycle.py:186, 320-321, 828-847`). Workflow-layer transactions complement this: shared state uses staged pending buffers committed or discarded only at superstep boundaries (`_workflows/_state.py:90-104`), checkpoints capture both state and pending external requests (`_checkpoint.py:59-91`), and a hold-back-then-flush gate gives transcript writes a genuine commit/drop boundary tied to egress verdicts (`_sessions.py:1151-1179`). Pro: exactly-once semantics for dangerous operations with honest failure representation and spec-enforced regression coverage. Con: process-local ledgers lose authority state on restart; ungated third-party tools leave no durable trace; batch aborts cannot stop synchronous tools already running (`_tools.py:1866-1876`).

**Server-owned ledger, client-side projection (openhands).** The event stream is authoritative and lives behind REST/WebSocket APIs; the client seeds via paginated search then catches up (`event-service.api.ts:102-181`) and keeps a memory-only, id-deduplicated store that is explicitly a session cache (`use-event-store.ts:92-129, 209-222`). Every mutation is an `ActionEvent`+`ObservationEvent` pair joined by ids, which makes the display ledger complete-by-construction and lets cards supersede in place (`handle-event-for-ui.ts:404-441`). Change visibility is built entirely on runtime git endpoints — deliberately omitting `ref` so agent-made commits remain visible (`agent-server-git-service.api.ts:143-149`) — and freshness is derived, not pushed: mutation observations are classified and used to invalidate React Query caches (`use-auto-refresh-files-on-edit.ts:8-48`). Pro: rich, tested UX answers "what changed?" at per-call, working-tree, and commit granularity with near-zero server coupling. Con: the client cannot reconstruct history if the backend store is lost, non-git workspaces have no equivalent inventory, and every safeguard the client owns (confirmation dedup, pending-action binding) evaporates on reload (`event-message-store.ts:14-26`).

## Pattern Catalog

**Pair-linked intent/outcome records joined by a stable ID.** Every source structures the ledger as (intent record, outcome record) rather than a flat mutation log: `ActionEvent` carries `tool_name`/`tool_call_id`/`llm_response_id` and its `ObservationEvent` back-references `action_id` (`action-event.ts:33-71`, `observation-event.ts:27-39`); agent-framework stores approval requests keyed by `call_id` and settles results under the same identity (`_approval_lifecycle.py:137-144, 849-875`); temporal chains scheduled/completed event pairs per activity, child workflow, and Nexus operation (`historybuilder/event_store.go:297-360`). *Why it works:* pending work becomes representable (the intent half exists before any outcome), UI can replace in place instead of appending duplicates, and correlation survives async delivery. *Copy when:* anything executes asynchronously or may never produce an outcome. *Overkill when:* purely synchronous, infallible reads. *Evidence:* all three source reports.

**Before/after snapshots as latent compensation data.** openhands' `FileEditorObservation.old_content`/`new_content`/`prev_exist` turn every edit into self-contained undo data (`observation.ts:130-141`) — an asset the report explicitly flags as underexploited since no frontend control invokes the schema-supported `undo_edit` command (`action.ts:69`). agent-framework reaches the same conclusion in Future Considerations: its write tools "already know prior content in many cases." *Why it works:* snapshots make rollback a local operation decoupled from any transaction coordinator. *Copy when:* file-like resources dominate your effect surface. *Risky when:* snapshots bloat the ledger for large artifacts — consider content-addressed references instead. *Evidence:* openhands report (Observations, Future Considerations).

**Uncertainty as a first-class status.** Rather than collapsing ambiguous outcomes into "failed," all three give uncertainty its own representation: `OperationPossiblySucceeded(err)` partitions persistence errors into guaranteed-non-commit vs possibly-committed, and unknown errors trigger shard re-acquisition with a fresh `RangeID` so later reads resolve the outcome deterministically (`error_type.go:5-22`, `context_impl.go:1538-1547`); `ApprovalStatus.INDETERMINATE` retains possibly-started executions for 7 days, excluded from purgeable retention (`_approval_lifecycle.py:113-119, 242-244`); openhands maps `exit_code === -1` to `timeout`, not `error` (`get-observation-result.ts:30-34`). *Why it works:* callers can distinguish "retry safely" from "reconcile externally" — conflating them causes either double execution or abandoned cleanup. *Copy when:* you execute effects whose completion you cannot observe directly. *Cost:* consumers must actually handle the extra states; agent-framework documents that indeterminate occurrences require external reconciliation. *Evidence:* all three source reports.

**Validate-before-execute idempotency gates.** temporal's CHASM handlers reject stale/duplicate deliveries before running any update function: Nexus invocations validate `op.Status == SCHEDULED && op.Attempt == task.Attempt`, and already-seen request IDs are rejected with `ErrRequestIDAlreadyUsed` (`operation_tasks.go:61-69`, `chasm_engine.go:554-577`). agent-framework binds authority exclusively to the stored request snapshot — never replayed history or response payloads — and consumes approvals once so they cannot authorize a different or repeated call (`security.py:2057-2076`, spec lines 366-371). MCP tasks capture the server-issued `task_id` before any reconnect retry and never re-issue an augmented call whose receipt is unknown (`_mcp.py:2246-2278`, comment at 2376). openhands' `submittedEventIds` set is the weakest variant — memory-only, per-session. *Why it works:* moving the dedup check before the effect eliminates an entire class of double-execution bugs that post-hoc detection cannot fix. *Copy when:* any retried delivery mechanism. *Evidence:* all three source reports; temporal and agent-framework include failure-injection tests (`test_approval_lifecycle.py:720-830`, `common/persistence/tests/execution_mutable_state.go:174-307`).

**Staged buffers resolved at explicit commit points.** agent-framework stages workflow state in pending buffers committed/discarded at superstep boundaries (`_state.py:90-104`) and queues durable history writes until an egress verdict permits flushing or forces dropping (`_sessions.py:1151-1179`). temporal mirrors this at finer grain: response buffers are created up front, cancelled on any persistence error, and applied only after the durable write succeeds (`respondworkflowtaskcompleted/api.go:245-259, 673-715`), with provisional in-memory states finalized by `OnAfterCommit`/`OnAfterRollback` closures (`update/update.go:258-368`). *Why it works:* downstream observers never see state that was never durable — the classic cause of phantom UI entries after crashes. *Copy when:* you have any consumer reacting to in-progress mutations. *Note:* openhands lacks this pattern entirely on the client; its store mutates immediately and relies on server truth to self-correct. *Evidence:* agent-framework and temporal reports.

**Retention-bounded ledgers with exempt identity classes.** Both platform sources cap unbounded growth: temporal sweeps CHASM request IDs older than `RequestIDMaxAge` and enforces `MaximumRequestIDsPerExecution`, while keeping event-backed IDs forever (`mutable_state_impl.go:2655-2700`); agent-framework applies tiered retention (pending expiry 24h, indeterminate 7 days, terminal 15 min, capacity 10k) with structured `retention_purge` audit events (`_approval_lifecycle.py:242-247, 704-740, 762-778`). *Why it works:* dedup ledgers otherwise grow monotonically with traffic; bounding them with exemptions for permanent identities keeps memory predictable. *Risk:* temporal's own report notes that extremely old duplicate retries could theoretically re-execute after age-based eviction — a corner with no covering test. *Copy when:* your dedup keys have a natural retry horizon shorter than your data lifetime.

**Completeness-proofs and quarantine over silent partiality.** openhands' transcript loader detects repeated cursors, non-advancing pagination, and count mismatches, throwing instead of exporting a silently truncated history (`load-complete-events.ts:86-123, 153-160`). agent-framework quarantines corrupt session snapshots and preserves the originals rather than deleting (`_sessions.py:1959-1972, 2055-2065`). temporal provides archived-history read-through fallback so old runs remain retrievable past retention (`workflow_handler.go:995-1000`). *Why it works:* an audit trail you cannot prove complete is worse than none — consumers will wrongly treat absence as evidence of no action. *Copy when:* anything exports or migrates ledger data. *Evidence:* openhands and agent-framework reports primarily.

**Rejection as a first-class record.** openhands materializes refusals as `UserRejectObservation` with `rejection_reason` and `action_id`, keeping even refusals inside the ledger (`observation-event.ts:42-52`); agent-framework's spec mandates rejected calls "execute zero times" yet still produce a synthetic rejection result so the transcript stays coherent (spec lines 377-383). *Why it works:* audits need negative evidence too; without rejection records, "nothing happened" is indistinguishable from "the record was lost." *Copy when:* humans (or policies) can veto actions.

## Key Differences

**What the ledger records.** temporal records *outcomes of everything the platform does* — scheduling, timers, markers, outbound Nexus calls with attempts and backoffs ("retries are recorded, not hidden," `operation_statemachine.go:21-75`). agent-framework records *authority plus outcome for gated calls only*: name, exact arguments, owner, decision, and replayable result under the original call identity (`_approval_lifecycle.py:173-192, 849-875`); ungated tools leave only OTel spans. openhands records *a display projection* of a server-owned stream — complete per tool call, but with bash mutations visible only indirectly via exit codes and refreshed diff queries.

**Where the transaction boundary lives.** temporal: storage-layer conditional writes fenced by shard range ownership. agent-framework: two places — superstep commit/checkpoint for workflow state and the batch-abort/persistence-gate for tool and transcript effects. openhands: nowhere on the client; the only pre-commit gate is the user confirmation POST (`use-respond-to-confirmation.ts:21-30`), and no begin/commit/rollback semantics exist anywhere in the repo (searches for `transaction|rollback|compensat` match no functional code).

**Compensation philosophy.** This is the sharpest divergence. temporal makes every outbound effect *retryable-and-idempotent* so compensation becomes a workflow-level concern — duplicate activity starts replay the original confirmation as a positive response instead of double-starting (`recordactivitytaskstarted/api.go:150-166`). agent-framework prefers *prevention plus truthful surrender*: fail-closed batch aborts, best-effort remote `tasks/cancel` with an abandonment-vs-terminal taxonomy (`_mcp.py:2573-2608`), and `mark_indeterminate` when recovery is impossible. openhands *records undo data but wires nothing*: `old_content` snapshots and the `undo_edit` schema command sit unused, leaving git as implicit compensation.

**Dedup-as-confirmation vs dedup-as-error.** When temporal detects a duplicate (same request ID on an already-started activity), it *replays the original confirmation*, converting a potential double-execution into a success signal. When agent-framework detects an unrecoverable duplicate situation (unknown-receipt MCP reconnect), it surfaces a typed user-visible failure (`ToolExecutionException("connection lost; task state unknown")`, `_mcp.py:2537-2543`). Same goal — no double execution — opposite user experience: liveness-preserving replay versus loud refusal.

**Durability locus of safeguards.** temporal keeps everything durable with bounded sweeps; its residual weakness is only eventual consistency of derived views. agent-framework splits: session-held request snapshots persist via atomic `os.replace` file writes (`_sessions.py:2019-2022`), but the AG-UI occurrence machine and the security `audit_log` are process-local dicts/lists (`_approval_lifecycle.py:236-265`, `security.py:1697-1698`). openhands delegates all durability server-side; its client-owned guards are explicitly session caches.

**Change-summary substrate.** openhands derives summaries from git (changes list, diffs, aggregate +/- stats, commits pane). temporal exposes them via ledger APIs (`GetWorkflowExecutionHistory`, `DescribeWorkflowExecution` surfacing pending activities/callbacks/Nexus ops, `workflow_handler.go:3320-3372`). agent-framework surfaces them as protocol events (approval requested/responded mappings in DevUI, AG-UI thread snapshots) and notably ships **no aggregate end-of-run "changes made" summary component** — a gap openhands partially closes only for automation runs (CSV export keyed by run/conversation IDs, `automation-activity-log-export.ts:12-27`).

## Tradeoffs

**Append-first vs single-transaction write order (temporal).** Appending history outside the mutable-state DB transaction avoids holding shard locks during history I/O, buying throughput at the cost of a crash window that leaves orphaned history rows until best-effort `trimHistoryNode` runs (`sql/execution.go:338-350`, `execution_manager.go:1083`). Alternative seen: agent-framework's atomic temp-file + `os.replace` writes achieve single-operation atomicity but only for small local files — not viable at temporal's scale. Best fit: high-concurrency platforms with a documented, bounded cleanup story. Failure mode: unbounded orphans if trimming silently stops working.

**Prevention-first gating vs post-hoc journaling (agent-framework vs openhands).** Defaulting every write-ish harness tool to `always_require` maximizes auditability and prevents unauthorized effects outright, but requires explicit opt-outs or auto-approval rules to run unattended (`_tool_approval.py` middleware, `_file_access.py:1231-1244`). Journaling-everything (openhands) preserves flow and completeness but cannot prevent anything — its only preventive control is the confirmation gate, whose client-side binding is fragile. Best fit: prevention-first for frameworks hosting agents in regulated contexts; journaling-first for observation-heavy products where the operator is trusted.

**In-memory simplicity vs restart survivability (agent-framework, openhands).** Both pay this tax: `ApprovalLifecycle` dicts + RLocks, the security `audit_log` list, and openhands' `submittedEventIds` all vanish on reload, meaning pending-authority state and one-shot decision markers are lost precisely during the interruptions they exist for. temporal pays complexity instead (fencing, range rotation, sweeps) and gets durability everywhere. Failure mode observed in openhands: a reload during `AWAITING_USER_CONFIRMATION` loses the submitted marker and can re-offer buttons (server presumably still enforces one response — unverified).

**Exactly-once enforcement vs liveness (agent-framework vs temporal).** Refusing to re-issue unknown-receipt MCP calls guarantees no double execution but strands users behind `ToolExecutionException` until manual reconciliation. temporal's replay-the-confirmation approach keeps workers productive across retries but requires every subsystem to implement confirmation replay faithfully (activities do; the report notes request-ID-ledger eviction as the residual hole). Best fit: loud refusal where effects are expensive and irreversible; replay where idempotency infrastructure is thorough.

**Derived freshness vs push-based fanout (openhands vs temporal).** openhands invalidates whole query families whenever any bash observation arrives — correct but potentially chatty, because shell commands are opaque (`use-auto-refresh-files-on-edit.ts:57-64`). temporal's post-commit fanout notifies engines about exactly-the-committed-facts (`transaction_impl.go:589-654`) but requires the notification machinery to be part of the transaction protocol itself. Pull-based wins for thin clients over heterogeneous backends; push-based wins when you own both ends.

**Bounded ledgers vs long-horizon retries (both platforms).** Age/count caps keep memory predictable but create a theoretical resurrection window (temporal: days-later duplicate after eviction; agent-framework: terminal records purged after 15 minutes, so late audits rely on logs, not the ledger). Exempting event-backed identities (temporal) narrows but does not eliminate the window; the honest alternative is documenting the horizon as part of the contract.

## Decision Guide

Choose an approach model by **ownership position**, then tighten safeguards by **blast radius**:

1. **Building an execution engine or platform that owns persistence?** Copy temporal: append-only chained ledger as the source of truth, conditional writes using the ledger's own watermark as the CAS condition, and an explicit error taxonomy separating definitely-not-committed from possibly-committed. Accept that business-level compensation belongs to your users; document the boundary (temporal does, via retry semantics docs).
2. **Building a framework/library embedded in someone else's app?** Copy agent-framework's authority model: immutable request snapshots as the sole source of executable truth, one-time consumption, idempotency keys for safe retry recovery, and an `INDETERMINATE` status so ambiguity is representable. Learn from their gap: put durability into the occurrence ledger *earlier* — process-local state machines are the weakest link in an otherwise mature design.
3. **Building a client/UI over a server-owned ledger?** Copy openhands: pair-linked rendering with in-place supersession, git (or equivalent VCS) as the change-summary substrate, completeness-proof exports, and pull-based convergence. Do not copy its confirmation binding — attach gates to specific action IDs, not "whatever event is last."

Decision rules for specific forks:

- **Gate or journal?** Gate (confirm-before-execute) when unauthorized execution is unacceptable and latency tolerance is human-scale; journal when autonomy matters more than prevention and effects are reversible or low-cost. agent-framework defaults its own write tools to gated — a reasonable prior for file/shell surfaces.
- **Retryable-idempotent or prevent-and-refuse?** Retryable if you control the receiver and can thread request IDs end-to-end (temporal's Nexus handlers receive forwarded request IDs, `operation_tasks.go:153-161`); refuse-and-mark-indeterminate if the remote's receipt semantics are unknown (agent-framework's MCP posture).
- **Compensate or classify?** Compensate only effects you own (temporal trimming its own orphaned nodes); for external-world effects, invest in idempotency and honest classification instead — all three sources independently arrived at this line, and none crossed it.

## Practical Tips

- Record before/after content on every mutation even if you ship no undo today — openhands' `old_content` snapshots are described as the highest-leverage upgrade available precisely because the data already exists.
- Give ambiguity its own status value from day one (`INDETERMINATE`, `timeout`, `OperationPossiblySucceeded`); retrofitting a third outcome into a boolean success/failure world breaks every consumer.
- Make rejection produce a durable, typed record carrying the refused action's ID — both the UI (openhands) and the transcript contract (agent-framework spec) stay coherent because refusals are events, not silences.
- Bind every confirmation/approval to the specific gated action's identifier and consume it exactly once against a stored snapshot; derive executable data from the request, never from the response payload (agent-framework's anti-replay core).
- Classify persistence errors before deciding what to tell downstream consumers: notify speculatively only on possibly-committed failures, and rotate whatever fencing token you have so subsequent reads resolve the ambiguity (temporal's range rotation).
- Bound every dedup/idempotency ledger with age and count limits, and exempt permanently-backed identities from sweeping (temporal's event-backed request IDs).
- Use atomic write primitives for any local ledger file and quarantine corrupt snapshots rather than deleting them (agent-framework's `os.replace` + quarantine pattern).
- Spec-mandate regression coverage for exactly-once properties — agent-framework declares the function-calling loop high-risk with a mandatory scenario matrix including "a possibly started side effect is not retried" (`docs/specs/004-python-function-calling-loop.md:30-45, 333-338`); the tests exist and pass (`test_approval_lifecycle.py:720-830`).
- Prove completeness at export time: detect pagination loops and count mismatches, and fail loudly rather than shipping a truncated audit trail (openhands).

## Anti-Patterns / Caution Signs

- **Memory-only guards for one-shot decisions.** openhands' `submittedEventIds`, agent-framework's in-process `audit_log`, and the AG-UI occurrence dicts all lose their protective state on restart. Caution sign: any "already handled?" check living in module-level memory.
- **Weak binding of human gates.** openhands finds the awaited action by scanning reversed events for *any* agent-sourced event while awaiting confirmation — the predicate ignores event content (`conversation-confirmation-buttons.tsx:30-36`). If your confirmation UI can attach to the wrong action, the gate is decorative.
- **Unaudited divergence between world state and transcript.** agent-framework documents that a synchronous tool in a worker thread completes its side effects during batch cancellation while its result is discarded (`_tools.py:1866-1876`) — the effect lands, nothing records it. Any cancellation path that discards results without marking the possibility-of-execution creates this hole.
- **Opaque side-effect surfaces forcing broad invalidation.** openhands must invalidate *all* file-change queries on any bash observation because shell commands could touch anything — correct but chatty, and a signal that the harness cannot enumerate what its own tools affect.
- **Best-effort compensation without observability.** temporal's orphaned-history trim is acceptable because it is bounded and documented; the same pattern becomes an anti-pattern when nobody measures trim backlog. If you adopt append-first-write orders, instrument the orphan window.
- **Ledgers that only cover the well-behaved subset.** agent-framework's approval ledger is exemplary for gated calls, but ungated third-party tools leave no durable trace beyond OTel spans — "what did the agent change?" quietly becomes unanswerable for exactly the tools most likely to do damage. Caution sign: coverage percentages of your effect surface that you cannot state.
- **Conflating timeout with failure.** openhands explicitly separates soft timeouts (`exit_code === -1`, still running) from errors; treating in-flight work as failed triggers premature compensation or user alarm.

## Notable Absences

- **No generic saga/business-level compensation anywhere.** All three reports confirm the absence: agent-framework searched `saga|compensat|rollback|undo` across Python and .NET trees with only unrelated hits; temporal states the boundary as design ("at-least-once, deduplicated, recorded" — compensation is the developer's job, `retry.go:43-53`); openhands found no multi-step transactional semantics ("apply these 5 edits atomically").
- **No durable confirmation-decision record verified in openhands.** `respondToConfirmation` returns only `{success}` (`event-service.types.ts:9-11`); whether the server logs the accept/reject decision as an event could not be verified from this repo.
- **Nothing sends `undo_edit` in the openhands repo.** Only schema definitions and observation mirrors exist; the capability may be purely server/agent-side.
- **No revert controls in openhands' UI** despite git data being present — the actions menu exposes commit/push flows only.
