## Executive Summary

This dimension could be evaluated against **two of ten** sources. Only `langfuse` (TypeScript Next.js observability platform exposing layered REST APIs, **8/10**) and `openhands` (the `@openhands/agent-canvas` npm package combining an operator CLI, standalone web app, and embeddable library, **7/10**) yielded populated snapshots. Both land in the rubric's 7–8 band — "clear model with tests, explicit interfaces, and operational safeguards" — and both earned it through the same fundamental move applied to very different product shapes: they define their public API with **one small, named, centrally enforced boundary artefact**, back it with **automated checks that fail when the surface drifts**, and give **evolution its own explicitly labelled namespace** rather than mutating existing entry points silently. The other eight sources scored 1/10 because their directories contain zero files — a statement about the study pipeline, not about the upstream projects (flagged independently by nearly every empty-source report, e.g. the orchestration-level critique in the pydantic-ai report's failure-modes section).

In langfuse the boundary is the route-wrapper pair `withMiddlewares` + `createAuthedProjectAPIRoute` (`web/src/features/public-api/server/withMiddlewares.ts:84-206`, `web/src/features/public-api/server/createAuthedProjectAPIRoute.ts:307-492`): every project-scoped REST route funnels through them for authentication, strict-Zod validation, rate limiting, deprecation stamping, CORS, and normalised errors, while three separate Fern API definitions define three auth audiences and generate the published OpenAPI specs via `pnpm run openapi:export` (`package.json:41`). In openhands the boundary is the package export map plus curated barrels: `package.json:206-248` declares eight npm subpath exports wired through per-domain barrels aggregated by `src/lib/index.ts:1-57`, guarded by CI tests that assert the published shape (`__tests__/library-entrypoints.test.ts:10-49`) and block raw backend access (`src/api/no-direct-agent-server-calls.test.ts:32-79`), with `AgentServerUIProviders` (`src/components/providers/agent-server-ui-providers.tsx:48-123`) as the single host-integration entry point.

They diverge where their products diverge. Langfuse serves third-party integrators over the network, so it invests in URL-versioned route families (`/api/public/v2/*`, `/v3/*` beside legacy v1), an explicitly fenced `/api/public/unstable` namespace carrying its own machine-readable error envelope (`web/src/features/public-api/shared/unstable-public-api-error-schema.ts:3-23`), `_deprecation` payloads stamped onto response bodies (`web/src/features/public-api/server/deprecations.ts:99-114`), and rate-limit responses that name the replacement endpoint (`web/src/features/public-api/server/rateLimitUpgradePaths.ts:10-47`). Openhands ships code into hosts' builds, so it invests instead in `types`/`import`/`require` triplets per subpath, published CSS-isolation constants hosts can target without reading source (`src/styles/agent-server-ui-style-scope.ts:1-95`), and router-decoupled navigation abstractions (`src/context/navigation-context.tsx:7-41`) — but has **no stability markers at all** on exported symbols and **no embedder-facing examples**, the two largest gaps found in either mature source.

Both systems pay their consistency tax at exactly the same place: where an entry point cannot fit the central boundary. Langfuse's SCIM, OTel, and native-ingestion endpoints bypass the wrapper with hand-rolled auth and `z.any()` validation (`web/src/pages/api/public/scim/Users/index.ts:1-313`, `web/src/pages/api/public/otel/v1/traces/index.ts:29-30`); openhands's conversation barrel re-exports a React-Router-coupled route component (`src/components/conversation/index.ts:1`), coupling library consumers to the standalone app's routing. The pattern is clear: the boundary is the load-bearing design decision, and exceptions to it need their own documented contract or they become the surface's weak points. Finally, the eight empty sources contribute a meta-lesson that belongs in any API-surface checklist: an API surface is a deliverable first — if the artefact never reaches its consumers, internal quality is irrelevant.

## Core Thesis

> A durable public API surface is not produced by naming discipline, documentation effort, or language visibility rules alone; it is produced by **mechanised enforcement at a single named boundary**, with evolution quarantined in explicitly labelled namespaces. Langfuse demonstrates this at API-platform scale: one route factory governs auth/validation/errors/rate-limits for all project-scoped routes (`web/src/features/public-api/server/createAuthedProjectAPIRoute.ts:307-492`), Fern YAML is the single contract source that generates OpenAPI and drives deprecation syncing (`web/scripts/openapi/sync-deprecations.ts:17-25`), and the `/unstable` prefix plus a distinct error schema make "this may change" machine-checkable (`web/src/features/public-api/shared/unstable-public-api-error-schema.ts:3-68`). Openhands demonstrates the same principle at package scale: an exports map plus assertion tests keeps the npm surface narrow and regression-checked, including asserting that removed symbols *stay removed* (`__tests__/library-entrypoints.test.ts:44-48`). Both codebases leak precisely where entries bypass the boundary — which is direct evidence that the boundary, not the number of endpoints, is what holds the surface together. The corollary from the eight empty sources: before evaluating whether an API is well-designed, verify it is reachable; an unmaterialised artefact silently converts every downstream consumer (or dimension) into a no-evidence outcome, and pipelines should fail fast on that condition rather than grade the void.

## Approach Models

Clustering by how the public surface is defined, separated from internals, and kept stable yields two substantive models and one non-model.

**Model A — Contract-first API platform (langfuse).** The intended public surface is a set of HTTP route families, each owned by a declarative contract. Three Fern APIs define three audiences with three auth models: project-scoped REST under Basic auth rooted at `/api/public` (`fern/apis/server/definition/api.yml:1-28`), organization-admin REST under a self-hosted-only Bearer `ADMIN_API_KEY` (`fern/apis/organizations/definition/api.yml:24`), and a deliberately reduced bearer-only client API scoped to score creation so SDKs holding limited keys cannot read anything else (`fern/apis/client/definition/api.yml:4`, `fern/apis/client/definition/score.yml:38-40`). The implementation mechanism is uniform route wrapping: `createAuthedProjectAPIRoute` authenticates via `ApiAuthService` (`web/src/features/public-api/server/apiAuth.ts:35-291`), rate-limits through a Redis-backed service that fails open when Redis is missing (`web/src/features/public-api/server/RateLimitService.ts:52-100`, fail-open at `:93-96`), parses strict-Zod query/body schemas whose generics infer handler argument types (`createAuthedProjectAPIRoute.ts:43-100`), stamps `_deprecation` payloads, attaches OpenTelemetry context, and serialises the response. Supporting mechanisms: dev-only response-schema validation to catch handler drift without production cost (`createAuthedProjectAPIRoute.ts:466-471`), family-level deprecation constants sharing one sunset date (`web/src/features/public-api/server/deprecations.ts:11-97`), endpoint-named server tests covering every route family (`web/src/__tests__/server/*.servertest.ts`), and an AGENTS.md contributor contract declaring the wrapper + Fern update flow mandatory (`web/AGENTS.md:127-128`, `AGENTS.md:96-99`).

**Model B — Audience-partitioned embeddable package (openhands).** The intended public surface is three coordinated artefacts aimed at three audiences: operators get the `agent-canvas` CLI binary with flags (`--version`, `--info`, `--public`, `--frontend-only`, `--backend-only`, `-p/--port`) and documented env vars (`bin/agent-canvas.mjs:26-122`, env surface at `:85-95`); application users get the standalone web app mounted behind `AgentServerUIRoot` with first-run onboarding and recovery screens (`src/root.tsx:92-113`, `:339-380`); extension authors get eight npm subpath exports wired through per-domain barrels and aggregated by `src/lib/index.ts:1-57`, with `AgentServerUIProviders` as the canonical host-integration entry (`src/components/providers/agent-server-ui-providers.tsx:48-123`). The main mechanism is packaging-as-boundary: the `exports` map with `types`/`import`/`require` triplets per subpath (`package.json:206-248`), narrowed declaration emit via `tsconfig.lib.json`, and CI tests asserting both metadata shape and symbol resolvability (`__tests__/package-library.test.ts:23-158`, `__tests__/library-entrypoints.test.ts:10-49`). Supporting mechanisms: two hard access rules enforced by tests (agent-server calls must go through `@openhands/typescript-client` classes, `src/api/no-direct-agent-server-calls.test.ts:32-79`; browser-to-cloud calls must flow through `callCloudProxy()`, `src/api/cloud/proxy.ts:18-39`), a documented service-adapter naming convention (`src/api/README.md:1-98`), router decoupling so library consumers never wire React Router themselves (`NavigationProvider`/`NavigationLink`, `src/context/navigation-context.tsx:7-41`, `src/components/shared/navigation-link.tsx:11-105`), and published style-scope constants so host CSS targets `[data-agent-server-ui]` without parsing source (`src/styles/agent-server-ui-style-scope.ts:1-95`).

**Non-model — absent evidence (eight sources).** `agent-framework`, `crewai`, `langgraph`, `letta`, `opa`, `openai-agents-sdk`, `pydantic-ai`, and `temporal` present zero inspectable surface: no manifests, no modules, no routes, no docs, no tests inside their snapshot directories (each per-source report documents the search boundary exhaustively; e.g., the letta report's finding that `find … -type f` returned zero results). Their manifests name upstream URLs but contain no code, and the source-isolation rule correctly prevented any cross-source inference. These are not "bad APIs"; they are *no* APIs within the inspection boundary — a distinction that matters for how the ratings above should be read and for the pipeline questions raised under Open Questions.

## Pattern Catalog

Patterns appear below only if demonstrated by both materialized sources or shown unusually clearly by one. Each includes the problem it solves and its evidence basis.

**P1. Single choke-point entry artefact.**
*Problem:* keeping cross-cutting concerns (auth, validation, errors, rate limits, telemetry) consistent across dozens of public entry points.
*Demonstrated by:* langfuse, where changing auth semantics or the error envelope touches exactly two files (`web/src/features/public-api/server/withMiddlewares.ts:84-206`, `web/src/features/public-api/server/createAuthedProjectAPIRoute.ts:307-492`); openhands, where `AgentServerUIProviders` mounts QueryClient/i18n/analytics/backends/style scope in one shot (`src/components/providers/agent-server-ui-providers.tsx:48-123`) and `getAgentServerClientOptions()` is the single way to assemble SDK client options (`src/api/agent-server-client-options.ts:52-69`).
*Why it works:* every entry point inherits policy changes for free; reviewers know the one place security-relevant logic lives; per-route configuration stays declarative (flags like `errorContract`, `rejectInEventsOnlyMode`, `allowInAppAgentKey`, `isAdminApiKeyAuthAllowed` in langfuse).
*When to copy:* once a surface exceeds a handful of externally visible entry points.
*Overkill/risky when:* an entry point's wire format fundamentally differs from the norm — forcing SCIM RFC 7644 or OTLP protobuf through the wrapper either bloats it with special cases or pushes authors to bypass it, which is strictly worse (both outcomes observed in langfuse's SCIM and OTel handlers).
*Evidence:* langfuse report §Architectural Decisions 1–2; openhands report §Architectural Decisions 1–3.

**P2. Generated or machine-checked contract artefacts as the published truth.**
*Problem:* documentation, specs, and runtime behaviour drifting apart as the surface evolves.
*Demonstrated by:* langfuse, where Fern YAML is the single source generating three OpenAPI specs via `pnpm run openapi:export`, post-processed by a deprecation-sync script that copies `availability.status: deprecated` markers into the spec (`package.json:41`, `web/scripts/openapi/sync-deprecations.ts:1-25`, `web/scripts/openapi/fern-deprecations.ts:71-114`), with hand-editing of `web/public/generated/**` forbidden by the AGENTS contract (`AGENTS.md:96-99`); openhands, where the `package.json` exports map *is* the contract and tests assert its shape, exact-semver pinning, and absence of git dependencies (`__tests__/package-library.test.ts:23-158`).
*Why it works:* the contract, the docs, and (in langfuse's case) parts of the runtime behaviour become projections of one source; drift becomes a build/test failure instead of a support ticket.
*When to copy:* whenever the surface has more than a few endpoints or packages, or whenever external codegen consumes your spec.
*Overkill/risky when:* the surface is small and stable enough that generation machinery costs more than hand-syncing — though both studied sources suggest that threshold arrives early.
*Evidence:* langfuse report §Summary and §Architectural Decision 3; openhands report §Rating rationale.

**P3. CI-enforced boundary tests, including negative (removal) assertions.**
*Problem:* public surface accreting accidentally because nothing fails when internals leak outward.
*Demonstrated by:* openhands most sharply — `__tests__/library-entrypoints.test.ts:44-48` asserts not only that every published subpath resolves but that a deliberately removed export (`AgentServerSettings`) *stays* removed; `src/api/no-direct-agent-server-calls.test.ts:32-79` blocks raw axios/fetch calls to the agent server, forcing traffic through the typed client package; langfuse complements this with a drift test failing the build if the v3 sunset date diverges between Fern messages, the notice constant, and the date literal (`openapi-deprecations.servertest.ts`, referenced at `web/src/features/public-api/server/deprecations.ts:10`).
*Why it works:* privacy conventions (`_internal/`, underscore prefixes, unexported identifiers) are advisory; a test that inspects the *published artefact* converts the convention into an invariant. Negative assertions additionally prevent well-meaning re-additions.
*When to copy:* always, for any surface consumed outside the team. The removal-assertion variant is cheap and uniquely protects against regression-by-revert.
*Overkill/risky when:* never meaningfully — the cost is one test file.
*Evidence:* openhands report §Answers Q2 and §Evidence rows "Library-entrypoint CI guard", "Package-library metadata guard"; langfuse report §Failure Modes ("OpenAPI ↔ Fern drift").

**P4. Explicit instability namespaces with their own contracts.**
*Problem:* evolving features break consumers who cannot tell experimental from stable.
*Demonstrated by:* langfuse's `/api/public/unstable/*` namespace, which is unambiguously labelled by URL prefix (`fern/apis/server/definition/unstable/evaluators.yml:9`), carries a distinct machine-readable error schema with `.strict()` binding and a stable enum of codes such as `evaluator_preflight_failed` and `rate_limited` with `retryAfterSeconds` detail (`web/src/features/public-api/shared/unstable-public-api-error-schema.ts:3-68`, mapping in `web/src/features/public-api/server/unstable-public-api-error-contract.ts:160-262`), and is documented as free to evolve while the data model is redesigned (`fern/apis/server/definition/unstable/evaluators.yml:41-42`).
*Why it works:* instability is signalled at every layer a consumer touches — URL, type names (`unstable-*` type files), error envelope — so agents and SDKs can program against the contract (e.g., retry on `evaluator_preflight_failed`) without parsing prose.
*When to copy:* shipping any feature whose data model is still moving but which needs real users now.
*Overkill/risky when:* the namespace lacks a graduation policy — langfuse itself flags that criteria for leaving `unstable` are not codified (see Notable Absences), which risks permanent limbo.
*Evidence:* langfuse report §Summary, §Architectural Decision 5, §Notable Patterns.

**P5. Machine-readable migration guidance attached to the responses that need it.**
*Problem:* deprecating endpoints without stranding integrators.
*Demonstrated by:* langfuse — `attachDeprecation` stamps a structured `_deprecation` object (`replacement`, `docsUrl`, `sunsetAt`) onto JSON bodies (`web/src/features/public-api/server/deprecations.ts:99-114`); every legacy route maps to its replacement via `rateLimitUpgradePaths` propagated into 429 responses (`web/src/features/public-api/server/rateLimitUpgradePaths.ts:10-47`, `RateLimitService.ts:391-396`); even ClickHouse resource errors carry messages naming the exact v2 endpoint to switch to (`withMiddlewares.ts:47-60`).
*Why it works:* the guidance arrives at the moment of failure, in-band, parseable by machines — no doc lookup required.
*When to copy:* any long-lived API with versioned replacements; pairs naturally with P4.
*Overkill/risky when:* sunset semantics get muddled — langfuse's `V3_SUNSET_DATE` refers to a *product* version migration, not API v3, a documented recurring confusion (`deprecations.ts:11-16`). Name axes carefully.
*Evidence:* langfuse report §Architectural Decisions 6, 10; §Tradeoffs (sunset-axis item).

**P6. Audience-partitioned surface with one entry point per audience.**
*Problem:* operators, application developers, and extension authors need different contracts from the same system.
*Demonstrated by:* both sources independently. Langfuse partitions by auth mode bound to separate Fern APIs (project keys / limited-scope score keys / admin keys, `fern/apis/{server,client,organizations}/definition/*.yml`); openhands partitions by distribution tier (CLI binary at `package.json:16-18`, standalone app at `src/root.tsx:92-113`, library subpaths at `package.json:206-248`).
*Why it works:* each audience gets the minimal surface it needs — limited-scope keys cannot read traces; library consumers never see stores or services; operators get one binary with `--help` (`bin/agent-canvas.mjs:58-122`). Minimal surfaces are cheaper to keep stable.
*When to copy:* whenever more than one consumer class exists — which is essentially always for agent harness infrastructure.
*Overkill/risky when:* partitioning multiplies maintenance (three parallel route trees in langfuse; two CLI launchers behaving differently in openhands, `bin/agent-canvas.mjs:151-159`).
*Evidence:* both reports' §Answers Q1.

**P7. Publish customization constants instead of hiding magic.**
*Problem:* embedders and integrators need extension points but shouldn't reverse-engineer internals.
*Demonstrated by:* openhands exporting `AGENT_SERVER_UI_SCOPE_ATTRIBUTE`/`_SCOPE_SELECTOR`/`_DEFAULT_CSS_VARIABLES`/`_DEFAULT_THEME` so host CSS targets the widget tree legitimately (`src/styles/agent-server-ui-style-scope.ts:1-95`), theme tokens living as `--oh-*` CSS variables requiring no React surface, and window globals (`window.__AGENT_CANVAS_LOCK_TO_CLOUD__`, `src/api/agent-server-config.ts:141-181`) enabling serve-time configuration without rebuilds; langfuse's analogue is query-level field-group selection in v2 observations letting callers shrink payloads (`fern/apis/server/definition/observations.yml:39-44`, handler at `web/src/pages/api/public/v2/observations/index.ts:14-93`).
*Why it works:* sanctioned hooks displace unsanctioned ones; the alternative is consumers reaching into internals, which freezes your implementation forever.
*When to copy:* any embedded or highly configured component.
*Overkill/risky when:* constants multiply faster than their consumers — each published constant is a compat commitment.
*Evidence:* openhands report §Architectural Decisions (CSS isolation, window globals); langfuse report §Notable Patterns (field-group selection).

## Key Differences

**Where the contract lives.** Langfuse externalises the contract into a declarative DSL (Fern YAML) from which specs and docs are generated; openhands keeps the contract in package metadata (`exports` map) plus code-adjacent assertion tests. Neither trusts prose. Langfuse's choice buys richer downstream artefacts (client codegen, hosted references) at the cost of a generation pipeline and sync scripts; openhands' choice buys zero tooling dependencies at the cost of thinner consumer-facing documentation. Both are valid responses to different distribution models: langfuse's consumers are remote HTTP clients who need a spec, openhands' consumers import compiled modules and need a resolvable surface.

**How versions are expressed.** Langfuse versions by URL family — `/api/public/v2/observations`, `/v3/scores` coexisting with deprecated v1 (`web/src/pages/api/public/v2/observations/index.ts:14-93`; deprecation constants at `deprecations.ts:11-97`) — allowing side-by-side operation and per-family sunset dates. Openhands versions by semver plus subpaths plus pinned peers (`react-router: 7.18.2` as a peer dependency, `package.json:249-253`), meaning breaking changes are release events rather than new routes. URL versioning fits network APIs where old clients live beyond your deploy cycle; semver/subpaths fit libraries where the consumer controls upgrade timing. These are not quality differences.

**Error philosophy.** Langfuse normalises everything into typed envelopes — the default contract maps error classes to statuses in one middleware, and the unstable namespace goes further with a strict enumerated error schema carrying retry metadata (`withMiddlewares.ts:117-139` mapping; `unstable-public-api-error-schema.ts:3-68`). Openhands relies on typed exceptions (`NoBackendAvailableError`, `src/api/agent-server-client-options.ts:55-58`) propagating to a central QueryClient toast handler (`src/query-client-config.ts:31-77`). Envelopes suit machine clients integrating over HTTP; exception-plus-handler suits in-process React hosts. Again: constraint-driven divergence, not maturity difference.

**Documentation depth asymmetry.** Langfuse writes rich inline examples into its contract source — the unstable evaluators definition ships a full worked POST body with recovery guidance (`fern/apis/server/definition/unstable/evaluators.yml:11-55`) — so generated docs inherit them. Openhands documents its operator surface thoroughly (`README.md:50-118`, `docs/SELF_HOSTING.md`, `examples/acp-docker/`) but its library/embedder audience gets only JSDoc; there is no `examples/embed-host-app/` walkthrough of mounting `AgentServerUIProviders` (openhands report §Answers Q4). The lesson cuts both ways: put examples where the contract is defined, and audit example coverage per audience, not per repository.

**Nature of boundary violations.** Langfuse's violations are *documented necessity*: SCIM must speak RFC 7644 and OTel must accept protobuf, so they bypass the Zod wrapper — but nothing marks these as intentional exemptions for future contributors, and the langfuse report explicitly warns someone may later "fix" SCIM by retrofitting the wrapper and break the wire format (its §Questions/Gaps). Openhands' violations are *accidental coupling*: `ConversationView` re-exported from a domain barrel drags router state into library consumers (`src/components/conversation/index.ts:1`). Different failure shapes, same root cause: exceptions to the boundary lack their own explicit contract.

## Tradeoffs

**Centralized wrapper vs. distributed convention.** Benefit of the wrapper (both sources): policy changes land in one or two files; per-route behaviour stays declarative. Cost: bypasses are tempting for unusual formats, and each bypass erodes the guarantee (langfuse's four bypassing families). Best-fit: surfaces with homogeneous formats. Failure mode: special-case creep until the wrapper fits nothing cleanly. Alternative seen: openhands' access-rule tests achieve partial centralization *without* a runtime wrapper — enforcement moves from call-time to build-time.

**External DSL codegen (Fern) vs. package-metadata-as-contract.** Benefit (langfuse): one source generates OpenAPI, docs, and deprecation sync; client SDKs can be generated from the same truth (`fern/apis/client/definition/score.yml:38-40` ships inline examples for SDK maintainers). Cost: regeneration is opt-in (`pnpm run openapi:export`) and CI does not appear to enforce spec/code sync beyond targeted drift tests (langfuse report §Tradeoffs). Benefit of the metadata approach (openhands): no external toolchain; tests run anywhere. Cost: the "spec" is thin — no request/response documentation for consumers, contributing to the missing embedder story. Best-fit context: codegen when many external SDKs consume you; metadata-plus-tests when consumers compile against your build.

**URL version families vs. semver + subpaths.** Benefit (langfuse): old and new endpoints run simultaneously; migrations are caller-paced with in-band guidance (P5). Cost: file proliferation across parallel trees and a discoverability gap — six route families exist without a single generated index table (langfuse report §Questions/Gaps). Benefit (openhands): one canonical surface per capability; smaller cognitive load. Cost: breaking changes require either major-version churn or permanent backward-compat scaffolding; peer-dependency pins force consumer upgrades (`package.json:249-253`).

**Dev-only runtime validation vs. build-time assertions.** Langfuse runs `responseSchema.safeParse` only in development — catching handler drift cheaply but leaving production regressions to end-to-end tests that need a running server (`createAuthedProjectAPIRoute.ts:466-471`; acknowledged cost in its report §Tradeoffs). Openhands asserts the published artefact statically in CI — catching surface drift before publish but verifying nothing about runtime behaviour. These are complementary, not competing; a mature surface likely wants both.

**Social enforcement (contributor contracts) vs. automated enforcement.** Both repos lean on AGENTS.md for what tests can't reach — langfuse mandates wrapper usage and Fern updates (`web/AGENTS.md:127-128`), openhands documents API access rules. The observed cost of social enforcement is identical in both: it decays exactly where automation is absent (langfuse's undocumented intentional bypasses; openhands' implicit internal-only zones where stores/routes/services aren't re-exported but remain type-reachable). Automated what you can; document the remainder as named exceptions, not silence.

**Opt-out defaults on user-affecting behaviour.** Openhands' telemetry defaults to enabled — hosts must pass `analytics={false}` to disable PostHog, and the install event fires before consent (`src/components/providers/agent-server-ui-providers.tsx:33-35`, `src/hooks/use-telemetry.ts:77-83`). Benefit: better default data for the vendor. Cost: trust and compliance burden shifts to every embedder. Langfuse shows the contrast in kind rather than degree: its public surface treats rate limits, auth scopes, and deprecation notices as things the *caller* opts into, not out of. For public APIs, defaults are policy.

## Decision Guide

Rules of thumb distilled from the two evidence-bearing sources, ordered by decision point:

1. **HTTP service with external integrators?** Adopt Model A: one authenticated-route factory, strict request/response schemas at the boundary, contract DSL generating your spec, endpoint-named tests, and body-stamped deprecations with replacement pointers (all evidenced in langfuse). Reserve raw handlers for wire formats that genuinely cannot fit (SCIM/OTLP analogues), and mark them as named exceptions in contributor docs.
2. **Embeddable library or plugin surface?** Adopt Model B: an explicit export map over curated barrels, a single provider/facade entry point for hosts, CI tests asserting the published shape including removal regressions, published customization constants, and decoupled abstractions for anything app-specific (routing, storage) so consumers don't inherit your stack choices (all evidenced in openhands).
3. **Choosing a versioning strategy:** network APIs whose clients outlive your deploys → URL families with in-band migration guidance (P5). In-process libraries → semver + subpaths + narrow peer deps, and consider whether each peer dependency is truly unavoidable (openhands flags its React Router pin as a candidate for removal).
4. **Feature still moving but needs users now?** Give it a labelled namespace with its own machine-readable contract (P4) — but write the graduation criteria down at creation time, or the namespace becomes permanent (gap observed in langfuse).
5. **Deciding enforcement mechanisms:** automate whatever guards the *published artefact* (export-map shape, symbol resolution, spec/date consistency — P2/P3); reserve prose contracts for judgement-call rules; and treat any convention violated more than twice as a signal to automate it or redesign around it.
6. **Multiple audiences?** Partition deliberately (P6) and give each audience its own entry-point inventory — then verify each inventory has runnable examples, because the audiences do not share documentation (asymmetry observed in both sources).

## Practical Tips

**Patterns to copy:**

- Wrap every public handler in one factory and express per-route variation as declarative flags, not forked middleware stacks (langfuse, `createAuthedProjectAPIRoute.ts:307-492`).
- Assert the published surface in CI — including that deleted exports stay deleted (`__tests__/library-entrypoints.test.ts:44-48`). This is the cheapest high-value test identified in the entire study.
- Stamp structured migration info onto the objects callers already receive (`_deprecation` with `replacement`/`docsUrl`/`sunsetAt`, `deprecations.ts:99-114`) rather than relying on headers or release notes.
- Map every deprecated or rate-limited endpoint to its replacement programmatically so 429/resource-error responses teach the migration (`rateLimitUpgradePaths.ts:10-47`, `withMiddlewares.ts:47-60`).
- Export the constants your embedders need to integrate (scope selectors, theme variables, i18n namespaces — `AGENT_SERVER_UI_SCOPE_SELECTOR`, `OPENHANDS_I18N_NAMESPACE` at `src/i18n/index.ts:13`) so they never scrape source.
- Validate responses against schemas in dev mode to catch drift at near-zero production cost (`createAuthedProjectAPIRoute.ts:466-471`).
- Provide one options assembler per client-construction pattern so credentials/config can't be assembled ad hoc (`getAgentServerClientOptions()`/`getAgentServerHttpClientOptions()`, `src/api/agent-server-client-options.ts:52-79`).

**Patterns to avoid or delay until needed:**

- Don't create parallel version trees before you have a route-manifest/discoverability story — langfuse's six coexisting route families are its largest discoverability debt (report §Questions/Gaps).
- Don't ship a second error contract (default vs. unstable) until the first demonstrably fails your evolving features; two contracts double client-side handling logic.
- Don't gate deprecation behaviour on deployment-mode flags that silently change endpoint semantics per install (`rejectInEventsOnlyMode` returning 404 only in v4 events-only deployments, `createAuthedProjectAPIRoute.ts:82-88, 324-338`) without surfacing that in the spec.
- Don't commit generated code outside your generation pipeline — langfuse's hand-managed OTLP protobuf file (`web/src/pages/api/public/otel/otlp-proto/generated/root.ts`, README warning at `:7-8`) has an orphaned lifecycle no script regenerates.
- Don't default user-affecting integrations (analytics) to on for embedders; make consent explicit (openhands counter-example above).

## Anti-Patterns / Caution Signs

Signals that a public API surface is becoming brittle or over-coupled, each observed in the materialized sources:

- **Undocumented wrapper bypasses.** Endpoints skipping the standard auth/validation/error path with no marker explaining why (SCIM, OTel, ingestion in langfuse, `scim/Users/index.ts:1-313`). Caution sign for the future: contributors "fixing" them into conformance and breaking wire formats.
- **`z.any()` on important ingress.** Losing boundary validation on a primary ingestion path (`otel/v1/traces/index.ts:29-30`) — the schema layer stops being the safety net exactly where payloads are least trusted.
- **Library barrels re-exporting app-internal constructs.** Route components coupled to a specific router leaking through public subpaths (`ConversationView` from `routes/conversation.tsx`, `src/components/conversation/index.ts:1`).
- **Zero stability markers on exports.** No `@stable`/`@beta`/`@deprecated` tags anywhere in openhands' public barrels (report §Questions/Gaps) — consumers cannot calibrate risk.
- **Missing surface inventory.** No single machine-readable manifest of route → version → auth → deprecation status in langfuse; the newest agent-facing endpoint (public MCP) is invisible to OpenAPI entirely, documented only by a test (`web/src/pages/api/public/mcp/index.ts`, `mcp-public-api-tools.servertest.ts`).
- **Ambiguous deprecation semantics.** Sunset dates tied to product versions rather than API versions (`V3_SUNSET_DATE`, `deprecations.ts:11-16`) — recurring integrator confusion reported as such.
- **Audience documentation gaps.** Operator docs rich, embedder docs absent (openhands): a host developer must read component source to discover the provider entry point.
- **Divergent launchers behind one command name.** Dev-mode and published-binary behaviours sharing an entry but differing subtly (`bin/agent-canvas.mjs:151-159`) — operator expectations set by `--help` may not match runtime.
