## Executive Summary

Across seven agent frameworks, three distinct DI patterns emerge for handing tools their runtime context: (1) **opt-in typed context object** (agent-framework, langgraph, openai-agents-sdk, pydantic-ai), (2) **field-as-DI / bag-of-managers** (crewai, letta), and (3) **injector framework + request-state** (openhands). The first pattern dominates on the tool side and is consistently paired with annotation-driven discovery and unit testability without an app boot. The second is closer to service-layer DI and trades per-call context for explicit constructor wiring. The third is server-scoped and treats the agent as the boundary, not the tool.

The single most important convergence: **vanilla tools are hermetic by default and opt into context via parameter typing or Pydantic fields**. This is true even in the frameworks that rank lowest (crewai) — the difference is that crewai offers no opt-in for runtime metadata, so opting in requires constructing the tool with a field already populated by an upstream actor.

Five of seven frameworks rate 7-9 because their tool context is a typed, mockable object with at least one of explicit testability, sealed secrets at rest, or permission state. The two outliers rate 5-6 because context is hoarded by an orchestrator (crewai) or split across six constructor parameters (letta). No framework provides a first-class cancellation primitive for tools; only langgraph approximates it with a cooperative `RunControl`. No framework provides per-tool permission ACLs; approval gating is opt-in per tool or per middleware.

## Core Thesis

**The boundary between a tool and its runtime context has converged on typed, opt-in injection, but the *granularity* and *what is on the other side of the boundary* still varies widely.** A library author writing tools today can assume: (a) the framework inspects the tool's signature and chooses what to inject, (b) anything that varies per-call flows through a typed object the tool reads, and (c) tests can build that typed object by hand. What is *not* guaranteed: cancellation, scoped logger, scoped secrets store, or per-tool ACLs.

The most reusable patterns across the seven sources are: **annotation-driven context injection** (agent-framework, langgraph, openai-agents-sdk, pydantic-ai), **system-injected values winning over LLM-supplied values** (agent-framework, langgraph), **per-call isolation of the context object** (langgraph, openai-agents-sdk fork, pydantic-ai replace), and **opt-in approval / permission gating on the context** (agent-framework `approval_mode`, openai-agents-sdk `_approvals`, pydantic-ai `requires_approval`).

## Approach Models

### Group A: Typed-context-object DI (opt-in via annotation)

Four of the seven sources converge on this model. The tool declares its first parameter as a typed context class; the framework detects it during schema construction and injects a per-call instance. Discovery is annotation-driven and cached, so tools that do not declare the parameter run with no overhead.

- **agent-framework** — `FunctionInvocationContext` (`python/packages/core/agent_framework/_middleware.py:204-285`). Discovery via `FunctionTool._discover_injected_parameters` (`python/packages/core/agent_framework/_tools.py:411-436`). Typed or untyped-`ctx` opt-in; multiple typed contexts raise at construction (`_tools.py:428-430`).
- **langgraph** — `Runtime[ContextT]` for nodes (`libs/langgraph/langgraph/runtime.py:124-258`), `ToolRuntime[ContextT, StateT]` for tools (`libs/prebuilt/langgraph/prebuilt/tool_node.py:1662-1750`). Three injection annotations: `InjectedState`, `InjectedStore`, `ToolRuntime` (`tool_node.py:1753-1901`). Single-pass analysis cached in `ToolNode._injected_args`.
- **openai-agents-sdk** — `RunContextWrapper[TContext]` (`src/agents/run_context.py:43-63`) base + `ToolContext` subclass (`src/agents/tool_context.py:36`). Discovery via `function_schema` annotation check (`src/agents/function_schema.py:289-314`); runtime chooses shape via `_get_function_tool_invoke_context` (`src/agents/tool.py:1772-1803`).
- **pydantic-ai** — `RunContext[AgentDepsT]` (`pydantic_ai_slim/pydantic_ai/_run_context.py:36-127`). Discovery via `FunctionSchema.function_schema` inspects first parameter (`pydantic_ai_slim/pydantic_ai/_function_schema.py:149-172`).

What flows through the context:
- **Session/state** (agent-framework `session`, langgraph `state`, openai-agents-sdk `context`, pydantic-ai `deps`).
- **Identity/user** (openai-agents-sdk `context`, langgraph `server_info.user`, agent-framework indirect).
- **Tool-call identity** (openai-agents-sdk `tool_call_id`/`tool_name`, pydantic-ai `tool_call_id`/`tool_name`/`tool_call_metadata`, langgraph `tool_call_id`, agent-framework `metadata["call_id"]`).
- **Approval/permission state** (agent-framework `approval_mode` + harness `ToolApprovalRule`, openai-agents-sdk `_approvals` dict, pydantic-ai `requires_approval`).
- **Config/usage** (openai-agents-sdk `usage`/`turn_input`, langgraph `config`/`execution_info`/`server_info`, pydantic-ai `usage`/`retries`/`run_id`).

### Group B: Field-as-DI / bag-of-managers (constructor + per-call kwargs)

- **crewai** — Collaborators are Pydantic fields on `BaseTool` subclasses (`lib/crewai/src/crewai/tools/base_tool.py:103-191`); runtime context is hoarded on `ToolUsage` (`lib/crewai/src/crewai/tools/tool_usage.py:89-112`) and never reaches `_run`. Tools opt in by *adding a field* at construction; the orchestrator is the only thing that sees the per-call metadata.
- **letta** — `ToolExecutor` ABC takes 5 service managers + actor (`letta/services/tool_executor/tool_executor_base.py:16-46`); `ToolExecutionManager` adds `agent_state` + `sandbox_env_vars` per call (`letta/services/tool_executor/tool_execution_manager.py:68-92`). Sandbox tools opt in via AST parsing of the function signature (`letta/services/tool_sandbox/base.py:74-95`).

This pattern is more verbose (six parameters repeated across executors) but more explicit at construction time. The cost: per-call metadata is hoarded in an orchestrator and dropped at the tool boundary.

### Group C: Injector framework + per-request state

- **openhands** — `Injector[T]` ABC (`openhands/app_server/services/injector.py:12-34`) produces `AsyncContextManager[T]` for `async with` and FastAPI `Depends` for routes. `InjectorState: TypeAlias = State` is the per-FastAPI-request state bag (`openhands/app_server/services/injector.py:9`). Tool runtime context (`AgentContext`, `LocalWorkspace`) is composed at agent-build time (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:1630-1640`); tools themselves are imported from external `openhands-tools` and are out of scope.

This model is server-scoped and treats the request as the boundary. It excels at long-lived services (httpx, DB session) and request-scoped identity (`UserContext`), but defers the "how does a tool see context" question to the external package.

## Pattern Catalog

### 1. Annotation-driven injection with cached analysis

**Problem.** Tools need different context per call, but declaring a single context parameter is verbose, and inspecting signatures on every call is expensive.

**What it solves.** A tool authors the signature once; the framework inspects it once (at construction) and caches the injection map. Tools that don't need context run at zero overhead.

**Sources.** agent-framework (`_tools.py:411-436` + `FunctionTool._discover_injected_parameters`); langgraph (`ToolNode._injected_args` at `libs/prebuilt/langgraph/prebuilt/tool_node.py:773-786`, `_get_all_injected_args` at `:1967-2029`); openai-agents-sdk (`function_schema.py:289-314`); pydantic-ai (`_function_schema.py:149-172`).

**Why it works.** Python's `inspect.signature` + `typing.get_type_hints(..., include_extras=True)` are stable, the surface area is small (one parameter), and the result is type-checkable. PEP 563 stringified annotations resolve correctly (`agent-framework tests/core/test_tools_future_annotations.py`).

**When to copy.** For any framework that wants typed, opt-in, mockable tool context. It's the dominant pattern and the lowest-friction one for tool authors.

**When it is overkill.** When the tool surface is small and the context surface is uniform (no per-tool opt-out possible), the cost of building a schema and inspecting it is more than the cost of just passing the context unconditionally. Letta's sandbox tools use AST parsing for this reason.

**What evidence supports it.** Four of seven frameworks converge on it, all four are rated 8-9. The one framework that doesn't (crewai) is the lowest-rated.

### 2. System-injected values win over LLM-supplied values

**Problem.** The LLM can craft tool-call arguments with names that collide with injected parameters (e.g. `auth`). If LLM-supplied values overwrite system-injected values, the trust boundary breaks.

**What it solves.** The framework guarantees that values the system injected (state, store, runtime context) cannot be overridden by model output.

**Sources.** agent-framework (`_tools.py:633-640` rejects stray kwargs at invoke time; MCP denylist at `_mcp.py:88-98`); langgraph (`tool_node.py:1422-1429` strips LLM-supplied values for injected keys, then re-adds system values; documented in `.github/THREAT_MODEL.md:207`).

**Why it works.** Two layers: (a) the schema-level filter that hides injected parameters from the model-visible schema, and (b) the runtime merge that strips any LLM-supplied collisions before applying system values. agent-framework also has a denylist of framework-internal kwarg names that an MCP server might echo back.

**When to copy.** Always. This is the single most important security property for tool injection.

**When it is risky.** Only if the merge order is wrong. agent-framework's `test_tool_invoke_rejects_unexpected_runtime_kwargs` (`tests/core/test_tools.py:614-629`) and langgraph's `test_read_secret` (`libs/prebuilt/tests/test_tool_node.py:2208-2238`) pin the property.

### 3. Per-call isolation of the context object

**Problem.** Parallel tool calls share the same context; mutations collide. Also: a tool that needs to mutate `tool_input` should not leak that mutation back to other tools.

**What it solves.** Each tool invocation gets its own context copy, with shared read-only data and isolated mutable slots.

**Sources.** langgraph (`tool_node.py:802-816` constructs a fresh `ToolRuntime` per call; parallel calls get independent copies); openai-agents-sdk (`RunContextWrapper._fork_with_tool_input` at `src/agents/run_context.py:470-485` shares `_approvals`/`usage`/`turn_input` but isolates `tool_input`); pydantic-ai (`RunContext` is replaced per step in `_agent_graph.py:1260-1288`); agent-framework (`FunctionInvocationContext` is constructed per call in `_tools.py:1537-1543`).

**Why it works.** Either clone the dataclass (langgraph `Runtime.patch_execution_info`, pydantic-ai `dataclasses.replace`) or fork with shared+isolated fields (openai-agents-sdk).

**When to copy.** Any time tool calls can run concurrently or be retried. Both langgraph and pydantic-ai rely on this for their retry and deferred-execution machinery.

**When it is overkill.** For sequential, single-threaded tool loops, sharing a context is fine. The cost of cloning is rarely significant but adds a class invariant (`replace(...)` shared-set hazards in pydantic-ai at `_run_context.py:1423-1427`).

### 4. INJECTABLE / serialize-side DI contract

**Problem.** Tools are constructed with callables (the tool body), context objects, sessions, etc. None of these should be persisted to disk or sent over the wire as part of the tool definition.

**What it solves.** A class-level set declares "these fields are runtime-only and must be supplied at construction, not serialized".

**Sources.** agent-framework (`SerializationMixin.INJECTABLE` at `python/packages/core/agent_framework/_serialization.py:268`, applied to `FunctionTool.func`, `AgentContext.agent`, `ChatContext.client`). crewai's `SerializableCallable` (`lib/crewai/src/crewai/types/callback.py:153-158`) is a related idea but opt-in per-type.

**Why it works.** The class declares the rule once; `to_dict`/`from_dict(..., dependencies=...)` enforces it. Tests (`test_serializable_mixin.py:33-167`) pin the behavior.

**When to copy.** Any framework that serializes tool definitions for transport or persistence. agent-framework's pattern is the cleanest: a class-level `set[str]` consumed by the base class.

**When it is risky.** When `INJECTABLE` changes the persisted shape silently, the diff is invisible to the user. agent-framework's tests catch it; without tests, a renamed field would silently drop the dependency.

### 5. Opt-in approval/permission gating on the context

**Problem.** Some tool calls need user approval (shell exec, file write); others do not (read file, search). A blanket "always ask" is too noisy; "never ask" is too dangerous.

**What it solves.** The tool declares whether it needs approval, or the framework provides an approval hook on the context object.

**Sources.** agent-framework (`approval_mode: Literal["always_require", "never_require"]` at `_tools.py:96`; harness `ToolApprovalMiddleware` at `_harness/_tool_approval.py`). openai-agents-sdk (`RunContextWrapper._approvals` dict at `src/agents/run_context.py:30-61`, public `approve_tool`/`reject_tool`/`is_tool_approved` API at `:355-445`). pydantic-ai (`Tool(..., requires_approval=True)` at `pydantic_ai_slim/pydantic_ai/tools.py:482, 576`; `ApprovalRequiredToolset` wrapper at `toolsets/approval_required.py:16-32`).

**Why it works.** Approval state travels with the context object; the dispatcher checks it before invoking. Per-tool opt-in lets the user choose which tools gate and which don't.

**When to copy.** When tools can have side effects beyond read-only. The openai-agents-sdk model is the most ergonomic — approval is a method on the wrapper, so a tool can read its own approval state without separate API calls.

**When it is overkill.** When the agent has no human in the loop or when every tool is read-only. Forcing approval gates adds API surface with no payoff.

### 6. AST-driven sandbox injection (signature-as-contract)

**Problem.** Tools run in subprocesses (sandbox); they need agent state, identity, etc., but cannot be passed Python objects directly.

**What it solves.** Parse the tool's source AST; only inject variables whose names appear in the function signature.

**Sources.** letta sandbox (`AsyncToolSandboxBase.generate_execution_script` at `letta/services/tool_sandbox/base.py:126-175`; injection flags at `:74-95`). Modal variant uses `co_varnames` inspection (`letta/services/tool_manager.py:163-167`).

**Why it works.** The user writes `def my_tool(agent_state, x)` and "just works" — `agent_state` is injected because the name appears in `co_varnames`; nothing else is. No annotation, no decorator, no context object.

**When to copy.** When tools run in subprocesses that cannot share memory with the orchestrator. The alternative (passing a serialized context object) is heavier.

**When it is risky.** When a rename silently disables injection (`agentState` vs `agent_state`). Implicit contracts are easy to break. Letta documents the AST flags but does not assert them at construction time.

### 7. Per-request state bag as a DI container

**Problem.** Web frameworks need per-request DI: each request has its own user, DB session, HTTP client. Singletons are wrong.

**What it solves.** Use the framework's per-request state object as the DI container; injectors store resolved dependencies on it for the duration of the request.

**Sources.** openhands (`Injector[T]` ABC at `openhands/app_server/services/injector.py:12-34`; `InjectorState: TypeAlias = State`). The FastAPI/Starlette `Request.state` is the container; `KEEP_OPEN` flags let background tasks opt out.

**Why it works.** The framework already provides per-request lifecycle; piggybacking on it avoids inventing a parallel container.

**When to copy.** When the agent is behind a web API and per-request identity matters. openhands is the only framework in this study that uses this pattern because it is the only one that is a long-running server.

**When it is overkill.** For library code that doesn't run behind a web server. agent-framework and langgraph deliberately don't use per-request state because they don't know if there *is* a request.

### 8. `ContextVar` override for nested test/runtime substitution

**Problem.** Deeply nested code needs to swap dependencies (test fixtures, override at runtime) without threading them through every signature.

**What it solves.** A per-agent `ContextVar` that holds override values; nested `with agent.override(...)` blocks stack correctly.

**Sources.** pydantic-ai (`_override_deps` at `pydantic_ai_slim/pydantic_ai/agent/__init__.py:544-554`; `Agent.override` at `:1780-1944`). openhands `as_admin(request)` (`openhands/app_server/user/specifiy_user_context.py:55-65`).

**Why it works.** `ContextVar` is the standard library mechanism for lexically scoped, async-safe overrides. The token-stack model means nested overrides unwind correctly.

**When to copy.** When you need a "test mode" or "admin mode" escape hatch that doesn't pollute every call site. pydantic-ai's tests rely on this (`tests/test_deps.py:80-93`).

**When it is risky.** ContextVar makes DI implicit; readers of the call chain who don't know about the override can't see what's actually injected.

### 10. Middleware-based tool-call interception

**Problem.** Cross-cutting concerns (logging, retries, audit, caching) need to wrap tool calls without modifying the tool itself.

**What it solves.** A wrapper callable (`wrap_tool_call` / `awrap_tool_call`) receives the `ToolCallRequest` and an `execute` callback; can retry, cache, short-circuit, or modify the call.

**Sources.** langgraph (`ToolCallWrapper` at `libs/prebuilt/langgraph/prebuilt/tool_node.py:202-277`, async variant at `:279-283`). crewai has global hooks (`hooks/tool_hooks.py:24-77`) but no per-tool wrapper. openai-agents-sdk has guardrails (`src/agents/tool_guardrails.py:120-145`) but they run before dispatch, not as wrappers.

**Why it works.** The wrapper pattern composes — multiple wrappers can stack. The `ToolCallRequest.override()` produces an immutable copy (`tool_node.py:151-199`).

**When to copy.** When you need cross-cutting behavior that should not require editing every tool. langgraph's `wrap_tool_call` is the canonical example; it's also the closest thing to a permission/audit hook in the OSS library.

**When it is risky.** When wrapper ordering matters but isn't documented. langgraph doesn't pin a default ordering.

## Key Differences

### Per-call context vs. constructor-bound context

agent-framework, langgraph, openai-agents-sdk, pydantic-ai all deliver **per-call context** through a typed parameter. crewai and letta deliver **constructor-bound context** through Pydantic fields (crewai) or a bag of services (letta). The distinction matters for testability:

- Per-call context is mockable in isolation: build the context, call the tool. agent-framework, langgraph, and openai-agents-sdk all have tests that do exactly this.
- Constructor-bound context requires mocking collaborators or building real ones: letta's tests use `MagicMock()` for every manager (`tests/integration_test_builtin_tools.py:198-205`), crewai's tests do the same for `tools_handler`/`task`/`function_calling_llm`/`agent`/`action` (`tests/tools/test_tool_usage.py:120-126`).

### Server-scoped vs. library-scoped DI

openhands is the only server-scoped model; the other six are library-scoped. openhands's `Injector[T]` rides on FastAPI `Request.state`, which doesn't exist in library code. This makes openhands excellent for service-layer testing (`tests/unit/app_server/test_live_status_app_conversation_service.py:159-199` constructs the service with 7 mocks) but it means the *tool* context is opaque — tools live in `openhands-tools` and their `ToolContext` shape is not visible in this repo.

### Single context type vs. split context types

langgraph splits context into `Runtime` (nodes) and `ToolRuntime` (tools). The other typed-context frameworks use a single class. The split costs conceptual overhead (the overlap is documented at `libs/langgraph/langgraph/runtime.py:138-142` but tools still can't heartbeat for idle-timeout because `heartbeat` isn't in `ToolRuntime`) but buys tighter scoping per surface.

### Annotation-driven vs. Pydantic-field-driven vs. AST-driven

Three ways to declare "this tool wants context":
1. **Annotation** (agent-framework, langgraph, openai-agents-sdk, pydantic-ai): type the parameter, framework inspects once.
2. **Pydantic field** (crewai): declare `Field(...)` on the tool subclass, framework constructs the tool with the value.
3. **AST** (letta sandbox): parse the source, inject anything whose name appears in `co_varnames`.

Annotation is the most type-safe; AST is the most implicit. Pydantic field is the most "Pythonic" but forces every collaborator to live on the tool class.

### Approval/permission surfaces

- agent-framework: per-tool `approval_mode` + harness `ToolApprovalMiddleware`/`ToolApprovalRule`. Approval is opt-in per tool; standing rules ("don't ask again") live in a session-backed store.
- openai-agents-sdk: `RunContextWrapper._approvals` dict. Approval is a method on the wrapper, so the tool can read its own state. Per-call vs. global keys resolved through `_resolve_approval_keys` (`src/agents/_tool_identity.py:362-410`).
- pydantic-ai: `requires_approval=True` per tool + `ApprovalRequiredToolset` wrapper that gates `call_tool`. Approval state is `ctx.tool_call_approved`.
- langgraph: no first-class primitive; the only hook is `wrap_tool_call` middleware (deprecated `ValidationNode` only validates schema). Permission data is `server_info.user` when the LangGraph Server is in front.
- letta: actor-based (`User.organization_id`) — every manager call is filtered by actor; `ToolRulesSolver` runs at the agent loop, not inside the executor.
- crewai: `before_tool_call`/`after_tool_call` hooks can block; `SecurityConfig.fingerprint` exists but is built and dropped at the tool boundary.
- openhands: `ConfirmationPolicyBase` and `SecurityAnalyzerBase` configured once at agent build time; no per-tool ACL.

### Cancellation

- None of the seven sources provide a first-class cancellation token injected into the tool.
- langgraph's `RunControl.request_drain(reason)` is the closest — it's a cooperative signal, not a token (`libs/langgraph/langgraph/runtime.py:79-104`).
- agent-framework, pydantic-ai, openai-agents-sdk rely on `asyncio.CancelledError` propagation.
- letta uses polling (`_check_run_cancellation` against `RunManager` at `letta/agents/letta_agent.py:155-171`).
- openhands uses `asyncio.Task.cancel()` at task boundaries.
- crewai has no documented cancellation path; `asyncio.CancelledError` only appears in `mcp_tool_wrapper.py:193` after a timeout.

## Tradeoffs

### Per-call typed context vs. constructor-bag DI

- **Per-call typed context** (agent-framework, langgraph, openai-agents-sdk, pydantic-ai)
  - **Benefit**: small tool signature; mockable in isolation; schema-level filter hides injected params from the LLM.
  - **Cost**: every new dependency requires either (a) adding a field to the context class or (b) smuggling it through `kwargs`/`metadata`.
  - **Best-fit**: libraries that want tools to be portable across agent implementations.
  - **Failure mode**: a wide context object whose field availability differs by hook (pydantic-ai `model_settings is None` in tool hooks per `_run_context.py:98-105`).
  - **Alternative**: Pydantic field injection (crewai), bag of managers (letta).

- **Constructor-bag DI** (crewai, letta)
  - **Benefit**: explicit at construction; type-checkable; IDE-friendly.
  - **Cost**: tool signature bloats with collaborators; tests require `MagicMock` for every field.
  - **Best-fit**: server applications with stable collaborators (letta's managers are injected into a long-lived executor).
  - **Failure mode**: dropped parameters (`ToolExecutionManager.job_manager` is accepted but never stored, `letta/services/tool_executor/tool_execution_manager.py:71-92`).
  - **Alternative**: typed context object; per-request injector (openhands).

### Annotation-driven vs. AST-driven injection

- **Annotation-driven** (agent-framework, langgraph, openai-agents-sdk, pydantic-ai)
  - **Benefit**: explicit, type-checkable, easy to validate.
  - **Cost**: requires the user to import and type the context class.
  - **Best-fit**: any framework where tool authors are also library users.
  - **Failure mode**: a tool with PEP 563 stringified annotations requires `typing.get_type_hints(..., include_extras=True)` to resolve correctly (covered by `agent-framework tests/core/test_tools_future_annotations.py`).

- **AST-driven** (letta sandbox)
  - **Benefit**: zero-effort opt-in; works for user-authored source code in subprocesses.
  - **Cost**: implicit contract; rename silently disables injection.
  - **Best-fit**: sandboxed execution where context flows through `co_varnames`.
  - **Failure mode**: `agent_state` vs `agentState` (camelCase) silently breaks injection.

### MCP arg safety: denylist vs. allowlist vs. type system

- **agent-framework** uses both: an allowlist of declared schema `properties` plus a denylist of framework-internal kwarg names (`_MCP_FRAMEWORK_DENYLIST` at `_mcp.py:88-98`).
- **crewai** does not have a per-call context object; MCP arg safety is transport-level only (`MCPServerHTTP.headers`, `MCPServerStdio.env`).
- **langgraph** uses the schema itself — injected parameters are stripped from the LLM-visible schema via `InjectedToolArg`.
- **letta** has no env-var denylist in sandbox; `_gather_env_vars` puts every agent env var into the subprocess (`base.py:476-517`).

The denylist approach is fragile (new framework-internal kwarg names must be added by hand) but cheap; the type-system approach (langgraph) is more durable but requires the framework to own the schema.

### Secrets in tool context

- **Sealed at rest + framework-managed**: letta (`Secret` Pydantic model + `CryptoUtils` at `schemas/secret.py:13-69`); openhands (`SecretSource` discriminated union — `StaticSecret` vs `LookupSecret`).
- **Caller-managed**: pydantic-ai (`deps` is a user-defined dataclass); openai-agents-sdk (`context` is whatever the user passes in; `docs/context.md:43` warns explicitly).
- **Telemetry-gated**: agent-framework (`OBSERVABILITY_SETTINGS.SENSITIVE_DATA_ENABLED` gates span attributes; default off).
- **Not addressed**: langgraph (user-defined context dataclass, no framework-managed secret store); crewai (secrets flow via `os.environ` and module-level globals, no tool-side visibility).

The frameworks that treat secrets as a first-class concern (letta, openhands) also have the most rigorous permission model. The frameworks that treat secrets as "whatever you put in your context" (pydantic-ai, openai-agents-sdk) document the responsibility but don't enforce.

### Per-tool logger

- No framework injects a logger into the tool.
- agent-framework uses module-level `logger = logging.getLogger("agent_framework")` (`_tools.py:87`).
- letta uses module-level `get_logger(__name__)` per executor (`builtin_tool_executor.py:15`); request-scoped correlation comes from `JSONFormatter` reading OTel span context (`log.py:74-86`), not from injection.
- openhands uses module-level `_logger` (`live_status_app_conversation_service.py:142`); request id is not auto-bound.
- pydantic-ai relies on `RunContext.tracer` for OpenTelemetry; no logger injection.

The closest thing to "request-scoped logger" is `pydantic-ai`'s `RunContext.tracer` (OpenTelemetry tracer, not Python `logging.Logger`).

## Decision Guide

### If you want a single typed context per call

Use **agent-framework's `FunctionInvocationContext`** model or **pydantic-ai's `RunContext[AgentDepsT]`** model. Both are:
- Annotation-driven (typed first parameter).
- Per-call isolated (each tool invocation gets its own instance).
- Testable in isolation (build the context, call the tool).

Pick **agent-framework** if you want explicit schema-level rejection of unexpected kwargs and INJECTABLE serialization. Pick **pydantic-ai** if you want user-defined deps (the user owns the shape; the framework only owns the type parameter).

### If you want per-tool opt-in approval

Use **openai-agents-sdk's `RunContextWrapper.approve_tool`/`reject_tool`** model. Approval is a method on the wrapper, so:
- Tools can read their own approval state.
- Handoffs and nested calls preserve approval state (it moves with the wrapper).
- Per-call and global keys resolve through `_resolve_approval_keys` (`_tool_identity.py:362-410`).

Alternative: agent-framework's `approval_mode` (binary `always_require`/`never_require`) is simpler but less expressive; pydantic-ai's `requires_approval=True` per tool is also simpler.

### If you want hardened injection security

Use **langgraph's documented threat model** (`.github/THREAT_MODEL.md:207-303`). It explicitly addresses:
- Strip LLM-supplied values for injected keys (`tool_node.py:1422-1429`).
- System-injected values overwrite collisions.
- Schema-level filter hides injected params from the LLM-visible schema.
- Validation errors are filtered to LLM-controlled args only.

agent-framework has the same property but documents it less rigorously; the behavior is pinned in tests (`tests/core/test_tools.py:614-629`).

### If you want server-scoped per-request DI

Use **openhands's `Injector[T]`** pattern. It composes with FastAPI `Depends` and `async with` from one ABC, with per-request caching on `Request.state` and `KEEP_OPEN` flags for background tasks.

This is only useful if you actually have a server. For library code, prefer typed context objects.

### If you want subprocess/sandbox isolation

Use **letta's AST-driven injection**. The user writes `def my_tool(agent_state, x)`; the framework injects `agent_state` because the name is in `co_varnames`. For Modal/e2b variants, use the namespace-dict pattern (`tool_manager.py:129-141`).

Watch out for: implicit contracts (a rename silently disables injection) and the lack of an env-var denylist (`base.py:487-513` puts every agent env var into the subprocess).

### If you want to keep tool signature hermetic

Use **pydantic-ai's plain tool** (`ToolFuncPlain: Callable[ToolParams, Any]`). The framework auto-detects `RunContext[...]` in the first parameter; if absent, no context is injected. The tool runs as if it were a normal Python function.

This is the simplest opt-in. The cost: a tool that wants context must import `RunContext` and type its first parameter.

## Practical Tips

### Patterns to copy

1. **Annotation-driven injection with cached analysis** — universal across the four highest-rated frameworks.
2. **System-injected values win over LLM-supplied** — non-negotiable security property.
3. **INJECTABLE serialization set** — clean way to mark runtime-only fields (`agent-framework _serialization.py:268`).
4. **Per-call isolation** — clone or fork the context for parallel calls (langgraph, pydantic-ai, openai-agents-sdk fork).
5. **Approval as a method on the context** — openai-agents-sdk's `RunContextWrapper.approve_tool` model is the most ergonomic.
6. **`agent.override(deps=...)` ContextVar pattern** — for test fixtures and runtime substitution (pydantic-ai).
7. **Threat-model documentation** — langgraph's `.github/THREAT_MODEL.md` is the most thorough; pin the property in tests.
8. **`ValidationNode`-style schema validation** — deprecated but the concept is right: validate LLM-supplied args against a schema before dispatch (langgraph).
9. **`SecretSource` discriminated union** — `StaticSecret` for OSS, `LookupSecret` for SaaS (openhands) so the wire format changes without changing the call site.

### Patterns to avoid or delay

1. **Constructor-bag DI for per-call context** — verbose and not extensible to new deps without editing every subclass (letta).
2. **Module-level logger** — no request correlation; `JSONFormatter` reading OTel span context is a workaround, not a fix.
3. **Dead DI fields** — `_logger: Logger = PrivateAttr(default_factory=Logger)` declared on `CrewStructuredTool` and never used (`structured_tool.py:141`); `config=` parameter accepted by `CrewStructuredTool.invoke` and ignored (`structured_tool.py:296-364`).
4. **Dropped parameters at the boundary** — `ToolExecutionManager.job_manager` accepted but never stored (`tool_execution_manager.py:71-92`).
5. **Stringly-typed approval keys** — openai-agents-sdk's `_approvals` dict uses string keys derived from tool name/namespace; a malformed `tool_name` can collide.
6. **Split context types with overlapping fields** — langgraph's `Runtime`/`ToolRuntime` split has caused deprecation churn (`chat_agent_executor.py:53-116`).
7. **Wide dataclass with `None` defaults in tool hooks** — pydantic-ai's `RunContext` is dense; field availability differs by hook.

### Decision rules

- **Tool needs runtime metadata (session, store, identity, current state)** → typed context object, annotation-driven.
- **Tool needs stable collaborators (HTTP client, DB, memory)** → constructor injection; if the tool is long-lived, use bag-of-managers (letta).
- **Tool needs subprocess/sandbox isolation** → AST-driven injection (letta); or namespace dict + `exec` (Modal).
- **Tool needs approval gating** → method-on-context (openai-agents-sdk) or per-tool `requires_approval` (pydantic-ai).
- **Tool needs cancellation** → `asyncio.CancelledError` propagation; for cooperative drain, `RunControl` (langgraph).
- **Tool needs to be unit-tested without an agent** → typed context, constructible by hand (agent-framework, langgraph, openai-agents-sdk, pydantic-ai all have this property).

## Anti-Patterns / Caution Signs

1. **Multiple typed context parameters** — `@tool` should raise at construction if there are two `FunctionInvocationContext` parameters (`agent-framework _tools.py:428-430`). If your framework silently picks one, the user has no way to detect a bug.

2. **Implicit `ctx` + typed context** — both forms in the same signature is ambiguous; agent-framework raises (`test_tools.py:1077-1088`). Don't silently last-wins.

3. **`**kwargs` smuggling of runtime data** — agent-framework's `invoke()` rejects stray kwargs at `_tools.py:633-640`. If your framework accepts them, runtime data can leak into persisted state.

4. **MCP denylist maintenance burden** — agent-framework's `_MCP_FRAMEWORK_DENYLIST` (`_mcp.py:88-98`) is a stringly-typed safety net. New framework-internal kwarg names must be added by hand. There is no automated test for it. If you use this pattern, add a test that fails when a new internal kwarg is added without updating the denylist.

5. **Sandbox env-var leakage** — letta's `_gather_env_vars` (`base.py:487-513`) puts every agent env var into the subprocess. There is no denylist. A compromised tool can read any env var. Compare against agent-framework's MCP denylist.

6. **Dropped parameters at the boundary** — `ToolExecutionManager.job_manager` accepted but never stored (`tool_execution_manager.py:71-92`). Constructor signature lies about what's actually wired. Always assert at the boundary.

7. **Dead DI fields** — `_logger` on `CrewStructuredTool` (`structured_tool.py:141`), `config` on `CrewStructuredTool.invoke` (`structured_tool.py:296-364`). Either wire them or remove them. Dead DI is worse than no DI because it lies about the contract.

8. **MCP `header_provider` only on HTTP transport** — agent-framework's `MCPStreamableHTTPTool` (`_mcp.py:2707-2731`) propagates `_mcp_call_headers` ContextVar; stdio and websocket transports don't. Document the limitation; don't claim symmetry that doesn't exist.

9. **Telemetry gate is global** — `OBSERVABILITY_SETTINGS.SENSITIVE_DATA_ENABLED` is process-wide (`agent-framework observability.py:1146-1165`). A tool that needs to log sensitive intermediate results can't opt out per-call. Add per-tool redaction if you need it.

10. **`Runtime.control` borrowed from parent, defaults to fresh `RunControl()`** — langgraph's `pregel/main.py:2887-2895` falls through to a new `RunControl()` if both are `None`. A long-lived parent without `RunControl` won't see drain requests.

11. **Wide dataclass with hook-dependent field availability** — pydantic-ai's `RunContext.model_settings` is `None` in tool hooks (`_run_context.py:98-105`). Readers must check docstrings to learn what's safe to touch. Slim down the context or document per-hook availability.

12. **MCP tools using a different context model** — openhands's MCP tools read identity from `get_http_request()` (`mcp_router.py:167-174`), not the typed `UserContext` used elsewhere. Two context models in the same system is a maintenance burden; pick one.

13. **Async `get_config()` on Python <3.11** — langgraph raises `RuntimeError` (`config.py:18-25`). Document the Python version requirement; don't silently degrade.

14. **Substring matching in user annotations** — naive annotation matching could mistake a custom wrapper named `MyRunContextWrapper` for the SDK class. openai-agents-sdk uses `get_origin(annotation) is RunContextWrapper/ToolContext` (`tool.py:1772-1803`) and pins it with tests (`tests/test_tool_context.py:299-371`). Don't use `name == "RunContextWrapper"`.

## Notable Absences

1. **No framework injects a per-request logger.** Even the highest-rated (agent-framework, 9/10) uses a module-level `logger`. The closest workaround is pydantic-ai's `RunContext.tracer` (OpenTelemetry tracer, not Python `Logger`) and letta's `JSONFormatter` reading OTel span context.

2. **No framework provides a first-class cancellation token for tools.** langgraph's `RunControl` is cooperative; agent-framework, pydantic-ai, openai-agents-sdk rely on `asyncio.CancelledError`; letta uses polling; openhands uses `asyncio.Task.cancel()`. There is no per-tool cancellation primitive in any of the seven sources.

3. **No framework provides per-tool ACLs.** Approval is opt-in per tool (agent-framework, pydantic-ai) or per method (openai-agents-sdk), but role-based or scope-based access control is absent in every source. The closest is letta's actor-based filtering (`actor.organization_id` flows through every manager call), which is organizational, not per-tool.

4. **No framework provides a framework-managed secret store.** Secrets are caller-managed (pydantic-ai, openai-agents-sdk, langgraph) or Pydantic-model-sealed at rest (letta, openhands `SecretSource`). Agent-framework has `SecretString` (a `str` subclass with masked repr) but not a store.

5. **No framework injects a metrics/tracing primitive directly into the tool body.** Tracing flows through decorators (`@trace_method` in letta) or through the OpenTelemetry tracer (pydantic-ai's `RunContext.tracer`). A tool that wants to record its own spans has to import the framework's tracer.

6. **No framework distinguishes between "this tool needs context" and "this tool's caller needs context"** in a single API. langgraph comes closest with `InjectedState(field)` (sub-state) vs `ToolRuntime` (full context), but the distinction is still binary.

7. **No framework has a published test pattern for the tool-injection contract itself.** The closest is langgraph's `test_tool_node.py:55-81` (mock runtime in config), which is a pattern, not a test harness.

8. **No framework enforces a max-context-size or serialization-redaction policy.** The only secret warning is documented (`openai-agents-sdk docs/context.md:43`, `docs/human_in_the_loop.md:200`) but unenforced.

9. **No framework threads a `permissions` field through the typed context.** langgraph's `server_info.user` is the only authorization data, and it's only populated when the LangGraph Server is in front.

## Per-Source Notes

### agent-framework

- **Approach**: opt-in `FunctionInvocationContext` per call, annotation-driven.
- **Where**: `python/packages/core/agent_framework/_middleware.py:204-370`, `_tools.py:411-436`, `_mcp.py:88-98`.
- **Mechanism**: `FunctionTool._discover_injected_parameters` inspects the signature; rejects multiple typed contexts; skips context param in schema generation; passes `kwargs` through context only.
- **Standout**: `SerializationMixin.INJECTABLE` pattern (`_serialization.py:268`); MCP denylist (`_mcp.py:88-98`); `FunctionInvocationContext.add_tools`/`remove_tools` for progressive tool exposure (`_middleware.py:287-370`); harness `ToolApprovalMiddleware` (`_harness/_tool_approval.py`).
- **Tradeoffs**: opt-in only — vanilla tools get nothing; no cancellation token; no logger injection; telemetry gate is global.
- **Gaps**: no `FunctionInvocationContext.cancellation`; module-level logger; MCP `header_provider` only on HTTP transport; .NET side relies on `AIFunctionFactory` and has different surface.

### crewai

- **Approach**: Pydantic-field injection on `BaseTool`; runtime metadata hoarded on `ToolUsage`.

- **Gaps**: no `ToolContext` accessible to tool bodies; `SecurityConfig.fingerprint` built and dropped at boundary; `Tool.from_langchain` deserialization is opt-in (`CREWAI_DESERIALIZE_CALLBACKS=1`).

### langgraph

- **Approach**: split typed context (`Runtime` for nodes, `ToolRuntime` for tools), annotation-driven.

### letta

- **Approach**: `ToolExecutor` ABC with bag-of-managers; AST-driven injection in sandbox.
- **Where**: `letta/services/tool_executor/tool_executor_base.py:16-46`, `tool_execution_manager.py:32-92`, `tool_sandbox/base.py:74-95`.

### openai-agents-sdk

- **Approach**: `RunContextWrapper[TContext]` (generic) + `ToolContext` (tool-call metadata); annotation-driven.
- **Where**: `src/agents/run_context.py:43-63`, `src/agents/tool_context.py:36`, `src/agents/tool.py:1772-1803`.

### openhands

- **Approach**: `Injector[T]` ABC with per-FastAPI-request state; tools external.
- **Where**: `openhands/app_server/services/injector.py:12-34`, `app_conversation/live_status_app_conversation_service.py:199-226, 1630-1664`.

- **Approach**: single typed `RunContext[AgentDepsT]` with user-defined deps; annotation-driven; `agent.override()` ContextVar.

## Open Questions

1. **Why does no framework inject a logger?** Five of seven use module-level `logger`; pydantic-ai uses OpenTelemetry tracer; letta uses `JSONFormatter` reading OTel span context. Is logger injection genuinely not needed, or is the pattern just not adopted?

2. **Why is there no first-class cancellation token?** `asyncio.CancelledError` propagation is the universal answer; langgraph's `RunControl` is the only cooperative signal. Is there a reason no framework adopts a structured cancellation primitive (similar to `asyncio.Task.cancel()` but tool-side)?

3. **Why is per-tool permission absent?** Approval gating exists; ACL does not. Is there a reason per-tool permission is consistently modeled as "approval needed yes/no" rather than "scope of access"?

4. **What does the openhands tool-side context look like?** The actual `BaseTool`/`ToolDefinition` shape lives in `openhands-tools` (external). Without inspecting that package, we cannot compare the consumer-side DI to the tool-side DI.

5. **Does `ToolExecutionManager.job_manager` get stored in any subclass?** letta's `tool_execution_manager.py:71-92` accepts `job_manager` but never assigns `self.job_manager = job_manager`. Is this intentional (forward-looking API) or a bug?

6. **Can `RunControl.drain_reason` be propagated into `ToolRuntime`?** langgraph's `Runtime.control` is not in `ToolRuntime` (`tool_node.py:1722-1730`). Would forwarding it break the split between node-runtime and tool-runtime?

7. **Does anyone use the `LookupSecret` JWT expiry hook?** openhands's `access_token_hard_timeout` defaults to 14 days (`live_status_app_conversation_service.py:2458-2464`). Is there a per-secret refresh hook or do long-lived agent-server processes need to re-fetch the JWT?

8. **What happens across `agent.override()` + `asyncio.create_task`?** pydantic-ai uses `ContextVar` for overrides (`agent/__init__.py:1780-1944`). Does the override propagate correctly into spawned tasks, or only into the synchronous call chain?

9. **Is `MCP FRAMEWORK_DENYLIST` tested for staleness?** agent-framework's `_mcp.py:88-98` enumerates eight names by hand. If a new framework-internal kwarg is added without updating the list, no test fails. Should there be an automated guard?

10. **What is the canonical "permissions for tools" pattern across the seven sources?** Approval (3 sources), actor filter (1 source), middleware wrapper (1 source), no enforcement (2 sources). Is the absence of a unified pattern a research gap, or a signal that one approach isn't dominant?
