## Executive Summary

Four of six sources (`agent-framework`, `langgraph`, `opa`, `temporal`) returned empty source trees, collapsing every dimension question to "no evidence found" and the rating to the 1/10 floor. The substantive findings are entirely concentrated in two sources:

- **langfuse** (4/10) — a multi-package monorepo whose CI pipeline fans out into ~10 jobs and gates release-image builds on an aggregator (`all-ci-passed`). Code-based evals run in CI against a Floci Lambda mock, but no eval pass-rate baseline, drift dashboard, or eval-quality regression gate exists. Golden-SQL snapshots catch query-shape regressions, and the only baseline concept in the codebase is a user-facing experiment diff UI.
- **openhands** (5/10) — a UI frontend whose CI is a multi-tier machine (unit + lint + build + mock-LLM E2E + docker E2E), with `test-and-build (ubuntu)` as the load-bearing release gate. Like langfuse, it has zero baseline comparison, zero drift tracking, and a deliberate policy of postponing mutation/coverage thresholds until "a stable baseline" exists.

The cross-source pattern is striking: both populated sources have **strong gating with weak historical observability**. Both block merges and tag-gated releases on deterministic checks; neither computes, stores, or compares eval pass-rates over time. Across the four empty sources, the rating does not reflect a design choice — it reflects missing materialization, and the study cannot answer the guiding question ("Can a code change that degrades quality be blocked before deployment?") for those sources.

## Core Thesis

For this dimension, the populated sources demonstrate a common shape: **test-pass/fail is a first-class CI signal; eval-quality is not**. Both langfuse and openhands converge on the same anti-pattern: deterministic test failures gate merges and releases, but soft metrics (pass-rate, mutation score, coverage, eval drift) are emitted only as per-run human-readable reports and never compared against a stored baseline. The gap is not tooling — both repos have snapshot harnesses, custom reporters, and PR comment renderers — but a missing layer: an eval-baseline file, a baseline-compare step, and a time-series store for drift.

The four empty sources are not evidence of "this dimension is poorly supported." They are evidence of a workspace provisioning gap that prevents comparison. Any study that needs to compare actual implementation choices here must first materialize the missing source trees.

## Approach Models

The two populated sources illustrate distinct "approach models" for this dimension:

**A. Aggregator-gated release images, no eval baseline (langfuse).** The CI workflow is a fan-out + aggregator pattern. Many test jobs run in parallel; an `all-ci-passed` job depends on all of them and exports a single `success` output. The release-image build job requires that output to be `true`. Code-based evals run inside the worker test job against a local Lambda mock. LLM-as-judge evals are excluded from default worker tests and only run in a path-filtered `test-worker-llm-connections` job. There is no eval pass-rate comparison anywhere — only test pass/fail. The closest baseline mechanism is a *code-shape* snapshot harness (golden-SQL) for a specific refactor, and a *user-facing* experiment baseline that lets a human pick a dataset run as a reference. (Evidence: `langfuse.md:16-63`, `langfuse.md:117-160`.)

**B. Multi-tier required-check CI with marker-based test handoff, no eval baseline (openhands).** CI is decomposed into multiple workflows (unit/lint/build, mock-LLM E2E, docker E2E, live-LLM E2E, SDK version sync, script tests) that all run on every PR except live-LLM (label-gated). A single matrix entry, `test-and-build (ubuntu)`, is the load-bearing release gate. Playwright E2E writes a `.all-passed` marker file so the CI wrapper can disambiguate "teardown hang" from "test failure." PR comments are upserted (not appended) using HTML-comment markers so historical reports don't pile up. There is no eval pass-rate baseline, no coverage threshold, and no mutation threshold — the project documents a deliberate deferral. (Evidence: `openhands.md:17-34`, `openhands.md:74-117`.)

**C. Absent source material (agent-framework, langgraph, opa, temporal).** Four sources returned empty source trees. These are not design choices; they are provisioning gaps. The "approach model" is unknowable from the in-scope evidence and the rubric forces 1/10.

## Pattern Catalog

Patterns that appear in multiple sources or in a single source with unusual clarity:

### 1. Aggregator job that aggregates all CI outputs into a single gate
- **Problem**: Many independent test jobs in a fan-out; downstream jobs need a single pass/fail signal.
- **Sources**: langfuse (explicit `all-ci-passed` aggregator).
- **Why it works**: A single output simplifies release gating to one `needs:` + one `if:` clause; downstream workflows don't have to enumerate every test job.
- **When to copy**: Large monorepos with many test jobs that must all pass before a release image is built. A release-time aggregator is the right shape; a PR-time branch-protection rule enumerating N jobs is more brittle.
- **When it is overkill or risky**: If the test jobs are cheap and homogeneous, an aggregator adds a layer of indirection that can mask individual failures. A flat `needs:` list with no aggregator is easier to debug.
- **Evidence**: `langfuse.md:18-25`, `langfuse.md:169-178`.

### 2. Mocked third-party backend in CI (Lambda mock for code evals)
- **Problem**: Code-based evals depend on AWS Lambda in production, but CI cannot call real AWS.
- **Sources**: langfuse (Floci Lambda mock for code-eval dispatchers).
- **Why it works**: The same worker code path drives both prod and CI; only the dispatcher config differs (`LANGFUSE_CODE_EVAL_AWS_LAMBDA_ENDPOINT` points at Floci). Production-equivalent behavior is exercised without secrets or network calls.
- **When to copy**: Whenever production has a sidecar runtime (Lambda, container, external service) that hosts user-supplied code or eval logic. The mock allows the dispatch path to be tested in CI.
- **When it is overkill or risky**: When the runtime behavior is not the unit under test (e.g., the eval logic itself is what matters, not the Lambda runtime). Be aware of behavior drift between Floci and real Lambda (concurrency, payload limits, network egress).
- **Evidence**: `langfuse.md:74-76`, `langfuse.md:93-99`, `langfuse.md:243-251`.

### 3. Golden / snapshot harness for code-shape regression
- **Problem**: During a large refactor, silent changes to emitted output (SQL, JSON, etc.) break callers without failing any existing test.
- **Sources**: langfuse (`goldenHarness.ts` for ClickHouse SQL emitted by repositories).
- **Why it works**: A record-on-mock + `clickhouse format` normalize + `toMatchSnapshot` loop captures exact emitted shape; PRs that change the shape without updating the snapshot fail CI.
- **When to copy**: Any time a refactor touches a code path whose output is a stable contract (SQL, JSON-schema, protobuf, generated code). Snapshots are cheap and high-signal.
- **When it is overkill or risky**: When the output is meant to evolve (e.g., log format). Snapshots can become a maintenance burden if they are too granular or normalize too aggressively. langfuse's harness is gated on `clickhouse format` availability and skips with a warning when absent — a soft contract that can be silently disabled.
- **Evidence**: `langfuse.md:50-58`, `langfuse.md:111-114`, `langfuse.md:227-231`, `langfuse.md:252-254`.

### 4. Custom CI reporter for human-readable test summaries
- **Problem**: Default test reporters emit JSON or dot output that doesn't surface the actionable signal (slowest tests, retries, flakes).
- **Sources**: langfuse (custom Vitest reporter for slowest/retried/flaky tests); openhands (Playwright `DoneMarkerReporter` for per-test JSON and `.all-passed` marker).
- **Why it works**: Custom reporters can write structured data (JSON files, marker files) that downstream CI steps can consume, and human-readable summaries that PR comments can show. The marker file pattern in particular decouples "test framework exit code" from "test outcome."
- **When to copy**: Always, when test output is the primary CI signal. The pattern is low-cost and high-value.
- **When it is overkill or risky**: Never, in this dimension. Even small projects benefit from explicit pass/fail handoff via a marker file.
- **Evidence**: `langfuse.md:107-108`, `langfuse.md:213-214`; `openhands.md:55-58`, `openhands.md:132-136`.

### 5. Per-run PR comment upsert via hidden-marker
- **Problem**: PR comments accumulate across CI runs, burying the most recent report.
- **Sources**: openhands (live-E2E and mock-LLM E2E both use HTML-comment markers like `<!-- agent-canvas-mock-llm-e2e-report -->` to find-and-replace the previous comment rather than appending).
- **Why it works**: A deterministic marker string lets the upsert script locate the previous comment and edit it in place. PRs end up with one report per workflow, not N reports.
- **When to copy**: Whenever a workflow posts a per-run report to a PR. The marker string should encode the workflow name so multiple workflows can coexist.
- **When it is overkill or risky**: Rarely. Edge case: if the marker is too generic, two workflows can collide.
- **Evidence**: `openhands.md:54-55`, `openhands.md:133-134`.

### 6. Path-triggered "detect-pr-changes" pre-job for selective CI
- **Problem**: Heavy CI jobs (full E2E, Docker builds) should run on relevant PRs but not on docs-only changes; required checks must still report `completed` (not `pending`) on every PR.
- **Sources**: openhands (`detect-pr-changes` job in `mock-llm-e2e.yml` and `mock-llm-docker-e2e.yml` queries `gh api pulls/{n}/files` and outputs `should_run: true/false`).
- **Why it works**: A lightweight pre-job determines whether downstream jobs should run; if not, the workflow still completes successfully so the required check is green.
- **When to copy**: Whenever a heavy job is required but only relevant to certain PRs. The pre-job pattern is cheaper than branch protection exceptions.
- **When it is overkill or risky**: When the heavy job is cheap enough to always run. Also: the resolver must fail closed to the full suite if the path mapping is malformed — a silent skip is worse than a full run.
- **Evidence**: `openhands.md:130-131`, `openhands.md:152-153`.

### 7. Opt-in live-LLM / live-integration E2E on a PR label
- **Problem**: Some tests require real external services (LLM APIs, Docker registry) that are expensive, non-deterministic, or credentialed. Running them on every PR is too costly.
- **Sources**: openhands (`live-e2e` label triggers the live LLM-backed Playwright suite; fork PRs are short-circuited before any secret-handling step).
- **Why it works**: Opt-in gates the cost behind an explicit human decision ("this PR is worth the spend"). The label is a coordination signal between reviewer and CI.
- **When to copy**: Whenever a test tier is too expensive or non-deterministic for always-on CI. The opt-in mechanism (label, path filter, manual dispatch) is interchangeable.
- **When it is overkill or risky**: If the live-LLM behavior is the primary correctness signal, opt-in creates a regression that only surfaces when someone remembers to apply the label. openhands documents this as a process risk.
- **Evidence**: `openhands.md:52-53`, `openhands.md:144-145`, `openhands.md:165-166`.

### 8. Explicit deferral of soft-metric thresholds until a baseline exists
- **Problem**: Coverage and mutation-testing thresholds are arbitrary until the codebase has been measured under stable conditions; premature thresholds create noise that erodes trust.
- **Sources**: openhands (Stryker mutation testing is "report-only initially; establish a stable baseline before adding a failing threshold" per `docs/DEVELOPMENT.md:144-146`; coverage has reporters but no threshold).
- **Why it works**: It acknowledges that baselines are a prerequisite for thresholds, and avoids the trap of a threshold so noisy that contributors ignore it.
- **When to copy**: Whenever a soft metric (coverage, mutation, performance, pass-rate) is being introduced for the first time. Report first, threshold second.
- **When it is overkill or risky**: Never, in the early stage. But: indefinite deferral is itself a risk. The repo must eventually set a threshold or admit the metric doesn't matter.
- **Evidence**: `openhands.md:65-66`, `openhands.md:125-126`, `openhands.md:177`.

## Key Differences

The populated sources differ on:

1. **Where the gate lives.** langfuse uses an aggregator job (`all-ci-passed`) that downstream release-image builds depend on. openhands uses a single matrix entry (`test-and-build (ubuntu)`) that the release-please workflow polls for via the check-runs API. Both shapes work; the difference is that langfuse's gate is in-workflow (`needs: + if:`) while openhands's gate is cross-workflow (API polling). The cross-workflow shape is heavier (40-minute wait budget) but works across multiple workflows without an explicit dependency graph.

2. **What counts as an "eval."** langfuse interprets "eval" as a user-facing feature: code-based evaluators and LLM-as-judge evaluators that produce `Score` rows. openhands interprets "eval" as a UI E2E tier (Playwright against mock-LLM, docker, or live-LLM). The dimension is "regression gating and CI integration," so both interpretations are valid; the gap is that langfuse tests eval execution but doesn't gate on eval results, while openhands gates on test results but doesn't measure eval-quality.

3. **Whether eval results are a CI artifact.** Neither source emits an aggregate eval pass-rate as a CI artifact. langfuse writes `Score` rows through the standard ingestion pipeline (queryable, but not compared across runs). openhands writes a per-run report via PR comment but doesn't compare it to anything. Both miss the "baseline file + compare step" pattern.

4. **What the deploy path actually does.** langfuse has two distinct workflows: `pipeline.yml` (CI + release-image build) and `deploy.yml` (ECS service deploy). The release image is gated; the ECS deploy is not. openhands has a single release path gated on `test-and-build (ubuntu)`, with the heavier E2E jobs as required checks but not as release blockers. The trade-off: langfuse's separate `deploy.yml` allows fast iteration on `main` but risks shipping a failing test; openhands's centralized gate is more conservative but adds latency.

5. **Whether fork-PR safety is addressed.** openhands explicitly checks `is_fork == 'true'` and short-circuits the live-E2E job before any secret-handling step. langfuse's source report does not surface an equivalent guard (its `pipeline.yml` runs on `pull_request` without an obvious fork bypass), so this is a likely gap rather than a verified pattern.

## Decision Guide

Use this section to choose between the observed approaches for a new project.

**1. Do you need a release gate, or a PR gate, or both?**
- If releases are tagged images: use an aggregator job that all test jobs `needs:` and a release-image job that requires the aggregator (langfuse pattern).
- If releases are branch-protection enforced: use a single required-check matrix entry that the release workflow polls for via the check-runs API (openhands pattern).
- If you have both: make sure the deploy workflow depends on the CI workflow. langfuse's `deploy.yml` does not depend on `pipeline.yml`, which is the single biggest gap in the populated sources.

**2. Do your tests depend on a third-party runtime?**
- If yes and the runtime is testable locally: mock it (langfuse Floci). Be aware of behavior drift; consider a path-filtered live-integration job for the highest-stakes paths.
- If yes and the runtime is not testable locally: opt-in via label (openhands `live-e2e` pattern). Document the process risk explicitly.

**3. Do you need snapshot-based regression detection?**
- If you are mid-refactor on a stable-output code path: introduce a golden / snapshot harness (langfuse `goldenHarness.ts`). Gate on `toMatchSnapshot` and make the harness fail closed if the normalize tool is missing.
- If the output is meant to evolve: skip snapshots; use a behavior-level test instead.

**4. Do you want pass-rate drift tracking?**
- Neither populated source has it. If you need it: persist per-run pass-rates to a time-series store, emit an aggregate artifact from CI, and compare against a stored baseline file in a follow-up step. The pattern is not present in any of the six sources, so you are inventing it.
- If you don't need it yet: be explicit about the deferral (openhands documents it for mutation/coverage).

**5. Do you have a soft metric (coverage, mutation, latency) you want to gate on?**
- Report first, threshold second (openhands pattern). If you set a threshold before the codebase is stable, you will get noise that erodes trust.

## Practical Tips

Patterns to copy:
- **Aggregator job for fan-out CI.** One job that `needs:` every test job and exports a single `success` output. Downstream release jobs `if: needs.aggregator.outputs.success == 'true'`. (langfuse)
- **Mock third-party runtime in CI via endpoint swap.** Production dispatcher vs. CI dispatcher; same code path, different config. (langfuse)
- **Custom reporter that writes a marker file for CI handoff.** Decouples "test framework exit code" from "test outcome." Survives teardown hangs. (openhands)
- **Per-run PR comment upsert via hidden HTML-comment marker.** One report per workflow per PR. (openhands)
- **Path-triggered pre-job that fails closed.** Lightweight detection of changed files; downstream heavy jobs skip if not relevant but the required check still completes. (openhands)
- **Opt-in heavy E2E via PR label with fork-PR short-circuit.** Cost-gated; safe against secret leaks. (openhands)
- **CI-script self-tests.** Pytest over `.github/scripts/` when those files change. The gating logic itself has regression coverage. (openhands)

Patterns to avoid or delay until needed:
- **No baseline comparison in CI.** If you need pass-rate drift, you must persist per-run results. Both populated sources skip this and acknowledge the gap.
- **No coverage / mutation threshold until a stable baseline.** Document the deferral; do not leave it implicit. (openhands)
- **Separate deploy workflow with no `needs:` to CI.** Causes CI green != deploy safe. (langfuse)
- **Snapshot harness gated on a normalize tool that can be absent.** Soft contract that silently disables the gate. (langfuse)
- **Soft-metric thresholds set before the codebase is measured.** Noise erodes trust in the gate. (anti-pattern, both sources avoid)

Decision rules for choosing between approaches:
- **Aggregator vs. matrix entry as release gate**: aggregator when many parallel test jobs exist; matrix entry when CI is small enough to enumerate in branch protection.
- **Mock vs. opt-in live for third-party runtime**: mock when production-equivalent behavior is testable locally and the runtime differences are bounded; opt-in when the runtime is the variable under test or the cost is prohibitive.
- **Snapshot vs. behavior test**: snapshot when the output is a stable contract; behavior test when the output is meant to evolve.
- **Coverage / mutation threshold now or later**: now if the codebase has been measured under stable conditions for at least one quarter; later (with explicit deferral) otherwise.

Caution signs the design is becoming brittle:
- **CI green != deploy safe**: separate deploy workflows without `needs:` to the CI workflow. (langfuse gap)
- **LLM-eval drift hides between releases**: path-filtered live-eval jobs only run on certain file changes or tags. (langfuse)
- **Flaky tests masked by retries**: vitest/pytest retries plus a `flaky: true` flag, with no flake-rate metric or N-consecutive-flakes policy. (langfuse partial)
- **Snapshot file silently disabled**: the normalize tool is absent on a runner and the test skips with a warning instead of failing. (langfuse)
- **Required check is actually pending, not completed**: a heavy job that doesn't run on docs-only PRs but also doesn't have a `detect-pr-changes` pre-job. The PR shows a yellow check indefinitely.
- **Mutation/coverage never gets a threshold**: deferral becomes permanent. Set a date, or admit the metric doesn't matter. (openhands risk)
- **Per-run artifacts uploaded but never consumed**: storage cost grows, but no dashboard, no history, no drift detection. (both sources)
- **No evidence of "what would unblock this dimension"**: the source is empty. The dimension study cannot proceed. (agent-framework, langgraph, opa, temporal)

## Anti-Patterns / Caution Signs

- **Aggregator release-gate with independent deploy workflow** (langfuse): CI green implies release-image safety but does not imply ECS deploy safety. A failing test on `main` can still ship via `deploy.yml` before the release tag is cut. Fix: `needs: [CI/CD]` from the deploy job.
- **Soft contract on a normalize tool** (langfuse golden-SQL): if `clickhouse format` is absent, the golden test skips with a warning and the only baseline-snapshot gate is silently disabled. Fix: fail closed when the tool is missing, or vendor the normalizer.
- **LLM-eval tests only on tag pushes or path-filtered changes** (langfuse): the full LLM-eval path is rarely exercised on a regular PR, so LLM-eval regressions can ship. Fix: always-on LLM eval against a fixture dataset with `LANGFUSE_SKIP_EVALUATOR_MODEL_CALL_VALIDATION=false`.
- **Flaky tests masked by retry without a flake budget** (langfuse partial): a flaky test that eventually passes is not surfaced as a failure; there is no policy to fail the build on N consecutive flaky runs. The CI reporter's `[flaky]` output is human-readable only. Fix: promote flaky count to a metric that fails the build when a test is flaky N times in a row.
- **Code-eval runtime mismatch between CI mock and prod Lambda** (langfuse): worker tests use Floci, production uses real AWS Lambda. Behavior differences (concurrency, payload limits, runtime versions, network egress) are not regression-tested. Fix: a periodic live-integration job against real Lambda.
- **Opt-in live E2E as a process risk** (openhands): real-LLM regressions only surface when someone remembers to apply the `live-e2e` label. Fix: scheduled nightly live-E2E in addition to label-gated.
- **Mutation / coverage without a threshold, indefinitely** (openhands): "report-only initially" can become "report-only forever." Fix: set a deadline for establishing a baseline and a threshold.
- **Ephemeral PR artifacts that can pollute main** (openhands): `.pr/` directory contains QA screenshots/videos that are pushed to the PR branch. The cleanup-on-approval workflow is the only safeguard. Fix: never push artifacts to the PR branch; upload them as CI artifacts only.
- **Soft contract on `clickhouse format` for golden-SQL** (langfuse): see above. The skip-with-warning pattern is the same anti-pattern regardless of the normalize tool.
- **Empty source tree with a non-trivial source manifest** (agent-framework, langgraph, opa, temporal): the dimension cannot be studied because there are no files to inspect. The rating is forced to 1/10. Fix: materialize the source clone before running the dimension, or skip the dimension in the schedule.

## Notable Absences

These are things the dimension expects to find but that no source exhibits:

- **No eval pass-rate baseline file**. No populated source has a `__eval-baselines__/`, `golden.json`, or `expected.json` for eval scores. langfuse's golden-SQL snapshot is for code shape, not eval scores. openhands has no baseline of any kind.
- **No eval drift dashboard**. Neither langfuse nor openhands tracks pass-rate over time. langfuse's CI-runtime analyst (`ci-runtime-analyst.md`) tracks CI step drift, not eval drift. openhands has no historical storage at all.
- **No eval report file emitted from CI**. langfuse writes `Score` rows through the standard ingestion pipeline; openhands writes a per-run PR comment. Neither emits a structured eval report artifact (JSON / JUnit / SARIF) that a downstream compare step could consume.
- **No flake budget policy**. langfuse's CI reporter flags flaky tests; openhands' reporter tracks `retryCount`. Neither has a "fail the build if a test is flaky N times in a row" policy.
- **No coverage or mutation threshold**. openhands explicitly defers. langfuse has no coverage configuration. The dimension's rubric band 9-10 ("proven under failure or scale") implies these thresholds; neither source is there.
- **No scheduled nightly eval job**. openhands' live-E2E is label-gated. langfuse's LLM-eval job is path-filtered. Neither has a fixture-dataset nightly run.
- **No cross-source consistency on the deploy-gate relationship**. langfuse separates `deploy.yml` from `CI/CD`; openhands has a single release path. The dimension's guiding question ("Can a code change that degrades quality be blocked before deployment?") cannot be answered uniformly.
- **No source material in 4 of 6 sources**. agent-framework, langgraph, opa, and temporal all have empty source trees. The dimension is unstudiable for these sources; the rating is forced to 1/10.
