## Executive Summary

None of the three studied systems builds a model-facing repository map. Exhaustive negative searches in every source report — for repo-map, code-map, tree-sitter, ctags, symbol-index, and file-tree constructs — returned zero agent-facing matches in all three codebases (agent-framework: pattern searches over all `.py`/`.cs`; langgraph: searches across all libs; openhands: searches returning only CSS `outline-*` utilities). The dimension's headline question — "Can the model find the right file without being told the path?" — is answered **no by design** everywhere, but each system answers a *different adjacent question* well:

- **agent-framework** (rated 4/10) gives the model safe exploration primitives (`file_access_ls` with glob filters, recursive regex `file_access_grep`) plus self-maintained markdown indexes of its *own memory outputs* (`memories.md`, `MEMORY.md`) that are rebuilt incrementally and injected automatically.
- **langgraph** (rated 3/10) maps its *own computation graph*, not any filesystem: `get_graph()` assembles a drawable structural map via bounded static simulation, while versioned channels and delta checkpointing provide exact incremental workspace-state tracking.
- **openhands** (rated 5/10) builds a polished *human-facing* workspace map — bounded enumeration, client-side tree building, event-driven invalidation — and deliberately delegates all model-facing context construction to a sibling SDK repo.

The strongest convergence is not in what is mapped but in **how freshness is engineered**: rebuild-on-write indexes with self-healing (agent-framework), version vectors with delta anchors (langgraph), and event-driven cache invalidation with TTLs (openhands) are three mature, tested implementations of the same underlying discipline — treat context maps as derived state, keep them incrementally current, and degrade gracefully when they break. That machinery is directly transferable to repository mapping; only the mapped domain is missing.

## Core Thesis

**Every studied harness has already solved the hard part of context maps — incremental maintenance, bounded staleness, and graceful degradation — but none applies it to a repository.** Each source instead maps a surrogate domain chosen by its product shape: agent-framework maps the agent's own prior outputs because it is sandbox-first and cannot assume a real checkout; langgraph maps its computation graph because it orchestrates state, not files; openhands maps the workspace visually because it serves human operators while its architecture explicitly assigns model-facing context to another repo.

The consequence for practitioners is clarifying rather than discouraging: if you build an agent that must navigate a real codebase, none of these systems will hand you a repomap, a symbol index, or scored file selection. You will either compose their primitives (grep/ls tools), reuse their freshness patterns (versioned derived state, event-driven invalidation), or build the map layer yourself. What you should *copy* from this study is the incremental-update discipline; what you should not expect is a finished answer to "where is X defined?"

## Approach Models

Three distinct models emerge, one per source:

**1. Tool-mediated exploration with self-curated memory indexes (agent-framework).**
The framework refuses to precompute anything about a codebase. It scopes all file tools to a task store rooted at `{cwd}/agent-file-memory/{timestamp}_{guid}`, exposes always-on read primitives and approval-wrapped writes, and lets the LLM drive discovery (`dotnet/src/Microsoft.Agents.AI/Harness/FileAccess/FileAccessProvider.cs:41-47`; `python/packages/core/agent_framework/_harness/_file_access.py:1488-1561`). In place of a repo map, the harness maintains markdown table-of-contents files over its own memory store — `memories.md` capped at 50 entries, rebuilt synchronously after every write/delete under a lock (`python/packages/core/agent_framework/_harness/_file_memory.py:77-78, 280-299`), and `MEMORY.md` as an "always-loaded table of contents" with keyword-scored topic selection into context (`python/packages/core/agent_framework/_harness/_memory.py:32, 1295, 1078-1098`). Semantic search over files is offloaded to provider APIs (`SupportsFileSearchTool`, `python/packages/core/agent_framework/_clients.py:789`).

**2. Explicit construction with structural self-description (langgraph).**
Nothing about the world is discovered; developers register nodes and edges by hand (`StateGraph.add_node/add_edge/add_conditional_edges`, `libs/langgraph/langgraph/graph/state.py:376,928,982`), and deployment entry points must be declared in `langgraph.json` (`libs/cli/schemas/schema.json` `$defs.GraphDef {path}`; validated at `libs/cli/langgraph_cli/config.py:323`). What the system *does* map is itself: `draw_graph()` simulates the Pregel loop statically against empty inputs to discover edges, capped at 250 supersteps (`libs/langgraph/langgraph/pregel/_draw.py:42-277, 53`), exposed through `Pregel.get_graph(xray=...)` (`libs/langgraph/langgraph/pregel/main.py:845-871`) and mirrored remotely via `GET /assistants/{assistant_id}/graph` (`libs/langgraph/langgraph/pregel/remote.py:256-289`). Workspace *state* is summarized on demand: `get_state()`/`get_state_history()` read fresh snapshots from the checkpointer with pending-write overlays (`libs/langgraph/langgraph/pregel/main.py:1392-1435, 1145-1185`).

**3. Human-facing workspace mirror with delegated model context (openhands).**
The frontend enumerates the workspace with a pruned, capped `find` (14 heavy directories excluded, 2000-entry cap) executed locally or server-side depending on backend kind (`src/hooks/query/use-workspace-files.ts:16, 24-47, 42-47, 129-165`), builds a sorted tree client-side using an O(1) parent side-table (`src/utils/file-tree.ts:69-98, 22-35`), and keeps everything fresh by watching the conversation event stream — every editor observation invalidates workspace-file, content, diff, and git queries (`src/hooks/use-auto-refresh-files-on-edit.ts:8-25, 135-141`). Model-facing navigation is intentionally absent: per the repo's own `AGENTS.md` placement table, agent/tool behavior belongs to the sibling SDK, so the agent discovers code through its own sandbox tools. The one machine-authored environment map is the `<RUNTIME_SERVICES>` topology block appended to the system message suffix (`src/api/agent-server-adapter.ts:215-297, 749-755`).

## Pattern Catalog

Patterns appear below only if demonstrated in multiple sources or unusually clearly in one.

### P1. Derived index rebuilt on mutation, degraded gracefully when corrupt
- **Problem:** A summary artifact over a growing store goes stale or corrupt; consumers need it fresh or safely absent, never wrong.
- **Demonstrated:** agent-framework rebuilds `memories.md` after every write/delete under a per-instance lock; an unreadable index is skipped with a warning and self-heals on next successful write; unchanged indexes are not rewritten (`python/packages/core/agent_framework/_harness/_file_memory.py:266-299, 496-520`; tests at `python/packages/core/tests/core/test_harness_memory.py:292`). openhands applies the same idea structurally: query results are normalized, de-duped, and re-capped post-fetch (`src/hooks/query/use-workspace-files.ts:97-104`). langgraph's analog is at the storage layer: checkpoints carry `updated_channels` so downstream consumers know exactly what changed (`libs/checkpoint/langgraph/checkpoint/base/__init__.py:92-127`).
- **Why it works:** The index is treated purely as derived state — there is no cache-invalidation problem because there is no cache, only recomputation; corruption degrades to "skip injection," not "inject lies."
- **Copy when:** Your map/index covers a store your system itself mutates. **Overkill/risky when:** the store is large or externally mutated — full rebuild becomes O(store) work per mutation (agent-framework's report flags exactly this scaling concern).
- **Evidence:** agent-framework report (Failure Modes: corrupt index handling); openhands report (Defensive data shaping); langgraph report (checkpoint versioning).

### P2. Keyword-overlap scoring as a first ranking layer before embeddings
- **Problem:** Selecting relevant entries into a limited context window without infrastructure.
- **Demonstrated:** agent-framework's `_select_topics` scores index entries by word intersection with user input and loads top-N=3 with score > 0 (`python/packages/core/agent_framework/_harness/_memory.py:1078-1098`). langgraph offers the heavyweight alternative behind config: `BaseStore.search(query=...)` with `IndexConfig(dims, embed, fields)` activates vector search only when configured (`libs/checkpoint/langgraph/store/base/__init__.py:779-800, 578-660`). openhands shows the failure mode of the third option — a hand-curated basename priority scorer (`sortFilesByPriority`) that ended up orphaned dead code with only its own test as consumer (`src/utils/file-priority.ts:98-106`; `__tests__/utils/file-priority.test.ts:3`).
- **Why it works:** Keyword overlap is deterministic, explainable, zero-dependency; embedding search is powerful but adds infra burden; hand-curated lists rot silently.
- **Copy when:** Bootstrapping relevance ranking; graduate to embeddings (langgraph style, opt-in) only when keyword overlap demonstrably misses. **Avoid:** shipping curated priority lists without wiring them into production paths — openhands proves they get abandoned.
- **Caveat:** agent-framework's selection silently returns nothing when keywords don't overlap (`_memory.py:1087-1089`) — no fallback set. Pair with a recency fallback.

### P3. Bounded simulation to generate a structural map
- **Problem:** Producing a map of behavior that only manifests at runtime.
- **Demonstrated:** langgraph's `draw_graph` executes node writers against an empty checkpoint with input `{}` to collect static writes and discover conditional edges, with a hard `limit: int = 250` superstep cap guaranteeing termination on loopy graphs (`libs/langgraph/langgraph/pregel/_draw.py:88-151, 53, 118`). Map regressions are pinned byte-for-byte in Mermaid snapshot tests including xray expansions (`libs/langgraph/tests/test_pregel.py:1754, 3090-3173`).
- **Why it works:** Deterministic and dependency-free; the cap converts potential non-termination into a documented fidelity loss.
- **Copy when:** Topology is mostly static and you can tolerate under-reporting runtime-guarded branches (langgraph's report names this blind spot explicitly, `_draw.py:192-216` deferred-node stitching aside).
- **Risky when:** Behavior is input-dominated — the map will systematically lie by omission.

### P4. Version vectors + seen-sets for exact incremental awareness
- **Problem:** Knowing precisely what changed since a consumer last looked, without diffing content.
- **Demonstrated:** langgraph tracks monotonic `channel_versions` against per-node `versions_seen`, computing `updated_channels` on every write application (`libs/checkpoint/langgraph/checkpoint/base/__init__.py:109-122`; update sites `libs/langgraph/langgraph/pregel/_algo.py:262-269, 320-334`); uncommitted results surface as `pending_writes` overlays rather than mutating stored checkpoints (`libs/langgraph/langgraph/pregel/main.py:1145-1185`).
- **Why it works:** Turns "is my view stale?" from a heuristic into arithmetic.
- **Copy when:** Building any cache/coherence layer where correctness matters more than simplicity. This is the most transferable pattern in the study for a future repo-map implementation: a file map could carry per-file versions and per-consumer seen-sets identically.

### P5. Deltas with periodic anchor snapshots
- **Problem:** Incremental representations grow replay costs unboundedly.
- **Demonstrated:** langgraph's beta `DeltaChannel` stores sentinel `MISSING` between snapshots and reconstructs by folding ancestor writes through the reducer, forcing full-value snapshots every ≥1000 updates or 5000 supersteps (`libs/langgraph/langgraph/channels/delta.py:25-64, 139-157, 193-202`; predicate at `libs/langgraph/langgraph/pregel/_checkpoint.py:50-73`), with a benchmark suite for tuning (`libs/langgraph/tests/test_delta_channel_benchmark.py:1-83`).
- **Why it works:** Bounds worst-case replay depth structurally rather than hoping workloads stay small.
- **Risky when:** Retention ops interact badly — `prune`/`delete_thread` can permanently break reconstruction unless savers implement `get_delta_channel_history` correctly (`libs/checkpoint/langgraph/checkpoint/base/__init__.py:340-412, 582`); the whole surface is flagged beta (`delta.py:29-36`). Copy the *shape* (deltas + anchored snapshots + documented cadence knobs), heed the hazard labels.

### P6. Event-driven invalidation scoped to mounted consumers
- **Problem:** Keeping a rendered view of mutable files fresh without polling everything forever.
- **Demonstrated:** openhands watches editor/bash observations from the conversation stream (skipping read-only `view`) and surgically invalidates TanStack Query keys, deliberately exempting immutable sha-addressed commit queries and limiting refetches to mounted queries (`src/hooks/use-auto-refresh-files-on-edit.ts:8-25, 127-141, 131-134, 50-68`); a monotonic mutation counter appended as `?v=<n>` busts browser caches for previews (`src/stores/use-workspace-mutation-counter.ts:30-34, 41-53`); TTLs bound residual staleness to seconds (30s listings, 5s content, 10s git re-probe — `use-workspace-files.ts:108-109`, `use-workspace-file-content.ts:299-300`, `use-local-git-info.ts:158-159`).
- **Why it works:** Cost proportional to actual writes; idempotent processing via id Set + WeakSet handles out-of-order events (`use-auto-refresh-files-on-edit.ts:77-103`).
- **Copy when:** Any UI or agent observing a workspace an external process (the agent) is mutating.
- **Known tradeoff accepted:** shell-command observations don't bump the preview cache-buster to avoid iframe flicker, accepting brief staleness in rich previews (`use-auto-refresh-files-on-edit.ts:56-64`).

### P7. Uniform injection seams for context
- **Problem:** Context maps are useless unless something inserts them into the prompt at the right moment.
- **Demonstrated:** agent-framework funnels memory indexes and environment snapshots through a single `ContextProvider.before_run` hook (`python/packages/core/agent_framework/_sessions.py:793-797`; `python/packages/tools/agent_framework_tools/shell/_environment.py:103-104`); openhands routes its environment topology through `buildAgentContext → agent_context.system_message_suffix` (`src/api/agent-server-adapter.ts:749-755`) and notes this seam is where a file map would attach if ownership were settled.
- **Why it works:** One injection contract means adding a new context source requires no orchestration changes.
- **Copy when:** Designing a harness — define the seam before defining the maps that flow through it.

## Key Differences

**What converges despite different implementations:**

- **No model-facing repository map, anywhere.** All three sources report zero evidence of repo-map generation, symbol indexing (no tree-sitter/ctags/AST subsystems), or token-budgeted map artifacts aimed at the LLM (all three reports' Questions/Gaps sections; e.g., openhands found only CSS utilities and terminal-prompt parsing for "symbol" searches, `src/utils/parse-terminal-output.ts:4-15`).
- **Freshness discipline is universal.** Rebuilt-after-mutation indexes with self-healing (agent-framework, `_file_memory.py:496-520`), fresh-by-construction checkpointer reads with version arithmetic (langgraph, `pregel/main.py:1428`; `checkpoint/base/__init__.py:109-122`), and layered event+TTL invalidation (openhands) are the same engineering value expressed in three runtimes.
- **Delegation over construction.** All three push "find the right file" onto someone else: the model itself (agent-framework), applications built atop the framework (langgraph's explicit statement that teams must add retrieval/RAG layers), or a sibling repo (openhands' SDK boundary).
- **Inspectability of map artifacts.** Markdown indexes humans can edit (agent-framework, `_memory.py:1295`), Mermaid/PNG graph renderings pinned in snapshots (langgraph, `tests/test_pregel.py:1754`), and browsable directory trees (openhands, `file-tree.ts:69-98`) — every source renders its map in a format a person can read directly.

**Why they diverge — product shape, not quality:**

- **Framework vs product.** agent-framework and langgraph are libraries that cannot assume a repository exists at all; openhands is a product frontend that can assume a workspace but is contractually barred from model-context concerns by its `AGENTS.md` placement table (openhands report, Architectural Decisions).
- **Safety posture.** agent-framework's sandbox-first scoping makes real-repo mapping deliberately difficult even when an integrator wants it — confinement-first design trades usefulness for safety (its report, Architectural Decision 2; `HarnessAgentOptions.cs:240`; symlink fail-closed skill discovery at `_skills.py:3552-3560`).
- **Mapped-domain choice follows the system's own artifact type.** langgraph's state lives in channels, so it versions channels; agent-framework's durable output is memory files, so it indexes memory files; openhands' users look at files, so it mirrors files.
- **Selection-policy maturity differs meaningfully.** langgraph's selection is human-authored at build time and validated up front (`config.py:323`) — maximally predictable, zero discovery. agent-framework's selection is runtime keyword-scoring over its own index (`_memory.py:1078-1098`) — automated but shallow. openhands had an automated selector and abandoned it (orphaned `sortFilesByPriority`), falling back to coarse pruning plus user clicks. These are genuinely different responses to the same problem, not rank-orderable quality differences.

## Tradeoffs

- **Precomputed map vs live exploration.** A repo map compresses many ls/grep round-trips into one prompt block but goes stale and is expensive to build correctly across languages. All three sources chose live exploration or explicit registration; agent-framework pays the token cost knowingly (its report, Tradeoffs: "Token economics vs correctness"). Alternative seen: nobody paid the map-building cost, which is itself informative — none of these products is a CLI coding agent operating directly on a real checkout, where that trade flips.
- **Rebuild-on-write vs read-through vs event-driven freshness.** agent-framework's synchronous rebuild-under-lock (`_file_memory.py:266-299`) is simplest and always correct but becomes O(store) per mutation at scale; langgraph's read-through checkpointer with version vectors (`pregel/main.py:1428`) is always fresh with no write-path cost but pays on every read; openhands' event-driven invalidation with TTL backstops (`use-auto-refresh-files-on-edit.ts`) is cheapest in steady state but accepts second-scale staleness and flicker tradeoffs. Choose by mutation-to-read ratio.
- **Delta compression vs replay cost.** langgraph shrinks blobs by storing sentinels, then charges every delta read an ancestor-walk + reducer fold, mitigated by cadence knobs tuned via benchmark (`delta.py:26-39`; `test_delta_channel_benchmark.py:1-83`). agent-framework takes the opposite pole: never store deltas, always rebuild fully. openhands doesn't compress at all — it just re-fetches within caps.
- **Static-map fidelity vs termination.** langgraph's 250-step simulation cap guarantees `get_graph()` halts but under-reports branches reachable only under real inputs (`_draw.py:53, 118`). The alternative — no static map at all — is what the other two sources do.
- **Explicitness vs discoverability.** langgraph requires `langgraph.json` entry-point declarations, avoiding wrong-file surprises at the cost of zero automatic introspection (`config.py:323, 827-1056`); agent-framework discovers skills by scanning depth-bounded directories (`_skills.py:3545-3560`). Registry beats scan when wrong picks are expensive; scan beats registry when contributors forget to register.
- **Sandbox safety vs real-repo utility.** agent-framework's confinement means the out-of-box experience cannot map a real checkout even if desired (its report, Tradeoffs). openhands faces the inverse constraint — cloud backends disable local path probes to avoid leaking local paths (`use-local-git-info.ts:82-87`). Both show environment-trust boundaries dictating map scope.
- **Human-readable formats vs capacity.** Markdown indexes are inspectable and diffable but capped hard (50 entries; 200 lines × 150 chars — agent-framework, `_file_memory.py:78`; `_memory.py:44-68`), losing fidelity as stores grow. Structured formats would scale further at the cost of the inspection property all three sources visibly value.

## Decision Guide

Rules of thumb distilled from the compared approaches:

1. **Does your agent operate on a sandbox it owns, or a real checkout?** Sandbox → copy agent-framework's model: safe primitives + approval-wrapped mutations + self-maintained indexes over the agent's own outputs. Real checkout → none of these sources solves it; plan to build or integrate a dedicated repo-map layer, reusing the freshness patterns cataloged above.
2. **What is your mutation-to-read ratio?** Write-heavy small stores → rebuild-on-write (agent-framework). Read-heavy execution state → read-through with version vectors (langgraph). UI-adjacent views of an externally mutated filesystem → event-driven invalidation with TTL backstops (openhands).
3. **Do you need ranking before you have embeddings infra?** Start with keyword-overlap scoring (agent-framework, `_memory.py:1078-1098`); adopt opt-in semantic search (langgraph `IndexConfig`) only when overlap demonstrably fails; never ship curated priority lists unwired (openhands' orphaned scorer is the cautionary example).
4. **Must your map terminate on adversarial/loopy structure?** Use bounded simulation with an explicit fidelity-loss cap (langgraph's 250 steps), and pin expected output in snapshot tests.
5. **Where does model-facing context ownership live in your org?** Decide the seam before the feature. openhands' `AGENTS.md` placement table prevented duplication but also left the capability unbuilt; agent-framework's single `before_run` hook shows what a settled ownership boundary enables.
6. **Is your incremental representation beta?** If so, gate destructive operations on it (langgraph's prune/DeltaChannel interplay) and document saver/consumer contracts — otherwise retention ops will silently destroy reconstructibility (`checkpoint/base/__init__.py:340-412`).

## Practical Tips

- **Define the injection seam first.** Adopt a single uniform hook (agent-framework's `ContextProvider.before_run`, `_sessions.py:793-797`) so every future context source — env snapshot today, repo map tomorrow — plugs in without orchestration changes.
- **Treat every index as disposable derived state.** Rebuild rather than patch; skip-and-warn on corruption rather than serving partial truth; heal on next mutation (agent-framework, `_file_memory.py:496-520`). Tests should cover round-trip, trim, unchanged-no-rewrite, and concurrency (mirrored at `test_harness_memory.py:95, 134, 292, 640`).
- **Bound every enumeration twice:** structural exclusions (openhands prunes 14 known-heavy dirs, `use-workspace-files.ts:24-39`) *and* a hard entry cap (2000, `use-workspace-files.ts:16`). Then surface truncation — openhands' silent cap is flagged by its own report as a defect to fix.
- **Make map outputs snapshot-tested artifacts.** langgraph pins Mermaid renderings byte-for-byte across dozens of cases (`test_pregel.py:3090-3173`); openhands locks in tree-builder performance (`__tests__/utils/file-tree.test.ts:63`). Regressions become visible diffs, not vibes.
- **Track staleness arithmetically where correctness matters.** Version vectors + seen-sets (langgraph, `_algo.py:262-269`) beat timestamps and heuristics; the same scheme ports directly to per-file versions in a future repo map.
- **Scope selections to sessions/workspaces explicitly.** openhands tags file selections with conversation ids to prevent cross-workspace leakage (issue #1350 fix, `files-tab.tsx:93-106`) — apply the same keying to any agent-side context cache keyed by working directory.
- **Document what your freshness machinery deliberately does *not* do.** openhands' inline rationale comments (bash events don't bump preview counters; git probe disabled on cloud, `use-local-git-info.ts:82-87`) prevent well-meaning regressions later.
- **Extend keyword scoring toward files before adopting embeddings.** agent-framework's own Future Considerations propose exactly this: score project files by name/path/recency heuristics as a principled first probe of unfamiliar workspaces (`_memory.py:1078-1098` as the seed pattern).

## Anti-Patterns / Caution Signs

- **Silent truncation.** openhands' 2000-file cap yields an incomplete map with no user-visible indicator (`use-workspace-files.ts:104, 155`). Any bounded map needs a "truncated" signal.
- **Orphaned smart features.** A tested-but-unwired scorer (`sortFilesByPriority`) signals design intent that lost its champion; dead intelligence rots and misleads readers (openhands report, Questions/Gaps).
- **Curated lists without consumers or eviction.** agent-framework has no aging/eviction policy beyond entry caps, and keyword selection returns nothing on zero overlap (`_memory.py:1087-1089`) — both are quiet degradation paths.
- **Beta surfaces exposed to destructive ops.** langgraph's prune/delete can permanently break DeltaChannel reconstruction for unaware custom savers (`checkpoint/base/__init__.py:340-412, 551`). If your map format has a reconstruction contract, retention tooling must be contract-aware.
- **Silent schema drift.** langgraph drops unknown-channel writes with only a warning during `apply_writes` (`_algo.py:308-313`) — context loss disguised as tolerance.
- **O(store) rebuilds framed as free.** "Always rebuild" is simple until stores grow; if your index rebuild runs per mutation, instrument its cost early (agent-framework report, Failure Modes).
- **Flicker-driven partial invalidation.** Excluding some mutation sources from refresh (shell edits don't refresh rich previews, openhands `use-auto-refresh-files-on-edit.ts:56-64`) is a reasonable tradeoff but must be paired with another freshness path for those sources (diff views still refresh) — otherwise it becomes a hole.
- **Caution signs a context-map area is going brittle:** caps that bind without telemetry, selectors whose only caller is their test, freshness guarantees measured in "should be fine" rather than TTLs/events, and map formats lacking conformance tests (contrast langgraph's checkpointer conformance suite, `libs/checkpoint-conformance/tests/test_validate_memory.py:16-20`).

## Notable Absences

Absences corroborated across multiple sources:

- **No repository map generator of any kind** in any source (all three reports' negative-search sections).
- **No symbol indexing whatsoever** — no tree-sitter, ctags, AST outlines, or definition indexes exposed to agents; nearest hits are incidental (DevUI sample discovery via `ast.parse`, `python/packages/devui/agent_framework_devui/_discovery.py:556-559`; CSS focus utilities and terminal-prompt parsing in openhands).
- **No token-budgeted or relevance-scored file selection for prompts** in any source; the only scoring targets memory topics (agent-framework) or store items (langgraph).
- **No directory-tree rendering tool** in agent-framework — enumeration is strictly level-by-level `ls` (pattern search for directory-tree constructs returned zero matches).

Single-source absences worth noting:

- **No workspace-state summarization of a repository** (build status, layout, dependency graph): absent in agent-framework; nearest analogs summarize conversation history (`_compaction.py:1197`) and shell environment (`_environment.py:103-104`).
- **No truncation indicator, staleness telemetry, or byte-accurate cloud binary serving** in openhands (`use-workspace-file-content.ts:224-228` acknowledges the last).
- **No unified "context view" API** in langgraph — consumers must orchestrate `get_state`, `get_state_history`, and Store search separately (`pregel/main.py:1392, 1480`; `store/base/__init__.py:779`).
- **No automatic project introspection at deploy time** in langgraph — entry points are registry-only (`config.py:323`).

These absences are consistent with the thesis: the mapped object (a repository) falls outside each product's responsibility boundary, so no source was motivated to build the missing layer.
