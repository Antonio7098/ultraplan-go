Two sources — opa and temporal — are not agent harnesses at all; they are a policy engine and a workflow orchestrator studied as mature reference implementations of capability modeling for "programs" and "API callers." Their ratings measure the same dimension applied to their own trust domains, not agent safety per se.

## Executive Summary

Seven systems with radically different product shapes converge on the same architectural answer to this dimension's guiding question: the model (or caller) only ever issues *requests*; a runtime-owned choke point decides what actually executes. Where they diverge is in where the choke point sits, how the capability surface is enumerated, what the default posture is, and how much of the enforcement is proven under attack rather than merely documented.

The strongest performer is openai-agents-sdk (9/10), whose capability model is validated by adversarial test suites covering forged approvals, mount-credential spoofing, and sandbox escape attempts. Four systems score 8/10 (agent-framework, langfuse, opa, temporal): each has a clear, tested, explicit model with one identified seam — opt-in gating (agent-framework), AWS-coupled isolation (langfuse), unrestricted server-mode egress (opa), and allow-all defaults (temporal). openhands scores 7/10: a well-composed capability model with several deliberate fail-open edges. letta scores 6/10: an explicit, well-engineered capability *model* undermined by fragile operational boundaries — unauthenticated-by-default serving, header-asserted identity, and a local sandbox that inherits the server's entire OS environment.

The clearest cross-cutting weakness: **network egress policy is the least-developed trust boundary in every source.** Six of seven either lack it entirely, delegate it to operators or cloud providers, or implement it only as prompt text. The second-weakest layer is *default posture* — most systems ship permissive defaults and treat security as a configuration act.

## Core Thesis

Request/execution separation is a solved problem in design terms: every source implements some form of "intents are inert until a runtime-owned gate admits them." Maturity is instead determined by whether enforcement survives hostile conditions — forged approval responses, colliding tool names, deserialized state, misconfigured networks, and compromised adjacent tiers. The gap between a 9 (openai-agents-sdk) and a 6 (letta) is not architectural imagination but adversarial testing, credential discipline, and refusal to leave dangerous defaults silent. A second-order finding: capability systems that enumerate their surface as inspectable data (langfuse's policy map, temporal's API metadata, opa's capabilities JSON) age better than those that distribute authority across conventions.

## Approach Models

Three clusters emerge from the per-source reports, plus a distinctive fifth shape worth calling out separately.

### Cluster A — Choke-point interception (agent-framework, openai-agents-sdk)

Both SDKs concentrate authority in a single, well-defined invocation pipeline and compose enforcement as middleware/decorators around it. agent-framework routes every model intent through the function-invocation loop where batch classification reads `approval_mode` from the tool registry, not from the call (`python/packages/core/agent_framework/_tools.py:1763,1787`), wrapped in tiered middleware (agent/function/chat scopes, `python/packages/core/agent_framework/_middleware.py:1006-1166`). openai-agents-sdk places four named chokepoints in the run loop: pre-execution approval checks (`src/agents/run_internal/tool_actions.py:480-527`), caller verification (`src/agents/run_internal/tool_caller.py:47-66`), path-policy normalization (`src/agents/sandbox/workspace_paths.py:365-459`), and mount-credential provenance checks (`src/agents/sandbox/_mount_security.py:193-257`). In both, approvals are first-class control-plane state, not flags.

### Cluster B — Enumerated capability tables (langfuse, temporal, opa)

These systems make the capability surface explicit, static data that enforcement reads from. langfuse maintains an exhaustive ~80-tool policy map pairing every tool with an approval class and required RBAC scope, with type-level exhaustiveness forcing classification of new tools before they can be gated (`packages/shared/src/in-app-agent/server/mcpPolicy.ts:22-360`). temporal annotates ~120 API methods with Scope/Access metadata consumed by any authorizer (`common/api/metadata.go:70-216`). opa serializes its entire builtin power set into versioned JSON snapshots embedded per release (`v1/ast/capabilities.go:204-243`). The common property: "what can X do?" is answerable by reading one artifact, diffing it in CI, and auditing it in review.

### Cluster C — Execution-location containment (letta, with variants in langfuse and both SDKs)

Containment by choosing *where* code runs rather than evaluating permissions at call time. letta's executor factory maps tool type to execution venue — core tools in-process, custom tools through a Modal→E2B→local-subprocess chain, MCP proxied externally (`letta/services/tool_executor/tool_execution_manager.py:35-57`). The model is simple and auditable but binary: once an executor is selected, no further authorization applies inside it. langfuse refines this with isolation-by-provider (network-disabled dev Docker, capped Lambda MicroVMs in prod) and deliberately auto-approves sandbox tools because the provider contract is the boundary (`mcpPolicy.ts:410-421`). Both SDKs offer sandbox packages but do not mandate them.

### Distinctive shapes

- **Command delegation (temporal):** workers return proposed *commands* inside task completions; the history service validates and transactionally applies them or rejects them. Workers hold zero state authority — the purest realization of "request without possess" in the study (`common/tasktoken/token.go:9-61`; `common/rpc/interceptor/namespace_validator.go:233-257`).
- **RBAC inheritance (langfuse):** the agent's toolset is filtered by the *driving user's* project role before the model ever sees it — "the assistant never sees tools its user could not use manually" (`mcpPolicy.ts:451-470`), and approval "does not widen the user's project permissions" (`web/src/features/in-app-agent/README.md:231`). Authority flows from the principal, not from the agent.
- **Grant-shaping frontend (openhands):** the UI composes the entire grant — tool names, confirmation policy, security analyzer, skills, secret bindings — in one pure, unit-tested builder function (`src/api/agent-server-adapter.ts:1050-1231`), while executing only browser-native powers itself, after server acknowledgment (`src/services/child-conversation-launch.ts:451-458`).

## Pattern Catalog

### P1. Request/execution separation at a single choke point

- **Problem:** Model output is untrusted; anything it can invoke directly becomes attacker-controlled compute.
- **Demonstrated by:** All seven. Most explicitly: openai-agents-sdk ("everything — the model emits structured requests," execution always in SDK-owned paths, `docs/sandbox/guide.md:29`), temporal (workers propose commands, history service owns state), agent-framework (inert function-call intents crossing host-controlled interceptors).
- **Why it works:** One place to audit, test, and evolve enforcement; the batch classifier reads authority from the registry rather than the request, so a tool cannot declare itself safe.
- **Copy when:** Always. This is the load-bearing wall of every high scorer.
- **Risky/overkill:** Never, though the *placement* varies legitimately — SDK run loops, gRPC interceptors, or HTTP payload builders.
- **Evidence:** openai-agents-sdk `src/agents/run_internal/tool_actions.py:480-527`; temporal `service/frontend/fx.go:286-326`; agent-framework `dotnet/src/Microsoft.Agents.AI/ChatClient/ChatClientAgent.cs:62-69`.

### P2. Approvals as durable, resumable state — not callbacks

- **Problem:** Human-in-the-loop must survive process restarts, page reloads, and multi-client access without becoming a forgeable channel.
- **Demonstrated by:** agent-framework (approvals as registered content kinds flowing through history/sessions/checkpoints/workflows, `python/packages/core/agent_framework/_types.py:1273-1313`), letta (persisted `ApprovalRequestMessage` with typed `ApprovalReturn` resume, `letta/schemas/message.py:178-191`), openai-agents-sdk (`RunState.approve()/reject()` interruptions persisted as records, `src/agents/run_state.py:1255-1298`), langfuse (approvals as persisted events; continuation resolves tool name from history, "never client input," `web/src/features/in-app-agent/server/backgroundRunService.ts:396-400`).
- **Why it works:** Decisions become auditable facts bound to specific requests; the approval channel cannot be spoofed by model-generated content because resolution reads server-persisted state.
- **Copy when:** Any HITL flow expected to outlive a single process lifetime — which in practice means always.
- **Risky:** Only if resume-path validation is weaker than the original gate. openai-agents-sdk guards exactly this: restored state is re-validated and aliased approval identities rejected (`src/agents/run_state.py:300-529`).

### P3. Scoped standing approvals and identity-confusion defenses

- **Problem:** "Always allow tool X" rules leak across contexts — same-named tools on other servers, other callers, other namespaces.
- **Demonstrated by:** agent-framework (standing rules embed `server_label` so hosted same-named tools cannot inherit local approvals, `python/packages/core/agent_framework/_harness/_tool_approval.py:218-234`; forged standing approvals dropped in tests, `test_harness_tool_approval.py:708`), openai-agents-sdk (hosted-MCP sticky decisions keyed `(server_label, tool_name)` with legacy bare-name keys denied, `tests/test_run_context_approvals.py:245-267`), temporal (cross-namespace commands re-authorized against the target namespace, `common/authorization/interceptor.go:351-417`; inbound principal headers stripped unconditionally, `interceptor.go:156-158`).
- **Why it works:** Approval scope is bound to full provenance identity, not a mutable display name.
- **Copy when:** Any standing/auto-approve feature exists. This is the single most commonly attacked boundary in the study.
- **Risky:** Skipping it invites the documented failure mode both SDKs warn about — name collisions silently bypassing the approval boundary (agent-framework `ToolApprovalAgentOptions.cs:41-68`).

### P4. Capability enumeration as data

- **Problem:** Distributed, ad-hoc permission checks drift and become unauditable.
- **Demonstrated by:** langfuse (exhaustive policy map, type-enforced completeness, `mcpPolicy.ts:22-360`), temporal (single metadata table, `common/api/metadata.go:70-216` — with a happy asymmetry: unannotated APIs yield `ScopeUnknown` and the default authorizer denies them, `default_authorizer.go:55-56`), opa (versioned capability snapshots enabling `opa build --capabilities v0.22.0` compatibility targeting, `cmd/build.go:223-256`).
- **Why it works:** Turns security review into data review; makes additions impossible-to-forget (type errors or deny-by-default catch omissions); enables tooling (`opa capabilities --current`, `cmd/capabilities.go:36-103`).
- **Copy when:** The surface is enumerable and changes over time — i.e., almost always.
- **Risky:** When entries go stale relative to reality (temporal's Access field is explicitly "advisory," `metadata.go:9-13`); pair with exhaustiveness enforcement as langfuse does.

### P5. Fail-closed edges with explicit, named escape hatches

- **Problem:** Error paths, unknown values, and malformed input tend to fail open unless deliberately designed otherwise.
- **Demonstrated by:** opa (undefined authz decision → 500, empty `AllowNet` → deny all, `authorizer.go:134-138`, `http.go:402-407`); langfuse (malformed override header degrades to read-only; missing triggering user aborts the run — "must never implicitly mean 'trusted system'," `executeInAppAgentRun.ts:241-245`); openai-agents-sdk (unparseable approval-rule arguments force manual approval, `src/agents/util/_approvals.py:18-29`; serialized manifests raise TypeError on authority-expanding keys, `manifest.py:597-606`); agent-framework (unknown declarative approval modes map to AlwaysRequire, `McpServerToolApprovalModeExtensions.cs:20-28`; dangerous configs demand `acknowledgeUnsafe: true`, `LocalShellExecutor.cs:315-347`).
- **Why it works:** Failure lands in the safe state; opting out requires naming the risk in code, which shows up in review.
- **Copy when:** Everywhere ambiguity exists — unknown enums, parse failures, missing config, restoration of persisted state.
- **Counter-example:** openhands fails open on tool discovery (no advertised `usable_tools` ⇒ allowed, `src/api/agent-server-compatibility.ts:149-155`) and pays for it in its own rating rationale.

### P6. Secrets indirection and redaction at boundaries

- **Problem:** Credentials adjacent to model execution leak through prompts, logs, telemetry, error tracebacks, and sandboxes.
- **Demonstrated by:** openhands (LookupSecret URL pointers resolved server-side at spawn; UI sees only masked/Fernet forms, `src/api/agent-server-adapter.ts:995-1000`), langfuse (ephemeral per-run `isInAppAgentKey` minted atomically and deleted at terminal state, `executeInAppAgentRun.ts:381-399`), openai-agents-sdk (mount failures rebuilt as sanitized exceptions with traceback locals scrubbed, `_mount_security.py:487-557`; end-to-end test proves the sandbox cannot read client credentials, `integration_tests/security/test_local_sandbox_isolation.py:114`), letta and agent-framework (masked `Secret`/`SecretString` reprs, telemetry stripping), temporal (payloads opaque; encryption delegated client-side to DataConverters).
- **Why it works:** The model and its execution context handle references, not values; blast radius of any single compromise shrinks to one run.
- **Copy when:** Any credential could appear in a context the model influences.
- **Risky:** Indirection adds latency and infrastructure (langfuse accepts a DB transaction per run for this); half-measures are worse than none — letta's local sandbox undermines its own `Secret` hygiene by copying `os.environ` wholesale (`letta/services/tool_sandbox/base.py:487`).

### P7. Revalidation-at-use over trust-at-enqueue

- **Problem:** Cached grants, enqueued payloads, and restored state reflect decisions made under conditions that may no longer hold.
- **Demonstrated by:** langfuse ("nothing from enqueue time is trusted"; stored grants rebuilt against current roles per run, `executeInAppAgentRun.ts:196-257, 335-339`), openai-agents-sdk (state restore re-validates approval payloads, refuses malformed/aliased identities), agent-framework (`ApprovalResponseBindingChatClient` binds inbound responses to framework-recorded requests so model-injected content cannot forge approvals, `dotnet/src/Microsoft.Agents.AI/ChatClient/ApprovalResponseBindingChatClient.cs:158-277`), temporal (task-token namespace takes priority over request namespace, `namespace_validator.go:233-257`).
- **Why it works:** Role changes, revocations, and stale authority expire at the moment of use, not at the moment of grant.
- **Copy when:** Any async queue, checkpoint/restore, or long-lived grant mechanism exists.
- **Risky:** Adds per-use cost; langfuse mitigates with dedup/single-flight cleanup.

### P8. Honesty about non-boundaries

- **Problem:** Integrators overtrust mechanisms that look like isolation but aren't.
- **Demonstrated by:** agent-framework (LocalCodeAct README states it is *not* a sandbox; FileSystemAgentFileStore documented "not a sandbox," `dotnet/src/Microsoft.Agents.AI.LocalCodeAct/README.md:5-14`), openai-agents-sdk (instruction-based remote-mount injection defense labeled advisory, paired with hard read-only enforcement, `remote_mount_policy.py:8-46`), langfuse (process-group kill acknowledged as best-effort with descendants able to escape, `server.ts:402-404`), openhands (unsandboxed PDF iframe carries inline residual-risk rationale, `file-content-viewer.tsx:140-158`).
- **Why it works:** Written-down deviations prevent silent assumption drift; they also document the compensating control.
- **Copy when:** Any mitigation is advisory, partial, or environment-dependent.

## Key Differences

- **Default posture.** agent-framework runs registered tools ungated until a developer attaches middleware (`ChatClientAgent.cs:66-68`; Python `approval_mode="never_require"` default, `_tools.py:331-332`); temporal's entire authz subsystem is a no-op allow-all until configured (`noop_authorizer.go:12-14`); letta serves unauthenticated by default (`app.py:797-799`). langfuse is the outlier: its exhaustive table means mutating tools require approval by default and unknown classifications deny (`registry.ts:188`). The difference is product position — SDKs optimize developer time-to-first-success; embedded product assistants owe duty-of-care to end users who never read configuration.

- **Who defines policy.** temporal and opa push policy fully outward (pluggable Authorizer; user-supplied Rego at `data.system.authz`, `authorizer.go:107-227`). The SDKs embed policy mechanisms but let developers choose activation. langfuse fixes policy in-product and inherits authority from RBAC. None of these is strictly better; they answer to different principals (operators vs developers vs end users).

- **Identity strength.** openai-agents-sdk verifies caller identity structurally (`allowed_callers` defaulting to direct-only, `tool_caller.py:47-66`) and binds approvals to call IDs to prevent replay. temporal strips spoofable headers unconditionally and validates JWTs against pinned algorithms/JWKS. letta trusts a caller-supplied `user_id` header (`dependencies.py:38-61`); opa deliberately treats bearer tokens as opaque extracted identities (`identifier/token.go:24-31`); openhands shares one session key across browser, agent, and automation tiers (`dev-with-automation.mjs:1202-1234`). Same dimension, three orders of magnitude of rigor.

- **Token integrity.** temporal's task tokens and Nexus callback tokens are unsigned protobuf/base64 blobs whose integrity rides entirely on TLS and URL unguessability (`serializer.go:15-26`; `callback_token.go:23-33`); langfuse hashes keys at rest and scopes them per run. When authority travels as a token, cryptographic binding is the difference between "network-compromise-tolerant" and "network-compromise-fatal."

- **Sandbox honesty vs sandbox reliance.** agent-framework ships multiple graded options and labels which are *not* boundaries; langfuse concentrates all code-execution risk in one provider contract and names the weak option `dangerous-docker`; letta's fallback silently runs agent-authored code as a host subprocess with inherited secrets (`base.py:487`) — the same spectrum ends at opposite poles of disclosure.

- **Frontend vs runtime enforcement.** openhands demonstrates that a UI tier can still own real trust work — grant composition, content sanitization with XSS regression tests, replay ledgers — provided it treats itself as a composer delegating execution (`no-direct-agent-server-calls.test.ts:7-11` enforces this architecturally in CI).

## Tradeoffs

**Opt-in gating vs safe-by-default** (agent-framework, temporal, letta, opa vs langfuse)
- Benefit: zero-friction onboarding; samples work immediately; no policy engine forced on users who don't need one.
- Cost: naive deployments run fully empowered; security becomes a configuration act that misconfiguration silently undoes.
- Best fit: developer tools with competent operators; documentation-heavy mitigation (temporal's startup warning, opa's misconfiguration detection).
- Failure mode: internet-exposed unconfigured instances — temporal's own report calls this out as "accepts everything as system admin."
- Alternative: langfuse's exhaustive-table default (classify-before-ship), viable when the surface is product-owned.

**Isolation-by-provider vs in-process convenience** (langfuse, openai-agents-sdk sandboxes vs plain FunctionTools / letta LOCAL)
- Benefit: strong containment (fresh VM per run, killed after; network-disabled containers) without approval friction.
- Cost: concentrated trust in one provider contract; AWS coupling (langfuse `config.ts:42-64`); dev/prod asymmetry (openai-agents-sdk notes macOS/Linux devs often run weaker isolation than they deploy, `docs/sandbox/guide.md:73`).
- Failure mode: provider misconfiguration converts directly into arbitrary code execution with workspace privileges — langfuse's stated tradeoff.
- Alternative: letta's local subprocess maximizes compatibility but inherits the server environment — the study's clearest negative example.

**Expressiveness vs containment** (opa, temporal)
- Benefit: stored policies get `http.send`; real admission control needs egress; plugin authorizers accept enterprise IdP integration.
- Cost: anyone who can upload a policy holds egress capability; the authz guard is mutable through the same door it guards (authz-policy rewrite escalation, `authorizer.go:117-119`).
- Best fit: infrastructure with external network controls available.
- Failure mode: server-mode egress unbounded by default (no `--capabilities` on `opa run`); cloud-metadata reachability.
- Alternative: ad-hoc query restriction — opa already compiles submitted queries with `http.send` unsafe while stored policies retain it (`server.go:104`), proving selective restriction is implementable.

**Enumeration rigidity vs auditability** (langfuse/temporal/opa vs convention-based systems)
- Benefit: diffable, CI-checkable, tooling-inspectable power sets; forced classification of new surface.
- Cost: maintenance burden; temporal's Access field needs per-API annotation discipline; langfuse pays a transaction per run for its credential layer.
- Failure mode: staleness — advisory metadata that no longer matches behavior is worse than none, because it manufactures false confidence.
- Alternative: agent-framework's compositional middleware trades central auditability for flexible assembly.

**Shared credentials vs per-actor differentiation** (openhands vs langfuse)
- Benefit: one key simplifies ops and local development enormously.
- Cost: the agent's blast radius against the automation backend equals the user's; no tier-scoped revocation.
- Best fit: single-user desktop deployments.
- Failure mode: any XSS-reachable storage (localStorage) holding a full-authority key.
- Alternative: langfuse's ephemeral per-run keys with deletion guards (`apiKeys.ts:124-134`).

## Decision Guide

Choosing between the main approaches found in the sources:

- **Building an SDK or framework?** Follow agent-framework / openai-agents-sdk: one invocation chokepoint, middleware composition, per-tool approval declaration, approvals as resumable state. Budget most of your security effort for adversarial tests of the approval state machine — it is what separates 9 from 8 here. Accept opt-in defaults but invert them for high-risk built-in categories (the shell/file precedent in agent-framework).
- **Building a product-embedded assistant acting for end users?** Follow langfuse: inherit authority from the driving user's RBAC, classify every tool exhaustively before it can be gated, add an independent enforcement layer at the credential level so policy bugs alone cannot grant mutation, and revalidate everything at claim time.
- **Building a multi-tenant server running arbitrary user tools?** Learn from letta's model but not its defaults: keep the declarative rules DSL and durable approval protocol; refuse its LOCAL-sandbox environment inheritance and header identity. Require an isolated executor before enabling custom tools in shared mode.
- **Building a workflow/orchestration layer where workers execute user code?** Follow temporal: workers propose commands, the state owner validates and applies; enumerate the API surface as annotated metadata; make unannotated mean denied. Sign your delegation tokens — temporal's unsigned tokens are its own flagged debt.
- **Need a general-purpose, auditable permission substrate?** Adopt opa's two-axis insight: restrict the language surface (what functions exist) AND the runtime targets (what hosts may be contacted), and serialize the power set as versioned data. Wire the restriction into your long-running mode, not just batch commands — opa's server-mode gap is the cautionary seam.
- **Rendering agent-produced content in a web UI?** Follow openhands: sanitize against an explicit schema after raw conversion, script-less sandboxed iframes for previews, replay ledgers for non-idempotent client actions, and corrective-feedback validation that turns policy violations into model-guidance rather than user-facing errors.

Rule of thumb distilled from all seven: **grant at composition time, enforce at execution time, revalidate at use time.** Systems that collapse these into one moment accumulate their worst failure modes.

## Practical Tips

**Patterns to copy**

1. Make approvals durable records bound to full provenance (server label + tool name + call ID), and drop anything that doesn't match a recorded pending request (agent-framework, openai-agents-sdk, langfuse).
2. Enforce exhaustiveness on capability classifications via types or startup assertions so new surface cannot ship unclassified (langfuse `mcpPolicy.ts:22-26`).
3. Add an enforcement layer *below* your policy layer — a credential or registry check that would stop abuse even if policy logic were buggy (langfuse's `isInAppAgentKey` + `canCallTool`).
4. Convert malformed requests into structured corrective feedback returned to the model, not thrown at the user (openhands `child-conversation-launch.ts:505-528`).
5. Annotate what is *not* a boundary next to what is (agent-framework's honesty annotations).
6. Test the hostile paths explicitly: forged approvals, name collisions, aliased identities, deserialized-state injection, subclass spoofing (openai-agents-sdk's test suites are the benchmark).
7. Strip spoof-prone identity inputs unconditionally, even when enforcement is disabled (temporal's `StripPrincipal`).

**Patterns to avoid or delay**

1. Standing auto-approval keyed on bare tool names — both SDKs document this as a live bypass vector; ship qualified identities from day one.
2. Instruction-only security policies without an enforcement backup (openhands' advisory network map; writable remote mounts guarded only by prompt text in openai-agents-sdk).
3. Ambient environment inheritance for executed code — letta's `os.environ.copy()` is the cautionary tale; build explicit env gatherers instead.
4. Convenience skip-flags in supply-chain paths (opa's `--skip-verify` concentrating downgrade risk in deploy scripts).

**Decision rules**

- If a capability is irreversible or billable → require durable human approval regardless of how benign the annotation looks (openhands' child-conversation gap).
- If code originates outside your trust domain → choose its execution venue by containment grade, and degrade visibly when the good venue is unavailable (never silently, as letta's E2B→LOCAL fallback does).
- If authority must travel (tokens, pointers, manifests) → bind it cryptographically or to server-side records; transport security alone is a borrowed guarantee.
- If you cannot enumerate the surface → you cannot secure it; enumeration-as-data is the prerequisite investment.

## Anti-Patterns / Caution Signs

Signs the capability/trust area is going brittle, from concrete incidents in the sources:

- **Name-based identity anywhere in the approval path.** Auto-approval collisions documented in agent-framework (`LocalShellExecutor.cs:331-337`) and defended against with regression tests in openai-agents-sdk. If your rules match on display names, you have a latent privilege-widening bug.
- **Fail-open discovery or availability checks.** openhands' `usable_tools`-absent-means-allowed is flagged in its own rating rationale. Any "if metadata missing, assume yes" branch deserves scrutiny.
- **Vestigial or dead auth surfaces.** letta's `/auth` endpoint calls methods that no longer exist (`auth/index.py:36` vs `server.py:114`) — half-built trust paths confuse integrators and rot silently.
- **Self-referential trust anchors without compensation.** opa's authz policy lives in the store it protects; acceptable only with external proxies/signed bundles in place. Ask: what happens if the guard rewrites itself?
- **Silent isolation downgrades.** letta falling back E2B→LOCAL without surfacing the change; openhands degrading `worktree`→`shared` with a textual warning. Every containment downgrade should be loud and, ideally, blocking.
- **Undifferentiated credentials across trust tiers.** One key for browser, agent, and automation (openhands) means no tier-scoped revocation and equal blast radius everywhere.
- **Enforcement that trusts its own persisted inputs.** If resume/restore paths validate less strictly than first-run paths, attackers target persistence (both SDKs found and fixed such gaps; your system likely has equivalents).
- **Security posture documented but not enforced.** temporal's allow-all default mitigated "purely documentary"; openhands' network policy existing only as prompt text. Documentation is not a boundary.
