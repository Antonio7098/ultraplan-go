## Executive Summary

Nine sources, all with full evidence, scored between 7 and 9 on this dimension — the tightest band of any dimension studied so far, which itself is a finding: **every serious agent harness, runtime, or engine now treats causal linkage as a first-class design concern**, not a logging afterthought. All nine embed lineage directly in their primary data structures (typed contents, messages, checkpoints, events, decision records), and all nine can answer the dimension's guiding question — *can you trace a final answer back to the tool call that provided each fact?* — affirmatively **at event/tool-call granularity**, via shared call identifiers (`tool_call_id`, `call_id`, `ScheduledEventId`, `action_id`).

What separates a 7 from a 9 is not whether linkage exists but **where lineage is anchored and what happens at the seams**:

- **temporal (9)** makes lineage identical with execution: an append-only event log where a factory constructs every event with its cause references baked in, completions are validated against causally-addressable task tokens, and worker build IDs are stamped and searchable (`service/history/historybuilder/event_factory.go:26-1118`, `common/tasktoken/token.go:22-58`). It is the only source rated in the "proven under failure or scale" band.
- **A middle band of 8s** (langfuse, langgraph, letta, openai-agents-sdk, pydantic-ai) each anchor lineage durably somewhere — ClickHouse columns, a checkpoint DAG, relational foreign keys, serializable run state, or the serialized message history — and each loses points for one class of seam: heuristic extraction (langfuse), pruning that silently severs chains (langgraph), nullable foreign keys with legacy bypasses (letta), exports that drop inputs and approvals without actors (openai-agents-sdk), and durability delegated entirely to callers (pydantic-ai).
- **The 7s** (agent-framework, opa, openhands) have explicit, tested models but several provenance mechanisms are opt-in, silently lossy, or bound by heuristics rather than identifiers — privacy-gated argument capture and hand-parsed traceparents (agent-framework), unpersisted explain traces and unlogged authorization decisions (opa), and id-less approval requests forcing client-side guessing (openhands).

Three absences are universal across all nine sources: **fact-level citation inside free-text answers** (no system maps prose spans to their source observations), **cryptographic/tamper-evident chaining** of inputs to outputs, and **weight/snapshot-level model-version tracking** (everything tracks model-name strings or build IDs, not immutable versions).

## Core Thesis

**Lineage quality is determined less by whether a system records causal links than by three structural choices: where the lineage lives (execution log, database schema, in-memory data model, ingestion pipeline, or client reconstruction), what identity scheme joins causes to effects (framework-minted addresses vs. reused provider-native IDs), and how transformation boundaries are treated.**

Across these nine sources, the convergent core is remarkably stable: one join key per cause-effect pair, lineage stamped at centralized choke points, raw payloads retained beside normalized views. The divergent parts are almost perfectly explained by product shape:

- Engines and platforms that own persistence (temporal, letta, langfuse) build lineage into durable schemas and can guarantee it; their failure modes are erosion vectors (nullable FKs, dangling references, async indexes).
- Libraries that hand results back to callers (pydantic-ai, openai-agents-sdk, agent-framework, langgraph) put lineage on transferable objects and make it survive serialization; their failure modes are opt-in depth and dependence on host discipline.
- A frontend consuming someone else's stream (openhands) reconstructs chains programmatically and proves completeness before exporting — but is hostage to the weakest identifier in the protocol (its id-less confirmation request).
- A policy engine (opa) flattens everything into self-contained audit events; its failure modes are what falls outside the flat record (unpersisted traces, unlogged authz decisions).

And the recurring failure mode in every source is the same shape: **not missing links, but silently severed ones at transformation boundaries** — pruning (langgraph delta reconstruction), truncation (letta tool returns), redaction and size limits (opa cache dropping), malformed correlation strings (agent-framework traceparent parsing), pagination degradation (openhands chat history), discarded buffered events (temporal signal links). The mature systems (temporal, pydantic-ai, opa, langfuse) make every such boundary either self-documenting (recorded masks/pointers), marked (synthesized-return metadata), counted (Prometheus drop counters), or fail-closed (export-time completeness proofs). The weaker ones degrade quietly.

## Approach Models

### Model A — Event sourcing: lineage *is* the execution model (temporal)

**Where implemented.** The history service. Every workflow mutation is a `HistoryEvent` produced exclusively through `EventFactory`, whose methods embed cause references per event type (`service/history/historybuilder/event_factory.go:26-1118`); event IDs are allocated sequentially per run (`event_store.go:58-62`).

**Main mechanism.** Effect events carry explicit back-references: activity completions carry `ScheduledEventId` + `StartedEventId`; command-derived events carry `WorkflowTaskCompletedEventId`; terminal events carry the completing task's ID and result. Workers dispatch against opaque task tokens embedding `(namespaceID, workflowID, runID, scheduledEventId, startedEventId)` (`proto/internal/temporal/server/api/token/v1/message.proto:39-56`), so completions are provably tied to the exact invocation (`respondactivitytaskcompleted/api.go:60-110`).

**Supporting mechanisms.** Sequential-ID allocation resolved through buffered batches (`wireEventIDs`, `event_store.go:381-454`); cross-run continuation fields (`ContinuedExecutionRunId`, reset fork points, branched `VersionHistories`); typed size-limited `Link` vocabulary (`common/links/validator.go:17-88`); worker build-ID stamps surfaced as searchable attributes (`worker_versioning.go:93-139`); vector-clock consistency leases rejecting stale attributions; dual-plane persistence (authoritative history + queryable visibility + post-close archival).

**Standout patterns.** Factory-enforced attribution makes forgetting a causal field impossible per event type. Self-healing chains: if a Started event is missing at completion time, the server fabricates it rather than emitting an orphan completion (`api.go:87-105`). Root anchoring (`RootWorkflowExecution`) enables flat traversal of deep child trees.

**Where it would not fit.** Systems that cannot afford strict per-run total ordering (all writes serialize through one shard transaction) or full payload retention. This model buys perfect attribution with write-throughput and storage costs.

### Model B — Durable relational/checkpoint lineage (letta, langgraph)

**Where implemented.** letta: ORM foreign keys `messages.step_id/run_id`, steps recording full model/provider config, provider-trace payloads keyed by step (`letta/orm/message.py:48-71`, `letta/orm/step.py:34-52`); all stamping funneled through one choke point (`_checkpoint_messages`, `letta/agents/letta_agent_v3.py:758-786`). langgraph: an immutable checkpoint DAG where every snapshot carries `parent_config`, `source`, `step`, `parents`, and `run_id`, with per-task writes persisted under `(thread_id, checkpoint_ns, checkpoint_id, task_id)` (`libs/checkpoint/langgraph/checkpoint/base/__init__.py:38-62`; Postgres PK at `libs/checkpoint-postgres/langgraph/checkpoint/postgres/base.py:66-88`).

**Main mechanism.** letta: database-enforced structure plus REST traversal (`/runs/{id}/steps/messages/trace`). langgraph: deterministic identity — task IDs are hashes of `(checkpoint id, namespace, node, triggers)` so crash/resume recomputes the same addresses, letting pending writes, interrupt IDs, and resume maps reconnect with no registry (`libs/langgraph/langgraph/pregel/_algo.py:613-623`).

**Supporting mechanisms.** letta: monotonic `sequence_id` ordering, serialization that *raises* when `tool_call_id` is missing (`schemas/message.py:1460-1468`), cancellation writing denial records for every pending call, prefix-typed IDs, git-style memory commits with parent SHAs. langgraph: special write channels with reserved negative indices so errors/interrupts/resumes get identical durability (`base/__init__.py:788-795`); hashed interrupt IDs matched across `INTERRUPT`/`RESUME` writes; a public `get_state_history` audit API.

**Tradeoffs.** Both pay write amplification for attribution granularity (every task's writes stored separately; run-existence validated per insert). Both show the erosion risk of durable-but-mutable schemas: letta's nullable `SET NULL` FKs and commented-out validators; langgraph's documented silent-empty reconstruction after naive pruning.

### Model C — In-process typed ledger on transferable objects (pydantic-ai, openai-agents-sdk, agent-framework)

**Where implemented.** On the data objects themselves. pydantic-ai: every `ModelRequest`/`ModelResponse` carries `run_id`/`conversation_id` stamps, provider response IDs, and model names; one `tool_call_id` joins calls, returns, retries, approvals, deferred results, and the final structured output (`pydantic_ai_slim/pydantic_ai/messages.py:2539-2618`, `_deferred.py:26-96`, `result.py:1031-1044`). openai-agents-sdk: every run item names its producing agent; a contextvar-nested span tree gives each operation a typed payload; approvals live in serializable `RunState` hardened by SHA-256 semantic fingerprints over invocation arguments (`src/agents/items.py:97-106`, `src/agents/tracing/spans.py:289-324`, `src/agents/_tool_invocation.py:155-219`). agent-framework: linkage keys are fields on typed `Content` variants — `call_id` pairing, approval responses embedding the entire requested function call, citation annotations, and per-message `_attribution` markers (`python/packages/core/agent_framework/_types.py:474-589`, `_sessions.py:624-698`).

**Main mechanism.** Make lineage travel with the object: anything that serializes the transcript (session store, history provider, caller's own persistence) carries the causal graph without a join table. pydantic-ai adds a repair pipeline that keeps pairing integrity under context eviction, marking synthesized returns with `SYNTHESIZED_TOOL_RETURN_METADATA_KEY` (`_agent_graph.py:2771-2813`).

**Supporting mechanisms.** Fail-loud integrity: duplicate `tool_call_id`s abort processing, reused `run_id`s raise `UserError`, unknown approval keys raise `ValueError` (pydantic-ai); reused provider call IDs for different invocations raise `ModelBehaviorError` (openai-agents-sdk). Trace identity survives suspension via persisted `TraceState` reattachment (openai-agents-sdk). Workflows propagate W3C trace contexts inside inter-executor messages and express fan-in causality as OTel span *links* (agent-framework, `observability.py:3223-3280`).

**Tradeoffs.** Zero infrastructure and automatic serializability — but durability is the caller's job, deep provenance (content payloads) is privacy-gated by default in two of three, and there is no framework-owned audit sink anywhere in this cluster.

### Model D — Denormalized recording with server-side reference resolution (langfuse, opa)

**Where implemented.** The ingestion/persistence layer. langfuse materializes each causal relationship as first-class columns on the record — `trace_id`/`parent_observation_id`, `prompt_id/name/version`, `provided_model_name` vs `internal_model_id`, tool-call arrays, score references (`packages/shared/clickhouse/migrations/unclustered/0002_observations.up.sql:3-17`, `0033_add_tool_call_columns.up.sql`). opa denormalizes one flat `EventV1`: `decision_id`, echoed input, result, path/query, bundle revisions, W3C trace/span IDs (`v1/plugins/logs/plugin.go:49-76`).

**Main mechanism.** Clients send weak references (prompt name+version, model names); the platform resolves them to strong IDs at ingestion and **stores both halves** (`IngestionService/index.ts:320-333,405-408`). Provenance through transformations is preserved by duality: `provided_usage_details` kept beside enriched values; dataset items snapshotted immutably into run items at execution time (`0024_dataset_run_items.up.sql:18-27`).

**Supporting mechanisms.** opa: post-hoc lineage filtering walks `ParentID` chains of eval traces (`v1/topdown/lineage/lineage.go:48-86`); non-deterministic builtin calls journaled input→output for replay; masking records erased/masked JSON pointers onto the event itself; oversized uploads drop the ND cache first with a Prometheus counter. langfuse: schema-enforced pairing (`promptName`+`promptVersion` together or not at all), bitemporal dataset item versioning, append-only approval-decision events, admin replay of raw ingested events.

**Tradeoffs.** Reads are O(1)-filterable and each record independently auditable — but renames/deletions leave stale copies with no cross-store FK protection, extraction from unstructured payloads is best-effort, and (for opa) the richest view (explain traces) evaporates with the request.

### Model E — Client-side reconstruction from a wire event stream (openhands)

**Where implemented.** A TypeScript frontend over a Python agent-server's persisted event stream. The wire schema encodes causal edges explicitly: `ObservationEvent.action_id`/`tool_call_id`, `ActionEvent.llm_response_id`, `CondensationEvent.forgotten_event_ids`, `SystemPromptEvent` persisting the offered tool list (`src/types/agent-server/core/events/observation-event.ts:9-39`, `action-event.ts:15-66`, `system-event.ts:5-25`).

**Main mechanism.** The client rebuilds chains programmatically — the transcript exporter builds an `actionsById` map and resolves every observation to its producing action — and refuses to export unverifiable history: cursor-cycle detection, independent event-count cross-check, strict-pagination rethrow (`src/utils/transcript-export/index.ts:275-277`, `load-complete-events.ts:85-124`).

**Tradeoffs.** Any consumer can reconstruct chains from one append-only API — but the protocol's weakest identifier bounds the whole system: the confirmation request carries only `{accept}` with no action id, so the UI binds approvals heuristically to "the last agent event in the store" (`conversation-confirmation-buttons.tsx:30-36`).

## Pattern Catalog

### P1. Lineage embedded in the primary data model

**Problem.** Separate audit tables drift from the data they describe and break under serialization.
**Sources.** All nine — the single most universal pattern in the study.
**Why it works.** Wherever the object goes (session store, checkpoint, caller's persistence, exported JSON), its causal graph goes too. agent-framework's serialized transcripts thus *are* causal graphs; pydantic-ai's message dump is replayable lineage; temporal needs no audit table because the log *is* the state.
**When to copy.** Always, as a baseline. **When risky.** Never by itself sufficient for platforms — without a durable store or query surface (the libraries' shared weakness) lineage remains latent.
**Evidence.** `python/packages/core/agent_framework/_types.py:474-589`; `pydantic_ai_slim/pydantic_ai/messages.py:2539-2618`; `service/history/historybuilder/event_factory.go:26-1118`.

### P2. One canonical join key per cause-effect pair

**Problem.** Distributed provenance requires cheap, unambiguous stitching of effects to causes.
**Sources.** pydantic-ai (uniform `tool_call_id` across calls, returns, retries, approvals, output tools, OTel spans); letta (OpenAI-native `tool_call_id`, required at serialization); agent-framework (`call_id` mirroring constructors); temporal (sequential event IDs + `(scheduled, started)` pairs); openhands (`action_id`/`tool_call_id`).
**Why it works.** Dict-lookup reconstruction; uniformity means new linkage types reuse the existing key. pydantic-ai's `FinalResult.tool_call_id` even ties the final output to the exact producing invocation (`result.py:1041-1042`).
**When to copy.** Whenever a result must be attributable to its request. **When risky.** When the key is *provider-native* and recycled — see P3 and Tradeoffs.
**Evidence.** `pydantic_ai_slim/pydantic_ai/messages.py:1308,2173`; `letta/schemas/message.py:287-295`; `src/types/agent-server/core/events/observation-event.ts:9-39`.

### P3. Deterministic / stable identity for replay resilience

**Problem.** Resume, retry, and replay must reconnect lineage without a central registry of "what happened."
**Sources.** langgraph (`uuid6(clock_seq=step)` checkpoints; xxhash task IDs over causal coordinates, `_algo.py:613-623`; `ensure_message_ids` stamped pre-serialization after the team hit double-counting bugs, `_messages.py:426-445`); temporal (sequential IDs; Nexus completion tokens embedding the original scheduled event's `request_id` so resets stay completable, `token/v1/message.proto:90-92`); letta (OTIDs bit-packing chunk index into the message UUID low bits); pydantic-ai (UUID7 run/conversation IDs).
**Why it works.** Re-execution recomputes the same addresses, so pending writes and resume values find their owners after crashes.
**When to copy.** Any resumable/replayable loop. **When risky.** Bit-packing trades fan-out limits (letta caps at 128 chunks/message, raising `ValueError` beyond); hash-based identity couples you to coordinate stability.
**Evidence.** `libs/langgraph/langgraph/pregel/_checkpoint.py:206-214`; `letta/schemas/message.py:2648-2665`.

### P4. Fail-loud binding-integrity enforcement

**Problem.** Silently mis-bound results (duplicate/reused IDs, forged approvals) corrupt audits invisibly.
**Sources.** pydantic-ai (duplicate call IDs abort before execution, `_tool_execution.py:405-419`; unknown approval keys raise); openai-agents-sdk (call-ID reuse raises `ModelBehaviorError`, `run_context.py:327-332`; fingerprints prevent approval rebinding); letta (`TypeError` when a tool return lacks `tool_call_id`); temporal (task-token validation rejects stale/not-found completions); langfuse (schema refinement requiring prompt name+version paired).
**Why it works.** Converts silent corruption into immediate, diagnosable failure at the cheapest possible moment.
**When to copy.** Everywhere binding ambiguity is possible. **Cost.** Hard failures on provider quirks require companion repair strategies (P6).
**Evidence.** `src/agents/run_context.py:304-333`; `letta/schemas/message.py:1460-1468`.

### P5. Approvals bound by value or verified key

**Problem.** An approval must be provably about one action, surviving resume, and resistant to forgery/mis-binding.
**Sources (strongest).** agent-framework: approval responses embed the entire requested function call plus request ID; middleware rejects forged standing approvals whose metadata doesn't bind to an observed request (`tests/core/test_harness_tool_approval.py:708-742`). openai-agents-sdk: decisions serialized into `RunState` with SHA-256 fingerprints over semantic fields, surviving process restarts (`run_state.py:1326-1339`). letta: `ApprovalReturn` *requires* `tool_call_id`; requests/responses persist as messages; cancellation fabricates denials for all pending calls (`run_manager.py:694-748`). langfuse: append-only decision events naming `toolCallId` and deciding user. langgraph: hashed interrupt IDs matched across `INTERRUPT`/`RESUME` pending writes.
**Weakest observed.** openhands: `{accept}` with no id, UI guesses the target.
**Why it works.** Value-binding (embedding the action) or verified-key binding (fingerprint/hash) removes ambiguity even out-of-band.
**When to copy.** Any human-in-the-loop flow. **Gap to note.** Even strong sources mostly omit *actor identity + timestamp* on the decision record (openai-agents-sdk explicitly; langfuse is the exception with `decidedByUserId`).
**Evidence.** `python/packages/core/agent_framework/_types.py:1293-1362`; `packages/shared/src/in-app-agent/approvalEvents.ts:7-28`.

### P6. Repair-with-markers over reject-or-silence for externally broken chains

**Problem.** Context eviction, hand-built histories, and provider quirks orphan calls/results; failing hard kills runs, staying silent corrupts them.
**Sources.** pydantic-ai: ordered-walk detector drops orphaned results and synthesizes returns for dangling calls, each marked `SYNTHESIZED_TOOL_RETURN_METADATA_KEY` (`_agent_graph.py:2702-2813`; repaired-chain tests at `tests/test_transcript_repair.py:749,784`). temporal: fabricates a missing Started event rather than emitting an orphan completion (`api.go:87-105`). Contrast the silent variants: langgraph warns in docs that pruned ancestors make delta state "silently reconstruct as empty"; agent-framework's malformed traceparent yields link-less spans asserted as normal.
**Why it works.** Preserves run availability while keeping downstream consumers able to distinguish real from repaired evidence.
**When to copy.** When chain breakage comes from outside your control. **When risky.** Repair logic itself becomes high-blast-radius (agent-framework flags exactly this class of code in `python/AGENTS.md:60-64`).
**Evidence.** `pydantic_ai_slim/pydantic_ai/_agent_graph.py:2771-2813`; `libs/checkpoint/langgraph/checkpoint/base/__init__.py:374-415`.

### P7. Centralized stamping choke points

**Problem.** Per-call-site lineage stamping guarantees eventual omission.
**Sources.** temporal (EventFactory is the only event constructor); letta (`_checkpoint_messages` is documented as "ONLY place where messages are persisted," force-stamping `run_id`/`step_id`, `letta_agent_v3.py:758-786`); pydantic-ai (`fill_run_metadata` sole owner of the framework-tracked field list, preserving producer-supplied values, `_utils.py:560-569`); langgraph (single metadata merge point `get_checkpoint_metadata`); openai-agents-sdk (contextvar auto-nesting makes parenting a runtime invariant, not caller discipline).
**Why it works.** New lineage fields need exactly one edit; individual paths cannot forget.
**When to copy.** Always. **Failure mode.** Choke-point bypass: letta's manual compaction endpoints persist summaries with `run_id=None, step_id=None` precisely because they route around the choke point (`conversations.py:1128`).
**Evidence.** `letta/agents/letta_agent_v3.py:758-786`; `pydantic_ai_slim/pydantic_ai/_utils.py:560-569`.

### P8. Resolve soft references at ingestion; store both halves

**Problem.** Clients hold weak references (names, versions) that rot as registries change.
**Sources.** langfuse resolves `promptName`+`promptVersion` to a concrete prompt row at ingest and persists `prompt_id` alongside the original name/version (`IngestionService/index.ts:320-333,405-408`); likewise client model names vs matched `internal_model_id`. opa snapshots bundle revisions into each event at decision time.
**Why it works.** Chains survive later renames/deletions; the weak reference documents intent, the strong ID enables joins.
**When to copy.** Any pipeline accepting third-party identifiers. **Failure mode.** Unresolved lookups degrade to sentinel values (`prompt_id: ""` on miss, `index.ts:406`) — prefer nullable semantics plus a data-quality metric.
**Evidence.** `worker/src/services/IngestionService/index.ts:320-333`.

### P9. Raw-vs-normalized duality

**Problem.** Normalization loses provider fidelity exactly when audits need it most.
**Sources.** agent-framework (`raw_representation` on every content/message/response, accumulated through merges, `_types.py:1668-1679`); langfuse (`provided_*` columns adjacent to computed ones); letta (full `request_json`/`response_json` per step); openhands (verbatim LLM `tool_call` retained beside parsed action because the two can diverge, `action-event.ts:42-49`); temporal (full inputs embedded in start events); opa (echoed input AST + raw).
**Why it works.** Enrichment/redaction/merging become auditable transformations rather than lossy ones.
**Cost.** Storage growth — mitigated in letta by backend selection and metadata-only variants, in opa by size-limit degradation with counters.
**Evidence.** `packages/shared/clickhouse/migrations/unclustered/0002_observations.up.sql:19-23`; `letta/schemas/provider_trace.py:46-66`.

### P10. Explicit, observable degradation at lineage boundaries

**Problem.** Size limits, privacy modes, and failures will drop provenance; the question is whether anyone finds out.
**Sources (good).** opa: ND-cache dropped first under upload limits, incrementing a counter — "provenance loss is explicit, not silent" (`encoder.go:179-208`); mask operations record applied pointers on the event. pydantic-ai: interrupted runs retain partial messages marked `state='interrupted'`. openhands: export fails closed rather than shipping truncated chains.
**Sources (bad, instructive).** letta's trace endpoint swallows all exceptions returning null; agent-framework's hand-parsed traceparents silently produce zero links; openhands' interactive pagination returns empty pages on backend 500s.
**When to copy.** Every provenance-affecting gate needs a signal path. **Evidence.** `v1/plugins/logs/encoder.go:105-120`; `letta/server/rest_api/routers/v1/steps.py:103-110`.

### P11. Execution-time model/version stamps

**Problem.** "Which model/code produced this output?" must be answered per record, not per deployment.
**Sources.** temporal: `WorkerVersionStamp` on task/activity events, searchable via build-ID attributes (`event_factory.go:131-149`; `worker_versioning.go:110-139`). letta: steps persist `model/model_handle/model_endpoint/provider_name`; auto-mode updates the step with the *actually resolved* model even on mid-flight failure, specifically for billing/audit (`letta_agent_v3.py:1076-1087`). openhands: per-component usage metrics keyed `"default"/"condenser"/"profile:<name>:<uuid>"` plus mid-run `SwitchLLMObservation` events replayable from history. langfuse: client-claimed vs registry-matched model stored two-sided. Weakest: langgraph — model identity rides only on ephemeral stream metadata, absent from durable `CheckpointMetadata`.
**Evidence.** `letta/orm/step.py:34-52`; `src/types/agent-server/core/events/conversation-state-event.ts:10-54`.

## Key Differences

**Durability locus.** The sharpest split: platforms owning storage (temporal, letta, langfuse) guarantee lineage and expose query surfaces (REST traversal, SQL indexes, ClickHouse filters); libraries (pydantic-ai, openai-agents-sdk, agent-framework, langgraph) produce portable lineage and depend on hosts to persist it — pydantic-ai's report states plainly there is "no queryable lineage database or artifact registry," and openai-agents-sdk has no default on-disk trace store. Same pattern quality, opposite operational guarantees.

**Join-key philosophy.** temporal mints its own causal addresses (sequential event IDs, capability task tokens) and validates them server-side; langgraph derives deterministic addresses from causal coordinates. Three sources adopt provider-native `call_id`s as join keys and each pays a defensive tax: agent-framework builds occurrence-aware matching because providers recycle IDs (spec-documented at `docs/specs/004-python-function-calling-loop.md:231-256`), openai-agents-sdk layers semantic fingerprints over them, letta inherits provider mangling (length clamps, sanitization) eroding uniqueness. Framework-minted identity avoids that tax at the cost of translation layers to provider formats.

**Approval binding strength.** A clean spectrum: value-bound (agent-framework embeds the whole action) → verified-key (openai-agents-sdk fingerprints) → required-key with persistence (letta, pydantic-ai, langfuse, langgraph interrupts) → heuristic/id-less (openhands' `{accept}`). Notably, strength correlates with where approvals were a core product requirement, not with overall maturity.

**Privacy posture.** Four distinct answers to "does the audit trail contain content?": always-record-what's-reported (langfuse, letta's opt-in traces), gated-by-flag with structural metadata always emitted (openai-agents-sdk's `trace_include_sensitive_data`, pydantic-ai's `include_content`, agent-framework's sensitive-data gate), and policy-governed redaction recorded in-band (opa — the only source where the audit trail describes its own redactions). None is wrong; they serve different regulators.

**Transformation handling.** temporal bridges transformations with explicit pointer fields (continuations, resets, forks); langfuse freezes mutable artifacts at reference time (snapshots); pydantic-ai repairs with markers; agent-framework matches by ordered occurrence; openhands records what condensation forgot (`forgotten_event_ids`). These are five different correct answers to the same problem, chosen per constraint: log immutability vs mutable registries vs external histories.

**Why divergence is rational, not quality difference.** opa's unpersisted traces reflect a policy engine evaluating millions of sub-second decisions per second — synchronous explain plus flat logs is proportionate. langgraph's ephemeral model metadata reflects a framework delegating observability to tracers. openhands' client-side heuristics reflect a frontend that cannot change the server protocol unilaterally. Judging these as defects would misread the constraints.

## Tradeoffs

**Denormalized self-containment vs payload cost.** OPA's flat events make each record independently auditable but grow until size limits force dropping the ND cache — losing replay fidelity for exactly the largest, most complex decisions (`encoder.go:105-120`). temporal embeds full inputs/results making every fact locally attributable but driving history growth, mitigated by continue-as-new at the price of fragmenting the single-log narrative. Alternative seen in langgraph: store deltas and reconstruct at read time — cheaper writes, but reconstruction silently breaks when ancestors are pruned.

**Provider-native join keys vs defensive complexity.** Reusing provider `call_id`s minimizes translation loss (letta) but inherits recycling and mangling; the defenses — agent-framework's occurrence tracking (flagged in its own AGENTS.md as high-blast-radius where small changes can "orphan call/result pairs [or] replay stale approval authority") and openai-agents-sdk's fingerprinting — are substantial engineering. Framework-minted IDs (temporal, langgraph) avoid both the recycling problem and the defense, at the cost of maintaining address spaces.

**Fail-loud vs repair vs tolerate.** pydantic-ai rejects ambiguous bindings outright — safest for correctness, brittle against hostile providers. Its own repair pipeline handles the external cases it can't control. openhands tolerates malformed historical events during export (skips them, `transcript-export/index.ts:488-491`) — maximum availability, minimum forensic completeness. Best-fit depends on who controls the data source: reject what your model sends, repair what eviction breaks, tolerate what history delivers.

**Privacy gating vs audit completeness.** Default-off argument capture (agent-framework) protects data but a default trace proves *that* a tool ran (`gen_ai.tool.call.id`) without proving *with what*. openai-agents-sdk's default-on content capture maximizes auditability but ships prompts to the trace backend unless operators act. opa's middle path — record shape-of-redaction (`masked`/`erased` pointers) while destroying content — is the most reusable compromise observed.

**Portability vs run attribution.** agent-framework's checkpoints deliberately omit the creating run instance so graphs can be shared/restored across instances (`_workflows/_checkpoint.py:37-41`) — and consequently cannot answer "which run wrote this?" from the artifact alone. temporal's continue-as-new makes the inverse trade: perfect run-scoped attribution, fragmented narrative. Choose by whether artifacts are shared (definition-scoped) or investigated (run-scoped).

**Structured relational lineage vs write amplification.** letta validates run existence on every message insert and maintains purpose-built indexes — integrity and fast bidirectional traversal, paid per batch. langfuse's column-per-relationship design buys O(1) filterable reads but leaves staleness after registry mutations with only application-level cascades. Event-log designs avoid the consistency machinery but push multi-hop queries to clients (temporal's noted gap).

## Decision Guide

- **Building a library/framework:** put lineage on your transferable objects (P1/P2), stamp via one helper (P7), fail loud on ambiguity (P4), and define the serialization contract so lineage survives round-trips (pydantic-ai's `ModelMessagesTypeAdapter` test pins this, `tests/test_messages.py:861-905`). Do *not* force a persistence store; do provide OTel GenAI semconv mapping so hosts get durable lineage free.
- **Building a platform/system of record:** choose event sourcing (Model A) when attribution-under-failure is the product; choose relational/checkpoint lineage (Model B) when you need indexed bidirectional queries and moderate write rates. Either way, adopt factory/choke-point construction (P7) and causally-addressable dispatch tokens (temporal's task tokens) so mis-attribution is detectable server-side.
- **Need resume/replay:** derive identities deterministically from causal coordinates (P3) rather than minting fresh randoms per attempt — this is what lets langgraph reconnect interrupts and temporal validate completions after crashes without coordination.
- **Human approvals in the loop:** require an immutable action identifier on every approval request/response; bind decisions by embedding the action (value) or verifying a semantic fingerprint (key); persist decisions append-only with actor and timestamp (langfuse is the only source doing all four; everyone else misses at least the actor/timestamp half).
- **High-volume observability intake:** resolve soft references to strong IDs at ingestion storing both halves (P8), freeze mutable artifacts at reference time (snapshot-on-reference), keep provided-vs-computed duality (P9), and make every drop-path emit metrics (P10).
- **Frontend/consumer of someone else's stream:** treat server-assigned IDs as your only dedup and correlation keys, prove completeness before exporting (openhands' count cross-check), and refuse to correlate by content strings — openhands' exact-match echo reconciliation is the cautionary example.
- **Choosing between provider-native and framework-minted join keys:** if you execute against multiple providers whose IDs may recycle or be sanitized, mint your own and translate at the edge; if you're single-provider and want wire-level debuggability, reuse theirs but add a reuse guard (P4).

## Practical Tips

- Give every effect a field pointing at its cause *at construction time* — a factory or single persistence function beats documentation (temporal, letta).
- Mirror IDs symmetrically in constructor pairs so a result physically cannot exist without its call's ID (agent-framework's `from_function_call`/`from_function_result`).
- When truncating or summarizing history, record *what left*: `forgotten_event_ids` (openhands), compaction stats, or summary-to-source links — future auditors will need the diff, not just the result.
- Emit structural lineage metadata even when payloads are withheld (IDs, types, usage, timing) — openai-agents-sdk's redaction-aware exports keep audits useful under privacy modes.
- Add a marker to any synthetic/repaired record (`SYNTHESIZED_TOOL_RETURN_METADATA_KEY`); unmarked repairs are indistinguishable from evidence.
- Store the client's claim next to your computation (`provided_model_name` vs `internal_model_id`) so enrichment is auditable and disputes resolvable.
- Test lineage as topology, not presence: snapshot the exact expected span tree / assert `ParentInitiatedEventId == InitiatedEventId` across processes (openai-agents-sdk, temporal) — presence tests pass while links rot.
- Pin provenance-propagation invariants in regression tests: langgraph asserts `thread_id`/`run_id` reach stream metadata while secrets don't (`tests/test_pregel.py:6918-6969`).
- Format provenance into the text the model itself consumes (letta's search results embed passage IDs/filenames/scores) so citations survive into reasoning context — cheap retrieval provenance even without a citation subsystem.
- Count what you drop: every size limit, redaction, or filter that removes lineage should increment a metric (opa) or set a state flag (`state='interrupted'`, pydantic-ai).

## Anti-Patterns / Caution Signs

- **Id-less control-plane requests.** openhands' `{accept}` confirmation forces the UI to guess the pending action from store order — misattribution is one out-of-order event away (`conversation-confirmation-buttons.tsx:30-36`). If your approval protocol has no action ID, stop.
- **Nullable lineage foreign keys with deletion-nulling and disabled validators.** letta's `SET NULL` plus commented-out `run_id` assertions (`orm/message.py:48-53`, `schemas/message.py:312-317`) mean deletion quietly destroys forensics and nothing enforces stamping.
- **Silent exception swallowing on lineage reads/writes.** letta's trace endpoint (`except Exception: pass`), langfuse's tool-extraction failures degrading to empty arrays, agent-framework's malformed traceparents yielding link-less spans — all mask data-quality incidents as "no evidence."
- **Content-string correlation instead of identifiers.** openhands reconciles optimistic user bubbles to echoes by exact text match with FIFO fallback; any server-side munging pops the wrong entry (`optimistic-user-message-store.ts:169-198`).
- **Browser-local storage for cross-session lineage.** openhands' profile switches, child-launch ledger, and conversation metadata live in localStorage — invisible to other clients and unauditable.
- **Heuristic extraction presented as contract.** langfuse's `isToolCallLike` shape-sniffing maximizes compatibility but false negatives silently lose lineage; promote to declared contracts once SDK support exists (its own report recommends this).
- **Ephemeral-only critical metadata.** langgraph's model/provider versions vanish unless a tracer persists stream metadata; durable lineage answers nothing about "which model wrote this step."
- **Sentinel foreign keys.** langfuse's `prompt_id: ""` on lookup miss creates rows whose strong ID cannot be dereferenced — use nullability plus a data-quality metric instead.
- **Skipped CI tests guarding lineage invariants.** langgraph's nested-tracing interop test (asserting contiguous `trace_id`/`parent_run_id`) is skipped for CI timeouts (`test_tracing_interops.py:60`) — exactly the invariant that rots unnoticed.
- **Growing exclusion lists and string-encoded coordinates.** langgraph's `EXCLUDED_METADATA_KEYS` and `node:<task_id>` namespace surgery in retry logic are early brittleness signs; so is agent-framework's occurrence-matching code being self-flagged as high-blast-radius. When lineage plumbing needs its own warning labels, the design is carrying too much.
- **Systemic caution sign:** any of — fallback chains to locate record boundaries (pydantic-ai's three-layer `new_messages()` scan), tolerance of corrupt ledgers over safety (openhands resetting the launch ledger), or "graceful" empty pages in history loading — indicates the lineage layer is absorbing uncertainty that should surface as errors.

## Notable Absences

- **Fact-level citation inside free-text answers.** Absent in all nine sources; explicitly confirmed absent in openhands, pydantic-ai, and langfuse searches. Only structured outputs carry direct pointers (pydantic-ai's `FinalResult.tool_call_id`); only retrieved-context provenance exists as annotations/passages (agent-framework citations, letta passages) — nothing maps answer *spans* to sources.
- **Cryptographic / tamper-evident chaining.** No source hashes inputs-to-outputs for integrity. temporal checked explicitly and found none (`BinaryChecksum` identifies binaries, not data); opa's nearest control is bundle signature verification tying artifacts to signing keys.
- **Weight/snapshot-level model versions.** Everything tracks model-name strings, endpoints, or build IDs; no deployment/snapshot hashes anywhere (confirmed absent in agent-framework, letta, pydantic-ai, langfuse searches).
- **Framework-generated run identifiers in two libraries.** agent-framework has none (`AgentResponse.response_id` is provider-supplied or None); langgraph's `run_id` is checkpoint-metadata-only and model identity stays ephemeral.
- **Artifact↔run registries in libraries.** langgrep (langgraph) found no artifact linkage at all in-repo; pydantic-ai's artifacts exist only as message-contained media; agent-framework's checkpoints are definition-scoped. Platforms do better: langfuse media associations (with origin enum), letta `job_messages`/batch items, temporal callbacks/Nexus completion tokens, openai-agents-sdk sandbox snapshots.
- **Actor/timestamp on approval decisions.** openai-agents-sdk's `_ApprovalRecord` carries neither; only langfuse records the deciding user; opa has no human approvals at all.
- **Cross-store referential integrity.** langfuse's ClickHouse lineage columns have no FKs to Postgres registries; dangling references rely on cascade workers.
- **Engine/build version inside audit events.** opa's `EventV1` carries bundle revisions but not OPA version — correlating old events with the producing binary needs out-of-band knowledge (its `ProvenanceV1` exists only on live responses).
- **Native multi-hop lineage queries.** temporal provides pointers/links but no server-side graph traversal; consumers compose chains themselves.
- **Structured retrieval-provenance schema in observability platforms.** langfuse has a RETRIEVER span *type* but no document/chunk-source columns; the "trace a fact to its source document" loop closes nowhere end-to-end.
