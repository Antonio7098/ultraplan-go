## Executive Summary

Across eight sources, exactly one — langfuse (9/10) — can answer the dimension's guiding question structurally: prompts are immutable rows keyed by `(projectId, name, version)`, runs pin a resolved `prompt_id` at ingest time (`packages/shared/prisma/schema.prisma:742`; `worker/src/services/IngestionService/index.ts:321-333`). The other seven cannot answer it from their own artifacts. Six of them record zero prompt version identifiers anywhere in their codebases (repo-wide searches in langgraph, crewai, letta, pydantic-ai, openhands, and agent-framework all returned no hits), and the remaining two delegate version identity entirely to external platforms (openai-agents-sdk's optional `version` on hosted OpenAI prompts; agent-framework's Foundry `agent_version`).

What every source *does* converge on is a weaker substitute: capturing the full rendered prompt text at run time through some observability channel — OTel spans (agent-framework, pydantic-ai), event buses (crewai), persisted system-message rows (letta), dedicated system-prompt events (openhands), named trace steps (langgraph). This gives point-in-time fidelity ("what bytes did this run see?") but not identity ("which revision was that?"). Worse, in four sources the text-capture channel is privacy-gated off by default or silently absent from exported traces, so even content-level provenance evaporates in production configurations.

Scores span 3–9 and correlate tightly with product shape: the source whose product *is* prompt management scores highest; frameworks that treat prompts as caller-supplied values score lowest; applications in between persist rendered text but not versions. The practical takeaway is not "build a registry" — it is that provenance requires two cheap structural additions almost everyone is missing: a stable identifier stamped onto the run record, and capture paths that do not depend on opt-in privacy flags.

## Core Thesis

**The industry default posture is "prompts are values, provenance is telemetry" — and telemetry is not a provenance system.** Seven of eight sources store prompts as ordinary values (code constants, constructor strings, config files, package assets) and push run-to-prompt correlation onto generic observability plumbing: trace spans, event payloads, message history. This substrate captures exact text but no identity, is frequently gated behind privacy flags that default off (agent-framework's `ENABLE_SENSITIVE_DATA`, pydantic-ai's `include_content`), and is ephemeral unless operators independently build retention.

Structural provenance — an immutable prompt artifact with a version identity plus a run-record column binding runs to that identity — appears only where prompt management is the product itself (langfuse) or where it is delegated to someone else's product (openai-agents-sdk → OpenAI platform; agent-framework → Foundry). The lesson generalizes: nobody builds prompt versioning as a framework feature because it looks like infrastructure with no runtime payoff until an incident happens; the sources that did build it did so because their users demand it as a feature, not because the framework needed it internally.

Two corollaries emerge from the comparison. First, snapshotting beats inheritance for behavioral stability but destroys fleet consistency (letta copies prompts onto agents at creation; existing agents never receive fixes). Second, cache-performance pressure actively works against provenance: letta overwrites rendered system messages in place to keep prefix caches warm (`letta/services/agent_manager.py:1595-1604`), crewai pins volatile content at the prompt tail (`lib/crewai/src/crewai/utilities/prompts.py:144-148`), and pydantic-ai orders static parts first so providers can cache stable prefixes (`pydantic_ai_slim/pydantic_ai/messages.py:1782-1785`) — all reasonable optimizations that make the prompt surface less auditable, not more.

## Approach Models

Clustering the eight sources by how they model prompt storage and identity yields five distinct approaches:

### Model A: Managed append-only registry (langfuse)

Prompts are database rows. Content is JSON, versions are integers unique per `(projectId, name)` (`packages/shared/prisma/schema.prisma:742`), creation is strictly insert-only (`web/src/features/prompts/server/actions/createPrompt.ts:106-109,170`), and consumers address prompts through mutable labels (`production`, `latest`) rather than raw versions (`getPromptByName.ts:49-55`). Runs bind to prompts at ingestion: generation events carry `promptName`+`promptVersion` as an all-or-nothing pair (`packages/shared/src/server/ingestion/types.ts:493-500`), resolved to a canonical `prompt_id` and stamped onto ClickHouse observations (`worker/src/services/IngestionService/index.ts:320-333`). This is the only model where label promotion changes what production serves without touching any deployment.

### Model B: Platform-delegated versioning (openai-agents-sdk, agent-framework/Foundry)

The framework stores only references; a platform stores content and versions. openai-agents-sdk's `Prompt` TypedDict holds `{id, version?, variables}` forwarded verbatim to the Responses API (`src/agents/prompts.py:23-33`; `src/agents/models/openai_responses.py:980`); omitting `version` floats to whatever the platform serves next. agent-framework does the same with Foundry PromptAgents, emitting `{name, type: agent_reference, version}` (`python/packages/foundry/agent_framework_foundry/_agent.py:143-152`). Both keep application code stable while prompt content iterates server-side — but both are vendor-coupled (openai-agents-sdk drops the prompt entirely on Chat Completions adapters, `src/agents/models/openai_chatcompletions.py:259`) and neither records the resolved reference on their own telemetry.

### Model C: Code/config-resident values + observability substrate (langgraph, pydantic-ai, crewai, agent-framework Python core)

Prompts are ordinary values entering at construction time — langgraph's `Prompt = str | SystemMessage | Callable | Runnable` union (`libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py:121-126`), pydantic-ai's `AgentInstructions` union including validated Handlebars templates and YAML specs (`pydantic_ai_slim/pydantic_ai/_instructions.py:12-18`; `template.py:16-108`; `spec.py:33-69`), crewai's packaged JSON slices (`lib/crewai/src/crewai/translations/en.json:1-102`), agent-framework's module-level constants with constructor overrides (`_magentic.py:108-245`). Provenance is reconstructed post-hoc from named trace spans (`PROMPT_RUNNABLE_NAME` in langgraph), OTel attributes (`gen_ai.system_instructions` in agent-framework and pydantic-ai), or event payloads (`LLMCallStartedEvent.messages` in crewai). None of these channels carries a version identifier.

### Model D: Snapshot-on-create with mutable rendered state (letta)

A distinctive hybrid: built-in templates live as Python constants (`letta/prompts/system_prompts/__init__.py:15-27`), but each agent copies its chosen template onto its row at creation (`letta/services/agent_manager.py:516-520`), and the fully rendered system message persists as a role=`system` row linked to runs (`letta/orm/message.py:23-53`). Running agents are insulated from deploy-time prompt changes — at the cost that rebuilds overwrite the rendered message in place by reusing its ID (`agent_manager.py:1595-1604`), destroying history. A DB-backed `prompts` registry exists as migration-plus-ORM but has zero consumers (`alembic/versions/ddecfe4902bc_add_prompts.py:22-36`) — an unfinished migration toward Model A.

### Model E: Event-sourced prompt materialization (openhands frontend)

Prompts are observed, not stored: the backend owns the core system prompt, and the frontend consumes it as an immutable persisted `SystemPromptEvent` containing the exact text, tool list, and dynamic context for every conversation (`src/types/agent-server/core/events/system-event.ts:5-26`), supplemented by per-message `activated_skills` lists (`message-event.ts:14`). User-authored skills are plain markdown files on disk (`skill-scope.ts:15-19`); automations are REST-managed rows in a backend SQLite DB. Version identity is anticipated in types (`SkillInfo.version?: string`) but unpopulated end-to-end, and display slots render hardcoded `null` (`system-message-adapter.ts:32-33`).

## Pattern Catalog

### P1: Append-only versions + label indirection

- **Problem:** Prompts must iterate freely while production stays stable and history stays reproducible.
- **Demonstrated by:** langfuse (only complete implementation).
- **Why it works:** Immutability makes every historical version reproducible; labels decouple *what exists* from *what serves* — promoting a version is a metadata patch (`promptVersionHandler.ts:16-33`) while ingest-time pinning keeps run history exact regardless of later promotions.
- **Copy when:** Multiple consumers share prompts across deployments; you need rollback, audit, or staged rollout.
- **Overkill when:** A single application owns its handful of prompts in-repo — git history plus text capture covers most needs.
- **Evidence:** `createPrompt.ts:160-188` (transactional append-only create), `PromptService/index.ts:102-130` (version-XOR-label lookup), `prompts.v2.servertest.ts:421-489` (run association integration test).

### P2: Persist the rendered prompt per run (prompts-as-events / prompts-as-messages)

- **Problem:** You must be able to answer "what exactly did the model see?" after the fact.
- **Demonstrated by:** openhands (`SystemPromptEvent` with full text + tools + dynamic context, `system-event.ts:5-26`), letta (rendered role=`system` message linked to `run_id`/`step_id`, `orm/message.py:41-53`), pydantic-ai (timestamped `SystemPromptPart`s inside serialized message history, `messages.py:180-201`), crewai (`LLMCallStartedEvent.messages` carrying full rendered payloads, `events/types/llm_events.py:38-61`), agent-framework and pydantic-ai via `gen_ai.system_instructions` spans.
- **Why it works:** Capturing effective bytes sidesteps all the hard questions about composition order, variable substitution, and merging — the trace *is* the answer.
- **Copy when:** Always; it is the cheapest insurance in the dimension.
- **Risky when:** It substitutes for identity instead of complementing it — comparing two runs' prompts then requires manual text diffing (openhands notes exactly this cost), and privacy gating can remove the trail entirely (see P7).
- **Caveat from evidence:** letta shows the failure mode — if the rendered record is overwritten in place (`agent_manager.py:1595-1604`), persistence without append-only discipline still loses history.

### P3: Reference-vs-content split

- **Problem:** Application code should not change when prompt content changes.
- **Demonstrated by:** openai-agents-sdk (`pmpt_*` ids in code, content on the platform, `docs/agents.md:88`; `examples/basic/prompt_template.py:21`), agent-framework Foundry path (name+version `agent_reference`, `foundry/_agent.py:143-152`).
- **Why it works:** Classic indirection — the stable id is the compile-time contract; mutable content lives behind the API boundary.
- **Copy when:** A trusted platform exists to host content and you accept its availability/coupling.
- **Avoid when:** Portability matters — openai-agents-sdk silently drops hosted prompts on non-Responses adapters (`openai_chatcompletions.py:259,471`).
- **Refinement worth copying:** openai-agents-sdk separates prompt *version* (identity) from `prompt_cache_key` (cache affinity, `run_internal/prompt_cache_key.py:13`) — adjacent names, deliberately independent mechanisms.

### P4: Copy-on-create snapshotting

- **Problem:** Deploys should not retroactively change running agents' behavior.
- **Demonstrated by:** letta (per-agent `system` copied at creation, compaction prompt materialized into per-agent JSON, `summarizer_config.py:35-45,84-89`).
- **Why it works:** Behavioral stability — a bad prompt fix... er, a bad prompt *release* cannot break existing agents mid-lifecycle; prefix caches stay warm.
- **Cost:** Fleet drift. A critical fix never reaches existing agents; there is no version pin, drift report, or bulk-migration mechanism (letta's own future-work list asks for exactly this, hooking the existing `rebuild_system_prompt_async(force=True)`).
- **Contrast:** langfuse solves the same problem oppositely — nothing running is ever affected because consumers fetch by label at call time, and history stays intact.

### P5: Typed multi-form prompt inputs with a callable escape hatch

- **Problem:** Frameworks cannot know where prompts should come from, yet must allow externalized prompt sources without building them.
- **Demonstrated by:** langgraph (`Runnable` form permits a remote-config-backed fetcher, `chat_agent_executor.py:124-125`), openai-agents-sdk (`DynamicPromptFunction` receiving run context for store lookups/A-B selection, `prompts.py:36-47`), pydantic-ai (dynamic instruction/system-prompt functions re-evaluated per turn via `dynamic_ref`, `_agent_graph.py:707-732`), agent-framework (constructor overrides for all seven Magentic prompts, tested at `orchestrations/tests/test_magentic.py:1139-1193`).
- **Why it works:** Extension by composition rather than configuration — the type system defines the seam; the storage decision stays outside the framework.
- **Failure mode common to all four:** the escape hatch has no validation or identity semantics. pydantic-ai's `dynamic_ref = __qualname__` keeps pointing at the same name after the body changes (`_system_prompt.py:55`); langgraph warns that captured closures can be mutated post-compile so two runs of one graph see different prompts with identical traces.

### P6: Static/dynamic classification as the cache boundary

- **Problem:** Provider-side prompt caching rewards byte-stable prefixes, but prompts contain volatile fragments.
- **Demonstrated by:** pydantic-ai (static parts sorted before dynamic ones so Anthropic/Bedrock/OpenRouter cache points land after stable prefixes, `messages.py:1782-1785`; `anthropic.py:2216-2231`; OpenRouter skips caching entirely when dynamic instructions present), crewai (date injection kept at the tail explicitly to preserve the cache anchor, `prompts.py:144-148`; `mark_cache_breakpoint` tags stable prefixes, `llms/cache.py:27`), letta (diff-gated rebuilds and laziness specifically to avoid busting provider caches, with byte-stability integration tests `integration_test_system_prompt_prefix_caching.py:40-112`), openai-agents-sdk (hashed persistent `prompt_cache_key`).
- **Why it works:** Making volatility explicit lets caching decisions become mechanical instead of accidental.
- **Side effect:** This classification is also free provenance metadata — pydantic-ai already records `dynamic: bool` on instruction parts — that no source exploits for versioning purposes.

### P7: Privacy-gated content capture (the broken tradeoff)

- **Problem:** Prompts may contain secrets/PII; dumping them into telemetry by default is unsafe.
- **Demonstrated by:** agent-framework (`ENABLE_SENSITIVE_DATA` defaults False and is "explicitly discouraged outside dev/test", `observability.py:762-780`; baseline semconv omits instructions entirely, asserted at `test_observability.py:372-388`), pydantic-ai (`include_content` gate, `instrumented.py:110-112`), crewai (product telemetry categorically excludes prompt content, `telemetry.py:4`), openai-agents-sdk (spans export only `response_id`+`usage`, `tracing/span_data.py:236-241`).
- **Why it fails as provenance:** The gate is exactly inverted for incident forensics — the runs you need to explain are production runs, which are precisely where capture is off. Four independent sources hit this wall.
- **Fix pattern implied by evidence:** Capture identity always, capture content conditionally. Langfuse stamps `prompt_name`+`prompt_version` columns with no privacy concern because they reference rows, not text; agent-framework's own future-work proposes emitting a hash alongside the existing gated text capture for the same reason.

### P8: Declarative spec files as the deployment-decoupling seam

- **Problem:** Non-developers should edit prompts; prompt edits should not require code releases.
- **Demonstrated by:** pydantic-ai (`AgentSpec` YAML/JSON with stated purpose "separating agent configuration from application code", `spec.py:33-69`; `docs/agent-spec.md:1-9`; templates validated against the deps type at load, catching drift early), agent-framework (YAML `PromptAgent` loading plus PowerFx `=Env.X` indirection behind safe-mode, `_loader.py:291`; `_models.py:51-80`), crewai (`Crew(prompt_file=...)`, `crew.py:329-332`), openhands (user/project skill markdown picked up on next conversation).
- **Where it breaks down:** Every implementation freezes at load time — pydantic-ai reads specs eagerly at construction with no watch/hot-reload; crewai memoizes per-path forever (`lru_cache(maxsize=None)`, so corrected files are invisible until restart); agent-framework env substitution creates cross-environment drift with no version field to flag it. And crewai shows the validation gap: whole-file replacement with no merge and late `KeyError`-style failures mid-execution despite docs promising otherwise.

## Key Differences

**Registry vs. values.** Langfuse treats a prompt change as a data write with schema enforcement (`@@unique([projectId, name, version])`); everyone else treats it as a value change flowing through code review or file edits. This single difference produces nearly all rating separation: identity, immutability, rollback, and run binding all fall out of "the prompt is a row."

**Delegation vs. ownership.** openai-agents-sdk and agent-framework/Foundry outsource versioning to platforms they control or integrate; langgraph explicitly defers to ecosystem tooling it does not ship (hub usage appears only in example notebooks). Delegators get real version semantics for free but lose portability and local diffability — and notably, both delegators still fail to record the resolved reference on their own traces, so delegation alone doesn't close the loop.

**Snapshot vs. live inheritance.** Letta freezes prompts onto agents at creation; openai-agents-sdk unpinned hosted prompts float to platform-latest on every turn. Same dimension, opposite poles: letta risks permanent divergence between an agent and its improved defaults, while floating risks silent behavior change after a platform edit with "no local signal distinguishing 'prompt changed' from 'model/code changed'" (source report's words).

**Append vs. overwrite.** Langfuse inserts new versions; letta mutates the rendered system message's row in place. Both optimize for something real (history integrity vs. recall-storage economy and cache warmth — the docstring admits avoiding "flood[ing] recall storage"), but only one preserves the ability to ask "why did the agent behave differently last week?"

**Front-of-book vs. back-of-book versioning.** openhands and letta show half-built version systems — openhands has `version` fields in wire types, catalog mapping that drops them, and null-hardcoded UI slots; letta has a migrated-in `prompts` table with project scoping and audit columns that no manager references. Versus langfuse, where the deprecated `isActive` flag lingers but the live system fully owns its labels-and-versions model. The difference is finishing: incomplete migrations leave worse archaeology than no attempt at all.

**Text vs. hash.** Where provenance exists at all, six sources persist full text (unambiguous, bulky, ungrouppable) and none computes a content hash at the framework level — langfuse's integer versions work because the registry assigns them, not because anyone hashes anything.

## Tradeoffs

- **Langfuse uses a registry because prompt management is its product; langgraph ships no storage because prompt lifecycle is out-of-framework scope.** Benefit of the registry: rollback, audit, promotion semantics, run binding. Cost: Postgres tables, cache invalidation machinery, epoch rotation logic, conflict handling — infrastructure a thin framework cannot justify. Best-fit context follows product shape, not engineering quality.
- **openai-agents-sdk makes `version` optional to keep the ergonomics light; requiring it would force reproducibility discipline.** Omission floats silently to platform-latest with zero warnings (`prompts.py:80` forwards `None`), trading reproducibility for convenience — the source itself recommends warning or adding a "latest" sentinel.
- **Letta trades observability for stability via copy-on-create plus in-place rebuilds.** Existing agents never regress from deploys (benefit), but prompt fixes never reach them and rendered history is destroyed (cost). Alternative seen in langfuse: labels give fleet-wide updates without touching history.
- **agent-framework trades durability for privacy via gated telemetry.** Default-off sensitive capture protects users (`observability.py:762-774`) but removes the run→prompt trail exactly where incidents happen; the alternative demonstrated by langfuse is stamping identifiers (not content) unconditionally.
- **crewai trades correctness guarantees for simplicity in its override seam.** Whole-file replacement with no merge, no load-time key validation, and process-lifetime caching means custom files are all-or-nothing, fail mid-execution, and go stale invisibly — versus pydantic-ai's spec files, which validate template variables against the deps type at construction.
- **openhands bundles public skills at build time to eliminate clone latency** (`skills-service.ts:29-33`), gaining reproducibility and startup speed at the cost of freshness: public prompt fixes wait for an npm release, while user/project files update instantly — a deliberate two-speed system within one product.
- **pydantic-ai recomputes instructions fresh per request rather than trusting supplied history** (`docs/agent.md:1347-1356`), avoiding stale-prompt bugs but breaking the invariant that serialized history is a complete record of what past requests saw — cross-run comparison then depends entirely on external telemetry having been enabled.

## Decision Guide

Choosing a prompt storage/versioning approach, based on the models observed:

1. **You are shipping a library/framework others build on** → Model C (typed values + named-step trace capture + callable escape hatch), with two amendments the sources prove necessary: emit a content hash alongside gated text capture (agent-framework's proposed fix), and document the override placeholder contract like .NET's `MagenticPromptOverrides.cs:55-62` does instead of Python's unvalidated strings.
2. **You are shipping a product/platform where multiple consumers share prompts** → Model A (langfuse blueprint): append-only rows, composite unique constraint, label indirection, ingest-time pinning into run records, integration-tested end to end. Do not skip the tests-under-failure that langfuse includes (Redis outage fallback, concurrent-create conflicts).
3. **A trusted platform already hosts your prompts** → Model B (reference indirection), but pin versions explicitly when reproducibility matters (openai-agents-sdk's examples do, `examples/basic/prompt_template.py:35,59`), and record the resolved `{id, version}` somewhere durable — neither delegator currently does.
4. **Long-lived stateful agents whose behavior must not shift under them** → Model D (snapshot-on-create), but add what letta lacks from day one: a drift-report/bulk-upgrade hook and append-only rendered history. Never reuse message IDs across rebuilds.
5. **Regulated/compliance context** → Combine Model A's identity stamping with P2's text capture, and ensure neither depends on privacy flags. The four-source convergence on "gated capture = no forensics" is the strongest cautionary evidence in this study.
6. **Small team, few prompts** → Git-versioned spec files (pydantic-ai style, with load-time validation) plus unconditional event/text capture. Skip the registry; add a hash field now so retrofitting later doesn't require replaying from raw text.

Decision rule distilled from the comparisons: **if you cannot name who consumes a prompt besides the code that loads it, values suffice; the moment a second consumer (another service, another environment, another time) appears, you need identity.**

## Practical Tips

- **Stamp identity even without a registry.** A content hash or semantic-version string on the few framework-owned prompt surfaces (agent-framework suggests starting with the Magentic manager fields) converts gated text capture into ungated correlation. It costs one column.
- **Capture rendered text AND identity.** Text alone (six sources) answers "what"; identity alone answers "which"; audits need both. openhands' transcript export omits the system prompt entirely even though the in-app modal can show it — parity gaps like this surface during incidents.
- **Never let the only provenance channel sit behind a default-off flag.** If capture must be gated, gate the *content*, not the *reference*. This is the single most repeated self-inflicted wound across agent-framework, pydantic-ai, crewai, and openai-agents-sdk.
- **Validate custom prompt files at load time.** pydantic-ai validates template variables against the deps type at construction; crewai raises generic exceptions at first retrieval mid-kickoff. Fail eager, fail specific.
- **Document placeholder contracts for overridable structured prompts.** .NET documents that omitting `{schema}` breaks JSON parsing and speaker routing; Python exposes the same overrides with no contract. An override typo should fail loudly at definition, not silently at routing.
- **Separate cache-affinity keys from provenance identities** (openai-agents-sdk's deliberate split) and don't let naming invite conflation — `prompt_cache_key` vs `prompt.version`.
- **Freeze consciously.** Import-time loading (openai-agents-sdk `functools.cache` markdown, crewai singleton, langgraph import-string baking) is fine for reproducibility but decide it explicitly; there is no config hook in these systems to redirect templates per environment afterward.
- **If you snapshot on create, plan for drift from day one.** Letta's missing piece isn't the snapshot, it's the diff-report/bulk-upgrade story for a fleet of agents pinned to stale prompts.
- **When composing instructions from multiple providers, give the blend an identity too.** agent-framework joins provider/session contributions with `"\n".join(...)` producing a blended prompt with no identity of its own — composition is where version tracking usually dies.

## Anti-Patterns / Caution Signs

Signs a codebase's prompt-handling design is going brittle, drawn directly from observed failure modes:

- **Dormant version infrastructure.** Letta's migrated-but-unreferenced `prompts` table and openhands' populated-nowhere `version` fields with hardcoded-null UI slots (`system-message-adapter.ts:32-33`) are worse than absence — operators trust surfaces that return nothing.
- **Docs contradicting loader semantics.** CrewAI docs promise merging; the loader replaces wholesale (`i18n.py:37-39` vs `customizing-prompts.mdx:221`). Users following the docs get mid-run exceptions.
- **Substring-based change detection.** Letta skips rebuilds when old memory is a substring of current content, with in-code comments admitting fragility (`agent_manager.py:1562-1563`) — false negatives mean stale prompts ship as "current."
- **Naive `.replace()` templating without consumed-marker validation.** CrewAI's blind global `{goal}/{role}/{backstory}` replacement can rewrite user-authored slices containing those tokens; stop-word extraction splits unconditionally on `{{ .Response }}`. openai-agents-sdk at least tests placeholder leakage; crewai does not.
- **Silent fallbacks that degrade prompt content.** openai-agents-sdk returns `None` base instructions when the packaged `.md` is unreadable (sandbox runs unprompted, no warning); openhands' skill loader degrades to bundled catalog silently; agent-framework returns unevaluated PowerFx expressions at debug-log level; pydantic-ai drops empty-string instruction results quietly. Each individually reasonable; together a pattern where the effective prompt diverges from intent with no signal.
- **In-place mutation of historical artifacts.** Message-ID reuse across rebuilds (letta) is the canonical case; the tell is optimizing storage/cache while losing "why did behavior change?" forensic ability.
- **Environment-variable prompt indirection without version tracking.** Agent-framework's `=Env.X` in YAML means two deployments of one artifact run different instructions with nothing but environment state distinguishing them — untracked configuration surface (langgraph's unknown-key warning shows the same gap from the tooling side).
- **Mutable objects captured at graph construction.** Langgraph's note that a post-compile mutation of a captured `SystemMessage` changes effective prompts while every trace says merely `"Prompt"` — identity-less capture plus mutable input equals silent divergence.

## Notable Absences

Evidence-checked absences reported across the sources:
