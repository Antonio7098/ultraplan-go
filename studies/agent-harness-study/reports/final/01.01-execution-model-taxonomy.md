## Executive Summary

Eight codebases were analyzed for their fundamental execution model. Four distinct primary models appear — bounded step/turn loops, Pregel/BSP superstep graphs, event-sourced state machines backed by persistent task queues, and event-driven DAG routers — and **every substantive source layers more than one model**. No source ships exactly one. The differences that matter are not *which* models they mix but *how deliberately* they mix them: the top-rated sources (langgraph 9, pydantic-ai 9, temporal 9, openai-agents-sdk 9) each name one primary substrate, encode "what advances execution" in a typed artifact (a discriminant union, a node-return edge, a validated state transition), align durability boundaries with loop boundaries, and compile every user-facing pattern onto that single engine. The lower-rated sources lose points for accidental mixing: letta (5) carries three near-identical in-tree step loops behind a factory, crewai (7) exposes four models with four vocabularies at three selectable layers, and openhands (6) hides the actual agent loop inside a pinned external package (`openhands-sdk==1.29.0`, per its report's `pyproject.toml:61`) with no in-repo pointer to it. The `reports` source is an empty directory registered as a study source and yields no evidence.

## Core Thesis

**There is no single winning execution model; mature harnesses converge on "one named engine, many compiled surfaces."** They pick one primary substrate — a turn loop (openai-agents-sdk), a tiny typed FSM graph (pydantic-ai), a Pregel superstep engine (langgraph, agent-framework), or a state machine + transactional-outbox + queue stack (temporal) — give advancement a small typed vocabulary, and express everything else (streaming, handoffs, human-in-the-loop, durability, multi-agent patterns) as layers that reduce onto that substrate. Ratings track this discipline more than feature depth: openai-agents-sdk scores 9 with a plain `while True`, while letta scores 5 with a well-built loop undermined by three parallel implementations of itself. Divergence between sources is mostly a function of product shape — library SDK vs orchestration framework vs durable infrastructure vs hosted platform — not quality, and several divergences are valid responses to different constraints.

## Approach Models

Clustered by the taxonomy categories from the dimension definition:

### Cluster A — Bounded step / turn loops (ReAct-family)

The dominant library-level model: advance by calling the LLM once per iteration, executing tools, then deciding whether to continue.

- **letta**: `AgentLoop.load()` (`letta/agents/agent_loop.py:19`) selects one of four loop classes; production paths run `for i in range(max_steps)` (`DEFAULT_MAX_STEPS = 50`, `letta/constants.py:75`) calling `_step()` per iteration, with a `ToolRulesSolver`-driven `should_continue`/`stop_reason` deciding continuation (`letta/agents/letta_agent_v3.py:222-441`). Continuation is set in six-plus places inside `_step()` — explicit shape, emergent semantics.
- **openai-agents-sdk**: `while True` in `AgentRunner.run` (`src/agents/run.py:768`) dispatches on a tagged union `SingleStepResult.next_step` with exactly four variants — `NextStepFinalOutput`, `NextStepHandoff`, `NextStepRunAgain`, `NextStepInterruption` (`src/agents/run_internal/run_steps.py:154-218`). Streaming swaps only the per-turn workhorse (`run_single_turn_streamed`, `src/agents/run_internal/run_loop.py:1242-1705`) while keeping identical dispatch.
- **crewai (ReAct path)**: classic text-parsed `while not AgentFinish` (`lib/crewai/src/crewai/agents/crew_agent_executor.py:330-468`) and native-tool variant — explicitly deprecated in favor of the Plan-and-Execute executor, yet still live inside `LiteAgent._invoke_loop` (`lib/crewai/src/crewai/lite_agent.py:860-960`).
- **agent-framework (function-calling layer)**: a bounded `for attempt_idx in range(...)` over `max_iterations` (default 40) lives in `FunctionInvocationLayer.get_response` (`python/packages/core/agent_framework/_tools.py:2565-2696`), below the agent core — deliberately in the chat-client substrate, which its report flags as a mental jump when reasoning about "the agent loop."

### Cluster B — Graph / superstep executors

Advance by scheduling batches of node executions against pre-built edges, with a barrier between batches.

- **langgraph**: Pregel/BSP explicitly — `while loop.tick(): ... runner.tick(...) ... loop.after_tick()` (`libs/langgraph/langgraph/pregel/main.py:2979-3003`), with the Plan/Execution/Update phases named in the docstring (`main.py:455-476`). Writes apply through an `apply_writes` barrier (`libs/langgraph/langgraph/pregel/_algo.py:232-345`); dynamic fan-out rides `Send` objects deposited into a TASKS topic (`libs/langgraph/langgraph/types.py:664`).
- **pydantic-ai**: the whole agent is a 4-node FSM — `UserPromptNode → ModelRequestNode → CallToolsNode → (loop or SetFinalResult → End)` — built and wired declaratively (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:2110-2139`). The runner drains `GraphTask`s from an anyio TaskGroup fed by a memory object stream in `iter_graph` (`pydantic_graph/pydantic_graph/graph_builder.py:646-825`) — BSP/superstep semantics with fork/join/decision primitives.
- **agent-framework (Workflow engine)**: `Runner.run_until_convergence` iterates synchronous supersteps, draining pending messages concurrently per edge group until `has_messages()` is false (`python/packages/core/agent_framework/_workflows/_runner.py:78-101,149-153`); .NET mirrors this via `ISuperStepRunner.RunSuperStepAsync` (`dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs:305-336`). Five orchestration builders (sequential/concurrent/handoff/Magentic/group-chat) all compile to this one engine.

### Cluster C — Event-sourced state machines + persistent queues

- **temporal**: a deliberate composition of four-plus models: event-sourced workflow state machines validated by explicit transition tables (`service/history/workflow/mutable_state_state_status.go:21-125`), an HSM framework (`service/history/hsm/sm.go:18-66`), the CHASM typed successor (`chasm/engine.go:16-59`), persistent per-shard/per-category queue processors running `processEventLoop` goroutines (`service/history/queues/queue_immediate.go:132-161`, `queue_scheduled.go:175-201`), and a long-poll matcher for worker delivery (`service/matching/matching_engine.go:629-664`). Advancement is atomic: event → validated transition → history append + outboxed tasks in one DB write (`docs/architecture/history-service.md:319-321`).

### Cluster D — Event-driven DAG routers

- **crewai Flow**: `@start`/`@listen`/`@router` decorators build a static contract (`FlowMethodDefinition`, `lib/crewai/src/crewai/flow/flow_definition.py:612`); the runtime advances via label dispatch — a router method emits a `Literal` value that triggers matching listeners through recursive `_execute_listeners` calls (`lib/crewai/src/crewai/flow/runtime/__init__.py:3239`). Notably, CrewAI implements its Plan-and-Execute agent *as* a Flow (`experimental/agent_executor.py:164`), reusing the DAG runtime as an internal state machine instead of writing a `while` loop.

### Cluster E — Control-plane/runtime splits

- **openhands**: the repo contains no agent loop at all; execution advances when webhooks (or a lazily-started global poller, `openhands/app_server/sandbox/remote_sandbox_service.py:682-768`) deliver events from the sandboxed `openhands-sdk` agent_server process into webhook handlers that persist events and fan out to `EventCallbackProcessor`s (`openhands/app_server/event_callback/webhook_router.py:453-522`, `sql_event_callback_service.py:208-232`). Conversation startup is an explicit 9-state FSM streamed as an async generator (`app_conversation_models.py:262`, `live_status_app_conversation_service.py:309-538`).
- Related but milder: **openai-agents-sdk** delegates Codex runs to a subprocess line-stream consumer (`src/agents/extensions/experimental/codex/thread.py:96-160`); **letta** stubs remote offload via `LettuceClient.step` (`letta/services/lettuce/lettuce_client_base.py:9-87`); **agent-framework** re-encodes its entire Pregel workflow as a replayable generator-based durable orchestrator (`python/packages/durabletask/agent_framework_durabletask/_workflows/orchestrator.py:689-911`).

## Pattern Catalog

### 1. Typed advancement artifacts (discriminants, node returns, transition tables)

- **Problem solved:** "What advances execution?" becomes checkable rather than folklore scattered through a loop body.
- **Demonstrated by:** openai-agents-sdk (`next_step` dataclass union with an unknown-variant raise, `src/agents/run.py:1495-1497`; exhaustively tested in `tests/test_run_step_execution.py:2749-2780`); pydantic-ai (outgoing edges inferred from `BaseNode.run` return annotations, `pydantic_graph/pydantic_graph/basenode.py:104-136`); temporal (`setStateStatus` rejects undeclared transitions with `invalidStateTransitionErr`, `service/history/workflow/mutable_state_state_status.go:127-138`; HSM/CHASM `Transition.Apply` returns `ErrInvalidTransition`, `chasm/statemachine.go:70-72`); crewai (`@router` return annotations captured as emitted Literals, `lib/crewai/src/crewai/flow/dsl/_router.py:97`).
- **Why it works:** static tools and tests can pin every legal continuation; unknown states fail loudly instead of silently continuing.
- **When to copy:** any loop whose continuation decision has more than two outcomes (continue / finalize / pause / delegate).
- **When risky:** overkill for genuinely linear flows; also brittle if the vocabulary is stringly-typed without a registry — crewai's report notes renaming a router Literal silently breaks routing since emits are captured at definition time with no central registry.
- **Contrast:** letta's `should_continue` boolean set in six-plus places inside `_step()` shows what happens without this pattern — continuation semantics become emergent (per its report).

### 2. Superstep barrier aligned with the checkpoint boundary

- **Problem solved:** durability without torn state — you can snapshot exactly when no task is half-done.
- **Demonstrated by:** langgraph (per-superstep checkpoint after `apply_writes`, three Durability modes gating blocking behavior, `libs/langgraph/langgraph/pregel/_loop.py:1116-1189`); agent-framework (checkpoint created after each superstep in both stacks, `python/.../_runner.py:144`; convergence = checkpoint per its report); pydantic-ai (per-node snapshots via `BaseStatePersistence`, resume via `iter_from_persistence`, `pydantic_graph/pydantic_graph/graph.py:261`).
- **Why it works:** the barrier gives a globally consistent point where all writes have landed and none are pending.
- **When to copy:** long-running, resumable, human-in-the-loop workflows.
- **When risky/costly:** `sync` durability couples loop throughput to checkpoint latency (langgraph blocks the next tick on checkpoint persistence, `libs/langgraph/langgraph/pregel/main.py:3002-3003`); langgraph's `exit` mode needs a synthetic parent-checkpoint stub when no parent exists (`_loop.py:1201-1293`) — a non-obvious quirk its report calls out.

### 3. Transactional outbox connecting state change to follow-up work

- **Problem solved:** a crash between "state changed" and "follow-up task enqueued" cannot strand work.
- **Demonstrated by:** temporal — history events + mutable state + follow-up tasks written in one persistence call (`docs/architecture/history-service.md:319-321`); CHASM formalizes pure tasks (in-lock, no I/O) vs side-effect tasks (post-commit, must call back via `Engine.UpdateComponent`) around the same idea (`chasm/task.go:27-74`).
- **Why it works:** the queue processors become derivable, replayable consequences of committed state.
- **When to copy:** whenever correctness under crash/failover matters more than latency.
- **When overkill:** single-process in-memory agents; the cost is a persistence layer and task-drain machinery that simple loops don't need. None of the loop-based libraries attempt it in-process; pydantic-ai instead delegates durability to external engines (Temporal/DBOS/Prefect wrappers, `pydantic_ai_slim/pydantic_ai/durable_exec/temporal/_agent.py:301-370`).

### 4. Layered iteration caps at every loop layer

- **Problem solved:** non-convergence fails fast with a named error instead of burning tokens forever.
- **Demonstrated by:** agent-framework (workflow 100, `python/.../_const.py:4`; function calls 40, `_tools.py:90`; outer agent loop 10, `_harness/_loop.py:117`; judge loop 5, `_harness/_loop.py:122`); openai-agents-sdk (`MaxTurnsExceeded`, `src/agents/run.py:1066` and stream equivalent `run_loop.py:889-956`); langgraph (`recursion_limit` → `GraphRecursionError`, `libs/langgraph/langgraph/pregel/_loop.py:600-602`); letta (`DEFAULT_MAX_STEPS = 50`); crewai (`max_method_calls` RecursionError cap, `flow/runtime/__init__.py:3178-3185`; replan caps `experimental/agent_executor.py:984-992`).
- **Why it works:** cheap, local, easy to reason about.
- **Limits:** caps detect nothing about *why* the loop isn't terminating. Both openai-agents-sdk and agent-framework reports explicitly found no fingerprint-based cycle detection; langgraph relies solely on the user-set limit. Caps also misfire when legitimate fan-out exceeds the multiplier (crewai counts successful listener invocations toward `max_method_calls = max_iter * 10`).

### 5. Streaming as an additive view over the same state machine

- **Problem solved:** adding token/event streaming without forking the execution model.
- **Demonstrated by:** openai-agents-sdk (streaming swaps only the per-turn workhorse; same four `next_step` variants; `asyncio.Queue` + `QueueCompleteSentinel` termination, `src/agents/result.py:483-485`, `src/agents/run_steps.py:52-56`); pydantic-ai (`ModelRequestNode.stream` / `CallToolsNode.stream` are node-local async context managers, `pydantic_ai_slim/pydantic_ai/_agent_graph.py:606,1081`); letta (`stream()` mirrors `step()` with chunk-yielding, `letta/agents/letta_agent_v3.py:443-717`); agent-framework (.NET `ExecutionMode` OffThread/Lockstep/Subworkflow are delivery shapes over one `ISuperStepRunner`, `ExecutionMode.cs:5-23`).
- **Why it works:** the state machine stays single-sourced; streaming is presentation.
- **Cost:** mirror-path drift. openai-agents-sdk's report notes `run_single_turn` and `run_single_turn_streamed` share intent but not code and must be changed in lockstep (`AGENTS.md:58-66`); letta's duplicated `step()`/`stream()` bodies produced a real bug where `stop_reason=max_steps` is set only on the last iteration (`letta/agents/letta_agent_v3.py:394-395`).

### 6. Interruption/pause as persisted, resumable state

- **Problem solved:** human-in-the-loop and approvals survive process restarts.
- **Demonstrated by:** openai-agents-sdk (`NextStepInterruption` serialized into schema-versioned `RunState`, `CURRENT_SCHEMA_VERSION = "1.11"`, `src/agents/run_state.py:131-149`, resume re-enters the loop with `_current_step` pre-populated); langgraph (interrupts raised inside nodes become replayable `("__interrupt__", ...)` pending writes, `libs/langgraph/langgraph/pregel/_loop.py:806-834`); agent-framework durable host (`yield ctx.wait_for_external_event(request_id)` HITL pause, `orchestrator.py:863-900`); crewai (persisted paused-flow state via `CheckpointConfig` and `HumanFeedbackPending`).
- **Why it works:** pausing becomes just another legal continuation with a durable artifact, not an ad-hoc side channel.
- **When to copy:** any approval-gated tool use.
- **Gaps:** openai-agents-sdk's realtime session has its own approval lifecycle but no `RunState` parity (its report flags this); codex threads have no resumable state at all.

### 7. Compile-many-patterns-to-one-engine

- **Problem solved:** offering many user-facing orchestration styles without N engines.
- **Demonstrated by:** agent-framework (five orchestrators → same `Workflow`/`Runner` via shared builder base); langgraph (`StateGraph.compile`, functional `entrypoint`, and `create_react_agent` all lower to `Pregel`, `libs/langgraph/langgraph/graph/state.py:130`, `prebuilt/chat_agent_executor.py:789-990`); crewai (Plan-and-Execute implemented *as* a Flow); pydantic-ai (the ReAct cycle expressed as a 4-node graph).
- **Why it works:** one advancement story to test, instrument, and make durable; patterns become configuration.
- **Failure mode when absent:** letta's factory picks between three independently-evolving loop classes sharing ~80% shape (`letta/agents/agent_loop.py:15-63`), and its own report documents divergence in tool-rule handling, retry strategy, and approval flow as a top maintenance cost.

### 8. In-loop error routing instead of exception bubbling

- **Problem solved:** failures become recoverable transitions without unwinding the run.
- **Demonstrated by:** langgraph (node errors schedule a sibling error-handler task; `ERROR_SOURCE_NODE` markers drive handler routing on resume, `libs/langgraph/langgraph/pregel/_runner.py:226-243`, `_loop.py:739-804`); pydantic-ai (`ErrorMarker` lets capability hooks recover by sending replacement tasks, `pydantic_graph/pydantic_graph/graph_builder.py:134-143`); temporal (Ack/Nack with DLQ on terminal errors plus monitor/mitigator back-pressure, `service/history/queues/executable.go`, `mitigator.go`).
- **Why it works:** recovery policy sits where the state is.
- **Caution:** pydantic-ai's `wrap_run` short-circuit means "did the graph run?" is not always well-defined — power that needs discipline (its report's tradeoff).

### 9. Cooperative drain/cancel between steps

- **Problem solved:** stopping work cleanly at a consistent boundary instead of tearing mid-step.
- **Demonstrated by:** langgraph (`RunControl.request_drain` flips a flag observed by `tick()`, `libs/langgraph/langgraph/runtime.py:79-105`); openai-agents-sdk (`cancel(mode="immediate" | "after_turn")` checked each iteration, `src/agents/result.py:648-694`); letta (cancellation surfaces as a `cancelled` stop reason without aborting the underlying request).
- **When to copy:** any long-running loop exposed to interactive clients.

## Key Differences

**What converges despite different substrates.** All eight real sources bound their loops with explicit caps; all make advancement decisions somewhere inspectable; all treat human-in-the-loop/approvals as first-class; all layer streaming atop their base model rather than replacing it; and all mix multiple models. Even the purest loop (openai-agents-sdk) ships four sibling models (realtime listener router, voice pipeline, Codex subprocess, REPL), and the purest engine (temporal) is explicitly plural. The agentic think-act cycle itself is substrate-independent: pydantic-ai expresses it as graph edges, crewai as Flow router labels, openai-agents-sdk as `NextStepRunAgain`, letta as `should_continue`.

**Where they diverge, and why.**

- *Library SDKs optimize explainability.* openai-agents-sdk and pydantic-ai expose one entry verb family (`run`/`run_streamed`, `run`/`iter`/`run_stream`) with a model a newcomer learns in two sentences — appropriate because their users embed the harness in arbitrary code (openai-agents-sdk report's contributor test).
- *Orchestration frameworks optimize durable multi-agent graphs.* langgraph and agent-framework adopt BSP because the superstep barrier doubles as the snapshot boundary and cycles/fan-out are first-class — a fit for "long-running agents with human-in-the-loop checkpoints" (langgraph report) and "graph-based collaboration patterns" (agent-framework report).
- *Durable infrastructure optimizes crash correctness.* temporal chooses event-sourced state machines plus queues because shard ownership, replication, and worker delivery dominate; long-poll beats push to avoid fan-out storms (temporal report). Latency-per-turn is not the objective function.
- *Platforms split control plane from runtime.* openhands pushes the loop into a sandboxed sidecar so the app_server stays HTTP-only and SDK-replaceable — right for hosted SaaS, at the cost of an implicit cross-repo model and reconciliation machinery (webhook + polling dual path).
- *Multi-tenant servers embed loops amid operations.* letta wraps its loop in credit checks, Redis conversation locks, SSE keepalive, and batch offload — product requirements the libraries don't carry, which partly explains (though doesn't excuse, per its report) implementation sprawl.

These are constraint-driven differences, not quality rankings: openhands' 6 reflects an undocumented seam, not a wrong architecture, and temporal's complexity is intrinsic to its guarantees.

## Tradeoffs

- **Turn loop vs graph substrate.** openai-agents-sdk's `while True` + discriminant union keeps vocabulary minimal and control dynamic, but adding a `NextStep*` variant means editing every dispatch site (its report names this maintenance cost). langgraph/pydantic-ai make structure statically visible, render diagrams (Mermaid, `pydantic_graph/pydantic_graph/graph.py:336`), and resume per node — at the price of heavier concepts (channels, forks, joins, decisions) that pydantic-ai's docs themselves warn not to use unnecessarily.
- **One engine with compiled patterns vs parallel native implementations.** agent-framework compiles Magentic/group-chat/handoff to one Workflow; letta maintains `LettaAgent`/`V2`/`V3` (1983/1487/2134 lines per its report) plus Voice/Batch variants with no shared continuation abstraction. The first scales features; the second accretes bugs — letta's post-loop fallback misclassifies exceptions as `end_turn` precisely because stop-reason logic is duplicated (`letta/agents/letta_agent_v3.py:394-395,:412-413`).
- **Numeric caps vs convergence termination.** Most sources cap iterations; agent-framework's workflow and langgraph terminate on absence-of-work/messages, which is elegant but means runaway graphs surface only via `WorkflowConvergenceException` or `recursion_limit` — neither system detects cycles structurally (both reports note this gap).
- **In-process loop vs out-of-process runtime.** openhands gains a clean seam (SDK iterates independently, version-checked at `live_status_app_conversation_service.py:874-919`) but pays with dual sources of truth, webhook-loss risk with silent message deletion on failed delivery (`live_status_app_conversation_service.py:1996-2003`), and a module-global polling task with no supervisor (`remote_sandbox_service.py:924-932`). letta's Lettuce offload stub shows the same ambition without evidence of the interaction semantics being solved (its report's open question).
- **Shared mutable state vs message passing.** pydantic-ai passes one `GraphAgentState` by reference to every node — easy coordination, hard isolation (mutation-in-place is a documented invariant, `_agent_graph.py:1431-1456`). langgraph communicates only through channel updates with versioned triggers — strict barriers, amortized cost via a trigger index (`pregel/main.py:4190-4196`). crewai compromises with lock-wrapped `StateProxy` proxies because sync bodies run on threads (`flow/runtime/__init__.py:353-664`).
- **Durability coupling.** langgraph's `sync` durability trades throughput for strictness (blocks next tick on checkpoint persistence); `exit` accumulates delta writes needing synthetic anchoring. Temporal makes durability non-negotiable and accepts per-shard rebalancing complexity during upgrades (its report).
- **Two-language mirroring.** agent-framework duplicates its engine across Python/.NET with no shared core (explicit finding: "No shared cross-language execution engine"); every new edge-group type is implemented twice. Parity gaps follow — .NET's workflow runner lacks the numeric iteration cap Python has.

## Decision Guide

Rules distilled from the comparative evidence:

1. **Building an embedded agent library?** Use a turn-discriminated step loop (openai-agents-sdk pattern): one outer loop, a typed union of continuations, streaming as a swapped workhorse. Copy its exhaustive per-variant tests (`tests/test_run_step_execution.py:2749-2780`).
2. **Need inspectable/durable/resumable control flow, or multi-agent fan-out?** Adopt a superstep graph (langgraph/agent-framework) or a small typed FSM (pydantic-ai). If you want the ReAct feel, express the cycle *as* graph nodes (pydantic-ai's 4-node graph) rather than bolting a loop beside a graph.
3. **Correctness under crash/failover/shard loss is the product?** Event-sourced state machine + transactional outbox + queue processors (temporal). Do not try to retrofit this onto an in-memory loop; instead wrap the loop externally as pydantic-ai does with its Temporal/DBOS/Prefect subclasses.
4. **Hosted multi-user platform?** Keep the loop in-process but gate concurrency per conversation (letta's Redis lock, `letta/services/streaming_service.py:269-329`); split control plane from runtime (openhands) only when SDK replaceability/sandboxing demands it — and if you do, document the seam prominently and make webhook ingestion durable before trusting it.
5. **Realtime/voice latency trumps durability?** Accept a separate event-listener model (openai-agents-sdk realtime session) knowing it forfeits the turn loop's resume machinery — a documented, deliberate trade there.
6. **Batch/offload workloads?** Give them an explicit alternate loop shape with its own resume protocol (letta's `step_until_request`/`resume_step_after_request`; MAF's durable orchestrator `ctx.task_all` per superstep) rather than contorting the foreground loop.
7. **Whenever you ship more than one loop:** ensure they share the advancement vocabulary (one stop-reason enum, one interrupt representation). This is the single discriminator between the 9s and the 5–7s in this cohort.

## Practical Tips

- **Name the model where contributors will read it.** langgraph's `Pregel` docstring and MAF's `"Pregel supersteps"` module docstring (`_runner.py:31`) mean a newcomer gets the model before reading a line of logic. OpenHands' report lists the missing pointer to the external agent_server as its top documentation fix.
- **Put continuation in a type, not a boolean.** Prefer openai-agents-sdk's four-variant union or temporal's validated transition tables over letta-style `should_continue` scattered through `_step()`.
- **Align your persistence boundary with your loop boundary.** Superstep = checkpoint (langgraph/MAF) or turn = serializable state (openai-agents-sdk `RunState`); per-node snapshots if you need finer grain (pydantic-ai).
- **Give every loop layer its own cap and a named exhaustion error.** MAF's 100/40/10/5 ladder shows the granularity worth copying; pair it with a forced final call (`tool_choice="none"`) so bounded runs end with usable output (`_tools.py:2665-2683`).
- **Make streaming additive early.** Decide on day one that streaming shares the base state machine (OAI/pydantic-ai style); retrofitting mirror loops later is how letta accumulated duplicated bodies and stop-reason bugs.
- **Route recoverable errors back into the loop.** Error-handler tasks (langgraph), `ErrorMarker` + replacement tasks (pydantic-ai), or DLQ/mitigator (temporal) beat try/except wrapping the whole run.
- **Hide retry/fallback behind abstractions.** Both letta and its report recommend lifting inlined summarizer-retry and circuit-breaker logic out of `_step()`; pydantic-ai's capability middleware (`wrap_run`, `on_node_run_error`) is the cleanest observed hook surface for cross-cutting concerns.

## Anti-Patterns / Caution Signs

Observed failure modes worth treating as warnings:

- **Parallel near-identical loop implementations** (letta V1/V2/V3; crewai's four vocabularies; OAI's mirrored streaming/non-streaming turn functions). Caution sign: a factory whose branches "all basically do the same thing."
- **Deprecated-but-live paths.** crewai's ReAct executor is deprecated yet still drives `LiteAgent`, silently denying those users planning/parallelism — undeprecated siblings must be migrated or gated.
- **Stop-reason misclassification.** Defaulting an unset `stop_reason` to `end_turn` conflates success with failure (letta). Always distinguish "completed" from "crashed before deciding."
- **Enum-order-dependent control flow.** letta's `StepProgression` integer comparisons couple error recovery to declaration order — fragile.
- **Global lazy background tasks without supervisors.** openhands' module-global polling task starts on first request and only dies on `CancelledError`.
- **Ack-before-durable-write and delete-on-failed-delivery.** openhands' webhook handler and pending-message replay can silently lose events; both flagged for dead-letter/outbox treatment.
- **Recursion caps that count legitimate work.** crewai's global `max_method_calls` punishes router-heavy plans that fan out legitimately.
- **Unbounded buffering under pathological fan-out.** MAF's unbounded .NET event channel (with `Lockstep` as countermeasure) — size your streaming buffers.
- **Leaky seams patched in code comments.** openhands injecting `user_id` into JSON because the pinned SDK lacks the field is a recurring-smell warning: bump or vendor the contract instead.
- **Coarse-grained safety heuristics.** crewai's parallel-tool gating checks only `result_as_answer`/`max_usage_count`; mutating tools can still race.

## Notable Absences

- **No cycle detection anywhere.** Neither openai-agents-sdk nor agent-framework found any fingerprint-based loop detector; langgraph relies purely on `recursion_limit`. Every source terminates via caps or convergence, never via structural repetition detection.
- **No unified sibling-model abstraction in openai-agents-sdk.** Realtime, voice, and Codex share no state, hooks, or resume semantics with the turn loop; only `SingleAgentVoiceWorkflow` delegates back into `Runner.run_streamed`.
- **No in-repo agent loop in openhands** — the closest analog is the poller's `while True` (`remote_sandbox_service.py:699`), which polls conversations, not turns.
- **Letta has no unified streaming entrypoint** and no shared abstraction between its singleton step loop and the batch mode's map-of-continuations (`letta/agents/letta_agent_batch.py:66`).
- **Temporal lacks a single cross-cutting execution-model document**; each architecture doc covers a slice, leaving the end-to-end narrative implicit (its report's first gap).
- **No shared engine across MAF's languages**, and no numeric iteration cap on the .NET workflow runner (parity gap).
- **The `reports` source contains nothing**: zero files, verified by logged zero-result searches. Its report recommends pre-flight validation that rejects zero-file sources before consuming task budget — a pipeline-level anti-pattern now on record.
