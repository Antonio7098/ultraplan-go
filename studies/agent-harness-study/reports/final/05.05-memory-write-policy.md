## Executive Summary

Across four sources, memory writing is consistently treated as a deliberate subsystem with enumerated triggers — but the *policy* layer is thin everywhere it matters. Three of four sources (agent-framework, crewai, letta) converge on the same core mechanism: an LLM acts as the gatekeeper that decides what is durable enough to remember, backed by structural validation (JSON schemas, exact-match edit checks, embedding-dimension guards), and semantic conflict resolution is deferred to a later LLM consolidation pass rather than checked at write time. The fourth (openhands) contributes a different lesson: consent as policy — persistent memory is default-off and requires explicit user opt-in before any write machinery activates at all.

The sharpest convergence is in what all sources lack: none screens sensitive facts before storing (crewai's extractor prompt even labels users' personal facts "HIGH PRIORITY and must always be extracted" — `lib/crewai/src/crewai/translations/en.json`, key `memory.extract_memories_system`); none gates individual memory writes behind user approval by default, despite three of four shipping generic approval mechanisms they simply never wire to memory; and confidence metadata exists only at agent-framework's Cosmos integration edge (`python/packages/azure-cosmos-memory/agent_framework_azure_cosmos_memory/_context_provider.py:97`), external to every studied write path.

Where sources diverge — fail-open vs fail-closed persistence, tool-mediated edits vs pipeline extraction, always-on vs frequency-gated vs consent-gated triggers — the differences track product shape (library vs hosted server vs frontend), not quality. All three framework sources land at 7/10: clear models with real operational safeguards, held back by absent approval flows, absent sensitive-fact handling, and missing trust metadata. Openhands scores 5/10 because its observable surface contains only the consent gate; the actual write policy lives outside its boundary.

## Core Thesis

**No source verifies *truth* before remembering — every mature write policy in this study validates only *form*, and delegates durability judgment to prompts.** The state of the art across these four codebases is: structural validation of the write operation (schema checks in agent-framework `_memory.py:1424-1459`, uniqueness/exact-match checks in letta `core_tool_executor.py:380-391`, pydantic-constrained analysis in crewai `analyze.py:37-56`), plus prompt-level instructions about what deserves to be remembered (agent-framework `_memory.py:44-56`; letta `sleeptime_v2.py:1-39`; crewai `en.json`). Contradictions are not detected at write time anywhere; they are reconciled later by probabilistic LLM consolidation (agent-framework `_memory.py:1575-1657`; crewai `analyze.py:321-375`) or never (letta's archival tier, which has no reconciliation at all). Meanwhile, the safety properties that would make remembering trustworthy — approval gates, sensitive-fact screening, confidence/provenance metadata — exist as unused mechanisms or are absent entirely. A team copying these systems inherits sophisticated write plumbing around an unverified content channel.

## Approach Models

Four distinct models for deciding when memory gets written:

- **agent-framework — portfolio-of-policies on a shared lifecycle.** A common `before_run`/`after_run` provider contract hosts multiple writers with different policies: the flagship harness `MemoryContextProvider` runs post-turn LLM extraction capped at 5 items (`python/packages/core/agent_framework/_harness/_memory.py:40,1444`); `FileMemoryProvider` gives the model raw file CRUD tools and is on by default (`python/packages/core/agent_framework/_harness/_agent.py:185-187`); Foundry/mem0/Cosmos providers forward whole turns and delegate "what's worth remembering" to backing services. One framework, four write philosophies.
- **crewai — staged encoding pipeline.** Every write, regardless of trigger (automatic post-task, `RememberTool`, developer API), funnels through one five-stage `EncodingFlow`: batch embed → intra-batch dedup (≥0.98 cosine) → similar-record search → parallel LLM analysis → plan execution (`lib/crewai/src/crewai/memory/encoding_flow.py:112-501`). Uniformity is the point: automatic, tool, and API paths all get identical treatment.
- **letta — typed memory tools with editor semantics.** The model writes only through purpose-built tools (`core_memory_append`, `memory_replace`, `memory_apply_patch`, `memory_rethink`, ...) whose validation mirrors a code editor: replacements must match exactly once, view artifacts like line numbers are rejected, null bytes sanitized (`letta/services/tool_executor/core_tool_executor.py:346-773`). Background sleeptime agents run on a turn-frequency counter (`letta/groups/sleeptime_multi_agent_v4.py:132-148`). Write surface is enumerable and permission-scopable via `read_only` flags.
- **openhands — capability gate, mechanics delegated.** The entire in-repo policy is one boolean: `agent_context.load_memory`, schema-defaulted false, requiring explicit Settings save (`src/mocks/settings-handlers.ts:364`; `src/components/features/settings/sdk-settings/sdk-section-page.tsx:718-732`). Extraction/validation/conflict logic lives in the sibling `software-agent-sdk` repo and was out of boundary.

These map cleanly onto product shape: the library (crewai) standardizes a pipeline so all entry points behave alike; the multi-package framework (agent-framework) embraces pluralism because integrations have different backends; the hosted agent server (letta) invests in precise, auditable edit operations because memory directly mutates system prompts; the frontend (openhands) owns only consent because ownership of mechanics sits elsewhere.

## Pattern Catalog

### P1. LLM-as-gatekeeper extraction with structural-only validation
- **Problem:** Deciding what is worth remembering from unbounded conversation without human review.
- **Demonstrated by:** agent-framework (extraction prompt returning JSON candidates, item-by-item schema validation, cap of 5 — `_memory.py:44-56,1424-1459,1444`); crewai (structured-output `ExtractedMemories` extraction then constrained `MemoryAnalysis` field inference — `analyze.py:155-197,267-315`); letta (sleeptime prompts instructing selective edits — `sleeptime_v2.py:4-39`).
- **Why it works:** Caps volume cheaply, keeps the durability judgment in an overridable prompt rather than hard-coded rules, and structural validation catches malformed output before it corrupts stores.
- **When to copy:** Any auto-extraction design; pair with explicit caps and schema validation as all three sources do.
- **When risky:** When "durable" is left entirely to prompt wording — hosts overriding extraction prompts inherit full quality responsibility (agent-framework report, Tradeoffs), and nothing grounds facts in any source.
- **Evidence:** See citations above; all three reports answer dimension Q3 ("Are facts verified?") with variants of "structurally, never semantically."

### P2. Deferred consolidation with conservative defaults instead of write-time conflict checks
- **Problem:** New memories contradicting stored ones without blocking the write path.
- **Demonstrated by:** agent-framework (consolidation gated on ≥N sessions AND ≥24h, window preserved on failure — `_memory.py:39-41,1541-1549`); crewai (similarity ≥0.85 routes to consolidation producing keep/update/delete plans with prompt-level "be conservative: prefer 'keep'" — `unified_memory.py:116-123`; `analyze.py:321-375`).
- **Why it works:** Keeps writes fast; lets evidence accumulate before judging conflicts; crash-safe windows mean transient failures don't silently skip maintenance (agent-framework test `test_harness_memory.py:799-834`).
- **When to copy:** Long-lived agents where stale-preference drift matters more than instant consistency.
- **When risky:** Append-first merging means a corrected preference coexists with the stale one until consolidation fires (agent-framework `_merge_memory` appends without contradiction checks, `_memory.py:1494-1501`); a wrong LLM delete verdict permanently destroys records (crewai deletes execute first, `encoding_flow.py:453-455`); letta's archival tier has no reconciliation whatsoever.

### P3. Consent gate ahead of any write machinery
- **Problem:** Persistent cross-session state being created without the user ever asking for it.
- **Demonstrated by:** openhands (default-off toggle, off-by-default pinned by test, frontend defaults omit the config entirely — `src/mocks/settings-handlers.ts:364`; `__tests__/routes/agent-context-settings.test.tsx:43-53`; `src/services/settings.ts:35-52`).
- **Why it works:** Makes remembering an explicit grant; contrasts sharply with forgetting, which in the same repo is automatic and default-on via condensation (`src/services/settings.ts:18-19`) — "forgetting is default-on; remembering is default-off."
- **When to copy:** Products where agents touch user workspaces or personal preferences; regulated environments.
- **When overkill:** Developer libraries where the deploying developer *is* the consenting party (crewai's `read_only` flag serves the analogous role there).

### P4. Actor-attributed audit trails for memory mutations
- **Problem:** Answering "who wrote this memory" after the fact.
- **Demonstrated by:** letta most concretely — `BlockHistory` snapshots record `actor_type`/`actor_id` (LETTA_AGENT vs LETTA_USER) with monotonic sequence, feeding undo/redo (`letta/orm/block_history.py:36-39`; `block_manager.py:842-911`) and attributed git commits (`git_operations.py:351-409`); crewai emits `MemorySaveStarted/Completed/FailedEvent` with agent_role and timing (`events/types/memory_events.py:53-79`); agent-framework tags records with `session_ids`/`updated_at` (`_memory.py:349-358`).
- **Why it works:** Attribution converts opaque mutation into a correctable, diffable history.
- **When to copy:** Whenever memory feeds prompts — attribution is prerequisite for trust-weighted retrieval.
- **Gap:** crewai's consolidation `reason` fields are computed then discarded, not persisted (`lancedb_storage.py:270-287` carries no reason column).

### P5. Concurrency discipline tuned to write shape
- **Problem:** Multiple writers racing on shared memory.
- **Demonstrated by:** agent-framework per-topic asyncio locks with state locks released before long LLM calls (`_memory.py:1025-1050,1513-1526`) plus idempotent index writes skipped when unchanged (`_memory.py:834-835`); crewai single-worker save pool with drain barriers before recall (`unified_memory.py:165-171,350-364`); letta fresh DB reads per persist plus Redis-locked linear git commits (`agent_manager.py:1759`; `git_operations.py:351-377`).
- **Why it works:** Each matches granularity to its store: file topics parallelize across locks, vector saves serialize cheaply, prompt-bearing blocks get optimistic freshness checks.
- **When to copy:** Always — but choose the mechanism by contention profile, not fashion.
- **Failure mode if absent:** letta documents residual last-writer-wins between main and sleeptime agents on shared blocks (`agent_manager.py:1776-1778` comment acknowledges the race).

### P6. Untrusted-channel injection of derived memories
- **Problem:** Poisoned or hallucinated memories becoming persistent instructions.
- **Demonstrated by:** agent-framework — harness memory context injected as user-role messages, never system instructions (`_memory.py:1332-1344`), Cosmos summaries framed as untrusted reference data (`azure-cosmos-memory/_context_provider.py:389-412`); markdown heading-escaping prevents stored LLM output forging section markers on read-back (`_memory.py:107-111`).
- **Why it works:** Treats yesterday's model output as today's untrusted input — the write policy's downstream consequence made safe at the read boundary.
- **When to copy:** Every time remembered content re-enters a prompt.

### P7. Capability removal as opt-out
- **Problem:** Disabling writes without intercept-and-reject complexity.
- **Demonstrated by:** crewai `read_only` makes writes silent no-ops *and* removes the `RememberTool` from the model's toolset (`tools/memory_tools.py:104-130`; `unified_memory.py:148-151`); letta's per-block `read_only` flags enforced pre- and post-execution (`core_tool_executor.py:320-321`; `agent.py:190-198`).
- **Why it works:** Not offering the tool beats rejecting calls to it.
- **Caveat:** Silent no-op writes give callers no signal their write was dropped (crewai report, Tradeoffs).

## Key Differences

**Trigger philosophy: coverage vs consent vs cadence.** agent-framework wires `FileMemoryProvider` into every harness agent by default (`_agent.py:185-187`) and crewai writes after *every* completed task with no salience budget (`base_agent_executor.py:42-63`) — both maximize capture. letta gates background rewriting on a tunable turn counter (`sleeptime_multi_agent_v4.py:139-146`) — cost control. openhands requires explicit opt-in before anything (`settings-handlers.ts:364`) — consent control. Same capability, three different defaults driven by whether the deployer is a developer (library), operator (server), or end user (product).

**Write granularity: records vs blocks vs files.** crewai mutates vector records via LLM-produced plans (keep/update/delete per record, `encoding_flow.py:371-451`); letta mutates prompt-bearing blocks via deterministic string operations with exactly-once matching (`core_tool_executor.py:380-391`); agent-framework appends lines to per-topic markdown files (`_memory.py:1472-1503`). The choice follows what memory *does*: retrieval ranking favors record ops; live prompt composition demands editor precision; human-inspectable notes favor plain files.

**Failure stance: fail-open vs fail-closed.** crewai deliberately persists on every LLM-analysis failure with safe defaults ("never lose the observation" — `analyze.py:309-315,369-375`), accepting noise precisely when the LLM is degraded. agent-framework does the opposite for extraction/consolidation: transient errors skip the write but preserve retry state, while transcript archiving still captures the raw content (`_memory.py:1420-1422,1541-1549`). Both positions are defensible; they optimize different losses (data loss vs retrieval pollution). letta splits the difference mechanically — edit operations fail loudly on mismatch, but archival embeddings degrade silently to None (`passage_manager.py:572-582`).

**Correction surface richness.** letta offers REST block PATCHes, undo/redo checkpoints, git history, and read-only protection of user-authored content (`blocks.py:157-166`; `block_manager.py:842-911`; `schemas/block.py:36`). crewai exposes programmatic `update`/`forget`/`reset` plus an opt-in HITL loop that distills feedback into lessons (`unified_memory.py:852-896,1015-1035`; `human_feedback.py:301-359`). agent-framework relies on the model itself ("read then correct topic files" per injected instructions, `_memory.py:1306`) or hand-editing documented markdown. openhands users can only flip the global toggle — no list/edit/delete UI exists (`settings-nav.tsx:38-49`).

## Tradeoffs

- **Automatic capture vs curation.** crewai writes after every task for zero-effort coverage, but admits "long-running crews accumulate everything" with no salience gate beyond the extractor prompt; agent-framework caps extraction at 5/turn yet archives full transcripts unconditionally (`store_inputs`/`store_outputs` default true, `_memory.py:988-994`). Alternative: openhands' consent gate trades discoverability for safety — most conversations "never benefit from learned preferences, but also never leak state across sessions without consent."
- **Durability vs accuracy under failure.** crewai's fail-open guarantees observations survive LLM outages but stores unanalyzed blobs and default-importance rows exactly when quality control is weakest (`analyze.py:191-197`). agent-framework's fail-closed extraction keeps curated stores clean at the cost of skipping extraction for degraded turns.
- **Model autonomy vs memory integrity.** letta grants whole-block rewrite (`memory_rethink`) and block lifecycle commands, so "a hallucinated 'correction' silently destroys good memory"; recovery is manual undo/git only. Contrast agent-framework, where the model can append freely but cannot overwrite topic files wholesale through the primary path — merge is append-only under lock.
- **LLM-judged conflicts vs deterministic rules.** Semantic consolidation (crewai, agent-framework) reconciles paraphrased contradictions that exact-duplicate dedup cannot, but a wrong verdict is unrecoverable in crewai's case (deletes execute first) and merely delayed in agent-framework's (both lines persist until consolidation). letta avoids LLM judgment in the edit path entirely, gaining determinism but losing any contradiction resolution in archival memory.
- **Soft limits vs enforcement.** letta renders `chars_current/chars_limit` as advisory prompt metadata and enforces nothing — flexible for legitimate reorganizations, but unbounded growth surfaces only as context-window errors elsewhere (`llm_api/error_utils.py:22`), and `bulk_update_block_values_async`'s docstring claims enforcement that doesn't exist (`block_manager.py:797-836`). agent-framework enforces counts (extraction caps, index line limits) but not content length either.
- **Background latency hiding vs error surfacing.** crewai's async saves keep agents responsive but failures surface as events, not exceptions (`unified_memory.py:535-559`); agent-framework's fire-and-forget Foundry updates swallow errors to logs (`foundry/_memory_provider.py:274-276`). Producers stay fast; silent write loss becomes possible in both.

## Decision Guide

Choosing a memory write policy:

1. **Who consents?** If end users own the data being remembered, start from openhands' model: default-off capability gate with tested propagation, *then* pick mechanics. If the deploying developer is the consenting party, a library flag (crewai `read_only`) suffices.
2. **What does memory feed?** If remembered content is composed into live system prompts (letta's situation), demand editor-grade deterministic edit semantics, read-only guards enforced pre- and post-execution, and attributed history before granting autonomy. If it's retrieved as context, pipeline-based record writes with dedup thresholds are adequate.
3. **One trigger class or many?** If you support automatic, tool-invoked, and API writes simultaneously, copy crewai's funnel-everything-through-one-pipeline structure — divergent per-path policies (as in agent-framework's portfolio) are justified only when backends genuinely differ.
4. **Fail-open or fail-closed on extractor outage?** Fail-open (crewai) when losing an observation is worse than storing noise; fail-closed with preserved retry windows (agent-framework) when store cleanliness matters or a transcript archive already captures raw content anyway. Make the choice configurable — neither source did.
5. **Conflict resolution at write time or deferred?** Deferred wins in all four sources: write-time contradiction checking doesn't appear anywhere, and both implementing sources route conflicts to similarity-triggered consolidation. If you need stronger guarantees, you're inventing beyond this evidence base.
6. **Approval gating:** Every framework here shipped the generic mechanism and declined to wire it to memory. If your memories influence consequential behavior, do what none of them did — set the existing flag (`letta/schemas/tool.py:59-61` pattern) or mirror `FileAccessProvider`'s `always_require` default for memory mutations (agent-framework `_file_access.py:1447` contrast).

## Practical Tips

- **Cap extraction volume explicitly.** agent-framework's three-level caps (≤5 extracted items/turn, ≤200 index lines, ≤50 FileMemory entries — `_memory.py:40`; `_file_memory.py:78`) are the only write-amplification controls found in the study.
- **Validate extractor output per-item, not per-batch.** Skipping invalid items with warnings while keeping valid ones (`_memory.py:1427-1459`) beats all-or-nothing rejection.
- **Make maintenance windows crash-safe.** Advance the consolidation cursor only after at least one topic succeeds, preserving it otherwise (agent-framework `_memory.py:1541-1549`, proven by `test_harness_memory.py:799-834`).
- **Separate extraction from commitment.** crewai documents `extract_memories()` as "a pure helper — it does NOT store anything" (`unified_memory.py:667-679`); this decoupling enables dry-run policy testing.
- **Add a read barrier before recall.** Draining pending background saves before searching prevents just-written records going missing (crewai `unified_memory.py:350-357`).
- **Escape persisted LLM output against your storage format.** Heading-escaping in agent-framework prevents stored text from forging document structure on read-back (`_memory.py:107-120`) — the write-path analog of XSS escaping.
- **Attribute writes to an actor from day one.** Retrofitting provenance is painful; letta's `BlockHistory.actor_type/actor_id` shows the minimal viable version (`orm/block_history.py:36-39`).
- **Keep secrets on a separate channel from memory configuration.** Openhands enforces `request.secrets` as the sole credential path and pins it by test (`agent-server-adapter.test.ts:561-566`).
- **Give background failures an event, not silence.** crewai's `MemorySaveFailedEvent` (`unified_memory.py:324-348`) is the study's best observability hook for dropped writes.

## Anti-Patterns / Caution Signs

- **Approval mechanisms that skip memory.** agent-framework registers all six memory tools `approval_mode="never_require"` while its own `FileAccessProvider` defaults file-write tools to `always_require` (`_memory.py:1223,1240,1266` vs `_file_access.py:1447`) — the asymmetry is visible in one codebase. Caution sign: generic approval infra exists but memory paths bypass it.
- **Docstring claims enforcement that code doesn't perform.** letta's `bulk_update_block_values_async` promises a `ValueError` on limit violation that never raises (`block_manager.py:797-836`). Caution sign: advertised constraints diverging from behavior.
- **Extraction prompts that prioritize sensitive capture.** crewai's extractor labels personal facts "HIGH PRIORITY and must always be extracted" with no compensating redaction anywhere (`en.json`, key `memory.extract_memories_system`). Caution sign: policy prompts optimizing for recall of personal data.
- **String-matched exclusion filters.** crewai excludes delegation outputs by matching exact formatted text `"Action: Delegate work to coworker"` — brittle against upstream wording changes (`base_agent_executor.py:40-41`).
- **Dual implementations of the same write op with divergent guards.** Legacy letta `core_memory_append` skips the read-only check its native counterpart performs (`functions/function_sets/base.py:246-260` vs `core_tool_executor.py:320-321`). Caution sign: two code paths for one mutation.
- **Silent capability removal.** crewai's `read_only` no-ops return `None`, indistinguishable from success — callers can't detect dropped writes.
- **Consent without revocation.** Openhands disabling the toggle stops future writes but offers "no purge of existing `.openhands/memory/` content" — consent granted once, data persists indefinitely.
- **Unchunked append-only archival.** letta inserts oversized text as one passage with an open TODO for token-count validation and falls back to None embeddings on failure (`passage_manager.py:562-593`).

## Notable Absences

Absent across *all* sources unless noted:

- **Sensitive-fact exclusion at write time:** no redaction/scrubbing/PII logic found in any write path (all four reports searched independently). Only read-path mitigations exist: agent-framework's untrusted framing (`_context_provider.py:389-412`), crewai's `private` visibility flag — which restricts recall, not storage, and is never set by the auto-write path (`encoding_flow.py:47,55`).
- **Memory-specific approval gates:** all generic mechanisms (agent-framework `ToolApprovalMiddleware`, letta `default_requires_approval`, crewai `tool_hooks`) exist unwired to memory. Openhands is the sole source with a real gate — at capability level only.
- **Confidence metadata:** present only in agent-framework's Cosmos edge via external toolkit (`_context_provider.py:97`); crewai's `importance` is a retrieval-ranking weight, explicitly *not* truth confidence (`types.py:40-45`); letta and openhands have none. Consolidation reasons in crewai are computed and discarded.
- **Fact verification / grounding:** no source cross-examines new memories against sources or existing knowledge; verification is uniformly syntactic.
- **TTL/expiry policies:** deletion is caller-driven or LLM-consolidation-driven only (crewai gap note; letta archival has no supersession).
- **Per-write observability events:** crewai has save lifecycle events; agent-framework emits only a feature-usage telemetry mark (`_memory.py:1176`); openhands notes condensation has event types while memory writes have none.
- **Test coverage of write-validation branches:** letta found no unit tests exercising native executor validation (uniqueness, read-only, artifact rejection); agent-framework is the counter-example with disk-full, concurrency, and transient-failure tests (`test_harness_memory.py:640-859`).

## Per-Source Notes

- **agent-framework (7):** Most operationally hardened write path in the study — atomic temp-file replaces tested against simulated disk-full, per-topic locking with concurrent-write survival tests, failure-mode triage distinguishing transient (swallow+warn, preserve retry window) from programmer errors (propagate). Its portfolio approach means policy quality varies by provider: the harness extractor is deliberate; pass-through providers (Foundry/mem0/.NET ChatHistory) store everything non-empty and shift trust outward. Confidence exists only via the external Cosmos toolkit; .NET lacks any extraction-style curation.
- **crewai (7):** Cleanest architectural statement — every trigger funnels through one inspectable `EncodingFlow` built on the framework's own Flow engine, with grouped fast-paths minimizing LLM calls per write (group A needs zero). Fail-open philosophy is explicit and tested (`test_remember_survives_llm_failure`). Namespacing by construction (`/crew/<name>`, `/flow/<name>`, `/agent/<role>`) bounds conflict-resolution domains. Weaknesses: fail-open stores raw blobs on outage; first-wins action collapse discards competing intents; zero-vector rows occupy the store unfindably.
- **letta (7):** Richest correction and audit story — REST block PATCHes, undo/redo with actor attribution, git-backed linear history under Redis locks, read-only blocks protected pre- and post-execution. Editor-metaphor tools coach the model toward correct usage via error messages. Weakest spots: advertised-but-unenforced size limits, legacy/native implementation drift, append-only archival with acknowledged TODOs, no unit tests on write-validation branches.
- **openhands (5):** Scored strictly on its own boundary: a well-tested consent gate (default-off, diff-based PATCH, propagation pinned on inline and profile launch paths) plus architectural secrets/memory channel separation. Everything else — extractors, validation, conflict handling, confidence, per-write approval, correction UI — lives in the sibling `software-agent-sdk` and is explicitly flagged as unverifiable here. Its contribution to this dimension is the consent pattern and the principle that forgetting is default-on while remembering is default-off.

## Open Questions

- **Is autonomy-by-default intentional policy or drift?** agent-framework's uniform `never_require` on memory tools is undocumented in-repo; letta found no shipped configuration setting `default_requires_approval=True` on memory tools despite the mechanism existing.
- **Can consolidation actually see contradictions?** agent-framework consolidates per-topic, so a contradictory pair split across topics may never be judged together (source report gap note); crewai's consolidation searches are bounded by scope and a similarity threshold — below-threshold redundant records coexist by design.
- **How is Cosmos confidence computed?** Outside the studied boundary (external `azure-cosmos-agent-memory` dependency) — the only confidence mechanism in the study is a black box here.
- **Do main/sleeptime agents race on shared letta blocks at scale?** Fresh DB reads mitigate but static reading could not establish concurrency guarantees (`agent_manager.py:1776-1778`).
- **What happens to `.openhands/memory/` contents when the toggle is disabled?** Deletion semantics unknown from the frontend source.
- **Does the software-agent-sdk (openhands' sibling) implement the fact-level machinery this dimension asks about?** A companion study would be required; the frontend evidences only the gate.
- **Would strict-mode persistence (quarantine on analysis failure) serve compliance-sensitive deployments better than crewai's unconditional fail-open?** Neither source implements configurability here; the tradeoff is documented but unresolved.
