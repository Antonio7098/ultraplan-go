## Executive Summary

All six sources have converged on MCP as *the* external tool protocol, but they occupy four distinct positions on how to adopt it. openai-agents-sdk (9/10) ships a first-class dual-mode client — local sessions over stdio/SSE/Streamable HTTP plus a hosted tool delegated to the provider — with the deepest failure-mode engineering in the study (~10,800 lines of MCP tests; openai-agents-sdk: `tests/mcp/test_server_errors.py`). agent-framework (8/10) pairs a full client stack with an explicit "MCP servers are untrusted third parties" posture: deny-by-default sampling, approval modes that resolve ambiguity toward approval, origin-scoped header injection, and schema-derived argument allowlists. pydantic-ai (8/10) makes external tools just another composable toolset behind wrapper combinators and adds provider-native relays so one URL works across providers. crewai (8/10) built a first-party client whose signature move is structural failure isolation: a fresh client per invocation, proven by tests after shared clients produced anyio cancel-scope crashes. langgraph (5/10) deliberately implements almost nothing in-repo — hosted-MCP specs pass through as opaque dicts, MCP-client duty belongs to ecosystem packages, and serving agents as MCP endpoints is a config contract over a closed-source server. openhands (8/10) is the outlier shape: as a product frontend it owns none of the wire protocol but excels at the management plane — encrypted secrets shown only as redacted placeholders, backend-executed connectivity probes with per-provider semantic interpreters, and truthful partial-success labels.

Three findings span every source. First, **no source generates tools from OpenAPI**, has a generic plugin-manifest system for tools, or sandboxes external tool processes — these are uniform absences, not competitive gaps. Second, **every implementing source compiles remote tools into its native tool representation** (FunctionTool, Pydantic model, BaseTool), which is what lets approvals, tracing, and error envelopes apply uniformly to local and external tools. Third, **trust defaults diverge more than features do**: agent-framework defaults to deny at call time, openai-agents-sdk is fail-closed once policy exists, crewai and pydantic-ai trust by default with documentation warnings (pydantic-ai even skips client-side argument validation against declared schemas on purpose), and langgraph's authorization accepts requests when no handler matches.

The dimension question — *"can the system adopt external tools without weakening security?"* — is answered affirmatively only by sources that treat trust boundaries as code rather than documentation: agent-framework and openai-agents-sdk demonstrate it is achievable; crewai and pydantic-ai show the common shortcut of warning-and-trusting; langgraph shows the cost of pass-through without validation.

## Core Thesis

Adopting MCP is table stakes; where a system places the trust boundary is the actual design decision. The ecosystem has split into two architectures: **compile external tools into your native tool representation** (openai-agents-sdk, agent-framework, pydantic-ai, crewai), which buys uniform downstream machinery — approvals, filters, tracing, error conversion — at the price of owning schema conversion, name collision handling, and SDK-generation compat; versus **pass opaque specs through to providers** (langgraph exclusively; hosted variants in the others), which buys zero-cost tracking of provider innovation at the price of losing all local enforcement — unvalidated URLs and headers shipped to remote endpoints, unknown spec dialects silently dropped, and no place to hang per-tool permissions. Within the compiled camp, maturity correlates not with feature breadth but with the density of fail-closed defaults and failure-mode tests around an inherently trusting protocol: the same three transports appear everywhere, yet only some systems redact credentials from exception chains, refuse double execution of side-effecting tasks after connection loss, or exclude a tool when its filter callback raises.

## Approach Models

Six approach models emerge, clustered from the per-source reports:

**1. Full local client, dual-mode (openai-agents-sdk).** The SDK acts purely as an MCP client over stdio (`MCPServerStdio`, `src/agents/mcp/server.py:1869-1966`), SSE, and Streamable HTTP (`server.py:2002-2554`), while `HostedMCPTool` (`src/agents/tool.py:1087-1114`) moves entire round-trips onto OpenAI Responses infrastructure. Remote tools are compiled once into native `FunctionTool`s (`src/agents/mcp/util.py:509-585`) so the run loop has no MCP-specific execution path — approvals, guardrails, and tracing apply uniformly, with provenance preserved via `ToolOrigin(type=MCP)` (`src/agents/mcp/util.py:580-583`).

**2. Defense-in-depth client with hosting adapters (agent-framework).** One 3,455-line module owns the entire client surface — stdio, streamable HTTP/SSE, WebSocket transports (`python/packages/core/agent_framework/_mcp.py:2728, :2927, :3250`), sampling guardrails, SEP-2663 tasks — under the stance that servers are untrusted: sampling callbacks are deny-by-default with rate limits (`_mcp.py:1477-1548`), ambiguous approval names resolve to require-approval (`_mcp.py:1704-1718`), headers travel via origin-scoped providers that skip cross-origin redirects (`_mcp.py:3041-3067`). Server-side, `hosting-mcp` publishes agents/workflows as MCP tools while explicitly refusing to own transport, auth, or session policy (`python/packages/hosting-mcp/_agent_tool.py:22`). Hosted MCP is normalized behind a `SupportsMCPTool` protocol implemented by four providers (`python/packages/core/agent_framework/_clients.py:757-785`).

**3. Composable toolsets over delegated protocol (pydantic-ai).** `AbstractToolset` (`pydantic_ai_slim/pydantic_ai/toolsets/abstract.py:76`) is the portability spine: `MCPToolset` is just another toolset built on the FastMCP client (`pydantic_ai_slim/pydantic_ai/mcp.py:716`), so `.filtered()`, `.prefixed()`, `.renamed()`, `.approval_required()`, and `.defer_loading()` combinators work identically on local and external tools (`abstract.py:194-257`). A capability layer pairs provider-native MCP with a local fallback via `NativeOrLocalTool` (`pydantic_ai_slim/pydantic_ai/capabilities/native_or_local.py:18-22`), and the reverse direction is supported too: agents run inside MCP servers and sample back through `MCPSamplingModel` (`pydantic_ai_slim/pydantic_ai/models/mcp_sampling.py:22-98`).

**4. First-party client with structural isolation (crewai).** CrewAI built its own `MCPClient` over the official SDK's transport primitives rather than delegating wholesale (`crewai/src/crewai/mcp/client.py:168-185`; transports in `crewai/src/crewai/mcp/transports/{stdio,http,sse}.py`), gaining control of timeouts, retry classification, and event instrumentation. Its defining decision is a fresh `MCPClient`+transport pair per invocation (`crewai/src/crewai/tools/mcp_native_tool.py:101-119`) — the tested structural answer to anyio cancel-scope cross-talk — plus stdio subprocesses receiving a sanitized environment instead of `os.environ` (`crewai/src/crewai/mcp/transports/stdio.py:86-96`).

**5. Pass-through delegation and platform contracts (langgraph).** Zero MCP client/server implementation in-repo. Dict-shaped tool specs are classified as provider-hosted, excluded from the local `ToolNode`, and forwarded verbatim to `model.bind_tools()` (`libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py:554-561, :586-588`); calling external MCP servers is delegated to user-supplied ecosystem packages scoped to run execution via `ServerRuntime.execution_runtime` (`libs/sdk-py/langgraph_sdk/runtime.py:97-127`); and exposing deployments *as* MCP/A2A servers is a documented config contract over closed-source routes (`libs/cli/langgraph_cli/schemas.py:471-480`).

**6. Management-plane ownership (openhands).** The frontend never speaks MCP; it owns configuration, validation, credential safety, and observability UX around a backend-executed integration. Secrets render only as `**********` placeholders substituted from encrypted storage just-in-time (`src/api/mcp-service/mcp-redacted-credentials.ts:84-98`); sparse merge patches never transmit unchanged redacted values (`src/utils/mcp-config.ts:319-378`); pre-save connectivity runs through a backend probe endpoint augmented with per-provider read-only tool calls that catch credentials "list tools succeeds anyway" providers would miss (`src/utils/mcp-credential-validation.ts:52-84`).

Models 1–4 are not mutually exclusive: every full-client source except crewai also ships a hosted/provider-native variant, confirming that the local-vs-hosted split is now a standard axis rather than an either/or choice.

## Pattern Catalog

### P1. Compile external tools into the native tool representation

- **Problem:** external tools would otherwise need their own execution, approval, tracing, and error paths.
- **Demonstrated by:** openai-agents-sdk (`inputSchema` → `params_json_schema`, `src/agents/mcp/util.py:509-585`), agent-framework (`inputSchema` → `FunctionTool(input_model=...)`, `python/packages/core/agent_framework/_mcp.py:1876-1936`), crewai (`inputSchema` → Pydantic `args_schema` via a shared utility, `crewai/src/crewai/mcp/tool_resolver.py:630-639`), pydantic-ai (`inputSchema`/`outputSchema` → `ToolDefinition` schemas, `pydantic_ai_slim/pydantic_ai/mcp.py:1295-1325`).
- **Why it works:** downstream machinery — approvals, guardrails, name sanitization, result mapping, tracing — is written once against one representation.
- **Copy when:** building any harness with both local function tools and remote protocols. **Overkill/risky when:** specs are pure provider pass-throughs (langgraph's dict route) where compilation would add nothing since execution never happens locally.
- **Evidence:** all four conversions above, each with dedicated tests (e.g., crewai's end-to-end JSON-Schema→Pydantic suite at `crewai/tests/utilities/test_pydantic_schema_utils.py:760-860`).

### P2. Normalize the same protocol edge cases independently

- **Problem:** non-conforming servers and SDK major-version churn break naive integrations.
- **Demonstrated by:** openai-agents-sdk injects empty `properties` because OpenAI rejects object schemas without them (`src/agents/mcp/util.py:538-543`), and agent-framework applies the same normalization for non-conforming servers (`python/packages/core/agent_framework/_mcp.py:1884-1891`). Both openai-agents-sdk (`src/agents/mcp/_compat.py:21-126`) and pydantic-ai (`pydantic_ai_slim/pydantic_ai/_mcp_compat.py:20-56`) ship v1/v2 field-name compat layers reading camelCase or snake_case spellings.
- **Why it works:** independent convergence on identical fixes is strong evidence these are real-world requirements, not gold-plating.
- **Copy when:** consuming arbitrary third-party servers or surviving dependency upgrades. **Risky when:** silent normalization masks drift — crewai's config parser quietly drops malformed candidates (`src/utils/mcp-config.ts:77-138` is openhands, see P9 note below; crewai's analog is `parseMcpConfig`-style coercion noted in its report as resilient-but-maskable).

### P3. Snapshot and invalidate cached tool lists defensively

- **Problem:** cached tool lists get mutated by callers/filters or go stale when servers change their catalogs.
- **Demonstrated by:** openai-agents-sdk returns deep copies and exposes dirty-flag invalidation (`src/agents/mcp/server.py:131-133, :861-866, :1486-1489`); pydantic-ai invalidates caches on `*ListChangedNotification`s via a synthesized message handler (`pydantic_ai_slim/pydantic_ai/mcp.py:1627-1644`); crewai uses a 5-minute TTL keyed by transport+URL (`crewai/src/crewai/mcp/client.py:50-51`).
- **Why it works:** freshness and integrity become properties of the cache, not caller obligations.
- **Copy when:** tool lists feed security decisions (filters, allowlists). **Caution:** crewai's module-level TTL cache is not namespaced per agent/run — a rotation on one server persists up to five minutes across tenants (its report flags this as poisoning risk); prefer notification- or snapshot-based designs.

### P4. Structural failure isolation at the connection level

- **Problem:** shared async clients crash or corrupt state across concurrent calls (anyio cancel scopes require same-task teardown).
- **Demonstrated by:** crewai spins a fresh client per invocation, with regression tests proving parallel safety (`crewai/src/crewai/tools/mcp_native_tool.py:101-119`; `crewai/tests/mcp/test_mcp_config.py:183-301`); openai-agents-sdk keeps pooled sessions but retries failed calls on fresh isolated sessions with explicit budget accounting (`src/agents/mcp/server.py:2325-2457`) and routes lifecycle ops through per-server worker tasks to preserve task affinity (`src/agents/mcp/manager.py:113-148`); pydantic-ai commits session state atomically only after successful handshake and ref-counts enter/exit (`pydantic_ai_slim/pydantic_ai/mcp.py:1167-1250, :1251-1268`).
- **Why it works:** concurrency bugs are prevented by construction rather than by discipline.
- **Copy when:** any async MCP usage. **Trade-off:** crewai's approach pays a full connect+initialize per call — fine for low-frequency side-effecting tools, painful for high-frequency remote reads (see Tradeoffs).

### P5. Fail-closed resolution of ambiguous policy

- **Problem:** partially specified trust policy creates accidental permissiveness.
- **Demonstrated by:** openai-agents-sdk excludes a tool when its dynamic filter raises ("for safety") and requires approval for callable policies lacking context (`src/agents/mcp/server.py:815-846, :1054-1065`); agent-framework resolves ambiguous approval names to require-approval (`python/packages/core/agent_framework/_mcp.py:1704-1718`) and denies sampling when callbacks throw (`python/packages/core/tests/core/test_mcp.py:2699`); openai-agents-sdk rejects overlapping always/never names and invalid shapes at construction (`src/agents/mcp/server.py:709-813`).
- **Why it works:** misconfiguration degrades toward restriction instead of exposure.
- **Copy always.** Contrast with the anti-pattern in langgraph where handler shadowing can silently widen access relative to an intended global deny (`libs/sdk-py/langgraph_sdk/auth/__init__.py:96-107`, composition gap flagged in its report).

### P6. Credential hygiene as a cross-cutting invariant

- **Problem:** URLs, headers, and error payloads leak secrets into logs, traces, and UIs.
- **Demonstrated by:** openai-agents-sdk strips userinfo/query/fragments from derived names and replaces unsafe HTTPX exception causes with fixed-data stand-ins across logs, spans, and chained exceptions (`src/agents/mcp/_logging.py:14-45`; `src/agents/mcp/server.py:181-302, :1176-1217`); openhands scrubs configured values longest-first plus generic token patterns before display (`src/utils/redact-mcp-secrets.ts:110-130`) and keeps plaintext out of the browser entirely (`src/api/mcp-service/mcp-redacted-credentials.ts:34-98`); agent-framework pins headers to same-origin requests so tokens cannot ride redirects (`python/packages/core/agent_framework/_mcp.py:3041-3067`), mirrored in .NET by disabled cookies/auto-redirect and origin pinning (`dotnet/src/Microsoft.Agents.AI.Workflows.Declarative.Mcp/DefaultMcpToolHandler.cs:184-248`); crewai filters ambient environment variables out of stdio spawns by default (`crewai/src/crewai/mcp/transports/stdio.py:83-96`, leak test at `crewai/tests/mcp/test_stdio_transport.py:11-52`).
- **Copy when:** always; redaction must cover tracebacks and exception chains, not just display strings.

### P7. Backend-executed validation probes with semantic interpretation

- **Problem:** "connection succeeded" says nothing about whether credentials actually authorize useful work.
- **Demonstrated by:** openhands probes through the agent-server (the exact environment runtime will use, `src/api/mcp-service/mcp-service.api.ts:183-192`), attaches catalog-declared read-only tool calls (GitHub `get_me`, Linear `list_teams`, Slack channel list) with interpreters distinguishing real auth failures from vendor codes like `missing_scope` (`src/utils/mcp-credential-validation.ts:33-99`), gates interpretation on the probe tool actually being advertised (`src/api/mcp-service/mcp-service.api.ts:100-122`), and labels results truthfully as `verified` vs `connectivity-only` (`src/api/mcp-health/probe-mcp-server-health.ts:38-88`).
- **Copy when:** users configure servers through a UI. **Avoid:** its known gap — the cloud path returns synthetic success and skips discovery entirely (`src/api/mcp-service/mcp-service.api.ts:190-195`), deferring all failures to conversation time.

### P8. Double-execution prevention for long-running operations

- **Problem:** reconnecting or falling back after an uncertain submit can re-fire a side-effecting tool.
- **Demonstrated by:** agent-framework refuses to re-issue a task submit whose outcome is unknown after connection loss, distinguishes abandonment (best-effort cancel) from terminal failure (never cancel), and declines plain-call fallback when a malformed success payload arrives (`python/packages/core/agent_framework/_mcp.py:2243-2295`; `python/packages/core/tests/core/test_mcp.py:6897-6926`); .NET mirrors this with remote cancellation on stuck polls and local cancellation (`dotnet/tests/Microsoft.Agents.AI.Mcp.UnitTests/TaskAwareMcpClientAIFunctionTests.cs:377-712`).
- **Copy when:** tools mutate state and the transport can drop mid-flight. This pattern appears nowhere else in the study — adopt it even if your framework does not.

### P9. Standard config-file portability with fail-closed templating

- **Problem:** users maintain server configs across many hosts; hand-transcription breeds drift.
- **Demonstrated by:** pydantic-ai parses Claude Desktop/Cursor-style `mcpServers` JSON with `${VAR}`/`${VAR:-default}` expansion that fails closed on undefined variables (`pydantic_ai_slim/pydantic_ai/mcp.py:1877-1974`); openhands accepts both the standard `{mcpServers:{...}}` wrapper and flat SDK maps (`src/utils/mcp-config.ts:17-32`); langgraph surfaces graph schemas over REST specifically to feed MCP/A2A integrations (`libs/sdk-py/langgraph_sdk/runtime.py:80-89`).
- **Copy when:** targeting practitioners who already hold MCP configs. **Risk:** configs are trusted input that can spawn executables and read env vars — pydantic-ai documents exactly this (`docs/mcp/client.md:218-220`); openhands' defensive parsing drops malformed entries silently (`src/utils/mcp-config.ts:82-137`), trading resilience for masked corruption.

### P10. Instrumentation wired into the protocol layer itself

- **Problem:** external tool behavior is otherwise invisible during incidents.
- **Demonstrated by:** agent-framework emits OTel spans per RPC (`python/packages/core/agent_framework/_mcp.py:1853`) with a dedicated test module; openai-agents-sdk wraps list-tools in `mcp_tools_span` and stamps `mcp_data.server` on function spans (`src/agents/tracing/create.py:466`; `src/agents/mcp/util.py:814-823`); crewai emits typed events for every connect/list/call lifecycle stage, shared by console formatting and checkpoint restoration (`crewai/src/crewai/events/types/mcp_events.py:24-98`).
- **Copy when:** operating anything beyond prototypes. Prefer discriminated event types over free-form strings — crewai's `error_type="authentication"|"network"|"timeout"` classification enables downstream handling without string matching (`crewai/src/crewai/mcp/client.py:250-321`).

## Key Differences

**What converges despite different implementations.**

- **Protocol choice:** MCP is universal; every source supports it and none offers another inbound external-tool protocol. Searches for OpenAPI-to-tool generation returned negative results in all six reports — agent-framework gets closest with declarative `OpenApiTool` YAML models and provider-executed OpenAPI (`python/packages/declarative/agent_framework_declarative/_models.py:819-840`; `dotnet/src/Microsoft.Agents.AI.Foundry/FoundryAITool.cs:45`), but nothing generates local tools from OpenAPI anywhere.
- **Transport set:** stdio, SSE, and Streamable HTTP recur in openai-agents-sdk, crewai, pydantic-ai, agent-framework, and openhands' config normalization (`src/utils/mcp-config.ts:60-70`); WebSocket appears only in agent-framework (`_mcp.py:3250`).
- **Errors become model-visible data:** langgraph converts handled tool exceptions into `ToolMessage`s with configurable strategies (`libs/prebuilt/langgraph/prebuilt/tool_node.py:674-694, :982-1009`); openai-agents-sdk's `failure_error_function` does the same for MCP failures (`src/agents/mcp/util.py:729-751`); pydantic-ai maps server errors to `ModelRetry`/`ToolFailed` by policy (`pydantic_ai_slim/pydantic_ai/mcp.py:764-776`); crewai classifies and forwards typed failures; agent-framework wraps into `ToolExecutionException` (`_mcp.py:2249-2260`). Crashing the run on tool failure is universally rejected.
- **Anyio ExceptionGroup discipline:** openai-agents-sdk splits groups replacing unsafe parts with fixed-data stand-ins (`server.py:249-272`); pydantic-ai unwraps only groups containing solely tool errors and re-raises cancellation-containing ones (`mcp.py:1420-1447`); crewai suppresses teardown noise on disconnect (`transports/http.py:126-150`). Three teams independently learned the same asyncio lesson.
- **Name collisions raise, don't shadow:** openai-agents-sdk raises `UserError` with opt-in prefixed names hashed collision-free (`src/agents/mcp/util.py:305-335, :416-506`); agent-framework raises when two remote tools map to one local name (`_mcp.py:1906-1912`); crewai deterministically prefixes by domain/path (`tool_resolver.py:486-492`); pydantic-ai offers `.prefixed()` wrappers.
- **Limiting context pollution:** static/dynamic tool filters (openai-agents-sdk `server.py:983-1067`; crewai `filters.py:32-163`), experimental progressive-disclosure loaders (agent-framework `_mcp.py:93-95, :530-538`), and pydantic-ai's `.defer_loading()` combinator all attack the same problem of too many advertised tools.

**Why sources diverge — constraint-driven, not quality-driven.**

- **Product shape.** langgraph is a platform layer: protocol serving belongs to its closed-source deployment server, so the open repo owns configuration contracts and lifecycle seams only. openhands is a product frontend: its threat surface is the browser, so excellence concentrates in secret handling and validation UX rather than wire protocol. Neither is "less mature"; they optimize different layers.
- **Security philosophy vs audience.** agent-framework (enterprise lineage, .NET sibling packages hardened against redirect hijacking and cookie theft) treats servers as adversaries by default. crewai and pydantic-ai target developer-first products where operator trust and documentation warnings are the accepted posture (`docs/edge/en/mcp/security.mdx:10-51`; `docs/mcp/client.md:218-220`). These are deliberate responses to different user bases, though the study shows the safe end of the spectrum is achievable without usability collapse (openai-agents-sdk balances both).
- **Performance posture.** crewai sacrificed latency for correctness (fresh client per call after shared-client regressions); openai-agents-sdk engineered pooled sessions plus isolated-session retry to keep keep-alive benefits while bounding blast radius; pydantic-ai amortizes connections via ref-counted sharing but then faces the single-identity-per-toolset hazard for multi-tenant use (`docs/mcp/client.md:463-500`).
- **Build-vs-delegate.** openai-agents-sdk and agent-framework implement directly atop the `mcp` Python SDK; crewai builds its own client layer over SDK transport primitives for control of semantics; pydantic-ai delegates the protocol to FastMCP and keeps caching/policy/result-mapping local. Delegation bought pydantic-ai full protocol breadth (sampling, elicitation, roots, OAuth) fastest; delegation costs crewai-style projects control and bought langgraph a 5/10 when the delegated pieces left the studied boundary entirely.

## Tradeoffs

**Hosted/provider-native MCP vs local client.**
- *Benefit:* no local connection, credentials stay with the provider, provider-side `require_approval` comes free (langgraph: `libs/prebuilt/tests/test_react_agent.py:313-327`; openai-agents-sdk: `src/agents/tool.py:1087-1114`).
- *Cost:* escapes local middleware entirely — agent-framework documents that hosted tools bypass approval interception and IFC labeling (`python/packages/core/agent_framework/security.py:3354-3360`); openai-agents-sdk loses observability since tool selection happens remotely; langgraph cannot validate `server_url`/`headers` before shipping secrets to a provider endpoint.
- *Best fit:* SaaS deployments trusting the provider more than the local environment. *Failure mode:* two divergent security postures for the same protocol within one product, discovered only during incident response.
- *Alternative:* agent-framework normalizes hosted behind one protocol interface so user code stays uniform even as postures differ (`_clients.py:757-785`) — the least-bad version of this tradeoff found.

**Fresh-client-per-call vs pooled sessions.**
- *Benefit (fresh):* total isolation from cancel-scope cross-talk; proven by parallel-safety tests (crewai: `crewai/tests/mcp/test_mcp_config.py:183-301`).
- *Cost:* full connect+`session.initialize()` per invocation negates HTTP keep-alive for high-frequency tools (crewai's own report names this).
- *Best fit:* fresh-per-call for infrequent side-effecting calls; pooled-with-isolated-retry for hot paths (openai-agents-sdk: `src/agents/mcp/server.py:2325-2457`).
- *Failure mode:* pooled sessions break subtly under cancellation unless lifecycle ops are task-affinity-aware (the exact bug class crewai's design forecloses).

**Client-side strictness vs server-side authority on arguments.**
- *Benefit (strict):* malformed calls fail fast before network I/O; agent-framework forwards only schema-declared parameters (`_mcp.py:2166-2207`).
- *Cost:* even "strict" frameworks inherit the server's word — agent-framework candidly documents that a malicious server widens its own argument surface simply by declaring properties (`_mcp.py:3084-3094`); pydantic-ai skips declared-schema validation entirely (`mcp.py:632-636`), so bad arguments always cost a round trip.
- *Best fit:* validate what you can locally, but plan detection for hostile metadata regardless — neither posture defends against prompt injection via tool descriptions, which openai-agents-sdk lists as residual risk (`src/agents/mcp/util.py:569` passthrough) and crewai documents as unmitigable in-band (`docs/edge/en/mcp/security.mdx:38-51`).

**Permissive defaults vs friction.**
- *Benefit:* low onboarding friction (langgraph custom routes unauthenticated unless opted in, `libs/cli/langgraph_cli/schemas.py:522-529`; crewai serves every advertised tool absent a filter, `tool_resolver.py:383-402`).
- *Cost:* burden shifts onto every user; langgraph additionally accepts requests when no authorization handler matches (`libs/sdk-py/langgraph_sdk/auth/__init__.py:96-107`) — secure posture becomes a recipe users must know to follow (install `deny_all` first, per its own docs at `auth/__init__.py:61-64`).
- *Best fit:* openai-agents-sdk's middle path scales best — execution defaults permissive but all policy machinery fails closed once present (P5).

**Memory-only vs persisted health verdicts (openhands).**
- *Benefit:* stale "healthy" claims are impossible; reload resets to unchecked (`src/api/mcp-health/mcp-health-store.ts:8-14`).
- *Cost:* repeated probing and re-entry anxiety; combined with race-guarded check IDs (`mcp-health-store.ts:43-60`), correctness wins over convenience here — a defensible product call, but worth revisiting if probe cost grows.

**Breadth vs dependency weight (pydantic-ai).**
- Full protocol support (tasks, in-process servers) arrives only behind `[mcp]` extras with hard import guards and actionable errors (`pyproject.toml:126-138`; `mcp.py:26-47, :59-75`) — good hygiene, but the feature matrix fragments across install profiles, and era-specific warnings must be maintained forever (`mcp.py:1175-1238`).

## Decision Guide

Choose between the main approaches using these rules, each grounded in observed evidence:

1. **If you are a library consumed by others and want near-zero protocol maintenance:** follow langgraph's pass-through for provider-hosted specs — *but* add structural validation and reject/warn on unknown shapes. Langgraph's silent skipping produced confusing downstream "Missing tools" errors (`chat_agent_executor.py:201-210, :214-215`); do not copy that part.
2. **If tools may act on the world unattended:** require the approval machinery of openai-agents-sdk (per-tool/per-server policies, grouped forms mirroring the TS SDK for cross-SDK config portability, `docs/mcp.md:260-262`) plus agent-framework's ambiguity-resolves-to-approval rule (`_mcp.py:1704-1718`) and double-execution prevention (P8).
3. **If multi-tenancy is in scope:** scope connections per-run/per-user — langgraph's `execution_runtime` narrows expensive wiring to actual runs (`runtime.py:97-145`); pydantic-ai documents that shared toolsets carry a single identity and prescribes per-run construction (`docs/mcp/client.md:467-500`).
4. **If a browser touches configuration:** adopt openhands' redaction-placeholder lifecycle wholesale — placeholders rendered, sparse patches omitting unchanged secrets, substitution from encrypted storage only at test time (`mcp-redacted-credentials.ts:34-98`), scrubbing applied to error text (`redact-mcp-secrets.ts:110-130`).
5. **If the same server URL must work across heterogeneous providers:** pydantic-ai's `NativeOrLocalTool` flips execution sides automatically per model support (`capabilities/mcp.py:186-199`); agent-framework's `SupportsMCPTool` achieves API-uniformity across four providers (`_clients.py:757-785`). Pick the former for automatic adaptation, the latter for explicit control.
6. **If protocol breadth (sampling, elicitation, roots, OAuth, tasks) matters more than dependency control:** delegate to FastMCP as pydantic-ai does; if timeout/retry/observability semantics must be uniformly yours, build the crewai-style thin first-party layer over official SDK primitives.
7. **If you need to expose your agents as tools to other systems:** prefer the adapter pattern — agent-framework's `hosting-mcp` provides schema derivation and arg conversion while refusing transport/auth ownership (`hosting-mcp/AGENTS.md`); langgraph's platform-route model works only if you own the deployment substrate. Note crewai lacks any server-side path (its report confirms no `mcp_server_*` exists).
8. **Default rule when unsure:** compile remote tools to your native representation (P1), instrument the protocol layer (P10), make every policy resolution fail closed (P5), and redact everything twice (P6). These four choices were consistent across every high-scoring source.

## Practical Tips

**Patterns to copy:**

- Tag converted tools with provenance at creation time so approvals and audits can distinguish MCP-originated calls later (openai-agents-sdk `ToolOrigin(type=MCP)`, `src/agents/mcp/util.py:580-583`).
- Test against real in-process protocol servers, not client mocks — .NET's `InMemoryMcpServerFixture` (`InMemoryMcpServerFixture.cs:24`), crewai spawning a real `FastMCP("Echo Server")` (`crewai-tools/tests/adapters/mcp_adapter_test.py:77-237`), and pydantic-ai's 2,239-line suite against an in-process server (`tests/test_mcp.py`) all catch bugs mocks hide.
- Distinguish authentication failures from transient network errors in retry logic — retrying 401s wastes rounds and masks root cause (crewai promotes unauthorized handshakes immediately: `client.py:193-215, :694-699`; openai-agents-sdk treats broken sessions distinctly from transient errors).
- Pre-validate required arguments client-side before network round-trips (openai-agents-sdk: `server.py:1576-1608`) — cheap win pydantic-ai currently skips.
- Warn loudly when configured features can never fire on newer session styles instead of silently dropping them (pydantic-ai sampling/elicitation degradation warnings: `mcp.py:1207-1228`).
- Label partial successes truthfully in UX — openhands' `verified` vs `connectivity-only` distinction (`probe-mcp-server-health.ts:41-45`) prevents false confidence at negligible cost.
- Keep lazy imports for heavy protocol SDKs to protect cold-start (crewai measured ~400 ms: `crewai/src/crewai/mcp/__init__.py:36-51`; openai-agents-sdk defers imports until attribute access: `src/agents/mcp/__init__.py:32-83`).

**Patterns to avoid or delay:**

- Don't build OpenAPI-to-tool generation preemptively — six sources skipped it; REST surfaces are wrapped as MCP servers externally when needed (each report's gaps section).
- Don't add OS-level sandboxing inside the harness — no source attempts it; permissioning layers plus host-environment isolation are the established division of labor.
- Don't unify config parsing with silent field-dropping until you have telemetry for dropped entries; openhands' parser drops malformed candidates quietly (`src/utils/mcp-config.ts:77-138`) and its report flags masking drift as the cost.

**Decision heuristics distilled from comparisons:**

- Choosing cache strategy: notification-driven invalidation (pydantic-ai) > snapshot+dirty-flag (openai-agents-sdk) > bare TTL (crewai) — in that order of robustness per unit complexity.
- Choosing retry bounds: cap attempts, classify auth as non-retryable, and account retry budgets explicitly when sessions may be rebuilt mid-failure (openai-agents-sdk `server.py:1219-1239, :2359-2457`); avoid unbounded `-1` settings in production paths.
- Choosing where approvals live: enforce them in the tool-execution path you own (compiled representation) rather than relying on provider-side fields you merely forward (langgraph's only gate for hosted tools is the spec's own `require_approval`, enforced elsewhere).

## Anti-Patterns / Caution Signs

**Anti-patterns observed in-source:**

- **Silent skipping of unrecognized spec shapes.** Langgraph ignores bound dicts lacking expected keys during name matching, surfacing later as a confusing ValueError or a model that never sees the tool (`chat_agent_executor.py:201-210`). Any protocol layer should reject-or-warn, never vanish.
- **Synthetic success short-circuits validation.** Openhands' cloud path returns `ok: true` with zero tool discovery at install time (`mcp-service.api.ts:190-195`), converting install-time failures into runtime surprises. Convenience that hides failure discovery is debt.
- **Authorization defaults that accept.** Langgraph accepts requests when no handler matches and leaves custom routes unauthenticated unless opted in (`auth/__init__.py:96-107`; `schemas.py:522-529`); its own docs teach deny-all-first as a recipe — evidence the default is wrong.
- **Handler composition that widens access.** Specific authz handlers shadow broader ones, so adding a narrow allow can accidentally defeat an intended global deny (`auth/__init__.py:98-103`). Policy engines need explicit precedence semantics.
- **Module-level unbounded caches.** Crewai's schema cache is process-global, not namespaced by agent/run, with no invalidation API — server-side rotations propagate stale schemas cross-tenant for up to five minutes (`client.py:50-51`; `tool_resolver.py:41-42`).
- **Raw error text into telemetry.** Crewai forwards unredacted failure messages to its event bus (truncated only in console rendering), risking credential leakage for remote servers (`events/types/mcp_events.py:76-85`); compare openai-agents-sdk, which redacts at exception-chain depth.
- **Experimental APIs carrying the strongest guarantees.** Agent-framework's best isolation surfaces (progressive disclosure, `SecureMCPToolProxy`/IFC labeling) are explicitly experimental (`security.py:3324`), meaning production users cannot yet reach the safest posture through stable APIs.

**Caution signs that this design area is going brittle:**

- Two security postures for the same protocol (hosted vs local) with the gap documented but not bridged — agent-framework warns that hosted bypasses local middleware (`security.py:3354-3360`); if your audit story assumes middleware ran, you will audit nothing.
- Shared mutable identity across concurrent runs — pydantic-ai's single-identity toolset means first-run credentials silently apply to overlapping runs (`docs/mcp/client.md:467-500`); a sign tenancy was retrofitted.
- Trust enforced at discovery time but not call time (or vice versa) without saying so — agent-framework exposes every advertised tool absent `allowed_tools` (`_mcp.py:2818-2820`) while gating execution; crews consuming its catalogs must know which half is guarded.
- Health verdicts that upgrade partial success, missing race guards on concurrent checks (contrast openhands' checkId discipline), or persisted "healthy" claims without staleness windows.
- Schema validation performed against the wrong artifact — e.g., validating structure as generic dicts while forwarding whatever arrived (pydantic-ai's permissive validator at `mcp.py:632-636` is deliberate but demands compensating monitoring).

## Notable Absences

Uniformly absent across all six sources — treat these as ecosystem-level gaps, not differentiators:

- **OpenAPI-to-tool generation:** negative search results in every report; agent-framework's declarative `OpenApiTool` and Foundry provider-executed OpenAPI are the nearest neighbors, and none generate local callable tools from specs.
- **Plugin manifests declaring tools:** openhands plugins bundle skills and files, not tools (`plugins-management-service.ts:13-25`); openai-agents-sdk extensibility is subclassing and callbacks; no manifest discovery/loading exists anywhere.
- **OS-level/process/container sandboxing of external tools:** every report explicitly notes its absence; stdio servers run as ordinary child processes with caller-supplied env (e.g., agent-framework `_mcp.py:2910-2924`; pydantic-ai `mcp.py:1960-1966`). Isolation = permissioning layers + host environment, nothing more.
- **Signature verification, cert pinning, or verified registries:** crewai lists TOFU/pinning as future work (`docs/edge/en/mcp/security.mdx` context); no source verifies server identity beyond transport TLS.
- **In-band mitigation of prompt injection via tool descriptions/schemas:** acknowledged as residual risk by openai-agents-sdk (description passthrough at `util.py:569`), crewai (documented risk), and addressed experimentally only by agent-framework's IFC proxy auto-labeling tools UNTRUSTED (`security.py:3388`).
- **Serving-side coverage is uneven:** langgraph (platform routes), pydantic-ai (docs + sampling model), and agent-framework (adapters) support being consumed as MCP servers; crewai has no server-side path; openhands delegates to its backend; openai-agents-sdk reports no serving mechanism.
- **Scale/benchmark evidence:** no load or concurrency benchmarks found in any report (agent-framework notes lifecycle locks and serialized header-provider tests but no scale data).

## Open Questions

Carried forward from the per-source reports, unanswered within the studied boundaries:

1. **Where does openhands establish MCP sessions at conversation runtime?** Enforcement, exclusion of disabled servers, and per-tool trust tiers live in the agent-server/software-agent-sdk, outside the analyzed source (openhands report, Questions/Gaps).
2. **What transport does langgraph's `/mcp` route speak** (streamable-HTTP vs SSE vs stdio)? The flag exists but implementation is closed-source (`schemas.py:471-475`; langgraph report, Gaps).
3. **Do realtime sessions in openai-agents-sdk accept MCP servers?** Filtering hooks suggest yes; no `mcp_servers` field was found in scope (openai-agents-sdk report, Gaps).
4. **Is end-to-end MCP OAuth verified anywhere?** pydantic-ai delegates `'oauth'` to FastMCP without handshake tests; crewai has OAuth infrastructure unwired from MCP; agent-framework found no flow for streamable HTTP; openhands alone demonstrates a complete browser-mediated flow — but only in its management plane.
5. **Can per-server MCP capabilities gate invocation (not just discovery)?** crewai found only schema-implied capability with no invocation gating (Questions/Gaps).
6. **How do the strongest isolation mechanisms behave once stable?** agent-framework's FIDES labeling and progressive disclosure, and openhands' proposed deferred first-use probes for cloud installs, are designed futures rather than measured behaviors.
7. **Cross-language divergence risk:** agent-framework notes Python/.NET differences in skills-over-MCP archive handling (in-memory vs disk) — unresolved which behavior is canonical.
