## Executive Summary

Four agent systems with four different memory architectures agree on one thing: **scoping is the pillar they engineer seriously, and nearly everything else in the privacy stack is thin**. Every source enforces memory scope in queries with tests behind it — letta through a centralized ORM access predicate applied to every list/read/bulk-delete (letta: letta/orm/sqlalchemy_base.py:871-902), crewai through storage-layer scope-prefix predicates in both backends (crewai: lib/crewai/src/crewai/memory/storage/lancedb_storage.py:387-390; lib/crewai/src/crewai/memory/storage/qdrant_edge_storage.py:243-253), agent-framework through typed scope objects, compiled vector filters, and Cosmos partition keys (agent-framework: dotnet/src/Microsoft.Agents.AI/Memory/ChatHistoryMemoryProvider.cs:380-410; dotnet/src/Microsoft.Agents.AI.CosmosNoSql/CosmosChatHistoryProvider.cs:194-215), and openhands through explicit scope flags on the skill API it owns (openhands: src/api/skills-service.ts:48-56).

Beyond scoping, the picture converges in the opposite direction. None of the four filters or redacts sensitive content before persisting it; none implements an audit trail of memory reads/writes/deletes; retention exists exactly once — a Cosmos DB TTL in agent-framework (dotnet/src/Microsoft.Agents.AI.CosmosNoSql/CosmosChatHistoryProvider.cs:84-88) against an explicit "no TTL" admission in its own Valkey provider (dotnet/src/Microsoft.Agents.AI.Valkey/ValkeyChatHistoryProvider.cs:25-28); and identity everywhere is caller-supplied rather than cryptographically bound to a scope — mem0 scope strings (agent-framework: python/packages/mem0/agent_framework_mem0/_context_provider.py:147-154), crewai's free-form `source` field (crewai: lib/crewai/src/crewai/memory/types.py:60-73), letta's client-supplied `user_id` headers behind one shared server password with a default-actor fallback (letta: letta/services/user_manager.py:122-135), and openhands' single shared session key per browser profile (openhands: src/api/agent-server-client-options.ts).

Deletion is the middle ground: broad and thoughtful in letta (hard deletes propagated to vector and git stores, letta: letta/services/passage_manager.py:767-796; letta/services/memory_repo/git_operations.py:629-638) and crewai (`forget()`/`reset()` APIs plus a CLI with verified deletion counts, crewai: lib/crewai/src/crewai/memory/unified_memory.py:818-850; lib/crewai/src/crewai/utilities/reset_memories.py:94-132), patchy across agent-framework's provider matrix (delete exists for some providers, provably absent for others), and absent for the thing users would most want to erase in openhands — accumulated agent memory under `.openhands/memory/` has no view/export/delete surface at all (openhands: src/routes/agent-context-settings.tsx:5-10).

Ratings cluster tightly at 5–6/10: every source has a real scoping model worth studying, and no source clears the "operational safeguards" bar.

## Core Thesis

Trust in agent memory today is **boundary trust, not lifecycle trust**. All four sources can give a reasonably confident answer to *"will this user's memory land in another user's context?"* because scoping is typed or structural, enforced at query time, and tested — e.g., dedicated cross-org invisibility tests in letta (letta: tests/managers/test_block_manager.py:303-355) and root-scope isolation suites in crewai (crewai: lib/crewai/tests/memory/test_memory_root_scope.py:841-1054). None can give a confident answer to *"how long does it live, who has seen it, and can the user prove it is gone?"* because retention, auditing, and content-level privacy controls are either delegated to deployment configuration via doc contracts (agent-framework: dotnet/src/Microsoft.Agents.AI.CosmosNoSql/CosmosChatHistoryProvider.cs:23-36), implemented as honor-system flags filtered above the enforcement layer (crewai: lib/crewai/src/crewai/memory/unified_memory.py:746-751), scaffolded but switched off (letta's accepted-then-discarded `access` argument, letta: letta/orm/sqlalchemy_base.py:890), or simply outside the component's reach (openhands' frontend-only view of a server-side store). A team adopting these designs should expect to inherit the scoping engineering for free — and to build retention, audit, and content hygiene themselves.

## Approach Models

- **agent-framework — "scoping-first, everything else delegated."** A matrix of independent memory subsystems (session-scoped harness file memory, owner-scoped durable memory with LLM extraction, service-backed Foundry/Mem0/Cosmos providers mirrored across Python and .NET). Scope is a first-class, typed, host-supplied concept resolved once per invocation and enforced at query time or via physical partitioning; encryption-at-rest, access control, network security, and mostly retention are assigned to deployment configuration through XML-doc "security considerations" remarks (agent-framework: dotnet/src/Microsoft.Agents.AI.CosmosNoSql/CosmosChatHistoryProvider.cs:23-36; dotnet/src/Microsoft.Agents.AI.Mem0/Mem0Provider.cs:29-37).

- **crewai — "tenancy as a naming convention."** One unified `Memory` facade over pluggable stores; hierarchical filesystem-like `scope` paths are the sole tenancy primitive, auto-derived per crew/flow (`/crew/<name>`, `/flow/<name>` — crewai: lib/crewai/src/crewai/crew.py:652-684; lib/crewai/src/crewai/flow/runtime/__init__.py:832-836) and enforced as prefix predicates inside the backends. A record-level `private` flag plus unauthenticated `source` string are filtered post-search at the orchestration layer (lib/crewai/src/crewai/memory/unified_memory.py:746-751). Deletion is API+CLI-first; there is no expiry daemon anywhere in `crewai/memory/`.

- **letta — "org-wall with centralized enforcement."** The organization is the tenant boundary for every memory primitive via `OrganizationMixin` (letta: letta/orm/mixins.py:19-24); `SqlalchemyBase.apply_access_predicate` injects the org/user WHERE clause into list/read/bulk-delete paths, managers double-filter, external stores encode org into namespaces/prefixes, and deletion is hard-delete by contract. Row-level permissions are scaffolded (`access` accepted then discarded) so intra-org visibility is all-or-nothing.

- **openhands — "frontend delegation."** The frontend owns secrets transport, localStorage blobs, telemetry identity/consent, and skill scope labeling (`project`/`personal`/`public` derived from path heuristics — openhands: src/utils/skill-scope.ts:79-106); persistent agent memory itself is a single opt-in global boolean whose enforcement lives server-side and is not verifiable from this repo (openhands: src/api/agent-server-adapter.ts:1100-1106).

These models diverge for reasons of product shape, not quality. Letta is a multi-tenant server product, so tenancy must be structural (org columns, namespaces, REST delete endpoints). CrewAI is a local library for a single operator, so naming-convention tenancy and cooperative privacy are defensible defaults. Agent-framework is a backend-agnostic framework that cannot know which store a customer deploys, so it types what it can enforce locally and documents the rest. OpenHands is a client that cannot see the server's memory implementation, so it hardens only what crosses its own boundary (secrets, localStorage, toggles).

## Pattern Catalog

### P1. Centralized enforcement chokepoint

- **Problem:** scattered WHERE-clause/filter construction means one forgotten call site leaks data.
- **Seen in:** letta applies one access predicate inside the ORM base for every list/read/size/bulk-delete path (letta: letta/orm/sqlalchemy_base.py:265-267, 871-902, 726-728); crewai pushes the scope prefix into both storage engines so every search is scoped regardless of caller (crewai: lib/crewai/src/crewai/memory/storage/lancedb_storage.py:387-390); agent-framework builds one AND-combined filter expression for vector search (agent-framework: dotnet/src/Microsoft.Agents.AI/Memory/ChatHistoryMemoryProvider.cs:380-410).
- **Why it works:** the check lives below the layer that has many callers; letta even logs a SECURITY warning when an org-scoped query runs without an actor (letta: letta/orm/sqlalchemy_base.py:256-258).
- **Copy when:** multiple query paths or third-party call sites exist.
- **Risky when:** a bypass exists below the chokepoint — crewai's raw `storage.search(scope_prefix=None)` returns unscoped rows (crewai: lib/crewai/tests/memory/test_memory_root_scope.py:912-939 documents global recall semantics).
- **Evidence:** cross-org isolation asserted by test in letta (tests/managers/test_block_manager.py:303-355); compiled-filter match/non-match tests in agent-framework (dotnet/tests/Microsoft.Agents.AI.UnitTests/Memory/ChatHistoryMemoryProviderTests.cs:464-531); root-scope suites in crewai (lib/crewai/tests/memory/test_memory_root_scope.py:841-1054).

### P2. Storage-topology-encoded tenancy

- **Problem:** logical filters are only as good as the code that remembers them; physical layout survives application bugs.
- **Seen in:** Cosmos hierarchical partition keys `TenantId→UserId→ConversationId` with partition-scoped queries and batch assertions (agent-framework: dotnet/src/Microsoft.Agents.AI.CosmosNoSql/CosmosChatHistoryProvider.cs:194-215, 359-379); Turbopuffer namespaces keyed by org/archive (letta: letta/helpers/tpuf_client.py:312-350); git memory repos addressed by `(agent_id, org_id)` prefix (letta: letta/services/memory_repo/git_operations.py:629-638); LanceDB/Qdrant precomputed scope indexes (crewai: lib/crewai/src/crewai/memory/storage/qdrant_edge_storage.py:65-78).
- **Why it works:** cross-tenant reads become structurally impossible rather than merely filtered.
- **Copy when:** any external store (vector DB, object store, git) participates in memory.
- **Risky when:** topology drifts from SQL truth — letta tolerates vector-store divergence in non-strict mode (see P5).

### P3. Fail-closed retrieval gates

- **Problem:** misconfigured or missing scope silently widens access.
- **Seen in:** agent-framework's mem0 provider refuses retrieval unless an explicit search scope is configured while writes proceed independently (agent-framework: python/packages/mem0/agent_framework_mem0/_context_provider.py:50-62, 147-154); Foundry providers reject empty scope at construction (python/packages/foundry/agent_framework_foundry/_memory_provider.py:132-139; dotnet/src/Microsoft.Agents.AI.Foundry/Memory/FoundryMemoryProviderScope.cs:26-30); crewai's integration points call recall without `include_private`, hiding private records by default (crewai: lib/crewai/src/crewai/agent/core.py:646-655).
- **Why it works:** the failure direction is "no data" instead of "wrong user's data."
- **Copy when:** any scope dimension is optional.
- **Risky when:** it degrades UX for legitimate broad queries; agent-framework deliberately keeps nullable .NET scope dimensions that "span all users" for agent-wide memory, trading convenience for foot-guns (dotnet/src/Microsoft.Agents.AI/Memory/ChatHistoryMemoryProviderScope.cs:34-52).

### P4. Verified and race-safe destructive operations

- **Problem:** deletion that half-happens, resurrects data, or lies about success destroys trust.
- **Seen in:** crewai counts rows before/after every delete branch and drains pending background writes under a re-entrant lock before reset, with a test proving a save cannot interleave (crewai: lib/crewai/src/crewai/memory/storage/lancedb_storage.py:422-464; lib/crewai/src/crewai/memory/unified_memory.py:1015-1035; lib/crewai/tests/memory/test_unified_memory.py:990-1035); agent-framework's file delete removes sidecar files and rebuilds the index (python/packages/core/agent_framework/_harness/_file_memory.py:368-389); openhands treats 404 as success for idempotent retries (src/api/secrets-service.ts:140-152); letta re-applies the access predicate on bulk DELETE statements (letta: letta/orm/sqlalchemy_base.py:708-740).
- **Why it works:** deletion is treated as an operation with observable outcomes, not an assumption.
- **Copy when:** always, wherever destructive ops exist.
- **Risky when:** verification is skipped elsewhere in the same codebase — agent-framework's `EnsureStoredMemoriesDeletedAsync` has zero test references (per-source grep over `dotnet/tests`).

### P5. Derived-copy deletion propagation

- **Problem:** memories live in SQL *and* a vector store / sidecar files / derived indexes; deleting the primary leaves searchable ghosts.
- **Seen in:** letta dual-deletes passages in Turbopuffer with a `strict_mode` that fails closed on vector errors (letta: letta/services/passage_manager.py:767-796, 783-792); message deletes also scrub vector recall state (letta/services/message_manager.py:1045-1090); agent-framework rebuilds its file-memory index after delete (python/packages/core/agent_framework/_harness/_file_memory.py:368-389).
- **Why it works:** erasure guarantees cover every copy that can serve a query.
- **Copy when:** any secondary index or cache mirrors memory content.
- **Failure mode:** best-effort mode lets deleted passages remain searchable after partial failure (letta: letta/services/passage_manager.py:789-792); strict-by-default would surface this to callers.

### P6. Provenance and attribution seams

- **Problem:** without knowing which principal/session produced or touched a memory, downstream DLP/compliance work has nothing to build on.
- **Seen in:** injected memory messages carry deduplicated `origin_session_ids` (agent-framework: python/packages/core/agent_framework/_harness/_memory.py:1317-1346; _sessions.py:180-185); every row records `created_by_id`/`last_updated_by_id` and block checkpoints record editor identity (letta: letta/orm/base.py:30-35; letta/orm/block_history.py:35-37); crewai stamps `source` provenance on records and emits save/query events attributed to agent role (crewai: lib/crewai/src/crewai/memory/types.py:60-73; lib/crewai/src/crewai/events/types/memory_events.py:23-79).
- **Why it works:** attribution makes later auditing possible without redesigning the schema.
- **Limit:** this is a seam, not an audit log — none of the three captures reads, failed accesses, or a tamper-evident trail.

### P7. Secret redaction protocols for transport and display — never for stored content

- **Problem:** credentials and tokens must not leak through UIs, logs, error text, or round-trips.
- **Seen in:** openhands' placeholder protocol swaps unchanged sentinels for stored *encrypted* values only at probe/persist time, plus two display scrubbers including generic token patterns (openhands: src/api/mcp-service/mcp-redacted-credentials.ts:40-59; src/utils/redact-mcp-secrets.ts:100-127; src/utils/redact-custom-secrets.ts:1-27); agent-framework redacts telemetry fields by default with an opt-out flag (dotnet/src/Microsoft.Agents.AI/Memory/ChatHistoryMemoryProvider.cs:122, 497; ChatHistoryMemoryProviderOptions.cs:47-64); letta's `Secret.__str__/__repr__` never expose values and exports scrub messages (letta: letta/schemas/secret.py:271-279; letta/services/agent_serialization_manager.py:196).
- **Why it works:** layered scrubbing assumes any single layer will regress.
- **Critical boundary:** in all four sources these mechanisms stop short of memory content itself — stored block values, passage text, and conversation-derived memories persist verbatim (letta: letta/orm/passage.py:28; crewai docs even demo storing an API key as a private memory, lib/crewai/docs/edge/en/concepts/memory.mdx:466-478; agent-framework persists full message text, dotnet/src/Microsoft.Agents.AI/Memory/ChatHistoryMemoryProvider.cs:272-293).

### P8. Capability removal instead of permission checks

- **Problem:** agents that hold a write tool will eventually use it where they shouldn't.
- **Seen in:** crewai's read-only `MemorySlice` simply omits the RememberTool so agents are "never offered a save capability they cannot use" (crewai: lib/crewai/src/crewai/memory/memory_scope.py:234-236; lib/crewai/src/crewai/tools/memory_tools.py:104-130); letta raises on tool writes to `read_only` blocks (letta: letta/services/tool_executor/core_tool_executor.py:320-321).
- **Why it works:** removing capability beats policing behavior.
- **Copy when:** exposing memory tools to LLM-driven control flow.

### P9. Stored-memory untrusted-channel injection

- **Problem:** recalled memory is attacker-influencable content; injecting it as system/instruction text converts stored data into privilege escalation.
- **Seen in:** agent-framework injects retrieved summaries as user-role messages explicitly framed as untrusted reference data (agent-framework: python/packages/azure-cosmos-memory/agent_framework_azure_cosmos_memory/_context_provider.py:392-412); provenance-based message filters keep framework-internal messages out of stored context (dotnet/src/Microsoft.Agents.AI.Abstractions/AIContextProvider.cs:62-64).
- **Why it works:** preserves the instruction/data boundary even when memory content is hostile.
- **Single-source pattern:** demonstrated unusually clearly here; the other sources do not address stored-prompt-injection in their memory paths.

## Key Differences

The five dimension questions answered comparatively:

| Question | agent-framework | crewai | letta | openhands |
|----------|-----------------|--------|-------|-----------|
| Leak between users? | Mitigated by design; correctness caller-owned (fail-closed mem0 gate, partition keys) but scopes unbound to auth and `"default"` fallback pools anonymous users | Yes under concrete conditions: global recall without root_scope, storage-layer bypass of private flag, spoofable `source` | Across orgs no (tested); within an org yes by design; default actor collapses anonymous traffic into one identity | Not in frontend flows; but per-backend/org scoping means one shared session key exposes everything on shared machines |
| Users can delete? | Partially — patchy matrix: file/topic deletes yes; .NET ChatHistoryMemoryProvider and Python service providers have none | Yes, strongest area: forget/reset/CLI, verified counts, race-safe resets | Yes, most comprehensive incl. vector/git propagation and cascade attempts | Secrets/localState/telemetry yes; persistent agent memory no |
| Sensitive data stored? | Yes, verbatim; acknowledged in docs; redaction covers telemetry only | Yes, plaintext local stores; private flag hides records from recall, not from disk | Yes, plaintext content; only credentials encrypted (with plaintext fallback) | Secret values protected end-to-end; but API keys and draft prose sit plaintext in localStorage |
| Access audited? | No — operational logging + provenance attribution only | No — opt-in observability events include content but no actor; deletions emit nothing | No — attribution columns and checkpoints only; no audit table found | No — telemetry covers funnel events, not data access |
| Scopes enforced in queries? | Yes — five tiers from physical partitions to fail-closed gates | Yes — prefix predicates in both backends, tested; bypassable below the facade | Yes — centrally, redundantly, tested | Yes where frontend owns the query (skill flags, disable lists) |

Where enforcement lives differs sharply: in the database layer for letta, in the storage engine for crewai, in provider query construction for agent-framework, and in API request shaping for openhands. Tenancy granularity likewise spans org walls (letta), arbitrary path hierarchies (crewai), host-decided typed dimensions (agent-framework), and backend/org keying (openhands). Intra-boundary privacy is the biggest split: crewai is the only source with a record-level privacy flag at all (untested — no exercise of `private=True`/`include_private` found in `lib/crewai/tests/memory/`), while letta explicitly discards its scaffolded per-user access levels (letta: letta/orm/sqlalchemy_base.py:884-890) and agent-framework's nullable user dimensions make accidental global scope invisible rather than forbidden.

Default posture is another genuine divergence: agent-framework turns file memory **on by default** writing under `{cwd}/agent-file-memory` with approval-free tools (python/packages/core/agent_framework/_harness/_agent.py:183-186; _file_memory.py:315), whereas openhands makes persistent memory **opt-in** with `default: false` (src/mocks/settings-handlers.ts:349-371) — continuity-favoring vs data-minimization-favoring philosophies on identical functionality.

## Tradeoffs

- **Centralized ORM predicate (letta) vs typed per-provider scopes (agent-framework).** Benefit of centralization: one place guarantees coverage, managers add redundant defense-in-depth (letta: letta/services/block_manager.py:324-327). Cost: the chokepoint enforces only what it knows — intra-org granularity was dropped, and the predicate currently ignores the `access` argument. Best fit: products with one canonical store. Failure mode: anything outside SQL (vector ghosts, orphaned archives on agent deletion, letta: letta/services/agent_manager.py:1320-1396) escapes the guarantee. Alternative seen: agent-framework accepts unevenness across providers in exchange for backend pluralism.

- **Orchestration-layer privacy filter (crewai) vs enforcement at/below storage (others).** Benefit: the storage protocol stays simple and backends stay dumb/fast. Cost: `list_records`/`get_record`/raw search return private rows unfiltered (crewai: lib/crewai/src/crewai/memory/storage/lancedb_storage.py:371-409), and every higher-level caller must remember the filter. Best fit: single-operator libraries. Failure mode: any new consumer below the `Memory` facade sees everything. Alternative seen: pushing predicates into the engines (P1/P2).

- **Org-wall sharing (letta) vs record/user boundaries (crewai's private flag, agent-framework's user dimensions).** Benefit of the org wall: team collaboration is frictionless — one mutable shared block propagates to every connected agent (letta: letta/services/block_manager.py:61-68). Cost: individual users' contributed data is visible to every actor in the org; there is no per-user ACL layer. Best fit: internal team workspaces. Failure mode: onboarding an untrusted member exposes the whole corpus.

- **Comprehensive hard delete (letta, crewai) vs absent delete surfaces (openhands memory, parts of agent-framework).** Benefit: right-to-erasure flows are implementable today against letta/crewai. Cost: hard deletes are unrecoverable except via letta's block-history checkpoints, and LLM consolidation in crewai also deletes records without user initiation (lib/crewai/src/crewai/memory/encoding_flow.py:398-479), complicating compliance narratives. Best fit: deletion-first lifecycle for local tools; checkpointed hard delete for servers. Failure mode: "disable ≠ delete" — turning off openhands' `load_memory` halts loading but leaves prior notes intact and invisible (openhands: src/routes/agent-context-settings.tsx:5-10).

- **Best-effort vs strict dual-store deletion (letta `strict_mode`).** Benefit of best-effort default: uptime over consistency. Cost: deleted content stays searchable in the vector namespace after partial failure (letta: letta/services/passage_manager.py:789-792). Best fit: availability-critical deployments. Failure mode: silent erosion of erasure guarantees. Alternative seen: agent-framework's file memory rebuilds derived state synchronously as part of the delete.

- **Default-on memory with approval-free tools (agent-framework) vs opt-in memory (openhands).** Benefit of default-on: continuity out of the box. Cost: an agent can read or destroy its whole memory corpus unprompted (`never_require` approval, agent-framework: python/packages/core/agent_framework/_harness/_file_memory.py:315), and data minimization is lost unless hosts opt out. Best fit: personal assistants; the inverse for shared/embedded deployments.

- **Delegation-by-documentation (agent-framework) vs shipping controls in-product (openhands secrets, letta crypto).** Benefit of delegation: backend neutrality and honest scoping of responsibility. Cost: two deployments of the same provider differ completely in protection, and the shipped code alone provides no encryption/access-control guarantee. Best fit: frameworks consumed by sophisticated enterprises. Failure mode: operators who never read the security remarks deploy unprotected.

- **LLM-gated extraction as the only content policy (agent-framework) vs no content policy (others).** Agent-framework's extraction prompt restricts memories to "durable facts, preferences, decisions" (python/packages/core/agent_framework/_harness/_memory.py:44-56) — but whether sensitive content becomes a durable fact depends entirely on extractor-model compliance; there is no sensitivity review after successful extraction.

## Decision Guide

Choosing between the main approaches found here:

- **Building a multi-user/server product:** adopt letta's shape — tenant column on every memory table, one centralized predicate applied in the persistence layer, tenant-encoded namespaces in every external store, dedicated two-directional isolation tests (letta: tests/managers/conftest.py:104-127; tests/managers/test_block_manager.py:303-355, 733-765). Then fix what letta lacks: bind actors to real authentication before mapping them to tenants, require the encryption key rather than falling back to plaintext (letta: letta/schemas/secret.py:59-68), and add an append-only audit log.
- **Building a local developer library/tool:** adopt crewai's shape — auto-namespaced root scopes, prefix predicates inside whatever storage you embed, verified/race-safe deletes, and a CLI reset path (crewai: lib/crewai/src/crewai/utilities/reset_memories.py:94-132). Do not copy its orchestration-only privacy filter; push any privacy predicate into the storage layer and test it.
- **Building a framework with pluggable backends:** adopt agent-framework's shape — typed scope objects, fail-closed retrieval gates where scope is optional, per-provider "security considerations" documentation, and TTL surfaced only where the backend supports it. But make safe-by-default choices the framework did not: warn loudly on omitted scope dimensions and refuse a literal `"default"` user fallback.
- **Building a client/frontend:** adopt openhands' shape — encrypted round-trips with refusal of redacted fallbacks (openhands: src/api/settings-service/settings-service.api.ts:479-509), display scrubbers, consent-gated telemetry with a real data-clear routine (src/services/telemetry.ts:830-869), opt-in persistence. Add what it lacks: a memory management surface (view/export/delete) as soon as the server exposes one.

Universal rules independent of product shape:

1. Bind scope identifiers to authenticated principals somewhere; every source that skips this names it as its top residual risk.
2. Enforce scope below the highest-traffic facade, and prove it with a negative test (foreign-tenant record invisible).
3. Treat every derived copy of memory (vector index, sidecar, export, log) as a deletion target.
4. Ship a deletion story before shipping accumulation; disable-without-delete is not a lifecycle.
5. Reserve redaction pipelines for secrets now, but design the provenance seams (P6) so content-level DLP can be added without schema surgery.

## Practical Tips

- **Copy the fail-closed gate** whenever a scope field is optional: retrieve nothing rather than everything (agent-framework: python/packages/mem0/agent_framework_mem0/_context_provider.py:147-154).
- **Copy verified deletion accounting**: return actual removed-row counts computed before/after (crewai: lib/crewai/src/crewai/memory/storage/lancedb_storage.py:422-464); tolerate 404 for idempotency but never swallow per-shard failures silently — crewai's Qdrant cleanup logs shard delete failures at debug level, so reported counts can overstate removal (lib/crewai/src/crewai/memory/storage/qdrant_edge_storage.py:408-409).
- **Copy the drain-before-reset lock** if background writes exist; otherwise a queued write resurrects data after a wipe (crewai: lib/crewai/src/crewai/memory/unified_memory.py:1022-1029).
- **Encode tenancy into storage topology** for every external store: partition keys, namespaces, key prefixes (agent-framework: CosmosChatHistoryProvider.cs:194-215; letta: letta/helpers/tpuf_client.py:312-350; letta/services/memory_repo/git_operations.py:629-638).
- **Remove capabilities instead of gating them** when handing memory tools to agents (P8).
- **Frame recalled memory as untrusted data**, never instructions (agent-framework: azure-cosmos-memory/_context_provider.py:392-412).
- **Wire provenance into injected messages** (`origin_session_ids`) so hosts can distinguish memory-derived content — a prerequisite for audit/DLP (agent-framework: _sessions.py:180-185).
- **Delay/avoid until needed:** record-level privacy flags with admin overrides (crewai's `include_private` requires no elevation, lib/crewai/docs/edge/en/concepts/memory.mdx:476-477) and scaffold-but-discard permission parameters (letta's discarded `access`) both create false confidence; ship either working enforcement or nothing.

## Anti-Patterns / Caution Signs

- **Silent scope widening via defaults:** nullable .NET scope dimensions that "span all applications/users" with no warning (agent-framework: ChatHistoryMemoryProviderScope.cs:34-52); a literal `"default"` user id pooling anonymous callers (azure-cosmos-memory/_context_provider.py:257); letta's `DEFAULT_USER_ID` fallback collapsing attribution (letta/services/user_manager.py:122-135); crewai's legacy configs restoring as bare `Memory` with `root_scope=None` and global visibility (memory_scope.py:20-35). If your design needs documentation to explain what an omitted field does, it is a foot-gun.
- **Privacy logic living above the enforcement layer:** post-search filtering that raw storage calls bypass (crewai: lancedb_storage.py:371-409). Caution sign: the same data reachable through two public paths with different visibility.
- **Identity as free-text data:** spoofable `source` strings granting access to another user's private memories by passing the matching string (crewai: unified_memory.py:750). Caution sign: any "principal" that is a constructor argument rather than a credential.
- **Disable ≠ delete:** toggles that stop future accumulation while past data persists invisibly (openhands memory toggle; also crewai's fire-and-forget background saves with no TTL, unified_memory.py:297-322).
- **Untested privacy features:** crewai's `private`/`include_private` has zero test coverage despite documented semantics; agent-framework's scope-delete endpoint has no test references. Caution sign: privacy behavior described only in docs or remarks.
- **Content-bearing observability:** events carrying full query/content text to in-process listeners (crewai: events/types/memory_events.py:27-28) and Trace-level logs emitting full memory queries/results (agent-framework: ChatHistoryMemoryProvider.cs:148-155, 339-349) turn debugging sinks into leak vectors.
- **Encryption with a silent off switch:** letta stores credentials plaintext when the key env var is unset, warning only (letta: letta/schemas/secret.py:59-68; settings.py:449). Caution sign: any secure mode reachable only by optional configuration.
- **Hidden ≠ protected:** visibility flags that merely filter listings while records remain addressable by ID (letta: letta/services/block_manager.py:350-351).
- **Deletion dead zones:** providers within one framework differing in whether delete exists at all (agent-framework matrix); orphaned archives surviving agent deletion (letta: agent_manager.py:1320-1396); rename-via-upsert stranding old secrets on crash (openhands: src/api/secrets-service.ts:118-120).

## Notable Absences

Across all four sources, four capabilities are absent outright — these are the field's open ground, not implementation gaps:

- **Audit trails of memory access.** Every source substitutes proxies: operational logging (agent-framework), opt-in observability events without actors (crewai), attribution columns and checkpoints (letta), funnel telemetry (openhands). No tamper-evident log of reads/deletes/failed access exists anywhere; searches for `audit` returned no implementations in any repo.
- **Content-level privacy filtering before persistence.** Raw conversation text, block values, and passage text are stored verbatim in all sources; the nearest approximations are an LLM extraction prompt heuristic (agent-framework: _memory.py:44-56), a recall-time visibility flag (crewai), reasoning-trace scrubbing and export scrubbing (letta: letta/helpers/reasoning_helper.py:25), and display-side scrubbers (openhands). Anonymization of memory content: none.
- **Retention policies.** Exactly one mechanism exists — Cosmos `MessageTtlSeconds` (agent-framework: CosmosChatHistoryProvider.cs:84-88) — while agent-framework's own Valkey provider states retention is the caller's job, and repo-wide searches for retention/TTL/expiry in crewai and letta memory paths return nothing.
- **Authenticated binding of scopes to principals.** Nothing verifies a session is entitled to its claimed scope value in any source; agent-framework's hosting remark that audit/authz sinks are the host's concern (dotnet/src/Microsoft.Agents.AI.Hosting/AgentSessionStore.cs:43) is the closest anyone comes to assigning the responsibility.

Also notable: an existing confidentiality-label primitive with exfiltration gating sits unwired in agent-framework core (python/packages/core/agent_framework/security.py:267-279) — evidence that the gap is recognized even where it is unfilled.

## Per-Source Notes

- **agent-framework (6/10):** Broadest provider matrix; strongest anti-leak design is the mem0 storage/retrieval scope split with a fail-closed read gate; physical partitioning on Cosmos; delete coverage asymmetric between Python and .NET and across providers; no audit; privacy beyond scoping delegated via doc remarks.
- **crewai (5/10):** Cleanest deletion lifecycle (API + CLI + verified counts + race-safe resets) and well-tested hierarchical scoping; undermined by an untested, storage-bypassable private-record filter on unauthenticated identity, plaintext local persistence, and LLM consolidation performing non-user-initiated deletes.
- **letta (6/10):** Strongest scoping architecture (centralized ORM predicate, mixin-driven ownership columns, org-encoded external stores, two-directional isolation tests) and most complete deletion including vector/git propagation; weakest edges are intra-org all-or-nothing visibility, credential-only encryption with plaintext fallback, default-actor collapse, and org-deletion cascade ambiguity (letta: letta/orm/mixins.py:24; organization_manager.py:79-83).
- **openhands (6/10):** Best secret-handling protocol observed (encrypted round-trips, sentinel placeholders, layered display scrubbing) and a genuinely privacy-conservative opt-in default for persistent memory; but the frontend offers no inspection or deletion of accumulated agent memory, holds API keys/drafts in plaintext localStorage (src/api/backend-registry/storage.ts:98), and audits nothing.
