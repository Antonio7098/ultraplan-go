## Executive Summary

Eight harnesses were studied on the question of how a validated tool call becomes running work. Seven of the eight dispatch tools in-process — as asyncio tasks, thread-pool futures, or awaited coroutines inside the agent loop — and none of those seven embeds a persistent queue or worker pool for individual tool calls. The one outlier, temporal, *is* the durable dispatch substrate: it schedules "tools" (activities) through a three-hop DB-backed pipeline ending in pull-based workers.

Despite radically different substrates, the sources converge on a surprisingly stable contract: tool calls are batched per model response, dispatched concurrently by default (or degraded deliberately), and their results are **reassembled in model-emission order** regardless of completion order — a guarantee implemented via index-keyed collection in at least five sources and pinned by tests in four. Failure containment is likewise convergent: a failing call triggers sibling cancellation with bounded drain, never silent stragglers. Where sources genuinely diverge is on three axes: durability (process-lifetime vs event-sourced), trust boundaries (who is allowed to run what, where), and whether scheduling decisions themselves are observable — which almost nowhere they are; most systems can show you *what* ran but not structured evidence of *why it ran now*.

## Core Thesis

Across all eight sources, mature tool dispatch is defined less by the concurrency mechanism than by two discipline points that recur everywhere:

1. **Separate gating from execution.** The strongest dispatchers classify the whole batch before running any of it — approvals (agent-framework whole-batch pause), dedupe/fingerprints (openai-agents-sdk), exec-spec staging (letta), kind classification + deferred collection (pydantic-ai), degradation checks (crewai), confirmation policy (openhands). Partially executing a mixed batch before its gates resolve is treated as a bug class, not an optimization.
2. **Treat ordering as an assembly-time reconstruction, not an execution property.** Every source that allows concurrent completion rebuilds deterministic order afterward — `ordered_results[idx]` futures (crewai), index-sorted appends in a `finally` block (pydantic-ai), per-call result groups flattened after gather (agent-framework), results keyed by tool-run id (openai-agents-sdk), index placement (letta), sorted write application (langgraph).

The rubric question — *"can the runtime explain why this tool ran now?"* — exposes the field's shared gap: observability is rich about execution (spans, events, metrics) but thin about decision attribution. agent-framework, langgraph, pydantic-ai, and openhands each explicitly list "why did this run now" attribution as missing or future work; temporal comes closest with dedicated dispatch-latency metrics, yet even there distributed tracing stops at the history-executor boundary.

## Approach Models

Six distinct approach models emerge:

**A. Batch fan-out runtime** (agent-framework, crewai). The model response's tool calls form one native unit: classified, then executed concurrently — one `asyncio.create_task` per call joined by gather (agent-framework, `python/packages/core/agent_framework/_tools.py:1848-1864`) or futures into an ephemeral thread pool capped at 8 (crewai, `lib/crewai/src/crewai/agents/crew_agent_executor.py:742-767`). Ordering is preserved by writing results back into emission-index slots. No queue exists anywhere in-repo; durability equals process lifetime.

**B. Plan-partition-execute pipeline** (openai-agents-sdk). Dispatch is decomposed into named phases — discovery (`ProcessedResponse`, `src/agents/run_internal/run_steps.py:117-131`), planning (`ToolExecutionPlan`, `tool_planning.py:557-573`), execution (`_execute_tool_plan`, `tool_planning.py:944-1101`). Function tools run eagerly as capped asyncio tasks; side-effect-heavy categories (shell, apply_patch, computer) serialize internally. This is stated maintainer policy, not accident (`.agents/references/tool-execution-lifecycle.md:7`).

**C. Strategy-processor segmented scheduler** (pydantic-ai). One dispatcher module selects among `'early'/'graceful'/'exhaustive'` processor subclasses; within a strategy, calls are segmented around `sequential=True` barriers so independent tools overlap while gated tools run alone (`_tool_execution.py:232-251`). Deferred (`external`/`unapproved`) calls leave the process as a `DeferredToolRequests` hand-off rather than entering an internal queue.

**D. Engine-mediated generic task dispatch** (langgraph, temporal). Neither has a tool-specific scheduler. langgraph lowers tool calls into `Send("tools", ...)` packets consumed by a BSP superstep engine (`libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py:849-859`; sends execute in superstep n+1, `libs/langgraph/langgraph/pregel/_algo.py:961-967`), inheriting checkpointing, retries, interrupts, and error routing from generic task machinery. temporal routes activity commands through DB-backed transfer queues and a layered scheduler (interleaved weighted round-robin → execution-aware sequential queues → FIFO pool, `service/history/queues/scheduler.go:151-175`) to a matching service that sync-matches or spools to durable backlog (`service/matching/task_queue_partition_manager.go:600-677`).

**E. Type-keyed executor factory in an application server** (letta). A declarative map from seven `ToolType`s to executor classes (`letta/services/tool_executor/tool_execution_manager.py:35-43`) routes each call; user-authored code is process-isolated (local subprocess with terminate→kill escalation, or E2B/Modal remote sandboxes). Parallelism is opt-in per tool via `enable_parallel_execution` (default `False`, `letta/schemas/tool.py:62-64`).

**F. Thin-client trigger with inverted client tools** (openhands frontend). The browser never runs agent tools; it triggers runs (`{run: true}` over WebSocket, REST queue fallback when disconnected) and executes only server-advertised *client tools* whose ActionEvents arrive on the socket (`src/api/agent-server-adapter.ts:1116-1119`). Scheduling authority is entirely remote; the client's job is defensive ordering and consumer-side idempotency.

These models are responses to different constraints, not quality tiers: A/B/C fit library shape and process-local guarantees; D buys replayability and scale by making tools indistinguishable from other work; E buys isolation for untrusted code; F buys a single authoritative scheduler behind stateless clients.

## Pattern Catalog

### P1. Index-keyed deterministic reassembly
- **Problem:** Concurrent execution destroys ordering that both the LLM conversation and reproducibility depend on.
- **Sources:** agent-framework (`_tools.py:1878-1879`, spec at `docs/specs/004-python-function-calling-loop.md:340`), crewai (`crew_agent_executor.py:743-776`), openai-agents-sdk (`tool_execution.py:2239-2305`, resume sort at `turn_resolution.py:2503-2508`), pydantic-ai (`_tool_execution.py:204-229,838-847`: parts appended `for index in sorted(...)` inside `finally`), letta (`letta_agent_v3.py:1855-1862`), langgraph (sorted write application `_algo.py:256`; deterministic output test `tests/test_pregel.py:1207-1217`).
- **Why it works:** Completion stays free; the only serialization point is cheap list assembly, so the model always sees its own emission order and replays are reproducible.
- **Copy when:** Any fan-out feeds conversation history or checkpoints.
- **Overkill/risky when:** Never really — but note openai-agents-sdk's caveat that intermediate observers see out-of-order completions; the guarantee holds only for final item lists.
- **Evidence strength:** Direct code + tests in six sources; this is the dimension's strongest convergence.

### P2. Classify-the-whole-batch-before-executing-any
- **Problem:** Mixed batches (some calls need approval / are unknown / are side-effectful) invite partial execution before safety gates resolve.
- **Sources:** agent-framework pauses the entire batch if any call needs approval (`_tools.py:1775-1832`); crewai degrades to first-call-only when `result_as_answer`/`max_usage_count` tools appear (`crew_agent_executor.py:698-724`); letta diverts approval/client tools to an approval gate that stops the loop (`letta_agent_v3.py:1681-1709`); openai-agents-sdk partitions approvals during planning before invocation (`tool_planning.py:593-646`); pydantic-ai collects deferred kinds during the walk and resolves them as one batch (`_tool_execution.py:910-1050`); openhands configures confirmation policy at conversation start and releases held calls via REST (`agent-server-adapter.ts:600-604`).
- **Why it works:** Safety semantics become batch-granular and explainable ("this batch paused because call 3 needs approval") instead of emergent from interleaving.
- **Copy when:** Any approval/HITL or usage-limit semantics exist.
- **Cost:** Latency — human gates serialize mixed batches (agent-framework names this tradeoff explicitly); crewai discards sibling calls entirely for that turn.

### P3. Sibling-failure cancellation protocol
- **Problem:** When one call fails mid-fan-out, stragglers either leak side effects or hang the run.
- **Sources:** openai-agents-sdk is the reference implementation — cancel → bounded drain (0.25s/64 steps/0.1s windows) → deterministic failure arbitration by priority then call order (`tool_execution.py:167-169,258-304,1685-1715`). agent-framework cancels and awaits every sibling on `BaseException` then re-raises (`_tools.py:1863-1876`). pydantic-ai runs `cancel_and_drain(*tasks)` on both exception shapes (`_tool_execution.py:828-837`). langgraph cancels siblings via `_should_stop_others` and panics unless routed to an error-handler node (`_runner.py:616-697`).
- **Why it works:** Bounded drain plus deterministic error selection makes failure behavior a contract, testable and identical across runs — openai-agents-sdk has ~30 tests on these paths alone.
- **Copy when:** Concurrency exists. **Watch for:** sync bodies can't truly be cancelled anywhere (thread offloading) — agent-framework documents exactly this honesty in tests (`test_middleware_with_agent.py:2596-2659`); langgraph can cancel only not-yet-started sync tasks (`_executor.py:59`).

### P4. Explicit concurrency cap as configuration
- **Problem:** Unbounded eager fan-out amplifies cost, races, and provider load.
- **Sources:** openai-agents-sdk `RunConfig.tool_execution.max_function_tool_concurrency` implemented as FIFO slot refill, with queued-but-unstarted calls never started after a failure (`run_config.py:136-158`; `tool_execution.py:1643-1653`; tests `test_run_step_execution.py:250-363`). langgraph `max_concurrency` semaphore over async tasks (`_executor.py:131-140`; test caps 100 Sends at 10). crewai hardcodes `min(8, len(plan))`. letta uses a binary per-tool flag instead of a numeric cap. temporal bounds per-workflow concurrency via pending-activity limits plus multi-tenant rate limiting (`workflow_task_completed_handler.go:520-522`; `ratelimit_manager.go:68-110`).
- **Why it works:** Caps decouple model verbosity from resource consumption while preserving emission-order output.
- **Copy when:** Tool count per turn is untrusted. **Gap elsewhere:** agent-framework found no configurable limit (searched; unbounded except by batch size); pydantic-ai has limits only at run/model level, not per tool.

### P5. Idempotency-by-construction at the dispatch boundary
- **Problem:** Replays, resumes, and at-least-once delivery must not double-run side effects.
- **Sources:** openai-agents-sdk fingerprints invocations `(type, call_id, content hash)` and rejects duplicates before any callback (`tool_planning.py:339-486`); pydantic-ai fails closed on duplicate `tool_call_id`s (`_tool_execution.py:405-420`); openhands guards every non-idempotent side-effect consumer-side — dedup before terminal effects (#1656 regression-tested), submitted-id sets, localStorage claim ledger claimed *before* network I/O (`conversation-websocket-context.tsx:556-568`; `child-conversation-launch.ts:196-227`); temporal accepts at-least-once delivery and compensates with attempt counters/vector clocks (`transfer_queue_task_executor_base.go:115`); agent-framework settles dangling service-conversation calls with synthetic errors so providers don't reject the follow-up request (`_tools.py:3082-3157`).
- **Why it works:** Dedupe at identity level is cheaper and more reliable than deduping at effect level.
- **Risky variant:** openhands' browser-scoped ledger silently degrades if storage fails (`child-conversation-launch.ts:220-226`) — a reminder that consumer-side ledgers need failure stories.

### P6. Durable spool with opportunistic fast path
- **Problem:** Durability normally costs latency on every dispatch.
- **Sources:** temporal tries in-memory sync-match first, spools to DB backlog otherwise, and adds eager execution handing the activity back inside the workflow-completion response (`task_queue_partition_manager.go:618-662`; `workflow_task_completed_handler.go:542-658`). Analogously, langgraph matches cached task writes before executing and streams hits as `cached=True` (`_loop.py:1549-1570`).
- **Why it works:** The slow path is the correctness path; fast paths are best-effort optimizations that fall back cleanly.
- **Cost:** Fast paths weaken simple invariants — eager execution records activity starts before the completion transaction commits (temporal), and cache-hit streaming needs explicit marking (langgraph).

### P7. Contract/spec documents binding dispatch behavior to tests
- **Problem:** Dispatch semantics live in subtle async code that drifts easily.
- **Sources:** agent-framework maintains a written spec with scenario-to-test mapping that changes must update (`docs/specs/004-python-function-calling-loop.md:433-532`, enforced via `python/AGENTS.md`); openai-agents-sdk codifies rules like "Preserve model order in emitted outputs" in a maintainer reference with review checklist (`.agents/references/tool-execution-lifecycle.md:21-47`); temporal publishes the fairness design (`service/matching/fairness.md`).
- **Why it works:** Turns implicit scheduling guarantees into reviewed artifacts.
- **When overkill:** For a small library with one dispatcher function — though pydantic-ai achieves similar clarity with rationale comments in code (`_tool_execution.py:204-217`).

### P8. Context propagation into fan-out tasks
- **Problem:** Ambient context (traces, logging scopes) doesn't cross task/thread creation automatically.
- **Sources:** agent-framework `contextvars.copy_context().run(asyncio.create_task, ...)` (`_tools.py:1848-1862`, trace-parenting test `test_observability.py:5991-6034`); crewai uses the identical pattern in its pool (`crew_agent_executor.py:748-749`); langgraph's executor submits copy contextvars (`_executor.py:54-75`); openai-agents-sdk's submit does the same (`_executor.py:40-75`).
- **Why it works:** Without it, parallel tool spans orphan from the agent span, breaking the observability story precisely where concurrency begins. Copy it everywhere you spawn.

## Key Differences

- **Durability locus.** agent-framework/openai-agents-sdk/pydantic-ai accept crash-loss of in-flight work as inherent to in-process dispatch (openai-agents-sdk notes plans are plain data and the natural seam for future externalization, `tool_planning.py:557-573`); langgraph gets per-task durability from checkpointed writes committed as futures complete (`_runner.py:574-613`); letta pushes durability upward to Run records and a separate Anthropic-batch pipeline, leaving inline steps unreplayable; temporal makes durability the default and treats synchronous match as the optimization.
- **Default concurrency posture.** Open by default: agent-framework, openai-agents-sdk, pydantic-ai, langgraph all start every eligible call immediately. Conservative by default: letta (`enable_parallel_execution=False` plus client-side truncation of surplus provider calls, `letta_agent_v3.py:1335-1342`) and crewai's degradation rule. These are product-shape choices — SDKs optimize latency for trusted developers; servers managing memory-mutating agents optimize predictability.
- **Where "batch" ends.** Every source batches exactly one model response's calls; none coalesces across turns. The exceptions redefine granularity upward, not sideways: letta fans a step across many agents via Message Batches API with out-of-process `aiomultiprocess.Pool` execution (`letta_agent_batch.py:397-451`); langgraph's Send API fans arbitrary graph-level fan-out beyond tool nodes.
- **Ordering philosophy.** Libraries reconstruct order post-hoc (P1). langgraph makes planning/commits deterministic and lets execution float. temporal intentionally relaxes global FIFO — fairness passes spread task IDs out of order, requiring B-tree re-merge and admitting repeated dispatch after failover (`fairness.md:13-16,26-28`) — because multi-tenant fairness outweighs strict ordering at its scale. openhands trusts nothing on the wire and defensively re-sorts/dedups on receive (`use-event-store.ts:100-151`).
- **Failure containment granularity.** openai-agents-sdk arbitrates *which* failure surfaces deterministically; agent-framework separates model-recoverable failures (error results fed to the model) from host-fatal ones (`MiddlewareFailure` aborts everything); langgraph offers error-handler-node routing as an alternative to panic; crewai resolves an ignore/warn/raise policy through a tool→task→agent→crew chain (`tool_failure.py:177-208`); temporal escalates repeated executor errors to DLQs (`executable.go:237-241`).
- **Sync-body handling.** Uniform pattern, uneven guarantees: all offload to threads (`asyncio.to_thread` in agent-framework, anyio in pydantic-ai, pools in crewai/langgraph) and all concede such bodies are uninterruptible. Only pydantic-ai converts overrun deadlines into `ModelRetry` so the model self-corrects (`toolsets/function.py:684-693`); crewai's whole-task timeout abandons the worker detached (`agent/core.py:912-918`).

## Tradeoffs

**Inline execution vs durability.**
Benefit: zero infrastructure, transactional locality between tool effects and persistence (letta leans on this — `letta_agent_v2.py:1230-1238`). Cost: restart abandons in-flight steps; only letta's batch mode and langgraph's checkpoints recover anything. Alternative seen: temporal's spool-everything, paying a DB write per unmatched task. Best-fit: libraries stay inline; products promising resumable sessions need at least langgraph-grade commit-on-completion.

**Parallel batching vs side-effect predictability.**
Benefit: wall-clock wins proven by tests (langgraph asserts parallel runtime < sum of durations, `test_pregel.py:5258-5288`; crewai asserts overlap ≥2 from event timestamps, `test_native_tool_calling.py:103-141`). Cost: widened race surface — crewai's repeated-usage guard and last-used tracking exist only on the serial ReAct path (`tool_usage.py:779-789`); letta relies on per-tool discipline for memory mutation, with the sandbox executor asserting immutability by convention (`sandbox_tool_executor.py:135-138`). Alternatives seen: category serialization (openai-agents-sdk), first-call degradation (crewai), opt-in flags (letta), barriers (pydantic-ai).

**Whole-batch approval pause vs throughput.**
Benefit: agent-framework's pause avoids partial side effects when one call needs sign-off. Cost: human latency serializes safe siblings; crewai instead discards the rest of the turn (losing work); openai-agents-sdk partitions approvals so clean calls proceed. Best-fit depends on whether approvals are rare (pause is fine) or frequent (partition or defer).

**Eager start vs capped start.**
Benefit: minimal latency when calls are few and fast. Cost: oversized turns race past budget checks — agent-framework's `max_function_calls` overshoots by up to one batch (verified: limit 5, counter 6, `_tools.py:1348-1351`); pydantic-ai projects usage limits before dispatch instead (`_tool_execution.py:445-448`). Alternative seen: openai-agents-sdk slot-refill keeps queued calls unstarted on failure — turning the cap into a blast-radius control, not just a throttle.

**Observability depth vs hot-path overhead.**
Benefit: letta's reflect-and-scrub `trace_method` plus per-execution metrics/spans/events make dispatch forensics trivial (`otel/tracing.py:228-268`). Cost: paid on every call. Mitigations seen: sensitive-data gating (agent-framework, openai-agents-sdk redaction-aware logging), ToolNode opting out of a redundant node-level span (langgraph, `tool_node.py:772`).

**Generic-engine uniformity vs tool-specific ergonomics.**
Benefit: langgraph's tools-as-nodes inherits retries/timeouts/interrupts/error-routing free; temporal's typed categories get uniform executor-wrapper guarantees (panic recovery, metrics, DLQ, `executable.go:255-349`). Cost: one extra superstep of latency per model→tool transition (langgraph), and decision attribution ("why this ran") sinks below generic abstractions — a recurring theme in the gaps.

## Decision Guide

Choosing an approach model for a new harness:

1. **Building an SDK/library where the host owns the process?** In-process fan-out (model A/B/C). Non-negotiables distilled from the 9-scored sources: index-keyed reassembly, a real concurrency cap, deterministic failure arbitration, and a written lifecycle contract. openai-agents-sdk's plan/partition/execute split and pydantic-ai's barrier segmentation are the two cleanest templates; pick the former if you have heterogeneous tool kinds, the latter if your complexity is in end-strategy semantics (early return vs accumulate).
2. **Need replay, resume, HITL interrupts, or time-travel debugging?** Engine-mediated dispatch (model D). langgraph shows the minimum viable version: content-addressed task IDs derived from (checkpoint, namespace, step, node, path) so resumed runs map onto the same identity (`_algo.py:616-623`). Don't build tool-specific machinery — lower tools into whatever your engine already schedules.
3. **Hosting untrusted/user-authored tools?** letta's type-keyed factory plus process isolation is the reference: enum value + executor class per runtime, subprocess with terminate→kill escalation, remote sandboxes for heavy cases. Apply the MCP timeout lesson: every executor boundary gets an enforced deadline, not a settings entry nobody reads (`base_client.py:104-113`).
4. **Thin client over a remote brain?** openhands' model: trigger surface + status observation + defensive receive path. Budget engineering for reconnect-replay idempotency (they regression-test it) and accept that queue depth/retry policy become invisible.
5. **Human approvals in the loop?** Gate at classification time, never mid-execution. Choose pause-the-batch (rare approvals), partition-and-proceed (frequent approvals), or defer-out-of-process (long approvals, à la pydantic-ai's `DeferredToolRequests`) — but never partially execute a mixed batch without an explicit policy.
6. **Multi-tenant scale with fairness needs?** Nothing in the agent-harness set solves this in-process; temporal demonstrates the required inventory: weighted round-robin across tenants, per-key rate limits, schedule-to-start expiry, ack-level progress tracking, DLQ escalation.

## Practical Tips

- **Write results into pre-allocated slots keyed by emission index** (P1). It's ~10 lines, kills an entire class of ordering bugs, and makes downstream consumers (LLM history, UI, checkpoints) deterministic. Test it the way langgraph does: assert final output order despite concurrent completion.
- **Make the concurrency cap a first-class config value, validated ≥1, documented against the provider-side knob** (openai-agents-sdk explicitly distinguishes SDK-side `max_function_tool_concurrency` from provider `parallel_tool_calls`, `docs/running_agents.md:170-191`). Confusing these two is a likely integration bug.
- **Emit started/finished lifecycle events even on failure paths** — crewai fires the finished event in a `finally` block and sequences retries only *after* emission so subscribers see complete lifecycles for failed attempts too (`tool_usage.py:744-752,754-756`). Their internal tests then measure actual concurrency from event timestamps — proof the trace answers "what ran when."
- **Propagate ambient context explicitly into every spawned task** (`copy_context().run` or equivalent). Four sources independently converged on this; without it your tracing dies exactly at fan-out.
- **Convert tool timeouts into retry feedback to the model** rather than bare exceptions (pydantic-ai: `TimeoutError` → `ModelRetry('Timed out...')`), and track retry budgets per tool name across steps with reset-on-success.
- **Fail closed on ambiguous identities**: duplicate call IDs should raise, not mis-bind results (pydantic-ai `UserError`; openai-agents-sdk `ModelBehaviorError` with a dedicated reuse suite).
- **Settle dangling calls before surfacing an abort** when the conversation lives server-side — unresolved `function_call` items get rejected by providers on the next request (agent-framework's synthetic-error settlement).
- **Pair every fast path with its fallback**: sync-match falls back to spool; eager execution falls back to normal dispatch; WS send falls back to queued REST. Untested fallback paths are where dispatch systems rot.
- **Document cancellation honesty**: say precisely what happens to a sync body surviving cancellation (agent-framework's test suite does: side effect completes, result discarded, no further model call). Undocumented half-cancellation is worse than documented loss.

## Anti-Patterns / Caution Signs

- **Dispatch logic forked across implementations.** crewai's three paths drift on unknown-tool behavior (raise vs structured failure), batching, and guard coverage — the report's primary score limiter. Caution sign: the same conceptual step implemented twice in one package. Same smell in pydantic-ai's graceful/exhaustive skeletons and langgraph's `tick`/`atick` duplication, both flagged internally.
- **Configuration that doesn't reach execution.** letta defines `mcp_execute_tool_timeout` yet awaits MCP calls with no wrapper — dead config that manufactures hangs. Audit that every knob is read on the hot path.
- **Magic numbers governing cleanup.** openai-agents-sdk's fixed 0.25s/64-step/0.1s drain windows bound correctness by constants; fine until a pathological handler exceeds them and gets abandoned as background work. Expose or justify such constants.
- **Module-global mutable state coordinating async lifecycles.** langgraph's `SKIP_RERAISE_SET` weakset suppresses duplicate exception surfacing across functions — works, but process-global and explicitly self-flagged as fragile.
- **Ack-before-execute across a trust boundary.** openhands' server acknowledges client tools before the browser does the work; the agent may act on stale assumptions until the follow-up message arrives. If you must ack early, carry the divergence in-band (their result-prefix protocol) — and expect to explain it forever.
- **Consumer-side idempotency keys in ephemeral storage.** localStorage claim ledgers die with site data and degrade silently when full (`child-conversation-launch.ts:220-226`). Exactly-once-ish claims belong server-side.
- **Generational accretion without deletion.** letta's V1/V2/V3 loops implement overlapping dispatch semantics (V1's "temp hack" takes only the first parallel call); three generations triple the drift surface. If a new loop ships, schedule the old ones' funeral.
- **Timestamp sorting as ordering substrate.** openhands sorts events by lexicographic ISO strings — broken by mixed timezone offsets. Ordering derived from clocks is ordering you don't own.
- **Traces that stop at a service boundary.** Even temporal — the observability leader here — lacks OTEL in the matching service, so cross-service dispatch causality requires log archaeology. Trace continuity is part of dispatch design, not a nice-to-have.

## Notable Absences

Across all eight sources, no evidence was found of:

- **Priority schemes or dependency graphs among calls within a batch.** Execution order is model-emission order everywhere; only temporal implements priorities, and only across workflows/tasks, not within a model turn (langgraph explicitly lists intra-superstep priority as absent).
- **Cross-turn coalescing.** No source merges tool calls from separate model responses into one dispatch unit. Batching scope equals the provider response in every case.
- **First-class decision attribution.** No source emits a structured record tying a dispatch to its trigger (model turn N, approval event ID, budget state). agent-framework, langgraph, pydantic-ai name it as future work; openhands reconstructs causality from the event log; temporal's `task_dispatch_latency` measures the hop, not the cause.
- **Per-tool cancellation that actually interrupts running work.** Thread-offloaded sync bodies are uninterruptible in agent-framework, crewai, langgraph, pydantic-ai alike; letta polls cancellation only at step boundaries; langgraph cancels only not-yet-started sync tasks.
- **In-repo durable queues for individual tool calls** in any framework source. Durability, where present, lives at coarser granularity: runs (letta), graph checkpoints (langgraph), deferred hand-offs (pydantic-ai), or the whole system (temporal).
- **Configurable dispatch concurrency in agent-framework** — searched for semaphores/pools in both languages; unbounded apart from batch size.

## Per-Source Notes

- **agent-framework (8):** The Python function-invocation loop is the study's most completely specified in-process dispatcher — layered pipeline, budgets-as-state surviving streaming re-entry, fail-closed aborts with settlement, MCP long-running tasks surfaced transparently. .NET borrows the external M.E.AI loop with compensating decorators, leaving its scheduling semantics unauditable here.
- **crewai (7):** Best-in-class event-bracketed lifecycle tracing and creative guardrails (atomic usage claims, RPM gates, hook vetoes), undercut by three parallel dispatch implementations whose batching semantics disagree and whose differences are undocumented.
- **langgraph (8):** Tools become ordinary checkpointed tasks via `Send`, buying replay/interrupts/retries from the engine. Pays an n+1 superstep barrier, carries fragile global reraise state, and can't force-cancel sync tasks — but its content-addressed task identity is the study's cleanest resume story.
- **letta (7):** The only source that isolates user code by construction (subprocess/remote sandboxes) and the richest operational telemetry (spans, two metrics, persisted step metrics, loop watchdog). Inline dispatch means crashes lose steps; the dead MCP-timeout setting and untested V3 parallel branch are concrete liabilities.
- **openai-agents-sdk (9):** Reference architecture for plan-partition-execute with deterministic failure arbitration and exceptional failure-path testing; its maintainer lifecycle contract is the artifact other sources approximate. Costs: magic drain constants and private-attribute asyncio introspection.
- **openhands (6):** Studied from the frontend, so the decisive scheduler is out of view — but what's visible is disciplined: transport-degradation queues, flush-barrier display ordering, regression-tested replay idempotency, inverted client-tools with claim ledgers. Score reflects unverifiable core, not poor engineering.
- **pydantic-ai (9):** Densest dispatch design in the set: three end strategies, per-tool barriers, three managed orderings (start/completion/history), deferral as an out-of-process continuation, and meticulous cancellation hygiene — concentrated in modules complex enough to carry `# noqa: C901`.
- **temporal (9):** Not an agent harness; included as the durable-dispatch ceiling. Event-sourced three-hop pipeline, fairness via ordered fair-level B-trees, sync-match/eager fast paths, uniform executor wrappers with panic recovery and DLQs. Its absences (matching-hop traces, single composed ordering doc) show even mature systems have seams.

- **openai-agents-sdk:** What are the intended entry points for the undocumented `parallel=False` branch of `_execute_tool_plan`? Were the drain constants tuned empirically?
- **pydantic-ai:** Is the `'early'` strategy's skip-stubbing of function tools observable to consumers purely via events? End-to-end verification is missing.
- **temporal:** Can the composed end-to-end ordering semantics (priorities × fairness × partitions) be stated in one place? Will OTEL extend into matching dispatch?
