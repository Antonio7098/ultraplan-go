## Executive Summary

Tool permission and approval handling in this corpus falls into a clear spectrum from "the framework owns it" to "the user owns it entirely". Three sources — `agent-framework` (8/10), `pydantic-ai` (8/10), and `openhands` (7/10) — ship explicit, runtime-enforced approval models with persistence, tests, and visible policy metadata. Two sources — `openai-agents-sdk` (6/10) and `crewai` (5/10) — ship a partial surface: a per-tool approval flag in the SDK, a hooks-only surface in CrewAI. `langgraph` (3/10) and `opa` (5/10) operate in fundamentally different domains; LangGraph deliberately delegates to user wrappers, while OPA's capabilities model is a compile-time allowlist for builtins in a decision language, not a runtime approval gate for agent tools.

No source ships a true risk taxonomy (read-only / write / delete / network / secret / money) as first-class tool metadata. `openhands` is closest with its typed `SecurityRisk = UNKNOWN | LOW | MEDIUM | HIGH` enum, but that value is LLM-predicted per action, not declared per tool. Everywhere else, risk is a developer-set boolean, a callable, or absent entirely. This is the most consistent cross-source finding: the **declared** risk surface is binary ("needs approval or not"), and richer classification is something users must layer on.

Yes, the runtime can stop a high-risk tool even if the model asks for it — but only in the sources that ship a declarative approval flag (`agent-framework`, `openai-agents-sdk`, `pydantic-ai`) or a centralized policy class (`openhands`). In `crewai` and `langgraph`, the answer is "only if user code exists". In `opa`, the answer is "only at compile time for builtins, only for network hosts at runtime, and never in server mode".

## Core Thesis

**The maturity axis for tool permission/approval is not "does the framework have a permission system?" but "does the framework refuse to execute a high-risk tool by default, without the developer having to remember to enable safety?".** A scoring rubric that reflects this:

1. *Refusal-by-default* — can the runtime stop a high-risk tool even if neither the developer nor the operator configured anything? (OPA's compile-time allowlist qualifies; agent-framework's `_try_execute_function_calls` short-circuit qualifies for any tool whose `approval_mode` is set.)
2. *Declarative metadata* — is there a typed field on the tool object that the runtime reads? (Three sources have this; four do not.)
3. *Selective approval granularity* — per-call? per-tool? per-arguments? per-session? per-server-boundary? (Pydantic AI leads here.)
4. *Persistence and audit* — do approval decisions survive serialization, restart, or schema upgrades? (OpenAI Agents SDK leads with its versioned `RunState`; agent-framework via session state; pydantic-ai via the conversation log; openhands only for settings.)
5. *Risk classification* — is there a typed enum that distinguishes read-only / network / secrets / etc.? (Nobody ships one as a first-class tool field.)

The most consequential difference between the top three and the bottom four sources is **whether the framework's own execution loop short-circuits unapproved calls**. If it does — `agent-framework`'s `_try_execute_function_calls`, `pydantic-ai`'s `deferred_calls_by_kind['unapproved']`, `openai-agents-sdk`'s `_collect_runs_by_approval`, `openhands`'s SDK-side `ConfirmationPolicyBase` — safety travels with the framework and the developer cannot accidentally disable it. If it does not — `crewai`'s hook list, `langgraph`'s wrapper callback — safety is the developer's responsibility, and a forgotten hook means a forgotten safeguard.

## Approach Models

The seven sources cluster into four approach models, each with a distinct cost/benefit profile.

### Model 1: Declarative flag + runtime gate

`agent-framework`, `openai-agents-sdk`, `pydantic-ai` all use a per-tool boolean (or callable) that the framework's execution loop checks before invoking the tool body. The execution path is guaranteed to be gated — there is no user code that can skip the check.

- **agent-framework** stores the flag as `FunctionTool.approval_mode: Literal["always_require", "never_require"]` (`_tools.py:96`); the function-call loop computes `approval_tools = {name for name, tool in tool_map.items() if tool.approval_mode == "always_require"}` and short-circuits before any invocation (`_tools.py:1691-1755`).
- **openai-agents-sdk** stores the flag as `needs_approval: bool | Callable` on every tool type (`tool.py:426, 1221, 1269, 1300`); three independent code paths — `_collect_runs_by_approval` (`tool_planning.py:376-447`), per-tool executors (`tool_actions.py:456-485, :645-674, :818-842`), and `_resolve_tool_run` (`tool_execution.py:2233-2278`) — all gate on the same helper.
- **pydantic-ai** stores the flag as `requires_approval: bool` and *derives* `ToolKind = Literal['function', 'output', 'external', 'unapproved']` from it (`tools.py:649`); the agent graph routes `'unapproved'` calls into `deferred_calls_by_kind['unapproved']` (`_agent_graph.py:1749-1776`).

All three default the flag to "off / not required". The difference is in extensibility:

- agent-framework adds a parallel `kind: str` field (currently only `"shell"`) and an experimental IFC layer (`IntegrityLabel`, `ConfidentialityLabel`).
- openai-agents-sdk adds a callable form so policies can be per-call functions; `RunContextWrapper._approvals` carries sticky and per-call decisions.
- pydantic-ai adds a wrapper-toolset pattern (`ApprovalRequiredToolset`) that wraps any toolset in a runtime predicate.

**Best-fit**: products that ship built-in tools (file access, shell, MCP) and want safety to travel with the tool object.

### Model 2: User-supplied wrapper as the only enforcement

`crewai` and `langgraph` ship no permission system; the framework hands the user a hook point and trusts them to wire safety into it.

- **crewai** maintains a process-global `_before_tool_call_hooks` list (`hooks/tool_hooks.py:124-125`); the four execution paths (`utilities/tool_utils.py:105-114,225-234`, `agents/crew_agent_executor.py:954-979`, `experimental/agent_executor.py:1953-1977`, `utilities/agent_utils.py:1508-1528`) all iterate the list; a `False` return blocks the call. The hook context exposes `request_human_input` (`hooks/tool_hooks.py:79-121`) which calls `builtins.input()` — a synchronous stdin prompt.
- **langgraph** exposes `wrap_tool_call` / `awrap_tool_call` callbacks (`tool_node.py:755-778,1014-1067,1161-1222`) that receive `ToolCallRequest` and may short-circuit by returning early without invoking `execute`. `interrupt(value)` raises `GraphInterrupt` (`types.py:811-934`) and is the only declarative pause primitive.

Both frameworks enforce nothing by default. CrewAI's risk-allowlist recipe is `destructive_tools = [...]` inside a hook (`docs/edge/en/learn/tool-hooks.mdx:160-179`). LangGraph's risk gate is a `wrap_tool_call` that inspects `request.tool_call["name"]`.

**Best-fit**: libraries that want maximum flexibility and assume the application developer will write their own policy. The cost is that a new user with zero configuration has no protection.

### Model 3: External SDK policy class with transport

`openhands` is the only source that splits the policy decision across two processes. `_select_confirmation_policy(confirmation_mode, security_analyzer)` (`app_conversation_service_base.py:641-652`) chooses one of three SDK classes (`NeverConfirm`, `ConfirmRisky`, `AlwaysConfirm`) and ships it to a remote `agent-server` Docker container via HTTP POST (`app_conversation_service_base.py:683-697`). The runtime's confirmation enforcement happens inside that container; this tree only handles policy selection and UI surfacing.

`openhands` is also the only source that ships a typed risk enum (`SecurityRisk = UNKNOWN | LOW | MEDIUM | HIGH`) on every action event (`frontend/src/types/v1/core/base/common.ts:59-64`), but the value is LLM-predicted per call by `LLMSecurityAnalyzer`, not declared per tool.

**Best-fit**: products with a backend/frontend split where the agent runs in a sandbox container. The cost is operational split-brain (HTTP failure leaves the conversation with whatever analyzer was already installed) and a global flag instead of a per-tool matrix.

### Model 4: Compile-time allowlist for a non-agent registry

`opa` is structurally different: it is a policy decision engine, not an agent framework. Its "tools" are builtins like `http.send` and `opa.runtime`. The permission surface is `Capabilities.Builtins` (`v1/ast/capabilities.go:84-101`), enforced by `WithCapabilities` at compile time (`v1/ast/compile.go:571-574, 1997-2005`). At runtime, only `allow_net` (`v1/topdown/http.go:374-383`) re-checks; everything else is trusted to compile-time gates.

Critically, `opa run` server mode has no `--capabilities` flag (`cmd/run.go` is silent on `capabilities`), so the primary production deployment mode cannot restrict builtins at all. The `Nondeterministic` flag that marks `http.send`, `opa.runtime`, `io.jwt.encode_sign*` exists for partial-evaluation correctness, not for risk gating (`v1/topdown/save.go:494`).

**Best-fit**: a registry of pure functions where the threat is "an untrusted policy calls a dangerous function". Risk is categorical (this function is dangerous, that one is not), not per-invocation.

## Pattern Catalog

Patterns that appear in multiple sources or that one source demonstrates with unusual clarity.

### Pattern 1: Approval as a first-class discriminated kind, not a boolean flag

**Problem**: A boolean "needs approval" flag is invisible to the model and forces the runtime to remember to check it. Mixing multiple side-effect behaviors (execute / external service / requires approval) under one boolean is error-prone.

**Where demonstrated**:
- `pydantic-ai` — `ToolKind = Literal['function', 'output', 'external', 'unapproved']` (`tools.py:682`); the agent graph branches on `kind` rather than checking a flag.
- `agent-framework` — `Content` types include `function_approval_request` and `function_approval_response` as first-class items (`_types.py:1213-1299`), so approval flows as ordinary messages.

**Why it works**: The runtime's switch statement becomes exhaustive over a closed set; new kinds (e.g., "payment") can be added by adding a value, not by patching every execution path.

**When to copy**: When you have ≥3 distinct invocation semantics (execute locally, defer for external, require approval). For 1-2 semantics, a boolean is fine.

**When overkill**: A simple read-only API with one tool class — the boolean is clearer.

### Pattern 2: Callable policy with strict type validation

**Problem**: Approval policies often need context (args, deps, run state, prior calls) to decide. A boolean forces operators to write per-tool subclasses.

**Where demonstrated**:
- `openai-agents-sdk` — `needs_approval` accepts `bool | Callable[[RunContextWrapper, dict, str], Awaitable[bool]]` (`tool.py:426-433`); invalid types raise `UserError` (`util/_approvals.py:27-31`, tested at `test_hitl_error_scenarios.py:868-910`).
- `pydantic-ai` — `AbstractToolset.approval_required(approval_required_func)` wraps any toolset; default predicate is `lambda ctx, td, args: True` (`toolsets/abstract.py:230-242`, `toolsets/approval_required.py:22-32`).

**Why it works**: Policies become functions the user writes once and the framework normalizes. Strict validation catches typos at registration time, not in production.

**When to copy**: When policy depends on validated arguments, run context, or prior decisions. Always validate the type.

**When overkill / risky**: When the policy is just "approve this single tool". A boolean is simpler.

### Pattern 3: Per-call-id approval, not per-tool-name approval

**Problem**: Two parallel calls to the same `delete_file(path="/a")` and `delete_file(path="/b")` may have different risk profiles; per-tool approval loses that distinction.

**Where demonstrated**:
- `pydantic-ai` — `DeferredToolResults.approvals: dict[str, bool | DeferredToolApprovalResult]` is keyed by `tool_call_id` (`tools.py:389-392`); a single run can approve one and deny the other.
- `openai-agents-sdk` — `_ApprovalRecord.approved: bool | list[str]` carries per-call `call_id` lists alongside sticky booleans (`run_context.py:29-41`); `_apply_approval_decision` keeps them coherent (`run_context.py:309-353`).

**Why it works**: Granularity matches the model's request granularity; the UI can render "approve one, deny one" without inventing a new schema.

**When to copy**: Whenever the same tool can be called multiple times in one turn. The cost is per-call storage.

**When overkill**: Single-call tools. A sticky decision is simpler.

### Pattern 4: Server-label boundary for hosted tools

**Problem**: Two MCP servers may both expose a tool named `delete_file`; an "approve delete_file once" should not auto-approve the identically-named tool on the other server.

**Where demonstrated**:
- `agent-framework` — hosted-tool approval rules match on `server_label` so same-named tools on different remote servers don't share approvals (`_harness/_tool_approval.py:61-65, 310-323`); test `_standing_rules_include_hosted_server_boundary`.

**Why it works**: Identity in hosted-tool scenarios needs server + name, not just name. The cost is one extra field in the rule.

**When to copy**: Whenever tools can come from multiple external sources (MCP servers, A2A agents, plugin marketplaces).

### Pattern 5: Approval content as a typed envelope, not a free-form payload

**Problem**: `interrupt(value)` accepting arbitrary Python objects forces every UI integration to invent its own schema. A typed envelope round-trips through serialization cleanly.

**Where demonstrated**:
- `pydantic-ai` — `DeferredToolApprovalResult = Annotated[ToolApproved | ToolDenied, Discriminator('kind')]` (`tools.py:365`); `ToolApproved.override_args: dict[str, Any] | None` lets approvers edit validated args (`tools.py:329-336`); `ToolDenied.message: str` lets approvers inject a model-facing explanation (`tools.py:339-348`).
- `agent-framework` — `Content.from_function_approval_request(...)` / `Content.from_function_approval_response(...)` as named Content types (`_types.py:1213-1299`); policy-violation metadata travels on `additional_properties`.

**Why it works**: Discriminated unions serialize and deserialize cleanly across durable engines (Pydantic AI: Temporal, Prefect); typed fields prevent "what does this key mean again?" drift.

**When to copy**: When the approval flow crosses a transport boundary (HTTP, durable engine, UI).

**When overkill**: When the approval surface is a single function call in one process — a dict will do.

### Pattern 6: Server-side deny-by-default on inbound resume

**Problem**: When an approval is in flight, a missing or hostile client response must not silently execute the tool.

**Where demonstrated**:
- `pydantic-ai` — AG-UI adapter documents and enforces "approval requires an explicit payload" so a missing response cannot execute (`ui/ag_ui/_interrupt.py:104-132`); the adapter converts inbound payloads to `ToolApproved`/`ToolDenied` and defaults to denial.

**Why it works**: Fail-closed defaults for approval are safer than fail-open. The cost is needing to teach the UI client to send explicit payloads.

**When to copy**: Whenever approval state crosses a network boundary.

### Pattern 7: Pipeline stage as policy enforcement point

**Problem**: A scattered set of `if approval_required: ...` checks across the runtime is brittle; a single named stage is testable and skippable.

**Where demonstrated**:
- `opa` — each policy check is a named, individually skippable compile stage (`v1/ast/compile.go:212, 254, 475-479`); `StageID` constants make the enforcement points enumerable.
- `agent-framework` — `ToolApprovalMiddleware` and `PolicyEnforcementFunctionMiddleware` are pluggable middleware classes (`_harness/_tool_approval.py:345`, `security.py:1529`), each with its own priority and chain position.

**Why it works**: Stages can be disabled in tests, observed in production, and reordered for performance.

**When to copy**: When the policy stack is complex enough that order matters.

### Pattern 8: Defense-in-depth: bypass closure at mock/replacement boundaries

**Problem**: A "deny dangerous tool" check can be bypassed via `with`-replacement, sandbox rewrites, or wrapper injection. A single check is not enough.

**Where demonstrated**:
- `opa` — `validateWith` / `isBuiltinRefOrVar` reject unsafe builtins used as `with` replacement targets (`v1/ast/compile.go:7017-7026, 7146-7152`); tests assert denial covers the mock path (`compile_test.go:11413, 11422`).
- `agent-framework` — MCP applies both an allowlist built from `inputSchema.properties` and a denylist of framework-named parameters (`_mcp.py:88-98, 1769-1803`); explicit per-tool "extras" win over the denylist.

**Why it works**: A determined attacker finds the bypass you didn't think of. Closing the obvious mock boundary is cheap insurance.

**When to copy**: Whenever your runtime supports `with`-style overrides, monkeypatching, or schema-driven argument injection.

### Pattern 9: Sticky rejection message for "always reject" decisions

**Problem**: If the call_id is reissued after a sticky "always reject" decision, the model needs to know *why* the call was rejected — not just "rejected".

**Where demonstrated**:
- `openai-agents-sdk` — `_ApprovalRecord.sticky_rejection_message` (`run_context.py:40`) carries a stable message that survives call-id reissue.

**When to copy**: When rejection is sticky (i.e., remembered across calls), so the model can adapt its strategy.

### Pattern 10: Risk as event-attribute, not tool-attribute

**Problem**: Declaring risk per tool means the runtime has to know every tool in advance. Predicting risk per call lets the runtime defer to a smarter classifier.

**Where demonstrated**:
- `openhands` — `ActionEvent.security_risk: SecurityRisk` (`frontend/src/types/v1/core/events/action-event.ts:61`) is computed by `LLMSecurityAnalyzer` per call.

**Why it works**: The LLM can decide that `rm -rf /tmp/scratch` is LOW-risk in one context and HIGH-risk in another. The cost is non-determinism and reliance on model quality.

**When to copy**: When tool risk genuinely depends on arguments or context. When risk is a property of the tool itself, declare it on the tool.

### Pattern 11: Compile-time vs. runtime split for permission gates

**Problem**: Runtime gating costs a per-call check; compile-time gating has zero per-call overhead but cannot defend against already-compiled code.

**Where demonstrated**:
- `opa` — capabilities are enforced at compile (`v1/ast/compile.go:1997-2005`); only `allow_net` re-checks at runtime (`v1/topdown/http.go:374-383`).

**When to copy**: When the threat model is "untrusted policy arrives pre-compiled" (OPA, WASM modules). For agent tool calls, runtime gating is essential.

## Key Differences

### Why sources diverge

- **Library vs. application** — `langgraph` and `crewai` are libraries whose consumers wire policy themselves; `agent-framework`, `pydantic-ai`, `openai-agents-sdk` are batteries-included frameworks where the user expects some safety defaults.
- **Multi-process deployment** — `openhands` ships an agent-server Docker image; its policy must cross HTTP. Single-process frameworks (everything else) can pass policy objects directly.
- **Maturity of risk model** — `agent-framework` has an experimental IFC layer (`security.py`); pydantic-ai has only an opaque `metadata` field. The IFC is a research artifact; the metadata is a placeholder.
- **Threat model** — `opa` defends against an attacker submitting a policy; the others defend against a model calling a dangerous tool. Compile-time allowlists make sense for the first; runtime gates make sense for the second.

### What converges across sources

- **Default posture is opt-in.** None of the seven sources ships a "default-require-approval" mode. `agent-framework`'s `approval_mode` defaults to `"never_require"` (`_tools.py:398`); `openai-agents-sdk`'s `needs_approval` defaults to `False` (`tool.py:428`); `pydantic-ai`'s `requires_approval` defaults to `False` (`tools.py:455`); `openhands`' `confirmation_mode` defaults to `False` (`frontend/src/services/settings.ts:13`); `opa` is permissive unless capabilities are supplied; `crewai` and `langgraph` have no default policy at all.
- **Per-call granularity is universal where approval exists.** Sources that ship approval (`agent-framework`, `openai-agents-sdk`, `pydantic-ai`, `openhands`) all key decisions by `tool_call_id`, not just tool name.
- **Risk taxonomy is universally absent.** No source ships a typed enum distinguishing read-only / write / network / secret / money on the tool object.
- **Persistence is variable.** OpenAI Agents SDK uses schema-versioned `RunState`; agent-framework uses `AgentSession.state`; pydantic-ai uses the conversation log; openhands persists settings but not individual decisions; crewai, langgraph, opa persist nothing related to approval.
- **Failure mode is fail-closed in the top tier.** Agent-framework, openai-agents-sdk, pydantic-ai all convert approval policy exceptions into "needs approval" (`run_internal/turn_resolution.py:929-932`); openai-agents-sdk converts invalid types to `UserError`. OPA is fail-open for `allow_net` (`v1/topdown/http.go:375-377`) — a documented exception.

## Tradeoffs

### Per-tool boolean vs. callable vs. wrapper

| Approach | Gain | Cost | Best fit | Failure mode | Alternative seen |
|----------|------|------|----------|--------------|------------------|
| Boolean (agent-framework, pydantic-ai, openai-agents-sdk) | Simple; static | Cannot encode args/context-dependent risk | Tools with uniform risk | Forgotten flag on a destructive tool | callable (openai-agents-sdk) or wrapper predicate (pydantic-ai) |
| Callable (openai-agents-sdk, pydantic-ai predicate) | Per-call context; args-aware | User-supplied code can raise/swallow; not sandboxed | Tool risk varies by arguments | Exception swallowed → fail-closed default in pydantic-ai, fail-closed in openai-agents-sdk via `UserError` | typed metadata schema |
| User-supplied wrapper (crewai hook, langgraph `wrap_tool_call`) | Maximum flexibility; framework-agnostic | Framework cannot enforce; forgotten wrapper = no protection | Library authors who want to delegate | Forgotten hook | declarative flag |

### Per-call vs. sticky approval

| Approach | Gain | Cost | Best fit | Failure mode |
|----------|------|------|----------|--------------|
| Per-call only (no memory) | Minimal UX overhead | Every call must be decided | Read-mostly flows | Annoying for harmless repeat calls |
| Per-call + sticky ("don't ask again") | Less friction for safe tools | User can forget what they auto-approved | Mixed flows | Standing rules persist across runs (`agent-framework` documents this explicitly; OpenAI Agents SDK persists in `RunState`) |
| Server-label-bounded sticky (agent-framework) | Prevents cross-tenant leakage | One extra field | Hosted MCP, A2A | None documented |

### Persistence location

| Location | Gain | Cost | Best fit | Failure mode |
|----------|------|------|----------|--------------|
| Session state (agent-framework) | Survives session resume; one source | Not durable across process restart unless serialized | Long-running agent loops | Cross-restart re-prompts |
| Conversation log (pydantic-ai) | Always with the run | Replay exposes prior approvals to anyone with the log | Durable engine workflows | Log compromise exposes approvals |
| Schema-versioned state (openai-agents-sdk) | Forward-incompatible versions fail-fast | Operators upgrading mid-pause must rebuild state | Production deployments with rolling upgrades | Older SDK rejects newer payload |
| Settings (openhands) | One source of truth | Cannot persist per-call decisions | Configuration-level policy | No audit trail |
| None (crewai, langgraph, opa) | Zero overhead | Decisions die with the process | Ephemeral workflows | No audit, no replay |

### Compile-time vs. runtime enforcement

| Layer | Gain | Cost | Best fit | Failure mode |
|-------|------|------|----------|--------------|
| Compile-time (opa capabilities) | Zero per-call overhead; errors carry source locations | No defense-in-depth; already-compiled code is unconstrained | Bundles, packages, pre-compiled policies | Compiled-then-evaluated bypass (`v1/topdown/eval.go:211-224`) |
| Runtime gate (everywhere else) | Per-call defense; rejects even if the flag is wrong | Per-call check cost | Agent tool calls | Forgotten hook/wrapper |

## Decision Guide

**Choose a declarative per-tool boolean** when you ship built-in tools (file access, shell, MCP) and want safety to travel with the tool object. Default the flag to off, but make the runtime's execution loop unconditionally check it. This is what `agent-framework`, `openai-agents-sdk`, and `pydantic-ai` all do, and it's the simplest path to a guarantee.

**Add a callable form** when policy depends on validated arguments, run context, or prior decisions. Strict-mode type validation (`UserError` for invalid types in `openai-agents-sdk/util/_approvals.py:27-31`) catches typos at registration time. Convert callable exceptions to "needs approval" rather than aborting the run.

**Add a wrapper-toolset / middleware layer** when you need cross-cutting behavior (filtering, metadata, approval, prefixing) that should not be duplicated across each toolset. Pydantic AI's `ApprovalRequiredToolset` and agent-framework's `ToolApprovalMiddleware` show the pattern: a wrapper that intercepts before the leaf executes.

**Use typed envelopes (`ToolApproved`/`ToolDenied`)** when the approval flow crosses a transport boundary (HTTP, durable engine, UI). Discriminated unions round-trip through serialization; free-form payloads force every consumer to invent its own schema.

**Persist approvals in a versioned store** if the run can resume mid-pause in a different process or later. `RunState` with `CURRENT_SCHEMA_VERSION = "1.11"` and `_serialize_approvals` (`run_state.py:359-379`) is the pattern. Agent-session state with explicit serialization is the lighter-weight alternative.

**Skip the central allowlist if your threat model is "the developer registers the wrong tool".** Every framework in this corpus defaults to opt-in approval. The forgotten-flag problem (a developer wraps a destructive tool without setting `needs_approval=True`) is universal. Mitigations exist (typed metadata, linting, default-deny mode) but no source ships one as a default.

**Skip the global `confirmation_mode` flag if your users will want per-tool granularity.** OpenHands' global flag is easy to explain and test, but cannot say "auto-approve `git commit` but require approval for `git push`". A per-tool registry (the future work item in `openhands` and `pydantic-ai`) trades simplicity for expressiveness.

## Practical Tips

Patterns to copy:

- **Expose the approval flag as `bool | Callable` and validate types strictly.** OpenAI Agents SDK's `UserError` for invalid types catches typos that would otherwise become silent runtime bugs (`util/_approvals.py:27-31`).
- **Make the runtime's execution loop unconditionally gate on the flag.** `agent-framework`'s `_try_execute_function_calls` (`_tools.py:1691-1755`) computes the approval set every call, even when no middleware is installed.
- **Key decisions by `tool_call_id`, not tool name.** Two `delete_file` calls in one turn can have different decisions. Pydantic AI (`tools.py:389-392`) and OpenAI Agents SDK (`run_context.py:29-41`) both demonstrate this.
- **Bound hosted-tool approvals by server label.** Agent-framework (`_harness/_tool_approval.py:61-65`) prevents cross-tenant leakage from name collisions.
- **Persist approvals in a schema-versioned store.** OpenAI Agents SDK's `RunState` with explicit `_serialize_approvals` and a forward-incompatible version check (`run_state.py:128-130`) is the strongest pattern.
- **Convert callable policy exceptions to "needs approval".** OpenAI Agents SDK (`run_internal/turn_resolution.py:929-932`) and pydantic-ai (`tool_manager.py:847-919`) both fail closed.
- **Use discriminated unions for approval envelopes.** `ToolApproved.override_args` (`pydantic-ai/tools.py:333`) is the cleanest example — approvals can edit the request, not just gate it.
- **Filter callable policies with named entries.** Pydantic AI's `_ToolHookEntry.tools: frozenset[str]` (`capabilities/hooks.py:86-89`) is reusable for any "do X to tools named Y" pattern.

Patterns to avoid or delay until needed:

- **A central risk enum (read-only/write/network/secrets/money) on the tool object.** Every source in this corpus considered it; none shipped it. The cost of inventing one is high; the value is unproven. Wait for a use case.
- **A global `confirmation_mode` flag without a per-tool matrix.** OpenHands' flag is easy to explain; users will quickly want per-tool control. Build the per-tool layer alongside the flag, not after.
- **Module-level global hook lists.** CrewAI's `_before_tool_call_hooks` (`hooks/tool_hooks.py:124-125`) leaks across agents and tests; clearing requires a dedicated helper (`clear_all_tool_call_hooks`, `hooks/tool_hooks.py:304-317`). Per-instance or per-execution registries are cleaner.
- **`builtins.input()` for approval prompts.** CrewAI's `request_human_input` (`hooks/tool_hooks.py:114`) blocks the event loop in async contexts; the async fallback `asyncio.to_thread(input)` (`core/providers/human_input.py:441`) is fragile. Use a queue/webhook from day one.
- **Compile-time-only enforcement for tool calls.** OPA's model works for builtins because policies are pre-compiled; it would fail for agent tool calls because the runtime must reject at call time. Don't copy compile-time-only for runtime tool gating.
- **Persistence via untyped `additional_properties` dicts.** Agent-framework's IFC metadata (`security.py:837-846`) lives as string-keyed dict members; a typo silently disables policy. Pydantic AI's `metadata: dict[str, Any]` (`tools.py:734-738`) has the same problem. Use a Pydantic model.
- **Naming a module `tool_validator.py` when it validates argument schemas.** LangGraph's `tool_validator.py` (`libs/prebuilt/langgraph/prebuilt/tool_validator.py:43-114`) is a misleading name that future readers will assume is the permission surface. Name it for what it does.

Decision rules:

- **Library, not application?** Lean toward user-supplied wrappers (langgraph/crewai model) so consumers don't pay for a permission system they don't use.
- **Application with built-in tools?** Lean toward a declarative flag (agent-framework/openai-agents-sdk/pydantic-ai model) so safety is on by default for your own tools.
- **Multi-process / sandbox deployment?** Lean toward a settings-driven policy class with HTTP transport (openhands model).
- **Decision engine, not agent framework?** Compile-time allowlists (opa model) work for pre-built bundles; runtime gates are unnecessary overhead.
- **Want strict-mode type validation?** OpenAI Agents SDK's `UserError` is the pattern.

Caution signs:

- The flag defaults to "off" and the documentation does not say "set this for destructive tools". Forgotten flags are the #1 cause of permission bugs.
- The approval policy is a free-form dict (`additional_properties`, `metadata: dict[str, Any]`). Typo = silent disable.
- Persistence is in-memory only (`security.py:1586` in agent-framework). Cross-restart re-prompts users.
- The enforcement loop is in a wrapper the user must install. Forgotten wrapper = no protection (langgraph, crewai).
- The approval helper swallows exceptions. A bug in policy code is invisible.
- The deny is just an error string (`unsafe built-in function calls in expression: %v`, `opa/v1/ast/compile.go:7214`). Operators cannot aggregate or alert.
- The runtime has a separate path that doesn't go through the gate. `crewai`'s `ToolUsage._use` / `_ause` (`tools/tool_usage.py:469-707,222-467`) skips the hook; agent-framework's `_try_execute_function_calls` is the loop, but custom invocation flows can skip it.

## Anti-Patterns / Caution Signs

### Anti-pattern 1: Default-deny without operator override

**Source**: `crewai` ships no default policy. A new user with zero configuration has zero protection.

**Mitigation seen**: Documentation recipes (`docs/edge/en/learn/tool-hooks.mdx:181-204`) compensate, but recipes are not code that ships.

**Lesson**: Either ship a default policy (opt-in safety) or document the risk loudly. CrewAI does neither.

### Anti-pattern 2: Compile-time enforcement with no eval-time re-check

**Source**: `opa`'s `eval.builtinFunc` (`v1/topdown/eval.go:211-224`) never consults capabilities. A workflow that compiles with permissive capabilities and evaluates with restricted ones gets no restriction.

**Mitigation seen**: None.

**Lesson**: Permission gates belong at the point of action, not at the point of compilation, when the threat is "the runtime calls a dangerous function".

### Anti-pattern 3: Allowlist flag that fails open

**Source**: `opa`'s `allow_net` returns `nil` (allow) when `AllowNet == nil` (`v1/topdown/http.go:375-377`). Distinction between "omitted" (allow all) and "empty array" (allow none) is documented only in a struct comment.

**Mitigation seen**: None in OPA's `allow_net`.

**Lesson**: A permission flag should fail closed (deny if uncertain) unless the operator explicitly opts in to permissive mode. "Omitted = allow all" is a footgun.

### Anti-pattern 4: Naming a thing after what it doesn't do

**Source**: LangGraph's `tool_validator.py` (`libs/prebuilt/langgraph/prebuilt/tool_validator.py:43-114`) validates Pydantic argument schemas, not permissions. The next reader will assume it's the approval surface.

**Mitigation seen**: None.

**Lesson**: Name modules for what they do. `tool_validator.py` should be `argument_validator.py` or `schema_validator.py`.

### Anti-pattern 5: Two parallel approval surfaces with deprecation

**Source**: LangGraph deprecated `HumanInterruptConfig` (`libs/prebuilt/langgraph/prebuilt/interrupt.py:7-10`) and moved it to `langchain.agents.interrupt`. The shim remains, but no tests assert the new path works.

**Mitigation seen**: Deprecation redirect.

**Lesson**: When deprecating an approval API, make sure the replacement is documented and tested before removing the old one.

### Anti-pattern 6: Approval policy as user code with no sandbox

**Source**: OpenAI Agents SDK's callable `needs_approval` (`tool.py:426-433`) runs in the runner's event loop with full Python privileges. Exceptions are converted to "needs approval" but the policy itself is unconstrained.

**Mitigation seen**: Exception handling.

**Lesson**: User-supplied approval policies are code. Sandboxing, rate-limiting, and resource caps belong there.

### Anti-pattern 7: LLM-classified risk as the only signal

**Source**: OpenHands' `LLMSecurityAnalyzer` classifies risk per call (`frontend/src/types/v1/core/events/action-event.ts:43-48`). A `rm -rf /tmp/scratch` may be flagged LOW when it should be HIGH; the prediction is non-deterministic and depends on model version.

**Mitigation seen**: `AlwaysConfirm` fallback for unknown analyzer values.

**Lesson**: LLM-classified risk is a useful signal but not a substitute for declared risk on well-understood tools. Use both.

### Anti-pattern 8: Approval store without persistence

**Source**: CrewAI's hooks are in module-level lists (`hooks/tool_hooks.py:124-125`); they vanish with the process. Agent-framework's `_approved_violations` (`security.py:1586`) is in-memory only.

**Mitigation seen**: Agent-framework persists `ToolApprovalRule` in session state (`_harness/_tool_approval.py:250-277`), but policy-violation approvals do not.

**Lesson**: If users will be re-prompted after restart, that is a UX bug. Persist or document.

## Notable Absences

- **No source ships a typed risk taxonomy on the tool object.** The closest is openhands' `SecurityRisk` enum on the *action event*, which is LLM-predicted per call. A typed `RiskClass = Literal["read_only", "write", "delete", "network", "secret", "money"]` on the tool does not exist in any of the seven sources.
- **No source ships a global allow/deny list keyed on tool identity or risk class.** The closest is agent-framework's `allow_untrusted_tools` (`security.py:1562-1582`), which has different semantics (which tools may run when context is UNTRUSTED), not "which tools may run period".
- **No source ships an audit log of approval decisions.** Agent-framework has an audit log for *policy violations* (`security.py:1584, 1904-1913`), but not for *granted* approvals. Crewai has `ToolUsageStartedEvent`/`ToolUsageFinishedEvent` (`tools/tool_usage.py:273, 996`) but no denial event. OpenAI Agents SDK persists approvals in `RunState` but does not emit them as observability events.
- **No source ships a cross-process approval ledger.** All approvals are local to the run/session/process. Two independent runs cannot share an "approval for `send_email`" record unless the user wires it manually.
- **No source ships tool-name-based filtering as a first-class policy surface.** Pydantic AI's hooks have a `tools=['name1', 'name2']` filter (`capabilities/hooks.py:86-89`), but it is on the hook, not the policy. LangGraph's `interrupt_before=["tools"]` (`libs/langgraph/langgraph/pregel/_loop.py:660-664`) operates on node names, not tool names.
- **No source ships a default-deny mode.** Every framework's default posture is "approve unless flagged". A `default_deny=True` mode that requires explicit opt-in for safe tools is not present in any source.
- **No source ships approval TTL / replay protection.** Once approved (sticky), the approval is forever. There is no `expires_after` or `requires_re_approval_after` field in any source.
- **No source ships a server-side webhook approval surface.** All approval prompts are local (stdin, UI, HTTP call from the same app). CrewAI's `request_human_input` is stdin-only; openhands' `respond_to_confirmation` is the user clicking a button. No source has an "approve via Slack/email/external webhook" primitive.
- **No source ships a network/secret classifier on the tool body.** A function tool that reads secrets and posts them externally looks identical to one that reads a JSON file. The runtime cannot tell.
- **No source ships a "policy engine" decoupled from the runtime.** OPA's compile-time capabilities are the closest, but they are for builtins, not tool calls. Embedding OPA as a sidecar for agent tool calls is not in any source's architecture.

## Per-Source Notes

### agent-framework (8/10)

The strongest single-corpus implementation. `FunctionTool.approval_mode: Literal["always_require", "never_require"]` is the simplest primitive; the execution loop unconditionally checks it (`_tools.py:1691-1755`). The optional `ToolApprovalMiddleware` (`_harness/_tool_approval.py:345`) adds standing rules persisted in session state, hosted-tool server-label boundary, and heuristic auto-rules. The experimental `PolicyEnforcementFunctionMiddleware` (`security.py:1529`) layers an IFC model with typed `IntegrityLabel`/`ConfidentialityLabel` and per-tool `additional_properties` for `accepts_untrusted` / `max_allowed_confidentiality`. MCP has its own `MCPSpecificApproval` map (`_mcp.py:58-69`) and denies server-initiated sampling by default (`_mcp.py:1045-1073`). The richest test coverage in the corpus (823-line test module + 24 scenarios). Pulls down from 9-10 because IFC metadata is untyped dict members (typo = silent disable), `_approved_violations` is in-memory only, and `ToolApprovalMiddleware` is experimental.

### pydantic-ai (8/10)

The cleanest typed-envelope design. `ToolKind = Literal['function', 'output', 'external', 'unapproved']` (`tools.py:682`) routes calls into different execution paths, so approval is a property of the kind, not a flag checked separately. `ToolApproved.override_args` and `ToolDenied.message` give approvers structured envelopes. The `ApprovalRequiredToolset` wrapper (`toolsets/approval_required.py:14-32`) is the right shape for cross-cutting behavior — it composes with `FilteredToolset`, `SetMetadataToolset`, `PreparedToolset`. Durable-engine serialization (Temporal, Prefect) preserves `tool_call_approved` across activity boundaries. UI adapters (AG-UI, Vercel) ship typed approval/decline payloads. Pulls down from 9-10 because there is no risk taxonomy (only opaque metadata), `requires_approval` is opt-in per tool, and the capability chain is order-sensitive without explicit semantics.

### openhands (7/10)

The only source with a typed `SecurityRisk = UNKNOWN | LOW | MEDIUM | HIGH` enum on action events, though it is LLM-predicted rather than declared. `_select_confirmation_policy` (`app_conversation_service_base.py:641-652`) is a tidy three-class policy decision (NeverConfirm/ConfirmRisky/AlwaysConfirm) with seven parametrized tests. Settings persistence is solid (`Settings.update` round-trips through the V1 REST API). UI surfacing (RiskAlert for HIGH-risk actions, confirmation buttons with `v1SubmittedEventIds` dedup) is well thought out. The gVisor runtime (`runtime_class = "gvisor"` default) is belt-and-braces. Pulls down from 8 because (a) the SDK enforcement lives in an external Docker image and is not inspectable in this tree, (b) there is no per-tool matrix (only a global flag), (c) no approval audit log, (d) the RiskAlert component only renders for HIGH severity.

### openai-agents-sdk (6/10)

The richest policy-as-callable surface. `needs_approval: bool | Callable` accepts per-call functions with full context. `_ApprovalRecord` (`run_context.py:29-41`) carries sticky `bool` and per-call `list[str]` decisions coherently. `RunState` schema versioning (`run_state.py:131-149`) makes approval state durable across processes. Strict-mode `UserError` for invalid types (`util/_approvals.py:27-31`) catches typos. Realtime shares the same store as batched runs. The SDK ships with **opt-in** posture and documents the trade-off (`docs/human_in_the_loop.md:11-38`). Pulls down from 7 because there is no central risk taxonomy, the approval store is process-local unless serialized, and hosted shell bypasses approval entirely (`tool.py:1251-1256`).

### opa (5/10)

A decision engine, not an agent framework, so the dimension applies obliquely. `Capabilities.Builtins` (`v1/ast/capabilities.go:84-101`) is a typed, versioned, serializable permission surface — stronger than most agent frameworks on durability. Enforcement is compile-time (`v1/ast/compile.go:1997-2005`); runtime only re-checks `allow_net` (`v1/topdown/http.go:374-383`). The deprecation of `WithUnsafeBuiltins` (`v1/ast/compile.go:598-604`) in favor of capabilities is good hygiene. Pulls down because there is no runtime re-check of the builtin allowlist, `opa run` server mode has no `--capabilities` flag, `opa.runtime` leaks env vars without a gate, and `allow_net` fails open when omitted.

### crewai (5/10)

The strongest wrapper-as-policy demonstration. Four execution paths (`utilities/tool_utils.py:105-114,225-234`, `agents/crew_agent_executor.py:954-979`, `experimental/agent_executor.py:1953-1977`, `utilities/agent_utils.py:1508-1528`) all iterate the same global hook list; first `False` blocks. Filter-driven hook scoping (`@before_tool_call(tools=[...], agents=[...])`) is reusable. Documentation recipes (`docs/edge/en/learn/tool-hooks.mdx:160-204`) compensate for the missing default policy. Pulls down because the hook registry is module-global (leaks across sessions), `request_human_input` is stdin-only and blocking, the `SecurityConfig` fingerprint is identity-only and never enforced, and the native calling path (`ToolUsage._use`/`_ause`) skips the hooks entirely.

### langgraph (3/10)

The most minimal of the seven. `wrap_tool_call` / `awrap_tool_call` (`tool_node.py:755-778,1014-1067,1161-1222`) are clean interceptor points, and `interrupt(value)` is a flexible pause primitive. The Send API enables per-tool dispatch in v2 of `create_react_agent`. Pulls down to 3 because there is no declarative risk, no deny-by-default, no test asserts a framework-side denial path, the deprecated `HumanInterruptConfig` was moved to `langchain.agents.interrupt` without a clear replacement, and the server `Auth` covers resources but has no `tools` resource (`libs/sdk-py/langgraph_sdk/auth/__init__.py:322-326`). The "can the runtime stop a high-risk tool" question has no positive evidence beyond user code.

## Open Questions

- **Will any source evolve toward a typed risk enum?** Pydantic AI's `metadata: dict[str, Any]` and agent-framework's `additional_properties` for IFC are obvious places to add one. OpenHands' per-event `SecurityRisk` could be promoted to a per-tool declared field. None has shipped.
- **Will the openai-agents-sdk's `RunState` schema versioning remain fail-fast indefinitely?** Operators upgrading mid-pause must rebuild state (`run_state.py:128-130`). Migration tooling or auto-conversion between adjacent versions would smooth this.
- **Will agent-framework's FIDES layer graduate from `@experimental`?** The IFC primitives (`IntegrityLabel`, `ConfidentialityLabel`, `PolicyEnforcementFunctionMiddleware`) are wrapped in `@experimental(feature_id=ExperimentalFeature.FIDES)`. The untyped `additional_properties` is the main obstacle.
- **Will pydantic-ai's `ApprovalRequiredToolset` accept a default-deny predicate?** Currently the default is `lambda ctx, td, args: True` (`toolsets/approval_required.py:22-24`); a user wanting defense-in-depth must wrap the entire agent. A `default_deny=True` flag would be cleaner.
- **Will openhands ship a per-tool matrix?** `_select_confirmation_policy` is a single global flag. The SDK's `ConfirmRisky` could be parameterized by tool name, but the tree does not wire it.
- **Will any source ship a server-side webhook approval surface?** All current sources are local-only (stdin, UI, HTTP call from same app). A `webhook_approval_endpoint` config would let a Slack channel approve tool calls.
- **How will OPA's `allow_net` tri-state resolve?** The omitted-vs-empty distinction is currently in a struct comment (`v1/ast/capabilities.go:96-97`); a `DenyByDefault` flag would close the footgun.
- **What is the durability story for `ToolApprovalState.rules` across `AgentSession.from_dict`?** State goes through `to_dict()/from_dict()` and rules are rehydrated (`agent-framework/_harness/_tool_approval.py:120-156, 187-217`), but cross-version compatibility is not pinned in code.
- **Will any source ship a default-deny mode at the agent level?** All seven default to opt-in. A `default_deny=True` agent-level switch (where every tool must be explicitly marked safe) would invert the posture for high-security deployments.
- **Will any framework ship an "approval ledger" — a cross-process, cross-run record of who approved what when?** Currently approvals are local to a run/session; sharing requires the user to serialize and reload.
