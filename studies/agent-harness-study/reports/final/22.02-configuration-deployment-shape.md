## Executive Summary

Ten sources spanning four product shapes — embedded Python SDKs (pydantic-ai, openai-agents-sdk, crewai), a dual-language SDK family (agent-framework), deployable servers/platforms (langfuse, langgraph, letta, temporal, opa), and a frontend-plus-launcher product (openhands) — were studied for configuration layering, environment management, deployment modes, feature flags, and config validation.

Three findings dominate. First, **environment variables are the universal runtime interface**: every source resolves at least some behavior through env vars, and even file-first designs deliberately bridge into them (letta flattens YAML into `LETTA_*` vars before pydantic-settings reads them, `letta/config_file.py:177-232`; temporal compiles an env-var-driven template into the binary itself, `common/config/loader.go:20-21`). Second, **no source ships a first-class dev/staging/prod environment abstraction**; the closest approximations are temporal's legacy `base.yaml → <env>.yaml → <env>_<zone>.yaml` overlay hierarchy (`common/config/loader.go:172-176`) and detection-based adaptation (agent-framework's `FOUNDRY_HOSTING_ENVIRONMENT`, `python/packages/core/agent_framework/_telemetry.py:86-121`; crewai's process-context marker tables, `lib/crewai-core/src/crewai_core/runtime_env.py:104-159`). Third, **feature flags are the weakest sub-dimension everywhere except the two operated platforms**: only temporal (dynamic config with monotonic percentage rollouts and scheduled changes) and langfuse (DB-backed per-user flags plus env-var migration gates) have real systems; everyone else has static toggles, lifecycle gating, or nothing.

The guiding question — *can the same binary run in dev, staging, and prod with config changes only?* — is answered yes by all ten sources structurally, with three concrete exceptions where rebuilds are required: langfuse's `NEXT_PUBLIC_*` values baked into the web image (`web/Dockerfile:71-114`), langgraph's config dicts serialized as Dockerfile `ENV` lines for self-hosted images (`libs/cli/langgraph_cli/config.py:1132-1162`), and openhands' compile-time `VITE_BASE_PATH`/telemetry key (`docker/Dockerfile:43-47`).

Scores range from 6 (crewai) to 9 (temporal) with a median of 8, but the spread measures fit-to-product-shape as much as quality: libraries cannot and should not carry server-grade config machinery, and the lowest score reflects internal inconsistency rather than missing capability.

## Core Thesis

**Configuration architecture is determined primarily by what gets deployed, not by engineering sophistication.** Each source implements essentially the same discipline — one explicit precedence contract, eager validation, an environment-agnostic artifact — at whichever boundary its product actually owns:

- **Libraries own the code boundary.** pydantic-ai, openai-agents-sdk, and crewai push all environment-specific input through constructor arguments, env vars, and kill switches; "deployment" is composition of injected backends (providers, sandboxes, sessions). Validation happens at object construction because that is the last moment the library controls.
- **Deployable services own the boot boundary.** langfuse, letta, opa, and temporal parse and validate everything at process start so bad config crashes immediately rather than degrading per-request; deployment modes are expressed as artifact topology (one image vs many processes) selected purely by config.
- **Operated-at-scale services add a runtime boundary.** temporal's dynamic config and langfuse's migration gates exist because those products need to change behavior without redeploying fleets; nothing in the library-tier sources needs this, and none of them builds it.
- **Frontend products own two boundaries because bundlers bake env.** openhands compensates for Vite's compile-time `import.meta.env` with a runtime injection channel (`window.__AGENT_CANVAS_*__` globals served into HTML, `scripts/static-server.mjs:325-374`) — the same problem langfuse acknowledges and partially mitigates differently (serving client settings through tRPC, `web/src/env.mjs:514-521`).

The practical corollary: comparing "config maturity" across these sources is only meaningful within a cluster. A 7-rated library is not inferior to an 8-rated server; each is near the ceiling of what its shape permits, and the deltas within clusters reveal real design choices.

## Approach Models

Four approach models emerge, keyed to deployment shape rather than language.

### Model A — Boundary-coercion library config

**Who:** openai-agents-sdk, pydantic-ai, crewai (runtime half), agent-framework (Python half).

Configuration is resolved at the moment application code meets library code. openai-agents-sdk normalizes every public boundary through shared coercion functions that accept typed instances or plain dicts and raise on unknown fields (`src/agents/_config_coercion.py:45-97`), with precedence implemented once as `_resolve_str(explicit, default, os.getenv(...))` (`src/agents/models/openai_agent_registration.py:114-121`). pydantic-ai repeats the same contract verbatim across ~30 provider constructors (`pydantic_ai_slim/pydantic_ai/providers/groq.py:138-139`) and layers model profiles through a documented four-step chain (`pydantic_ai_slim/pydantic_ai/models/__init__.py:863-903`). agent-framework centralizes it further: a dependency-free `load_settings()` implements overrides > `.env` > env vars > defaults over TypedDict schemas, reused by every provider package under a distinct prefix (`python/packages/core/agent_framework/_settings.py:199-235`, prefix survey at `python/packages/openai/agent_framework_openai/_shared.py:218-260`). crewai shows the un-centralized version of this model: the same param > env > file > default chain is re-implied in at least four subsystems with no shared helper (`lib/crewai-core/src/crewai_core/plus_api.py:174-178`; `lib/crewai/src/crewai/events/listeners/tracing/utils.py:108-137`), which is precisely why it scores lowest.

### Model B — Schema-parsed env boot

**Who:** langfuse, letta (terminal stage), agent-framework Python.

All configuration arrives as environment variables and is parsed against a schema exactly once, at process start. Langfuse partitions this by runtime: a ~156-key shared Zod schema, a web-only t3-env schema with server/client sections, a worker schema, and a minimal EE schema, each failing fast at module load (`packages/shared/src/env.ts:32,584-587`; `web/src/env.mjs:40`; `worker/src/env.ts:5`; `ee/src/env.ts:4-9`). Defaults live inside the schemas, making them the single source of truth for both shape and defaults. Letta reaches the same endpoint via a different route — YAML is deep-merged across user/project/explicit locations, flattened into prefixed env vars, then read by eight pydantic-settings singletons (`letta/config_file.py:59-100,177-232`; `letta/settings.py:640-648`) — gaining file-based layering but inheriting import-time global mutation as a cost.

### Model C — Declarative file compiled to deployment targets

**Who:** langgraph, temporal (static half), openhands, opa (file+override half).

A declarative file is validated once and lowered into multiple artifacts. Langgraph is the purest case: `langgraph.json` is canonicalized by `validate_config` and compiled to a Dockerfile, a docker-compose document, and a platform-API payload (`libs/cli/langgraph_cli/config.py:367-389,1263-1551,1651-1780`; `libs/cli/langgraph_cli/host_backend.py:73-92`). Temporal loads typed YAML through functional options with three mutually exclusive strategies — embedded template, single file, legacy env-overlay hierarchy — guarded by a startup flag-conflict check (`common/config/loader.go:129-141,145-148,172-176`; `cmd/server/main.go:144-153`). Openhands makes one JSON file the contract for four independent consumers (JS launchers, app imports, a Docker build stage that pre-compiles it to shell-sourceable `defaults.env`, and CI extraction), with tests that execute the real extracted blocks to prevent drift (`config/defaults.json:1-2`; `docker/Dockerfile:49-70`; `.github/workflows/docker.yml:86-94`; `__tests__/scripts/docker-vscode-route-sync.test.ts:53-92`). OPA layers interpolation, deep-merged CLI overrides, and viper env-mapping on top of its file, then hands the result to an embedded Rego validation policy that injects defaults and warns on unknown keys (`internal/config/config.go:80-184`; `v1/config/validate.rego:25-60`).

### Model D — Runtime-mutable dynamic layer

**Who:** temporal (dynamic config), opa (discovery bundles), langfuse (DB flags + migration gates).

Behavioral knobs are separated from structural topology and made mutable without restart. Temporal's dynamic config is the most complete: statically registered typed settings with defaults and descriptions (~3,700 lines of catalogued keys in `common/dynamicconfig/constants.go`), constraint-scoped overrides by namespace/task queue/task type/shard, file polling with change subscriptions, monotonic stable-hash percentage rollouts, and scheduled value flips (`common/dynamicconfig/collection.go:30-53`; `rollout.go:17-27`; `gradual_change.go:15-24`; `file_based_client.go:133-141`). OPA achieves dynamism differently: a discovery plugin downloads bundles and rewrites the running config while protecting boot-critical sections from change (`v1/plugins/discovery/discovery.go:466-545,505-526`). Langfuse splits the difference by audience — per-user flags live in Postgres and evaluate per request (`web/src/features/feature-flags/utils.ts:15-53`), while operational migration gates are env vars requiring restart (`worker/src/env.ts:560-599`).

## Pattern Catalog

### P1. The uniform precedence idiom

**Problem:** Layered config becomes unpredictable when each subsystem invents its own resolution order.
**Demonstrated by:** openai-agents-sdk (`_resolve_str`, tested in `tests/models/test_agent_registration.py:23-62`), pydantic-ai (`arg or os.getenv('X') or default` repeated greppably across providers), agent-framework (one loader enforcing the chain for every package), crewai (negative example — same chain, four hand-rolled copies).
**Why it works:** One helper means precedence is testable once, documented once, and identical everywhere; agent-framework backs it with ~40 unit tests covering ordering, coercion, and mutual exclusion (`python/packages/core/tests/core/test_settings.py:40-379`).
**Copy when:** Any codebase with more than a handful of tunables.
**Overkill when:** A truly single-knob tool.
**Evidence:** `src/agents/models/openai_agent_registration.py:114-121`; `pydantic_ai_slim/pydantic_ai/providers/sambanova.py:102,110`; `python/packages/core/agent_framework/_settings.py:253-292`.

### P2. Schema-as-single-source-of-truth (defaults live in the validator)

**Problem:** Defaults duplicated between loaders, docs, and examples drift silently.
**Demonstrated by:** langfuse (Zod `z.coerce.*.default(...)` embeds defaults in the schema, `packages/shared/src/env.ts:32`); langgraph (TypedDict docstrings double as reference documentation and the validator fills defaults during canonicalization, `libs/cli/langgraph_cli/schemas.py:615-773`, `libs/cli/langgraph_cli/config.py:367-389`); agent-framework (TypedDict settings classes).
**Why it works:** Editing a default requires touching exactly one place; documentation cannot lag implementation because they are the same artifact.
**Copy when:** Building any server or CLI with a config surface.
**Risky when:** The schema is duplicated per runtime — see Anti-Pattern A2.
**Evidence:** `web/src/env.mjs:40`; `packages/shared/src/env.ts:584-587`.

### P3. Compile-one-file-to-many-targets

**Problem:** Ports, versions, and paths duplicated across Makefiles, Dockerfiles, workflows, and app code drift apart.
**Demonstrated by:** langgraph (`langgraph.json` → Dockerfile/compose/platform payload), openhands (`defaults.json` → scripts/app/Docker `config-gen` stage/CI), temporal (embedded template rendered from env for the container path).
**Why it works:** Single edit point plus generated artifacts; openhands additionally extracts the riskiest block into a test that executes production code (`__tests__/scripts/docker-vscode-route-sync.test.ts:53-92`).
**Copy when:** One logical setting must appear in more than two artifacts.
**Overkill when:** Config consumers are few and co-located.
**Evidence:** `libs/cli/langgraph_cli/config.py:1651-1780`; `docker/Dockerfile:51-70`; `common/config/config_template_embedded.yaml:1`.

### P4. Boot-sovereign configuration under remote reconfiguration

**Problem:** Remote/dynamic config systems can brick agents if a bad update removes the ability to reach the control plane.
**Demonstrated by:** opa (discovered config may not change the discovery service or keys present in boot config; bootstrap labels and persistence dir are merge-only, `v1/plugins/discovery/discovery.go:505-526`; `v1/plugins/plugins.go:1004-1015`); temporal (update failures are logged throttled-not-fatal and the last-good snapshot keeps serving via atomic snapshot, `common/dynamicconfig/collection.go:202-207`; `file_based_client.go:38`); langfuse (persisted last-good discovery analog: opt-out flags gate auto-migrations in the entrypoint, `web/entrypoint.sh:89-125`).
**Why it works:** It preserves the invariant that a running system can always be repaired from its boot state.
**Copy when:** Introducing any remote-config or bundle-download mechanism.
**Skip when:** Config is fully local.
**Evidence:** `v1/plugins/discovery/discovery.go:491-526`.

### P5. Self-describing deployments

**Problem:** Support and debugging require knowing which mode/topology a running instance is.
**Demonstrated by:** openhands (`/server_info.runtime_services.mode` reports "docker"/"dev:automation"/etc., assembled by a module shared between dev launchers and Docker entrypoint, `scripts/runtime-services-info.mjs:60-149`); agent-framework (hosted-context User-Agent prefix from `FOUNDRY_HOSTING_ENVIRONMENT`, `python/packages/core/agent_framework/_telemetry.py:86-121`); letta (`settings.environment` wired into Sentry/Datadog tags, `letta/server/rest_api/app.py:300-323`).
**Why it works:** Topology truth travels with the instance instead of being reconstructed from logs.
**Copy when:** More than one supported deployment mode exists.
**Evidence:** `src/api/agent-server-adapter.ts:202-206`.

### P6. Docs-as-test-contract

**Problem:** Configuration documentation rots relative to behavior.
**Demonstrated by:** pydantic-ai (the "Supported by:" bullets in `ModelSettings` docstrings are parsed and verified against captured wire payloads in both directions, `tests/models/test_model_settings_support.py:1-24`); openhands (tests execute the actual Docker entrypoint config block, `__tests__/scripts/docker-vscode-route-sync.test.ts:117+`); langgraph (compose topologies pinned by tests, `libs/cli/tests/unit_tests/test_docker.py:371-440`); agent-framework (~40 precedence tests).
**Why it works:** Documentation becomes executable; drift fails CI.
**Copy when:** Config semantics are subtle enough that prose matters.
**Evidence:** `tests/models/test_model_settings_support.py:1-24`.

### P7. Remediation-oriented validation errors

**Problem:** Config errors that name the violation but not the fix send users to source-diving.
**Demonstrated by:** langgraph ("did you mean" unknown-key suggestions plus copy-pastable fix snippets like `'  "source": {"kind": "uv", "root": ".."}'`, `libs/cli/langgraph_cli/config.py:422-428,593-605`); pydantic-ai (close-match model-id suggestions and a keyless-model hint appended to every credential error, `pydantic_ai_slim/pydantic_ai/models/__init__.py:1548-1561`; `pydantic_ai_slim/pydantic_ai/providers/__init__.py:26-39`); agent-framework (`SettingNotFoundError` names the exact env var to set, `python/packages/core/agent_framework/_settings.py:296-305`); opa (unknown-option warnings at any depth via pattern specs, `v1/config/validate.rego:46-60`).
**Why it works:** Error text becomes the primary config documentation at failure time.
**Copy when:** Always, for anything operator-facing.
**Contrast:** letta swallows YAML errors entirely (`letta/config_file.py:92-98`) and crewai ignores unknown `CREWAI_*` typos — the same mechanisms absent here are the ones causing their documented failure modes.
**Evidence:** `libs/cli/langgraph_cli/config.py:422-428`.

### P8. Layered kill switches matched to blast radius

**Problem:** Different failures need different rollback speeds.
**Demonstrated by:** temporal (monotonic `RolloutAccepts` hash gate — accepted at P implies accepted at ≥P — plus time-windowed `GradualChange`, `common/dynamicconfig/rollout.go:8-27`; `gradual_change.go:15-24`); langfuse (query-rewrite kill switch, shadow-query sample rate, v4 write-mode triad refusing data-losing combos at boot, org-cohort cutoffs by creation date, `web/src/env.mjs:536-546`; `worker/src/env.ts:694-721,568-582`); pydantic-ai (process-global spend kill switch `ALLOW_MODEL_REQUESTS`, closed by default in the test suite, `pydantic_ai_slim/pydantic_ai/models/__init__.py:1388-1439`; `tests/conftest.py:91`); telemetry kill switches in agent-framework, crewai, langgraph, opa.
**Why it works:** Cohort-cutoff and monotonic-percentage primitives make rollouts forward-safe, which ad-hoc booleans cannot guarantee.
**Copy when:** Operating multi-tenant or fleet deployments.
**Overkill when:** Single-instance tools.
**Evidence:** `common/dynamicconfig/rollout.go:17-27`.

### P9. Fail-closed development/administrative surfaces

**Problem:** Dev conveniences become production liabilities when bound publicly.
**Demonstrated by:** agent-framework (DevUI refuses token-less non-loopback binds in both languages, `python/packages/devui/agent_framework_devui/_server.py:145-169`; `dotnet/src/Microsoft.Agents.AI.DevUI/DevUIOptions.cs:17-58`); openhands (`--public` mode exits unless `LOCAL_BACKEND_API_KEY` is set, `scripts/dev-with-automation.mjs:412-420`; auto-generated secrets persisted `chmod 600`, `docker/entrypoint.sh:179-209`); pydantic-ai (DNS-rebinding host allowlist returning 421 for unlisted Hosts, `pydantic_ai_slim/pydantic_ai/ui/_web/app.py:216-236`); letta (`mcp_disable_stdio=True` default documented as multi-tenant guard, `letta/settings.py:45-54`); temporal (loud warning unless `--allow-no-auth`, `cmd/server/main.go:203-209`); opa (public-interface bind warning, `cmd/run.go:389-391`).
**Why it works:** Secure defaults survive operator error; escape hatches exist but are affirmative.
**Copy when:** Anything serving UI or admin APIs beyond loopback.
**Evidence:** `python/packages/devui/agent_framework_devui/_server.py:157-158`.

### P10. Secret hygiene at defined boundaries

**Problem:** Resolved config leaks credentials through logs, diagnostics, and child processes.
**Demonstrated by:** temporal (`render-config` pipes output through a masker so diagnostics never need to remember to redact, `common/config/config.go:720-725`; DB passwords resolvable via external command, `common/config/persistence.go:285-300`); opa (`ActiveConfig()` strips credential fields before `/v1/config` serves it, `v1/config/config.go:299-326`); agent-framework (`SecretString` repr masking, `python/packages/core/agent_framework/_settings.py:52-82`); openai-agents-sdk (log/trace redaction secure-by-default, `src/agents/_debug.py:20-28`; `run_config.py:53-56`); crewai (atomic 0o600 writes, hidden keys, `lib/crewai-core/src/crewai_core/settings.py:50-73,140-144`); openhands (auto-generated persisted keys replace known defaults, `docker/entrypoint.sh:175-178`). Counter-example: openai-agents-sdk's Codex sidecar inherits the full parent environment unless explicitly overridden (`src/agents/extensions/experimental/codex/exec.py:214-220`).
**Why it works:** Redaction applied mechanically at one boundary is reliable; redaction-by-discipline is not.
**Evidence:** `common/config/config.go:720-725`.

## Key Differences

Clustered by what actually drives divergence:

**Library vs service determines where validation lives, and both are right.** Libraries validate at construction (openai-agents-sdk rejects conflicting client/key args eagerly with a regression test documenting that a prior bare-`assert` version silently passed under `python -O`, `src/agents/models/openai_provider.py:90-98`; `tests/test_config.py:131-136`), while services validate at boot (langfuse parses at module load, `packages/shared/src/env.ts:584-587`) or even at container start (letta aborts boot if Alembic fails, `letta/server_startup.sh` via `letta/server/startup.sh:54-60`). Neither can adopt the other's timing: a library has no boot, a server has no constructor.

**Detection vs declaration of environments.** agent-framework and crewai *detect* context (hosted-env variable; ordered CI/serverless/container/notebook marker tables) and adapt behavior automatically (`python/packages/core/agent_framework/_telemetry.py:86-121`; `lib/crewai-core/src/crewai_core/runtime_env.py:104-159`); temporal *declares* environment through `--env` selecting a file overlay (`cmd/server/main.go:55-61`). Detection minimizes operator burden but makes behavior sensitive to ambient variables — a wrongly set/unset `FOUNDRY_HOSTING_ENVIRONMENT` flips security posture (`dotnet/src/Microsoft.Agents.AI.Foundry.Hosting/ServiceCollectionExtensions.cs:382-392`). Declaration costs operators a convention but is auditable. Most sources do neither and leave environments entirely implicit.

**Build-time baking is a frontend/bundler constraint, not a design failure.** openhands and langfuse both face Vite/Next compile-time env. Openhands built a second runtime channel (HTML-injected globals, `scripts/static-server.mjs:282-324`); langfuse accepts baking for `NEXT_PUBLIC_*` and routes individual client-visible settings through tRPC to preserve artifact parity case-by-case (`web/src/env.mjs:514-521`). Server-only sources (temporal, letta, opa) never face this tradeoff, which is a constraint difference, not a quality difference.

**Feature-flag depth tracks fleet size.** Temporal (thousands of catalogued keys, constraint-scoped, hot-reloaded) and langfuse (per-user DB flags, cohort rollouts) operate multi-tenant fleets where rollout control is existential. Everything else — SDKs and self-hosted servers — rationally settles for restart-time toggles; letta explicitly substitutes runtime *readiness machinery* for dynamic flags, treating degradation as a health-probe concern (`letta/settings.py:600-637`; `letta/monitoring/load_gate.py:14-40`).

**Compatibility burden explains apparent sloppiness in mature sources.** crewai's alias chains and three hand-rolled `.env` parsers, opa's two overlapping env mechanisms, letta's still-live legacy configparser used by Alembic (`alembic/env.py:7,26`), and openhands' `OH_*`/bare/`CONFIG_*` alias families are scar tissue from evolution under published surfaces. Greenfield-looking designs (pydantic-ai's uniform providers, langfuse's schema partitioning) simply haven't accumulated it yet.

**Config-file philosophy splits along who edits config.** Operator-edited systems grow files with merging and profiles (temporal, opa, letta). Developer-edited systems keep a single project file (langgraph's `langgraph.json`) or no file at all (the SDKs), because the editor is the same person writing the code and IDE validation substitutes for layering — pydantic-ai even emits JSON Schemas so editors apply the same `extra='forbid'` rules the runtime does (`pydantic_ai_slim/pydantic_ai/agent/spec.py:27-30,197`).

## Tradeoffs

**Layered file hierarchies vs flat single files.** Temporal's `base.yaml → <env>.yaml → <env>_<zone>.yaml` overlays give true per-environment inheritance (`common/config/loader.go:172-176`), while langgraph's single flat file forces users to duplicate whole configs per environment or manage divergence through env/secrets. Benefit of layering: minimal diffs per environment. Cost: two of temporal's loading models coexist (the legacy hierarchy is deprecated yet still the path taken when `--env` is passed, `cmd/server/main.go:170-175` vs `common/config/loader.go:164-166`), duplicating the mental model. Flat wins for developer-facing tools; layering wins for ops-facing servers.

**Strict unknown-field rejection vs deliberate leniency.** openai-agents-sdk raises `TypeError` listing unknown fields at every boundary (typo-proof, but adding a field breaks older callers passing newer dicts — mitigated by pinning and a pydantic `extra="allow"` escape hatch, `src/agents/_config_coercion.py:84-97`). pydantic-ai intentionally ignores unsupported generic `ModelSettings` keys to stay portable across providers, backstopped by wire-payload doc tests instead (`pydantic_ai_slim/pydantic_ai/models/AGENTS.md` rules 26/912). OPA warns but lands typos functionally ignored in `Extra`. Langfuse hard-fails. Best-fit depends on whether config crosses a version boundary (be strict) or a provider matrix (be lenient + test docs).

**Static restart-time flags vs runtime-mutable flags.** Static booleans (letta's ~30 typed settings, langgraph's nine `disable_*` routes) are predictable and need no infrastructure, but make gradual rollout impossible in-process (`letta/settings.py:409-412`). Temporal's dynamic layer enables fleet-wide rollouts but adds polling latency (5s floor, `common/dynamicconfig/file_based_client.go:23`), staleness risk on poll failure, and a second config model to learn. Langfuse's split — dynamic for user-facing features, static for infra migrations — shows the hybrid is viable when audiences differ.

**Import-time resolution vs lazy resolution.** Letta mutates `os.environ` at import so every consumer (including third-party libs like ddtrace) shares one contract (`letta/settings.py:15`) — uniform but provenance-destroying and order-sensitive. Langgraph binds recursion limits at import (`libs/langgraph/langgraph/_internal/_config.py:32-35`) and openai-agents-sdk captures debug flags at import (`src/agents/_debug.py:20-25`) — deterministic but restart-bound. openai-agents-sdk's tracing disable uses cache-on-first-read with manual override always winning (`src/agents/tracing/provider.py:340-352`), and agent-framework's .NET caches the disabled state statically while Python re-reads per call (`FeatureUsage.cs:28` vs `python/packages/core/agent_framework/_telemetry.py:132-134`) — an intra-project inconsistency worth avoiding.

**Embedded dependencies vs external dependencies in one artifact.** Letta's all-in-one image (Postgres/Redis/OTEL collector inside, auto-started only when external URIs are absent, `Dockerfile:42-72`; `letta/server/startup.sh:24-51`) makes zero-config first run trivial and literal same-binary parity true, at the cost of a heavyweight image and shell-based process supervision. Langfuse's compose stack keeps concerns separate and independently scalable (`docker-compose.yml:6-210`) at the cost of first-run complexity. Temporal supports both shapes with one binary and documented co-hosting init order (`temporal/server_impl.go:40-48`).

**Fail-open libraries vs fail-closed deployers.** CrewAI degrades quietly at runtime (corrupt settings file → defaults, `lib/crewai-core/src/crewai_core/settings.py:212-217`; telemetry never crashes the app, `lib/crewai-core/src/crewai_core/telemetry.py:66-74`) but fails loudly at deploy time (blocking validator, `lib/cli/src/crewai_cli/deploy/main.py:52-61`). This is a coherent pairing — embedded runtimes shouldn't crash hosts; deploy gates should catch what runtime forgiveness hides — and other sources converge on halves of it without stating it: agent-framework's DevUI and openhands' launchers fail closed on security-relevant misconfig, while observability setup everywhere logs-and-continues.

## Decision Guide

- **Building an SDK/library?** Adopt the uniform precedence idiom (P1) and construction-time fail-fast coercion (openai-agents-sdk's shared coercion module is the reference implementation). Do not build config-file parsing, environment profiles, or flag services — five of ten sources prove the library tier works without them. Add exactly one process-global safety kill switch (spend, tracing) with a context-manager override, following pydantic-ai's `ALLOW_MODEL_REQUESTS`.
- **Building a deployable server?** Parse all env/file config against a schema exactly once at boot and crash on failure (langfuse model). Put defaults in the schema (P2). If you support multiple topologies, select them by config, not artifacts (temporal's per-service flags, letta's presence-derived internal deps).
- **Building a CLI that produces deployments?** Use one declarative source compiled to targets (P3), validate with remediation-oriented errors (P7), and gate deploys on preflight checks (crewai's nine-category validator is the deepest example, including cross-checking API keys referenced in code against `.env`, `lib/cli/src/crewai_cli/deploy/validate.py:854-912`).
- **Need feature flags?** Before building anything, ask whether you operate a fleet. If yes: typed registry with defaults and descriptions (temporal), constraint scoping if multi-tenant, monotonic percentage gates if rolling out data-affecting changes. If no: typed boolean settings plus a documented restart requirement (letta) is sufficient and honest. Avoid hardcoded stub interfaces left in place (openhands) — delete them or wire them.
- **Choosing between detection and declaration for environments?** Declare (named env selecting config) when operators manage environments; detect (marker variables) only for orthogonal facts like CI vs interactive, where crewai's closed-vocabulary tables also prevent PII leaking into telemetry (`lib/crewai-core/src/crewai_core/runtime_env.py:176-189`).
- **Frontend with baked env?** Assume you need a runtime channel from day one; openhands' HTML injection generalizes, and langfuse's serve-through-API pattern covers per-user values.
- **Introducing remote config?** Copy P4 first: protect boot config, keep last-good snapshots, throttle-not-fail on update errors. Then add validation for the remote format equal to local (temporal's `validate-dynamic-config` CLI exists precisely for this, `cmd/server/main.go:82-107`).

## Practical Tips

1. **Write the precedence chain down next to the loader and test it.** agent-framework documents four layers in the loader docstring and enforces ordering in ~40 tests; openai-agents-sdk regression-tests arg > setter > env. An undocumented chain *will* fork (crewai did).
2. **One boolean parser for the whole codebase.** CrewAI's three truthiness conventions mean `"no"` disables headless mode but leaves telemetry on (`lib/cli/src/crewai_cli/utils.py:75` vs `lib/crewai-core/src/crewai_core/telemetry.py:232-237`).
3. **Normalize empty strings to unset before parsing env** — Compose `${VAR:-}` placeholders otherwise clobber schema defaults (langfuse's `removeEmptyEnvVariables`, `packages/shared/src/utils/environment.ts:3-10`).
4. **Make diagnostics mask secrets by construction**, not by caller discipline (temporal's masked `render-config`, opa's redacted `ActiveConfig`, agent-framework's `SecretString`).
5. **Prefer error messages containing fixes**: did-you-mean key suggestions, copy-pastable snippets, and the exact env var name to set (langgraph, pydantic-ai, agent-framework).
6. **Test your docs about config** — derive docstring claims from wire payloads (pydantic-ai) or execute extracted production config blocks (openhands).
7. **Give every deployment mode a machine-readable identity** exposed at runtime (openhands' `runtime_services.mode`), so support never reconstructs topology from port scanning.
8. **When bridging files into env vars, document that provenance is lost** and warn loudly on parse failure — letta's silent swallow is the cautionary tale (`letta/config_file.py:92-98`).
9. **Gate paid/side-effectful actions behind a default-open-in-lib, default-closed-in-tests switch** (pydantic-ai) to make test suites accidentally-safe against real API spend.
10. **Keep the core library free of deployment config** (langgraph keeps `libs/langgraph` to two env constants while all ops machinery lives in the CLI, `libs/langgraph/langgraph/_internal/_config.py:32-35`); it preserves embedders' freedom and keeps framework concerns separate from ops concerns.

## Anti-Patterns / Caution Signs

**A1. Silent exception swallowing on the config load path.** Letta wraps YAML reads in `except Exception: pass` — a typo'd `conf.yaml` yields stock defaults with zero signal (`letta/config_file.py:92-98`); crewai's `Settings.dump()` passes on every write failure, making persistence loss unobservable (`lib/crewai-core/src/crewai_core/settings.py:249-250`). Caution sign: any `pass` in a config codepath.

**A2. Duplicated schema definitions synced by comments.** Langfuse defines `LANGFUSE_MIGRATION_V4_WRITE_MODE` three times with "keep this value in sync" comments (`packages/shared/src/env.ts:322-330`; `worker/src/env.ts:555-564`; `web/src/env.mjs:504-512`); the shared S3 fragment shows the fix exists but isn't applied generally (`worker/src/env.ts:68-73`). Caution sign: the words "keep in sync" in config code.

**A3. Case-sensitive or free-form environment-name gating.** Letta compares `settings.environment == "PRODUCTION"` in one file and `== "prod"` in others, so `LETTA_ENVIRONMENT=Production` silently skips both gates (`letta/agent.py:1302-1305` vs `letta/services/tool_manager.py:649-652`); tests encode the ambiguity by parametrizing each spelling separately (`tests/managers/conftest.py:779-786`; `tests/test_managers.py:1022-1027`). Caution sign: string comparisons against environment names anywhere outside a normalization helper.

**A4. Import-time mutation of ambient state.** Letta writes YAML into `os.environ` at import (`letta/settings.py:15`); crewai's library calls `load_dotenv()` at import, which once caused litellm to overwrite unrelated vars — now defended by lazy-loading with the incident recorded in comments (`lib/crewai/src/crewai/llm.py:74-78`). Caution sign: side effects between `import` and first use.

**A5. Flag/interface drift between schema and consumers.** Langgraph's `disable_persistence` is passed by `langgraph dev` but missing from `_KNOWN_CONFIG_KEYS`, so the project's own validator warns about it (`libs/cli/langgraph_cli/cli.py:859` vs `config.py:564-590`); openai-agents-sdk keeps a legacy transport shim synced "on read" with a comment admitting tests mutate it (`src/agents/models/_openai_shared.py:14-15,60-68`); openhands' typed flag interface returns hardcoded literals (`option-service.api.ts:33-37`). Caution sign: two representations of one setting bridged by reconciliation code.

**A6. Undocumented precedence between overlapping mechanisms.** OPA's `${VAR}` interpolation and `OPA_<CMD>_<FLAG>` mapping compose implicitly, and undefined variables stay literal rather than failing (`internal/config/config.go:147-153`); agent-framework's Python and .NET stacks define provider env names independently. Caution sign: two ways to set the same value with no written rule for which wins.

**A7. Partial-credential fallbacks to insecure defaults.** Letta's partial Postgres env specs fall through to `letta:letta@localhost` instead of erroring (`letta/settings.py:471-478`); pydantic-ai substitutes placeholder API keys for keyless local endpoints, deferring discovery to first request (`pydantic_ai_slim/pydantic_ai/providers/openai.py:106-108`). Caution sign: fallback chains that terminate in a working-looking default rather than a loud miss.

**A8. Alias families accreting without deprecation.** Openhands resolves `OH_VSCODE_PORT` → `VSCODE_PORT` → `CONFIG_VSCODE_PORT` → literal (`docker/entrypoint.sh:94-95`) and its report recommends consolidation before each addition multiplies collapse logic. Caution sign: a resolution function whose length grows with each release.

## Notable Absences

Across all ten sources, the following were searched for and not found — their absence is a finding about the ecosystem, not an oversight of any single project:

- **No named dev/staging/prod environment abstraction anywhere.** Only fragments exist: temporal's env-file overlay naming, langfuse's cloud-region enum that includes `STAGING`/`DEV` as discriminators (`worker/src/env.ts:21-23`), opa's `labels.environment` documentation convention and tracing `deployment_environment` key (`docs/docs/configuration.md:40-44`; `v1/config/validate.rego:150-153`), letta's staging-as-tag-alias in OTEL normalization (`letta/otel/resource.py:27-28`). Environment promotion is left to operators in every case.
- **No third-party feature-flag service integration** (LaunchDarkly/Statsig/Unleash) in any source; the only dynamic systems are homegrown (temporal dynamic config, langfuse DB flags).
- **No centralized secret management in-repo** (Vault/KMS/sealed secrets). Secrets arrive via `${VAR}` interpolation (opa, pydantic-ai MCP), platform injection (langfuse Helm reference, `README.md:120-121`), command indirection (temporal password-command), or generated-at-boot files (openhands); redaction exists only at observation boundaries.
- **No config hot-reload outside the operated platforms.** Only temporal (file polling) and opa (discovery bundles) reload; letta, langgraph, and the SDKs are explicitly restart-required.
- **No self-hosting story in crewai's repo** — production guidance defers entirely to the hosted AMP platform (`docs/edge/en/concepts/production-architecture.mdx:124-135`), the sharpest library-vs-platform strategic divergence in the study.
- **Unknown-variable warnings nowhere except schema-validated systems.** crewai and letta silently ignore typo'd env keys/setting names; opa computes unknown keys but stops at warnings with no strict mode.

## Per-Source Notes

Brief capsules; full detail lives in the per-source reports.

- **agent-framework (8):** Dual-language SDK. Python's `load_settings()` gives a tested four-layer precedence with per-provider prefixes and secret masking; .NET uses DI registration plus fail-fast sample conventions. Environment handled by hosted-context detection; deployment expressed as a menu of composable hosting adapters (A2A, Azure Functions, Durable Task, Foundry Hosted Agents, self-hosted) with push-button Container Apps deploy (`python/samples/04-hosting/README.md:5-21`). Concerns: cross-stack naming drift, `.env`-overrides-env quirk (`test_settings.py:109`), .NET/.Python disabled-flag read asymmetry.
- **crewai (6):** Env-var-first, ~50 ad-hoc `CREWAI_*` reads, consistent-but-unregistered param > env > file > default chains. Bright spots: pre-deploy validator with nine check categories and blocking errors, hardened 0o600 settings persistence, excellent test-environment parity harness (`.env.test`, network blocking, isolated storage). Concerns: three divergent `.env` parsers, inconsistent boolean truthiness, silent write loss, hosted-platform-only deployment docs.
- **langfuse (8):** Env-only config in four per-runtime Zod schemas, fail-fast at import, cross-field semantic validation refusing data-loss flag combos, empty-string normalization, entrypoint credential/migration diagnostics. Two-image product (web/worker) shaped by ~30 queue-consumer toggles. Feature flags: DB-backed per-user registry plus env migration gates with cohort cutoffs. Concern: triple-duplicated keys kept aligned by comments; validators lack direct unit tests.
- **langgraph (7):** One `langgraph.json` compiled to dev server, compose stack, OCI image, platform payload, and `RemoteGraph` embedded client; engine runtime mode swaps topologies. Validation is the standout (did-you-mean, fix snippets, injection sanitization, reserved-var blocklist, ~50 tests). Concerns: zero file layering, build-baked `ENV` lines, one known schema/consumer drift (`disable_persistence`).
- **letta (7):** Four-layer config (defaults < deep-merged YAML < env < argv) bridged into env vars feeding eight pydantic-settings singletons. One multi-arch image runs all-in-one (auto-started internal Postgres/Redis), sidecar compose, vLLM GPU sidecar, or managed-backends mode purely via env; migration-gated boot. Concerns: silent YAML swallow, case-sensitive prod gates, untested config layer, legacy configparser alive in Alembic.
- **opa (8):** One binary (REPL/server/SDK/offline tools) with layered file + `${VAR}` + `--set` + `OPA_*` flag env mapping, validated by an embedded Rego policy injecting defaults and warning on unknown keys, extensible via reflection-derived specs. Discovery plugin provides guarded runtime reconfiguration with sovereign boot config; `/v1/config` serves redacted active config. Concerns: warning-only strictness, fragmented toggle mechanisms (build tags/import side effects/config presence/ad-hoc env), undocumented precedence between the two env mechanisms.
- **openai-agents-sdk (8):** Pure library; deployment = swapping injected providers/sandboxes/sessions, documented as decision tables for laptop→container→hosted parity. Shared coercion layer rejects unknown fields everywhere; precedence arg > setter > env regression-tested. Standout validation culture (eager conflict guards, resource-safety bounds, `python -O` regression lesson). Concerns: import-time debug flags, mutable globals without reset API, scattered ~15+ env vars, environment-inheriting subprocess sidecar.
- **openhands (8):** Frontend-centric product with one JSON contract across launcher scripts, app code, Docker build stage, and CI; four web config layers ending in runtime-injected window globals that rescue bundle-baked values. Five shipping modes (npm CLI, Docker all-in-one, Helm/K8s, Electron, embeddable library) with self-describing `runtime_services` metadata. Cross-artifact tests execute real config blocks. Concerns: residual bake-time values, hardcoded flag stub, localStorage key exposure acknowledged in docs.
- **pydantic-ai (7):** Three independent layers (provider creds arg→env→default across ~30 providers; shallow `ModelSettings` merge; four-step profile chain) plus declarative pydantic-validated `AgentSpec` files with editor JSON Schemas. Five documented modes including air-gapped web chat and durable execution on external engines with loud rejection of unserializable model instances. Concerns: deliberate `ModelSettings` silence (typos dropped), no env abstraction, worker-side config duplication in durable mode.
- **temporal (9):** The reference implementation for the whole dimension. Three static loading strategies behind a conflict-guarded CLI (embedded env-template in-binary, single file, deprecated-but-live env/zone overlay hierarchy), optional per-file Sprig templating, multi-layer validation up to a dedicated `validate-dynamic-config` command, secret-masked `render-config`, env-discipline package keeping server code off `os.Getenv`. Dynamic config doubles as the flag system with constraint scoping, polling subscriptions, monotonic rollouts, and scheduled changes. Concerns: dual static loaders coexist, comment-sniffed template activation, no OSS remote flag admin tooling.

## Open Questions

- **Does any source's staging story work end-to-end?** Every report found either no staging concept or only indirect evidence (langfuse's region enum, langgraph's dashboard hostname mapping for staging backends, `libs/cli/langgraph_cli/deploy.py:661-679`). How operated platforms (Langfuse Cloud, Letta Cloud, CrewAI AMP) actually promote environments is outside all studied trees.
- **Would temporal's dynamic-config primitives (constraints, monotonic rollouts) generalize to smaller projects, or do they presuppose temporal's scale and fx-based architecture?** The `Client` interface is narrow (`common/dynamicconfig/client.go:13-33`), suggesting portability, but no studied source has adopted anything similar.
- **Is the env-var surface converging or diverging across the agent-SDK cluster?** agent-framework's report explicitly proposes a cross-language env-name manifest; pydantic-ai and openai-agents-sdk each note sprawl. Whether the ecosystem will standardize provider credential names (beyond de facto `OPENAI_API_KEY`) remains unresolved.
- **Do build-time-baked frontend values have a settled best practice?** Openhands' injection channel and langfuse's serve-through-API are two partial answers; neither source claims full single-artifact parity yet.
- **What consumes langgraph's distributed-mode `N_JOBS_PER_WORKER`?** Set by the CLI (`libs/cli/langgraph_cli/docker.py:267-268`) but consumed in the external `langgraph-api` server, unverifiable within the source boundary.
- **Are opa's ad-hoc env toggles (e.g., `OPA_DECISIONS_INTERMEDIATE_RESULTS`, bypassing the validation pipeline entirely) transitional or permanent surface?** Not determinable from code (`v1/server/server.go:105`).
