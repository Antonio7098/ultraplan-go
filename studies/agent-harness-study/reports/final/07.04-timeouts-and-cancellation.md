## Executive Summary

Three sources produced code-level evidence for this dimension, and they occupy three distinct positions on the same problem. **pydantic-ai** (9/10) ships the most mature model: layered deadlines (`@tool(timeout=)` > `FunctionToolset.timeout` > `Agent(tool_timeout=)`) enforced with `anyio.fail_after` and translated into retryable `ModelRetry` feedback (`pydantic_ai_slim/pydantic_ai/toolsets/function.py:686-691`), plus a first-party cancellation controller — `CancellationToken` + `RunCancellation` — that distinguishes its own cancellations from external asyncio ones via `Task.uncancel()` accounting (`pydantic_ai_slim/pydantic_ai/_cancel.py:203-242`) and recovers run state from externally cancelled runs through `RunCancelled.from_cancellation()` (`pydantic_ai_slim/pydantic_ai/exceptions.py:318-362`). **agent-framework** (7/10) takes a surface-local approach: each subsystem owns the bound type that fits it — iteration/function-call caps for the model loop (`python/packages/core/agent_framework/_tools.py:1332-1386`), wall-clock deadlines plus TTL/cancel semantics for MCP long-running tasks (`python/packages/core/agent_framework/_mcp.py:346-380`), SIGTERM→SIGKILL escalation for shell subprocesses (`python/packages/tools/agent_framework_tools/shell/_killtree.py:50-131`) — with cooperative asyncio cancellation throughout and aborts made "loud" by settling dangling service-side tool calls before the failure propagates (`python/packages/core/agent_framework/_tools.py:3082-3157`). **openhands** (7/10) is a browser frontend and therefore splits ownership by network boundary: the client guarantees its own transports never hang (a 10 s WebSocket handshake watchdog because browsers never time out a `CONNECTING` socket, `src/utils/websocket-handshake.ts:17-26`; per-endpoint HTTP timeouts from 3 s to 5 min, `src/api/agent-server-adapter.ts:178` … `src/api/conversation-service/agent-server-conversation-service.api.ts:79`), while tool deadlines are forwarded to the agent-server as payload fields with a +10 s transport grace (`src/api/runtime-service/agent-server-runtime-service.ts:51`), and user-initiated stop is a first-class UI flow with confirmation, optimistic status patching, and structured cancel APIs (`src/hooks/mutation/use-unified-stop-conversation.ts:58-71`).

Despite very different products, the three converge on the same skeleton: no global whole-run wall-clock timeout exists anywhere; layered per-surface bounds are used instead; cancellation of in-process code is cooperative, never forced; parallel tool work cancels siblings on failure; every "best-effort" cleanup path carries its own deadline; and timeouts/cancellations always surface as structured, conversation-visible artifacts rather than silent hangs. Most strikingly, all three independently built *cancellation provenance discrimination* — three different mechanisms for one problem: count-based `Task.uncancel()` reconciliation (pydantic-ai), `task.cancelling() > 0` predicates (agent-framework, `python/packages/core/agent_framework/_mcp.py:405-418`), and error-type discrimination between `TimeoutError` and manual-abort `AbortError` (openhands, `src/api/llm-balance-service.ts:34-40`). The main divergences track ownership boundaries: who enforces the deadline (in-process runtime vs remote server), what a timeout means downstream (retryable model feedback vs terminal structured result vs UI status union), and how much of the stack each source owns.

The dimension's central question — *can a stuck shell command or API call be stopped without killing the whole run?* — is answerable "yes" in all three materialized sources for asynchronous work: tool tasks are isolated leaves whose cancellation does not take down the run, and tests prove it (`tests/test_run_cancellation.py` in pydantic-ai; `test_failure_cancels_concurrent_sibling_tool` at `python/packages/core/tests/core/test_middleware_with_agent.py:2548-2594` in agent-framework; handshake-watchdog and queue-sweep tests at `__tests__/hooks/use-websocket.test.ts:533-584` and `__tests__/hooks/use-bash-command-runner.test.ts:135-153` in openhands). The universal residual gap is synchronous code: neither Python framework can interrupt a sync tool body already running on a worker thread — both document this explicitly and test the limitation (`pydantic_ai_slim/pydantic_ai/_utils.py:162-180`; `python/packages/core/tests/core/test_middleware_with_agent.py:2596-2659`) — and openhands' bash runner has no client-side deadline of its own, trusting the server to honor the forwarded timeout.

## Core Thesis

**Mature agent harnesses do not solve "stop the stuck thing" with one timeout — they solve it with ownership.** Each layer that can hang gets the kind of bound matching its unit of work (iteration counts for model roundtrips in agent-framework's `FunctionInvocationConfiguration`, wall-clock scopes for I/O in pydantic-ai's `anyio.fail_after` idiom, drain deadlines for teardown in both), each cancellation path is cooperative but *bounded* (even fire-and-forget remote cancels get a 5 s budget — `_MCP_TASK_CANCEL_TIMEOUT`, `python/packages/core/agent_framework/_mcp.py:326`), and every termination produces a structured artifact — a synthesized `'interrupted'` tool return (`pydantic_ai_slim/pydantic_ai/messages.py:1292-1295`), a `[command timed out]` shell result (`python/packages/tools/agent_framework_tools/shell/_types.py:35-47`), an `"timeout"` outcome-union member (`src/hooks/use-await-context-compaction.ts:11`), a `shutdown_reason="cancelled"` hook (`python/packages/core/agent_framework/_agent_hooks.py:1097-1107`) — so the conversation, the cache, and the operator can all observe what happened.

The three materialized sources implement this thesis at different ownership boundaries — framework-runtime-enforced (agent-framework), library-coordinated with a dedicated controller object (pydantic-ai), client-delegated (openhands) — and their residual failures cluster exactly where ownership is ambiguous: sync worker threads nobody can kill, forwarded deadlines nobody locally verifies (openhands' bash promise pending until socket death if the server drops silently, `src/hooks/use-bash-command-runner.ts:122-135`), and count-based attribution that misreads absorbed cancellations (pydantic-ai issue #7240, `pydantic_ai_slim/pydantic_ai/_cancel.py:144,222-223`). The transferable lesson is not any single mechanism but the discipline: bound what you own with the right unit, attribute every cancellation, repair shared state before propagating, and document the ceiling you cannot fix.

## Approach Models

**pydantic-ai — coordinated library model: a first-party cancellation controller plus a layered deadline ladder.** Cancellation is promoted from an ambient exception into a named object: `CancellationToken` (thread-safe, idempotent, may govern multiple runs, `pydantic_ai_slim/pydantic_ai/_cancel.py:42-89`) and `RunCancellation` (owns the run-driving task, tracks issued cancellations, resolves at the outer edge, `_cancel.py:92-242`). Deadlines are expressed per layer in the unit that layer understands: tool-level via `anyio.fail_after` mapped to `ModelRetry` (`pydantic_ai_slim/pydantic_ai/toolsets/function.py:684-693`), hook-level identically (`pydantic_ai_slim/pydantic_ai/capabilities/hooks.py:239-252`), HTTP per-request via `ModelSettings.timeout` (`pydantic_ai_slim/pydantic_ai/settings.py:209-222`) over a 600 s default (`pydantic_ai_slim/pydantic_ai/_http.py:24`), MCP init/read separately (`pydantic_ai_slim/pydantic_ai/mcp.py:893-1043`). Whole-run wall-clock bounds are deliberately deferred to callers wrapping `agent.run()` in `asyncio.timeout()` / `anyio.fail_after()` / a token from a timer (`docs/timeouts.md:18`). Supporting machinery: shielded `cancel_and_drain` for parallel tool tasks (`pydantic_ai_slim/pydantic_ai/_utils.py:312-329`), a `raise_if_cancelling()` backstop against absorbed cancellations (`_utils.py:332-368`), `release_issued()` as a `finally` invariant so issued counts never contaminate outer scopes (`_cancel.py:244-257`), and explicit rejection of same-process tokens at Temporal/Prefect/DBOS activity boundaries (`pydantic_ai_slim/pydantic_ai/durable_exec/_runtime_toolsets.py:38-49`).

**agent-framework — distributed runtime model: surface-local bounds with a loud/graceful stop vocabulary.** There is no central controller; instead each subsystem owns the knob that expresses its natural failure unit: iteration/function-call/consecutive-error budgets for the function-invocation loop (`python/packages/core/agent_framework/_tools.py:1332-1386`, normalization guards at `:1389-1409`), TTL/max-wait/cancel-on-disconnect semantics for MCP long-running tasks (`MCPTaskOptions`, `_mcp.py:346-380`), wall-clock `asyncio.wait_for` plus killtree escalation for shells (`python/packages/tools/agent_framework_tools/shell/_executor.py:72-80`), a drain deadline for background agents (`release_session(timeout=30.0)`, `python/packages/core/agent_framework/_harness/_background_agents.py:345-360`), and per-client HTTP timeouts forwarded to the OpenAI SDK (`python/packages/openai/agent_framework_openai/_chat_client.py:522`). Stop semantics are split into two named signals: `MiddlewareTermination` stops gracefully with an optional substitute result, while `MiddlewareFailure` fails closed — siblings cancelled, results discarded, and on service-managed conversations dangling calls settled with synthetic error results before re-raising (`python/packages/core/agent_framework/_middleware.py:75-99`; `_tools.py:3082-3157`).

**openhands — delegated client model: the UI guarantees its own layers and forwards tool time.** Because tool execution lives behind an agent-server, the frontend's contract is narrower but strictly held: WebSocket handshakes are force-closed by a shared watchdog (`src/utils/websocket-handshake.ts:17-26`) since browsers never time out `CONNECTING`; every HTTP surface carries an explicit numeric timeout sized per concern (health probe 4 s, `/server_info` 5 s, LLM balance 10 s, cloud proxy 30 s, typed-client default 60 s, conversation create 5 min); tool commands carry a caller-supplied seconds value sent to the server rather than enforced locally, with the cloud proxy deriving `timeoutSeconds = timeout + 10` so the transport provably outlives the tool (`src/api/runtime-service/agent-server-runtime-service.ts:51`). Termination is UX-first: a visible stop button drives `pauseConversation` (immediate `/interrupt` on local backends, cooperative sandbox pause on Cloud — `src/hooks/mutation/conversation-mutation-utils.ts:36-61`), success optimistically patches `PAUSED` statuses into caches (`use-unified-stop-conversation.ts:63-66`), and automation runs expose an explicit cancel endpoint gated to in-flight runs (`src/api/automation-service/automation-service.api.ts:446-451`).

**The remaining six sources share a fourth "model": none.** Each report documents an empty checkout with a bounded search audit and rates 1/10 as an evidence gap. Three of them independently flag the same study-infrastructure root cause and remedy (fail-fast preflight when a selected source contains zero files), and two propose curated scoped checkouts as the pragmatic fix.

## Pattern Catalog

### P1. Deadline-per-layer in the native unit of that layer

- **Problem:** a single global timeout either strangles legitimate long work or protects nothing; different subsystems fail in different units (roundtrips, seconds, process lifetimes).
- **Sources:** all three materialized. agent-framework uses iteration counts for the model loop but wall-clock for shells/MCP/search (`python/packages/core/agent_framework/_tools.py:1332-1386` vs `python/packages/tools/agent_framework_tools/shell/_executor.py:72-80`); pydantic-ai uses deadline scopes for tools/hooks and request timeouts for HTTP (`pydantic_ai_slim/pydantic_ai/toolsets/function.py:686-691`, `pydantic_ai_slim/pydantic_ai/settings.py:209-222`); openhands sizes each endpoint constant per concern from 3 s metadata probes to a 5 min provisioning call (`src/api/agent-server-adapter.ts:178`, `src/api/conversation-service/agent-server-conversation-service.api.ts:79`).
- **Why it works:** the bound is expressed in the currency the layer actually spends, so defaults are tight where hangs are cheap to detect and loose where work is legitimately slow.
- **Copy when:** you own multiple heterogeneous surfaces (model calls, subprocesses, polling loops).
- **Overkill/risky when:** you have one homogeneous call path — then a single documented default beats seven knobs.
- **Cost:** discoverability. agent-framework's own report counts ~7 configuration surfaces needed to bound one agent; pydantic-ai documents that `Agent(tool_timeout=...)` does not reach user-constructed or MCP toolsets (`docs/timeouts.md:25`).

### P2. Cancellation provenance discrimination

- **Problem:** once a library raises or catches `CancelledError` internally, it can misattribute caller-driven cancellation (wrongly swallowing it, or wrongly treating internal cleanup as a user abort).
- **Sources:** all three, via three mechanisms. pydantic-ai issues its own `Task.cancel()` and consumes exactly that issuance with `Task.uncancel()` at the run edge, translating to `RunCancelled` only when no external cancel remains (`pydantic_ai_slim/pydantic_ai/_cancel.py:203-242`); agent-framework gates re-raise decisions on `asyncio.current_task().cancelling() > 0` (`python/packages/core/agent_framework/_mcp.py:405-418`); openhands classifies `TimeoutError` (deadline) distinctly from `AbortError` (manual abort) including wrapped `cause`s (`src/api/llm-balance-service.ts:34-40`, log classification at `src/hooks/query/use-bash-command-logs.ts:80-98`).
- **Why it works:** external cancellation keeps its native surface (`TimeoutError` from `asyncio.timeout()`, `CancelledError` from TaskGroups) while first-party termination becomes a richer typed event — pydantic-ai states this as policy (`docs/agent.md:647,777-782`).
- **Copy when:** your code both initiates cancellations internally and must honor external ones (any framework driving tasks).
- **Overkill when:** you never cancel internally — plain propagation suffices.
- **Known limits:** counting is not identity — a user `Task.uncancel()` followed by an external cancel can be mis-credited (pydantic-ai #7240, tracked at `pydantic_ai_slim/pydantic_ai/_cancel.py:144,222-223`); agent-framework degrades on Python < 3.11 where the predicate is unavailable.

### P3. Structured termination artifacts and state repair

- **Problem:** an aborted batch leaves dangling tool calls, stale caches, or histories the provider will reject on resume.
- **Sources:** all three, at their respective boundaries. pydantic-ai synthesizes `outcome='interrupted'` tool returns so cancelled histories remain provider-valid (`pydantic_ai_slim/pydantic_ai/messages.py:1292-1295,1335-1351`, repair at `pydantic_ai_slim/pydantic_ai/_agent_graph.py:2880-2887`); agent-framework's `_settle_dangling_service_function_calls` submits one error `function_result` per dangling call before re-raising so the hosted thread's continuation endpoint is clean (`python/packages/core/agent_framework/_tools.py:3082-3157,3275-3290`); openhands patches `execution_status: PAUSED` into query caches synchronously so downstream gates react before the next poll (`src/hooks/mutation/use-unified-stop-conversation.ts:58-71`) and models `"timeout"` as a first-class outcome member, not an error collapse (`src/hooks/use-await-context-compaction.ts:11,150-154`).
- **Why it works:** consumers (LLM providers, UI gates, analytics) never observe a torn intermediate state; the abort becomes a normal transition in the machine.
- **Copy when:** anything shares state with your run — conversation history, caches, persisted threads.
- **Overkill when:** the aborted unit is fully private and discarded wholesale.

### P4. Sibling cancellation with shielded drain in parallel batches

- **Problem:** one failing tool in a parallel batch must not strand its siblings' promises or leak their resources.
- **Sources:** agent-framework gathers children then re-cancels siblings on `MiddlewareFailure`, discarding even completed late results (`python/packages/core/agent_framework/_tools.py:1863-1876`; test `test_failure_cancels_concurrent_sibling_tool`, `python/packages/core/tests/core/test_middleware_with_agent.py:2548-2594`); pydantic-ai cancels siblings on *any* exception and drains under `anyio.CancelScope(shield=True)` so teardown cannot itself be cancelled (`pydantic_ai_slim/pydantic_ai/_tool_execution.py:828-836`, `pydantic_ai_slim/pydantic_ai/_utils.py:312-329`); openhands' analogous move is a single `rejectAll(reason)` sweep across waiting/pending/active command queues on any fatal socket event (`src/hooks/use-bash-command-runner.ts:141-156`).
- **Why it works:** no orphaned promises; the shield prevents re-delivery storms during teardown; openhands additionally nulls handlers before closing to guarantee exactly-once rejection (`:164-174`).
- **Copy when:** fan-out execution exists anywhere in the stack.
- **Risky when:** siblings hold non-interruptible resources — then drain needs its own deadline (see P8).

### P5. Watchdogs and abandon-marks for primitives the platform never times out

- **Problem:** some platform primitives have no deadline semantics at all (browser sockets in `CONNECTING`; Python worker threads).
- **Sources:** openhands closes stuck handshakes at 10 s and routes the abort through the socket's *normal* close path so existing reconnect/reject handling does the work — no parallel failure path (`src/utils/websocket-handshake.ts:7-26`; tests `__tests__/hooks/use-websocket.test.ts:533-584`). The Python frameworks generalize the idea as *abandonment*: pydantic-ai marks sync-tool threads abandoned and discards results while documenting that side effects persist (`pydantic_ai_slim/pydantic_ai/_utils.py:162-180`; test asserting thread runs to completion, `tests/test_tools.py:3111-3140`); agent-framework's `_drain_runtime` abandons tasks that ignore cancellation after a logged warning (`python/packages/core/agent_framework/_harness/_background_agents.py:415-440`; test at `python/packages/core/tests/core/test_harness_background_agents.py:725`).
- **Why it works:** the caller/event loop stays responsive even when the underlying unit cannot be killed; abandonment converts an unbounded hang into a bounded, observable leak.
- **Copy when:** the host primitive lacks deadlines (sockets, threads, foreign event loops).
- **Overkill when:** the primitive already supports cancellation signals.

### P6. Escalation ladders for the things you *do* own (processes)

- **Problem:** killing a timed-out process naively orphans grandchildren.
- **Sources:** agent-framework only (the other two own no processes). Stateless shell: `asyncio.wait_for(communicate(), timeout)` → `kill_process_tree` with SIGTERM → grace → SIGKILL, psutil with stdlib fallbacks incl. `taskkill.exe`/POSIX `killpg` (`python/packages/tools/agent_framework_tools/shell/_executor.py:72-80`, `_killtree.py:50-131`); persistent shell: sentinel wait times out → SIGINT/`CTRL_BREAK_EVENT` to interrupt the current command → killtree fallback (`python/packages/tools/agent_framework_tools/shell/_session.py:268-290,410-419`).
- **Why it works:** polite-first escalation preserves output and exit-status fidelity (`ShellResult.timed_out` with `exit_code -1`/sentinel `124`, `_types.py:24-47`) while guaranteeing eventual termination; the timed-out result is fed back to the model as `[command timed out]`.
- **Copy when:** you spawn OS processes.
- **Not applicable when:** execution lives behind a service boundary — then forward the deadline and add a grace margin (openhands' `timeout + 10` invariant, `src/api/runtime-service/agent-server-runtime-service.ts:51`).

### P7. Timeout-as-error, never timeout-as-absence

- **Problem:** mapping a timeout to an empty/default value lets caches and UIs memorize the wrong answer permanently.
- **Sources:** clearest in openhands — the balance service deliberately rethrows timeouts because `null` would be cached with `staleTime: Infinity` and hide the balance card forever (`src/api/llm-balance-service.ts:57-69,84-97`); 404 maps to `null` (hide UI) but abort-like errors rethrow. pydantic-ai encodes the same instinct structurally: interruption gets its own neutral outcome (`'interrupted'`) distinct from `'failed'`, so it is never funneled into the transient-error channel (`pydantic_ai_slim/pydantic_ai/messages.py:1335-1351`). agent-framework surfaces search timeouts as raised `ValueError` to the calling model rather than silent emptiness (`python/packages/core/agent_framework/_harness/_file_access.py:106-125`).
- **Why it works:** absence-of-data and failure-to-fetch have different recovery strategies; conflating them creates sticky lies.
- **Copy when:** any result is cached, memoized, or feeds analytics.
- **Cheap always:** there is no context where this hurts.

### P8. Bounded best-effort cleanup — "even cleanup has a budget"

- **Problem:** best-effort cancellation of *remote* state (server-side tasks, sessions) can itself hang, wedging shutdown.
- **Sources:** agent-framework bounds everything: `_MCP_TASK_CANCEL_TIMEOUT = 5 s` around fire-and-forget `tasks/cancel` (`python/packages/core/agent_framework/_mcp.py:326`), `release_session(timeout=30.0)` computes a wall-clock deadline and abandons stragglers with a warning (`python/packages/core/agent_framework/_harness/_background_agents.py:401-440`), session close writes `exit\n` then waits `SHUTDOWN_GRACE=2.0` before killtree (`python/packages/tools/agent_framework_tools/shell/_session.py:151-175`); pydantic-ai registers `finish()` as a `stack.callback` so the controller is neutralized even on exception paths (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:1808`) and releases issued-cancel counts in a `finally` (`_cancel.py:244-257`); openhands orders unmount teardown (null handlers → close socket) so sweeps run exactly once (`src/hooks/use-bash-command-runner.ts:164-174`).
- **Why it works:** the invariant "no path is unbounded" holds transitively, including teardown paths.
- **Copy when:** you cancel anything across a network or process boundary.
- **Tradeoff:** abandonment means remote state may still be running — agent-framework pairs the bound with honest naming (`_MCPTaskAbandoned` distinguishes abandonment from terminal failure, `_mcp.py:335-340,2303-2308`).

### P9. Negotiated ceilings and validated knobs for user-facing timeouts

- **Problem:** user-supplied timeouts can exceed what the backend honors, failing late and confusingly.
- **Sources:** openhands validates automation timeouts positive-int and caps them against a deployment-advertised maximum before the request leaves the browser (`src/utils/automation-timeout.ts:19-37`; seam test `__tests__/manifests/automation-interface.test.ts:63,73`); agent-framework rejects invalid budgets at construction (`max_iterations < 1` etc., `python/packages/core/agent_framework/_tools.py:1389-1409`) and validates MCP TTL/wait positivity (`_mcp.py:382-386`); pydantic-ai validates `tool_timeout > 0` at agent construction (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:661-680`).
- **Why it works:** misconfiguration fails fast at the API boundary with a clear message instead of mid-run.
- **Copy when:** users configure timeouts at all.
- **Overkill when:** knobs are developer-facing constants under review.

## Key Differences

**What converges despite different implementation choices.** All three materialized sources: (1) refuse to provide a global run timeout and route whole-run bounds to caller-level wrappers (`docs/timeouts.md:18`; `python/packages/core/agent_framework/_agents.py:1849-1880` showing no `timeout=` on `Agent.run`; per-module constants with no settings key in openhands); (2) treat cancellation as cooperative and document the sync-code ceiling explicitly rather than pretending (`docs/agent.md:737-738`; `python/packages/core/agent_framework/_middleware.py:93-99`; openhands' docstring that the backend "deliberately leaves the in-flight agent turn running", `src/hooks/mutation/conversation-mutation-utils.ts:94-99`); (3) make parallel work cancel-safe (P4); (4) produce structured termination artifacts (P3); and (5) discriminate cancellation provenance (P2). This convergence across a browser app and two Python libraries suggests these are load-bearing properties of the problem, not stylistic accidents.

**Why they diverge.** The divergence axes are product shape and ownership, not quality:

- *Ownership of execution.* openhands cannot enforce tool timeouts (the executor is another repo — noted explicitly as outside its isolation boundary), so it enforces what it owns (transports) and forwards what it doesn't, adding the `timeout + 10` ordering invariant so the transport provably outlives the tool (`src/api/runtime-service/agent-server-runtime-service.ts:51`). agent-framework and pydantic-ai own the loop, so they enforce inside it — but neither owns the caller's stack frame, hence no run-level timeout there either.
- *Coordination style.* pydantic-ai centralizes cancellation identity in one controller object with a state machine and 68 regression tests (`tests/test_run_cancellation.py`, 1879 lines); agent-framework distributes the concern across subsystems, each strongly tested, accepting fragmentation as the price of per-unit fidelity; openhands treats cancellation mostly as a UX workflow (stop button → confirm modal → mutation → optimistic cache patch). Same property, three altitudes.
- *Runtime constraints.* Browsers lack timers on connecting sockets (→ watchdog, openhands); Python cannot terminate threads (→ abandon-marks, both frameworks); service-managed conversations persist across runs (→ settlement before re-raise, agent-framework only — neither pure-library nor pure-frontend faces this constraint).
- *Durability integration.* Only pydantic-ai shows an explicit cross-process story: same-process tokens raise `UserError` at Temporal/Prefect/DBOS activity boundaries because a serialized token would be ignored or silently cancel a replay (`pydantic_ai_slim/pydantic_ai/durable_exec/_runtime_toolsets.py:38-49`). The others show no equivalent surface in this dimension.
- *What a timeout means downstream.* pydantic-ai converts tool timeouts into retryable model feedback (`ModelRetry('Timed out after N seconds.')`, consuming retry budget — `tests/test_tools.py:3202-3221,3285-3306`); agent-framework converts them into terminal structured results (`ShellResult.timed_out`) or loud exceptions; openhands converts them into UI outcome unions and statuses. These are genuinely different contracts serving different consumers (model vs operator vs user), and none is strictly better.

## Tradeoffs

- **Central controller vs distributed knobs.** pydantic-ai's `RunCancellation` gives one place to reason about attribution, delivery-before-bind, and finish semantics (`pydantic_ai_slim/pydantic_ai/_cancel.py:121-152,194-201`), at the cost of building and testing a bespoke state machine. agent-framework avoids that build cost but pays in user-facing fragmentation — its own report counts ~7 surfaces to learn. Best-fit: controller when cancellation crosses many layers; knobs when each layer's semantics differ materially.
- **Enforce-in-loop (Python frameworks) vs forward-with-grace (openhands).** Enforcement gives real guarantees but requires owning process/thread management; forwarding keeps the client thin but makes correctness depend on server compliance — openhands accepts that a silently dropping server leaves the bash promise pending until socket death (`src/hooks/use-bash-command-runner.ts:122-135`), mitigated only by the eventual `rejectAll` sweep. Best-fit: enforce when you own the executor; forward + watchdog your own layers + derive a grace margin when you don't.
- **Iteration budgets vs wall clocks.** agent-framework's `max_iterations`/`max_function_calls` are deterministic and provider-independent but cannot bound a slow single call (its report notes the loop can sit on one provider call up to the SDK's TCP-stack timeout, default connect 5 s / total 600 s, `python/packages/openai/agent_framework_openai/_chat_client.py:558-559`); wall-clock scopes (pydantic-ai) bound real time but introduce flakiness under load. They compose: use both.
- **Batch-granular caps vs hard caps.** agent-framework documents that `max_function_calls` is checked *after* each parallel batch — 20 requested calls execute even with a limit of 10 (`python/packages/core/agent_framework/_tools.py:1348-1351,2637-2638`). Benefit: simpler, no partial-batch bookkeeping. Cost: overshoot proportional to batch size. Alternative seen: pydantic-ai cancels siblings immediately on exception, but neither framework truncates pre-execution.
- **Immediate interrupt vs cooperative drain from one button.** openhands ships both semantics behind one control: local `/interrupt` cancels in-flight LLM requests immediately while Cloud pause "waits for current LLM call to finish" to preserve sandbox state (`src/hooks/mutation/conversation-mutation-utils.ts:36-61`). Benefit: each backend gets the correct contract. Cost: identical UI, different latency promises — a documentation burden its report flags.
- **Retryable timeout vs terminal timeout.** pydantic-ai maps tool timeouts to `ModelRetry` so the model adapts (budget-consuming, tested at `tests/test_tools.py:3285-3306`); `ToolFailed` remains available for terminal failures that should not consume budget (`docs/timeouts.md:41`). Choosing wrong either burns retries on hopeless tools or robs the model of self-correction.
- **Optimistic convergence vs wait-for-truth.** openhands patches `PAUSED` synchronously into caches so the WS gate fires instantly (`use-unified-stop-conversation.ts:58-66`); cost is potential divergence if the server disagrees, which the poll later reconciles. The Python frameworks have no UI cache and instead invest in history repair (P3) — the same principle applied to a different shared medium.

## Decision Guide

Choose the enforcement locus first, everything else follows:

- **You own the run loop (library/framework):** adopt pydantic-ai's shape — a first-party cancellation handle exposed on run/context/stream objects, deadlines enforced at the tool boundary with retryable feedback, external cancellation passed through untouched with state attached for recovery (`pydantic_ai_slim/pydantic_ai/exceptions.py:318-362`). Add agent-framework's settlement discipline if your conversations persist server-side.
- **You orchestrate heterogeneous surfaces with different natural units (runtime with tools, MCP, shells, background agents):** follow agent-framework — per-surface knobs in the native unit (P1), loud/graceful signal separation, escalation ladders for processes, bounded drains everywhere.
- **You are a client over an execution service:** follow openhands — bound every transport you own, forward tool deadlines as payload with a derived grace margin, install watchdogs only where the platform lacks deadlines, and invest in stop UX with structured statuses rather than trying to manage remote processes.
- **Deciding whether to build a provenance mechanism (P2):** yes if you ever raise `CancelledError` internally or wrap caller tasks — all three sources needed it. Pick by platform: `uncancel()` counting where you control issuance (Python ≥3.11), `task.cancelling()` checks where you only need a boolean, error-type discrimination in TypeScript-style `AbortSignal` worlds.
- **Deciding on a global run timeout:** none of the three provides one; all three document caller-side wrapping. Follow suit unless you can also solve the attribution problem it creates (a wrapper-induced `TimeoutError` must remain distinguishable from tool timeouts).
- **Deciding how to handle sync tools:** assume uninterruptible. Either require `async def` for anything slow, or adopt the abandon-mark contract (discard result, warn, document side-effect persistence) — both frameworks converged here independently, and openhands sidesteps it entirely by delegation.

## Practical Tips

- Give every async leaf a deadline *and* a translation rule: pydantic-ai's pairing of `anyio.fail_after` + `ModelRetry` for tools, and the identical idiom reused for hooks (`pydantic_ai_slim/pydantic_ai/capabilities/hooks.py:239-252`), shows one idiom applied uniformly beats bespoke handling per site.
- Route forced aborts through normal failure paths where possible: openhands' watchdog closes the socket so regular close handling (reconnect, reject queues) does the cleanup — no second code path to maintain (`src/utils/websocket-handshake.ts:7-11`).
- Set the flag *before* tearing down: pydantic-ai sets `_cancelled = True` prior to `close_stream()` because teardown itself may throw (`pydantic_ai_slim/pydantic_ai/models/__init__.py:1082-1097`), and suppresses resulting transport errors as non-errors (`iterator_with_cancel_guard`, `:1046-1080`). Order matters; copy it.
- Register cancellation interest before entering queues/limiters: pydantic-ai attaches tokens before the concurrency limiter so a pre-cancelled run never waits for a slot (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:1802-1815`, test `test_token_cancels_run_queued_behind_concurrency_limiter`).
- Derive dependent timeouts, don't duplicate them: openhands' `timeoutSeconds = timeout + 10` encodes "transport outlives tool" as arithmetic rather than convention (`src/api/runtime-service/agent-server-runtime-service.ts:51`).
- Make aborted state boring: synthesize the missing artifact (interrupted tool return, settled function result, patched status) so every consumer sees a legal state machine (P3). pydantic-ai's `_repair_dangling_tool_calls` is the reference implementation for provider-valid resumes.
- Bound and name abandonment: a warning plus a distinct concept (`_MCPTaskAbandoned`) tells operators "we stopped waiting" versus "it failed" (`python/packages/core/agent_framework/_mcp.py:2303-2308`).
- Test the seams where hangs actually occur: handshake watchdogs, device-flow timeouts, compaction timers, MCP timeout classification, cap-reached and sibling-cancel paths — the three sources' test inventories (`__tests__/hooks/use-websocket.test.ts:533-584`; `tests/test_run_cancellation.py`; `python/packages/core/tests/core/test_function_invocation_logic.py:1527-1634`) are a checklist of what to cover.
- Add jitter when multiple clients retry against one backend: openhands' ≤30 % jitter specifically de-synchronizes its main and planning sockets (`src/hooks/use-websocket.ts:18-20,125-132`).

## Anti-Patterns / Caution Signs

- **Scattered magic numbers with no registry.** openhands carries ~10 hand-tuned per-endpoint constants across modules (its report lists `PROBE_TIMEOUT_MS` through `CREATE_CONVERSATION_TIMEOUT_MS`); changing global responsiveness requires touching every file. Caution sign: grep finds timeout literals in more than a handful of modules.
- **Forwarding a deadline nobody verifies locally.** A client that sends `timeout` but never ticks its own clock inherits whatever the server does (or fails to do) — openhands' acknowledged bash-runner gap. Caution sign: correctness arguments that cite another component's good behavior.
- **Caps checked after the fact.** Batch-completed cap checks allow proportional overshoot (`python/packages/core/agent_framework/_tools.py:1348-1351`). Caution sign: any limit enforced only at loop-top after unbounded fan-out.
- **Swallowed cancellation defeating backstops.** User code catching `CancelledError` without `Task.uncancel()` misleads pydantic-ai's counter — documented as deliberate fail-safe policy but still a trap (`pydantic_ai_slim/pydantic_ai/_utils.py:332-368`); `asyncio.shield` around critical sections produces related surprises. Caution sign: cancellation tests that pass only when tools behave.
- **Timeout collapsed into absence.** Mapping timeouts to `null`/empty poisons caches (openhands' `staleTime: Infinity` example, `src/api/llm-balance-service.ts:62-69`). Caution sign: cached values whose refresh path can return "empty" on error.
- **Conflated stop semantics behind one control.** Same button meaning instant-cancel on one backend and cooperative-drain on another without surfaced latency contracts (openhands local-vs-Cloud). Caution sign: support tickets about "stop feels slow" only from one environment.
- **Untunable internals.** agent-framework's MCP poll intervals are module constants with a "promote if need arises" comment (`_mcp.py:322-326`) — fine until someone's slow server needs them. Caution sign: comments deferring configurability with no tracking issue.
- **Attribution by counting.** Known mis-credit path in pydantic-ai (#7240). Acceptable with tracking; dangerous ignored.
- **Silent best-effort remote cancels.** Fire-and-forget cancel without budget, logging, or abandonment naming leaves operators guessing whether remote work died (`python/packages/core/agent_framework/_mcp.py:2599-2605` shows the correct shape: budget + warning + still-raise).

## Notable Absences

- **Six of nine sources could not be evaluated.** `crewai`, `langgraph`, `letta`, `openai-agents-sdk`, `temporal`, and `reports` were empty locally; their reports uniformly recommend materializing checkouts before dispatching dimension tasks and adding harness-level fail-fast preflight for zero-file sources. Several note the specific upstream areas to prioritize post-materialization (e.g., LangGraph's `libs/langgraph/langgraph/pregel/` and `prebuilt/ToolNode`; OpenAI Agents SDK's `src/agents/run.py` and `src/agents/tool.py`). Until re-run, conclusions about the ecosystem are three-source conclusions.
- **No global run timeout anywhere.** All three materialized sources defer whole-run wall-clock bounds to callers (`docs/timeouts.md:18`; absent `timeout=` on `Agent.run`, `python/packages/core/agent_framework/_agents.py:1849-1880`; no scaling settings key in openhands). Notably, pydantic-ai's report proposes `Agent.run(timeout=...)` symmetry as future work.
- **No forced stop with rollback.** Nothing demonstrates terminating sync code or compensating its side effects; pydantic-ai states rollback is absent by design (`docs/agent.md:737-738`). Compensation is left to tool authors.
- **Server-side kill semantics unobserved.** What actually happens when openhands' forwarded bash `timeout` expires (SIGKILL escalation, etc.) lives in a separate repo outside the study boundary — a deliberate evidence gap, not a finding.
- **Provider-side generation cancel reliability.** pydantic-ai documents that remote generation may continue after local stream close and usage accounting on cancel is unreliable (`docs/agent.md:837-839`); no source exposes a hard-stop API for provider-side inference.
- **Step-count masquerading as time.** openhands' settings mention only "Maximum number of agent steps allowed before the conversation stops" (`src/mocks/settings-handlers.ts:390`) — a proxy bound, possibly mock-only, never a wall-clock guard.
- **Streaming cancellation asymmetries.** agent-framework notes a returned `ResponseStream` exposes no `cancel()`, losing inner sibling-cancel benefits; pydantic-ai's `StreamedRunResult.cancel()` stops only the current response, not the run (`pydantic_ai_slim/pydantic_ai/result.py:158-167`) — flagged as the likeliest user confusion in that codebase.
