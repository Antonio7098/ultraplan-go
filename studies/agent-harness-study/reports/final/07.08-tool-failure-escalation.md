## Executive Summary

Every source answers the dimension's guiding question identically: **a failed tool becomes a recovery path, not a dead end**. Each harness converts tool failure into a message that re-enters the model's context — a synthetic `function_result` carrying `"Error: Function failed."` (`python/packages/core/agent_framework/_tools.py:1412-1434`), an error-status `ToolMessage` with "Please fix your mistakes" templates (`libs/prebuilt/langgraph/prebuilt/tool_node.py:108-121`), a formatted `function_call_output` ("An error occurred while running the tool. Please try again…", `src/agents/tool.py:1863-1872`), a `RetryPromptPart` or failed `ToolReturnPart` (`pydantic_ai_slim/pydantic_ai/messages.py:1637-1697`, `:1335-1351`), ReAct Observation prose (`lib/crewai/src/crewai/tools/structured_tool.py:59-63`), a `{status:"error", error, guidance}` envelope posted back into the conversation (`src/services/child-conversation-launch.ts:68-89, 459-497`), or a catchable terminal history event (`service/history/api/respondactivitytaskfailed/api.go:105-121`). Dead ends exist only as deliberate, named exits.

The real differentiation lies in four design decisions. **(1) Where retry authority lives:** server-side and authoritative (temporal, `service/history/workflow/retry.go:31-112`), framework-side engines (langgraph `RetryPolicy`, `libs/langgraph/langgraph/types.py:418-437`; pydantic-ai per-tool budgets, `pydantic_ai_slim/pydantic_ai/tool_manager.py:256-265`; crewai layered counters, `tools/tool_usage.py:109-110`), a consecutive-error circuit breaker inside the invocation loop (agent-framework, `_tools.py:2718-2733`), or nowhere but the model itself (openai-agents-sdk retries only model calls, `src/agents/run_internal/model_retry.py:574-679`; openhands never auto-retries tools). **(2) Default disclosure to the model:** from intentionally generic (agent-framework gates detail behind `include_detailed_errors`) to maximally actionable (langgraph embeds `repr(e)` and full kwargs, `tool_node.py:430`). **(3) Exhaustion representation:** machine-readable stop reasons — temporal's `RetryState` enum (`mutable_state_impl.go:4627-4666`), pydantic-ai's docs-linked `UnexpectedModelBehavior` (`tool_manager.py:262-265`), agent-framework's forced no-tool final answer (`_tools.py:3307-3313`) — versus silent propagation. **(4) Human involvement:** universally pre-execution approvals (agent-framework `_tools.py:1796-1832`; openai-agents-sdk `RunState.approve/reject`, `run_state.py:1255-1294`; pydantic-ai `ApprovalRequired`, `exceptions.py:150-183`; openhands confirmation mode, `conversation-confirmation-buttons.tsx:38-136`) or pull-based operator surfaces (temporal DLQ/Pause APIs, `service/frontend/workflow_handler.go:7166-7228`) — never automatic paging on repeated failures, in any source.

Scores span 7–9. The shared maturity signature is: typed failure taxonomies, errors-as-messages defaults, per-audience observability, and tests pinning exact model-visible strings. The shared residual gaps are: no push-based alerting anywhere in-repo, no cross-run aggregation of failures grouped by cause, and a persistent actionability-vs-leakage tension around raw exception text in model-facing envelopes.

## Core Thesis

Tool failure escalation matures when failure information is treated as **routed data, not an exception**: capture once in a single typed envelope, classify by cause, then fan out to distinct audiences — model, caller/caller-code, end user, operator, retry system — through independent channels whose disclosure levels are configured separately. True control-flow escapes (fatal aborts, human approvals, supervision interrupts) must be *named and protected* exits that ordinary error absorption can never swallow. Every source scoring 8–9 implements this shape; the corpus's lowest score belongs to the source where part of this routing lives outside its audited boundary (openhands' core loop sits in an external agent-server).

Two corollaries recur across sources:

- **Recovery-by-default needs a counterweight.** Absorbing every failure into a benign message hides systemic breakage (agent-framework tradeoff note at `_tools.py:2718-2733`; openai-agents-sdk "silent degradation", `src/agents/run_internal/tool_execution.py:1685-1714` context). Mature designs pair absorption with bounded budgets, breaker trips, handled-vs-fatal span labels, or terminal-failure records so operators can distinguish "model recovering" from "deployment incident."
- **Escalation to humans is a state machine, not a callback.** Approvals serialize into resumable state (openai-agents-sdk `RunState`, pydantic-ai `DeferredToolRequests`, langgraph checkpointed `GraphInterrupt`, agent-framework approval snapshots at `_tools.py:2109-2140`), because a human decision may arrive minutes later, after a process restart.

## Approach Models

Normalized into the dimension's vocabulary (failure taxonomy → envelopes → audience routing → retry/exhaustion → human escalation):

- **agent-framework — "fail-open envelope with gated disclosure."** Ordinary exceptions become terminal `function_result` content with an `exception` metadata field; disclosure is config-gated (`include_detailed_errors`, default generic text, full exception logged operator-side). Enforcement middleware escapes via a protected control-flow trio (`MiddlewareTermination` graceful, `MiddlewareFailure` fatal fail-closed cancelling siblings, `UserInputRequiredException` carrying HITL payloads — `python/packages/core/agent_framework/_middleware.py:85-118`). A consecutive-error circuit breaker forces `tool_choice="none"` and one final no-tool call (`_tools.py:96, 2718-2733, 3299-3300`). MCP gets transport-aware single-reconnect retry and side-effect-safe task abandonment (`_mcp.py:2096-2160, 2243-2256`).
- **crewai — "declarative failure object + scoped reaction policy."** Tools declare failure by *returning* a frozen `ToolFailure(message, reason, code, retryable, details)`; detection is strictly declarative, never heuristic (`tools/tool_failure.py:154-162`). A four-scope policy chain (tool → task → agent → crew → default `warn`) decides record-and-continue versus abort-with-`ToolExecutionFailedError`, the latter protected by `_passthrough_exceptions` so retry handlers cannot swallow it (`agent/core.py:141`; test `tests/tools/test_tool_failure.py:741-764`).
- **langgraph — "layered policy objects across two granularities."** Tool-call granularity uses the `handle_tool_errors` union type (bool/str/callable/type/tuple, `tool_node.py:749-753`) with signature-inferred handled types (`:444-507`); node granularity uses declarative `RetryPolicy` dataclasses with cause-classified `retry_on` (`types.py:418-437`). Retry exhaustion escalates to dedicated error-handler nodes injected with a structured `NodeError(node, error)` (`errors.py:148-165`; `pregel/_algo.py:1110-1240`), and all failures persist as `__error__` channel writes so they survive resume (`pregel/_runner.py:594-603`).
- **openai-agents-sdk — "formatter pipeline with named opt-outs."** One shared catch/format/log/span machinery wraps every function tool regardless of origin (`tool.py:698-756`); `failure_error_function=None`, `timeout_behavior="raise_exception"`, and default-fatal `tool_not_found` are each explicit, documented switches (`docs/tools.md:521-606`). Run-wide `tool_error_formatter` handles `approval_rejected`/`tool_not_found` kinds with fallback-to-default if it misbehaves (`run_config.py:83-105`; `run_internal/tool_execution.py:1275-1295`).
- **openhands — "errors-as-events display escalation."** Failures arrive on the same WebSocket event stream as normal work, so they replay, dedupe, and persist like successes; display is dual-channel (inline cards for agent/tool errors, banner above composer for conversation/server errors, `src/hooks/use-handle-ws-events.ts:35-39`). Client-executed tools never reject: failures become `{status:"error", error, guidance}` envelopes handed back to the model (`child-conversation-launch.ts:499-528`). A normalized verdict function maps 16 observation kinds onto `success | error | timeout` (`get-observation-result.ts:22-69`).
- **pydantic-ai — "two-envelope model with split budget semantics."** `ModelRetry` produces a budget-consuming `RetryPromptPart` ("Fix the errors and try again."); `ToolFailed` produces a terminal failed `ToolReturnPart(outcome='failed')` that consumes no budget (`exceptions.py:57-147`; `docs/retries.md:99`). One `outcome` field ('success'/'failed'/'denied'/'interrupted') is the provider-abstraction seam — Anthropic `is_error`, Bedrock `status='error'`, JSON `{"error": ...}` framing elsewhere (`messages.py:1347-1350`; pinned in `tests/test_tool_failed_wire.py:291-316`). Control flow (`CallDeferred`, `ApprovalRequired`, denial) bypasses retry accounting entirely.
- **temporal — "authoritative central retry gate over one persisted envelope."** Every failure class (worker-reported, timeout, determinism, Nexus termination) is captured in `failurepb.Failure` (`common/failure/failure.go:14-46`), persisted with an explicit `RetryState`, and routed by one decision point: pure retryability classifier + backoff math either reschedules or declares exhaustion with a machine-readable reason (`RETRY_STATE_MAXIMUM_ATTEMPTS_REACHED/TIMEOUT/NON_RETRYABLE_FAILURE`, `service/history/workflow/retry.go:31-112`). Oversized failures wrap as `ServerFailure{Cause: truncated-original}` preserving diagnosability under storage limits (`mutable_state_impl.go:7217-7238`).

## Pattern Catalog

### P1. Errors-as-messages (recovery-by-default)

- **Problem:** a crashing tool otherwise kills the run or strands the model mid-task.
- **Demonstrated by:** all seven sources — this is the corpus's strongest convergence.
- **Why it works:** the model is often the cheapest repair agent; feeding the failure back as ordinary context lets it fix arguments, pick another tool, or answer without it (langgraph default wiring constructs ToolNode with the recovery handler at `chat_agent_executor.py:558-561`; openai-agents-sdk makes this zero-configuration, `src/agents/tool.py:2516`).
- **Copy when:** building any agent loop with model-invoked tools. It is now table stakes.
- **Risky when:** applied without bounds — a permanently broken tool yields endless error-message turns unless paired with budgets/breakers (P3) or terminal outcomes (P6).
- **Evidence:** agent-framework `_tools.py:1549-1574`; crewai `tools/tool_usage.py:708-736`; langgraph `tool_node.py:1005-1012`; openai-agents-sdk `tool.py:653-667`; openhands `child-conversation-launch.ts:459-497`; pydantic-ai `messages.py:1699-1721`; temporal `api.go:105-121`.

### P2. Audience-stratified disclosure (per-consumer redaction boundaries)

- **Problem:** the model, logs/traces, hooks, and end users need different amounts of failure detail, and one leaky channel contaminates all.
- **Demonstrated by:** agent-framework (config-gated model detail, type-names-only across hook boundaries, full strings only in operator logs — `_tools.py:1426-1428`, `_agent_hooks.py:1448-1465`); openai-agents-sdk (independent log/trace/model policies; `OPENAI_AGENTS_DONT_LOG_TOOL_DATA` defaults True, `_debug.py:12-28`; trace strings replaced by "Error details are redacted.", `util/_tool_errors.py:5-14`); temporal (internal errors masked behind a correlation hash shared with support flows, `common/rpc/interceptor/mask_internal_error.go:67-87`); openhands (analytics carry kind/source/error_id but never raw messages, `error-handler.ts:22-45`); crewai (parse failures report empty tool_name so model output never enters a metrics dimension, `tool_usage.py:925-929`).
- **Why it works:** disclosure becomes a routing decision rather than an accident of where `str(e)` happened to be printed.
- **Copy when:** any deployment handling sensitive payloads or multi-tenant users.
- **Risky when:** enforced unevenly — agent-framework's DevUI streams full `str(e)` to the browser contrary to its own core posture (`devui/.../_executor.py:324-326`); langgraph and openai-agents-sdk embed raw exception text model-side with no redaction hook (`tool_node.py:430`; `tool.py:1872`).
- **Evidence:** see inline citations above.

### P3. Exhaustion-as-data

- **Problem:** "the loop gave up" must be distinguishable from "policy forbids retry" and "deadline passed," both for the caller and for operators.
- **Demonstrated by:** temporal's `RetryState` enum traveling alongside the failure in the terminal event (`mutable_state_impl.go:4627-4666`, backoff decision at `retry.go:43-111`); agent-framework's circuit breaker logging a warning, forcing `tool_choice="none"`, and synthesizing a fallback assistant message when the budget expires without content (`_tools.py:2729-2733, 2013-2036`); pydantic-ai's exhaustion message naming tool, count, and remediation docs URL (`tool_manager.py:256-265`); crewai's iteration-cap recovery injecting `force_final_answer` instead of dying (`utilities/agent_utils.py:376-433`).
- **Why it works:** machine-readable stop reasons let callers branch programmatically and let dashboards separate rate (retries happening) from slope (activities dying) — temporal ships exactly this metric pair (`activity_task_fail` incl. retries vs `activity_fail` terminal, `common/metrics/metric_defs.go:980-990`).
- **Copy when:** any long-running or production system; exhaustion should be a queryable fact.
- **Risky when:** the reason enum is incomplete — temporal's `RETRY_STATE_PAUSED` path is still commented out (`mutable_state_impl.go:6925-6927`), so paused stalls masquerade as IN_PROGRESS.

### P4. Control-flow ≠ failure (protected escape hatches)

- **Problem:** if everything is absorbed into error messages, legitimate control flow (approvals, supervision, deliberate aborts) gets swallowed too.
- **Demonstrated by:** agent-framework's trio of never-converted exceptions with `MiddlewareFailure` cancelling in-flight siblings (`_middleware.py:85-137`); langgraph's `GraphBubbleUp` always re-raised before tool handlers and retry logic (`tool_node.py:973-983`; `pregel/_retry.py:618-634`); crewai's passthrough tuple excluding `ToolExecutionFailedError` from five historically swallowing retry handlers (`agent/core.py:141`; adversarial test `tests/tools/test_tool_failure.py:741-764`); pydantic-ai recording deferrals as span attributes rather than span errors (`capabilities/instrumentation.py:452-471`); openai-agents-sdk re-raising `AgentsException` subclasses untouched at the run boundary (`run_internal/tool_execution.py:1839-1852`).
- **Why it works:** fail-open recovery and fail-closed enforcement coexist because the escape hatches are typed, named, and tested against accidental absorption.
- **Copy when:** you add guardrails, approvals, or HITL alongside error-absorption — which is essentially always.
- **Risky when:** new `try/except Exception` sites appear after the tests were written (crewai mitigates with per-site assertions; nothing else is quite as systematic).

### P5. Policy objects with documented precedence

- **Problem:** "what happens on failure?" must answer per tool, per task, per agent, per run, without a flag explosion.
- **Demonstrated by:** crewai's one attribute name resolved most-specific-wins across five scopes with safe degradation on bad values (`tools/tool_failure.py:177-208`); langgraph's union-type handler plus signature inference making configuration live in ordinary function annotations (`tool_node.py:444-507, 749-753`); pydantic-ai's documented precedence ladder for retry budgets (per-tool → per-toolset → override → per-run → spec → agent-wide, `docs/tools-advanced.md:562-573`); temporal validating policies at ingestion so users get `InvalidArgument` before any execution (`common/retrypolicy/retry_policy.go:103-141`).
- **Why it works:** a small uniform config surface with deterministic resolution beats scattered booleans.
- **Copy when:** failure behavior must vary by scope; validate policy values early.
- **Risky when:** two layers have subtly different semantics — pydantic-ai tracks an acknowledged output-vs-tool budget mismatch as issue #5238 rather than papering over it (`tool_manager.py:855-862`).

### P6. Cause-classified taxonomies feeding grouping

- **Problem:** "failures happen" is not actionable; operators need them grouped by cause, and models benefit from cause-specific coaching.
- **Demonstrated by:** crewai's six-value `ToolFailureReason` with a test asserting every member is actually produced (`tools/tool_failure.py:35-54`; `tests/tools/test_tool_failure.py:1577`); openai-agents-sdk's blame-oriented hierarchy — model-caused (`ModelBehaviorError`), developer-caused (`UserError`), operational (`ToolTimeoutError`), safety (guardrail tripwires) — `src/agents/exceptions.py:434-572`; temporal's expected-vs-unexpected allowlist deciding which failures increment the alarming `service_failures` metric versus informational counters (`request_error_handler.go:119-184`); pydantic-ai's four-value `outcome` separating execution failure from policy denial and interruption (`messages.py:1335-1351`).
- **Why it works:** classification at capture time enables downstream grouping in telemetry without parsing prose.
- **Copy when:** you have more than a handful of failure kinds or any operational on-call duty.
- **Risky when:** classification drifts from reality — crewai's MCP client classifies retryability by substring matching over lowercased messages, so a payload containing "not found" would be misclassified (`mcp/client.py:719-727`); openhands leans on similar substring sniffing (`user-facing-error.ts:53-79`).

### P7. Parallel-batch failure arbitration

- **Problem:** one failing call among concurrent siblings must not mask the root cause, lose sibling results ambiguously, or leak cancellation as success.
- **Demonstrated by:** openai-agents-sdk's ~800-line arbitration: siblings cancelled on first failure, drained within bounded windows, late failures merged by priority (Cancelled < Exception < BaseException) with source attribution `direct`/`cancelled_teardown`/`post_invoke` (`run_internal/tool_execution.py:167-550, 1685-1714`); agent-framework cancelling the batch and settling dangling calls on hosted conversations so the thread isn't rejected next turn (`_tools.py:1606-1641, 2883-2933`); langgraph treating any non-interrupt exception as fatal → cancel peers → panic-rethrow (`pregel/_runner.py:620-696`); temporal's busy-loop guard dropping repeated identical workflow-task failures (`respondworkflowtaskfailed/api.go:72-77`).
- **Why it works:** deterministic attribution prevents nondeterministic crash reports under concurrency.
- **Copy when:** executing multiple tools per turn — even modest fan-out hits these races.
- **Risky when:** the machinery itself becomes the complexity center (openai-agents-sdk explicitly notes the maintenance cost).

### P8. Human escalation as resumable state machine

- **Problem:** a human decision arrives asynchronously; ad-hoc callbacks cannot survive restarts.
- **Demonstrated by:** openai-agents-sdk approvals serializing into `RunState` with sticky decisions and rejection messages that become model-visible output on resume (`run_state.py:1255-1294`); pydantic-ai runs ending with a `DeferredToolRequests` output resumable via `DeferredToolResults`, duplicate `tool_call_id`s failing closed before ambiguous binding (`_tool_execution.py:405-420, 964-1050`); langgraph interrupts checkpointed with stable IDs and replayed via `Command(resume=...)` (`types.py:851-960`; `pregel/_runner.py:582-590`); agent-framework snapshotting pending approvals into session state (`_tools.py:2109-2140`); openhands pausing at `WAITING_FOR_CONFIRMATION` with high-risk alerting and duplicate-submission guards (`conversation-confirmation-buttons.tsx:92-118`).
- **Why it works:** durable state turns human oversight into ordinary workflow rather than a special case.
- **Copy when:** any pre-execution approval requirement exists.
- **Risky when:** resume-time world drift — openai-agents-sdk raises `ModelBehaviorError` if an approved tool vanished between pause and resume unless configured otherwise (`turn_resolution.py:2181-2199`).

### P9. Failure-history hygiene

- **Problem:** failures interact badly with caches, replays, and dedup — a cached transient error becomes permanent; a replayed event double-fires.
- **Demonstrated by:** crewai's cache refusing to store `ToolFailure` objects ("replaying one would make a transient error permanent") plus clearing attributed cache entries on hook-blocked calls (`agents/cache/cache_handler.py:23-41`; `utilities/agent_utils.py:1741-1746`); openhands deduping replayed events by id before non-idempotent side effects (`conversation-websocket-context.tsx:556-568`) and idempotency-ledgering child launches (`child-conversation-launch.ts:510`); langgraph persisting errors as checkpointer writes coercible back to exceptions on resume, with an `ERROR_SOURCE_NODE` marker preventing double-handling (`pregel/_runner.py:594-603`; `_loop.py:751-800`).
- **Why it works:** failure durability and failure idempotency are separate concerns that must both be handled explicitly.
- **Copy when:** you cache tool results, reconnect sockets, or checkpoint runs — i.e., almost always in production.

## Key Differences

**Retry authority location (the deepest divergence).**
Temporal makes the *server* the authoritative retry controller — workers cannot miscount attempts because the decision is a deterministic part of history (`service/history/workflow/mutable_state_impl.go:6868-6959`). Langgraph and pydantic-ai put engines in the framework (node-level `RetryPolicy` at `libs/langgraph/langgraph/pregel/_retry.py:573-838`; per-tool budgets at `tool_manager.py:155-167`). CrewAI scatters independent counters across four layers (parse, guardrail, task `max_retry_limit=2`, MCP transport) that do not share budgets (`tools/tool_usage.py:109-110`; `agent/core.py:255-258`; `mcp/client.py:688-739`). Agent-framework deliberately refuses blanket tool retries, bounding total work instead (`max_iterations`=40, consecutive-error cap=3, `_tools.py:95-104`). Openai-agents-sdk and openhands delegate tool retry entirely to the model or the human — a transient network blip costs a full model turn (`src/agents/lifecycle.py:70-103` shows no error hook exists to intercept it). This maps to product shape: infrastructure (temporal) owns correctness; libraries optimize simplicity; frontend (openhands) keeps side-effect control server-side.

**Default disclosure level.**
Agent-framework minimizes model-facing detail by default (generic `"Error: Function failed."`, detail opt-in via `include_detailed_errors`, `_tools.py:1426-1428`) — trading recovery speed against leakage risk. Langgraph maximizes it (templates plus `repr(e)` plus full kwargs, `tool_node.py:108-121, 430`) — trading leakage safety against immediate repair ability. Openai-agents-sdk sits between ("Please try again. Error: {str(error)}"), documenting custom formatters as the remedy but enforcing nothing (`tool.py:1863-1872`; `docs/tools.md:589-594`). Pydantic-ai splits by channel kind: validation details flow on retry prompts; terminal failures carry what happened without instructions. Notably, langgraph filters validation errors down to only the arguments the model controls, scrubbing injected values (`tool_node.py:510-563`) — a third way: detailed but scoped.

**What consumes the retry budget.**
Pydantic-ai is alone in giving developers a first-class choice: retry prompts consume the per-tool budget while terminal failed outcomes don't (`docs/retries.md:99`), with a subtle consequence — a tool that always fails loops forever unless run-level `UsageLimits` are set. Agent-framework counts failing *batches*, not calls, toward its breaker (`_tools.py:2718-2733`), so one large failing batch equals one step. Pydantic-ai also reveals a budget-keying hole: hallucinated tool names get fresh budgets under their invented names, bounded only by whole-run request limits (`docs/retries.md:37`). CrewAI's mixed parse+execution counter means a flaky tool and a malformed call compete for the same slots (`tool_usage.py:711-736`).

**Enforcement posture.** All sources are fail-open by default for ordinary tools; they differ in what triggers fail-closed. Agent-framework: enforcement middleware failure. CrewAI: user-selected `raise` policy. Langgraph: unhandled exception types escaping the configured handler set (`tool_node.py:383-391`). Openai-agents-sdk: timeouts (opt-in mode), disabled-tool misuse, malformed-model-behavior defaults. Temporal: undeliverable oversized messages terminate outright (`respondworkflowtaskfailed/api.go:88-101`), and canceled/terminated activities are never retried (`common/retrypolicy/retry_policy.go:27-64`).

**Where the studied logic lives.** Six sources implement escalation in-repo; openhands implements its *display and client-side half* while the model-recovery decision lives in an external SDK — the direct cause of its 7/10, since the harness's central question was unverifiable within the boundary.

## Tradeoffs

- **Generic vs detailed model-facing envelopes.** Agent-framework's generic default avoids leaking internals to the model but can burn the entire 3-attempt error budget on blind retries (a typo'd argument name is invisible; `_tools.py:91` analysis, evidence `_tools.py:1426-1428`). Langgraph's `repr(e)` approach maximizes repair speed but leaks filesystem paths and internals into transcripts with no redaction hook (`tool_node.py:430`). Best-fit: generic for untrusted multi-tenant inputs; detailed-plus-scoping (langgraph's validation filter, `tool_node.py:510-563`) for developer-owned tools. Failure mode of the middle road (openai-agents-sdk): sensitive payloads reach the model whenever tool authors forget to customize (`docs/tools.md:589-594` documents but does not enforce).
- **Framework-side retries vs model-mediated recovery.** Automatic retries (temporal, langgraph, pydantic-ai, crewai-MCP) resolve transient blips cheaply but risk double-executing side effects; temporal manages this with worker-supplied `NextRetryDelay` overrides and pause-aware absorption (`retry.go:48-67`; `mutable_state_impl.go:6906-6928`) and agent-framework refuses to resubmit long-running tasks before a `task_id` is known (`_mcp.py:2243-2246`). Model-mediated recovery (openai-agents-sdk, openhands) is side-effect-safe and simple but costs tokens and latency per blip. Openai-agents-sdk's own future-work note proposes exactly the missing middle: a `ToolRetrySettings` with replay-safety vetoes analogous to its model-layer ones.
- **Tolerant warn-defaults vs strict raise-defaults.** CrewAI finishes runs "successfully" with failures attached and pushes verification onto callers via `TaskOutput.has_tool_failures` (`tasks/task_output.py:50-61`; doc warning at `docs/edge/en/concepts/tools.mdx:437-439`) — availability-friendly, but silent-tolerant defaults burden anyone who forgets to check. Everyone else fails visibly at exhaustion instead.
- **Rich arbitration machinery vs simple teardown.** Openai-agents-sdk buys precise failure attribution under concurrency at ~800 lines of draining/priority/merge code (`tool_execution.py:167-550`); langgraph's simpler "cancel peers, rethrow first" loses successful siblings' writes for that step (`_runner.py:620-696`). Choose by how much concurrency-attributed forensics you need.
- **Dual implementations kept aligned by discipline.** Temporal's legacy vs CHASM retry paths (`chasm/lib/activity/activity.go:1369` cross-reference) and crewai's three execution stacks aligned by mirroring comments and parity tests (`utilities/tool_utils.py:95-96`) both show migration-in-place honesty — and both are standing drift risks that shared modules would retire.
- **Privacy vs debuggability.** Temporal masks internal errors behind a hash requiring manual log correlation (`mask_internal_error.go:76-86`); openhands strips raw messages from analytics entirely (`error-handler.ts:22-45`). Both preserve privacy at the cost of slower diagnosis; the hash-correlation pattern is the better compromise of the two.

## Decision Guide

1. **Choosing a default failure disposition:** start with errors-as-messages (universal baseline). Add framework-side retries only for provably idempotent operations or with replay vetoes (temporal's classifier whitelists schedule-to-start/close timeouts only via explicit prefix, `retry_policy.go:27-64`; openai-agents-sdk separates `approve_unsafe_replay` from `retry=True`, `retry.py:123-129`). If your tools are heavily side-effecting and idempotency is unclear, adopt the openai-agents-sdk/openhands posture: no tool retries, model-mediated recovery only.
2. **Choosing a disclosure default:** if prompts may contain sensitive data, gate detail (agent-framework style) or scope it (langgraph-style validation filtering). If tools are developer-authored and internal, detailed-by-default maximizes recovery. Either way, keep operator channels richer than model channels, and apply one redaction policy per consumer — not one global flag.
3. **Representing exhaustion:** prefer explicit stop reasons over bare raises. If you have durable storage, follow temporal (persisted `RetryState` in history); if not, pydantic-ai's docs-linked exception messages are the lightweight equivalent. Always separate "gave up" from "policy forbids."
4. **Bounding misbehavior:** combine a per-tool budget with a run-level bound. Learn from pydantic-ai's hole: key budgets such that invented tool names cannot mint fresh ones, and add a consecutive-error breaker (agent-framework) as the coarse backstop.
5. **Adding human oversight:** implement approvals as serialized, resumable state with stable IDs (P8) from day one; retrofitting durability onto callbacks is painful. Decide rejection-message semantics up front — openai-agents-sdk turning a rejection into model-visible output is the pattern that closes the loop.
6. **Operating it:** ship attempt-level and terminal-level metrics separately (temporal), label handled vs fatal failures distinctly (openai-agents-sdk's "(non-fatal)" span labels, `tool.py:2679-2680`), and emit cause tags captured at classification time rather than parsed from message text later.

## Practical Tips

- Pin exact model-visible error strings in tests — agent-framework asserts both generic and detailed modes (`tests/core/test_function_invocation_logic.py:3274-3408`) and pydantic-ai pins wire framing across providers (`tests/test_tool_failed_wire.py:291-316`); this is cheap and prevents regressions in the most user-visible surface you have.
- Write adversarial tests asserting your abort/fatal paths survive your own broad `except` handlers (crewai's passthrough suite, `tests/tools/test_tool_failure.py:741-764`); every framework that added retries later needed exactly this.
- Never cache failures next to successes (crewai `cache_handler.py:23-41`); dedupe replayed events before side effects (openhands `conversation-websocket-context.tsx:556-568`).
- Give unknown-tool errors the list of valid tools — done independently by langgraph (`tool_node.py:1268-1279`), pydantic-ai (`tool_manager.py:496-517`), and crewai (`translations/en.json:52`) — and consider pydantic-ai's refinement of saying "not available yet: search/load first" so the model takes a recovery action rather than concluding the tool doesn't exist (`tool_manager.py:519-550`).
- Make your formatter/hook layer defensive: openai-agents-sdk falls back to default messages when an application formatter throws or returns non-strings (`tool_execution.py:1275-1295`), though notably its inner per-tool wrapper lacks the same guard — mirror the guarded version.
- Record deferrals/approvals as non-error signals in tracing (pydantic-ai span attributes, `instrumentation.py:452-471`) so dashboards don't count normal HITL flow as incident volume.
- When truncating failures for storage, preserve the retryability flag through truncation (temporal `failure.go:69-81`) — losing it silently corrupts downstream retry decisions.
- Surface a structured verdict function early (openhands' `getObservationResult`, `get-observation-result.ts:22-69`) so UIs, exports, and grouping share one truth about what counts as failure.

## Anti-Patterns / Caution Signs

- **Dead metadata flags.** crewai's `ToolFailure.retryable` and openhands' `classification.retryable` are produced but consumed by nothing (`tool_failure.py:95-98` producers only; banner actions string-match literal connection text instead, `chat-interface.tsx:589-593`). Caution sign: classification fields that exist to satisfy schema, not behavior.
- **String-matching classifiers.** Substring checks over error text for retryability/auth/network classification (crewai `mcp/client.py:719-727`, openhands `user-facing-error.ts:53-79`, `probe-mcp-server-health.ts:22-23`) break silently when upstream wording changes. Caution sign: `lower().contains(` near a retry decision.
- **Parallel pipelines aligned only by comments/tests.** crewai's three duplicated detect→record→emit stacks; temporal's legacy/CHASM twins; agent-framework's per-layer independent redaction implementations. Caution sign: comments like "Mirrors the native paths…" — extract shared code before the copies diverge.
- **Unrecognized input defaulting to success.** An unknown observation kind in openhands reads as `"success"` (`get-observation-result.ts:67-68`); misconfigured tool filters in agent-framework produce confusing model-facing "not found" messages instead of loud config errors (`_tools.py:1502-1505`). Caution sign: default-to-success enums and pass-through unknown-name paths.
- **Formatter crashes masking original errors.** openai-agents-sdk's per-tool wrapper has no inner try around the formatter, so a buggy customizer replaces the real failure (`tool.py:653-667`); its run-level counterpart is properly guarded — inconsistent robustness between two formatter layers is itself a smell.
- **Unbounded quiet loops.** pydantic-ai's terminal `ToolFailed` consumes no budget (deliberate, but requires `UsageLimits` discipline, `docs/retries.md:99`); openhands' WS reconnect defaults to Infinity attempts while the circuit breaker covers only REST probes (`use-websocket.ts:113-114`). Caution sign: any "recoverable forever" path without an adjacent counter.
- **Memory-of-one breakers.** crewai's repeated-usage guard compares only the immediately previous call, so alternating A,B,A,B evades it until iteration caps bite (`tool_usage.py:784-789`). Caution sign: loop detection with O(1) memory.
- **Legacy paths outside the envelope.** crewai's delegation tools still return bare error strings that never join the record stream (`base_agent_tools.py:88-124`), so runs can look clean while delegation repeatedly failed. Caution sign: error paths predating the taxonomy.

## Notable Absences

Across all seven sources, none were found to have:

- **Push-based operator alerting** (webhooks, pagers, metrics-export rules wired in-repo). Every source delegates notification to whatever consumes its logs/traces/metrics — explicitly searched and absent in agent-framework (`on_error`/`alert` search), langgraph (zero otel/prometheus production hits), openai-agents-sdk, pydantic-ai, temporal, and openhands. This is the corpus's single most universal gap.
- **Automatic human escalation on repeated failure or retry exhaustion.** Humans are engaged pre-execution (approvals) or pulled via surfaces (DLQ merge/delete, Pause/Reset APIs, dismiss buttons, resume-after-pause); no source pages anyone because a tool kept failing. Temporal comes closest operationally with `task_terminal_failures` metrics feeding DLQ workflows, but the paging loop is external.
- **In-core cross-run aggregation of failures grouped by root cause.** Classification exists everywhere (P6); clustering/counting beyond a single run or batch does not — it is uniformly left to telemetry backends. Langgraph's own report suggests run-end cause summaries as future work.
- **Per-tool retry configuration for ordinary tools** in agent-framework Python (only MCP has fixed reconnect behavior) and openai-agents-sdk (none at all); openai-agents-sdk additionally lacks an `on_tool_error` lifecycle hook (`lifecycle.py:70-103` covers start/end only).
- **Cause attributes in some telemetry:** crewai's spans record tool name but not failure reason (`telemetry.py:666-694`), so operators cannot distinguish rate-limits from schema mismatches without replaying events.

## Per-Source Notes

- **agent-framework (8).** The most formally specified source: a normative spec maps every error behavior to named tests (`docs/specs/004-python-function-calling-loop.md:317-343, 516-560`). Distinctive mechanisms: occurrence-aware correlation so error results never attach to the wrong logical call after replays, service-managed conversation settlement of dangling calls on abort (`_tools.py:2883-2933`), and side-effect-safe MCP task abandonment. Weaknesses: no configurable retry policy for ordinary tools, DevUI contradicting the redaction posture, .NET loop outsourced to external M.E.AI and unverifiable in-tree.
- **crewai (8).** Richest *declarative* model: failures are returned objects, not raised errors, with a five-scope policy chain and ~90 dedicated tests including concurrency isolation. Distinctive: ContextVar-scoped collectors for concurrent executions on shared agents (`tool_failure.py:260-285`), fuzzy `SequenceMatcher` tool-name rescue (>0.85), model-tier-adaptive retry counts. Weaknesses: dead `retryable` flag, telemetry without reason attributes, triple-duplicated execution pipelines, legacy delegation tools outside the envelope.
- **langgraph (8).** Only source with a *first-class post-exhaustion escalation target*: graph-wired error-handler nodes receiving `NodeError(node, error)` that can repair state or route via `Command`, proven to survive checkpoint resume (`tests/test_retry.py:2009-2397`). Distinctive: signature-driven handler typing, interceptor onion (`wrap_tool_call` execute-callable invocable multiple times), timeouts modeled as retryable via deliberate subclass avoidance (`errors.py:190-199`). Weaknesses: `repr(e)` leakage, observability flowing through private server-only config keys, sync nodes unable to time out.
- **openai-agents-sdk (9).** Deepest defense-in-depth: redaction defaults across logs/traces, traceback-chain scrubbing from redacted exceptions (`exceptions.py:315-405`), schema-aware error encoding (`{"error": ...}` for programmatic callers), and the corpus's most rigorous parallel-failure arbitration with provenance labels. Distinctive: replay-safety vetoes decoupled from retry decisions; approvals as serialized sticky-decision state. Weaknesses: no tool-level retry, no `on_tool_error` hook, unguarded inner formatter path, aggregate metrics absent.
- **openhands (7).** Studied as the frontend mirror; its value here is UX-pattern evidence — errors as durable replayable events, sticky-vs-transient error memory in the store (`error-message-store.ts:4-9`), keyboard-first confirmation, jittered reconnects, persisted backend circuit breaker, and consent-gated analytics without raw payloads. Its low score reflects boundary limits (core loop external), heuristic classification, and an unconsumed `retryable` flag — not absent escalation design.
- **pydantic-ai (9).** Cleanest conceptual model: two wire envelopes × provider-native error channels × split budget semantics, all centralized in `ToolManager` with cross-provider wire tests. Distinctive: free-first-refusal budgeting (first availability refusal costs nothing so one act of disobedience isn't fatal on default budget 1, `tool_manager.py:587-595`), retry-wins invariant suppressing stale final results, fail-closed duplicate-ID matching, MCP ExceptionGroup splitting keeping protocol errors retryable. Weaknesses: hallucinated-name budget minting, unbounded terminal-failure loops, acknowledged #5238 budget mismatch.
- **temporal (9).** Infrastructure-grade reference: one proto envelope for every failure class, server-authoritative deterministic retries, exhaustion-as-data, masking-with-hash-correlation, truncation preserving semantic flags, and the corpus's only metrics that separate attempt-rate from terminal-slope. Distinctive: policy validation before execution, pause-aware retry absorption, DLQ workflows for internal tasks. Weaknesses: pull-only human escalation, `RETRY_STATE_PAUSED` unfinished, dual implementation drift risk, no push notifications.

## Open Questions

- **Cross-language parity claims:** agent-framework's .NET loop is external M.E.AI code whose exception-handling options cannot be cited line-by-line (`dotnet/AGENTS.md` External Dependencies); langgraph's findings cover only the Python runtime (no JS ToolNode exists in-monorepo). Whether advertised equivalence holds is unverified in both cases.
- **openhands boundary question:** where the agent-server converts `is_error` observations into the next LLM prompt — the actual model-recovery mechanism — lives outside the repo and could not be audited.
- **temporal Nexus mapping:** how `failurepb.Failure` on a Nexus operation translates to a remote caller's handler error was not located in inspected files; likely in the callback library or external SDK.
- **crewai platform gap:** whether automatic HITL-on-failure exists in enterprise/platform features referenced by `plus_api.py` (outside the OSS surface studied), and whether the experimental executor copy is slated for promotion or deletion.
- **Disclosure policy posture:** whether openai-agents-sdk considers raw `str(error)` in the default model-facing envelope acceptable for production privacy (docs offer customization; no knob enforces it), and whether agent-framework's `exception` metadata reaches providers verbatim across all ~30 provider adapters (traced only for core + OpenAI-family).
- **Alerting ownership:** given the universal absence of push alerting, which layer *should* own it — harness, platform, or telemetry backend — remains undecided by every source; several list an `on_tool_failure` webhook/callback as future work (pydantic-ai, temporal, agent-framework).
