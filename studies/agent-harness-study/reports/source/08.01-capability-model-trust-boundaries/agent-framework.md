## Summary

Microsoft Agent Framework (MAF) implements a layered, opt-in capability-control model rather than a single monolithic sandbox. The core trust boundary is the **function/tool invocation layer**: tools are advertised to the model as schema declarations, and every execution decision passes through a pipeline of interceptors before any side effect occurs.

The framework's central stance is explicit in both languages: by default, **tools given to an agent execute without user approval** — the developer grants capabilities at registration time (`dotnet/src/Microsoft.Agents.AI/ChatClient/ChatClientAgent.cs:66-68` states "all provided tools are invoked without user approval… these arguments should be treated as untrusted input"; Python's `FunctionTool` defaults to `approval_mode="never_require"`, `python/packages/core/agent_framework/_tools.py:331-332`). On top of that baseline, MAF layers several enforcement mechanisms:

1. **Per-tool risk declaration.** Tools carry `approval_mode`; approval-required calls are converted into `function_approval_request` control-plane content *before execution*, pausing the batch (`python/packages/core/agent_framework/_tools.py:1775-1832`). .NET mirrors this with `ApprovalRequiredAIFunction` wrapping and a `requireApproval=true` default for shell/file tools that refuses to construct an ungated function without an explicit `acknowledgeUnsafe: true` acknowledgment (`dotnet/src/Microsoft.Agents.AI.Tools.Shell/LocalShellExecutor.cs:315-347`).
2. **Standing-approval middleware with anti-forgery.** Session-persisted "don't ask again" rules (`ToolApprovalAgent`, `python/packages/core/agent_framework/_harness/_tool_approval.py:343-418`; .NET `dotnet/src/Microsoft.Agents.AI/Harness/ToolApproval/ToolApprovalAgent.cs:52-108`) are scoped by `server_label` so hosted same-named tools cannot inherit local approvals; inbound approval responses are bound to framework-recorded requests so a model-injected response cannot forge a human approval (`dotnet/src/Microsoft.Agents.AI/ChatClient/ApprovalResponseBindingChatClient.cs:47,158-277`).
3. **Policy middleware over information-flow labels.** An experimental FIDES-style module enforces integrity/confidentiality labels (`PUBLIC < PRIVATE < USER_IDENTITY`) on every tool call, with deny-by-default behavior for unlisted tools in untrusted contexts and an option to convert violations into approval requests (`python/packages/core/agent_framework/security.py:1643-1723`, label hierarchy at `security.py:249-319`).
4. **Untrusted-external-system hardening.** Remote MCP servers are treated as untrusted: tool exposure is allow-listed (`allowed_tools`, `python/packages/core/agent_framework/_mcp.py:447,889-892`), arguments are filtered to schema-derived allowlists, and server-initiated sampling requests are **denied by default** unless an explicit callback approves them (`_mcp.py:1434-1547`).
5. **Sandbox packages as separate opt-ins.** VM-isolated code execution (Hyperlight), interpreter-sandboxed Python (Monty), and Docker-isolated shell with regex policy gating are shipped as distinct packages (`dotnet/src/Microsoft.Agents.AI.Hyperlight/README.md:1-27`; `python/packages/monty/agent_framework_monty/_execute_code_tool.py:167`; `python/packages/tools/agent_framework_tools/shell/_docker.py:260`, policy at `shell/_policy.py:71-123`) — the framework does not pretend the host process is a boundary (`.NET LocalCodeAct README.md:5-14` explicitly says it is *not* a sandbox).
6. **Secrets hygiene.** API keys are wrapped in a `SecretString` whose `__repr__` masks the value (`python/packages/core/agent_framework/_settings.py:52-82`), sensitive payload capture in telemetry is off by default behind `enable_sensitive_data` / `ENABLE_SENSITIVE_DATA` (`python/packages/core/agent_framework/observability.py:771-792`), and OTel tool definitions strip everything except type/name/description/parameters so MCP authorization headers never reach telemetry (`observability.py:2635-2679`). .NET applies redacting telemetry by default unless `EnableSensitiveTelemetryData` opts in (e.g., `dotnet/src/Microsoft.Agents.AI/Memory/Mem0Provider.cs:95`).

Authority separation follows the dimension's key question well: **the model can request power but does not possess it.** The model only emits function-call intents; execution authority lives in host-configured pipelines (`FunctionMiddleware` in Python, `FunctionInvokingChatClient` + delegating chat clients in .NET), human approval flows, and policy middleware. The workflow engine generalizes the same pause/resume primitive (`request_info`/response handlers) so approval requests become durable, checkpointable HITL suspensions (`python/packages/core/agent_framework/_workflows/_agent_executor.py:434-449`; .NET `RequestPort` at `dotnet/src/Microsoft.Agents.AI.Workflows/RequestPort.cs:13-33`).

## Rating

**8 / 10.**

Rationale against the rubric:

- **Clear model with explicit interfaces (7–8 band):** The capability surface is first-class — `approval_mode` per tool (`python/packages/core/agent_framework/_tools.py:316`), `ApprovalRequiredAIFunction` marker types in .NET, declarative YAML approval modes that fail safe to `AlwaysRequire` for unknown values (`dotnet/src/Microsoft.Agents.AI.Declarative/Extensions/McpServerToolApprovalModeExtensions.cs:20-28`), and documented default pipeline order (`dotnet/src/Microsoft.Agents.AI/ChatClient/ChatClientExtensions.cs:52-123`).
- **Tests:** Approval behavior is heavily tested, including adversarial scenarios — forged standing approvals are dropped (`test_tool_approval_middleware_drops_forged_standing_approval`, `python/packages/core/tests/core/test_harness_tool_approval.py:708`), recorded-tool disappearance blocks execution (`:842`), and hosted-server-boundary rules are enforced (`:1224`). A dedicated specification governs the function-calling loop and its approval paths, with a scenario-to-test mapping (`docs/specs/004-python-function-calling-loop.md:17-35`). Shell approval refusal is tested in `dotnet/tests/Microsoft.Agents.AI.Tools.Shell.UnitTests/LocalShellExecutorTests.cs`.
- **Operational safeguards:** Deny-by-default MCP sampling with rate limits and token caps (`python/packages/core/agent_framework/_mcp.py:1492-1547`), invocation budgets (`max_iterations`, `max_function_calls`, `max_consecutive_errors_per_request` — `python/packages/core/agent_framework/_tools.py:1332-1409`), auto-approval iteration caps (`DefaultMaxAutoApprovalIterations = 40`, `dotnet/src/Microsoft.Agents.AI/Harness/ToolApproval/ToolApprovalAgent.cs:55`), and fail-safe AgentHooks behavior that halts runs when enforcement itself fails (`dotnet/src/Microsoft.Agents.AI.AgentHooks/Core/AgentHooksFunctionMiddleware.cs:78,122-134`).
- **Why not 9–10:** The secure posture is largely **opt-in**, not default-on: plain agents run all tools ungated until a developer attaches approval/policy middleware; the strongest module (Python `security.py`) is explicitly experimental; and some boundaries rely on convention (unique tool names to avoid auto-approval collisions) rather than structural enforcement. These gaps keep it out of the "proven under failure or scale everywhere by default" tier.

## Answers to Dimension Questions

**1. What can the agent do?**
An agent can do exactly what its host configures: run chat completions against configured providers, invoke the tools registered via `tools=` / `ChatOptions.Tools` (`dotnet/src/Microsoft.Agents.AI/ChatClient/ChatClientAgent.cs:80-96`; `python/packages/core/agent_framework/_agents.py:819,1505`), use hosted provider-side tools (code interpreter, file search, web search — e.g., `HostedWebSearchTool` added by default in the harness, `dotnet/src/Microsoft.Agents.AI.Harness/HarnessAgent.cs:312-315`), reach MCP servers attached to the agent (`python/packages/core/agent_framework/_mcp.py:447`), read/write files through the opt-in file-access store (`python/packages/core/agent_framework/_harness/_file_access.py`), run skills/scripts through the skills provider (`python/packages/core/agent_framework/_skills.py`), and participate in graph workflows with checkpointing (`python/packages/core/agent_framework/_workflows/`). There is no implicit network, filesystem, or process access granted by the framework itself — those arrive only via registered tools or provider-hosted services.

**2. What can the model only request but not directly do?**
The model never executes anything directly. It emits function-call intents; the invocation layer decides execution. Concretely: (a) calls to `always_require` tools become `function_approval_request` content returned to the caller, not executed (`python/packages/core/agent_framework/_tools.py:1796-1832`); (b) calls to declaration-only tools are surfaced as `user_input_request` for the host to implement elsewhere (`_tools.py:1833-1843`); (c) unknown tool names raise instead of executing when `terminate_on_unknown_calls` is set (`_tools.py:1794-1795`); (d) in .NET, `ApprovalRequiredAIFunction`-marked tools require `ToolApprovalResponseContent` bound to a genuine prior request before dispatch (`dotnet/src/Microsoft.Agents.AI/ChatClient/ApprovalResponseBindingChatClient.cs:158-277`); (e) MCP server-initiated sampling requires host approval (`python/packages/core/agent_framework/_mcp.py:1434-1547`); (f) policy middleware can downgrade any requested call to blocked/approval-required based on labels (`python/packages/core/agent_framework/security.py:2004-2084`).

**3. Where is authority enforced?**
At four chokepoints: (1) the **function-invocation loop** — the single place where model intents become executions (`python/packages/core/agent_framework/_tools.py:1725-1854`; .NET `FunctionInvokingChatClient` inserted by `dotnet/src/Microsoft.Agents.AI/ChatClient/ChatClientExtensions.cs:93-108`); (2) **middleware pipelines** wrapping each of agent-run / function-invocation / chat-call scopes (`python/packages/core/agent_framework/_middleware.py:1006,1093,1166`; .NET `UseFunctionInvocation`/`Use` extensions, pipeline order documented at `dotnet/src/Microsoft.Agents.AI/ChatClient/ChatClientExtensions.cs:52-123`); (3) **host approval flows** persisted in session state (`python/packages/core/agent_framework/_harness/_tool_approval.py:343-418`); (4) the **workflow runtime**, which converts pending approvals/user-input requests into durable pauses matched back via response handlers (`python/packages/core/agent_framework/_workflows/_agent_executor.py:434-449`; `dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs:406-437`). Runtime authority (the framework) is separated from tool authority (each tool's own `approval_mode`/sandbox): the framework cannot be bypassed by a tool declaring itself safe, because the batch classifier reads `tool.approval_mode` from the registry, not from the call (`_tools.py:1763,1787`).

**4. Are dangerous capabilities isolated?**
Yes, through layered mechanisms rather than one kernel boundary. Shell tools refuse ungated construction (`dotnet/src/Microsoft.Agents.AI.Tools.Shell/LocalShellExecutor.cs:341-347`), offer a Docker-isolated variant with policy gating and extra-flag rejection (`python/packages/tools/agent_framework_tools/shell/_docker.py:104-126`), and process-group kill on timeout (`shell/_killtree.py`). Code execution ships in VM-level sandboxes (Hyperlight, with network allow-lists and approval modes — `dotnet/src/Microsoft.Agents.AI.Hyperlight/README.md`) or OS-free interpreters (Monty rejects OS/filesystem/network calls — `python/packages/monty/agent_framework_monty/_execute_code_tool.py:7`). File access is rooted and symlink-rejecting (`FileSystemAgentFileStore`, `python/packages/core/agent_framework/_harness/_file_access.py:1447-1474`), though honestly documented as "not a sandbox" (`:788`). Remote systems (MCP) are quarantined behind allowlists and deny-by-default sampling. Isolation quality varies by package and is always opt-in — the in-process `LocalCodeAct` variant is explicitly flagged as not providing isolation (`dotnet/src/Microsoft.Agents.AI.LocalCodeAct/README.md:5-14`).

> **Can the model request power without possessing power?** Yes — this is the framework's defining property. Model outputs are inert function-call intents; every path to side effects crosses a host-controlled interceptor, an approval record, or a policy gate. The residual power the model *does* possess is choosing among pre-granted capabilities and crafting arguments — which both platforms explicitly classify as untrusted input (`dotnet/src/Microsoft.Agents.AI/ChatClient/ChatClientAgent.cs:66-68`; MCP argument filtering, `python/packages/core/AGENTS.md`).

## Architectural Decisions

1. **Opt-in gating over default-deny.** Both platforms default tools to no-approval (`python/packages/core/agent_framework/_tools.py:331-332`; `dotnet/src/Microsoft.Agents.AI/ChatClient/ChatClientAgent.cs:66-68`), pushing responsibility to developers, while high-risk built-ins (shell, files, skills) invert this with mandatory defaults. This maximizes flexibility but means a naive integration runs fully empowered.
2. **Control-plane content types for approvals.** Approvals are message contents (`function_approval_request`/`function_approval_response`, registered kinds at `python/packages/core/agent_framework/_types.py:373,1273-1313`) rather than out-of-band flags, so they flow through history, streaming, sessions, checkpoints, and workflows uniformly.
3. **Decorator/delegating composition.** Trust enforcement is implemented as composable decorators at every scope (Python middleware tiers; .NET `DelegatingChatClient` chain), letting hosts insert policy between the model and every effect without subclassing agents (`dotnet/src/Microsoft.Agents.AI/ChatClient/ChatClientExtensions.cs:52-123`).
4. **Fail-safe defaults at the edges.** Unknown declarative approval modes → AlwaysRequire (`dotnet/src/Microsoft.Agents.AI.Declarative/Extensions/McpServerToolApprovalModeExtensions.cs:27`); missing MCP sampling callback → deny (`python/packages/core/agent_framework/_mcp.py:1434-1443`); enforcement failure → halt the run (`dotnet/src/Microsoft.Agents.AI.AgentHooks/Core/AgentHooksFunctionMiddleware.cs:78`); symlink/OSError during skill discovery → treat as unsafe (`python/packages/core/AGENTS.md`, `FileSkillsSource` section).
5. **Spec-governed critical region.** The function-calling loop and its approval/replay semantics are protected by a written specification requiring synchronized updates and extra validation, acknowledging that small changes here can duplicate side effects or resurrect stale approval authority (`docs/specs/004-python-function-calling-loop.md:17-35`).

## Notable Patterns

- **Occurrence-aware approval correlation:** `call_id` reuse after completed rounds is handled by matching ordered call occurrences and consuming approved results per occurrence, not per ID (`python/packages/core/tests/core/test_harness_tool_approval.py:45-108` and the AGENTS.md "occurrence-aware" notes).
- **Server-label scoping of approvals:** standing rules embed `server_label` so a same-named hosted tool on another server cannot inherit a local approval (`python/packages/core/agent_framework/_harness/_tool_approval.py:218-234`; test at `test_harness_tool_approval.py:1224`).
- **Anti-confused-deputy design for MCP:** treating the remote server as an adversary — argument allowlisting, sampling denial, `_meta` provenance separation, task double-execution prevention (non-parseable success responses raise rather than fall back, `python/packages/core/AGENTS.md` MCP tasks section).
- **Explicit unsafe opt-outs:** dangerous configurations require naming the risk (`acknowledgeUnsafe: true`, `LocalShellExecutor.cs:48,71,109`; `lambda params: True` to restore legacy MCP sampling auto-approve, `_mcp.py:1492-1494`) — a consent pattern borrowed from security APIs.
- **Honesty annotations:** docs mark what is *not* a boundary (LocalCodeAct, FileSystemAgentFileStore "not a sandbox") alongside what is — rare and valuable for integrators assessing real trust boundaries.

## Tradeoffs

- **Flexibility vs. safe-by-default:** the ungated default keeps simple samples trivial but makes the secure path a deliberate act; the framework compensates with warnings (`ChatClientAgent.cs:66-68`) rather than enforcement.
- **Convention-based identity:** auto-approval rules match by tool name; collisions silently widen permissions unless developers choose unique names (`LocalShellExecutor.cs:331-337`, `ToolApprovalAgentOptions.cs:41-48`). Detection exists (tests forge and drop such approvals), but prevention is not structural.
- **MCP allowlist provenance gap:** runtime kwargs merged into model arguments lose provenance before filtering, so a server declaring a property name receives runtime values (e.g., credentials) even if the model never sent them — documented with mitigations (`python/packages/core/AGENTS.md`, `function_invocation_kwargs` section).
- **Two-platform divergence:** identical concepts have different shapes and defaults (`approval_mode="never_require"` strings in Python vs. `ApprovalRequiredAIFunction` markers + `requireApproval` booleans in .NET; archive-based MCP skills extracted to disk in .NET vs. purely in memory in Python), increasing the cost of reasoning about cross-language trust properties.
- **Experimental core security module:** the most principled mechanism (label-based policy enforcement, `security.py`) is experimental, so production deployments typically fall back to coarser name-based approval rules.

## Failure Modes / Edge Cases

- **Auto-approval name collision:** registering a shell tool under a name approved by another feature's rule bypasses the human approval boundary entirely (`dotnet/src/Microsoft.Agents.AI.Tools.Shell/LocalShellExecutor.cs:331-337`).
- **Stale approval authority replay:** reused `call_id`s could re-authorize different calls; addressed by binding pending policy approvals to body signature + label key + session key (`python/packages/core/agent_framework/security.py:1624-1639`) and occurrence-aware matching — the spec flags this as a regression-prone area (`docs/specs/004-python-function-calling-loop.md:31`).
- **Untrusted session restoration:** a compromised storage backend can rewrite message roles and escalate trust; documented as equivalent to accepting untrusted input (`dotnet/src/Microsoft.Agents.AI.Abstractions/AgentSession.cs:46-52`).
- **Runaway loops:** bounded by `max_iterations`/`max_function_calls`/auto-approval caps (`python/packages/core/agent_framework/_tools.py:1332-1409`; `ToolApprovalAgent.cs:55`), including budget accounting for paused-for-approval executions.
- **Task double-execution:** ambiguous MCP task responses raise instead of retrying to avoid re-running side effects (`python/packages/core/AGENTS.md`, permissive fallback note).
- **Mixed batches:** approval-required and free tools in one model turn pause the whole batch, hiding already-approved siblings until resume — correctness preserved at the cost of latency (`python/packages/core/agent_framework/_tests... _tools.py:1796-1832`; tests at `test_harness_tool_approval.py:418-574`).
