## Summary

The selected source is the OpenHands **Agent Canvas frontend** — a single React/TypeScript SPA that is also published as a re-embeddable npm library (`@openhands/agent-canvas`, see `package.json:2`), bundled as a Docker all-in-one image, and packaged as an Electron desktop app. It is one slice of a multi-repo stack: the actual agent runtime lives in `software-agent-sdk` and is reached only through the `@openhands/typescript-client` SDK (see AGENTS.md "Repository Map"). The frontend is therefore not a "runtime, tools, memory, evals" framework in the traditional sense; it is a UI + service-layer app whose boundaries are organised around **feature domain** (browser, chat, files, settings, sidebar, terminal, automations, backends, MCP, skills, plugins) × **backend kind** (local agent-server vs OpenHands Cloud) × **architectural role** (`api/`, `components/`, `hooks/`, `services/`, `stores/`, `utils/`, `constants/`, `types/`, `i18n/`, `styles/`, `manifests/`, `mocks/`, `routes/`).

The boundary model is **explicit, tested, and enforced by CI**:

- A single-source-of-truth **public API surface** at `src/lib/index.ts:1-57`, re-exported by `src/index.ts:1` and pinned to eight subpath exports in `package.json:206-248` (`.`, `./browser`, `./conversation`, `./files`, `./settings`, `./sidebar`, `./terminal`, `./i18n`).
- A **typed-client-only rule** for agent-server calls: raw `fetch`/`axios` against `/api/...` paths is banned by `src/api/no-direct-agent-server-calls.test.ts:32-79` and `eslint.config.js:252-262` (with a 3-file allowlist at `src/api/no-direct-agent-server-calls.test.ts:7-11`).
- A **cloud proxy rule**: any browser→Cloud call must go through `callCloudProxy()` in `src/api/cloud/proxy.ts:18-39`, which forces the request through `/api/cloud-proxy` on the local agent-server (CORS workaround).
- A **backend-registry singleton** (`src/api/backend-registry/active-store.ts:116-193`) that resolves "which backend am I talking to?" with a publish/subscribe model, typed `Backend` (`src/api/backend-registry/types.ts:4-13`) with a `kind: "local" | "cloud"` discriminant, and a `NO_BACKEND` sentinel for the empty-registry case (`src/api/backend-registry/active-store.ts:22-39`).
- A **library/app build split** enforced by `tsconfig.lib.json:1-34` — only barrel files, the five top-level settings/conversation routes, the i18n subsystem, the query client, and the components tree enter the `npm run build:lib` output. Internal modules like `src/api/`, `src/stores/`, and `src/hooks/` are *not* re-exported.
- **Boundary unit tests** for both the runtime boundary and the published library surface: `src/api/no-direct-agent-server-calls.test.ts`, `__tests__/library-entrypoints.test.ts:1-49` (asserts `publicApi.ConversationView`, `publicApi.AgentServerUIProviders`, etc. are functions), `__tests__/package-library.test.ts:1-158` (asserts `package.json#exports` shape, no git deps, exact-pinned versions).
- **CSS-scope isolation** for embedders: `vite.config.ts:195-214` uses `postcss-prefix-selector` to scope every emitted CSS rule under `[data-agent-server-ui]`, with a custom transform in `src/styles/agent-server-ui-style-scope.ts` to remap global selectors; the public constants (`AGENT_SERVER_UI_SCOPE_ATTRIBUTE`, `AGENT_SERVER_UI_DEFAULT_THEME`, etc.) are re-exported from `src/lib/index.ts:33-41`.

The boundary is **mostly unidirectional** (UI → hooks → services → SDK clients → HTTP), with a few well-contained cross-cuts (the `Backend` discriminant flows through ~20 service files, the `OPENHANDS_I18N_NAMESPACE` flows through every translated component, the `getCachedAgentServerInfo` cache is shared by `agent-server-compatibility.ts` and `agent-server-adapter.ts`). **No circular imports were observed**; the barrel files in `src/components/*/index.ts` are leaf-only re-export points (e.g. `src/components/terminal/index.ts:1` is a single line), and `src/lib/index.ts:1-57` is the only barrel that cross-cuts multiple feature domains.

Modules **can be used independently**: a host app can `import { AgentServerUIProviders, AgentServerUIRoot, ConversationView, TerminalPanel } from "@openhands/agent-canvas"` without pulling in the agent-server, the stores, or the route tree — verified by `vite.config.ts:215-244` (library mode builds `dist/` with `preserveModules: true, preserveModulesRoot: "src"`) and by `tsconfig.lib.json:5-17` (declaration emit only for `src/lib/**`, `src/components/**`, `src/i18n/**`, the five named route files, and `src/query-client-config.ts`).

**Internal APIs are distinguished from public ones** through a three-layer contract:

1. `src/lib/index.ts:1-57` is the single "ship-list" barrel — it chooses the seven feature subpath exports, the providers, the i18n surface, the style-scope constants, and the telemetry public API (`useTelemetry`, `trackEvent`, `setTelemetryConsent`, `getTelemetryConsent`).
2. `package.json#exports` (`package.json:206-248`) maps each subpath to a typed `dist/components/<domain>/index.{cjs,js,d.ts}` triplet with separate `types`/`import`/`require` conditions.
3. `src/api/` services, `src/stores/`, `src/hooks/`, and `src/utils/` are deliberately *not* re-exported from `src/lib/index.ts`. Library consumers that reach for `import { ConversationService } from "@openhands/agent-canvas"` will not get it; they get only what `src/lib/index.ts` surfaces.

## Rating

**8 / 10** — Clear model with tests, explicit interfaces, and operational safeguards.

Rationale: The boundary model meets the rubric's 7-8 band on every dimension.

- **Public vs internal API**: explicit `src/lib/index.ts` barrel + `package.json#exports` + `tsconfig.lib.json` allowlist + `__tests__/library-entrypoints.test.ts` regression coverage. Internal modules are *not* accidentally reachable.
- **Boundary enforcement**: `src/api/no-direct-agent-server-calls.test.ts:32-79` is a file-walking static test that fails CI if anyone adds a raw `axios.get(\`/api/...\`)` or `fetch(\`/api/...\`)` to `src/`. Mirrored by the `no-restricted-imports` rule on `@openhands/typescript-client/client/http-client` in `eslint.config.js:252-262`.
- **Dependency direction**: a single source of truth for client options (`src/api/agent-server-client-options.ts:52-79`) means the only valid HTTP path is SDK-typed clients constructed with that helper. No service reaches around the helper.
- **Independent use**: a host app can `npm install @openhands/agent-canvas` and import `ConversationView` / `TerminalPanel` / `AgentServerUIProviders` without picking up the agent-server, the local backend, MSW mocks, or the route tree (verified by `tsconfig.lib.json:1-19` include list).
- **Cycles**: no clear evidence of circular imports; the barrel files are thin (most `src/components/*/index.ts` files are 1-8 lines).
- **Test discipline**: 43 in-source test/spec files plus ~70 `__tests__/` files cover the boundary surface explicitly.

The score does not reach 9-10 because: (a) `src/api/agent-server-adapter.ts` is 1,297 lines of cross-cutting translation logic (local-model → SDK model + cloud-model hybrid + encrypted-headers + system-message-suffix injection), and (b) the cloud-vs-local branch is hand-written in many services (`src/api/event-service/event-service.api.ts:40-181`, `src/api/conversation-service/agent-server-conversation-service.api.ts:23-46`, `src/api/automation-service/automation-service.api.ts`) rather than hidden behind a single strategy, so the cloud/local seam is *visible* in every cross-cutting service file even though the seam is well-typed. Also, the Vite `manualChunks`-style domain barrels (e.g. `src/components/conversation-events/chat/event-message-components/index.ts:1-8`) intentionally exist for library consumers — internal callers must deep-import (`./messages`, `./event-message-components/<name>`) per AGENTS.md, which is an implicit discipline rather than an enforced one.

## Answers to Dimension Questions

1. **Are modules cleanly separated?**
   Yes, with one well-known cross-cut. The feature/role split is:
   - `src/api/` — backend service layer (twenty-plus service files grouped by domain under per-domain subdirectories, plus `backend-registry/`, `cloud/`, and the compatibility/config/options trio at the root of `api/`).
   - `src/components/` — React tree, organised by feature (`features/backends`, `features/chat`, `features/settings`, `features/mcp-page`, `features/onboarding`, `features/automations`, `features/conversation-panel`, ...) with shared primitives under `components/shared/`, `components/ui/`, and a dedicated `components/providers/` for the embedder-facing wrapper.
   - `src/hooks/` — split by use case: `query/` (TanStack Query data), `mutation/` (writes), top-level `use-*.ts` (stateful side-effecting hooks).
   - `src/stores/` — 24 Zustand stores, each owning a single concern (`browser-store.ts`, `event-message-store.ts`, `conversation-state-store.ts`, ...).
   - `src/services/` — non-React singleton services (`telemetry.ts`, `cloud-funnel-analytics.ts`, `agent-state-service.ts`, `canvas-ui.ts`, `chat-service.ts`, `settings.ts`, `telemetry-context.ts`, `child-conversation-launch.ts`).
   - `src/utils/`, `src/constants/`, `src/types/`, `src/context/`, `src/contexts/`, `src/manifests/`, `src/styles/`, `src/i18n/`, `src/mocks/`, `src/wrapper/` — leaf-level support modules.
   - `src/routes/` — the React Router route table; the only routes that ship in the library are the five named in `tsconfig.lib.json:13-17` (`conversation`, `app-settings`, `llm-settings`, `mcp-settings`, `secrets-settings`).
   The cross-cut is the `Backend` registry: the typed `Backend` discriminant flows through ~25 service/hook files, but the *flow* is unidirectional — the active store pushes `Backend` into typed-client constructors, and SDK responses are translated back to local DTOs in `agent-server-adapter.ts`. There is no two-way coupling: services don't import the active store's `setRegisteredBackends` (only the storage layer does), and UI components read `getActiveBackend()` via the `ActiveBackendContext` provider rather than calling the store directly.
2. **Do dependencies flow in one direction?**
   Yes. The chain is:

## Architectural Decisions

- **Single-source public barrel at `src/lib/index.ts:1-57`.** The barrel is hand-curated (not generated from `src/components/**/index.ts`) and excludes internals by omission rather than by tooling. A spec test (`__tests__/library-entrypoints.test.ts:44-48`) is the closest thing to a contract that the public surface has not silently grown.
- **No internal-but-shared modules are re-exported from the library.** `src/api/skills-service.ts`, `src/api/conversation-service/agent-server-conversation-service.api.ts`, `src/stores/`, `src/hooks/`, `src/utils/`, and the `services/` tree are deliberately not in `src/lib/index.ts`. Library consumers who need them must vendor the source.
- **Per-domain barrels exist for the *library surface* and are *discouraged* in the app code.** AGENTS.md "Bundle/dev-graph hygiene" explicitly states: "Internal callers use deep paths (`./messages`, `./event-message-components/<name>`) so Vite dev doesn't fan out the barrel."
- **Two-backend (local + cloud) abstraction via `Backend` registry.** The `kind: "local" | "cloud"` discriminant is a literal-string union (per the AGENTS.md Rule 3, "discriminated-union tags use string-literal types, not bare strings") and the only piece of state that varies between backends is the host/auth/header bundle. The `NO_BACKEND` sentinel (`src/api/backend-registry/active-store.ts:29-35`) makes the empty-registry case a typed state rather than a thrown exception.
- **`callCloudProxy` indirection for all browser→Cloud traffic.** Cloud hosts do not permit CORS from `localhost`, so the proxy wraps every Cloud call as a server-to-server request. The cloud service files under `src/api/cloud/` are the only consumers; UI code never reaches Cloud directly.
- **SDK as the only HTTP client for agent-server.** `@openhands/typescript-client/clients` is the only sanctioned way to reach `/api/*`, `/server_info`, and `/sockets`. Raw `axios`/`fetch` is banned by the file-walking test in `src/api/no-direct-agent-server-calls.test.ts:32-79` and by `eslint.config.js:264-271`. Three allowlisted files (`automation-service/automation-service.api.ts`, `cloud/proxy.ts`, `main-app-auth.ts`) are documented as exceptions for infrastructure reasons.
- **Library/app build split at the TypeScript level.** `tsconfig.lib.json:1-34` is the only configuration that knows which files belong to the library; `tsconfig.json:1-36` is the app-wide project. There is no `tsconfig.test.json` — tests are run by Vitest on the same source files but excluded from declaration emit.
- **CSS isolation at build time.** `postcss-prefix-selector` rewrites every emitted selector under `[data-agent-server-ui]` (`vite.config.ts:195-214`). The `transformAgentServerUISelector` helper handles the global `:root`/`html`/`body` exception so the CSS is portable to a host page without leaking into the host's own stylesheet.
- **Constants for the shared, hidden things.** Module-private constants like `LOCK_TO_CLOUD_WINDOW_KEY` in `src/api/agent-server-config.ts:14` are declared `const` (not `export const`) so they can only be read by their own file. The AGENTS.md "No Magic Strings" Rule 2 forces every string the program reads (storage keys, query keys, event names, route paths, env vars) to live in a single named constant; `eslint.config.js:351-368` enforces the no-literal-translation-keys and no-raw-settings-query-keys halves of the rule.

## Notable Patterns

- **Object-literal services for stateless APIs.** `src/api/skills-service.ts:67` defines `export const SkillsService = { getSkills: async () => { ... } }` and is consumed as `SkillsService.getSkills()`. Lightweight, no constructor, no `this`.
- **Class services with `static` methods for per-conversation state.** `src/api/conversation-service/conversation-service.api.ts:16-77` uses `class ConversationService { static currentConversation: AppConversation | null; static setCurrentConversation(...); static getVSCodeUrl(...); static uploadFiles(...) }` because the per-conversation `session_api_key` is needed for VS Code URL + file upload.
- **Same class service, cloud-vs-local branch at call time.** `src/api/event-service/event-service.api.ts:40-181` branches on `getActiveBackend().backend.kind === "cloud"` and dispatches to `callCloudProxy` or `new ConversationClient(getAgentServerClientOptions(...))`. The branch is hand-written per method, with a comment block at lines 18-38 explaining the rationale.
- **Hooks wrap services, never the other way around.** `src/hooks/query/use-skills.ts` consumes `SkillsService` via `useQuery`; `src/hooks/mutation/use-save-llm-profile.ts` consumes a settings mutation via `useMutation`. The `src/api/README.md:64-89` doc block mandates the layering.
- **Centralised query-key helpers per concern.** `src/hooks/query/query-keys.ts:8-73` defines `SETTINGS_QUERY_KEYS`, `LLM_PROFILES_QUERY_KEYS`, `AGENT_PROFILES_QUERY_KEYS`, `PROVIDER_CONNECTIONS_QUERY_KEYS`, `LLM_SUBSCRIPTION_QUERY_KEYS`, `LOCAL_WORKSPACES_QUERY_KEYS`, `PLUGINS_QUERY_KEYS`, `SETUP_QUERY_KEYS`, plus a `QUERY_KEYS` namespace for non-domain-specific keys. `eslint.config.js:351-358` rejects raw `["settings", ...]` literals in `queryKey` to enforce the pattern.
- **`agent-server-adapter.ts` is the only cross-cutting translation module.** Everything that does local-DTO ⇄ SDK-DTO conversion, encrypted settings, system-message-suffix injection, or ACP-vs-litellm agent discrimination lives there. This is intentional centralisation — alternatives would be a `mapper` directory per service.
- **Per-domain barrel + per-domain `index.ts` for the library surface.** Each library-shipped feature has exactly one barrel file under `src/components/<domain>/index.ts`, which is what `src/lib/index.ts:1-6` and `package.json:212-241` re-export.
- **Lazy-loading the embed-only surface.** `AlertBanner`, `CommandMenu`, `SettingsModal`, the `Terminal` tab, and `AgentServerUIRoot` are all `React.lazy(...)`'d so the embed entrypoints ship small initial chunks (per AGENTS.md "Bundle/dev-graph hygiene (Tier 1 cleanup landed)").
- **`/* @__PURE__ */` annotations for tree-shakeable re-exports.** `src/i18n/index.ts:11` re-exports `translationResources` with the annotation, and `src/i18n/resources.ts:43-44` annotates the `buildTranslationResources(...)` call, so the 1 MB `translation.json` is dropped from the standard app build but kept for the `@openhands/agent-canvas/i18n` subpath consumers.

## Tradeoffs

- **`src/api/agent-server-adapter.ts` is 1,297 lines.** It is the only place that does DTO translation, encrypted settings, system-message-suffix injection, and ACP-vs-litellm agent discrimination. Centralising keeps the cloud/local seam in one place, but the file size pushes the team toward "one module to refactor when the SDK shape changes" risk. Mitigation: `__tests__/api/agent-server-adapter.test.ts:1-1776` covers the build-payload paths.
- **`src/api/conversation-service/agent-server-conversation-service.api.ts` is 947 lines** — the entire conversation-create/start/fork/vscode/git-changes pipeline lives in one file, partly because it imports both `agent-server-conversation-service.types.ts` (298 lines) and the cloud conversation service. Reasonable for now, but a future refactor toward per-action files would benefit from a `conversation-service/` sub-package.
- **Cloud-vs-local branch is hand-written in many services.** The pattern (`if (active.kind === "cloud") return callCloudProxy({ ... }); return new ConversationClient(getAgentServerClientOptions({ ... })).method(...)`) repeats in `event-service.api.ts`, `conversation-service.api.ts`, `agent-server-conversation-service.api.ts`, `agent-server-adapter.ts`, `automation-service.api.ts`, etc. A `dispatchByBackend(cloud, local)` helper would compress the pattern, at the cost of one more indirection. Currently the team has chosen explicit dispatch for readability.
- **Library test surface is not exhaustively snapshot-tested.** `__tests__/library-entrypoints.test.ts:1-49` only asserts that seven functions are `typeof "function"` and three constants equal specific values. A consumer that imports `AgentServerUIProviders` and gets a renamed prop would not see a test failure until their app crashes. A typed `.d.ts` round-trip test (build the lib, then re-typecheck against a stub consumer) would catch prop renames, but the codebase does not have one.
- **`src/api/` services are *not* exposed to library consumers.** The trade-off is that library consumers who want to *programmatically* start a conversation (e.g., a host app that wants to pre-populate one) must go around the library surface and instantiate the SDK clients themselves. This is consistent with the "no internal surface leak" principle but is occasionally inconvenient.
- **Per-route import depth in the library build.** `tsconfig.lib.json:13-17` includes `src/routes/conversation.tsx`, `src/routes/app-settings.tsx`, `src/routes/llm-settings.tsx`, `src/routes/mcp-settings.tsx`, `src/routes/secrets-settings.tsx` but excludes the rest of the route tree. A new route that the library wants to expose requires editing `tsconfig.lib.json`; this is intentional (it forces a manual decision about public surface) but can be missed.
- **`src/api/backend-registry/storage.ts` uses `window.localStorage` directly.** A unit test that wants to exercise the registry in jsdom can do so, but a non-DOM environment (e.g., Node SSR) returns `[]` from `readStoredBackends`. The boundary is clearly defined but not abstracted — a `BackendPersistence` interface would be the next step.
- **Module-private constants can drift from runtime values.** `LOCK_TO_CLOUD_WINDOW_KEY = "__AGENT_CANVAS_LOCK_TO_CLOUD__"` in `src/api/agent-server-config.ts:14` is `const`; the matching string in `scripts/static-server.mjs` is a literal. AGENTS.md acknowledges this in a comment, but there is no compile-time check linking the two.

## Failure Modes / Edge Cases

- **Stale session API key in `localStorage`.** The published-binary path injects `__AGENT_CANVAS_SESSION_API_KEY__` via `scripts/static-server.mjs`; if the injection is missed, `makeDefaultLocalBackend()` returns null, the registry seeds empty, and `root.tsx` traps the user behind the "Manage Backends" modal instead of onboarding. Mitigated by `syncLauncherDefaultLocalBackend()` (`src/api/backend-registry/storage.ts:70-93`) and a window-global fallback (`src/api/agent-server-config.ts:119-132`). No automated regression test covers the "published binary with no window global" case end-to-end.
- **Backend-registry fallback in dead-active-backend case.** `pickFallbackBackend` (`src/api/backend-registry/active-store.ts:52-62`) consults the synchronous health store; if the health store is empty (e.g., immediately after a backend removal), the fallback picks the first healthy local backend. The logic is correct but order-sensitive — a future change to "prefer cloud backends" would have to update the test at `__tests__/api/backend-registry/active-store.test.ts:1-263`.
- **Cloud backend that hasn't yet supported the new pagination filters.** `EventService.searchEvents` (`src/api/event-service/event-service.api.ts:117-163`) attempts the full request first and falls back to a limit-only request on failure, logging a warning. The fallback returns `{ items: [], next_page_id: null }` so the UI doesn't loop indefinitely. A future cloud backend that returns a *partial* response without the filter fields would still cause the limit-only retry to return the same already-seen events.
- **`postcss-prefix-selector` for `:root`/`html`/`body`.** These selectors cannot be nested under `[data-agent-server-ui]`; the `transformAgentServerUISelector` helper in `src/styles/agent-server-ui-style-scope.ts` remaps them onto the scoped shell. A future Tailwind upgrade that introduces a new global selector (e.g., `@layer base { :host {} }`) would need a corresponding remap.
- **Library consumer overrides `getDefaultQueryClient` after mount.** `src/components/providers/agent-server-ui-providers.tsx:65-79` uses a `previousProvidersRef` to keep the first-observed client stable across re-renders; if a host app passes a different `QueryClient` on re-render, the resolved client is updated but old query subscriptions are not migrated. This is the documented behaviour but can be surprising.
- **Concurrent `setRegisteredBackends` callers.** `src/api/backend-registry/active-store.ts:164-178` writes synchronously to `localStorage` and recomputes the snapshot, but does not lock against concurrent `getActiveBackend()` readers. In a single-tab SPA this is fine (JS is single-threaded), but a future multi-tab sync would need an explicit ordering protocol.
- **Mocks are excluded from the boundary test but not from the build.** `src/api/no-direct-agent-server-calls.test.ts:6` excludes `mocks` from the source-file walk; however, MSW handlers in `src/mocks/` are still bundled into the `dev:mock` build (`package.json:80`). The library build is unaffected because `tsconfig.lib.json` does not include `src/mocks/`, but the app build does. A consumer who runs `dev:mock` against a real backend would see MSW swallow the traffic — `src/mocks/should-start-mock-worker.ts` is the gatekeeper and assumes `VITE_MOCK_API=true`.
- **Electron `node` PATH bridging.** The first attempt (wrapping `node`/`npm`/`npx` with thin shell scripts that ran Electron-as-Node) was abandoned in favour of bundling a real Node.js distribution (`scripts/download-node.mjs`); the failing mode of stdio MCP servers exiting with `McpError: Connection closed` is documented in AGENTS.md but not in code comments. Future Electron upgrades that bump the bundled Node major version would have to re-validate all spawned stdio MCPs.

## Future Considerations

- **Extract per-action modules under `src/api/conversation-service/`.** The 947-line `agent-server-conversation-service.api.ts` could be split into `start-conversation.ts`, `fork-conversation.ts`, `update-conversation.ts`, `delete-conversation.ts`, `condense-conversation.ts`, each importing the shared types from `agent-server-conversation-service.types.ts`. - **Add a typed `.d.ts` round-trip test to the library surface.** `npm run build:lib` produces `dist/components/<domain>/index.d.ts`; a stub consumer that imports from `@openhands/agent-canvas` and re-typechecks against a fresh `tsconfig` would catch silent prop renames before publish.
- **Move the cloud-vs-local dispatch into a small helper.** `dispatchByBackend({ cloud, local, runtime, ... })` (or a `BackendDispatcher` class) would let the per-method branch collapse to one line. Trade-off: one more indirection in the call stack.
