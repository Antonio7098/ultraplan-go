## Summary

Langfuse models most cross-process contracts as discriminated Zod schemas that are published from a single shared package and consumed by both the Next.js web tier and the BullMQ worker. Three layers stand out: (1) queue payload schemas owned by `packages/shared/src/server/queues.ts` with a paired `TQueueJobTypes` lookup that ties queue names to validated job shapes; (2) the in-app agent runtime, where AG-UI events, an MCP-tool approval policy, a sandbox provider interface, and Postgres-CAS run-lifecycle state machines form a tightly bounded contract; (3) provider/feature plug-in boundaries, where `StorageService`, `LLMAdapter` + `buildAiSdkModel`, `SandboxProvider`, `ManagedCredentialProvider`, and `BillingProvider` each express small TypeScript interfaces with one or more concrete adapters behind a factory. Errors, cancellation, idempotency, and lifecycle are encoded as a small set of stateful primitives (`InAppAgentRunStatus` enum, `BaseError` subclass hierarchy, AbortSignal propagation through the runtime stream). Compatibility for rolling deploys is enforced by an explicit "backward-compatibility is required, but new fields are optional" rule that is repeated in code comments (`packages/shared/src/server/queues.ts:30-48`, `packages/shared/src/server/queues.ts:53-78`) and covered by tests (`packages/shared/src/server/queues.test.ts:53-87`). The two notable weaknesses are the absence of an explicit conformance suite for cross-process schemas and the use of `instanceof Tool` duck-typing fallbacks across package boundaries (`worker/src/features/in-app-agent/runtime/tools.ts:132-135`). The rating of 8 reflects a clear model with tests, explicit interfaces, and operational safeguards, with one or two rough edges and missing cross-implementation conformance tests.

## Rating

**8/10 — Clear model with tests, explicit interfaces, and operational safeguards.**

Rationale: contracts are owned by the consumer package, encode lifecycle and error states as enums/discriminated unions, are validated at every process boundary, and ship with regression tests for rolling-deploy compatibility. The model stops short of 9–10 because (a) there is no formal conformance suite that proves a second implementation of, e.g., `SandboxProvider` would behave identically, (b) `withOptionalSilentMcpOutput` deliberately avoids `instanceof Tool` in favour of a structural check (`worker/src/features/in-app-agent/runtime/tools.ts:132-135`) which signals a contract gap between Mastra versions, and (c) the AG-UI schemas in `packages/shared/src/in-app-agent/schema.ts:10-15` are locally duplicated because the upstream types do not compile under Zod v4 — a known upstream-compatibility debt.

## Answers to Dimension Questions

1. **Are interfaces small, coherent, and owned by the consumer side?**
   Yes for the two largest contract surfaces. The queue payload schemas are owned by `packages/shared/src/server/queues.ts:1-667`, which is consumed by both web and worker. The in-app agent durable contracts are owned by the consumer web app and worker: `InAppAgentRunRequestSchema` (`packages/shared/src/features/inAppAgent/types.ts:79-102`) lives next to the Prisma model, and the contract types in `packages/shared/src/in-app-agent/server/{runLifecycle,persistence,mcpPolicy,modelProvider,toolErrors,toolResults}.ts` are imported by both web and worker. The `SandboxProvider` interface is owned by the consumer (the worker runtime) at `worker/src/features/in-app-agent/runtime/sandbox/types.ts:55-84`, not by either adapter. Two of the shared interfaces are larger than necessary: `StorageService` carries 10 methods (`packages/shared/src/server/services/StorageService.ts:235-272`), and `SandboxSession` mixes operation dispatch with `syncReadonlyFiles` (`worker/src/features/in-app-agent/runtime/sandbox/types.ts:21-48`).

2. **Do contracts specify behavior, not just method signatures?**
   Behavioural semantics are encoded as state machines and CAS rules rather than prose docs. `InAppAgentRunStatus` and `InAppAgentRunErrorCode` enums (`packages/shared/src/features/inAppAgent/types.ts:12-69`) plus the `classifyStaleRun` classifier (`packages/shared/src/in-app-agent/server/runLifecycle.ts:696-747`) make the run state machine explicit and unit-tested. The MCP policy is more than a list of names: each entry pairs `approval: "auto" | "approval"` with `availability.scope: ProjectScope` (`packages/shared/src/in-app-agent/server/mcpPolicy.ts:15-360`), and the `createInAppAgentToolPolicy` resolver (`packages/shared/src/in-app-agent/server/mcpPolicy.ts:477-510`) describes exactly how a tool becomes available. By contrast, several contracts remain shape-only: `SandboxProvider` does not document how `suspendSession` differs from `terminateSession` for the Docker provider (which does not implement suspend), and the AG-UI event types are accepted as `Record<string, unknown>` in some handlers (`packages/shared/src/in-app-agent/server/persistence.ts:1438-1453`).

3. **Can providers, tools, stores, and runtimes be replaced safely?**
   Yes, with two caveats. The `SandboxProvider` contract is small and both adapters (`worker/src/features/in-app-agent/runtime/sandbox/providers/{docker,lambdaMicrovm}.ts`) honor the same session-id semantics; `createInAppAgentSandbox` validates every outbound call against the `InAppAgentSandbox*ResultSchema` (`worker/src/features/in-app-agent/runtime/sandbox/service.ts:92-125`), so a new provider cannot pass non-conforming results without the worker failing. `StorageService` has four real implementations (`packages/shared/src/server/services/StorageService.ts:352-1270`) selected via the factory at `packages/shared/src/server/services/StorageService.ts:297-348`. `ManagedCredentialProvider` is a 12-line port with a stateful `RefreshingTokenManager` (`packages/shared/src/server/auth/credentials/RefreshingTokenManager.ts:19-99`) that gives any conforming provider refresh semantics for free. The two caveats: (a) `withOptionalSilentMcpOutput` does a structural `isWrappableMcpTool` check rather than relying on the `Tool` type (`worker/src/features/in-app-agent/runtime/tools.ts:109-118`) because `instanceof Tool` is unreliable across package realms — so a new Mastra-shaped tool must still expose `execute` + `inputSchema` and (b) the in-app agent's `Bedrock`-only model config (`packages/shared/src/in-app-agent/server/modelProvider.ts:4-9`) is by design; replacing it requires edits to the resolver, but the type still rejects a non-`"bedrock"` branch at compile time.

4. **Are compatibility failures caught early by tests or validation?**
   Yes. The most explicit evidence is the rolling-deploy compatibility test suite for queue payloads: `packages/shared/src/server/queues.test.ts:53-87` re-validates `IngestionEvent` and `OtelIngestionEvent` against payloads missing attribution fields, mirroring the comments that warn consumers at `packages/shared/src/server/queues.ts:30-48` and `packages/shared/src/server/queues.ts:53-78`. Validation at every cross-process boundary is the rule: the in-app agent queue processor parses the payload (`worker/src/queues/inAppAgentRunQueue.ts:9-13`), the sandbox server parses incoming JSON with `SandboxOperationSchema.parse(...)` (`packages/in-app-agent-sandbox-runtime/src/server.ts:151`), and the worker `createInAppAgentSandbox` validates every tool result before returning (`worker/src/features/in-app-agent/runtime/sandbox/service.ts:92-125`). The lifecycle has dedicated tests for race conditions (`packages/shared/src/in-app-agent/server/runLifecycle.test.ts:72-126`, `128-170`). The `LLMValidationError` marker uses `Symbol.for(...)` so `isInstance` works across realms (`packages/shared/src/server/llm/errors.ts:7-40`). The gap is that there is no contract-level conformance suite asserting that an independently implemented `SandboxProvider` or `ManagedCredentialProvider` would satisfy the consumer — only the two Langfuse-provided adapters are tested.

## Architectural Decisions

- **Consumer-owned schemas in the shared package.** Queue payload, in-app agent run/request/status/error, AG-UI message, MCP tool policy, and cloud config schemas all live in `packages/shared/src` so that both web and worker import the same Zod schema, removing producer/consumer drift (`packages/shared/src/server/queues.ts:1-12`, `packages/shared/src/in-app-agent/index.ts:1-9`).
- **Delivery-only queues for in-app agent runs.** `InAppAgentRunQueue` sets `attempts: 1` with an explicit comment that Postgres owns correctness via the claim CAS and reconcile-on-read, and BullMQ is delivery-only (`packages/shared/src/server/redis/inAppAgentRunQueue.ts:30-39`). This is a contract decision about who guarantees what.
- **Per-queue type map keyed by `QueueName`.** `TQueueJobTypes` (`packages/shared/src/server/queues.ts:476-667`) is a TypeScript mapped type tying queue name to payload + job-name literal, so producers and consumers get a compile-time link between `QueueName.InAppAgentRunQueue` and `InAppAgentRunQueueEventType`.
- **Discriminated unions over `type`/`actionId`/`role`/`operation`.** Wherever the consumer needs to route, a `z.discriminatedUnion` is used: `BatchActionProcessingEventSchema` (`packages/shared/src/server/queues.ts:180-265`), `WebhookOutboundEnvelopeSchema` (`:310-321`), `AgUiMessageSchema` (`packages/shared/src/in-app-agent/schema.ts:158-197`), `SandboxOperationSchema` (`packages/in-app-agent-sandbox-runtime/src/contracts.ts:8-41`), `InAppAgentRedirectToolInputStrictSchema` (`worker/src/features/in-app-agent/runtime/tools.ts:350-435`).
- **Run lifecycle as a Postgres CAS state machine.** The state machine is implemented entirely as `updateMany` filters on `in_app_agent runs` keyed by `status` (`packages/shared/src/in-app-agent/server/runLifecycle.ts:37-58`, `:64-84`, `:93-124`, `:411-451`). The `ActiveRun` conflict is mapped from a Prisma P2002 error to a typed `LangfuseConflictError` (`:805-840`).
- **MCP-tool policy as a closed registry.** `IN_APP_AGENT_LANGFUSE_MCP_TOOL_POLICIES` is a `satisfies Record<string, InAppAgentMcpToolPolicy>` literal (`packages/shared/src/in-app-agent/server/mcpPolicy.ts:27-360`); the type `InAppAgentLangfuseMcpToolName` is derived as `keyof typeof ...` so a new tool name cannot ship without a policy entry.
- **Provider model discriminates narrower than the generic LLM one.** The in-app agent is intentionally `provider: "bedrock"` only today, but the contract is a discriminated record so a future provider can be added without breaking call sites (`packages/shared/src/in-app-agent/server/modelProvider.ts:4-9`, `:24-42`).
- **Provider options translation is lossless or fails closed.** `TranslatedProviderOptions` is `{ok: true, value} | {ok: false, unknownKeys: string[]}` and the resolver wraps unknown errors in `LLMValidationError` (`packages/shared/src/server/llm/ai-sdk/providers/types.ts:7-9`, `packages/shared/src/server/llm/ai-sdk/resolveAiSdkModelConfig.ts:103-115`).
- **Sentinel-valued credentials for default chains.** `BEDROCK_USE_DEFAULT_CREDENTIALS = "__BEDROCK_DEFAULT_CREDENTIALS__"` and the `resolveBedrockProviderAuth` switch (`packages/shared/src/server/llm/ai-sdk/providers/bedrock.ts:111-151`) make the "ambient credential" decision explicit and testable.
- **Custom fetch contract for outbound LLM calls.** `CreateSecureFetch` is a factory that registers adapter-specific sensitive headers (`packages/shared/src/server/llm/ai-sdk/providers/index.ts:24-27`, `:72-86`, `:100-118`), so the security policy is part of the contract, not a side effect of the SDK.

## Notable Patterns

- **Single source of truth, narrow interface, tested at every boundary.** A representative chain: `MCPClient.listToolsets` → `filterInAppAgentAvailableLangfuseMcpTools` → `withOptionalSilentMcpOutput` → `withInAppAgentToolApproval` → `withToolExecutionTiming` → `Mastra Agent` (`worker/src/features/in-app-agent/runtime/agent.ts:1094-1130`). Each step has a tight contract and the final tool shape is fed to the constructor; tests assert the resulting schema/result behaviour (`worker/src/features/in-app-agent/runtime/sandbox/sandbox.test.ts:149-275`).
- **Pure functions for state-machine classification.** `classifyStaleRun` (`packages/shared/src/in-app-agent/server/runLifecycle.ts:696-747`) is a pure predicate; `reconcileConversationRuns` is the only writer. This keeps reconciliation testable without persistence.
- **Marker-based error identification across realms.** `LLMValidationError` uses a `Symbol.for(...)` marker instead of `instanceof`, so the type check survives bundling (`packages/shared/src/server/llm/errors.ts:4-40`).
- **Backward-compatible shape evolution with explicit comment.** New queue-payload fields are added as `.optional()` with a comment explaining the rolling-deploy constraint and a test that the old shape still parses (`packages/shared/src/server/queues.ts:30-48`, `:53-78`, `packages/shared/src/server/queues.test.ts:53-87`).
- **Pluggable sandbox via small structural port.** `SandboxProvider` is 4 optional methods, both providers conform, and the worker validates the result with Zod before returning — so a new provider cannot pass non-conforming data without an explicit test failure (`worker/src/features/in-app-agent/runtime/sandbox/types.ts:55-84`, `service.ts:92-125`).
- **Token refresh as a reusable resource.** `ManagedCredentialProvider` is a 3-property port; `RefreshingTokenManager` provides the refresh-ahead timer and listener fan-out for free (`packages/shared/src/server/auth/credentials/types.ts:1-12`, `RefreshingTokenManager.ts:19-99`).
- **Routing schema is a single discriminated union.** `WebhookOutboundEnvelopeSchema` unifies prompt-version, monitor-alert, and project-notification envelopes behind one `type` discriminator (`packages/shared/src/server/queues.ts:309-321`), and the corresponding handler switches on `type` so the producer/consumer contract is one type.
- **`satisfies` for typed literal registries.** `IN_APP_AGENT_LANGFUSE_MCP_TOOL_POLICIES satisfies Record<string, InAppAgentMcpToolPolicy>` (`packages/shared/src/in-app-agent/server/mcpPolicy.ts:360`) gives a closed registry with per-key validation and a derived `keyof` type.

## Tradeoffs

- **Conservative schema evolution vs velocity.** New queue payload fields are required to be `.optional()` with tests for old shapes. This is safe but slow: a feature that wants a new required field has to ship a multi-stage migration. The 4 `.optional()` fields on `OtelIngestionEvent` (`packages/shared/src/server/queues.ts:50-78`) are the visible cost.
- **In-process patching of upstream libraries.** `patchMastraApprovalChunks` (`worker/src/features/in-app-agent/runtime/agent.ts:1348-1456`) and the duplicate AG-UI schemas (`packages/shared/src/in-app-agent/schema.ts:7-15`) are both pragmatic workarounds for upstream gaps. They keep the team moving but create a maintenance liability when the upstream changes.
- **`SandboxProvider` is small but lifecycle semantics are uneven.** Both providers implement `ensureSession`; the Docker provider does not suspend (`worker/src/features/in-app-agent/runtime/sandbox/providers/docker.ts:211-219`) while the Lambda provider does. A future provider must read the comment to learn that suspension is "leave the container running" vs `SuspendMicrovmCommand`.
- **`StorageService` is broad and partly implicit.** The interface has 10 methods and three different upload strategies (`uploadFile`, `uploadFileBuffered`, `uploadWithSignedUrl`); the buffer/signed paths return `undefined` for non-S3 adapters (`packages/shared/src/server/services/StorageService.ts:235-272`, `:240-242`). The implicit "this method may not work" semantics is documented inline but the type system does not encode it.
- **Discriminated unions for routing are easy to extend and easy to forget to test.** `BatchActionProcessingEventSchema` (`packages/shared/src/server/queues.ts:180-265`) covers 9 action IDs; new ones are added in the union but the test file only exercises two webhooks paths and two ingestion paths, so a new action may not have a payload parse regression test.
- **`withOptionalSilentMcpOutput` does not use `instanceof Tool`.** This is necessary for cross-package-realm tools, but it means the contract is structural — a tool with the right shape but the wrong `execute` signature will silently fall through (`worker/src/features/in-app-agent/runtime/tools.ts:109-118`).
- **AG-UI events accepted as `Record<string, unknown>` in some handlers.** `toPersistableAgentEvent` uses string-based lookups (`packages/shared/src/in-app-agent/server/persistence.ts:1438-1453`) rather than narrowing the union. This keeps the code from being broken by upstream changes but loses exhaustiveness checks at the consumer.
- **Delivery-only BullMQ means duplicate execution is the consumer's problem.** `attempts: 1` on the in-app agent queue (`packages/shared/src/server/redis/inAppAgentRunQueue.ts:30-39`) shifts correctness to Postgres, which is correct, but it also means an unexpected BullMQ redelivery will hit the `claimQueuedRun` CAS and silently no-op — which is the right outcome, but only because the CAS is there.

## Failure Modes / Edge Cases

- **Cross-process payload drift on rolling deploys.** Mitigated by `.optional()` + comment + regression test (`packages/shared/src/server/queues.ts:30-48`, `packages/shared/src/server/queues.test.ts:53-87`). A new required field would break in-flight jobs.
- **Lost/terminated sandbox session.** `probeSession` is called eagerly so the model is told on the first tool call that the workspace is gone (`worker/src/features/in-app-agent/runtime/sandbox/service.ts:46-54`); the prompt carries a `<sandbox_workspace_reset>` instruction (`worker/src/features/in-app-agent/runtime/agent.ts:151-157`).
- **Stuck RUNNING worker.** `IN_APP_AGENT_HEARTBEAT_STALE_MS` plus `IN_APP_AGENT_RUN_MAX_DURATION_MS` plus the `classifyStaleRun` verdict on read path (`packages/shared/src/in-app-agent/server/tunables.ts:1-14`, `runLifecycle.ts:696-747`).
- **MCP error envelope misclassified as success.** The `tool-error` patch and the `getToolFailureMessage` classifier look for explicit `error: true` or `isError: true`, not text patterns (`worker/src/features/in-app-agent/runtime/agent.ts:1397-1430`, `packages/shared/src/in-app-agent/server/toolErrors.ts:8-46`). Tests assert this is not text-driven (`worker/src/features/in-app-agent/runtime/sandbox/sandbox.test.ts:277-313`).
- **Approval replay race.** `decideToolApproval` CAS protects against a double-decision; expired approvals are handled by the same transaction (`packages/shared/src/in-app-agent/server/runLifecycle.ts:222-397`).
- **Token expiry mid-call.** `RefreshingTokenManager` schedules a refresh ahead of expiry and exposes `onRefresh` listeners (`packages/shared/src/server/auth/credentials/RefreshingTokenManager.ts:60-99`).
- **Stored tool grant that the user's role no longer covers.** `createInAppAgentToolPolicy` re-derives availability from RBAC, so a stale `alwaysAllowedTools` entry cannot grant a tool the role lost (`packages/shared/src/in-app-agent/server/mcpPolicy.ts:501-509`, `packages/shared/src/in-app-agent/server/tools.test.ts:5-24`).
- **Cloud-config parse failure cascading.** `CloudConfigSchema` is parsed by `parseDbOrg`, which nulls the whole `cloudConfig` on failure; comments warn that this can drop a Stripe customer id and silently stop billing (`packages/shared/src/interfaces/cloudConfigSchema.ts:38-67`).
- **`SandboxProvider.suspendSession` semantics differ between adapters.** Documented in the runtime constant at `worker/src/features/in-app-agent/runtime/sandbox/config.ts:15-19` and in the Docker adapter's log line ("leaving container running across local session suspend") — not a hard failure but a behaviour a new adapter must mirror.
- **Cloud spend alert is on a separate queue with no payload in `TQueueJobTypes`.** The queue exists but its job entry has no `payload` field (`packages/shared/src/server/queues.ts:639-643`), which is intentional but unusual and not asserted by a test.

## Future Considerations

- **Add a conformance suite per cross-process contract.** Today, the only "second implementation" tests are the four cloud storage adapters and the two sandbox providers — but they live in their own files. A dedicated `conformance/` suite under `packages/shared` that constructs a minimal `SandboxProvider`/`ManagedCredentialProvider`/`StorageService` and runs the worker through it would catch contract drift.
- **Promote `SandboxSession` operations to a `SandboxCommand` discriminated union.** Today, `SandboxSession.read/write/edit/bash` each take a different shape; promoting them to a single `SandboxCommand` would make the surface uniform with the wire schema `SandboxOperationSchema` and reduce caller branching.
- **Type-narrow `StorageService` upload strategies.** A `BufferedUploadCapable` mixin interface would let the compiler reject `uploadFileBuffered` on non-S3 adapters instead of the current `Promise<UploadPartStats | undefined>` shape (`packages/shared/src/server/services/StorageService.ts:240-242`).
- **Backport the AG-UI schemas into `@ag-ui/core` once the upstream PR lands.** The TODO at `packages/shared/src/in-app-agent/schema.ts:7-15` is the right call to revert.
- **Add schema regression tests for every `BatchAction` actionId.** Today only 2 of 9 are exercised by the shared queue test. A `it.each` over all actionIds would catch payload additions.
- **Promote the in-app agent's `Bedrock` provider discriminator to a real union.** Even if the second branch is "TBD", `InAppAgentModelConfig` could become `{ provider: "bedrock"; ... } | { provider: "openai"; ... }` to make future migration mechanical.
- **Add an `LLMValidationError` boundary check at the public API layer.** Today the type is checked inside `resolveAiSdkModelConfig` (`packages/shared/src/server/llm/ai-sdk/resolveAiSdkModelConfig.ts:103-115`); doing the same at the public-API ingress would mean callers never see a raw Zod parse error.
- **Document the delivery-only contract for `InAppAgentRunQueue` in the shared AGENTS.md.** The comment lives in code (`packages/shared/src/server/redis/inAppAgentRunQueue.ts:30-39`); promoting it to docs would help new contributors.
