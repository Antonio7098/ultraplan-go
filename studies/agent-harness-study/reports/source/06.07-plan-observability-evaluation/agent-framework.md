## Summary

Agent Framework has no dedicated plan trace or plan evaluation subsystem. Plans are represented as a `TodoProvider`-managed list of `TodoItem(id,title,description,is_complete)` mutated via tools (`todos_add`/`todos_complete`/`todos_remove`/`todos_get_all`/`todos_get_remaining`) and secondarily as a markdown file in `FileMemoryProvider`. Observability is limited to session-state persistence (`TodoSessionStore` in `AgentSession.state`, opt-in `TodoFileStore` JSON per session) and a single user-role injection of the current list before each model turn. There is no OTel span, workflow event, structured plan version log, or per-item execution linkage. Evaluation exists as a generic framework (`_evaluation.py` `LocalEvaluator`, `evaluate_agent`/`evaluate_workflow`, `keyword_check`/`tool_called_check`) that can assert tool use but defines no plan-quality metric, no planning dataset, and no regression test that binds planning quality to success. The only closed-loop diagnosis lives in Magentic's LLM-generated `ProgressLedger` (`is_request_satisfied`/`is_in_loop`/`is_progress_being_made` with stall counter), which is not wired to the harness todo path. Result: a developer can recover what the current plan is but cannot debug plan vs execution from traces alone.

## Rating

**4/10 — Present but inconsistent, weakly documented, and fragile for observability/evaluation**

Rationale: Plan state is durably persisted with atomic writes, per-session locks, and explicit tests, and the current list is injected into the model prompt. However: (a) no structured plan trace/event stream exists (OTel, workflow events, or log) — inspection requires reading `session.state`; (b) no link from tool calls/executor outputs back to originating `TodoItem.id`; (c) no plan-specific quality metric, rubric, or eval dataset; (d) Magentic's diagnosis is the only automated poor-plan detector and is isolated to orchestrations; (e) no evidence that planning improves success rate is measured or gated in CI. Raising to 7 would require `TodoUpdated` workflow/OTel events, execution attribution (`tool_call.todo_id`), a plan adherence evaluator with datasets, and regression tests for `plan → execution divergence`.

## Answers to Dimension Questions

### 1. Are plans observable?
**Partially — current snapshot is, history and trace are not.** The live plan is observable via three paths: (a) `TodoProvider` tools `todos_get_all`/`todos_get_remaining` (`python/packages/core/agent_framework/_harness/_todo.py:577-590`) callable by model and test harness; (b) the injected user message `### Current todo list` added in `before_run` (`python/packages/core/agent_framework/_harness/_todo.py:597-615`); (c) durable state in `session.state[source_id]` (`TodoSessionStore` `python/packages/core/agent_framework/_harness/_todo.py:245-285`) or JSON file `todos.<source_id>.json` (`TodoFileStore` `python/packages/core/agent_framework/_harness/_todo.py:344-443`). Workflow-level `WorkflowRunResult` and OTel spans (`python/packages/core/agent_framework/observability.py:294-330`, `python/packages/core/agent_framework/_workflows/_workflow.py:103-167`) do not emit plan-specific events, so comparing `plan vs execution` requires manually correlating `session.state` snapshots with transcript/tool-call logs — no `TodoUpdated` event, no OTel `gen_ai.todo.*` attribute, and revisions overwrite in place. You can answer "what is the plan now?" but not "how did the plan evolve during this run?" from traces alone.

### 2. Can each action be linked to a plan item?
**No.** `TodoItem.id` (`python/packages/core/agent_framework/_harness/_todo.py:54`) is sequential and `todos_complete` requires `reason` (`python/packages/core/agent_framework/_harness/_todo.py:144-177`), but `FunctionTool` (`python/packages/core/agent_framework/_tools.py`), `Content` function-call/result (`python/packages/core/agent_framework/_types.py`), and `WorkflowEvent` (`python/packages/core/agent_framework/_workflows/_events.py`) carry no `todo_id`/`plan_item_ref`. `AgentLoopMiddleware` only checks the aggregate `any(not is_complete)` (`python/packages/core/agent_framework/_harness/_loop.py:937-973`), not which todo a tool call satisfies, and `todos_remaining_message` merely lists open titles. Post-hoc linkage requires substring matching title to tool name — fragile and not enforced. The `.NET` parity `TodoCompletionLoopEvaluator` (`dotnet/src/Microsoft.Agents.AI/Harness/Loop/TodoCompletionLoopEvaluator.cs`) is identical.

### 3. Are plans evaluated?
**Only via generic evaluators, not plan-specific.** The framework ships `_evaluation.py:182-850` with `evaluate_agent`/`evaluate_workflow` and `LocalEvaluator` plugging `EvalCheck` functions. Provided checks are `keyword_check` (`python/packages/core/agent_framework/_evaluation.py:1061-1085`), `tool_called_check` (`python/packages/core/agent_framework/_evaluation.py:1089-1148`), `tool_calls_present`/`tool_call_args_match` (`python/packages/core/agent_framework/_evaluation.py:1171-1277`) — all assert response text or that expected tools were called. No metric measures plan completeness, adherence (fraction of todos mapped to actions), revision churn, or plan quality (e.g., missing decomposition). `MagenticProgressLedger` (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:310-345`) and `JudgeVerdict` (`python/packages/core/agent_framework/_harness/_loop.py:104-117`) can act as ad-hoc plan verifiers when caller supplies `criteria` (`AgentLoopMiddleware.with_judge` `python/packages/core/agent_framework/_harness/_loop.py:350-415`), but they are opt-in loop predicates, not part of `EvalResults` or CI gates. No planning eval dataset was found.

### 4. Can poor planning be diagnosed?
**Only in Magentic; otherwise manual.** Magentic diagnoses stuck/drifting plans via model-generated `is_in_loop`/`is_progress_being_made` with `stall_count` increment/decrement and `max_stall_count=3` threshold triggering `_reset_and_replan` (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:1109-1118`); `_reset_and_replan` emits `REPLANNED` and clears `chat_history`. The single-agent harness has no validator: drift guidance is instructional text ("adjust your todos accordingly" `python/packages/core/agent_framework/_harness/_todo.py:35-48`, plan-mode steps `python/packages/core/agent_framework/_harness/_mode.py:33-70`). A developer can diagnose after the fact by diffing `todos_get_all` snapshots against tool-call logs and using injected progress (`AgentLoopMiddleware: record_feedback` `python/packages/core/agent_framework/_harness/_loop.py:299-320`) or `WorkflowRunResult.status_timeline` (`python/packages/core/agent_framework/_workflows/_workflow.py:164-167`), but the framework does not automatically flag orphaned todos, contradictory edits, or uncovered output.

### 5. Does planning improve success rate?
**No evidence collected.** `EvalResults` (`python/packages/core/agent_framework/_evaluation.py:373-443`) supports `result_counts`, `per_evaluator` breakdowns, `raise_for_status`, and `assert_score_at_least`, but no test or report correlates `TodoProvider` usage vs. non-todo runs, nor is there an A/B harness or telemetry histogram of `todos_remaining` iterations vs. task success. `FeatureIndex.CORE_TODO_PROVIDER` (`python/packages/core/agent_framework/_telemetry.py:49`) tracks adoption via User-Agent token, not outcome. Samples use `create_harness_agent` with default todo enabled (`python/packages/core/agent_framework/_harness/_agent.py:176-177`) but do not publish success-rate deltas. Answer is "not measured within this source."

## Architectural Decisions

- **Todo list as implicit plan, not a first-class Plan type** — `TodoItem`/`TodoProvider` (`python/packages/core/agent_framework/_harness/_todo.py:51-615`) is the executable plan; no `Plan` class, status enum, or version chain. Keeps API small but pushes traceability and lifecycle to ad-hoc session state.
- **Session-state as sole structured log** — `TodoSessionStore` default (`python/packages/core/agent_framework/_harness/_todo.py:245-285`) vs opt-in `TodoFileStore` atomic JSON (`python/packages/core/agent_framework/_harness/_todo.py:288-443`). Enables durability and GC-safe mutation locks (`WeakKeyDictionary` `python/packages/core/agent_framework/_harness/_todo.py:481-492`) but intentionally overwrites rather than appends, so history is lost.
- **Prompt injection as observability surface** — current todos injected as a synthetic user message plus instructions (`DEFAULT_TODO_INSTRUCTIONS` `python/packages/core/agent_framework/_harness/_todo.py:25-48`, `DEFAULT_MODE_INSTRUCTIONS` `python/packages/core/agent_framework/_harness/_mode.py:15-27`). Cheap and visible to model, but not structured for offline tracing.
- **Generic evaluation framework decoupled from planning** — `_evaluation.py:682-850` is provider-agnostic (Foundry/local/custom) with `EvalItem.split_messages` strategies; planning is not a privileged dimension. Keeps evaluation extensible but leaves plan adherence to caller-authored `EvalCheck`s.
- **Magentic as isolated quality island** — Fact/plan ledger + progress ledger (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:285-355`) with LLM-as-judge stall detection is the only mature plan-diagnosis loop; not shared with harness `TodoProvider`, creating two disjoint planning stories.
- **OTel for workflow/agent infra, not for plan** — `observability.py:294-330` defines workflow/executor/edge-group spans via `create_workflow_span`; no `OtelAttr` for todo/plan. Plan operations are invisible in the deployed trace backend even when `enable_instrumentation` is on.

## Notable Patterns

- **Per-session serialized mutations with GC eviction** — `TodoProvider._mutation_locks: WeakKeyDictionary[AgentSession, asyncio.Lock]` (`python/packages/core/agent_framework/_harness/_todo.py:481-492`) mirrors .NET `ConditionalWeakTable`; prevents duplicate `next_id` under concurrent `todos_add`/`todos_complete` and is validated by `test_todo_provider_serializes_concurrent_mutations` (`python/packages/core/tests/core/test_harness_todo.py:322-367`).
- **Reason-gated completion** — `TodoCompleteInput(id, reason)` validates non-empty reason (`python/packages/core/agent_framework/_harness/_todo.py:144-177`) and `todos_complete` returns `{"completed": N}` (`python/packages/core/agent_framework/_harness/_todo.py:528-561`). Minimal justification channel, but reason is not persisted on `TodoItem`.
- **Judge-pattern as replanning verifier** — `AgentLoopMiddleware.with_judge` replaces `{{criteria}}` in instructions and surfaces `JudgeVerdict.reasoning` as `feedback` kwarg to `next_message`/`record_feedback` (`python/packages/core/agent_framework/_harness/_loop.py:152-214,203-212`). Enables criteria-driven plan verification without touching `TodoProvider`.
- **Progress ledger stall counter** — Magentic's decrement-on-progress/increment-on-stall (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:1109-1118`, `max_stall_count=3` default) bounds LLM-replanning to avoid infinite reset loops, with human plan-review gate (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:998-1040`) as fallback.

## Tradeoffs

- **Ergonomics vs auditability** — Free-form `todos_add`/`remove` and file overwrites make planning frictionless but erase why/when each revision occurred. Persisted `reason` on `todos_complete` is transient (tool arg only), so post-hoc "why completed?" must scrape transcript.
- **Prompt-visible vs queryable** — Injecting the todo list as a user message makes the model aware with zero infra, but buries the plan in the transcript rather than a typed `WorkflowEvent` or OTel span that external dashboards can aggregate and alert on.
- **Generic evaluation vs plan-specific rigor** — `LocalEvaluator(keyword_check, tool_called_check)` is framework-agnostic and cheap for CI smoke tests, but caller must invent plan adherence logic; no shared `plan_completeness`/`orphaned_todo`/`decomposition_quality` evaluator ships, so teams diverge.
- **Atomic snapshot vs versioned history** — `TodoFileStore` atomic `os.replace` (`python/packages/core/agent_framework/_harness/_todo.py:431-443`) prevents corruption and is tested (`test_todo_file_store_writes_state_atomically` `python/packages/core/tests/core/test_harness_todo.py:130-150`) at the cost of discarding prior revisions that would power `plan vs execution` diffing.
- **Magentic depth vs harness breadth** — Stall-aware replanning is bounded and tested for orchestrations, but the harness path most samples use (`create_harness_agent` `python/packages/core/agent_framework/_harness/_agent.py:176-177`) has no equivalent drift guard — quality is prompt-compliance dependent.

## Failure Modes / Edge Cases

- **Silent plan divergence** — Instructions to sync todos on topic change (`python/packages/core/agent_framework/_harness/_todo.py:35-48`) are unenforced; agent can add tasks without removing obsolete ones, causing `todos_remaining` to loop on phantom work or `todos_get_all` to show stale open items with no validator comparing executed tool calls to todo titles.
- **Reason not persisted** — `TodoCompleteInput.reason` is validated but not stored on `TodoItem` (`python/packages/core/agent_framework/_harness/_todo.py:51-107`); `todos_remove` has no reason field at all, so audits lose intent and `WorkflowRunResult`/`FileHistoryProvider` cannot answer "why was plan item removed?".
- **Corrupted todo state is fatal to turn** — Both stores raise `ValueError` on malformed `items`/`next_id` (`python/packages/core/agent_framework/_harness/_todo.py:192-202,261-276`) and bubble as a tool-call error; no repair/quarantine path exists, and the agent's attempted fix must be inferred from transcript rather than a typed recovery event.
- **Fresh-context discards plan mutations** — `AgentLoopMiddleware` with `fresh_context=True` snapshots `session.to_dict()` before loop and restores it before each iteration (`python/packages/core/agent_framework/_harness/_loop.py:436-437,583-586`); in-loop `todos_add`/`complete` and `FileMemoryProvider` writes are lost except via injected progress log, silently reverting plan revisions.
- **Judge/Magentic JSON fragility** — `with_judge` fallback parses `JUDGE_VERDICT_DONE/MORE` markers in free text (`python/packages/core/agent_framework/_harness/_loop.py:192-199`); Magentic's `_run_inner_loop_helper` catches any exception from `create_progress_ledger` and triggers `_reset_and_replan` (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:1083-1085`), so persistent model inability to emit valid JSON drives an unbounded reset loop up to `max_reset_count` (default unlimited).
- **No execution linkage means false attribution** — Because tool calls lack `todo_id`, a post-hoc heuristic mapping `tool_call` → `TodoItem.title` will misattribute when titles are vague ("Investigate issue") or when one tool satisfies multiple todos; observability consumers cannot distinguish.
- **Telemetry blind spot** — With `enable_sensitive_data=false` (default) message content is stripped from OTel spans (`python/packages/core/agent_framework/observability.py:1015-1022`); even with it enabled, todo content is still not emitted as a distinct span/event, so plan observability depends on session-store introspection absent from the trace pipeline.

## Future Considerations

- Emit `WorkflowEvent(type="todo_updated")` or OTel span `todo.update` with `todo.id`, `todo.title`, `todo.is_complete`, `reason`, `revision_id` on each `todos_add/complete/remove`; wire to `WorkflowRunResult.status_timeline` (`python/packages/core/agent_framework/_workflows/_workflow.py:164-167`) and `OtelAttr` so DevUI and collectors can chart `plan vs execution`.
- Add `todoId`/`planItemId` optional correlation on `Content.function_call`/`function_result` or via `context.metadata`, populated when model calls a tool in context of a todo; enables `tool_call → plan item` join and plan adherence metric.
- Version the todo store: append-only JSONL `todos.<source_id>.jsonl` or `previous_checkpoint_id` chain like `WorkflowCheckpoint` (`python/packages/core/agent_framework/_workflows/_checkpoint.py:40-110`) with `author` (model/user/system) and `diff`; expose `todos_get_history(revision_id)` tool.
- Ship plan-quality evaluators: `plan_completeness_check`, `orphaned_todo_check`, `decomposition_quality_check` as `EvalCheck`s alongside `keyword_check` (`python/packages/core/agent_framework/_evaluation.py:1060-1148`), plus a small curated dataset under `python/packages/core/tests/assets/plan-eval/` and CI gate `assert_score_at_least` on plan adherence.
- Promote `MagenticProgressLedger` stall logic to a shared `drift_detector(LLM, todos, recent_tool_calls)` utility usable as `loop_should_continue` for single-agent harness; add explicit `todos_remaining` + `drift_detector` composition in `create_harness_agent` (`python/packages/core/agent_framework/_harness/_agent.py:176-180`).
- Persist `completion_reason` on `TodoItem` and tombstone removed items (`removed_at`, `removed_reason`) rather than deleting; restores post-hoc diagnosis without transcript scraping.
