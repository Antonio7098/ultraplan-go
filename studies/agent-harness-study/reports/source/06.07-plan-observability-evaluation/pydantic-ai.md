## Summary

`pydantic-ai` itself contains **no first-class planning abstraction**. There is no `Plan`, `PlanItem`, `TaskStatus`, or planning evaluator inside `pydantic_ai_slim/pydantic_ai`, `pydantic_graph`, or `pydantic_evals`. Planning is explicitly delegated to the external sibling package `pydantic-ai-harness` via its `Planning` capability (`PlanItem`/`Planning`/`PlanningToolset`), referenced only in documentation and in the GH shim's todo-bridge (`docs/capabilities/third-party.md:8`, `.github/scripts/pydantic_ai_gh_aw_shim/todo_write.py:15`). The single in-tree `Plan`/`Step` definition (`examples/pydantic_ai_examples/ag_ui/api/agentic_generative_ui.py:22-31`) is an illustrative user-owned tool schema, not a framework type.

What the framework does provide is generic execution observability that could be used to *infer* plan behaviour: a full `ModelMessage` history with `run_id`/`conversation_id`/`tool_call_id` correlation (`pydantic_ai_slim/pydantic_ai/messages.py:1852-1856`, `pydantic_ai_slim/pydantic_ai/messages.py:1309`), the ordered agent graph (`pydantic_graph/pydantic_graph/graph_builder.py:158`, `pydantic_ai_slim/pydantic_ai/_agent_graph.py:299`), and a spec-compliant OTel pipeline (`pydantic_ai_slim/pydantic_ai/_instrumentation.py:444`, `pydantic_ai_slim/pydantic_ai/capabilities/instrumentation.py:68`). The eval harness (`pydantic_evals/pydantic_evals/dataset.py:177`, `pydantic_evals/pydantic_evals/evaluators/agentic.py:191`) evaluates *execution trajectories* (tool name sequences, argument correctness, call budgets), not plan quality. There are no plan traces, plan-item IDs, execution-to-plan links, planning metrics, planning eval datasets, or planning regression tests inside the studied source. Result: plan observability and evaluation are absent/outsourced — the strict reading of this dimension scores **2/10**.

## Rating

**2 / 10 — Absent / Implicit / Ad-hoc**

Rationale: the selected source (the `pydantic-ai` repo) ships no native planning model. All evidence for planning lives outside the isolation boundary (the `pydantic-ai-harness` repo). Inside the boundary, execution is highly observable (message history, OTel spans, graph instrumentation) but plan-aware observability — logging a plan, assigning stable plan-item IDs, linking each `ToolCallPart`/`ToolReturnPart` or graph node to a plan item, and scoring plan quality — is entirely missing. `pydantic-evals` contributes trajectory evaluators that are useful proxies for plan adherence, but none assess a plan artifact itself. The illustrative `Plan` example is user code, not a tested framework contract, and has no regression coverage.

## Answers to Dimension Questions

**1. Are plans observable?**
No — not as a first-class artifact inside the studied source. `GraphAgentState` (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:299-344`) stores only `message_history`, `usage`, `run_id`/`conversation_id`, and queue buffers; there is no `plan` or `plan_revision` log. The only OTel payloads emitted are `gen_ai.input.messages`, `pydantic_ai.all_messages`, tool definitions, and per-span tool call arguments (`pydantic_ai_slim/pydantic_ai/capabilities/instrumentation.py:236-277`, `pydantic_ai_slim/pydantic_ai/_instrumentation.py:444-542`) — no `plan.*` span attribute, no plan snapshot, and no plan diff event. The user can make a plan observable by modelling it as ordinary tools/messages (as in `examples/pydantic_ai_examples/ag_ui/api/agentic_generative_ui.py:22-96`), in which case it appears as regular `ToolCallPart`/`ToolReturnPart` entries in the history, but the framework does not tag or version it as a plan.

**2. Can each action be linked to a plan item?**
No. Tool calls are correlated to returns via `tool_call_id` (`pydantic_ai_slim/pydantic_ai/messages.py:1309`, `pydantic_ai_slim/pydantic_ai/messages.py:2174`) and to the run via `run_id`/`conversation_id` (`pydantic_ai_slim/pydantic_ai/messages.py:1852-1856`), and graph tasks carry `ForkStack`/`TaskID` (`pydantic_graph/pydantic_graph/graph_builder.py:389-428`), but there is no `plan_item_id` field on `ToolCallPart`, `ToolReturnPart`, `ModelRequest`, `ModelResponse`, or `GraphTask`. `ToolAvailabilityDeltaPart` (`pydantic_ai_slim/pydantic_ai/messages.py:1791-1805`) records tool set changes, not plan step progress. The only stable plan-item linkage exists outside the boundary, in `pydantic_ai_harness.planning.PlanItem` (imported at `.github/scripts/pydantic_ai_gh_aw_shim/todo_write.py:15`), which is not vendored or re-exported here and cannot be inspected in an isolated study.

**3. Are plans evaluated?**
No. `pydantic_evals` ships no planning dataset, planning metric, or planning-specific evaluator. The dataset model (`pydantic_evals/pydantic_evals/dataset.py:177`) is fully generic, and the built-in evaluators score final outputs (`Equals`, `Contains`, `LLMJudge`, `GEval` at `pydantic_evals/pydantic_evals/evaluators/common.py:33-338`) or execution trajectories derived from OTel spans (`ToolCorrectness`, `TrajectoryMatch`, `ArgumentCorrectness`, `MaxToolCalls` at `pydantic_evals/pydantic_evals/evaluators/agentic.py:191-582`). Trajectory evaluators can act as proxies for plan adherence (e.g., `TrajectoryMatch(order='exact')` asserts tool order), but they score what was executed, not what was planned, and cannot distinguish a good plan poorly executed from a poor plan faithfully executed.

**4. Can poor planning be diagnosed?**
Only indirectly and with manual effort. A failed run can be debugged by replaying `all_messages()` / `new_messages()` (`pydantic_ai_slim/pydantic_ai/run.py:636-699`) and by querying the OTel trace (`invoke_agent` → `chat` → `execute_tool` spans in `pydantic_ai_slim/pydantic_ai/capabilities/instrumentation.py:152-319`, plus span-tree queries via `HasMatchingSpan` at `pydantic_evals/pydantic_evals/evaluators/common.py:342`). `ThinkingPart` (`pydantic_ai_slim/pydantic_ai/messages.py:1928`) surfaces model reasoning when the provider emits it. None of these surfaces separate a planning error (wrong decomposition, missing step, hallucinated dependency) from an execution error (tool failure, bad arguments, context overflow). There is no plan-vs-execution diff view, no plan revision history, and no evaluator that grades plan completeness, ordering, or feasibility.

**5. Does planning improve success rate?**
No evidence found inside the selected source. The repo contains no A/B harness, no benchmark that toggles planning on/off, and no reported correlation between a planning capability and task success. `pydantic_evals` supports running a `Dataset` twice and comparing `EvaluationReport` averages (`pydantic_evals/pydantic_evals/dataset.py:281`, `pydantic_evals/pydantic_evals/dataset.py:1056`) — the infrastructure to measure such an effect exists — but no planning benchmark, baseline, or dashboard is shipped. Claims that planning helps would need to be validated externally (e.g., in `pydantic-ai-harness` benchmarks), out of scope for this isolated source.

## Architectural Decisions

* **Planning outsourced to `pydantic-ai-harness`.** The core framework deliberately avoids a built-in planner; docs route users to `pydantic_ai_harness.planning.Planning` (`docs/capabilities/third-party.md:8-11`). This keeps `pydantic-ai-slim` small and provider-agnostic and lets the harness iterate on plan caching, progress tracking, and filesystem/shell integration without coupling to the agent loop. The cost is zero plan observability inside the studied source.
* **Message history as universal trace.** `GraphAgentState.message_history: list[ModelMessage]` (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:303`) plus `run_id`/`conversation_id` stamping (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:307-318`) is the single persisted artifact. Structured tool plans (like the `Plan` tool in the AG-UI example) piggyback on this, so they are observable only insofar as tool calls are — without plan-specific indexing or versioning.
* **OTel/Logfire as evaluation substrate.** `pydantic_evals` evaluators read `ctx.span_tree` (`pydantic_evals/pydantic_evals/evaluators/agentic.py:224`, `pydantic_evals/pydantic_evals/evaluators/agentic.py:326`) populated by `Instrumentation` (`pydantic_ai_slim/pydantic_ai/capabilities/instrumentation.py:68`). Trajectory evaluators query span names/attributes (`gen_ai.tool.name`, `gen_ai.operation.name == 'chat'` at `pydantic_evals/pydantic_evals/evaluators/agentic.py:71-143`) — a deliberate coupling that makes execution traces the ground truth for eval, while plan documents remain out-of-band.
* **`pydantic-graph` models control flow, not task plans.** `Graph`/`Fork`/`Join`/`Decision`/`Step` (`pydantic_graph/pydantic_graph/graph_builder.py:158-193`) encode deterministic workflow topology with first-class fork/join semantics, not model-authored natural-language plans. Observing graph execution tells you which `NodeStep` ran, not whether the agent's task decomposition was sensible.

## Notable Patterns

* **Capability composition for cross-cutting concerns.** Planning, tool search, thinking, and instrumentation are all `AbstractCapability` subclasses (`pydantic_ai_slim/pydantic_ai/capabilities/abstract.py:1`, `pydantic_ai_slim/pydantic_ai/capabilities/instrumentation.py:68`, `pydantic_ai_slim/pydantic_ai/capabilities/thinking.py:14`). The harness planning capability plugs in the same way `Instrumentation` does — a clean extension point that also explains why plan telemetry is capability-private rather than framework-built-in.
* **Tool-call/return correlation via `tool_call_id`.** Every `BaseToolCallPart` (`pydantic_ai_slim/pydantic_ai/messages.py:2174`) and `BaseToolReturnPart` (`pydantic_ai_slim/pydantic_ai/messages.py:1309`) share a `tool_call_id` with outcome discriminator (`success`/`failed`/`denied`/`interrupted` at `pydantic_ai_slim/pydantic_ai/messages.py:1336`), providing the join key that plan-item linkage would reuse if it existed.
* **Spec-compliant OTel without domain extensions.** `_instrumentation.py` (`pydantic_ai_slim/pydantic_ai/_instrumentation.py:1-746`) and `capabilities/instrumentation.py` implement only `gen_ai.*` / `logfire.*` conventions. Custom attributes beyond the spec are avoided (see repo `AGENTS.md` rule 17), which is why plan-specific attributes are absent rather than ad-hoc.
* **Process-agnostic eval dataset.** `Dataset`/`Case`/`EvaluatorContext` (`pydantic_evals/pydantic_evals/dataset.py:111-246`) are typed generically (`InputsT`, `OutputT`, `MetadataT`) and transport OTel `SpanTree`/`metrics`/`attributes` (`pydantic_evals/pydantic_evals/dataset.py:1000-1009`) — the right shape to add a `Plan` field without breaking existing evaluators, but that extension has not been made.

## Tradeoffs

* **Slim core vs. out-of-box planning.** Not vendoring `Planning` keeps dependency weight and API surface low and avoids pinning a single task-planning UX, but it forces every study of planning quality to cross the isolation boundary. Teams that adopt only `pydantic-ai` get no opinionated planning loop, no plan logger, and no plan-aware evals — they must build their own or add the harness.
* **Generality of trajectory evaluators.** `TrajectoryMatch` F1 (`pydantic_evals/pydantic_evals/evaluators/agentic.py:287-366`) and `ToolCorrectness` multiset checks (`pydantic_evals/pydantic_evals/evaluators/agentic.py:191-245`) work for any agent without a planning vocabulary, at the cost of conflating planning and execution. A redundant extra tool call penalizes F1 the same way whether it reflects a bad plan or a retry.
* **Provider portability vs. deep reasoning traces.** Unified `ThinkingLevel` (`pydantic_ai_slim/pydantic_ai/capabilities/thinking.py:14-26`) surfaces reasoning portably, but whether reasoning is available depends on `model_profile` flags rather than a framework guarantee. Plans inferred from reasoning text are therefore provider-dependent and non-structured compared to an explicit `PlanItem` list.

## Failure Modes / Edge Cases

* **Silent absence of plan data.** Because the absence of a plan is not an error, instrumentation and eval continue to succeed with empty/undefined plan state. A regression that drops plan steps (in the harness) or silently changes plan serialization would not surface as a failure inside `pydantic-ai` tests — the only signal would be downstream task success rates degrading.
* **Tool-call/return mismatch without plan guard.** History repair for interrupted tool calls (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:547-558`, `pydantic_ai_slim/pydantic_ai/messages.py:1293-1296` `INTERRUPTED_TOOL_RETURN_CONTENT`) synthesizes returns to keep history well-formed, but without a plan there is no way to mark which planned item the synthesized return corresponds to — post-mortem attribution of `outcome='interrupted'` to a plan step is lost.
* **In-place history mutation evades detection until end-of-run.** `MessageJsonCache` and `has_stale_message_json` (`pydantic_ai_slim/pydantic_ai/_instrumentation.py:90-120`, `pydantic_ai_slim/pydantic_ai/_instrumentation.py:256-281`, `pydantic_ai_slim/pydantic_ai/capabilities/instrumentation.py:220-234`) detect stale `gen_ai.input.messages` only at run end and only for messages still present. A plan-like tool result mutated in place and then pruned by a `HistoryProcessor` (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:719`) would have produced a stale span without a warning, corrupting any after-the-fact plan reconstruction.
* **Span tree absence degrades evaluators to false negatives.** All `agentic` evaluators return `EvaluationReason(value=False, reason=_NO_SPAN_TREE_REASON)` (`pydantic_evals/pydantic_evals/evaluators/agentic.py:182`, `pydantic_evals/pydantic_evals/evaluators/agentic.py:328`) when `ctx.span_tree` is unavailable (e.g., Logfire not configured, `include_content=False`). A CI pipeline that disables OTel for speed would see trajectory/plan-proxy checks fail open without distinguishing missing telemetry from poor planning.
* **Graph `Fork`/`Join` cancellation races.** `GraphRun._cancel_sibling_tasks` (`pydantic_graph/pydantic_graph/graph_builder.py:1096-1106`) and `iter_graph` cancellation scopes (`pydantic_graph/pydantic_graph/graph_builder.py:857-884`) can drop sibling tasks when a reducer votes to cancel — observable as missing tool calls in `TrajectoryMatch` but indistinguishable from a planner choosing not to execute a branch.

## Future Considerations

* **Vendor a minimal `PlanItem` contract in `pydantic-ai-slim` or `pydantic-graph`.** Even a thin `PlanItem { id, content, status }` plus `plan_version` on `ModelRequest`/`ModelResponse` and `gen_ai.plan.*` span attributes would make plans observable without importing the harness. The harness could then implement the richer `Planning` capability against that contract while keeping the source-isolated core independently testable. Track parity with `pydantic_ai_harness.planning` to avoid divergence.
* **Add first-class plan-vs-execution evaluators.** Extend `EvaluatorContext` to carry an optional `plan: list[PlanItem]` and add evaluators `PlanCompleteness`, `PlanFeasibility`, `PlanAdherence` (plan/execution alignment score), and `PlanEfficiency` (redundant steps). Reuse the `SpanTree`/`metrics` plumbing (`pydantic_evals/pydantic_evals/evaluators/agentic.py:65-89`) so plan quality can be scored without LLM judges.
* **Ship a planning eval dataset fixture.** Add `pydantic_evals/datasets/planning/` with cases that assert multi-step decomposition, ordering constraints, and tool preconditions — and a `repeat`/`report_evaluator` harness (`pydantic_evals/pydantic_evals/dataset.py:269-413`) that measures success-rate lift when a planning capability is enabled vs. disabled.
* **Plan-aware OTel and regression coverage.** Emit `pydantic_ai.plan.items`, `pydantic_ai.plan.version`, `pydantic_ai.plan.item_id` on tool spans and `has_stale_message_json`-style staleness detection for plan mutations; add `tests/evals/test_planning_evaluators.py` and `tests/test_plan_observability.py` covering plan logging, linkage, and `TrajectoryMatch`-vs-`PlanAdherence` divergence.
* **Expose `all_messages` plan extraction helper.** Provide `AgentRunResult.plan_items()` / `messages.extract_plan()` that parses `ToolCallPart` with `tool_kind='plan'` (paralleling `ToolSearchCallPart` at `pydantic_ai_slim/pydantic_ai/messages.py:1268`) so downstream UIs (AG-UI/CLI) can render plan vs. execution without ad-hoc JSON parsing.
