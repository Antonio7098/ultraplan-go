## Summary

CrewAI does not have a single, first-class "approval session" abstraction. Instead it ships **three parallel human-in-the-loop (HITL) mechanisms** with very different durability and audit properties:

1. **Crew/Task-level `human_input`** — a blocking console feedback loop on the agent executor. Ephemeral: lives only in the process's stdin (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/task.py:233`, `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/core/providers/human_input.py:147-264`).
2. **Hook-based approval gates** — `before_tool_call` / `before_llm_call` hooks that can call `context.request_human_input()` (blocking `input()`) or raise `HookAborted` to deny a tool/LLM call (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/hooks/tool_hooks.py:86-128`, `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/hooks/dispatch.py:64`). Also ephemeral.
3. **Flow-level `@human_feedback` with async providers** — the only mechanism that models approval as a *durable session*: a provider raises `HumanFeedbackPending`, the framework persists the full resume context (`PendingFeedbackContext`) plus flow state to SQLite (`pending_feedback` table), returns the pending object to the caller, and later restores via `Flow.from_pending(flow_id)` + `flow.resume(feedback)` (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/async_feedback/types.py:18-218`, `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/persistence/sqlite.py:96-112`, `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:1199-1266`). This is the mechanism that answers the dimension's driving question ("can an approval session survive a browser refresh?") with *yes* — it survives full process restarts.

Scoping exists but is coarse: hook approvals can be scoped by tool name and agent role (`tools=`/`agents=` filters), flow HITL is scoped per-method. There is no "approve once / approve all for N calls" memory or delegation semantics anywhere. Timeouts exist only for `Flow.ask()`; persisted pending-approval rows never expire. Auditing is event-bus-only (`HumanFeedbackRequestedEvent`/`ReceivedEvent`, `FlowPausedEvent`, `FlowInputRequested/ReceivedEvent`) plus in-memory histories; nothing durable is written by default.

**Rating: 6/10.** The Flow pause/resume model is a genuinely clear, tested, durable design with explicit protocols (`HumanFeedbackProvider`, `FlowPersistence`), which pulls the score up. But the three mechanisms are inconsistent with each other, two of three are process-bound blocking prompts, pending approvals have no TTL/expiry, and there is no durable audit trail of who approved what.

## Rating

**6 / 10** — Present but inconsistent.

- **Why not lower:** The Flow HITL subsystem has explicit public interfaces (`HumanFeedbackProvider` protocol at `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/async_feedback/types.py:221-298`; `FlowPersistence.save_pending_feedback/load_pending_feedback/clear_pending_feedback` at `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/persistence/base.py:70-116`), a real persistence implementation with WAL + cross-process file locking (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/persistence/sqlite.py:71-112`), and dedicated tests for save/load/clear/replace of pending sessions and resume behavior (`studies/agent-harness-study/sources/crewai/lib/crewai/tests/test_async_human_feedback.py:274-655`).
- **Why not higher:** No timeout/TTL on persisted approvals (only `ask()` has one); approval "decisions" are raw free-text collapsed by an LLM rather than signed decisions; hooks/console approvals cannot survive any interruption; no durable audit log (events only, in-memory history); no approve-once/approve-all semantics; three overlapping HITL APIs fragment the model.

## Answers to Dimension Questions

### 1. How is approval requested?

Three ways. (a) **Hooks**: a `PRE_TOOL_CALL` hook calls `context.request_human_input(prompt=...)`, which pauses live console rendering, prints a yellow prompt, and blocks on stdin `input()` (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/hooks/tool_hooks.py:86-128`); denial raises `HookAborted` (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/hooks/dispatch.py:64`), which the executor turns into a synthetic "Tool execution blocked by hook" tool result fed back to the LLM (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/agents/crew_agent_executor.py:962-966`). (b) **Flows**: `@human_feedback` runs `_run_human_feedback_step` after the method completes, building a `PendingFeedbackContext` and delegating to a provider (`request_feedback`) — synchronous providers return a string, async providers raise `HumanFeedbackPending` (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:3518-3604`). (c) **Tasks/Crews**: `human_input=True` triggers a rich-console panel and a prompt→re-invoke loop until the user presses Enter (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/core/providers/human_input.py:256-264, 318-369`). Additionally `Flow.ask()` is a generic mid-method input request routed through an `InputProvider` (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:3368-3516`).

### 2. Are approval sessions durable?

**Only in Flows.** When `HumanFeedbackPending` propagates, kickoff persists `{state_json, context_json}` keyed by `flow_uuid` into a dedicated SQLite table and returns the pending object instead of failing (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:2355-2406`; schema at `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/persistence/sqlite.py:96-112`). A brand-new process can reconstruct everything via `Flow.from_pending(flow_id)` and continue with `resume(feedback)` (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:1199-1266, 1285-1336`) — this survives a "browser refresh" equivalent (process death). Hook approvals, console `request_human_input`, and Task `human_input` are blocking reads of stdin: nothing is persisted; killing the process discards them. The backend is pluggable (`set_flow_persistence_factory`, `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/persistence/factory.py:31-45`).

### 3. Can approvals be scoped?

Partially. Hooks support static scoping by tool name list and agent role list (`@on(InterceptionPoint.PRE_TOOL_CALL, tools=["delete_file"], agents=["Developer"])`), implemented as filter wrappers, plus crew-local registration when declared inside `@CrewBase` (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/hooks/dispatch.py:383-421`; `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/hooks/decorators.py:42-85`). Flow HITL is scoped per decorated method, with optional routing outcomes (`emit=["approved","rejected"]`) and a global-vs-per-decorator provider chain (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:3652-3668`). **No evidence found** for dynamic scope semantics such as "approve once", "approve all for this session", allow-listing after first approval, or delegated approvers — every call site re-prompts; searched for `approve all|remember|allowlist` patterns across `lib/crewai/src`. The nearest concept is static `allowed_tools` in skill frontmatter (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/skills/models.py:53,81`), which pre-authorizes tools declaratively rather than scoping an interactive approval.

### 4. Do approvals time out?

Barely. `Flow.ask(timeout=N)` enforces a wall-clock limit using a single-thread executor and returns `None` on expiry — explicitly documented as best-effort since the underlying provider thread keeps running (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:3392-3398, 3452-3470`). Everything else has **no timeout**: hook `request_human_input` blocks on `input()` indefinitely, the console `ConsoleProvider.request_feedback` blocks indefinitely (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/async_feedback/providers.py:104-137`), and persisted `pending_feedback` rows carry `created_at` but no TTL/expiry/reaper logic — a grep for `ttl|expire` across `src/crewai/flow` returns only the `ask()` docstring. A paused flow stays resumable forever unless externally cleaned.

### 5. Are approvals audited?

Minimally and non-durably. The event bus emits typed lifecycle events — `HumanFeedbackRequestedEvent` (with an optional platform-assigned `request_id` for cross-system correlation), `HumanFeedbackReceivedEvent`, `FlowPausedEvent`, `FlowInputRequestedEvent`, `FlowInputReceivedEvent` (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/events/types/flow_events.py:115-135, 145-188, 244-287`) — so observability subscribers *can* audit, and docs show webhook integrations. But there is no dedicated approval audit sink: `human_feedback_history`/`last_human_feedback` (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:580-581, 3648-3649`) and `_input_history` (`:754, 3492-3501`) are in-memory only, and the persisted `PendingFeedbackContext.metadata` is free-form with no identity/attribution fields. Hook approvals emit no events at all — the only trace is the synthetic blocked-result string shown to the LLM. No evidence found of approval records being written to storage by default (searched `audit` across `src/`; hits are unrelated fingerprinting and task-output replay features, e.g. `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/security/fingerprint.py:4`).

## Architectural Decisions

1. **Pause-as-exception, resume-as-return-value.** `HumanFeedbackPending` is raised by providers but *returned* by `kickoff()`/`astream()` so callers handle pausing without try/except (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/async_feedback/types.py:148-167`; `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:1982-1983, 2404-2406`). The framework owns persistence, so providers only notify external systems.
2. **Serialization-first resume context.** Everything needed to resume — including the LLM config used for outcome collapsing (serialized via `to_config_dict`, API keys excluded per test `test_serialize_llm_excludes_api_key`, `studies/agent-harness-study/sources/crewai/lib/crewai/tests/test_human_feedback_integration.py:804`) and the outer execution UUID for trace continuity — is captured in a JSON-safe dataclass (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/async_feedback/types.py:71-115`).
3. **Pluggable transport via protocols.** `HumanFeedbackProvider`, `InputProvider`, and `FlowPersistence` are small protocols/ABCs with console defaults, letting Slack/webhook/DB implementations replace the terminal without touching the engine (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/async_feedback/types.py:221-298`; `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/persistence/base.py:18-36`).
4. **Denial = synthetic observation, not crash.** Blocked tool calls become the string "Tool execution blocked by hook…" returned to the agent (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/agents/crew_agent_executor.py:964-966`), keeping the loop alive and making denial visible to the model.
5. **Free-form feedback collapsed by LLM.** Rather than binary buttons, CrewAI accepts arbitrary text and uses a configured LLM to map it onto declared outcomes (`emit`), falling back through `default_outcome` → `emit[0]` (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:3606-3650, 3739+`). This trades decision integrity for conversational flexibility.

## Notable Patterns

- **Auto-checkpoint before waiting**: state is snapshotted under method name `_ask_checkpoint` prior to any `ask()`, so a crash while waiting loses nothing (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:3343-3366`).
- **One pending session per flow**: the `pending_feedback.flow_uuid` column is `UNIQUE` and inserts use `INSERT OR REPLACE`, so re-pausing overwrites the previous request — a deliberate simplification with consequences (see Failure Modes).
- **Cross-process safety**: SQLite access is wrapped in WAL mode and a named file lock from `crewai_core.lock_store` (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/persistence/sqlite.py:71-77`), and the factory docstring warns factories must return instances backed by shared durable state (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/persistence/factory.py:36-46`).
- **Resume-loop re-pause**: `resume_async_body` catches a fresh `HumanFeedbackPending` from downstream listeners and re-persists, enabling approve→revise cycles (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:1524-1557`).
- **Filter-wrapper scoping**: hook scoping implemented by wrapping functions and short-circuiting on mismatched tool/agent attributes, shared between legacy decorators and the new `@on()` dialect (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/hooks/dispatch.py:362-380`).

## Tradeoffs

- **Durability vs. simplicity**: the durable path is exclusive to Flows. Crews/tasks get only ephemeral stdin prompts — cheap to ship, useless for headless/remote deployments (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/core/providers/human_input.py:318-369`).
- **No-TTL persistence vs. operational hygiene**: keeping pending rows forever maximizes resumability but means stale approvals accumulate silently and can be resumed arbitrarily late, against possibly-changed code or policy.
- **LLM-mediated consent**: mapping prose to "approved" via an LLM (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:3623-3637`) is user-friendly but introduces misrouting risk in exactly the place where intent fidelity matters most.
- **Blocking stdin UX vs. embeddability**: pausing live console updates around `input()` gives a clean TUI but hard-couples approval to an interactive terminal, forcing anyone embedding CrewAI to reimplement providers to avoid it.
- **Events-everywhere auditability vs. zero default retention**: emitting typed events makes audit trivially addable, but out-of-the-box CrewAI retains no approval record once the process exits.

## Failure Modes / Edge Cases

- **Overwrite of concurrent pauses**: because `flow_uuid` is UNIQUE with `INSERT OR REPLACE` (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/persistence/sqlite.py:100, 229-244`), a second pause for the same flow silently replaces the first pending request; there is no queue of outstanding approvals.
- **Zombie provider threads on `ask()` timeout**: the timed-out `request_input` continues running in background; `executor.shutdown(wait=False, cancel_futures=True)` explicitly avoids joining it (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:3452-3470`), so late input is dropped and the thread leaks until natural completion.
- **Swallowed hook errors**: hook dispatch logs/swallows handler exceptions based on verbosity (`dispatch(..., verbose=_hook_verbose(context))` at `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/hooks/tool_hooks.py:164-190`); an approval gate whose prompt crashes fails open (tool proceeds) unless it raises `HookAborted`.
- **Silent degradation without persistence override**: `FlowPersistence.save_pending_feedback`'s default just calls `save_state`, dropping the resume context (`studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/persistence/base.py:87-88`); a custom backend that forgets the overrides yields flows that pause and can never resume (`from_pending` raises `ValueError`, `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:1247-1249`).
- **Empty-input ambiguity**: empty feedback means "approve/skip" everywhere (falls through to `default_outcome`/first emit option, `studies/agent-harness-study/sources/crewai/lib/crewai/src/crewai/flow/runtime/__init__.py:3618-3622`) — an accidental Enter counts as consent, and whitespace-only input is normalized to the same effect (`studies/agent-harness-study/sources/crewai/lib/crewai/tests/test_human_feedback_integration.py:732`).
