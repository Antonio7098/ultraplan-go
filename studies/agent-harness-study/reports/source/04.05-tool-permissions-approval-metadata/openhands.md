## Summary

OpenHands V1 — the `app_server` tree — defines a concrete permission model for tools that the user can enable, the agent can request, and the runtime can interrupt. Three ingredients make it work:

1. A persisted per-user **policy pair** stored on `Settings.conversation_settings`: `confirmation_mode: bool` and `security_analyzer: "llm" | "none"` (`openhands/app_server/settings/settings_models.py:108-136`). Settings round-trip through `Settings.update()` (`settings_models.py:186-260`) and the merged payload is sent to the agent-server when a conversation starts.
2. A **policy decision function** in `_select_confirmation_policy()` that maps `(confirmation_mode, security_analyzer)` to one of three SDK policy classes: `NeverConfirm`, `ConfirmRisky`, or `AlwaysConfirm` (`openhands/app_server/app_conversation/app_conversation_service_base.py:641-652`). This is the only declarative gate between model output and tool execution.
3. A typed **risk enum** on every action event — `SecurityRisk = UNKNOWN | LOW | MEDIUM | HIGH` (`frontend/src/types/v1/core/base/common.ts:59-64`) carried on `ActionEvent.security_risk` (`frontend/src/types/v1/core/events/action-event.ts:61`). The same field is what `ConfirmRisky` reads inside the SDK to decide whether to block.

The actual enforcement (the place where a `ConfirmRisky` policy halts the run, prompts the user, and waits) is not visible in this source tree — it runs inside the separate `agent-server` Docker image at `ghcr.io/openhands/agent-server:1.29.0-python` (`openhands/app_server/sandbox/sandbox_spec_service.py:16`), which imports `openhands.sdk.security` (`openhands/app_server/app_conversation/app_conversation_service_base.py:37-44`). The role of this tree is the **wiring**: choose policy, install it on the running conversation, and surface the resulting `AWAITING_USER_CONFIRMATION` state to a React UI that posts back to `/api/conversations/{id}/events/respond_to_confirmation` (`frontend/src/api/event-service/event-service.api.ts:20-40`).

What is **not** present: a per-tool allow/deny registry keyed on tool identity, args, or risk. There is no `Risk` enum on the tool definition itself (tools live in `openhands-sdk`, not here), and the confirmation policy is a single global switch — users cannot pre-approve `git push` while still requiring approval for `curl`. There is also no per-approval audit log: a "confirm" response flows over the live conversation stream (`useRespondToConfirmation` mutation, `frontend/src/hooks/mutation/use-respond-to-confirmation.ts`) but is not stored as a "user X approved tool Y" record. Sandbox isolation of bash commands comes from the gVisor runtime (`runtime_class = "gvisor"` default in `openhands/app_server/sandbox/remote_sandbox_service.py:891-894`), which is execution-environment protection — not a tool-permission mechanism.

**Can the runtime stop a high-risk tool even if the model asks for it?** Yes, when `confirmation_mode=True`. `ConfirmRisky` blocks every action whose risk classifier returns `HIGH`; `AlwaysConfirm` blocks every action unconditionally. The block is enforced inside the SDK's policy classes, and the UI surfaces a `RiskAlert` for HIGH-risk actions before letting the user click Continue (`frontend/src/components/shared/buttons/v1-confirmation-buttons.tsx:107-123`).

## Rating

**7/10** — Clear model with explicit interfaces and unit tests; the policy is centralized but its full enforcement story is split across this tree, an external SDK package, and a remote sandbox, and there is no per-approval audit log or per-tool allow/deny registry.

Rationale:
- Three explicit policy classes (`NeverConfirm`, `ConfirmRisky`, `AlwaysConfirm`) imported as named symbols (`openhands/app_server/app_conversation/app_conversation_service_base.py:37-44`); the decision function `_select_confirmation_policy` is short, readable, and has seven dedicated unit tests parametrized over the entire `security_analyzer` input space (`tests/unit/app_server/test_app_conversation_service_base.py:448-552`).
- Typed `SecurityRisk` enum is part of the V1 event schema (`frontend/src/types/v1/core/base/common.ts:59-64`) and appears on every `ActionEvent` (`frontend/src/types/v1/core/events/action-event.ts:61`). This makes risk a first-class piece of UI data, not a free-form comment.
- The model is centralized in one function (`_select_confirmation_policy`) and one transport (`_set_security_analyzer_from_settings`), both with passing test coverage for skip-when-None, skip-when-no-key, success, and failure paths (`tests/unit/app_server/test_app_conversation_service_base.py:556-718`).
- Settings persistence, transport to the agent-server, and back-end response (the user clicking "Continue") are all wired — settings round-trip in tests (`tests/unit/storage/settings/test_file_settings_store.py:52-86`, `tests/unit/storage/data_models/test_settings.py:35-36`, `tests/unit/app_server/test_settings_api.py:128-201`) and the HTTP layer is typed (`frontend/src/api/event-service/event-service.types.ts:1-8`).
- Limitations that keep this out of 8–10 range: (a) per-tool allow/deny lists are absent; users get one global `confirmation_mode` flag, not a matrix, (b) the actual enforcement code (the `ConfirmationPolicyBase.confirm()` method) is in `openhands-sdk`, not inspectable here, (c) approval decisions are not persisted as an audit trail — the user response flows back over the in-flight WebSocket/event stream, (d) the "Web overrides by Session Init" comment (`config.template.toml:228-232`) is operational inconsistency: the same config surface means different things for CLI vs. Web.

## Answers to Dimension Questions

1. **Are tools risk-classified?** Yes — every V1 action event carries `security_risk: SecurityRisk` from the `UNKNOWN|LOW|MEDIUM|HIGH` enum (`frontend/src/types/v1/core/base/common.ts:59-64`; `frontend/src/types/v1/core/events/action-event.ts:61`). The risk value is set by the SDK's `LLMSecurityAnalyzer` running inside the agent-server, whose documentation note explicitly states the classifier predicts risk for the LLM's tool call (`frontend/src/types/v1/core/events/action-event.ts:43-48`). The same data field is the predicate that `ConfirmRisky` uses to decide whether to gate an action. Tools that lack metadata receive `SecurityRisk.UNKNOWN` by default (the front-end `v1-confirmation-buttons.tsx:110` falls back to `UNKNOWN` when the awaiting action is not an `ActionEvent`). No evidence was found in this tree of an at-rest `risk_classification` registry that pre-classes tools; risk is established dynamically per-call.

2. **Are permissions enforced?** Yes — but only at the level of `confirmation_mode`. When `confirmation_mode=True` and `security_analyzer="llm"`, every HIGH-risk tool call is interrupted before execution and `AgentState.AWAITING_USER_CONFIRMATION` is set (`frontend/src/components/shared/buttons/v1-confirmation-buttons.tsx:30-105`); the runtime cannot proceed until the user clicks Confirm, which posts back to `/events/respond_to_confirmation` (`frontend/src/api/event-service/event-service.api.ts:20-40`). Enforcement is **inside the SDK** (`ConfirmationPolicyBase` subclasses `NeverConfirm`, `ConfirmRisky`, `AlwaysConfirm`); this tree just selects the policy and forwards it. There is no per-tool declarative allow/deny registry (e.g., a `permissions.json` read by the runtime) and no argument-level rule (no "deny `curl * | sh`"); the only decision variables are the user's two settings.

3. **Can users approve selectively?** Partially. The UI offers a single binary `accept: boolean` per blocked action (`frontend/src/api/event-service/event-service.types.ts:1-4`); the user cannot, for example, "approve for this turn but not for all future `rm -rf` calls." However, *which* actions reach the user is selective: under `ConfirmRisky` only HIGH-risk actions interrupt (low/medium proceed automatically), and the UI surfaces a `RiskAlert` warning before allowing confirmation of HIGH-risk actions (`frontend/src/components/shared/buttons/v1-confirmation-buttons.tsx:107-123`). Per-approval edit (rewriting the command before approving) is not supported by the V1 path. The legacy V0 button path emits `AgentState.USER_CONFIRMED` / `AgentState.USER_REJECTED` instead of a typed response body (`frontend/src/components/shared/buttons/confirmation-buttons.tsx:60-119`).

4. **Are approvals persisted?** Settings persistence is solid (`confirmation_mode` + `security_analyzer` round-trip through `Settings.update` and the V1 REST API in tests at `tests/unit/app_server/test_settings_api.py:128-201`, `tests/unit/storage/settings/test_file_settings_store.py:52-86`). **Individual approval decisions are not persisted as an audit log** — the confirm/reject response is an in-flight POST that returns to the agent-server over the conversation event stream but does not get stored as "user X approved tool Y for conversation Z at time T." The only client-side persistence is the `v1SubmittedEventIds` dedup set in `useEventMessageStore` (`frontend/src/components/shared/buttons/v1-confirmation-buttons.tsx:48,102`) which is in-memory UI state, not durable. No `approval_audit_log` table or equivalent was found in this source.

5. **Can policy block a model-requested tool?** Yes, via the SDK confirmation policies installed at conversation start. The matrix in `_select_confirmation_policy` (`openhands/app_server/app_conversation/app_conversation_service_base.py:641-652`) is the canonical gate:
   - `confirmation_mode=False` → `NeverConfirm()` (no block; risk classification still surfaces on the event)
   - `confirmation_mode=True + security_analyzer="llm"` → `ConfirmRisky()` (blocks only HIGH-risk)
   - `confirmation_mode=True + anything else` (incl. `None`, `''`, `'none'`, `'custom'`) → `AlwaysConfirm()` (blocks every action)
   
   In all three branches the model cannot force execution of a blocked action; the SDK raises a confirmation event that surfaces as `WAITING_FOR_CONFIRMATION` in this tree.

**Direct answer to the dimension question — "Can the runtime stop a high-risk tool even if the model asks for it?"** Yes when `confirmation_mode=True`. The runtime installs `ConfirmRisky` (LLM-analyzer path) or `AlwaysConfirm` (every other analyzer), the SDK holds execution until a `respond_to_confirmation` POST is received from the UI, and the React confirmation button serializes the user's choice via `useRespondToConfirmation`. When `confirmation_mode=False` the runtime installs `NeverConfirm` and the model receives no gate.

## Architectural Decisions

- **Settings as the single source of truth.** Confirmation policy is stored on `Settings.conversation_settings` (`openhands/app_server/settings/settings_models.py:108-136`); the model `_normalize_inputs()` validator (lines 326-380) routes `conversation_settings` through `ConversationSettings.from_persisted()` so the SDK owns schema versioning. There is no parallel "policy" table — the UI, REST API, agent-server transport, and SDK policy all read the same persisted blob.
- **One decision function, three policy classes.** `_select_confirmation_policy()` is the single map from `(confirmation_mode, security_analyzer)` to a `ConfirmationPolicyBase` subclass (`openhands/app_server/app_conversation/app_conversation_service_base.py:641-652`). The dispatch is exhaustive over `confirmation_mode ∈ {True, False}` and routes the four `security_analyzer` shapes (`None`, `''`, `'none'`, `'llm'`, anything else) into exactly three policy outcomes. Unknown analyzer values degrade to `AlwaysConfirm` (the safest default for users who turned confirmation on).
- **Risk is a per-event attribute, not a per-tool attribute.** Tools are not classified in advance; risk is computed each turn by the LLM-analyzer inside the agent-server and attached to the resulting `ActionEvent`. This means a single tool can be classified HIGH-risk in one context and LOW-risk in another, and the policy responds accordingly. The cost is that low/medium classifications are not deterministic across model versions.
- **Transport is HTTP, not in-process.** The policy class is constructed in this backend, but its enforcement runs in a separate Docker container (`ghcr.io/openhands/agent-server:1.29.0-python`, `openhands/app_server/sandbox/sandbox_spec_service.py:16`). `_set_security_analyzer_from_settings()` sends the analyzer payload over HTTP (`POST /api/conversations/{id}/security_analyzer` with `X-Session-API-Key`, `openhands/app_server/app_conversation/app_conversation_service_base.py:683-697`); failures log a warning but do not fail conversation creation (lines 698-703). The trade is operational split-brain if the sandbox is unreachable.
- **V0 and V1 paths coexist.** V0 actions carry an embedded `confirmation_state ∈ {awaiting_confirmation, confirmed, rejected}` and a numeric `ActionSecurityRisk` (`frontend/src/types/core/actions.ts:23-53`; `frontend/src/stores/security-analyzer-store.ts:3-16`); V1 uses the typed `SecurityRisk` enum and a state machine through `AgentState.AWAITING_USER_CONFIRMATION` (`frontend/src/components/shared/buttons/v1-confirmation-buttons.tsx:30-110`). The two paths are mapped by `use-agent-state.ts` (`frontend/src/hooks/use-agent-state.ts:32-33`) and de-duplicated by `verification-settings.tsx` (`frontend/src/routes/verification-settings.tsx:6-19`) which acknowledges the SDK 1.17.0 deprecation and awaits SDK 1.22.0 to fully remove the duplicate.
- **Sandbox isolation is environmental, not permission-based.** Bash commands run inside `runtime_class="gvisor"` by default (`openhands/app_server/sandbox/remote_sandbox_service.py:891-894`); gVisor's runsc kernel is what prevents a `rm -rf /` from leaving the container. This is belt-and-braces with the policy layer: even if a high-risk call bypassed confirmation, gVisor would contain it. The two systems are independent — toggling `confirmation_mode` does not weaken gVisor, and changing `runtime_class` does not change policy.

## Notable Patterns

- **Three-class policy enumeration.** `NeverConfirm / ConfirmRisky / AlwaysConfirm` is a tidy closed set; the decision tree in `_select_confirmation_policy` covers every `confirmation_mode × security_analyzer` combination (`openhands/app_server/app_conversation/app_conversation_service_base.py:641-652`). The intent is clear: never confirm is the bypass; confirm-risky is the LLM-classifier path; always confirm is the conservative fallback.
- **Risk enum on the event, not the tool.** Carrying `security_risk` on `ActionEvent` (`frontend/src/types/v1/core/events/action-event.ts:61`) decouples risk from tool identity. The UI can display `"HIGH"` regardless of whether the tool is `ExecuteBashAction`, `MCPToolAction`, or `BrowserNavigateAction` (`frontend/src/components/v1/chat/event-content-helpers/get-action-content.ts:28-95`).
- **Vendor-prefixed env auto-forwarding.** `AUTO_FORWARD_PREFIXES = ('LLM_', 'LMNR_')` (`openhands/app_server/sandbox/sandbox_spec_service.py:79-140`) plus `OH_AGENT_SERVER_ENV` JSON override is a clean mechanism for letting operators set policy via env without writing code; the comment block at lines 102-119 is explicit about precedence.
- **Tavily proxy via FastMCP namespace.** `"allowing sandboxes to use Tavily search without the API key being exposed"` (`openhands/app_server/mcp/mcp_router.py:50-53`) is the model for how secrets-crossing-sandbox-boundary is handled: the key lives on the app-server side, the sandbox sees only a `tavily_*` tool, and MCP routes the call back through the proxy.
- **`v1SubmittedEventIds` UI dedup.** Prevents double-clicks from posting two accept/reject bodies during a single confirmation (`frontend/src/components/shared/buttons/v1-confirmation-buttons.tsx:48,102`); the equivalent for V0 is in `event-message-store.ts`. This is operationally necessary because the user response is not idempotent at the agent-server level.
- **Type-gated legacy back-compat.** `verification-settings.tsx` uses an `excludeKeys` set to render only the canonical copy of the field (`frontend/src/routes/verification-settings.tsx:16-19`), admitting in TODO comments that this is a temporary fix until SDK 1.22.0 removes the deprecated `VerificationSettings.{confirmation_mode, security_analyzer}` fields.

## Tradeoffs

- **Global confirmation flag vs. per-tool matrix.** The single `confirmation_mode` boolean is easy to explain and test; the cost is that there is no way to say "auto-approve `git commit` but require approval for `git push`". Users who want fine-grained control have to write custom MCP tools or rely on `AlwaysConfirm` always.
- **LLM-classified risk vs. declared risk.** `LLMSecurityAnalyzer` makes per-tool risk dynamic and context-aware, but the prediction is non-deterministic, depends on model version, and may misclassify outright (e.g., `rm -rf /tmp/scratch` flagged LOW when it should be HIGH). No static, auditable pre-classification is available.
- **HTTP transport of policy vs. in-process API call.** `_set_security_analyzer_from_settings` is `async` and crosses the network (`openhands/app_server/app_conversation/app_conversation_service_base.py:683-697`); local-failure isolation is handled (warn-and-continue, line 700-703) but the conversation may begin with the agent-server's default policy if the POST fails, silently. No retry, no idempotency key.
- **Settings overrides in Web vs. CLI.** The `config.template.toml` `[security]` section comment is explicit that CLI uses these flags but Web is overridden by Session Init (`config.template.toml:228-232`). This means the same product surface behaves differently across deployment modes — a source of operator confusion.
- **RiskAlert only renders for HIGH severity.** The component's `if (severity === "high")` early-return with `return null` otherwise means medium- and low-risk approvals are invisible to the user (`frontend/src/components/shared/risk-alert.tsx:19-35`). The V1 path calls it only for HIGH, and the V0 path does not call it at all — so MEDIUM risk never triggers a UI banner, despite the risk enum existing.
- **De-duplication across two settings locations.** `agent_settings.verification` still carries `confirmation_mode` / `security_analyzer` for back-compat, and only a manual `excludeKeys` set (`frontend/src/routes/verification-settings.tsx:16-19`) prevents the field from rendering twice. This is acknowledged technical debt (`TODO: drop this set once openhands-sdk 1.22.0 lands`).
- **No audit log of user approvals.** The `ConfirmationResponseRequest { accept, reason? }` (`frontend/src/api/event-service/event-service.types.ts:1-4`) is observed but not persisted as an event of its own. `reason` is captured but unused anywhere visible — a future audit feature would need new wiring on both the agent-server and app-server sides.

## Failure Modes / Edge Cases

- **`confirmation_mode=False` silently disables the lock.** The `ConfirmationModeEnabled` lock icon returns `null` whenever the flag is false (`frontend/src/components/features/chat/confirmation-mode-enabled.tsx:7-26`), so users who flip the toggle off cannot see a confirmation that high-risk actions are now bypassing approval. Default in `DEFAULT_SETTINGS` is `false` (`frontend/src/services/settings.ts:13`), meaning new users start in bypass mode unless they explicitly enable confirmation.
- **Unknown analyzer strings silently degrade.** `_create_security_analyzer_from_string("custom")` logs a warning and returns `None` (`openhands/app_server/app_conversation/app_conversation_service_base.py:635-639`); a future deployment that adds a new analyzer class will silently fall back to no-analyzer — i.e., `AlwaysConfirm` if the user kept `confirmation_mode=True`. There is no schema-level enforcement of allowed strings, only a runtime string comparison.
- **Transport failure is non-fatal.** `_set_security_analyzer_from_settings` catches `Exception` and warns rather than raising (`openhands/app_server/app_conversation/app_conversation_service_base.py:698-703`). A network partition between the app-server and the agent-server will leave the conversation running with whatever analyzer was already installed (default = none), not surface the failure to the user. The test `test_set_security_analyzer_logs_warning_on_failure` (`tests/unit/app_server/test_app_conversation_service_base.py:682-718`) codifies this behavior.
- **No idempotency key for the security-analyzer POST.** Two concurrent `_set_security_analyzer_from_settings` calls (e.g., race between two different conversations writing the same user setting) will both POST — there is no request id, so the agent-server must dedupe at its own level.
- **MCP tools carry no risk declaration.** `@mcp_server.tool()` definitions in `mcp_router.py:147-487` do not declare a risk class. The runtime will fall back to whatever the LLM-analyzer assigns at call-time, so a `create_pr` tool that pushes production code may be classified LOW by the model and bypass confirmation. The proxy API key at `Tavily` is protected by *transport boundary*, not by *risk approval*.
- **`user_id` / `session_api_key` mismatch.** The endpoint requires `X-Session-API-Key` and the test `test_set_security_analyzer_skips_when_no_session_key` (`tests/unit/app_server/test_app_conversation_service_base.py:555-583`) confirms the early return. But the `HEADERS={'X-Session-API-Key': session_api_key}` literal construction on line 691 means a single typo in env propagation translates to silent skip rather than a visible 401.
- **V0/V1 split risk double-classification.** The same `frontend/__tests__/components/v1/chat/event-message-think-action.test.tsx:54,85` test references `SecurityRisk.UNKNOWN` (`SecurityRisk.UNKNOWN = "UNKNOWN"`); if a deprecated `ActionSecurityRisk.UNKNOWN = -1` (numeric) were ever wired through the V1 schema, the comparison `risk === SecurityRisk.HIGH` on `v1-confirmation-buttons.tsx:112` would always be false. The split is intentional but fragile.
- **RiskAlert not yet wired to MEDIUM/LOW.** The component only renders when `severity === "high"` (`frontend/src/components/shared/risk-alert.tsx:19-35`). Even if `risk === SecurityRisk.MEDIUM` flows into the confirmation panel, `RiskAlert` will render `null`. The inline comment confirms this is by design ("Currently, we are only supporting the high risk alert").

## Future Considerations

- Persist approval decisions server-side as part of the conversation event stream (similar to `ActionEvent`) so that audit logs and post-hoc analysis become possible — the typed `ConfirmationResponseRequest { accept, reason? }` payload (`frontend/src/api/event-service/event-service.types.ts:1-4`) is already structured to carry a reason.
- Allow the security-analyzer string set to be schema-validated (e.g., Pydantic `Literal["llm", "none"]`) so unknown strings are rejected at the settings boundary instead of silently logged at transport time (`openhands/app_server/app_conversation/app_conversation_service_base.py:635-639`).
- Add a per-tool allow/deny list to the `ConversationSettings` model so `confirm_risky(["execute_bash", "ipython"])` becomes expressible without user-supplied wrappers. The SDK's `ConfirmRisky` already accepts a `RISKY_SAFE`-style classified set; this tree would only need to wire it through.
- Wire `RiskAlert` for `MEDIUM` severity as well — the component is already structured for it (`frontend/src/components/shared/risk-alert.tsx:4-36`), the consumer at `v1-confirmation-buttons.tsx:112-122` is already gate-gated, and the comment explicitly says the change is wanted.
- Reduce the V0/V1 split: drop the deprecated `VerificationSettings.{confirmation_mode, security_analyzer}` once SDK 1.22.0 lands (`frontend/src/routes/verification-settings.tsx:13-15`) and let the `excludeKeys` shim be deleted. After that, the legacy `confirmation-buttons.tsx` path can be retired.
- Add retries with idempotency keys to `_set_security_analyzer_from_settings` so that a flaky network does not leave a conversation running with a stale analyzer (`openhands/app_server/app_conversation/app_conversation_service_base.py:683-697`).
- Surface a banner when `confirmation_mode` is toggled off so users understand the model is no longer gated; the current `ConfirmationModeEnabled` (`frontend/src/components/features/chat/confirmation-mode-enabled.tsx:7-26`) renders only when the flag is on and provides no symmetric warning when it is off.

## Questions / Gaps

- **No evidence in this tree that `confirm_risky` differentiates by tool identity.** The SDK's `ConfirmRisky` was characterized as "block only on HIGH-risk actions (per LLM classifier)"; whether the SDK supports a configurable deny-list of `(tool_name, args-pattern)` pairs is **not visible in this source**. Future analysis should inspect `openhands-sdk/openhands/sdk/security/risk.py` (if it exists) directly.
- **`ConfirmationPolicyBase.confirm()` semantics.** The runtime's `AsyncRemoteWorkspace` (`openhands/app_server/app_conversation/app_conversation_service_base.py:46`) drives the policy inside the agent-server; this tree ships the policy class via HTTP but does not show what happens when the user neither confirms nor rejects within a timeout, nor whether a re-asking loop is implemented.
- **`v1SubmittedEventIds` lifetime.** The dedup set is in `useEventMessageStore` (`frontend/src/components/shared/buttons/v1-confirmation-buttons.tsx:48,102`) — no persistence boundary is mentioned; whether it survives page reload, conversation archival, or restart is not in this code.
- **`reason` field in confirmation requests is unused.** `ConfirmationResponseRequest.reason?: string` (`frontend/src/api/event-service/event-service.types.ts:1-4`) is declared but no consumer in this tree references it; the agent-server side may or may not persist it.
- **No tool-risk registry.** `toolsByName` style catalogs (à la LangGraph's `tools_by_name`) do not exist in this backend because the tool implementations themselves are in `openhands-sdk`. As a result, there is **no at-rest place** in this source tree that lists which tools are considered HIGH-risk *a priori* — risk is purely LLM-predicted per call.
- **`ConfirmationResponseResponse { success: boolean }`** is the only field returned (`frontend/src/api/event-service/event-service.types.ts:6-8`); there is no per-action outcome, no error envelope (see dimension 04.06), and no link back to the policy class that produced the interrupt.
- **Behavior of `confirm_risky` for non-V1 actions.** The V0 path sends `AgentState.USER_CONFIRMED` via the chat socket (`frontend/src/components/shared/buttons/confirmation-buttons.tsx:60-119`) instead of a typed HTTP body; the resulting server-side handling is not in this source tree (it would be in the V0 runtime / web client). How the two paths reconcile on the same conversation is not documented here.
