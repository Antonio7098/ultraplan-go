## Summary

Letta implements a deliberate, first-class secrets model centered on an encrypted-at-rest `Secret` value type (`studies/agent-harness-study/sources/letta/letta/schemas/secret.py:13`) backed by AES-256-GCM with PBKDF2 key derivation (`studies/agent-harness-study/sources/letta/letta/helpers/crypto_utils.py:104`). Secrets exist in three tiers: (1) server/operator credentials configured via env vars or YAML config (`studies/agent-harness-study/sources/letta/letta/settings.py:22`, `studies/agent-harness-study/sources/letta/letta/settings.py:114`), (2) per-organization sandbox env vars and per-agent "secrets" stored encrypted in Postgres/SQLite and injected into tool sandboxes as environment variables at execution time (`studies/agent-harness-study/sources/letta/letta/services/sandbox_config_manager.py:210`, `studies/agent-harness-study/sources/letta/letta/services/tool_sandbox/base.py:476`), and (3) provider/MCP credentials stored via the same `Secret` type (`studies/agent-harness-study/sources/letta/letta/schemas/providers/base.py:39`, `studies/agent-harness-study/sources/letta/letta/schemas/mcp.py:39`). Identity is handled by a separate first-class `Identity` primitive bound to organizations, projects, and agents (`studies/agent-harness-study/sources/letta/letta/schemas/identity.py:44`), while request identity comes from a client-supplied `user_id` header with a default-actor fallback that can be disabled by a security flag (`studies/agent-harness-study/sources/letta/letta/server/rest_api/dependencies.py:38`, `studies/agent-harness-study/sources/letta/letta/services/user_manager.py:113`).

The model is strong where it is explicit (encrypted columns, masked `__str__`/`__repr__`, export scrubbing, dedicated tests) but inconsistent at the observability boundary: decrypted sandbox env vars are written verbatim into OTEL trace events (`studies/agent-harness-study/sources/letta/letta/services/tool_sandbox/e2b_sandbox.py:90`), MCP bearer tokens are returned unmasked in REST responses (`studies/agent-harness-study/sources/letta/letta/schemas/mcp_server.py:313`), and without `LETTA_ENCRYPTION_KEY` set, secrets silently degrade to plaintext storage (`studies/agent-harness-study/sources/letta/letta/schemas/secret.py:55`). There is no global log/trace redaction filter anywhere in the codebase.

## Rating

**6 / 10** — A clear and tested encryption model with explicit interfaces (`Secret`, `CryptoUtils`, `value_enc` columns, export scrubbing) earns the upper-middle band of the rubric ("clear model with tests, explicit interfaces"), but operational safeguards leak at the edges: trace-event logging of raw env var dicts, plaintext fallback when the master key is absent, dual plaintext+encrypted OAuth columns, and unmasked MCP tokens in API responses keep it out of the 7–8 band.

## Answers to Dimension Questions

**1. Can the model see secrets?**
Not directly. Secrets are never rendered into prompts or context messages; they reach tools exclusively through the sandbox process environment assembled in `studies/agent-harness-study/sources/letta/letta/services/tool_sandbox/base.py:476-517`. However, two indirect exposures exist: (a) sandboxed tool code runs with all decrypted env vars available to `os.environ` and can print them into `stdout`, which is fed back to the model as tool output (`studies/agent-harness-study/sources/letta/letta/services/tool_executor/tool_execution_sandbox.py:102-106`); (b) the injected `agent_state` pickle embedded in generated sandbox code contains the full `AgentState.secrets` list including decrypted values (`studies/agent-harness-study/sources/letta/letta/schemas/agent.py:122-124`, `studies/agent-harness-study/sources/letta/letta/schemas/agent.py:176-182`, serialization at `studies/agent-harness-study/sources/letta/letta/services/tool_executor/tool_execution_sandbox.py:526-528`), so anything executing in the sandbox can read them programmatically.

**2. Can tools use secrets without exposing them?**
Yes, by design: env-var injection keeps credentials out of LLM-visible tool arguments and context entirely; MCP HTTP configs additionally support `{{ VAR }}` templating so tokens stored as sandbox env vars are substituted at connect time (`studies/agent-harness-study/sources/letta/letta/functions/mcp_client/types.py:194-202`), and the optional credentials webhook lets operators deliver per-run secrets that never touch agent memory (`studies/agent-harness-study/sources/letta/letta/services/sandbox_credentials_service.py:45-59`). The caveat is that exposure moves to the telemetry plane instead (see Q3): any secret delivered this way lands in OTEL event attributes for E2B executions.

**3. Are secrets redacted in traces?**
Partially, inconsistently. Positive: `Secret` objects mask themselves in logs/reprs (`studies/agent-harness-study/sources/letta/letta/schemas/secret.py:271-279`), agent exports wipe secret values (`studies/agent-harness-study/sources/letta/letta/services/agent_serialization_manager.py:240-244`), and deprecated provider plaintext fields are nulled in responses (`studies/agent-harness-study/sources/letta/letta/services/provider_manager.py:350-352`). Negative: the E2B execution-start OTEL event logs the entire decrypted `env_vars` mapping (`studies/agent-harness-study/sources/letta/letta/services/tool_sandbox/e2b_sandbox.py:90-99`, legacy equivalent at `studies/agent-harness-study/sources/letta/letta/services/tool_executor/tool_execution_sandbox.py:360-363`), `log_event` applies no filtering (`studies/agent-harness-study/sources/letta/letta/otel/tracing.py:484-496`), and MCP server REST payloads include the decrypted bearer token (`studies/agent-harness-study/sources/letta/letta/schemas/mcp_server.py:313-338`). No regex/pattern-based redaction filter exists for logs or traces anywhere in the repo (searches for `redact`, `mask`, `scrub`, `SENSITIVE` returned only reasoning-content handling, export scrubbing, and unrelated loss-mask code). So today, **an E2B tool-execution trace cannot be shared without leaking whatever credentials were injected into that run's sandbox**.

**4. Are identities scoped per user/task?**
Organization scope is enforced consistently (identity queries filter by actor org, `studies/agent-harness-study/sources/letta/letta/services/identity_manager.py:51-58`; env vars carry `OrganizationMixin`, `studies/agent-harness-study/sources/letta/letta/orm/sandbox_config.py:38-60`). Task-level granularity is supported structurally: agent-scoped env vars override org-global ones (`studies/agent-harness-study/sources/letta/letta/services/tool_sandbox/base.py:476-506`), identities attach to projects/agents (`studies/agent-harness-study/sources/letta/letta/schemas/identity.py:44-53`), and MCP OAuth sessions are per-user rows (`studies/agent-harness-study/sources/letta/letta/orm/mcp_oauth.py:21-31`). But the runtime trust anchor is weak: the acting user comes from an unauthenticated client header, and unless `no_default_actor=true`, requests without it silently execute as a shared default user (`studies/agent-harness-study/sources/letta/letta/services/user_manager.py:113-133`). The webhook broker can further specialize credentials per tool/agent since its payload carries `tool_name` and `agent_id` (`studies/agent-harness-study/sources/letta/letta/services/sandbox_credentials_service.py:50-53`).

## Architectural Decisions

1. **A typed `Secret` value object instead of scattered string handling.** All new credential fields (provider keys, MCP tokens, env var values, OAuth tokens) converge on one Pydantic-integrated type whose serializer stores ciphertext and whose repr masks plaintext (`studies/agent-harness-study/sources/letta/letta/schemas/secret.py:291-343`). This makes accidental logging the exception rather than the rule.
2. **Application-level envelope encryption over DB-level encryption.** AES-256-GCM with per-value salt/IV and PBKDF2 derivation happens in Python against a single `LETTA_ENCRYPTION_KEY` (`studies/agent-harness-study/sources/letta/letta/helpers/crypto_utils.py:104-150`), keeping the SQLite/Postgres split simple at the cost of CPU cost management concerns visible throughout (async wrappers, dedicated crypto thread pool, lru-cached key derivation — `studies/agent-harness-study/sources/letta/letta/helpers/crypto_utils.py:19`, `studies/agent-harness-study/sources/letta/letta/helpers/crypto_utils.py:61-101`).
3. **Decrypt-as-late-as-possible injection pipeline.** Values stay encrypted in DB and in transit through managers; decryption happens in the last step before subprocess/E2B launch (`studies/agent-harness-study/sources/letta/letta/services/sandbox_config_manager.py:322-340` → `studies/agent-harness-study/sources/letta/letta/services/tool_sandbox/base.py:489-493`).
4. **Layered precedence for environment configuration.** OS env < org-global sandbox vars < provided vars < agent vars < call-time additions, with identity context injected as `LETTA_AGENT_ID`/`LETTA_PROJECT_ID`/`LETTA_TOOL_ID` (`studies/agent-harness-study/sources/letta/letta/services/tool_sandbox/base.py:476-517`) — giving multi-tenant override semantics in a flat namespace.
5. **Pluggable credential sourcing.** Beyond static env vars, an outbound webhook can mint credentials per (user, org, tool, agent) tuple (`studies/agent-harness-study/sources/letta/letta/services/sandbox_credentials_service.py:19-70`), anticipating short-lived, task-scoped secrets.
6. **Multi-tenant hardening by default for risky transports.** MCP stdio (which spawns local processes) is disabled unless explicitly opted in (`studies/agent-harness-study/sources/letta/letta/settings.py:45-54`), and a kill-switch exists for the default-actor fallback (`studies/agent-harness-study/sources/letta/letta/settings.py:466-469`).
7. **Deprecated-but-present plaintext columns.** Rather than dropping `value`/`access_token` columns, they are retained NOT NULL, written as empty strings or NULL, and documented as deprecated (`studies/agent-harness-study/sources/letta/letta/orm/sandbox_config.py:49`, `studies/agent-harness-study/sources/letta/letta/orm/provider.py:35`) — a migration-friendly but attack-surface-preserving choice.

## Notable Patterns

- **Masking-by-type:** `<Secret: ****>` repr plus a regression test asserting the plaintext never appears in `str()` output (`studies/agent-harness-study/sources/letta/letta/schemas/secret.py:271-279`; `studies/agent-harness-study/sources/letta/tests/test_secret.py:121-140`).
- **Heuristic plaintext detection:** `CryptoUtils.is_encrypted` excludes well-known API-key prefixes (`sk-`, `ghp_`, `AKIA`, `xoxb-`, …) to avoid double-encrypting or misdetecting real keys (`studies/agent-harness-study/sources/letta/letta/helpers/crypto_utils.py:23-41`, `studies/agent-harness-study/sources/letta/letta/helpers/crypto_utils.py:303-322`), with dedicated tests (`tests/test_crypto_utils.py:241-335`).
- **Async-first crypto ergonomics:** every blocking operation has an `_async` twin plus bounded-concurrency batch helpers so PBKDF2 (100–500 ms) never blocks the event loop or exhausts DB pools (`studies/agent-harness-study/sources/letta/letta/schemas/secret.py:71-135`; `studies/agent-harness-study/sources/letta/letta/utils.py:1546-1578`).
- **Export/import hygiene:** secret values are blanked at both the service layer (`studies/agent-harness-study/sources/letta/letta/services/agent_serialization_manager.py:240-244`) and the marshmallow dump hook (`studies/agent-harness-study/sources/letta/letta/serialize_schemas/marshmallow_agent.py:211-221`), then re-settable at load time.
- **Deprecation guardrails via dunder interception:** reading/writing legacy plaintext provider fields triggers warnings (`studies/agent-harness-study/sources/letta/letta/schemas/providers/base.py:43-56`) — steering callers toward `_enc` fields while preserving compatibility.

## Tradeoffs

- **Encryption opt-in by omission:** with no `LETTA_ENCRYPTION_KEY`, secrets are written *in cleartext into the `_enc` column* with only a warning (`studies/agent-harness-study/sources/letta/letta/schemas/secret.py:55-69`; test codifying the behavior at `tests/test_secret.py:36-54`). Availability was chosen over fail-closed security.
- **PBKDF2-per-value vs KMS:** deriving a fresh key per secret with 100k iterations is portable and stateless but expensive enough that the codebase grows caching/thread-pool machinery around it (`studies/agent-harness-study/sources/letta/letta/helpers/crypto_utils.py:56-101`); a managed KMS would remove both cost and the "single master key in env" risk.
- **Observability vs secrecy:** rich tracing (full code + env vars per E2B execution, raw provider request/response persistence, `llm_api_logging` default true at `studies/agent-harness-study/sources/letta/letta/settings.py:382-387`) maximizes debuggability but turns trace backends (OTLP collectors, ClickHouse, Postgres) into secret stores.
- **API usability vs exposure:** returning decrypted MCP tokens in server-config responses simplifies client round-tripping (`studies/agent-harness-study/sources/letta/letta/schemas/mcp_server.py:313-338`) but violates write-only secret hygiene applied elsewhere.
- **Header-based actor identity:** skipping mandatory auth keeps self-hosted/desktop usage frictionless (`studies/agent-harness-study/sources/letta/letta/server/rest_api/dependencies.py:38-39`), deferring real tenancy enforcement to deployments that flip `no_default_actor` and put an authenticating proxy in front.

## Failure Modes / Edge Cases

- **Trace leakage (highest impact):** any E2B tool execution publishes decrypted sandbox env vars — potentially org-wide provider keys — into OTEL spans exported to third-party backends (`studies/agent-harness-study/sources/letta/letta/services/tool_sandbox/e2b_sandbox.py:90-99`).
- **Key-loss unrecoverability:** losing `LETTA_ENCRYPTION_KEY` permanently corrupts all `_enc` data; the decrypt path then guesses "maybe it was plaintext" via heuristics (`studies/agent-harness-study/sources/letta/letta/schemas/secret.py:196-213`).
- **False-positive encryption detection:** long alphanumeric API keys resembling base64 ≥45 bytes can be misclassified; mitigated by the prefix list, which is inherently incomplete for novel providers (`studies/agent-harness-study/sources/letta/letta/helpers/crypto_utils.py:303-322`).
- **Cross-run interference in legacy local mode:** `run_local_dir_sandbox_directly` swaps the entire server-process `os.environ` mid-request (`studies/agent-harness-study/sources/letta/letta/services/tool_executor/tool_execution_sandbox.py:114-122`, `:272`); concurrent executions on shared threads could observe each other's credentials. The newer subprocess-based sandbox avoids this (`studies/agent-harness-study/sources/letta/letta/services/tool_sandbox/local_sandbox.py:139-145`).
- **Sandbox-side exfiltration:** because secrets are plain env vars inside the sandbox and `AgentState.secrets` rides along in the pickled payload (`studies/agent-harness-study/sources/letta/letta/services/tool_executor/tool_execution_sandbox.py:526-528`), malicious or buggy tool code can trivially echo credentials into results/logs; there is no allowlist filtering of which env vars enter the sandbox.
- **Default-actor confusion:** without `no_default_actor`, omitted headers attribute actions and secrets access to a universal default user (`studies/agent-harness-study/sources/letta/letta/services/user_manager.py:113-133`), collapsing per-task audit trails.
- **Modal baking staleness:** env vars are baked into deployed Modal apps at deploy time (`studies/agent-harness-study/sources/letta/letta/services/tool_manager.py:1303-1319`); rotating a secret requires re-deployment or stale credentials persist.

## Future Considerations

- Redact or allowlist attributes in `log_event`/`trace_method` (e.g., drop or mask `env_vars` keys matching secret sources) so traces can be shared safely — directly addressing the dimension's guiding question (`studies/agent-harness-study/sources/letta/letta/otel/tracing.py:484-496`).
- Fail closed or loudly surface "encryption disabled" state (startup banner + health endpoint) instead of silent plaintext fallback; optionally refuse writes of agent secrets when the key is absent.
- Mask MCP tokens in API responses (echo last 4 chars only), aligning MCP with provider behavior (`studies/agent-harness-study/sources/letta/letta/schemas/mcp_server.py:313-338` vs `studies/agent-harness-study/sources/letta/letta/services/provider_manager.py:350-352`).
- Drop residual plaintext columns (`providers.api_key`, `mcp_oauth.access_token`/`refresh_token`/`client_secret`) once migration windows close (`studies/agent-harness-study/sources/letta/letta/orm/provider.py:35`; `studies/agent-harness-study/sources/letta/letta/orm/mcp_oauth.py:41-54`).
- Filter which env vars are serialized into the sandbox `agent_state` pickle, or stop embedding secrets in `AgentState` handed to tool code.
- Consider per-org or per-agent derived encryption keys (HKDF from master + org id) so a leaked org database subset cannot be decrypted wholesale, and short-lived credentials via the existing webhook mechanism as the default rather than an option.

## Questions / Gaps

If redaction exists, it lives outside this repository (e.g., in the OTel collector config under `otel/`, which contains only compose wiring, not processors).
