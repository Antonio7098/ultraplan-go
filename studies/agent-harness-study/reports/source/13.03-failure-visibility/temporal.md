## Summary

Temporal implements failure visibility as a deliberate per-stakeholder pipeline rather than a single error channel. **Program-facing (the "model" analog)**: failures are first-class protobuf data (`failurepb.Failure`) that drive retry semantics — the server reads `ApplicationFailureInfo.NonRetryable`, timeout types, and worker-supplied `NextRetryDelay` to decide backoff (`service/history/workflow/retry.go:31-64`, `common/retrypolicy/retry_policy.go:27-62`), and every workflow-task failure is persisted as a `WorkflowTaskFailedEvent` in durable history that workers replay (`service/history/workflow/workflow_task_state_machine.go:889-970`). Oversized worker failures are replaced with a non-retryable server failure whose cause is truncated to the warn-size budget (`service/frontend/workflow_handler.go:1293-1310`, `common/failure/failure.go:48-91`). **User-facing (gRPC clients; CLI/Web UI live in separate repos)**: internal/unknown errors are masked by default into "something went wrong, please retry (<hash>)" with a correlation hash, while the full error is logged server-side with the same hash (`common/rpc/interceptor/mask_internal_error.go:21,67-112`; key `frontend.maskInternalErrorDetails` defaults true, `common/dynamicconfig/constants.go:874-878`). **Developer-facing**: a central request error handler classifies expected-vs-unexpected errors by gRPC code and Go type, records typed metrics, and suppresses noisy-but-expected errors unless a namespace opts in via `system.logAllReqErrors` (`common/rpc/interceptor/request_error_handler.go:56-184`, `common/dynamicconfig/constants.go:3637-3641`), with workflow context extracted from requests and task tokens onto every log line (`common/rpc/interceptor/logtags/workflow_tags.go:32-63`). **Operator-facing**: a metrics taxonomy separates unexpected `service_errors` from all `service_error_with_type` plus specialized counters for resource exhaustion and nondeterminism (`common/metrics/metric_defs.go:657-665,687,693`); task processing escalates repeated failures to "Critical error processing task" logs after 30 attempts and routes terminal failures to DLQs with an operator runbook keyed on exact log lines (`service/history/queues/executable.go:104,582-624`; `docs/admin/dlq.md:28-44`). The design's core tradeoff: users get safety-by-default masking with hash-based escalation paths, while full detail remains durably available to operators through logs, metrics, DLQs, and history events.

## Answers to Dimension Questions

**1. Is the model informed of failures?**
Yes — richly, because in Temporal the autonomous program (SDK/worker) is the primary consumer and failures are protocol-level data. Every activity/workflow-task failure persists as a structured `failurepb.Failure` inside history events (`service/history/workflow/workflow_task_state_machine.go:889-943`), and the same structure drives server behavior: retry eligibility is computed from failure fields (`NonRetryable` flags, timeout types, terminated/canceled info — `common/retrypolicy/retry_policy.go:27-62`), and workers can even steer retry timing via `ApplicationFailureInfo.NextRetryDelay` (`service/history/workflow/retry.go:55-64`). Server-generated failures (timeouts, size limits) use distinct failure-info types with `Source: "Server"` so programs can distinguish them from application errors (`common/failure/failure.go:36-46`). The one deliberate degradation: when a failure payload exceeds blob limits it is replaced by a non-retryable ServerFailure whose cause chain is byte-truncated (`service/frontend/workflow_handler.go:1293-1310`, `common/failure/failure.go:48-91`) — the program learns *that* it failed and why (size), but loses deep root-cause detail.

**2. Is the user informed appropriately?**
Mostly yes, by design. External users (SDK/CLI/UI over gRPC — the CLI and Web UI themselves live in separate repos and are outside this source) get: (a) masked neutral messages for Internal/Unknown errors with a correlation hash, enabled by default per namespace (`common/rpc/interceptor/mask_internal_error.go:67-87`, `common/dynamicconfig/constants.go:874-878`); (b) actionable remapped errors where internals would leak nothing useful — shard ownership loss becomes "shard unavailable, please backoff and retry" (`common/rpc/interceptor/frontend_service_error.go:41-42`); (c) machine-readable resource-exhaustion signals in response headers (`frontend_service_error.go:45-49`); (d) structured typed errors with gRPC details for programmatic handling (`common/serviceerror/shard_ownership_lost.go:35-45`, `convert.go:11-57`). Durable failure facts remain queryable by any user via history events, including continued-as-new runs carrying their predecessor's failure forward (`service/history/api/get_history_util.go:617-628`). The gap: a masked error alone leaves the user unable to self-diagnose — recovery requires an operator to search logs for the hash.

**3. Can developers debug failures?**
Strongly. Three coordinated channels: (a) every RPC error is centrally classified and logged with operation, namespace, grpc code, and workflow identity extracted even from opaque task tokens (`common/rpc/interceptor/request_error_handler.go:75-97`; `logtags/workflow_tags.go:32-63`); (b) task-processing failures accumulate attempt counters and structured tags, escalating to critical-level logging after 30 attempts (`service/history/queues/executable.go:582-595`), with panics captured alongside stack traces (`executable.go:325-338`); (c) nondeterminism — the hardest workflow bug class — gets a dedicated log line and metric at the point of report (`service/frontend/workflow_handler.go:1312-1319`). Infrastructure hardening keeps debug channels trustworthy under stress: log-field marshaling cannot panic the process (`common/log/zap_logger.go:50-77`) and invariant violations DPanic instead of silently proceeding (`common/serviceerror/service_error_with_dpanic.go:8-12`). Caveat: expected errors (including all context deadlines and ResourceExhausted) are log-suppressed unless the namespace enables `system.logAllReqErrors` (`request_error_handler.go:84-91`), so debugging latency-related failures requires flipping a config.

**4. Can operators detect failure patterns?**
Yes, with strong primitives but no shipped dashboards. The metric layer distinguishes total errors by type (`service_error_with_type`) from genuinely unexpected ones (`service_errors`) — preventing alert fatigue from client-caused 4xx-class errors (`common/metrics/metric_defs.go:657-665`) — and adds specialized counters for resource exhaustion with cause/scope tags (`metric_defs.go:687`, recorded with tags at `request_error_handler.go:102-109`), nondeterminism (`metric_defs.go:693`), and query success/timeout/failure splits (`service/history/api/queryworkflow/api.go:444-479`). Poisoned tasks are quarantined into DLQs with regex-based routing config (`history.TaskDLQErrorPattern`, `common/dynamicconfig/constants.go:2918-2922`), and an in-repo runbook maps exact log lines to investigation steps and admin purge/merge commands (`docs/admin/dlq.md:28-60`, `service/frontend/admin_handler.go:1876,1914`). OTel tracing and wide events provide higher-cardinality analysis (`common/telemetry/grpc.go:38-75`, `common/wideevents/events.go:12-52`). What was not evidenced: reference Grafana dashboards or alert rules in-repo — the provisioning directory points at an empty dashboard folder (`develop/docker-compose/grafana/provisioning/dashboards/dashboard.yml:1-13`).

## Architectural Decisions

1. **Failures are protocol data, not just exceptions.** The `failurepb.Failure` graph (typed failure-info oneofs, cause chains, stack traces) is the canonical currency between server, workers, and history storage (`common/failure/failure.go:14-46`). This lets the *same* object inform retry decisions (`retry.go:31-64`), persist as audit trail (`workflow_task_state_machine.go:931-948`), and surface to user queries — one representation, three consumers.
2. **Mask by default, correlate by hash.** Instead of choosing between secrecy and debuggability, Internal/Unknown errors are replaced by a neutral message plus an 8-hex hash of the original message (`mask_internal_error.go:80-86`, `common/util.go:409-414`); the full error lands in server logs carrying the identical hash (`mask_internal_error.go:89-111`). Support conversations become join-able on the hash string.
3. **Layered sanitization with documented ordering.** The frontend chains mask-interceptor → service-error-interceptor (length cap, DataLoss normalization) → frontend-remap-interceptor (friendly Unavailable messages, exhaustion headers) outermost, with in-code comments declaring the intent (`service/frontend/fx.go:286-315`). Each layer narrows what escapes without duplicating logic.
4. **Expected/unexpected split as the noise firewall.** One central handler decides, per error, whether it is a normal outcome (client mistake, cancellation, namespace throttling) or a genuine server failure, and only the latter increments the `service_errors` alerting metric and writes error logs by default (`request_error_handler.go:64-116`). Namespace-scoped `system.logAllReqErrors` restores full fidelity when needed.
5. **Escalation ladders instead of silent retries.** Repeated unexpected task failures escalate log severity after 30 attempts (`executable.go:591-595`), then route to DLQ with a doc-synced marker log line (`executable.go:603-618`), giving operators a deterministic trail from symptom to remediation runbook (`docs/admin/dlq.md:32-60`).
6. **Detail preservation under resource constraints.** When payloads exceed limits, information is truncated in priority order (NonRetryable flag → Source/Message/StackTrace → cause chain within depth 20) rather than discarded wholesale (`common/failure/failure.go:52-91`), keeping retry semantics intact even for oversized failures.

## Notable Patterns

- **Dual-channel masked errors:** the user receives `"something went wrong, please retry (%s)"` while the same call site emits `tag.Error(err)` plus `tag.String("hash", ...)` into logs (`mask_internal_error.go:82-86,106-111`) — visibility split by audience from a single interception point.
- **Typed gRPC details round-trip:** server-local error structs serialize domain fields (e.g., owner/current host) into proto `errordetailsspb` on the status, and `FromStatus` rebuilds the typed error at the receiving service (`shard_ownership_lost.go:35-45`, `convert.go:16-56`), so cross-service hops preserve programmatic handleability.
- **Config-as-taxonomy:** nearly every visibility knob is a named dynamic-config setting with docstring and default (`frontend.maskInternalErrorDetails`, `system.maxServiceErrorMessageLength`, `system.logAllReqErrors`, `history.TaskDLQErrorPattern`), all discoverable in one file (`common/dynamicconfig/constants.go:874-878,2918-2922,3631-3641`).
- **Doc-code log-line contracts:** DLQ documentation quotes exact log strings developers must keep synchronized, enforced by adjacent code comments referencing the doc section (`executable.go:603,615`; `docs/admin/dlq.md:44`).
- **Panic-hardened observability:** both the logger encoder (`zap_logger.go:59-77`) and task executor (`executable.go:325-338`) treat "the instrumentation itself failing" as a first-class case.

## Tradeoffs

- **Masking vs. self-service debugging:** default-on masking protects internal topology (shard layout, host names, persistence internals) but converts every internal error into an operator-mediated support flow; the hash mitigates cost, it does not eliminate the dependency (`mask_internal_error.go:67-87`).
- **Noise suppression vs. forensic completeness:** suppressing expected errors (deadlines, ResourceExhausted) keeps logs useful at scale, but latency incidents often manifest precisely as deadline-exceeded storms, which are invisible until the namespace opts into `system.logAllReqErrors` (`request_error_handler.go:84-91`).
- **Truncation vs. root-cause fidelity:** size-limit replacement preserves retry semantics but discards the original failure body beyond the warn-size budget; a huge stack trace or cause chain is unrecoverable from history afterward (`workflow_handler.go:1306-1309`, `failure.go:52-91`).
- **Hand-maintained classification lists:** the expected-error type switch is explicit and greppable but admits incomplete coverage in its own comments; new service errors default to "unexpected," inflating `service_errors` until the list is updated (`request_error_handler.go:148-154`).
- **Throttled logging vs. completeness:** token-bucket throttling silently drops duplicate diagnostics under bursts; only Fatal/Panic/DPanic bypass (`throttle_logger.go:22,60-80,91-95`).

## Failure Modes / Edge Cases

- **Hash collisions:** `ErrorHash` is a 32-bit fingerprint of the message string (`common/util.go:409-414`); two distinct failures with equal text share a hash, and 8 hex chars give ~4 billion space — fine for human support flows, weak as a unique identifier.
- **Unresolvable namespace disables masking:** if the namespace can't be resolved from the request, `shouldMaskErrors` returns false and raw Internal/Unknown errors escape unmasked (`mask_internal_error.go:59-65`, pinned by test at `mask_internal_error_test.go:73-84`).
- **Transient workflow tasks lose the event:** `AddWorkflowTaskFailedEvent` returns nil events for transient tasks (documented at `workflow_task_state_machine.go:901,931`), so history shows fewer failure events than attempts occurred.
- **DLQ disabled ⇒ drop-with-Warn:** tasks already marked terminally failed are dropped with only a Warn log when no DLQ is configured — permanent loss visible solely through logs (`executable.go:369-381`).
- **Depth-limited cause chains:** `TruncateWithDepth` stops recursing causes at depth 20 or zero byte-budget, so deep exception chains collapse silently; the note "bytes are given to earlier calls first" means Message wins over StackTrace and Cause (`failure.go:57-88`).
- **Log-field serialization degradation:** concurrent-mutation fatals and unexported-map races are explicitly out of scope for the panic guard — such values still crash the process (comment at `zap_logger.go:55-58`).
