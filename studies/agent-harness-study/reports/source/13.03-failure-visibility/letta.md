## Summary

Letta implements failure visibility as four deliberately separated channels. **The model** sees tool failures as bounded, structured returns: every executor path converts exceptions into `ToolExecutionResult(status="error", func_return=<friendly message>, stderr=[traceback])` (`letta/services/tool_executor/tool_execution_manager.py:131-155`, `letta/schemas/tool_execution_result.py:8-13`) where the message is `"Error executing function {name}: {ExcType}: {msg}"` truncated to a 1,000-char cap (`letta/utils.py:1091-1097`, `letta/constants.py:430`). **The user** gets a typed exception→HTTP-status registry (~30 mappings in `letta/server/rest_api/app.py:556-611`) that masks unhandled 500s behind "An unknown error occurred" (`app.py:466-473`), rewrites hostile UUID-validation errors into friendly copy with examples and a `trace_id` (`app.py:477-532`), emits SSE `event: error` frames mid-stream (`letta/server/rest_api/streaming_response.py:365-394`), and persists run failures into queryable job metadata (`{"error": ...}` with `JobStatus.failed`, `letta/agents/letta_agent_v2.py:648-651`, `letta/agents/letta_agent.py:1377-1384`). **Developers** get structured JSON logs with Datadog/OTEL trace correlation and request-context injection (`letta/log.py:16-126`, `log.py:149-180`), process-wide hooks for main-thread/thread/asyncio faults (`letta/server/global_exception_handler.py:14-108`), OTel spans that record exceptions and stamp `trace_id` into error response bodies (`letta/otel/tracing.py:38-69,127-142`), and full LLM request/response provider traces with pluggable Postgres/ClickHouse/socket backends (`letta/schemas/provider_trace.py:25-66`, `letta/settings.py:571-592`). **Operators** get liveness/readiness endpoints backed by an explicit readiness state machine with multi-source degradation tracking (`letta/server/rest_api/routers/v1/health.py:18-40`, `letta/monitoring/readiness_state.py:39-84`), an event-loop hang watchdog (`letta/monitoring/event_loop_watchdog.py:26-100`), a load gate that flips readiness on saturation (`letta/monitoring/load_gate.py:139-198`), and a ~40-metric registry including failure-specific counters (`letta/otel/metric_registry.py:94-494`). Detail levels are partially configurable (`settings.debug`, `LETTA_LOGGING_JSON_LOGGING`, Datadog/profiling toggles, readiness gates all default-OFF), though one advertised knob (`LogSettings.log_level`) is dead code and streaming vs REST masking policies disagree about raw error exposure.

## Rating

**8 / 10** — Clear per-stakeholder model with explicit interfaces (typed exception hierarchy mapped through a single handler registry; `ToolExecutionResult` contract; `StopReasonType` taxonomy; readiness state machine), operational safeguards (watchdog, load gate, readiness gates, Sentry capture), and real test coverage (`tests/test_exception_logging.py:43-227`, `tests/test_log_context.py:10-120`, `tests/test_otel_tracing.py:101-224`). It falls short of 9–10 because: (1) the streaming layer leaks raw `str(exc)` to clients (`streaming_response.py:369`) while the REST layer masks it (`app.py:469`), so the detail-exposure policy is inconsistent across boundaries; (2) `LogSettings.log_level` is declared but never consumed — level control actually derives from `settings.debug` only (`letta/settings.py:527` vs `letta/log.py:13,258-261`; verified by searching all `log_settings.` uses, which hit only `json_logging`/`verbose_telemetry_logging`); and (3) the runtime toggle for exposing error details in 500 responses exists only as commented-out code (`app.py:470-471`).

## Answers to Dimension Questions

**1. Is the model informed of failures?**
Yes — this is the strongest channel. Tool execution never throws across the agent boundary: `execute_tool_async` catches both `asyncio.CancelledError` and general exceptions and returns a `ToolExecutionResult(status="error")` whose `func_return` is the formatted friendly message and whose `stderr` keeps the full traceback for the client/UI (`letta/services/tool_executor/tool_execution_manager.py:131-155`). The message shape `"Error executing function {name}: {ExceptionName}: {msg}"` (`letta/utils.py:1091-1097`) gives the model the failing symbol and cause, capped at 1,000 chars so a failure can't blow the context window (`letta/constants.py:430`). Sandbox/E2B errors follow the same path with tracebacks preserved in `stderr` (`letta/services/tool_executor/tool_execution_sandbox.py:376-391`). By contrast, LLM-provider failures are *not* fed back to the model — they classify into `StopReasonType.llm_api_error`/`invalid_llm_response` and fail the run (`letta/agents/letta_agent_v2.py:556-561`), except context-window overflow, which retries through forced summarization first (`letta_agent_v2.py:562-573`) — a sensible split since retrying the same prompt with an API-error string appended rarely helps.

**2. Is the user informed appropriately?**
Largely yes, with deliberate tiering. Synchronous clients receive correct status codes from a ~30-entry typed mapping (`letta/server/rest_api/app.py:556-611`), actionable retry guidance on transient DB contention (`Retry-After: 1` + plain-language deadlock copy, `app.py:613-641`), and softened validation errors with example IDs and a `trace_id` for support handoff (`app.py:477-532`). Unhandled 500s are masked as "An unknown error occurred" unless the server runs with `debug=True`, where FastAPI prints the stack trace in the response (`app.py:417,466-473`). Streaming clients get protocol-level signals: `event: error` frames mid-stream, graceful `event: cancelled` on run cancellation, and a distinct `LettaUnexpectedStreamCancellationError` for server-side termination (`letta/server/rest_api/streaming_response.py:328-394`). Async users can inspect durable state instead of reading errors off the wire: failed runs carry `{"error": ...}` metadata (`letta/agents/letta_agent.py:1377-1384`) and steps expose `error_type`/`error_data` including traceback (`letta/schemas/step.py:62-64`). One inconsistency: the streaming error frame includes raw `str(exc)` (`streaming_response.py:369`) even though the REST path masks the equivalent case.

**3. Can developers debug failures?**
Yes. All logs flow through one configured root logger whose JSON formatter attaches exception type/message/stacktrace, Datadog `dd.*` ids, and OTEL span-derived trace ids (`letta/log.py:48-94,74-86`), while `LogContextFilter` stitches agent/actor/org context into every line (`letta/log.py:149-180`). Faults outside the request cycle are still captured via `sys.excepthook`, `threading.excepthook`, and an asyncio loop handler (`letta/server/global_exception_handler.py:14-108`). Errors become navigable traces: middleware marks ERROR status and records exceptions (`letta/otel/tracing.py:63-69`), the error-handler dependency stamps `exception.*` attributes and returns the trace id inside the error body (`tracing.py:127-142`), and `x-api-request-log-id` correlates steps with upstream cloud-api logs even through streaming responses (`letta/server/rest_api/middleware/request_id.py:1-60`). For model-side debugging specifically, full provider request/response payloads are retained as `ProviderTrace` rows with selectable storage backends and a metadata-only privacy mode (`letta/schemas/provider_trace.py:25-66`, `letta/settings.py:571-592`).

**4. Can operators detect failure patterns?**
Yes, via layered signals. Liveness (`/v1/health/`) and readiness (`/v1/ready/`) are separate, with readiness driven by an explicit state machine whose degradation is multi-source reference-counted (`mark_degraded`/`clear_degraded`) and exposed as `readiness_state_gauge` (`letta/server/rest_api/routers/v1/health.py:24-40`, `letta/monitoring/readiness_state.py:39-84`). An event-loop watchdog measures scheduler lag and dumps hung tasks (`letta/monitoring/event_loop_watchdog.py:85-100`), and a load gate translates foreground/background saturation and admission-wait spikes into degraded states with stabilization windows to prevent flapping (`letta/monitoring/load_gate.py:139-198`, `letta/settings.py:626-637`). The metric registry enumerates failure-shaped series an operator can alert on — timeouts (request/redis/provider), DB-pool checkout errors, SSE disconnects, tool-execution success/failure split — with error samples tagged by tool name and step id (`letta/otel/metric_registry.py:94-494`, `letta/services/tool_executor/tool_execution_manager.py:156-160`). Sentry provides cross-instance aggregation of unhandled exceptions (`letta/server/rest_api/app.py:463-464`). What is *not* in-repo: dashboard or alert-rule definitions; operators must assemble them from these metric names (see Gaps).

**Detail-level configurability?** Partially. Debug logging, JSON formatting, Datadog tracing/profiling, OTEL export, provider-trace backends/metadata-only mode, and every readiness threshold are environment-configurable (`letta/settings.py:282,355,520-592,600-637`; `letta/log.py:195-212`). However, `LogSettings.log_level` is dead configuration — declared at `letta/settings.py:527` but no code reads it (all `log_settings.` usages touch only `json_logging`/`verbose_telemetry_logging`), so the effective level is tied solely to `settings.debug` (`letta/log.py:13,259-264`) — and the hook for surfacing error details in production 500s exists only commented out (`letta/server/rest_api/app.py:470-471`).

## Architectural Decisions

1. **Errors cross the agent/model boundary as data, not exceptions.** Tool failures become `ToolExecutionResult` values with separated `func_return` (model-safe summary) and `stderr` (full traceback for humans/UI) (`letta/schemas/tool_execution_result.py:8-13`, `letta/services/tool_executor/tool_execution_manager.py:151-155`), keeping the LLM context bounded while preserving forensic detail elsewhere.
2. **One typed hierarchy, one dispatch point.** `letta/errors.py` defines `LettaError`/`LLMError` families with semantic subclasses (rate-limit, credits, context-window, MCP timeout, message-parse failures — `letta/errors.py:259-345,352-431`), and `app.py` maps them to HTTP codes in a single registry (`letta/server/rest_api/app.py:534-611`), making presentation policy auditable in one place. ORM-layer errors are separately typed for lock/deadlock/constraint cases (`letta/orm/errors.py:5-33`) and rendered as retryable 409s (`app.py:613-641`).
3. **Loop terminations are classified, not just thrown.** `StopReasonType` gives every abnormal exit a stable enum value persisted onto steps and filterable via the runs API (`letta/schemas/letta_stop_reason.py:9-49`, `letta/agents/letta_agent_v2.py:654-665`, `letta/server/rest_api/routers/v1/runs.py:57`).
4. **Mask-by-default with escape hatches.** Production 500s hide internals (`app.py:466-473`) and expected tool errors are logged at DEBUG specifically to keep Sentry quiet (`tool_execution_sandbox.py:230-232,377-380`), while `debug=True` re-exposes stacks and Sentry captures everything unhandled.
5. **Readiness as an explicit, opt-in subsystem.** All gating flags default OFF ("non-breaking", `letta/settings.py:600-628`) so observability rollout can't destabilize existing deployments; degradation requires sustained overload (stabilization windows, `settings.py:631-637`) and multi-source agreement (`readiness_state.py:64-84`).

## Notable Patterns

- **Trace-id in the error body**: validation and traced error responses embed `trace_id` so a user-reported failure maps directly to a span (`letta/server/rest_api/app.py:487`, `letta/otel/tracing.py:142`).
- **Dual-channel tool errors**: `func_return` for the model vs `stderr` for humans within the same result object (`letta/schemas/tool_execution_result.py:9-13`).
- **Noise-budgeted logging**: expected domain errors downgraded to DEBUG with an explicit anti-Sentry-alert rationale comment (`letta/services/tool_executor/tool_execution_sandbox.py:230-232`).
- **Streaming-aware correlation**: request-id stored in both contextvar and `request.state` because Starlette contextvars don't propagate into stream generators (`letta/server/rest_api/middleware/request_id.py:1-13`).
- **Observability must not harm liveness**: the watchdog swallows its own telemetry exceptions ("Observability must never interfere with watchdog safety", `letta/monitoring/event_loop_watchdog.py:97-100`), and Datadog init failure never blocks startup (`letta/server/rest_api/app.py:404-408`).
- **Sensitive-span hygiene under test**: tracing tests pin that `messages`, `content`, and `source_code` params never enter span attributes (`tests/test_otel_tracing.py:101-191`).

## Tradeoffs

- **Masking consistency sacrificed at the streaming boundary.** REST 500s say "An unknown error occurred" (`app.py:469`) while SSE error events ship `str(exc)` verbatim (`streaming_response.py:369`) — more debuggable for SDK clients, but leaks internal wording (and any exception-text secrets) on exactly the long-lived connections most exposed to partial failures.
- **Bounded messages vs complete causes.** The 1,000-char truncation in `get_friendly_error_msg` (`letta/utils.py:1095-1096`) can clip long exception chains mid-message; the model stays safe but may lose the actionable tail.
- **Silence-as-safety vs signal loss.** Client disconnects during streams are logged at INFO and processing continues without sending (`streaming_response.py:294-296,324-326`) — good for run durability, but it means user-visible failure and server-side failure records intentionally diverge.
- **Opt-in operator safety net.** Because every readiness gate defaults OFF (`letta/settings.py:600-628`), a default deployment's `/v1/ready/` always reports healthy (`routers/v1/health.py:29-30`) — zero false positives, but also zero protection until an operator discovers and enables the flags.
- **Dead knob erodes trust in config surface.** `LogSettings.log_level` looks adjustable but isn't read anywhere (`letta/settings.py:527`; usage search shows only `json_logging`/`verbose_telemetry_logging` consumed), so operators tuning verbosity via it silently get INFO/DEBUG-by-proxy (`letta/log.py:13`).

## Failure Modes / Edge Cases

- **Failure after logical completion**: if an exception lands after `end_turn`/`max_steps` was decided, the loop explicitly flags "this indicates a bug with our flow" and logs at ERROR with the conflicting stop reason (`letta/agents/letta_agent_v2.py:653-657`, `letta/agents/letta_agent_v3.py:1527-1539`) — a self-diagnosing invariant.
- **Empty-string exceptions**: `str(e)` can be empty for bare `raise Exception()`; v3 falls back to `repr(e)` so run metadata isn't blank (`letta/agents/letta_agent_v3.py:1514-1515`).
- **Mid-stream exception before headers**: if nothing was sent yet, the stream escalates to a proper HTTP 500 start message rather than an SSE event (`letta/server/rest_api/streaming_response.py:372-380`).
- **DB deadlock variants**: handled at three layers — typed ORM error, SQLAlchemy `DBAPIError` wrapper with asyncpg deadlock sniffing, and generic fallback returning 500 (`letta/server/rest_api/app.py:613-649`).
- **Rollback semantics on failure**: v3 documents that message persistence does not happen on exception ("rollback to previous state"), so users don't see half-applied turns (`letta/agents/letta_agent_v3.py:1513`).
- **Telemetry self-failure**: OTEL-less environments skip formatter correlation silently (`letta/log.py:74-86`), and pytest environments disable tracing entirely (`letta/otel/tracing.py:150-151`).

## Future Considerations

- Align the streaming and REST masking policies (e.g., reuse the generic-handler copy for SSE `event: error`, gated by the same future `debug` toggle) (`letta/server/rest_api/streaming_response.py:369` vs `letta/server/rest_api/app.py:466-473`).
- Wire up or remove `LogSettings.log_level`; honoring it in `DEVELOPMENT_LOGGING` would restore the advertised verbosity control (`letta/settings.py:527`, `letta/log.py:216-278`).
- Finish the commented-out `debug_info` mechanism so detail exposure in production 500s becomes a supported runtime switch rather than a code edit (`letta/server/rest_api/app.py:470-471`).
- Ship reference dashboard/alert definitions next to `MetricRegistry` (the metric names exist; no in-repo consumers define what "bad" looks like) (`letta/otel/metric_registry.py:14-494`).
