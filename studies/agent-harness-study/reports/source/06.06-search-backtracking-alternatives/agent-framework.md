## Summary

agent-framework does not implement generic search (tree/beam/MCTS) or first-class alternative-plan evaluation. Branching is expressed as workflow-graph routing (conditional edges, switch-case single-dispatch, fan-out broadcast) and iteration bounds; backtracking is realized narrowly as checkpoint restore (linear `previous_checkpoint_id` lineage) plus two loop-retry primitives that approximate replanning: `AgentLoopMiddleware` (predicate/judge-driven re-invocation with feedback log and optional session snapshot) and the `MagenticOrchestrator`/`StandardMagenticManager` pair which generates a `MagenticProgressLedger`-scored next-speaker decision, tracks `stall_count`/`reset_count`, and triggers fact/plan replanning. No mechanism forks isolated plan alternatives, retains failed branches as comparable candidates, or ranks alternatives with a pluggable scoring function; cost control is solely iteration/round Stall/Reset caps.

## Rating

**4 / 10** — Present but inconsistent, weakly documented, and fragile for the dimension.

Rationale: Conditional branching and fan-out parallelism, checkpoint-based time-travel, a generic agent retry loop, and Magentic's stall-detect → replan loop are implemented and tested. However they do not compose into a unified search/backtracking model: alternatives cannot coexist and be scored, backtracking is linear (no branch tree), failed branches are discarded except for a terminal `WorkflowEvent.failed`, and cost bounding is ad-hoc per-subsystem. The dimension's core question — "recover from a bad path without forgetting what was learned" — is answered only partially via checkpoints and Magentic's ledger.

## Answers to Dimension Questions

### 1. Can the system try alternatives?

**Partially, via three disjoint mechanisms — not a unified search.**

* Workflow graph: alternatives are modeled as data-dependent routes, not explored alternatives. `EdgeCondition` (`python/packages/core/agent_framework/_workflows/_edge.py:21-22`) and `SwitchCaseEdgeGroup` (`python/packages/core/agent_framework/_workflows/_edge.py:806-872`) evaluate predicates sequentially and dispatch to **exactly one** target. `FanOutEdgeGroup` with `selection_func` (`python/packages/core/agent_framework/_workflows/_edge.py:522-535`) can activate a subset of targets concurrently, but the runner delivers messages through edge runners in parallel supersteps (`python/packages/core/agent_framework/_workflows/_runner.py:179-229`) without retaining per-branch scores.
* `AgentLoopMiddleware` retries the same agent sequentially until `should_continue` returns false or `max_iterations` fires (`python/packages/core/agent_framework/_harness/_loop.py:747-758`). Each retry can receive `feedback` (second element of `(bool, str)` predicate return or judge `reasoning` at `python/packages/core/agent_framework/_harness/_loop.py:201`, `760-763`) and `progress` history. This is iterative improvement, not parallel alternative exploration.
* `MagenticOrchestrator` explicitly creates alternative plans: on `stall_count > max_stall_count` or parse failure it calls `_reset_and_replan` which clears `chat_history`, broadcasts `MagenticResetSignal`, and asks the manager to `replan` with updated facts (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:1116-1193`). This is the only place where a "bad path" produces a fresh plan that attempts to avoid prior mistakes (`ORCHESTRATOR_TASK_LEDGER_PLAN_UPDATE_PROMPT` at `python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:186-192`).

No component enumerates N candidate plans, executes them speculatively, and compares outcomes.

### 2. Are alternatives isolated?

**No forked-session / branch-isolated execution.**

* `Workflow` enforces exclusive execution: `self._active_run` weakref guard rejects concurrent `run()` on the same instance (`python/packages/core/agent_framework/_workflows/_workflow.py:367-374`, `768-771`). You cannot launch two alternative continuations off one checkpoint concurrently; you must build separate `Workflow` instances or reuse the same instance sequentially.
* `InProcRunnerContext` holds a single `_messages: dict[str, list[WorkflowMessage]]` and a single `_pending_request_info_events` dict (`python/packages/core/agent_framework/_workflows/_runner_context.py:324`, `334`). `apply_checkpoint` clears and replaces them (`python/packages/core/agent_framework/_workflows/_runner_context.py:498-514`), i.e. restore overwrites prior state rather than branching it. There is no copy-on-write branch or snapshot tree — lineage is linear (`previous_checkpoint_id` at `python/packages/core/agent_framework/_workflows/_checkpoint.py:85`).
* `AgentLoopMiddleware` with `fresh_context=True` does snapshot a `Session` dict pre-loop and restore it between iterations (`python/packages/core/agent_framework/_harness/_loop.py:436`, `462-476`, `583-586`) to avoid history leakage, but iterations remain sequential and the working-state mutations of that loop iteration are discarded — not retained as parallel candidates.
* .NET docs note "concurrent branches from same sessionStoreId (for example forking from OpenAI previous_response_id), without those branches observing one another's mutations" (`dotnet/src/Microsoft.Agents.AI.Hosting/AgentSessionStore.cs:76-78`) — the storage layer permits it, but the Python workflow runner does not expose a first-class fork API.

### 3. How are alternatives compared?

**No generic scoring/ranking; ad-hoc boolean signals in one orchestrator.**

* Workflows expose no `score(plan) -> float` or comparator. `OutputDesignation` (`python/packages/core/agent_framework/_workflows/_workflow.py:172-206`) only classifies yields as `output`/`intermediate`/hidden, not ranked.
* The sole scoring-like structure is `MagenticProgressLedger` (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:308-334`): `is_request_satisfied`, `is_in_loop`, `is_progress_being_made` (each with `reason` + boolean `answer`), plus `next_speaker` selection and `instruction_or_question`. This drives a ternary control flow (complete / stall→replan / continue to next speaker) at `python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:1111-1145`, but it scores the *current trajectory* against the task, not multiple concurrent alternatives against each other.
* `GroupChatOrchestrator` delegates to `selection_func: Callable[[GroupChatState], str]` returning a single speaker name (`python/packages/orchestrations/agent_framework_orchestrations/_group_chat.py:95`, `239-254`); no ranking of top-k candidates.

### 4. Is backtracking explicit?

**Yes, but linear and opt-in — not tree-structured.**

* Explicit APIs: `Workflow.run(checkpoint_id=..., checkpoint_storage=...)`, `Workflow.run(responses=...)`, and combined `responses + checkpoint_id` (`python/packages/core/agent_framework/_workflows/_workflow.py:682-795`), plus `Workflow._run_workflow_with_tracing(is_continuation=(message is None))` preserving iteration count for continuations (`python/packages/core/agent_framework/_workflows/_workflow.py:876-878`). `RunnerImpl.restore_from_checkpoint` and `restore_checkpoint(WorkflowCheckpoint)` are first-class restoration entry points (`python/packages/core/agent_framework/_workflows/_runner.py:278-389`).
* Backtracking mechanics: `InProcRunnerContext.apply_checkpoint` rehydrates `messages` and re-enqueues `pending_request_info_events` as events (`python/packages/core/agent_framework/_workflows/_runner_context.py:498-514`); `_mark_resumed` restores `iteration` and chain pointer (`python/packages/core/agent_framework/_workflows/_runner.py:448-455`). Each superstep also creates a checkpoint (`python/packages/core/agent_framework/_workflows/_runner.py:165-166`), and `Workflow._execute_with_message_or_checkpoint` / `_send_responses_internal` create entry checkpoints for HILReplayability (`python/packages/core/agent_framework/_workflows/_workflow.py:680`, `1043`).
* Magentic backtracking is explicit stall→reset→replan (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:1116-1130`) and plan-review HIL (`handle_plan_review_response` at `python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:993-1038`).
* Implicit gaps: `Workflow._run_core` warns but does not block when a fresh `message` arrives with pending `request_info` still outstanding (`python/packages/core/agent_framework/_workflows/_workflow.py:856-872`) — the earlier pending requests "remain pending, but this run advances executor and shared state." Similarly, `RunnerImpl.create_checkpoint_if_enabled` logs and swallows checkpoint-write failures (`python/packages/core/agent_framework/_workflows/_runner.py:268-276`), so a failed checkpoint silently degrades backtracking fidelity without failing the run.

### 5. Are costs bounded?

**Per-subsystem caps; no global budget.**

* Workflows: `DEFAULT_MAX_ITERATIONS=100` (`python/packages/core/agent_framework/_workflows/_const.py:4`), configurable per `WorkflowBuilder(max_iterations=...)` (`python/packages/core/agent_framework/_workflows/_workflow_builder.py:93`) and per `Workflow(max_iterations=...)` (`python/packages/core/agent_framework/_workflows/_workflow.py:287`). Exceeding it raises `WorkflowConvergenceException` only if `has_messages()` remains (`python/packages/core/agent_framework/_workflows/_runner.py:176-177`). Tests for this path exist but the bound is purely iteration count, not token/$/time.
* Agent loop: `DEFAULT_MAX_ITERATIONS=10`, judge `5` (`python/packages/core/agent_framework/_harness/_loop.py:122-127`), enforced before predicate evaluation (`python/packages/core/agent_framework/_harness/_loop.py:755`).
* Magentic: `max_stall_count=3`, `max_reset_count`, `max_round_count`, plus `progress_ledger_retry_count=3` with backoff `0.25*attempts` (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:475-545`, `588-590`, `722-735`). GroupChat: `max_rounds` + optional `termination_condition` + `retry_attempts` (`python/packages/orchestrations/agent_framework_orchestrations/_group_chat.py:118-126`, `309-332`, `526-536`).
* Checkpoint storage growth is unbounded (no retention/eviction): `InMemoryCheckpointStorage` is an unbounded `dict` (`python/packages/core/agent_framework/_workflows/_checkpoint.py:207`), `FileCheckpointStorage` appends `*.json` files per superstep with no pruning (`python/packages/core/agent_framework/_workflows/_checkpoint.py:384-399`). No token or dollar budget spans the whole system.

## Architectural Decisions

* **Graph routing over search tree.** `Edge`/`EdgeGroup` polymorphism (`Single`, `FanOut`, `FanIn`, `SwitchCase`, `Internal`) registered via `EdgeGroup.register` (`python/packages/core/agent_framework/_workflows/_edge.py:315-418`) lets builders declare topologies declaratively and serialize with `to_dict`/`from_dict` preserving `condition_name` / `selection_func_name` without persisting live callables (`python/packages/core/agent_framework/_workflows/_edge.py:396-465`). Tradeoff: determinism/serializability over dynamic plan generation.
* **Pregel supersteps as execution model.** `RunnerImpl.run_until_convergence` (`python/packages/core/agent_framework/_workflows/_runner.py:106-177`) runs synchronized supersteps, streams events with 50ms polling (`python/packages/core/agent_framework/_workflows/_runner.py:129-135`), commits `State` at boundaries (`python/packages/core/agent_framework/_workflows/_runner.py:163`). This yields reproducible fan-out/fan-in but precludes speculative parallel plan branches with isolated state.
* **Single copy-on-restore linear backtracking.** `WorkflowCheckpoint` carries `previous_checkpoint_id` lineage (`python/packages/core/agent_framework/_workflows/_checkpoint.py:85`) and `apply_checkpoint` replaces context (`python/packages/core/agent_framework/_workflows/_runner_context.py:498-514`). Intent is durability/HIL resume across process restarts, not search tree branching.
* **Middleware loop as reusable retry primitive.** `AgentLoopMiddleware` extracted from ad-hoc per-agent retry loops into a single `AgentMiddleware` with streaming/non-streaming support, aggregated `AgentResponse` (`python/packages/core/agent_framework/_harness/_loop.py:775-796`), and the `pending_approval_request` escape hatch mirroring .NET `LoopAgent.HasPendingApprovalRequests` (`python/packages/core/agent_framework/_harness/_loop.py:443-460`). Keeps concern orthogonal to workflow graph.
* **Manager/orchestrator split in Magentic.** `MagenticManagerBase` owns LLM prompts and ledger parsing; `MagenticOrchestrator` owns workflow wiring, stall detection, reset signaling, and HIL plan review (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:864-1038`). Allows plugging a different manager while reusing orchestration scaffolding, with checkpoint save/restore of `task_ledger` and orchestrator state (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:753-768`, `1274-1282`).

## Notable Patterns

* **Selection-function indirection for routing.** Fan-out multi-selection (`python/packages/core/agent_framework/_workflows/_edge.py:503-535`) and group-chat `selection_func: Callable[[GroupChatState], str]` (`python/packages/orchestrations/agent_framework_orchestrations/_group_chat.py:95`) both defer target choice to caller-supplied predicates, enabling conditional parallel dispatch without baked-in scoring.
* **Stateless prompt construction from mutable ledger.** `StandardMagenticManager._complete` creates a fresh `create_session()` per LLM call and sends `[*chat_history, new_user_msg]` so the manager's ledger prompts are stateless across rounds (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:592-613`), avoiding compounding duplication that reusing one `AgentSession` would cause.
* **Progress-log as continuity carrier across fresh-context resets.** `AgentLoopMiddleware` with `fresh_context=True` discards in-loop state and injects only the accumulated `progress: list[str]` (`_render_progress` at `python/packages/core/agent_framework/_harness/_loop.py:798-802`) into the next iteration, mirroring TODO-mode loops (`todos_remaining`/`todos_remaining_message` at `python/packages/core/agent_framework/_harness/_loop.py:925-1050`).
* **HIL as natural backtrack point.** `WorkflowContext.request_info` / `response_handler` (`python/packages/core/agent_framework/_workflows/_agent_executor.py:291-318`) and `MagenticPlanReviewRequest/Response` (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:802-859`) emit `WorkflowEvent{type="request_info"}` and store pending maps (`python/packages/core/agent_framework/_workflows/_runner_context.py:534-575`) that checkpoints capture (`pending_request_info_events` field), enabling human-guided plan revision that re-enters the inner loop.

## Tradeoffs

* **Expressiveness vs. search sophistication.** Edge conditions and switch-case cover rule-based branching (`python/packages/core/agent_framework/_workflows/_edge.py:100-198`) cheaply, but cannot evaluate multiple plans under a shared objective or learn a value function. Any A* / beam search must be built outside the workflow and fed in as a custom orchestrator selection function.
* **Linear lineage vs. branch retention.** `previous_checkpoint_id` chaining (`python/packages/core/agent_framework/_workflows/_checkpoint.py:85`) and `clear()+import_state` restore (`python/packages/core/agent_framework/_workflows/_runner.py:324-325`) keep memory simple but discard the abandoned branch's executor states. There is no "branch id" or fork tree, so comparing two historical branches requires external storage.
* **Iteration caps vs. cost semantics.** Caps like `DEFAULT_MAX_ITERATIONS=100` / loop `10` / Magentic `max_stall=3` bound wall-clock work with one knob each, but they are not comparable (superstep vs. agent run vs. stall count) and none maps to token usage or dollar cost. Over-tuning one while under-tuning another can leave global consumption uncapped.
* **Durability vs. callability serialization.** Persisting `condition_name` / `selection_func_name` instead of the callable (`python/packages/core/agent_framework/_workflows/_edge.py:608-611`, `441-449`) keeps `Workflow.to_dict` JSON-safe and deserialization deterministic, but after `from_dict` those edges install `_missing_callable` proxies (`python/packages/core/agent_framework/_workflows/_edge.py:50-72`) that `RuntimeError` on invocation — a resumed workflow built from persisted JSON cannot branch without re-registration.
* **Silent checkpoint failure trades availability for fidelity.** `RunnerImpl.create_checkpoint_if_enabled` warns and continues on save failure while retaining `previous_checkpoint_id`→last-successful chain (`python/packages/core/agent_framework/_workflows/_runner.py:268-276`). The workflow stays live, but the backtracking window shrinks without surfacing to the caller as a terminal error.

## Failure Modes / Edge Cases

* **Non-convergence without signal.** If `iteration >= max_iterations` yet `has_messages()` true, `WorkflowConvergenceException` is raised (`python/packages/core/agent_framework/_workflows/_runner.py:176-177`); if the graph merely idles without messages the exception is not raised and the caller sees success with potentially incomplete outputs — a silent truncation.
* **Switch-case with no match.** `SwitchCaseEdgeGroup.selection_func` raises `RuntimeError("No matching case found")` (`python/packages/core/agent_framework/_workflows/_edge.py:871`) despite the builder guaranteeing a `Default` branch; a deserialized or mutated group that lost the default falls into this path and fails the superstep with `WorkflowEvent.failed` rather than routing to a fallback.
* **Deserialized missing callables.** After `EdgeGroup.from_dict`, `FanOutEdgeGroup._selection_func` and `SwitchCaseEdgeGroupCase._condition` become `_missing_callable` proxies (`python/packages/core/agent_framework/_workflows/_edge.py:448-449`, `701-702`) that raise `RuntimeError("Callable 'name' is unavailable")` (`python/packages/core/agent_framework/_workflows/_edge.py:50-72`) — a checkpoint-restored workflow built from JSON (not in-memory `WorkflowCheckpoint` objects) can fail at the first conditional edge.
* **Concurrent run rejection vs. caller drop.** `Workflow.run` rejects a second concurrent run synchronously (`WorkflowException: already running` at `python/packages/core/agent_framework/_workflows/_workflow.py:769`) and uses a `weakref` to the prior `ResponseStream` so a dropped-but-not-GCed stream still blocks a new run; only after GC or full consumption does `weakref` deref to `None` (`python/packages/core/agent_framework/_workflows/_workflow.py:367-374`, `893-911`). A caller that drops the stream without iterating can be surprised by a blocked retry until collection runs.
* **Fresh-message while pending HIL requests outstanding.** `Workflow._run_core` only warns when `message` or `checkpoint_id` arrives while `pending_request_info_events` nonempty (`python/packages/core/agent_framework/_workflows/_workflow.py:856-872`): fresh messages do not drop pending requests but the run advances shared state, so a later delivered `response` may apply to a workflow that has moved on — noted as "inconsistent results" in the warning but not prevented.
* **Progress-ledger parse loop exhausts retries.** `StandardMagenticManager.create_progress_ledger` retries `progress_ledger_retry_count` (default 3) times with `0.25*attempts` sleep, then raises `RuntimeError("Progress ledger parse failed after N attempt(s)")` (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:718-739`); the orchestrator catches this as a stall and triggers `_reset_and_replan` (`python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:1088-1092`), so repeated LLM malformed JSON can burn reset budget and hit `max_reset_count` termination before the task is attempted.
* **Unbounded checkpoint accumulation.** `InMemoryCheckpointStorage._checkpoints: dict[CheckpointID, WorkflowCheckpoint]` (`python/packages/core/agent_framework/_workflows/_checkpoint.py:207`) and `FileCheckpointStorage` (`python/packages/core/agent_framework/_workflows/_checkpoint.py:384-421`) never evict — long-running workflows with per-superstep checkpoints accumulate O(supersteps) entries; `get_latest` does `max(..., key=datetime.fromisoformat)` (`python/packages/core/agent_framework/_workflows/_checkpoint.py:240`) scanning all entries, so large stores degrade both storage and lookup.

## Future Considerations

* Introduce a `Workflow.fork(checkpoint_id) -> Workflow` API that copies messages/state/pending maps into a new `RunnerImpl`/`InProcRunnerContext` with a `branch_parent_id`, preserving the `previous_checkpoint_id` chain plus a branch tree — prerequisite for scoring multiple candidates off one ancestor without overwriting it.
* Add a pluggable `BranchScorer` interface (`score(events, state) -> float`) used by a new `SearchEdgeGroup` or `BeamSelectionFunc` that runs N candidates (via forked workflows), collects `WorkflowRunResult.get_outputs()` and scorer values, and routes the best one plus optional retained traces.
* Unify cost bounds into a `WorkflowBudget{max_iterations, max_tokens, max_cost, max_wallclock}` checked in `RunnerImpl.run_until_convergence` and in `AgentLoopMiddleware._evaluate_stop`, and enforce it across Magentic/GroupChat orchestrators rather than per-subsystem caps.
* Change `create_checkpoint_if_enabled` failure handling from warn-and-continue to `WorkflowCheckpointException` propagation behind an opt-in `strict_checkpointing: bool` flag on `WorkflowBuilder`, so HIL/mission-critical workflows can fail loudly instead of silently losing backtracking fidelity.
* Persist conditional edges' callable bindings via an explicit registry (e.g., `Workflow.register_condition("name", fn)`) that rehydrates after `from_dict`/`load` from `FileCheckpointStorage`, avoiding the `_missing_callable` runtime trap.
