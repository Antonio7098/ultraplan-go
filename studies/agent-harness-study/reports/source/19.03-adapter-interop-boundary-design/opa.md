## Summary

OPA treats standards as **adapter-layer abstractions behind explicit core interfaces**, not as hard-coded core protocols. The dominant interop model is an out-of-tree adapter registered **before runtime initialization** via global registries (`runtime.RegisterPlugin`, `runtime.RegisterStorageBackend`, `runtime.RegisterHook`, `rego.RegisterPlugin`, `bundle.RegisterStoreFunc` / `RegisterDefaultBundleActivator`). Core defines narrow, documented Go interfaces (`plugins.Factory`/`Plugin`, `storage.Store`, `rest.HTTPAuthPlugin`, `hooks.Hook`, `rego.TargetPlugin`, `bundle` reader/writer) and the runtime (`v1/runtime.Runtime`) and manager (`v1/plugins.Manager`) orchestrate lifecycle (`Validate`→`New`→`Start`/`Reconfigure`/`Stop`) plus status, discovery-driven reconfiguration, and graceful shutdown. HTTP surface extensibility is delegated to adapter hooks (`Manager.ExtraRoute`, `ExtraMiddleware`, `ExtraAuthorizerRoute`). This yields clean separation and opt-in extensibility without forking core, but adapters are **build-time registered, not hot-swapped at runtime**; swapping code requires a custom build and restart, while runtime dynamism is limited to configuration/data via discovery and bundles. Documentation in `docs/docs/extensions.md` is thorough; conformance is demonstrated by extensive unit tests for built-in adapters, but no generic conformance harness enforces third-party compliance.

## Rating

**Score: 8 / 10 — Clear model with tests, explicit interfaces, and operational safeguards.**

Rationale: Core defines 6+ stable interop interfaces with explicit contracts and functional options; all examined adapters (storage, plugins, auth, hooks, extra HTTP routes, Wasm resolvers, bundle formats) are addable without modifying `v1/plugins`, `v1/storage`, `v1/server`, or `v1/runtime` core. `v1/plugins/plugins_test.go` (771 lines), `v1/plugins/rest/rest_test.go`, `v1/storage/inmem` tests, and `v1/runtime/runtime_test.go` exercise lifecycle, reconfiguration, and failure paths. Operational safeguards include plugin status state machine (`StateNotReady`/`StateOK`/`StateErr`/`StateWarn`), `Manager.UpdatePluginStatus`/`PluginStatus`/`RegisterPluginStatusListener`, discovery readiness gating (`Runtime.waitPluginsReady`), and `storage.Closer` graceful shutdown. Interop boundaries are documented in code godoc and `docs/docs/extensions.md`. Point deductions: adapters are global singleton registries (`registeredPlugins map[string]Factory` with `sync.Mutex`) requiring restart to swap code (not runtime swappable), no reusable conformance test suite per interface, and cross-cutting concerns (auth, tracing, metrics) threaded via Manager options rather than a single adapter middleware.

## Answers to Dimension Questions

**1. Are protocols core or adapter-layer?**
Core defines **abstract interfaces**; concrete protocols live in adapters. HTTP/REST handling is core (`v1/server/server.go:849-942` registers `/v0/data`, `/v1/data`, `/v1/policies`, `/v1/query`, `/v1/compile`, `/health`), but authentication is delegated to `rest.HTTPAuthPlugin` adapters (`v1/plugins/rest/rest.go:41-51`). Storage is abstract (`storage.Store` at `v1/storage/interface.go:19-44`); `inmem` (`v1/storage/inmem/inmem.go:34-59`) and `disk` (`v1/storage/disk/disk.go:97`) are adapters. Bundle format (tar.gz with `data.json`, `.rego`, `policy.wasm`, `plan.json`, `.manifest`, `.manifest.pb`, `signatures.json`) is defined by `v1/bundle/bundle.go:39-56`, `v1/bundle/bundle.go:496-530` but encoding/decoding and signing/verification are pluggable (`Reader.WithBundleVerificationConfig`, `Bundle.GenerateSignature`). Plugin protocol (`Factory`/`Plugin` at `v1/plugins/plugins.go:89-110`) is the primary interop boundary; decision logging, bundle, discovery, status are all plugins. Even Rego evaluation target is pluggable via `rego.TargetPlugin` (`v1/rego/plugins.go:18-21`). In short: standards are **core abstractions with adapter-layer implementations**.

**2. Can adapters be added without core changes?**
**Yes for documented extension points, no for new HTTP verbs or storage semantics that would require core interface changes.** Adding a new storage backend: implement `storage.Store` (`v1/storage/interface.go:20`) and call `runtime.RegisterStorageBackend(builder)` before `NewRuntime` (`v1/runtime/runtime.go:101-108`); `Params.StoreBuilder` (`v1/runtime/runtime.go:275-276`) then overrides the inmem default without touching `v1/runtime/runtime.go:498-519`. Adding a new auth method: implement `rest.HTTPAuthPlugin` (`v1/plugins/rest/rest.go:42`) and register as a `plugins.Factory` that also implements `HTTPAuthPlugin` (retrieved via `Manager.AuthPlugin` at `v1/plugins/plugins.go:739-749` and looked up in `Config.AuthPlugin` at `v1/plugins/rest/rest.go:88-101`). Adding a new plugin: implement `plugins.Factory`/`Plugin` and `runtime.RegisterPlugin` (`v1/runtime/runtime.go:95-99`). Adding custom HTTP endpoints/middleware/authz: call `Manager.ExtraRoute`/`ExtraMiddleware`/`ExtraAuthorizerRoute` from plugin `init`/`Start` (`v1/plugins/plugins.go:788-815`); `Server.initRouters` at `v1/server/server.go:888-890` and `instrumentHandler` at `v1/server/server.go:954-965` consume them without core edits. Adding a new Rego target: `rego.RegisterPlugin` (`v1/rego/plugins.go:36-43`). Adding bundle handling variants: `bundle.RegisterDefaultBundleActivator`/`RegisterStoreFunc` (`v1/bundle/bundle.go:468-484`). Counter-example: adding a new bundle file type beyond `RegoExt`/`WasmFile`/`PlanFile`/`data.json`/`patch.json`/`ManifestExt` requires modifying `v1/bundle/bundle.go:681-780` `Reader.Read` switch; adding a new trigger semantic requires changing `TriggerConfig` (`v1/storage/interface.go:219-230`). So **adapter addition is non-invasive iff it fits an existing interface**; novel protocol semantics still need core PRs.

**3. Are adapters tested for conformance?**
**Partially — built-in adapters are thoroughly tested; no generic conformance harness exists for third-party adapters.**
- **Positive:** `v1/plugins/plugins_test.go:103-168` verifies plugin status listener ordering, `UnregisterPluginStatusListener`, and post-`Stop` non-hanging semantics; `v1/plugins/plugins_test.go:27-101` verifies cache/ND cache triggers fire only on `Reconfigure`; `v1/plugins/plugins_test.go:662-770` exercises `RegisterExternalSource` wiring and recompilation guard (`no recompilation when no sources registered`). `v1/plugins/rest/rest_test.go:1808` and `v1/download/oci_download_test.go:441` mock `HTTPAuthPlugin` and verify `AuthPluginLookup` plumbing. `v1/storage/inmem/inmem.go:157-232` is exercised via `internal/storage/mock` transaction counting (`v1/plugins/plugins_test.go:245-268` idempotency). `v1/runtime/plugins_test.go:57-151` asserts `RegisterPlugin` idempotency, boot config via file paths, and `StoreBuilder` wiring. Server decoding/compression adapters are tested via `v1/server/cache_test.go`, `compile_handler_test.go`.
- **Gap:** No `storage.Store` conformance suite that a third-party implementer can run to validate `Truncate`/`Write`/`Read`/`Trigger`/`MakeDir`/`NonEmptyer` contracts; correctness is shown only by inmem/disk implementations and ad-hoc mocks. Similarly, there is no `HTTPAuthPlugin` conformance test verifying `NewClient` is idempotent/cached and `Prepare` is invoked per request — the invariant is documented in `CHANGELOG.md:735` and enforced indirectly in `v1/plugins/rest/rest.go:224-252` but not as a reusable test helper. Third-party plugin authors must infer contracts from godoc (`v1/plugins/plugins.go:42-110`) and copy built-in tests.

**4. Are interop boundaries documented?**
**Yes — both code-level and guide-level documentation are strong, with minor gaps on edge-case interactions.**
- **Guide:** `docs/docs/extensions.md:6-575` documents every boundary: custom built-ins (declaration via `ast`/`types`, `rego.Function1/2`, `Memoize`/`Nondeterministic`, `BuiltinContext`, example `github.repo` with `rego.RegisterBuiltin2` at `docs/docs/extensions.md:528-568`), custom plugins (`Factory`/`Plugin` lifecycle, `RegisterPlugin` before `cmd.RootCommand.Execute` at `docs/docs/extensions.md:312-324`), custom storage (`storage.Store` + `RegisterStorageBackend` at `docs/docs/extensions.md:369-402` plus `storage.Closer` note), and version ldflags. It also cross-links `pkg.go.dev` for `storage.Store` and `RegisterStorageBackend`.
- **Godoc:** `v1/plugins/plugins.go:42-110` spells out factory `Validate` (deserialize, validate, inject defaults, return config) and `New` (cast, instantiate, `UpdatePluginStatus`), and `Plugin.Start`/`Reconfigure` discovery contract; `v1/storage/interface.go:19-80` documents `TransactionParams.BasePaths` vs deprecated `RootOverwrite` and `Context.WithMetrics/Metrics`; `v1/plugins/rest/rest.go:41-51` documents `NewClient` “MUST NOT perform per-request” / “MUST be in Prepare” invariant (reinforced by `CHANGELOG.md:735-780` breaking change note); `v1/hooks/hooks.go:16-32` explains type-asserted hook dispatch and concurrent safety. `v1/server/types/types.go:240-281` documents `DataRequestV1`/`DataResponseV1` `Metadata` extensibility via `RegisterJSONFields`/`UnmarshalExtras`/`MarshalExtras` for future top-level keys.
- **Gaps:** No single interop matrix listing all extension points and their stability guarantees; interaction between `Hooks` (`ConfigHook` not run on `Reconfigure` vs `ConfigDiscoveryHook` on discovery) is noted only in `v1/hooks/hooks.go:36-41` and not in `extensions.md`; bundle manifest evolution (`rego_version`, `file_rego_versions`, proto vs JSON manifest at `v1/bundle/bundle.go:147-165`) is documented in code but not surfaced in user-facing interop guide.

## Architectural Decisions

- **Single Manager, many factories:** `v1/plugins.Manager` (`v1/plugins/plugins.go:192-245`) centralizes config, compiler, `storage.Store`, services, keys, router, Prometheus register, tracer provider, and plugin lifecycle. Decision favors global coordination (single compiler, single store transaction, single status channel) over isolated plugin runtimes. Tradeoff: simpler consistency but global lock (`mtx sync.Mutex`) and single `pluginStatusLoop` goroutine become contention points.
- **Global registry before `NewRuntime`:** `registeredPlugins map[string]Factory`/`registeredStorageBackend`/`registeredHooks` with `sync.Mutex` (`v1/runtime/runtime.go:68-76`) require registration in `init()` or before `NewRuntime`. Decision enables static linking without reflection or config-driven dynamic loading; aligns with Go’s static compilation model. Tradeoff: not runtime-swappable, not test-isolated (tests must `ResetTargetPlugins` or risk `panic: plugin already registered` at `v1/rego/plugins.go:40`).
- **Discovery as meta-plugin:** `discovery.Discovery` itself is a plugin registered in `NewRuntime` at `v1/runtime/runtime.go:598-599` and fed `registeredPlugins` via `discovery.Factories(registeredPlugins)` (`v1/runtime/runtime.go:586-587`). Decision makes config distribution (bundles, services) uniform with data bundles, allowing remote reconfiguration without code changes. Tradeoff: circular dependency risk (discovery bundle configures the manager that hosts discovery).
- **Storage as synchronous transaction + trigger:** `storage.Store` exposes `NewTransaction`/`Read`/`Write`/`Commit`/`Abort` plus `Register(TriggerConfig)` (`v1/storage/interface.go:20-44`, `232-236`). `Manager.onCommit` (`v1/plugins/plugins.go:1090-1139`) reloads compiler from `TriggerEvent.Policy` and `WasmResolvers` from `TriggerEvent.Data`, then fans out to `registeredTriggers` without holding `mtx` (comment at `v1/plugins/plugins.go:1108-1109` referencing #8873 deadlock fix). Decision gives plugins strong consistency (one writer via `inmem.store.wmu` at `v1/storage/inmem/inmem.go:149`) and immediate compiler coherence. Tradeoff: all triggers run synchronously on commit, so slow plugins block commits.
- **Auth as plugin + reflection:** `rest.Config.Credentials` struct (`v1/plugins/rest/rest.go:61-69`) enumerates credential kinds; `AuthPlugin` via reflection ensures at-most-one method (`v1/plugins/rest/rest.go:103-115`). Custom auth extends `HTTPAuthPlugin` rather than adding new `Credentials` fields, keeping `rest.Config` stable. `Client.ensureHTTPClient` (`v1/plugins/rest/rest.go:224-252`) caches `NewClient` result and applies `tracing.NewTransport` — decision to cache per client rather than per request.
- **HTTP extensibility via late-bound manager:** `Manager.extraRoutes`/`extraMiddlewares`/`extraAuthorizerRoutes` (`v1/plugins/plugins.go:239-241`) populated during plugin `init`/`Start` before `Server.Init` (`v1/server/server.go:888-899` consumes `ExtraRoutes`, `v1/server/server.go:954-965` wraps handlers). Decision avoids core modification for new endpoints while still applying Prometheus/OTel wrapping uniformly.
- **Bundle as versioned artifact with pluggable activation:** `Bundle` carrying `Raw` (`v1/bundle/bundle.go:87-91`) plus `lazyLoadingMode: HasExtension()` (`v1/bundle/bundle.go:528`) and `RegisterDefaultBundleActivator`/`BundleExtStore` (`v1/bundle/bundle.go:468-484`) allows alternative stores/activators without core changes. Decision supports OCI, disk persistence, and custom indexing.

## Notable Patterns

- **Factory + Manager injection:** Factories receive `*Manager` to access `Store`, `Config`, `Logger`, `AuthPlugin`, `PrometheusRegister`, `TracerProvider` — dependency injection via manager, not globals. Evidence: `v1/plugins/plugins.go:89-92`, `v1/runtime/runtime.go:551-556` wiring 10+ manager options.
- **Status state machine with listener fan-out:** `Status{State,Message}` + `pluginStatusLoop` select over `statusUpdate`/`statusInitPlugin`/`statusRegisterListener`/`statusQuery` channels, `copyPluginStatus`, and post-`Stop` `finalPluginStatus` draining (`v1/plugins/plugins.go:247-279`, `1389-1427`). Tested for not-hanging after stop (`v1/plugins/plugins_test.go:465-571`).
- **Extra route/middleware/authorizer late binding:** `Manager.ExtraRoute` panics on duplicate (`v1/plugins/plugins.go:790`), `Server.initRouters` instruments via `Managers.ExtraMiddlewares()` with `slices.Backward` (`v1/server/server.go:944-952`), enabling OTel/Prom wrapping for third-party routes.
- **Context as trigger carrier:** `storage.Context.Put(managerCompilerContextKey, compiler)` / `Put(managerWasmResolverContextKey, resolvers)` (`v1/plugins/plugins.go:294-313`) allows bundle plugin to skip reparse/reload — a form of transaction-context optimization.
- **Reflection-guarded credential exclusivity:** `Config.AuthPlugin` uses `reflect.ValueOf(c.Credentials).Fields()` to enforce at-most-one credential and fallback to `defaultAuthPlugin` (`v1/plugins/rest/rest.go:103-121`).
- **Metadata passthrough via JSON extras:** `DataRequestV1`/`DataResponseV1` carry `Metadata map[string]any` with `UnmarshalExtras`/`MarshalExtras` and `RegisterJSONFields` (`v1/server/types/types.go:240-293`) — forward-compatible interop for wrapping projects.
- **Functional options for manager/runtime/server:** `Logger`, `ConsoleLogger`, `WithRouter`, `WithPrometheusRegister`, `WithTracerProvider`, `WithDistributedTracingOpts`, `WithHooks`, `WithParserOptions`, `WithMinTLSVersion` etc (`v1/plugins/plugins.go:402-534`, `v1/server/server.go:283-464`) — consistent options pattern.
- **Hooks as type-asserted any:** `type Hook any` (`v1/hooks/hooks.go:32`) with `Each` type-switch dispatch — open extension without interface versioning, validated by `Hooks.Validate()` (`v1/hooks/hooks.go:100-112`).

## Tradeoffs

- **Extensibility vs runtime swappability:** Adapters are swappable **at build time** via `RegisterPlugin`/`RegisterStorageBackend` but **not at runtime** via config reload or discovery. Discovery can only swap `config.Config` (services, bundles, plugin config blobs) and trigger `Factory.Validate`/`Reconfigure` — code remains immutable. Consequence: adding a new auth method or storage backend requires rebuilding OPA (`go build -o opa++` at `docs/docs/extensions.md:330`), not a config push.
- **Global registries vs test isolation:** `registeredPlugins`/`registeredStorageBackend`/`targetPlugins` are process-wide singletons with `sync.Mutex` but no test-scoped isolation except `rego.ResetTargetPlugins` (`v1/rego/plugins.go:45-49`). Parallel tests that register plugins can collide (`panic` at `v1/rego/plugins.go:40`, `v1/runtime/runtime.go:98` idempotent but not isolated). This is a deliberate simplicity tradeoff over dependency-injection containers.
- **Single manager lock vs plugin concurrency:** `Manager.mtx` protects `plugins`, `services`, `keys`, `registeredTriggers`, etc., but `onCommit` deliberately copies `registeredTriggers` under lock then releases before invoking (`v1/plugins/plugins.go:1110-1117`) to avoid deadlocks (#8873). This trades a brief inconsistency window for liveness.
- **Inmem writer lock vs scalability:** `inmem.store` uses `wmu sync.Mutex` for single writer and `rmu sync.RWMutex` for readers (`v1/storage/inmem/inmem.go:115-155`). `Truncate` merges iterators into `map[string]any` then writes under transaction (`v1/storage/inmem/inmem.go:157-232`). Simple but limits write throughput; `disk.Store` offloads to Badger but still serializes via manager’s transaction — not partitioned.
- **Reflection for credential exclusivity vs static typing:** Reflection in `Config.AuthPlugin` avoids boilerplate as auth methods grow, but loses compile-time exhaustiveness and makes error messages (“a maximum one credential method must be specified” at `v1/plugins/rest/rest.go:111`) runtime-only.
- **Extra routes panics vs graceful error:** `Manager.ExtraRoute` panics on duplicate path (`v1/plugins/plugins.go:790`) — fail-fast during plugin init rather than returning error, which simplifies server init but can crash runtime if two plugins claim same path.
- **Cached `NewClient` vs per-request auth freshness:** `Client.ensureHTTPClient` caches `http.Client` + `HTTPAuthPlugin` (`v1/plugins/rest/rest.go:124-129`, `224-252`). `NewClient` is called once; `Prepare` per request. This avoids TLS setup per request but requires `HTTPAuthPlugin` implementers to understand the two-phase contract (recently clarified in CHANGELOG #8376).
- **Bundles as tar.gz vs incremental:** `Bundle.Writer`/`Reader` tar.gz plus `Patch` delta bundles (`v1/bundle/bundle.go:54-55`, `968-1004`) — simple and portable but not content-addressed at file granularity; OCI support is additional adapter (`v1/download/oci_download.go:367`).

## Failure Modes / Edge Cases

- **Missing lookup function:** `Config.AuthPlugin(nil)` returns `missing auth plugin lookup function` (`v1/plugins/rest/rest.go:93`) — caller must pass `Manager.AuthPlugin` via `cfg.ServiceOptions.AuthPlugin` (`v1/runtime/runtime.go:968-970`); tests catch via `mockAuthPluginLookup` but production miswiring returns opaque error.
- **Duplicate credential methods:** `Config.AuthPlugin` returns `a maximum one credential method must be specified` (`v1/plugins/rest/rest.go:111`) when reflection finds >1 non-nil `Credentials` field — fails `New`/`Reconfigure` with bundle/status plugin error, surfaces as plugin `StateErr`.
- **Duplicate extra route:** `Manager.ExtraRoute` panics `extra route already registered: <path>` (`v1/plugins/plugins.go:790`) — not recoverable; plugin init ordering determines winner. No test covers two plugins registering same path concurrently.
