## Summary

pydantic-ai treats standards as **core abstractions with adapter-layer implementations**. Core defines a unified, provider-agnostic surface — `AbstractModel`/`Model`, `Provider`, `ModelProfile`, `ModelRequestParameters`, `ModelMessage`/`ModelResponse`, `AbstractNativeTool`, `UIAdapter`, `AbstractCapability`/`AbstractToolset`, `MCPToolset` — and every external protocol (LLM provider APIs, MCP, AG-UI, Vercel AI) is implemented as a pluggable adapter that translates to/from that core. Adding a new LLM provider, UI protocol, native tool, or capability does not require patching core logic; it is a new subclass + registration, or simply a user-supplied `Model`/`Provider`/`UIAdapter` instance passed at runtime. Runtime swappability is proven via `infer_model`/`infer_provider`, `WrapperModel`/`InstrumentedModel`/`FallbackModel`, capability/toolset injection, and per-request `model=` overrides. Per-adapter test coverage is extensive (thousands of VCR-recorded and inline-snapshot tests), but there is no single cross-protocol conformance harness — conformance is verified ad-hoc per adapter.

## Rating

**8 / 10 — Clear model with tests, explicit interfaces, and operational safeguards**

Rationale: Core abstractions are narrow, stable, and reused across Python; all protocol handling lives in isolated adapters requiring no core edits for extension; runtime swappability is built into factory functions and dependency injection; tests cover wire rendering, profile resolution, and interop edge cases with snapshots. Gaps vs. 9–10: built-in provider/tool registry still requires adding a case to `infer_model`/`infer_provider_class` and a literal to `KnownModelName` for first-class `provider:model` strings (though custom `Model` subclasses avoid core edits entirely); there is no durable cross-protocol conformance matrix or chaos/failure-injection suite; observability across interop boundaries is telemetry-based (`InstrumentedModel`) rather than a unified boundary health dashboard.

## Answers to Dimension Questions

### 1. Are protocols core or adapter-layer?

**Adapter-layer with core abstractions.** Core (`pydantic_ai_slim/pydantic_ai/models/_abstract.py:19`, `pydantic_ai_slim/pydantic_ai/models/__init__.py:366`, `pydantic_ai_slim/pydantic_ai/providers/__init__.py:42`, `pydantic_ai_slim/pydantic_ai/profiles/__init__.py:47`, `pydantic_ai_slim/pydantic_ai/native_tools/__init__.py:69`, `pydantic_ai_slim/pydantic_ai/ui/_adapter.py:207`) defines *unified* abstractions: `Model`/`Provider`/`ModelProfile`/`ModelRequestParameters`/`ModelMessage` groups and `AbstractNativeTool`/`UIAdapter` seams. No provider wire format lives in core. Every external protocol is an adapter in its own module: `pydantic_ai_slim/pydantic_ai/models/openai.py:923`, `pydantic_ai_slim/pydantic_ai/models/anthropic.py`, `pydantic_ai_slim/pydantic_ai/models/google.py`, etc., plus `pydantic_ai_slim/pydantic_ai/providers/*.py` for auth/client, `pydantic_ai_slim/pydantic_ai/mcp.py:715` for MCP transport, and `pydantic_ai_slim/pydantic_ai/ui/ag_ui/_adapter.py:232` + `pydantic_ai_slim/pydantic_ai/ui/vercel_ai/_adapter.py:145` for UI wire formats. The design follows the AGENTS invariant: "Place provider-specific code in `models/{provider}.py`, not shared modules" (`pydantic_ai_slim/pydantic_ai/models/AGENTS.md:3`).

### 2. Can adapters be added without core changes?

**Yes for user-supplied adapters; first-class built-in provider names require a registry touch.**

- **Zero core change path (fully supported):** Users can subclass `Model` (`pydantic_ai_slim/pydantic_ai/models/__init__.py:366`) and/or `Provider` (`pydantic_ai_slim/pydantic_ai/providers/__init__.py:42`), implement `request`/`request_stream`, declare `supported_native_tools()`/`supported_tool_deferral_modes`, and pass the instance to `Agent(model=my_model)` or `Agent(provider=my_provider)` — `infer_model` short-circuits on `isinstance(model, Model)` (`pydantic_ai_slim/pydantic_ai/models/__init__.py:1540`). Similarly, a new UI protocol is a `UIAdapter` subclass (`pydantic_ai_slim/pydantic_ai/ui/_adapter.py:207`), a new native tool is an `AbstractNativeTool` subclass (`pydantic_ai_slim/pydantic_ai/native_tools/__init__.py:69`), and a new cross-cutting concern is an `AbstractCapability` (`pydantic_ai_slim/pydantic_ai/capabilities/__init__.py:1`). `FunctionModel`/`TestModel` (`pydantic_ai_slim/pydantic_ai/models/function.py:52`) demonstrates this in-repo.
- **Registry-touch path for built-in `provider:model` strings:** Adding a built-in shorthand like `myprovider:gpt-5` still requires editing the closed registries `infer_provider_class` (`pydantic_ai_slim/pydantic_ai/providers/__init__.py:142`), `infer_model` (`pydantic_ai_slim/pydantic_ai/models/__init__.py:1585-1650`), and optionally `KnownModelName` (`pydantic_ai_slim/pydantic_ai/models/_known_model_names.py:13`) for type-checker completion. This is not an architectural barrier — it is a distribution ergonomics choice; the hot-swappable instance path already avoids it. `ext/langchain.py:32-71` shows an external-ecosystem adapter that *does* avoid core edits by wrapping at the toolset layer.

### 3. Are adapters tested for conformance?

**Extensively per-adapter, but without a single cross-protocol conformance harness.**

- **Per-adapter wire assertions:** `tests/test_vercel_ai.py` holds ~150+ adapter assertions covering `load_messages`/`dump_messages` round-trips, metadata preservation, approval flows, and `dispatch_request` scaffolding (`tests/test_vercel_ai.py:4198-10511`). `tests/test_tool_availability_portability.py` captures rendered requests and asserts `supported_tool_deferral_modes` defaults rather than mocking SDK internals (`tests/test_tool_availability_portability.py:1449`). `tests/AGENTS.md:153` codifies that pattern: "capture the render … and assert against that."
- **Profile conformance matrix:** `tests/profiles/test_resolution_matrix.py` snapshots the full `Model.profile` resolution (DEFAULT → provider → user → `supported_native_tools` intersection) for every model family, failing if a profile and the wire disagree (`tests/profiles/test_resolution_matrix.py:114-1900`). `tests/providers/test_*.py` validate provider-level model_profile returns (`tests/providers/test_anthropic.py:83`, `tests/providers/test_bedrock.py:119-349`). The `models/AGENTS.md` rule mandates that every forwarded `ModelSettings` field be added to its `Supported by:` list and get a case in `tests/models/test_model_settings_support.py` (`pydantic_ai_slim/pydantic_ai/models/AGENTS.md:31`).
- **Gap:** There is no top-level `BaseCheckpointSaver`-style conformance suite that loops over *all* `Model` subclasses and runs identical contract tests (request/stream/count_tokens/prepare_messages/profile intersection) as a single harness; each adapter's suite is isolated. No chaos/failure-injection tests for interop boundaries were observed.

### 4. Are interop boundaries documented?

**Yes, at multiple levels — explicit but distributed, not centralized.**

- **Code as contract:** Every provider/model adapter file's docstring, every `ModelProfile` field docstring (`pydantic_ai_slim/pydantic_ai/profiles/__init__.py:55-189`), and `AbstractNativeTool`'s `Supported by:` per-class lists (`pydantic_ai_slim/pydantic_ai/native_tools/__init__.py:129-145`) state which protocols are supported and how they differ. `pydantic_ai_slim/pydantic_ai/ui/_adapter.py:227-260` documents `manage_system_prompt`, `allowed_file_url_schemes`, `allow_uploaded_files` security boundaries inline.
- **Per-area AGENTS guides:** `pydantic_ai_slim/pydantic_ai/models/AGENTS.md`, `pydantic_ai_slim/pydantic_ai/providers/AGENTS.md`, `pydantic_ai_slim/pydantic_ai/profiles/AGENTS.md`, `pydantic_ai_slim/pydantic_ai/ui/AGENTS.md`, `pydantic_ai_slim/pydantic_ai/native_tools/AGENTS.md`, `pydantic_ai_slim/pydantic_ai/capabilities/AGENTS.md` each define where provider API behavior belongs and what must remain in core.
- **User docs:** `docs/models/overview.md:74-87` (capability flags), `docs/models/*.md` per provider, `docs/native-tools.md:1-1141` (provider × tool matrix with parameter support), `docs/mcp/client.md`/`docs/mcp/server.md`, `docs/ui/ag-ui.md`/`docs/ui/vercel-ai.md`, `docs/capabilities/overview.md` (#provider-adaptive-tools), `docs/api/models/*` and `docs/api/providers.md`. The `native-tools.md` file alone is ~1,100 lines of support tables and is the canonical interop map for native tools.
- **Gap:** No single consolidated "Interop Boundary Diagram" (core ↔ middleware ↔ adapters ↔ transports) or versioned compatibility matrix across LLM and UI protocols; docs are discoverable per feature but scattered, so a newcomer must synthesize the overall boundary from multiple pages.

## Architectural Decisions

| **Provider owns client/auth/base_url; Model owns translation** — separation in `Provider` vs `Model` with `Provider.model_profile` as second layer in `Model.profile` resolution | Lets same `ModelProfile` be reused across providers (e.g., `OpenAIResponsesModel` behind 8 provider namespaces) while keeping auth concerns out of translation logic | `pydantic_ai_slim/pydantic_ai/providers/__init__.py:42-100` ; `pydantic_ai_slim/pydantic_ai/models/__init__.py:864-903` |
| **`WrapperModel` + `InstrumentedModel` + `FallbackModel` as composable decorators** | Runtime swappability without subclassing: instrumentation, fallback, threading, and durability wrap any `Model` instance via delegation and `__getattr__` forwarding | `pydantic_ai_slim/pydantic_ai/models/wrapper.py:32-158` ; `pydantic_ai_slim/pydantic_ai/models/instrumented.py:332-408` |

## Notable Patterns

- **Three-layer profile merge (DEFAULT → provider → user) with intersection guard.** `Model.profile` (`pydantic_ai_slim/pydantic_ai/models/__init__.py:864-903`) merges `DEFAULT_PROFILE` → `provider.model_profile(model_name)` → user `profile=` (dict or `Callable[[ModelProfile],ModelProfile]`), then intersects `supported_native_tools` with `cls.supported_native_tools()` so the adapter's implemented set is the single source of truth.
- **Adapter-declared capability sets intersected with profile claims.** `supported_tool_deferral_modes`/`supported_tool_addition_modes` on the `Model` subclass (`pydantic_ai_slim/pydantic_ai/models/openai.py:1946`, `pydantic_ai_slim/pydantic_ai/models/function.py:61`) gate profile claims (`pydantic_ai_slim/pydantic_ai/models/__init__.py:467-477`) — prevents emitting a wire flag for a mode the adapter can't render.
- **Boundary capture pattern for tests.** `tests/AGENTS.md:153` + `tests/test_tool_availability_portability.py` + `tests/providers/*.py` assert against *rendered* adapter output rather than mocking SDK internals, keeping tests valid when SDK internals change.
- **Version-gated UI adapter (`ag_ui_version` / `sdk_version`).** `AGUIAdapter.ag_ui_version` (`pydantic_ai_slim/pydantic_ai/ui/ag_ui/_adapter.py:237`) and `VercelAIAdapter.sdk_version` (`pydantic_ai_slim/pydantic_ai/ui/vercel_ai/_adapter.py:149`) gate new wire shapes behind version checks and `skip_unknown_tagged_items` forward-compat, per `pydantic_ai_slim/pydantic_ai/ui/AGENTS.md:3-12`.
- **MCP unified `local`↔`native` seam.** One `MCP(url=, native=, local=)` capability produces both a local `MCPToolset` (with `unless_native` filtering) and a native `MCPServerTool` advertisement, letting the same config work across models that support hosted MCP and those that don't (`pydantic_ai_slim/pydantic_ai/capabilities/mcp.py:27-148` ; `pydantic_ai_slim/pydantic_ai/mcp.py:715-1005`).
- **External ecosystem bridge at toolset layer.** `LangChainToolset` (`pydantic_ai_slim/pydantic_ai/ext/langchain.py:32-71`) avoids core edits by translating external tool schemas into `ToolDefinition` — the pattern for adding a new ecosystem without touching providers/models.

## Tradeoffs

| Tradeoff | Pro | Con |
|----------|-----|-----|
| **Closed provider/model registries + open instance path** (`infer_provider_class`, `infer_model`, `KnownModelName`) | Exhaustive type-checker completion and friendly `Did you mean ...?` suggestions (`pydantic_ai_slim/pydantic_ai/models/__init__.py:1446-1493`); clear distribution boundary | Adding a built-in shorthand still touches core registry files; third-party providers can't self-register a `provider:` prefix without a core PR (workaround: pass instance) |
| **Profile-intersection guard** (`supported_native_tools` & `Model.supported_native_tools()` intersection) | `model.profile` never lies about what the adapter can actually send | A profile that advertises a tool never gets surfaced silently — failures are deferred to `resolve_request_tools` `UserError` (`pydantic_ai_slim/pydantic_ai/models/__init__.py:1857-1870`) rather than a compile-time check |
| **Version-gated UI adapters instead of version bumps** | Old servers don't crash on new protocol fields (AG-UI `skip_unknown_tagged_items`, Vercel `sdk_version` fallback) | Adapter code accumulates version conditionals (`pydantic_ai_slim/pydantic_ai/ui/ag_ui/_adapter.py:238-256`, `pydantic_ai_slim/pydantic_ai/ui/vercel_ai/_adapter.py:285-295`); UI adapters carry ~1k+ lines each |

## Future Considerations

- **Self-registration for providers/models.** Replace the closed `infer_provider_class`/`infer_model` match blocks with a decorator registry (`@register_provider("myprovider")`) so third-party packages can add a `provider:model` prefix without forking core — keep `KnownModelName` as a curated union plus an escape hatch for external literals.
- **Cross-protocol conformance harness.** Extract a `ModelConformanceSuite` that runs the same contract tests (request/stream/prepare_messages/profile intersection/provider_details preservation) over every registered `Model` subclass, similar to the existing `test_resolution_matrix.py` but driven by `infer_model` enumeration rather than snapshots.
- **Centralized interop boundary spec.** Publish one page (e.g., `docs/interop-boundaries.md`) with a diagram (core ↔ providers ↔ native tools ↔ UI adapters ↔ MCP), a provider×feature matrix (streaming, cancellation, compaction, tool search, file search, reasoning tags), and explicit versioning/deprecation policy per adapter.
- **Pluggable visibility resolver.** Turn the `resolve_request_tools` branching table (`pydantic_ai_slim/pydantic_ai/models/__init__.py:1890-1936`) into a strategy object so a new `tool_deferral_mode` doesn't require editing the central function — adapters would supply a `VisibilityResolver` instead of a `can_withhold_tool_schemas` predicate pair.
