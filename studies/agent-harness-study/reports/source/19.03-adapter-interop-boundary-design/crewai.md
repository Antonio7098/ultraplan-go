## Summary

CrewAI treats external standards as **adapter-layer plugins** behind small core abstractions rather than as core domain objects. Three interop families coexist: LLM providers (native SDK wrappers over `BaseLLM` + LiteLLM fallback), MCP tool servers (typed configs + transport + client + resolver), and A2A remote agents (config + wrapper + extension registry). Boundaries are explicit and typed (Pydantic configs, ABCs, Protocols) with per-call isolation for MCP and hook-based extensibility for A2A. However, adding a truly new protocol (new LLM provider, new MCP transport, new A2A update mode) still requires touching core factory/registry code, there is no runtime plugin manifest, and conformance testing is uneven (strong for A2UI schemas, ad-hoc elsewhere).

## Rating

**Score: 7 / 10 — Clear model with explicit interfaces, tests, and operational safeguards, but requires core changes to add new protocols and shows inconsistent runtime swappability.**

Rationale: `BaseLLM` (`lib/crewai/src/crewai/llms/base_llm.py:150`), `BaseTool` (`lib/crewai/src/crewai/tools/base_tool.py:103`), `BaseTransport` (`lib/crewai/src/crewai/mcp/transports/base.py:37`), and `A2AExtension` (`lib/crewai/src/crewai/a2a/extensions/base.py:57`) define durable contracts. Adapter implementations are isolated under `lib/crewai/src/crewai/llms/providers/*/completion.py`, `lib/crewai/src/crewai/mcp/transports/*.py`, and `lib/crewai/src/crewai/a2a/extensions/a2ui/*.py`. Operational safeguards exist (timeouts, retry, per-invocation client factories, schema cache, events). Counterweights: provider/transport discovery is hard-coded in `lib/crewai/src/crewai/llm.py:478` and `lib/crewai/src/crewai/mcp/tool_resolver.py:281`, and conformance tests only systematically cover A2UI vendor schemas (`lib/crewai/tests/a2a/extensions/test_a2ui_schema_conformance.py:1`).

## Answers to Dimension Questions

**1. Are protocols core or adapter-layer?**
Adapter-layer behind narrow core contracts. LLM interop is split: `BaseLLM` (`lib/crewai/src/crewai/llms/base_llm.py:150`) is the core contract; six native SDK adapters implement it (`lib/crewai/src/crewai/llms/providers/openai/completion.py:180`, `anthropic`, `azure`, `bedrock`, `gemini`, `snowflake`, `openai_compatible`). Unmatched models fall back to LiteLLM (`lib/crewai/src/crewai/llm.py:478`). MCP is similarly adapterized: `BaseTransport` (`lib/crewai/src/crewai/mcp/transports/base.py:37`) defines the contract, three transports implement it, `MCPClient` (`lib/crewai/src/crewai/mcp/client.py:59`) encapsulates session + events, and `MCPToolResolver` (`lib/crewai/src/crewai/mcp/tool_resolver.py:45`) maps typed configs (`lib/crewai/src/crewai/mcp/config.py:12,53,90`) to `BaseTool` instances. A2A is an overlay: `A2AClientConfig`/`A2AServerConfig` (`lib/crewai/src/crewai/a2a/config.py:465,552`) model the protocol, while `wrap_agent_with_a2a_instance` (`lib/crewai/src/crewai/a2a/wrapper.py:97`) injects delegation without changing the agent's core `BaseAgent` contract. Tool interop follows the same split: `BaseTool`/`CrewStructuredTool` core (`lib/crewai/src/crewai/tools/base_tool.py:103`, `lib/crewai/src/crewai/tools/structured_tool.py:189`) plus framework bridges like `BaseToolAdapter`/`LangGraphToolAdapter` (`lib/crewai/src/crewai/agents/agent_adapters/base_tool_adapter.py:13`, `lib/crewai/src/crewai/agents/agent_adapters/langgraph/langgraph_tool_adapter.py:1`).

**2. Can adapters be added without core changes?**
Partially — configuration-level swappability is high, but code-level extensibility still touches core. *Without core change*: a new LLM model within an existing provider prefix (e.g. `openai/gpt-4o-mini`) auto-routes via `_matches_provider_pattern` (`lib/crewai/src/crewai/llm.py:515`); a new MCP server is just another `MCPServerStdio/HTTP/SSE` entry (`lib/crewai/src/crewai/mcp/config.py:12`); a new A2A remote agent is a new `A2AClientConfig(endpoint=...)`; a new A2A processing hook is a class implementing `A2AExtension` and passed via `client_extensions` (`lib/crewai/src/crewai/a2a/config.py:421`) then registered via `create_extension_registry_from_config` (`lib/crewai/src/crewai/a2a/extensions/registry.py:123`). *Requires core change*: a genuinely new LLM provider family needs an entry in `provider_mapping` + `_get_native_provider` + `SUPPORTED_NATIVE_PROVIDERS` + constants (`lib/crewai/src/crewai/llm.py:432,665,327`); a new MCP transport needs a new `BaseTransport` subclass plus a branch in `_create_transport` (`lib/crewai/src/crewai/mcp/tool_resolver.py:281`); a new A2A update mechanism needs a new `UpdateConfig` variant registered in the `a2a/updates` package. No declarative plugin manifest or entry-point discovery exists.

**3. Are adapters tested for conformance?**
Uneven. Strongest is A2UI: `test_a2ui_schema_conformance.py:206` cross-validates every vendor payload and catalog component against both Pydantic models and vendored JSON schemas, failing the build when they drift. MCP and A2A have behavioral integration tests rather than spec-conformance suites: MCP transport wiring + parallel/fresh-client tests (`lib/crewai/tests/mcp/test_mcp_config.py:49,187,218`) and A2A wrapper/kickoff tests (`lib/crewai/tests/agents/test_agent_a2a_wrapping.py`, `lib/crewai/tests/agents/test_agent_a2a_kickoff.py`). LLM provider conformance is exercised indirectly via streaming + finish-reason + tool-call tests (`lib/crewai/tests/llms/*`, `lib/crewai/tests/test_llm.py`) but there is no shared `BaseLLM` contract test that asserts every provider obeys `call`/`_apply_stop_words`/`supports_multimodal` semantics identically. No operation was found that proves failure/scale behavior of adapters under partition (e.g., MCP server flap) beyond retry paths in `lib/crewai/src/crewai/mcp/client.py:44,688`.

**4. Are interop boundaries documented?**
Code-level boundaries are well documented, user-level uneven. Each adapter boundary carries intent docstrings: `BaseTransport` contract (`lib/crewai/src/crewai/mcp/transports/base.py:37`), `BaseLLM` provider guidance (`lib/crewai/src/crewai/llms/base_llm.py:150`), `A2AExtension` note distinguishing CrewAI processing hooks from A2A protocol `X-A2A-Extensions` header (`lib/crewai/src/crewai/a2a/extensions/base.py:1,9`), and the header mechanics themselves (`lib/crewai/src/crewai/a2a/extensions/registry.py:1,51`). User docs cover the common MCP path (`docs/edge/en/mcp/overview.mdx`, `docs/.../mcp/multiple-servers.mdx`) but the broader adapter catalog (how to author a new `BaseLLM`, `BaseTransport`, or `A2AExtension`, version negotiation, security scheme mapping) lives primarily in type signatures and examples rather than a single interop handbook.

## Architectural Decisions

- **Narrow abstract cores with typed Pydantic configs.** LLM, MCP, and A2A each expose a Pydantic/ABC surface (`BaseLLM`, `MCPServerConfig` union, `A2AClientConfig`/`A2AServerConfig`, `A2AExtension`) — observed in `lib/crewai/src/crewai/llms/base_llm.py:150`, `lib/crewai/src/crewai/mcp/config.py:123`, `lib/crewai/src/crewai/a2a/config.py:465`, `lib/crewai/src/crewai/a2a/extensions/base.py:57`. Tradeoff: strong static checking and editor support vs. verbosity of config and extra indirection through factory/resolver layers.
- **Factory centralization for LLMs (`LLM.__new__`).** Single routing site (`lib/crewai/src/crewai/llm.py:393`) decides native vs LiteLLM, extracts provider, validates against constants, and memoizes 404→Responses-only learning (`lib/crewai/src/crewai/llms/providers/openai/completion.py:61`). Tradeoff: concise call site (`LLM(model="openai/gpt-4o")`) vs. hard-coded provider knowledge that must be updated for each new ecosystem.
- **Resolver + per-call client factories for MCP.** `MCPToolResolver._resolve_native` creates a throwaway discovery transport then closure-captures `_client_factory` inside `MCPNativeTool` (`lib/crewai/src/crewai/mcp/tool_resolver.py:315,417`) so concurrent invocations never share a `ClientSession`. Tradeoff: eliminates transport-level races (proved by `test_each_invocation_gets_fresh_client` at `lib/crewai/tests/mcp/test_mcp_config.py:187`) at the cost of reconnect overhead and limited connection pooling.
- **Monkey-patch wrapper for A2A instead of inheritance.** `wrap_agent_with_a2a_instance` replaces `execute_task`/`kickoff` via `MethodType` (`lib/crewai/src/crewai/a2a/wrapper.py:166,232`) and restores `task.description`/`response_model` in `finally` blocks. Keeps agent class hierarchy stable but entangles interception order and makes wrapper stacking fragile.
- **Dual meaning of "extension".** CrewAI separates `A2AExtension` processing hooks (`lib/crewai/src/crewai/a2a/extensions/base.py`) from A2A protocol `AgentExtension` URIs sent via `X-A2A-Extensions` (`lib/crewai/src/crewai/a2a/extensions/registry.py:51`). Correct but discoverability suffers; newcomers conflate the two without reading header docs.
- **LiteLLM as universal fallback.** Non-native models route to `litellm.completion` lazily loaded (`lib/crewai/src/crewai/llm.py:113,494`). Buys broad model coverage with near-zero adapter authoring cost; downgrade path is opaque when LiteLLM mapping drifts from vendor reality.
- **Skill distribution via registry + cache.** `resolve_registry_ref` (`lib/crewai/src/crewai/skills/registry.py:114`) implements local→`~/.crewai/skills/`→download precedence with version pins and HMAC-aware caching. Distribution adapter, not protocol adapter, but shows the team's preference for explicit resolution over implicit import-hooks.

## Notable Patterns

- **Template-method + hook reducer.** `BaseLLM.call` template emits `LLMCallStartedEvent` → `_invoke_before_llm_call_hooks` → provider RPC → `_apply_stop_words`/`_invoke_after_llm_call_hooks` → `LLMCallCompletedEvent` (`lib/crewai/src/crewai/llms/base_llm.py:552,988,1050`). Mirrored in A2A's `ExtensionRegistry` reducer chain (`lib/crewai/src/crewai/a2a/extensions/base.py:213,233,253`).
- **Transport abstraction with memory streams.** `BaseTransport._set_streams`/`_clear_streams` over AnyIO `MemoryObjectReceiveStream/SendStream` (`lib/crewai/src/crewai/mcp/transports/base.py:36`) gives stdio/SSE/HTTP uniform `read_stream`/`write_stream` accessors consumed by `mcp.ClientSession`.
- **Policy-aware tool description.** `formatted_description` lazy-composes `Tool Name / Tool Arguments (JSON Schema) / Tool Description` on demand (`lib/crewai/src/crewai/tools/base_tool.py:495`, `lib/crewai/src/crewai/tools/structured_tool.py:145`) preserving authored `description` — previous mutation-in-`__init__` caused checkpoint skew.
- **Schema fork tolerance.** OpenAI `ResponsesAPI` built-in tools use flat `{"type":"function","name":…,"parameters":…}` vs Chat Completions' nested form; `_convert_tools_for_responses` (`lib/crewai/src/crewai/llms/providers/openai/completion.py:920`) and `_to_responses_input` (`lib/crewai/src/crewai/llms/providers/openai/completion.py:750`) bridge the fork rather than exposing it to agents.
- **Validated extension protocol.** `ValidatedA2AExtension = Annotated[Any, BeforeValidator(_validate_a2a_extension)]` (`lib/crewai/src/crewai/a2a/extensions/base.py:36`) enforces protocol conformance at Pydantic validation time for `A2AClientConfig.client_extensions` (`lib/crewai/src/crewai/a2a/config.py:421`).

## Tradeoffs

- **Explicit typing vs. plugin agility.** Every new provider/transport/client extension is explicit in code and validated at construction — great for mypy/IDE, poor for third-party out-of-tree distribution without a PR to `llm.py`/`tool_resolver.py`. No entry-point or registry scanning.
- **Per-call isolation vs. throughput.** MCP's fresh-client-per-call (`lib/crewai/src/crewai/mcp/tool_resolver.py:417`) removes need for a pooled session manager and passes parallel-execution tests (`lib/crewai/tests/mcp/test_mcp_config.py:218`), but pays TLS/handshake cost even for high-churn tools. `cache_tools_list` (`lib/crewai/src/crewai/mcp/client.py:44`) only mitigates discovery, not execution.
- **Native SDK fidelity vs. LiteLLM breadth.** Native wrappers (`lib/crewai/src/crewai/llms/providers/*/completion.py`) preserve vendor nuances (Bedrock `max_completion_tokens`, OpenAI Responses `include: reasoning.encrypted_content`) while LiteLLM flattens them via `get_supported_openai_params`. Users straddle two observability stacks (vendor SDK + `crewai_event_bus`) when debugging provider differences.
- **Wrapper monkey-patching vs. composition.** A2A `MethodType` wrapping (`lib/crewai/src/crewai/a2a/wrapper.py:166`) avoids a taxonomy of `A2AAgent` subclasses and keeps `Agent` serializable, but buries interception order and makes it easy to double-wrap or shadow task mutation side-effects.
- **Two extension planes.** Keeping CrewAI processing hooks separate from A2A protocol `extensions` header (`lib/crewai/src/crewai/a2a/extensions/registry.py:51` vs `base.py:57`) is semantically correct per `a2a-protocol.org`, yet creates a naming collision that requires careful reading to avoid miswiring.

## Failure Modes / Edge Cases

- **Provider routing misclassification.** A typo'd provider prefix (e.g. `opneai/gpt-4o`) silently becomes a LiteLLM model name with prefix-as-provider (`lib/crewai/src/crewai/llm.py:468`) — LiteLLM then fails with a remote API error rather than a local validation error.
- **New model outside constants but behind custom endpoint.** `openai/<unknown>` with `custom_openai=True` requires explicit `base_url` / `api_base` (`lib/crewai/src/crewai/llms/providers/openai/completion.py:258`, `lib/crewai/src/crewai/llm.py:409`); without it, routing throws `ValueError` even though the endpoint could serve the model. The `_LEARNED_RESPONSES_ONLY_MODELS` set (`lib/crewai/src/crewai/llms/providers/openai/completion.py:65`) also retains 404 state per process for the whole session — a transient 404 poisons later calls.
- **MCP event-loop contention.** `_resolve_native` detects a running loop and marshals discovery onto a `ThreadPoolExecutor` (`lib/crewai/src/crewai/mcp/tool_resolver.py:362`); if that secondary loop also hits `asyncio.run` cancellation scopes, the error is reclassified as `ConnectionError` (`lib/crewai/src/crewai/mcp/tool_resolver.py:376`) and may obscure the original auth failure. `MCPClient._cleanup_on_error` also re-raises its own `RuntimeError` on `aclose` failure (`lib/crewai/src/crewai/mcp/client.py:359`), masking the root cause.
- **Tool-filter contract drift.** `ToolFilter` accepts either `Callable[[dict], bool]` or `Callable[[ToolFilterContext, dict], bool]`; dispatch tries context-aware first, falls back on `TypeError/AttributeError` (`lib/crewai/src/crewai/mcp/tool_resolver.py:394`). An async filter or a filter raising a different exception bypasses this and fails the discovery entirely.
- **A2A card fetch `fail_fast` semantics.** `_fetch_agent_cards_concurrently` (`lib/crewai/src/crewai/a2a/wrapper.py:262`) collects failures per endpoint; with `fail_fast=True` (default `lib/crewai/src/crewai/a2a/config.py:409`) a single unreachable remote aborts the whole task, with `fail_fast=False` the task silently degrades to LLM-only — both modes emit different prompts (`UNAVAILABLE_AGENTS_NOTICE_TEMPLATE` vs threaded exception).
- **LiteLLM absence at runtime.** `LLM.__new__` raises an `ImportError` with install guidance only after failing both native resolution and lazy `_ensure_litellm()` (`lib/crewai/src/crewai/llm.py:494`); agents constructed before LiteLLM is installed but used after install still hold the earlier error path until re-instantiated.
- **AMP bulk fetch partial failure.** `_resolve_amp` (`lib/crewai/src/crewai/mcp/tool_resolver.py:118`) emits `MCPConfigFetchFailedEvent` per missing slug but returns the tools for the remaining slugs — callers must correlate events to understand which tools are absent, there is no aggregated `Result` object.
