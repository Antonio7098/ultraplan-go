## Summary

Langfuse is an LLM observability platform, not a generic agent harness. Its interop surface is ingestion-oriented: a legacy Langfuse event batch (`POST /api/public/ingestion`), a standards-compliant OTLP trace endpoint (`POST /api/public/otel/v1/traces`), a Model Context Protocol (MCP) server over Streamable HTTP, and a closed set of LLM provider adapters (OpenAI, Anthropic, Azure, Bedrock, VertexAI, Google AI Studio) mediated through Vercel AI SDK. MCP is the only place an explicit adapter/registry abstraction exists (`McpFeatureModule` + `ToolRegistry`), but registration is static at boot and every new feature still requires editing `bootstrap.ts`. LLM adapters are a compile-time `enum` with an exhaustive `switch` — not a plugin interface. OTel ingestion is a monolithic processor class (`OtelIngestionProcessor`, ~3636 lines) with no pluggable serialization/allocation adapter. Adding any new protocol (new LLM provider, new MCP feature, new telemetry signal, new ingestion encoding) touches core shared/web/worker code, queue definitions, and Fern specs. Tests are product-level servertests per protocol, not adapter conformance suites, and extension points are documented only via inline code comments and Fern YAML, not via an extension guide.

## Rating

**5 / 10 — Present but inconsistent, weakly documented, and fragile to extend.**

Rationale: MCP feature registry (`web/src/features/mcp/server/registry.ts:49`) and LLM provider translation (`packages/shared/src/server/llm/ai-sdk/providers/`) demonstrate awareness of adapter boundaries and have systematic tests, but (a) protocols are core, not adapters — ingestion queues and OTel processor are first-class platform concepts (`packages/shared/src/server/queues.ts:405`, `packages/shared/src/server/otel/OtelIngestionProcessor.ts:241`), (b) adapters are not swappable at runtime — `LLMAdapter` (`packages/shared/src/server/llm/types.ts:246`) is a closed enum and MCP features are statically imported in `bootstrap.ts:30-46`, (c) no generic conformance harness exists — each protocol has bespoke servertests rather than a `ToolRegistry`-driven contract test, (d) adding a new adapter always requires core changes (exhaustive switch in `llmText.ts:545`, manual entry in `MCP_FEATURES`). Operational hardening is strong on the edge (auth, rate-limit, payload validation) but not on extensibility.

## Answers to Dimension Questions

**1. Are protocols core or adapter-layer?**

Protocols are **core**, with one partial adapter layer. The two ingestion protocols are top-level Next.js routes (`web/src/pages/api/public/ingestion.ts:55`, `web/src/pages/api/public/otel/v1/traces/index.ts:27`) backed by shared queue contracts (`packages/shared/src/server/queues.ts:405`) and a monolithic `OtelIngestionProcessor` (`packages/shared/src/server/otel/OtelIngestionProcessor.ts:241`). LLM "adapters" are a closed enum (`packages/shared/src/server/llm/types.ts:246`) whose exhaustive switch (`packages/shared/src/server/llm/llmText.ts:545`) lives in shared core. MCP is the exception: `McpFeatureModule` (`web/src/features/mcp/server/registry.ts:49`) + `ToolRegistry` (`web/src/features/mcp/server/registry.ts:72`) + `defineTool` (`web/src/features/mcp/core/define-tool.ts:112`) constitute a genuine adapter boundary where feature modules contribute tools without editing the server handler — but even there, wiring is static in `bootstrap.ts:30`.

**2. Can adapters be added without core changes?**

No. All three surfaces require core edits:

- New LLM provider: add enum value in `types.ts:246`, add entry in `supportedModels` (`types.ts:459`), add `case` in `translateLegacyProviderOptions` (`llmText.ts:545`), add new file under `ai-sdk/providers/`, update `buildAiSdkModel` resolver, update `llmConnections` Fern/API types (`fern/apis/server/definition/llm-connections.yml`). The `never` check (`llmText.ts:599`) enforces this at compile time.
- New MCP feature: create `web/src/features/mcp/features/<name>/index.ts` exporting a `McpFeatureModule`, add import and array entry in `web/src/features/mcp/server/bootstrap.ts:13-46`, add policy entries in `packages/shared/src/in-app-agent/server/mcpPolicy.ts:27` (otherwise `in-app-agent-mcp-policy.servertest.ts:13` fails). Redeploy required; no dynamic loading or `package.json` plugin.
- New telemetry signal (e.g., OTLP logs): add route `web/src/pages/api/public/otel/v1/logs`, new processor/queue (`queues.ts:405`), handling in `OtelIngestionProcessor` (currently trace-only; `validateOtelSpanIds` at `otel/v1/traces/index.ts:132` explicitly rejects log exports). Adding a new serialization (msgpack, etc.) similarly requires route + middleware change (`withMiddlewares.ts:88` bodyParser config).

**3. Are adapters tested for conformance?**

Partially and non-generically. There is no shared adapter-conformance harness; each protocol has bespoke servertests that implicitly act as conformance:

- OTel: `otelMapping.servertest.ts:89` covers 30+ sender variants (OpenLit, TraceLoop, Semantic Kernel, Genkit, GenAI semconv priority at `otelMapping.servertest.ts:2781`), and `utils.test.ts:76` covers malformed ID / collection shape. These verify translation correctness, not the `OtelIngestionProcessor` interface itself. Worker queue tests (`worker/src/queues/__tests__/otelFlueMapping.test.ts:5`, `otelToObservationForEval.test.ts:108`) repeat coverage per consumer.
- MCP: helpers assert the transport contract `content: [{type:"text", text: JSON.stringify(result)}]` (`mcp-helpers.ts:84-85`), but not MCP JSON-RPC framing conformance against the SDK spec. The strongest gate is the policy exhaustiveness test (`in-app-agent-mcp-policy.servertest.ts:13`) which fails if a registry tool lacks a `mcpPolicy` entry. Auth/security tests (`mcp-auth.servertest.ts:20`, `mcp-security.servertest.ts:17`) cover boundary hardening, not tool contract.
- LLM: `llmConnections.test.ts:27` and per-provider `*.test.ts` files (`anthropic.test.ts`, `openai.test.ts`) test provider option translation, not a uniform `LLMAdapter` interface (no contract that all adapters accept the same `ModelParams` shape and return an `ai` `LanguageModel`).

Gap: no property-based or cross-adapter matrix (e.g., "every `LLMAdapter` must round-trip through `generateLLMText` via AI SDK mock") and no MCP compliance suite against the official MCP Inspector.

**4. Are interop boundaries documented?**

Inconsistently. Wire contracts are well documented where Fern exists: `fern/apis/server/definition/opentelemetry.yml:7` describes OTLP endpoint, content types, gzip, and links integration guide; `fern/.../ingestion.yml:12` documents deprecation and points to OTel. Generated OpenAPI (`web/public/generated/api/openapi.yml:3817`) mirrors these. Code-level boundaries have inline doc comments: `web/src/pages/api/public/mcp/index.ts:3-24` explains Streamable HTTP 2025-03-26, stateless per-request pattern, and why `withMiddlewares` is not used; `packages/shared/src/server/llm/llmText.ts:503-507` explains the compatibility boundary between persisted `ChatMessage` and AI SDK `ModelMessage`; `web/src/features/mcp/server/mcpServer.ts:31-36` documents tool evolution expectations. However, there is no `docs/adapter-boundaries.md` or extension guide; `packages/shared/AGENTS.md:59` and `web/AGENTS.md` list which barrels to import but not how to add a new adapter. An external contributor discovering `defineTool` (`define-tool.ts:89-111`) would need to infer usage from existing feature examples (`web/src/features/mcp/features/prompts/tools/*`).

## Architectural Decisions

- **Shared owns queue and ingestion contracts.** `pnpm-workspace.yaml:3-6` defines `web`, `worker`, `packages/**`, `ee` with `worker -> @langfuse/shared <- web` ordering (`AGENTS.md`). Queue payload schemas (`packages/shared/src/server/queues.ts:31-70`) and Zod ingestion schemas (`ingestion/types.ts:415`) are the single source of truth, preventing web/worker drift during rolling deploys.
- **Monolithic OTel processor over pluggable mappers.** `OtelIngestionProcessor` (`otel/OtelIngestionProcessor.ts:1-3636`) centralizes all semconv translation (GenAI v1.37+, OpenInference, `langfuse.observation.*`) rather than a chain of adapter objects. Benefits: single place for array-slot budgeting (`OtelIngestionProcessor.ts:112-120`), observation type priority (`ObservationTypeMapper.ts:216`), and conversion-failure logging (`OtelIngestionProcessor.ts:3444`). Cost: high coupling, hard to add new signal without expanding the god class.
- **MCP registry pattern mimicking harness plugin systems, minus dynamism.** `ToolRegistry` enforces duplicate detection (`registry.ts:82-96`) and enablement filtering (`registry.ts:117-189`), closely resembling a plugin manager. But auto-bootstrap on import (`bootstrap.ts:70`) makes it look like a registry while behaving like a manifest — all features are bundled, no lazy load, no external package discovery. Suggests intent toward extensibility, truncated at static wiring.
- **Closed LLMAdapter enum as intentional wall.** The exhaustive switch with `_exhaustiveCheck: never` (`llmText.ts:599`) deliberately prevents silent passthrough of unknown adapters, valuing correctness over open-ended extension. Provider translation is isolated per file, but the decision point remains centralized — a conservative trade for API correctness over community-contributed providers.
- **Dual-write migration mode (`events_only` vs `dual`).** `web/src/pages/api/public/ingestion.ts:154-254` and `web/src/pages/api/public/otel/v1/traces/index.ts:270` implement a write-mode gate (`LANGFUSE_MIGRATION_V4_WRITE_MODE`) that rejects legacy trace events in `events_only` deployments. This documents that the legacy ingestion adapter is being retired in favor of the OTel adapter, with `dual` as the bridge — a pragmatic interop lifecycle rather than perpetual dual support.

## Notable Patterns

- **Feature-module as adapter unit (MCP).** Each domain (`prompts`, `datasets`, `scores`, ...) contributes an object `{name, description, tools, isEnabled?}` that self-registers (`registry.ts:49`). `defineTool` separates `baseSchema` (for JSON Schema generation via `z.toJSONSchema(..., draft-7)`) from `inputSchema` (for runtime validation with refinements) — `define-tool.ts:31-34` — handling the MCP JSON Schema draft-7 limitation where unions/intersections are illegal (`define-tool.ts:138-142`).
- **Per-request server, context-in-closure (MCP).** Fresh `new Server(...)` per HTTP request with `ServerContext` captured in handlers (`mcpServer.ts:57-83`). Avoids session state and aligns with Next.js serverless execution; trades connection reuse for isolation. Similar to harness agent-per-request isolation.
- **Array-slot budget as backpressure on OTel attribute abuse.** `ArraySlotBudget` (`OtelIngestionProcessor.ts:112`) transactionally reserves dotted-path array lengths (`langfuse.observation.metadata.foo`) against `MAX_OTEL_RECONSTRUCTED_ARRAY_SLOTS`; overflow drops the attribute branch and increments `OTEL_ARRAY_ATTRIBUTE_DROPPED_METRIC`. Prevents OTel attribute-cardinality blowups from materializing huge arrays — a production-hardening pattern missing from simpler adapters.
- **Policy-as-shared-contract for in-app-agent.** `IN_APP_AGENT_LANGFUSE_MCP_TOOL_POLICIES` (`mcpPolicy.ts:27`) in shared makes web and worker agree on approval/availability without importing web registry, and the plating `langfuse_<tool>` prefix (`mcpPolicy.ts:366`) avoids collision across surfaces. `createInAppAgentToolPolicy` (`mcpPolicy.ts:477`) centralizes RBAC checks via `hasProjectAccessByRole`.
- **Secure fetch stripping on redirect.** `createSecureLlmFetch` (`llmText.ts:306-318`) concatenates `extraHeaders` keys onto sensitive headers that are stripped on cross-origin redirects — an interop boundary safeguard against SSRF/credential leak when custom `baseURL` points to user-controlled gateways.

## Tradeoffs

- **Correctness vs extensibility (LLM):** Centralizing all provider translation in `llmText.ts:545` enables strict validation (`LLMValidationError` if unknown keys, `assertDefinitionOnlyTools` at `llmText.ts:417`) but blocks community-contributed providers. A dynamic provider registry (e.g., map from `adapterId` → module) would allow third-party adapters but requires sandboxing and versioning.
- **Simplicity vs isolation (OTel):** One processor with direct S3 → queue → ClickHouse flow (`otel/OtelIngestionProcessor.ts:311` S3 upload, `OtelIngestionQueue` publishing) keeps the write path simple and observable. A mapper-per-semconv adapter chain (GenAI mapper, OpenInference mapper, Langfuse extension mapper) would isolate concerns but multiplies maintenance points and cross-mapper ordering bugs.
- **Bundle-size vs discoverability (MCP):** Static imports in `bootstrap.ts:13` guarantee tree-shaking visibility and TypeScript exhaustiveness, but produce a fat bundle (all 15 features always loaded) and prevent zero-downtime incremental rollout of new features behind flags without full redeploy.
- **Deprecation velocity vs compatibility:** `ingestion.yml:10-12` marks legacy ingestion deprecated with a hard date (2026-11-16 on Cloud) and `events_only` rejection (`ingestion.ts:154`). Strong signal to move to OTel, but forces integrations on pinned SDK versions to either upgrade or set `dual` mode — operational cost for slow-moving clients.
- **Stateless per-request vs streaming session:** MCP's per-request `Server` (`mcpServer.ts:58`) aligns with stateless HTTP and simplifies auth (no session token management), but loses server-side resource subscriptions and progress notifications that MCP supports via persistent SSE sessions; future extended MCP features (resources, roots) would need session affinity.

## Failure Modes / Edge Cases

- **OTel log export misrouted to trace endpoint** (`web/src/pages/api/public/otel/v1/traces/index.ts:123-236`): ResourceLogs shares protobuf field numbers with ResourceSpans, so logs decode as spans with valid scope but no `traceId`/`spanId`. `validateOtelSpanIds` catches `invalidSpanCount` and `malformedCollectionCount`, returning 400 with hints (`traceId and spanId are required...`, `attributes must be arrays...`) rather than silently burning all 6 BullMQ retries. Without this, worker jobs would retry until drop; previously observed in production (comment at `otel/v1/traces/index.ts:115`).
- **OTel attribute cardinality blowup**: `OtelIngestionProcessor.ts:112-154` budget guard drops `langfuse.observation.metadata` branches that would allocate >`MAX_OTEL_RECONSTRUCTED_ARRAY_SLOTS` slots; `metadataDropped.test.ts:87-630` shows `drop`, `primitive_drop`, `parse_failure`, and `metadata_drop` counters. Failure mode: spammy sender can inflate ClickHouse `metadata` column if guard is bypassed; guard trades data loss (dropped attribute) for write stability.
- **Cross-origin redirect leaks provider keys** (`packages/shared/src/server/llm/secureLlmFetch.ts` via `llmText.ts:306-318`): Custom `baseURL` + `extraHeaders` could leak on redirect if not stripped. `secureLlmFetch` treats `extraHeaders` keys as sensitive alongside `Authorization`. Missing this would allow open-redirect SSRF to exfiltrate gateway credentials — tested in `worker/src/__tests__/secureLlmFetch.test.ts:138`.
- **MCP tool name collision** (`registry.ts:88-94`): Duplicate `tool.definition.name` throws at bootstrap, crashing the web pod. Intentional fail-fast, but depends on human review of `MCP_FEATURES` array — no build-time dedup lint. Adding a third-party feature that reuses a name would be a DoS vector if dynamic registration were allowed.
- **MCP auth bypass via Bearer / org keys** (`web/src/pages/api/public/mcp/index.ts:99-105`): Endpoint explicitly requires `accessLevel==="project"` + BasicAuth. Org-scoped or Bearer keys yield 403. Failure mode: clients reusing SDK ingestion keys (org-level) would be silently rejected; error message is explicit but not discoverable without hitting the endpoint.
- **Ingestion version future-proofing** (`web/src/pages/api/public/otel/v1/traces/index.ts:270-283`): Unknown `x-langfuse-ingestion-version > 4` is rejected (400). Prevents newer SDKs with incompatible payloads from silently corrupting the queue; future ingestion modes require coordinated version bump.
- **Survivor of `bootstrap.ts` import side-effect ordering**: `bootstrapMcpFeatures()` is called at import time (`bootstrap.ts:70`). If a feature module has a circular import or side effect, initialization order becomes fragile. Observed duplication is guarded by `if (this.features.has(...)) throw` (`registry.ts:83`), but repeated hot-reload in dev could double-register and throw — mitigated only by process-restart isolation.
