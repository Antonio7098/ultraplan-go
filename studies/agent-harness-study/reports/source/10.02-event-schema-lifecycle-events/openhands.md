## Summary

OpenHands' frontend mirrors a typed, ordered, parent-linked agent-server event model. Every event extends `BaseEvent` with `id` (string), `timestamp` (ISO 8601), and a `source` union (`agent | user | environment | hook`) (`src/types/agent-server/core/base/event.ts:10-25`, `src/types/agent-server/core/base/common.ts:56`). The discriminated `OpenHandsEvent` union covers actions, observations, message echoes, condensation, hooks, conversation-state updates, ACP sub-agent tool calls, errors, pause, and streaming deltas (`src/types/agent-server/core/openhands-event.ts:25-46`). Ordering is by ISO-lexicographic `timestamp` plus dedup-by-`id` (`src/stores/use-event-store.ts:24-35`, `src/stores/use-event-store.ts:100-107`), and the wire is resynchronized via REST `after_timestamp` then WebSocket `resend_mode='since'` (`src/contexts/conversation-websocket-context.tsx:368-400`, `src/contexts/conversation-websocket-context.tsx:971-973`). There is **no explicit event-version field**; lifecycle breadth is gained through tagged kinds plus a `ConversationStateUpdateEvent` discriminated union carrying `full_state | execution_status | stats | goal` snapshots (`src/types/agent-server/core/events/conversation-state-event.ts:99-151`). Lifecycle coverage is comprehensive for tool calls, agent errors, server/conversation errors, condensation, goal loops, hooks, and pause; there is **no dedicated "conversation started" / "conversation finished" event** — completion is inferred from `FinishAction`/`FinishObservation` and `execution_status` (`src/types/agent-server/core/base/action.ts:13-18`, `src/types/agent-server/core/events/pause-event.ts:4-8`, `src/types/agent-server/core/events/conversation-state-event.ts:154-173`). 

## Rating

**Score: 7 / 10 — Clear model with tests, explicit interfaces, and operational safeguards, but no event-version field and a few lifecycle gaps.**

Rubric justification:
- **Typed and versioned (events typed yes; version field no).** Discriminated unions with `kind` discriminators where needed (`src/types/agent-server/core/events/condensation-event.ts:6`, `src/types/agent-server/core/events/conversation-state-event.ts:103`, `src/types/agent-server/core/events/hook-execution-event.ts:24`, `src/types/agent-server/core/events/acp-tool-call-event.ts:42`), runtime `isBaseEvent`/`isAgentServerEvent` guard (`src/types/agent-server/type-guards.ts:45-62`, `src/types/agent-server/type-guards.ts:299-301`). No `schema_version`/`event_version` field found across the events module (`grep -rn "event_version\|EventVersion\|schema_version"` returned no hits in `src/types/agent-server/`). Additive evolution is documented in comments (`src/types/agent-server/core/events/system-event.ts:24` — "Optional for older persisted events").
- **ordered and timestamped.** ISO-8601 `timestamp` on every event (`src/types/agent-server/core/base/event.ts:19`); store sorts by ISO lexicographic order (`src/stores/use-event-store.ts:24-35`); WebSocket history replay anchored on `after_timestamp` (`src/contexts/conversation-websocket-context.tsx:368-373`, `src/contexts/conversation-websocket-context.tsx:972`). No monotonic sequence number on events — timestamp is the only ordering key, with a known caveat that ordering falls through when timestamps are absent (`src/stores/use-event-store.ts:29-31`).
- **Sufficient context.** `BaseEvent` carries `id` + `timestamp` + `source`; actions carry `tool_call_id`, `llm_response_id`, `security_risk`, `critic_result`, `summary` (`src/types/agent-server/core/events/action-event.ts:11-72`); observations carry `tool_call_id` and `action_id` to back-link (`src/types/agent-server/core/events/observation-event.ts:9-39`); hooks carry `action_id`/`message_id` and exit metadata (`src/types/agent-server/core/events/hook-execution-event.ts:66-99`); ACP tool-call events carry `tool_call_id` linking started/terminal pairs (`src/types/agent-server/core/events/acp-tool-call-event.ts:50-67`). Goal status carries `iteration`, `verdict`, and lifecycle status (`src/types/agent-server/core/events/conversation-state-event.ts:82-97`). ConversationId is *not* an event field — it's inferred from URL/route, with one documented limitation: cloud conversations whose sandbox is paused do not get a "paused" event, the WebSocket is just suppressed (`AGENTS.md:765-772` "Cloud conversation resume gating" section).
- **Comprehensive lifecycle events.** Tool calls (ActionEvent→ObservationEvent with `action_id` link), Finish (action + observation), Pause, Hooks (six types), Goal (`running/complete/capped/interrupted` per `src/types/agent-server/core/events/conversation-state-event.ts:85`), Condensation (`request` + completion + summary), AgentError, ConversationError, ServerError. **Missing dedicated events**: explicit `ConversationStarted`/`RunStarted`; cancel is expressed via `PauseEvent` (`src/types/agent-server/core/events/pause-event.ts:4-8`) and `ExecutionStatus.PAUSED`/`STUCK`/`ERROR` (`src/types/agent-server/core/base/common.ts:67-75`) rather than a typed cancellation event; there is no replay/resume marker. ACP lifecycle piggy-backs on `status: "pending"|"in_progress"|"completed"|"failed"` (`src/types/agent-server/core/events/acp-tool-call-event.ts:17-22`), which is a soft lifecycle rather than an event-level one.

The frontend can reconstruct tool lifecycle (id+tool_call_id+action_id), error lifecycle (AgentError/ConversationError/ServerError with codes), goal loop (ConversationStateUpdateEvent with `key:"goal"`), and pause (`PauseEvent` + `execution_status` update). Reconstructing conversation-level create/finish timestamps relies on `created_at`/`updated_at` on `AppConversation` (`src/api/conversation-service/agent-server-conversation-service.types.ts:200-215`), not on event-stream records.

## Answers to Dimension Questions

### 1. Are events typed and versioned?

**Typed: yes.** The discriminated `OpenHandsEvent` union (`src/types/agent-server/core/openhands-event.ts:25-46`), `BaseEvent` (`src/types/agent-server/core/base/event.ts:10-25`), and per-kind interfaces (`ActionEvent`, `ObservationEvent`, `MessageEvent`, `HookExecutionEvent`, `ACPToolCallEvent`, `StreamingDeltaEvent`, `CondensationEvent`, `ConversationStateUpdateEvent`, `ServerErrorEvent`, `PauseEvent`, etc.) collectively provide strict typing. Runtime validation comes from `isAgentServerEvent` → `isBaseEvent` (`src/types/agent-server/type-guards.ts:45-62`, `299-301`), and the WS handler in `conversation-websocket-context.tsx:546-547` drops anything that fails the guard.

**Versioned: partially.** There is **no `schema_version`/`event_version` field** anywhere in `src/types/agent-server/` (search returned zero hits). Additive evolution is handled via optional fields and explicit comments: e.g., `dynamic_context?: TextContent` is "Optional for older persisted events" (`src/types/agent-server/core/events/system-event.ts:21-25`); `ACPToolCallEvent.status` tolerates `null` for legacy builds before the field was required (`src/types/agent-server/core/events/acp-tool-call-event.ts:65-66`). Tests assert the null-status path explicitly (`__tests__/components/conversation-events/chat/event-content-helpers/should-render-event.test.ts:96-103`). The `OpenHandsEvent` union also adds a frontend-only `isFromPlanningAgent` flag (`src/stores/use-event-store.ts:10-12`) — not a wire version, but it shows how the union is extended for routing without breaking the schema.

### 2. Are events ordered and timestamped?

**Timestamped: yes.** Every event has `timestamp: string` (ISO 8601) on `BaseEvent` (`src/types/agent-server/core/base/event.ts:19`). Mock fixtures and live data both emit ISO strings (`src/fixtures/table-demo-conversation.ts:32-34`, `src/mocks/conversation-handlers.ts:137`). `formatTimestamp` in the transcript export parses the string and re-emits ISO (`src/utils/transcript-export/index.ts:121-124`).

**Ordered: yes, by ISO timestamp.** `compareEventsByTimestamp` uses lexicographic comparison (`src/stores/use-event-store.ts:24-35`), and the store re-sorts when a new event arrives out of order or when older pages are bulk-added (`src/stores/use-event-store.ts:131-151`, `src/stores/use-event-store.ts:202-207`). Pagination params `timestampGte` / `timestampLt` and sort order `TIMESTAMP` / `TIMESTAMP_DESC` (`src/api/event-service/event-service.types.ts:10-29`) make ordering an explicit wire contract. The chat re-sorts the tail chronologically after REST preload (`src/hooks/query/use-conversation-history.ts:64-65`).

**No monotonic sequence number.** Ordering falls back to "events without timestamps go to the end" (`src/stores/use-event-store.ts:28-31`). Two events with identical timestamps stay in store order because `Array.prototype.sort` is stable (`src/utils/transcript-export/load-complete-events.ts:148-149`). Replay dedup uses event `id`, not sequence (`src/contexts/conversation-websocket-context.tsx:559-561`; `src/stores/use-event-store.ts:99-107`).

### 3. Do events carry sufficient context?

**Yes for tool calls, error reporting, goal loops, and hooks:**
- `ActionEvent` carries `tool_call_id`, `llm_response_id`, `security_risk`, `critic_result`, `summary`, `thought`, `thinking_blocks`, and a copy of the raw `tool_call` (`src/types/agent-server/core/events/action-event.ts:11-72`).
- `ObservationEvent` carries `tool_call_id` and `action_id` so any action can be linked to its observation; `UserRejectObservation` adds `rejection_reason` (`src/types/agent-server/core/events/observation-event.ts:9-52`).
- `HookExecutionEvent` carries six hook-type discriminators, success, blocked, exit_code, reason, stdout/stderr, error, additional_context, action_id, message_id (`src/types/agent-server/core/events/hook-execution-event.ts:6-99`).
- `ACPToolCallEvent` carries `tool_call_id` so two events per call (started, terminal) link by id; status union spans `pending | in_progress | completed | failed` (`src/types/agent-server/core/events/acp-tool-call-event.ts:17-67`).
- `ConversationStateUpdateEvent` carries a typed `value` per `key`: `ConversationState`, `ExecutionStatus`, `ConversationStats`, or `GoalStatus` (`src/types/agent-server/core/events/conversation-state-event.ts:99-151`).
- `GoalStatus` carries `iteration`, `max_iterations`, `objective`, `verdict` (with `score` and `missing`), and a `running | complete | capped | interrupted` state (`src/types/agent-server/core/events/conversation-state-event.ts:68-97`).
- `ConversationErrorEvent`/`ServerErrorEvent` carry `code` and `detail` (and `classification` from `@openhands/typescript-client`); `AgentErrorEvent` carries `tool_name`, `tool_call_id`, `error`, `classification` (`src/types/agent-server/type-guards.ts:80-89`, `572-608`).

**No conversation/run/parent IDs in the event payload.** `conversation_id` is implicit in the WebSocket URL (`src/utils/websocket-url.ts:120-134`); there is no `run_id`/`span_id` field. Goal verdict `event_ids` lists `string[]` (`src/types/agent-server/core/base/critic.ts:31-35`) — the critic metadata includes the events it judged, providing per-event traceability but not a hierarchical run/span model.

### 4. Are lifecycle events comprehensive?

**Lifecycle coverage is strong for tool runs and errors:**
- Tool calls: `ActionEvent` → `ObservationEvent`/`UserRejectObservation` (paired by `action_id`/`tool_call_id`).
- Completion: `FinishAction` + `FinishObservation` (`src/types/agent-server/core/base/action.ts:13-18`; `src/types/agent-server/core/base/observation.ts:24-33`). `FinishObservation` is suppressed in `uiEvents` to avoid duplicate render (`src/utils/handle-event-for-ui.ts:425-430`).
- Pause: `PauseEvent` (`src/types/agent-server/core/events/pause-event.ts:4-8`) and `ExecutionStatus.PAUSED` / `STUCK` / `ERROR` / `FINISHED` (`src/types/agent-server/core/base/common.ts:67-75`).
- Failure: `AgentErrorEvent`, `ConversationErrorEvent`, `ServerErrorEvent` (`src/types/agent-server/type-guards.ts:80-89`, `242-260`).
- Hooks: `HookExecutionEvent` with six lifecycle types (`src/types/agent-server/core/events/hook-execution-event.ts:6-12`).
- Condensation: `CondensationRequestEvent` → `CondensationEvent` (forgotten ids + summary) → `CondensationSummaryEvent` (`src/types/agent-server/core/events/condensation-event.ts:5-51`).
- Goal: `ConversationStateUpdateEvent` with `key:"goal"` and `GoalStatus.status` ∈ `running | complete | capped | interrupted` (`src/types/agent-server/core/events/conversation-state-event.ts:82-151`).
- ACP sub-agent tool calls: `ACPToolCallEvent` with `status` ∈ `pending | in_progress | completed | failed` (`src/types/agent-server/core/events/acp-tool-call-event.ts:17-22`).
- Conversation-level lifecycle: `ConversationStateUpdateEvent` `key:"full_state"` snapshot, `key:"execution_status"` deltas (`src/types/agent-server/core/events/conversation-state-event.ts:114-132`).

**Gaps:**
- **No dedicated "conversation started" event.** Conversation creation is metadata on `AppConversation.created_at` (`src/api/conversation-service/agent-server-conversation-service.types.ts:200-215`), not an event-stream record.
- **No dedicated "conversation finished" or "run finished" event.** Termination is inferred from `FinishAction` + `FinishObservation` + `execution_status` transitions.
- **No cancellation event** — cancellation rides on `PauseEvent` + `ExecutionStatus.PAUSED`. There is no separate "cancelled" execution status; `STUCK`/`ERROR` are the closest (`src/types/agent-server/core/base/common.ts:67-75`).
- **Cloud sandbox pause/resume is not an event** — `AGENTS.md` documents that `WebSocketProviderWrapper` must suppress the URL when `sandbox_status === "PAUSED"` because no event signals the transition. Operationally, this means a closed-from-UI cloud conversation is invisible to event-based observability until the sandbox resumes.

## Architectural Decisions

- **Two transports for the same wire.** REST `RemoteEventsList.search()` loads the latest 50 events by `sortOrder:"TIMESTAMP_DESC"` (`src/hooks/query/use-conversation-history.ts:30-72`, `src/api/event-service/event-service.api.ts:102-181`), then the WebSocket opens with `resend_mode="since"` + `after_timestamp=<latest>` to resume without re-streaming history (`src/contexts/conversation-websocket-context.tsx:971-973`). Planning-agent sub-conversation still uses `resend_all=true` until migrated to the REST+WS pattern (`src/contexts/conversation-websocket-context.tsx:1006-1007`).
- **Timestamp as the only ordering key.** No monotonic sequence numbers on the wire; ordering falls back to ISO-lexicographic and is explicitly acknowledged as a known weakness (`src/stores/use-event-store.ts:28-31`, `src/utils/transcript-export/load-complete-events.ts:148-149`).
- **Event `id` as the dedup key.** REST + WS overlap is resolved with an `eventIds: Set<string|number>` (`src/stores/use-event-store.ts:100-107`, `src/contexts/conversation-websocket-context.tsx:559-561`). Streaming deltas are deliberately excluded to keep the per-token Set copy O(1) (`src/stores/use-event-store.ts:95-107`, `__tests__/stores/use-event-store.test.ts:206-225`).
- **Discriminator tags, not bare `string` "kind".** `kind` is typed as a string literal on each event so the union narrows in `if` branches (e.g. `kind: "Condensation"` (`src/types/agent-server/core/events/condensation-event.ts:6`), `kind: "ConversationStateUpdateEvent"` (`src/types/agent-server/core/events/conversation-state-event.ts:103`)). Hooks, ACP tool calls, streaming deltas, server errors all use `kind`.
- **`source` enum narrowed to 4 values.** `agent | user | environment | hook` (`src/types/agent-server/core/base/common.ts:56`) lets the runtime guard reject malformed events cheaply (`src/types/agent-server/type-guards.ts:57-60`).
- **ConversationStateUpdateEvent as a state-snapshot envelope.** Rather than emit distinct events for each state field, the server emits one event with a typed `key: "full_state" | "execution_status" | "stats" | "goal"` and a typed `value` union (`src/types/agent-server/core/events/conversation-state-event.ts:99-151`). Goal status, stats, and execution status all travel this same channel.
- **Action→Observation supersede in UI.** `handleEventForUI` finds the matching action by id and replaces it in place (`src/utils/handle-event-for-ui.ts:418-441`), and `ThinkObservation`/`FinishObservation` are dropped entirely (`src/utils/handle-event-for-ui.ts:418-430`). This is a deliberate UI projection choice, not a wire-level lifecycle decision.
- **ACP sub-agent: two events per `tool_call_id` rather than per-progress frames.** Status field replaces a fan-out of `ToolCallProgress` events; merged in place by `tool_call_id` (`src/components/conversation-events/chat/event-content-helpers/should-render-event.ts:125-141`, `src/utils/handle-event-for-ui.ts:404-415`).
- **Cloud pagination as a strict mode.** `EventService.searchEvents` lets completeness-sensitive callers pass `strictPagination: true` so transcript export never accepts a partial history (`src/api/event-service/event-service.types.ts:23-29`, `src/api/event-service/event-service.api.ts:144-163`, `src/utils/transcript-export/load-complete-events.ts:33-161`). `loadCompleteTranscriptEvents` walks pages, falls back from `next_page_id` to `timestampLt` cursors, and rejects when `fetchedEventIds < expectedEventCount` (`src/utils/transcript-export/load-complete-events.ts:33-161`).

## Notable Patterns

- **One canonical capture per event.** Repeated business milestones (model switches, plan file writes) use deterministic ids / event-driven store state, not process-local caches. Examples: ACP tool-call started/terminal pair replaces per-progress frames (`src/components/conversation-events/chat/event-content-helpers/should-render-event.ts:125-141`); `seedModelSwitchesFromHistory` rebuilds inline "Switched to" messages from REST-preloaded history (`src/contexts/conversation-websocket-context.tsx:338-341`).
- **Two-tier streaming-delta handling.** Transient `StreamingDeltaEvent`s are coalesced into a single persisted bubble per frame (`src/utils/streaming-delta-batcher.ts:21-49`) and excluded from the dedup `Set` (`src/stores/use-event-store.ts:95-107`). Final `FinishAction`/`MessageEvent` (agent) reconciles streamed text into the action card (`src/utils/handle-event-for-ui.ts:215-301`, `374-385`).
- **Sender scoping prevents cross-agent contamination.** `isSameStreamingSender` discriminates by `isFromPlanningAgent` so a planning-agent delta cannot concatenate onto a main-agent bubble (`src/utils/handle-event-for-ui.ts:34-37`, `__tests__/stores/use-event-store.test.ts:227-242`).
- **Pure logic tests for grouping/hoisting.** `groupEvents` lives in `src/components/conversation-events/chat/group-events.ts` with a Vitest suite in `__tests__/components/conversation-events/chat/group-events.test.ts`; the prompt doesn't load that file but the file is referenced from the test directory listing.
- **Defensive dedup of replayed events.** On WS reconnect with `since`-replay, the event-store Set dedups by id but side-effects (cache invalidation, error banner, etc.) are also gated on `eventIds.has` to stay idempotent (`src/contexts/conversation-websocket-context.tsx:559-568`).
- **Conversation-scoped invariants.** `loadedConversationId` is set/cleared atomically with the events arrays so a half-applied clear can't expose the previous conversation's events under the new id (`src/stores/use-event-store.ts:55-90`, `src/stores/use-event-store.ts:216-222`, `src/contexts/conversation-websocket-context.tsx:303-318`).

## Tradeoffs

- **No event-version field, additive-only evolution.** Additive evolution is cheap (optional fields, comments), but old clients can't detect a wire schema they don't understand and will silently ignore unknown kinds. `dynamic_context?: TextContent` is the canonical example of "if it's there use it" (`src/types/agent-server/core/events/system-event.ts:21-25`).
- **No monotonic sequence number.** Two events with the same ISO timestamp can appear in either order depending on REST vs. WS arrival; the transcript export relies on stable `Array.prototype.sort` to preserve causal order from the server's response (`src/utils/transcript-export/load-complete-events.ts:148-152`). For events with identical ids (idempotent writes) this is fine; for unique events with timestamp collisions it is non-deterministic.
- **Pause and conversation-cancellation ride on a generic state channel.** `PauseEvent` + `ExecutionStatus.PAUSED` makes the "user paused" case indistinguishable from "stuck" without cross-referencing the source field (`src/types/agent-server/core/events/pause-event.ts:4-8`; `src/types/agent-server/core/base/common.ts:67-75`).
- **Cloud pagination is a fallback rather than a primary contract.** When the cloud backend doesn't support `timestamp__gte`/`timestamp__lt`, the chat gracefully degrades to "no more pages" rather than erroring (`src/api/event-service/event-service.api.ts:149-163`); for transcript export, `strictPagination: true` rethrows to fail loud instead (`src/api/event-service/event-service.types.ts:23-29`).
- **Cloud sandbox resume is observed via poll, not events.** No event marks the `PAUSED → RUNNING` transition; the UI relies on `useActiveConversation`'s 3-second refetch loop while `sandbox_status === "PAUSED"` (`AGENTS.md` "Cloud conversation resume gating"). Reconstructing the lifecycle from events alone would miss this transition entirely.
- **ActionEvent.summary is server-supplied.** `summary?: string \| null` is the LLM-generated tool-call label (`src/types/agent-server/core/events/action-event.ts:71`). When empty, the UI falls back to `tool_name` or the humanized `kind` (`src/utils/transcript-export/index.ts:171-177`), which means the same tool can appear under multiple labels across runs.

## Failure Modes / Edge Cases

- **Replay dedup edge case: side-effect idempotency.** Side-effects in the WS handler are guarded by `eventIds.has` to skip the non-idempotent parts on a `since`-replay (`src/contexts/conversation-websocket-context.tsx:559-568`); a regression here would re-trigger error banners, model-switch metadata writes, and metric aggregations on every reconnect.
- **Cloud pagination fallback hides incompleteness.** If `searchEvents` falls back to the empty page (`src/api/event-service/event-service.api.ts:149-163`), the user sees an early "end of history" without a warning unless `strictPagination: true` is set. Chat callers don't set it; transcript export does (`src/api/event-service/event-service.api.test.ts:42-55`).
- **`compareEventsByTimestamp` skips events without a timestamp.** Events that lack `timestamp` are sorted to the end (`src/stores/use-event-store.ts:28-31`), and `needsSorting` becomes a no-op when either endpoint is missing (`src/stores/use-event-store.ts:48-49`). A burst of "timeless" events interleaves non-deterministically.
- **Cloud sandbox pause leaves no event.** A conversation closed from the UI emits no event; the WebSocket is just suppressed on the next render. There is no event-log record of the pause/resume (`AGENTS.md` "Cloud conversation resume gating").
- **`StreamingDeltaEvent` per-token merging can hide late content.** A final `MessageEvent`/`FinishAction` reconciles streamed text by collapsing the trailing deltas (`src/utils/handle-event-for-ui.ts:215-301`, `374-385`); if a model emits a final token after the action has reconciled, that token is folded into the existing bubble via `mergeStreamingDeltaEvent` (`src/utils/handle-event-for-ui.ts:20-29`). The `StreamedSegments` matcher explicitly tolerates supersets to avoid losing content (`src/utils/handle-event-for-ui.ts:287-300`).
- **`HookExecutionEvent.tool_name` is nullable but pre-tool hooks always carry one.** Type permits `string | null` (`src/types/agent-server/core/events/hook-execution-event.ts:64`), but `SessionStart`/`SessionEnd`/`Stop` will be null in practice — callers must null-check.
- **`ConversationStateUpdateEvent` for `goal` carries `value.active` alongside `status`.** A "running" loop can also be "interrupted" (e.g. on pause); the renderer keys on `!event.value.active` to decide whether to render inline (`src/components/conversation-events/chat/event-content-helpers/should-render-event.ts:54-60`). Misreading either field produces a wrong banner state.
- **Goal-loop re-prompts can leak as user turns.** `GOAL_REPROMPT_PREFIXES` matches on text content because the persisted event carries no `is_goal_reprompt` flag (`src/components/conversation-events/chat/event-content-helpers/should-render-event.ts:23-26`); the test for this is intentionally a string match and brittle by design.
- **ActionEvent.tool_call vs ActionEvent.action divergence.** `tool_call` is kept verbatim from the LLM and may carry an LLM-predicted `security_risk` that `action` does not (`src/types/agent-server/core/events/action-event.ts:42-49`). Downstream code that reads `action.security_risk` would miss the LLM-side prediction; readers should prefer `event.security_risk` (`src/types/agent-server/core/events/action-event.ts:61`).
- **`RemoteEventsList.search` pagination cursor semantics.** Some older servers omit `next_page_id` for filtered searches; `loadCompleteTranscriptEvents` falls back to `timestampLt` and only allows the fallback when `expectedEventCount` can prove completeness, otherwise it throws (`src/utils/transcript-export/load-complete-events.ts:103-124`). Chat callers without an `expectedEventCount` would silently stop on the first full page.

## Future Considerations

- **Add an explicit `event_version`/`schema_version` to `BaseEvent`.** Today, schema drift is invisible to old clients. Even a single integer (`v1`, `v2`) would let a future wire change be detected and rejected at the WS layer.
- **Add typed `conversation_started`/`conversation_finished` events.** Currently `AppConversation.created_at`/`updated_at` is the only record; embedding those as stream events would let event-log viewers reconstruct run boundaries without joining on conversation metadata.
- **Promote pause/cancel to a typed event.** A `CancelEvent` with `reason` and `source: "user" | "agent" | "system"` would disambiguate user-pause from auto-pause and remove the need to cross-reference `execution_status`.
- **Add a monotonic `seq` to event payloads.** With ordering-by-timestamp alone, two events with identical timestamps are non-deterministic; a server-side sequence number would let the frontend detect dropped events and clients order by `seq` as a tiebreaker.
- **Emit cloud sandbox resume/pause as `ConversationStateUpdateEvent` `key:"sandbox_status"`.** Today the WS handler suppresses the URL while paused (`AGENTS.md`); promoting this to an event would make sandbox lifecycle part of the event log.
- **Promote the `is_goal_reprompt` heuristic to a server flag.** `GOAL_REPROMPT_PREFIXES` matches on prompt text (`src/components/conversation-events/chat/event-content-helpers/should-render-event.ts:23-26`) and the comment notes it as brittle-by-design until a durable flag lands.
- **Formalise ACP tool-call lifecycle as distinct events.** The current design collapses started/terminal into a single event shape with a status field; if more lifecycle points (e.g. cancellation, retry) emerge, splitting into `ACPToolCallStarted` + `ACPToolCallCompleted` would scale better.
- **Cover `BaseEvent` validation with explicit unit tests.** `isBaseEvent` is the chokepoint for malformed wire data (`src/types/agent-server/type-guards.ts:45-62`); the test suite in `__tests__/components/conversation-events/chat/event-content-helpers/should-render-event.test.ts` exercises specific kinds but no dedicated `type-guards.test.ts` was found (`find ... -name "*type-guard*"` returned nothing).
