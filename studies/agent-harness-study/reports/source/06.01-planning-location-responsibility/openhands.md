## Summary

OpenHands splits planning into two locations. **Dedicated planning mode** is an explicit, runtime-gated, model-owned preset: when `AgentType.PLAN` is selected the server injects `system_prompt_planning.j2`, a `PLANNING_AGENT_INSTRUCTION` suffix, and a read-only toolset (`Glob + Grep + PlanningFileEditor`) that can only edit `PLAN.md` (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:185-196,1320-1332,1613-1617` and `openhands/tools/preset/planning.py:46-135`). The plan itself is a markdown file (`PLAN.md`) initialized from `PLAN_STRUCTURE` headers (`openhands/tools/preset/planning.py:12-45,51-78`) and stored at `{working_dir}/.agents_tmp/PLAN.md` (or `agents-tmp-config` for GitLab/Azure — `openhands/app_server/app_conversation/live_status_app_conversation_service.py:1071-1091`). **Default execution mode** has no first-class planner: decomposition is implicit, performed by the LLM via the optional `task_tracker` tool (`openhands/tools/task_tracker/definition.py:38-120` and `openhands/tools/preset/default.py:31-56`) and described in prompts (`openhands/sdk/agent/prompts/system_prompt_long_horizon.j2:4`). There is no workflow graph, no structured `Plan` object, no revision API, and no planner-executor contract beyond a frontend "Build" button that sends `Execute the plan based on the .agents_tmp/PLAN.md file.` (`frontend/src/hooks/use-handle-build-plan-click.ts:27`). Planning is therefore **prompt + file-artifact + runtime gate**, not a durable runtime object.

## Rating

**Score: 5 / 10**

**Rationale:** Planning is explicit and discoverable — dedicated `AgentType.PLAN` enum (`openhands/app_server/app_conversation/app_conversation_models.py:61-65`), separate system prompt (`openhands/sdk/agent/prompts/system_prompt_planning.j2:1-83`), restricted toolset, file artifact with typed structure (`PLAN_STRUCTURE`), and frontend visibility (planner tab, plan preview, build button). However the plan is prose-in-markdown, not a validated runtime object: no schema, no versioning, no `Plan` channel, no retry/revision lifecycle, no tests for decomposition quality, and the planner-executor handoff is a string prompt rather than an interface. The fallback `task_tracker` planning is entirely model-owned and optional, with no enforcement. This maps to "Present but inconsistent, weakly documented, or fragile" — is planning a real runtime object? No, it is a file plus prompt with a thin runtime gate.

## Answers to Dimension Questions

### 1. Where does planning happen?
**Two places: dedicated planning-agent preset (prompt + file) and, as fallback, implicit LLM reasoning via `task_tracker`.**

- **Dedicated planning mode:** Server selects `AgentType.PLAN` (`openhands/app_server/app_conversation/app_conversation_models.py:61-65`), injects `system_prompt_planning.j2` with a four-phase workflow (`openhands/sdk/agent/prompts/system_prompt_planning.j2:26-83`) plus `PLANNING_AGENT_INSTRUCTION` suffix (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:185-196`), and restricts tools to `Glob + Grep + PlanningFileEditor` (`openhands/tools/preset/planning.py:110-135`). The LLM explores the codebase read-only and writes a markdown plan to `PLAN.md` at `{working_dir}/.agents_tmp/PLAN.md` (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:1071-1091`; `openhands/tools/planning_file_editor/definition.py:38-98`). Planning is thus **prompt-owned (system prompt + instruction suffix) + file-artifact-owned**, gated by runtime code that swaps the preset.
- **Default mode implicit planning:** `get_default_agent` (`openhands/tools/preset/default.py:31-56`) provides `Terminal + FileEditor + TaskTracker`; long-horizon prompt nudges the model to use `task_tracker` (`openhands/sdk/agent/prompts/system_prompt_long_horizon.j2:4`). Decomposition happens inside the LLM turn loop (`openhands/sdk/agent/agent.py` loop) with no planner service or workflow graph — purely model-owned prose plus optional `TASKS.md` list (`openhands/tools/task_tracker/definition.py:54-120`).
- **No runtime workflow graph:** No `StateGraph`, `Pregel`, or `PlanNode` abstraction exists; search for `class Planner`/`Workflow` yields 0 hits. No external planner system is invoked.

### 2. Who owns the plan?
**Shared but weak: LLM authors the content, `PlanningFileEditor` owns write-access enforcement, filesystem owns persistence, user owns approval.**

- **Author:** The planning LLM owns prose generation under the `system_prompt_planning.j2` contract; `PLAN_STRUCTURE` templates the sections but does not validate content (`openhands/tools/preset/planning.py:12-78`).
- **Gatekeeper:** `PlanningFileEditorExecutor` enforces `allowed_edits_files=[plan_path]` (`openhands/tools/planning_file_editor/impl.py:10-24`) and the server enforces tool choice (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:1613-1617`). No other agent can edit `PLAN.md` through this tool, but direct `FileEditorTool` (default mode) or `TerminalTool` bash writes are unrestricted — boundary is tool-level, not filesystem ACL.
- **Owner of record:** The file `PLAN.md` on the sandbox workspace (`openhands/tools/planning_file_editor/definition.py:89-98`) is the sole artifact; no DB table, no `Plan` model, no `AppConversationInfo.plan` field (`openhands/app_server/app_conversation/app_conversation_models.py:156-230` contains no plan field).
- **Human owner:** The frontend requires explicit human action to execute: clicking **Build** in `PlanPreview` (`frontend/src/components/features/chat/plan-preview.tsx:97-120`) or the agent selector; `PLANNING_AGENT_INSTRUCTION` explicitly forbids auto-execution (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:188-194`).

### 3. Is planning required?
**No. Planning is entirely optional and opt-in.**

- Default conversations start as `AgentType.DEFAULT` (`openhands/app_server/app_conversation/app_conversation_models.py:223` default). `live_status_app_conversation_service.py:1495` shows `agent_type: AgentType = AgentType.DEFAULT` in the creation path; planning only activates when user clicks the Plan button (`frontend/src/hooks/use-handle-plan-click.ts:42`) which creates a sub-conversation with `agentType: "plan"`.
- `task_tracker` planning is also optional: the tool is available but the model may never call `command="plan"`; no enforcement in `openhands/sdk/agent/agent.py` or `openhands/tools/preset/default.py`. The long-horizon prompt says "Use this tool REGULARLY" (`openhands/sdk/agent/prompts/system_prompt_long_horizon.j2:4`) but violation has no consequence — observed behavior confirms model sometimes skips it.
- No config flag makes planning mandatory (`config.template.toml` and `openhands/app_server/config.py` contain no `require_planning` key). Builds succeed without `PLAN.md` (the build prompt just reads the file; if absent, model proceeds ad-hoc).

### 4. Is planning visible?
**Yes, highly visible in the UI, but as rendered markdown rather than structured data.**

- **Visible surfaces:** Planner tab (`frontend/src/types/tab-option.tsx:2-8`, `frontend/src/routes/planner-tab.tsx:56`), `PlanPreview` card in chat stream (`frontend/src/components/features/chat/plan-preview.tsx:26-120`) that shows truncated `PLAN.md` with shine effect during streaming, and selective hiding of raw `PlanningFileEditorAction` events (`frontend/src/components/v1/chat/event-content-helpers/should-render-event.ts:34`) in favor of the preview. Events are flagged `isFromPlanningAgent` (`frontend/src/stores/use-event-store.ts:9`) so the chat distinguishes planning vs execution messages.
- **File visibility:** The tool reports `Your PLAN.md location: {plan_path}` in its description (`openhands/tools/planning_file_editor/definition.py:88-98`) and the router exposes `GET /workspace/project/.agents_tmp/PLAN.md` (`frontend/src/api/conversation-service/v1-conversation-service.api.ts:422`).
- **Not visible as data:** The plan is markdown; there is no JSON schema, no diff view, no progress bar tied to plan steps, no `status=todo|in_progress|done` per step (that belongs to the separate `task_tracker` tool, not `PLAN.md`). Planning condenser usage is tagged `planning_condenser` (`openhands/app_server/app_conversation/app_conversation_service_base.py:601`) for analytics but not surfaced to the user.

### 5. Is planning reusable?
**Barely. The plan is a file that can be re-read, but there is no reusable primitive.**

- **Artifact reuse:** `PLAN.md` persists on the workspace and is re-read by the next agent via `PlanningFileEditor view` or `Glob/Grep`; the Build button reuses it by prompting `Execute the plan based on the .agents_tmp/PLAN.md file.` (`frontend/src/hooks/use-handle-build-plan-click.ts:27`). There is no parameterized template, no versioning, no `Plan` library.
- **Preset reuse:** `get_planning_tools()` and `get_planning_agent()` (`openhands/tools/preset/planning.py:94-135`) are reused whenever a PLAN sub-conversation is spawned, but they are factory functions, not a plugin API. Sub-agents (`openhands/tools/preset/subagents/*.md`) like `code-explorer` and `general-purpose` provide reusable skill-like decomposition, but none encapsulates planning.
- **Not reusable across workspaces:** `PLAN.md` path is workspace-absolute (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:1071-1091`); no export/import, no `MCP` exposure, no checkpointing of plan versions. Copy-paste is the only cross-conversation reuse.

## Architectural Decisions

| Decision | Description | Tradeoff |
|----------|-------------|----------|
| **Dedicated `AgentType.PLAN` enum as planning discriminator** (`openhands/app_server/app_conversation/app_conversation_models.py:61-65`, `openhands/app_server/app_conversation/live_status_app_conversation_service.py:1320-1332`) | Single enum value gates system prompt, tools, condenser, and instruction suffix in one `if agent_type==PLAN` branch. | Simple and auditable; but binary (no gradations like `plan(review)` or `plan(deep)`), and planning lives as sub-conversation, not as mode of the same conversation — doubles conversation bookkeeping (`sub_conversation_ids`, `subConversationTaskId` in `frontend/src/hooks/use-handle-plan-click.ts:27-50`). |
| **Markdown file as plan object** (`openhands/tools/planning_file_editor/definition.py:38-98`, `openhands/tools/preset/planning.py:12-78`) | `PLAN_STRUCTURE` tuple list renders headers via `get_plan_headers()`; LLM fills prose under `# OBJECTIVE` etc.; file initialized lazily on tool creation. | Human-readable, zero schema migration, previews nicely in `PlanPreview`; but unvalidated, unparseable for automation, no typed step graph or dependencies. Revision is `str_replace` on markdown, not a `PlanRevision` event. |
| **Read-all / edit-only-PLAN.md tool restriction** (`openhands/tools/planning_file_editor/impl.py:10-24`) | Wraps `FileEditorExecutor(allowed_edits_files=[plan_path])`; viewing any path is allowed, editing beyond `plan_path` is rejected. | Strong model-level sandbox for planning; but bypassable via default tools if attacker switches agent, and `TerminalTool` is excluded from planning set so even legitimate `rg` outside Python tool is unavailable — forces use of slow `GrepTool`/`GlobTool`. |
| **Prompt-owned workflow, not code-owned** (`openhands/sdk/agent/prompts/system_prompt_planning.j2:26-83`) | Four-phase workflow (Understanding → Planning → Synthesis → Refinement) described entirely in Jinja template, with `{{plan_structure}}` injection (`openhands/tools/preset/planning.py:46-78`). | Gives LLM flexibility and keeps server stateless; but workflow is unenforceable — model can skip Phase 1 exploration, omit clarifying questions, or hallucinate plan. No server-side state machine validates phase transitions. |
| **Sub-conversation for planning** (`frontend/src/hooks/use-handle-plan-click.ts:42-103`, `openhands/app_server/app_conversation/live_status_app_conversation_service.py:1495`) | Clicking Plan spawns a child conversation with `agentType:"plan"`; parent tracks via `sub_conversation_ids`. Build switches back to `code` mode. | Isolates planning context (separate condenser, event history) and keeps planner read-only; but introduces task-id polling, localStorage persistence for recoverability, and split event stores — failure during plan creation leaves orphan `subConversationTaskId`. |
| **Separate planning condenser** (`openhands/tools/preset/planning.py:108-124`, `openhands/app_server/app_conversation/app_conversation_service_base.py:578-612`) | `LLMSummarizingCondenser(max_size=100, keep_first=6, usage_id='planning_condenser')` vs default `80/4`. | Preserves more codebase context for thorough exploration; but doubles LLM summary cost and creates two condenser code paths that must be tested separately (`tests/unit/app_server/test_app_conversation_service_base.py:388-439` covers both). |

## Notable Patterns

- **Preset factory pattern:** `get_planning_tools(plan_path)` + `get_planning_condenser(llm)` + `get_planning_agent(llm)` in `openhands/tools/preset/planning.py:94-135` mirror `get_default_tools/agent/condenser` in `openhands/tools/preset/default.py:31-56` — pure functions returning `list[Tool]`/`Condenser`/`Agent`, applied via `configured_agent_settings.create_agent()` (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:1617-1630`). Clean separation but no registry or capability negotiation.
- **System-prompt injection with suffix composition:** `effective_suffix = f'{PLANNING_AGENT_INSTRUCTION}\n\n{system_message_suffix}'` (`openhands/app_server/app_conversation/live_status_app_conversation_service.py:1594-1600`) composes hard planning boundary over user-provided `system_message_suffix` and optional `WEB_HOST` context — defense-in-depth for prompt injection.
- **Lazy file bootstrap:** `PlanningFileEditorTool.create()` calls `plan_file.write_text(get_plan_headers())` if absent (`openhands/tools/planning_file_editor/definition.py:88-98`), ensuring every planning session starts with a scaffold even if workspace is fresh.
- **Event filtering for UX:** `shouldRenderEvent` returns `false` for `PlanningFileEditorAction` (`frontend/src/components/v1/chat/event-content-helpers/should-render-event.ts:34`) while `usePlanPreviewEvents` reconstructs `PLAN.md` content from `PlanningFileEditorObservation` (`frontend/src/components/v1/chat/hooks/use-plan-preview-events.ts:42`) — plan edits are not shown as raw tool calls but as a rendered card.
- **Dual planning primitives:** Formal `PLAN.md` (dedicated mode, visible, file-backed) coexists with lightweight `task_tracker` (`TASKS.md`, status `todo|in_progress|done`, `openhands/tools/task_tracker/definition.py:38-120`) for ad-hoc default-mode decomposition — two non-interoperating planning surfaces with overlapping intent.

## Tradeoffs

- **Visibility vs. structure:** Markdown plan is instantly human-readable in `PlanPreview` and planner tab, but stringly-typed prose cannot be queried, validated, or executed step-wise by runtime (contrast to a `Plan = list[Step{id, goal, method, status}]` object). The Build handoff is a natural-language prompt (`frontend/src/hooks/use-handle-build-plan-click.ts:27`), not a typed `ExecutePlan(plan_id)` call, so executor must re-parse prose.
- **Isolation vs. continuity:** Sub-conversation isolation gives the planner a clean read-only sandbox and separate `planning_condenser` context, but severs planning events from the execution conversation's history; building requires the executor to re-discover context by re-reading `PLAN.md` rather than inheriting planner reasoning trace.
- **Read-only safety vs. tool poverty:** Excluding `TerminalTool`/`FileEditorTool` from planning prevents accidental mutation, but also removes the planner's ability to run `ls | grep`, `git log`, or scripted checks that would improve plan quality; planner is limited to `Grep`/`Glob` + view.
- **Prompt flexibility vs. enforcement:** Four-phase workflow in Jinja2 is easy to iterate without code changes, but phases are unenforceable guidelines — the model may produce a shallow plan that passes the only gate (non-empty `PLAN.md` file exists). No server-side validator checks that all 5 headers are filled or that steps reference real files.
- **Opt-in vs. adoption:** Optional planning respects user autonomy and avoids token overhead for trivial tasks, but means most sessions never create a `PLAN.md`; the codebase lacks data on plan quality because decomposition is usually ad-hoc via `task_tracker` or no tracking at all.

## Future Considerations

- **Structured `Plan` runtime object:** Promote `PLAN_STRUCTURE` from markdown headers to a Pydantic/JSON schema `Plan { objective: str, context: str, approach: str, steps: list[Step{goal, method, file_refs[], status}], validation: str }` persisted in `AppConversationInfo` or a new `plan` table, with `str_replace` replaced by `UpdatePlanStep` typed events. Would enable validation, step-wise execution, and progress tracking without parsing markdown.
- **Typed planner-executor contract:** Replace the Build prompt string (`frontend/src/hooks/use-handle-build-plan-click.ts:27`) with `POST /conversations/{id}/execute-plan {plan_id, mode="steps"}` that atomically switches `agent_type`, injects the parsed plan into `AgentContext`, and creates a `PlanExecution` record. Enables retries, partial execution, and inter-step HITL.
- **Plan lifecycle and revision API:** Add `GET/PUT /conversations/{id}/plan` + `GET /plan/history` with versioning, diff rendering in planner tab, and `task_tracker` sync (map `Plan.steps` ↔ `TaskTracker` items). Currently two orthogonal planners (`PLAN.md` vs `TASKS.md`) should be unified.

Surface warnings in `PlanPreview` instead of silently building a broken plan.
