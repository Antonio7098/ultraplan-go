## Summary

Pydantic AI models tool availability through a layered abstraction: an `AbstractToolset` (pydantic_ai_slim/pydantic_ai/toolsets/abstract.py:74) is the unit of catalog; `ToolDefinition` (pydantic_ai_slim/pydantic_ai/tools.py:687) is the wire-facing record; `RunContext.available_tool_names` / `available_capability_ids` (pydantic_ai_slim/pydantic_ai/_run_context.py:181,159) are the read-side observers; `Model.prepare_request()._resolve_native_tool_swap` (pydantic_ai_slim/pydantic_ai/models/__init__.py:437) is the per-request filter that decides what reaches the provider.

Discovery is opt-in via `ToolDefinition.defer_loading=True` (pydantic_ai_slim/pydantic_ai/tools.py:747). The `ToolSearch` capability (pydantic_ai_slim/pydantic_ai/capabilities/_tool_search.py:43) is auto-injected into every agent (pydantic_ai_slim/pydantic_ai/agent/__init__.py:2924), wrapping the agent's toolset in `ToolSearchToolset` (pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:246). That toolset splits the corpus into "visible" vs "deferred" entries, stamps `with_native='tool_search'` and `defer_loading=False/True` per turn, and emits either a `search_tools` function tool or relies on the provider's native tool-search builtin (Anthropic bm25/regex, OpenAI `tool_search`). Discovered tool names are tracked in message history (`ToolSearchReturnPart` / `NativeToolSearchReturnPart`) and rehydrated at the start of every step via `parse_discovered_tools` (pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:185) and `_refresh_discovered_tool_names` (pydantic_ai_slim/pydantic_ai/_agent_graph.py:1450).

Routing is composed out of wrapper toolsets and capability hooks. `CombinedToolset` (`pydantic_ai_slim/pydantic_ai/toolsets/combined.py:26`) merges multiple toolsets and surfaces `UserError` on name conflicts (pydantic_ai_slim/pydantic_ai/toolsets/combined.py:73). Capability-level wrappers — `FilteredToolset`, `PrefixedToolset`, `RenamedToolset`, `PreparedToolset`, `ApprovalRequiredToolset`, `DeferredLoadingToolset`, `CapabilityOwnedToolset`, `IncludeReturnSchemasToolset`, `SetMetadataToolset`, plus the per-run `ToolSearchToolset` and `DeferredCapabilityLoaderToolset` — compose like middleware (`pydantic_ai_slim/pydantic_ai/toolsets/abstract.py:192-279`, `pydantic_ai_slim/pydantic_ai/toolsets/wrapper.py:60`). The agent assembles this stack once per run in `Agent._get_toolset` (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:2591`), wrapping the combined toolset inside-out: a `PreparedToolset` for `prepare_tools`, then the capability's `get_wrapper_toolset` (e.g. `ToolSearch`), then the output toolset prepended.

Routing is also observable from outside the agent: every tool call goes through `ToolManager` (pydantic_ai_slim/pydantic_ai/tool_manager.py:78) which caches the per-step tool map, classifies calls (`_resolve_tool`, pydantic_ai_slim/pydantic_ai/tool_manager.py:356), validates args via Pydantic schema + custom `args_validator_func`, dispatches through capability hooks (`before/after/wrap_tool_validate`, `before/after/wrap_tool_execute`), and raises `ModelRetry` with the available tool names if the model hallucinates one (`tool_manager.py:362-369`). Approval, deferred-execution and tool-denied results surface as control-flow exceptions routed through the same manager.

Capability-level discovery is the symmetric "bundle" layer: a capability with `defer_loading=True` is hidden until the model calls the framework-managed `load_capability` tool (`pydantic_ai_slim/pydantic_ai/toolsets/_deferred_capability_loader.py:31`), which is added by `DeferredCapabilityLoader` (auto-injected when any capability has `defer_loading=True`, pydantic_ai_slim/pydantic_ai/agent/__init__.py:1392). Loading is recorded in message history as `LoadCapabilityCallPart`/`LoadCapabilityReturnPart` and rehydrated by `parse_loaded_capabilities` (pydantic_ai_slim/pydantic_ai/_deferred_capabilities.py:141). The capability's contributed toolset is wrapped in `CapabilityOwnedToolset` (`pydantic_ai_slim/pydantic_ai/toolsets/_capability_owned.py:19`), which stamps `capability_id` and (if the capability defers) `defer_loading=True` onto each tool.

## Rating

**9/10 — Mature.** Pydantic AI has a deliberate, capability-driven separation between the catalog (toolset), the per-request filter (`Model._resolve_native_tool_swap`), and the per-turn visibility state (`RunContext.available_tool_names` / `discovered_tool_names`). Discovery supports server-side native, client-executed native, custom-callable, and local-keyword strategies, with a single `_resolve_native_tool_swap` four-rule filter that keeps the wire shape consistent across providers (`models/__init__.py:437-521`). The model is end-to-end typed (`ToolSelector` with `'all'` / `Sequence[str]` / `dict[str, Any]` / callable, `pydantic_ai_slim/pydantic_ai/tools.py:168`), traceable (`RunContext.tools`, `available_tool_names`, `_resolve_tool` listing available names on retry), extensible (capability-level `prepare_tools` / `prepare_output_tools` / `get_wrapper_toolset`), and tested (`tests/test_tool_search.py` is 5,500 lines). Deductions are for the documented tech debt on `ToolDefinition.defer_loading` carrying both user-intent and current-visibility meaning (`pydantic_ai_slim/pydantic_ai/tools.py:747-768`) and the dual-purpose `unless_native`/`with_native` pair that toolsets must coordinate via four implicit rules (the rules are documented but not enforced — `toolsets/_tool_search.py:316-330`).

## Answers to Dimension Questions

1. **Does every agent see every tool?** No. The catalog is the union of all registered toolsets, but per-request visibility is filtered by (a) `ToolDefinition.defer_loading` (pydantic_ai_slim/pydantic_ai/tools.py:747), (b) `RunContext.discovered_tool_names` (pydantic_ai_slim/pydantic_ai/_run_context.py:144), and (c) `RunContext.loaded_capability_ids` (pydantic_ai_slim/pydantic_ai/_run_context.py:129). `Model._resolve_native_tool_swap` further drops entries by their `unless_native` / `with_native` flags (pydantic_ai_slim/pydantic_ai/models/__init__.py:437-521). `RunContext.available_tool_names` (pydantic_ai_slim/pydantic_ai/_run_context.py:181) returns the exact callable subset.
2. **Are tools filtered by task?** Not by default — the agent exposes its full catalog subject to the discovery/loading machinery. Per-step / per-task filtering is supported via three orthogonal mechanisms: `ToolsPrepareFunc` from a `PrepareTools` capability (`pydantic_ai_slim/pydantic_ai/tools.py:125`), `prepare_tools` hook on any custom `AbstractCapability` (`pydantic_ai_slim/pydantic_ai/capabilities/abstract.py:371`), and `FilteredToolset` (`pydantic_ai_slim/pydantic_ai/toolsets/filtered.py:14`).
3. **Are tools filtered by permission?** Two layers. `ApprovalRequiredToolset` blocks `call_tool` until human approval (`pydantic_ai_slim/pydantic_ai/toolsets/approval_required.py:16-31`); `requires_approval=True` on a `Tool` does the same per-tool (`pydantic_ai_slim/pydantic_ai/tools.py:482`, `pydantic_ai_slim/pydantic_ai/toolsets/function.py:102`). Approval/denial is dispatched through `ToolManager._resolve_single_deferred` → `HandleDeferredToolCalls.handle_deferred_tool_calls` (`pydantic_ai_slim/pydantic_ai/tool_manager.py:847-936`). External tools (`ExternalToolset`) are visible but cannot be called in-process (`pydantic_ai_slim/pydantic_ai/toolsets/external.py:44-47`).
4. **Can tools be hidden from the model?** Yes, three ways: per-tool `defer_loading=True` (hides until discovered), toolset-level `DeferredLoadingToolset(...)` (hides all or selected tools), and capability-level `defer_loading=True` (hides the whole capability's tools and instructions until `load_capability` is called). All three are reflected in `RunContext.available_tool_names` and the `ModelRequestParameters.function_tools` sent to the provider.
5. **Is tool availability explainable?** Yes. `RunContext.tools` exposes the per-step tool map; `available_tool_names` and `available_capability_ids` are derived properties with comment-rich derivations (`pydantic_ai_slim/pydantic_ai/_run_context.py:181-225`); the agent-graph `_refresh_loaded_capability_ids` / `_refresh_discovered_tool_names` document the source of each set (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:1431-1456`); `ToolManager._resolve_tool` includes the full available list in its `ModelRetry` message when the model hallucinates a tool name (`pydantic_ai_slim/pydantic_ai/tool_manager.py:362-369`). All built-in `AbstractToolset.label`/`tool_name_conflict_hint` are designed for error messages (`pydantic_ai_slim/pydantic_ai/toolsets/abstract.py:97-109`).

## Architectural Decisions

- **Toolsets, not bare tool lists, are the catalog unit.** A toolset owns lifecycle (`__aenter__`/`__aexit__`), per-run (`for_run`) and per-step (`for_run_step`) instance resolution, instructions, identity (`id` for durable execution), and a stable error label (`pydantic_ai_slim/pydantic_ai/toolsets/abstract.py:74-190`). This is the right granularity because a toolset is what has an open connection, a schema source, or an approval policy — exposing individual tools to the agent graph would lose those bindings.
- **Wrapper toolsets compose middleware-style rather than subclasses.** `WrapperToolset` (`pydantic_ai_slim/pydantic_ai/toolsets/wrapper.py:14`) is the explicit base for `Filtered`, `Prefixed`, `Renamed`, `Prepared`, `ApprovalRequired`, `CapabilityOwned`, `ToolSearch`, `DeferredCapabilityLoaderToolset`. The convention is enforced via the AGENTS rule "Extend `WrapperToolset` for cross-cutting toolset behavior — don't modify base classes or individual toolset implementations" (`pydantic_ai_slim/pydantic_ai/AGENTS.md:987`). Cross-cutting behavior is added without coupling.
- **`prepare_tools`/`prepare_output_tools` are capability hooks, not toolset flags.** The hook is dispatched inside a `PreparedToolset` that wraps the combined non-output toolset (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:2617-2631`), with the output toolset getting its own `PreparedToolset` so the two hooks see disjoint sets. The ordering (inside the capability wrapper, outside other transforms) is explicit.
- **Discovery is a per-tool flag, not a per-call decision.** `ToolDefinition.defer_loading` is set by the user (or by `DeferredLoadingToolset`) and consumed by `ToolSearchToolset.get_tools` (pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:284-345), which then flips `defer_loading=False` for entries the model has already discovered this turn. The dual meaning of the field is acknowledged tech debt (`pydantic_ai_slim/pydantic_ai/tools.py:747-768`) — a `RunContext.loaded_tools` view is the planned fix.
- **Native-vs-local is decided at request time, not registration time.** A `NativeOrLocalTool` capability registers both a `native` tool and a `local` fallback tagged `unless_native=<native.unique_id>` (`pydantic_ai_slim/pydantic_ai/capabilities/native_or_local.py:165-186`). `Model._resolve_native_tool_swap` then drops the local copy if the profile supports the native (`pydantic_ai_slim/pydantic_ai/models/__init__.py:496-508`). This is what makes `FallbackModel` work — it can't know at registration which model will serve, so the choice happens per request inside `prepare_request`.
- **Auto-injection of `ToolSearch` and `DeferredCapabilityLoader`.** `ToolSearch` is added to every agent so any deferred tool benefits (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:2924-2928`). `DeferredCapabilityLoader` is only added when at least one capability has `defer_loading=True` (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:1392-1396`). This keeps the steady-state cost at zero.
- **Discoveries and capability loads survive across runs via message history.** `parse_discovered_tools` and `parse_loaded_capabilities` scan history for typed parts (`pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:185`, `pydantic_ai_slim/pydantic_ai/_deferred_capabilities.py:141`), so resuming a conversation or switching models mid-run doesn't force re-discovery.

## Notable Patterns

- **Capability ordering middleware.** `CombinedCapability` topologically sorts children by their `CapabilityOrdering` (`pydantic_ai_slim/pydantic_ai/capabilities/capability.py`, `pydantic_ai_slim/pydantic_ai/capabilities/_ordering.py`); the same idea applies to toolsets via `get_wrapper_toolset` being called once per run on the already-assembled toolset.
- **`prepared_tools` is identity-stable.** `PreparedToolset` rejects adds/renames (`pydantic_ai_slim/pydantic_ai/toolsets/prepared.py:33-36`), forcing structural changes to go through dedicated wrappers (`RenamedToolset`, `add_function`). This keeps the prepare hook pure (filter / modify).
- **`with_native` / `unless_native` symmetric pair.** Documented as a symmetric pair on `ToolDefinition` (`pydantic_ai_slim/pydantic_ai/tools.py:770-799`); consumed by a single 4-rule filter in `Model._resolve_native_tool_swap` (pydantic_ai_slim/pydantic_ai/models/__init__.py:437-449).
- **`capability_id` as a stable per-run identity for capability-owned tools.** Assigned once at toolset wrap (`pydantic_ai_slim/pydantic_ai/toolsets/_capability_owned.py:36-42`) and used by `RunContext.available_tool_names` to decide visibility (`pydantic_ai_slim/pydantic_ai/_run_context.py:213-217`) and by `ToolSearch.before_model_request` to discover newly-loaded capabilities (`pydantic_ai_slim/pydantic_ai/capabilities/_tool_search.py:215-255`).
- **Tool-search corpus is keyed on the real tool name.** A single entry per deferred tool is emitted with `with_native='tool_search'` regardless of visibility (`pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:316-328`). The `defer_loading` field on that entry toggles per turn; `_resolve_native_tool_swap` reads the pair to decide wire inclusion.
- **`FunctionToolset` is the universal "register functions as tools" surface.** It backs `@agent.tool` / `@agent.tool_plain`, `FunctionToolset` standalone, `LangChainToolset`, `ACIToolset`, and the `_AgentFunctionToolset` private class (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:3055`, `pydantic_ai_slim/pydantic_ai/ext/langchain.py:67`, `pydantic_ai_slim/pydantic_ai/ext/aci.py:83`).
- **`ToolManager` separates validation from execution.** `validate_tool_call` and `execute_tool_call` are public, callable independently (pydantic_ai_slim/pydantic_ai/tool_manager.py:419-501). Output tools have parallel `validate_output_tool_call` / `execute_output_tool_call` that go through output hooks, not tool hooks (pydantic_ai_slim/pydantic_ai/tool_manager.py:505-699). This is what lets streaming vs. non-streaming paths share validation but differ on hooks.
- **`apply` / `visit_and_replace` on both `AbstractToolset` and `AbstractCapability`.** Lets code walk the composite tree without unwrapping it (pydantic_ai_slim/pydantic_ai/toolsets/abstract.py:182-190, pydantic_ai_slim/pydantic_ai/capabilities/abstract.py:232-239). Used by `DeferredCapabilityLoaderToolset._collect_owned_toolset_instructions` (`pydantic_ai_slim/pydantic_ai/toolsets/_deferred_capability_loader.py:91-97`) and the sampling-model walker (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:2769`).

## Tradeoffs

- **Per-step `get_tools()` cost.** Every model request rebuilds the full tool map (filtered, prepared, capability-owned, search-stamped). For toolsets that need I/O to list tools (MCP, FastMCP), this means a server round-trip per step. Mitigated by `_cached_tool_defs` on the MCP classes (`pydantic_ai_slim/pydantic_ai/mcp.py:1119`) and by durable execution caches (`pydantic_ai_slim/pydantic_ai/durable_exec/temporal/_mcp_toolset.py:48-60`).
- **`ToolDefinition.defer_loading` double-meaning.** Carries both the user opt-in intent and the current-turn visibility flag (acknowledged in `pydantic_ai_slim/pydantic_ai/tools.py:747-768`). Workaround: toolset-set values flow on per-step `ToolDefinition` instances built via `replace`, never mutating the user's persisted definitions.
- **`unless_native` / `with_native` requires manual coordination.** Toolsets that participate must stamp exactly one of the flags with the right `unique_id`. There is no static check that the local tool's `unless_native` matches the native tool's `unique_id`; correctness is enforced by the four-rule filter at request time.
- **`CombinedToolset` is order-sensitive for capability ownership.** `_build_toolset_list` always prepends the function toolset (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:2691`). User / dynamic / cap toolsets follow in that order; if two toolsets both claim a tool, `CombinedToolset` raises (`pydantic_ai_slim/pydantic_ai/toolsets/combined.py:73-77`). Users have to disambiguate by namespacing or `PrefixedToolset`.
- **Tool-search native path requires provider support.** `None` strategy falls back to local keyword search on providers without `ToolSearchTool` support; explicit `'bm25'` / `'regex'` raises `UserError` on unsupported models (`pydantic_ai_slim/pydantic_ai/capabilities/_tool_search.py:182-184`). `'bm25'`/`'regex'` are also rejected when the search corpus is owned by a deferred capability, because the native server-side search can't gate by capability state (`pydantic_ai_slim/pydantic_ai/capabilities/_tool_search.py:186-210`).
- **`load_capability` catalog is stable per turn.** Listing already-loaded capabilities in the catalog costs nothing in user intent but wastes a prompt slot — by design, to keep the cache prefix warm (`pydantic_ai_slim/pydantic_ai/capabilities/_deferred_capability_loader.py:35-51`).
- **Deferred tools lose their user-set name during discovery.** `ToolSearchToolset.get_tools` keeps the real tool name but flips `defer_loading`; on discovery the model still needs to call the tool by its real name, so tool-naming discipline matters (covered in `docs/tools-advanced.md:636`).

## Failure Modes / Edge Cases

- **Model calls an unknown tool name.** `ToolManager._resolve_tool` raises `ModelRetry` with the full available list (`pydantic_ai_slim/pydantic_ai/tool_manager.py:362-369`). This is a retry signal that costs one retry-budget entry.
- **Model calls a deferred tool by its real name without searching first.** On native-supporting providers the corpus entry with `defer_loading=True` is sent to the wire so the provider can reveal it on demand (`pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:316-330`). On unsupported providers the corpus is dropped (`pydantic_ai_slim/pydantic_ai/models/__init__.py:505-506`), so the model can't call it; the call surfaces as `Unknown tool name: ... Available tools: ...`.
- **Tool name conflicts across toolsets.** `CombinedToolset` raises `UserError` with a hint (`pydantic_ai_slim/pydantic_ai/toolsets/combined.py:73-77`); the hint is overridable per toolset via `tool_name_conflict_hint` (`pydantic_ai_slim/pydantic_ai/toolsets/abstract.py:105-108`).
- **Native tool unsupported but no local fallback and `optional=False`.** `_resolve_native_tool_swap` raises `UserError` with the supported native-tools list (`pydantic_ai_slim/pydantic_ai/models/__init__.py:474-487`). No silent substitution.
- **Tool-search corpus empty (no deferred tools exist).** Auto-injected `ToolSearchTool` is dropped from the request (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:519-525`); the local `search_tools` function tool is also suppressed (`pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:295-296`).
- **`load_capability` on an already-available capability.** Raises `ModelRetry(LOAD_CAPABILITY_ALREADY_AVAILABLE_MESSAGE_TEMPLATE)` (`pydantic_ai_slim/pydantic_ai/toolsets/_deferred_capability_loader.py:73-74`), deliberately one wasted retry rather than busting the prompt-cache prefix by mutating the catalog.
- **History truncation removes discovery parts.** Discovered-tool state lives in `ToolSearchReturnPart`/`NativeToolSearchReturnPart` content (`pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:185-216`); history processors that drop them force re-discovery (`docs/tools-advanced.md:718-719`). Same for `LoadCapabilityReturnPart` → `parse_loaded_capabilities`.
- **`prepare_tools` returns `None`.** Emits a warning (`pydantic_ai_slim/pydantic_ai/toolsets/prepared.py:29-30`); the function is effectively a no-op for that step. Returning `[]` is the supported way to hide all tools for the step (`pydantic_ai_slim/pydantic_ai/capabilities/prepare_tools.py:30`).
- **`PreparedToolset` adds or renames.** Raises `UserError` (`pydantic_ai_slim/pydantic_ai/toolsets/prepared.py:33-36`) — forces structural changes through dedicated wrappers.
- **Deferred capability with no `id`.** Construction-time `UserError` (`pydantic_ai_slim/pydantic_ai/agent/__init__.py:2953-2957`).
- **`Tool.defer_loading=True` overridden at toolset level by `defer_loading=False`.** Per-tool `defer_loading` is set by `FunctionToolset.add_function` (defaults to toolset-level `defer_loading`, `pydantic_ai_slim/pydantic_ai/toolsets/function.py:554-555`), so `DeferredLoadingToolset` wrapping a non-deferred toolset can override any explicit `True`.

## Future Considerations

- **Replace dual-meaning `defer_loading`.** A `RunContext.loaded_tools`-style derived view would let `ToolDefinition.defer_loading` be a pure user-input flag again (`pydantic_ai_slim/pydantic_ai/tools.py:761-766`). Currently the responsibility is split across `ToolSearchToolset.get_tools` (turn-level) and `_resolve_native_tool_swap` (per-request filter).
- **Schema-level types for `with_native`/`unless_native`.** Today the names are bare strings that must match a native tool's `unique_id`. A typed literal or enum per native tool would prevent silent typos.
- **Smarter cache-friendly catalog for `DeferredCapabilityLoader`.** The catalog currently lists every deferred capability on every turn (pydantic_ai_slim/pydantic_ai/capabilities/_deferred_capability_loader.py:35-51) to keep the cache prefix stable; an alternative would be a dedicated `load_capability` argument that exposes the catalog with minimal cache impact.
- **More named local strategies for `ToolSearch`.** Only `'keywords'` exists today (`pydantic_ai_slim/pydantic_ai/native_tools/_tool_search.py:54-63`); future local BM25 / TF-IDF / regex would join the literal. No local BM25/regex means `'bm25'`/`'regex'` strategies can't fall back when the provider doesn't support them (`pydantic_ai_slim/pydantic_ai/capabilities/_tool_search.py:178-181`).
- **More native providers with tool-search builtins.** Today only Anthropic (`bm25`, `regex`, `custom`) and OpenAI Responses (`tool_search`, custom via `execution='client'`) are listed (`pydantic_ai_slim/pydantic_ai/native_tools/_tool_search.py:127-131`); Google Gemini / xAI would extend `supported_native_tools`.
- **Validate uniqueness of tool names per agent eagerly.** Currently `CombinedToolset.get_tools` is the first place a name conflict surfaces, which can be late (during `prepare_request`). Earlier validation in `_build_toolset_list` could fail at agent construction.
- **Filter-by-permission beyond approval.** No permission model beyond `ApprovalRequiredToolset` and `requires_approval`; adding something like OAuth-scope-based filter as a `WrapperToolset` is the natural extension point.

## Questions / Gaps

- **No explicit exposure of `ModelRequestParameters` shape as public observability surface.** `tool_defs` is reachable via `m.last_model_request_parameters.function_tools` (referenced in `pydantic_ai_slim/pydantic_ai/.agents/skills/building-pydantic-ai-agents/SKILL.md:151`), but a `RunContext.model_request_parameters` view is not present. Hooks that want to inspect "what's going to the wire" must rely on `before_model_request`'s `ModelRequestContext`.
- **Tool-selection explanation across runs is not persisted.** Discoveries and capability loads are reconstructed from message history every run; cross-run audit ("what was visible when?") requires inspecting message history after the fact.
- **No evidence of a metrics surface for tool-selection behavior** (e.g. counters for "model called tool X before discovery"). Pydantic AI emits OTel spans via the `Instrumentation` capability (referenced in `pydantic_ai_slim/pydantic_ai/capabilities/abstract.py` and `pydantic_ai_slim/pydantic_ai/_instrumentation.py`), but per-tool discovery/call counters are not surfaced at the framework level. Whether they exist at the instrumentation tier was not directly inspected.
- **Dynamic `ToolsetFunc` per-step lifecycle has subtle transition hazards.** `_dynamic.py:88-96` documents the order ("detach the old toolset first so that if either the exit-old or enter-new step raises..."); for multi-agent / per-step toolset factories this is the place to look first when an `__aexit__` error appears.
- **`prefix_tools` capability wrapper's interaction with `CombinedToolset` name-conflict detection.** The capability exists (`pydantic_ai_slim/pydantic_ai/capabilities/prefix_tools.py`, declared on `AbstractCapability.prefix_tools` `pydantic_ai_slim/pydantic_ai/capabilities/abstract.py:951-958`) but its place in the per-run toolset assembly (`Agent._get_toolset`, pydantic_ai_slim/pydantic_ai/agent/__init__.py:2591-2660) is not obvious from the code; it appears to wrap individual capabilities rather than the assembled toolset, which could leave namespacing gaps if two non-prefixed capabilities expose the same tool name.
- **No evidence found** of a public, structured "tool policy" / "agent tool manifest" that downstream systems (UI, observability) can read to know which tool is exposed to which capability under which state. The closest is the implicit per-run `ModelRequestParameters`.
