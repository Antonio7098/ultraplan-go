## Summary

Langfuse carries an explicit, multi-layer error taxonomy that classifies failures by source category and uses the classification to drive retry, escalation, user-facing copy, observability tags, and HTTP / queue error contracts. The taxonomy spans (1) a small HTTP-oriented `BaseError` hierarchy for the public REST + tRPC surface (`packages/shared/src/errors/*.ts`), (2) a `kind` discriminator (`"provider" | "validation" | "ai-sdk" | "timeout" | "abort"`) on `LLMErrorInfo` for native AI SDK + Langfuse-side validation failures (`packages/shared/src/server/llm/errors.ts:43`), (3) a `ClickHouseResourceError` with `errorType: "MEMORY_LIMIT" | "OVERCOMMIT" | "TIMEOUT"` keyed off message discriminators (`packages/shared/src/server/repositories/clickhouse.ts:47-110`), (4) a `CodeEvalDispatcherErrorCode` enum (`INVALID_RESULT`, `INVALID_SOURCE`, `PAYLOAD_TOO_LARGE`, `RESULT_TOO_LARGE`, `SOURCE_TOO_LARGE`, `TIMEOUT`, `UNSUPPORTED_RUNTIME`, `USER_CODE_ERROR`, `LAMBDA_*`) with explicit `retryable: boolean` and an internal / public translation layer (`packages/shared/src/server/evals/codeEvalDispatcherTypes.ts:144-182`), (5) a `SlackApiError` carrying the upstream `slackErrorCode` for dispatch to user-facing messages (`packages/shared/src/server/services/SlackService.ts:21-29`), (6) an outbound-URL security taxonomy (`OutboundUrlValidationError`, `RedirectValidationError`, `MaxRedirectsExceededError`, `CircularRedirectError`) classified by name (not instanceof) at the dispatcher (`packages/shared/src/server/outbound-url/fetch.ts:29-67`, `worker/src/errors/findOutboundUrlValidationError.ts:17-90`), (7) an MCP-side split (`UserInputError` vs `ApiServerError`, Sentry-style) (`web/src/features/mcp/core/errors.ts:19-49`), (8) a `BaseError` + worker-only `UnrecoverableError` distinction used to short-circuit BullMQ retries (`worker/src/errors/UnrecoverableError.ts:3-17`, `worker/src/features/integrations/bullmqAttempts.ts:8-32`), and (9) a `InAppAgentRunErrorCode` enum with 14 source categories (`STALE`, `CANCELLED`, `AGENT_ERROR`, `INIT_FAILED`, `WORKER_SHUTDOWN`, `OUTCOME_UNKNOWN`, `ENQUEUE_FAILED`, `QUEUE_TIMEOUT`, `WORKER_LOST`, `RUN_TIMEOUT`, `APPROVAL_EXPIRED`, `APPROVAL_SUPERSEDED`, `APPROVAL_CANCELLED`, `STEP_LIMIT`) that drive both terminal CAS writes and UI copy (`packages/shared/src/features/inAppAgent/types.ts:30-69`).

Dispatch is concrete in every layer: tRPC `withErrorHandling` converts `BaseError.cause` into HTTP/tRPC codes and redacts 5xx messages (`web/src/server/api/trpc.ts:141-216`), the public REST `withMiddlewares` walks a six-branch `instanceof` ladder including `ClickHouseResourceError`, `BaseError`, `ZodError`, and Prisma exceptions (`web/src/features/public-api/server/withMiddlewares.ts:116-203`), and the unstable public API has its own second-level `code` enum (`unstablePublicApiErrorCodes`) mapping `BaseError` subclasses to stable wire codes (`web/src/features/public-api/shared/unstable-public-api-error-schema.ts:3-25`, `unstable-public-api-error-contract.ts:160-262`). The MCP layer translates these into `McpError` `ErrorCode` values (`web/src/features/mcp/core/error-formatting.ts:27-115`). Worker queue processors distinguish `UnrecoverableError` from retryable errors and emit distinct DB / log / trace outcomes (`worker/src/queues/codeEvalQueue.ts:43-88`, `worker/src/features/evaluation/evalService.ts:1060-1130`). Each classification has tests (e.g. `worker/src/features/integrations/bullmqAttempts.test.ts:41-66`, `packages/shared/src/server/llm/nativeErrors.test.ts:28-113`).

Documentation is split between inline (JSDoc on every class, plus the documented "Error handling (tRPC + REST)" playbook in `web/AGENTS.md:264-270`) and a backend-dev guidelines reference at `.agents/skills/backend-dev-guidelines/references/middleware-guide.md:280-342`. There is no central prose document describing the full taxonomy; the contract lives in code and tests, not in `docs/`.

Extensibility is reasonable for additive cases: the `BaseError` subclasses are pure subclasses of `BaseError` carrying `name`, `httpCode`, and `isOperational` — adding a new HTTP-coded error is a one-file subclass plus a barrel export. The `LLMErrorInfo.kind` union is a TypeScript string union closed to known kinds. `CodeEvalDispatcherErrorCode` is a `z.enum`, so additions are deliberate. `InAppAgentRunErrorCode` is a TypeScript enum persisted as a free-form string column — the comment explicitly warns readers to tolerate unknown strings (`packages/shared/src/features/inAppAgent/types.ts:25-29`), which is exactly the right extensibility posture for a persisted enum.

## Rating

**8 / 10** — Clear model with tests, explicit interfaces, and operational safeguards. Solid mapping from error source to retry/escalate/copy. Falls short of 9-10 because (a) the public surface uses two parallel contract vocabularies (`BaseError` httpCodes for the legacy REST API, `UnstablePublicApiError.code` for the new unstable contract) and the bridge between them is a long `if`/`instanceof` ladder rather than a registry, (b) several classifications rely on string-matching error message substrings (`BLOCK_REASON_PATTERNS` in `packages/shared/src/server/evals/classifyEvaluatorLlmError.ts:5-42`, the Slack `switch (slackErrorCode)` in `web/src/features/slack/server/router.ts:367-389`, and the `ClickHouseResourceError` discriminators at `packages/shared/src/server/repositories/clickhouse.ts:53-62`), which is fragile when upstream messages drift, (c) there is no central prose documentation of the taxonomy as a whole — discoverability depends on reading `AGENTS.md` playbooks plus hunting through `packages/shared/src/errors/`, and (d) the public API REST middleware does not import a registry; it `instanceof`-switches per error type.

## Answers to Dimension Questions

1. **Are errors classified by source?**
   Yes. Multiple parallel classifications exist: by **HTTP semantics** (`BaseError` subclasses, `packages/shared/src/errors/*.ts`), by **LLM stack layer** (`LLMErrorInfo.kind` = `provider | validation | ai-sdk | timeout | abort`, `packages/shared/src/server/llm/errors.ts:43`), by **ClickHouse failure mode** (`ClickHouseResourceError.errorType` = `MEMORY_LIMIT | OVERCOMMIT | TIMEOUT`, `packages/shared/src/server/repositories/clickhouse.ts:48-62`), by **code-eval dispatcher outcome** (`CodeEvalDispatcherErrorCode` z.enum + `retryable` flag, `packages/shared/src/server/evals/codeEvalDispatcherTypes.ts:144-182`), by **outbound-URL security layer** (`OutboundUrlValidationError`, `RedirectValidationError`, `MaxRedirectsExceededError`, `CircularRedirectError`, classified by name in `worker/src/errors/findOutboundUrlValidationError.ts:17-90`), by **provider error code** (`SlackApiError.slackErrorCode`, `packages/shared/src/server/services/SlackService.ts:21-29`), by **MCP user vs server** (`UserInputError` / `ApiServerError`, `web/src/features/mcp/core/errors.ts:19-49`), by **worker retryability** (`UnrecoverableError` vs `Error`, `worker/src/errors/UnrecoverableError.ts:3-17`), by **evaluator-policy decision** (`EvaluatorBlockReason` from message-pattern match, `packages/shared/src/server/evals/classifyEvaluatorLlmError.ts:5-110`), and by **in-app-agent run state** (14 `InAppAgentRunErrorCode` values, `packages/shared/src/features/inAppAgent/types.ts:30-69`). Coverage spans the dimension's source categories well, with the partial exceptions that "context" errors do not have a dedicated class (context overflow surfaces as `LLMValidationError("invalid-request")` or a `ClickHouseResourceError(TIMEOUT)`), and there is no single `UserError` class outside the MCP layer (HTTP 4xx is encoded as `BaseError.httpCode`).

2. **Is the taxonomy used for handling?**
   Yes, at every layer. **Retry**: `worker/src/features/integrations/bullmqAttempts.ts:8-32` short-circuits BullMQ retries on `UnrecoverableError`; `worker/src/queues/codeEvalQueue.ts:48-70` decides between persisting terminal ERROR vs rethrowing for retry based on `isUnrecoverableError`; `worker/src/features/evaluation/codeBased/executeCodeBasedEvaluation.ts:80-85` throws `UnrecoverableError` vs `CodeEvalExecutionError` based on `retryable`. **HTTP dispatch**: `web/src/server/api/trpc.ts:141-216` and `web/src/features/public-api/server/withMiddlewares.ts:116-203` map `BaseError.httpCode` → `TRPCError`/HTTP code and `ClickHouseResourceError` → 422 advice; `web/src/features/public-api/server/unstable-public-api-error-contract.ts:160-262` maps each `BaseError` subclass to a stable wire-level code; `web/src/features/mcp/core/error-formatting.ts:27-115` maps each MCP-typed error to an `McpError.ErrorCode`. **Logging / Sentry**: `web/src/features/public-api/server/withMiddlewares.ts:67-82` selects `logger.info` / `logger.warn` / `logger.error` based on `isUserError()` and `NOT_FOUND`/`UNAUTHORIZED`; `web/src/server/api/trpc.ts:151-173` does the same. **User-facing copy**: `web/src/features/in-app-agent/lib/backgroundExecutionSession.ts:573-599` maps each `InAppAgentRunErrorCode` to UI strings; `web/src/features/slack/server/router.ts:367-389` maps `slackErrorCode` to Slack-specific guidance; `web/src/features/evals/server/evaluator-preflight.ts:103-110` maps `statusCode === 404` to "model may be retired / misspelled / not available to your key". **Operational side effects**: `worker/src/features/evaluation/evalService.ts:1102-1109` pauses an evaluator with `EvaluatorBlockSource.LLM_COMPLETION_ERROR` when `classification.blockReason !== null` — i.e. the taxonomy drives durable state, not just logging. **APM**: `worker/src/features/evaluation/evalSpanAttributes.ts:84-117` exposes the LLM classification as low-cardinality span attributes (provider messages deliberately omitted). **Persistence**: `worker/src/features/in-app-agent/executeInAppAgentRun.ts:611-625` writes `errorCode` into the `in_app_agent_runs.error_code` column from the same enum. The headline question — "Can you tell from the error type whether to retry, escalate, or stop?" — is answered concretely for BullMQ (yes, `UnrecoverableError` + `codeEvalUserVisibleError.retryable`), LLM (yes, `LLMErrorInfo.kind` + `isRetryable`), ClickHouse (yes, `ClickHouseResourceError.errorType`), and code-eval (yes, `CodeEvalDispatcherErrorCode.retryable`).

3. **Are error categories documented?**
   Partially. There is no central prose document describing the full taxonomy as a single coherent system; the contract lives in code and tests. What is documented: every error class has a JSDoc block explaining when to throw it (`packages/shared/src/errors/*.ts`, `worker/src/errors/*.ts`, `web/src/features/mcp/core/errors.ts:1-7`); `web/AGENTS.md:264-270` documents the error-handling playbook (which classes to throw, how middleware should consume them, where to add new ones); `.agents/skills/backend-dev-guidelines/references/middleware-guide.md:280-342` shows the canonical `withMiddlewares` ladder including `BaseError` → HTTP and `ClickHouseResourceError` → 422; `InAppAgentRunErrorCode` carries a per-value comment explaining the operational scenario (`packages/shared/src/features/inAppAgent/types.ts:30-69`); `findOutboundUrlValidationError.ts:1-12` documents why the classifier ducks on `error.name` instead of `instanceof`. What is missing: no `docs/error-handling.md` or architecture overview that walks the reader through the full taxonomy (HTTP errors vs LLM errors vs ClickHouse vs outbound-URL vs MCP vs worker retry vs evaluator policy vs in-app-agent runs) and how they relate. The barrier to discovering the taxonomy is high for a new contributor — they would need to read `AGENTS.md`, the middleware guide, then grep for `extends Error` and `extends BaseError` to assemble the picture. A consolidated prose document or a typed-discriminated union aggregator would close this gap.

4. **Can new error types be added without breaking existing handling?**
   Mostly yes, with caveats. **Easy / closed-for-extension points**:
   - **HTTP `BaseError` subclasses** — add a one-file subclass in `packages/shared/src/errors/`, re-export from `index.ts`. The tRPC middleware (`web/src/server/api/trpc.ts:141-149`) and the public REST middleware (`web/src/features/public-api/server/withMiddlewares.ts:165-174`) handle any `BaseError` via `isBaseError` + `error.httpCode`. The unstable contract `toUnstablePublicApiError` (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:249-255`) falls back to a generic code based on httpCode band, but adding a known mapping for a new code is a one-place change. MCP `formatErrorForUser` (`web/src/features/mcp/core/error-formatting.ts:79-93`) similarly handles any `BaseError` via `error.httpCode >= 500` split, with a generic `InvalidRequest` fallback for 4xx.
   - **`InAppAgentRunErrorCode`** — explicitly designed as additive. The persisted column is free-form string and the comment at `packages/shared/src/features/inAppAgent/types.ts:25-29` requires readers to tolerate unknown strings. Adding a value requires updating the enum, the dispatch in `executeInAppAgentRun.ts`, the UI copy in `backgroundExecutionSession.ts:573-590`, the Storybook test matrix at `web/src/features/in-app-agent/lib/backgroundExecutionSession.clienttest.ts:1382-1398`, and the integrity runner test at `worker/src/features/in-app-agent-integrity-runner/index.test.ts`. All call sites are grep-able.
   - **`OutboundUrlValidationError` family** — adding a new outbound-URL error requires adding the name to `OUTBOUND_VALIDATION_ERROR_NAMES` in `worker/src/errors/findOutboundUrlValidationError.ts:30-34` and a corresponding branch in `describeOutboundFailure` (`:82-90`). The classifier duck-types on `error.name` so instanceof across module boundaries is not an issue.

   **Closed / requires coordinated change**:
   - **`LLMErrorInfo.kind`** — TypeScript string union closed to known kinds; adding a kind requires updating `packages/shared/src/server/llm/errors.ts:43`, the test matrix at `packages/shared/src/server/llm/nativeErrors.test.ts:28-113`, the APM attribute builder at `worker/src/features/evaluation/evalSpanAttributes.ts:84-117`, and every `instanceof` ladder that reads `kind`. Strict by design.
   - **`CodeEvalDispatcherErrorCode`** — `z.enum`, additive changes are deliberate and require updating the message map at `packages/shared/src/server/evals/codeEvalExecution.ts:40-58`, the internal/error set at `:33-38`, the `RETRYABLE_ERROR_CODES` / `USER_ERROR_CODES` sets at `packages/shared/src/server/evals/awsLambdaCodeEvalDispatcher.ts:43-58`, the doc-link helper, and any dispatcher call site. Closed by design.
   - **`UnrecoverableError`** — adding terminal categories is not via subclassing; call sites throw `new UnrecoverableError("...")` directly. The taxonomy here is "permanent" vs "retryable" — coarse but extensible without coordination.

   The pattern that works best is the `BaseError` extension, because the public REST, tRPC, MCP, and unstable public API all have generic `BaseError` fallbacks. The patterns that require coordination are the closed enum / union cases, but those coordination costs are intentional and well-localized.

## Architectural Decisions

- **HTTP as the lowest common denominator.** `BaseError` (named, httpCode, isOperational, isUserError) is the public REST/tRPC error contract. Every other surface (LLM, ClickHouse, code-eval, MCP, Slack, in-app-agent) eventually maps onto either an `httpCode`, a BullMQ retry decision, or a UI copy decision — three sinks for the entire taxonomy.
- **Two parallel wire contracts for the public API.** Legacy public REST uses `BaseError.httpCode` + `error.name` (`web/src/features/public-api/server/withMiddlewares.ts:170-174`). The unstable public API (`unstable-public-evals`) uses a stable string `code` enum plus `details` payload (`web/src/features/public-api/shared/unstable-public-api-error-schema.ts:3-67`). The bridge is `toUnstablePublicApiError` (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:160-262`), a long `instanceof` ladder that hardcodes every subclass. Acceptable for now but is a maintenance hazard if more `BaseError` subclasses are added without updating the bridge.
- **`UnrecoverableError` as a name, not a type.** The worker-side retryability marker uses `error.name === "UnrecoverableError"` rather than `instanceof UnrecoverableError` (`worker/src/features/integrations/bullmqAttempts.ts:8-32`, `worker/src/queues/codeEvalQueue.ts:48`). This is a deliberate choice to survive module-boundary / test-mock issues, documented in the comment at `worker/src/errors/findOutboundUrlValidationError.ts:7-12` for a similar pattern. This is unusual but well-reasoned.
- **String-matching for upstream error codes.** Three places rely on substring / property matching against upstream payloads: `BLOCK_REASON_PATTERNS` for evaluator block reasons (`packages/shared/src/server/evals/classifyEvaluatorLlmError.ts:5-42`), `ClickHouseResourceError` discriminators (`packages/shared/src/server/repositories/clickhouse.ts:53-62`), and Slack `switch (slackErrorCode)` (`web/src/features/slack/server/router.ts:371-389`). The LLM path additionally inspects `providerError.data.error.code` and `.type` (`packages/shared/src/server/evals/classifyEvaluatorLlmError.ts:112-128`). These are fragile to upstream message drift and would benefit from version-pinned adapters per provider.
- **Persisted enums with forward compatibility.** `InAppAgentRunErrorCode` is a TypeScript enum persisted as a free-form string column. The contract comment (`packages/shared/src/features/inAppAgent/types.ts:25-29`) explicitly requires readers to tolerate unknown values. This is the right posture for a persisted enum that may receive new values from older code paths or migrations.
- **Classification by AI SDK markers rather than rebuild.** `LLMValidationError` uses a `Symbol.for("langfuse.error.LLMValidationError")` marker so that its identity survives `instanceof` boundaries (`packages/shared/src/server/llm/errors.ts:3-5, 32-39`). Native AI SDK errors are kept untouched; only the classification walks cause chains. This avoids leaking Langfuse-specific exceptions into the AI SDK surface.
- **Error categorization is a precondition for action, not just logging.** `classifyEvaluatorLlmError.blockReason` drives `pauseEvaluator({ blockReason, source: EvaluatorBlockSource.LLM_COMPLETION_ERROR })` (`worker/src/features/evaluation/evalService.ts:1102-1109`), which pauses the evaluator at the DB level. The taxonomy does not just describe errors; it operates on them.
- **Errors intentionally preserved through observability rather than suppressed.** `tRPC errorFormatter` keeps `errorName` and redacts `stack` only for `ClickHouseResourceError` (`web/src/server/api/trpc.ts:113-122`), with an explicit comment that CH errors may contain sensitive data. Other errors preserve their stack for debugging. `errorFormatter` also flattens `ZodError` into `zodError` so frontend typesafety is preserved (`web/src/server/api/trpc.ts:111-113`).
- **Documentation is JSDoc + AGENTS.md playbooks, not a central prose doc.** Per-file JSDoc is consistent and high quality; the gap is the absence of a single document that explains how the layers relate.

## Notable Patterns

- **`isInstance` / `name`-based classifier, not `instanceof`**: `LLMValidationError.isInstance`, `isBaseError`, `isUnrecoverableError`, `isObservationNotFoundError`, `findOutboundUrlValidationError`, `bullmqAttempts.isFinalBullmqAttempt`, and `findInCauseChain` all walk the `cause` chain and classify by marker symbol, property shape, or `error.name`. This is consistent and well-documented in code comments.
- **Cause-chain walking with cycle protection**: `findInCauseChain` (`packages/shared/src/server/llm/errors.ts:159-177`) and `findOutboundUrlValidationError` (`worker/src/errors/findOutboundUrlValidationError.ts:48-71`) both use a `visited: Set<unknown>` to defend against cycles in wrapped error graphs.
- **Static `wrapIfResourceError` factory**: `ClickHouseResourceError.wrapIfResourceError` (`packages/shared/src/server/repositories/clickhouse.ts:87-109`) converts an arbitrary error into the resource-error class if message discriminators match, otherwise returns the original. Used at ClickHouse call sites to convert generic exceptions into typed ones.
- **Two-step normalization for code-eval errors**: raw `CodeEvalDispatcherError` → `getCodeEvalUserVisibleError` collapses internal-only codes (`LAMBDA_CONCURRENCY_LIMIT`, `LAMBDA_CONFIGURATION_ERROR`, `LAMBDA_INVOCATION_ERROR`) into a generic `INTERNAL_ERROR` for end users, while preserving the full code for traces (`packages/shared/src/server/evals/codeEvalExecution.ts:174-204`).
- **Per-route error contract override**: `withMiddlewares({ clickHouseResourceErrorMessage: "..." })` (`web/src/features/public-api/server/withMiddlewares.ts:42-65, 117-140`) lets legacy endpoints carry their own migration advice while new endpoints keep the default.
- **Duck-typed retryability ducking `instanceof`**: `bullmqAttempts.ts` comment explicitly calls out that `instanceof` can miss a real `UnrecoverableError` across module boundaries; the project chose `error.name` instead (`worker/src/features/integrations/bullmqAttempts.ts:11-13`). This is unusual but documented.
- **Symbol-marker for cross-package identity**: `LLM_VALIDATION_ERROR_MARKER = Symbol.for("langfuse.error.LLMValidationError")` lets `LLMValidationError.isInstance` work even when an error crosses a `vi.mock` boundary that does not preserve prototype chain (`packages/shared/src/server/llm/errors.ts:3-5, 32-39`).
- **APM card**: `buildEvaluatorLlmErrorSpanAttributes` exports the LLM classification as a low-cardinality span attribute set, explicitly excluding provider response bodies to avoid leaking data into Datadog APM (`worker/src/features/evaluation/evalSpanAttributes.ts:79-117`).
- **Severity-aware logging on the same `BaseError`**: `logErrorByStatus` / `logBaseError` use `isUserError()` (4xx) to decide warn vs error, and further downgrade `NOT_FOUND` / `UNAUTHORIZED` to `info`. Severity is computed from the type, not from the call site.

## Tradeoffs

- **String-matching fragility**: `BLOCK_REASON_PATTERNS`, `ClickHouseResourceError` discriminators, and the Slack code switch all match against upstream message / property strings. When OpenAI, Anthropic, or ClickHouse change a message, evaluation could misclassify (e.g. an unrecognised billing error becomes "internal" rather than `BILLING_EXHAUSTED`). This is a deliberate tradeoff for not having a typed schema per provider, but should be documented as a known hazard.
- **Two parallel wire contracts**: legacy public API uses `BaseError.httpCode`, unstable public API uses `UnstablePublicApiErrorCode`. New API clients see a richer, more stable code vocabulary; legacy clients see HTTP codes. The bridge is a long `if`/`instanceof` ladder. Maintaining two contracts is real cost; the alternative would be a single registry keyed by `BaseError` subclass.
- **Closed unions for LLM and code-eval kinds**: `LLMErrorInfo.kind` and `CodeEvalDispatcherErrorCode` are closed unions. This is intentional (forces deliberate taxonomy changes) but means a new AI SDK error type or a new code-eval dispatcher outcome needs coordinated updates. The `LLMValidationErrorCode` enum (`packages/shared/src/server/llm/errors.ts:7-10`) is similarly closed.
- **`UnrecoverableError` as a marker name, not a hierarchy**: a more expressive design would be `UnrecoverableError` subclasses per source (`UnrecoverableSchemaError`, `UnrecoverableBudgetError`, …) that carry code metadata. The current design works because the only thing dispatchers need to know is "retry or don't"; richer taxonomy would be premature optimization.
- **`BaseError` does not carry `code`**: the class only carries `httpCode`. The unstable public API layer adds `code` on top of `BaseError` via `UnstablePublicApiError.code` (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:33-47`), so the legacy REST API surfaces `error.name` (`web/src/features/public-api/server/withMiddlewares.ts:170-173`) while the unstable one surfaces `error.code`. Splitting this means clients must read both to get full signal.
- **Documentation is distributed**: per-file JSDoc is good, but there is no central "error taxonomy" document tying HTTP errors, LLM errors, ClickHouse, code-eval, MCP, Slack, outbound-URL, evaluator policy, and in-app-agent runs together. Discoverability suffers.
- **Test coverage is uneven**: `UnrecoverableError` is exhaustively tested (multiple test files), `LLMErrorInfo.kind` is tested in `nativeErrors.test.ts`, and `withMiddlewares` has `withMiddlewares.servertest.ts` for `BaseError`. The Slack switch, the MCP formatter, and the unstable public API bridge have less coverage (the Slack switch only has a client-side route test). The gap is mostly around the string-matching ladders.

## Failure Modes / Edge Cases

- **Provider message drift**: as above, substring-matching discriminators (`BLOCK_REASON_PATTERNS`, `ClickHouseResourceError`, Slack) can silently misclassify when upstream messages change. A new AWS Lambda error code would land in `INTERNAL_ERROR` rather than a typed `LAMBDA_*` bucket until `awsLambdaCodeEvalDispatcher.ts` is updated.
- **Cause-chain cycles**: defended by `visited` sets in `findInCauseChain` and `findOutboundUrlValidationError`, but `unwrapRetryError` and `classifyEvaluatorLlmError` rely on `RetryError.isInstance` which has its own cycle protection. If an SDK wraps its errors with back-references, the classifiers handle it; if a third-party SDK uses `cause` properties that point to non-Error wrappers, the chain walker would silently stop.
- **`ZodError instanceof` is broken across module boundaries**: the public REST middleware relies on `error.constructor.name === "ZodError"` (`web/src/features/public-api/server/withMiddlewares.ts:208-210`), because `zod` may have been bundled twice. This is documented in the comment but is fragile to bundler changes.
- **Free-form string column for `InAppAgentRunErrorCode`**: forward-compatible, but readers must tolerate unknown values, and DB queries that filter on `error_code` need a default-bucket strategy. The comment at `packages/shared/src/features/inAppAgent/types.ts:25-29` calls this out.
- **UnrecoverableError across module boundaries**: the duck-type on `error.name === "UnrecoverableError"` is intentional and documented, but a future error class that happens to set `this.name = "UnrecoverableError"` would be misclassified as terminal. The risk is low because the worker codebase owns the throw site.
- **`OUTCOME_UNKNOWN` is intentionally not retried**: `executeInAppAgentRun.ts:160-167, 611-625` documents that an approved mutation may have started but its result may not have persisted; the next turn must verify, not auto-retry. This is an operational policy encoded in code, not in a config flag.
- **`MEMORY_LIMIT` / `OVERCOMMIT` / `TIMEOUT` discriminators** are matched on substring. The classifiers do not inspect ClickHouse error codes or types; only the message body. A new ClickHouse error string with "timeout" in it would be classified as `TIMEOUT`.
- **Internal `CodeEvalDispatcherErrorCode` values**: `LAMBDA_CONCURRENCY_LIMIT`, `LAMBDA_CONFIGURATION_ERROR`, `LAMBDA_INVOCATION_ERROR` are intentionally collapsed to `INTERNAL_ERROR` for end users (`packages/shared/src/server/evals/codeEvalExecution.ts:33-38, 174-204`), but the underlying code is preserved in traces. A user looking only at `JobExecution.error` will see a generic message; deeper diagnosis requires opening the trace.
- **`backgroundExecutionErrors.ts`'s `BackgroundExecutionConnectionError.retryable`** is a boolean, but no code currently reads it. It exists for forward compatibility; the surrounding code in `backgroundAgentClient.ts` / `backgroundExecutionSession.ts` (referenced by tests) handles reconnect separately.

## Future Considerations

- **Consolidate the wire contract**. Replace the `instanceof` ladder in `toUnstablePublicApiError` (`web/src/features/public-api/server/unstable-public-api-error-contract.ts:160-262`) with a registry on `BaseError` subclasses — each subclass declares its `code` mapping once, and both legacy and unstable contracts read from the same source. This would also let the legacy API expose `code` to clients without breaking the `BaseError.httpCode` semantics.
- **A typed error taxonomy document**. Either a `docs/architecture/error-taxonomy.md` or a typed union aggregator (e.g. `AllLangfuseErrorKinds`) that lists every error type, its source category, its retryable flag, its HTTP code, and its public-API wire code. Useful for new contributors, useful for client SDKs.
- **Version-pinned provider adapters**. Replace substring-matching in `BLOCK_REASON_PATTERNS` and Slack / ClickHouse discriminators with per-provider adapters that declare known error codes once. Drift would be caught at test time rather than silently misclassifying at runtime.
- **A `BlockReason`-shaped span attribute for non-evaluator callers**. `buildEvaluatorLlmErrorSpanAttributes` is evaluator-specific; the same pattern would benefit the chat-completion handler and any future LLM call site that wants APM card per error kind.
- **Add an explicit `Context` error class**. Context overflow currently surfaces as a generic 4xx or a `ClickHouseResourceError(TIMEOUT)`. A first-class `ContextOverflowError` (HTTP 413 or a domain code) would help LLM callers distinguish "your prompt is too long" from "your prompt is malformed".
- **Single source of truth for retryability**. Today `UnrecoverableError`, `CodeEvalDispatcherError.retryable`, `LLMErrorInfo.isRetryable`, and `BackgroundExecutionConnectionError.retryable` are four independent boolean flags. A shared `isRetryable(error: unknown): boolean` would make the dispatch uniform across worker / web / MCP. The pieces exist; they are not unified.
- **Test the Slack `switch` ladder**. `web/src/features/slack/server/router.ts:367-389` is a `switch (slackErrorCode)` with 5 known codes and a default; it has no dedicated unit test asserting behavior on each known code.
- **`evaluator-policy` kind surfaces in APM**. The `kind` of an `EvaluatorLlmErrorClassification` is either an `LLMErrorInfo.kind` or `"evaluator-policy"`. `evalSpanAttributes.ts` already exposes `eval.llm.block.reason` and `eval.llm.block.source`, which captures most of the signal, but the `kind` itself is currently absent from the span attribute set.

## Questions / Gaps

- **No central prose document** describing the full taxonomy (HTTP / LLM / ClickHouse / code-eval / outbound-URL / MCP / Slack / evaluator policy / in-app-agent) and how the layers relate. New contributors must read `web/AGENTS.md`, `.agents/skills/backend-dev-guidelines/references/middleware-guide.md`, and grep for `extends Error` / `extends BaseError` to assemble the picture.
- **`BaseError` does not carry `code`**, only `httpCode`. Two wire contracts (legacy public REST and unstable public API) live on top, with a hand-maintained bridge. A registry-style mapping would remove the `instanceof` ladder.
- **Substring-matching discriminators** are fragile to upstream message drift. There is no per-provider pinned-adapter layer.
- **No documented `Context` error class**. Context overflow surfaces as a generic 4xx or a `ClickHouseResourceError(TIMEOUT)`. A first-class error type would let LLM callers distinguish "prompt too long" from "prompt malformed".
- **Two unrelated "is retryable" booleans** exist (`UnrecoverableError` via name check; `CodeEvalDispatcherError.retryable`; `LLMErrorInfo.isRetryable`; `BackgroundExecutionConnectionError.retryable`). They are not unified.
- **`SlackApiError`'s user-message switch** (`web/src/features/slack/server/router.ts:367-389`) has no dedicated unit test for each `slackErrorCode` branch.
- **`WithMiddlewares` uses both `instanceof` and `error.name` checks** for different error categories — fine in isolation but mixes paradigms in a single file (`web/src/features/public-api/server/withMiddlewares.ts:116-203`).
- **`evaluateLLMAsJudgeEvaluation.test.ts` and `evalService.test.ts` exhaustively cover `UnrecoverableError` paths**, but coverage of `classifyEvaluatorLlmError`'s evaluator-policy branch is harder to find — `classifyEvaluatorLlmError.ts` does not appear to have its own dedicated test file in the surfaced matches.
- **The `kind` of an `EvaluatorLlmErrorClassification` is either one of `LLMErrorInfo.kind` or `"evaluator-policy"**, but `evalSpanAttributes.ts` reads `classification.kind` without documenting the closed set.
