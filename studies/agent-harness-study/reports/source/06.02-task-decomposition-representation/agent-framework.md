## Summary

Agent Framework decomposes work through **two disjoint subsystems** rather than a single hierarchical plan model:

1. **LLM-driven flat todo list** — `TodoProvider` exposes five tools (`todos_add`, `todos_complete`, `todos_remove`, `todos_get_remaining`, `todos_get_all`) that let the model create and update a session-persisted `list[TodoItem]` (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:47-101`, `sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:447-620`). `TodoItem` carries only `id:int`, `title:str`, `description:str|None`, `is_complete:bool` — no type taxonomy, priority, or dependency edges (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:53-60`). State is held as `{"items": [...], "next_id": int}` in `AgentSession.state` or per-session JSON via `TodoFileStore` (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:227-350`).

2. **Developer-authored workflow DAG** — `WorkflowBuilder` + `Executor` + `Edge` compile a Pregel superstep graph. Executors declare typed handlers (`@handler` → `input_types`/`output_types`/`workflow_output_types`) and are wired via `add_edge(source, target, condition?)` (`sources/agent-framework/python/packages/core/agent_framework/_workflows/_workflow_builder.py:228`, `sources/agent-framework/python/packages/core/agent_framework/_workflows/_executor.py:30-120`). `Edge` optionally carries an async predicate (`sources/agent-framework/python/packages/core/agent_framework/_workflows/_edge.py:90-130`), fan-out/in via `FanOutEdgeGroup`/`FanInEdgeGroup`, and switch-case groups. This is the dependency graph — but it is authored statically by the developer, not emitted by the todo decomposition.

`BackgroundAgentsProvider` adds a third, small concurrency primitive: `BackgroundTaskInfo{id, agent_name, description, status: RUNNING|COMPLETED|FAILED|LOST}` (`sources/agent-framework/python/packages/core/agent_framework/_harness/_background_agents.py:30-65`) — again flat, no `depends_on`.

Evaluation of decomposition is via polling predicates (`todos_remaining(provider)` checks `any(not item.is_complete ...)` in `sources/agent-framework/python/packages/core/agent_framework/_harness/_loop.py:520-535`; .NET equivalent `TodoCompletionLoopEvaluator` in `dotnet/src/Microsoft.Agents.AI/Harness/Loop/TodoCompletionLoopEvaluator.cs:1-60`) or `MagenticProgressLedger{is_request_satisfied, is_in_loop, is_progress_being_made, next_speaker, instruction_or_question}` which is an LLM-judged heuristic, not a structural coverage check (`sources/agent-framework/python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:340-400`). Reordering is unsupported for todos; workflow reorder requires rebuilding the graph and checkpoint restore.

In short: todo representation is well-tested and durable, but deliberately flat and typeless; true dependency semantics live only in the workflow graph and are not addressable from the plan layer.

## Rating

**Score: 6 / 10 — Present but inconsistent and fragmented across subsystems.**

Rationale:
- **Strengths:** Explicit `TodoItem`/`TodoStore`/`TodoProvider` schema with strong operational safeguards — `TodoSessionStore` vs `TodoFileStore` with atomic write-then-rename (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:280-310`), `next_id` clamping to `max(id)+1` (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:200-210`), per-session `asyncio.Lock`/`WeakKeyDictionary` serialization of concurrent mutations (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:480-510`), and thorough tests for corruption, atomicity, path-traversal, and concurrent clamping (`sources/agent-framework/python/packages/core/tests/core/test_harness_todo.py:1-200`). Workflow validation is explicit (`WorkflowValidationError`, `validate_workflow_graph` at `sources/agent-framework/python/packages/core/agent_framework/_workflows/_validation.py:1-60`).
- **Deduction — no typed taxonomy:** `TodoItem` has no `type`, `priority`, `kind`, or `estimated_cost`; the framework's guidance is prose in `DEFAULT_TODO_INSTRUCTIONS` telling the model to "break down complex tasks into manageable todo items" (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:22-40`).
- **Deduction — no dependency graph:** `TodoState` is `{"items": list[TodoItem], "next_id": int}` in both Python and .NET (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:320-350`, `dotnet/src/Microsoft.Agents.AI/Harness/Todo/TodoState.cs:12-24`). No `depends_on`, no DAG, no `blocked_by`. The only dependency mechanism is workflow `Edge` conditions, which todo items cannot reference.
- **Deduction — no reorder/evaluate:** Todos support only append/complete/remove; no `reorder`, `reprioritize`, or `move_before`. Evaluation is binary `any(is_complete==False)` (`sources/agent-framework/python/packages/core/agent_framework/_harness/_loop.py:526-532`) or LLM judge (`MagenticProgressLedger`), not a plan-coverage metric.
- **Deduction — subsystem split:** The todo plan and the workflow graph are not linked — completing a todo does not advance an executor, and a blocked executor is not visible as a blocked todo. The answer to "which subtask is blocking?" is "no" for the todo layer; only the workflow runner's pending-message queue and `BackgroundTaskStatus.LOST/FAILED` answer it indirectly.

A score of 7 would require dependency edges on the plan objects themselves; 9-10 would require hierarchical, typed, reorderable decomposition proven under failure. Those are absent.

## Answers to Dimension Questions

**1. How is a task decomposed?**
Two parallel mechanisms. For agent-initiated planning, the LLM creates a flat list of `TodoItem`s via the `todos_add` tool; the model decides titles/descriptions and later marks them done via `todos_complete` with a `reason` (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:506-570`). Instructions in `DEFAULT_TODO_INSTRUCTIONS` explicitly direct the model to "break down complex tasks into manageable todo items" (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:22-40`) — decomposition is imperative and LLM-authored, not framework-generated. For developer-authored work, tasks are decomposed into a `Workflow` DAG of `Executor`s wired by `WorkflowBuilder.add_edge` (`sources/agent-framework/python/packages/core/agent_framework/_workflows/_workflow_builder.py:228`); high-level orchestrators (`SequentialBuilder`, `ConcurrentBuilder`, `GroupChatBuilder`, `MagenticBuilder`, `HandoffBuilder`) compile common patterns to that same engine. The two layers are not linked: todo items do not materialize executors, and executors do not correspond to todo items.

**2. Are subtasks typed?**
Barely. `TodoItem` has no `kind`/`type`/`priority`/`effort` fields — only `title`, `description`, `is_complete` (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:53-60`). The .NET mirror is identical (`dotnet/src/Microsoft.Agents.AI/Harness/Todo/TodoItem.cs:12-26`). Subtask typing exists one level down: `Executor` handlers are typed by `input_types`/`output_types`/`workflow_output_types` inferred from `@handler` signatures (`sources/agent-framework/python/packages/core/agent_framework/_workflows/_executor.py:30-80`), and `BackgroundTaskInfo` carries `agent_name` as a loose type proxy (`sources/agent-framework/python/packages/core/agent_framework/_harness/_background_agents.py:35-50`). But the plan-level todo taxonomy is free-form strings; callers cannot filter "all research tasks" vs "all code tasks" without parsing titles.

**3. Can dependencies be represented?**
Not in the plan layer. `TodoState` is `List[TodoItem]` + `nextId` with no `depends_on`/`blocked_by`/`after` edges (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:320-350`, `dotnet/src/Microsoft.Agents.AI/Harness/Todo/TodoState.cs:12-24`). There is no priority queue, no topological sort, and no "blocked subtask" derivation. Dependencies *can* be represented in the workflow layer via `Edge` with optional `condition` predicates, fan-out/in, and switch-case (`sources/agent-framework/python/packages/core/agent_framework/_workflows/_edge.py:80-160`), and orchestrators encode sequential vs concurrent precedence, but these are developer-declared graph edges, not plan subtask dependencies that the agent can author or a scheduler can reason over.

**4. Are statuses tracked?**
Partially — binary for todos, richer for runtime. `TodoItem.is_complete` is a boolean open/done signal (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:53`), and `todos_get_remaining`/`todos_get_all` return JSON arrays with that flag (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:580-610`). There is no `in_progress`, `blocked`, or `waiting_on` state. `BackgroundTaskInfo` does have a four-state enum (`RUNNING|COMPLETED|FAILED|LOST` at `sources/agent-framework/python/packages/core/agent_framework/_harness/_background_agents.py:28-35`) and workflow execution emits `executor_invoked/completed/failed` and `WorkflowRunState` transitions (`sources/agent-framework/python/packages/core/agent_framework/_workflows/_events.py:120-170`). The todo layer's `todos_remaining` predicate (`sources/agent-framework/python/packages/core/agent_framework/_harness/_loop.py:526-532`) only distinguishes "any open" vs "all done" and cannot answer "which todo is blocking?"

**5. Can decomposition be evaluated?**
Structurally, no; heuristically, yes via two helpers. Structural evaluation would require a typed, dependent plan with coverage checks — absent. What exists: (a) `AgentLoopMiddleware` with `todos_remaining(provider)` re-invokes the agent while `any(not is_complete)` holds, optionally bounded by `max_iterations=10` (`sources/agent-framework/python/packages/core/agent_framework/_harness/_loop.py:520-560`; .NET `TodoCompletionLoopEvaluator`), and (b) Magentic's `MagenticProgressLedger` yields LLM-authored booleans `is_request_satisfied`, `is_in_loop`, `is_progress_being_made` plus `next_speaker`/`instruction_or_question` (`sources/agent-framework/python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:340-400`) and `JudgeVerdict{answered, reasoning}` (`sources/agent-framework/python/packages/core/agent_framework/_harness/_loop.py:90-120`) for outer-loop judging. These are polling/judge heuristics, not plan-completeness verifiers; no API answers "is every required subtask covered?" or "is the decomposition minimal/complete?"

## Architectural Decisions

| Decision | Why it was made (inferred) | Consequence for this dimension |
|----------|-----------------------------|--------------------------------|
| **Flat todo list over hierarchical plan** (`TodoItem` + `next_id` only) | Keep LLM tool surface minimal and session-portable; avoid a complex plan DSL the model must learn (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:22-40`). | Enables any decomposition the model invents, but sacrifices dependency tracking, reordering, and blocking analysis. |
| **Dual-store strategy — session vs file** (`TodoSessionStore` + `TodoFileStore` with atomic rename and `WeakKeyDictionary` locks) | Support single-process ephemeral agents and multi-process / restart scenarios without mandating an external DB (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:280-350`). | Durability and concurrency are strong, yet the schema stays flat in both stores — persistence does not add structure. |
| **Separate workflow DAG from todo plan** (`WorkflowBuilder`/`Edge`/`Executor` vs `TodoProvider`) | Let developers compile deterministic graphs while letting the model author flexible plans; reuse the Pregel runner for both (`sources/agent-framework/python/packages/core/agent_framework/_workflows/_workflow_builder.py:53-80`). | Dependencies live only in the workflow layer; there is no bridge that turns todo items into executors or vice versa, so blocking cannot propagate across layers. |
| **Prose instructions over typed subtask taxonomy** (`DEFAULT_TODO_INSTRUCTIONS` bullet guide) | Avoid hardcoding categories that would constrain domain tasks; rely on the model's language understanding. | No machine-readable `type` to route subtasks to tools or agents; downstream evaluation/routing must parse free-form titles. |
| **`reason` required on `todos_complete`** (`TodoCompleteInput{id, reason}`) | Force the model to justify completion for auditability (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:140-170`). | The reason is not persisted to `TodoItem` (the stored item only flips `is_complete=True` at `sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:546-560`), so the justification is lost after the tool call. |
| **Experimental feature gating** (`@experimental(feature_id=ExperimentalFeature.HARNESS)` on `TodoProvider`/`AgentLoopMiddleware`) | Isolate harness surface for iteration without semver commitment. | Decomposition APIs may change; adopters should treat todo/loop contracts as unstable. |

## Notable Patterns

- **Tool-per-operation on a single flat collection** — five narrow tools over one `list[TodoItem]` with per-session serialized RMW (`todos_add` returns created items, `todos_complete`/`todos_remove` return counts) — easy to teach the model, easy to test (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:506-610`).
- **Session-state as the source of truth** — both Python (`AgentSession.state[source_id]`) and .NET (`ProviderSessionState<TodoState>` + `StateKeys`) treat the session bag as the durable log; file store is an optional physical projection with source-id namespace isolation (`todos.{source_id}.json`).
- **Clamped monotonic IDs with GC'd locks** — `_safe_next_id` (`max(existing_ids)+1`) prevents collisions after restore; `WeakKeyDictionary`/`ConditionalWeakTable` ensures per-session locks do not leak across GC in long-running services (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:190-210`, `dotnet/src/Microsoft.Agents.AI/Harness/Todo/TodoProvider.cs:90-110`).
- **Orchestrator builders compile to one runner** — `Sequential`, `Concurrent`, `GroupChat`, `Magentic`, `Handoff` all lower to `Executor` + `Edge` + `Runner` rather than owning separate schedulers, keeping the dependency model uniform at the workflow level.
- **Ledger-as-messages pattern (Magentic)** — `_MagenticTaskLedger{facts, plan}` and `MagenticProgressLedger` are stored as `Message` payloads serialized via `_message_to_payload`/`_message_from_payload`, not as typed plan objects that other subsystems can query (`sources/agent-framework/python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:220-320`).

## Tradeoffs

| Tradeoff | Pro | Con |
|----------|-----|-----|
| Flat todo list | Minimal schema; any LLM can author titles without learning a plan DSL; trivial session/file persistence. | No `depends_on`, no `priority`, no `blocked` — the system cannot derive critical path, cannot reorder, cannot answer "which todo blocks progress?" |
| `reason` on complete but not persisted | Encourages the model to justify work during the tool call. | Audit trail is transient — after `todos_complete`, `TodoItem` retains only `is_complete=True`, so post-hoc review cannot see *how* a subtask was resolved. |
| Prose instructions vs typed `type` | Domain-agnostic; no taxonomy to maintain. | No routing: the harness cannot auto-assign a "research" todo to a search agent or a "code" todo to a code agent without title parsing. |
| Workflow DAG owns dependencies, todo list does not | Clear separation: deterministic edges for developers, free-form todos for the model. | Fragmentation — the two decompositions are not composable; completing a todo never advances a workflow executor and waiting on an executor never updates a todo. |
| Five fine-grained todo tools | Explicit and testable; batch add/complete/remove reduce round-trips. | No batch upsert or reorder; moving a todo earlier/later requires `remove` + `add`, which loses its `id` and history. |
| Magentic ledger as LLM-judged heuristics | Lightweight evaluation without a formal plan verifier. | `is_request_satisfied`/`is_in_loop` are probabilistic text judgments, not structural guarantees; false positives/negatives under failure. |

## Failure Modes / Edge Cases

- **Lost reason / no completion audit** — `todos_complete` accepts `{id, reason}` but reconstructs items as `TodoItem(id, title, description, is_complete=True)` without storing `reason` (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:536-560`). After the call, the justification is not recoverable from state — important for compliance/replay.
- **No blocked detection → silent stall** — with no dependency edges, two todos like "write tests" and "ship feature (needs tests)" have no machine relation; `todos_remaining` returns `True` (something is open) but cannot surface which todo is blocked. The outer `AgentLoopMiddleware` keeps re-invoking with `DEFAULT_NEXT_MESSAGE="Continue working on the task"` (`sources/agent-framework/python/packages/core/agent_framework/_harness/_loop.py:40`) rather than targeting the blocker.
- **Flat IDs, no stable reordering** — `next_id` is monotonic and clamped, but there is no `order` field; reordering requires `todos_remove` + `todos_add`, which mints new IDs and breaks external references. Check `TodoState.NextId` and the lack of any position field in both stacks (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:320-350`, `dotnet/src/Microsoft.Agents.AI/Harness/Todo/TodoState.cs:12-24`).
- **Concurrent mutation serialization is correct but opaque** — the per-session lock prevents duplicate IDs / lost updates (tested via `asyncio.gather(add, add, complete)` in `sources/agent-framework/python/packages/core/tests/core/test_harness_todo.py:250-340`), but callers get no conflict signal — concurrent `todos_complete` calls silently report `{"completed": N}` with `N` clobbering duplicates, not a transactional error.
- **Orphaned background tasks → LOST** — `BackgroundAgentsProvider` runtime holds non-serializable `asyncio.Task` objects keyed by session; if the provider instance is lost or the process restarts, `_refresh_task_state` marks `RUNNING` tasks as `LOST` (`sources/agent-framework/python/packages/core/agent_framework/_harness/_background_agents.py:180-220`). There is no checkpoint to resume them, unlike `WorkflowCheckpoint`.
- **Magentic loop can repeat** — `MagenticProgressLedger.is_in_loop` and the outer `LoopAgent` rely on LLM self-diagnosis of loops (`sources/agent-framework/python/packages/orchestrations/agent_framework_orchestrations/_magentic.py:340-380`); under stuck or adversarial model output, the loop may cycle until `max_iterations` rather than repairing the plan.
- **No plan validation** — `validate_workflow_graph` checks workflow edges/types (`sources/agent-framework/python/packages/core/agent_framework/_workflows/_validation.py:1-60`), but there is no `validate_plan` for todos — empty title trimmed check is the only plan-level guard (`sources/agent-framework/python/packages/core/agent_framework/_harness/_todo.py:58-75`). A model can submit duplicate or contradictory todos and the harness accepts them.
- **HITL request leakage** — `SequentialBuilder.with_request_info` and `AgentApprovalExecutor` pause the workflow for human guidance, but todo state is not automatically reconciled with `request_info` pauses, so a human amendment must be manually reflected in both the conversation and the todo list.
