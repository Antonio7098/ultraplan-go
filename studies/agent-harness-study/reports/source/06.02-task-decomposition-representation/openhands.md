## Summary

OpenHands decomposes work through **three disjoint, LLM-authored mechanisms** with no unified plan object or dependency graph:

1. **Flat `TaskItem` list via `task_tracker`** — `TaskTrackerAction{command="plan", task_list: list[TaskItem{title, notes, status: todo|in_progress|done}}` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:32-52`) persisted as `TASKS.json` in `conv_state.persistence_dir` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:238-263`). `TaskTrackerExecutor` holds `._task_list: list[TaskItem]` in memory, `view`/`plan` are the only mutations (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:148-210`). Guidance is prose in `TASK_TRACKER_DESCRIPTION` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:270-400`) — decomposition is model-owned, not framework-generated.

2. **Markdown `PLAN.md` via `PlanningFileEditor`** — when `AgentType.PLAN` is active, `get_planning_tools(plan_path)` exposes `Glob + Grep + PlanningFileEditor` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/preset/planning.py:105-133`) gated by `PlanningFileEditorExecutor(allowed_edits_files=[plan_path])` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/planning_file_editor/impl.py:28-30`). Plan path is `{working_dir}/.agents_tmp/PLAN.md` (or `agents-tmp-config` for GitLab/Azure — `studies/agent-harness-study/sources/openhands/openhands/app_server/app_conversation/live_status_app_conversation_service.py:1140-1160`) initialized from `PLAN_STRUCTURE` 5-tuple headers (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/preset/planning.py:14-88`). Steps are markdown prose with `goal/method/reference` bullet guidance, not typed objects.

3. **Delegated sub-agents via `TaskTool/TaskManager`** — `TaskAction{description, prompt, subagent_type, resume}` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/definition.py:37-62`) → `TaskManager.start_task()` → `Task{id, conversation_id, status: running|completed|error, result, error}` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:48-90`) running a blocking `LocalConversation` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:319-342`). Parallel execution is not decomposed; tasks are independent conversations whose `subagents` dir is `{persistence_dir}/subagents` or temp (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:45`).

None of these carry `depends_on`, `priority`, `blocked_by`, or DAG edges. Reorder is whole-list replacement or markdown `str_replace`. Evaluation is `is_error` flag or LLM prose, not structural coverage.

## Rating

**Score: 4 / 10 — Present but inconsistent, weakly documented, and fragile.**

Rationale:
- **Present:** Explicit schemas `TaskItem`/`TaskTrackerAction`/`TaskTrackerObservation` with Pydantic validation, three-state `TaskTrackerStatusType` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:29-39`), persisted `TASKS.json` with load/save guards (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:233-266`), and distinct `Task` with `TaskStatus` enum for sub-agents (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:48-60`). `PLAN_STRUCTURE` is typed `list[tuple[str,str]]` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/preset/planning.py:14`) and `get_plan_headers()` seeds every `PLAN.md` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/preset/planning.py:78-88`).
- **Deduction — no typed taxonomy beyond free-form title/notes:** `TaskItem` has no `type`, `kind`, `priority`, `effort`, or `owner`; `PLAN.md` steps are bullet prose with optional `reference` string (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/preset/planning.py:38-45`). Caller cannot filter “research” vs “code” subtasks without parsing titles.
- **Deduction — no dependency graph:** Neither `TaskItem` nor `Task` has `depends_on`/`blocked_by` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:32-39`, `studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:61-77`). `TaskManager._tasks: dict[str,Task]` is flat with `threading.Lock` but no topological sort or DAG (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:102-104`).
- **Deduction — no reorder or partial update:** `task_tracker` only supports `command="view"|"plan"` with full-list replacement (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:45-52`, `studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:174-176`); reordering requires re-sending the entire array. `PLAN.md` edits are `str_replace` via `FileEditorAction` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/planning_file_editor/impl.py:46-55`).
- **Deduction — no blocking signal:** The three statuses collapse to boolean `done` vs not-done; there is no `blocked`/`waiting_on`. System cannot answer “which subtask is blocking progress?” — `TaskTrackerObservation.visualize` only counts `todo/in_progress/done` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:94-99`).
- A score of 6–7 would require explicit dependency edges, typed subtask taxonomy, and observable blocking evaluation; those are absent.

## Answers to Dimension Questions

**1. How is a task decomposed?**
Three parallel LLM-authored mechanisms, no framework-enforced decomposition. **In default mode**, the model may call `task_tracker` with `command="plan"` and supply `task_list: list[TaskItem>` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:45-52`); `TaskTrackerExecutor` replaces the whole list (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:174-176`) and persists to `TASKS.json` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:252-263`). Decomposition granularity is dictated by `TASK_TRACKER_DESCRIPTION` prose examples like “Design API → Implement controllers → Add validation → Test” (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:309-345`). **In planning mode**, decomposition is a markdown document: `PlanningFileEditor` is given `plan_path` and writes `PLAN.md` sections under `IMPLEMENTATION STEPS` where each bullet should contain `goal/method/reference` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/preset/planning.py:38-45`), seeded by `get_plan_headers()` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/preset/planning.py:78-88`). **For delegation**, the parent calls `TaskAction(prompt, subagent_type)` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/definition.py:37-62`) which `TaskManager._create_task` turns into a fresh `LocalConversation` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:218-262`); tasks are independent sub-conversations, not subtasks of a parent plan. No component generates the decomposition — the LLM decides titles, notes, and plan bullets.

**2. Are subtasks typed?**
Minimally. `TaskItem.status` is typed as `Literal["todo","in_progress","done"]` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:29-39`); `Task.Status` is `StrEnum{running, completed, error}` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:48-58`). Beyond status, subtasks are untyped: `TaskItem` has only `title: str` and `notes: str` as free-form prose (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:32-39`); `PLAN.md` steps have no `kind`/`type`/`effort`/`owner` field — typing is implicit in `notes` or bullet text. `TaskAction.subagent_type` (`general-purpose`, `code-explorer`, etc.) acts as a loose type hint routing to `get_agent_factory(subagent_type)` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:229-298`), but that types the *executor*, not the subtask itself. There is no taxonomy to query “all research subtasks” vs “all code subtasks” without parsing strings.

**3. Can dependencies be represented?**
No. Neither `TaskItem` nor `Task` exposes `depends_on`, `blocked_by`, `after`, or DAG edges. `TaskItem` is flat with `title/notes/status` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:32-39`); `TaskManager._tasks: dict[str, Task]` stores tasks as an unordered dict protected by `threading.Lock` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:102-103`) with `task_id = f"task_{len+1:08x}"` monotonic but not order-significant (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:130-135`). `PLAN.md` IMPLEMENTATION STEPS are enumerated `1. OBJECTIVE … 4. IMPLEMENTATION STEPS` headers but ordering is prose sequence, not an edge graph (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/preset/planning.py:14-45`). Sub-agents via `TaskTool` are launched sequentially via blocking `TaskExecutor.__call__` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/impl.py:26-66`) and cannot declare “run after task_00000002”. The system therefore cannot derive critical path or blocked set.

**4. Are statuses tracked?**
Binary to ternary, without blocking semantics. `TaskItem` tracks `todo → in_progress → done` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:35-39`); `TaskTrackerObservation.visualize` renders counts `todo/in_progress/done` and icons `⏳/🔄/✅` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:94-132`). `Task` for sub-agents tracks `running → completed|error` plus free-form `result`/`error` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:48-90`); parent metrics are synced as `usage_to_metrics[f"task:{task.id}"]` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:381-389`). Neither tracks `blocked`, `waiting_on`, or `priority`. Completion is `TaskTrackerAction.task_list` containing only `status=="done"` items or `Task.status==COMPLETED`; `is_error` signals failure (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:89-91`, `studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:85-90`). Because there is no `blocked` state or `depends_on`, the answer to “which subtask is currently blocking progress?” is always “no direct signal — scan `in_progress` and `todo` manually and infer”.

**5. Can decomposition be evaluated?**
Not structurally; only via prose polling. No validator checks that `TaskItem` titles cover the requirement, that `PLAN.md` headers are non-empty, or that every step has a `reference`. `_load_tasks` only validates Pydantic shape (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:242-250`); `_save_tasks` is unconditional JSON dump (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:252-266`). Evaluation is heuristic: `TASK_TRACKER_DESCRIPTION` instructs the model to “Mark tasks as done only when fully achieved … Keep status as in_progress if errors persist … Create new tasks for discovered issues” (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:370-398`) but enforcement is by the LLM reading the list via `command="view"` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:187-200`). The Build handoff is a string `Execute the plan based on the .agents_tmp/PLAN.md file.` (`studies/agent-harness-study/sources/openhands/frontend/src/hooks/use-handle-build-plan-click.ts:27`) with no coverage check — an empty `PLAN.md` (only headers from `get_plan_headers`) still executes vacuous. No `validate_plan`, `plan_score`, or dependency-blocked metric exists.

## Architectural Decisions

| Decision | Why it was made (inferred) | Consequence for this dimension |
|----------|-----------------------------|--------------------------------|
| **Flat `TaskItem` list over hierarchical/typed plan** (`TaskItem{title,notes,status}` at `studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:32-39`) | Keep LLM tool surface minimal; free-form titles let any domain task be expressed without a plan DSL to learn. | Enables arbitrary decomposition but sacrifices dependency, priority, and blocking observability; system cannot reorder or reason over critical path. |
| **Whole-list replacement on `plan`** (`_task_list = action.task_list` at `studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:176`) | Simplifies persistence to one JSON file and avoids partial-update merge conflicts. | `TASKS.json` is durable, but reordering or patching one subtask requires re-sending the entire array, losing granularity and increasing token cost. |
| **Markdown `PLAN.md` as planning artifact** (`PLAN_STRUCTURE` + `get_plan_headers` at `studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/preset/planning.py:14-88`) | Human-readable, zero-migration, renders nicely in `PlanPreview`; reuses `FileEditorTool` lineage. | Unvalidated prose — steps are not machine-queryable; Build is a natural-language prompt (`frontend/src/hooks/use-handle-build-plan-click.ts:27`), not a typed `ExecutePlan(plan_id)` call. |
| **Read-all / edit-only-`PLAN.md` gate** (`PlanningFileEditorExecutor(allowed_edits_files=[plan_path])` at `studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/planning_file_editor/impl.py:28-30`) | Prevent planning agent from mutating code while permitting broad codebase exploration via `Glob/Grep`. | Strong tool-level sandbox for planners, but boundary is not a filesystem ACL and `TerminalTool` is excluded, limiting planner tooling. |
| **Separate `TaskManager` sub-agent graph from `TaskTracker`** (`Task{status,conversation}` at `studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:61-77` vs `TaskItem`) | Let parent delegate blocking work to specialized agents (e.g., `code-explorer`) while keeping `task_tracker` as lightweight TODO list. | Fragmentation — `TaskItem` TODOs do not materialize `Task` sub-agents and vice versa; blocking cannot propagate across layers. |
| **Consistent `subagents` dir: temp vs `{persistence_dir}/subagents`** (`_SUBAGENTS_DIR="subagents"` at `studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:45`, `_ensure_parent` at line 109-119) | Keep parent self-contained when `persistence_dir` exists; otherwise use ephemeral `tempfile.mkdtemp(prefix="openhands_tasks_")`. | Persistence is bifurcated; `TaskManager.close()` only cleans temp dirs (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:391-407`), so non-persistent parents leak on crash. |

## Notable Patterns

- **Tool-per-operation on a single flat collection** — two commands `view`/`plan` over `list[TaskItem]` with immediate `TASKS.json` fsync (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:168-210`); `plan` returns count, `view` returns formatted `# Task List` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:212-231`).
- **Session persistence via `persistence_dir` injection** — `TaskTrackerTool.create(conv_state)->TaskTrackerExecutor(save_dir=conv_state.persistence_dir)` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:407-415`) and `TaskManager._ensure_parent` grouping under `{persistence_dir}/subagents` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:109-119`).
- **Prose-driven decomposition guidance** — `TASK_TRACKER_DESCRIPTION` enumerates 7 “use this tool” situations and 3 workflow phases with scenario breakdowns (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:270-400`); model quality depends on following prose, not schema enforcement.
- **Preset factory pattern** — `get_planning_tools(plan_path)`/`get_planning_condenser(llm)`/`get_planning_agent(llm)` mirror `get_default_tools`/`get_default_condenser` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/preset/planning.py:105-179` vs `studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/preset/default.py:36-96`) — pure functions returning `list[Tool]`/`Agent`.
- **Sub-agent visualizer inheritance** — `LocalConversation` for each `Task` inherits parent `_visualizer.create_sub_visualizer(label)` (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task/manager.py:272-289`) so the UI can nest delegated work, even though task_tracker cannot reference it.

## Tradeoffs

| Tradeoff | Pro | Con |
|----------|-----|-----|
| Flat TODO list with free-form titles | Minimal schema; any LLM can author; trivial JSON persistence (`TASKS.json` at `studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:238-263`) | No `depends_on`/`priority`/`blocked` — cannot derive blocker, cannot reorder without full resend, cannot filter by type |
| Whole-list `plan` vs patch | Simple conflict-free save; `load_tasks` rehydrates atomically with validation (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/task_tracker/definition.py:242-250`) | High token overhead; concurrent `view`→`plan` races can silently clobber; no `todonumber` ordering or `depends_on` |
| Markdown `PLAN.md` vs typed `Plan` object | Zero schema migration; immediate `PlanPreview` rendering; backward-compatible legacy `workspace/PLAN.md` fallback (`studies/agent-harness-study/sources/openhands/_sdk_inspect/tools/planning_file_editor/definition.py:98-113`) | Unqueryable for automation; executor must re-parse prose; two non-interoperating plan surfaces (`TASKS.json` vs `PLAN.md`) |
