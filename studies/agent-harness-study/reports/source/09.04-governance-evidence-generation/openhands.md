## Summary

`openhands` is the agent-canvas frontend. It does not own durable governance state — conversations, event history, and automation runs are persisted by the Python agent-server (`OpenHands/software-agent-sdk`) and the automation backend, which are out of scope for this repo. The frontend's contribution to governance evidence is limited to **read-and-export views** over remote state: (1) paginated conversation-event browsing (`EventService.searchEvents` → `RemoteEventsList` / cloud proxy) materialized in `useEventStore`; (2) per-automation run activity-log export to machine-readable JSON/CSV; (3) raw trajectory download (`ConversationService.getTrajectory` / `FileClient.downloadTrajectory`); and (4) consent-gated PostHog telemetry. There is no first-class compliance report, no policy-decision record, no approval workflow with timestamps, no SIEM exporter, and no retention policy for exported evidence. The only retention enforcement in-repo is a 7-day rotation for dev-script log files. An integration guide (`docs/DefenseClaw.md`) describes how an external security governance layer (DefenseClaw) *could* supply a SQLite audit store, OTLP/Splunk forwarding, and guardrail verdicts, but the document explicitly marks that integration as not implemented and lists it under Future Work requiring code changes.

## Rating

**4 / 10 — Present but inconsistent, weakly documented, and fragile.** The system can emit isolated, machine-readable slices of evidence (activity-log CSV/JSON, trajectory JSON, conversation events) with typed schemas and unit tests, but it cannot assemble a single reproducible compliance report for a run that binds what happened, what was checked, approval decisions, and tool execution results. Policy decisions and approval timestamps are absent; SIEM integration is documented-only; retention is ad-hoc and not enforced for governance artifacts.

## Answers to Dimension Questions

### 1. What evidence does the system produce?
The frontend itself produces **no durable evidence** — it renders and exports evidence that lives on the agent-server and automation backend:
- **Automation activity log**: per-automation paginated run history rendered in `ActivityLogSection` (`src/components/features/automations/detail/activity-log-section.tsx:29-46`) and exportable as a full dump via `fetchAllActivityLogExportRows` → `downloadActivityLogExport` (`src/utils/automation-activity-log-export.ts:113-170`). Each row captures `run_id`, `automation_id/name`, `trigger` (full JSON), `start_time`/`end_time`/`duration_seconds`, `status` (`PENDING|RUNNING|COMPLETED|FAILED|CANCELLED|SKIPPED` per `src/types/automation.ts:66-73`), `conversation_id` + deep link `conversation_url`, `error` (`error_detail`), and `cost` (USD, `src/types/automation.ts:89-95`). The exporter is unit-tested for pagination and CSV escaping (`__tests__/utils/automation-activity-log-export.test.ts:131-215`).
- **Conversation/tool execution trace**: raw `OpenHandsEvent` pages via `EventService.searchEvents` (`src/api/event-service/event-service.api.ts:102-181`) and `ConversationService.getTrajectory` (`src/api/conversation-service/conversation-service.api.ts:54-63`, cloud/local download in `src/api/conversation-service/agent-server-conversation-service.api.ts:673-681`). The store (`src/stores/use-event-store.ts:54-75`) keeps `events`, `uiEvents`, dedup set, and `loadedConversationId`. This is the tool-execution log surface, but it is a pass-through to the agent-server — the frontend stores it only in memory.
- **Telemetry events**: typed PostHog captures (`src/hooks/use-tracking.ts:48-81`, `src/services/telemetry.ts:809-817`) for product analytics (conversation creation, mcp config, download trajectory click, activity-log export). Not governance evidence.
- **Dev operational logs**: `scripts/logger.mjs:62-69` daily-rotated `agent-canvas.YYYY-MM-DD.log` (level debug, timestamped) — developer tooling, not run evidence.
- **Aspirational external evidence**: `docs/DefenseClaw.md:211-242` describes DefenseClaw's SQLite audit store and alerting, but the frontend creates none of it natively.
Missing entirely: policy decisions/justifications, approval records with approver identity and timestamp, signed compliance bundle, correlation IDs tying a policy verdict to a specific tool execution.

### 2. Is evidence machine-readable?
**Partially — the only intentionally machine-readable exports are the automation activity log.** `serializeActivityLogRowsCsv` (`src/utils/automation-activity-log-export.ts:48-64`) emits RFC-4180 CSV with a fixed column order (`CSV_COLUMNS`, `src/utils/automation-activity-log-export.ts:12-27`) plus JSON export `{runs: rows, total}` with pretty-print (`src/utils/automation-activity-log-export.ts:154-158`). Tests assert header presence, cost numeric fidelity, and escaping (`__tests__/utils/automation-activity-log-export.test.ts:104-129`). Conversation trajectory is also machine-readable JSON via `getTrajectory` (limit 10000), and `EventService.searchEvents` returns typed `EventSearchPage<OpenHandsEvent>` — but both are ad-hoc API snapshots, not a versioned evidence schema with signing or SIEM field mapping. Telemetry is machine-readable PostHog JSON but requires consent and is not governance-normalized. No code maps evidence to a SIEM common information model (CEF, OCSF, ECS) or emits OTLP/Splunk payloads; the OTLP/Splunk table in `docs/DefenseClaw.md:227-230` is CLI configuration for an external binary, with zero TypeScript integration.

### 3. Can evidence be reproduced?
**Weakly, with caveats.** The activity-log export re-pages `listAutomationRuns` deterministically until `offset >= total` (`src/utils/automation-activity-log-export.ts:121-135`) and the trajectory re-fetches all events at `limit:10000`. Re-running the export should return the same rows if the backend is immutable — but the frontend adds no reproducibility guarantees: no content hash, no export timestamp attestation, no signed manifest, no stable sort contract beyond the backend's `sort_order`/`timestampLt` params (which have a documented cloud fallback that returns empty on unsupported servers, `src/api/event-service/event-service.api.ts:149-162`). Event history itself is mutable in the sense that the agent-server is the source of truth and the frontend's store is ephemeral and cleared on conversation switch (`clearEventsForConversation`, `src/stores/use-event-store.ts:216-222`). There is no replay bundle that captures the policy inputs, tool allow-list (`usable_tools` is cached at conversation creation via `agent-server-adapter.ts` but never emitted in the export), or model/temperature that produced the run. `DefenseClaw.md:274-282` proposes `on_conversation_end` hooks and webhook audit bridges to make per-session evidence reproducible, but marks them as not implemented.

### 4. Are evidence retention policies enforced?
**No, except for dev log files and CI artifacts, which are not governance evidence.**
- The only enforced retention in-repo is `maxFiles: "7d"` for the dev script rotating log (`scripts/logger.mjs:66`) plus its audit file `.log-audit.json` (`scripts/logger.mjs:67`), and GitHub Actions artifact `retention-days` (`1` day for docker, `14` for desktop E2E in `.github/workflows/docker.yml:247`, `.github/workflows/desktop-macos.yml:84`).
- There is no retention policy for automation run exports (downloaded blobs), trajectory downloads, `useEventStore` contents, or `AutomationRun` history. Gaps flagged by grep for `retention|ttl|expire|purge` return only the above. The automation backend's own retention (if any) lives outside this frontend repo (`OpenHands/software-agent-sdk`) and is not referenced in `src/`. The frontend does not enforce immutability, WORM storage, legal hold, or purge schedules, nor does it surface a retention configuration UI.

## Architectural Decisions

- **Frontend-only repository boundary** — This repo is explicitly the React canvas that *consumes* agent-server APIs via `@openhands/typescript-client` (per `AGENTS.md`). That explains why governance persistence, policy evaluation, and retention are absent: the architectural decision is to own none of them. Evidence is therefore a projected view, not a ledger. Files `src/api/event-service/event-service.api.ts:1-10`, `src/api/conversation-service/agent-server-conversation-service.api.ts:7-13`, and `AGENTS.md` make this boundary explicit.
- **Cloud/local branching at the service layer** — `EventService.searchEvents` (`src/api/event-service/event-service.api.ts:111-164`) and `AgentServerConversationService` (`src/api/conversation-service/agent-server-conversation-service.api.ts:362-398`) branch on `getActiveBackend().backend.kind`. For governance evidence this means two distinct retrieval paths with different pagination limits (cloud caps at 100) and a defensive fallback when the cloud lacks filter support — a fragility that leaks into evidence completeness.
- **Export is client-assembled, not server-rendered** — `downloadActivityLogExport` pages the runs list and builds CSV/JSON locally (`src/utils/automation-activity-log-export.ts:113-170`) rather than calling a server-side "export report" endpoint. Decision favors frontend flexibility over a single authoritative server artifact, at the cost of no server-side signing or retention of the report itself.
- **DefenseClaw as external governance** — Rather than building native policy/approval/audit, the docs delegate to DefenseClaw (`docs/DefenseClaw.md:3-6`) via sidecar proxy and SQLite store. This keeps the frontend lean but means governance evidence maturity depends on an optional, separately deployed system that currently has no code hooks in the frontend (`Future Work: Code-Level Extensions`, `docs/DefenseClaw.md:246-282`).
- **Telemetry isolation from governance** — `telemetry.ts` owns a named PostHog instance (`agent-canvas`, `src/services/telemetry.ts:53-54`) with `before_send` immutable attribution (`src/services/telemetry.ts:133-146`) and `opt_out_capturing_by_default` (`src/services/telemetry.ts:350`). Decision cleanly separates product analytics from governance evidence rather than co-opting analytics as an audit log.

## Notable Patterns

- **Typed export row as audit schema** — `AutomationRunExportRow` (`src/types/automation.ts:108-126`) is the closest thing to an evidence schema: it normalizes optional `cost` to nullable, computes `duration_seconds`, and carries the full `trigger` JSON so consumers can reconstruct why a run fired.
- **Immutable attribution in telemetry** — `CANVAS_EVENT_PROPERTIES` (`src/services/telemetry.ts:110-115`) frozen and injected in `before_send` so producer code cannot override `client_source/version` — a governance-friendly pattern applied only to analytics, not to automation evidence.
- **Dedup + timestamp-sort in event store** — `useEventStore` uses `eventIds: Set<string|number>` for O(1) dedup and `compareEventsByTimestamp` for ISO lexicographic sort (`src/stores/use-event-store.ts:24-35`), ensuring tool-execution ordering is reproducible on re-fetch — but without vector clocks or sequence numbers, late-arriving events can be reordered silently.
- **Cloud pagination fallback as graceful degradation** — `EventService.searchEvents` returns `{items: [], next_page_id: null}` with a console warning when the cloud lacks filter support (`src/api/event-service/event-service.api.ts:157-162`) instead of looping on stale most-recent pages — prevents evidence inflation at the cost of truncation.
- **Export tracking as meta-evidence** — `trackAutomationActivityLogExported` (`src/hooks/use-tracking.ts:329-340`) records that an export occurred (with `backend_kind` and `format`) but not the export's content hash or recipient — meta-evidence without provenance.

## Tradeoffs

- **Rich exports vs. no compliance envelope** — CSV/JSON exports are well-typed and unit-tested (`__tests__/utils/automation-activity-log-export.test.ts:63-216`), but there is no signed bundle that ties together the activity row, the trajectory, `usable_tools`/`agent_settings`, and policy inputs for a given run. Consumers must stitch evidence manually.
- **Client-side pagination vs. server-side report** — Paging in the browser avoids a dedicated backend report endpoint and works offline against mocks, but increases fragility (network retries, offset drift if `total` changes mid-export) and provides no server-retained artifact to reference in a later audit.
- **7-day dev log rotation is operational, not governance** — `maxFiles: "7d"` (`scripts/logger.mjs:66`) bounds disk usage for developer workflows; it is too short and too narrow (only `agent-canvas.*.log` under `<stateDir>/logs`) to serve as a governance retention policy, yet it is the only retention the frontend enforces.
- **Delegation to DefenseClaw** — Outsourcing scan results, guardrail decisions, and audit store to DefenseClaw gives a clear path to SIEM (OTLP, Splunk HEC per `docs/DefenseClaw.md:227-230`) without bloating the frontend; however, because the integration requires no code changes, the frontend has zero guarantees that evidence is actually being collected when DefenseClaw is absent.
- **Cloud vs. local evidence divergence** — Cloud caps `limit` at 100 and may silently truncate older pages (`src/api/event-service/event-service.api.ts:120-162`), while local can fetch 10000 at once (`src/api/conversation-service/conversation-service.api.ts:60`). An auditor comparing exports from different backends sees different completeness.

## Failure Modes / Edge Cases

- **Incomplete evidence on cloud pagination fallback** — When `hasFilterParams` is true and the cloud proxy throws, `EventService.searchEvents` warns and returns empty (`src/api/event-service/event-service.api.ts:149-162`), causing `useLoadOlderEvents` to stop paginating. Older tool executions become invisible with no error surfaced to the user beyond a console warning.
- **Offset drift during activity-log export** — `fetchAllActivityLogExportRows` loops on `offset += page.runs.length` with `total = page.total` refreshed each iteration (`src/utils/automation-activity-log-export.ts:121-135`). If runs are appended/deleted mid-export, the loop can skip or duplicate rows, and `offset` accounting (using returned row count, not `EXPORT_PAGE_SIZE`) masks short pages without detecting concurrent mutation.
- **Missing retention = unbounded evidence exposure** — Exported blobs are created via `downloadBlob` (`src/utils/automation-activity-log-export.ts:155-169`) with no lifecycle: the file lives on the user's filesystem indefinitely, with no purge, no access log, and no watermark tying it to the exporter identity.
- **Telemetry loss as governance gap if relied upon** — `telemetry.ts` drops events when consent is `pending`/`denied`, when `VITE_DO_NOT_TRACK=1`, or when `posthog-js` fails to load (`src/services/telemetry.ts:276-305`, `src/services/telemetry.ts:254-269`). If anyone mistakes PostHog events for an audit trail, evidence disappears silently and without server-side fallback.
- **Tool execution blind spot for BAM/bundled tools** — The frontend does not gate or log `usable_tools` at run time beyond the `OptionService`/adapter cache; there is no pre-execution policy check or per-tool approval record. High-risk tools would execute without a decision artifact to audit.
- **Approval provenance absent** — PR approval (`cleanup-on-approval` in `.github/workflows/pr-artifacts.yml:16`) is GitHub-level, not run-level. No code links an automation run or conversation to an approver identity or timestamp, so "who authorized this run?" cannot be answered from exports.
- **SIEM integration is a no-op without DefenseClaw** — Without the sidecar, the OTLP/Splunk configuration in `docs/DefenseClaw.md:227-230` does nothing; the frontend emits no OTLP spans, no CEF syslog, and no webhook payload, so a SIEM relying on frontend evidence receives nothing.

## Future Considerations

- **Canonical run evidence bundle** — Add a server-owned `GET /v1/{automationId}/runs/{runId}/evidence` endpoint (agent-server + automation backend) that returns a versioned, signed JSON envelope containing: `run` row, full `trigger` + `filter` evaluation, `conversation_id` + trajectory hash, `usable_tools` + `agent_settings`/`model` at creation, policy verdicts (even if "no policy"), and `error`/`cost`/`duration`. Frontend should render and re-download that bundle rather than re-assembling it per export. Tag with `@spec` and cover with contract tests mirroring `__tests__/utils/automation-activity-log-export.test.ts`.
- **E2E SIEM smoke test** — If DefenseClaw is adopted, wire the audit bridge sketched in `docs/DefenseClaw.md:280-282` (`WebhookSpec` → `POST /audit/event`) and add a mock-LLM E2E that asserts a scan/guardrail decision appears in the audit store and forwards via a fake OTLP collector. Until then, remove or demote the DefenseClaw table to avoid implying SIEM readiness.
- **Retention and provenance for exports** — Introduce a retention setting (e.g., `automation_evidence_retention_days` in `config/defaults.json` and `SettingsService`) that governs server-side evidence bundle retention, and embed `exported_at`, `exported_by` (distinct ID from `telemetry.ts`), and `content_sha256` in every downloaded report. The current 7-day dev log rotation (`scripts/logger.mjs:66`) should be documented as non-governance and not referenced for compliance.
- **Approval workflow** — If automations gain a "require approval" mode, extend `AutomationRun` (`src/types/automation.ts:75-98`) with `approved_by`, `approved_at`, `approval_decision` (approve/deny + justification), and surface approval timestamps in `ActivityLogSection` and the CSV column set (`CSV_COLUMNS`, `src/utils/automation-activity-log-export.ts:12-27`) as additive columns.
- **Reproducibility via deterministic replay** — Persist `conversation.entropy`/`seed`, `agent_settings`, and `LLMConfig` alongside the trajectory so a run can be re-hydrated byte-identically (see `src/types/agent-server/core/base/critic.ts:29` note on event IDs for reproducibility).
