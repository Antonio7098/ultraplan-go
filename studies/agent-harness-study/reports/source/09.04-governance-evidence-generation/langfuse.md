## Summary

Langfuse is an LLM-observability platform, not an agent harness with a run loop. Its governance evidence is therefore organized around **mutating-operations auditability** and **observability-data exportability** rather than agent run compliance bundles. The durable core is the Postgres `AuditLog` table (`packages/shared/prisma/schema.prisma:852-876`) fed by a central `auditLog()` helper (`web/src/features/audit-logs/auditLog.ts:86-155`) invoked at 50+ tRPC/public-API call sites, enriched with actor (USER vs API_KEY), timestamps, org/project roles at action time, and `before`/`after` JSON snapshots. Evidence is surfaced through two tRPC readers (`web/src/server/api/routers/auditLogs.ts:78-277`), two EE viewer pages, and a first-class `BatchExportTableName.AuditLogs` export path (`worker/src/features/database-read-stream/getDatabaseReadStream.ts:635-673`) that produces paginated, cutoff-bounded JSON/CSV via `DatabaseReadStream` (`worker/src/__tests__/batchExport.test.ts:1600-1707`). Tool/interactive execution evidence exists in a parallel stream: `InAppAgentEvent` / `InAppAgentRun` (`schema.prisma:263-313`) for the embedded in-app agent, and `AutomationExecution` rows (`worker/src/queues/webhooks.ts:334-348,405-426`) for webhook/slack/github automations. No dedicated "compliance report for a given run" artifact exists; SIEM forwarding is generic (webhooks, BlobStorage/S3 exports) with no SIEM-specific schema or connector, and audit-log retention is deliberately **excluded** from the per-project `retentionDays` data-purge pipeline, giving indefinite retention by default but no configurable policy or immutability proof.

## Rating

**6 / 10** — Present but inconsistent, weakly documented, and fragmented.

*Why 6 and not higher:* Audit logging is real, typed, and widely instrumented with tests and a UI, and machine-readable export exists for it. That lifts Langfuse out of ad-hoc (1-3). What prevents 7-8: (a) no single compliance report aggregates "what happened + what was checked + what controls applied" for a run — audit logs, agent events, automation executions, and RBAC/entitlement checks live in separate stores with no join; (b) policy-decision records and approval timestamps are implicit or scattered (RBAC checks throw but do not emit a decision log; approval state is in `InAppAgentPendingToolApproval`/`InAppAgentRun.status = AWAITING_APPROVAL` with `expiresAt` but no centralized ledger); (c) SIEM integration is repurposed generic plumbing; (d) evidence retention for audit logs is absent from the formal `retentionDays` enforcement and has no immutability, signing, or WORM guarantee; (e) no evidence-signing or tamper-detection.

## Answers to Dimension Questions

### 1. What evidence does the system produce?

* **Mutation audit trail (implemented):** Every mutating tRPC/public-API handler is expected to call `auditLog()` (`web/src/features/audit-logs/auditLog.ts:86-155`). The persisted artifact is `audit_logs` (`packages/shared/prisma/schema.prisma:852-876`): `id, createdAt, updatedAt, type=USER|API_KEY, userId/apiKeyId, orgId + userOrgRole, projectId + userProjectRole, resourceType` (45+ literals at `auditLog.ts:7-52`), `resourceId, action, before, after`. Reads are via `auditLogs.all` (project) and `allByOrg` (org, `projectId=null`) with pagination (`auditLogs.ts:78-277`) and rendered in `AuditLogsTable`/`OrgAuditLogsSettingsPage` gated by entitlement `audit-logs`. Call-site coverage is broad (traces, scores, observations, datasets, prompts, models, org/project membership, API keys, SSO, billing — see `.structure-baseline.json` 50+ edges).
* **Bulk evidence export (implemented):** `getDatabaseReadStreamPaginated` for `audit_logs` (`getDatabaseReadStream.ts:635-673`) streams audit logs (`findMany where projectId, lt cutoffCreatedAt, orderBy createdAt desc`) into `DatabaseReadStream`. `BatchExportTableName.AuditLogs` (`worker/src/__tests__/batchExport.test.ts:1600-1707` proves round-trip including `before`/`after` string equality and DESC ordering) produces S3/blob-hosted JSON/CSV.
* **Agent/tool execution evidence (implemented, fragmented):** `InAppAgentEvent` (sequenced JSON events per `runId`, `schema.prisma:263-278`) + `InAppAgentRun` (status lifecycle `QUEUED/RUNNING/AWAITING_APPROVAL/SUCCEEDED/FAILED/CANCELLED`, `finishedAt`, `errorCode`, `request`), `InAppAgentPendingToolApproval` (`expiresAt`, `approvalFingerprint`), and `AutomationExecution` updates per webhook/slack/github dispatch (`webhooks.ts:334-348,405-426`). Agent instrumentation also emits `traceId/observationId` tied to `rootRunId` (`instrumentation.ts:244-246`) so tool steps appear in global traces.
* **Not produced as a single governance artifact:** There is no "compliance report for run X" that joins audit logs + approval decisions + RBAC policy evaluations + automation outcomes into one signed bundle. Evidence lives in four stores (Postgres audit_logs, Agent events/runs, AutomationExecutions, ClickHouse traces/scores) with no unified report builder. The prompt-level `prompt-version` webhook envelope (`PromptWebhookOutboundSchema`, `queues.ts:302-314` + `webhooks.ts:86-126`) and automation execution rows are the closest to an event-level report, but they are per-trigger, not per-governance-run.
* **Policy-decision and approval evidence (partial):** RBAC/entitlement decisions are checked (`throwIfNoEntitlement`, `throwIfNoProjectAccess` at `auditLogs.ts:87-99`) but not logged as policy-decision records; only the *allowed* mutation's audit log remains. Approval timestamps exist as `createdAt`/`expiresAt` on pending approvals and `finishedAt`/`createdAt` on runs, but there is no cross-cutting "who approved what, when, under which policy" ledger — the integrity runner's `APPROVAL_EXPIRED` code is the only explicit approval-failure evidence.

### 2. Is evidence machine-readable?

**Yes, for the audit-log and export surfaces; fragmented elsewhere.**

* **Structured audit-log API:** `auditLogs.all`/`allByOrg` return typed rows with `actor:{type, body}` (`auditLogs.ts:29-76`) including `id, createdAt, updatedAt, type, resourceType, resourceId, action, before/after`. The EE table maps directly to these fields (`AuditLogsTable.tsx:56-141`). This is JSON over tRPC, paginated with `totalCount`.
* **Structured bulk export:** Audit-log exports emit one JSON object per row with all columns (`getDatabaseReadStream.ts:652-668`), suitable for SIEM ingestion via Blob Storage/S3. The shared `Listable` score/trace exports use the same `DatabaseReadStream` abstraction, so tooling can treat audit logs uniformly.
* **Agent events are JSON but opaque:** `InAppAgentEvent.event: Json` (`schema.prisma:272`) is stored as `JsonB` and is machine-readable, but its schema is AG-UI/internal event typed, not a governance evidence schema, and is not documented as a compliance feed.
* **Automation outputs include HTTP evidence but truncated:** `responseBody.substring(0,1000)` (`webhooks.ts:422`) limits SIEM fidelity. Redirect chains are logged structurally (`webhooks.ts:280-289`) but only to application logs, not to the evidence store.
* **SIEM integration is DIY:** No native SIEM sink (Splunk HEC, Sentinel, Chronicle, OCSF) exists. Consumers must either poll the tRPC API, consume the S3 blob exports, or configure generic webhooks. No grep hit for `siem|SIEM|ocsf|cef|leef` in implementation code. Webhook dispatch is hardened (signature `x-langfuse-signature`, `decrypt(webhookConfig.secretKey)` at `webhooks.ts:535-541`, `fetchWithSecureRedirects` with `whitelistFromEnv`, `validateWebhookURL`) but those are transport controls, not SIEM schema controls.

### 3. Can evidence be reproduced?

**Partially reproducible; not cryptographically reproducible or independently verifiable.**

* **Deterministic snapshots:** `auditLog` stores `before` and `after` as `JSON.stringify` snapshots at call time (`auditLog.ts:88-93`). Together with `createdAt`, `resourceType/Id`, `action`, and actor/role-at-time, a reader can reconstruct *what changed* for any logged mutation. The `patchLLMToolAndLLLMSchemaAuditLogs` migration (`backgroundMigrations/patchLLMToolAndLLLMSchemaAuditLogs.ts:3-122`) demonstrates that before/after payloads are relied upon to fix misclassifications — evidence is treated as source of truth.
* **Ordered replay for agent runs:** `InAppAgentEvent.sequenceNumber` (`schema.prisma:270`) gives a total order per `runId`; `DatabaseReadStream` for audit logs is deterministically `orderBy: createdAt desc` (`getDatabaseReadStream.ts:645-646`). Export also enforces a `cutoffCreatedAt` (`getDatabaseReadStream.ts:641-643`) so a given export job is reproducible for its time window.
* **Not tamper-evident:** `before`/`after` are plain `String?` (`schema.prisma:866-867`), `AuditLog` rows are mutable via Prisma with no append-only constraint, no hash chain, no signature. The `updatedAt` column is auto-managed (`@updatedAt`) implying rows *can* be updated. No test asserts immutability.
* **Not fully joinable:** Reproducing "what controls applied for this action" requires correlating three separate writes: the RBAC check (not logged), the `auditLog` row, and the actor's membership/role history at that instant (snapshot stored only as `userOrgRole/userProjectRole` strings). Policy versioning (which RBAC rule revision was evaluated) is not recorded.
* **Re-export proves row equality:** `batchExport.test.ts:1675-1695` asserts `before`/`after` survive a database→export→assert round-trip byte-identically, which is the strongest reproducibility proof in the codebase.

### 4. Are evidence retention policies enforced?

**For observability data: yes, rigorously. For audit-log evidence: effectively indefinite, with no configurable policy — a deliberate omission.**

* **Per-project observability retention is enforced:** `Project.retentionDays: Int?` (`schema.prisma:135`; `null/0 = indefinite`) drives `DataRetentionQueue` daily at `15 3 * * *` (`dataRetentionQueue.ts:39-42`) → `handleDataRetentionSchedule` fans out one `DataRetentionProcessingJob` per `retentionDays>0` project (`handleDataRetentionSchedule.ts:14-18`) → `handleDataRetentionProcessingJob` re-fetches `retentionDays` from DB (stale-job guard at `:28-39`, `currentRetention !== retention` warning at `:52-56`), computes `cutoffDate = now - retention*24h` (`:58-60`), and deletes ClickHouse `traces/observations/scores/events` + S3 media + ingestion S3 refs + Postgres `media` rows (`:84-103`). Batch scale path uses `BatchDataRetentionCleaner` (`PeriodicExclusiveRunner`). Tests cover 8+ scenarios including cutoff, changed-retention skip, and media/blob branches (`dataRetentionProcessing.test.ts:439-553`, `batchDataRetentionCleaner.test.ts`).
* **Audit logs are explicitly outside that pipeline:** `handleDataRetentionProcessingJob.ts:87-100` imports and calls `deleteTracesOlderThanDays`, `deleteObservationsOlderThanDays`, `deleteScoresOlderThanDays`, `deleteEventsOlderThanDays`, `deleteMediaFiles`, `removeIngestionEventsFromS3AndDeleteClickhouseRefsForProject` — there is **no** `deleteAuditLogsOlderThanDays`. Consequently audit logs outlive the retention window for traces that reference them, which is good for governance but means no TTL, no purge schedule, no legal-hold toggle.
* **No WORM/immutability or evidence-specific retention config:** No `AUDIT_LOG_RETENTION_DAYS` env, no Prisma `@@index` on retention, no lifecycle policy for audit-log S3 exports. The only file-system retention in the repo is unrelated (`scripts/logger.mjs` rotation cited in openhands report, not present here).
* **Implication for the rating question:** A customer asking "retention is enforced according to policy for evidence" gets two answers: (a) traces/scores evidence: yes, strongly enforced with concurrency-safe re-read and bulk deletes; (b) audit-log evidence there is no policy to enforce — it is kept forever until manual deletion. For a strict compliance audit (e.g., 7-year hold vs. GDPR purge), Langfuse would require an out-of-band process; the system does not natively enforce a governed retention window on audit logs.

## Architectural Decisions

* **Centralize mutations through `auditLog()` but decentralize definition of "auditable"** — A single writer function (`web/src/features/audit-logs/auditLog.ts:86-155`) normalizes 50+ call sites, but the `AuditableResource` union (`auditLog.ts:7-52`) is a flat string catalog maintained by convention; adding a new resource requires adding a literal and remembering to emit `auditLog` at every mutation path, which the `.structure-baseline.json` dependency map makes auditable but not enforced by types beyond the string.
* **Preserve audit logs across FK deletion** — `AuditLog` has *no FK* (`schema.prisma:851` comment `No FK constraints to preserve audit logs`) and `@@index`es on `projectId/userId/orgId/apiKeyId`. This lets org/project/user deletion keep evidence, trading referential integrity for durability. The cost is orphan `userId`/`apiKeyId` resolved to `null` actor bodies in `mapAuditLogsWithActors` (`auditLogs.ts:48-53,58-63`).
* **Entitlement-gated, read-scoped audit access** — Both read paths check `hasEntitlement("audit-logs")` and `scope:"auditLogs:read"` (`auditLogs.ts:87-99,188-199`), separating SaaS Plan entitlement from RBAC role. This is intentional product-tier governance; it also means evidence is unavailable to lower tiers (e.g., `cloud:hobby` test at `batchExport-trpc.servertest.ts:116-141` asserts block on export of `audit_logs`).
* **Reuse generic bulk-export machinery for compliance evidence** — Rather than a bespoke compliance report, audit logs ride the same `DatabaseReadStream`/`BatchExport`/`BlobStorageIntegration` path as traces/scores (`getDatabaseReadStream.ts:42-52,635-673`). This reuses pagination, cutoff, and S3 delivery but conflates evidence exports with data exports and offers no compliance-specific attestation (no manifest signature, no chain-of-custody).
* **Embed agent evidence in ClickHouse-backed traces, not just Postgres** — Agent runs emit `InAppAgentEvent`s in Postgres for sequencing and `traceId/observationId` for ClickHouse linkage (`instrumentation.ts:244-246`), so governance reviewers must consult both stores. No single "run bundle" aggregates them.

## Notable Patterns

* **Before/after snapshot pattern** — Every `auditLog` call is expected to supply `before` and `after` snapshots (`auditLog.ts:58-59,88-93`); e.g., `notificationPreferences.ts:72,106` fetches existing preference as `before`. This gives change-data-capture at the application layer without DB triggers.
* **Dual-scope audit viewer** — Parallel `all` (project, `projectId != null`) and `allByOrg` (org, `projectId == null`) queries (`auditLogs.ts:78-277`) model org-level governance (membership, org API keys) separately from project-level governance, mirrored by two EE pages.
* **Stale-job guard for retention** — Re-reading `project.retentionDays` inside the processing job and preferring `currentRetention` over queued `retention` (`handleDataRetentionProcessingJob.ts:26-56`) plus the `skip if null/0` check (`:34`) prevents a retention-disable from becoming a data-loss race. This is the most mature retention-safety pattern in the corpus.
* **Secure webhook dispatch as generic SIEM transport** — `validateWebhookURL`, `whitelistFromEnv`, `fetchWithSecureRedirects` with `maxRedirects`, sensitive-header stripping, HMAC `createSignatureHeader` (`webhooks.ts:244-268,535-541`), and redirect-chain logging (`:280-289`) constitute a governance-grade externalization path, even though no SIEM schema rides it.
* **Background correction as evidence hygiene** — The `patchLLMToolAndLLLMSchemaAuditLogs` migration (`backgroundMigrations/patchLLMToolAndLLLMSchemaAuditLogs.ts:40-102`) batch-scans audit logs by `projectId` and reclassifies `resourceType` based on `before`/`after` JSON content — evidence correcting evidence.

## Tradeoffs

* **Broad coverage vs. centralized completeness** — 50+ `auditLog` call sites give wide coverage (prompt, dataset, score, model, etc.) at the cost of no compile-time guarantee that a new mutation path is covered; missing a call is silent, and the test suite asserts only isolated flows (`audit-log-in-app-agent.servertest.ts:2`).
* **Indefinite audit retention vs. governed lifecycle** — Not deleting `audit_logs` in the retention cascade preserves evidence for any future audit at the cost of unbounded growth and no GDPR-style purge without manual intervention; operators needing a bounded hold must build it themselves.
* **Generic exports vs. compliance-grade reports** — Riding `BatchExport`/`BlobStorageIntegration` achieves reuse and S3 delivery (good for SIEM pipelines) but sacrifices compliance specifics: no signed manifest, no retention attestation, no "this report covers run X, checked policies Y, applied controls Z" envelope. The export is row-dumped JSON, not a governance assertion.
* **No FKs for durability vs. joinability** — Removing FKs keeps evidence after principal deletion but forces `userMap`/`apiKeyMap` lookups that return `null` bodies (`auditLogs.ts:120-171`), weakening actor attribution for deleted users/keys; there is no tombstone or "deleted principal" record.
* **Entitlement gating vs. audit universality** — Gating audit logs behind `entitlement:"audit-logs"` aligns with SaaS pricing but means a paying-for-governance requirement can conflict with compliance mandates on lower tiers; evidence exists in DB but is unreadable to the caller.

## Failure Modes / Edge Cases

* **Missing audit emit on new mutation path** — Adding a tRPC mutation without an `auditLog` call leaves a silent governance gap; the only detection is the `web/.structure-baseline.json` dependency graph or code review — no runtime guard or test fails on "mutation without auditLog".
* **RBAC deny leaves no decision record** — `throwIfNoProjectAccess` / `throwIfNoEntitlement` throw `TRPCError` before any audit write; a denied exfiltration attempt is visible only in HTTP logs, not in `audit_logs`. Reconstructing "who tried to do what and was refused" requires external log aggregation.
* **Audit rows mutable and unsigned** — A compromised DB principal can `UPDATE audit_logs SET before=null, after=null` or delete rows; no hash chain or DB-level `REVOKE UPDATE` is configured, and Prisma `updatedAt` will advance without alarm.
* **Orphaned actor attribution** — After `user` or `apiKey` row deletion (or project deletion for org-level logs), `userMap.get(userId)` misses and the API returns `{id: userId, name:null, email:null}` (`auditLogs.ts:48-53`); SIEMs lose human attribution with no way to resolve the former identity.
* **Truncated webhook evidence** — `responseBody.substring(0,1000)` (`webhooks.ts:422`) clips evidence of exfiltration or integration failure; a 2 KB error JSON is lossy, and monitor-alert slack failures go through the Redis counter path (`slackMonitorAlertFailure` at `webhooks.ts:974-999`) with no persisted `AutomationExecution` row, so timeline reconstruction for that channel is incomplete.
* **Cutoff-bound export repeatability break** — `cutoffCreatedAt: lt cutoffCreatedAt` (`getDatabaseReadStream.ts:641-643`) excludes rows created after job enqueue; re-running the same export with a later cutoff produces a different bundle, so "reproduce evidence for run X" depends on capturing the exact `cutoffCreatedAt` used for that export (stored in `BatchExport` but not exposed in the report).
* **Retention re-read race is mitigated but not strongly consistent** — The `findUnique({select:retentionDays})` + `if (!retentionDays) skip` check (`handleDataRetentionProcessingJob.ts:28-39`) is not transactional with the subsequent bulk deletes; a `retentionDays` change between the check and the first `deleteTracesOlderThanDays` call could still delete under the new window, though the `currentRetention` preference minimizes the window.
* **InAppAgent approval window loss** — `InAppAgentPendingToolApproval.expiresAt` (`schema.prisma:324`) plus `APPROVAL_EXPIRED` error implies approvals can expire while evidence still shows `AWAITING_APPROVAL`; there is no persisted "approval granted at T by user U under policy P" row beyond the next `InAppAgentEvent` — if that event write fails, the approval evidence is lost.
