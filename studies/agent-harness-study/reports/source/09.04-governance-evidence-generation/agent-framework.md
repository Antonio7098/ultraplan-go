## Summary

Agent Framework (Microsoft) is a multi-language harness for building agents, not a governed runtime with compliance reporting. It can emit **observability evidence** (OTel traces/metrics/logs) and **security/approval evidence** (FIDES audit logs, ToolApproval session state, HistoryProvider persisted messages), but it has **no dedicated governance evidence report generator, no comprehensive policy-decision record with timestamps, no SIEM-specific connector, and no enforced retention policy** for evidence. Telemetry is mature and machine-readable via OTLP; security audit evidence is in-memory and ad-hoc. Reproducibility is partial via history replay/file checkpoints, but there is no signed, time-stamped compliance report per run.

## Rating

**Score: 4 / 10 — Present but inconsistent, weakly documented, fragile**

Rationale: OTel instrumentation (`python/packages/core/agent_framework/observability.py:422-1185`) and security audit logs (`python/packages/core/agent_framework/security.py:1643-2184`) exist with tests, and HistoryProviders persist conversation evidence. However (1) policy decisions lack approval timestamps and cryptographic attestation, (2) approval evidence persists as `ToolApprovalState` without expiration/timestamps (`python/packages/core/agent_framework/_harness/_tool_approval.py:158-215`), (3) evidence retention is caller-managed / undocumented with no enforcement (only `max_messages` in Redis and per-file append), (4) no `generate_compliance_report()` or SIEM integration code beyond generic OTLP env parsing (`observability.py:548-638`), and (5) FIDES/docs explicitly defer data governance to deployers (`TRANSPARENCY_FAQ.md:119-121`, `README.md:216`, `docs/specs/004-python-function-calling-loop.md:409`). This falls in the 4–6 band — features present but fragmented, not a coherent governance evidence subsystem.

## Answers to Dimension Questions

**1. What evidence does the system produce?**

- **OTel evidence:** Traces (spans), metrics (histograms for `gen_ai.client.operation.duration`, `gen_ai.client.token.usage`), and logs (OTel log exporter) via `observability.py:422-1080`, with resource attributes, `OtelAttr` semantic conventions (`python/packages/core/agent_framework/observability.py:223-362`), and per-tool spans (`test_observability.py:961-1003`). Also GenAI message events (`gen_ai.system.message` etc.) when `ENABLE_SENSITIVE_DATA` is set.
- **Security policy decision evidence:** In-memory `audit_log: list[dict[str,Any]]` in `PolicyEnforcementFunctionMiddleware` (`security.py:1698`, `2163-2172`) — each violation records `type` (`untrusted_context` / `max_allowed_confidentiality`), `function`, `context_label` (integrity/confidentiality dict), and `turn`. A parallel global store `_pending_policy_approvals: dict[str, _PendingPolicyApproval]` (`security.py:1704`) captures pending approval `body_signature`, `label_key`, `session_key`, `disclosed_violations` for exact binding, but not exported as a report.
- **Approval evidence:** `ToolApprovalState` in session state (`_harness/_tool_approval.py:158-215`) persists `rules` (standing approvals), `queued_approval_requests`, `collected_approval_responses` as serialized `Content` objects (`_content_to_state:82`). Inline approval requests are `function_approval_request` Contents with `additional_properties` including violation reason (`security.py:1904-1918`).
- **Tool execution evidence:** Function invocation layer produces `function_call`/`function_result` Contents and error results (`_tools.py:1412`, `2862`), retained in `HistoryProvider` stores (InMemory, File JSON Lines, Cosmos, Redis). Spec explicitly calls out audit retention: "History backing store (may retain approval wrappers for audit)" (`docs/specs/004-python-function-calling-loop.md:285`).
- **What it does NOT produce:** No signed compliance report, no per-run PDF/JSON evidence bundle, no centralized governance log with run ID + approval timestamps + controlling policy version, no DLP incident report beyond `DlpAction` enum in Purview provider (`dotnet/src/Microsoft.Agents.AI.Purview/Models/Common/DlpAction.cs:39`).

**2. Is evidence machine-readable?**

- **Yes for telemetry:** OTLP exporters (`observability.py:422-545`) emit protobuf/JSON to any OTLP endpoint (gRPC `http://localhost:4317` or HTTP `http://localhost:4318`), auto-appending `/v1/{traces,metrics,logs}` (`observability.py:606-610`). Span attributes are JSON-serializable `OtelAttr` strings; sensitive messages emit via OTel log record exporter when `enable_sensitive_data` is true.
- **Yes for security state:** `ContentLabel.to_dict` (`security.py:185-193`), `ToolApprovalState.to_dict` (`_tool_approval.py:204-215`), `Content.to_dict` all produce JSON-serializable dicts. `FileHistoryProvider` writes JSON Lines (single-line JSON enforced, ` _sessions.py:2423`) or msgpack length-prefixed binaries. `audit_log` entries are plain dicts, convertible to JSON, but ephemeral.
- **But limited for SIEM:** No pre-built SIEM schema, no CEF/LEEF/syslog formatter, no `evidence -> SIEM` adapter code found. Integration is "bring your own OTLP collector → SIEM" via standard OTEL env vars (`OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS`, etc., `observability.py:586-627`). A grep for `siem` returns zero code hits in core.

**3. Can evidence be reproduced?**

- **Partially, via replay but not via report regeneration.**
  - Conversation history can be replayed: `FileHistoryProvider` is append-only per session (`_sessions.py:2172-2250`), `RedisHistoryProvider` with `max_messages` window, and `InMemoryHistoryProvider` in session state. Workflow checkpoints store execution snapshots (not examined in detail here). History providers can be loaded with `load_messages=False` for audit-only sinking (`docs/decisions/0016-python-context-middleware.md:125-1792`).
  - Tool invocation layer is deterministic per the spec's ordered occurrence matching (`specs/004-python-function-calling-loop.md`), but the spec warns that small changes can duplicate side effects / replay stale approval authority — extra validation required.
  - However, `PolicyEnforcementFunctionMiddleware.audit_log` is process-local, not persisted to a store, not snapshotted to checkpoint files, and cleared on process exit; reproducing a run's policy decisions requires re-running with the same middleware instance + captured logs. `ToolApprovalState` IS persisted in `AgentSession.state` (`_harness/_tool_approval.py:248-275`) and thus replayable if the session store is durable (FileSessionStore, Cosmos, etc.), but the binding between policy violations and the approval timestamp cannot be reconstructed because timestamps are absent.
  - No `run_id`-scoped evidence bundle can be fetched post-hoc; there is no `get_evidence_report(run_id) -> EvidenceBundle` API.

**4. Are evidence retention policies enforced?**

- **No.** Evidence retention is caller-managed and undocumented as a governance policy:
  - `PolicyEnforcementFunctionMiddleware.audit_log` has no retention, no max size, no TTL; `clear_audit_log()` must be called manually (`security.py:2182-2184`). Tests never exercise eviction (`test_security.py:613-616` only checks initial length).
  - `FileHistoryProvider` retains messages indefinitely until manual `clear(session_id)` (noted as GDPR compliance helper in `samples/02-agents/conversations/cosmos_history_provider_messages.py:22`). No retention config beyond deprecated `max_messages` in Redis (`redis/tests/test_providers.py:503-525`).
  - `ApprovalLifecycle` in `ag-ui` implements `pending_retention_seconds` (default 86400s), `indeterminate_retention_seconds` (604800s), `terminal_retention_seconds` (900s) (`_approval_lifecycle.py:243-259`, `707-733`) and purges with `retention_purge` events, but this is scoped to AG-UI pending approvals, not to core governance evidence.
  - Documentation delegates retention to the host: `TRANSPARENCY_FAQ.md:121` ("review their privacy policies, security practices, data retention policies"), `README.md:216`, and hosting samples ("define retention" per tenant/user, `samples/04-hosting/af-hosting/local_telegram/README.md:138`). No per-evidence-type retention policy is codified or enforced in code.

## Architectural Decisions

- **OTel as the evidence transport:** Chose OpenTelemetry semantic conventions + OTLP exporters (`observability.py:548-1005`) over a bespoke audit pipeline. Good for interoperability with SIEMs/collectors, but leaves attestation/signing/immutability to downstream systems. Decision mirrors `docs/decisions/0003-agent-opentelemetry-instrumentation.md:60-77` (OpenTelemetryAgent wrapper pattern, compliance with GenAI semconv).
- **FIDES split into two middlewares (tracking vs. enforcement) with an in-memory audit log:** `LabelTrackingFunctionMiddleware` tracks `context_label` and auto-hides untrusted content; `PolicyEnforcementFunctionMiddleware` validates against `context_label` and writes `audit_log` dicts (`security.py:1643-2172`). Tradeoff: clean separation and deterministic label propagation (`0024-prompt-injection-defense.md:16,22,58` calls out audit trails for compliance), but the audit sink is a plain Python list, not a durable, tamper-evident store, and is not surfaced via OTel.
- **Approval state persisted in `AgentSession.state`, audit log not:** `ToolApprovalState` uses `SessionStore` serialization (`_tool_approval.py:248-275`) so approvals survive restarts when using durable session stores; `security.py:1698` audit_log does not — asymmetry means approval *outcomes* are durable but policy *violations* are not. This suggests FIDES was designed as a defense mechanism first, governance evidence second.
- **HistoryProvider filter deliberately hides approvals from LLM replay but preserves them in backing store:** Spec says providers "may retain approval control contents in their backing store for audit, but base history replay" filters them (`specs/004-python-function-calling-loop.md:409`). This creates a dual-use evidence stream: same store serves both replay and audit, risking accidental purge if retention is misconfigured.
- **No central EvidenceService:** No class like `EvidenceReport`, `ComplianceLedger`, or `RunEvidence` was found in `python/packages/core/agent_framework/`; evidence is scattered across OTel spans, middleware fields, and history files. This reflects a library/framework posture (caller owns storage) rather than a hosted governance service.

## Notable Patterns

- **OTel Layer pattern via `*TelemetryLayer` mixins:** `AgentTelemetryLayer`, `ChatTelemetryLayer` wrap agents/clients to emit spans without mutating core logic (`observability.py:1-14` header, tests: `test_observability.py:275-350`). Supports sensitive-data gating (`enable_sensitive_data`, `enable_message_events`) — relevant because governance evidence must avoid leaking PII into SIEM.
- **Content-typed control plane:** Policy violations surface as `function_approval_request` Content objects with `additional_properties` (`security.py:1919-1923`), enabling standard approval flow (`_harness/_tool_approval.py:382-450`) to surface governance evidence as just another message. Observable but requires a client that renders approval UI.
- **Tiered label propagation (embedded > source_integrity > input labels) as deterministic audit trail:** Documented in `security.py:690-718` and `FIDES_IMPLEMENTATION_SUMMARY.md:211`. Every tool result gets a label, and the middleware logs context taint (`security.py:818-829` INFO log). Could be extended to emit OTel events per taint, but currently only logs to `logger`.
- **Session-scoped evidence isolation:** `SecureAgentConfig` and `ToolApprovalMiddleware` bind evidence to `SessionContext` / `AgentSession.state[source_id]` (`security.py:2302-2324`, `_tool_approval.py:248-275`), matching hosted per-user session isolation (`docs/decisions/0031-hosted-per-user-session-storage-isolation.md`). Good for multi-tenant evidence separation, if the session store enforces it.

## Tradeoffs

- **Flexibility vs. governance completeness:** Caller-chosen storage (`InMemoryHistoryProvider`, `FileHistoryProvider`, `RedisHistoryProvider`, `CosmosHistoryProvider`) lets hosts fit their stack, but prevents the framework from guaranteeing immutability, signing, or retention. Evidence durability is only as good as the host's store configuration.
- **In-memory audit log vs. durable ledger:** Fast, testable, zero-schema migration (`list[dict]` + copy-on-read, `security.py:2174`), but loses evidence on crash, is not queryable post-hoc, and lacks timestamps — making forensic reconstruction and SIEM correlation hard. A durable append-only log (with run_id + timestamp + policy_version) would be heavier but governance-grade.
- **OTel for everything vs. explicit governance schema:** Reusing GenAI semconv (`OtelAttr.GEN_AI_*`, `workflow.*`) keeps telemetry unified and SIEM-ready via OTLP, but overloading spans with policy decision attributes (e.g., `max_allowed_confidentiality` violation) is not modeled; those decisions live only in the Python audit list, not in spans, so SIEM viewers see tool executions but not *why they were blocked*.
- **Sensitive-data gating protects privacy but starves evidence:** `OBSERVABILITY_SETTINGS.SENSITIVE_DATA_ENABLED` (`observability.py:921-925`) and `enable_audit_log` (`security.py:1678`) are opt-in; with defaults, SIEM gets token counts/durations but not prompt contents, tool arguments, or approval reasons — compliant with `TRANSPARENCY_FAQ.md:119` guidance but insufficient for a full compliance narrative without deliberate opt-in.

## Failure Modes / Edge Cases

- **Audit log loss on crash/restart:** Because `audit_log` is not persisted (`security.py:1698` plain list, no session binding), a process crash before evidence is exported discards all in-flight policy decisions. Re-running the agent produces a different `audit_log` ordering if timing changes; no WAL or file flush.
- **Approval replay without re-disclosure:** If a tool's `max_allowed_confidentiality` or `allow_untrusted_tools` set changes between approval grant and replay, `PolicyEnforcementFunctionMiddleware._violation_set_key` (`security.py:1771`) will detect the mismatch and re-request approval, but the *original* violation reason remains only in the old audit entry — correlating the two requires manual log stitching.
- **Single-cycle approval binding is fragile under duplicate `call_id`s:** The spec warns function-call budget and approval correlation are occurrence-aware (`AGENTS.md:161`, `specs/004-python-function-calling-loop.md:512`), and FIDES enforces per-occurrence, per-session, per-label binding (`security.py:1699-1710`, `1824-1862`). A buggy caller that reuses `call_id` across runs could still hit the expiry/reclamation window and need re-approval; no persistent sequence number anchors evidence across restarts.
- **History replay ambiguity hides evidence holes:** `FileHistoryProvider` JSON Lines must be single-line JSON (`_sessions.py:2423`); malformed snapshots are quarantined only for syntax errors, while schema/version failures preserve the original file — evidence could silently drift if the schema evolves, making reproduced evidence diverge from original run.
- **OTel exporter misconfiguration silences evidence:** `OBSERVABILITY_SETTINGS._configure_providers` no-ops if `ENABLED` is false or `_executed_setup` is already true (`observability.py:968`), and `enable_sensitive_telemetry` is silently dropped when `disable_instrumentation()` sticky flag is set (`observability.py:1207-1235`). A host that disables instrumentation early will produce no SIEM evidence with no error — governance-blind without an explicit health check.
- **Evidence retention misconfiguration causes data loss or non-compliance:** `RedisHistoryProvider` with `max_messages=0` retains nothing (`packages/redis/tests/test_providers.py:503`); `FileHistoryProvider` default is indefinite retention with no TTL — either extreme (premature purge or illegal indefinite retention) is possible because retention is caller-defined, not policy-enforced.

## Future Considerations

- Add a first-class `EvidenceReport` / `GovernanceLedger` API: `await agent.get_evidence_report(run_id) -> {policy_decisions: [...], approvals: [...with timestamps...], tool_executions: [...], history_ref: ...}` persisted to the same `SessionStore` as checkpoints, with a JSON schema and signing option. Capture `created_at`, `policy_version`, `run_id`, `session_id`, `principals` per entry.
- Emit policy decisions as OTel span events / log records (with `OtelAttr.ERROR_TYPE` / custom attributes for `violation_type`, `context_label`) so SIEM evidence and trace evidence are unified and queryable without a separate audit channel.
- Persist `PolicyEnforcementFunctionMiddleware.audit_log` into `AgentSession.state` (parallel to `ToolApprovalState`) or a dedicated `EvidenceProvider` HistoryProvider, with configured retention (`max_entries`, `ttl`) mirroring `ApprovalLifecycle` semantics, and add tests for timestamping and eviction.
- Provide a reference SIEM bridge: an OTLP → Loki/Sentinel/Splunk example collector config + a `EvidenceExporter` that writes evidence bundles as JSON Lines with W3C Trace Context correlation (already present on workflow messages, `_workflows/_edge_runner.py:340-345`), rather than requiring every deployer to wire OTel env vars.
- Enforce evidence retention policies with defaults and validation (e.g., reject `audit_log` unbounded growth, warn on `FileHistoryProvider` indefinite retention, surface `OTEL_RESOURCE_ATTRIBUTES` for retention tags), and document host responsibilities beyond the generic disclaimer in `TRANSPARENCY_FAQ.md:121`.

## Questions / Gaps

- No evidence found for a compliance report per run — `reports/repo/…` in this study is meta-analysis scaffolding, not product code; searched `python/packages/core/agent_framework/` for `report`, `evidence`, `compliance` and found only CI trend reports.
- No SIEM-specific integration code (Splunk HEC, Microsoft Sentinel, Datadog) — only generic OTLP env parsing (`observability.py:548-638`). If a managed SIEM connector exists, it is outside the studied source directory (per hard rules we did not search siblings).
- Approval timestamps not recorded — `audit_log` dicts (`security.py:2017-2044`) and `ToolApprovalState` (`_harness/_tool_approval.py:158-215`) carry no time fields; `_PendingPolicyApproval` also lacks timestamps, so latency/SLA analysis from evidence alone is impossible.
- Tool execution logs are sparse: `get_function_span` captures tool name/type/call_id, but does NOT record tool arguments/result unless `emit_tool_call_attributes` (requires both `SENSITIVE_DATA_ENABLED` and `use_latest_experimental_gen_ai_semconv`, `observability.py:928-934`). Default runs therefore produce evidence without input/output payloads, limiting forensic usefulness.
- Retention policy search boundary: checked all `python/packages/core/agent_framework/**`, `docs/**`, `python/packages/redis/**`, `python/packages/ag-ui/**`; no `governance/retention` config file exists. If retention is intended to be delegated to Azure Cosmos/Valkey TTL or Foundry zero-retention (`dotnet/src/Microsoft.Agents.AI.OpenAI/Extensions/OpenAIResponseClientExtensions.cs:114`), that is implicit at the SDK layer, not enforced as a governance control in this repo.
- Reproducibility gap: Can a run's evidence be reproduced bit-for-bit given the same inputs? HistoryProvider contents are replayable, but FIDES `context_label` taint is cumulative and order-sensitive, and `ContentVariableStore` UUIDs (`var_*` hex, `security.py:359`) are non-deterministic, so two runs with identical inputs produce different variable IDs / audit dict ordering unless deterministically seeded.
