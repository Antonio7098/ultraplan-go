## Summary

Agent Framework implements filesystem/network/process controls as an explicit, layered capability model spread across dedicated packages rather than a single sandbox module. The core thesis, stated in ADR-0024, is that "model-generated code is treated as untrusted relative to the host process" and that "the selected backend provides the primary isolation boundary" while the framework configures approvals and capabilities (`studies/agent-harness-study/sources/agent-framework/docs/decisions/0024-codeact-integration.md:24`). Four execution tiers exist:

1. **Local shell** (`Microsoft.Agents.AI.Tools.Shell` / `agent_framework_tools.shell`) — real host shell with approval-in-the-loop as the stated security boundary, an explicitly non-security regex policy pre-filter, process-tree kill on timeout, and optional clean environments.
2. **Docker shell** (same packages) — container-as-boundary with restrictive-by-default flags: `--network none`, non-root user, read-only rootfs, `--cap-drop=ALL`, `no-new-privileges`, memory and pids limits, size-capped tmpfs.
3. **Local CodeAct subprocess** (`Microsoft.Agents.AI.LocalCodeAct`) — child Python process with default-on AST allow-list validation, wall-clock timeouts, byte caps on stdout/stderr/result/captured files, and explicit documentation that it is NOT a sandbox.
4. **Hyperlight microVM/WASM sandbox** (`Microsoft.Agents.AI.Hyperlight`) — true isolation with snapshot/restore per invocation, opt-in file mounts, and an outbound-domain allow-list enforced inside the sandbox. The Python `monty` package offers a fifth tier: a Rust-based restricted interpreter where OS/filesystem/network calls are rejected with `PermissionError`.

The framework is unusually honest about residual risk: the Python security test suite encodes known deny-list bypasses as permanent xfail-documented contracts (`studies/agent-harness-study/sources/agent-framework/python/packages/tools/tests/test_security.py:124-164`), and every executor's XML docs/docstrings state which layer is and is not a security boundary.

## Rating

**8 / 10** — Clear tiered model with tests, explicit interfaces, and operational safeguards (top of the 7–8 band). Points keeping it out of 9–10: local shell timeouts default to disabled; the .NET Docker executor lacks the isolation-breaking-flag blocklist its Python counterpart has; LocalCodeAct has no CPU/memory limits (wall clock + byte caps only); container teardown is best-effort with documented leak paths.

## Answers to Dimension Questions

**1. What filesystem access does an agent have?**
By default, none beyond what the host process itself grants. Access is opt-in and scoped:
- CodeAct providers expose host directories only through `FileMount`s with explicit modes and write-byte caps (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.LocalCodeAct/FileMount.cs:10-17`, `studies/agent-harness-study/sources/agent-framework/python/packages/monty/agent_framework_monty/_types.py:22-34`). Monty defaults to `overlay` (in-memory writes, nothing touches the host).
- In LocalCodeAct, generated code cannot even call `open` (blocked builtin) or touch `os` file APIs (attribute allow-list of `environ`/`path` only) — `studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.LocalCodeAct/Resources/validator.py:127`, `studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.LocalCodeAct/Resources/validator.py:61`.
- Docker shell exposes host FS only via one optional workdir mount, read-only by default (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Tools.Shell/DockerShellExecutorOptions.cs:32-38`), on a read-only rootfs.
- Local shell runs with the full user permissions of the harness process — no filesystem confinement exists at this tier; approval-in-the-loop is the only gate (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Tools.Shell/LocalShellExecutor.cs:43-50`).

**2. What network access does an agent have?**
Tiered: Docker containers default to `--network none` (`studies/agent-harness-study/sources/agent-framework/python/packages/tools/agent_framework_tools/shell/_docker.py:70`); Hyperlight sandboxes have no outbound access until domains are allow-listed via `AllowedDomain`/`AllowDomain` (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Hyperlight/Internal/SandboxExecutor.cs:214-217`), with optional HTTP-method scoping; Monty rejects all network-capable calls with `PermissionError` (`studies/agent-harness-study/sources/agent-framework/python/packages/monty/agent_framework_monty/_monty_bridge.py:262-268`); LocalCodeAct AST-blocks `socket`/`urllib`/`requests`/`http` imports (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.LocalCodeAct/Resources/validator.py:37-55`) but this is a guardrail, not a boundary; local/Docker shell commands have unrestricted network at the OS level (the human approver is the control). There is no global egress proxy or policy engine for arbitrary tools — network governance is per-execution-tier configuration.

**3. Can the agent spawn arbitrary processes?**
Yes at the local-shell tier (that is its purpose), gated by human approval by default and optionally by an operator-supplied `ShellPolicy`. Inside sandboxes the answer narrows: Docker allows processes within pids-limit 256 and cap-dropped capabilities (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Tools.Shell/DockerShellExecutor.cs:71-72`, `387-388`); Monty cannot spawn processes at all (OS functions denied); LocalCodeAct blocks `subprocess`/`multiprocessing` imports and `__import__`, though the package explicitly warns it is "NOT a sandbox" and relies on external isolation (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.LocalCodeAct/LocalCodeActProvider.cs:26-29`).

**4. Are resources cleaned up after execution?**
Yes, with documented best-effort caveats: shells/process trees are killed on timeout/cancel/dispose (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Tools.Shell/LocalShellExecutor.cs:284-295`, `studies/agent-harness-study/sources/agent-framework/python/packages/tools/agent_framework_tools/shell/_killtree.py:50-61`); containers are force-removed with retry and leak logging (`studies/agent-harness-study/sources/agent-framework/python/packages/tools/agent_framework_tools/shell/_docker.py:635-676`); Hyperlight temp dirs are cleared per-run and cleaned on dispose (`studies/agent-harness-study/sources/agent-framework/python/packages/hyperlight/agent_framework_hyperlight/_execute_code_tool.py:296-304`); Hyperlight restores a warm snapshot before each run so state never accumulates (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Hyperlight/Internal/SandboxExecutor.cs:132-135`). Residual risk: a hung daemon can leak a container despite the `rm -f` fallback (`studies/agent-harness-study/sources/agent-framework/python/packages/tools/agent_framework_tools/shell/_docker.py:561-574`), and killed-process cleanup is explicitly "best-effort, never raises."

### Focus question: Can an agent download arbitrary files from the internet?

Not by default in the sandboxed tiers, but yes in the local tiers:
- **Docker shell**: no — default `--network none` means no interfaces; enabling egress requires deliberately setting `network="bridge"` or a custom network, and Python rejects `--network` spliced through `extra_run_args` (`studies/agent-harness-study/sources/agent-framework/python/packages/tools/agent_framework_tools/shell/_docker.py:80-100`).
- **Monty / LocalCodeAct**: effectively no — Monty denies socket-bearing operations outright; LocalCodeAct blocks network imports at AST level (bypassable in principle, hence the "not a sandbox" caveat).
- **Hyperlight**: only allow-listed domains/methods configured by the developer (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Hyperlight/AllowedDomain.cs:16-21`); the monty AGENTS.md confirms no URL primitive exists otherwise and suggests users wrap fetch as an audited host tool (`studies/agent-harness-study/sources/agent-framework/python/packages/monty/AGENTS.md:66-71`).
- **Local shell**: yes, subject only to human approval per command (e.g. `curl ... -o` would run if approved); the representative deny-list even includes `curl|bash` patterns as an *operator-supplied* option, not a default (`studies/agent-harness-study/sources/agent-framework/python/packages/tools/tests/test_security.py:41`).

## Architectural Decisions

1. **Backend-provides-isolation, framework-provides-capabilities.** ADR-0024 makes isolation a backend admission criterion: "If a backend cannot provide isolation appropriate for its trust model, it is not a suitable CodeAct backend," while the framework owns approvals, mounts, and allow-list plumbing (`studies/agent-harness-study/sources/agent-framework/docs/decisions/0024-codeact-integration.md:24`, `:40`). This lets one capability API span microVM, container, subprocess, and interpreted tiers.
2. **Implicit-off capability flags.** Rather than separate `filesystem_mode`/`network_mode` booleans, filesystem/network are disabled until mounts/allow-list entries are configured (`studies/agent-harness-study/sources/agent-framework/docs/decisions/0024-codeact-integration.md:195-198`) — fail-closed by construction.
3. **Honest threat modeling over security theater.** `ShellPolicy` ships no default deny-list because pattern matching "cannot see what the shell will actually execute after expansion"; the survey note records that no major framework uses regex as primary defense (`studies/agent-harness-study/sources/agent-framework/python/packages/tools/agent_framework_tools/shell/_policy.py:8-34`). Approval gating is wired as the mandatory default and can only be removed via an explicit `acknowledge_unsafe`/`acknowledgeUnsafe` token (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Tools.Shell/LocalShellExecutor.cs:341-347`).
4. **Restrictive-by-default container baseline.** Non-root UID, read-only rootfs, dropped capabilities, no-new-privileges, bounded tmpfs, memory/pids caps are applied unconditionally in the shared argv builder (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Tools.Shell/DockerShellExecutor.cs:360-418`).

## Notable Patterns

- **Pure argv builders for testability.** Both SDKs extract side-effect-free functions (`BuildRunArgv`/`build_run_argv`) so Docker isolation flags are unit-tested without a daemon (`studies/agent-harness-study/sources/agent-framework/python/packages/tools/agent_framework_tools/shell/_docker.py:155-211`, tested in `studies/agent-harness-study/sources/agent-framework/python/packages/tools/tests/test_docker_shell_tool.py:150-201`).
- **Negative-space testing.** The Python suite permanently encodes what is *not* defended: parametrized bypass cases assert the bypass works and xfail if ever caught (`studies/agent-harness-study/sources/agent-framework/python/packages/tools/tests/test_security.py:124-164`) — turning residual risk into a maintained, executable contract.
- **Config fingerprinting for sandbox reuse.** Hyperlight hashes tools+mounts+allow-lists into a fingerprint; any capability change forces sandbox rebuild so stale capabilities cannot persist (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Hyperlight/Internal/SandboxExecutor.cs:82-116`, `157-172`).
- **Structured subprocess IPC.** The CodeAct bridge speaks newline-delimited JSON with typed messages (`complete`/`error`/`tool_call`), unknown types ignored for forward compatibility (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.LocalCodeAct/Internal/ProcessBridge.cs:179-198`).
- **Interpreter-level denial as UX.** Monty resumes forbidden OS calls with a structured `PermissionError` instead of crashing, so the model receives actionable feedback (`studies/agent-harness-study/sources/agent-framework/python/packages/monty/agent_framework_monty/_monty_bridge.py:262-268`).
- **PATH-poisoning resistance in teardown.** `taskkill.exe` is resolved to its absolute System32 path so a compromised `PATH` cannot redirect the kill binary (`studies/agent-harness-study/sources/agent-framework/python/packages/tools/agent_framework_tools/shell/_killtree.py:39-47`).

## Tradeoffs

- **Usability vs. enforcement at the local tier.** Approval-in-the-loop is robust for interactive use but offers zero automated protection for unattended runs; the escape hatch (`acknowledge_unsafe`) is intentionally available but shifts all risk to the operator (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Tools.Shell/LocalShellExecutor.cs:46-49`).
- **AST allow-listing vs. expressiveness.** Blocking `getattr/setattr/open/import` makes LocalCodeAct safe-ish but excludes many legitimate data-processing programs; users must extend lists explicitly (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.LocalCodeAct/Resources/validator.py:435-444`).
- **Overlay vs. read-write Monty mounts.** Overlay gives free write containment but files vanish after the run; read-write enables artifact flow but writes through to the host, mitigated by byte caps (`studies/agent-harness-study/sources/agent-framework/python/packages/monty/README.md:144-145`).
- **Snapshot/restore vs. freshness.** Hyperlight trades per-invocation VM snapshot cost for guaranteed-clean state; the fingerprint mechanism adds rebuild latency whenever capabilities change (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Hyperlight/Internal/SandboxExecutor.cs:174-227`).
- **Best-effort teardown vs. complexity.** Multi-stage fallbacks (kill → rm -f → log) handle stuck daemons but accept possible container leaks rather than blocking the caller indefinitely (`studies/agent-harness-study/sources/agent-framework/python/packages/tools/agent_framework_tools/shell/_docker.py:520-574`).

## Failure Modes / Edge Cases

- **Timeouts disabled by default.** `LocalShellExecutorOptions.Timeout`/`DockerShellExecutorOptions.Timeout` are `null` = no timeout; the 30-second `DefaultTimeout` constant must be opted into explicitly (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Tools.Shell/LocalShellExecutorOptions.cs:75-80`, `LocalShellExecutor.cs:54-60`). A runaway approved command can hang the session forever.
- **No CPU/memory limits outside Docker/Monty.** `ProcessExecutionLimits` bounds wall-clock time and captured bytes only; a compute-spinning LocalCodeAct subprocess is limited solely by its 30s default timeout (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.LocalCodeAct/ProcessExecutionLimits.cs:15-28`).
- **SDK parity gaps.** Python rejects isolation-breaking `extra_run_args`; the .NET `ExtraRunArgs` are appended verbatim with no equivalent validation (compare `studies/agent-harness-study/sources/agent-framework/python/packages/tools/agent_framework_tools/shell/_docker.py:103-127` against `studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Tools.Shell/DockerShellExecutor.cs:410-413`). Similarly, Python's Docker tool has an `on_command` audit hook; no .NET counterpart was found.
- **Approval-name collision bypass.** If the shell tool's function name collides with another feature's auto-approved tool name, auto-approval rules match by name and bypass the human gate — warned about in both SDKs (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Tools.Shell/LocalShellExecutor.cs:331-338`).
- **Container leak on daemon failure.** If `docker kill` and `docker rm -f` both fail, the stateless container leaks and only an error log marks it (`studies/agent-harness-study/sources/agent-framework/python/packages/tools/agent_framework_tools/shell/_docker.py:561-574`).
- **mtime-coincidence capture misses.** Diff-based capture keys on (size, mtime); a same-size write preserving mtime_ns within one tick granularity would be invisible to capture on either stack (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.LocalCodeAct/Internal/FileMountHelper.cs:144-149`).
- **Policy evaluation is string-level.** Newline injection (`echo ok\nrm -rf /`) defeats single-line regex matching — documented and asserted in tests rather than mitigated (`studies/agent-harness-study/sources/agent-framework/python/packages/tools/tests/test_security.py:140`).
- **cmd.exe excluded from persistent mode.** Persistent cmd sessions throw `NotSupportedException`, forcing pwsh/POSIX (`studies/agent-harness-study/sources/agent-framework/dotnet/src/Microsoft.Agents.AI.Tools.Shell/LocalShellExecutor.cs:111-115`).
