## Summary

LangGraph's primary extension contract — `BaseCheckpointSaver` (`libs/checkpoint/langgraph/checkpoint/base/__init__.py:176`) — has a **dedicated, first-class conformance suite** in `libs/checkpoint-conformance`. The suite defines 9 capabilities (5 base required, 4 extended optional), auto-detects overrides, runs per-capability spec files, and emits a structured `CapabilityReport`. Fixtures and helpers (`test_utils.py`, `_delta_fixtures.py`, `initializer.py`) let third-party authors verify implementations via `@checkpointer_test` + `validate()` both standalone and inside pytest. `InMemorySaver` serves as the reference implementation and `InMemorySaver`/`AsyncPostgresSaver` showcase real conformance runs. No conformance equivalent exists for other extension points (`BaseChannel`, `BaseStore`, `SerializerProtocol`). Stability/breaking-change guarantees are externalized to `docs.langchain.com/oss/python/release-policy` and `versioning` links in every README; in-code guarantees are beta warnings for DeltaChannel surfaces rather than a versioned stability tier.

## Rating

**7 / 10** — Clear model with tests, explicit interfaces, and operational safeguards **for the checkpointer contract**, but incomplete coverage across the extension surface and weakly inlined stability guarantees.

**Rationale:** Checkpoint conformance is mature: explicit capability enum, override detection, 8-17 tests per capability (17 for `put`), isolated fixture generators, lifespan support for expensive setup, and `CapabilityReport.passed_all_base()`/`passed_all()` gates. Examples and self-tests use it. However (a) only one extension family is covered — `BaseChannel` (`libs/langgraph/langgraph/channels/base.py:19`), `BaseStore` (`libs/checkpoint/langgraph/store/base/__init__.py:708`), and `SerializerProtocol` have abstract interfaces but no conformance package; (b) stability documentation is a link to external policy, not an in-repo contract with SemVer tiers or deprecation windows; (c) DeltaChannel-related methods are explicitly beta/unstable (`libs/checkpoint/langgraph/checkpoint/base/__init__.py:66`, `149`, `340`, `387` and `libs/langgraph/langgraph/channels/delta.py:29`), lowering the durability claim. This matches the 7–8 band (clear model with operational safeguards) but not 9–10 (mature/durable/proven across all extensions and under failure/scale).

## Answers to Dimension Questions

**1. Are extension contracts tested?**

Yes — for the checkpointer contract, thoroughly. `libs/checkpoint-conformance` is a standalone PyPI package (`pyproject.toml:6-8` declares `langgraph-checkpoint-conformance` depending on `langgraph-checkpoint>=2.0.0`) providing 9 capability suites. Each suite has 8–17 behavioral tests (e.g., `test_put.py:370-388` lists 17 `put` tests) executed via `validate()` (`validate.py:45`). Capability detection (`capabilities.py:73-87`) auto-skips non-overridden extended methods, so partial implementations are testable. CI runs the package (`ci.yml:71,91`). Self-tests validate `InMemorySaver` (`checkpoint-conformance/tests/test_validate_memory.py:17-21` and `checkpoint/tests/test_conformance_delta.py:5-37`). Missing: no conformance harness for `BaseStore`, `BaseChannel`, or `SerializerProtocol` — those contracts are abstract methods raising `NotImplementedError` with no conformance runner discovered.

**2. Are fixtures provided for extension authors?**

Yes — rich fixtures scoped to checkpointer authors. `test_utils.py:19-137` gives factory helpers (`generate_checkpoint`, `generate_config`, `generate_metadata`, `put_test_checkpoint`, `put_test_checkpoints`) that handle `channel_versions`/`new_versions` wiring, plus assertion helpers (`assert_checkpoint_equal`, `assert_tuple_equal` at `test_utils.py:140-212`). `_delta_fixtures.py:20-99` provides `build_delta_chain` for delta-channel scenarios. `initializer.py:59-100` provides the ergonomic `@checkpointer_test` decorator with `skip_capabilities` filtering and `lifespan` for one-time DB setup/teardown, plus `RegisteredCheckpointer.create()`/`enter_lifespan()` context managers that yield fresh isolated savers per capability. `report.py:24-198` supplies `ProgressCallbacks` (dot, verbose, quiet) and `CapabilityReport` with `passed_all_base()` gate. No fixtures found for channel or store extension authors.

Documentation links (`checkpoint/README.md:58-68`, `checkpoint-conformance/README.md:19-23`) point to API reference and conceptual guides but no dedicated "writing a custom channel/store" guide was found in the isolated source scope.

## Architectural Decisions

- **Standalone conformance distribution.** `checkpoint-conformance` is a separate package (`pyproject.toml:6`) depending only on `langgraph-checkpoint` (`pyproject.toml:13-15`) and excluded from the monorepo dependency map in `AGENTS.md` downstream diagram, intentionally decoupling the harness from `langgraph` core (which already depends on `checkpoint`). This lets Postgres/SQLite/Redis/custom saver authors install only the harness plus the interface, aligning with the `uv.sources` path override for local dev (`pyproject.toml:71-72`). Tradeoff: `langgraph`-dependent delta tests import `langgraph` at test time despite it not being a declared dependency (`pyproject.toml:42-51` ty rule comments explain this intentional gap).

- **Capability-based, auto-detected test matrix.** Instead of a monolithic suite, capabilities are reified as `Capability(str, Enum)` (`capabilities.py:15-26`) partitioned into `BASE_CAPABILITIES` (5) and `EXTENDED_CAPABILITIES` (4) (`capabilities.py:30-48`). `_is_overridden()` (`capabilities.py:90-96`) checks `getattr(impl, method) is not getattr(BaseCheckpointSaver, method)`, so authors need not declare capabilities — the harness infers them. `validate()` (`validate.py:73-127`) then skips non-detected suites (`detected=False, passed=None, tests_skipped=1`). This enables partial implementations to get a `BASE` vs `BASE+PARTIAL` vs `FULL` report (`report.py:126-138`) without false failures. The filtering knobs `skip_capabilities` (`initializer.py:29`) and `capabilities` set (`validate.py:48`) give further control.

- **Isolated factory with lifespan.** `RegisteredCheckpointer` (`initializer.py:23-56`) stores an async generator factory plus an optional `LifespanFactory`. `create()` enters the generator once per capability (`validate.py:78`), guaranteeing a fresh saver per suite (no cross-capability state leakage). `enter_lifespan()` wraps the entire run for expensive setup (DB creation) as shown in `checkpoint-postgres` where `setup()`/`drop_database` patterns are expected (`README.md:109-124`). This mirrors pytest fixture scoping (function vs session) without requiring pytest.

- **Two-tier delta history verification.** Because `DeltaChannel` reconstructs state by replaying ancestor `checkpoint_writes` (`channels/delta.py:25-55`), the conformance suite includes a dedicated `delta_channel_history` capability with migration/seam scenarios (`test_delta_channel_history.py:150-268`). Simultaneously, `InMemorySaver` provides a storage-optimized override of `get_delta_channel_history` (`memory/__init__.py:142-223`) that walks `storage`/`blobs`/`writes` directly, while `BaseCheckpointSaver` provides the fallback parent-chain walk (`base/__init__.py:582-690`). Tests in `checkpoint/tests/test_memory.py:424-709` regression-guard the fallback path (including `TestBaseFallbackGetChannelWrites` with task-local re-entrancy checks), ensuring third-party savers inheriting the fallback still pass delta conformance (`test_conformance_delta.py:5-37`).

## Notable Patterns

- **Spec-as-data:** Each `spec/test_*.py` ends with `ALL_*_TESTS = [...]` and a `run_*_tests(saver, on_test_result)` executor that iterates the list, catches exceptions, reports via `on_test_result`, and returns `(passed, failed, failures)` — e.g., `test_put.py:370-411`. `validate.py:32-42` then maps `Capability -> runner` in `_RUNNERS`. Adding a new capability is adding an enum value, a method map entry, a spec file, and a runner entry — a regular extension point itself.

- **Beta-gated override warnings on destructive ops.** `copy_thread`, `prune`, `delete_for_runs`, and `get_delta_channel_history` docstrings explicitly warn that naive implementations break `DeltaChannel` reconstruction (e.g., `base/__init__.py:387-414` for `prune` detailing three safe strategies). This is an "unsafe default" disclosure pattern — correctness requires opt-in awareness.

- **Environment-driven snapshot cadence.** `DeltaChannel.snapshot_frequency` (`channels/delta.py:63,74-79`) plus system-wide `DELTA_MAX_SUPERSTEPS_SINCE_SNAPSHOT` (default 5000, env `LANGGRAPH_DELTA_MAX_SUPERSTEPS_SINCE_SNAPSHOT`, referenced in `base/__init__.py:79-81` and `channels/delta.py:50-55`) govern when `_DeltaSnapshot` blobs are written, bounding parent-chain walk length. The constant lives outside the extension interface, so custom savers cannot configure it per saver — a deliberate global bound.

## Tradeoffs

- **Depth vs breadth.** Investing in deep checkpointer conformance (9 capabilities, 40+ tests, delta history matrix, concurrency re-entrancy test at `checkpoint/tests/test_memory.py:519-561`) means other extension points (`BaseChannel`, `BaseStore`, `SerializerProtocol`) have zero conformance. An author writing a custom `BaseChannel` (e.g., a new CRDT) or `BaseStore` (e.g., DynamoDB adapter) must reverse-engineer correctness from `InMemorySaver`/`InMemoryStore` rather than run a harness. Verdict: high confidence for checkpointer authors, low for other extenders.

- **Auto-detection fragility.** `_is_overridden` identity check (`capabilities.py:90-96`) is simple but brittle: a subclass calling `super().aput` without overriding still registers as "overridden" (detected) and will be tested; a saver that overrides only the sync `put` but not `aput` will fail detection for `PUT` because only `aput` is mapped (`_CAPABILITY_METHOD_MAP:54-55` maps `PUT -> aput`). The sync surface is therefore untested by the async harness, even though `BaseCheckpointSaver` declares both.

- **Externalized versioning policy.** Pointing READMEs to `docs.langchain.com/oss/python/versioning` avoids duplicating policy but makes the contract unreviewable offline and untied to a specific commit. No in-repo `VERSIONING.md` or `CHANGELOG.md` was found in the isolated source scope, so an extension author cannot `git log` breaking changes or map them to capability additions without leaving the repo. The PR template's "describe breaking changes" (`PULL_REQUEST_TEMPLATE.md:22`) and `deprecated` decorators partially mitigate but are not a stability guarantee.

- **DeltaChannel beta exposure.** The newest, most complex feature (incremental channel storage with `_DeltaSnapshot` sentinel `"empty"` blobs at `memory/__init__.py:137`) is simultaneously the least stable (`channels/delta.py:29-36`, `base/__init__.py:66-87`). Extension authors must implement `get_delta_channel_history` correctly to pass delta conformance, yet the return shape `DeltaChannelHistory` (`base/__init__.py:149-174`: `writes` always present, `seed` omitted if walk hit root) is still beta — a risky foundation for third parties to build persistence layers on.

## Failure Modes / Edge Cases

- **Incomplete parent chain silently corrupts delta state.** As documented in `base/__init__.py:387-414`, a `prune("keep_latest")` that drops intermediate checkpoints + `checkpoint_writes` severs the chain to the nearest `_DeltaSnapshot`; `get_delta_channel_history` then returns `writes` with no `seed` (absent key means "start empty" per `base/__init__.py:158-169`), so reconstruction yields empty state with **no error raised**. Same for `delete_for_runs` deleting writes between head and snapshot (`base/__init__.py:340-346`) and `copy_thread` copying only the head (`base/__init__.py:361-371`). Conformance tests catch this for savers that run the `delta_channel_history` suite, but base-capability-only savers are unprotected.

- **Concurrency re-entrancy in `aget_delta_channel_history`.** `checkpoint/tests/test_memory.py:519-561` guards the fallback implementation against `threading.local()` vs task-local state: two concurrent `aget_delta_channel_history` calls on the same event-loop thread must not short-circuit each other to `writes=[]`. Custom savers overriding the async path with a thread-local guard would pass single-threaded tests but fail under `asyncio.gather`.

- **Migration plain-value seed handling.** `test_delta_channel_history.py:150-199` and `test_delta_channel_history.py:202-268` plus `memory/__init__.py:146-214` mixed-thread tests (`TestPreDeltaBlobTerminator` at `test_memory.py:563-709`) show that a pre-delta plain value (e.g., `BinaryOperatorAggregate` blob) must be treated as `seed` and its own writes must **still be replayed** (`test_history_seed_ancestor_own_writes_are_replayed`). Savers that skip the seed ancestor's writes will silently drop the first post-migration write — covered by conformance but easy to miss in manual implementations.

- **Incremental blob reconstruction.** `test_put.py:231-329` exercises `channel_values` reconstruction from incremental blobs (`new_versions` subset per step). A saver that stores only the latest `channel_values` snapshot per checkpoint without honoring `new_versions` incremental updates would pass simple round-trip tests but fail `test_put_incremental_channel_update`/`test_put_new_channel_added`/`test_put_channel_removed`.

- **Unsupported serializer types.** `test_memory.py:222-322` shows `JsonPlusSerializer` behavior with `allowed_msgpack_modules`: unregistered types warn (`_warned_unregistered_types`), strict `None` blocks and falls back to `model_dump()` dict. Custom savers that configure `serde` differently may change serialization semantics without conformance catching it (the suite uses the saver's own `serde`).

## Future Considerations

- Add conformance harnesses for `BaseStore` (`libs/checkpoint/langgraph/store/base/__init__.py:708`) and `BaseChannel` (`libs/langgraph/langgraph/channels/base.py:19`) mirroring the `checkpoint-conformance` pattern; without this, store/channel extensions remain ad-hoc and unverifiable.
- Inline the versioning/stability guarantee (stage: alpha/beta/stable per capability) adjacent to `capabilities.py:30-48` rather than relying solely on external `release-policy`/`versioning` links, and publish a `CHANGELOG.md` or `BREAKING_CHANGES.md` within the source tree so `git blame` on `BaseCheckpointSaver` reveals deprecation windows.
- Stabilize or version `DeltaChannelHistory` and `_DeltaSnapshot` (currently beta at `base/__init__.py:149` and `serde/types.py`) before recommending third-party saver investments; consider feature-flagging beta capabilities as opt-in in `validate()` rather than auto-detected.
- Extend `_is_overridden` detection to cover sync/async method pairs symmetrically (currently only `a*` methods are mapped at `capabilities.py:53-63`), or document that sync-only savers are out of scope for conformance.
- Provide a dedicated "Authoring a Custom Saver" guide under `docs/` with end-to-end example (sync + async, Delta-aware `prune`/`copy_thread`) analogous to the existing `checkpoint/README.md:58-68` interface list, reducing reliance on reading `InMemorySaver` source.
