## Summary

LangGraph builds lineage around a **persistent, parent-linked checkpoint chain** rather than an event log. Every superstep writes a `Checkpoint` whose metadata records `source` (input/loop/update/fork), `step`, a `parents` map of namespace→checkpoint-ID, and optionally the originating `run_id` (`studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/checkpoint/base/__init__.py:38-62`). Each checkpoint links to its predecessor via `CheckpointTuple.parent_config` and carries `pending_writes` keyed by task ID (`studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/checkpoint/base/__init__.py:139-146`). Task IDs are deterministic hashes of the checkpoint ID + node name + triggers (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_algo.py:616-623`), so writes can always be attributed to (thread, checkpoint-namespace, checkpoint, task) tuples — the same keying used by durable stores (`studies/agent-harness-study/sources/langgraph/libs/checkpoint-postgres/langgraph/checkpoint/postgres/base.py:66-88`).

Above this substrate, several causal-link layers exist: per-task config metadata (`langgraph_step/node/triggers/path/checkpoint_ns`) attached to every task (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_algo.py:654-660`); message-stream events tagged with that same metadata plus run IDs (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_messages.py:130-149`); interrupt/resume linkage via hashed interrupt IDs and special write channels (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/types.py:596-618`, `_loop.py:818-846`); and a stream-transformer layer that correlates subagent runs back to the LLM tool calls that spawned them via a task_id→tool_call_id map (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/stream/transformers.py:488-516`). The model is explicit, tested, and operational; the main gaps are partial model-version tracking (ephemeral stream metadata only), no provenance fields on long-term memory items (`BaseStore`), and no artifact-run association in this repo.

## Rating

**8 / 10.** Lineage is a first-class design concern with explicit interfaces (`CheckpointMetadata`, `CheckpointTuple`, `put_writes(task_id)`, `get_state_history`), deterministic identifiers that survive replay, and extensive tests asserting parent maps, sources, and run-config propagation. It falls short of 9–10 because model/provider versions are only captured in ephemeral stream metadata (not in durable checkpoint lineage), store items carry no provenance, artifact-run association is absent, and one cross-boundary tracing test is skipped in CI.

## Answers to Dimension Questions

1. **Can every output be traced to its inputs?**
   Yes at state and task granularity. Every state mutation lands as a checkpoint whose `parent_config` forms a walkable chain and whose metadata names `source`, `step`, `parents`, and (when resuming) the matching `run_id` (`studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/checkpoint/base/__init__.py:41-62`; `studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_loop.py:1125-1127`). Each contributing task's raw writes are stored separately under `(thread, ns, checkpoint_id, task_id)` (`studies/agent-harness-study/sources/langgraph/libs/checkpoint-postgres/langgraph/checkpoint/postgres/base.py:66-88`), so any value in a final answer's state can be attributed to the node/task that produced it. At message level, streamed tokens carry `langgraph_step/node/triggers/checkpoint_ns` metadata tying output text to the exact node execution (`studies/agent-harness-study/sources/langgraph/libs/langgraph/tests/test_pregel.py:6898-6915`). Tracing a *final answer sentence* back to the specific tool call works through message IDs: the AIMessage carries `tool_calls[].id` and the following `ToolMessage.tool_call_id` closes the loop (`studies/agent-harness-study/sources/langgraph/libs/prebuilt/langgraph/prebuilt/tool_node.py:808`) — but this link lives in message content, not in dedicated lineage metadata.

2. **Is provenance preserved through transformations?**
   Mostly. Reducer application (`apply_writes`) merges multiple task writes into channel values within a superstep; post-merge attribution survives only through `pending_writes`/`checkpoint_writes` (task-keyed), not inside `channel_values`. For delta channels, reconstruction replays the ordered write history along the ancestor chain, preserving which write produced what (`studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/checkpoint/base/__init__.py:629-649`). Fork/time-travel preserves provenance explicitly: forks record `"source": "fork"` and reuse the fork's parent checkpoint for subgraph replay positioning (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_loop.py:1040-1067`). One deliberate exception: writes to `UntrackedValue` channels are stripped before persistence (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_loop.py:439-454`), so those values are auditable only in-flight.

3. **Are model versions tracked in lineage?**
   Partially and ephemerally. Message-stream metadata includes `ls_provider`, `ls_model_type`, and `lc_versions` (LangChain package versions merged specially through configs) (`studies/agent-harness-study/sources/langgraph/libs/langgraph/tests/test_pregel.py:6908-6911`; merge logic at `studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/_internal/_config.py:87-99`). However `CheckpointMetadata` defines no model/model-version field (`studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/checkpoint/base/__init__.py:38-86`), so a checkpoint does not durably record which model produced the step. Concrete model identity/version must be recovered from external traces or message `response_metadata`.

4. **Can causal chains be audited?**
   Yes. Public APIs expose the whole chain: `get_state_history` streams snapshots with `parent_config`, metadata, tasks (with errors, interrupts, results) (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/main.py:1480-1531`); checkpointer `list(filter=...)` supports metadata-filtered audits; `stream_mode="debug"/"checkpoints"/"tasks"` projects live lineage including `parent_config` and per-task writes (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/debug.py:144-206`). Cross-process trace trees are maintained via callback managers carrying `run_id`/`parent_run_id` (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/callbacks.py:141-191`), verified by a nested-tracing test asserting contiguous `dotted_order`, matched `parent_run_id`s, and shared `trace_id` (`studies/agent-harness-study/sources/langgraph/libs/langgraph/tests/test_tracing_interops.py:113-118`) — though that test is currently skipped in CI (`test_tracing_interops.py:60`). Subagent runs additionally emit a machine-readable `cause` linking them to the triggering `tool_call_id` (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/stream/transformers.py:536-546`).

## Architectural Decisions

1. **Lineage as a persistent DAG, not an event log.** State snapshots are immutable nodes with `parent_config` edges; raw task writes are a separate append-only table joined by `(thread_id, checkpoint_ns, checkpoint_id, task_id, idx)` (`studies/agent-harness-study/sources/langgraph/libs/checkpoint-postgres/langgraph/checkpoint/postgres/base.py:66-88`). This makes "what did task X write" and "what preceded checkpoint Y" both O(1) lookups.
2. **Deterministic identity for replayability.** Checkpoint IDs use `uuid6(clock_seq=step)` (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_checkpoint.py:206-214`) and task IDs are hashes of checkpoint ID + namespace + triggers (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_algo.py:613-623`). Re-execution after crash/resume recomputes the same task IDs, which is what lets pending writes, resume maps, and interrupt IDs reconnect without a central registry.
3. **Namespace strings encode hierarchy.** Subgraph lineage lives in `checkpoint_ns` segments `graph|node:<task_id>` (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/_internal/_constants.py:87-90`), with a `checkpoint_map` configurable carrying ancestor namespace→checkpoint-ID pairs injected into every subgraph task (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_algo.py:741-744`) and surfaced back out via `patch_checkpoint_map` (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/_internal/_config.py:63-80`).
4. **Open, additive metadata contract.** `CheckpointMetadata` is `TypedDict, total=False` ("marked as total=False to allow for future expansion", `studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/checkpoint/base/__init__.py:37-38`), and user config metadata is folded into every persisted checkpoint (`get_checkpoint_metadata`, `base/__init__.py:757-775`). Extensible, but weakly typed.
5. **Special write channels with reserved indices.** Errors, interrupts, resumes, and schedules are written through the same write pipeline using negative indices (`WRITES_IDX_MAP = {ERROR: -1, SCHEDULED: -2, INTERRUPT: -3, RESUME: -4}`) so approval/error events get identical durability and auditability as normal state writes (`studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/checkpoint/base/__init__.py:788-795`).

## Notable Patterns

- **Lineage-as-config:** checkpoint coordinates (`thread_id`, `checkpoint_ns`, `checkpoint_id`, `checkpoint_map`) travel inside `RunnableConfig.configurable`, treated as "addressing its own checkpoint lineage" (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/_internal/_constants.py:98-105`).
- **Cross-payload correlation:** the streaming layer keeps a `task_id → tool_call_id` dict harvested from push-task inputs, then resolves a subagent's namespace segment `node:<task_id>` to recover its causing tool call — causal stitching across event payloads rather than a single enriched event (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/stream/transformers.py:416-421,488-516`).
- **Stable content identity:** message IDs are stamped before serialization (`ensure_message_ids`) precisely so replays produce the same UUID and traces don't double-count messages across streaming and node-return paths (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_messages.py:426-445`).
- **Run-level GC hooks:** `delete_for_runs(run_ids)` implies checkpoints/writes are associated with runs strongly enough to delete by run — an operational acknowledgment of run-scoped lineage (`studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/checkpoint/base/__init__.py:331-348`).
- **Test-enforced provenance propagation:** regression tests pin that `thread_id`, `run_id`, `assistant_id`, etc. propagate into stream metadata while secrets (`some_api_key`) do not (`studies/agent-harness-study/sources/langgraph/libs/langgraph/tests/test_pregel.py:6918-6969`), and that run configurables land in every historical checkpoint (`studies/agent-harness-study/sources/langgraph/libs/langgraph/tests/test_pregel_async.py:5547-5645`).

## Tradeoffs

- **String-encoded namespaces vs structured records:** `node:<task_id>|...` segments are compact and DB-friendly but require parsing/recasting (`recast_checkpoint_ns`, `studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/_internal/_config.py:38-49`) and string surgery in retry logic (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_retry.py:548,621`).
- **Config-metadata merging couples run config to durable storage:** arbitrary scalar metadata from every invocation is baked into checkpoint rows, requiring a maintenance-prone exclusion list (`EXCLUDED_METADATA_KEYS`, `studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/checkpoint/base/__init__.py:797-807`).
- **Attribution granularity vs storage cost:** keeping every task's writes separately doubles persistence relative to merged state; the DeltaChannel design (sentinel values + ancestor walks) trades read-time reconstruction work for write amplification savings, with counter bookkeeping in metadata (`counters_since_delta_snapshot`, `studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/checkpoint/base/__init__.py:63-86`).
- **Ephemeral vs durable lineage split:** rich causal context (model provider/version, run IDs on chunks) rides on callbacks/stream metadata that vanish unless a tracer persists it; durable lineage keeps only the checkpoint-level fields.

## Failure Modes / Edge Cases

- **Pruning can sever chains silently.** The saver docs explicitly warn that naive `keep_latest` pruning or `delete_for_runs` on ancestor writes will make DeltaChannel state "silently reconstruct as empty (no error raised)" (`studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/checkpoint/base/__init__.py:374-415,340-347`) — a known, documented corruption mode for lineage-dependent reconstruction.
- **Time-travel ambiguity between resume and replay.** Distinguishing "resume current head" from "replay old checkpoint" required gating on `source in ("update","fork")` plus `is_time_traveling` heuristics comparing `run_id`s (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_loop.py:851-900,1040-1067`) — subtle logic where getting it wrong drops cached RESUME writes or mis-anchors subgraphs.
- **Unattributed NULL_TASK_ID writes.** Writes outside any task accumulate under a null task ID with dedupe-by-channel semantics (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_loop.py:420-431`); their origin is the loop itself, not a node, limiting fine-grained attribution.
- **Cross-boundary trace continuity not continuously verified.** The one test asserting `parent_run_id`/`trace_id`/`dotted_order` integrity through LangSmith-style tracers is `@pytest.mark.skip("This test times out in CI")` (`studies/agent-harness-study/sources/langgraph/libs/langgraph/tests/test_tracing_interops.py:60-61`).
- **ID stability races.** Without pre-serialization ID stamping, replays could mint different message UUIDs per `get_state()` call — fixed by `ensure_message_ids` (`studies/agent-harness-study/sources/langgraph/libs/langgraph/langgraph/pregel/_messages.py:426-465`), evidence the team hit this class of bug.

## Future Considerations

- Persist model/provider identity (e.g., extend `CheckpointMetadata` with model name/version harvested from chat-model start events already flowing through `_messages.py`) so durable lineage answers "which model wrote this step".
- Add provenance fields (writer run/thread) to `BaseStore.Item` (`studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/store/base/__init__.py:51-64`) so retrieved-memory facts can be traced like channel writes.
- Provide a first-class lineage query API (e.g., writes-for-value lookup joining `checkpoint_writes` by channel+version) instead of requiring users to walk history manually.
- Un-skip or replace the CI-skipped nested-tracing test to keep run-tree linkage continuously verified.
- Replace string-parsed namespaces with structured coordinates where possible to reduce fragility in retry/replay code paths.

## Questions / Gaps

- **Artifacts:** No mechanism found in this repository linking produced artifacts (files, generated objects) to the run/task that created them. Search boundary: `grep -r "artifact"` across all libs matched only GitHub workflow files and test docstrings. Artifacts may be handled upstream (langchain-core / LangGraph Platform), not in this source.
- **Prompt-level lineage:** Inputs are recorded as checkpoint `channel_values` and task inputs, but there is no dedicated prompt-template/version field in checkpoint metadata; prompt provenance relies on user-supplied config metadata being merged (`studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/checkpoint/base/__init__.py:757-775`).
- **Retrieved-context provenance:** `BaseStore` items carry only `value/key/namespace/created_at/updated_at/score` (`studies/agent-harness-study/sources/langgraph/libs/checkpoint/langgraph/store/base/__init__.py:51-64`); no evidence that documents retrieved into state retain source pointers beyond whatever the application stores itself.
- **Model versions in durable lineage:** confirmed absent from `CheckpointMetadata` (see Q3); whether LangGraph Server adds it externally is out of scope for this isolated source.
