## Summary

The OpenHands V1 app server is a **surrounding control plane** for tool execution that lives in an external `openhands-sdk` package. The contract surfaces (`Event`, `ObservationEvent`, `ActionEvent`, `MessageEvent`, `ConversationStateUpdateEvent`) are imported and consumed but not defined here (`openhands/app_server/event_callback/webhook_router.py:57`, `openhands/app_server/event_callback/event_callback_models.py:30`, `openhands/app_server/event_callback/set_title_callback_processor.py:26`). Within this repo, **tool-result handling is dominated by three concerns**: (1) inbound webhook ingestion of SDK events and their persistence to a pluggable event service (`openhands/app_server/event/{filesystem,aws,google_cloud}_event_service.py`), (2) outbound serialization with **aggressive redaction** of secrets, API keys, URL credentials, and stack traces via Pydantic `field_serializer`, custom logging filters, and SDK `redact_*` utilities (`openhands/app_server/utils/logger.py:248-300,548-578`, `openhands/app_server/app_conversation/app_conversation_models.py:51-58,80-83`, `openhands/app_server/settings/settings_models.py:264-287`, `openhands/app_server/secrets/secrets_models.py:58-89`), and (3) MCP tool-error masking through `FastMCP('mcp', mask_error_details=True)` plus `fastmcp.exceptions.ToolError` (`openhands/app_server/mcp/mcp_router.py:8,43,113,210,284,351,418,485`).

Error envelopes are split between a typed hierarchy for HTTP (`OpenHandsError`/`AuthError`/`PermissionsError`/`SandboxError` in `openhands/app_server/errors.py:6-43`), value-based exceptions for LLM and provider failures (`openhands/app_server/types.py:19-34`, `openhands/app_server/integrations/service_types.py:171-198`), an analytics-only error taxonomy (`webhook_router.py:142-160`), and an `EventCallbackResult{Status}` envelope persisting callback outcomes (`openhands/app_server/event_callback/event_callback_result_models.py:11-31`). **Large results are NOT truncated or summarized inside this repo** — `_truncate_comment` exists only for outbound PR/MR comment bodies to third-party platforms (`openhands/app_server/integrations/service_types.py:222-228`); there is no equivalent for LLM tool outputs, which are delegated to the SDK. **Artifacts are referenced only as conversation links appended to PR descriptions** (`mcp_router.py:45-94,98-145`) and as a downloadable conversation-zip endpoint (`app_conversation_router.py:1550-1565`); there is no `Content.from_hosted_file` analogue for individual tool outputs. **Replay is implicitly supported** because every SDK event is serialized verbatim via `model_dump(mode='json')` and persisted to filesystem/S3/GCS, then re-ingested via the webhook (`filesystem_event_service.py:23-36`, `aws_event_service.py:56`, `google_cloud_event_service.py:60`, `webhook_router.py:150,452-460`).

## Rating

**6 / 10** — Present but inconsistent across layers. Within the app-server boundary there is a coherent, well-tested **outbound redaction contract** (env-var scanner, `SensitiveDataFilter`, `RedactURLParamsFilter`, `PluginSpec.source` URL credential redaction with explicit test coverage at `tests/unit/app_server/test_models.py:158-191`), a typed HTTP error hierarchy with a dedicated exception handler (`app.py:63-68`), a working MCP error-masking story via `mask_error_details=True`, and a typed success/error result envelope for event callbacks (`EventCallbackResultStatus.{SUCCESS,ERROR}`). However the **inbound tool-result contract is not owned by this repo** — it is imported from `openhands-sdk 1.21.1`, so there is no first-class `ToolMessage`/`Observation` schema or `tool_call_id` binding visible here. There is **no built-in truncation/summarization primitive for tool outputs** sent to the LLM, **no stack-trace scrubbing for LLM-bound messages** (only for logs), and **no artifact-reference helper** for individual tool results (only for whole conversations). `_redact_url_credentials` is locally reimplemented with a `TODO` to migrate to the SDK (`app_conversation_models.py:51-58`), and `_classify_error_type` matches error strings with substring heuristics (`webhook_router.py:142-160`) — durable, but not strictly typed. Deductions: spans multiple hierarchies, contract split between SDK and repo, and no LLM-output-length safeguards.

## Answers to Dimension Questions

1. **Is every tool result structured?** — Partially. SDK `ObservationEvent` is structured by construction (imported from `openhands-sdk`), but this repo does not own or document the schema. The app-server's own content envelopes are typed as `list[TextContent | ImageContent]` (`pending_message_models.py:23`, `app_conversation_models.py:361-364`). No `No clear evidence found` for an explicit "tool result schema" declared in this repo — the repo treats the SDK as the schema authority.
2. **Can the model distinguish success from failure?** — Yes, for what the repo controls. `EventCallbackResult.status` (`EventCallbackResultStatus.{SUCCESS,ERROR}`) and `AppSendMessageResponse.success: bool` give an explicit boolean; MCP errors surface as `ToolError`; HTTP routers return `Success` for 200-class and `JSONResponse({'error': ...})` for failure paths. Whether the **model** (LLM) sees a clear success/error is delegated to the SDK and not visible here.
3. **Are stack traces hidden from users/models?** — **Hidden from logs and HTTP responses, but not necessarily from the LLM.** Logging captures stack info for operators only (`StackInfoFilter` at `logger.py:96-110`); error `detail` strings are scrubbed through `redact_text_secrets(redact_api_key_literals(str(exc)))` before being shown to the user (`live_status_app_conversation_service.py:537`). No evidence of a similar scrub on the **observation text** sent back to the LLM.
4. **Are large results handled safely?** — **No, in this repo.** `_truncate_comment` exists only for outbound PR/MR comment bodies to third-party platforms (`integrations/service_types.py:222-228`); there is no `_truncate_tool_output`, no `MAX_OUTPUT`/`MAX_CONTENT` constant, and no summarization helper for LLM-bound tool results. That responsibility is delegated to the external SDK.
5. **Can tool results be replayed?** — **Yes, via persistence.** Every SDK `Event` (including `ObservationEvent`) is JSON-serialized (`filesystem_event_service.py:23-36`, `aws_event_service.py:56`, `google_cloud_event_service.py:60`) and re-ingested through the webhook (`webhook_router.py:150,452-460`). However, the **content of the observation payload** is whatever the SDK wrote — there is no dedicated replay-side normalization or de-duplication in the app-server.

## Architectural Decisions

- **Split contract ownership**: Tool/observation/result contracts live in the external `openhands-sdk 1.21.1` package. This repo imports them (e.g. `webhook_router.py:57`) and treats them as the authoritative schema; the app-server focuses on transport, persistence, and redaction. Trade-off: keeps schemas versioned in one place but means errors and edge cases surface in code outside this repo.
- **Pydantic-driven outbound redaction**: Sensitive fields opt into `field_serializer` that returns `str(SecretStr())` (= `"**********"`) by default, only revealing the secret when `SerializationInfo.context['expose_secrets'] == True`. This makes the default safe and the exposure path explicit (`settings_models.py:264-287`, `secrets_models.py:58-89`). `_redact_url_credentials` is intentionally reimplemented locally with a TODO to migrate to the SDK (`app_conversation_models.py:51-58`) — there is a known-but-pending centralization.
- **MCP error masking at the transport**: `FastMCP('mcp', mask_error_details=True)` (`mcp_router.py:43`) is a single point that decides whether internal exception text reaches the LLM-side MCP client; all tool raise sites use `ToolError(str(error))` (`mcp_router.py:113,210,284,351,418,485`). This is the strongest end-to-end guarantee visible in the repo.
- **String-based error taxonomy for analytics**: `_classify_error_type` (`webhook_router.py:142-160`) is heuristic (lowercase substring match) rather than typed. Trade-off: tolerant of arbitrary SDK exceptions, but brittle to error-message wording changes.
- **Webhook-driven ingestion**: Tool results (as `ObservationEvent`s) are pushed from the agent-server into the app-server via `POST /events/{conversation_id}` (`webhook_router.py:150,452-460`) rather than pulled. Trade-off: low latency, single ingest endpoint, but couples agent-server availability to app-server freshness.

## Notable Patterns

- **Pydantic `field_serializer` + `SecretStr` for opt-in secret exposure**: every secret-bearing field declares a serializer that checks `SerializationInfo.context['expose_secrets']` and defaults to masked (`secrets_models.py:58-100`, `settings_models.py:264-287`).
- **Layered logging redaction**: env-var scan → regex pattern → SDK `redact_api_key_literals` → SDK `redact_text_secrets` (`utils/logger.py:248-300`); uvicorn access log has a separate `RedactURLParamsFilter` (`utils/logger.py:548-578`) wired into both JSON and default log configs.
- **Typed HTTP exception hierarchy with a single FastAPI handler**: `OpenHandsError → AuthError | PermissionsError | SandboxError` (`errors.py:6-43`) plus one `@app.exception_handler(AuthenticationError)` (`app.py:63-68`).
- **Webhook ingest + filesystem/cloud pluggable storage**: same `Event` shape is round-tripped through filesystem, S3, and GCS implementations (`event/{filesystem,aws,google_cloud}_event_service.py`).
- **Conversation link artifact rather than inline content**: large PR descriptions get a `[continue refining the PR]({conversation_url})` link (`mcp_router.py:45-94`), keeping LLM tool-result context small.

## Tradeoffs

- **External contract dependency vs. internal clarity**: by importing `Event`/`ObservationEvent`/`ActionEvent` from the SDK, this repo avoids duplicating schema logic, but loses the ability to evolve the tool-result contract without an SDK bump.
- **Layered redaction cost**: every outbound model that touches a secret field must wire the `expose_secrets` context correctly; missing it leaks `**********` to authenticated callers and breaks SaaS integrations (`settings_models.py:276-287`, `secrets_models.py:58-89`).
- **String-based error classification vs. typed SDK exceptions**: substring matching (`webhook_router.py:142-160`) is forgiving but couples dashboards to exact error wording in upstream packages.
- **`mask_error_details=True` is server-wide**: a single toggle on the FastMCP server (`mcp_router.py:43`) decides whether the model ever sees stack traces from MCP tools — too coarse to expose details for some tools and not others.
- **No tool-output truncation in this layer**: any large observation passes through verbatim; the LLM receives whatever the SDK wrote. The repo's only truncation primitive targets PR-comment platforms, not model context (`integrations/service_types.py:222-228`).
- **Artifact references are conversation-scoped, not tool-scoped**: only whole-conversation links/zips exist (`mcp_router.py:45-94`, `app_conversation_router.py:1550-1565`); individual large tool outputs cannot be linked out via a stable handle.

## Failure Modes / Edge Cases

- **Missing `expose_secrets` context**: `field_serializer` always defaults to `"**********"`; if a downstream SaaS path forgets to pass `context={'expose_secrets': True}`, the secret arrives masked and downstream calls (e.g. remote sandbox credential lookup) silently fail (`settings_models.py:264-287`, `secrets_models.py:58-89`).
- **SDK pin lag**: `_redact_url_credentials` is locally reimplemented because the SDK pin is missing `redact_url_credentials` (`app_conversation_models.py:51-58`). If the SDK version diverges from the local regex, URL-credential redaction can drift between layers.
- **`mask_error_details=True` blanket behavior**: any MCP tool that needs to surface a structured, model-actionable failure (e.g. "missing required arg `path`") gets masked the same way as a stack trace (`mcp_router.py:43`).
- **Webhook availability**: agent-server events are pushed via `POST /events/{conversation_id}`; if the app-server is unreachable, observation events are dropped on the floor for that interval (`webhook_router.py:150,452-460`). The DB-backed callback service retries are unrelated to event persistence.
- **`_classify_error_type` brittleness**: `'budget' in msg_lower` matches unrelated log lines; `'cancel'` matches any phrase containing "cancel" (`webhook_router.py:142-160`). Re-wording in upstream packages silently re-classifies metrics.
- **No observation-content scrub before re-display**: error task detail is redacted (`live_status_app_conversation_service.py:537`) but the observation payload itself is not — internal paths/hostnames in successful outputs can still reach the model.
- **Conversation export lock contention**: `ExportTooLarge` / `ExportAlreadyRunning` returned to client without retry guidance (`app_conversation_router.py:1550-1665`).

## Future Considerations

- **Centralize URL-credential redaction in the SDK** and delete the local `_redact_url_credentials` implementation once `openhands.sdk.utils.redact.redact_url_credentials` is available — closes a TODO at `app_conversation_models.py:51-58`.
- **Add a typed `ToolResult` envelope in this repo** (separate from SDK `ObservationEvent`) if cross-layer transport ever needs to mutate or sanitize the observation payload independently of the SDK.
- **Introduce a tool-output length policy** (truncation, summarization, or hosted-link artifact) — the current gap is the absence of any `MAX_*` constant or `_truncate_tool_output` helper in this repo.
- **Replace substring error classification** with a typed taxonomy in `_classify_error_type` (`webhook_router.py:142-160`) — at minimum a regex/constant table with tests.
- **Per-tool MCP error masking** to replace the server-wide `mask_error_details=True` (`mcp_router.py:43`).
- **Redact observation payloads** with the same `redact_text_secrets(redact_api_key_literals(...))` chain used for error `detail` (`live_status_app_conversation_service.py:537`), applied before any observation is forwarded to the LLM.
