## Summary

Letta models every tool outcome as a typed `ToolExecutionResult` envelope (`status ∈ {"success","error"}`, `func_return`, `stdout`, `stderr`, `sandbox_config_fingerprint`) defined at `letta/schemas/tool_execution_result.py:8-18` and produced by an executor factory at `letta/services/tool_executor/tool_execution_manager.py:32-65`. Errors are normalized for the model through a single helper `get_friendly_error_msg` (`letta/utils.py:1091-1097`, capped at `MAX_ERROR_MESSAGE_CHAR_LIMIT=1000` at `letta/constants.py:430`), then re-wrapped at the persistence layer into a `Message(role=tool)` whose `tool_returns[i].status` and `tool_returns[i].func_response` carry the `{"status":"OK"|"Failed","message":..., "time":...}` envelope produced by `package_function_response` (`letta/system.py:150-168`). Cancellation, denial, and rule-violation paths route through dedicated `ToolReturn(status="error", func_response=...)` constructors (`letta/server/rest_api/utils.py:230-264`, `letta/agents/helpers.py:501-505`). Stack traces from the host process are recorded in the step error record (`letta/agents/letta_agent.py:495-501`, `letta/services/tool_executor/tool_execution_manager.py:141,154`) but are not placed on the model-visible `func_response`; the only model-visible traceback-bearing text is the `e2b.error.traceback` that is appended to `execution.logs.stderr` (`letta/services/tool_sandbox/e2b_sandbox.py:137`, `letta/services/tool_executor/tool_execution_sandbox.py:384`). Large results are bounded per-tool by `return_char_limit` (default 50_000, `letta/schemas/tool.py:51-56`, `letta/constants.py:438-439`) and truncated via `FUNCTION_RETURN_VALUE_TRUNCATED` (`letta/constants.py:200-203`) or `validate_function_response` (`letta/utils.py:898-939`); additional sandbox-timeouts (`tool_settings.tool_sandbox_timeout`, `letta/services/tool_sandbox/local_sandbox.py:197-207`) and output-size guards (`letta/services/tool_executor/files_tool_executor.py:36-46`) back the runtime. Replay is supported by stable `tool_call_id` IDs (`letta/schemas/letta_message.py:38-49`, `letta/schemas/letta_message.py:199-303`), and the `MessageManager` ships a backfill migration for a known historical gap (`letta/services/message_manager.py:30-114`). Artifacts are linked through the `LettaImage(file_id=…)` schema (`letta/schemas/letta_message_content.py:80-88`) and through the `tool_returns[*].tool_return` multi-content union (`letta/schemas/letta_message.py:38-49`, `letta/schemas/letta_message_content.py:145-179`).

## Rating

**7 / 10** — Clear model with tests, explicit interfaces, and operational safeguards. The `ToolExecutionResult` envelope is the only return type every executor must produce, the `status`/`func_return`/`stdout`/`stderr` fields are typed in Pydantic, and the failure normalization funnel (`get_friendly_error_msg` → `package_function_response`) is applied consistently across core, builtin, sandbox, MCP, files, and composio executors. Truncation, timeouts, and per-tool `return_char_limit` give operational safety. Gaps: a per-call error sub-discriminator beyond `success`/`error` (e.g., for retryable vs terminal) does not exist, the error envelope reaching the model is a JSON string with a `status` key rather than a typed `ErrorContent`, stack-trace handling differs between subprocess / in-process / e2b paths, and the global HTTP exception handler (`letta/server/rest_api/app.py:435-473`) intentionally suppresses `str(exc)` from API responses — helpful for end users but not the same as a model-facing redaction policy.

## Answers to Dimension Questions

1. **Is every tool result structured?** Yes. All six executors (core, builtin, sandbox, files, MCP, composio) return a typed `ToolExecutionResult(status, func_return, agent_state, stdout, stderr, sandbox_config_fingerprint)` (`letta/schemas/tool_execution_result.py:8-18`). Persisted form: a `Message(role=tool)` carrying `tool_returns: List[ToolReturn(tool_call_id, tool_return, status, stdout, stderr)]` (`letta/schemas/letta_message.py:279-303`). The result is normalized at `letta/server/rest_api/utils.py:475-498` into the on-the-wire `{"status":"OK"|"Failed","message":...,"time":...}` JSON via `package_function_response` (`letta/system.py:150-168`).
2. **Can the model distinguish success from failure?** Yes. Two discriminators reach the model: (a) the `status` field on each `ToolReturn` (`letta/schemas/letta_message.py:45`), and (b) the `status: "OK" \| "Failed"` key inside the packaged `func_response` JSON string (`letta/system.py:150-168`). Error text is also prefixed `"Error …"` by `get_friendly_error_msg` (`letta/utils.py:1091-1097`), giving a textual cue independent of JSON.
3. **Are stack traces hidden from users/models?** Partially. Host-side tracebacks are recorded only in `stderr` of `ToolExecutionResult` and in step metrics (`letta/services/tool_executor/tool_execution_manager.py:141,154`, `letta/agents/letta_agent.py:495-501`); the `func_return` always carries the friendly message. The E2B path appends `execution.error.traceback` into `execution.logs.stderr` (`letta/services/tool_sandbox/e2b_sandbox.py:137`, `letta/services/tool_executor/tool_execution_sandbox.py:384`), which becomes part of `ToolExecutionResult.stderr` and therefore part of the persisted `Message.tool_returns[i].stderr` — that field is plumbed to the model on Anthropic-style payloads (`letta/schemas/letta_message.py:47-48`). The HTTP error envelope explicitly suppresses `str(exc)` from non-debug clients (`letta/server/rest_api/app.py:466-473`). There is no global policy that strips a `ToolReturn.stderr` payload from model-facing content; visibility depends on which LLM adapter renders it.
4. **Are large results handled safely?** Yes. Two layers: per-tool `return_char_limit` (default 50 000) is enforced both at `ToolExecutionManager` (`letta/services/tool_executor/tool_execution_manager.py:124-129`) and in `validate_function_response` (`letta/utils.py:898-939`). File-tool outputs are paginated, capped at 1 000 matches / 50 MB per file / 200 MB total (`letta/services/tool_executor/files_tool_executor.py:36-46`). `conversation_search` results default to `RETRIEVAL_QUERY_DEFAULT_PAGE_SIZE` and explicitly filter tool-role messages to prevent context blow-up (`letta/services/tool_executor/core_tool_executor.py:138-167`). Subprocess tools enforce `tool_settings.tool_sandbox_timeout` (`letta/services/tool_sandbox/local_sandbox.py:197-207`). No "automatic summarization" layer was found: truncation is character-based, not semantic.
5. **Can tool results be replayed?** Partially. Each `Message` carries a stable `id`, `tool_call_id`, `run_id`, `step_id`, `seq_id` (`letta/schemas/letta_message.py:68-101`), and `ToolReturnMessage.tool_returns[i].tool_call_id` keys each return to its call (`letta/schemas/letta_message.py:299-303`). The `MessageManager` ships a migration that backfills missing `tool_call_id`s from a known historical bug (`letta/services/message_manager.py:30-114`). There is no content-addressable artifact store — replays reproduce from the persisted `Message` rows. `tool_returns[i].func_response` is a string that round-trips through `package_function_response` and survives re-serialization (`letta/system.py:150-168`).

## Architectural Decisions

- **One envelope, two layers.** `ToolExecutionResult` is the executor-internal envelope (typed, includes `agent_state`, `sandbox_config_fingerprint`); `ToolReturn` is the persisted/on-the-wire envelope (status, tool_return payload, stdout, stderr, tool_call_id). The transition is at `letta/server/rest_api/utils.py:475-498`, which writes the `func_response` already packaged so downstream adapters do not need to re-wrap.
- **Success/error as two-state discriminator.** No "retryable" / "rate-limited" / "context_overflow" sub-discriminator exists at the model boundary; everything collapses into `success` / `error` with `func_return` text. Retriable cues are conveyed by exception name in the friendly message (e.g., `RateLimitExceededError`, `ContextWindowExceededError` at `letta/errors.py:352-383`) rather than by a typed field.
- **Error text normalization is centralized.** `get_friendly_error_msg` is the single funnel for converting a host exception into a model-facing string (`letta/utils.py:1091-1097`). It is invoked by core, sandbox, files, MCP, builtin executors and by the orchestrator's outermost except clause. Cap at 1 000 chars via `MAX_ERROR_MESSAGE_CHAR_LIMIT` (`letta/constants.py:430`) prevents traceback-sized blobs from sneaking through if a custom tool raises something the helper doesn't abbreviate.
- **Cancellation and denial get their own constructors.** User cancellation → `create_tool_returns_for_denials` produces a `ToolReturn(status="error", func_response="Error: request to call tool denied. User reason: …")` (`letta/server/rest_api/utils.py:230-264`). Tool-rule violations → `_build_rule_violation_result` (`letta/agents/helpers.py:501-505`). This avoids the failure being indistinguishable from a tool crash.
- **Per-call stdout/stderr is plumbed through.** Unlike many frameworks, `ToolReturn` keeps `stdout: List[str]` and `stderr: List[str]` as first-class fields (`letta/schemas/letta_message.py:47-48`), giving adapters the option to surface them to the model (Anthropic-style) or hide them (OpenAI-style).
- **Tracebacks are demoted to telemetry, not deleted.** `traceback.format_exc()` is recorded into `stderr` for diagnostics (`letta/services/tool_executor/tool_execution_manager.py:141,154`, `letta/services/tool_executor/sandbox_tool_executor.py:147`) and into the step error record (`letta/agents/letta_agent.py:495-501`). They are not stripped from the model-facing envelope by a global policy — they live in a side field whose visibility is adapter-dependent.
- **Artifact references via typed content union.** Multi-modal returns use `ToolReturn.tool_return: str \| List[LettaToolReturnContentUnion]` where the union is `TextContent \| ImageContent` (`letta/schemas/letta_message.py:38-49`, `letta/schemas/letta_message_content.py:145-179`). Images can be referenced as `LettaImage(file_id, media_type, data, detail)` (`letta/schemas/letta_message_content.py:80-88`), giving stable references into the file store.
- **Sandbox boundary is a hard separator.** All non-core, non-builtin, non-files, non-MCP, non-Composio tools go through `SandboxToolExecutor` (`letta/services/tool_executor/sandbox_tool_executor.py:24-194`). Subprocess execution is wrapped by `parse_out_function_results_markers`, which uses a length prefix + MD5 checksum to detect corruption (`letta/services/tool_sandbox/local_sandbox.py:253-275`). Failure of the marker check raises an exception that becomes `"Function ran, but output is corrupted."`.
- **Truncation is character-based and tied to the tool, not the model.** `Tool.return_char_limit` lives on the schema (`letta/schemas/tool.py:51-56`); truncation suffix uses an explicit "NOTE: function output was truncated …" message (`letta/constants.py:200-203`, `letta/utils.py:920-937`). No token-based compaction of tool results was found; large results either truncate or paginate (e.g., `grep_files` `letta/services/tool_executor/files_tool_executor.py:521-534`).
- **HTTP layer treats tool errors as best-effort user errors.** `generic_error_handler` returns a sanitized `"An unknown error occurred"` payload (`letta/server/rest_api/app.py:435-473`), and a per-exception HTTP-code table (`letta/server/rest_api/app.py:557-612`) covers all the named `LettaError` subclasses (`letta/errors.py:11-492`). Sentry integration is conditional on `SENTRY_ENABLED` (`letta/server/rest_api/app.py:463-464`).

## Notable Patterns

- **Typed `ToolExecutionResult` envelope with `success_flag` helper.** Boolean derived from `status`, giving adapters a clean property to switch on (`letta/schemas/tool_execution_result.py:16-18`).
- **Single funnel for friendly error text.** `get_friendly_error_msg` is called from at least seven call sites; changes to error formatting happen in one place (`letta/utils.py:1091-1097`).
- **Deterministic sandbox envelope parsing.** `parse_out_function_results_markers` validates length + MD5 to detect corrupted payloads, then re-emits only the JSON-encoded base64 result (`letta/services/tool_sandbox/local_sandbox.py:253-275`, `letta/services/helpers/tool_parser_helper.py:12-32`).
- **Cancellation is a first-class path.** `CancelledError` is caught separately and returns a friendly message rather than a traceback (`letta/services/tool_executor/tool_execution_manager.py:131-142`). Mid-stream `CancelledError` in E2B is wrapped as `"Execution cancelled. Transient failure, please retry."` (`letta/services/tool_sandbox/e2b_sandbox.py:103-110`).
- **SSE error event for mid-stream failures.** `LettaErrorMessage(error_type, message, detail)` is emitted as `event: error` with a discriminating `error_type` for `internal_error`, `cleanup_error`, and `context_window_overflow_in_system_prompt` (`letta/agents/letta_agent_v3.py:670-735`). This is the closest analogue to a typed error envelope seen in the framework.
- **Backfill migration for tool IDs.** `backfill_missing_tool_call_ids` was written specifically for an Oct 1–6, 2025 incident where `tool_call_id` could be missing on persisted messages; it re-derives from adjacent assistant tool_calls (`letta/services/message_manager.py:30-114`). This is concrete evidence that replay/idempotency was treated as a real requirement.
- **`tool_return_message` discriminated union.** `LettaMessageUnion` discriminates on `message_type` including `tool_return_message` (`letta/schemas/letta_message.py:463-478`); clients parse by `message_type` rather than parsing a generic message.
- **MCP expected-error whitelisting.** `MCP_EXPECTED_ERROR_CLASSES = {"McpError", "ToolError"}` uses class-name string match to avoid pinning to specific MCP package versions (`letta/services/tool_executor/mcp_tool_executor.py:17-19`); this is fragile to upstream renames but pragmatic for a vendored interface.
- **Tool-rule violations get a distinct prefix.** `[ToolConstraintError]` is prepended (`letta/agents/helpers.py:504`), giving the model a way to distinguish rule rejection from generic tool failure without parsing the message body.

## Tradeoffs

- **`func_return` shape is `Any`.** The `ToolExecutionResult.func_return` field is typed `Optional[Any]` (`letta/schemas/tool_execution_result.py:10`). Adapters must inspect the runtime value to know whether to JSON-encode it; serialization is done ad-hoc (`letta/services/tool_executor/tool_execution_manager.py:124-129`, `letta/services/tool_executor/builtin_tool_executor.py:138-146`) and can drift.
- **No structured error sub-types at the model boundary.** Retryable vs terminal, rate-limited vs validation, are all surfaced as `status="error"` with text cues only. A model trying to route on "should I retry this tool call?" must rely on string parsing of `func_return`.
- **Traceback leakage through `stderr`.** `ToolReturn.stderr` carries `execution.error.traceback` for E2B (`letta/services/tool_sandbox/e2b_sandbox.py:137`, `letta/services/tool_executor/tool_execution_sandbox.py:384`) and `traceback.format_exc()` from the host process (`letta/services/tool_executor/tool_execution_manager.py:141,154`). Whether this reaches the model depends on the LLM adapter's rendering policy; there is no central stripper.
- **Pydantic `Message.role=tool` is the carrier, but `ToolReturnMessage.tool_return` (singular, deprecated) coexists with `tool_returns` (list).** Both `tool_returns: List[ToolReturn]` and the deprecated single-call fields are present on the schema (`letta/schemas/letta_message.py:295-303`), increasing the surface area clients must parse.
- **Truncation is character-based, not semantic.** 50 000 chars can still be 12 000+ tokens; `validate_function_response` warns but does not auto-summarize (`letta/utils.py:920-937`). No `ToolResultCompactionStrategy`-equivalent was found in the agent runtime.
- **HTTP layer redaction is decoupled from tool-error redaction.** `error_handler_with_code` returns `str(exc)` for HTTP responses (`letta/server/rest_api/app.py:534-542`), while `get_friendly_error_msg` returns a deliberately short message for the model (`letta/utils.py:1091-1097`). The two policies drift.
- **Sandbox success depends on `process.returncode == 0`, not on the marker being present.** `local_sandbox._execute_tool_subprocess` will report `status="success"` for a subprocess that exits 0 but emits no marker (`letta/services/tool_sandbox/local_sandbox.py:216-229`); the `func_return` would then be `None` and the model would see an empty success — recoverable but awkward.

## Failure Modes / Edge Cases

- **Subprocess crashes with no marker.** `parse_out_function_results_markers` returns `("", data)` when the marker is absent (`letta/services/tool_sandbox/local_sandbox.py:258-261`), and the orchestrator will return `func_return=None` with `status="success"` if `process.returncode == 0`. The model sees a `None`/empty successful tool call.
- **Subprocess emits a marker whose checksum mismatches.** The marker check raises `Exception("Function ran, but output is corrupted.")` (`letta/services/tool_sandbox/local_sandbox.py:271-273`), which the orchestrator catches and emits through `get_friendly_error_msg` — the model sees a friendly error, but no diagnostic detail.
- **E2B sandbox returns `execution.results = None` and `execution.error = None`.** Path raises `ValueError("Tool {self.tool_name} returned execution with None")` (`letta/services/tool_sandbox/e2b_sandbox.py:161`), bubbles up to the orchestrator's outer `except Exception` (`letta/services/tool_executor/tool_execution_manager.py:143-155`), and is re-emitted as a friendly error.
- **Timeouts.** Local subprocess timeout converts to `TimeoutError` with `Executing tool {tool_name} timed out after {seconds} seconds.` (`letta/services/tool_sandbox/local_sandbox.py:207`), with the subprocess terminated then killed. E2B cancellation converts to `"Execution cancelled. Transient failure, please retry."` (`letta/services/tool_sandbox/e2b_sandbox.py:110`). HTTP boundary: `LettaMCPTimeoutError` → 408 (`letta/server/rest_api/app.py:577`).
- **MCP `ExceptionGroup` with multiple inner errors.** Only single-exception `ExceptionGroup` is unwrapped (`letta/services/tool_executor/mcp_tool_executor.py:70-74`); multi-error groups fall through to the unexpected-error re-raise and become a friendly message at the orchestrator.
- **Cancellation from the orchestration layer.** `asyncio.CancelledError` is caught separately and returns a friendly error without traceback (`letta/services/tool_executor/tool_execution_manager.py:131-142`).
- **Pending approval while a tool call is mid-flight.** `PendingApprovalError` returns 409 with `error_code=PENDING_APPROVAL` (`letta/errors.py:48-56`), preventing double-execution.
- **Concurrent run / busy conversation.** `ConversationBusyError`, `MemoryRepoBusyError`, `NoActiveRunsToCancelError`, `ConcurrentUpdateError` all return 409 with structured `details` (`letta/errors.py:81-123`), letting clients decide whether to retry.
- **Step-level exceptions after the LLM has emitted tokens.** Caught in the agent loop; `message.is_err = True` is set if `settings.track_errored_messages` is enabled and `step_progression <= RESPONSE_RECEIVED` (`letta/agents/letta_agent.py:506-516`). The model is not re-fed the error in-band; it surfaces only on the next request.
- **Truncation that hides an actionable suffix.** `FUNCTION_RETURN_VALUE_TRUNCATED` appends a NOTE after the truncated content (`letta/constants.py:200-203`). If `func_return` is a `dict`, `validate_function_response` returns a string-truncated form (`letta/utils.py:920-937`), losing structured keys. No model-visible indication distinguishes "the dict was originally a dict" from "the original was already a string".

## Future Considerations

- **Add a typed `ErrorContent` (or `status: Literal["success","error","retry","rate_limited","context_overflow"]`) at the `ToolReturn` level.** The current `Literal["success","error"]` (`letta/schemas/letta_message.py:45`) forces downstream routing by text-parsing; promoting to a small enum of stable sub-states would let adapters route without parsing `func_return`. Candidates: `RateLimitExceededError`, `ContextWindowExceededError`, `LLMConnectionError` are all already classified (`letta/errors.py:259-316`).
- **Centralize redaction of `ToolReturn.stderr` for the model boundary.** Today, stderr is plumbed through `letta/schemas/letta_message.py:47-48` and adapter-dependent. A single policy (e.g., strip if `len(stderr) > N` or always strip traceback-pattern lines) would close the silent-leak risk in `letta/services/tool_sandbox/e2b_sandbox.py:137` and `letta/services/tool_executor/tool_execution_manager.py:141,154`.
- **Promote `tool_execution_result.stdout` / `stderr` to first-class summaries when exceeding thresholds.** `files_tool_executor` already paginates (`letta/services/tool_executor/files_tool_executor.py:521-534`); a similar convention for `run_code` / `run_code_with_tools` (`letta/services/tool_executor/builtin_tool_executor.py:138-146`) would close the gap where massive stdout is silently dropped by char-limit truncation.
- **Token-aware `return_char_limit`.** Currently character-based (`letta/utils.py:898-939`, `letta/services/tool_executor/tool_execution_manager.py:124-129`). Switching to a token-aware limit aligned with `ContextWindowExceededError` would reduce context-window pressure more predictably.
- **Promote the `LettaErrorMessage(error_type=..., message=..., detail=...)` SSE event to be reusable for tool failures.** Today it is only emitted on mid-stream agent failures (`letta/agents/letta_agent_v3.py:670-735`). Reusing it for tool-level errors would give SSE clients a consistent error envelope across the two phases.
- **Backfill `Message.tool_call_id` for parallel tool calls.** `backfill_missing_tool_call_ids` handles the single-call path (`letta/services/message_manager.py:30-114`) but does not address parallel `tool_calls` arrays with mismatched IDs — a related correctness gap that should be reviewed.
- **Tighten MCP error-class detection.** `MCP_EXPECTED_ERROR_CLASSES` uses class-name string match (`letta/services/tool_executor/mcp_tool_executor.py:17-19`). If MCP libraries rename `McpError`/`ToolError`, expected errors would be re-raised as unexpected and surface as tool crashes; pin to a specific MCP version or import via a `try/except ImportError` shim.
- **Persist error fingerprint alongside `stderr`.** Today the friendly message is text-only. Persisting `exception_class`, `sandbox_config_fingerprint`, `run_id`, `step_id` alongside `Message` would let clients filter/group by error class without re-running the tool.

## Questions / Gaps

Searches in `letta/services/tool_executor`, `letta/agents`, and `letta/services/summarizer` returned no such module. Existing summarization (`letta/services/summarizer`) operates on the conversation log, not on individual tool returns.
- No clear evidence found of a global redaction policy for `ToolReturn.stderr` content sent to the model. Whether stderr reaches the model depends on the LLM adapter's rendering (`letta/schemas/letta_message.py:47-48`); no central `redact_stderr` filter was found.
- No clear evidence found of a "max consecutive tool errors" guard in the agent loop. Timeouts are enforced at the sandbox layer (`letta/services/tool_sandbox/local_sandbox.py:197-207`), but no per-step `max_consecutive_errors_per_request` analogue surfaced.
- No clear evidence found of a structured `error_code` field at the model boundary. `details` exists on the HTTP envelope (`letta/server/rest_api/app.py:534-542`) and on `LettaError.details` (`letta/errors.py:30-43`) but is not propagated through `ToolReturn.tool_returns[i]`.
- Whether `ToolReturn.tool_return: Union[str, List[LettaToolReturnContentUnion]]` (`letta/schemas/letta_message.py:40-44`) round-trips perfectly through all LLM adapters was not directly verifiable from this analysis. Adapters under `letta/adapters/` parse this union, but no explicit adapter-level contract test was found.
