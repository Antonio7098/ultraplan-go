## Summary

CrewAI implements tool execution through **two parallel pipelines that produce string-only payloads**: the "text/ReAct" path (`ToolUsage._use` / `_ause`, `lib/crewai/src/crewai/tools/tool_usage.py:469-707` and `lib/crewai/src/crewai/tools/tool_usage.py:222-467`) and the "native function-calling" path (`execute_single_native_tool_call`, `lib/crewai/src/crewai/utilities/agent_utils.py:1399-1633` plus `lib/crewai/src/crewai/agents/crew_agent_executor.py:876-1071`). Both paths funnel results through `format_output_for_agent` (`lib/crewai/src/crewai/tools/structured_tool.py:54-83`, `lib/crewai/src/crewai/utilities/agent_utils.py:1386-1396`) which, when a `result_schema` is supplied, validates and serializes the result via `result_schema.model_validate(...).model_dump_json()` and falls back to `str(raw_result)` on schema failure. The contract is **a single `str` field**, not a structured envelope, so the model can only distinguish success from failure by string prefix (`"Error executing tool: ..."`, `"I encountered an error..."`, `"Action '<name>' don't exist..."`) or by a separate event stream. Errors are caught at multiple boundaries and converted to **i18n-templated plain-text strings** (`lib/crewai/src/crewai/translations/en.json:46-56`), then delivered to the model as a `"role": "tool"` chat message (`lib/crewai/src/crewai/utilities/agent_utils.py:1604-1609`, `lib/crewai/src/crewai/agents/crew_agent_executor.py:1082-1088`) or, for the text path, appended as `\nObservation: {result}` to the agent's previous assistant text (`lib/crewai/src/crewai/utilities/agent_utils.py:616`).

Redaction of internal errors is **partial and inconsistent**. Native failures are normalized into `"Error executing tool: {e}"` (`lib/crewai/src/crewai/utilities/agent_utils.py:1549`) without stack traces, but the TextTool path passes the full `repr(e)` (including chained causes) when `error=e` is f-string-substituted into the i18n template (`lib/crewai/src/crewai/tools/tool_usage.py:428-437`, `lib/crewai/src/crewai/tools/tool_usage.py:668-682`, `lib/crewai/src/crewai/translations/en.json:53`). MCP wrappers collapse exceptions into the message only and prepend a `f"Error executing MCP tool {name}: {e!s}"` string (`lib/crewai/src/crewai/tools/mcp_tool_wrapper.py:83`, `lib/crewai/src/crewai/tools/mcp_native_tool.py:97-99`). The MCP client carries an internal `_MCPToolResult(content, is_error)` NamedTuple (`lib/crewai/src/crewai/mcp/client.py:36-40`, `lib/crewai/src/crewai/mcp/client.py:578-588`), but this flag is only used to route to `MCPToolExecutionFailedEvent` vs `MCPToolExecutionCompletedEvent` (`lib/crewai/src/crewai/mcp/client.py:464-493`) — the model still receives `tool_result.content` (`lib/crewai/src/crewai/mcp/client.py:495`) without any error envelope.

Large results are not summarized or truncated for the model itself. The only safeguards are (a) console-preview truncation (`result[:200]` in `lib/crewai/src/crewai/utilities/agent_utils.py:1614` and `lib/crewai/src/crewai/agents/crew_agent_executor.py:1093`, `result[:500]` in `lib/crewai/src/crewai/events/utils/console_formatter.py:1389-1397`, `text[:2000] + "\n... [truncated]"` in `lib/crewai/src/crewai/utilities/agent_utils.py:243-244`), and (b) `summarize_messages` which is triggered only on context-length-exceeded, not on raw tool-result size (`lib/crewai/src/crewai/utilities/agent_utils.py:712-749`, `lib/crewai/src/crewai/utilities/agent_utils.py:920-1001`). Result cache replay is supported via `CacheHandler` (`lib/crewai/src/crewai/agents/cache/cache_handler.py:10-51`) and the `from_cache` flag on `ToolUsageFinishedEvent` (`lib/crewai/src/crewai/events/types/tool_usage_events.py:62-69`); the `_original_role`/`_role` strings and the raw tool result are persisted on the agent in `agent.tools_results` (`lib/crewai/src/crewai/agents/agent_builder/base_agent.py:324-326`).

Artifacts are not formally referenced. Tools that produce binary content (`ReadFileTool`, `lib/crewai/src/crewai/tools/agent_tools/read_file_tool.py:80-82`) inline-base64 the bytes into the model-visible string with a `[Binary file: name (mime)]` header; the `AddImageTool` returns a multimodal `{"role": "user", "content": [...]}` payload instead of a normal tool result (`lib/crewai/src/crewai/tools/agent_tools/add_image_tool.py:25-40`), so any "artifact reference" today is the URL string itself. The A2A layer has its own artifact concept (`lib/crewai/src/crewai/a2a/utils/task.py:249-267`) but it does not feed back into the tool result contract.

## Rating

**4 / 10** — Present but inconsistent, weakly documented at the boundary, and partially unsafe. Tool results are coerced into plain strings via a uniform `format_output_for_agent` hook, retries/usage limits/events exist, and the `result_schema` field produces structured JSON when present. But there is **no formal error envelope** (failures are detected by the model from a string prefix), no first-class stack-trace redaction (the text path forwards `repr(e)` and chained causes), no automatic result-size handling beyond console previews, and no artifact-reference primitive. The framework relies on i18n template strings to give the model "useful feedback" rather than crash, which works for opaque errors but is fragile when exceptions include stack data, secrets, or Python-internal types.

## Answers to Dimension Questions

1. **Is every tool result structured?**
   - No. The contract is a single `str` (`ToolResult.result` at `lib/crewai/src/crewai/tools/tool_types.py:8`, `ToolUsageError.message` at `lib/crewai/src/crewai/tools/tool_usage.py:72`, `result: str` at `lib/crewai/src/crewai/utilities/agent_utils.py:1380`, `tool_message["content"]` at `lib/crewai/src/crewai/utilities/agent_utils.py:1608`). Only when a `result_schema` (Pydantic `BaseModel`) is supplied does the result become structured JSON (`lib/crewai/src/crewai/tools/structured_tool.py:54-83`). Otherwise the value is serialized via `str(raw_result)`, including for `AddImageTool`, which bypasses the string contract entirely with a multimodal payload (`lib/crewai/src/crewai/tools/agent_tools/add_image_tool.py:25-40`). The MCP client carries an internal `_MCPToolResult(content, is_error)` (`lib/crewai/src/crewai/mcp/client.py:36-40`), but only the `content` string reaches the model (`lib/crewai/src/crewai/mcp/client.py:495`).

2. **Can the model distinguish success from failure?**
   - Only by string prefix. Failure messages always begin with a recognizable token (e.g., `"Error executing tool: {e}"` at `lib/crewai/src/crewai/utilities/agent_utils.py:1549`, `"Error executing MCP tool ..."` at `lib/crewai/src/crewai/tools/mcp_tool_wrapper.py:83`, `"Action '<name>' don't exist..."` at `lib/crewai/src/crewai/tools/tool_usage.py:785`, `"I encountered an error while trying to use the tool..."` at `lib/crewai/src/crewai/translations/en.json:53`). The MCP `is_error` flag is routed to a separate event (`lib/crewai/src/crewai/mcp/client.py:464-493`) but is **not** preserved in the model-visible string. There is no field on `ToolResult` / `NativeToolCallResult` that says "this is an error". The closest structured signal is `task.tools_errors` (`lib/crewai/src/crewai/task.py:142`, `lib/crewai/src/crewai/task.py:1063-1065`), but that lives on the task, not on the message delivered to the model. The native path emits `ToolUsageErrorEvent(error=e)` for observability (`lib/crewai/src/crewai/utilities/agent_utils.py:1553-1566`) without flagging the model-side message.

3. **Are stack traces hidden from users/models?**
   - Partially. Native function-calling swallows the exception and returns the message-only string `"Error executing tool: {e}"` (`lib/crewai/src/crewai/utilities/agent_utils.py:1549`), and `BaseLLM._auto_invoke_function` returns `None` while emitting a `ToolUsageErrorEvent(error=error_msg)` (`lib/crewai/src/crewai/llms/base_llm.py:715-743`). MCP wrappers similarly stringify only `e!s` (`lib/crewai/src/crewai/tools/mcp_tool_wrapper.py:83`, `lib/crewai/src/crewai/tools/mcp_native_tool.py:97-99`). **But the TextTool path embeds the full `repr(e)`** via i18n `.format(error=e, ...)` (`lib/crewai/src/crewai/tools/tool_usage.py:428-437`, `lib/crewai/src/crewai/tools/tool_usage.py:668-682`) — Python exceptions can include chained causes, custom `__repr__`, and very long message text. `_tool_calling` swallows the parse error and emits `ToolUsageError(f"...tool_usage_error...{error=e}")` (`lib/crewai/src/crewai/tools/tool_usage.py:879-881`), again passing the raw `e` into the template. There is **no global redaction layer**; a tool author who returns `raise RuntimeError(secret)` will see the secret embedded in the next observation. The MCP wrapper does match on substrings like `"authentication"` / `"unauthorized"` to avoid surfacing them verbatim (`lib/crewai/src/crewai/tools/mcp_tool_wrapper.py:142-154`), but this is classification for retry decisions, not for redaction. `safe_serialize_to_dict` (`lib/crewai/src/crewai/events/listeners/tracing/utils.py:415-423`) wraps serialization errors but only for tracing.

4. **Are large results handled safely?**
   - No automatic truncation for the model-facing message. The only safeguards are console-only previews (`result[:200]` at `lib/crewai/src/crewai/utilities/agent_utils.py:1614` and `lib/crewai/src/crewai/agents/crew_agent_executor.py:1093`, `result[:500]` at `lib/crewai/src/crewai/events/utils/console_formatter.py:1389-1397`, `text[:2000] + "\n... [truncated]"` at `lib/crewai/src/crewai/utilities/agent_utils.py:243-244`) and a tracing-only `truncate_messages` helper (`lib/crewai/src/crewai/events/listeners/tracing/utils.py:426-441`). `summarize_messages` is invoked **only on context-length overflow** (`lib/crewai/src/crewai/utilities/agent_utils.py:712-749`), not on raw tool-result size, and Snowflake has its own per-tool summarizer that only fires after a tool-cycle interruption (`lib/crewai/src/crewai/llms/providers/snowflake/completion.py:223-234`). `ReadFileTool` inlines base64 (`lib/crewai/src/crewai/tools/agent_tools/read_file_tool.py:80-82`), so binary content is fully forwarded to the model. There is no token-budget-aware "compact this tool result" pass for normal invocations.

5. **Can tool results be replayed?**
   - Yes, with caveats. Three replay layers exist:
     - **In-memory cache replay**: `CacheHandler` keys on `tool-input` and is consulted in both `ToolUsage._use`/`_ause` (`lib/crewai/src/crewai/tools/tool_usage.py:283-294`, `lib/crewai/src/crewai/tools/tool_usage.py:523-534`) and `execute_single_native_tool_call` (`lib/crewai/src/crewai/utilities/agent_utils.py:1485-1490`). Cached values are marked via `from_cache: bool` on `ToolUsageFinishedEvent` (`lib/crewai/src/crewai/events/types/tool_usage_events.py:67`).
     - **Per-agent tool history**: `agent.tools_results: list[dict]` accumulates `{result, tool_name, tool_args, result_as_answer}` for every successful invocation (`lib/crewai/src/crewai/agents/agent_builder/base_agent.py:324-326`, `lib/crewai/src/crewai/tools/tool_usage.py:377-391`, `lib/crewai/src/crewai/tools/tool_usage.py:617-631`).
     - **Crew-level replay**: `Crew.replay(task_id, inputs)` reruns from `kickoff_task_outputs_storage` rows that carry a `was_replayed` flag (`lib/crewai/src/crewai/crew.py:1918-1935`, `lib/crewai/src/crewai/memory/storage/kickoff_task_outputs_storage.py:54-95`).
     - **Event-bus replay**: `_replaying` context var + `event_bus.replay(source, event)` (`lib/crewai/src/crewai/events/event_bus.py:67-80`, `lib/crewai/src/crewai/events/event_bus.py:671-730`), used by Flow persistence (`lib/crewai/src/crewai/flow/runtime/__init__.py:2474-2688`).
   - However, **none of these include the cache-input hash, the error-recovery retries, or the failure-path envelope**. Caches store the success result; failed invocations are not cached. Replay of an interrupted run is bounded by the storage backend (file/SQLite/etc.).

## Architectural Decisions

- **Strings all the way down.** The tool-execution APIs (`invoke` / `ainvoke`) return `Any` (`lib/crewai/src/crewai/tools/structured_tool.py:296-364`), but `ToolUsage._format_result` always coerces to `str` before handing off (`lib/crewai/src/crewai/tools/tool_usage.py:709-714`). The downstream message types (`LLMMessage.content`, `ToolResult.result`, `NativeToolCallResult.result`) all share the same `str` contract (`lib/crewai/src/crewai/utilities/types.py:16-30`, `lib/crewai/src/crewai/tools/tool_types.py:1-9`, `lib/crewai/src/crewai/utilities/agent_utils.py:1374-1383`). This makes tool outputs trivial to splice into ReAct observations (`\nObservation: {result}`) but forces every consumer (LLM, console, cache, telemetry) to share the same lossy representation.
- **i18n error templates as the "envelope".** All failure messages flow through `I18N_DEFAULT.errors(<key>).format(...)` (`lib/crewai/src/crewai/translations/en.json:45-56`, `lib/crewai/src/crewai/utilities/i18n.py:67-77`). This gives operators a single place to localize and rewrite error text, but it also means changing the contract requires editing JSON and the keys are loosely typed (`str` keys into a `dict[str, dict[str, str]]` with a hard raise on miss at `lib/crewai/src/crewai/utilities/i18n.py:127-128`).
- **`result_schema` opt-in for structure.** When a Pydantic `BaseModel` subclass is declared as `result_schema` or inferred from the return annotation, `format_output_for_agent` validates and `model_dump_json()`s the result; otherwise it falls back to `str(raw_result)` with a `RuntimeWarning` on schema mismatch (`lib/crewai/src/crewai/tools/structured_tool.py:40-83`). This is the only path that produces structured JSON without a hand-rolled formatter.
- **Two execution paths.** The TextTool pipeline (`ToolUsage._use`/`_ause`) emits its result as a string-suffixed observation into `formatted_answer.text` (`lib/crewai/src/crewai/utilities/agent_utils.py:616-617`). The native-function-calling pipeline (`execute_single_native_tool_call`) emits a real `{"role": "tool", ...}` message (`lib/crewai/src/crewai/utilities/agent_utils.py:1604-1609`, `lib/crewai/src/crewai/agents/crew_agent_executor.py:1082-1088`). Both paths share the same `format_output_for_agent` hook and the same hook-before/hook-after surface, but the error-rendering and retry logic differ — text path retries up to `_max_parsing_attempts` (`lib/crewai/src/crewai/tools/tool_usage.py:422-446`), native path emits `ToolUsageErrorEvent` and increments `task.tools_errors` (`lib/crewai/src/crewai/utilities/agent_utils.py:1550-1566`).
- **Errors as a side-channel, not the envelope.** The four error-event types (`ToolUsageErrorEvent`, `ToolValidateInputErrorEvent`, `ToolSelectionErrorEvent`, `ToolExecutionErrorEvent` — `lib/crewai/src/crewai/events/types/tool_usage_events.py:72-100`) are observability-only. They do not influence how the result string is built. Only `task.tools_errors` and `agent.tools_results` are queryable from the agent/task scope (`lib/crewai/src/crewai/task.py:142`, `lib/crewai/src/crewai/agents/agent_builder/base_agent.py:324-326`).
- **Tool hook as opt-in transformation.** `before_tool_call`/`after_tool_call` hooks receive both `tool_result` (formatted) and `raw_tool_result` (unformatted) in `ToolCallHookContext` (`lib/crewai/src/crewai/utilities/agent_utils.py:1209-1313`). Hooks can replace the model-visible string (`lib/crewai/src/crewai/utilities/agent_utils.py:1579-1585`, `lib/crewai/src/crewai/utilities/tool_utils.py:132-141`), making this the de-facto redaction point for callers, but no built-in hook ships with the framework for security/secrets.
- **MCP parity through wrappers, not the core contract.** MCP tools are wrapped as `MCPToolWrapper` (string errors, retry with backoff, `lib/crewai/src/crewai/tools/mcp_tool_wrapper.py:69-115`) or `MCPNativeTool` (single fresh client per call, `lib/crewai/src/crewai/tools/mcp_native_tool.py:73-132`). Both return `str` from `_run`. The MCP client itself has the cleanest envelope (`_MCPToolResult(content, is_error)` at `lib/crewai/src/crewai/mcp/client.py:36-40`) but throws it away at the wrapper boundary.

## Notable Patterns

- **Unified string serializer at every boundary.** `format_output_for_agent` (`lib/crewai/src/crewai/tools/structured_tool.py:54-83`, `lib/crewai/src/crewai/utilities/agent_utils.py:1386-1396`) is the single funnel: structured if `result_schema` matches, else `str(raw_result)`, else warn-and-fallback. Tool hooks, both pipelines, and result caches all run through this hook.
- **Sentinel object for "no result yet".** `_RAW_RESULT_UNSET = object()` (`lib/crewai/src/crewai/tools/tool_usage.py:65`) plus `get_last_raw_result(fallback)` (`lib/crewai/src/crewai/tools/tool_usage.py:127-130`) lets after-hooks query the raw result even when the visible result is an error string.
- **Atomic usage claim.** `BaseTool._claim_usage()` uses `threading.Lock` to increment `current_usage_count` and returns the limit-exceeded string atomically (`lib/crewai/src/crewai/tools/base_tool.py:192`, `lib/crewai/src/crewai/tools/base_tool.py:295-313`). The same counter is mirrored on the `CrewStructuredTool` view via `_increment_usage_count` (`lib/crewai/src/crewai/tools/structured_tool.py:373-377`, `lib/crewai/src/crewai/tools/tool_usage.py:633-660`).
- **Retry-budget tracking per `_run_attempts`.** `_run_attempts` and `_max_parsing_attempts` are private state on `ToolUsage` (`lib/crewai/src/crewai/tools/tool_usage.py:100-119`, `lib/crewai/src/crewai/tools/tool_usage.py:422-446`, `lib/crewai/src/crewai/tools/tool_usage.py:662-686`). On exhaustion, the error string is appended with a `"Moving on then. ..."` hint (`lib/crewai/src/crewai/translations/en.json:18`, `lib/crewai/src/crewai/tools/tool_usage.py:435-437`).
- **Repeated-input detection.** `_check_tool_repeated_usage` short-circuits with `task_repeated_usage` i18n text when the same `(tool_name, arguments)` tuple is repeated, plus telemetry (`lib/crewai/src/crewai/tools/tool_usage.py:728-738`, `lib/crewai/src/crewai/translations/en.json:49`).
- **Conversation-replay support.** `event_bus.replay` plus `_replaying` context var (used by Flow persistence) lets listeners distinguish live events from replayed events (`lib/crewai/src/crewai/events/event_bus.py:67-80`, `lib/crewai/src/crewai/events/event_bus.py:671-730`).
- **Capability downgrade for tool selection.** `_select_tool` uses `SequenceMatcher` to fuzzy-match tool names (ratio > 0.85) and emits a `ToolSelectionErrorEvent` with the available-tool list (`lib/crewai/src/crewai/tools/tool_usage.py:759-802`).

## Tradeoffs

- **Uniformity vs. safety.** String-everywhere is simple and lets CrewAI drop into any LLM that accepts `role: tool`, but it means redaction, error typing, and size limits must be enforced at the tool author level. There is no framework-wide guard rail.
- **Opt-in vs. forced structure.** `result_schema` is opt-in; the majority of built-in tools (memory, delegation, file-read) return strings. This means most results are unstructured even when the underlying data is structured.
- **i18n templates as a single point of change.** Editing `translations/en.json` (`lib/crewai/src/crewai/translations/en.json:45-56`) can rewrite every error message, but it does not validate the substitutions (`error=e`, `tool=...`) — missing keys raise at runtime (`lib/crewai/src/crewai/utilities/i18n.py:127-128`).
- **Two pipelines, one string contract.** Text-tool and native-tool paths converge on the same `format_output_for_agent` and `LLMMessage` shape, which keeps cross-pipeline reuse simple but means the more sophisticated native path inherits the text path's lossy serialization.
- **Hooks as a security seam.** `ToolCallHookContext.tool_result`/`raw_tool_result` (`lib/crewai/src/crewai/utilities/agent_utils.py:1209-1313`) is the natural place to redact, but CrewAI ships no built-in secret-aware hook.
- **Cache reuse vs. error replay.** `CacheHandler` only stores success outputs (`lib/crewai/src/crewai/agents/cache/cache_handler.py:23-35`), so failures always re-execute on retry — desirable for transient errors, expensive for deterministic ones.

## Failure Modes / Edge Cases

- **Embedding the full `repr(e)` into the model message.** `_use`/`_ause` f-string-format `error=e` into the i18n template (`lib/crewai/src/crewai/tools/tool_usage.py:428-437`, `lib/crewai/src/crewai/tools/tool_usage.py:668-682`). A tool that raises with sensitive context (tokens, internal paths, env values in the exception message) will leak it into the next observation.
- **Schema mismatch silently downgrades to `str`.** `_format_tool_output_for_agent` catches all exceptions during `model_validate(...)` and falls back to `str(raw_result)` with a `RuntimeWarning` (`lib/crewai/src/crewai/tools/structured_tool.py:72-83`). There is no way for the model to tell that the structured contract was broken.
- **MCP `is_error` results flow through as success strings.** The client emits the right event (`lib/crewai/src/crewai/mcp/client.py:464-478`) but returns `tool_result.content` regardless (`lib/crewai/src/crewai/mcp/client.py:495`), so the MCP server's `isError=True` flag is invisible to the model.
- **Usage-limit error vs. exception.** When `max_usage_count` is hit, `_claim_usage()` returns the limit string (`lib/crewai/src/crewai/tools/base_tool.py:295-313`) but `CrewStructuredTool.invoke/ainvoke` raise `ToolUsageLimitExceededError` (`lib/crewai/src/crewai/tools/structured_tool.py:111-112`, `lib/crewai/src/crewai/tools/structured_tool.py:314-352`). The two surfaces give the same text but different exception types — callers can accidentally swallow the exception while the model sees the string.
- **Validation consumes the usage counter or not?** `BaseTool.run`/`arun` increment only after `_validate_kwargs` succeeds (`lib/crewai/src/crewai/tools/base_tool.py:319-325`, `lib/crewai/src/crewai/tools/base_tool.py:346-354`), and tests assert this (`lib/crewai/tests/tools/test_base_tool.py:312-316`, `lib/crewai/tests/tools/test_base_tool.py:665-669`). However, `CrewStructuredTool.ainvoke/invoke` increment first, then call `func` (`lib/crewai/src/crewai/tools/structured_tool.py:319-364`); a validation error in `_parse_args` will leave `func` uncalled but the counter is bumped — silent quota leak.
- **Hook errors swallow silently.** `try/except` in `utilities/tool_utils.py:115-141` and `utilities/agent_utils.py:1522-1525` logs but does not surface hook failures; if the `after_tool_call` hook that was supposed to redact secrets throws, the model still receives the unredacted string.
- **Console truncation hides model-side issues.** `result[:200]` for the green panel (`lib/crewai/src/crewai/utilities/agent_utils.py:1614`, `lib/crewai/src/crewai/agents/crew_agent_executor.py:1093`) gives a false sense that the result is small while the model receives the full string.
- **`AddImageTool` short-circuits the tool contract.** Returning `{"role": "user", "content": [...]}` (`lib/crewai/src/crewai/tools/agent_tools/add_image_tool.py:25-40`) bypasses `_format_result` and `format_output_for_agent`; the text path appends it directly as an assistant message (`lib/crewai/src/crewai/agents/crew_agent_executor.py:1469-1475`). A misuse of `AddImageTool` semantics would skip error handling.
- **`tool_calls_made` counter race.** `available_tool.current_usage_count += 1` (`lib/crewai/src/crewai/tools/tool_usage.py:410`, `lib/crewai/src/crewai/tools/tool_usage.py:650`) is not lock-protected; `BaseTool._claim_usage()` uses a `_usage_lock`, but the structured-tool fallback path does not, so concurrent invocations on the same `available_tool` may over-count.

## Future Considerations

- **Add a typed `ToolResult` (or `ToolCallOutcome`) envelope.** `success: bool`, `error: Exception | None`, `data: Any`, `metadata: dict`, and a `model_text` projection. Migrating `format_output_for_agent` to set both `model_text` and `data` would let providers (Anthropic/Bedrock/Gemini) emit proper structured errors without string parsing.
- **Force a redaction pass before string serialization.** Wrap every `{error=e}` template substitution in a sanitizer that truncates chained causes and applies a configurable secret pattern list. Today only MCP substrings get classified (`lib/crewai/src/crewai/tools/mcp_tool_wrapper.py:139-154`).
- **Persist failure outputs in `CacheHandler`.** Negative caching with TTL would let repeated deterministic failures (e.g., 404) short-circuit instead of blowing the retry budget (`lib/crewai/src/crewai/tools/tool_usage.py:306-313`, `lib/crewai/src/crewai/tools/tool_usage.py:546-553`).
- **Standardize large-result summarization.** Today `summarize_messages` (`lib/crewai/src/crewai/utilities/agent_utils.py:920-1001`) only fires on context overflow. A token-budget-aware "compact this tool result" pass before the result enters the chat history would prevent silent context bloat (`lib/crewai/src/crewai/tools/agent_tools/read_file_tool.py:80-82`).
- **Promote `result_schema` usage and add a default `ToolCallResult` schema.** Built-in tools (`MemoryTools`, `MCPToolWrapper`) currently return strings despite structured underlying data. A `ToolCallResult[T]` Generic would let `format_output_for_agent` produce schema-validated JSON by default.
- **Lock the structured-tool usage counter.** `available_tool.current_usage_count += 1` in `tool_usage.py:410`/`tool_usage.py:650` should reuse `BaseTool._claim_usage` to avoid races that exceed `max_usage_count` (`lib/crewai/src/crewai/tools/tool_usage.py:633-660`).
- **Adopt artifact references for binary content.** `ReadFileTool` currently inlines base64 (`lib/crewai/src/crewai/tools/agent_tools/read_file_tool.py:80-82`); a tool-side artifact handle (file id + MIME) plus a follow-up `read_artifact` tool would let the model reason about file references rather than carrying them in context.

## Questions / Gaps

- **What is the documented error contract for the LLM?** No top-level docstring or schema defines the success/failure prefix vocabulary. Tests assert substring matches (`lib/crewai/tests/tools/agent_tools/test_agent_tools.py:112-125`), but the production messages are produced by `lib/crewai/src/crewai/translations/en.json:45-56` and are not protected by a contract test.
- **How does `format_output_for_agent` interact with multimodal returns?** `AddImageTool` returns a dict that bypasses the hook entirely (`lib/crewai/src/crewai/tools/agent_tools/add_image_tool.py:25-40`); no other tool returns multimodal content, but the type system does not forbid it.
- **Where are stack traces logged?** `lib/crewai/src/crewai/utilities/agent_utils.py:1549` swallows `e` but does not log it; only the event bus subscribers (`lib/crewai/src/crewai/utilities/agent_utils.py:1553-1566`, `lib/crewai/src/crewai/tools/tool_usage.py:950-973`) see the exception object. If no listener is registered, the trace is lost.
- **What happens when `I18N_DEFAULT.errors(<key>)` is missing?** `I18N.retrieve` raises a bare `Exception` (`lib/crewai/src/crewai/utilities/i18n.py:127-128`); a typo in a translation key propagates as an unhandled error rather than a fallback message.
- **Are tool results replayed on resumption?** `Crew.replay` reloads task outputs (`lib/crewai/src/crewai/crew.py:1918-1935`) but does not reconstruct the per-tool cache; a replayed run that depends on tool-cache state would re-execute.
- **Is there a max-result-size guard at the LLM provider layer?** No clear evidence of a token-budget check prior to `format_output_for_agent`. Snowflake has a `_summarize_tool_results` (`lib/crewai/src/crewai/llms/providers/snowflake/completion.py:223-234`) but only after a cycle interruption; other providers do not.
