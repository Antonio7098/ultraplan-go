## Summary

Pydantic AI represents tool output and errors as a small, well-typed set of message parts: `ToolReturnPart` for normal returns, `RetryPromptPart` for "ask the model to try again" (covering validation errors, unknown tool names, and `ModelRetry` exceptions), and `NativeToolReturnPart` for provider-native tool returns. Success vs. failure is conveyed by **discriminator + kind**, not by an explicit `success: bool` flag — `ToolReturnPart.outcome` carries `'success' | 'failed' | 'denied'` (`pydantic_ai/messages.py:1150`) and `RetryPromptPart` carries the error payload itself, so a `ToolReturnPart` with `outcome='failed'` and a `RetryPromptPart` are both model-readable failure signals. All tool errors that should become model feedback are normalized through `ToolRetryError` (an internal control-flow exception) before being attached to the request (`pydantic_ai/_output.py:121-129`, `pydantic_ai/_agent_graph.py:2023-2024`). The framework never returns Python tracebacks to the model: `RetryPromptPart.model_response()` strips `ctx` and (for output validation) the duplicated top-level `input` (`pydantic_ai/messages.py:1446-1468`); `ModelHTTPError`/`ModelAPIError` are caught at the model-adapter boundary and surface in agent-run exceptions, not in the model-facing message stream. Large tool returns are **not summarized or truncated** by the framework — `BaseToolReturnPart` exposes `content_items`/`model_response_str`/`model_response_object`/`files` to let downstream consumers split data from multimodal files, but no built-in size cap exists. Artifact linking is first-class: file references survive a JSON round-trip via the `ToolReturnContent` recursive `TypeAliasType` (`pydantic_ai/messages.py:1088-1097`), and UI adapters recursively sanitize nested `FileUrl`/`UploadedFile` references in tool returns (`pydantic_ai/ui/_adapter.py:562-614`). Tool results are fully replayable because every field is Pydantic-serializable through `ModelMessagesTypeAdapter` (`pydantic_ai/messages.py:2381-2384`) and the framework carries `tool_call_id` / `provider_details` / `provider_metadata` for cross-provider replay.

## Rating

**8 / 10** — Clear model with explicit interfaces, comprehensive tests, and operational safeguards. A failed tool call reliably becomes structured, model-readable feedback (`RetryPromptPart`) rather than a crash, with discriminator-driven rehydration and an explicit `outcome` field for the tool-return side. Stack traces are never returned to the model. Coverage is missing in two places: (1) no built-in large-result summarization/truncation in the framework — users get `content_items`/`files` helpers but must write their own truncation; (2) the per-call `outcome` field is only set on the `denied` branch in normal execution (see `pydantic_ai/_agent_graph.py:2004-2009`); failed outcomes are signalled by the parallel `RetryPromptPart` rather than by `outcome='failed'` on `ToolReturnPart`, so a downstream consumer looking only at `outcome` could miss exceptions that escape `ModelRetry` rewrapping (e.g. uncaught `Exception` in a hook hitting `on_tool_execute_error`).

## Answers to Dimension Questions

1. **Is every tool result structured?** Yes. Every tool return is represented as a `BaseToolReturnPart` (or typed subclass such as `ToolReturnPart` / `NativeToolReturnPart` / `ToolSearchReturnPart`). `content: ToolReturnContent` is a recursive `TypeAliasType` that admits arbitrary `Any`, but Pydantic validates it via `tool_return_ta` so multimodal files inside dicts/lists survive round-trips (`pydantic_ai/messages.py:1088-1097`, `pydantic_ai/messages.py:2381-2384`). The success result from a tool function is always wrapped in `ToolReturn(return_value=...)` before being attached as `ToolReturnPart` (`pydantic_ai/_agent_graph.py:2026-2052`). Native tools have parallel `NativeToolCallPart` / `NativeToolReturnPart` dataclasses (`pydantic_ai/messages.py:1771-1955`).
2. **Can the model distinguish success from failure?** Yes, by **part type**. A `ToolReturnPart` (with `part_kind='tool-return'`) is a success path carrying `outcome: Literal['success', 'failed', 'denied']` (`pydantic_ai/messages.py:1150`). A `RetryPromptPart` (`part_kind='retry-prompt'`) is always an error path carrying either a string message or a `list[pydantic_core.ErrorDetails]` (`pydantic_ai/messages.py:1407-1444`). The model's view is built from a union of these two tagged types — a model cannot confuse them because `ModelRequestPart` discriminates on `part_kind` (`pydantic_ai/messages.py:2036-2044`).
3. **Are stack traces hidden from users/models?** Yes, by construction. The model never sees Python `repr` of an exception. `RetryPromptPart.model_response()` strips `ctx` and, for output retries, the top-level `input` field that would duplicate the model's own output (`pydantic_ai/messages.py:1446-1468`). `ToolRetryError._format_error_details` formats `ErrorDetails` into `loc` + `msg` + `[type=..., input_value=...]` lines (`pydantic_ai/exceptions.py:288-305`). `ModelHTTPError` / `ModelAPIError` carry only `message` (string) and `body` (response payload, not a traceback) — and they are surfaced as agent-run exceptions to the application, not as model input (`pydantic_ai/exceptions.py:236-266`). Hook-level exceptions raised by the user's code are caught by `on_tool_execute_error` (`pydantic_ai/tool_manager.py:330-335`) — the hook gets the original exception for custom handling, but if the hook doesn't raise a `ModelRetry`, the outer `_run_execute_hooks` re-wraps the exception as `ToolRetryError` and only the rewrapped message reaches the model (`pydantic_ai/tool_manager.py:341-350`).
4. **Are large results handled safely?** Partially. The framework does not summarize or cap tool returns in core. What it does do: (a) `BaseToolReturnPart` exposes `content_items(mode='raw' | 'str' | 'jsonable')` so consumers can iterate and serialize selectively (`pydantic_ai/messages.py:1201-1242`); (b) `files` separates multimodal content from data so large binaries can be sent as a separate `UserPromptPart` while the JSON body is small (`pydantic_ai/messages.py:1158-1199`, `pydantic_ai/messages.py:1271-1297`); (c) for providers whose tool result API is text-only, `model_response_str_and_user_content` replaces file bodies with `'See file {identifier}.'` placeholders and emits the file as a user-content part (`pydantic_ai/messages.py:1271-1297`). There is no built-in token-limit truncation, no automatic compaction, and no built-in summarization — users that need it must add a `history_processor` (see `docs/message-history.md`) or a custom tool wrapper.
5. **Can tool results be replayed?** Yes. Every part dataclass has a Pydantic-friendly discriminator field (`part_kind`), preserves `tool_call_id` for matching call ↔ result (`pydantic_ai/messages.py:1123-1127`, `pydantic_ai/messages.py:1434-1438`), and round-trips through `ModelMessagesTypeAdapter` (`pydantic_ai/messages.py:2381-2384`). The test suite exercises full VCR-recorded replay at `tests/test_agent.py:3897-3944` and `tests/test_mcp.py:1733-1849`, plus dedicated message-roundtrip tests at `tests/test_messages.py:1083-1612`. `ToolReturnPart` carries `metadata` (app-only) and `ToolReturn.metadata` (programmatic) so app-side state survives replay without leaking to the LLM (`pydantic_ai/messages.py:893-918`, `pydantic_ai/messages.py:1144-1145`).

## Architectural Decisions

- **Tagged-union part model over a single envelope.** `ModelRequestPart` and `ModelResponsePart` are Pydantic discriminated unions with `part_kind` as the discriminator; nested typed subclasses (`ToolSearchReturnPart`, `LoadCapabilityReturnPart`, `NativeToolReturnPart`) use a secondary `tool_kind` discriminator (`pydantic_ai/messages.py:2036-2044`, `pydantic_ai/messages.py:2075-2088`, `pydantic_ai/messages.py:2009-2033`). This avoids a single mega-envelope with an optional `error` field and gives the model a stable type contract.
- **`RetryPromptPart` for every error that the model can fix.** Whether it's a Pydantic validation failure, an `args_validator` `ModelRetry`, an unknown tool name, a timeout, or a FastMCP `ToolError`, the framework routes the failure through `_wrap_error_as_retry` / `_make_retry_prompt` to produce a `RetryPromptPart` (`pydantic_ai/tool_manager.py:183-191`, `pydantic_ai/_output.py:121-129`). A single `ToolRetryError` exception is the internal control-flow carrier (`pydantic_ai/exceptions.py:273-305`) so both output validation and tool execution share one transport.
- **`outcome` field on `ToolReturnPart` for non-retry failures.** A `ToolDenied` produces `ToolReturnPart(outcome='denied')` (`pydantic_ai/_agent_graph.py:2004-2009`); `outcome='failed'` is documented (`pydantic_ai/messages.py:1150-1156`) and reserved for situations where execution must report a failure without surfacing as a retry prompt (e.g. a deferred-tool result that can't be retried in-place). The framework deliberately does **not** set `outcome='failed'` for normal execution errors — those become `RetryPromptPart`s — so callers reading `outcome` should pair it with a check for the part kind.
- **`ToolReturn` (Generic) wrapper to separate model-facing content from app-facing state.** `return_value` (the value used in the tool result sent to the model), `content` (a separate `UserPromptPart` appended after the tool result, useful for multimodal data), and `metadata` (programmatic-only) are deliberately distinct fields (`pydantic_ai/messages.py:891-918`). The tool-execution pipeline auto-wraps a plain return in `ToolReturn[Any](return_value=...)` (`pydantic_ai/_agent_graph.py:2035-2036`).
- **Provider-specific data lives on `provider_details`, not on `provider_name` or `id`.** `BaseToolReturnPart` and `BaseToolCallPart` carry `provider_name` / `provider_details` separately so round-trips don't lose type information (`pydantic_ai/messages.py:1129-1145`, `pydantic_ai/messages.py:1798-1817`).
- **`ModelMessagesTypeAdapter` as the single canonical (de)serializer.** Every part dataclass is Pydantic-friendly; `defer_build=True` keeps import cost low; `ser_json_bytes='base64'` / `val_json_bytes='base64'` keeps binary content wire-safe (`pydantic_ai/messages.py:2381-2384`).
- **Hooks are the customization point for error handling, not subclasses.** `on_tool_execute_error`, `on_tool_validate_error`, `on_output_validate_error`, and `on_output_process_error` (`pydantic_ai/tool_manager.py:283-285`, `pydantic_ai/tool_manager.py:334-335`, `pydantic_ai/_output.py:163-169`, `pydantic_ai/_output.py:213-217`) let users redact, transform, or override the default retry behavior. Default policy is "validation/execution error → `ModelRetry` → `RetryPromptPart`"; users can short-circuit by raising a different model-readable error or returning a synthetic result.
- **`Capability` instead of subclass for cross-cutting behavior.** `WrapperToolset` (e.g. `ApprovalRequiredToolset`, `DeferredLoadingToolset`) applies features to any toolset without coupling (`pydantic_ai_slim/pydantic_ai/AGENTS.md:41`); the same applies to error handling — `HandleDeferredToolCalls` can short-circuit a `CallDeferred` / `ApprovalRequired` into `ToolReturn` / `ModelRetry` / `ToolDenied` (`pydantic_ai/tools.py:329-348`, `pydantic_ai/tool_manager.py:847-936`).

## Notable Patterns

- **Discriminated unions for parts** (e.g. `ModelRequestPart`, `ModelResponsePart`, `HandleResponseEvent`) with `part_kind` / `event_kind` discriminators — enables `isinstance` checks, Pydantic-driven (de)serialization, and typed-event streams (`pydantic_ai/messages.py:2036-2088`, `pydantic_ai/messages.py:2955-2967`).
- **`__get_pydantic_core_schema__` on `ModelRetry`** so it can be embedded in message history and replayed as part of a `ToolReturn` (`pydantic_ai/exceptions.py:61-77`).
- **Single internal control-flow exception (`ToolRetryError`)** that wraps a `RetryPromptPart` — used by both tool-validation and output-validation paths so retries share one transport (`pydantic_ai/exceptions.py:273-305`).
- **Recursive `TypeAliasType` (`ToolReturnContent`)** that lets arbitrary multimodal content nest inside lists/dicts while still being Pydantic-validated (`pydantic_ai/messages.py:1088-1097`).
- **Pydantic `TypeAdapter` (`tool_return_ta`)** for serializing arbitrary tool-return values to JSON, kept as a module-level singleton with `defer_build=True` for fast import (`pydantic_ai/messages.py:1084-1086`).
- **Multi-mode serialization helpers on `BaseToolReturnPart`** — `model_response_str`, `model_response_object`, `model_response_str_and_user_content`, `content_items`, `files` — letting consumers pick the right view per provider (`pydantic_ai/messages.py:1201-1297`).
- **`outcome` discriminator on tool returns** (`'success' | 'failed' | 'denied'`) (`pydantic_ai/messages.py:1150-1156`) — paired with the parallel `RetryPromptPart` so success and failure don't share a part kind.
- **Capability-handler extensibility for error envelopes** — `HandleDeferredToolCalls` and the underlying `DeferredToolResult` discriminated union (`pydantic_ai/tools.py:351-375`) let users shape how denied/deferred/retry results are surfaced, with `wrap_validation_errors` flipping the contract for nested callers (`pydantic_ai/tool_manager.py:771-936`).
- **Context-aware sanitization of tool-return content** for untrusted clients (UI adapters) — recursively strips disallowed `FileUrl` schemes and `UploadedFile` references inside tool returns, not just user prompts (`pydantic_ai/ui/_adapter.py:562-614`).
- **Telemetry neutrality** — `otel_event` / `otel_message_parts` methods on every part format `content` via `serialize_any` so OTel mirrors the model-visible form without leaking `metadata` or other app-only fields (`pydantic_ai/messages.py:1299-1323`, `pydantic_ai/messages.py:2343-2353`).

## Tradeoffs

- **No built-in summarization/truncation of large tool returns.** The framework leans on the `history_processor` extension point (`docs/message-history.md`) and the file-splitting helpers to keep large returns safe, but doesn't ship a default cap. Users who don't add a processor can send arbitrarily large tool results to the model and rely on the provider's context window.
- **`outcome='failed'` is reserved, not actively set.** Normal execution errors flow through `RetryPromptPart`, so downstream consumers that filter only by `outcome` would miss them. The tradeoff is a clean part-kind union (`retry-prompt` vs `tool-return`) over a single part with a richer enum.
- **No traceback exposure, but error messages can leak secrets if the user raises `ModelRetry` with sensitive data.** The framework cannot redact what the user wrote. Default FastMCP behavior wraps the raw `ToolError` message (`pydantic_ai/toolsets/fastmcp.py:264-271`), which can include server-side paths or stack snippets depending on the MCP server.
- **Recursive `ToolReturnContent` is `Any` at the leaves** for ergonomic reasons — it lets users return any structure, but the Pydantic `TypeAdapter(Any, ...)` skip-strict-validation approach trades type safety for flexibility (`pydantic_ai/messages.py:1084-1086`). Multimodal reconstruction (`BinaryContent` inside dicts/lists) is best-effort and depends on `kind` discriminators (`pydantic-ai/tests/test_messages.py:1083-1138`).
- **`ToolDenied` is **not** a `ToolReturn`** by default — it's an `isinstance`-distinguished sentinel. The docstring on `handle_call` explicitly warns callers to check for it (`pydantic_ai/tool_manager.py:802-809`); a sandboxed caller that ignores the warning can accidentally surface a denial as a successful return value.
- **Internal `ToolRetryError` is exported under `__all__`** but is control flow, not an error to catch (`pydantic_ai/exceptions.py:273-283`). It appears in `pydantic_ai/__init__.py` exports so it can be `except`-caught by capability authors, but treating it as user-facing muddies the contract.
- **`'INVALID_JSON'` key for malformed call args** lets a partially-formed tool call reach the model rather than crashing (`pydantic_ai/messages.py:1842-1850`). The tradeoff is a string-keyed `dict` flowing into a downstream schema that may not expect it.

## Failure Modes / Edge Cases

- **Retry-budget exhaustion**: `_check_max_retries` raises `UnexpectedModelBehavior` chained from the original error (`pydantic_ai/tool_manager.py:177-181`). The framework does **not** silently swallow the exception — the user sees a structured `AgentRunError` subclass (`pydantic_ai/exceptions.py:181-233`). Tests pin this behavior at `tests/test_agent.py:3897-3944` and `tests/test_agent.py:3999-4024`.
- **Max-retries on unknown-tool calls** specifically: the test at `tests/test_agent.py:11199-11220` (`test_unknown_tool_with_valid_tool_does_not_exhaust_retries`) shows that retry budget is per-tool, not global — so one bad tool doesn't poison the budget for the others.
- **`on_tool_execute_error` hook bypass**: if a user hook swallows the original exception and returns a value, no retry happens. If the hook itself raises `ModelRetry`, it propagates and is wrapped as `ToolRetryError` (`pydantic_ai/tool_manager.py:341-350`).
- **`SkipToolValidation` / `SkipToolExecution` exceptions** let capability hooks short-circuit validation or execution with a synthetic value (`pydantic_ai/exceptions.py:133-156`). They're part of the public API for capability authors and are documented as control-flow.
- **Streaming partial failures**: `stream_text` and `validate_response_output` swallow `ValidationError` / `ModelRetry` during streaming and only raise on the final pass (`pydantic_ai/result.py:90-93`, `pydantic_ai/result.py:304-309`). On the final non-partial pass, the framework raises `UnexpectedModelBehavior('Output validation failed during streaming, and retries are not supported in run_stream()')` — explicit about not retrying mid-stream.
- **Deferred-tool results that target a different `tool_kind`**: `ToolApproved.override_args` revalidates the call; if it fails, the framework raises `UnexpectedModelBehavior` (`pydantic_ai/_agent_graph.py:1819-1824`).
- **MCP server `isError`**: mapped to `ModelRetry(str(e))` by the FastMCP toolset, prefixed as `'Error executing tool {name}: ...'` in the resulting `RetryPromptPart.content` (`pydantic_ai/toolsets/fastmcp.py:267-269`). The VCR-recorded test at `tests/test_mcp.py:1733-1849` shows the prefix.
- **`ToolReturn` wrapped in a list**: explicitly rejected by the framework as a `UserError` rather than silently ignored (`pydantic_ai/_agent_graph.py:2028-2034`).
- **Output validator retry budget mismatches**: `tool_manager.py:622-633` documents that `ToolOutput(max_retries=N)` exceeding `max_output_retries` can fire `ctx.last_attempt` before the run terminates; tracked as a known limitation.
- **`INVALID_JSON` flow-through**: if a model emits malformed JSON for tool args, the call still goes out and the validator catches the parse error as a normal retry prompt — covered by `tests/test_messages.py:1455-1480` (regression for `args_as_dict(raise_if_invalid=True)`).

## Future Considerations

- **Built-in summarization/truncation of large tool returns** would close the largest gap — currently consumers must add a `history_processor` or wrap the tool themselves. The `_split_content` / `files` separation in `BaseToolReturnPart` (`pydantic_ai/messages.py:1158-1199`) gives a foundation, but the cap-and-summarize policy is left to the user.
- **Consistent `outcome` semantics**: today `outcome='denied'` is set by `_call_tool` (`pydantic_ai/_agent_graph.py:2004-2009`), `outcome='success'` is the default (`pydantic_ai/messages.py:1150`), and `outcome='failed'` is documented but not actively produced by the main execution path. A future change could route hook-recovered exceptions through `outcome='failed'` instead of silently returning them.
- **Configurable error redaction**: the framework currently passes through `ModelRetry.message` verbatim and FastMCP passes through `str(e)` (`pydantic_ai/toolsets/fastmcp.py:267-269`). A redaction hook or settings flag (analogous to `FunctionInvocationConfiguration['include_detailed_errors']` in agent-framework) would be a small, additive change.
- **Per-tool error-envelope profile**: each `ToolDefinition` could carry an explicit `error_strategy` (e.g. `'retry' | 'fail_silent' | 'custom_handler'`) to centralize today's distributed `ModelRetry` raise sites (`pydantic_ai/toolsets/function.py:656`, `pydantic_ai/toolsets/fastmcp.py:269`, `pydantic_ai/toolsets/_deferred_capability_loader.py:72-74`, `pydantic_ai/toolsets/_tool_search.py:412,431`).
- **`args_as_dict(raise_if_invalid=True)` as default**: the default behavior of swallowing malformed JSON (`pydantic_ai/messages.py:1842-1850`) is a tradeoff; making it configurable at the `Agent` level would let users opt into stricter validation.
- **Schema validation on `ToolReturn.content`**: it's currently `Any` at the leaves; pinning it to a model-defined schema would catch silent type drift when tool functions change shape.

## Questions / Gaps

- **No clear evidence found** for built-in large-result truncation or summarization at the framework level. `BaseToolReturnPart` provides the helpers to do this externally, but the policy lives outside the core.
- **No clear evidence found** for a centralized "error envelope" class — the contract is implicit (discriminated part type + `RetryPromptPart.content`), which is well-typed but distributed across `pydantic_ai/messages.py:1407-1444`, `pydantic_ai/tool_manager.py:183-191`, `pydantic_ai/_output.py:121-129`. A single `ToolResult` envelope could make the contract more discoverable.
- **No clear evidence found** for an opt-in redaction flag at the framework level. Users wanting to hide stack traces from the model must rely on (a) the framework never including tracebacks in `RetryPromptPart`/`ModelHTTPError.body` and (b) their own hooks to scrub `ModelRetry.message` content.
- **No clear evidence found** for an explicit `outcome='failed'` setter — only `'success'` (default) and `'denied'` (`pydantic_ai/_agent_graph.py:2004-2009`) are produced in the main code path. The `'failed'` value is documented (`pydantic_ai/messages.py:1150-1156`) but the search returned no production setter beyond the `'denied'` branch.
- **`ToolReturnPart` ↔ `NativeToolReturnPart` overlap**: both inherit from `BaseToolReturnPart`, share `content`, and carry the same `outcome` field, but native returns never get a `RetryPromptPart` sibling in the codebase searched (native failures propagate through the model adapter's `ModelAPIError` / `UnexpectedModelBehavior` instead). The contract is implicitly: native tool returns are always "successful" from the model's POV; failures become agent-run exceptions.
