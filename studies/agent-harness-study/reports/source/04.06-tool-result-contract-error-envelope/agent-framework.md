## Summary

The repository implements tool calls through a unified, structured `function_result` envelope on both stacks. In Python every tool output is normalized into `Content(type="function_result", call_id=…, result=…, items=[…], exception=…, additional_properties=…)` via `Content.from_function_result` (`python/packages/core/agent_framework/_types.py:817-874`). Raw return values are converted into a uniform `list[Content]` (`_tools.py:828-867`). Failures are caught at the invocation boundary (`_tools.py:1556-1569`, `_tools.py:1632-1645`) and re-rendered as model-readable error content with `exception=` set and a generic `"Error: ..."` prefix; detail is opt-in via `FunctionInvocationConfiguration["include_detailed_errors"]` (`_tools.py:1344-1398`, default `False`). MCP server `isError` results are mapped to `ToolExecutionException` and surfaced back through the same `Content.from_function_result` envelope (`_mcp.py:1690-1739`). .NET inherits `FunctionResultContent` from MEAI and uses it as the universal success/failure carrier (`Shared/Workflows/Execution/WorkflowRunner.cs:342-349`). It layers compaction-driven summarization on top: `ToolResultCompactionStrategy` collapses old tool-call groups into a YAML-like `[Tool Calls]` summary (`Microsoft.Agents.AI/Compaction/ToolResultCompactionStrategy.cs:172-254`), `ContextWindowCompactionStrategy` triggers it on token pressure (`Microsoft.Agents.AI/Compaction/ContextWindowCompactionStrategy.cs:72-108`), and the Responses hosting converter encodes results into the wire payload via `EncodeFunctionResultAsJsonStringPayload` (`Microsoft.Agents.AI.Foundry.Hosting/OutputConverter.cs:452-490`). Artifacts are linked via stable references (`Content.from_hosted_file` `_types.py:945-964`, `McpServerToolCallContent` shells), and the security middleware hides untrusted payloads behind variable-reference placeholders (`security.py:1384-1426`). Stack traces are not returned to the model by default — the framework logs them and returns a sanitized message; observability attributes (`OtelAttr.TOOL_RESULT`, `OtelAttr.ERROR_TYPE`) are only attached when `OBSERVABILITY_SETTINGS.SENSITIVE_DATA_ENABLED` (`_tools.py:733-779`, `observability.py:807-815`).

## Rating

**7 / 10** — Clear model with tests, explicit interfaces, and operational safeguards. Solid uniform `Content` envelope, configurable redaction, large-result summarization, and artifact references via file/vector-store IDs are all present and tested. Lacks a single dedicated "error envelope" subclass that is forced onto every failure path (errors are inferred from `exception=`/`result` prefix), and stack-trace leakage is controlled by an opt-in flag rather than enforced by construction.

## Answers to Dimension Questions

1. **Is every tool result structured?** Yes. Python normalizes through `Content.from_function_result` (`_tools.py:1474`, `_tools.py:1523`, `_tools.py:1549`, `_tools.py:1564`, `_tools.py:1611`, `_tools.py:1640`) and `FunctionTool.parse_result` (`_tools.py:828-867`). .NET uses `FunctionResultContent(callId, result)` from MEAI (`Shared/Workflows/Execution/WorkflowRunner.cs:348`). Both stacks produce uniform envelopes regardless of underlying tool.
2. **Can the model distinguish success from failure?** Yes. Python: `Content.exception=None` on success, `Content.exception=str(exc)` on failure, plus a `"Error: ..."` prefix in `result` text (`_tools.py:1476`, `_tools.py:1520-1528`, `_tools.py:1561-1569`, `_tools.py:1637-1645`). .NET: relies on MEAI conventions; success carries the value, failure surfaces as `ErrorContent` (compiled with `ErrorContentEventGenerator` for streaming) or as thrown exception handled by the host.
3. **Are stack traces hidden from users/models?** Yes by default. Python: `_auto_invoke_function` returns `"Error: Function failed."` (generic), only includes `Exception: {exc}` when `include_detailed_errors=True` (`_tools.py:1520-1569`, `_tools.py:1637-1645`); the full exception is logged separately via `capture_exception(span, …)` (`_tools.py:749-754`). .NET: `ToolBridge.InvokeAsync` (Hyperlight) and `ProcessBridge.SendToolResponseAsync` (LocalCodeAct) catch `Exception` and surface only `ex.Message` (no traceback). Foundry hosting emits `stream.EmitFailed(ResponseErrorCode.ServerError, message)` with no stack (`Microsoft.Agents.AI.Foundry.Hosting/OutputConverter.cs:251-255`, `AgentFrameworkResponseHandler.cs:217`, `AgentFrameworkResponseHandler.cs:282`). Stack traces are visible only in observability spans (gated by `SENSITIVE_DATA_ENABLED`).
4. **Are large results handled safely?** Yes. Both stacks ship explicit compaction strategies that summarize tool results: Python `ToolResultCompactionStrategy` (`_compaction.py:820-918`) plus `ContextWindowCompactionStrategy` (`_compaction.py:1314-1419`); .NET `ToolResultCompactionStrategy` (`Microsoft.Agents.AI/Compaction/ToolResultCompactionStrategy.cs:172-254`) + `ContextWindowCompactionStrategy` (`Microsoft.Agents.AI/Compaction/ContextWindowCompactionStrategy.cs:72-108`). The MCP layer also enforces per-tool max input size limits during result parsing (`_mcp.py:3008-3019`). MCP long-running tasks cap the poll loop via `max_task_wait` (`_mcp.py:281-295`).
5. **Can tool results be replayed?** Yes, with caveats. Python `Content` is `SerializationMixin` with full `to_dict`/`from_dict` round-trip including `items` (`_types.py:1304-1411`); `_compaction.py:900-903` retains `SUMMARY_OF_MESSAGE_IDS_KEY` so collapsed groups can be traced back. .NET sessions are serialized via `ChatClientAgentSession.Serialize` and the `PerServiceCallChatHistoryPersistingChatClient` decorator persists `FunctionResultContent` alongside paired `FunctionCallContent` (`Microsoft.Agents.AI/ChatClient/PerServiceCallChatHistoryPersistingChatClient.cs:160-161`, `Microsoft.Agents.AI/ChatClient/PerServiceCallChatHistoryPersistingChatClient.cs:236-237`). However, no explicit content-addressable storage is wired — replay depends on the chat-history provider implementation.

## Architectural Decisions

- **Single envelope type, error modeled as a field.** Python chooses `Content(type="function_result")` for both success and failure, with `exception` and a textual `"Error: …"` prefix in `result`. This keeps the chat-history schema uniform and avoids a separate `function_result_error` type.
- **Opt-in detail, default redacted.** `FunctionInvocationConfiguration["include_detailed_errors"]` (`_tools.py:1370-1371`, default `False`) — see also tests at `test_function_invocation_logic.py:1710-1780` — reflects a deliberate separation between developer-facing telemetry (full exception via OTel/logger) and model-facing messages (sanitized). This is reinforced by `OBSERVABILITY_SETTINGS.SENSITIVE_DATA_ENABLED` gating `OtelAttr.TOOL_RESULT` (`_tools.py:758-779`).
- **Bypass for hosted/approval-required tools.** `_is_hosted_tool_approval` (`_tools.py:1927-1937`) and the `server_label` branch in `_auto_invoke_function` (`_tools.py:1481-1496`) ensure MCP approvals are returned untouched rather than being wrapped in a local error envelope.
- **Loop-bound error handling.** `max_consecutive_errors_per_request` (default 3) and `max_function_calls` (default unlimited) bound the impact of repeated tool failures; once reached, `tool_choice="none"` forces a final text-only turn (`_tools.py:2586-2592`, `_tools.py:2632-2644`).
- **MCP errors map to local exceptions, then to the same envelope.** `_mcp.py:1690-1701` translates `CallToolResult.isError` to `ToolExecutionException` so the loop's central catch produces a uniform `function_result` envelope. Long-running task abandonment is distinguished from terminal failure via `_MCPTaskAbandoned` to drive cancel-on-abandonment behavior (`_mcp.py:244-249`, `_mcp.py:2099-2128`).
- **Security redaction via variable references.** Untrusted tool payloads are not returned to the model in raw form; `LabelTrackingFunctionMiddleware` swaps them for `VariableReferenceContent` placeholders that the agent can dereference through dedicated security tools (`security.py:1384-1426`, `security.py:2235-2278`).
- **Large-result management is a layer, not a tool property.** Both stacks treat compaction as a separable strategy that consumes `function_result` envelopes (`_compaction.py:820-918`, `Microsoft.Agents.AI/Compaction/ToolResultCompactionStrategy.cs:49-162`). This keeps tools from having to know about context pressure.
- **Wire-format quirks handled explicitly.** .NET `EncodeFunctionResultAsJsonStringPayload` (`Microsoft.Agents.AI.Foundry.Hosting/OutputConverter.cs:452-490`) documents why `BinaryData` auto-detection must be bypassed, and `DecodeFunctionResultPayload` mirrors it on the inbound side (`Microsoft.Agents.AI.Foundry.Hosting/InputConverter.cs:491-533`) so replays survive round-trip.

## Notable Patterns

- **Uniform `Content` envelope with rich `items` field.** `Content.from_function_result` normalizes every tool output into `list[Content]` carrying text/data/uri items alongside a flattened `result` string (`_types.py:817-874`).
- **`SKIP_PARSING` sentinel** lets callers (typically sandboxed runtimes) consume raw values without forcing `Content` wrapping (`_tools.py:101-125`, `_tools.py:698-701`).
- **Per-tool invocation limits + invocation-exception limits** on `FunctionTool` instance, layered with loop-level limits (`_tools.py:325-406`).
- **`FunctionApprovalResponse` carry-through.** When a tool's `function_approval_response` arrives mid-loop, already-approved requests are stored against visible approval IDs and reinjected only when the visible flow resumes (`_tools.py:1721-1755`, `_tools.py:1998+`).
- **OTel semconv compliance for MCP.** `error.type="tool_error"` attribute is set on spans when servers report `isError` (`_mcp.py:1697-1700`, `_mcp.py:1711-1712`).
- **Sandbox bridges neutralize exceptions.** `ToolBridge.InvokeAsync` (Hyperlight) and `ProcessBridge.SendToolResponseAsync` (LocalCodeAct) both convert exceptions into JSON envelopes with explicit `ok` flag (`Microsoft.Agents.AI.Hyperlight/Internal/ToolBridge.cs:37-51`, `Microsoft.Agents.AI.LocalCodeAct/Internal/ProcessBridge.cs:266-272`).
- **Streaming approvals.** `FunctionResultEventGenerator` and `ErrorContentEventGenerator` decouple wire-format generation from the model layer (`Microsoft.Agents.AI.Hosting.OpenAI/Responses/Streaming/FunctionResultEventGenerator.cs:13-27`, `Microsoft.Agents.AI.Hosting.OpenAI/Responses/Streaming/ErrorContentEventGenerator.cs:14-72`).

## Tradeoffs

- **Generic error vs. actionable error.** Defaulting to `"Error: Function failed."` (`_tools.py:1561`) prevents leaking internals to the model but also prevents the model from self-correcting. The opt-in `include_detailed_errors` requires per-client configuration, which can be forgotten.
- **Single envelope, no error sub-discriminator.** All failure is inferred from `exception=` presence + `"Error:"` prefix (`_tools.py:1476-1569`). Tools that want to distinguish retryable vs. terminal failures must encode it in the message text.
- **MCP `isError` always elevates to exception.** `_call_tool_with_retries` (`_mcp.py:1690-1701`) does not allow the model to read an `isError=true` result verbatim; the framework forces a `ToolExecutionException`. This is safe but breaks pass-through transparency for tools that intentionally return error-as-data.
- **Stack-trace leakage through observability.** `OBSERVABILITY_SETTINGS.SENSITIVE_DATA_ENABLED` is opt-in (`observability.py:807-815`), so production deployments that leave it off never log arguments/results, but developers toggling it on locally will see them. There is no per-tenant / per-tool override.
- **Compaction rewrites messages.** `ToolResultCompactionStrategy` (`_compaction.py:820-918`) mutates `messages` in place, which complicates transactional replay and breaks cross-process resumability.
- **No canonical "error envelope" subclass.** Errors and successes share `Content`; consumers must check `exception is not None` or the textual prefix. This is flexible but means a typo in the prefix (`"error:"` vs `"Error:"`) silently degrades observability.
- **.NET hosted mode drops `FunctionResultContent` without replacement.** `WorkflowRunner.InvokeFunctionAsync` (`Shared/Workflows/Execution/WorkflowRunner.cs:342-349`) builds `ChatMessage(ChatRole.Tool, [new FunctionResultContent(callId, JsonSerializer.Serialize(result))])` — exceptions from `functionTool.InvokeAsync` propagate unwrapped, so the model sees a chat-client failure instead of a tool-result error envelope.

## Failure Modes / Edge Cases

- **Tool not in tool map.** `Content.from_function_result(call_id, result="Error: Requested function \"…\" not found.", exception=str(KeyError))` (`_tools.py:1472-1479`); with `terminate_on_unknown_calls=True`, a hard raise instead (`_tools.py:1719-1720`).
- **Argument validation failure.** Model sees `Error: Argument parsing failed.` (generic) or `Error: Argument parsing failed. Exception: …` (detailed) (`_tools.py:1519-1528`).
- **Tool throws during invocation.** Caught centrally (`_tools.py:1556-1569`, `_tools.py:1632-1645`); tool's `invocation_exception_count` is incremented, and when `max_invocation_exceptions` is reached the tool refuses subsequent calls via `ToolException` (`_tools.py:524-531`).
- **Result parser raises.** Falls back to `str(result)` rather than crashing (`_tools.py:702-706`, `_tools.py:763-769`).
- **Declaration-only tool returned to model.** Flagged with `user_input_request=True` (`_tools.py:1716-1718`, `_tools.py:1757-1765`); `AgentExecutor` then emits a request-info event and pauses the workflow.
- **MCP server reports `isError=True`.** Server text becomes the exception message; `ToolExecutionException` carries it back to `_auto_invoke_function` which wraps as `function_result` with `exception` (`_mcp.py:1690-1701`, `_tools.py:1556-1569`).
- **MCP connection drops mid-call.** Retried once (`_mcp.py:1687-1727`); second failure becomes `ToolExecutionException("Failed to call tool '…' - connection lost.")`. With long-running tasks, dropped connection **after** `task_id` is known reconnects-and-retries once against the same id (`_mcp.py:2127`, `_mcp.py:1855`).
- **MCP `max_task_wait` exceeded.** Raises `ToolExecutionException("MCP task '…' exceeded max_task_wait of …")` and fires best-effort `tasks/cancel` (`_mcp.py:1864-1878`).
- **Consecutive error budget exceeded.** `tool_choice="none"` forced and a final non-tool turn is requested (`_tools.py:2632-2644`, `_tools.py:2673-2681`).
- **Function call missing `call_id`.** Raises `KeyError("Function \"…\" is missing call_id.")` (`_tools.py:1579-1581`); in MCP server tools, the wire-id ⇄ request-id mapping is preserved via `ToolApprovalIdMap` (`Microsoft.Agents.AI.Foundry.Hosting/ToolApprovalIdMap.cs:14-67`).
- **Content serialization excludes fields explicitly.** `DEFAULT_EXCLUDE` on `FunctionTool` omits `func`, `input_model`, histograms (`_tools.py:291-299`); `to_dict` honors per-call `exclude` (`_types.py:1304-1359`).
- **Streaming mid-iteration abort.** `ChatClientAgent.RunCoreStreamingAsync` ensures inner enumerator disposal so per-service-call history persistence does not leak dangling `FunctionResultContent` (`Microsoft.Agents.AI/ChatClient/ChatClientAgent.cs:398-401`).

## Future Considerations

- Promote `error_envelope` to a first-class sub-type (`Content(type="function_result_error", …)`) so consumers don't need to inspect `exception` or text prefixes; this would also let frameworks uniformly record `_severity`/`_retryable`.
- Force `include_detailed_errors` to default `False` at every layer; today the opt-in nature risks accidental traceback leakage in production.
- Wire `ReplacingRedactor` (`Shared/Redaction/ReplacingRedactor.cs:12-34`) into the .NET function-invocation path so error envelopes can be redacted at construction time, not only at log emission.
- Add explicit replay IDs (`replay_token`) to `FunctionResultContent` so checkpoint-replay workflows can detect duplicates (currently only chat-history persistence provides correlation via `callId`).
- Add per-tool cap on result size in `FunctionTool` itself (`max_result_bytes`) to prevent a single tool from blowing past compaction thresholds.
- Document a hard upper bound for `Content.result` text (today the only truncation lever is the `ContextWindowCompactionStrategy`).

## Questions / Gaps

- **No evidence found** for an explicit "error envelope" content type distinct from `function_result`. All failures are encoded as `Content(type="function_result", exception=…, result="Error: …")`.
- **No evidence found** that stack traces are programmatically scrubbed from `str(exc)`; the redaction depends on Python's default `__str__`, which for `ValueError` etc. is message-only but for some exception types may include formatted detail.
