## Summary

LangGraph expresses tool results as **`langchain_core.messages.ToolMessage`** objects with three structured fields: `content` (str or list of content blocks per `TOOL_MESSAGE_BLOCK_TYPES`), `tool_call_id` (binds the result to a specific `AIMessage.tool_calls[id]`), and `status` (the `"error"` flag on the failure path). The shape is produced and enforced centrally by `ToolNode` (`libs/prebuilt/langgraph/prebuilt/tool_node.py:622-1580`) and surfaced into chat-history validation by `_validate_chat_history` (`libs/prebuilt/langgraph/prebuilt/chat_agent_executor.py:243-271`), which raises `INVALID_CHAT_HISTORY` whenever an `AIMessage.tool_calls` entry lacks a paired `ToolMessage`. The error envelope is two-layered: a **dedicated exception subclass** `ToolInvocationError(ToolException)` (`libs/prebuilt/langgraph/prebuilt/tool_node.py:339-380`) that filters out injected arguments so the LLM only sees errors it can fix, plus a **generic failure envelope** built by `_handle_tool_error` (`libs/prebuilt/langgraph/prebuilt/tool_node.py:394-441`) using `TOOL_CALL_ERROR_TEMPLATE = "Error: {error}\n Please fix your mistakes."` rendered into a `ToolMessage(..., status="error")` (`tool_node.py:1007-1012`, `tool_node.py:1062-1067`, `tool_node.py:1154-1159`, `tool_node.py:1217-1222`).

Redaction of internal errors is **explicit but opt-in by configuration**, not enforced by construction. Stack traces are stripped by the runner in `_runner.py` via `EXCLUDED_FRAME_FNAMES` (`libs/langgraph/langgraph/pregel/_runner.py:58-68`, `tool_node.py:241-248`, `tool_node.py:351-358`, `tool_node.py:432-439`, `tool_node.py:565-572`) — when a node exception is re-raised, framework frames (`langgraph/pregel/{retry,runner,executor}.py`, `langgraph/utils/runnable.py`, `langchain_core/runnables/config.py`) are skipped while leaving the user-code trace intact. However the tool-level error envelope uses `repr(e)` (`tool_node.py:430`) which preserves the full exception type and args, and the validator path uses `_default_format_error` that returns `f"{repr(error)}\n\nRespond after fixing all validation errors."` (`tool_validator.py:34-41`). The `handle_tool_errors` knob (`tool_node.py:622-739`) lets users replace this default with a callable, fixed string, tuple of exception types, or `False` to disable. **There is no built-in "stack-trace redaction" toggle** — it is the user's responsibility to scrub.

Large-result handling is **delegated downstream**, not centralized in the tool layer. There is no summarizer, truncator, or artifact-reference primitive in `ToolNode`; the `ToolCallTransformer` (`libs/prebuilt/langgraph/prebuilt/_tool_call_transformer.py:44-165`) and `ToolCallStream` (`libs/prebuilt/langgraph/prebuilt/_tool_call_stream.py:17-117`) project `tools` channel events into `run.tool_calls`, allowing UIs to consume deltas but relying on the consumer to truncate. There is no `Content.from_hosted_file` analogue; tool output is whatever the tool returned, normalized to a `str | list[dict]` via `msg_content_output` (`tool_node.py:309-336`) that JSON-serializes arbitrary objects or falls back to `str(output)`. The `tools` stream-mode events (`tool-started`, `tool-output-delta`, `tool-finished`, `tool-error`) are the lifecycle hooks for downstream projection (`_tool_call_transformer.py:127-146`, `_tool_call_stream.py:54-88`).

Replays are fully supported at the message level: tool-call IDs, tool names, full `ToolMessage.content`, and `status` are persisted in checkpoints via `_serde.py` (`libs/langgraph/langgraph/_internal/_serde.py:73-74` includes `ToolMessage` and `ToolMessageChunk`), and the Pregel runner replays writes from earlier super-steps on resume (`test_time_travel_async.py:1-880`). Errors are also checkpointable via `task.writes.append((ERROR, exception))` in the runner's commit path (`_runner.py:579-603`).

## Rating

**8 / 10** — Clear model with tests, explicit interfaces, and operational safeguards. `ToolMessage` carries a first-class `status="error"` flag and is bound to `tool_call_id`, errors funnel through a templated envelope with multiple configuration knobs, framework frames are stripped from re-raised tracebacks, and the system supports wrapping, interceptor-based retries, per-tool error handlers, and node-level `error_handler=` fallbacks. Deductions: stack-trace redaction is **opt-in only** (the default `repr(e)` returns type+args and can include secrets), there is **no built-in large-result summarization or truncation** in the tool layer, and there is **no artifact-reference primitive** (`Content.from_hosted_file` analogue absent) — these are punted to the application layer.

## Answers to Dimension Questions

1. **Is every tool result structured?** Yes. `ToolNode` always emits a `ToolMessage` (or a `Command` containing one) on the success path (`tool_node.py:1432-1453`), and on every failure path always emits `ToolMessage(content=..., tool_call_id=..., status="error", name=...)` (`tool_node.py:1007-1012`, `tool_node.py:1276-1278`). The wrapper path also converts exceptions to `ToolMessage(status="error")` (`tool_node.py:1062-1067`, `tool_node.py:1217-1222`). The legacy `ValidationNode` uses `additional_kwargs={"is_error": True}` instead of `status` (`tool_validator.py:208-214`). `Command` returns are validated for exactly one terminating `ToolMessage` bound to the outer `tool_call_id` (`tool_node.py:1455-1501`, `tool_node.py:1503-1579`).

2. **Can the model distinguish success from failure?** Yes, in three independent ways: (a) the `status="error"` field on `ToolMessage` (`tool_node.py:1007-1012`), (b) the `"Error: ..."` content prefix from the templated envelope (`tool_node.py:108-121`, `tool_node.py:430`), and (c) for the legacy validator path, `additional_kwargs["is_error"]` (`tool_validator.py:213`). Chat history validation explicitly enforces the pairing (`chat_agent_executor.py:253-271`) so a missing `ToolMessage` raises `INVALID_CHAT_HISTORY` before the model sees the history.

3. **Are stack traces hidden from users/models?** Partially. The Pregel runner trims framework frames from re-raised exceptions via `EXCLUDED_FRAME_FNAMES` (`_runner.py:58-68`, `_runner.py:240-248`, `_runner.py:350-358`, `_runner.py:431-439`, `_runner.py:565-572`) before propagation. However, the `ToolMessage` error envelope uses `repr(e)` (`tool_node.py:430`), which surfaces `type(args)` and any string-formatted exception details that the user's tool implementations chose to include. There is **no opt-out flag** in `ToolNode` to suppress these — `handle_tool_errors` lets users replace the formatter entirely (`tool_node.py:622-739`) but does not provide a built-in "redact stack" mode. Stream-level PII redaction is supported by the `StreamTransformer` API but is the user's responsibility (`stream/_types.py:60-175`).

4. **Are large results handled safely?** Not by `ToolNode`. `msg_content_output` only handles serialization format (`tool_node.py:309-336`) and the streaming layer (`_tool_call_transformer.py:44-165`) projects `tool-output-delta` events for incremental consumption, but there is **no size cap, no truncation, no summarization**. `TOOL_INVOCATION_ERROR_TEMPLATE` includes the raw `tool_kwargs` (`tool_node.py:117-121`), so a large payload can echo back to the model on failure. Application-level `Command` returns can also include arbitrary message lists. The `chat_agent_executor.py` reference at line 397 only mentions `message trimming, summarization` as something the user could plug in via `pre_model_hook`/`post_model_hook`.

5. **Can tool results be replayed?** Yes — `ToolMessage` and `ToolMessageChunk` are first-class serializable types in the internal serde allowlist (`_internal/_serde.py:73-74`). Checkpoint writes include the full message (content, tool_call_id, status, name), and time-travel tests confirm re-running a graph from a checkpoint reproduces the same `ToolMessage` sequence (`test_time_travel_async.py:79-876`). Errors are also checkpointable as `(ERROR, exception)` writes (`_runner.py:579-603`) and survive resume (`test_retry.py:2161-2197`). The error-handler context (`NodeError`) similarly serializes (`errors.py:148-165`).

## Architectural Decisions

- **Use `langchain_core.messages.ToolMessage.status` as the canonical success/failure flag** rather than inventing a new envelope type (`tool_node.py:1007-1012`). The decision is documented in the legacy `ValidationNode` example at `tool_validator.py:96-113` (`additional_kwargs={"is_error": True}` predates `ToolMessage.status` and the legacy v1 chat-history check `if msg.additional_kwargs.get("is_error")` is still in place at `tool_validator.py:102`).
- **Centralize error envelope generation in `_handle_tool_error` and `_default_handle_tool_errors`** (`tool_node.py:383-441`) so every failure path — direct exception, validation error, wrapper exception, invalid tool name — flows through the same template + configuration. Tests pin this: `test_tool_node.py:269-602`.
- **Filter injected arguments from validation errors before they reach the LLM** (`tool_node.py:510-563`, `tool_node.py:961-966`). Rationale: injected args (`InjectedState`, `InjectedStore`, `ToolRuntime`) are not LLM-controlled, so surfacing their validation errors would be confusing noise. This is a model-readable-feedback decision, not a security decision.
- **Re-raise `GraphBubbleUp` (interrupts, drains, parent commands) without wrapping** (`tool_node.py:973-983`, `tool_node.py:1120-1130`). These are control-flow signals, not failures, and must propagate to the runner's interrupt-handling path (`_runner.py:584-603`).
- **Strip framework frames from `__traceback__` before re-raising** (`_runner.py:58-68`, `_runner.py:240-248`, `_runner.py:350-358`). The list is intentionally narrow: only the executor / retry / runnable plumbing is removed, leaving the user's code visible so the model can see *what* failed (the comment at `_runner.py:58-59` calls this out).
- **Persist `(ERROR, exception)` to the checkpointer alongside task writes** (`_runner.py:579-603`). This makes tool errors checkpointable and replayable and feeds the `ERROR_SOURCE_NODE` mapping used by the `_should_route_to_error_handler` decision (`_runner.py:598-602`).
- **Decouple streaming lifecycle from the chat-message stream** by introducing the `tools` stream mode (`_tool_call_transformer.py:44-150`) and `ToolCallStream` projection (`_tool_call_stream.py:17-117`). Consumers that want partial tool output subscribe to `tools`; the main event log stays free of in-progress tool messages. This avoids mutating chat history while a tool is still running.
- **Make `NodeError` a frozen dataclass injected by parameter name** (`errors.py:148-165`) so handlers stay typed; the alternative would be a global registry that loses information across serialization.

## Notable Patterns

- **Wrapper/interceptor pattern**: `wrap_tool_call` (`tool_node.py:202-217`) and `awrap_tool_call` (`tool_node.py:279-283`) are typed wrappers around the tool-invocation step that can short-circuit, retry, or modify the request. The execute callback is deliberately stateless and re-callable for retries (commented at `tool_node.py:212-217`). The `Conditional retry based on response` example at `tool_node.py:254-265` uses `result.status != "error"` to drive backoff.
- **Type-driven handled-exception inference** (`tool_node.py:444-507`): the framework reads the handler's first parameter annotation and only routes matching exception types to it. This converts what would be runtime `isinstance` checks into static type safety, validated by `_infer_handled_types` raising `ValueError` on non-`Exception` annotations (`tool_node.py:482-490`, `tool_node.py:494-503`).
- **Per-tool error handlers via `BaseTool.handle_tool_error`** (referenced at `test_tool_node.py:122`): individual tools can opt out of the node-wide `handle_tool_errors` by setting their own string/callable. Tests pin this at `test_tool_node.py:536-580`.
- **Layered error envelopes**: the runner writes `ERROR` and `ERROR_SOURCE_NODE` writes (`_runner.py:597-603`), the scheduler builds a handler `PregelExecutableTask` (`_algo.py:1110-1159`), and the handler itself produces a `Command(update=...)` to recover (`errors.py:148-165`). Three cooperating layers, each with a single responsibility.
- **StreamTransformer pre-lane**: `StreamMux` runs user transformers (PII redaction, profanity filters) before built-in transformers like `MessagesTransformer` (`stream/_types.py:60-175`, `tests/test_stream_before_builtins.py:151-295`). The redaction is mutating-in-place, which is documented as a load-bearing guarantee (`tests/test_pregel_stream_events_v3.py:1438-1465`).
- **`ToolCallWithContext` send payload** (`tool_node.py:286-306`, `tool_node.py:1237-1245`, `tool_node.py:1296-1313`): a typed dict sent over the `Send` API that bundles `tool_call` + state for parallel tool fan-out. The discriminator key `__type="tool_call_with_context"` is defensive against user-state key collisions (`tool_node.py:299-304`).

## Tradeoffs

- **Stack-trace redaction is opt-in, not enforced.** The default `TOOL_CALL_ERROR_TEMPLATE` includes `repr(e)` (`tool_node.py:111`, `tool_node.py:430`), which can leak exception details, secrets in error messages, or Python internals. Users must supply a callable handler that scrubs content (`tool_node.py:622-739`). Compare to agent-framework's `include_detailed_errors` flag, which defaults to `False`.
- **No built-in large-result cap.** `ToolNode` is silent on size; it is up to the tool author or downstream stream consumer to truncate (`msg_content_output` at `tool_node.py:309-336` is the only normalization, and it's purely about format). Large tool outputs can blow out the model's context window before any retry/summary kicks in.
- **Validator envelope (`tool_validator.py:208-214`) uses `additional_kwargs["is_error"]` instead of `status="error"`.** This is consistent with the older LangChain convention but means two error envelopes exist for the same failure mode. The `tool_validator.py` module is marked deprecated (`tool_validator.py:43-46`) in favor of `create_agent` from `langchain.agents`, but remains in the codebase.
- **Framework-frame stripping is hard-coded**, not configurable (`_runner.py:58-68`). If a user wants to see the full traceback (e.g., for debugging framework bugs), they cannot get it from a re-raised node exception.
- **`_handle_tool_error` uses `repr(e)`, which differs from `str(e)`.** `repr(e)` produces `ValueError('Test error')` (test at `test_tool_node.py:366`) while many users expect `str(e)`. The default template can be overridden (`tool_node.py:622-739`).
- **`GraphInterrupt` semantics require a checkpointer** (documented at `types.py:811-832`) — without persistence, interrupt + tool-call replay cannot work. This couples the error/pause contract to a deployment requirement.
- **`Command` validation requires exactly one terminating `ToolMessage`** (`tool_node.py:1479-1485`). This is correct for chat-model APIs (every `tool_calls[id]` must have a `ToolMessage`) but is a hard constraint that can surprise tools returning multiple non-terminator messages.

## Failure Modes / Edge Cases

- **`ValidationError` from Pydantic** is converted to `ToolInvocationError` with `filtered_errors` (`tool_node.py:959-966`). If `filtered_errors` ends up empty (e.g., the only errors were injected args), the user receives `TOOL_INVOCATION_ERROR_TEMPLATE` with an empty `error` string. Tests do not cover this case.
- **Multiple exceptions in parallel fan-out**: one tool call's `GraphInterrupt` does not cancel siblings (`_runner.py:300-301`, `_runner.py:417`). But a non-`GraphBubbleUp` exception does, via `_should_stop_others` (`_runner.py:616-634`).
- **`handle_tool_errors=False` re-raises** (`tool_node.py:1002-1003`, `tool_node.py:1149-1150`). For unhandled tool exceptions, the framework does not catch and continue — the exception bubbles up through the runner's standard error path (`_runner.py:240-248`). This can halt the entire run instead of producing a recoverable `ToolMessage`.
- **Concurrent tool calls** with mixed success/failure: each call's `ToolMessage` is emitted independently (`tool_node.py:822-826`, `tool_node.py:855-860`). There is no batch-level "any failed" flag for the LLM to consult; it must inspect each `status` field.
- **Stream-mode `tool-error` event is fired via `_fail(message)`** with `str(err)` (`_tool_call_transformer.py:161-164`). If the stream is not subscribed to, the error is **lost** — it only exists on the `ToolCallStream.error` handle (`_tool_call_stream.py:86-87`) and not in chat history.
- **`ToolCallRequest.__setattr__` emits a `DeprecationWarning`** when callers mutate instead of calling `override()` (`tool_node.py:151-168`). If users ignore the warning, the mutation works but bypasses the immutability contract.
- **Re-running a checkpoint re-executes the tool body**, not the recorded `ToolMessage` content (covered by `test_time_travel_async.py:79-291`). If the tool is non-idempotent, replay can produce different content; there is no built-in "use checkpointed output instead of re-executing" mode for tool calls.
- **`EXCLUDED_FRAME_FNAMES` filtering only happens on re-raise**, not on the in-memory exception (`_runner.py:241-247`). Logging or observability callbacks may still see the unfiltered traceback.
- **`_filter_validation_errors` only filters on `error["loc"][0]`** (`tool_node.py:548`). Errors at nested locs inside injected args (e.g., a validator inside `InjectedState["messages"][0]`) are still emitted because the outer loc is not in `injected_arg_names`.

## Future Considerations

- **Promote `status="error"` as the sole error flag.** The deprecated `tool_validator.py:208-214` still uses `additional_kwargs["is_error"]`, which means consumer code must check both. The migration path is incomplete.
- **Add a built-in redaction mode** analogous to agent-framework's `include_detailed_errors=False` (`tool_node.py:622-739`). Today the only safe option is to write a custom handler; an opt-in `redact_stack=True` flag would close the gap.
- **Add a result-size cap or summary hook** at the `ToolNode` boundary. The streaming projection exists (`_tool_call_transformer.py:44-165`) but no truncation policy is enforced before the message reaches chat history. This is the dimension's biggest gap.
- **Introduce a typed `ToolArtifact` reference** for files, URIs, vector-store IDs, etc. The current contract forces `msg_content_output` to JSON-serialize or `str()` the output (`tool_node.py:309-336`), which can produce huge or lossy payloads.
- **Unify `handle_tool_errors` with `handle_tool_error` (per-tool).** Two mechanisms exist (`tool_node.py:622-739` and `BaseTool.handle_tool_error` referenced at `test_tool_node.py:122`) and the precedence rules are implicit. A documented resolution order would help.
- **Persist `ToolMessage.status` in stream events** so consumers of `stream_mode="tools"` can branch on success vs error without joining against chat history. Today only `tool-finished` (success) and `tool-error` (failure) carry the distinction implicitly (`_tool_call_transformer.py:139-146`).
- **Make `EXCLUDED_FRAME_FNAMES` configurable** so users debugging framework bugs can opt back into full tracebacks.
- **Validate `Command` returns from tools** against the chat model's provider constraints (today only `tool_call_id` binding is enforced; some providers require name/content conventions).
