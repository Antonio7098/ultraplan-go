## Summary

Both the Python and .NET implementations ship a dedicated **compaction subsystem** that implements token budgeting as an explicit, pluggable strategy layer rather than ad-hoc truncation. The core model is identical in both languages: conversation messages are grouped into atomic units (`system`, `user`, `assistant_text`, `tool_call`, `summary`), per-message token counts are annotated (real tokenizer when supplied, otherwise a chars/4 or bytes/4 estimate), and strategies exclude whole groups — never partial tool-call groups — until an included-token budget is satisfied. A two-phase `ContextWindowCompactionStrategy` derives budgets from a caller-supplied model context window: tool-result eviction (collapse older tool groups into bounded summaries) at 50% of input budget and oldest-first truncation at 80%. An LLM-backed `SummarizationStrategy` is a separate, explicit opt-in with documented prompt-injection risk, failure escalation, and bidirectional provenance links between summaries and originals. Budgets are configurable per client, per agent, and per run; they are **not** derived automatically from model metadata. The main weaknesses are heuristic default tokenizers, no reconciliation of estimates against actual provider-reported usage, and the fact that a single oversized group still passes through to the provider.

## Rating

**8 / 10** — Clear model with tests, explicit interfaces, and operational safeguards. The design has: protocol/interface-based extensibility (`TokenizerProtocol`, `CompactionStrategy` in python/packages/core/agent_framework/_compaction.py:51-73; abstract `CompactionStrategy` with trigger/target delegates in dotnet/src/Microsoft.Agents.AI/Compaction/CompactionStrategy.cs:50-94); deterministic fallbacks that guarantee budget enforcement while never producing an empty projection (_compaction.py:1450-1472); atomicity guarantees for tool-call/reasoning groups backed by ~90 unit tests; failure escalation for summarization; observability hooks (.NET ActivitySource at dotnet/src/Microsoft.Agents.AI/Compaction/CompactionTelemetry.cs:13-15). It falls short of 9-10 because default token counting is heuristic (4 chars/token), estimated counts are never calibrated against real usage reported by providers, budgets require manual per-model configuration with no context-window registry, and single-group overflow can still reach the wire.

## Answers to Dimension Questions

**1. Is token usage measured before calling the model?**
Yes — pre-flight estimation on every model call. In Python, `BaseChatClient.get_response` resolves compaction overrides and calls `_prepare_messages_for_model_call` before dispatching to `_inner_get_response` (python/packages/core/agent_framework/_clients.py:510-558); this happens inside each iteration of the function-invocation loop because strategy/tokenizer are threaded through every loop call (python/packages/core/agent_framework/_tools.py:3647-3683). Measurement is per-message annotation (`annotate_token_counts`, _compaction.py:648-673) plus aggregate `included_token_count` (_compaction.py:709-715). In .NET, `CompactionMessageIndex` maintains `IncludedTokenCount` metrics consulted by trigger predicates (dotnet/src/Microsoft.Agents.AI/Compaction/CompactionMessageIndex.cs:349 area; CompactionTriggers.cs:42-59). However, measurement is **estimation**: Python defaults to `len//4` characters (_compaction.py:76-80) unless a caller supplies a real tokenizer; .NET uses `Microsoft.ML.Tokenizers` when provided and `UTF-8 byteCount/4` otherwise (CompactionMessageIndex.cs:446, 501-508). Actual usage returned by providers (`UsageDetails.input_token_count`, etc.) is tracked for observability (python/packages/core/tests/core/test_observability.py:5647-5659 shows cache/reasoning breakdowns) but there is **no code reconciling estimates against actual usage** — searched `usage` across `_compaction.py` (zero matches).

**2. What gets dropped when budget is exceeded?**
Whole logical groups, oldest first, with a strict priority order: (a) tool-result eviction collapses older tool-call groups into bounded text summaries, keeping the newest N verbatim (default `keep_last_tool_call_groups=4` in the harness default, _compaction.py:1665, 1710-1716); (b) truncation excludes oldest non-system groups toward `compact_to` (_compaction.py:856-867); (c) composed-strategy fallback excludes remaining non-system groups with reason `token_budget_fallback`, and finally even system anchors with reason `token_budget_fallback_strict` (_compaction.py:1450-1472). Protected throughout: the latest non-system group (never-empty projection guarantee, _compaction.py:778-786) and system groups (until the strict fallback, _compaction.py:851-853). Tool-call groups are never split — declarations, results, reasoning prefixes, and even non-adjacent results matched by `call_id` form one atomic group via union-find linking (_compaction.py:150-197, 253-297), tested at python/packages/core/tests/core/test_compaction.py:209-344. Dropped content is not deleted: messages stay in storage flagged `_excluded=True` with a machine-readable `_exclude_reason` ("truncation", "sliding_window", "tool_result_compaction", "summarized", "token_budget_fallback", ...) (_compaction.py:33-34, 718-724), and the after-run phase keeps them in history so annotations persist (_compaction.py:1619-1622). The .NET side mirrors this with `minimumPreservedGroups` hard floors (ContextWindowCompactionStrategy.cs:101-107 passes 2; TruncationCompactionStrategy.cs:22-23 documents the floor).

**3. Is summarization faithful?**
Two distinct mechanisms. The deterministic `ToolResultCompactionStrategy` is faithful-by-construction: it embeds verbatim tool-name/result excerpts, capped at 4096 chars, with an explicit `... [truncated]` marker rather than paraphrase (_compaction.py:983-986, 1085-1101; bound tested at test_compaction.py:1290). The LLM-backed `SummarizationStrategy` constrains fidelity contractually: the default prompt demands ≤5 sentences, reflection of both parties' contributions, incorporation of any previous summary, omission of nothing from earlier summaries, and forbids speculation/critique (_compaction.py:1176-1191). Faithfulness is auditable rather than guaranteed: every summary carries forward links to original message/group IDs and every original carries a back-link to its summary ID (_compaction.py:35-37, 1064-1077, 1374-1392; tested at test_compaction.py:848, 1356), and originals remain retrievable in storage. Operational honesty about failure is built in: summarizer exceptions or empty output abort compaction for that turn (history stays full) and repeated failures escalate to error logs (_compaction.py:1348-1372, 1273-1288; tests at 975-1047). Both languages document the trust boundary explicitly — a compromised summarizer injects persistent instructions into history (python _compaction.py:1207-1217; dotnet SummarizationCompactionStrategy.cs:36-45). No semantic-faithfulness verification (e.g., entailment checks or diff review) exists.

**4. Is budget configurable?**
Yes, at four levels, but never automatically per-model. (i) Client-level: constructor args on `BaseChatClient` (python/packages/core/agent_framework/_clients.py:292-305). (ii) Agent-level: `Agent(compaction_strategy=, tokenizer=)` with documented precedence over client settings (_agents.py:861-864, 886-888). (iii) Run-level: per-call overrides accepted by `run`/`run_stream` and threaded through middleware (_agents.py:1015-1031; _middleware.py:1352-1363). (iv) Strategy-level: thresholds (`tool_eviction_threshold=0.5`, `truncation_threshold=0.8`), retention counts, summarizer target/threshold, and summarizer input budget (8000 tokens default) are all constructor params with validation (_compaction.py:1258-1263, 1688-1697). The harness exposes `max_context_window_tokens` / `max_output_tokens` at agent creation and additionally sets `max_tokens` output cap in default options (_harness/_agent.py:311-312, 530-539, 633-634). Output-side `max_tokens` request validation exists in ChatOptions (python/packages/core/agent_framework/_types.py:3783-3784). What is missing: no registry maps a model id to its context window — callers must hardcode it (the .NET docs merely cite examples like "1,050,000 for gpt-5.4", ContextWindowCompactionStrategy.cs:52-55). There is no per-agent *automatic* differentiation beyond these constructor choices, though nothing prevents different agents sharing a client from using different strategies since strategies are instance state on the Agent.

## Architectural Decisions

1. **Compaction as annotated projection, not deletion.** Strategies mutate inclusion flags on immutable-in-place Message objects; the full transcript persists and the model sees a projected view (`project_included_messages`, python/packages/core/agent_framework/_compaction.py:705-737, 1475-1488). This preserves auditability and lets exclusions be reasoned about later.
2. **Group atomicity as the safety invariant.** Tool calls, their results (even non-adjacent, matched by ordered unambiguous `call_id` occurrence analysis), and attached reasoning form indivisible units (python/packages/core/agent_framework/_compaction.py:105-198, 510-541). The AGENTS.md spec elevates this to a contract requiring adapters to fail before sending requests whose required reasoning cannot be reconstructed (python/packages/core/AGENTS.md, "Reasoning content ... compaction must preserve that group atomically").
3. **In-place list mutation over copies** to fix silent summary loss across function-loop iterations, with regression comment referencing issue #4991 (python/packages/core/agent_framework/_clients.py:383-388).
4. **Trigger/target separation in .NET**: compaction policies are predicates over index metrics (`CompactionTrigger` delegate), composable via `All`/`Any`, decoupling *when* to compact from *how* (dotnet/src/Microsoft.Agents.AI/Compaction/CompactionTrigger.cs:14-15; CompactionStrategy.cs:64-79).
5. **Two-phase graduated response** (summarize tools at 50%, truncate at 80%) instead of a single cliff, acknowledging tool chatter as the dominant growth vector first (_compaction.py:1624-1637).
6. **LLM summarization as opt-in with security documentation**, isolated from the deterministic strategies and gated behind explicit client construction (_compaction.py:1207-1217).
7. **Dual-language parity**: the same strategy taxonomy exists in both stacks (dotnet/src/Microsoft.Agents.AI/Compaction/ contains Truncation/SlidingWindow/ToolResult/Summarization/ContextWindow/Pipeline counterparts), indicating a deliberate cross-platform design commitment.

## Notable Patterns

- **Incremental annotation with suffix reuse**: re-annotating only new messages, expanding back to unique declarations when a late result arrives, and preserving prefix group indices (_compaction.py:543-624). Token counts cached per message make steady-state compaction O(new messages).
- **Exclusion reasons as an audit vocabulary**: every strategy stamps a distinct reason string, enabling tests like "verify the truncation phase did NOT fire" by filtering on `_exclude_reason` (test_compaction.py:1835-1839).
- **Budget composition with early stop and deterministic last resort**: strategies run in order, tokens re-measured between steps, early stop at budget, then mechanical fallback ensures the invariant holds even if custom strategies under-perform (_compaction.py:1433-1472).
- **Turn-aware .NET metrics**: `IncludedTurnCount` and turn-indexed groups enable "compact after N user turns" policies, which Python lacks (CompactionMessageIndex.cs:60-70; CompactionTriggers.cs:62-79).
- **Session-state persistence of the compaction index** in .NET so exclusions survive process restarts (CompactionProvider.cs:143-165, 183-185), versus Python's reliance on history-provider `skip_excluded` semantics (_compaction.py:1619-1622; test at test_compaction.py:1734).
- **Deferral of persisted-history rewriting to end-of-turn** (`after_run_once_per_turn`) to avoid mutating the transcript mid-loop (_compaction.py:1532-1534).

## Tradeoffs

- **Estimation speed vs accuracy**: `chars//4` / `bytes//4` defaults are fast and dependency-free but systematically wrong for many languages and for JSON-heavy payloads; Python mitigates CJK inflation in serialization (_compaction.py:643-644) but the estimator itself remains crude. Real-tokenizer support exists in both stacks yet no default wiring ships (no `tiktoken` dependency in Python core — searched; no `TiktokenTokenizer` construction anywhere in dotnet tree — searched).
- **Never-deleting vs memory growth**: keeping excluded originals indefinitely preserves audit trails but means long-lived sessions grow unboundedly in storage; the framework accepts this in exchange for recoverability (_compaction.py:1619-1622).
- **Whole-group granularity vs tight packing**: excluding entire tool groups may overshoot the target (documented: "may remain above compact_to when that group alone exceeds it", _compaction.py:806-807), trading budget precision for API-valid histories.
- **Graduated thresholds vs complexity**: two independent composed pipelines (eviction/truncation) with ordering constraints (`truncation_threshold >= tool_eviction_threshold`) add configuration surface and validation burden (_compaction.py:1692-1697).
- **Cross-turn coherence vs simplicity**: running the before-strategy per model call on shared Message objects leaks `_excluded` flags onto stored history; correctness requires careful reload semantics, covered by dedicated multi-turn tests (test_harness_agent.py:431-444) — a subtle invariant future contributors can easily break.

## Failure Modes / Edge Cases

- **Single oversized group**: if one group alone exceeds the budget, the projection stays above budget and the request proceeds — potential provider-side context-length rejection. Explicitly documented in both strategies (_compaction.py:805-807, 1405-1408; tested at test_compaction.py:661, 1088). There is no pre-flight hard block or message-splitting fallback.
- **Summarizer outage**: graceful degradation — compaction skipped, warning logged, escalation after 3 consecutive failures, success resets the counter (_compaction.py:1273-1288; tests 975-1047). Context keeps growing until the deterministic truncation path handles it.
- **Oversized first summary group**: if no complete group fits within `max_summary_input_tokens`, summarization is skipped entirely with a warning rather than truncating mid-group (_compaction.py:1340-1346; test 917) — safe but can stall LLM-based compaction permanently for very large turns.
- **Ambiguous reused `call_id`s**: results pair only when exactly one unmatched declaration remains; genuinely ambiguous duplicates stay separate groups so compaction cannot orphan a result (_compaction.py:118-121, 294-310; test_compaction.py:294).
- **History corruption risk on shared objects**: per-call exclusions leak onto shared Message instances; guarded by reload semantics and a dedicated coherence test (test_harness_agent.py:431-444).
- **Estimate drift for multimodal content**: images/audio contribute byte-length-derived estimates (dotnet ComputeContentByteCount, CompactionMessageIndex.cs:455-496), which can diverge substantially from provider tokenization of visual inputs.

## Future Considerations

- Wire real tokenizers by default (tiktoken in Python; `TiktokenTokenizer.CreateForModel` in .NET) keyed off the configured model id, eliminating the largest source of budget error.
- Close the feedback loop: reconcile annotated estimates with `UsageDetails` from responses to auto-calibrate a per-session correction factor.
- Add a context-window metadata registry (model id → window/output limits) so `ContextWindowCompactionStrategy` can be constructed automatically instead of requiring hardcoded values.
- Handle single-group overflow explicitly (hard error, chunking, or offload-to-file pattern already present via FileMemoryProvider).
- Port .NET's turn-count triggers and session-persisted compaction index to Python for policy parity; port Python's non-ASCII-aware serialization insight into .NET's byte estimator.
- Add semantic spot-check tooling for LLM summaries (e.g., optional verification pass) to strengthen the faithfulness story beyond prompts and provenance links.
