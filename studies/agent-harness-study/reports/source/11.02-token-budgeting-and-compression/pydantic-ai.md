## Summary

Pydantic AI treats token budgeting as a **reactive, limit-enforcement problem** plus an **opt-in, provider-delegated compression problem**, rather than doing local token accounting or automatic context assembly.

On the budgeting side, the central primitive is `UsageLimits` (`pydantic_ai_slim/pydantic_ai/usage.py:417-472`): a per-run dataclass of request, tool-call, cumulative input/output/total-token, per-request input-token, and USD cost limits. Usage is *measured by the provider* and extracted from each response into `RequestUsage`/`RunUsage` (`pydantic_ai_slim/pydantic_ai/usage.py:272-334`, `pydantic_ai_slim/pydantic_ai/usage.py:303-334` via genai-prices); the agent graph checks limits before each request (`check_before_request`) and after each response (`check_tokens`, `check_per_request_input_tokens`) at `pydantic_ai_slim/pydantic_ai/_agent_graph.py:1600-1621` and `pydantic_ai_slim/pydantic_ai/_agent_graph.py:1786-1795`, including inside streaming iterators (`pydantic_ai_slim/pydantic_ai/result.py:1047-1062`). Pre-request measurement exists but is opt-in (`count_tokens_before_request=True`, `pydantic_ai_slim/pydantic_ai/usage.py:459-472`) and delegates to `Model.count_tokens` implementations on four adapters (OpenAI Responses, Anthropic, Google, Bedrock Converse).

On the compression side there is no client-side summarizer in core. Instead the framework defines a provider-neutral `CompactionPart` message type (`pydantic_ai_slim/pydantic_ai/messages.py:1988-2036`) and wraps OpenAI's and Anthropic's server-side compaction APIs as capabilities — `OpenAICompaction` (`pydantic_ai_slim/pydantic_ai/models/openai.py:4716-4897`, stateful token-threshold mode + stateless `/compact` endpoint with message-count or custom trigger) and `AnthropicCompaction` (`pydantic_ai_slim/pydantic_ai/models/anthropic.py:2680-2746`, input-token threshold defaulting to 150k). A carefully engineered wire-trim layer (`_trim_messages_before_compaction`, `pydantic_ai_slim/pydantic_ai/models/__init__.py:2072-2131`) drops pre-boundary history while preserving the standing system prompt, and `post_compaction_window` (`pydantic_ai_slim/pydantic_ai/messages.py:2774-2814`) is the single boundary definition all derived state (discovered tools, loaded capabilities) recomputes from. Fully model-agnostic compression is exposed as a user-written extension point: the `ProcessHistory` capability (`pydantic_ai_slim/pydantic_ai/capabilities/process_history.py:25-42`) runs user history processors (slice, summarize with a second LLM) before requests; richer strategies (sliding window, tool-result clearing, tiered escalation, near-limit warnings) live in the separate external `pydantic-ai-harness` package, not this repository (`README.md:28,41-47`; `docs/capabilities/compaction.md:37`).

## Rating

**7 / 10** — Clear model with tests, explicit interfaces, and operational safeguards for everything it chooses to own; points are lost because enforcement is post-hoc by default, proactive counting costs an extra provider call and covers only 4 of ~30 adapters, no adapter knows its model's context-window size (thresholds are hand-configured), and general-purpose context ranking/summarization is delegated to providers or to an out-of-repo package.

## Answers to Dimension Questions

**1. Is token usage measured before calling the model?**
Only if opted in. By default nothing is measured ahead of the request: `UsageLimits` documents that "token counts are provided in responses from the model, and the token limits are checked after each response" (`pydantic_ai_slim/pydantic_ai/usage.py:419-425`). Setting `count_tokens_before_request=True` makes `_prepare_request` deep-copy run usage, call `model.count_tokens(...)`, price the counted input, and enforce `per_request_input_tokens_limit` before sending (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:1603-1619`). The docstring flags the cost ("may incur additional overhead… disabled by default") and names supported adapters: Anthropic, Google, Bedrock Converse, OpenAI Responses (`pydantic_ai_slim/pydantic_ai/usage.py:459-472`); other models raise `NotImplementedError` (`pydantic_ai_slim/pydantic_ai/models/__init__.py:524-526`). Notably the OpenAI implementation mirrors the real request build (same tools/instructions/truncation params), honoring the repo's own rule that counting must match actual requests.

**2. What gets dropped when budget is exceeded?**
Nothing silently. Exceeding any configured limit raises `UsageLimitExceeded` and aborts the run — fail-fast, not degrade (`pydantic_ai_slim/pydantic_ai/exceptions.py:464` links limits as the budget-aware pattern). Actual content reduction only happens through explicitly enabled mechanisms: (a) provider-native compaction replaces pre-boundary history server-side, with the client trimming replayed prefix (`pydantic_ai_slim/pydantic_ai/models/__init__.py:2072-2131`); (b) OpenRouter's `middle-out` transform lets the provider truncate middle messages (`pydantic_ai_slim/pydantic_ai/models/openrouter.py:277-281`); (c) tool results are capped at the source, e.g. web fetch's 50k-char cut with an explicit `[Content truncated]` marker (`pydantic_ai_slim/pydantic_ai/common_tools/web_fetch.py:135-136`); (d) user-authored `ProcessHistory` processors may slice history, with docs warning that unpaired tool-call/return slicing causes provider errors (`docs/message-history.md:780-781,844-845`). There is no framework-level priority scheme deciding which message/tool result to drop first — that orchestration (tiered strategies) lives in the external harness package (`docs/capabilities/compaction.md:37`).

**3. Is summarization faithful?**
Unverifiable by design in core: summarization is delegated to providers. Anthropic compaction produces "a readable text summary" and OpenAI an opaque encrypted blob stored in `provider_details['encrypted_content']` with `content=None` (`pydantic_ai_slim/pydantic_ai/messages.py:1996-2005`) — for OpenAI, faithfulness cannot be inspected client-side at all; for Anthropic it can be read but never validated. `AnthropicCompaction` does allow custom summarization `instructions` (`pydantic_ai_slim/pydantic_ai/models/anthropic.py:2705-2712`), which is control but still not verification. The framework's honesty mechanism is structural rather than semantic: anything derived from dropped history (discovered tools, loaded capabilities) is recomputed from `post_compaction_window` so state survives lossy summaries (`pydantic_ai_slim/pydantic_ai/messages.py:2782-2787`). The user-level LLM-summarization recipe (`docs/message-history.md:816-842`) offers no faithfulness guarantee either, just prompt guidance.

**4. Is budget configurable?**
Yes, extensively, though per-run rather than as persistent agent defaults: every run method takes `usage_limits=` (`pydantic_ai_slim/pydantic_ai/agent/abstract.py:1763`, `pydantic_ai_slim/pydantic_ai/agent/__init__.py:1516` defaults it to `UsageLimits()` i.e. request_limit=50). Granularity spans requests, tool calls, cumulative and per-request tokens, and USD cost with best-effort pricing and a warning when pricing data is missing (`pydantic_ai_slim/pydantic_ai/usage.py:427-459`, `pydantic_ai_slim/pydantic_ai/usage.py:516-535`). Compression budgets are separately configurable per provider capability: `AnthropicCompaction.token_threshold` (default 150k, min 50k), `OpenAICompaction.token_threshold`/`message_count_threshold`/`trigger` callable, or raw `anthropic_context_management`/`openai_context_management` model settings (`pydantic_ai_slim/pydantic_ai/models/anthropic.py:2680-2746`, `pydantic_ai_slim/pydantic_ai/models/openai.py:4775-4848`). One genuine gap: budgets are expressed in absolute tokens, not as a fraction of the target model's context window — profiles carry no context-window field, so thresholds must be hand-tuned per model.

## Architectural Decisions

1. **Measure reactively, enforce at boundaries.** Usage arrives from providers and is checked at four chokepoints — pre-request, post-response, mid-stream, mid-continuation — rather than estimated locally (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:1600-1621,1786-1795`, `pydantic_ai_slim/pydantic_ai/result.py:1047-1062`, `pydantic_ai_slim/pydantic_ai/_agent_graph.py:875-893`). This avoids vendoring tokenizers and stays exact across modalities/providers, at the price of oversized requests being sent (and billed) before a cumulative limit trips.
2. **Compression delegated to providers, boundary owned by the framework.** Core ships no summarizer; it standardizes on `CompactionPart` and makes the *trim/boundary semantics* — where history stops being sent, what survives — a precise, tested, cross-cutting concern (`pydantic_ai_slim/pydantic_ai/messages.py:1988-2036,2774-2845`; `pydantic_ai_slim/pydantic_ai/models/__init__.py:2072-2131`).
3. **Adapter-declared compaction facts.** Whether an API honors a compaction item, needs its encrypted blob, or retains the standing prompt are `ClassVar` declarations on the adapter; one shared helper turns them into trim behavior (`pydantic_ai_slim/pydantic_ai/models/__init__.py:379-398,479-503`). This keeps provider mechanics out of shared code while making behavior uniform.
4. **Derived state recomputed from the post-compaction window.** Discovered tools and loaded capability ids are functions of `post_compaction_window(messages)`, not instance attributes, so compaction self-heals them (`pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:217-230`; `pydantic_ai_slim/pydantic_ai/_deferred_capabilities.py:141-156`).
5. **Fail-fast over silent truncation.** `UserError`s reject invalid combinations up front — e.g. Anthropic rejects `task_budget.remaining` together with server-side compaction because the API tracks that budget itself (`pydantic_ai_slim/pydantic_ai/models/anthropic.py:2657-2676`), and `OpenAICompaction` rejects mismatched stateful/stateless parameters (`pydantic_ai_slim/pydantic_ai/models/openai.py:4801-4824`).
6. **Extension point for model-agnostic strategies.** `ProcessHistory` composes arbitrary processors into the request pipeline (`pydantic_ai_slim/pydantic_ai/capabilities/process_history.py:25-42`), keeping the opinionated tiered strategies out of the slim core and in the harness package.

## Notable Patterns

- **Provenance stamping:** compaction items minted by the library's own compact call carry `STANDING_PROMPT_PLANTED_KEY` in `provider_details`; only stamped items are trusted to have already retained the standing prompt, so spliced or externally produced items get it re-inserted (`pydantic_ai_slim/pydantic_ai/messages.py:1979-1985`, `pydantic_ai_slim/pydantic_ai/models/__init__.py:2099-2106`).
- **Provider-exact vs conservative boundaries:** run-state derivation uses a provider-agnostic window (must hold across `FallbackModel` failover), while tool-dispatch evidence uses a provider-exact window anchored to the response's serving provider (`pydantic_ai_slim/pydantic_ai/messages.py:2789-2800,2848-2875`).
- **Cache-prefix awareness as a budget concern:** keeping the `search_tools` slot stable across turns specifically "preserves prompt caching" since dropping it would invalidate the prefix (`pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:362-367`); repo guidelines treat a moving injection anchor as a cost regression (`pydantic_ai_slim/pydantic_ai/models/AGENTS.md`, rule:478).
- **Priority ranking where it exists:** tool-search scoring sorts undiscovered-first with relevance as tiebreak so `max_results` trimming never hides a new match behind an available one (`pydantic_ai_slim/pydantic_ai/toolsets/_tool_search.py:475-483`).
- **Live-verified claims:** trim logic documents behaviors as "(live-verified)" — e.g. OpenAI bills replayed pre-compaction items, retention decays across re-compaction — showing empirical grounding of the compression path (`pydantic_ai_slim/pydantic_ai/models/__init__.py:2084-2110`).

## Tradeoffs

- **Exactness vs proactivity:** provider-measured usage is exact but post-hoc; avoiding local tokenizers means no cheap client-side estimate, so proactive enforcement always costs an extra API round trip and only 4 adapters implement `count_tokens` (`pydantic_ai_slim/pydantic_ai/usage.py:459-472`).
- **Delegation vs control:** server-side compaction is high fidelity and low effort, but summaries are opaque (OpenAI) and thresholds are blind guesses relative to the actual window since profiles lack context-window metadata; the model-agnostic alternative gives control but pushes pairing-correctness risk onto users (`docs/message-history.md:780-781`).
- **Fail-fast vs availability:** raising `UsageLimitExceeded` protects spend but ends the run; there is no built-in "compress and continue" reflex — that orchestration is left to capabilities/harness (`docs/capabilities/compaction.md:28-37`).
- **Per-run configurability vs operational defaults:** `usage_limits` must be passed per call (or you accept `request_limit=50`); agents don't persist budget policy, and durable-execution wrappers must serialize `UsageLimits` explicitly (`pydantic_ai_slim/pydantic_ai/durable_exec/temporal/_run_context.py:32`).
- **Char-based truncation vs token-based budgets:** tool-output caps like web fetch's 50k chars use a rough ~4 chars/token heuristic noted in the docstring (`pydantic_ai_slim/pydantic_ai/common_tools/web_fetch.py:175-176`) — simple, but disconnected from any real budget.

## Failure Modes / Edge Cases

Handled explicitly (with tests):
- Foreign-provider compaction parts and parts lacking renderable payloads are *not* treated as wire boundaries, preventing history loss with no summary standing in (`pydantic_ai_slim/pydantic_ai/messages.py:2817-2845`; tests at `tests/models/test_openai_responses.py:13678-13770`).
- Standing-prompt decay across repeated compactions: re-compaction replants the standing prompt and re-stamps provenance (`pydantic_ai_slim/pydantic_ai/models/openai.py:2128-2131`; test `tests/models/test_openai_responses.py:13404`).
- Continuation chains (Anthropic `pause_turn`, OpenAI background mode): merged segment usage is checked provisionally mid-turn so a chain can't blow the token budget before commit (`pydantic_ai_slim/pydantic_ai/_agent_graph.py:875-893`).
- Unpriced models with a `cost_limit` set emit `CostNotFoundWarning` instead of silently running unconstrained (`pydantic_ai_slim/pydantic_ai/usage.py:528-535`).
- Client-submitted compaction items in UI adapters are honored for visibility but never allowed to hide server-side stored history (`pydantic_ai_slim/pydantic_ai/ui/_adapter.py:521-523`; `docs/capabilities/compaction.md:22-26`).

Remaining risks:
- With `count_tokens_before_request=False` (default), a single oversized request is fully sent before `per_request_input_tokens_limit` trips — the docs acknowledge "the oversized request is still billed" (`pydantic_ai_slim/pydantic_ai/usage.py:455-457`).
- Cumulative `input_tokens_limit` counts cached-prefix tokens too, capping context size rather than cache-miss cost — surprising if users expect it to track spend (`pydantic_ai_slim/pydantic_ai/usage.py:449-453`).
- No guard prevents configuring a compaction threshold above the target model's actual context window; the framework simply doesn't know window sizes.

## Future Considerations

- Carry per-model context-window sizes in model profiles so compaction thresholds and warnings can be validated or defaulted relative to the real window (the codebase itself tracks this as #7255 for per-model compaction modes, `pydantic_ai_slim/pydantic_ai/messages.py:2835-2839`).
- Add lightweight local estimation (e.g. char/token heuristics or tiktoken for OpenAI-family) to warn before spending a `count_tokens` API call.
- Expose `WarnNearLimits`-style signals in core; today near-limit awareness is only available by reading `RunContext.usage` inside custom processors (`docs/message-history.md:788-806`) or the external harness package.
- Extend `count_tokens` beyond the four current adapters, or define a graceful fallback contract (estimate + warn) instead of `NotImplementedError` (`pydantic_ai_slim/pydantic_ai/models/__init__.py:524-526`).
