## Summary

Langfuse is an LLM observability/evaluation platform, not an agent harness that routes live user requests between cheap/expensive models. It has **no quality-cost router** in the dimension sense: no component selects a model tier based on prompt complexity, latency, risk score, or budget. What exists is **post-hoc cost accounting** via tiered pricing: each ingested observation is matched to a pricing tier (regex on usage keys or exact match on `model_parameters`/`metadata`) and cost is calculated `price * usage`; the winning tier's `id/name` is persisted for observability (`usage_pricing_tier_id/name`). The only runtime model selection is the in-app agent's static single-model config (`LANGFUSE_AWS_BEDROCK_MODEL`, optional `LANGFUSE_AWS_BEDROCK_SMALL_MODEL` for conversation titles) with no dynamic routing, no fallback chain between models, and only SDK-level retries. All evaluated areas are absent or repurposed for accounting, not routing.

## Rating

**2 / 10 — Absent, implicit, ad-hoc, or unsafe**

Rationale: Multiple models are catalogued for the playground and pricing, but there is no router, no selection criteria balancing quality/cost/latency/risk, no configurable routing policy, no LLM fallback chain, and no routing-decision tracing. Pricing-tier fallback (default tier) is the only "fallback" and it governs billing correctness, not execution resilience. The two-model in-app-agent setup is a fixed main vs. title-model split, not complexity-based routing. This is expected given the product's scope, but it means the dimension is unmet.

## Answers to Dimension Questions

**1. Are multiple model tiers available?**

Partially, but not for routing. There are two orthogonal notions: (a) The playground/evaluation catalog (`packages/shared/src/server/llm/types.ts:315-466`) exposes dozens of models per provider as *user-selectable* options; custom models can be added per API key (`LLMApiKeySchema.customModels/withDefaultModels`). (b) The pricing system (`worker/src/constants/default-model-prices.json:14-50`, `packages/shared/src/prisma/schema.prisma:843`) models each LLM identity as having 1..N `PricingTier`s (default + conditionals) — e.g., `gpt-4o` has `Standard` (default) and `Fast mode` (`service_tier in ["fast","priority"]` at 1.7× price). These tiers are cost-accounting tiers, not execution routers; the matcher (`packages/shared/src/server/pricing-tiers/matcher.ts:116-154`) selects exactly one tier per observation for billing. The in-app agent defines a two-slot config (`modelId` + `titleModelId` in `packages/shared/src/in-app-agent/server/modelProvider.ts:4-9`) where `LANGFUSE_AWS_BEDROCK_SMALL_MODEL` optionally provides a cheaper title model; this is the only runtime "cheap vs expensive" split and it is fixed by role, not by request complexity.

**2. What criteria drive model selection?**

No live quality-cost routing criteria exist. What does drive selection is:
- *Playground/eval*: explicit user choice of `model` string in the UI/API (`ModelParams.provider/adapter/model` in `packages/shared/src/server/llm/types.ts:272-276`); stored verbatim.
- *In-app agent & internal AI features*: static env var (`LANGFUSE_AWS_BEDROCK_MODEL` with fallback `LANGFUSE_AWS_BEDROCK_SMALL_MODEL` in `packages/shared/src/in-app-agent/server/modelProvider.ts:27-39` and `web/src/features/ai-features/server/availability.ts:42-43`); same model for every turn regardless of turn complexity, token budget, latency SLO, or risk.
- *Pricing-tier "selection"*: `matchPricingTier` criteria = (i) `usageDetailPattern` regex summed over `usage_details` compared via `gt/gte/lt/lte/eq/neq` against `value` (threshold-based, e.g., `input_tokens > 128000` for long-context surcharges) plus (ii) exact match on `model_parameters` or `metadata` key (`operator:"in"` values array) — e.g., `model_parameters.service_tier in [fast, priority]` — both documented in `packages/shared/src/features/model-pricing/validation.ts:60-82` and `fern/apis/server/definition/commons.yml:891-924`. Priority order (`priority ASC`) is the tie-breaker. These are post-hoc billing criteria, not router inputs like prompt complexity, latency budget, or quality threshold.

Cost, latency, quality, risk are not inputs to any LLM invoker (`packages/shared/src/server/llm/llmText.ts:98-115` shows `ModelParams` only carries `provider/adapter/model` + `max_tokens/temperature/top_p/maxReasoningTokens`). No risk scorer or quality gate feeds model choice.

**3. Are fallback chains defined?**

Only for pricing correctness, not for execution resilience.
- *Pricing*: every model must have exactly one default tier (`isDefault:true`, `priority:0`, `conditions:[]`) that always matches if no conditional tier does (`packages/shared/src/server/pricing-tiers/matcher.ts:139-150`, validated `packages/shared/src/features/model-pricing/validation.ts:174-185`). The OpenAPI spec calls this "fallback when no conditional tiers match" (`fern/apis/server/definition/commons.yml:891-914`).
- *LLM execution*: no fallback chain. `generateLLMText` accepts `maxRetries` (AI SDK retries same model) but never tries a different/cheaper model; `langfuseAiCompletion.ts:48-74` has no try-next-model logic; `executeInAppAgentRun.ts:203-210` fails the run (`INIT_FAILED`) if the single configured Bedrock model is missing and otherwise stays on that model for the whole turn, classifying errors as `AGENT_ERROR/OUTCOME_UNKNOWN` rather than falling back. Cache fallbacks in `modelMatch.ts` (`getModelWithPricesFromRedis → findModelInPostgres → NOT_FOUND_TOKEN` at `packages/shared/src/server/ingestion/modelMatch.ts:58-103`) are lookup-level cache tiers, not LLM fallback chains.

**4. Are routing decisions observable?**

In the dimension's sense (which model was chosen, why, and via which policy branch), no — because there is no router. The closest observable decision is the pricing-tier match: `worker/src/services/IngestionService/index.ts:1367-1374` debug-logs `pricingTier` with cost/usage and persists `usage_pricing_tier_id/name` per observation to ClickHouse (`packages/shared/clickhouse/migrations/unclustered/0031_add_usage_pricing_tier_columns.up.sql:1-2`), surfacing in `observations`/`events` repos and `modelMatchLocalCache` span attributes (`model_match_source`, `matched_model_id` at `packages/shared/src/server/ingestion/modelMatch.ts:106-139`). The in-app agent and `LangfuseInternalTraceEnvironment` tracing (`worker/src/features/in-app-agent/executeInAppAgentRun.ts:583-775`) records the model id used and run status, but not a routing policy trace because the policy is a single static assignment. There is no dashboard or trace field exposing "cheap model handled simple request while expensive handled complex one" — the prompt variation table instead proves the opposite: all 27 traces use one model per case (e.g., `gpt-4o-mini`).

## Architectural Decisions

- **Observability-first, not orchestration-first.** Langfuse centers on ingesting traces/observations and calculating cost post-hoc (`matchPricingTier` → `calculateUsageCosts` in `worker/src/services/IngestionService/index.ts:1341-1383`) rather than making routing decisions on the hot path. This keeps the ingestion pipeline deterministic and auditable but leaves execution routing entirely to external SDKs/apps.
- **Pricing tiers as billing policy, separate from runtime config.** Tiers are data-plane constructs (Postgres `pricing_tiers` + `Model.pricingTiers`, mirrored in `default-model-prices.json` and validated by `validatePricingTiers`) whose matching logic mirrors ingestion (`web/src/server/api/routers/models.ts:449` uses same matcher for preview). Keeping billing tiers independent of LLM invocation (`llmText.ts`) avoids coupling cost rules to provider SDK behavior, but means cost-tier changes never affect which model actually runs.
- **Single static Bedrock model for internal AI.** `getInAppAgentModelConfig` collapsing all internal AI (agent loop, conversation titles, search-bar filter generation, evals) to one (or two fixed-role) Bedrock model(s) simplifies credential handling (`BEDROCK_USE_DEFAULT_CREDENTIALS` in `packages/shared/src/server/llm/ai-sdk/providers/bedrock.ts:76-124`) and IAM, but forecloses quality-cost or latency-aware per-request selection.
- **No agent loop inside LLM boundary.** `generateLLMText` explicitly asserts `tool.execute` absent (`packages/shared/src/server/llm/llmText.ts:417-430`) and `createLLMToolSet` only builds definition-only tools; agent orchestration is pushed to the worker's Mastra loop (`worker/src/features/in-app-agent/runtime/`), preventing tool-level model escalation but also preventing tool-specific cheaper-model routing.
- **Cache tiering for model metadata, not for routing.** `findModel` layers `LocalCache (TTL 10s)` → Redis (`model-price-tiers` hash-tag prefix for cluster) → Postgres regex match (`model ~ match_pattern` in `packages/shared/src/server/ingestion/modelMatch.ts:272-305`) with `NOT_FOUND_TOKEN` negative caching. Durable for lookup cost, irrelevant to routing quality.

## Notable Patterns

- **Default-tier-always-matches invariant** enforced at API, validation, and matching layers (`packages/shared/src/features/model-pricing/validation.ts:149-210` + `packages/shared/src/server/pricing-tiers/matcher.ts:139-150` + `fern/apis/server/definition/commons.yml:826`) guaranteeing cost calculation never fails silently.
- **Condition union with dual sources:** `PricingTierCondition = UsageCondition (regex + threshold) | AttributeCondition (model_parameters/metadata, operator:"in")` (`packages/shared/src/features/model-pricing/validation.ts:78-82`) allowing threshold-based surcharges (long context) and attribute-based tiers (fast mode) in one priority-ordered list.
- **Priority-ordered first-match** routing pattern reused identically in ingestion, cost preview, and tests (`packages/shared/src/server/pricing-tiers/matcher.ts:122-136`, `web/src/server/api/routers/models.ts:449`, `worker/src/__tests__/pricing-tier-matcher.test.ts:659-1582`) — consistent but scoped to billing.
- **Fixed-role two-model split** (main + `titleModelId = LANGFUSE_AWS_BEDROCK_SMALL_MODEL ?? modelId`) used in `packages/shared/src/in-app-agent/server/persistence.ts:543` for titles and `web/src/features/ai-features/server/availability.ts:42-43` — minimal viable cost awareness without dynamic routing.

## Tradeoffs

- **Completeness of catalog vs. absence of router.** Exposing 70+ model IDs with per-model pricing tiers gives accurate cost visibility for any customer-reported model (`matchPattern` regex in `worker/src/constants/default-model-prices.json:5`), but without a router that selects among them on cost/latency/quality, users cannot ask Langfuse to "use Haiku for trivial classification, Sonnet for hard reasoning."
- **Billing determinism vs. execution resilience.** Requiring one default tier with priority 0 and persisting `usage_pricing_tier_*` per row makes costs auditable and retroactively repriceable, but provides no resilience benefit: an LLM failure on the single configured Bedrock model fails the run rather than falling back to a cheaper/faster model.
- **Static Bedrock focus vs. provider diversity.** Centralizing agent/title/search/eval on Bedrock simplifies auth (`AWS_BEARER_TOKEN_BEDROCK`/node provider chain in `packages/shared/src/server/llm/ai-sdk/providers/bedrock.ts:76-169`) and avoids per-feature credential sprawl, but forgoes cross-provider cost/latency tradeoffs (e.g., routing summarization to Gemini Flash, reasoning to Claude Opus).
- **Retry same model vs. cascade to cheaper model.** AI SDK `maxRetries`/`RetryError` handling in `packages/shared/src/server/llm/errors.ts:59-90` preserves queue durability semantics (evaluator `isRetryable` gates), yet a transient capacity error on Opus could have been served by Haiku rather than exhausting retries on the same expensive model.
- **Test depth for pricing matcher vs. zero routing coverage.** `pricing-tier-matcher.test.ts` thoroughly covers thresholds/regex/case sensitivity/attr fallback, which is valuable for billing correctness, but there is no test surface for routing criteria, fallback chains, or policy configurability.

## Failure Modes / Edge Cases

- **Single point of model failure.** `executeInAppAgentRun` throws `InAppAgentRunInitError` if `getInAppAgentModelConfig` is undefined and otherwise never retries with an alternate model; `generateLLMText` errors propagate as `AGENT_ERROR` or `WORKER_SHUTDOWN`/`CANCELLED` — a Bedrock outage or quota breach fails the whole run (`worker/src/features/in-app-agent/executeInAppAgentRun.ts:197-632`).
- **Mis-matched model name yields null pricing, silent zero cost.** `findModelInPostgres` uses `model ~ match_pattern` ordered by `project_id ASC` (`packages/shared/src/server/ingestion/modelMatch.ts:272-305`); `findModel` returns `{model:null, pricingTiers:[]}` on miss and `matchPricingTier` returns `null` → ingestion still writes observation but with no cost or `usage_pricing_tier_*`, silently under-reporting spend. Unknown-model audit (`model-price-audit.yml:158+`) only catches newly-known public models, not tenant typos.
- **Regex/threshold brittleness.** Usage-condition regexes are validated for `safe-regex` but a bad pattern still fails safe (returns `false` in `evaluateCondition` catch at `packages/shared/src/server/pricing-tiers/matcher.ts:70-72`) — the tier never matches and billing silently falls back to default, masking a misconfiguration. Threshold comparisons sum all keys matching regex, so overlapping key patterns can double-count.
- **Attribute-condition absent-key => no match, no log.** `evaluateCondition` returns `false` when `condition.key` missing from `modelParameters`/`metadata` (`packages/shared/src/server/pricing-tiers/matcher.ts:30-32`); missing metadata (e.g., `service_tier` not propagated by SDK) drops fast-mode surcharges or custom tiers without warning (only `modelMatch` debug logs at `worker/src/services/IngestionService/index.ts:1367`).
- **Cache staleness hides pricing changes.** `modelMatchLocalCache` TTL 10s + Redis TTL (`LANGFUSE_CACHE_MODEL_MATCH_TTL_SECONDS`) can serve stale `pricingTiers` after a pricing update until `clearModelCacheForProject`/`clearFullModelCache` runs; cost preview in `web/src/server/api/routers/models.ts:449` uses live Postgres tiers, so preview and ingested costs can diverge briefly.
- **Small-model env drift.** If `LANGFUSE_AWS_BEDROCK_SMALL_MODEL` points to a model not registered in Bedrock permission or not supporting required `max_tokens/temperature` shape, title generation in `packages/shared/src/in-app-agent/server/persistence.ts:543` will fail at runtime with no fallback to the main model; `availability.ts:43` does not validate model existence, only presence.
- **No backpressure between cost and routing.** A run over `IN_APP_AGENT_HEARTBEAT_INTERVAL_MS` step limit is marked `STEP_LIMIT` (`worker/src/features/in-app-agent/executeInAppAgentRun.ts:496-509`) after spend already incurred; there is no early routing to a smaller model or truncation policy that trades quality for cost before the cap.

## Future Considerations

- **Add an explicit quality-cost router if Langfuse ever orchestrates agent trajectories** (plan → retrieve → synthesize). Start with a `packages/shared/src/server/llm/router.ts` interface: `route(params: {taskKind, promptTokens, risk, latencySLO, budget}) → LLMModelRef` with policy file/YAML, fallback chain, and decision tracing; reuse existing `LLMAdapter`/`LLMApiKeys` plumbing so routing is testable without coupling to Bedrock.
- **Implement fallback chains per feature** (agent step, title, eval judge, search-bar filter) with tiers `primary → degraded → fail-open`, each with `isRetryable` gating from `errors.ts:87-90`, and persist `routing_decision {attempts[], chosenModel, reason, latency_ms}` alongside `usage_pricing_tier_*` for audit. Use `maxRetries` per hop, not globally.
- **Make routing observable** by adding `routing_decision` to ClickHouse `observations`/`events` (like `usage_pricing_tier_*`) and exposing it in trace UI and OTel ingestion response; currently the only observable routing artifact is the billing tier.
- **Consider latency/cost SLO signals** (p50 tool cost, token budget remaining in trajectory, retrieval hit quality) as future router inputs; none exist today because `IngestionService.getUsageUnits`/`matchPricingTier` are post-hoc and `llmText.ts` only carries `maxOutputTokens/temperature/topP`.
- **Unify internal AI model selection** behind `getInAppAgentModelConfig` but generalize to `getInternalAIModelConfig(feature: "agent"|"title"|"eval-judge"|"search")` with per-feature override env vars so cheap tasks (titles, search-bar) can stay on Haiku/Flash while agent stays on Opus/Sonnet without hardcoding two slots.

## Questions / Gaps

- **Why only two static slots?** `titleModelId = SMALL_MODEL ?? main` suggests cost awareness, but there is no design doc explaining why dynamic routing was rejected (cost vs. complexity vs. cloud-vs-self-hosted support burden). No evidence found in `modelProvider.ts:24-42` or `.agents/skills/add-model-price/`.
- **Intended self-hosted LLM path?** `supportedModels` maps Azure/Bedrock to `[]` (`packages/shared/src/server/llm/types.ts:465-466`) implying BYO models via `customModels` + `baseURL`/`extraHeaders`, but no router guidance for how self-hosters should balance quality vs cost across custom endpoints. No evidence found in docs or `ai-sdk/providers/`.
- **Pricing-tier vs. router convergence.** If pricing tiers already encode thresholds (e.g., long-context), should the router pre-emptively avoid the expensive tier by routing long prompts to a cheaper model? No issue or RFC was found linking the two subsystems.
- **Missing SLO definitions.** No file declares latency or cost budgets that a router would need to optimize against; the only timeout is `LANGFUSE_FETCH_LLM_COMPLETION_TIMEOUT_MS` (`packages/shared/src/env.ts:516-520`, capped 95s in `packages/shared/src/server/llm/llmText.ts:64-71`). Without SLOs, a future router has no objective.
