## Summary

Microsoft Agent Framework is an unopinionated orchestration framework, not a model gateway. It exposes a single-model-per-client abstraction (`BaseChatClient`, `Agent`) with provider-agnostic `ChatOptions` that are forwarded verbatim to the underlying LLM. The framework ships multiple independent provider clients (OpenAI Responses/ChatCompletions, Azure OpenAI, Anthropic, Bedrock, Gemini, Ollama) but provides no first-class router, policy engine, cost/latency/quality-aware selection logic, or automatic fallback chain between model tiers. Model choice is explicit construction-time configuration (`model="gpt-4o"`), optionally overridden per-run via `options={"model": ...}` and merged via `_merge_options`. The only cost-related surface is the pass-through `service_tier` / Azure deployment selection; it requires caller-supplied values. Workflow and agent-to-agent routing exists (edge groups, orchestrators, handoff) but routes *messages between executors/agents*, not model tiers by cost/quality. Observability captures request model (`gen_ai.request.model` / `gen_ai.response.model`) and token usage, but emits no routing-decision event. Bottom line: cheap-vs-expensive routing is entirely left to application code via custom `AgentMiddleware`/`ChatMiddleware` or external infrastructure.

## Rating

**2 / 10 — Absent, implicit, ad-hoc**

No router component, no multi-tier config, no criteria engine, no fallback chain, and no routing-decision trace exist in the framework. Single-model configuration is intentional by design; cost/quality tiering would require user-built middleware. The score reflects deliberate absence rather than a broken implementation, but from the dimension's lens (can cheap models handle simple requests automatically?) the capability is missing and unsafe to infer.

## Answers to Dimension Questions

**1. Are multiple model tiers available?**
Yes, as independent provider clients — not as tiers in a single router. The lazy root API re-exports `OpenAIChatClient`, `OpenAIChatCompletionClient`, `BedrockChatClient`, `GeminiChatClient`, `OllamaChatClient`, `Anthropic`/`Mistral`/`Foundry` clients (`python/packages/core/agent_framework/__init__.py:43` and provider `__init__.py` maps). Each client is configured with zero-or-one model (`python/packages/openai/agent_framework_openai/_chat_client.py:594`), and `Agent` binds to exactly one (`python/packages/core/agent_framework/_agents.py:813`). A consumer can instantiate N agents with cheap/expensive models and compose them manually, but the framework provides no `TieredClient`, `RouterClient`, or model-registry mapping tiers to model IDs.

**2. What criteria drive model selection?**
No framework criteria. Selection is caller-supplied at construction or per `run(options={"model": ...})`, merged by `_merge_options` where the override wins (`python/packages/core/agent_framework/_agents.py:138`). Options `service_tier`, `reasoning.effort`, `verbosity` (`python/packages/openai/agent_framework_openai/_chat_client.py:174`) allow caller-controlled cost/quality hints, but no latency, token-budget, risk, or complexity classifier reads them. Workflow edge conditions (`EdgeCondition`, `SwitchCaseEdgeGroup` at `python/packages/core/agent_framework/_workflows/_edge.py:173`) and orchestrators select the next *executor/agent*, not the next *model tier*.

**3. Are fallback chains defined?**
No. No `fallback_models`, `retry_on=rate_limit|content_filter`, or `escalate_to` chain exists on `BaseChatClient` or `ChatOptions`. The only fallbacks in the codebase are orthogonal: (a) MCP long-running task submit-vs-track single reconnect policy (`python/packages/core/agent_framework/_mcp.py:2243`) and (b) auth routing fallback for OpenAI vs Azure (`python/packages/openai/agent_framework_openai/_shared.py:284`). Model-level failover would need to be authored as `ChatMiddleware` that catches `ChatClientException`/`ChatClientInvalidRequestException` (`python/packages/core/agent_framework/exceptions.py:79`) and retries with a different client — the framework does not ship one. Tests confirm the absence: no test named `*fallback*model*` or `*routing*model*` exists.

**4. Are routing decisions observable?**
Partial observability for the chosen model, zero for the decision. Request/response model is emitted as `gen_ai.request.model` / `gen_ai.response.model` (`python/packages/core/agent_framework/observability.py:290`) with Azure `x-ms-served-model` extraction (`python/packages/openai/agent_framework_openai/_chat_client.py:819`). Token usage and duration histograms are emitted (`python/packages/core/agent_framework/observability.py:274`). No span attribute records *why* that model was chosen, what alternatives were considered, estimated cost, or fallback attempt count. Consequently, debugging a cost spike or quality regression from routing is not possible without custom middleware instrumentation.

## Architectural Decisions

*   **Provider-agnostic, single-model-per-client core** (`python/packages/core/agent_framework/_clients.py:217`, `python/packages/core/agent_framework/_agents.py:813`). Keeps `BaseChatClient` minimal and lets each provider package own its wire format (`openai/_chat_client.py`, `_chat_completion_client.py`, `_embedding_client.py`). Trade-off: every cross-provider concern (routing, fallback, cost attribution) must be layered outside the core.
*   **Explicit option forwarding, not interpretation.** `validate_chat_options` / `_prepare_options` validate and forward `ChatOptions` verbatim to `client.responses.create` / `create(..., stream=True)` (`python/packages/openai/agent_framework_openai/_chat_client.py:619`). The framework treats `model`, `service_tier`, `reasoning`, `temperature`, etc. as opaque provider keys. This preserves provider evolution (new fields need no framework release) but forgoes framework-level policy (no “use `flex` when latency > 2s”).
*   **Middleware as the extension seam for routing.** Layer ordering `FunctionInvocationLayer → ChatTelemetryLayer → ChatMiddlewareLayer` is documented (`python/packages/openai/agent_framework_openai/_chat_client.py:267`, `python/packages/core/agent_framework/_clients.py:993`). A custom `ChatMiddleware` that swaps `context` clients by classifier score, or an `AgentMiddleware` that fans out to a cheap scout model then escalates, is the sanctioned pattern. No built-in router is shipped, so teams must own complexity, retries, and tracing.
*   **Workflows route executors, not models.** `SwitchCaseEdgeGroup`, `FanOut/FanInEdgeGroup` (`python/packages/core/agent_framework/_workflows/_edge.py:296`) and `MessageRouter` (`dotnet/src/Microsoft.Agents.AI.Workflows/Execution/MessageRouter.cs:30`) branch on *payload type / edge condition*, enabling agentic patterns (sequential, concurrent, handoff, magentic) without coupling to model tiering.
*   **Azure vs OpenAI routing decision is the only built-in model-routing logic** — and it is auth/endpoint routing, not quality-cost routing. `load_openai_service_settings` implements precedence explicit Azure → explicit OpenAI → Azure env fallback (`python/packages/openai/AGENTS.md:40`, `python/packages/openai/agent_framework_openai/_shared.py:284`).

## Notable Patterns

*   **Raw + Full-Featured client pair**: `RawOpenAIChatClient` (no middleware/telemetry/function loop, `python/packages/openai/agent_framework_openai/_chat_client.py:377`) vs `OpenAIChatClient` (adds `ChatMiddlewareLayer`+`FunctionInvocationLayer`+`ChatTelemetryLayer`). Pattern repeats per provider and makes the middleware injection point explicit for custom routing.
*   **Loop and harness middleware for iterative refinement**: `AgentLoopMiddleware` (predicate or judge client, `python/packages/core/AGENTS.md` loop section) and harbor-style `create_harness_agent` wiring show how “judge decides to continue” is modeled — analogous to a quality gate, but it re-runs the *same* agent with nudge messages rather than swapping to a stronger model.
*   **Per-run `options` override without mutation**: `_merge_options` strips `None` and preserves caller dicts, so a transient `model: "gpt-4o-mini"` override for one turn does not poison `default_options` for the next turn (`python/packages/core/agent_framework/_agents.py:138`).
*   **Pass-through `service_tier` / `background` for cost/perf control**: `service_tier` (`auto|default|flex|priority`) and `background`+`continuation_token` are typed options that let callers opt into cheaper flex capacity or background polling (`python/packages/openai/agent_framework_openai/_chat_client.py:254`, `:272`), but the caller—not a router—must choose when to use them.

## Tradeoffs

*   **Simplicity vs autonomy**: One model per client is easy to reason about and debuggable; a built-in tier router would add latency (classifier call), cost (double invocation on escalation), and non-determinism. The framework chooses the former and pushes routing to user middleware.
*   **Provider fidelity vs framework policy**: Forwarding `ChatOptions` verbatim preserves access to every provider knop but means the framework cannot reason about cost (“flex is cheaper”) portably across providers. A `service_tier` abstraction for Anthropic/Bedrock would need a provider-agnostic cost model the team has not built.
*   **Workflow-level routing suffices for many use cases**: `HandoffOrchestrator`/`GroupChatOrchestrator` let a cheap triage agent hand off to an expensive specialist agent — a coarse-grained, agent-level analogue of quality-cost routing. Finer-grained token-level or per-tool-call tiering would require deeper integration than workflows expose.
*   **Observability gap is the cost of no router**: Emitting `request.model`/`response.model`/`input_tokens`/`output_tokens` (`python/packages/core/agent_framework/observability.py:249`) is sufficient for post-hoc cost dashboards but insufficient for attributing a decision (“routed to mini because input_tokens < 512”).

## Failure Modes / Edge Cases

*   **No graceful degradation on provider failure**: Without a fallback chain, a `ChatClientException` (rate limit 429, capacity 503, content filter) aborts the run and surfaces to the caller. A custom middleware that retries on a cheaper model must be careful not to create infinite escalation (e.g., cheap model also 429). The MCP single-retry discipline (`python/packages/core/agent_framework/_mcp.py:329`) illustrates the desired boundedness but does not apply to chat clients.
*   **Stale model override via shared `options` dict**: Docs note the `continuation_token` footgun where `FunctionInvocationLayer` reuses the same options dict across tool-loop iterations (`python/packages/openai/agent_framework_openai/_chat_client.py:778-785` comment). An ad-hoc middleware that mutates `options["model"]` in place risks leaking the cheap-model choice into the next iteration or turn; it should copy.
*   **Compaction + local tool removal at invocation limits**: Once `max_function_calls`/`max_iterations` disables local tools, `informational_only` provider-executed pairs remain but locally actionable `function_call` payloads are stripped (`python/packages/core/AGENTS.md` tool-approval section). A router that bases its decision on tool-calling history may see a truncated transcript and mis-route.
*   **`service_tier: flex` increases latency**: Flex trades lower cost for higher/variable latency (OpenAI docs). Blindly applying `service_tier=flex` to latency-sensitive turns via a naive cost router can violate SLOs; no framework guard exists.
*   **Azure `x-ms-served-model` divergence**: The actually served snapshot (`gpt-5-nano-2025-08-07`) may differ from the requested deployment alias (`gpt-5-nano`). Cost attribution keyed on requested model alone will misattribute. The client correctly surfaces `x-ms-served-model` (`python/packages/openai/agent_framework_openai/_chat_client.py:819`) for accurate tagging, but a custom router must read `ChatResponse.model`, not just `options["model"]`.
*   **Concurrent per-turn agent handoff vs model tiering**: `Agent.as_tool` with `propagate_session=False` creates isolated child sessions (`python/packages/core/agent_framework/_agents.py:689`) to avoid lane races. A router that delegates sub-tasks to cheap models as tools must decide session propagation carefully or risk orphaned history / token miscounting.

## Future Considerations

*   **Ship a `TieredChatClient` / `RoutingChatClient` example as a recipe, not core.** Implement a `ChatMiddleware`/`BaseChatClient` wrapper with `tiers: list[{model, max_input_tokens, cost_per_1k, latency_slo}]`, a `Classifier` hook `(messages, options) -> tier_index`, and a bounded fallback list `fallback_on: {"429","500","content_filter"} → next tier (max 2 hops)`. Emit a `routing.decision` span event `{chosen_model, candidate_tiers, reason, cost_estimate, fallback_attempt}` alongside existing `gen_ai.request.model`.
*   **Formalize cost/latency signals in `ChatResponse.usage` and OTel.** Already `UsageDetails` + histograms exist; add `cost_estimate` (requires provider price table) and `routing` attributes (`routing.policy_id`, `routing.tier`, `routing.fallback_index`) so dashboards can group by tier regardless of model literal.
*   **Policy config via `ChatOptions` extension or standalone file.** Add an optional `routing_policy: {policy_id, rules: [{when: "input_tokens < 800 && no_tools", use: "gpt-4o-mini"}]}` key validated by the router but ignored by non-routing clients (mirrors `service_tier` pass-through behavior). Keep it out of the core `ChatOptions` TypedDict to preserve provider fidelity; load from YAML/env via `load_settings`.
*   **Integrate `AgentLoopMiddleware` judge as a quality gate for escalation**: reuse the `JudgeVerdict` pattern (`python/packages/core/AGENTS.md` loop section) so a cheap first pass is scored; on `verdict.is_good == False` the middleware re-invokes with a stronger model, capturing both passes in a single trace.
*   **Test gap**: Add tests for simultaneous model `null` stripping, per-turn model override isolation, `service_tier` propagation, and fallback idempotency (same integration tests that cover `test_max_iterations_*` / `test_function_invocation_limit_*` at `docs/specs/004-python-function-calling-loop.md:531`).

## Questions / Gaps

*   **Go SDK not inspected for routing.** `go/` directory exists but was not sampled; confirmed no routing types in Python/.NET index, but Go could contain a gateway/forwarding sample that demonstrates tiering.
*   **Declarative agents routing is untyped content routing, not cost routing.** `CustomerSupport.yaml:68` names an executor `routing_agent` that classifies intent; whether declarative workflows could host a `routing_policy` binding remains undocumented (`declarative-agents/` spec not read).

*   **Provider price tables absent.** Any future cost-aware router will need a maintained `model_id → $/input,$/output` map with version drift; no such file was found under `python/packages/*/`, consistent with the pass-through philosophy.
