## Summary

The analyzed source is the OpenHands agent-canvas **frontend** (`package.json` name `@openhands/agent-canvas`, `package.json:2`), so its retry/fallback story is about surviving *backend and transport* outages rather than LLM-provider failover. The codebase implements four distinct resilience mechanisms with concrete code: (1) a generic `withRetry` helper with exponential backoff for settings/secrets API calls (`src/api/with-retry.ts:4-26`, duplicated in `src/api/settings-service/settings-service.api.ts:134-156`); (2) a WebSocket reconnect loop with exponential backoff (1 s base, 30 s cap) plus up to 30% random jitter to avoid synchronized main/planning-socket retries (`src/hooks/use-websocket.ts:18-20,125-136`) guarded by a handshake watchdog (`src/utils/websocket-handshake.ts:17-26`); (3) a persisted per-backend health store that acts as a coarse circuit breaker — after `MAX_CONSECUTIVE_FAILURES = 5` failed probes, polling for that backend is disabled and stays disabled across page reloads until the user edits config or explicitly re-probes (`src/api/backend-registry/health-storage.ts:10`, `src/api/backend-registry/health-store.ts:46-63`, `src/api/backend-registry/health-storage.ts:61-75`); and (4) numerous deliberate per-call-site degradation decisions (retry-disabled queries, degrade-to-defaults settings reads, empty-page pagination fallbacks).

Fallback *providers/models* are essentially absent as an automated mechanism. There is no automatic LLM model/provider failover anywhere in this repo; the only fallback routing is user- or agent-directed (launch target `"cloud"` vs `"local"` in child-conversation launch, `src/services/child-conversation-launch.ts:303-430`; runtime `/model` profile switching surfaced via `SwitchLLMObservation` events, `src/types/agent-server/type-guards.ts:161-167`). A legacy `STATUS$LLM_RETRY` status literal exists in the runtime-status union but has zero consumers — evidence that server-driven LLM-retry signaling was dropped in this frontend adaptation (`src/types/runtime-status.ts:18`).

Retry state persistence is split by design: backend-health failure counts persist to localStorage and survive reloads (`openhands-backend-health` key, `src/api/backend-registry/health-storage.ts:3,41-75`), while MCP server health is deliberately *not* persisted so a reload resets stale verdicts (`src/api/mcp-health/mcp-health-store.ts:9-13`). WebSocket attempt counters are in-memory only.

Overall: retry behavior is present, often thoughtful, well-commented, and partially tested — but inconsistent across layers (two copies of `withRetry` with no error-class discrimination, infinite WS retries by default, no automatic provider fallback, no formal half-open circuit breaker). It fits the "present but inconsistent" band more than the "clear tested model" band.

## Rating

**6 / 10** — Present but inconsistent.

Rationale against the rubric:

- **What earns points:** The WS reconnect path is genuinely mature for a frontend: exponential backoff with jitter, bounded handshake watchdog, replaced-socket suppression via a `WeakSet`, attempt reset on success, and direct unit tests asserting the backoff schedule and watchdog behavior (`__tests__/hooks/use-websocket.test.ts:533,605,662`). The backend-health disable cap is persisted, validated on read against tampering (`src/api/backend-registry/health-storage.ts:24-39`), and covered by tests including cap-flip and recovery cases (`__tests__/api/backend-registry/health-store.test.ts:28,50,67,89`). Retry policies are *documented at call sites* with reasons (e.g. why probe retries live inside the query function rather than React Query's `retry`, `src/hooks/query/use-backends-health.ts:143-163`).
- **What holds it back:** The generic `withRetry` retries *all* error classes including definitive 401/400 responses (`src/api/with-retry.ts:12-15`), unlike the more careful probe path which excludes auth errors (`src/hooks/query/use-backends-health.ts:164-171`) and the launcher seed script which skips 401/403 (`scripts/dev-with-automation.mjs:1256-1264`) — three different error-discrimination policies across layers. `withRetry` is duplicated verbatim instead of shared (`src/api/settings-service/settings-service.api.ts:131-156`). No automatic fallback model/provider exists; degraded mode is per-feature ad hoc (hidden balance card, default settings, empty pages). There is no true circuit breaker with half-open probing — disabled backends only re-arm via explicit user action (`probeDisabledOnce`, `src/hooks/query/use-backends-health.ts:203-210`) or config edits (`src/contexts/active-backend-context.tsx:145-155`).

## Answers to Dimension Questions

**1. Are retries configurable?**
Partially. The generic `withRetry` accepts `maxRetries` and `baseDelayMs` parameters (`src/api/with-retry.ts:4-8`) but every call site uses the defaults — no caller tunes them, and there is no user-facing or env-var configuration surface for retry behavior anywhere in the repo (no `retry` keys in `config/defaults.json` consumers documented in `AGENTS.md`). React Query retry is configured per-query in code: conditional retry on bootstrap (`src/hooks/query/use-config.ts:17-20`), `retry: false` on balance/auth/health queries (`src/hooks/query/use-llm-balance.ts:25`, `src/root.tsx:292`, `src/hooks/query/use-backends-health.ts:280`), and the probe's own inner retry with fixed attempts/delay constants (`src/hooks/query/use-backends-health.ts:140-141`). WS reconnect exposes `maxAttempts` in the options interface (`src/hooks/use-websocket.ts:12-15`) but the conversation context never sets it, leaving the `Infinity` default active (`src/hooks/use-websocket.ts:113-114`). Verdict: configurable in mechanism, not in operation.

**2. Are fallback providers available?**
No automated fallback providers/models exist in this source. Searched all of `src/` for `fallback`/`provider`: matches are i18n language fallbacks (`src/i18n/index.ts:42-48`), UI value fallbacks (`src/utils/utils.ts:46-48`, `src/utils/mcp-server-name.ts:7-14`), nav-path ordering (`src/utils/settings-utils.ts:68-76`), and subscription-model default selection in settings UI (`src/routes/llm-settings.tsx:563-572`) — none route traffic to a secondary provider. What does exist is *manual* fallback topology: multi-backend registration with an active-backend selector and health dots (`src/components/features/backends/backend-selector.tsx` per `AGENTS.md`; `useBackendsHealth`), and launch-target guidance where cloud failure messages explicitly suggest falling back to `target="local"` (`src/services/child-conversation-launch.ts:428`). Model switching between profiles happens mid-conversation but only via user/agent action observed through `SwitchLLMObservation` events (`src/contexts/conversation-websocket-context.tsx:562-564,688-722`; `src/types/agent-server/type-guards.ts:161-167`) — it is a feature, not failure recovery. Any LLM-level retry/fallback would have to live in the sibling agent-server repos (out of scope here); within this source, the answer to "can it survive a provider outage without failing all requests" is: the *UI* survives (reconnects, degrades, keeps state), but inference failover is delegated entirely to the backend tier.

**3. Does the system degrade gracefully?**
Yes, in many specific places, though ad hoc rather than via a framework. Examples: settings reads fall back to defaults on fetch failure while conversation-start credential fetches deliberately throw instead of degrading (`src/api/settings-service/settings-service.api.ts:471-475` vs `483-495`) — a well-judged asymmetry. The balance card hides itself when the endpoint 404s or times out (`src/constants/llm-balance.ts:1-14`, `src/hooks/query/use-llm-balance.ts:10-12`). Unsupported cloud pagination filters collapse to a single page instead of looping (`src/api/event-service/event-service.api.ts:153-162`). Unknown task statuses render a generic "Starting" label rather than crashing (`src/services/status.ts:51-54`). Stuck optimistic messages flip to an error state with a retry affordance after 150 s (`src/stores/optimistic-user-message-store.ts:131-139`). Connection errors auto-clear on first recovered event while sticky conversation errors persist (`src/stores/error-message-store.ts:4-9,62-65`). Transcript export refuses to silently produce a partial export (`src/utils/transcript-export/load-complete-events.ts:106-110`). The degradation choices are individually sound and consistently commented, but there is no central "degraded mode" concept or policy object tying them together.

**4. Are circuit breakers used to prevent cascading failure?**
There is no formal circuit breaker (no open/half-open/closed state machine; searched for `circuit`, `half-open`, `trip` — only an unrelated SVG icon import at `src/constants/settings-nav.tsx:4`). The closest analog is the backend health disable cap: five consecutive failed probes mark a backend `disabled`, stop its 30 s polling, and persist that verdict to localStorage so a reload doesn't re-arm hammering of a dead backend (`src/api/backend-registry/health-storage.ts:5-10`, `src/api/backend-registry/health-store.ts:40-63`, `src/hooks/query/use-backends-health.ts:220-283`). Recovery requires an external stimulus — success on a one-shot reprobe, or a config edit — rather than automatic half-open probing (`src/hooks/query/use-backends-health.ts:203-210`; `src/contexts/active-backend-context.tsx:145-155`). Additional anti-cascading measures: toast deduplication within a 3 s window prevents error storms from flooding the UI (`src/query-client-config.ts:53-61`), jittered WS reconnect prevents lockstep hammering (`src/hooks/use-websocket.ts:125-132`), and probe retries are kept inside the query function specifically so internal attempts don't multiply `recordBackendFailure` calls and trip the cap too fast (`src/hooks/query/use-backends-health.ts:154-159`). Effective, but coarse-grained (per-backend, not per-endpoint) and lacking automatic recovery probing.

## Architectural Decisions

1. **Per-call-site retry policy over a global policy.** Each layer decides its own retry posture with inline rationale: probe retries live inside the query function so exactly one outcome is recorded per logical probe (`src/hooks/query/use-backends-health.ts:154-159`); bootstrap retries conditionally on error class (`src/hooks/query/use-config.ts:17-20`); balance and auth queries opt out entirely (`src/hooks/query/use-llm-balance.ts:25`, `src/root.tsx:292`). Flexible but fragmentary — there is no single place to audit or tune retry behavior.
2. **Persisted negative verdicts, ephemeral positive ones.** Backend-health failure/disabled state persists to localStorage and is defensively validated on read (`src/api/backend-registry/health-storage.ts:24-39,61-75`), while MCP health deliberately resets on reload because "a health verdict is only as fresh as its probe" (`src/api/mcp-health/mcp-health-store.ts:9-13`). Two explicit, opposite persistence philosophies chosen per domain.
3. **Transport-level self-healing with watchdogs.** The browser's inability to time out a CONNECTING socket is compensated with a 10 s handshake watchdog whose abort flows through normal close handling into the reconnect path (`src/utils/websocket-handshake.ts:1-16`; `src/hooks/use-websocket.ts:61-64`), and reconnect identity is gated by a `WeakSet` so replaced sockets cannot corrupt successor state (`src/hooks/use-websocket.ts:31,105-108`).
4. **Degradation with escape hatches, not silent loss.** Degrading paths either preserve recoverability (optimistic message → retry link, `src/stores/optimistic-user-message-store.ts:67,131-139`) or refuse to degrade when correctness matters (conversation credentials throw; transcript export fails loudly on unprovable completeness, `src/api/settings-service/settings-service.api.ts:483-485`, `src/utils/transcript-export/load-complete-events.ts:106-110`).
5. **Frontend delegates LLM resilience to the backend tier.** The `STATUS$LLM_RETRY` leftover (`src/types/runtime-status.ts:18`) and absence of any provider-failover code show this repo's contract: the agent-server owns LLM retry/fallback; the canvas owns connection/UI survival.

## Notable Patterns

- **Jittered exponential backoff with thundering-herd commentary**: `delay = min(1s * 2^n, 30s) + rand()*0.3*base`, justified as keeping parallel main+planning sockets out of lockstep (`src/hooks/use-websocket.ts:125-132`).
- **Non-retryable error classification by message sentinel**: probe failures are classified by comparing against exported error-string constants (`INVALID_BACKEND_API_KEY_ERROR`, etc.) so decided failures surface immediately (`src/hooks/query/use-backends-health.ts:36-72,164-171`) — pragmatic, though string comparison is a fragile discriminator compared to error codes.
- **Failure-cache invalidation**: `getAgentServerHomeDir` caches the promise but evicts it on rejection so "the next call can retry" (`src/api/agent-server-home.ts:70-77`).
- **Watchdog-to-error-state conversion**: both the WS handshake watchdog and the optimistic-message watchdog convert hangs into the system's normal error/retry UX rather than introducing new failure paths (`src/utils/websocket-handshake.ts:8-11`, `src/stores/optimistic-user-message-store.ts:131-139`).
- **Recovery-through-explicit-affordance**: `BackendNotConfigured`/`ErrorState` components take `onRetry` callbacks wired to `refetchHealth`/`refetch` across automation routes (`src/routes/automations-list.tsx:358,439`; `src/components/features/automations/backend-not-configured.tsx:10-28`).
- **Adaptive polling intervals**: fast-poll (3 s) during degraded/resume states, slow-poll (30 s) otherwise, tuned to avoid competing for the browser's per-origin HTTP/1.1 pool (`src/hooks/query/use-active-conversation.ts:19-33`; `use-backends-health.ts:31-34`).

## Tradeoffs

- **Duplication vs decoupling**: `withRetry` exists twice with identical bodies (`src/api/with-retry.ts:4-26`, `src/api/settings-service/settings-service.api.ts:134-156`), likely for module-boundary reasons, but fixes (e.g. adding jitter or auth-error exclusion) must be applied twice and can drift.
- **Infinite WS retries vs eventual surrender**: `maxAttempts ?? Infinity` means a permanently dead conversation URL retries forever at 30 s intervals (`src/hooks/use-websocket.ts:113-114`). Cheap for one socket, unbounded for long-lived tabs; mitigated only by the user navigating away.
- **String-sentinel error classification vs typed errors**: readable and greppable, but a wording change in one constant breaks retry classification silently (`src/hooks/query/use-backends-health.ts:166-170`).
- **Persisted disabled state vs staleness**: persisting the disable flag survives reloads (good for cascading-failure prevention) but risks a recovered backend staying marked dead until the user opens Manage Backends or edits config (`src/hooks/query/use-backends-health.ts:196-210` acknowledges this and adds `probeDisabledOnce` as mitigation).
- **Degrade-to-defaults vs silent misconfiguration**: returning default settings on fetch failure keeps the app usable (`src/api/settings-service/settings-service.api.ts:471-475`) but means a transient outage can present factory defaults as if they were the user's real configuration, with only a `console.warn`.

## Failure Modes / Edge Cases

- **`withRetry` retries definitive failures**: a 401/invalid-key settings fetch is retried the full 3 attempts with backoff before surfacing (`src/api/with-retry.ts:12-15`), adding ~1.5 s latency to unavoidable failures — inconsistent with the auth-aware probe path.
- **Unauthenticated pre-connect window**: connection errors are suppressed until the first successful connect (`hasConnectedRefMain`, `src/contexts/conversation-websocket-context.tsx:144-145,987-992`), so a conversation that never connects shows "Connecting"-state rather than an error banner — graceful, but potentially indefinite given infinite retries.
- **Watchdog timer leak on abandoned messages**: each enqueued pending message schedules a 150 s `setTimeout` with no cancellation handle; a consumed message's timer still fires and does a redundant store lookup (`src/stores/optimistic-user-message-store.ts:134-139`) — harmless per message, unbounded under heavy use.
- **Cloud poll swallows probe errors**: `waitForCloudConversationId` treats any poll failure as terminal (`catch(() => null)` breaks the loop, `src/services/child-conversation-launch.ts:376-380`), so a single transient proxy hiccup during provisioning ends the wait early even before the deadline.
- **Fixed-delay launcher retries**: the Node-side seed script uses flat 2 s delays with no exponential growth or jitter (`scripts/dev-with-automation.mjs:1273,1285`), acceptable for a dev tool, inconsistent with the app-side backoff discipline.
- **Dead retry-status channel**: `STATUS$LLM_RETRY` has no producer or consumer in this repo (`src/types/runtime-status.ts:18`); if a backend ever emitted it, the UI would have no rendering path — a contract drift hazard inherited from the upstream frontend.

## Future Considerations

- Consolidate the two `withRetry` implementations into one shared helper and add error-class discrimination (skip 4xx auth/validation like the probe path already does) plus optional jitter; make `src/api/with-retry.ts:4-26` the single source.
- Add automatic half-open recovery for disabled backends (e.g. one background probe per N minutes) instead of requiring modal-open or config-edit stimuli (`src/hooks/query/use-backends-health.ts:203-210`).
- Bound WS `maxAttempts` for conversation sockets (or add an exponential ceiling with user-visible "give up" state) rather than relying on the `Infinity` default (`src/hooks/use-websocket.ts:113-114`).
- Introduce a small typed error taxonomy (status-code-based) to replace string-sentinel classification in `isRetryableProbeError` (`src/hooks/query/use-backends-health.ts:164-171`).
- Either wire `STATUS$LLM_RETRY` into the status renderer or delete it to prevent contract confusion (`src/types/runtime-status.ts:18`).
- Expose retry/backoff tuning through `config/defaults.json` (the repo's declared single source of truth per `AGENTS.md`) so operations can adjust behavior without code changes.

- **Server-driven retry semantics unknown**: whether the agent-server emits retry-progress events the UI should render cannot be determined from this repository; `STATUS$LLM_RETRY` suggests an older contract existed.
- **No evidence found** of request-idempotency handling for retried mutations (e.g. dedupe keys on `withRetry`-wrapped PUTs in `src/api/secrets-service.ts:69-136`); retried writes could double-apply if the first attempt succeeded server-side but timed out client-side.
