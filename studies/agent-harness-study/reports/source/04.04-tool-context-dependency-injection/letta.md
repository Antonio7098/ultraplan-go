## Summary

Letta uses a **per-tool-type executor hierarchy with constructor-injected manager dependencies** rather than a single tool-context object. The root abstraction is the abstract base class `ToolExecutor` (`letta/services/tool_executor/tool_executor_base.py:16-46`), which receives five service managers (`MessageManager`, `AgentManager`, `BlockManager`, `RunManager`, `PassageManager`), the actor `User`, and (per call) an `AgentState`, `SandboxConfig`, and `sandbox_env_vars` dict (`tool_executor_base.py:19-45`). A `ToolExecutorFactory` (`tool_execution_manager.py:32-65`) selects the concrete executor based on `ToolType` and propagates the same manager bag to each subclass — `LettaCoreToolExecutor`, `LettaBuiltinToolExecutor`, `LettaFileToolExecutor`, `ExternalMCPToolExecutor`, `ExternalComposioToolExecutor`, and `SandboxToolExecutor` (`tool_execution_manager.py:35-43`).

The wrapper `ToolExecutionManager` (`tool_execution_manager.py:68-160`) is the public surface used by every agent and the REST API (`letta/agents/letta_agent.py:1952`, `letta/agents/letta_agent_v2.py:1318`, `letta/agents/letta_agent_batch.py:83`, `letta/agents/voice_agent.py:452`, `letta/server/server.py:1648`, `letta/server/rest_api/routers/v1/agents.py:794`). It carries the manager bag plus `agent_state` and `sandbox_env_vars` for the lifetime of one tool call; `execute_tool_async` is `@trace_method`-instrumented (`tool_execution_manager.py:94`) and records metrics via `MetricRegistry` (`tool_execution_manager.py:113-160`).

Inside sandboxed tools, runtime context is **synthesized into a generated Python script** by `AsyncToolSandboxBase.generate_execution_script` (`letta/services/tool_sandbox/base.py:126-175`) which inspects the tool's source AST and conditionally injects `agent_state` (pickled), `agent_id`, and a `letta_client.Letta` instance as in-script variables (`base.py:74-95, 156-174, 212-262`). Environment variables are layered by `_gather_env_vars` (`base.py:476-517`): OS env (local only) → global DB-stored sandbox env vars → provided `sandbox_env_vars` → agent env vars → runtime additions, with `LETTA_AGENT_ID`, `LETTA_PROJECT_ID`, `LETTA_TOOL_ID` always injected (`base.py:509-513`). Credentials for sandboxed tools are fetched per-call by `SandboxCredentialsService` from an external webhook (`letta/services/sandbox_credentials_service.py:12-80`).

There is **no single typed `ToolContext` object**; context is fragmented into the constructor-injected manager bag plus the per-call `function_name` / `function_args` / `tool` / `actor` / `agent_state` / `sandbox_config` / `sandbox_env_vars` arguments on `execute(...)`. Logger access is global via `get_logger(__name__)` in every executor (`tool_executor_base.py` does not inject one), and there is **no `CancellationToken` object** passed to executors — cancellation relies on `asyncio.CancelledError` propagation caught in `ToolExecutionManager.execute_tool_async` (`tool_execution_manager.py:131-142`) plus a polling `_check_run_cancellation` against the `RunManager` (`letta/agents/letta_agent.py:155-171`).

## Rating

**6/10**

Rationale:
- **Strengths**
  - One consistent DI surface — `ToolExecutor` abstract base class — defines exactly which dependencies are available to every tool kind (`letta/services/tool_executor/tool_executor_base.py:16-46`); every subclass accepts the same manager bag (`builtin_tool_executor.py:18`, `core_tool_executor.py:26`, `files_tool_executor.py:33`, `sandbox_tool_executor.py:24`, `mcp_tool_executor.py:22`, `composio_tool_executor.py:15`).
  - `ToolExecutorFactory` (`tool_execution_manager.py:32-65`) makes the manager bag uniform across `ToolType` — the same `message_manager`, `agent_manager`, `block_manager`, `run_manager`, `passage_manager`, and `actor` flow into core, builtin, file, MCP, composio, and sandbox executors (`tool_execution_manager.py:35-43, 58-65`).
  - **Tool source-AST introspection** decides which context to inject per tool (`base.py:74-95`): `agent_state` only if the function signature names it; `agent_id` only if the signature names it; `client` (the Letta SDK) is always available as a script-level variable. This is opt-in via function-signature convention, not module-level globals (`base.py:80-91`).
  - **Sandbox env layering is explicit and ordered** (`base.py:476-517`): OS env (local) → global sandbox env vars from DB → provided per-call `sandbox_env_vars` → agent env vars → runtime additions → reserved `LETTA_AGENT_ID`/`LETTA_PROJECT_ID`/`LETTA_TOOL_ID`. The function `_gather_env_vars` filters out `None` values to prevent subprocess errors (`base.py:516`).
  - **Secrets are stored encrypted at rest** via the `Secret` Pydantic model and `CryptoUtils` (`letta/schemas/secret.py:13-30, 34-69`); `SandboxEnvironmentVariable.from_orm_async` (`letta/schemas/environment_variables.py:44-69`) and `AgentEnvironmentVariable.from_orm_async` (`environment_variables.py:89-114`) pre-decrypt asynchronously before injection.
  - **Per-call sandbox credentials** are fetched via `SandboxCredentialsService` (`letta/services/sandbox_credentials_service.py:12-80`), keyed by `actor`, `tool_name`, and `agent_id`, with timeout and HTTP error handling returning `{}` (`sandbox_credentials_service.py:72-78`); the unit tests cover all five failure modes (`letta/services/sandbox_credentials_service_test.py:22-148`).
  - **Testability is good for the typed executors**: `tests/integration_test_builtin_tools.py:198-205, 286-293, 463-470` instantiate `LettaBuiltinToolExecutor` with `MagicMock()` for every manager and `actor`, then call `executor.web_search(agent_state=mock_agent_state, ...)` directly — no app boot required. `tests/integration_test_typescript_tool_execution_sandbox.py:658` exercises `SandboxToolExecutor._prepare_function_args` as a `@staticmethod`. `tests/integration_test_composio.py:70-81` instantiates `ToolExecutionManager` against a real `SyncServer`.
  - **Tracing and metrics are automatic**: `ToolExecutionManager.execute_tool_async` is `@trace_method` (`tool_execution_manager.py:94`) and records `tool_execution_time_ms_histogram` + `tool_execution_counter` with `tool.name` and `tool.execution_success` attributes (`tool_execution_manager.py:113-160`). `ToolExecutor.execute` is also `@trace_method` in every concrete executor (`builtin_tool_executor.py:21`, `core_tool_executor.py:…`, `mcp_tool_executor.py:25`, `composio_tool_executor.py:18`, `sandbox_tool_executor.py:27`, `files_tool_executor.py:…`).
  - **Permission enforcement is layered via the actor**: every executor receives a `User` actor and forwards it to manager methods that filter by `actor.organization_id` (`tool_execution_manager.py:110, 120` → `MessageManager.search_messages_async(actor=actor, …)` at `core_tool_executor.py:141-149`); tool lookup raises if the tool is not provisioned to the actor's org (`base.py:65-67`).
  - **Structured JSON logging with `dd.trace_id` / `dd.span_id` correlation** via `JSONFormatter` (`letta/log.py:16-130`) — log records automatically pull trace context from the current OpenTelemetry span, so logs are request-scoped via contextvars (`log.py:74-86`) even though the logger object is module-level.
- **Limitations**
  - **No typed `ToolContext` object** — context is split across six constructor parameters, four per-call parameters, and the generated script's globals (`tool_executor_base.py:19-45`). Tests that exercise only one piece (e.g. `executor.web_search`) cannot reuse a single fixture; every test wires its own mocks (`integration_test_builtin_tools.py:198-205`).
  - **Tool rule / approval enforcement happens outside the executor** — `ToolRulesSolver` lives in `letta/helpers/tool_rule_solver.py:1-300` and gates which tools the model may call, but the `ToolExecutor.execute` signature does not carry the `ToolRule` set or approval state, so per-execution policy enforcement is not part of the DI contract (search of `services/tool_executor/*.py` for `tool_rule`/`approval` returns no hits).
  - **Cancellation is not first-class**: `ToolExecutionManager` catches `asyncio.CancelledError` (`tool_execution_manager.py:131-142`) and returns a synthetic `ToolExecutionResult(status="error", …)`, but there is no `CancellationToken`/`asyncio.Event` passed to executors. The agent has to poll `JobStatus.cancelled` via `RunManager` in `_check_run_cancellation` (`letta/agents/letta_agent.py:155-171`), which is a coarse loop rather than a propagated token.
  - **Logger is module-level**, not injected — `LettaBuiltinToolExecutor` uses `logger = get_logger(__name__)` (`letta/services/tool_executor/builtin_tool_executor.py:15`); `LettaFileToolExecutor` does the same (`files_tool_executor.py:69`); the `ToolExecutor` base class never assigns `self.logger`. Request-scoped correlation only works because `JSONFormatter` reads the current OTel span (`log.py:74-86`), not because the logger was injected.
  - **`actor` is positional but typed as `Optional` in `LettaCoreToolExecutor.execute` indirectly** — the type annotation is `actor: User` (non-optional) but the kwarg is forwarded twice: once as `actor` to the manager call and once as a function argument to the tool method (`core_tool_executor.py:64` — `function_map[function_name](agent_state, actor, **function_args_copy)`). This means core tools receive the actor as a *real Python positional argument* in their function signature, not as injected context.
  - **`SandboxToolExecutor` lazily reaches global state** via `SandboxCredentialsService()` and `AgentManager()` instantiations inside `execute` (`letta/services/tool_executor/sandbox_tool_executor.py:45, 142`) — these are no-arg constructors that read `os.environ` (`sandbox_credentials_service.py:15-17`) and create fresh managers, bypassing the constructor-injected `agent_manager` for the post-execution memory persist (`sandbox_tool_executor.py:142`).
  - **`LettaFileToolExecutor.__init__` allocates its own `FileAgentManager()`, `FileManager()`, `SourceManager()`** even though `ToolExecutorFactory` only forwards five managers (`letta/services/tool_executor/files_tool_executor.py:66-69`); comment `TODO: This should be passed in to for testing purposes` (`files_tool_executor.py:65`) admits this — unit tests cannot swap these out without monkey-patching.
  - **`run_manager` is injected but rarely used inside executors** — search across `services/tool_executor/*.py` for `self.run_manager.` returns only the constructor assignments; no concrete executor invokes `self.run_manager.*` for run-state mutation. Including it in the base signature is forward-looking but currently dead weight.
  - **`SandboxToolExecutor._prepare_function_args` swallows coercion errors defensively** (`letta/services/tool_executor/sandbox_tool_executor.py:165-169`) — `try/except (ValueError, TypeError): return function_args` means a malformed type annotation silently flows un-coerced into the sandbox, hiding DI contract violations.
  - **Sandbox env precedence can be surprising**: the order in `AsyncToolSandboxBase._gather_env_vars` is OS env → global DB → provided → agent → additional → reserved IDs (`base.py:487-513`), but `SandboxToolExecutor.execute` *also* overrides `sandbox_env_vars` with fetched credentials + `PROJECT_ID` before constructing the sandbox (`sandbox_tool_executor.py:53-61`), then passes the merged dict as `sandbox_env_vars=` to the sandbox constructor (`sandbox_tool_executor.py:91, 115, 127`) — the executor's pre-merge and the base's layer both run, with the executor's merge winning because `provided_sandbox_env_vars` is checked first (`base.py:496-497`).
  - **Secrets passed via `sandbox_env_vars` are placed directly into the subprocess environment** for local sandboxes (`local_sandbox.py:81, 113-119`); there is no allowlist/denylist of variable names — any agent env var becomes a sandbox env var (`base.py:496-506`). Compare against MCP, where `_MCP_FRAMEWORK_DENYLIST` (agent-framework style) is absent.
  - **`Tool` is a Pydantic model and contains source code** (`letta/schemas/tool.py:46`) — there is no separate "function callable" object that can be wired at DI time; tool execution always requires re-parsing the source string and re-`exec()`-ing or re-subprocess-ing it.
  - **No `JobManager` is forwarded** through `ToolExecutor` even though callers construct `ToolExecutionManager(job_manager=self.job_manager, …)` (`letta/agents/letta_agent.py:1957`, `integration_test_composio.py:74`); the constructor accepts `job_manager` but never stores it on `self` (`tool_execution_manager.py:71-92` — no `self.job_manager = job_manager` assignment despite the parameter). This silently drops a dependency at the boundary.

## Answers to Dimension Questions

1. **What context does a tool receive?**
   Two layers, depending on execution path:
   - For built-in executors (`core`, `builtin`, `files`, `mcp`, `composio`): a `ToolExecutor` instance with constructor-injected `MessageManager`, `AgentManager`, `BlockManager`, `RunManager`, `PassageManager`, `actor: User`, and per-call `function_name`, `function_args`, `tool: Tool`, optional `agent_state: AgentState`, optional `sandbox_config: SandboxConfig`, optional `sandbox_env_vars: Dict[str, Any]` (`tool_executor_base.py:16-45`). Tools then receive `agent_state`, `actor`, and `**function_args` as Python positional/keyword arguments (e.g. `core_tool_executor.py:64`).
   - For sandboxed custom tools: a generated Python script with `agent_state` (pickled → `pickle.loads`), `agent_id`, and a Letta SDK client available as `client` globals (`base.py:156-262`); environment variables layered into `os.environ` (`base.py:476-517`); function kwargs passed by name with type coercion via `coerce_dict_args_by_annotations` (`sandbox_tool_executor.py:161-169`, `base.py:270-289`). The Modal variant runs in a Modal container with `tool_namespace = {"__builtins__": __builtins__, "os": os, "agent_id": agent_id, "_LETTA_API_KEY": letta_api_key}` and `exec(tool.source_code, tool_namespace)` (`tool_manager.py:129-141`).

2. **Is context explicit or global?**
   Explicit at the boundary but **global at the worker**. The `ToolExecutor` constructor and the `ToolExecutionManager.execute_tool_async` signature explicitly enumerate dependencies (`tool_executor_base.py:19-27`, `tool_execution_manager.py:71-92`). However, every executor also reaches global state: `SandboxCredentialsService()` (`sandbox_tool_executor.py:45`), `AgentManager()` (`sandbox_tool_executor.py:142`), `ToolManager()` (`base.py:62`), and module-level `get_logger(__name__)` (`builtin_tool_executor.py:15`, `files_tool_executor.py:69`). The `ToolSettings` singleton (`letta/settings.py:22-72`) holds sandbox API keys as global config (`tool_settings.e2b_api_key`, `tool_settings.exa_api_key`), accessed directly without injection (`builtin_tool_executor.py:57, 152, 235, 343`). `tools_settings.tool_sandbox_timeout` is similarly a global read (`local_sandbox.py:197`).

3. **Are secrets passed safely?**
   Mostly yes, with caveats. At rest, env-var values are stored encrypted via the `Secret` Pydantic model and decrypted asynchronously on load (`schemas/secret.py:13-69`, `schemas/environment_variables.py:60-69, 105-114`). At fetch time, `SandboxCredentialsService` uses an HTTPS webhook with `Authorization: Bearer <key>` header and a 10s timeout (`sandbox_credentials_service.py:43-78`); failures return `{}` rather than raising (`sandbox_credentials_service.py:72-78`). At injection time, secrets flow into `sandbox_env_vars` (a plain `Dict[str, str]`) and are placed directly into `os.environ` of the subprocess (`local_sandbox.py:81, 113-119`) or sent to e2b as `envs=` (`e2b_sandbox.py:102`). For Modal, secrets flow as `modal.Secret.from_dict(secrets_dict)` (`tool_manager.py:82`) and as `LETTA_API_KEY` env var in the namespace (`tool_manager.py:129-136`). **There is no env-var denylist** to prevent leaking framework-internal vars (`LETTA_AGENT_ID`, `LETTA_PROJECT_ID`, `LETTA_TOOL_ID` are always injected — `base.py:509-513`). Tool return values are truncated by `return_char_limit` (`tool_execution_manager.py:127-128`), but secrets in stdout/stderr are not scrubbed before logging (`local_sandbox.py:209-210`).

4. **Can tools be unit tested?**
   Yes, for the typed executors. `tests/integration_test_builtin_tools.py:198-205, 286-293, 463-470` constructs `LettaBuiltinToolExecutor(message_manager=MagicMock(), agent_manager=MagicMock(), block_manager=MagicMock(), run_manager=MagicMock(), passage_manager=MagicMock(), actor=MagicMock())` and calls `executor.web_search(agent_state=mock_agent_state, query="…", num_results=10)` directly with no app boot. `tests/integration_test_typescript_tool_execution_sandbox.py:658` calls `SandboxToolExecutor._prepare_function_args(args, tool, name)` as a static. `tests/integration_test_composio.py:70-81` builds a real `ToolExecutionManager` from `SyncServer` (close to integration, not pure unit). `tests/integration_test_builtin_tools.py:436-485` exercises `run_code` with mock agent state — requires `tool_settings.e2b_api_key`. `tests/managers/test_tool_manager.py:40-2370` exercises the ToolManager CRUD path against a real `SyncServer`. Pure unit isolation is possible for builtin/core executors but requires manual mock wiring because the base class has six dependencies, no test fixtures, and `LettaFileToolExecutor` instantiates three managers inside its constructor (`files_tool_executor.py:66-69`).

5. **Can context enforce permissions?**
   Yes, via the actor. Every executor receives a `User` actor (`tool_executor_base.py:26, 41`) and forwards it to manager calls (e.g. `self.message_manager.search_messages_async(actor=actor, …)` at `core_tool_executor.py:141-149`); tool lookup raises if the tool is not provisioned to the actor's org (`base.py:65-67`). Approval gates are *not* part of the executor DI signature — the executor does not see `requires_approval` rule state. **There is no permission check inside `SandboxToolExecutor.execute` that limits which env vars a tool can read**, and `_gather_env_vars` does not enforce a sandbox-config-level allowlist (`base.py:476-517`).

## Architectural Decisions

- **Strategy pattern per ToolType** rather than a single executor (`tool_execution_manager.py:35-43`): each executor type owns the contract for a class of tools (core, builtin, file, MCP, composio, sandbox). New tool kinds add a new executor without modifying existing ones.
- **Bag-of-managers DI**: five service managers + actor + agent_state + sandbox_env_vars are passed as constructor/keyword args (`tool_executor_base.py:19-27`, `tool_execution_manager.py:71-92`). No service locator, no DI container, no global state for the manager bag.
- **Code-generated sandbox scripts**: tools are stored as source text in the DB (`schemas/tool.py:46`); at execution time, `AsyncToolSandboxBase.generate_execution_script` builds a Python script that imports `pickle`, deserializes `agent_state`, optionally constructs a Letta SDK `client`, sets `agent_id`, inlines the tool's `source_code`, then invokes the tool function and pickle-encodes the result (`base.py:126-388`). This is the entire injection mechanism for sandboxed tools.
- **Actor-based permission propagation**: `User` flows through every layer and every DB query is filtered by `actor.organization_id`. SQLAlchemy row-level access uses `actor` as the filter (`letta/orm/sqlalchemy_base.py:446, 885-890`).
- **Modal-as-isolated-runtime** for sandboxed tools, using a namespace with `__builtins__`, `os`, `agent_id`, and `_LETTA_API_KEY` as globals, then `exec(tool.source_code, tool_namespace)` (`tool_manager.py:129-141`). AgentState is reconstructed from a dict to dodge cloudpickle schema drift (`tool_manager.py:88-117`).
- **Per-call trace + metric context**: `ToolExecutionManager.execute_tool_async` is `@trace_method` and uses `AsyncTimer` + `MetricRegistry` to record histogram + counter with `tool.name` and `tool.execution_success` attributes (`tool_execution_manager.py:94, 113-160`). The OTel `ContextVar` attributes from `get_ctx_attributes()` are spread into every metric record (`tool_execution_manager.py:115, 157-160`).
- **Per-call credential webhook**: `SandboxCredentialsService` hits an external endpoint to fetch credentials keyed by `(actor, tool_name, agent_id)`, with the webhook URL/key sourced from env vars (`sandbox_credentials_service.py:14-17`). This decouples credential storage from the Letta database.
- **Env var layering with reserved IDs**: `_gather_env_vars` always appends `LETTA_AGENT_ID`, `LETTA_PROJECT_ID`, `LETTA_TOOL_ID` so tools can identify themselves (`base.py:509-513`). TypeScript tools do not get `agent_state` injection — only `LETTA_AGENT_ID` via env (`base.py:74-78`).
- **Markdown result markers** for local-sandbox result extraction: `LOCAL_SANDBOX_RESULT_START_MARKER` + 4-byte length + md5 checksum + payload encoded into stdout (`local_sandbox.py:253-274`). This lets Letta separate tool return data from tool `print()` output.

## Notable Patterns

- **Factory + abstract base class** (`ToolExecutorFactory` → `ToolExecutor`) is the canonical Letta pattern for swappable strategy (`tool_execution_manager.py:32-65`, `tool_executor_base.py:16-46`).
- **Bag-of-services constructor** rather than property setters or service locators: every `ToolExecutionManager` and `ToolExecutor` accepts its dependencies as named kwargs and stores them as instance attrs (`tool_executor_base.py:28-33`, `tool_execution_manager.py:83-92`).
- **AST-driven injection**: `AsyncToolSandboxBase._init_async` parses the tool's source AST via `parse_function_arguments` and sets `inject_agent_state`/`inject_agent_id`/`inject_letta_client` flags based on whether the tool signature names those parameters (`base.py:74-95`, `tool_parser_helper.py:35-44`). Tools opt into context by naming it in their signature.
- **Decorator-driven tracing/metrics**: `@trace_method` (`tool_execution_manager.py:94`) and `AsyncTimer(callback_func=…)` (`tool_execution_manager.py:118`) instrument every call without polluting tool source code.
- **ContextVar log context** (`_log_context: ContextVar[dict[str, Any]]`) for cross-async-task correlation (`log_context.py:1-33`); OTel trace_id/span_id injected into log records via `JSONFormatter` (`log.py:74-86`).
- **`@enforce_types` runtime type checks** on every manager method (`utils.py:533`, applied 70+ times in `agent_manager.py`, `tool_manager.py`, etc.) — replaces static typing where Pydantic models would be too heavyweight.
- **Pydantic secret wrapper** that stays encrypted in memory until `.get_plaintext()`/`get_plaintext_async()` is called (`schemas/secret.py:13-69`); `from_orm_async` does async decryption to avoid blocking the event loop on PBKDF2 key derivation (`schemas/secret.py:72-100`, `schemas/environment_variables.py:60-69`).

## Tradeoffs

- **Single-execution result schema vs. richer context**: `ToolExecutionResult` carries only `status`, `func_return`, `agent_state`, `stdout`, `stderr`, `sandbox_config_fingerprint` (`schemas/tool_execution_result.py:8-14`). There is no place for trace context, last-applied tool rule, approval state, or actor identity on the result — those flow through the surrounding agent loop instead.
- **Manager-bag DI vs. service locator**: the manager bag is explicit (good for test mocks, type-checked) but every new executor repeats the same `def __init__(self, message_manager, agent_manager, block_manager, run_manager, passage_manager, actor)` signature, which is verbose and not extensible to new dependencies without modifying every subclass (`tool_executor_base.py:19-33`).
- **AST-driven injection vs. registration-driven**: AST scanning lets users write `def my_tool(agent_state, x)` and "just works" (`base.py:80-91`), but it means the contract is implicit (a rename from `agent_state` to `agentState` silently disables injection) and the test surface must re-scan to verify (`integration_test_typescript_tool_execution_sandbox.py:630-660`).
- **Module-level logger vs. injected logger**: per-class `logger = get_logger(__name__)` (`builtin_tool_executor.py:15`) is simple and OTel-aware via `JSONFormatter` (`log.py:74-86`), but tools cannot receive a request-scoped logger, so per-execution correlation depends entirely on the OTel contextvar.
- **Sandbox subprocess vs. in-process**: local sandbox runs the tool in `asyncio.create_subprocess_exec` with full env-var injection (`local_sandbox.py:192-194`), which is isolated but has 180s timeout (`settings.py:36`) and no in-process test path; e2b and Modal are fully remote.
- **Manager bag includes `run_manager` but no executor uses it**: the constructor accepts `run_manager` (`tool_executor_base.py:24, 31`) but no concrete executor invokes `self.run_manager.*` for run-state mutation (only `_check_run_cancellation` in the agent loop uses it). This is forward-looking but currently dead weight in the DI surface.
- **`job_manager` accepted but never stored**: `ToolExecutionManager.__init__` accepts `job_manager` (`tool_execution_manager.py:71-92`) but the signature silently lacks `self.job_manager = job_manager`. Callers pass it (`letta_agent.py:1957`, `integration_test_composio.py:74`), so the parameter looks alive but no executor can read it back. This is a contract-vs-implementation drift.

## Failure Modes / Edge Cases

- **`SandboxCredentialsService` returns `{}` on timeout/HTTP error** (`sandbox_credentials_service.py:72-78`); tools that assume credentials are present will fail with `KeyError` or `None` access rather than a clean "credentials unavailable" error.
- **Modal agent_state round-trip**: if `AgentState` schema differs between Modal's letta version and the server's, fields are silently filtered out (`tool_manager.py:96-107`); a model mismatch prints to stderr (`tool_manager.py:107`) but does not raise.
- **Local sandbox subprocess timeout terminates without cleanup guarantee**: `process.terminate()` then 5s wait then `process.kill()` (`local_sandbox.py:200-205`), but the `temp_file_path` cleanup at `local_sandbox.py:155-156` only runs in the `finally` if `settings.debug` is False — a debug run leaks the script.
- **`SandboxToolExecutor._prepare_function_args` swallows type errors** (`sandbox_tool_executor.py:165-169`) so a malformed annotation silently flows un-coerced; downstream coercion in the generated script (`base.py:276-289`) also has a `try/except Exception: pass` (`base.py:289`), so the tool receives raw strings regardless.
- **`SandboxToolExecutor` calls `AgentManager()` inside `execute`** (`sandbox_tool_executor.py:142`) instead of using the injected `self.agent_manager`; if a test mocks the injected `agent_manager`, the memory persist step still hits a fresh global manager.
- **`ToolExecutionManager` accepts `job_manager` but does not store it** (`tool_execution_manager.py:71-92`); agents that pass `job_manager` see no error but cannot influence run state via the executor.
- **Actor in core tools flows as a positional arg** (`core_tool_executor.py:64`); if a user-defined tool also defines an `actor` parameter, the actor and the user value collide silently because the executor always forwards `actor` positionally.
- **Env var leakage**: `_gather_env_vars` does not enforce a sandbox-config-level allowlist (`base.py:476-517`); a compromised tool can read any env var in `os.environ` (local) or any var in `envs=` (e2b/Modal).
- **`LettaFileToolExecutor` always constructs `FileAgentManager()`, `FileManager()`, `SourceManager()` in `__init__`** (`files_tool_executor.py:66-69`); tests that don't pre-populate a DB fixture crash.
- **`return_char_limit` truncation happens after executor returns** (`tool_execution_manager.py:127-128`); executors that exceed the limit during execution still pay the full cost before truncation.

## Future Considerations

- **Promote `actor` and `agent_state` from positional tool args to a typed `ToolContext` object** so users stop needing to enumerate them in tool signatures (analogous to agent-framework's `FunctionInvocationContext` at `_middleware.py:204-370`).
- **Inject `RunManager` and `JobManager` into `ToolExecutor`** and store them on `self`, then surface cancellation as an explicit `asyncio.Event` or `CancellationToken` (currently absent).
- **Inject a request-scoped `Logger`** alongside `actor` so log lines can carry per-call correlation beyond OTel span context.
- **Add an env-var allowlist at the sandbox-config level** to prevent arbitrary `os.environ` from leaking into untrusted tool sandboxes; mirror the `_MCP_FRAMEWORK_DENYLIST` pattern from agent-framework's `_mcp.py:88-98`.
- **Move `LettaFileToolExecutor`'s in-constructor `FileAgentManager/FileManager/SourceManager` allocations** into the `ToolExecutor` base signature so unit tests can swap them with mocks (currently gated by the `TODO` at `files_tool_executor.py:65`).
- **Centralize sandbox credential injection** — currently `SandboxToolExecutor` does its own merge (`sandbox_tool_executor.py:53-61`) that overrides `_gather_env_vars` precedence (`base.py:496-497`); pick one precedence rule and document it.
- **Drop `job_manager` from `ToolExecutionManager.__init__`** (or store it) to resolve the contract drift (`tool_execution_manager.py:71-92`).
- **Use `SerializationMixin.INJECTABLE`-style marking** so the `Tool.source_code` is excluded from any persistence layer that doesn't need it (compare to agent-framework's `_serialization.py:268`).
- **Surface `ToolRulesSolver` and approval state in the executor signature** so per-call policy enforcement is part of the DI contract, not just an agent-loop concern.
