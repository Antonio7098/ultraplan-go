## Summary

Agent Framework ships a **context-object-based tool DI model** centered on `FunctionInvocationContext` (`python/packages/core/agent_framework/_middleware.py:204-370`). Tools opt in to receiving context by either (a) declaring a parameter annotated as `FunctionInvocationContext` or (b) declaring an untyped `ctx` parameter when an explicit `schema=` is supplied (`_tools.py:411-436`, `_tools.py:432-436`). Once opted-in, a tool can read `ctx.kwargs`, `ctx.session`, `ctx.metadata`, `ctx.tools` (live, mutable), `ctx.arguments`, `ctx.function`, and override `ctx.result` or raise `MiddlewareTermination` to short-circuit execution.

Runtime injection is **centralized in `FunctionInvocationLayer.get_response`** (`_tools.py:2467-2699`) which extracts `function_invocation_kwargs` / `client_kwargs` / `options["additional_function_arguments"]` into a single `runtime_kwargs` dict (`_tools.py:1500-1508`), populates `runtime_kwargs["session"]` when an `AgentSession` is attached (`_tools.py:1507-1508`), and constructs a `FunctionInvocationContext` per call (`_tools.py:1537-1543, 1571-1577`). Both the no-middleware fast path (`_tools.py:1532-1569`) and the middleware pipeline path (`_tools.py:1570-1629`) build the context from the same `runtime_kwargs` and `invocation_session`, so a tool receives the same runtime surface whether or not middleware is configured.

The framework also has a **secondary DI surface for serialization** via `SerializationMixin.INJECTABLE` (`_serialization.py:268`, `_tools.py:290-299`): fields listed in `INJECTABLE` are excluded from `to_dict()` (e.g. `FunctionTool.func` is marked `INJECTABLE` so the wired callable is never persisted) and must be supplied via `dependencies={...}` during `from_dict()` (`_serialization.py:392-509, 532-552`). A typed `SecretString` (`_settings.py:52-82`) plus `OBSERVABILITY_SETTINGS.SENSITIVE_DATA_ENABLED` (`_tools.py:733, 758, 771`) gate telemetry so injected secrets are not echoed into spans or logs.

**MCP safety** is implemented as a complementary allowlist + denylist: `_MCP_FRAMEWORK_DENYLIST` (`_mcp.py:88-98`) drops framework-internal kwarg names a server might declare (e.g. `session`, `chat_options`, `conversation_id`), `_prepare_call_kwargs` (`_mcp.py:1745-1791`) forwards only declared `properties` plus user-explicit extras via `additional_tool_argument_names`, and a `contextvars.ContextVar(_mcp_call_headers)` (`_mcp.py:99, 2724-2731`) carries per-call auth headers produced by an `header_provider` callable that receives the runtime `kwargs` directly from `FunctionInvocationContext.kwargs`.

The `.NET` side, by contrast, relies on the `Microsoft.Extensions.AI` `AIFunction` factory (`AIFunctionFactory.Create`); the framework does not invent a separate context-object model there. Tools are wired through `HostedAgentBuilder.WithAITool(factory:)` for DI-aware lifetimes (`dotnet/src/Microsoft.Agents.AI.Hosting/HostedAgentBuilderExtensions.cs:87-156`); the `.NET` evaluation focuses entirely on the Python stack below.

## Rating

**9/10**

Rationale:
- **Strengths**
  - A single, well-typed context object (`FunctionInvocationContext`) carries every runtime dependency a tool could want: validated `arguments`, `session`, `metadata`, runtime `kwargs`, live `tools` list, the wrapped `function`, and a mutable `result` (`_middleware.py:204-285`).
  - **Discovery is introspection-driven** via `FunctionTool._discover_injected_parameters` (`_tools.py:411-436`) so users do not need to register dependencies; just declare a parameter. The discovery enforces "at most one typed context parameter" (raises `ValueError`) to keep the contract unambiguous (`_tools.py:428-430`; test `tests/core/test_tools.py:1067-1088`).
  - **Testability is first-class**: `FunctionTool.invoke(arguments=..., context=...)` works in isolation from any agent/chat-client (`_tools.py:577-775`); tests construct a `FunctionInvocationContext` directly and invoke a `@tool` with no agent in scope (`tests/core/test_tools_future_annotations.py:116-134`, `tests/core/test_tools.py:968-1064`). No global state is required.
  - **Permissions are enforced via `approval_mode`** (`_tools.py:96, 306-321`) plus the experimental `ToolApprovalMiddleware` and `ToolApprovalRule` (`_harness/_tool_approval.py`). The framework refuses to let a vanilla `**kwargs` tool silently receive session or internal objects (test `test_agent_tool_without_context_does_not_receive_session`, `tests/core/test_agents.py:1720-1755`); session is only injected through `FunctionInvocationContext.session` (`tests/core/test_agents.py:1758-1794`).
  - **MCP argument safety** is layered: argument allowlist from declared schema + user-explicit extras, framework denylist as safety net, reserved `_meta` extraction (`_mcp.py:88-98, 1745-1791`). Runtime kwargs flow to the `header_provider` callback exclusively via `FunctionInvocationContext.kwargs` (`_mcp.py:2708-2731`), with a `contextvars` reset on exit.
  - **Progressive tool exposure** is enabled at runtime through `FunctionInvocationContext.add_tools/remove_tools` (`_middleware.py:287-370`), with atomic all-or-nothing semantics and a `RuntimeError` if called outside a function-calling loop (`_middleware.py:312-317, 345-350`). The list handed back to the model and the live list held by the context are the same Python object (`_tools.py:2549-2550, 1689-1690`).
  - **Secrets-aware**: `SecretString` masks its repr (`_settings.py:72-82`); `OBSERVABILITY_SETTINGS.SENSITIVE_DATA_ENABLED` (`_tools.py:733, 742-744, 758, 771-774`) gates whether tool arguments/results are recorded onto OpenTelemetry spans, and `OBSERVABILITY_SETTINGS.ENABLED` separately gates logger output (`_tools.py:694-715`).
  - **Serialization-aware DI**: `SerializationMixin.INJECTABLE` (`_serialization.py:268, 532-552`) plus `dependencies=` payloads during `from_dict()` let non-serializable runtime objects (callables, sessions, context objects) round-trip cleanly without leaking into persisted state (`_serialization.py:392-509`).
  - **Harness-level factory assembly** (`_harness/_agent.py:238-525`) wires `FileMemoryProvider`, `FileAccessProvider`, `SkillsProvider`, `BackgroundAgentsProvider`, `CompactionProvider`, `ToolApprovalMiddleware` into a single agent declaratively, with keyword flags to disable each (`_harness/_agent.py:255-275`).
- **Limitations**
  - **Opt-in only**: a vanilla `@tool def foo(x: int) -> str` receives no runtime context — not even session, logger, or cancellation. Users must declare a `ctx`/`FunctionInvocationContext` parameter; otherwise the tool is hermetic. This is by design but worth knowing (test `test_ai_function_with_kwargs_rejects_runtime_invoke_kwargs`, `tests/core/test_tools.py:934-966`).
  - **Context lifetime is per-function-call, not per-invocation of a tool by the agent** — `FunctionInvocationContext.metadata["call_id"]` and `metadata["approval_response"]` are set immediately before invocation (`_tools.py:1584-1589`) and disappear after. There is no built-in per-tool lifetime DI; long-lived collaborators must be passed via `session.state` or declared explicitly in the function signature.
  - **No cancellation token is injected on the context object**: `FunctionInvocationContext` does not carry an `asyncio` cancellation/timeout primitive. Tools that need cooperative cancellation must accept it via their own kwargs or assume the surrounding task's `CancelledError`. (Search across `_middleware.py:204-370` returns no `cancel`/`timeout` field.)
  - **Logger is not injected**. `FunctionTool` uses the module-level `logger = logging.getLogger("agent_framework")` (`_tools.py:87`) globally — tools cannot receive a per-request logger. Logging is therefore not request-scoped.
  - **Secret redaction in telemetry only**: secrets that bypass `SecretString` (raw strings passed through `kwargs`) are still recorded in spans unless the type system catches them. The allowlist of serialized kwargs in `_tools.py:719-732` filters framework-internal keys but does not scrub user-defined secret-named kwargs.
  - **Secrets passed via `FunctionInvocationContext.kwargs` are reachable by middleware** in plaintext (`_middleware.py:204-285`); the `FunctionMiddlewarePipeline` (`_middleware.py:930-1000`) hands the same context to every middleware. There is no DI-level tool visibility control for secret-bearing values.
  - **`FunctionInvocationConfiguration`** (`_tools.py:1344-1421`) is a `TypedDict`, not a class — no methods, no constructors. Defaults are reapplied on every normalization (`_tools.py:1401-1421`) and re-validated each call.
  - **MCP `header_provider` only works on `MCPStreamableHTTPTool`** (`_mcp.py:2707-2731`); stdio and websocket transports do not propagate `_mcp_call_headers` because they don't have an HTTP request hook.
  - **Cross-stack parity is partial**: .NET hosts tool registration through `HostedAgentBuilder.WithAITool(factory:)` with lifetime validation (`dotnet/src/Microsoft.Agents.AI.Hosting/HostedAgentBuilderExtensions.cs:87-156`) but the Python side has no equivalent factory-based DI for tool providers — Python relies on positional/keyword arguments to `@tool` / `FunctionTool(...)`.

## Answers to Dimension Questions

1. **What context does a tool receive?** A `FunctionInvocationContext` object (`_middleware.py:204-285`). If the tool opted in (typed `FunctionInvocationContext` param or untyped `ctx` with explicit `schema=`), the framework injects the populated context: `function` (the `FunctionTool` itself), `arguments` (validated dict), `session` (the `AgentSession` if available), `metadata` (mutable dict), `result` (mutable; can be overridden), `kwargs` (the runtime `function_invocation_kwargs` + `options["additional_function_arguments"]`), and `tools` (the live, mutable list binding the model's tool list to the runtime, enabling `add_tools`/`remove_tools`). The framework also explicitly rejects runtime data passed outside of context (`_tools.py:633-640`).
2. **Is context explicit or global?** Explicit and **opt-in**. The framework does not put runtime state in module-level globals — `FunctionTool.__call__` (`_tools.py:516-543`) only knows about positional/keyword arguments. Context is delivered only through (a) the typed `FunctionInvocationContext` parameter and (b) the untyped `ctx` shortcut. Validation tests (`test_tools.py:614-629, 934-966`) prove that `invoke()` rejects stray kwargs with `TypeError`. Logger access is global (`_tools.py:87`), which is the one place where framework-code reaches for a global.
3. **Are secrets passed safely?** Three layers cooperate. (a) `SecretString` masks `__repr__` (`_settings.py:72-82`). (b) `SerializationMixin.INJECTABLE` (`_serialization.py:268, 313, 532-552`) prevents runtime objects (callables, sessions, contexts) from being persisted. (c) `OBSERVABILITY_SETTINGS.SENSITIVE_DATA_ENABLED` (`_tools.py:733, 758`) gates whether tool arguments and results are recorded onto OpenTelemetry spans, with explicit default-off behavior (`_tools.py:733-735, 758-761, 771-774`). However, **secrets embedded in tool `kwargs`** are reachable by any `FunctionMiddleware` because middleware sees the same `FunctionInvocationContext` (`_middleware.py:204-285, 963-1000`); there is no per-tool visibility filter.
4. **Can tools be unit tested?** Yes, fully. `FunctionTool.invoke(arguments=..., context=..., tool_call_id=..., skip_parsing=...)` is a public coroutine (`_tools.py:555-715`) that does not require a chat client, an agent, or any global state. Tests build a `FunctionInvocationContext` and call `tool.invoke(context=ctx)` directly (`test_tools_future_annotations.py:116-134`; `test_tools.py:968-1064`). The harness wide-body tests use `MockChatClient` (`tests/core/conftest.py`, used in `test_function_invocation_logic.py`) to exercise the full function-invocation pipeline without external IO. There is no need to "boot the whole app" to verify tool-side behavior.
5. **Can context enforce permissions?** At the tool-approval level, yes: `FunctionTool.approval_mode` (`_tools.py:96, 306-321`, validated as `Literal["always_require", "never_require"]`) gates whether a tool call requires user approval before execution; the default is `"never_require"`. The `ToolApprovalMiddleware` and `ToolApprovalRule` model (`_harness/_tool_approval.py`) coordinate session-backed standing approvals, heuristic `auto_approval_rules`, and queued approval requests. At the argument level, MCP enforces an allowlist (declared schema params + user-extras) and a denylist (`_mcp.py:88-98, 1745-1791`) that drops framework-internal kwarg names so a malicious server cannot inject e.g. `session` or `conversation_id` into a tool call. However, the `FunctionInvocationContext` object itself does not expose role-based or per-tool permission scopes — permissions are enforced at the pipeline boundary (approval flow + argument allowlist), not on the context API.

## Architectural Decisions

- **A single context object per call.** The framework chose one `FunctionInvocationContext` class with a typed shape (`function`, `arguments`, `session`, `metadata`, `result`, `kwargs`, `tools`) instead of a fluent builder, a DI container, or per-dep objects. This trades flexibility for a small surface area that is easy to inspect and to mock (`tests/core/test_middleware.py:75-95`, `tests/core/test_middleware_context_result.py`).
- **Opt-in injection, validated at decoration time.** Instead of always injecting something, the framework inspects the wrapped function once and refuses ambiguous shapes: multiple `FunctionInvocationContext` parameters raise `ValueError` at construction (`_tools.py:429`; `test_tools.py:1067-1075`); mixing implicit `ctx` and typed `runtime: FunctionInvocationContext` raises the same error (`test_tools.py:1077-1088`). Schema generation skips the ctx parameter (`_tools.py:509-512`), so model-visible prompts never expose it.
- **Rejection of untyped `**kwargs` smuggling.** `FunctionTool.invoke` raises `TypeError` for any kwarg not declared in the schema (`_tools.py:633-640`), which forces every runtime dependency through either a real parameter or the context object. Tests (`test_tools.py:614-629, 934-966`) pin this behavior.
- **Live tool list shared between model and runtime.** `FunctionInvocationLayer.get_response` puts the per-run tool list on `ChatOptions` (`_tools.py:2549-2550`) and the same list object on `FunctionInvocationContext.tools` (`_tools.py:1690`), so `add_tools` / `remove_tools` (`_middleware.py:287-370`) takes effect on the next iteration automatically without bookkeeping.
- **`FunctionInvocationConfiguration` is a TypedDict, not a class.** Configuration passes through `normalize_function_invocation_configuration` (`_tools.py:1401-1421`) which validates constraints (`>=1`, `>=0`) on every read. The per-call budget state (`attempt_count`, `total_function_calls`) rides on a private kwargs key (`_FUNCTION_INVOCATION_BUDGET_STATE_KEY`, `_tools.py:95, 2504-2507`) so the loop survives across iterations and into streamed variants.
- **MCP argument allowlist + denylist over framework kwargs.** `_MCP_FRAMEWORK_DENYLIST` (`_mcp.py:88-98`) is a safety net for declared-but-internal names; `_prepare_call_kwargs` (`_mcp.py:1745-1791`) is the runtime filter. `additional_tool_argument_names` is **configuration only** (no per-call override), so the model cannot widen the allowlist at invocation time (`_mcp.py:1767-1769`).
- **SecretString via inheritance, not secret-aware typing.** `SecretString` is a `str` subclass with a custom `__repr__` (`_settings.py:52-82`). The framework chose simplicity over type-system checks: any code path that reads `str(api_key)` still exposes the value; only accidental `repr()` / `print(api_key)` are masked. This is consistent with Pydantic's `SecretStr` ergonomics.
- **Telemetry is redacted by default-off.** `OBSERVABILITY_SETTINGS.SENSITIVE_DATA_ENABLED` is the gate for whether arguments and results land on spans (`_tools.py:733-735, 758-761, 771-774`). The default is off, so secrets in tool calls are not emitted unless the operator actively enables it (`observability.py:1146-1165`).

## Notable Patterns

- **`@tool` decorator with signature-driven schema + context discovery.** `_tools.py:1148-1338` builds a `FunctionTool`, which inspects the function signature in `__init__` (`_tools.py:382-397, 411-436`) and produces a Pydantic `input_model` from it (`_tools.py:484-514`). The same `inspect.get_type_hints(..., include_extras=True)` call also resolves `Annotated[T, "..."]` descriptions into Pydantic `Field(description=...)` while preserving `Literal[...]` types.
- **Descriptor for bound methods.** `FunctionTool.__get__` (`_tools.py:453-482`) supports methods (first param `self`) as tools, returning a *copy* with `_instance` set so `__call__` can dispatch as `func(self._instance, *args, **kwargs)` (`_tools.py:538-539`). This lets users write class-based agents whose methods are exposed to the model without per-method glue.
- **Pipeline as nested `call_next`.** `BaseMiddlewarePipeline` subclasses (`AgentMiddlewarePipeline`, `FunctionMiddlewarePipeline`, `ChatMiddlewarePipeline` — `_middleware.py:843-1092`) build a recursive chain of closures that share one mutable context. The cleanest implementation is `FunctionMiddlewarePipeline.execute` (`_middleware.py:963-1000`): if no middleware, the final handler is called directly; otherwise each middleware's `await call_next()` invokes the next link.
- **Decorator-based middleware typing.** `@agent_middleware`, `@function_middleware`, `@chat_middleware` (`_middleware.py:678-774`) attach a `_middleware_type: MiddlewareType` marker; `categorize_middleware` (`_middleware.py:1513-1556`) routes based on the marker (or falls back to parameter-type inspection at `_middleware.py:1438-1504`) so a single `Agent.middleware=[fn1, mw2, mw3]` works without manual classification.
- **Progressive tool exposure with atomicity.** `add_tools` validates the merged batch against a throwaway copy first, then mutates `self.tools[:] = merged` (`_middleware.py:321-322`). A duplicate name with a different object raises `ValueError`; same object is a no-op.
- **`INJECTABLE` set as a serialization-side DI contract.** `SerializationMixin.INJECTABLE` (`_serialization.py:268`) is declared at class-level. `to_dict` automatically excludes those fields (`_serialization.py:313`); `from_dict(..., dependencies=...)` requires callers to supply them or raise clear errors (`_serialization.py:532-552`). `FunctionTool.INJECTABLE = {"func"}` (`_tools.py:290-299`) is the canonical example.
- **MCP ContextVar for per-call headers.** `_mcp_call_headers = ContextVar("_mcp_call_headers")` (`_mcp.py:99`) is set in `MCPStreamableHTTPTool.call_tool` (`_mcp.py:2724-2731`), read by the httpx `event_hooks["request"]` callback (`_mcp.py:2691-2699`), and reset in `finally`. The `header_provider` callable is **the canonical DI hook** for runtime auth metadata reaching the wire.
- **`SessionContext` as a per-invocation scratchpad.** `_sessions.py:154-219` is the analog of `FunctionInvocationContext` for the broader agent invocation: holds `session_id`, `service_session_id`, `input_messages`, `context_messages` (per source), `instructions`, `tools`, `middleware`, `metadata`, with serializable `_response`. The two context objects are intentionally distinct (per-call vs per-invocation).
- **Harness-aware factory as the "batteries included" DI root.** `create_harness_agent` (`_harness/_agent.py:238-525`) takes per-feature flags that switch providers in/out (`disable_todo`, `disable_file_memory`, `file_memory_store=...`, `disable_web_search`, `disable_tool_auto_approval`, `auto_approval_rules=...`) — a Pythonic equivalent of `.NET`'s `HostedAgentBuilder` factory chain.

## Tradeoffs

- **Strict schema enforcement vs. flexibility.** `invoke()` rejecting every kwarg not in the schema (`_tools.py:633-640`) keeps telemetry deterministic and prevents accidental info-leak, but it also forces tools that need any runtime object (config, secrets, clients) to declare it via the context — even tiny helpers. Adding a new runtime dependency is a one-line schema annotation plus an explicit handler.
- **Single context object vs. scoped DI.** Using one `FunctionInvocationContext` per call keeps the surface small and mockable, but it cannot model multiple scopes (e.g., per-tenant vs per-session) without shoehorning them into `kwargs`. Users with multi-tenant requirements have to wrap themselves (`session.state["tenant"] = ...`) rather than rely on a built-in container.
- **Opt-in vs. always inject.** Not auto-injecting context means vanilla `@tool def foo(x)` tools cannot read session or runtime kwargs. Tests demonstrate this is intentional (`test_agents.py:1720-1755`). The cost: discoverability — users have to know the `FunctionInvocationContext` parameter exists.
- **`INJECTABLE` is a serialization-side override.** The framework hides fields from `to_dict()` based on a per-class `INJECTABLE` set. This is powerful but coupled: changing the set changes what's persisted, with no explicit "do not serialize" call site in the user code. Tests (`test_serializable_mixin.py:33-167`) cover the behavior; documentation in code stringifies the contract (`_serialization.py:160-265, 390-509`).
- **MCP denylist over typed interface.** `_MCP_FRAMEWORK_DENYLIST` (`_mcp.py:88-98`) is a stringly-typed safety net. New framework-internal kwarg names (e.g., a future `*_endpoint` setting) must be added to the denylist by hand. There is no schema-level enforcement; the comment block at `_mcp.py:77-87` is the only documentation that names which keys are protected.
- **Telemetry sensitivity gate, not scrubber.** `OBSERVABILITY_SETTINGS.SENSITIVE_DATA_ENABLED` is binary and global (`observability.py:1146-1165`). It cannot be set per-call or per-tool. Tools that need to log sensitive intermediate results have to wait for the global toggle or skip logging via custom formatters.

## Failure Modes / Edge Cases

- **Multiple typed context parameters** — `@tool` raises `ValueError` with message `"Function '{name}' defines multiple FunctionInvocationContext parameters."` so users get a clear construction-time error rather than silent last-wins dispatch (`_tools.py:428-430`; `test_tools.py:1067-1075`).
- **Implicit `ctx` + typed context** — `test_tools.py:1077-1088` asserts `ValueError` when both forms are present.
- **PEP 563 (stringified annotations)** — resolved correctly via `typing.get_type_hints(..., include_extras=True)` (`_tools.py:498-501`); covered by `test_tools_future_annotations.py` (entire file).
- **`add_tools`/`remove_tools` outside a function-calling loop** — `RuntimeError("Cannot add tools: this FunctionInvocationContext is not bound to a live agent run. add_tools is only available for functions invoked within an agent's function-calling loop.")` (`_middleware.py:312-317, 345-350`).
- **Duplicate tool names** — `_append_unique_tools` raises `ValueError`; covered by `test_tools.py:1167-1295` (group): the test exercises duplicate names across direct construction, `Agent(tools=[...])`, and `Agent.run(tools=[...])` overrides.
- **Tool returned from `_inner_get_response` is not in the live list** — `add_tools` is the only documented way to inject tools mid-run; the model cannot reach a tool that is registered after `get_response` returns. If a tool is added during iteration 1 but the in-flight model call already requested iteration 1's calls, those calls still execute (`_middleware.py:296-297, 333-335`).
- **MCP denylist miss** — if a new framework-internal kwarg name is added without updating `_MCP_FRAMEWORK_DENYLIST`, it could be forwarded to a server. No tests guard against this; only the comment at `_mcp.py:77-87` documents the protected names.
- **MCP `header_provider` not callable** — `MCPStreamableHTTPTool.__init__` accepts `header_provider: Callable[[dict[str, Any]], dict[str, str]] | None`; if the user passes a non-callable, the failure is at call time, not construction. The httpx event hook is only added once (`_mcp.py:2689-2699`), but a guard `if not callable(_provider)` is not present.
- **Telemetry redaction off-by-default** — `SENSITIVE_DATA_ENABLED` defaults to False, so by default tool payloads are not in spans; however, the inverse (operators enabling it accidentally) is not gated by a confirmation step. `ENABLE_SENSITIVE_DATA` env var (`observability.py:1165`) can flip it at startup.
- **Pagination / streaming context reuse** — `FunctionInvocationContext.metadata` is per call, not per agent run; cross-iteration state must be stored in `session.state`, not in `metadata`.
- **Cancellation** — the context carries no cancellation token; an `asyncio.CancelledError` raised inside a tool will bubble through the pipeline but not be observable to middleware via the context. (No `cancel` field in `_middleware.py:204-285`.)
- **`Live tools list shared object** is mutable** — `FunctionInvocationContext.tools` is the same list reference shared with `options["tools"]`. Mutating it from inside a tool must use the `add_tools`/`remove_tools` helpers to keep the allowlist semantics intact (`_middleware.py:312-322, 345-370`). The comment at `_middleware.py:218-224` is the API contract.
- **`FunctionInvocationConfiguration` bounds best-effort** — `max_function_calls` is checked *after* the current batch completes (`_tools.py:2636-2644, 2806-2816`); a model that requests 20 parallel calls with `max_function_calls=10` will execute all 20 before stopping.

## Future Considerations

- **Per-tool logger injection.** Logger is currently global (`_tools.py:87`). Adopting a `function_invocation_logger_factory` parallel to `header_provider` would let tools emit request-scoped logs without changing every `@tool` body.
- **Cancellation token on context.** Adding `FunctionInvocationContext.cancellation: asyncio.Event | None` (or a `Timeout` instance) would give middleware and tools a uniform cancellation primitive matching `MCPTaskOptions.max_task_wait` semantics (`_mcp.py:283-332`).
- **Typed secret-aware params.** A `Secret[T]` type / `Annotated[Secret, ...]` would let Pydantic schema generation flag secret-bearing parameters explicitly so observability can redact them by default rather than relying on a global toggle. `SecretString` (`_settings.py:52-82`) is already a `str` subclass; one more layer could close the loop.
- **Auto-discover `@tool` extensions** (`_harness/_skill.py`, `_harness/_file_memory.py`) for richer DI surfaces; this is largely already in place via the harness (`_harness/_agent.py:430-525`).
- **Cross-stack parity for `.NET`.** The Python side has a rich context pipeline; the .NET stack relies on `AIFunctionFactory.Create` and Microsoft's hosting extensions (`dotnet/src/Microsoft.Agents.AI.Hosting/HostedAgentBuilderExtensions.cs:87-156`). A documented cross-stack mapping for context/permissions would help operators who maintain both.
- **Per-tool permission scopes.** `approval_mode` is binary (`_tools.py:96`); richer states (e.g., "approve per session", "approve per argument signature") would let `ToolApprovalRule` (`_harness/_tool_approval.py`) drive finer-grained access control without middleware.
- **Schema-driven discovery of provider-bound tests.** Currently, harness tests reuse `MockChatClient` heavily; a fixture for "boot a harness agent in 3 lines" would let new test suites exercise the full factory without copy-paste.

## Questions / Gaps

- **No cancellation or timeout primitive on `FunctionInvocationContext` (and no explicit record of the gap).** Searches across `_middleware.py:204-370` confirm there is no `cancel`/`timeout` field. The `_mcp.py` LRO machinery has its own `MCPTaskOptions.max_task_wait` (`_mcp.py:283-332`) but it does not surface on the context.
- **Logger is module-global**. `logger = logging.getLogger("agent_framework")` at `_tools.py:87`. No way for a tool to receive a request-scoped logger.
- **No DI for the persistence layer (history provider, file store) at the tool level.** `FileMemoryProvider` (`_harness/_file_memory.py`) and `FileAccessProvider` (`_harness/_file_access.py`) hard-code `FileSystemAgentFileStore` rooted at `{cwd}/agent-file-memory` and `{cwd}/working` respectively when no store is supplied. Tool code cannot ask for a different root mid-call without rebuilding the provider.
- **MCP denylist maintenance burden.** `_mcp.py:88-98` enumerates eight names; this is a comment-level invariant. There is no automated test that fails when a new framework kwarg is added without updating the denylist.
- **`header_provider` only on `MCPStreamableHTTPTool`.** Stdio and websocket subclasses do not propagate headers (`_mcp.py:1547-1574, 2734+`). For stdio/websocket transports, auth has to travel another channel (env vars or process stdin).
- **Where do "private" runtime values get hidden from middleware?** `FunctionInvocationContext.kwargs` is reachable by every middleware in the pipeline (`_middleware.py:204-285, 963-1000`). A tool that receives, e.g., an `api_key` via `kwargs` cannot keep it out of an arbitrary `FunctionMiddleware.process`. The MCP denylist addresses this for MCP server calls but not for general middleware.
- **Telemetry gate is global, not per-tool.** `OBSERVABILITY_SETTINGS.SENSITIVE_DATA_ENABLED` is process-wide (`observability.py:1146-1165`). Per-tool redaction would need either a new `FunctionInvocationContext.redact_args: bool` or a per-tool decorator (`@tool(redact_in_telemetry=True)`).
