## Summary

agent-framework's timeouts and cancellation model is **scoped per surface rather than global**: it has structured bounds for the model-call loop (`max_iterations`, `max_function_calls`, `max_consecutive_errors_per_request` on a `FunctionInvocationConfiguration`), structured deadlines for the optional MCP long-running-task lifecycle (`MCPTaskOptions.max_task_wait`, `default_ttl`, `cancel_remote_task_on_local_cancellation`), a path-aware wall-clock bound for the optional local shell subprocess (`run_stateless(..., timeout=...)`), a wall-clock bound for the harness regex search (`_SEARCH_TIMEOUT_SECONDS`), and HTTP-layer timeouts for the OpenAI SDK (`RawOpenAIChatClient(... timeout=...)` / `RawOpenAIChatCompletionClient(... timeout=...)`). Cancellation is cooperative: `asyncio.CancelledError` propagates through the model loop, the parallel tool batch, the MCP lifecycle, the background-task lifecycle, and the workflow runner — with explicit, instrumented "loud" exits (`MiddlewareFailure`, `_settle_dangling_service_function_calls`, `_MCPTaskAbandoned`) for cases that need to clean up server-side conversation state before bailing. The most mature behaviour concentrates in the MCP long-running-task harness, the local shell executor, and the function-invocation loop's batch cancellation; bare-agent `Agent.run(...)` has no first-class `timeout=` argument — caller cancellation rides standard asyncio (`asyncio.Task.cancel()` against the task wrapping `await agent.run(...)`).

## Rating

**7 / 10** — Clear model for the layers that have it (function-invocation loop, MCP task harness, shell subprocess, regex search, background agent lifecycle, workflow runner) with explicit config keys, tests covering the cap-reached and sibling-cancellation paths, and well-instrumented loud exits (`shutdown_reason="cancelled"` in `_emit_shutdown`, `_settle_dangling_service_function_calls` for service-managed threads). Deductions: there is **no top-level agent-run timeout** — `Agent.run(...)` does not accept a timeout/cancel argument and depends on the caller wrapping it in `asyncio.wait_for(...)` or cancelling the wrapping task; the function-invocation loop's `max_iterations` and `max_function_calls` are **not** time-based (the only "wall-clock" knob in the inner chat layer is the per-client `timeout` forwarded to the OpenAI SDK); and the cooperative-cancellation limitation for synchronous tools running in `asyncio.to_thread` is explicitly documented (`test_failure_with_sync_sibling_discards_late_result` at `python/packages/core/tests/core/test_middleware_with_agent.py:2596-2659`) — workers can complete their side effects after the run has been aborted. No generic `FunctionTool`-level per-tool timeout exists for the bare `@tool`-decorated path.

## Answers to Dimension Questions

1. **Can a tool hang forever?** — Barely, and only in narrow surfaces. The MCP long-running-task layer, the shell subprocess layer, the harness regex search, the OpenAI client, and the background-agents lifecycle all bound wall-clock or budget explicitly. The function-invocation loop in core (the default `Agent` path) has **no** wall-clock tool-budget — only `max_iterations`, `max_function_calls`, and `max_consecutive_errors_per_request`, and a sync tool body inside `asyncio.to_thread` cannot be interrupted (`python/packages/core/agent_framework/_tools.py:1863-1876`, `python/packages/core/tests/core/test_middleware_with_agent.py:2596-2659`). A user `FunctionTool` whose body returns nothing but blocks indefinitely is the documented footgun.
2. **Are timeouts configurable?** — Yes, but the axes are fragmented. Each layer has its own knob: chat-client HTTP layer (`RawOpenAIChatClient(timeout=...)` at `python/packages/openai/agent_framework_openai/_chat_client.py:522`), model loop (`FunctionInvocationConfiguration["max_iterations" / "max_function_calls" / "max_consecutive_errors_per_request"]` at `python/packages/core/agent_framework/_tools.py:1332-1386`), harness outer loop (`AgentLoopMiddleware(..., max_iterations=...)` at `python/packages/core/agent_framework/_harness/_loop.py:269`), MCP HTTP/SSE read (`MCPTool(request_timeout=...)` at `python/packages/core/agent_framework/_mcp.py:454`), MCP long-running-task deadline (`MCPTaskOptions(max_task_wait=...)` at `python/packages/core/agent_framework/_mcp.py:347-380`), shell subprocess (`run_stateless(..., timeout=...)` and `ShellSession.run(command, *, timeout=...)` at `python/packages/tools/agent_framework_tools/shell/_executor.py:72-80` and `_session.py:268-290`), regex search (`_SEARCH_TIMEOUT_SECONDS=10.0` constant at `python/packages/core/agent_framework/_harness/_file_access.py:77`), and background-agents drain (`release_session(..., timeout=30.0)` at `python/packages/core/agent_framework/_harness/_background_agents.py:345-360`). There is **no** per-tool timeout on the generic `@tool`/`FunctionTool` path; users must wrap their body themselves.
3. **Can users cancel?** — Yes. Cooperative cancellation is the dominant mechanism: `Agent.run()` returns an awaitable the caller can wrap with `asyncio.wait_for(...)` or `asyncio.Task.cancel()` (`python/packages/core/agent_framework/_agents.py:1849-1880`), tool batches honour sibling cancellation on `MiddlewareFailure` (`python/packages/core/agent_framework/_tools.py:1863-1876`), the workflow runner cancels its iteration task on outer cancellation (`python/packages/core/agent_framework/_workflows/_runner.py:137-142`), and the background-agent surface exposes explicit `release_session(..., cancel_running=True)` (`python/packages/core/agent_framework/_harness/_background_agents.py:345-360`). The MCP layer augments local cancellation with a best-effort server-side `tasks/cancel` (`_spawn_best_effort_cancel` at `python/packages/core/agent_framework/_mcp.py:2573-2582`).
4. **Is cancellation cooperative or forced?** — Cooperative everywhere. The framework's `MiddlewareFailure` docstring is explicit: *"Cancellation is cooperative: an async sibling stops at its next suspension point, while a synchronous tool body already executing in a worker thread cannot be interrupted and may still complete its side effects — its result is discarded either way"* (`python/packages/core/agent_framework/_middleware.py:93-99`). Even where the framework "forces" cancellation (e.g. `kill_process_tree` at `python/packages/tools/agent_framework_tools/shell/_killtree.py:50-131`), the subtree is signaled first (SIGTERM → SIGKILL) rather than pried open; the worker-thread limitation is the same — the thread runs to completion (`python/packages/core/tests/core/test_middleware_with_agent.py:2596-2659`). Pure cancellation (`CancelledError`) is the loud-control-plane signal; user code that fires `MiddlewareFailure` is the loud-abort signal.
5. **Does cancellation leave resources dirty?** — Generally no, but with documented caveats. The loud-escape path explicitly settles a service-managed conversation before propagating so the hosted thread does not contain dangling tool calls (`_settle_dangling_service_function_calls` at `python/packages/core/agent_framework/_tools.py:3082-3157` and the catch blocks at `:3275-3290`, `:3457-3471`); `agent-hooks` always emits `agent_shutdown(reason="cancelled")` via `_emit_shutdown` even when a tool aborts mid-loop (`python/packages/core/agent_framework/_agent_hooks.py:1097-1107`); `ShellSession.close()` is graceful→`kill_process_tree` and `_reader` tasks are awaited (`python/packages/tools/agent_framework_tools/shell/_session.py:151-185`); MCP closes the lifecycle queue and tracks pending reload tasks (`python/packages/core/agent_framework/_mcp.py:1170-1260`); the background-agent drain loop guarantees the bounded deadline (`python/packages/core/agent_framework/_harness/_background_agents.py:401-440`). Caveats: (a) a worker-thread `FunctionTool` may finish its side effect after `MiddlewareFailure`, but its result is discarded (`test_failure_with_sync_sibling_discards_late_result`); (b) a MCP `tasks/cancel` is best-effort and may time out, leaving the remote task potentially still running (`test_call_tool_as_task_max_wait_exceeded_raises_and_cancels`).

## Architectural Decisions

- **Surface-local bounds rather than a single global timeout.** Each subsystem (`FunctionInvocationConfiguration`, `MCPTaskOptions`, `ShellResult.timeout`, `release_session(timeout=...)`, `RawOpenAIChatClient(timeout=...)`, `_SEARCH_TIMEOUT_SECONDS`) owns the kind of bound that makes sense for it (iteration, wall-clock, reconnect timeout, drain deadline). There is no single "agent timeout" — the cost is user-visible fragmentation across ~7 places; the benefit is that the right unit (model roundtrip count vs. HTTP wall-clock vs. process tree lifetime) is the right knob to express.
- **Loud vs. graceful stop are two distinct signals.** `MiddlewareTermination` stops the loop **gracefully**, optionally substituting a result (`python/packages/core/agent_framework/_middleware.py:75-83`). `MiddlewareFailure` is the **fail-closed** abort: siblings are cancelled, the local run raises, and on a service-managed conversation the loop submits a synthetic error `function_result` per dangling call before raising so the hosted thread does not contain unresolved tool calls (`python/packages/core/agent_framework/_tools.py:3082-3157`, `:3275-3290`). The split is enforced — middleware that swallows `MiddlewareFailure` is documented as *converting a fail-closed abort back into a running loop* (`python/packages/core/agent_framework/_middleware.py:117-118`).
- **Service-thread settlement is owned by the framework, not the caller.** When a `MiddlewareFailure` aborts mid-batch against a service-managed conversation, `_settle_dangling_service_function_calls` is invoked with `tool_choice="none"` and a synthetic error per call (`python/packages/core/agent_framework/_tools.py:3082-3157`). The settlement response becomes the next continuation endpoint on response-ID runs; the abort still propagates. The trade-off is one extra request on the failure path; the benefit is that the *next* run does not start on a poisoned thread.
- **MCP long-running-task lifecycle is owned by the framework via SEP-2663.** `MCPTaskOptions` is a frozen dataclass with three fields (`default_ttl`, `cancel_remote_task_on_local_cancellation`, `max_task_wait`), with abandonment paths `tasks/cancel`ing server-side regardless of the local-cancel flag (`python/packages/core/agent_framework/_mcp.py:346-380`, comment at `:366-376`). The framework distinguishes *abandonment* (remote task may still be running) from *terminal failure* (server already done) via `_MCPTaskAbandoned`, which the loop catches and re-raises as `ToolExecutionException` (`python/packages/core/agent_framework/_mcp.py:335-340`, `:2303-2308`).
- **Submit-vs-track reconnect policy.** A dropped MCP connection before a `task_id` is known raises `ToolExecutionException("connection lost; task state unknown")` without re-issuing the augmented `tools/call`, so the server cannot be made to start the same side-effecting operation twice (`python/packages/core/agent_framework/_mcp.py:2530-2546`). Once a `task_id` exists, `tasks/get`/`tasks/result` reconnect once and retry against the same id.
- **`asyncio.CancelledError` provenance.** On Python ≥ 3.11 the framework uses `task.cancelling() > 0` to distinguish caller-driven cancellation from library-internal `CancelledError` raised inside anyio cancel scopes (`_should_propagate_cancelled_error` at `python/packages/core/agent_framework/_mcp.py:405-418`); on older Pythons it always converts to `ToolExecutionException`. Same predicate applied per call site via `_close_and_check_cancelled(ex)` (`:1261-1270`).
- **Shell subprocess timeout is enforced with a killtree, not a force-kill.** `kill_process_tree` first SIGTERMs the parent's children and a process group then SIGKILLs (`python/packages/tools/agent_framework_tools/shell/_killtree.py:50-131`); for persistent shells the timeout signal path is `SIGINT` (POSIX) / `CTRL_BREAK_EVENT` (Win32) sent to the shell, with `kill_process_tree` as the fallback (`_session.py:410-419`). The reason is that a partially-killed subprocess leaves grand-children orphaned.
- **Cancellation is always bounded by wall-clock for cleanup paths.** `_drain_runtime` computes `deadline = loop.time() + timeout` and abandons still-pending tasks (`python/packages/core/agent_framework/_harness/_background_agents.py:401-440`); `_MCP_TASK_CANCEL_TIMEOUT = 5s` bounds the fire-and-forget `tasks/cancel` (`python/packages/core/agent_framework/_mcp.py:326`). Even "best-effort" cancellation has a budget.

## Notable Patterns

- **Tri-state action enum** — `_process_function_requests` uses `"return" | "stop" | "continue"` (`python/packages/core/agent_framework/_tools.py:2227-2270`); `"stop"` flips `tool_choice="none"` on the next pass; `"return"` exits the loop; `"continue"` continues. The same pattern is reproduced for streaming (`_stream_response_with_function_invocation`). Tri-state is more compact than a 4-element exception-class ladder and matches the four-state outcomes (finalize, force-text, retry, continue).
- **Service-thread pre-settlement** — `_settle_dangling_service_function_calls` resolves a `MiddlewareFailure`-aborted batch by submitting one error `function_result` per dangling call before re-raising, advancing the persisted continuation to the settlement endpoint (`python/packages/core/agent_framework/_tools.py:3082-3157`). Same hook is re-armed during the approval-resume path via `settle_dangling_calls=settle_approval_replay_calls` (`:3202-3211`, `:3362-3372`).
- **Cancellation provenance via `task.cancelling()`** — `_should_propagate_cancelled_error` (`:405-418`) prevents the framework from being fooled by an inner cancel-scope cancellation; `_close_and_check_cancelled` (`:1261-1270`) wraps `_safe_close_exit_stack` and tells the caller whether to re-raise.
- **`_RunPersistenceGate`** — `_agent_hooks.py` keeps the "transactional" piece of the agent seam; on `CancelledError` the `_emit_shutdown` call in `finally` still fires, so the session trail is closed cleanly even if the persistence was deferred through the gate (`shutdown_reason = "cancelled"` at `_agent_hooks.py:1097-1107`).
- **Budget state on the loop entry** — `_resolve_approval_responses` and `_process_model_function_calls` each advance `attempt_count` and `total_function_calls` in `budget_state`, which is read back by the parent loop with `attempt_start = int(budget_state.get("attempt_count", 0) or 0)` (`_tools.py:3198-3200`). This lets a restarted run pick up where a previous run left off instead of resetting hard.
- **Force-text fallback after cap** — `_FUNCTION_INVOCATION_LIMIT_FALLBACK_TEXT` is the canonical "I gave up on tools" sentence injected as a text-only assistant message whenever the budget runs out (`_tools.py:101-104`, `:2013-2036`); this is the user-visible structured result of a budget-based "cancellation".
- **Two-layer cancellation in the harness loop** — `AgentLoopMiddleware` returns immediately if `_has_pending_approval_request(result)` is true (`_harness/_loop.py:447-459`); the only other termination is `should_continue` + `max_iterations`. This means *user-driven* cancellation inside the harness loop is implicit via `should_continue = False`, not via a cancel handle.
- **Periodic event-poll with cooperative iteration cancel** — `WorkflowRunner.run_until_convergence` polls `asyncio.wait_for(self._ctx.next_event(), timeout=0.05)` while the iteration task is in flight, then on outer cancellation cancels and re-awaits the iteration task (`python/packages/core/agent_framework/_workflows/_runner.py:121-142`).

## Tradeoffs

- **Per-surface timeout knobs, not a single `Agent(timeout=)` parameter.** The benefit is that each layer uses the right unit (wall-clock vs. iter count vs. cumulative tool count); the cost is that a user has to learn ~7 configuration surfaces to bound a single agent. **Evidence**: configuration entry points at `_tools.py:1373-1377`, `_harness/_loop.py:269`, `_mcp.py:347-380, 454`, `_chat_client.py:522`, `_shell/_executor.py:72`, `_file_access.py:77`, `_background_agents.py:350`.
- **Worker-thread `FunctionTool` cannot be cancelled.** A synchronous body wrapped by `asyncio.to_thread(...)` keeps running after `MiddlewareFailure`; the result is discarded but the side effects happen. This is **explicitly documented** as a limitation in the `MiddlewareFailure` docstring (`_middleware.py:93-99`) and is verified by `test_failure_with_sync_sibling_discards_late_result` (`test_middleware_with_agent.py:2596-2659`). Mitigations available to user code: wrap the body in a worker-thread cancellation primitive, or use `async def` so the tool body is interruptible at suspension points.
- **No top-level `cancel_token=` argument on `Agent.run`.** Cancellation rides `asyncio.Task.cancel()` against a wrapper task; `asyncio.wait_for(...)` causes `TimeoutError` (not `CancelledError`) and only "cancelled" reason is wired (`_agent_hooks.py:1097-1098`). **No clear evidence found** for a typed `agent.cancel()` or `token=` parameter.
- **`_MCP_TASK_MIN_POLL_INTERVAL` / `_MCP_TASK_MAX_POLL_INTERVAL` are module constants, not user-tunable.** Comment at `_mcp.py:322-326`: "Internal polling bounds for MCP long-running tasks. Not user-tunable today; promote to MCPTaskOptions if a concrete need arises." A user with a slow MCP server cannot increase `_MCP_TASK_MAX_POLL_INTERVAL` without a runtime patch.
- **`max_function_calls` is best-effort across parallel batches.** The docstring explicitly notes "checked *after* each batch of parallel tool calls completes, not before. If the model requests 20 parallel calls in a single iteration and the limit is 10, all 20 will execute before the loop stops" (`_tools.py:1348-1351`). Hard caps require a per-tool counter, which the framework does not have today.
- **`max_iterations` is iteration-bound, not time-bound.** A slow provider can stall iteration `attempt_idx` indefinitely; the only wall-clock cap is the inner `timeout=` forwarded by the chat client (`RawOpenAIChatClient(timeout=...)`). For a generic `Agent` running against a provider that has not been configured with a timeout, the loop can be stuck on a single model call for the provider's TCP-stack timeout duration.
- **Default `release_session` timeout = 30 s, not configurable per session.** `_drain_runtime`'s `timeout=` parameter is `30.0` by default (`_background_agents.py:350`); a user wanting a longer drain for many children has to wrap `release_session` themselves.
- **`dotnet/` side uses `CancellationToken` pervasively** (2984 occurrences in `dotnet/src`), but this study focuses on Python; the two surfaces have similar shape but use different primitives.

## Failure Modes / Edge Cases

- **Orphan tool call after `MiddlewareFailure`** — Mitigated by `_settle_dangling_service_function_calls` for service-managed conversations (`_tools.py:3082-3157`). For local `BaseChatClient` clients, the batch is just abandoned, the caller's `MiddlewareFailure` propagates, and history providers see whatever `Attempted_run`-scoped persistence was set.
- **Sync `FunctionTool` completes after `MiddlewareFailure`** — Documented limitation; result is discarded (`_middleware.py:93-99`, `test_middleware_with_agent.py:2596-2659`). The only mitigation is `async def`.
- **`tool_choice == "required"` would loop forever** — Mitigated by `_reset_required_tool_choice(options)` after every iteration (`_tools.py:3304, 3486`). Comment in the loop body: "checked after each batch of parallel calls completes, so the current batch always runs to completion even if it overshoots" (`_tools.py:2637-2638`).
- **MCP `tasks/cancel` server-side silent** — `_spawn_best_effort_cancel` is fire-and-forget; if it times out (`_MCP_TASK_CANCEL_TIMEOUT=5s`) or fails, a warning is logged but the local `ToolExecutionException` is still raised (`_mcp.py:2599-2605`). The remote task may continue to run; cancellation is best-effort by design.
- **MCP connection lost after `task_id` known** — `_send_with_one_reconnect` issues one reconnect per send (`_mcp.py:2530-2546`); a second disconnect raises `_MCPTaskAbandoned` → `tasks/cancel` → re-raise.
- **Worker-thread runaway regex** — `_run_search_with_timeout` raises `ValueError` after `_SEARCH_TIMEOUT_SECONDS=10.0s`; the regex itself keeps running on the thread. The framework accepts this — "the caller and event loop stay responsive" — and surfaces the failure as a `ValueError` to the calling model (`_file_access.py:73-75`, `:117-125`).
- **Background-task released while running** — `release_session(..., cancel_running=False, ...)` raises `RuntimeError("Cannot release session {id}: {n} tasks still running")` rather than silently releasing (`_background_agents.py:369-370`). The default is `cancel_running=True`.
- **Orphan task ignores cancel** — `_drain_runtime` logs "Session release timed out before all tasks finished. Abandoning N task(s)" and stops awaiting (`_background_agents.py:423-430`). Tested by `test_release_session_times_out_if_task_ignores_cancellation`.
- **MCP `CancelledError` inside an anyio cancel-scope** — `_should_propagate_cancelled_error` returns `False` for that case; the framework treats the `asyncio.CancelledError` as a transport cleanup error and converts to `ToolExecutionException` (`_mcp.py:405-418`).
- **Workflow idle cancellation** — `WorkflowRunner.run_until_convergence` polls `next_event()` with `asyncio.wait_for(..., timeout=0.05)`; on outer cancellation, the iteration task is cancelled and awaited with cancellation suppression (`_workflows/_runner.py:127-142`).
- **Streaming `ChatResponseUpdate` emitted after cap** — Stripped by `_drop_unexecutable_tool_contents_from_update` so a tool-only delta after the cap becomes a no-op (`_tools.py:3418-3422`).
- **`agent_shutdown(reason="cancelled")` only on per-run sessions** — `_emit_shutdown` is "best-effort, per-run sessions only; blocks there are record-only" (`_agent_hooks.py:1031-1042`). A session-scoped cancel route does not emit the record-trail event.

## Future Considerations

- **First-class `Agent.run(timeout=...)` / `cancel_token=...` argument.** Currently the only way to bound `agent.run` is `asyncio.wait_for(...)` (`_agents.py:1849-1880`); a `timeout=` argument that interacts with `_emit_shutdown` (e.g. adding a `"timeout"` reason alongside `"cancelled"`) would close this gap. Today `agent-hooks` only knows `"completed" / "error" / "cancelled"` (`_agent_hooks.py:1097-1107`).
- **Promote `_MCP_TASK_MIN_POLL_INTERVAL` / `_MCP_TASK_MAX_POLL_INTERVAL` into `MCPTaskOptions`.** Comment at `_mcp.py:322-326` explicitly defers this until the need is concrete; a slow MCP server would benefit.
- **Per-tool timeout on the generic `FunctionTool` path.** The `@tool`/`FunctionTool` path has no per-call wall-clock budget; users must wrap their body themselves. A `timeout=` argument on `@tool` that mirrors `asyncio.wait_for(...)` semantics (with cooperative cancellation, and a `MiddlewareFailure` on hard timeout) would close the gap.
- **Hard cap on `max_function_calls` across parallel batches.** Today the loop checks `_function_call_limit_reached` only after a batch completes (`_tools.py:1348-1351`). Per-call counters would let the loop enforce a hard wall.
- **`_drain_runtime(timeout=...)` default → per-session config.** Today the 30 s default is the only knob (`_background_agents.py:350`); a multi-task fast cleanup vs. a long-tail cleanup are not distinguished.
- **Cancellation reason taxonomy extension** — Add `"timeout"` alongside `"cancelled"` so wrapped `asyncio.wait_for(...)` runs are observable in the record trail (`_agent_hooks.py:1097-1098`). Today the host has to inspect `asyncio.TimeoutError` separately.
- **Cancellation API for streaming `Agent.run`** — A returned `ResponseStream` does not expose `cancel()`; outer cancellation requires wrapping the iterator in `asyncio.wait_for(...)`, which loses the cooperative sibling-cancel benefits provided to the inner batch.
- **`MCPTaskOptions.cancel_remote_task_on_local_cancellation = False` semantics** — The flag is named "local" but today only gates `CancelledError`; abandonment paths always cancel regardless (`_mcp.py:366-376`). Renaming to `cancel_remote_task_on_local_cancellation_or_abandonment` would be more honest.
